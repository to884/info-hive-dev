# データプラットフォームからエージェントが機能するアーキテクチャへ: Knowledge Catalog、Ossie、GenAI

[Ahmet Kalafat](https://medium.com/@ahmet.kalafat?source=post_page---byline--bc212259184f------------------------------------------)

読了時間 8 分、2026年11月1日

ここ数週間にデータと GenAI の世界で発表された内容をまとめて見ると、データアーキテクチャが責任を負う範囲が広がっていると感じる。

データを集め、変換し、クエリできる状態にすることは、今も私たちの中心的な仕事である。そこに新しい問いが加わる。

AI エージェントは、どの指標を使うべきかをどうやって知るのか。正しいテーブルと join の関係をどうやって見つけるのか。使っているビジネス定義が最新であることを、どうやって確かめるのか。データにアクセスしたあと、どのような操作を実行できるのか。

Google Knowledge Catalog、Apache Ossie、Dataflow、GPT‑6.1 Terra、プラットフォーム間のクエリに関する動きを、これらの問いを軸に評価したい。関連する節では、Microsoft Azure、Fabric、Purview 側の似た機能にも触れる。

## 1. セマンティックモデルが AI エージェントの共通の参照元になりつつある

Google が **2026年10月30日** に発表した Knowledge Catalog の拡張は、Looker LookML、dbt MetricFlow、Snowflake Semantic Views、Databricks Metric Views、BigQuery Graph、SAP CSN などのソースにあるセマンティック定義を、共通のコンテキストグラフにまとめる。

ここでの価値は、カタログで指標の名前を見つけられるという点にとどまらない。指標の計算式、フィルター、join の関係、元のテーブル、lineage、データ品質のシグナルをまとめて評価できる。

たとえば、ユーザーが **「先月の純売上はいくらだったか」** と尋ねたとき、SQL を生成できるだけでは足りない。

![](https://miro.medium.com/v2/resize:fit:1225/1*RWIfAabJPV6smUEOO-sYQA.jpeg)（未取得）

図 2. 同じ質問でも、コンテキストが違う。概念を示した図であり、測定した性能の結果ではない。

返品はどの日付を基準に差し引くのか。キャンセルされた注文は除外するのか。どの為替レートを使うのか。財務部門と営業部門で、純売上の定義は同じか。使うテーブルの grain と鮮度は、この質問に適しているか。

![](https://miro.medium.com/v2/resize:fit:1225/1*fMZEYSDOfYRerjzItFsfng.jpeg)（未取得）

図 3. 純売上の質問の裏にある問いと、それぞれに必要なビジネスコンテキスト。

これらの問いの答えは、多くの組織にすでにある。ただし、さまざまなモデル、レポート、ドキュメント、人々の頭の中に散らばっている。

Knowledge Catalog は、これらの定義を元のソースと関連づけ、エージェントが使える構造で提示する。異なるシステムの間で定義が食い違う場合も、ソースとともに見える形にする。どの定義をどの目的で使うかを決める責任は、引き続き組織にある。

**エージェントが正しい SQL を生成することと同じくらい、正しいビジネス定義を選ぶことが重要である。**

## Apache Ossie はこの全体像のどこにあるのか

Apache Ossie は、指標、ディメンション、リレーションシップ、ビジネス上の意味をツール間で共有するための、オープンでベンダーに依存しないセマンティックメタデータの標準を開発している。プロジェクトは Apache Incubator の段階にある。

2 つのアプローチが焦点を当てる問いは異なる。

- **Apache Ossie:** ビジネス定義を、異なるプラットフォーム間でどの共通フォーマットにより共有できるか。
- **Knowledge Catalog:** 既存の定義をどのように発見して関連づけ、AI エージェントに信頼できるコンテキストとして提供するか。

Ossie はセマンティック定義の可搬性と相互運用性に焦点を当てている。Knowledge Catalog は、これらの定義をカタログ、lineage、品質、その他の組織の情報と関連づける。

![](https://miro.medium.com/v2/resize:fit:1225/1*0lwVoLxp_A3V9ekYHYwHFA.jpeg)（未取得）

図 4. Apache Ossie と Knowledge Catalog: 同じ全体像の、2 つの異なる層。

このため、アーキテクチャとしては互いに補完し合える可能性があると考える。ただし、Google の該当する発表には Ossie への直接の対応が挙げられていない。この関係を、現時点で用意された製品の統合として評価すべきではない。

共通のフォーマットを使っても、組織内の定義の違いが自然に解消されるわけではない。「純売上」の 2 つの異なる計算式を、同じ標準で表現することは可能である。どちらがどの文脈で有効かを決めることは、依然としてデータモデリングとガバナンスの仕事である。

## Microsoft 側の対応するもの

最も近い機能上の対応は、**Fabric IQ、Power BI のセマンティックモデル、Microsoft Purview** をあわせて見たときに現れる。

Fabric IQ は、ビジネスのエンティティとその関係を通じて、エージェントにコンテキストを提供する。Power BI のセマンティックモデルは、メジャー、階層、分析上の定義を持つ。Purview は、カタログ、lineage、データ品質の面を担う。

このため、Knowledge Catalog を Purview だけと比較すると、セマンティックモデルとエージェントのコンテキストの側が抜け落ちる。

## 2. コンテキストにもライフサイクルがある

Google が **2026年10月22日** に Preview として発表した self-learning context enrichment と Knowledge Studio は、カタログの保守に新しい機能を加える。

このシステムは、ユーザーとエージェントのやり取りから、欠けているコンテキストや古くなったコンテキストを特定し、ドキュメントやコードリポジトリを活用して修正案を作ることを目指している。提案は、ソースと信頼度スコアとともに確認できる。

ここで私が注目するのは、**エージェントの誤りをデータアーキテクチャにフィードバックできる**という点である。

エージェントが繰り返し誤ったテーブルに向かうなら、関係の欠落、あいまいな指標定義、古い説明などが原因かもしれない。

このような場合、次のループが意味を持つ。

**やり取りを観察する → 欠けているコンテキストを特定する → 修正を提案する → 検証する → 公開する → 再び測定する。**

![](https://miro.medium.com/v2/resize:fit:1225/1*FmULDrTyvfjEaFFMVOa8Bg.jpeg)（未取得）

このアプローチは、コンテキストの管理を、テストでき追跡できるエンジニアリングのプロセスに変える。

## Google が共有したベンチマーク結果

Google は、Knowledge Catalog で支援したエージェントについて、社内のベンチマークで次の改善を報告している。

- **精度:** 約 4 倍。
- **レイテンシ:** 最大 33% 減。
- **トークン使用量:** 最大 75% 減。

![](https://miro.medium.com/v2/resize:fit:1225/1*jFxbkgIEFCufiS43nLesAg.jpeg)（未取得）

図 6. Google が報告した社内ベンチマークの結果。独立したテストではない。

これらの数値は、Google の **2026年10月22日** の発表にある社内の結果である。独立したテストや、Azure との直接の性能比較として読むべきではない。各測定の出発点と評価方法も重要であり、これらの割合を 1 つの総合的な性能スコアにまとめることはできない。

自分たちの環境で結果を左右するのは、実際のビジネスの質問、現在のモデルの品質、そして評価の方法である。

私がこのような試行をするなら、同じ質問セットを 2 つの構成で実行したい。テーブルスキーマだけを与えたエージェントと、検証済みのセマンティックコンテキストで支援したエージェントである。そのうえで、回答の精度、正しいソースの選択、レイテンシ、合計のトークン消費量を別々に測定する。

## Microsoft 側の対応するもの

**Fabric IQ Ontology Agent — Preview** は、自然言語でオントロジーを作成し、発展させる作業を支援する。Purview 側にも、AI を使ったデータプロファイリングと、品質ルールの提案がある。

これらは似た保守の必要に対応している。ただし、Google のユーザーとエージェントのやり取りからコンテキストを継続的に更新するアプローチと、範囲がまったく同じというわけではない。

比較では、「AI 支援」という表現よりも、どの入力が使われるか、どの変更が提案されるか、承認のプロセス、結果がどう測定されるかを見る必要がある。

## 3. Dataflow でレイテンシとコストの目標をより明示的に管理する

GenAI アプリケーションにデータを供給するデータフローの運用品質は、今も重要である。

Dataflow の **2026年10月29日** の更新で、Streaming Engine のジョブ向けに、レイテンシレベルと繰り返しの autoscaling スケジュールが発表された。

**low_latency、medium_latency、high_latency** のオプションは、autoscaler が backlog の時間にどれだけ敏感に反応するかを設定する。スケジュールにより、ワーカー数の最小値と最大値、ワーカーの使用率の目標、レイテンシレベルなどのパラメーターを、特定の時間帯に変更できる。

これらのレベルは、エンドツーエンドのレイテンシの保証としてではなく、スケーリングの挙動を制御する設定として評価すべきである。

小売では、キャンペーンの開始、店舗のオープン、夜間に動く連携が、異なるトラフィックのプロファイルを作りうる。キャパシティの管理がこのリズムを反映することには価値がある。

Kafka → BigQuery のようなフローでは、次の 3 つの測定をあわせて監視したい。

- **エンドツーエンドの p95 レイテンシ:** データの大部分が使える状態になるまで、どれくらいかかるか。
- **backlog の解消時間:** トラフィックが増えたあと、システムはどれだけ速く回復するか。
- **処理したデータあたりのコスト:** 提供されたサービスレベルにいくらかかるか。

![](https://miro.medium.com/v2/resize:fit:1225/1*ZUdPKulC8HIcpkzNSb7LhQ.jpeg)（未取得）

図 8. Kafka から BigQuery へのフローで監視する 3 つの測定。

また、**2026年10月21日** に Preview として発表された streaming high availability は、Streaming Engine の状態を同じリージョン内の複数のゾーンに複製することを目指している。

ここでは、複数ゾーンの耐障害性と、リージョン間のディザスタリカバリを、別々の要件として扱う必要がある。

## Azure 側の対応するもの

**Azure Stream Analytics の custom autoscale** は、使用率のしきい値と稼働時間に基づいて、streaming unit のキャパシティを変更できる。

たとえば、勤務時間中はより多く、それ以外の時間はより少ないキャパシティを使える。これは似た運用上の必要に対応するが、Dataflow のレイテンシレベルと同じ制御モデルを使うわけではない。

Dataflow の batch と streaming をあわせた範囲を、Stream Analytics だけと同一視することも避けるべきである。ここでの比較は、streaming のキャパシティの自動管理という観点で行うべきである。

## 4. GPT‑6.1 Terra: データを理解することから、アプリケーションで操作することへ

OpenAI が **2026年10月26日** に発表した GPT‑6.1 Terra は、視覚的な理解、コンピューター操作、複数ステップのタスクの実行に焦点を当てている。

データエンジニアリングの観点では、これに対応するものは、ブラウザで動くポータル、ファイルのダウンロードの工程、画面からの情報収集、アプリケーション間での操作の実行といった領域に見られるだろう。

多くの組織では、データフローは API だけで成り立っていない。人がレポートをダウンロードし、フォームに入力し、ファイルを転送するアプリケーションも、これらのフローの一部である。

コンピューターを使えるモデルは、これらの工程の一部を自動化の対象にすることを可能にするかもしれない。

そのようなソリューションを評価するとき、私にとって目立つ測定は次のとおりである。

- タスクを正しく完了する割合。
- 人の介入が必要になる度合い。
- エラー後の回復。
- 成功した操作あたりのコスト。

権限の範囲、操作の記録、結果の検証も、本番のアーキテクチャの一部であるべきである。

## Azure 側の対応するもの

Microsoft Foundry Agent Service 側には、**Computer Use — Preview** の機能がある。エージェントが視覚的な内容を活用して、デスクトップとブラウザのインターフェイス上で操作を実行できるようにする。

ここでの比較は、コンピューター使用の機能という観点で行うべきである。これは、GPT‑6.1 Terra モデルが Azure で同じように提供されるという意味ではない。

## 5. BigQuery から、異なるプラットフォームにあるデータへアクセスする

Google の **2026年10月13日** の技術ガイドは、Iceberg REST カタログを通じて、Databricks、Snowflake、AWS Glue 側の適したテーブルを BigQuery からクエリし、1 つのクエリで結合する方法を示している。

同じ例は、結合したデータに対する自然言語での分析も扱っている。

![](https://miro.medium.com/v2/resize:fit:1225/1*abM4IsG7W9swsdHk06JntA.jpeg)（未取得）

図 10. BigQuery から Iceberg REST カタログを通じて、異なるプラットフォームのデータにアクセスする。

このアプローチは、分析のニーズごとに、すべてのデータをまず 1 つのプラットフォームに移す必要があるのかを、見直す機会を与える。ただし、実現できるかどうかは、テーブルのフォーマット、カタログのサポート、権限、リージョンの選択肢、ネットワークの条件に左右される。

データをその場でクエリすることも、コストなしでアクセスできることを意味しない。クラウド間のデータ転送、cache の挙動、メタデータの更新間隔、データの所在に関する要件を、あわせて検討する必要がある。

## Microsoft 側の対応するもの

**Fabric OneLake Shortcuts とメタデータ mirroring** は、サポートされるソースにあるデータを、共通のアクセス構造で使える状態にする。

ここで使う方法を区別する必要がある。

- **OneLake Shortcuts:** ソースにあるデータを参照する。データはその場に残る。
- **メタデータ mirroring:** サポートされるソースでカタログ情報を取得し、shortcut を通じてデータにアクセスする。
- **データのレプリケーションを使う mirroring:** データが OneLake に複製される。

したがって、すべての mirroring のシナリオを「データを移動せずにアクセスする」ものとして評価することはできない。

## データにアクセスすることと、ビジネス上の意味を保つこと

これらの動きは、3 つの別々のアーキテクチャ上の必要に対応している。

**データへのアクセス:** Iceberg、カタログのインターフェイス、フェデレーション、shortcuts は、異なるプラットフォームにあるデータを使える状態にする。

**セマンティックの可搬性:** Apache Ossie のようなオープンな標準は、指標とビジネス定義をプラットフォーム間で共有することを目指している。

**エージェントへの組織のコンテキストの提供:** Knowledge Catalog や Fabric IQ のようなプラットフォームの機能は、定義をデータソースやその他の組織の情報と関連づける。

これらは同じソリューションの別名ではなく、アーキテクチャの中で異なる責任を担うアプローチである。それらの間の関係も、用意された統合がいつもあるという意味ではない。

![](https://miro.medium.com/v2/resize:fit:1225/1*r4YcGSQfvKtGUfQ9H_1ekg.jpeg)（未取得）

## データアーキテクチャの範囲が広がっている

長年、データウェアハウス、BI、データプラットフォームに取り組んできて、繰り返し目にする状況がある。あいまいなビジネス定義、誤った grain、誤った join、オーナー不在の指標が、今も結果に影響を与え続けている。

GenAI は、これらの問題の影響をより目に見えるものにする。エージェントが、新しい質問に答え、アプリケーション上で操作を実行しようとするからである。

このため、物理的なデータ、セマンティック定義、コンテキスト、運用上の挙動を、あわせて設計する必要がある。

私の見方では、これらの発表に共通する価値は、既存のデータアーキテクチャの規律を、エージェントが機能する環境へ持ち込むことにある。成功を決めるのは、これらの機能をどれだけ正しくモデル化し、管理し、測定するかである。

**あなたの組織では、AI エージェントが使う指標定義はどこで管理されていて、それらの定義が最新であることに誰が責任を持っているか。**
