# ADR-0001：127.0.0.1 だけで待ち受けるサーバーは、方針 G の「ホスト型 wiki」に当たらない

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月3日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0002、`info-hive/UPSTREAM.md`、`info-hive/docs/porting-plan.html`（方針 G、Q4） |

## 背景

info-hive は、移植元の llm-wiki-plugin から「ホスト型 wiki」を削った。移植計画の方針 G は「ホスト型 wiki は提供せず、関連する機能を削る」で、Q4「ホスト型サーバーを提供するか」への回答は「提供しない」である。

移植元のホスト型 wiki は、Cloudflare Workers の上で動くサーバーだった。トークンで認証し、`/ui/<wiki>/` で読み取り専用のリーダーを提供していた。info-hive は、このサーバーと、それにつなぐ機能（`wiki_remote.py`、`/wiki:migrate`、`--hosted`、判定の `hosted` バックエンド）を削った。

その後、Wiki を整形して表示する閲覧コマンド（仮称 `/wiki:browse`）を検討した。有力な構成は、利用者の PC の 127.0.0.1 でだけ待ち受ける HTTP サーバーを使う。方針 G がこの種のサーバーまで禁じているのかが、文書からは読み取れなかった。

## 決定

方針 G が禁じるのは、**PC の外に公開し、外部のサービスの上に Wiki を置くこと**と解釈する。次の条件をすべて満たすサーバーは、方針 G の「ホスト型 wiki」に当たらない。

1. 127.0.0.1 などのループバックのアドレスでだけ待ち受け、PC の外からは接続できない
2. Wiki の正本は利用者の PC の Markdown のままで、サーバーは内容を外部のサービスに送らない
3. Wiki を書き換える API を持たない

一時的に起動するサーバーも、常駐するサーバーも、この条件を満たせば検討の対象にしてよい。

## 理由

- 移植元のホスト型 wiki は、Cloudflare Workers という外部のサービスの上に Wiki を置く仕組みだった。移植計画は Q4 で「提供しない」と答え、それを受けて削った。計画のレビューでは、英語前提の TypeScript の実装と仕様を保守し続ける負担も、削除に賛成する理由として挙がっていた（`info-hive/docs/agent-runs/2026-11-02-porting-plan-review/`）。ループバックのサーバーは、外部のサービスを使わず、TypeScript の実装も要らない。
- 要件定義書の「ローカル完結」（Wiki の内容を PC の外に送らない）は、条件 1 と 2 で守られる。
- 「ホスト型」を「HTTP サーバーを立てること」とまで広げると、ブラウザで Wiki を検索する機能や、RAG の検索結果を表示する機能が作れなくなる。`file://` で開いたページからは、ブラウザが別のローカルファイルを取得できないためである（`docs/research/llm-wiki-browse-options.md` 第6.2節）。

## 検討した選択肢

| 選択肢 | 結果 |
| --- | --- |
| 方針 G を「HTTP サーバーを一切立てない」と読む | 採らない。静的 HTML を `file://` で開く方式しか残らず、検索、RAG 統合、複数 Wiki の切り替えができない |
| ループバック限定のサーバーは対象外と読む（本 ADR） | 採る |
| LAN の他の PC からも見られるサーバー（0.0.0.0 で待ち受け）も認める | 採らない。Wiki の内容が PC の外から読め、ローカル完結に反する |

## 影響

- `/wiki:browse` は、ループバックのサーバーを使う構成を採れる（ADR-0002）。
- サーバーを作るときは、上の 3 条件を守るための対策を実装する。待ち受けのアドレスを 127.0.0.1 に固定すること、起動ごとのトークン、Host ヘッダーの確認、書き込みの API を持たないことである（`docs/research/llm-wiki-browse-options.md` 第6.8節）。
- `info-hive/UPSTREAM.md` の方針 G の説明は変えない。移植元から削った機能の説明としては正しいためである。
- 今後、外部に公開する機能を検討するときは、本 ADR の条件に照らして判断する。条件を外れるなら、方針 G を見直す ADR を新たに書く。
