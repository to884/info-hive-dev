# ADR-0028：`/wiki:query` の回答には、規則で決める 3 段階の確からしさを付け、低ければ上げる方法を提案する

| 項目 | 内容 |
| --- | --- |
| 状態 | 提案 |
| 決定日 | （承認の日を入れる） |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0011（埋め込みと索引。答えを返さない判断は未解決）、ADR-0012（MCP サーバー）、to884/info-hive-wiki の 0.20.0 |

## 背景

`/wiki:query` の回答は出典の `[[wikilink]]` を付けるが、wiki がその回答をどれだけ裏づけているかは示していなかった。利用者は、出典のページを開くまで、回答が元の資料に直接書かれたことなのか、エージェントが組み合わせて導いたことなのか、仮説や古い記述にもとづくのかを見分けられない。作者は、回答に確からしさ（confidence）を付け、低いときは上げる方法を提案するよう求めた（2026年11月16日）。

付ける場所は 2 つ考えられた。1 つは回答そのもの（A）、もう 1 つは検索の結果の各行（B、MCP の `query` と CLI の `--json`）である。調べて分かったことは次のとおりである。

- 検索の行の `score` は RRF の値で、順位だけから決まる（`weight/(k+rank)`）。クエリをまたいで比べられない。
- 意味の検索の距離は、MCP の索引では融合の前に捨てている（`wiki_index.py` の `search`）。行に載せる変更は小さい。
- ADR-0011 の較正データ（natural、日本語）では、wiki に答えのない質問 12 問の最も近い距離は 0.151〜0.163 で、答えのある質問 47 問のうち 6 問は答えに届くのに 0.151 以上を要した。距離 0.15 未満を「高い」とする粗い区分なら作れるが、0.15〜0.208 は正例と負例が混ざる。評価は小さく、PC 1 台で測ったものである。
- 距離の意味はモデルごとに違う。MCP は ruri-v3-130m、CLI は multilingual-e5 で、語彙検索だけのときは距離がない。
- 回答の正誤を確かめた評価のデータはない。

## 決定

| 項目 | 決定 |
| --- | --- |
| 付ける場所 | 回答（A）にだけ付ける。検索の行（B）には付けない |
| 形 | 「高」「中」「低」の 3 段階と理由。パーセントや 0〜1 の数値にしない |
| 判定する単位 | 回答の結論と、結論を導くのに使ったすべての前提。結論が変わらない補足は判定しない |
| 決め方 | 前提は書かれていた場所で出発点を決め、結論は前提の確からしさと導き方で決める。それぞれに上限を当てて低いほうを取り、回答全体はもっとも低いものに合わせる。上げる方向の要因は設けない |
| 前提の出発点 | 表を上から順に見て、最初に当たった行にする。wiki の外の知識 → 低。検索の抜粋だけ → 低。wiki 自身の事柄を、その記録（`log.md`、`SCHEMA.md`、インデックス、シンセシスを含むページの frontmatter）で答えた → 高。シンセシスのページにしかない → 根拠に数えず、前提をたどって決め直し、見つからなければ低。ソースの要約ページか raw でその主張を確かめた → 高。そのほかの wiki のファイル（コンセプトやエンティティのページなど）だけ → 中。確かめに読むソースの要約ページは、1 つの前提につき 2 ページまで |
| 結論の導き方 | そのまま述べた → 前提と同じ。計算、数え上げ、書かれた値の比較などの決まった手順 → 使った前提の最小。前提にない判断を加えた → 前提の最小と中の低いほう。迷えば判断を加えたものとする |
| 上限 | 仮説、グラフのエッジの `confidence: medium` か `status: proposed` → 中。エッジの `confidence: low` か `status: disputed`、読んだページの間の解決していない矛盾、今を問うのに置き換えられた記述 → 低。時期や版で変わるのに時期が書かれていない、新しい記述と食い違う → 中。インデックスで見つからず検索に頼り、結果の `mode` が `hybrid` でないか `index.state` が `embedding` → 中。縮退の理由（ページ単位、`--no-embed`、モデルを使えない、埋め込みの途中、不明）は、上から順に最初に当たったものにする |
| 使わないもの | 検索の `score`、`--decide` の行ごとの判定の値（順位か関連の度合いで、回答の確からしさではない）。`--decide` の `failed_open`（ふるい分けをしなかっただけで、結果は通常の検索と同じ） |
| 上げる方法 | 「中」か「低」のとき、確からしさを決めた要因ごとに、それを解消する方法（取り込む資料、確かめるページ、使うコマンド）を提案する。raw を読んで確かめる方法は、承認があればその場で行う。wiki を書き換える方法は提案だけにする |
| 保存 | 「低」の回答はシンセシスとしての保存を提案しない。保存するときは確からしさを本文に残し、frontmatter には書かない。シンセシスのページは根拠に数えず、保存された判定も引き継がない。回答を保存しても確からしさは変わらない |
| 置き場所 | 決め方の正本は `skills/info-hive/references/query-workflow.md` の手順 5b。`commands/query.md` は要点だけを書いて、正本を指す |

## 理由

- 回答の確からしさを左右するのは、検索の順位よりも、根拠が元の資料までたどれるか、仮説や矛盾や古い記述に頼っていないかである。これらは wiki のページと frontmatter に書かれていて、エージェントが読んで確かめられる。
- 正誤の評価がないので、数値にすると、較正していないものを較正したように見せることになる。3 段階に理由を添えれば、利用者は判定を自分で確かめられる。
- 出発点と上限の最小を取る形は、要因を数える順番や読み手の印象で結果が変わらない。上げる方向の要因を設けないのは、エージェントが自信ありげな書きぶりで高めに付けるのを防ぐためである。
- 上げる方法を要因に対応させると、提案が具体的になり、「資料を足してください」のような一般論にならない。
- 保存した判定を引き継ぐと、wiki が変わったあとも古い判定が残る。シンセシスを根拠に数えると、自分の回答を根拠に確からしさを上げられてしまう。
- 1 回目の敵対的レビュー（GPT-6.1 Sol、却下）で、最初の版の 3 つの前提が崩れた（`docs/agent-runs/2026-11-16-wiki-query-confidence/review-1.md`）。
  - 「ページに直接書かれ、そのページの `sources` からソースまでたどれれば高」としていた。これでは、推論の回答をシンセシスとして保存すると、次のクエリでは「直接書かれていてソースまでたどれる」ので高になる。ページ単位の `sources` は、個々の主張がそのソースから来たことを保証しない。そこで、高の条件を、ソースの要約ページか raw の中で主張そのものを確かめたことにし、シンセシスは根拠から外した。
  - 根拠の形を「1 ページか、複数のページの組み合わせか」で分けていた。これでは、1 ページの値から計算した回答（成功 8 件と失敗 2 件から成功率 80%）がどの行にも当たらない。導き方は前提が何ページにあるかでは決まらないので、前提と結論を分け、結論は導き方（決まった手順か、判断を加えたか）で決めることにした。
  - 検索の縮退を 1 つの要因にまとめ、直し方を「埋め込みを待つ」としていた。縮退には原因が 4 つあり（MCP の埋め込みの途中、MCP のモデルが使えない、CLI の `--no-embed`、CLI の意味の検索の失敗）、待って直るのは 1 つだけである。縮退は結果の `mode` と `index.state` で見分け、直し方は理由ごとに分けた。`--decide` の `failed_open` は、結果を減らさないので縮退から外した。
- 2 回目の敵対的レビュー（同じく却下、`review-2.md`）で、1 回目の直しが場合を並べただけで、もれと重なりを生んでいたことが分かった。
  - 前提の出発点をページの種類で並べたので、`log.md` や `SCHEMA.md` を根拠にする回答（取り込みの時系列、wiki の規約）がどの行にも当たらなかった。出発点は「その事柄の正本に書かれていたか」で決め直し、wiki 自身の事柄では wiki の記録を正本とした。表は上から順に見て最初に当たった行を取る形にし、最後に「どれにも当たらない wiki のファイル → 中」を置いて、もれをなくした。
  - 縮退の理由を `index.state` から推し量っていた。`index.state` は埋め込み済みの件数が足りているかだけを表し、理由を表さない（モデルを使えないときも `embedding` になる）。また、ページ単位の検索は正常でもいつも語彙検索で、どの理由にも当たらなかった。理由は付けた引数と `warning`、標準エラーで決め、表を上から順に見る形にし、最後に「理由が分からない」を置いた。
- 3 回目の敵対的レビュー（`review-3.md`）は「採用可」だった。残った軽微な 3 点（シンセシスの frontmatter を wiki 自身の記録として読む順、裏の埋め込みが失敗したときの案内、この ADR の説明の食い違い）は直した。

## 検討した選択肢

| 選択肢 | 評価 |
| --- | --- |
| 検索の行に、距離から作る確からしさを付ける（B） | 採らない（今回は）。MCP の ruri でしか較正がなく、CLI の e5 と語彙検索だけのときに値を定義できない。粗い区分でも、評価が小さい。答えを返さない判断（ADR-0011 の残り）と合わせて、別に検討する |
| 回答に 0〜1 の数値を付ける | 採らない。正誤の評価がなく、較正できない |
| 根拠の数（独立したソースの数）で段階を上げる | 採らない。同じ資料を言い換えたページを独立と見誤りやすく、上げる方向の要因は判定を甘くする。独立したソースの数は理由に書いてよい |
| 確からしさをシンセシスの frontmatter に保存する | 採らない。wiki が変われば判定が変わる。lint とスキーマの変更も要る |
| 確からしさを付けるのを任意にする | 採らない。付けたり付けなかったりすると、付いていないことの意味が分からなくなる |

## 影響

- `/wiki:query` の回答が、確からしさの数行だけ長くなる。「中」か「低」のときは、上げる方法も付く。
- 判定はエージェントが規則を当てはめて行うので、同じ wiki と質問でも、前提の切り分け方によって違うことがある。規則を表にして、ぶれを小さくしている。
- 世の中の事柄の前提を高にするには、ソースの要約ページか raw でその前提を確かめる必要がある（wiki 自身の事柄は、wiki の記録で高になる）。クエリで読むページが、そのぶんだけ増える。確かめるのは結論の前提だけで、1 つの前提につきソースの要約ページを 2 ページまでに限る。
- 矛盾と置き換えの上限は、そのクエリで読んだページにある記述にだけ効く。インデックスを先に読み、すべてのページを読まない設計なので、読まなかったページの反証は判定に入らない。これは受け入れる。
- 上げる方法のうち、wiki を書き換えるものは提案にとどめる。ただし、関係を問う質問でグラフが古いときに extract で作り直す既存の手順（`references/graph-workflow.md`）は、この ADR では変えない。
- 検索のコード、MCP のツール、`--json` の形は変えない。2 つの wiki を引く問い合わせの設計（`docs/plans/wiki-query-two-wikis-2026-11-16.md`、別のセッション）も `commands/query.md` を変えるので、後から入る側が合わせる。

## 見直す条件

- 回答の正誤を確かめた評価のデータができ、段階と正しさの関係を測れるようになったとき。
- 検索の行の確からしさ（B）か、答えを返さない判断を入れるとき。
- 利用者が、同じ質問で判定がぶれると報告したとき。
