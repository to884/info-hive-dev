# ADR-0005：知識ページの図は mermaid を本文に書き、svg は wiki/assets/ に置く

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月3日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | 要件定義書の §6.5（F-W01〜F-W06）、D-03、AC-P20。ADR-0002。`docs/research/web-page-ingest-brainstorm.md` のクラスタ F |

## 背景

wiki の知識ページは文章だけで書かれてきた。`page-conventions.md` にも、図を入れる決まりはない。ユーザーは、図表で説明できる内容には図表を足し、取り込んだ画像と同じように、別の LLM が読んで分かる説明を添えたいと考えている。図は png より svg と mermaid を使いたいという方針も示した。

図の置き方には、今のプラグインの作りによる制約がある。

- `/wiki:browse` は生の HTML を出力しない設定で作る（ADR-0002）。Markdown に `<svg>` を直接書いても表示されない。
- browse のサーバーはページ一覧にあるパスしか返さないので、`wiki/assets/` のファイルは今の設計では配信されない（`docs/research/llm-wiki-browse-options.md` L512〜514）。mermaid.js の同梱は構想だけで、第一段階に入っていない（同 L217、L547）。
- lint のページの大きさの判定は、ファイル全体の文字数と行数で数える（`wiki_lint.py` L182、L192）。mermaid のブロックもそのまま数える。
- 検索はコードフェンスの中身をそのまま索引に入れる（`wiki_search.py` L360〜399）。
- Obsidian の埋め込み `![[img.png]]` は wikilink として検出され、リンク切れとして報告される。標準の `![alt](path)` は検出されない。

## 決定

| 項目 | 決定 |
| --- | --- |
| 図 | mermaid のコードブロックで本文に書く。流れ、順序、状態、関係、時系列が対象 |
| mermaid で描けない図 | モデルが svg を書いて `wiki/assets/<ページのスラッグ>-NN.svg` に置き、`![説明](assets/<ページのスラッグ>-NN.svg)` で参照する。箱の配置を示すアーキテクチャの図などが対象 |
| 表 | 比較は Markdown の表で書く |
| 説明 | 図表の直後に `> <モデルの表示名> 補足: ` で始まる引用ブロックを置き、図表を見ずに内容が分かるようにする。取り込んだ画像の説明（F-I14）と同じ形式 |
| 使わないもの | png などのラスター画像。Web ページから取り込んだ svg（`raw/assets/` に保存するだけで、`wiki/` に写さない） |
| 文字 | 図の中の文字は日本語で書き、識別子だけ英語にする |
| 描く手段 | まず利用できるスキルの一覧を見て、図表を作るスキルがあれば、用途に合うものを使う。なければモデルが mermaid か svg を直接書く。プラグインは外部のスキルに依存しないので、手順にスキル名を書かず、特定のスキルがあることを前提にしない。スキルの出力は、上の形式に変換して説明を添える。確実に特定のスキルを使わせたいときは、wiki を置くプロジェクトの指示ファイルにスキル名を書く |
| 大きさの判定 | コードフェンスの中身と画像の行は、文字数・行数から除く |
| browse での表示 | mermaid.js の同梱と `wiki/assets/` の配信は将来の作業とし、ADR-0002 の第一段階には含めない |

## 理由

- mermaid は文字で書けるので、差分が読め、モデルが書きやすく、Obsidian や VS Code の拡張、GitHub でそのまま描かれる。svg を別ファイルにするのは、生の HTML を出さない browse の方針（ADR-0002）と合わせるためである。
- svg は差分が読みにくく、モデルが書くと大きくなりやすい。mermaid で足りる図まで svg にすると、ページの保守が重くなる。描けないものに限る。
- png を使わないのは、文字として差分が取れず、モデルが描き直せないためである。
- 図の直後に説明を置くのは、検索が図の中身を文章として拾えるようにするためでもある。説明がなければ、mermaid のソースの断片だけが索引に入る。
- 大きさの判定から図を除くのは、上限（空白を除いて 4,000 文字、8,000 文字）が本文の密度を見るためのもので、図のソースの長さは別の問題だからである。
- スキル名を手順に書かないのは、プラグインを入れた環境にそのスキルがあるとは限らず、スキルの名前や出力の形式が変わるとプラグインの手順が壊れるためである。一方で、スキルがあるのに使わないのは惜しいので、「一覧を見て、あれば使う」と書く。Claude Code のスキルはモデルが一覧と説明文を見て選ぶものなので、この書き方なら名前を書かなくてもたいてい選ばれる。ただし保証ではないため、確実に使わせたい人は自分の `CLAUDE.md` にスキル名を書く。
- browse での表示を第一段階から外すのは、`/wiki:browse` の構成（ADR-0002）をまだ実装していないためで、図の表示を足すと第一段階が大きくなる。図は Obsidian や VS Code でも見られる。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| mermaid だけにし、svg を使わない | 配置を示す図が描けない。ユーザーは svg も使うと決めた |
| svg だけにし、mermaid を使わない | 差分が読みにくく、モデルの作業が重い |
| Markdown に `<svg>` を直接書く | browse が生の HTML を出力しないので表示されない。ファイルも大きくなる |
| png を許す | 差分が取れず、描き直せない。ユーザーが使わないと決めた |
| Obsidian の埋め込み `![[x.svg]]` で参照する | lint が wikilink として検出し、リンク切れとして報告する。標準の `![alt](path)` にそろえる |

## 影響

- 要件定義書に §6.5（F-W01〜F-W06）と AC-P20 を足し、D-03 に browse の将来の作業を書き添えた。
- 実装では次を直す。`page-conventions.md` に図表の決まりを書く。`wiki_lint.py` の大きさの判定からフェンスの中身と画像の行を除き、`![alt](assets/x.svg)` の参照先の存在を確かめ、`wiki/assets/` を lint の対象から除く。`wiki_search.py` でフェンスの中身を索引から除くかを決める。`--suggest-pages` の走査から alt テキストとフェンスの中身を除く。`init_wiki.py` で `wiki/assets/` を作る。`.gitattributes` に `*.svg` を足す。
- `/wiki:browse` の実装では、mermaid と svg は描かれない。ADR-0002 の「見直す条件」に、図の表示を足すときの判断を書く必要がある。

## 見直す条件

- `/wiki:browse` を実装し、図が描かれないことが使いにくいと分かったとき。mermaid.js の同梱と `wiki/assets/` の配信を足す。
- モデルが書く svg が大きくなりすぎるとき。別の記法（PlantUML、D2 など）を比べる。
