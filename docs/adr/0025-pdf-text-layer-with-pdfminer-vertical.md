## 背景

PDF を wiki に取り込む経路は 2 つあり、本文の取り出し方が違う。

| 経路 | 本文の取り出し方 |
| --- | --- |
| rag が使えるとき | rag のワーカーが、PDFium（pypdfium2）の文字の層をページごとに取り出し、ページを判定する（`rag_pdf.inspect_page`）。`ocr_mode` が `auto` なら、判定が `garbled`、`scan`、`vertical` のページを NDLOCR-Lite で OCR し、本文を置き換える。`always` ならすべてのページを、`off` なら OCR せず、OCR が要るページでエラーにする |
| rag を使わないとき | `ingest-workflow.md` の手順 2 で、`pdf-reading` スキルか、`pdftotext` か `pdfminer` を使う。どれを使うかはエージェントが選ぶ |

ADR-0024 は、rag を使わない経路も PDFium の文字の層にそろえることを提案した。公開の PDF で承認の条件を確かめると、条件を満たさなかった（[検証の報告](../research/adr-0024-verification-2026-11-15.md)）。PDFium は、版面の順ではなく、ファイルの中の文字の順に返していると考えられ、組版のソフトで作った日本の官公庁の資料で読み順が崩れた。行末のハイフンで分けた語には U+FFFE が入った。この 2 つは、rag の本文と索引にも同じく入っている。

そこで、同じ 10 ページ（LaTeX の論文、白書、官報）で、ほかの方式も比べた。判定は Sol（GPT-6.1 Sol）に、ページの画像を正解として、方式の名前を伏せて 3 回させた。点は 1〜5 で、10 ページの平均である。

| 方式 | 総合 | 読み順 | 表 | 文字の正しさ | 依存 | 1 ページあたりの時間 |
| --- | --- | --- | --- | --- | --- | --- |
| ADR-0024 の試作（PDFium の文字の層。`vertical` などのページは本文を出さない） | 3.2〜3.4 | 2.8〜3.0 | 4.0 | 4.1〜4.4 | 8.1 MiB | 約 0.01 秒 |
| pdfminer（縦書きの検出あり） | 3.5〜3.7 | 3.6〜3.7 | 3.4〜3.6 | 4.2〜4.4 | 19.5 MiB | 0.08〜0.18 秒 |
| pdfminer（既定） | 3.3 | 3.3〜3.4 | 3.2 | 3.7〜4.0 | 19.5 MiB | 約 0.1 秒 |
| Xpdf の pdftotext | 3.5 | 3.4〜3.6 | 3.0 | 3.8 | 別のプログラムと日本語の対応表が要る | － |
| Docling（OCR なし） | 3.4〜3.8 | 3.9〜4.0 | 3.4 | 4.3〜4.4 | 約 1.1 GB（torch を含む） | 1.2〜2.3 秒（準備に 13〜26 秒） |
| NDLOCR-Lite（全ページを OCR） | 2.9 | 3.5 | 2.2 | 3.2 | rag が使用中 | 1.4〜4.5 秒 |
| pdf_oxide | 2.3 | 2.2 | 2.8 | 3.7 | 約 12 MB | 約 0.01 秒 |
| pdfplumber（方向の指定なし） | 2.9 | 2.5 | 3.6 | 3.4 | pdfminer と同じ | 約 0.1 秒 |

最初の行は、生の PDFium の文字の層ではなく、ADR-0024 の仕様どおりに、判定が `vertical` などのページの本文を出さない試作の点である。官報の 2 ページ目の低い点には、本文を出さなかったことが含まれる。

ページの種類ごとに見ると、次のとおりだった。

- **日本の官公庁の資料:** ADR-0024 の試作だけが読み順を崩した（2〜3 点）。pdfminer（縦書きの検出あり）と Docling は、白書のポイントと概要の構成のページで 5 点だった。
- **縦書きの官報:** NDLOCR-Lite の OCR がもっとも良く（総合 4）、次が pdfminer（縦書きの検出あり）だった（総合 2〜3）。ほかは読み順が 1 点だった。pdfminer は、縦書きの検出がないと 1 文字ずつ改行した（官報の 1 ページで 2,225 行）。
- **英語の論文:** 表は ADR-0024 の試作と Docling が良く、pdfminer（縦書きの検出あり）はそれに次いだ。数式（分数、総和記号）は、どの方式でも崩れた。pdfminer は、総和記号を `(cid:80)` と出した。

この比較には限りがある。

- 判定したのは 10 ページで、各判定は 1 回ずつである。同じ方式の点も、判定のあいだで最大 0.4 動いた。平均の差の小さいものは、ぶれの範囲と読む。
- 公開の PDF の作成したソフトは 4 種類（pdfTeX、InDesign、記録なし、Acrobat Distiller）しか試していない。
- スキャンの PDF は合成だけで、実物は試していない。

## 決定

### 何をそろえ、何をそろえないか

| 対象 | そろえるか |
| --- | --- |
| ページの区切りと番号 | そろえる。どちらの経路でも、PDF のページの順に `p. 1` から番号を付ける。要約ページの根拠の位置（ページ番号）は、経路によらず同じに書ける |
| 文字の層の本文（pdfminer の取り出しの結果） | そろえる。ただし、同じ抽出の識別（下の「抽出の識別」）で取り出したときに限る。比べるのは、改行を `\n` にそろえた文字列で、ファイルのバイト列ではない。同じ識別なら、別のプロセスで取り出しても同じ文字列になるようにする（下の「本文を毎回同じにする」） |
| ページの判定 | そろえる。rag の今の `inspect_page`（PDFium）の判定を、同じ閾値で使う |
| 最終の本文 | そろえない。rag が OCR したページ（`auto` のときは判定が `garbled`、`scan`、`vertical` のページ、`always` のときはすべてのページ）では、rag の本文は OCR の結果になる。wiki は OCR をしないので、そのページの本文は rag と違う。判定が `garbled` と `scan` のページは、wiki は本文を出さない |

判定は、OCR に回すかと、本文を出すかを決める。そのため、判定を誤ると、出す本文が変わる。たとえば、横書きの表を 90 度回したページを `vertical` と誤ると、rag は OCR の結果を本文にする。wiki は、警告を付けて pdfminer の本文を出す。判定を `garbled` と誤ると、wiki は本文を出さない。

### 役割の分け方

| 役割 | 方式 |
| --- | --- |
| 文字の層の本文 | pdfminer.six で、`LAParams(detect_vertical=True)` で取り出す。ほかの値は既定値にする。文書を 1 回だけ読み、ページごとに本文を受け取る（`extract_text(page_numbers=[i])` をページごとに呼び直すと、呼ぶたびに文書を読み直すので、1 ページに 1〜2 秒かかった）。テキストボックスをまとめる順は、下の「本文を毎回同じにする」のとおりに決める |
| ページの判定 | rag の今の `inspect_page`（PDFium の文字の層から数値を数える）。判定のためだけに使い、その本文は使わない |
| 本文の崩れの検出 | pdfminer の本文で、`(cid:<数>)` と U+FFFD を数える。判定とは別の数値として持つ（下の「確かめるべきページ」） |
| OCR とその画像 | rag の今の NDLOCR-Lite と PDFium の描画。wiki は OCR をしない |
| OCR の確信度 | rag が、NDLOCR-Lite の認識器（PARSeq）の出力から、文字ごとの確率を数える（下の「OCR の確信度とページの確認」） |

### 本文を毎回同じにする

pdfminer.six 20260107 は、同じ PDF から、プロセスによって違う本文を返すことがある。546 ページの公開の PDF（令和 7 年版防衛白書）を 6 回（3 つのプロセスで、ページごとの受け取りと文書全体の取り出しをそれぞれ）取り出すと、5 ページで本文が変わった。変わったのは行の並びだけで、行の中身と文字の数は同じだった（[承認の条件の測定](../research/adr-0025-measurement-2026-11-15.md)）。

原因は `LTLayoutContainer.group_textboxes` にある。この関数は、テキストボックスの組を、距離の近い順にヒープからまとめる。距離が同じ組の順は `id(obj)`、つまりオブジェクトのメモリーの番地で決まる。番地はプロセスごとに変わるので、距離の同じ組があるページでは、まとめる順と本文の並びが変わる。

本文が変わると、契約の試験 1（wiki と rag の本文が同じ）、ページの本文の SHA-256、`--from` の続きの位置（ページの中の文字の位置）が成り立たない。そこで、次のようにする。

- **決め方:** 距離が同じ組の順を、`id(obj)` ではなく、ページの中で決まった順（テキストボックスを初めて見た順の番号）で決める。試しに、`group_textboxes` を呼ぶあいだだけ、`pdfminer.layout` の中の `id` を置きかえると、3 つのプロセスで 546 ページの本文がすべて同じになった。この置きかえはモジュールの変数を書きかえるので、並行して呼ぶと壊れる。試しのためだけに使う。製品では、`group_textboxes` と同じ手順で、組の順をページの中の番号で決める関数を持ち、スレッドのあいだで状態を共有しない。wiki と rag で同じ関数を使う。
- **抽出の識別:** この決め方の版を、抽出の識別に入れる。pdfminer.six の版は `==` で固定する。版を上げるときは、契約の試験 7 で、この決め方がまだ効くことを確かめる。
- **品質の判定との関係:** Sol が判定した本文は、この決め方を入れる前の pdfminer の出力である。決め方を入れると、距離の同じ組があるページで、行の並びが判定した本文と変わりうる。防衛白書では、直した版と直していない版の 1 回が違ったのは 1 ページだった。判定した 10 ページでは、直した版も、別々の 3 つのプロセスで、判定に渡した本文と同じだった（[承認の条件の測定](../research/adr-0025-measurement-2026-11-15.md)、2026-11-16）。判定の点は、直した版にそのまま当てはまる。

### 確かめるべきページ

判定（`kind`）とは別に、次のどれかに当たるページを「確かめるべきページ」とする。判定を変えないので、rag と判定がずれることはない。

- PDFium の `image_coverage` が 0.5 以上である（本文の大部分が画像かもしれない）。
- pdfminer の本文で、`(cid:<数>)` か U+FFFD が 1 つ以上ある（文字を復号できていない。数式の記号のことが多い）。

私用領域の文字は数えない。行頭の記号を記号のフォントで書いた資料では、ふつうに出てくるためである（白書の概要では、12 ページ中 8 ページに出た）。この条件では、検証の公開の 33 ページのうち 8 ページに印が付いた（BERT の数式のページ 2 つ、白書の概要の表紙とグラフのページ、官報の 4 ページ）。閾値（0.5 と 1 つ以上）は最初の値で、承認の条件の測定で見直す。

### wiki（rag を使わないとき）

wiki に `wiki_pdf.py` を足す。`uv run --script` で動かし、依存は `pdfminer.six` と `pypdfium2` で、どちらも版を `==` で固定する。

| 判定 | 出すもの |
| --- | --- |
| `text` | pdfminer の本文 |
| `vertical` | ページの本文の先頭に、縦書きのページで列の順が崩れることがあると書いた 1 行を付け、pdfminer の本文を続ける |
| `garbled` | 本文を出さず、PDFium が文字を復号できなかったページであることを書いた 1 行を出す。pdfminer の本文が読めるかは確かめていないが、信頼できないので出さない |
| `scan` | 本文を出さず、スキャンのページであることを書いた 1 行を出す |
| `blank` | 見出しだけを出す |

出し方は次のとおりにする。

- **形:** ページごとに `## p. <番号>`、空行、ページの本文を並べ、ページのあいだを `\n\n` でつなぐ。今の rag の `document.md` と同じつなぎ方である。
- **分けて読む:** 1 回の出力の文字数に上限を設け、上限を超えない（上限は 500 文字以上）。続きがあれば、標準エラーに続きの位置を書き、終了コード 3 で終わる。続きは `--from <PDF の SHA-256 の先頭 12 文字>:<ページ>:<ページの本文の中の文字の位置>:<抽出の識別の短い印>` で読む。続きの出力は、ページの途中から本文だけを続け、見出しも縦書きの 1 行も出し直さない。SHA-256 が今の PDF と違うか、抽出の識別が変わっていれば、止まる。分けて読んだ出力をつなぐと、一度に出した出力と同じになる。
- **`--json`:** 全体の要約として、PDF の SHA-256、ページの数、判定ごとのページの数、確かめるべきページの数、文字の層の本文が空のページの数、抽出の識別と、ページの一覧（下の「ページの一覧の形」）を返す。文字の層の本文が空のページの一覧は、rag が古いときの代わりの手順（下の「読めないページの扱い」）で、rag の本文が空のページと比べるのに使う。ページごとの詳細（判定、判定の数値、本文の崩れの数、本文の SHA-256）は、`--pages` を付けたときだけ、その範囲を返す。
- **写し:** 取り出した本文の写しは作らない。
- **uv がないとき:** 止まって、uv が要ることを伝える。
- **手順の書き換え:** 手順から、`pdf-reading` スキル、`pdftotext`、`pdfminer` の直接の呼び出しを外す。Read は、図と版面、確かめるべきページ、判定が `text` 以外のページを見るときに使う。
- **記録:** 取り込みのログの行の下に、抽出の識別をサブ行で書く。

### 読めないページの扱い

判定が `text` 以外のページ、確かめるべきページ、OCR の結果が空のページがあれば、エージェントはページの番号と数をユーザーに伝える。OCR の確信度が低いページは、下の「OCR の確信度とページの確認」のとおりに確認を求める。エージェントがそれを知る経路は、経路ごとに次のとおりである。

| 経路 | ページの情報の取り方 |
| --- | --- |
| rag を使わないとき | `wiki_pdf.py --json` の全体の要約 |
| rag を使い、rag が `page_report` を返すとき | `job_status` の結果の `page_report`（下の「rag」）。`result.extracted_markdown` には、判定も印も入っていないので、それだけを読んではいけない |
| rag を使うが、rag が `page_report` を返さないとき（この ADR より前の rag） | 同じ PDF に `wiki_pdf.py --json` を動かし、判定と確かめるべきページを得る。`--json` の SHA-256 が rag の `result.sha256` と違えば、rag が処理したあとで PDF が変わっているので、ページの情報を使わない。OCR したかと、OCR の結果が空かは分からない。そこで、判定によらず、すべてのページについて、`extracted_markdown` のそのページの本文が空かを確かめる。`ocr_mode` が `always` なら、判定が `text` のページも OCR され、その結果が空のこともあるためである。`extracted_markdown` の本文が空で、`wiki_pdf.py` の本文が空でないページは、「rag の本文が空のページ」として伝える（OCR の結果が空だった見込みが高いが、rag が古いので確かめられない）。`status` が設定を返さないときは、`ocr_mode` が分からないことをユーザーに伝える。rag の抽出の識別が分からないので、本文が wiki と同じとは言えない |

ページの一覧の形は、`wiki_pdf.py --json` と `page_report` で同じにする。ただし、OCR に関わる一覧（OCR したページ、OCR の結果が空のページ、OCR の確信度が低いページ、確信度が不明のページ、確認の状態ごとのページ）は、OCR をする rag の `page_report` だけが返す。

- **数:** 判定ごと、確かめるべきページ、OCR したページ、OCR の結果が空のページ、OCR の確信度が低いページ、確信度が不明のページ、確認の状態（確認待ち、そのまま使う、直した、却下した、古くなった）ごとのページの、それぞれの正確な数を返す。
- **番号:** ページの番号を、続いた番号をまとめた範囲（`1-200,901`）で返す。
- **続き:** 範囲の数が 200 を超えるときは、先頭の 200 個を返し、続きを取る位置（`next`）を付ける。`wiki_pdf.py --json --list-from <位置>` と、`job_status` の引数 `page_report_from` で続きを取る。続きをたどれば、すべての番号が取れる。

そのうえで、rag が実際にできることに合わせて、次のように扱う。

| ページ | rag で OCR されるか | エージェントがすること |
| --- | --- | --- |
| 判定が `garbled`、`scan`、`vertical` | `ocr_mode` が `auto` か `always` なら OCR される。`off` ならジョブがエラーになる。OCR の結果が空のこともある（`page_report` の OCR の結果が空のページ） | rag で取り込むかをユーザーに聞く。今の `ocr_mode` を `status` の設定で確かめ（下の「rag」で足す）、`off` ならそのことを伝える。OCR の結果が空のページは、読めなかったページとして扱う |
| 確かめるべきページ（判定は `text`）、判定が `blank` | `auto` では OCR されない | Read でページの画像を見る。画像から読んだ内容を要約に使うときは、要約ページにそう書く |

rag の `ocr_mode` を `always` にすれば、すべてのページが OCR される。ただし、次のことから、この手順には入れない。ユーザーが `always` を使いたいと言ったときは、これらを伝える。

- `configure` でその PC の設定を変えることになる。すべてのページを OCR するので時間がかかり、未完了のジョブがあると設定は変えられない。
- OCR の設定は、索引の方針の指紋に入っている。設定を変えると、その PC のすべての wiki の索引が方針の違う索引になり、次の取り込みでその wiki の索引が空になる。ほかの PDF は、登録し直すまで検索の対象から外れる（ADR-0014）。
- rag のジョブは、登録したときの設定を持ち、その設定で動く。設定を変えても、すでにあるジョブ（`retry_job` で再試行するジョブを含む）は前の設定のまま動く。
- 新しい設定で OCR させるには、設定を変えたあとで、`register_pdf` で新しく登録する。

### OCR の確信度とページの確認

rag が OCR したページでは、OCR の確信度を数える。確信度の低いページは、要約に使う前に、ユーザーに見てもらい、そのまま使うか、直すか、却下するかを決めてもらう。

**確信度の数え方**

- **文字:** 認識器（PARSeq）の ONNX の出力は、文字の位置ごとのロジット（7,142 の文字の種類ごとの値）である。30、50、100 文字用の 3 つの認識器のどれも、合成の行の画像で、位置ごとの和が 1 にならなかった（[測定](../research/adr-0025-measurement-2026-11-15.md)の `results/parseq-probe.json`）。位置ごとに softmax をかけ、選んだ文字の確率を、その文字の確信度とする。NDLOCR-Lite の `PARSEQ.read` は `argmax` で文字を選び、確率を捨てているので、rag の `rag_ocr.py` の側で、同じ前処理と同じ選び方で読み、確率も受け取る。NDLOCR-Lite のファイルは変えない。
- **終わりの記号:** PARSeq は、終わりの記号（番号 0）を選んだ位置で読むのをやめる。終わりの記号を選んだ確率も、文字の確率と同じに扱う。終わりの記号を迷って選んだ行（行の途中で読むのをやめたかもしれない行）も、確信度が下がる。
- **行:** 行の確信度は、その行の文字の確率と、終わりの記号の確率の最小値とする。1 文字の誤りで意味が変わるので、平均は使わない。NDLOCR-Lite は、長い行を左右に分けて読み、つなぐことがある。そのときは、つないだあとの文字の並びに、確率を同じ順に並べ、2 つの読みの終わりの記号の確率も入れる。
- **読めなかった行:** 検出器が見つけた行で、認識した本文が空の行は、「読めなかった行」とし、確信度を 0 とする。終わりの記号を確信して選んでいても、行があるのに文字がないので、確かめる対象にする。
- **ページ:** 行の確信度が閾値より低い行（読めなかった行を含む）が 1 つ以上あるページを「OCR の確信度が低いページ」とする。閾値は決めず、承認の条件 5 で決める。
- **確かめる不変条件:** 行ごとに、文字の確率の数が、最終的に採った OCR の本文の文字の数（改行を除く）と一致し、終わりの記号の確率の数が、その行を作った読みの数と一致する（読みが最大の長さに達して終わりの記号がないときは、その読みの分を数えない）。NDLOCR-Lite は、行を長さに応じて別の認識器で読み直し、読みは複数のスレッドで並行に走る。確率は、最終的に採った読みのものだけを、行に結びつけて持つ。
- **確信度が表さないもの:** 文字を読み違えた確からしさと、読み終わりを迷った確からしさだけを表す。検出器が見落とした行、縦書きのページの列の順の誤り、表の崩れは、確信度を下げない。終わりの記号を確信して選んだのに、実は文字が残っていた行も、確信度を下げない。検出器が行ごとに出す `confidence`（ここに文字の行がある確からしさ）は、記録するが、印には使わない。
- **確信度がないページ:** wiki だけの経路は OCR をしないので、確信度はない。rag でも、この ADR より前の OCR の結果（移した結果を含む）には確率がない。そのページは「確信度が不明」として数え、確信度が高いとは扱わない。確信度を得るためだけに OCR をやり直すことはしない（ページを選んで OCR させる仕組みは「決めないこと」）。

**保存**

- 文字の確率と終わりの記号の確率（小数第 4 位まで）と行の確信度は、OCR の結果と一緒に、OCR の保存先（下の「rag」の「OCR の結果を別に保存する」）に保存する。数え方の版（`OCR_CONFIDENCE_REVISION`）も一緒に書く。版が違うか、書いていない結果は、確信度が不明として扱う。
- 閾値は、索引の方針の指紋に入れない。印は、`page_report` を作るときに、保存した行の確信度と、そのときの閾値から数える。

**ユーザーの確認**

確信度の低いページがあると、エージェントは、要約のページを書く前に、ユーザーに確認を求める。

1. ページの数と番号を伝え、次から選んでもらう。ページが多くても、1 回の質問にまとめる。
   - **いま確かめる:** ページごとに、確信度の低い行（ページの番号、行の本文、確信度）を示す。ユーザーは PDF のそのページを見て、ページごとに「そのまま使う」「直す」「却下する」「あとで」を選ぶ。エージェントは、Read でページの画像を見て、どの行が怪しいかを説明してよい。
   - **すべてそのまま使う:** 確信度の低いページを、すべて「そのまま使う」にする。
   - **あとで確かめる:** ページを「確認待ち」のまま残す。
   ページが多いときは、確信度の低い順に、1 回に 10 ページまでを示す。残りは、続けるか、あとにするかを聞く。
2. **直す:** ユーザーが直した本文を書く。エージェントがページの画像から直した本文の案を作ってもよいが、ユーザーが案を承認するまで保存しない。記録には、ユーザーが書いたか、エージェントの案をユーザーが承認したかを残す。案を作ってよいとしたのは、作者の判断である（2026-11-16）。ユーザーが自分で書くだけにすると、直す手間が大きく、直さずに「すべてそのまま使う」が選ばれやすい。承認するまで保存しないので、案が黙って本文に入ることはない。確信度の低い行だけの案にしないのは、確信度が検出の漏れや段の順の誤りを捉えないためである。
3. **却下する:** その wiki の索引から、そのページを外す。その wiki に返す本文（下の「確認の結果を当てた本文」）のそのページは、見出しと、OCR の結果を却下したことを書いた 1 行だけにする。
4. **要約との順:** 要約のページは、確認の結果が索引に反映されてから書く（反映されたかは `page_report` の「反映した確認の版」で分かる）。「あとで」と「確認待ち」のページの本文は、要約に使わない。要約のページに、確認待ちのページの番号を書く。確認が済んだら、エージェントは、要約のページを直すかをユーザーに聞く。
5. **答えがないとき:** セッションが終わるなどして答えがないページは、「確認待ち」のまま残す。黙って「そのまま使う」にはしない。`status` は、wiki ごとの確認待ちのページの数を返し、次の取り込みのときに、エージェントはそれを伝える。
6. **確認待ちのページの検索:** 確認待ちのページも索引に入れ、検索の結果に、そのページが確認待ちであることを付ける。印は索引には入れず、検索するときに、その wiki で反映したページの状態から付ける。エージェントは、確認待ちのページを根拠にするとき、そのことを書く。確認待ちのページを検索の対象にするのは、作者の判断である（2026-11-16）。答えがないページは確認待ちのまま残る（手順 5）ので、検索の対象から外すと、検索できないページが増え続ける。印があれば、誤った OCR の本文は、疑って読むことで害を抑えられる。順位を下げる案は、下げ幅の閾値が増え、下がった理由が利用者に見えにくいので採らない。

**確認の結果の置き場所**

確認の結果は wiki ごとに違いうる（同じ PDF を、wiki A では直し、wiki B では却下する）。一方、抽出の結果は、同じ `data_dir` を使う wiki のあいだで共有している（`Config.extraction_root`）。そこで、置き場所を 3 つに分け、共有するものに確認の結果を混ぜない。

| 置き場所 | 中身 | 共有するか |
| --- | --- | --- |
| 抽出の結果 | 文字の層の本文、OCR の結果（確率を含む）、抽出したままの `document.md` | wiki のあいだで共有する。確認の結果は入れない |
| 確認の台帳 | 確認の結果の履歴 | wiki ごと |
| 確認の結果を当てた本文と索引 | 抽出の結果に、台帳のある版までの確認の結果を当てた本文（`reviewed.md`）と、その索引の行 | wiki ごと |

- **台帳:** wiki、PDF の SHA-256、ページの番号を鍵にして、確認の結果を保存する。中身は、選んだこと（そのまま使う、直す、却下する）、直した本文、決めた人（ユーザーか、エージェントの案をユーザーが承認したか）、決めた日時、確かめたときの OCR の本文の SHA-256 である。結果を受け付けるたびに、wiki と PDF ごとの「確認の版」を 1 つ上げる。前の結果は消さずに履歴として残す。
- **当てた本文と索引:** 確認の結果を当てた本文と索引の行は、当てた確認の版を持つ。索引の行と埋め込みの途中経過の鍵（`generation`）に、当てた確認の版を入れる。台帳の版が当てた版より新しければ、今の「同じ PDF と同じ指紋なら索引を使い回す」の分岐を通らず、作り直す。前の版の途中経過は使い回さない。
- **公開:** 検索は、その文書の公開した `generation` の行だけを返す。新しい版の行をすべて書き終えてから、公開する `generation` を切りかえ、前の版の行を消す。作り直しが途中で止まったり失敗したりしても、検索は前の版の行を返し続ける。
- **状態の表示:** `page_report` と検索の結果の印は、台帳ではなく、公開した版から作る。台帳の版が公開した版より新しいあいだは、そのページを「反映待ち」として示す。反映待ちのページは、公開した版での状態（確認待ちなど）のまま検索され、反映待ちの印も付く。作り直しが失敗したら、`page_report` に失敗を書き、再試行できる。
- **返す本文:** `job_status` の `extracted_markdown` は、その wiki の確認の結果を当てた本文を指し、当てた確認の版を一緒に返す。確認の結果がない wiki では、共有の `document.md` を指してよい。
- **作り直しのジョブ:** 作り直しのジョブは、今の取り込みのジョブの重複の除き方（同じ取り込みの条件で処理中のジョブがあれば、それを返す）を使わない。wiki と PDF ごとに、作り直しのジョブを 1 つだけ持つ。ジョブは、処理を始めるときに台帳の最新の版を読んで当てる。終えたときに、台帳の版が当てた版より新しければ（処理中に次の確認を受け付けたとき）、続けてもう一度作り直す。処理中に受け付けた確認を取りこぼさない。
- **検索できる本文がなくなったとき:** 確認の結果を当てると検索できる本文がなくなる（すべてのページを却下したなど）ときも、作り直しを失敗にしない。その文書の行が 0 の版を公開し、`page_report` にそのことを書く。今の「検索できるテキストがありません」のエラーは、最初の取り込みのときだけに使う。却下を書いた 1 行は、索引に入れない。
- **索引の作り直しとの関係:** 確認の結果は、抽出の版や設定を変えて索引を作り直しても残り、作り直した索引に当てる。索引の方針の指紋には入れない。
- **古くなった結果:** OCR をやり直して OCR の本文の SHA-256 が変わったら、そのページの確認の結果は当てず、ページを「確認待ち」に戻す。`page_report` に、古くなったページとして載せる。

**確認のツール**

今の取り込みの結果には、`review_pages`（出典の PDF が変わった wiki のページ）というキーがある。名前がぶつからないよう、OCR の確認には別の名前を使う。

- `ocr_page_detail`: ジョブの ID とページの番号を受け取り、そのページの OCR の本文、その SHA-256、確信度の低い行（行の番号、本文、確信度、ページの中の位置）、今の確認の結果、台帳の確認の版、公開した確認の版を返す。OCR の本文は共有の抽出の結果から返すので、直したり却下したりしたあとでも、元の OCR の本文が分かる。
- `decide_ocr_pages`: ジョブの ID、もとにした台帳の確認の版、ページごとの選んだこと、直した本文、確かめたときの OCR の本文の SHA-256 を受け取る。台帳の版が、もとにした版と違うか、SHA-256 が今の OCR の本文と違えば、受け付けない（別のセッションで決めた結果を、知らずに上書きしないため）。受け付けたら、台帳の版を上げ、その wiki の当てた本文と索引を作り直すジョブを登録する。「そのまま使う」にしたページを、あとで「直す」や「却下する」に変えることもできる。

### rag

- **本文:** 判定が `text` のページの本文を、PDFium の文字の層から、pdfminer（縦書きの検出あり）の本文に変える。OCR したページの本文は、今と同じく OCR の結果を使う。
- **抽出の版:** `EXTRACT_REVISION` を `extract-v2` に上げる。ADR-0014 のとおり、すべての wiki の索引が取り込み直しの対象になる。
- **抽出の識別:** 抽出の識別を、`EXTRACT_REVISION`、pdfminer.six の版、`LAParams` の値、pypdfium2 の版の組にする。この識別を、文字の層の抽出の結果の鍵、保存したページ、索引の方針の指紋（`Config.fingerprint`）のすべてに入れる。識別が違う保存済みの結果と索引は使い回さない。識別を持たない保存済みの結果（今の形式のもの）は、識別が違うものとして扱う。
- **OCR の結果を別に保存する:** 今は、OCR の結果がページの抽出の結果（`page-*.json`）に入っていて、抽出の版を上げると、OCR もやり直しになる。これを分け、OCR の結果を別の鍵で保存する。鍵は、PDF の SHA-256、ページの番号、描画の識別（pypdfium2 の版と描画の dpi）、NDLOCR-Lite の版、OCR のモデルの版である。OCR の結果には、行ごとの本文、文字の確率、行の確信度、検出器の `confidence`、確信度の数え方の版を入れる。文字の層の取り出し方を変えても、OCR の結果は使い回せる。描画の識別が変われば、OCR の入力の画像が変わりうるので、使い回さない。
- **今の OCR の結果を移す:** 今の `page-*.json` のうち `ocr` が真のものは、同じ PDF の SHA-256、同じ `ocr_dpi`、同じ OCR の版のときだけ、新しい OCR の保存先に移して使い回す。条件が合わないものは、OCR をやり直す。今の結果には、描画した pypdfium2 の版が記録されていない。移すときは、描画の識別を「不明（rag 0.5 以前）」として記録し、移したあとで描画の識別が変われば使い回さない。つまり、移す 1 回だけは、描画の版が分からない結果を使い回す。描画の版の違いで OCR の結果が変わるかは確かめていない。それでも使い回すのは、作者の資料の OCR をすべてやり直すと時間がかかりすぎるためで、意図した割り切りである。
- **ページの情報を返す:** `job_status` の結果に `page_report` を足す。中身は、ページの数、判定ごとのページ、確かめるべきページ、OCR したページ、OCR の結果が空のページ、OCR の確信度が低いページ、確信度が不明のページ、確認の状態ごとのページ（反映待ちを含む）、台帳の確認の版と公開した確認の版、確信度の閾値と数え方の版、抽出の識別である。ページごとの OCR の詳しいことは `ocr_page_detail` で返す（上の「確認のツール」）。一覧の形は、上の「ページの一覧の形」のとおりにする（`job_status` に引数 `page_report_from` を足す）。確かめるべきページは、wiki と同じ関数と条件で数える。ジョブが失敗したときも、それまでに処理したページの `page_report` を、どこまで処理したかと一緒に保存して返す。今の rag は、すべてのページの OCR の結果が空だとジョブを失敗にし、例外の文字列だけを保存するので、失敗の理由に当たるページが分からない。
- **設定を返す:** `status` の結果に、今の設定（`ocr_mode`、`ocr_dpi`）と、wiki ごとの確認待ちのページの数を足す。
- **確認を受け取る:** MCP のツール `ocr_page_detail` と `decide_ocr_pages` を足す（上の「OCR の確信度とページの確認」）。
- **依存:** `pdfminer.six` を版を固定して足す。`pypdfium2` も、範囲（`>=5,<6`）ではなく版を固定する。
- **返す値:** `job_status` の結果に、抽出の識別を入れる。

### wiki と rag のそろい方

wiki は rag のスクリプトを読み込まない（rag は wiki に依存し、別のプラグインの内部のスクリプトは呼ばない決まりである）。そのため、ページごとの本文の取り出しと判定の関数を、両方に同じ中身で持つ。

info-hive-dev の `tests/` には、次の契約の試験を置く。

1. 同じ PDF を wiki と rag の関数に通し、すべてのページで、文字の層の本文の文字列、判定、判定の数値、本文の崩れの数が同じであることを確かめる。
2. wiki の出力そのものを確かめる。
   - 判定が `garbled`、`scan` のページの本文が出ていない。
   - `vertical` のページに 1 行が付いている。
   - 分けて読んだ出力をつなぐと、一度に出した出力と同じになる（ページの途中で分けた場合を含む）。
   - PDF を変えたあとに続きを読むと止まる。
3. rag の OCR の保存を確かめる。
   - 文字の層の識別だけを変えて取り込み直すと、OCR を呼ばずに保存した結果を使う。
   - 描画の識別を変えると、OCR をやり直す。
   - 今の形式の結果は、移す条件が合うときだけ移し、描画の識別を「不明」と記録する。
   - 移した結果は、描画の識別が移したときと同じあいだは使い回す。描画の識別が変わったあとは、移した結果も使わず、OCR をやり直す。移した結果を、もう一度移すことはない。
4. rag の `page_report` を確かめる。
   - 判定ごとのページと確かめるべきページが、wiki の `--json` と同じ番号になる。
   - OCR したページと OCR の結果が空のページが、OCR のスタブが返した結果と合う。
   - 範囲の数が 200 を超える PDF で、続きをたどるとすべての番号が取れる。
   - ジョブが途中で失敗したときも、それまでのページの `page_report` が返る。
5. 古い rag との組み合わせを確かめる。`page_report` を返さない rag の応答を使って、上の「rag を使うが、rag が `page_report` を返さないとき」の手順で、判定、確かめるべきページ、rag の本文が空のページが分かることを確かめる。`ocr_mode` が `always` で、判定が `text` のページの OCR の結果が空になった応答も試料に含める。
6. 試料には、[検証](../research/adr-0024-verification-2026-11-15.md)で使った公開の PDF（URL と SHA-256 で取り直す）と合成の PDF を使う。OCR の試験では、OCR を呼んだ回数を数えるために、OCR の代わりのスタブを使ってよい。
7. 本文が毎回同じになることを確かめる。距離の同じテキストボックスの組ができる合成の PDF と公開の PDF を、別々のプロセスで 3 回以上取り出し、すべてのページの本文の SHA-256 が同じになる。決め方を外すと違いが出ることも確かめ、試験が原因を捉えていることを示す。
8. OCR の確信度と確認を確かめる。
   - 行ごとに、文字の確率の数と終わりの記号の確率の数が、上の不変条件のとおりになる（長い行を分けて読んだ場合と、別の認識器で読み直した場合を含む）。
   - 確率をスタブで決めた OCR で、閾値より低い行のあるページだけが、確信度の低いページになる。認識した本文が空の行は、読めなかった行になり、そのページは確信度の低いページになる。
   - 確率のない OCR の結果（移した結果）は、確信度が不明のページになり、確信度の低いページにも、高いページにも数えない。
   - 同じ PDF を 2 つの wiki に登録し、片方で「直す」、もう片方で「却下する」を受け付けると、それぞれの wiki の索引と返す本文がそれに合い、共有の抽出の結果は変わらない。
   - OCR の本文の SHA-256 か、もとにした台帳の版が違う確認は、受け付けない。
   - 作り直しのジョブを、行を書く途中で止めると、検索は前の版の行を返し、`page_report` はそのページを反映待ちとして示す。再試行すると、新しい版が公開される。前の版の埋め込みの途中経過は使い回さない。
   - 作り直しの処理中に次の確認を受け付けると、処理のあとで、次の版も公開される。
   - 1 ページの PDF でそのページを却下すると、行が 0 の版が公開され、作り直しは失敗にならない。
   - 抽出の版を上げて索引を作り直しても、確認の結果が残る。OCR の本文が変わると、そのページが確認待ちに戻る。
   - 確認待ちと反映待ちのページの検索の結果に、それぞれの印が付く。

取り出し方か判定を変えるときは、wiki と rag の両方の `EXTRACT_REVISION` を同じ値に上げて変える。

契約の試験で分かるのは、試験した版の組み合わせと試料で一致することだけである。wiki と rag は別々に配られるので、利用者の手元では版がずれることがある（古い wiki と新しい rag など）。版がずれても、ページの区切りと番号は同じである。文字の層の本文は違いうるが、wiki のログと rag の `job_status` に抽出の識別が残るので、違いに気づける。rag が古く `page_report` や設定を返さないときは、「読めないページの扱い」の代わりの手順を使う。版を合わせることは、この ADR では強制しない。

### 決めないこと

- **Docling:** 既定にはしない。品質は上位だが、約 1.1 GB の依存と、1 ページに 1〜2 秒の時間がかかり、図の多いページで網羅と表の点を下げた。rag のワーカーで、利用者が選べる取り出し方として足すかは、別に決める。
- **NDLOCR-Lite の更新:** rag が固定しているコミット（e57f7c6）には、そのあとに入った縦書きの読み順の修正（a12fb49）が含まれていない。更新するかは、rag の側で別に決める。
- **表と数式:** pdfminer の表の点（3.4〜3.6）は、ADR-0024 の試作（4.0）より低い。数式は、どの方式でも崩れた。表を Markdown の表にすること（pdfplumber の `extract_tables` など）は、別に検討する。
- **ページを選んで OCR させる仕組み:** rag に足すかは、rag の側で決める。
- **OCR の確信度の閾値:** 承認の条件 5 で決める。
- **pdfminer への報告:** 距離の同じ組の順が番地で決まることを、pdfminer.six に報告するかは、別に決める。

## 承認の条件

次の 5 つを確かめてから承認する。1〜3 の測定の結果は、[承認の条件の測定](../research/adr-0025-measurement-2026-11-15.md)にある。

1. **長い PDF での時間とメモリ:** 500 ページ以上の公開の PDF を、製品と同じくページごとに取り出す。1 ページあたりの平均の時間（判定と取り出しの合計）が 0.5 秒以下で、プロセスのメモリの最大が 1 GB 以下であることを確かめる。図の多いページは 1 ページに数秒かかるので、ページごとの上限は設けない。代わりに、0.5 秒を超えたページの数と、最も遅いページの時間を記録する。「本文を毎回同じにする」の決め方を入れた版でも測る。
2. **ページの対応:** ページの判定（PDFium）と本文（pdfminer）が同じページを指すことを確かめる。試料の 7 つの PDF では、ページの数が一致した。回転したページ、ページツリーの入れ子、注釈だけのページを含む PDF でも確かめる。あわせて、判定に使った 10 ページで、「本文を毎回同じにする」の決め方を入れた版と入れない版の本文を比べ、違うページがあれば、判定の結果がそのまま使えるかを確かめる。
3. **本文の崩れの検出:** 試料の公開の PDF で、確かめるべきページの印が、`(cid:<数>)` を含むページ（BERT の 6 ページ目など）に付くことを確かめる。印の付いたページは、公開の試料のページの 3 割以下とする（今の条件で 33 ページ中 8 ページ、24%）。3 割を超えたら、条件を見直してから承認する。
4. **契約の試験:** 上の「wiki と rag のそろい方」の試験（OCR の保存、`page_report`、本文が毎回同じになること、OCR の確信度と確認を含む）を書いて通す。
5. **OCR の確信度の閾値:** 公開の PDF と合成の PDF だけを使い、行の確信度と、行の OCR の誤り（正解との編集距離が 1 以上の行）を比べて、閾値を決める。
   - **正解:** 合成の PDF では描いた文字、公開の PDF では、文字の層が正しいと目で確かめたページの文字の層とする。
   - **画像で区別できない符号（作者の決定、2026-11-19）:** 画像で字の符号を区別できない箇所に限り、元PDFの描画命令とフォントのCID対応を、正式な正解作成と監査の補助証拠として使える。画像を読む二系統には符号を伏せ、字の位置・個数・所属と周囲の本文を独立に確認する。固定画像、正規化と数値の合否は従来どおりとする。[次版の手順](../plans/adr-0025-condition5-source-anchored-reference-v10-2026-11-19.md)
   - **試料:** 合成の PDF には、解像度を下げたもの、ぼかしたもの、雑音を足したもの、傾けたものを含める。閾値を選ぶ資料と、確かめる資料に、測る前に分ける。分ける単位は、ページではなく原稿（合成では描いた文章、公開では PDF）とし、同じ原稿から作った画像（ぼかしたもの、雑音を足したものなど）は、同じ側に入れる。閾値は選ぶ資料だけで選ぶ。
   - **基準（測る前に決めておく）:** 確かめる資料で、合成と公開のそれぞれについて、次の 3 つを満たすこと。(a) 閾値より低い行のうち、誤りを含む行が 5 割以上。(b) 誤りを含む行のうち、閾値より低い行が 8 割以上。(c) 確信度の低いページが、OCR したページの 2 割以下。
   - **満たさないとき:** 確信度の数え方か、確認の単位（ページごと）を見直してから承認する。

## 理由

- **測った方式の中で、もっとも釣り合っていた。** 比べた 2 回の判定（2 回目と 3 回目）のどちらでも、総合と読み順で上位か並びだった。白書のポイントと概要の構成のページでは、読み順が 5 点だった。縦書きの官報の 2 ページ目では、OCR を除けば読み順がもっとも良かった（3 点、ほかの方式は 1 点）。
- **依存が小さい。** pip だけで入る純粋な Python のパッケージ（MIT、19.5 MiB）で、別のプログラムも torch も要らない。
- **wiki と rag の文字の層の本文がそろう。** 同じ識別で取り出せば、同じ PDF から同じ文字の層の本文とページ番号が出る。PDFium の文字の層に入る U+FFFE も、本文に入らなくなる。
- **縦書きのページも読める本文を出す。** ADR-0024 は縦書きのページの本文を出さなかった。pdfminer（縦書きの検出あり）は、縦書きの文字の層を行としてつなぐので、警告を付けて出す。
- **OCR の結果を守る。** OCR の結果を文字の層の抽出と分けて保存するので、取り出し方を変えても、時間のかかる OCR をやり直さずに済む。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| pdfminer（縦書きの検出あり）で本文、PDFium で判定と画像 | 採る |
| PDFium の文字の層で本文（ADR-0024） | 採らない。組版のソフトで作った日本語の資料で読み順が崩れ、U+FFFE が入る |
| Poppler か Xpdf の pdftotext | 採らない。別のプログラムと日本語の対応表を、利用者に入れてもらう必要がある |
| pdfminer の既定の設定 | 採らない。縦書きを 1 文字ずつ改行する |
| Docling | 既定にはしない（「決めないこと」） |
| すべてのページを NDLOCR-Lite で OCR する | 採らない。表と英語の論文で点が低く、1 ページに数秒かかる。縦書きのページには、rag の今の判定どおり使う |
| pdf_oxide | 採らない。白書で文の一部が抜け、読み順が低かった。版も 0.x である |
| pdfplumber の `extract_text` | 採らない。2 段組みの論文で左右の段を行ごとに混ぜた。表の取り出しは別に検討する |
| MarkItDown | 採らない。前のベンチマークで、2 段組み、スライド、表計算の PDF に、意味を変える誤りを作った |
| ページごとに、方式を選び分ける | 採らない。選び分ける規則を確かめる手立てがなく、wiki と rag をそろえるのも難しくなる |
| 判定も pdfminer で行う | 採らない。rag の今の判定と OCR の回し方を変えることになり、判定の閾値を確かめ直す必要がある。本文の崩れは、判定を変えない「確かめるべきページ」の印で補う |

## 見直す条件

- 承認の条件の測定で、時間、メモリ、ページの対応、本文の崩れの検出に問題が見つかったとき。
- 作成したソフトの違う PDF（Word、Google ドキュメント、日本語の LaTeX など）で、読み順が崩れる例が見つかったとき。
- 表や数式の崩れが、取り込みで実際に問題になったとき。
- Docling のような版面の解析が、軽く速くなったとき。
- OCR の確信度の低いページの確認が多すぎて、ユーザーが確かめきれないとき。または、確信度が実際の誤りと対応しない例が見つかったとき。
- pdfminer.six が、距離の同じ組の順を自分で決まった順にしたとき（こちらの決め方を外せるか確かめる）。
