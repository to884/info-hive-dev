## 背景

PDF を wiki に取り込む経路は 2 つあり、本文の取り出し方が違う。

| 経路 | 本文の取り出し方 |
| --- | --- |
| rag が使えるとき | rag のワーカーが、PDFium（pypdfium2）の文字の層をページごとに取り出し、ページを判定する（`rag_pdf.inspect_page`）。`ocr_mode` が `auto` なら、判定が `garbled`、`scan`、`vertical` のページを NDLOCR-Lite で OCR し、本文を置き換える。`always` ならすべてのページを、`off` なら OCR せず、OCR が要るページでエラーにする |
| rag を使わないとき | `ingest-workflow.md` の手順 2 で、`pdf-reading` スキルか、`pdftotext` か `pdfminer` を使う。どれを使うかはエージェントが選ぶ |

ADR-0024 は、rag を使わない経路も PDFium の文字の層にそろえることを提案した。公開の PDF で承認の条件を確かめると、条件を満たさなかった（[検証の報告](../research/adr-0024-verification-2026-11-15.md)）。PDFium は、版面の順ではなく、ファイルの中の文字の順に返していると考えられ、組版のソフトで作った日本の官公庁の資料で読み順が崩れた。行末のハイフンで分けた語には U+FFFE が入った。この 2 つは、rag の本文と索引にも同じく入っている。

そこで、同じ 10 ページ（LaTeX の論文、白書、官報）で、ほかの方式も比べた。判定は Sol（GPT-6.1 Sol）に、ページの画像を正解として、方式の名前を伏せて 3 回させた。点は 1〜5 で、10 ページの平均である。

| 方式 | 総合 | 読み順 | 表 | 文字の正しさ | 依存 | 1 ページあたりの時間 |
| --- | --- | --- | --- | --- | --- | --- |
| ADR-0024 の試作（PDFium の文字の層。`vertical` などのページは本文を出さない） | 3.2〜3.4 | 2.8〜3.0 | 4.0 | 4.1〜4.4 | 8.1 MiB | 約 0.01 秒 |
| pdfminer（縦書きの検出あり） | 3.5〜3.7 | 3.6〜3.7 | 3.4〜3.6 | 4.2〜4.4 | 19.5 MiB | 0.08〜0.18 秒 |
| pdfminer（既定） | 3.3 | 3.3〜3.4 | 3.2 | 3.7〜4.0 | 19.5 MiB | 約 0.1 秒 |
| Xpdf の pdftotext | 3.5 | 3.4〜3.6 | 3.0 | 3.8 | 別のプログラムと日本語の対応表が要る | － |
| Docling（OCR なし） | 3.4〜3.8 | 3.9〜4.0 | 3.4 | 4.3〜4.4 | 約 1.1 GB（torch を含む） | 1.2〜2.3 秒（準備に 13〜26 秒） |
| NDLOCR-Lite（全ページを OCR） | 2.9 | 3.5 | 2.2 | 3.2 | rag が使用中 | 1.4〜4.5 秒 |
| pdf_oxide | 2.3 | 2.2 | 2.8 | 3.7 | 約 12 MB | 約 0.01 秒 |
| pdfplumber（方向の指定なし） | 2.9 | 2.5 | 3.6 | 3.4 | pdfminer と同じ | 約 0.1 秒 |

最初の行は、生の PDFium の文字の層ではなく、ADR-0024 の仕様どおりに、判定が `vertical` などのページの本文を出さない試作の点である。官報の 2 ページ目の低い点には、本文を出さなかったことが含まれる。

ページの種類ごとに見ると、次のとおりだった。

- **日本の官公庁の資料:** ADR-0024 の試作だけが読み順を崩した（2〜3 点）。pdfminer（縦書きの検出あり）と Docling は、白書のポイントと概要の構成のページで 5 点だった。
- **縦書きの官報:** NDLOCR-Lite の OCR がもっとも良く（総合 4）、次が pdfminer（縦書きの検出あり）だった（総合 2〜3）。ほかは読み順が 1 点だった。pdfminer は、縦書きの検出がないと 1 文字ずつ改行した（官報の 1 ページで 2,225 行）。
- **英語の論文:** 表は ADR-0024 の試作と Docling が良く、pdfminer（縦書きの検出あり）はそれに次いだ。数式（分数、総和記号）は、どの方式でも崩れた。pdfminer は、総和記号を `(cid:80)` と出した。

この比較には限りがある。

- 判定したのは 10 ページで、各判定は 1 回ずつである。同じ方式の点も、判定のあいだで最大 0.4 動いた。平均の差の小さいものは、ぶれの範囲と読む。
- 公開の PDF の作成したソフトは 4 種類（pdfTeX、InDesign、記録なし、Acrobat Distiller）しか試していない。
- スキャンの PDF は合成だけで、実物は試していない。

## 決定

### 何をそろえ、何をそろえないか

| 対象 | そろえるか |
| --- | --- |
| ページの区切りと番号 | そろえる。どちらの経路でも、PDF のページの順に `p. 1` から番号を付ける。要約ページの根拠の位置（ページ番号）は、経路によらず同じに書ける |
| 文字の層の本文（pdfminer の取り出しの結果） | そろえる。ただし、同じ抽出の識別（下の「抽出の識別」）で取り出したときに限る。比べるのは、改行を `\n` にそろえた文字列で、ファイルのバイト列ではない |
| ページの判定 | そろえる。rag の今の `inspect_page`（PDFium）の判定を、同じ閾値で使う |
| 最終の本文 | そろえない。rag が OCR したページ（`auto` のときは判定が `garbled`、`scan`、`vertical` のページ、`always` のときはすべてのページ）では、rag の本文は OCR の結果になる。wiki は OCR をしないので、そのページの本文は rag と違う。判定が `garbled` と `scan` のページは、wiki は本文を出さない |

判定は、OCR に回すかと、本文を出すかを決める。そのため、判定を誤ると、出す本文が変わる。たとえば、横書きの表を 90 度回したページを `vertical` と誤ると、rag は OCR の結果を本文にする。wiki は、警告を付けて pdfminer の本文を出す。判定を `garbled` と誤ると、wiki は本文を出さない。

### 役割の分け方

| 役割 | 方式 |
| --- | --- |
| 文字の層の本文 | pdfminer.six の `extract_text` を、ページごとに、`LAParams(detect_vertical=True)` で呼ぶ。ほかの値は既定値にする |
| ページの判定 | rag の今の `inspect_page`（PDFium の文字の層から数値を数える）。判定のためだけに使い、その本文は使わない |
| 本文の崩れの検出 | pdfminer の本文で、`(cid:<数>)` と U+FFFD を数える。判定とは別の数値として持つ（下の「確かめるべきページ」） |
| OCR とその画像 | rag の今の NDLOCR-Lite と PDFium の描画。wiki は OCR をしない |

### 確かめるべきページ

判定（`kind`）とは別に、次のどれかに当たるページを「確かめるべきページ」とする。判定を変えないので、rag と判定がずれることはない。

- PDFium の `image_coverage` が 0.5 以上である（本文の大部分が画像かもしれない）。
- pdfminer の本文で、`(cid:<数>)` か U+FFFD が 1 つ以上ある（文字を復号できていない。数式の記号のことが多い）。

私用領域の文字は数えない。行頭の記号を記号のフォントで書いた資料では、ふつうに出てくるためである（白書の概要では、12 ページ中 8 ページに出た）。この条件では、検証の公開の 33 ページのうち 8 ページに印が付いた（BERT の数式のページ 2 つ、白書の概要の表紙とグラフのページ、官報の 4 ページ）。閾値（0.5 と 1 つ以上）は最初の値で、承認の条件の測定で見直す。

### wiki（rag を使わないとき）

wiki に `wiki_pdf.py` を足す。`uv run --script` で動かし、依存は `pdfminer.six` と `pypdfium2` で、どちらも版を `==` で固定する。

| 判定 | 出すもの |
| --- | --- |
| `text` | pdfminer の本文 |
| `vertical` | ページの本文の先頭に、縦書きのページで列の順が崩れることがあると書いた 1 行を付け、pdfminer の本文を続ける |
| `garbled` | 本文を出さず、PDFium が文字を復号できなかったページであることを書いた 1 行を出す。pdfminer の本文が読めるかは確かめていないが、信頼できないので出さない |
| `scan` | 本文を出さず、スキャンのページであることを書いた 1 行を出す |
| `blank` | 見出しだけを出す |

出し方は次のとおりにする。

- **形:** ページごとに `## p. <番号>`、空行、ページの本文を並べ、ページのあいだを `\n\n` でつなぐ。今の rag の `document.md` と同じつなぎ方である。
- **分けて読む:** 1 回の出力の文字数に上限を設ける。続きは `--from <PDF の SHA-256 の先頭 12 文字>:<ページ>:<ページの本文の中の文字の位置>` で読む。続きの出力は、ページの途中から本文だけを続け、見出しも縦書きの 1 行も出し直さない。SHA-256 が今の PDF と違えば、止まる。分けて読んだ出力をつなぐと、一度に出した出力と同じになる。
- **`--json`:** 全体の要約（PDF の SHA-256、ページの数、判定ごとのページの数と先頭の 200 個までの番号、確かめるべきページの数と先頭の 200 個までの番号、抽出の識別）を返す。ページごとの詳細（判定、判定の数値、本文の崩れの数、本文の SHA-256）は、`--pages` を付けたときだけ、その範囲を返す。
- **写し:** 取り出した本文の写しは作らない。
- **uv がないとき:** 止まって、uv が要ることを伝える。
- **手順の書き換え:** 手順から、`pdf-reading` スキル、`pdftotext`、`pdfminer` の直接の呼び出しを外す。Read は、図と版面、確かめるべきページ、判定が `text` 以外のページを見るときに使う。
- **記録:** 取り込みのログの行の下に、抽出の識別をサブ行で書く。

### 読めないページの扱い

判定が `text` 以外のページ、確かめるべきページ、OCR の結果が空のページがあれば、エージェントはページの番号と数をユーザーに伝える。エージェントがそれを知る経路は、経路ごとに次のとおりである。

| 経路 | ページの情報の取り方 |
| --- | --- |
| rag を使わないとき | `wiki_pdf.py --json` の全体の要約 |
| rag を使うとき | `job_status` の結果の `page_report`（下の「rag」）。`result.extracted_markdown` には、判定も印も入っていないので、それだけを読んではいけない |

そのうえで、rag が実際にできることに合わせて、次のように扱う。

| ページ | rag で OCR されるか | エージェントがすること |
| --- | --- | --- |
| 判定が `garbled`、`scan`、`vertical` | `ocr_mode` が `auto` か `always` なら OCR される。`off` ならジョブがエラーになる。OCR の結果が空のこともある（`page_report` の OCR の結果が空のページ） | rag で取り込むかをユーザーに聞く。今の `ocr_mode` を `status` の設定で確かめ（下の「rag」で足す）、`off` ならそのことを伝える。OCR の結果が空のページは、読めなかったページとして扱う |
| 確かめるべきページ（判定は `text`）、判定が `blank` | `auto` では OCR されない | Read でページの画像を見る。画像から読んだ内容を要約に使うときは、要約ページにそう書く |

rag の `ocr_mode` を `always` にすれば、すべてのページが OCR される。ただし、次のことから、この手順には入れない。ユーザーが `always` を使いたいと言ったときは、これらを伝える。

- `configure` でその PC の設定を変えることになる。すべてのページを OCR するので時間がかかり、未完了のジョブがあると設定は変えられない。
- OCR の設定は、索引の方針の指紋に入っている。設定を変えると、その PC のすべての wiki の索引が方針の違う索引になり、次の取り込みでその wiki の索引が空になる。ほかの PDF は、登録し直すまで検索の対象から外れる（ADR-0014）。
- rag のジョブは、登録したときの設定を持ち、その設定で動く。設定を変えても、すでにあるジョブ（`retry_job` で再試行するジョブを含む）は前の設定のまま動く。
- 新しい設定で OCR させるには、設定を変えたあとで、`register_pdf` で新しく登録する。

### rag

- **本文:** 判定が `text` のページの本文を、PDFium の文字の層から、pdfminer（縦書きの検出あり）の本文に変える。OCR したページの本文は、今と同じく OCR の結果を使う。
- **抽出の版:** `EXTRACT_REVISION` を `extract-v2` に上げる。ADR-0014 のとおり、すべての wiki の索引が取り込み直しの対象になる。
- **抽出の識別:** 抽出の識別を、`EXTRACT_REVISION`、pdfminer.six の版、`LAParams` の値、pypdfium2 の版の組にする。この識別を、文字の層の抽出の結果の鍵、保存したページ、索引の方針の指紋（`Config.fingerprint`）のすべてに入れる。識別が違う保存済みの結果と索引は使い回さない。識別を持たない保存済みの結果（今の形式のもの）は、識別が違うものとして扱う。
- **OCR の結果を別に保存する:** 今は、OCR の結果がページの抽出の結果（`page-*.json`）に入っていて、抽出の版を上げると、OCR もやり直しになる。これを分け、OCR の結果を別の鍵で保存する。鍵は、PDF の SHA-256、ページの番号、描画の識別（pypdfium2 の版と描画の dpi）、NDLOCR-Lite の版、OCR のモデルの版である。文字の層の取り出し方を変えても、OCR の結果は使い回せる。描画の識別が変われば、OCR の入力の画像が変わりうるので、使い回さない。
- **今の OCR の結果を移す:** 今の `page-*.json` のうち `ocr` が真のものは、同じ PDF の SHA-256、同じ `ocr_dpi`、同じ OCR の版のときだけ、新しい OCR の保存先に移して使い回す。条件が合わないものは、OCR をやり直す。今の結果には、描画した pypdfium2 の版が記録されていない。移すときは、描画の識別を「不明（rag 0.5 以前）」として記録し、移したあとで描画の識別が変われば使い回さない。つまり、移す 1 回だけは、描画の版が分からない結果を使い回す。描画の版の違いで OCR の結果が変わるかは確かめていない。それでも使い回すのは、作者の資料の OCR をすべてやり直すと時間がかかりすぎるためで、意図した割り切りである。
- **ページの情報を返す:** `job_status` の結果に `page_report` を足す。中身は、ページの数、判定ごとのページの数と番号、確かめるべきページの数と番号、OCR したページの番号、OCR の結果が空のページの番号、抽出の識別である。番号は、それぞれ先頭の 200 個までにし、それより多ければそのことを示す印を付ける。確かめるべきページは、wiki と同じ関数と条件で数える。
- **設定を返す:** `status` の結果に、今の設定（`ocr_mode`、`ocr_dpi`）を足す。
- **依存:** `pdfminer.six` を版を固定して足す。`pypdfium2` も、範囲（`>=5,<6`）ではなく版を固定する。
- **返す値:** `job_status` の結果に、抽出の識別を入れる。

### wiki と rag のそろい方

wiki は rag のスクリプトを読み込まない（rag は wiki に依存し、別のプラグインの内部のスクリプトは呼ばない決まりである）。そのため、ページごとの本文の取り出しと判定の関数を、両方に同じ中身で持つ。

info-hive-dev の `tests/` には、次の契約の試験を置く。

1. 同じ PDF を wiki と rag の関数に通し、すべてのページで、文字の層の本文の文字列、判定、判定の数値、本文の崩れの数が同じであることを確かめる。
2. wiki の出力そのものを確かめる。
   - 判定が `garbled`、`scan` のページの本文が出ていない。
   - `vertical` のページに 1 行が付いている。
   - 分けて読んだ出力をつなぐと、一度に出した出力と同じになる（ページの途中で分けた場合を含む）。
   - PDF を変えたあとに続きを読むと止まる。
3. rag の OCR の保存を確かめる。
   - 文字の層の識別だけを変えて取り込み直すと、OCR を呼ばずに保存した結果を使う。
   - 描画の識別を変えると、OCR をやり直す。
   - 今の形式の結果は、移す条件が合うときだけ移し、描画の識別を「不明」と記録する。
4. rag の `page_report` が、wiki の `--json` と同じページの番号を返す。
5. 試料には、[検証](../research/adr-0024-verification-2026-11-15.md)で使った公開の PDF（URL と SHA-256 で取り直す）と合成の PDF を使う。OCR の試験では、OCR を呼んだ回数を数えるために、OCR の代わりのスタブを使ってよい。

取り出し方か判定を変えるときは、wiki と rag の両方の `EXTRACT_REVISION` を同じ値に上げて変える。

契約の試験で分かるのは、試験した版の組み合わせと試料で一致することだけである。wiki と rag は別々に配られるので、利用者の手元では版がずれることがある（古い wiki と新しい rag など）。版がずれても、ページの区切りと番号は同じである。文字の層の本文は違いうるが、wiki のログと rag の `job_status` に抽出の識別が残るので、違いに気づける。版を合わせることは、この ADR では強制しない。

### 決めないこと

- **Docling:** 既定にはしない。品質は上位だが、約 1.1 GB の依存と、1 ページに 1〜2 秒の時間がかかり、図の多いページで網羅と表の点を下げた。rag のワーカーで、利用者が選べる取り出し方として足すかは、別に決める。
- **NDLOCR-Lite の更新:** rag が固定しているコミット（e57f7c6）には、そのあとに入った縦書きの読み順の修正（a12fb49）が含まれていない。更新するかは、rag の側で別に決める。
- **表と数式:** pdfminer の表の点（3.4〜3.6）は、ADR-0024 の試作（4.0）より低い。数式は、どの方式でも崩れた。表を Markdown の表にすること（pdfplumber の `extract_tables` など）は、別に検討する。
- **ページを選んで OCR させる仕組み:** rag に足すかは、rag の側で決める。

## 承認の条件

次の 4 つを確かめてから承認する。

1. **長い PDF での時間とメモリ:** 500 ページ以上の公開の PDF を、製品と同じくページごとに取り出す。1 ページあたりの時間が 0.5 秒以下で、プロセスのメモリの最大が 1 GB 以下であることを確かめる。
2. **ページの対応:** ページの判定（PDFium）と本文（pdfminer）が同じページを指すことを確かめる。試料の 7 つの PDF では、ページの数が一致した。回転したページ、ページツリーの入れ子、注釈だけのページを含む PDF でも確かめる。
3. **本文の崩れの検出:** 試料の公開の PDF で、確かめるべきページの印が、`(cid:<数>)` を含むページ（BERT の 6 ページ目など）に付くことを確かめる。印の付いたページは、公開の試料のページの 3 割以下とする（今の条件で 33 ページ中 8 ページ、24%）。3 割を超えたら、条件を見直してから承認する。
4. **契約の試験:** 上の「wiki と rag のそろい方」の試験（OCR の保存と `page_report` を含む）を書いて通す。

## 理由

- **測った方式の中で、もっとも釣り合っていた。** 比べた 2 回の判定（2 回目と 3 回目）のどちらでも、総合と読み順で上位か並びだった。白書のポイントと概要の構成のページでは、読み順が 5 点だった。縦書きの官報の 2 ページ目では、OCR を除けば読み順がもっとも良かった（3 点、ほかの方式は 1 点）。
- **依存が小さい。** pip だけで入る純粋な Python のパッケージ（MIT、19.5 MiB）で、別のプログラムも torch も要らない。
- **wiki と rag の文字の層の本文がそろう。** 同じ識別で取り出せば、同じ PDF から同じ文字の層の本文とページ番号が出る。PDFium の文字の層に入る U+FFFE も、本文に入らなくなる。
- **縦書きのページも読める本文を出す。** ADR-0024 は縦書きのページの本文を出さなかった。pdfminer（縦書きの検出あり）は、縦書きの文字の層を行としてつなぐので、警告を付けて出す。
- **OCR の結果を守る。** OCR の結果を文字の層の抽出と分けて保存するので、取り出し方を変えても、時間のかかる OCR をやり直さずに済む。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| pdfminer（縦書きの検出あり）で本文、PDFium で判定と画像 | 採る |
| PDFium の文字の層で本文（ADR-0024） | 採らない。組版のソフトで作った日本語の資料で読み順が崩れ、U+FFFE が入る |
| Poppler か Xpdf の pdftotext | 採らない。別のプログラムと日本語の対応表を、利用者に入れてもらう必要がある |
| pdfminer の既定の設定 | 採らない。縦書きを 1 文字ずつ改行する |
| Docling | 既定にはしない（「決めないこと」） |
| すべてのページを NDLOCR-Lite で OCR する | 採らない。表と英語の論文で点が低く、1 ページに数秒かかる。縦書きのページには、rag の今の判定どおり使う |
| pdf_oxide | 採らない。白書で文の一部が抜け、読み順が低かった。版も 0.x である |
| pdfplumber の `extract_text` | 採らない。2 段組みの論文で左右の段を行ごとに混ぜた。表の取り出しは別に検討する |
| MarkItDown | 採らない。前のベンチマークで、2 段組み、スライド、表計算の PDF に、意味を変える誤りを作った |
| ページごとに、方式を選び分ける | 採らない。選び分ける規則を確かめる手立てがなく、wiki と rag をそろえるのも難しくなる |
| 判定も pdfminer で行う | 採らない。rag の今の判定と OCR の回し方を変えることになり、判定の閾値を確かめ直す必要がある。本文の崩れは、判定を変えない「確かめるべきページ」の印で補う |

## 見直す条件

- 承認の条件の測定で、時間、メモリ、ページの対応、本文の崩れの検出に問題が見つかったとき。
