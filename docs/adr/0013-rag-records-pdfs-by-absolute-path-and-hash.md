# ADR-0013：rag は参照ルートを持たず、PDF を絶対パスと内容の SHA-256 で記録する

| 項目 | 内容 |
| --- | --- |
| 状態 | 提案 |
| 決定日 | 2026年11月7日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0007、ADR-0012、[日本語 PDF のローカル RAG の選択肢](../research/japanese-pdf-local-rag-options.md)（決定事項 12、第 6.9 節） |

## 背景

rag 0.3.0 は、PDF を「参照ルート」の下だけで扱う。`/rag:setup` で、PDF のあるフォルダに名前を付けて登録する（`configure` の `reference_roots={名前: 絶対パス}`）。台帳と wiki のソースのページには、PDF の場所を「ルートの名前と、そこからの相対パス」（例: `ebooks:Oreilly/xxx.pdf`）で記録する。この形は、2026年11月3日の決定（調査の決定事項 12）による。

参照ルートには 3 つの役目がある。

1. **可搬性**: 別の PC でパスが変わっても、名前と絶対パスの対応を直すだけで済む。
2. **読む範囲の制限**: MCP の `register_pdf` は、モデルから渡されたパスを読む。ルートの外は拒むので、任意のファイルを読まれない。
3. **原本への書き込みの防止**: 派生データとキャッシュがルートの中にあると拒む。

使ってみると、この仕組みは PDF の置き方に合わなかった。

- PDF はドライブのあちこちにある。ルートの外の PDF は「PDF が参照ルートにありません」で拒まれ、`/rag:setup` からやり直すことになる。
- ドライブ全体のような広いルートは、派生データの既定の置き場所（`%LOCALAPPDATA%`）がその中にあると拒まれる。作者の PC では `%LOCALAPPDATA%` が `D:\Users\...` にあるので、`D:\` をルートにできない。
- 可搬性が効くのは wiki の `raw:` だけである。台帳は PC ごとの `data_dir` にあり、別の PC には持っていかない。別の PC では、PDF の置き場所が違うのが普通である。

2026年11月7日、作者は参照ルートの設定を廃止すると決めた。あわせて、場所は絶対パスと内容の SHA-256 で記録し、0.3.0 の設定と台帳との互換は捨てると決めた。製品版の rag を使った台帳は、作者の PC にもない。

## 決定

| 対象 | 決定 |
| --- | --- |
| 入力 | `register_pdf` と `ingest_pdf` の `source` は、PDF の絶対パスにする。先頭の `~` は展開する。相対パスと「名前:相対パス」は受け付けない |
| 読む前の確認 | パスを解決する（シンボリックリンクをたどる）。解決したパスが通常のファイルで、拡張子が `.pdf`（大文字と小文字を問わない）で、先頭の 5 バイトが `%PDF-` であることを確かめる。派生データ（`data_dir`）、モデルのキャッシュ、uv のキャッシュの中にあるファイルは拒む |
| 書かない | rag は `data_dir` とキャッシュの外に書かない。今までどおりで、原本の場所には何も書かない |
| 台帳の場所のキー | `locations` の主キーは、解決した絶対パスを正規化した文字列にする。正規化は、Unicode の NFC にそろえたあと、`os.path.normcase` をかける（Windows では大文字と小文字を区別しない）。表示と読み込みには、解決した絶対パスをそのまま持つ |
| 文書の同一性 | 今までどおり、内容の SHA-256（`doc_id`）で決める。同じ内容を別のパスで登録したら同じ文書とし、もうないパスを台帳から外す（移動と改名） |
| 版の更新 | 今までどおり、同じパスの内容が変わったら新しい版に置き換え、古い版を出典にしていた wiki のページを要再確認にする |
| 返す値 | 取り込みの結果と検索の結果の `raw` は、解決した絶対パスにする。内容の SHA-256 を `sha256` として足す |
| wiki のソースのページ | `raw:` に `result.raw`（絶対パス）を、新しいキー `raw_sha256:` に `result.sha256` を書く。別の PC では、同じ PDF を登録し直すと、SHA-256 で同じ文書と分かる |
| 設定 | `reference_roots` を設定と `configure` から外す。`/rag:setup` は、派生データの保存先、モデル、検索の設定だけを扱う |
| 互換 | 0.3.0 の設定ファイルに残った `reference_roots` は読まない。`configure` で保存し直すと消える。0.3.0 の台帳（`catalog.sqlite` の `documents` に `root` の列がある）を開いたら、理由と消す場所を書いて止まる。自動では消さない。0.3.0 の未完了のジョブも再開しない |
| 版 | rag は 0.4.0 にする。wiki は、取り込みの手順（`raw_sha256:` と、`/rag:setup` の案内をやめること）を直した版を出す |

## 理由

- 登録の手間をなくす。どこにある PDF でも、絶対パスを渡せば登録できる。ドライブ全体を登録するために、派生データの置き場所を動かすこともない。
- 可搬性は、内容の SHA-256 で足りる。台帳は PC ごとにあり、別の PC の rag は PDF を登録し直す。そのとき SHA-256 が `raw_sha256:` と一致すれば、同じ出典だと分かる。ルートの名前と絶対パスの対応を PC ごとに保つ手間は、これに見合わない。
- 読む範囲の制限は、PDF であることの確認で代える。rag は読むだけで、原本に書かない。読めるのは PDF の形をしたファイルに限られ、抽出した本文は、利用者が頼んだ取り込みの結果として wiki に返るだけである。派生データの中の PDF を拒むので、rag が自分の作ったファイルを取り込むこともない。
- 互換を捨てても、作り直すデータはない。互換の層を持たなければ、台帳の形とコードが 1 つで済む。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 絶対パスと内容の SHA-256 で記録する | 採る |
| 設定はなくし、初めて見るフォルダーの PDF を登録したときに、その親のフォルダーを名前付きのルートとして自動で足す | 採らない。`raw:` は「名前:相対パス」のまま残るが、別の PC で名前と絶対パスの対応を直す手間が残る。名前が重なったときの扱いも要る |
| ルートは残し、ルートの外の PDF を登録しようとしたら、ルートの追加を利用者に確かめる | 採らない。登録の手間が減るだけで、設定は残る |
| パスを記録せず、SHA-256 だけを記録する | 採らない。同じパスの内容が変わったことの検出と、ジョブの再開に、パスが要る |
| 0.3.0 の「名前:相対パス」と `reference_roots` を読めるように残す | 採らない（作者の判断）。製品版の台帳を使った人がいない |

## 影響

- rag: `scripts/rag_config.py`（`roots` と `reference()` を外し、PDF の確認を足す）、`scripts/rag_index.py`（台帳の列、返す値、0.3.0 の台帳の検出）、`scripts/rag_jobs.py`、`scripts/rag_server.py`（`configure` の引数）、`commands/setup.md`、`README.md`、`CHANGELOG.md`、`plugin.json`。
- wiki: `commands/ingest.md`、`skills/info-hive/references/ingest-workflow.md`（`source` は絶対パス、`raw_sha256:` を書く、`/rag:setup` で参照ルートを登録する案内を消す）。`raw:` は `wiki_graph_extract.py` が `raw:<値>` のノードにするので、絶対パスでも動く。
- 開発リポジトリ: `tests/rag/` の試験と検証のスクリプトから `reference_roots` を外す。
- wiki のソースのページに、PC のフォルダーの構成（利用者名を含むことがある）が絶対パスとして残る。wiki を公開するときは、これが見える。今までの「名前:相対パス」なら、ルートより上は見えなかった。
- 調査の決定事項 12 のうち、「名前を付けた参照ルートを設定し、ルートの名前と相対パスで記録する」部分は、この ADR で置き換える。PDF を動かさず、複製せずに参照すること、常に最新版だけを残すことは変えない。
- ADR-0012 の rag の移行（索引を wiki のサーバーに頼む形）とは独立している。台帳の SQLite は、移行のあとも rag が持つ。

## 見直す条件

- 複数の PC で同じ wiki を使い、`raw:` の絶対パスが PC ごとに食い違うことが問題になったとき。
- 公開する wiki に、絶対パスを載せたくない利用者が出てきたとき。
