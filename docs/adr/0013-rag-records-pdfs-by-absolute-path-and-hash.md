# ADR-0013：rag は参照ルートを持たず、PDF を絶対パスと内容の SHA-256 で記録する

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月7日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0007、ADR-0012、[日本語 PDF のローカル RAG の選択肢](../research/japanese-pdf-local-rag-options.md)（決定事項 12、第 6.9 節） |

## 背景

rag 0.3.0 は、PDF を「参照ルート」の下だけで扱う。`/rag:setup` で、PDF のあるフォルダーに名前を付けて登録する（`configure` の `reference_roots={名前: 絶対パス}`）。台帳と wiki のソースのページには、PDF の場所を「ルートの名前と、そこからの相対パス」（例: `ebooks:Oreilly/xxx.pdf`）で記録する。この形は、2026年11月3日の決定（調査の決定事項 12）による。

参照ルートには 3 つの役目がある。

1. **可搬性**: 別の PC でパスが変わっても、名前と絶対パスの対応を直すだけで済む。
2. **読む範囲の制限**: MCP の `register_pdf` は、モデルから渡されたパスを読む。ルートの外は拒むので、利用者が登録したフォルダーの外は読まない。
3. **原本への書き込みの防止**: 派生データとキャッシュがルートの中にあると拒む。

使ってみると、この仕組みは PDF の置き方に合わなかった。

- PDF はドライブのあちこちにある。ルートの外の PDF は「PDF が参照ルートにありません」で拒まれ、`/rag:setup` からやり直すことになる。
- ドライブ全体のような広いルートは、派生データの既定の置き場所（`%LOCALAPPDATA%`）がその中にあると拒まれる。作者の PC では `%LOCALAPPDATA%` が `D:\Users\...` にあるので、`D:\` をルートにできない。
- 可搬性が効くのは wiki の `raw:` だけである。台帳は PC ごとの `data_dir` にあり、別の PC には持っていかない。別の PC では、PDF の置き場所が違うのが普通である。

2026年11月7日、作者は参照ルートの設定を廃止すると決めた。あわせて、場所は絶対パスと内容の SHA-256 で記録し、0.3.0 の設定と台帳との互換は捨てると決めた。製品版の rag を使った台帳は、作者の PC にもない。

## 決定

### 登録と読み込み

| 対象 | 決定 |
| --- | --- |
| 入力 | `register_pdf` と `ingest_pdf` の `source` は、PDF の絶対パスにする。先頭の `~` は展開する。相対パスと「名前:相対パス」は受け付けない。改行などの制御文字（C0 と C1、U+0085 を含む）を含むパスも、渡されたパスと解決したパスの両方で拒む（frontmatter に書くと、wiki の手書きのパーサーと PyYAML で値が食い違う）。ジョブには、解決したパスではなく、渡されたままの絶対パスを記録し、ワーカーで同じように確かめ直す。ネットワークドライブの PDF は解決すると UNC になるので、解決したパスを記録すると、ワーカーの確かめ直しで拒まれる |
| 拒むパス | UNC パス（`\\server\share\...`）と、Windows のデバイスのパス（`\\?\`、`\\.\`）は、解決する前に拒む。Windows では `/\server/...` のように区切りを混ぜても UNC になるので、文字列の先頭に加え、組み立てたパスのドライブでも判定する。モデルが渡したパスで、知らないサーバーに接続して認証情報を送ることを防ぐ。ドライブ文字を割り当てたネットワークドライブは、利用者が自分で用意したものなので受け付ける。Windows で、ネットワークドライブでないドライブのパスが UNC に解決されたとき（ローカルのフォルダーに置かれたリンクがネットワーク上のファイルを指すとき）も拒む。ただし、解決の途中でそのサーバーへの接続は起きうる。そうしたリンクを置けるのは、その PC に書き込める者に限られる |
| 登録のときの確認 | パスを解決し（シンボリックリンクとジャンクションをたどる）、解決したパスを `lstat` で調べる。通常のファイルで、拡張子が `.pdf`（大文字と小文字を問わない）で、派生データ（`data_dir`）、モデルのキャッシュ、uv のキャッシュの外にあることを確かめる。中身は読まない。ファイルの識別子（`st_dev` と `st_ino`）、大きさ、更新時刻をジョブに記録する。解決と `lstat` は待つことがある（応答しないネットワークドライブなど） |
| 読み込みのときの確認 | ワーカーは、解決したパスを 1 回だけ開き、開いたファイルの `fstat` が、開く直前の `lstat` と同じファイル（`st_dev`、`st_ino`、大きさ、更新時刻）であることを確かめる。開いたファイルは、登録したときに記録したファイルの識別子、大きさ、更新時刻とも同じでなければならない。登録のあとで親のフォルダーを差し替えられても、確かめていないファイルを読まないためである。識別子を返さないファイルシステム（`st_ino` が 0）では、大きさと更新時刻だけを比べる。そのファイルからすべてのバイト列を読み、読み終えたあとの `fstat` も同じであることを確かめる。先頭の 5 バイトが `%PDF-` であることは、この読んだバイト列で確かめる。SHA-256 と抽出も、同じバイト列に対して行う |
| 同意の層 | どの PDF を読むかを利用者が決めるのは、ホストのツールの許可（Claude Code が `register_pdf` の呼び出しを確かめる）と、wiki の取り込みの手順（利用者が指定したパスを渡す）である。上の確認は、読めるものを PDF に限るだけで、利用者が選んだフォルダーに限ることはしない。利用者が `register_pdf` を許可の一覧に入れて確認を省いたときは、モデルが利用者の指定と違う PDF を渡しても、人は呼び出しを見ない。wiki の手順はモデルへの指示であり、rag は渡されたパスと利用者の指定を照らさない。参照ルートより弱いことを受け入れる |
| 書く場所 | rag が書くのは、`data_dir` とキャッシュ、版が変わったときに要再確認の印を付ける wiki のページだけである。PDF の場所には何も書かない |

### 台帳

| 対象 | 決定 |
| --- | --- |
| 場所のキー | `locations` の主キーは、解決した絶対パスの文字列をそのまま使う。行には、そのファイルの識別子（`st_dev` と `st_ino` を文字列にしたもの）も持つ。Unicode の正規化も、大文字と小文字の同一視もしない。NFC と NFD の別の名前のファイルや、大文字と小文字を区別するフォルダーの `A.pdf` と `a.pdf` を、同じ場所と取り違えないためである。Windows の `Path.resolve()` は、ドライブ文字の大小と 8.3 形式の短い名前を、実在の名前にそろえる |
| 同じファイルの別名 | 同じファイルが別の綴りやハードリンクで 2 つのキーになることはある。取り込むときは、登録した場所に加え、同じファイルの識別子を持つほかの場所の行も、新しい版の文書に移す。ただし、記録した識別子だけでは決めず、公開の直前にその場所を調べて、同じ識別子、大きさ、更新時刻のときだけ別名とみなす。片方を独立したファイルに置き換えてリンクの関係が切れたあと（取り込みの途中を含む）に、残っている古い版を消さないためである。もうない別名の行は台帳から外す。片方の名前で書き換えて取り込んでも、もう片方の名前が古い版の出典に残らない |
| 文書の同一性 | 今までどおり、内容の SHA-256（`doc_id`）で決める。同じ内容を別のパスで登録したら同じ文書とし、もうないパスを台帳から外す（移動と改名） |
| 文書のパス | `documents` には代表のパスを持たない。文書のパスは `locations` から引く。最後に登録を確かめた順に見て、記録した大きさと更新時刻が今のファイルと合う場所を使う。合う場所がなければ `raw` を返さない（`null`）。中身が変わったかもしれない場所を、古い版の出典として返さないためである。0.3.0 は `documents` に代表のパスを持ち、同じ内容の A と B を登録したあと B だけを書き換えると、古い本文の出典が書き換えた B を指した |
| 版の更新 | 今までどおり、同じパスの内容が変わったら新しい版に置き換え、古い版を出典にしていた wiki のページを要再確認にする。ほかの場所に古い版が残っていれば、古い版の文書は残す。古い版の文書を消すときは、その版の索引の行と抽出の結果に加え、内部の途中経過（`catalog.sqlite` の `jobs` の行）も消す。内容を古い版に戻して取り込んだとき、途中経過が残っていると、埋め込みを飛ばして索引に何も入らないためである（0.3.0 にもあった不具合） |
| ジョブの重ね方 | 同じパス、大きさ、更新時刻、設定、ページ、題名の登録は、受け付け済み、処理中、一時停止のジョブがあればそれを返す。完了、失敗、キャンセルのジョブしかなければ、新しいジョブを作る。0.3.0 は完了したジョブを返していたので、大きさと更新時刻を変えずに中身を差し替えた PDF を取り込み直せなかった。新しいジョブは内容を読み直し、SHA-256 が同じなら抽出を省く |

### 返す値と wiki

| 対象 | 決定 |
| --- | --- |
| 返す値 | 取り込みの結果と検索の結果の `raw` は、解決した絶対パスを `/` 区切りにした文字列にする（Windows では `C:/Books/x.pdf`）。内容の SHA-256 を `sha256` として足す |
| wiki のソースのページ | `raw:` に `result.raw` を、新しいキー `raw_sha256:` に `result.sha256` を書く。値は二重引用符で囲み、frontmatter の決まり（`wiki_text.py`）どおり `\` を `\\`、`"` を `\"` と書く。`/` 区切りなので、Windows のパスにも `\` は入らない |
| グラフ | `wiki_graph_extract.py` は `raw:` の値を `raw:<値>` のノードにするので、絶対パスでも動く。`raw_sha256:` は使わない。別の PC で登録した同じ PDF は、グラフでは別のノードになる。グラフは `raw:` を NFC にそろえるので、名前が NFC と NFD だけ違う 2 つの PDF は、台帳では別の場所でも、グラフでは同じノードになる |

### 設定、互換、版

| 対象 | 決定 |
| --- | --- |
| 設定 | `reference_roots` を設定と `configure` から外す。`/rag:setup` は、派生データの保存先、モデル、検索の設定だけを扱う |
| 古いデータ | 新しい版は、ジョブの台帳を `jobs-v2.sqlite` に、wiki ごとの台帳と索引を `wikis-v2/<wiki のハッシュ>/` に置く。0.3.0 の `jobs.sqlite` と `wikis/` は開かない。0.3.0 の未完了のジョブは再開せず、設定の変更も止めない。`status` は、0.3.0 のデータが `data_dir` に残っていれば、その場所と、消してよいことを伝える。自動では消さない |
| 設定の変更を塞ぐジョブ | 設定の変更を塞ぐのは、受け付け済み、処理中、一時停止のジョブだけにする。失敗したジョブは、明示的な再試行でしか動かず、動くときは自分の設定の写しを使うので、塞がない。0.3.0 は失敗したジョブも塞いでいたので、公開を始めたあとに失敗したジョブ（キャンセルできない）が、設定の変更を塞ぎ続けた |
| 古い設定 | 0.3.0 の設定ファイルに残った `reference_roots` は読まない。`configure` で保存し直すと消える |
| 方針の指紋 | `Config.fingerprint` の方針の名前を `rag-v1` から `rag-v2` にする |
| 版 | rag は 0.4.0 にする。wiki は、取り込みの手順（`raw_sha256:`、エスケープ、`/rag:setup` の案内をやめること）を直した版を出す |

## 理由

- 登録の手間をなくす。どこにある PDF でも、絶対パスを渡せば登録できる。ドライブ全体を登録するために、派生データの置き場所を動かすこともない。
- 可搬性は、内容の SHA-256 で足りる。台帳は PC ごとにあり、別の PC の rag は PDF を登録し直す。そのとき SHA-256 が `raw_sha256:` と一致すれば、同じ出典だと分かる。ルートの名前と絶対パスの対応を PC ごとに保つ手間は、これに見合わない。
- 場所のキーは、取り違えないことを優先する。別のファイルを同じ場所とみなすと、版の更新と要再確認の印を誤る。同じファイルを別の場所とみなしても、文書は SHA-256 で 1 つになるので、害は場所の行が増えることだけである。
- 確認と読み込みを同じファイルで行う。パスを何度も開き直すと、確認したファイルと読んだファイルが違うことがありうる。
- 古いデータは、ファイル名を変えて開かない。0.3.0 の台帳とジョブを検出して止めると、止めたジョブが設定の変更、キャンセル、再試行を塞ぐ。開かなければ、その状態が生じない。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 絶対パスと内容の SHA-256 で記録する | 採る |
| 設定はなくし、初めて見るフォルダーの PDF を登録したときに、その親のフォルダーを名前付きのルートとして自動で足す | 採らない。`raw:` は「名前:相対パス」のまま残るが、別の PC で名前と絶対パスの対応を直す手間が残る。名前が重なったときの扱いも要る |
| ルートは残し、ルートの外の PDF を登録しようとしたら、ルートの追加を利用者に確かめる | 採らない。登録の手間が減るだけで、設定は残る |
| パスを記録せず、SHA-256 だけを記録する | 採らない。同じパスの内容が変わったことの検出と、ジョブの再開に、パスが要る |
| 場所のキーを NFC と `os.path.normcase` で正規化する | 採らない。NFC と NFD で別の名前のファイルや、大文字と小文字を区別するフォルダーの別のファイルを、同じ場所とみなす |
| 場所のキーをファイルの識別子（`st_dev` と `st_ino`）にする | 採らない。ネットワークドライブや一部のファイルシステムでは識別子が安定しない。パスが変わったことの検出にもパスが要る |
| 0.3.0 の台帳を検出して、理由を書いて止まる | 採らない。止めたジョブが設定の変更、キャンセル、再試行を塞ぐ。ジョブを受け付けたあと台帳を作る前に止まった場合は、検出もできない |
| 0.3.0 の「名前:相対パス」と `reference_roots` を読めるように残す | 採らない（作者の判断）。製品版の台帳を使った人がいない |

## 影響

- rag: `scripts/rag_config.py`（`roots` と `reference()` を外し、パスの確認を足す）、`scripts/rag_index.py`（台帳の列、`documents` の代表のパスをやめる、読み込みの確認、返す値、置き場所の名前）、`scripts/rag_jobs.py`（`jobs-v2.sqlite`、ジョブの重ね方）、`scripts/rag_worker.py`（登録のときの大きさと更新時刻の確認）、`scripts/rag_server.py`（`configure` の引数、`status` の古いデータの案内）、`commands/setup.md`、`commands/status.md`、`README.md`、`CHANGELOG.md`、`plugin.json`。
- wiki: `commands/ingest.md`、`skills/info-hive/references/ingest-workflow.md`（`source` は絶対パス、`raw_sha256:` を書く、エスケープ、`/rag:setup` で参照ルートを登録する案内を消す）。
- 開発リポジトリの試験: `tests/rag/` の試験と検証のスクリプトから `reference_roots` を外す。次の試験を足す。
  - NFC と NFD の別の名前の PDF を、別の場所として扱う
  - 大きさと更新時刻を変えずに中身を差し替えた PDF を、取り込み直せる
  - 同じ内容の A と B を登録し、B だけを書き換えたあと、古い版の出典が A を指す
  - UNC パスと、派生データの中の PDF を拒む
  - 先頭が `%PDF-` でないファイルを拒む
  - 0.3.0 の `jobs.sqlite` と `wikis/` を開かず、`status` がそれを伝える
  - ハードリンクの片方で書き換えた PDF を取り込むと、もう片方も新しい版を指す
  - 内容を H、G、H と戻して取り込んでも、H の索引の行がそろう
  - Windows で、ローカルのリンクがネットワーク上のファイルを指すときに拒む
  - 登録のあとで同じ大きさと更新時刻の別のファイルに差し替えたら、読まない
  - 公開を始めたあとに失敗したジョブが、設定の変更を塞がない
  - ハードリンクの関係が切れたあと（取り込みの途中を含む）に片方を書き換えても、残っている古い版を消さない
  - 消えた別名の行が、古い版を残し続けない
  - ジョブが渡されたままのパスを記録し、ワーカーがそれで取り込める
  - 区切りを混ぜた UNC とデバイスのパスを、解決する前に拒む
  - 制御文字を含むパスを拒む
  - 大きさと更新時刻を変えずに中身を書き換えた PDF を、新しいジョブで取り込み直せる
  - `raw` が `/` 区切りで、`sha256` を返す
  - wiki の frontmatter に書いた `raw:` と `raw_sha256:` を、wiki の手書きのパーサーとグラフの PyYAML が同じ値で読む
- wiki のソースのページに、PC のフォルダーの構成（利用者名を含むことがある）が絶対パスとして残る。wiki を公開するときは、これが見える。今までの「名前:相対パス」なら、ルートより上は見えなかった。
- 調査の決定事項 12 のうち、「名前を付けた参照ルートを設定し、ルートの名前と相対パスで記録する」部分は、この ADR で置き換える。PDF を動かさず、複製せずに参照すること、常に最新版だけを残すことは変えない。
- ADR-0012 の rag の移行（索引を wiki のサーバーに頼む形）とは独立している。台帳の SQLite は、移行のあとも rag が持つ。

## 見直す条件

- 複数の PC で同じ wiki を使い、`raw:` の絶対パスが PC ごとに食い違うことが問題になったとき。
- 公開する wiki に、絶対パスを載せたくない利用者が出てきたとき。
- ホストのツールの許可を通さずに、`register_pdf` を呼ぶ経路ができたとき。
