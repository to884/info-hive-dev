# ADR-0007：RAG は MCP、共通コア、永続ジョブで構成する

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月3日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | [実行方式の比較](../research/rag-execution-architecture/brainstorm-diverge-converge.md)、[日本語 PDF 向けローカル RAG の調査](../research/japanese-pdf-local-rag-options.md) |

## 背景

`rag@info-hive` は `wiki@info-hive` に依存し、wiki が PDF を取り込むことを起点に、抽出、OCR、埋め込み、索引更新を実行する。
長時間かかる処理と、検索や状態取得の呼び出しをどう接続するかを、24 案、6 系統に分けて比較した。

ユーザーは、Claude Code を閉じた場合は進捗を保存して処理を止め、次回起動時に再開する方式を選んだ。
そのうえで、比較レポートの「MCP＋共通コア＋永続ジョブ」の案を採用し、今回は記録にとどめるよう指示した。

## 決定

| 対象 | 決定 |
| --- | --- |
| 全体構成 | 比較レポートの案 14「共通コアと短い登録 API」を採用する |
| MCP | PDF の登録、検索、ジョブの状態取得など、Claude Code から操作する窓口にする |
| 共通コア | RAG の処理本体を独立した Python コアに置き、MCP、CLI、ワーカーから同じ処理を使う |
| CLI | 共通コアを呼び、PoC、再実行、診断に使う |
| 永続ジョブ | PDF の参照情報と処理要求を保存し、ワーカーが抽出、必要な OCR、チャンク化、埋め込み、索引更新を進める |
| 起点 | wiki の PDF 取り込み手順から、短い登録 API を明示的に呼ぶ。一般的な PDF 閲覧操作をフックで推測して起点にしない |
| 受付と完了 | ジョブを保存した状態を「受付済み」とし、索引化の完了と区別する |
| 中断と再開 | Claude Code の終了時に進捗を保存して停止する。次回、`rag` が有効なセッションで MCP 接続が成功したときに未完了ジョブを再開する。明示的にキャンセルしたジョブは自動再開しない |
| 常駐サービス | OS の常駐サービスは初期構成に含めない |
| 今回の作業範囲 | 採用決定の記録のみとする。実装と PoC は再開しない |

## 理由

MCP を窓口にすると、Claude Code は構造化された検索結果とジョブの状態を受け取れる。
処理本体を共通コアに分けることで、Claude Code を起動せずに CLI から同じ処理を試験できる。

永続ジョブに受付と進捗を保存することで、セッションの終了後も次回の再開に必要な情報を残せる。
wiki の登録処理から明示的にジョブを作るため、単なる PDF の閲覧とインジェストを区別できる。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 同期 MCP 呼び出しで全処理を行う | 長時間処理の進捗保存と再開を別に設計する必要がある |
| CLI のみで索引化と検索を行う | 試験には使いやすいが、検索ごとのモデル読み込みを含めた性能検証が必要になる |
| 一般的なツール操作をフックで検知する | PDF の閲覧と登録を、ツールの引数だけから区別しにくい |
| 独立デーモンや OS サービスを動かす | セッション終了後も処理を続ける要件が生じた場合に見直す |

## 影響と未決事項

この決定で確定するのは全体構成である。
ワーカーを MCP と同じプロセスに置くか子プロセスにするか、ジョブの保存方式、モデルの保持と共有は、詳細設計と PoC の対象として残す。
MCP Tasks の採否も未決とする。

LanceDB、Qdrant、埋め込みモデル、OCR の比較 PoC は未実施である。
検索時間、メモリ、容量、復旧動作の目標を達成したという判断は、この決定に含めない。
既存の試作コードも未検証の状態にあり、今回は変更しない。

実装を再開する際は、比較レポートの P0〜P4 を検証計画の出発点にする。
