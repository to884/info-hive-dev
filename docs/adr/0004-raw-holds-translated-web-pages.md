# ADR-0004：Web ページは訳文と図の説明を raw に置き、原文は出所とハッシュで記録する

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月3日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | 要件定義書の F-I03、F-I10〜F-I15、§7、S-01、AC-P18。`docs/research/web-page-ingest-brainstorm.md` のクラスタ A〜E |

## 背景

wiki プラグインの `/wiki:ingest` は URL を引数に受け付けるが、Web ページを取りに行く手順はなく、ユーザーが Obsidian Web Clipper などで保存した Markdown を前提にしていた（`info-hive-wiki/skills/info-hive/references/ingest-workflow.md` L19）。画像は読むだけで、wiki に残す手段がなかった（同 L33）。

これまで `raw/` は「手を加えない原本」として扱ってきた。`SKILL.md` L35 は「LLM は読むだけで、変更しない」とし、要件定義書 §7 は「原資料の内容は取り込み後に変更しない」としている。要件 F-I03 も「原資料を保存し、取得日時、由来、内容ハッシュを記録する」としていた。

一方、ユーザーは、日本語でない Web ページは日本語に訳して取り込み、画像には別の LLM があとで読んで分かる説明を添えたいと考えている。訳文と説明はモデルが作るものなので、「手を加えない原本」という `raw/` の考えと、そのままでは合わない。

## 決定

| 項目 | 決定 |
| --- | --- |
| raw/ に置くもの | HTML の本文を Markdown に変えたもの。日本語でないページは、その訳文。本文の画像と、各画像の直後に置く `> <モデルの表示名> 補足: ` の説明 |
| 原文 | 保存しない。訳文の先頭の frontmatter に、URL、題名、取得日時、原文 HTML の SHA-256、何に対するハッシュか、原文の言語、訳したモデルの表示名、取得に使ったスクリプトを記録する |
| 取得の手段 | プラグインに標準ライブラリだけで書いた `wiki_fetch.py` を足す。HTML の取得、SHA-256、本文の抽出、Markdown 化、画像のダウンロード、frontmatter の出力、言語判定の材料の報告を行う。残った雑音の削除、言語の判定、翻訳、図の説明はモデルが行う |
| 翻訳 | 段落ごとに訳す。見出しの階層、コードブロック、URL、識別子、固有名詞の英語表記は変えない |
| 画像 | 本文の中の画像を `raw/assets/<ソースのスラッグ>/` に出現順の連番で保存し、元の URL を Markdown の title 属性に残す。小さい画像と本文の外の画像は保存しない |
| 再取り込み | `source_sha256` を比べ、同じなら何もしない。違えば別版として扱う |
| raw の不変性 | 保存した訳文は、ほかの原資料と同じく取り込み後に変えない。訳の誤りは、再取得して別版として直す |

## 理由

- 訳文を raw に置くと、wiki のソースページの引用と型付きグラフの根拠を訳文から取れる。根拠の照合は wiki のソースページの本文に対して行う（`wiki_graph_lint.py` L335）ので、照合は訳文どうしで一致する。原文のまま置くと、英語の根拠と日本語の要約が並び、照合が通らない。
- 原文を保存しない代わりに、原文 HTML の SHA-256 を記録すれば、同じ内容かの確認（F-I08）はできる。訳文に対してハッシュを取ると、同じ原文から別の訳ができたときに別の内容と判定されるので、ハッシュは原文に対して取る。
- Claude Code の WebFetch は、取得した HTML そのものを返さず、小さなモデルが要約した結果を返す。ハッシュも取れず、画像も保存できない。ブラウザのツールも、ファイルを保存する手段がない。どちらも Claude Code にしかなく、ほかのエージェントでスキルを使う人は再現できない。スクリプトなら、どの環境でも同じ結果になる。
- 標準ライブラリだけで書くのは、`CONTRIBUTING.md` L33 の「新しい補助の処理には標準ライブラリを優先する」に合わせるためである。本文抽出の品質が足りないときは、`uv run --script` で依存を固定する既存の仕組みに乗せて、`trafilatura` などを使う案に切り替えられる。
- 図の説明をモデルの表示名つきで書くのは、人が書いた説明と区別し、あとで別のモデルが読んだときに、どのモデルの解釈かを分かるようにするためである。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| 原文と訳文を別ファイルで両方保存する | ユーザーが訳文だけを残すと決めた。容量が 2 倍になり、どちらを `raw:` に書くかも決める必要がある |
| 1 ファイルに原文と訳文を並べる | 検索で英語と日本語が混ざり、読みにくい |
| WebFetch やブラウザのツールだけで取る | ハッシュと画像の保存ができない。Claude Code 以外で再現できない |
| `trafilatura` を固定して使う | 本文抽出の品質は高いが、依存が大きい。自前の変換で足りないときの切り替え先として残す |
| 出所をソースページの `x_wiki.provenance` にだけ書く | raw のファイルだけを見たときに出所が分からず、再取り込みのときにスクリプトがハッシュを読めない |
| 原文 HTML も `raw/assets/` に保存する | F-I03 をそのまま守れるが、訳文だけを残すという決定に反する。容量も増える |

## 影響

- 要件 F-I03 を、「原資料の出所を記録する。PDF などは原本を保存し、Web ページは本文の Markdown（日本語でなければ訳文）を保存する」に改めた。F-I10〜F-I15 を足した。§7 と S-01 に追記した。
- `raw/` は「原本または、原本から機械とモデルが作った訳文」を置く場所になる。`SKILL.md` と `architecture.md` の raw の説明を、実装のときに直す。
- 実装では、`wiki_fetch.py` の新設、`commands/ingest.md` と `ingest-workflow.md` の手順、`SKILL.md` の起動条件（URL の依頼の例）を直す。詳細は `docs/research/web-page-ingest-brainstorm.md` §5 にある。
- 根拠の照合が訳文どうしになるので、英語のページを取り込む評価セットを足し、訳文からの引用が一致することを確かめる。
- 描画に JavaScript が要るページは、スクリプトで本文を取れない。ブラウザのツールで補う手順を書き、頻度を見て扱いを決める（O-15）。ブラウザを使うときは、ユーザーがふだん使っているブラウザを使う。認証情報がそこに入っているためで、ツールが用意する別のブラウザではログインが要るページを取れない。ログインが要るページの本文には非公開の情報が含まれうるので、共有範囲は S-03 と S-04 で確認する。
- Web ページから取り込んだ画像と svg は信頼しない入力として扱い、svg は `wiki/` に写さない（S-01）。

## 見直す条件

- 自前の変換で本文を取り切れないサイトが目立つとき。`trafilatura` などの依存を固定して使う案を見直す。
- 原文を参照する必要（訳の検証、法的な記録）が出たとき。原文 HTML を `raw/assets/` に保存する案を見直す。
- `raw/` を Foam などほかのツールが索引化して、frontmatter つきの訳文を知識ページと取り違えるとき。要件 §3.3 の除外設定で防ぐが、効かない場合は置き場所を見直す。
