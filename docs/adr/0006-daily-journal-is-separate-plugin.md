# ADR-0006：日々の記録は wiki と別のプラグイン `log` にする

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認。保存先とノートの置き場所は ADR-0008 で置き換え済み |
| 決定日 | 2026年11月3日 |
| 改訂 | 2026年11月5日：日付ノートの frontmatter の例の `type: daily` を `type: "daily"` に改めた。wiki の仕様では、文字列の値を二重引用符で囲む（`SCHEMA.md.template` の 69 行目） |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | `docs/research/daily-journal-methodology-options.md`（方法論の検討）、`docs/research/daily-journal-decision-matrix.md`（構成と置き場所の決定行列）、ADR-0003（プラグインごとにリポジトリを分ける） |

## 背景

info-hive に、日々の予定、タスク、メモを記録する機能を足す。依頼の要件は次の 6 つである。

- 書き散らしても、後で LLM が整理できる
- 記入が負担にならない
- エージェントが入力を支援する
- 1 日が 1 ファイル
- 作業メモに開始時刻、終了時刻、タスクの状態、一行の内容を書く
- Claude Code のデスクトップ版アプリから入力する

既存の `wiki` プラグインは、取り込んだ資料から知識のページを作るもので、日付ノートやタスクを扱う型がない。wiki の lint は被リンクのないページを全て孤立として報告する（`wiki_lint.py` の 280 行目）。日付ノートを wiki に入れると、孤立の指摘が毎日増える。

方法論は 16 件を採点し、構成と置き場所は決定行列で比べた。その結果をもとに、決定者が以下を決めた。

## 決定

| 項目 | 決定 |
| --- | --- |
| 置き場所 | 新しいリポジトリ `to884/info-hive-log` にプラグイン `log` を置く。コマンドは `/log:<名前>` で呼ぶ。wiki のコードは変えない |
| 名前 | リポジトリ名は `info-hive-log`、プラグイン名は `log` にする。`wiki` と同じく、リポジトリ名から `info-hive-` を除いたものをプラグイン名にする。導入の指定は `log@info-hive` になる |
| 方法論 | 1 日 1 ファイル（Daily Notes）に、作業の切れ目ごとに時刻付きの一行を書く（Interstitial Journaling）。未完了の繰り越しは Bullet Journal の Migration に、週次の見直しは GTD に倣い、エージェントのコマンドが受け持つ |
| 状態の書き方 | Markdown 標準のチェックボックス `[ ]` `[x]` だけを使う。補助の状態は行末の `@wait(理由)`、`@drop`、`@from(YYYY-MM-DD)` で書く。`[/]` や `[>]` のような拡張の記号は使わない |
| 時刻の書き方 | 開始と終了を 1 行に `09:12-10:40` と書き、行の先頭に置く。終了のない `10:45-` は作業中を表す |
| 作業メモとタスク | 別の節に書く。作業メモはその時間に何をしたかを一行で簡潔に書き、詳細はタスクの側に書く |
| タスクの節 | 「前日からの繰り越し」「本日のタスク」「次回への繰り越し」の 3 つの小節に分ける。「次回への繰り越し」は、翌日以降に回すタスクの欄である |
| 問題と突発事項 | その日に起きた問題や突発的な出来事を書く節を設ける |
| 保存先 | グローバル（`~/daily/`）とプロジェクト（`<プロジェクト>/daily/`）の両方を選べるようにし、既定はグローバルにする。パスは既定値と設定で扱い、仕様に固定しない |
| テンプレート | 日付ノートのテンプレートは Foam のテンプレートの置き場 `.foam/templates/daily-note.md` に置く。VS Code の Foam で日付ノートを開いたときも、`log` のコマンドで作ったときも、同じテンプレートを使う |
| 知識の取り出し | 日付ノートから wiki に直接は入れない。ノウハウなどは `<保存先>/notes/` にノートとして書き出し、ユーザーが編集する。wiki に入れるかは、ユーザーが `/wiki:ingest` で決める |
| フックによる自動記録 | 保留にする。最初の版には入れない |

1 日 1 ファイルの形は次のとおりである。節の見出しは日本語の固定の名前にし、スクリプトはこの見出しで節を探す。frontmatter のキーと `type` の値は英語にする（AGENTS.md の方針 B）。

```markdown
---
type: "daily"
title: "2026-11-03"
date: 2026-11-03
tags: []
created: 2026-11-03
updated: 2026-11-03
---

## 予定
- 10:00-11:00 定例

## タスク

### 前日からの繰り越し
- [ ] 問い合わせに返信する @wait(先方の回答待ち) @from(2026-11-02)

### 本日のタスク
- [ ] log プラグインの決定事項を ADR にまとめる
  - 決定行列の結果を反映する
  - テンプレートの置き場所を Foam に合わせる

### 次回への繰り越し

## 作業メモ
- [x] 09:12-10:40 決定行列の採点
- [ ] 10:45- ADR の下書き

## 問題・突発事項
- 11:20 CI が Windows で失敗した。原因は改行コード

## メモ
- 09:40 lint の孤立判定は、被リンクのないページ全てが対象

## ふりかえり
```

## 理由

- **別のプラグインにした理由。** wiki は、どのページも被リンクを持ち、取り込むたびに厳選して書くことを前提にしている。1 日に何十回も追記する日付ノートはこの前提と合わない。wiki に入れると、lint と検索の両方に例外を足し続けることになる。決定行列では別のプラグイン（8.40 点）が 1 位で、wiki のページ型にする案（5.51 点）はどの重みでも最下位だった。
- **方法論の組み合わせ。** 方法論の採点では、Interstitial Journaling（109 点）、Daily Notes（107 点）、Engineering daybook（104.5 点）、Bullet Journal（102 点）が上位を占めた。GTD、PARA、Zettelkasten は書く時点で分類先を決めさせるので、入力が重くなる。それぞれ受け持つ層が違うので、書く側と整理する側に分けて組んだ。
- **標準のチェックボックスにした理由。** GitHub Flavored Markdown のタスクリストが認めるのは空白と `x` だけで、拡張の記号はただの文字として表示される。
- **作業メモとタスクを分けた理由。** 作業メモは時間の記録として簡潔に残したい。タスクの説明や途中の判断まで同じ行に書くと、作業メモが読みにくくなる。決定者の判断である。
- **名前を `log` にした理由。** コマンドには必ずプラグイン名が付くので、プラグイン名が長いと毎回の入力が長くなる。入力の軽さは要件の中で最も重く見ている。単数形にしたのは、既存の `wiki` と揃え、`/log:start` のようにコマンドとして自然に読めるようにするためである。名前は決定者が決めた。
- **既定をグローバルにした理由。** 日々の記録は、作業するリポジトリをまたいで 1 か所にあるほうが探しやすい。wiki の既定はプロジェクトなので、ここは wiki と既定が逆になる。
- **テンプレートを Foam に置いた理由。** 利用者は VS Code と Foam で日付ノートを開くこともある。テンプレートが 1 つなら、どちらの経路で作っても同じ形になる。
- **wiki に直接入れない理由。** 日付ノートから取り出した内容は、そのままでは知識のページとして粒度も表現も揃っていない。ユーザーが `notes/` で手を入れてから wiki に入れるかを決めるほうが、wiki の質を保てる。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| wiki にページ型 `type: daily` を足す | 日付ノートが孤立として報告され、検索結果にも作業ログが混ざる |
| wiki プラグインに別のスキルとして同居させる | コマンドが `/wiki:log` になり、wiki の操作ログ `log.md` と紛らわしい。日付ノートの変更のたびに wiki の版が上がる |
| Agent Skill 1 つだけで配る | 自然文での呼び出しは、起動するかどうかが安定しない。版の管理も弱い |
| 状態を拡張チェックボックス（`[/]` `[>]` `[-]`）で表す | GitHub などの表示で記号がそのまま文字として出る |
| 作業メモとタスクを同じ節に書く | 作業メモに詳細が混ざり、時間の記録として読みにくくなる |
| 日報の三部構成（朝の予定、夕方の実績と所感） | 開始と終了の時刻が残らず、作業メモの要件を満たさない |
| 日付ノートから wiki に直接昇格させる | 粒度と表現の揃わない内容が wiki に入る |
| プラグイン名を `daily` にする | 検討の途中で使っていた仮の名前。決定者が `log` を選んだ |
| プラグイン名を `info-hive-activity-log` や `info-hive-activity-logs` にする | コマンドが `/info-hive-activity-log:start` のように長くなる。複数形は、コマンドとして読んだときに不自然になる |

## 影響

- ADR-0003 の手順で、`to884/info-hive-log` を作り、このリポジトリのサブモジュール `info-hive-log/` にする。`info-hive-marketplace/.claude-plugin/marketplace.json` の `plugins` に項目を足し、AGENTS.md に `log` の開発の節を足す。
- メモの節に追記するコマンドは、方法論レポートでは `log` と呼んでいた。プラグイン名と重なって `/log:log` になるので、別の名前（たとえば `memo`）にする。
- プラグインのスクリプトは、Foam のテンプレートを読んで日付ノートを作る。そのため、Foam のテンプレートの変数のうち、少なくとも `$FOAM_DATE_YEAR`、`$FOAM_DATE_MONTH`、`$FOAM_DATE_DATE` を自分で置き換える必要がある。テンプレートの frontmatter にある `foam_template` のブロック（`name`、`description`、`filepath`）も、作った日付ノートからは除く。Foam 自身がこのブロックを除くかは確かめていない。
- テンプレートの置き場は Foam のワークスペースの直下の `.foam/templates/` なので、保存先によって変わる。グローバルなら `~/daily/.foam/templates/daily-note.md` になる。プロジェクトならプロジェクトの直下の `.foam/templates/daily-note.md` になり、`filepath` で `daily/` の下を指す。すでに `daily-note.md` がある場合は、上書きせずに利用者に知らせる。
- `notes/` のノートは、wiki の frontmatter の必須の 5 項目（`type`、`title`、`tags`、`created`、`updated`）を持たせ、元になった日付ノートを記録する。そうしておけば、`/wiki:ingest` の素材にそのまま渡せる。
- 方法論レポートで提案した `promote`（wiki への昇格）は、`notes/` にノートを書き出すコマンドに置き換える。

## 未決の事項

- **作業メモとタスクの結び付け方。** 作業メモとタスクを別の節に書くので、作業メモの行がどのタスクの作業かを示す手段が要る。決定行列の R3 の案のように、タスクに短い識別子（例：`^t2`）を付け、作業メモの行の末尾にも同じ識別子を付ける方法を提案する。識別子はコマンドが付け、手で書くときは省略してよいことにする。設計書で決める。
- **コマンドの名前。** 問題と突発事項を書くコマンドと、`notes/` にノートを書き出すコマンドの名前は、設計書で決める。

## 見直す条件

- 1〜2 週間使ってみて、作業メモとタスクの書き分けが入力の負担になったとき。作業メモにタスクを兼ねさせる形（方法論レポートの元の案）に戻すかを見直す。
- wiki の検索で日付ノートや `notes/` を探したくなったとき。決定行列の P5 の案（wiki 側に、指定したディレクトリを孤立の判定から外す設定を足す）を検討する。
- フックによる自動記録の必要が出たとき。
