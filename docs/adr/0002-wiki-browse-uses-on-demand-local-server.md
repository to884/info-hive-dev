# ADR-0002：`/wiki:browse` は、必要なときだけ起動するローカルサーバーで作る

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認。作る順序と書き出しは ADR-0010 で置き換え済み |
| 決定日 | 2026年11月3日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0001、要件定義書の D-03・F-G06・AC-D02・O-11 |

## 背景

info-hive が作る LLM Wiki は、YAML の frontmatter を持つ Markdown のファイル群で、ページどうしは `[[slug]]` 形式の wikilink でつながる。VS Code やテキストエディタで読むと、frontmatter がそのまま見え、wikilink をたどりにくく、被リンクもわからない。そこで、Wiki を整形して表示する閲覧コマンド（仮称 `/wiki:browse`）を加えることにした。

依頼で重視すると示された要件は、ローカル PC で動くこと、将来の拡張性、日本語で表示が崩れないことの 3 つである。拡張の方向として、日本語の全文検索、グラフと被リンク、RAG 検索との統合、複数 Wiki の横断表示の 4 つを重視する。

選択肢は 2 段階で調べた。まず 96 の案を 7 つのクラスタに分けて部品ごとに採点した（`docs/research/llm-wiki-browse-options.md`）。次に、現状維持と Obsidian を含む 8 つの構成を決定行列で比べた（`docs/research/llm-wiki-browse-decision-matrix.md`）。

## 決定

`/wiki:browse` を次の構成で作る。決定行列の構成 B に当たる。

| 項目 | 決定 |
| --- | --- |
| 表示の経路 | Python の標準ライブラリの HTTP サーバーを 127.0.0.1 で起動し、既定のブラウザで開く。Claude desktop ではブラウザペインで開ける |
| 起動の既定 | 必要なときだけ起動し、操作がない状態が続いたら終了する。常駐は既定にしない |
| Markdown の変換 | markdown-it-py と mdit-py-plugins を使う。生の HTML は出力しない設定にする |
| リンクの解決 | `wiki_lint.py` と `wiki_search.py` の `resolve_link()` を共通モジュールに切り出し、描画でも同じ規則を使う |
| frontmatter | `wiki_text.py` の `canonical_meta()` で日本語の別名キーをそろえてから描く |
| 検索 | `wiki_search.py`（BM25 と埋め込み）をサーバー経由で呼ぶ |
| 書き出し | 既定ではファイルに書き出さず、ページを開いたときに変換する。静的 HTML の書き出し（構成 A）は副機能にする |
| 閲覧専用 | Wiki を書き換える API を持たない。閲覧の操作で Wiki のファイルを変えない |
| 対応 OS | Windows・macOS・Linux |
| 作る順序 | 第 1 段階で読む画面を作り、次に日本語の全文検索を加える。全体のグラフ、複数 Wiki、RAG 統合、静的 HTML の書き出しはその後にする |

## 理由

- 決定行列の加重合計で、構成 B は 8.2 点で 1 位だった。2 位の静的 HTML（7.0 点）に約 18% の差がある。重みと点を乱数でゆらした 20,000 回の試行では、92% で 1 位になった。
- B が上回るのは、重みの大きい日本語の正しさ、拡張性、info-hive の規則との整合の 3 基準である。差の大部分は拡張性から来ている。重視する 4 方向の拡張を、どれもサーバーの側に加えられるのは B だけである。
- Wiki の規則に合わせられることが大きい。既製の静的サイト生成器（Quartz、Zensical、MkDocs、Docsify）と Obsidian は、wikilink の大文字小文字、NFD の扱い、日本語の別名キーのどれかで info-hive の規則と食い違う。Obsidian で日本語のコーパスを開いて確かめると、未解決のリンクをクリックするだけで Wiki に空のページができた（決定行列の第4.2節）。
- 合成した日本語の Wiki で測ると、起動から最初のページを出せるまでは 1,000 ページで約 1.1 秒、3,000 ページで約 3.8 秒と見積もれた（決定行列の第4.1節）。
- 新しく加える依存は、markdown-it-py と mdit-py-plugins（どちらも MIT）だけで、Python 3.10 以上と uv の前提を変えない。

## 検討した選択肢

| 選択肢 | 加重合計 | 採らなかった理由 |
| --- | --- | --- |
| A 静的 HTML を `file://` で開く | 7.0 | `file://` ではブラウザが別のファイルを取得できず、検索と RAG 統合ができない。B の部品で作れるので、副機能として残す |
| D 現状維持（VS Code と Foam） | 6.6 | 開発の負担はないが、frontmatter がそのまま見え、読みにくさが解決しない |
| E Obsidian で開く | 6.1 | 画面の完成度は高いが、リンクの規則が食い違い、閲覧の操作で Wiki のファイルが増える |
| C4 Docsify | 5.5 | リンクの規則を JavaScript で作り直すことになり、info-hive の規則とずれる |
| C1 Quartz v5 | 5.2 | Node.js 22 以上が要り、wikilink の照合で大文字小文字を区別しない。日本語の別名キーも解釈しない |
| C2 Zensical | 5.1 | アルファ版で、Python 3.11 以上が要る。グラフと被リンクを持たない |
| C3 MkDocs と Material for MkDocs | 4.8 | Material は保守のみの状態で、MkDocs 2.0 に移れない |

## 影響

良い影響：

- lint と画面でリンクの解決が一致し、どちらかでだけリンク切れになることがない。
- 日本語の全文検索、RAG 統合、複数 Wiki を、同じサーバーに順に加えられる。

悪い影響と、その対策：

- 画面、サーバー、安全対策を自前で作って保守する。選択肢レポートでは、Python 1,000〜1,500 行と JavaScript・CSS 300〜500 行と見積もった（推定）。
- 最初の画面の完成度は、Quartz や Obsidian に及ばない。第 1 段階の範囲を絞り、PoC で使い勝手を確かめる。
- Claude Code は終了時にバックグラウンドの処理を止める。サーバーは Claude Code のセッションの間だけ動くものとして設計する。
- ポートを開くので、ADR-0001 の 3 条件を守る対策（127.0.0.1 への固定、起動ごとのトークン、Host ヘッダーの確認、書き込みの API を持たないこと）を実装する。

守ること：

- 第 1 段階の合格の目安は、選択肢レポートの第7.2節のとおりとする。とくに、未解決リンクの一覧が `wiki_lint.py` の結果と一致すること、1,000 ページで 5 秒以内に表示できること、127.0.0.1 以外への通信が 0 件であることを確かめる。
- コマンドを加えるときは、`info-hive-marketplace/.claude-plugin/marketplace.json` のコマンドの本数、`info-hive-wiki/docs/commands.md`、`README.md`、`SKILL.md`、`CHANGELOG.md` もあわせて更新する。

## 見直す条件

次のどれかが起きたら、本 ADR を見直す。

- PoC で、第 1 段階の合格の目安を満たせない
- 拡張の 4 方向のどれも使わないと決まる。その場合は、静的 HTML（構成 A）で足りる
- 自前の画面の保守の負担が、見積もりを大きく超える。決定行列では、開発と保守の負担の重みを 31% 以上にすると、現状維持が 1 位になる
