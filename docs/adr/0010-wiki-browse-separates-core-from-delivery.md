# ADR-0010：`/wiki:browse` は Wiki を解釈する中核と表示の方式を分け、どの方式でも同じ契約で動かす

| 項目 | 内容 |
| --- | --- |
| 状態 | 提案 |
| 決定日 | 未定 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0001（3 条件）、ADR-0002（本 ADR が補う）、ADR-0005（図の表示）、ADR-0007（rag の構成）、ADR-0008（作業領域）、ADR-0009（グラフ層）、ADR-0012（wiki の MCP サーバー）、ADR-0013（`raw:` の絶対パス）、要件定義書の F-G06・AC-D02・S-07、`docs/agent-runs/2026-11-05-wiki-browse-viewer-agnostic-design/`（4 体のエージェントによる設計、相互レビュー、総括）、[未決と実装前の PoC](../research/wiki-browse-adr-0010-poc-2026-11-07.md) |

## 背景

ADR-0002 は、`/wiki:browse` を必要なときだけ起動するローカル HTTP サーバー（決定行列の構成 B）で作ると決めた。静的 HTML の書き出しは副機能とした。

その後、閲覧の手段を次の 3 つのどれかにすることになった。どれを採っても作り直しにならない設計が求められた。

- ローカル HTTP サーバー
- Obsidian のような専用のビューワ（デスクトップアプリ）。実装言語はデスクトップアプリを作れるものにし、移植性も考える
- 静的 HTML

この設計を 4 体のエージェント（Claude Opus 5.5、Claude Fable 5.1、GPT-6.1 Sol、GPT-6 Astra）に独立に検討させ、相互に敵対的なレビューをさせ、総括をまとめた。4 体は独立に同じ骨格に達した。Wiki の解釈を 1 か所に置き、3 つの方式はその出力を表示する薄いアダプタにする、という骨格である。レビューでは、骨格を壊しうる事実と、契約に足すべき規則が見つかった。

コードの事実は、本体のチェックアウトのサブモジュールで確かめた（`info-hive-wiki` 3028923、`info-hive-rag` 3541ec4）。worktree のサブモジュールは空だった。

2026年11月7日、wiki 0.6.0（`info-hive-wiki` 36a4089）と rag 0.4.0（`info-hive-rag` 6a760b9）で事実を確かめ直し、実装前の PoC を行った（[未決と実装前の PoC](../research/wiki-browse-adr-0010-poc-2026-11-07.md)、試作は `poc/browse/`）。その間に ADR-0012（wiki が 127.0.0.1 の MCP サーバーを持つ）と ADR-0013（ソースのページの `raw:` が PDF の絶対パスになる）が承認され、未決の 4 に案が加わり、`raw:` の扱いが新しい未決になった。本文の行番号は、断りがなければ 36a4089 と 6a760b9 のものである。

## 決定

### 構成

| 項目 | 決定 |
| --- | --- |
| 中核 | Wiki の解釈を wiki プラグインの Python の 1 か所に置く。対象は、ページの走査、frontmatter の正規化（`canonical_meta()`）、リンクの解決（`resolve_link()`）、見出し ID、被リンク、型付きの関係、Markdown から HTML への変換（生の HTML は出さない）、診断である。表示の側は Markdown を解釈しない |
| アダプタ | ローカル HTTP サーバー、デスクトップアプリの IPC、静的 HTML の生成器を、中核の出力を届けるだけの薄い層にする。どの方式も中核の規則を書き直さない |
| 中核の呼び方 | Python 以外で書いたアプリからも使えるように、中核は子プロセスとして呼べる形（UTF-8 を明示した JSON の入出力）にする。Python のアダプタは import してよい |
| 契約の基準 | 3 方式でいちばん厳しい `file://` に合わせる |
| 静的 HTML の位置付け | 副機能ではなく、サーバー、アプリと並ぶ 1 つの方式とする。ADR-0002 の「書き出し」の行を置き換える。サーバーで開いたときに変換する既定の動作は変えない |
| ADR-0002 との関係 | 構成 B は、最初に作るアダプタとして残す。ADR-0002 のうち変えるのは「作る順序」と「書き出し」の 2 行だけである。Markdown の変換（markdown-it-py）、閲覧専用、ADR-0001 の対策などのほかの行は保つ |

### 画面の契約

| 項目 | 決定 |
| --- | --- |
| リンク | ページ間のリンクは相対の href だけで書く。同じ HTML を、`file://`、`http://127.0.0.1:<port>/<token>/…`、アプリの独自スキームのどれで開いても動かす |
| スクリプト | classic な `<script src>` だけを使う。ES モジュール、`fetch`、Web Worker を前提にしない。検索の索引などのデータは `data/*.js` として書き出し、`<script src>` で読む |
| ナビゲーション | 各ページに埋め込まず、共有の `nav.js` を読み込む。JavaScript がないときのために `<noscript>` で `index.html` へのリンクを残す |
| 事前に描く範囲 | ページの本文、メタ欄、被リンク、ページごとの関係表、未解決リンクは、中核が描いた HTML に含める。JavaScript を切っても読める |
| 外部への通信 | しない。CDN を使わない。CSP で外部からの読み込みを禁じる |
| サーバーのトークン | URL のパスの先頭に置く。相対リンクが自然に引き継ぐので、ページの HTML を方式ごとに変えずに済む |
| 複数 Wiki | ADR-0002 では拡張の方向の 1 つで、決定の行はない。本 ADR では、Wiki の識別子を URL のパス（`/w/<wiki-id>/…`）に含めて切り替える。相対リンクだけで閉じているので、`file://` でも成り立つ |

### データの契約

| 項目 | 決定 |
| --- | --- |
| ページの識別子 | NFC にそろえた POSIX の相対パスから `.md` を除いたものを論理的な識別子にする。出力のファイル名と URL の名前は、中核の 1 つの関数（仮称 `export_name()`）だけで決める。名前の規則は「未決の事項」で決める |
| リンクの状態 | 解決済み、未解決、`ambiguous` を区別する。`ambiguous` は、重複したスラッグへのパスのないリンクで、どちらかのページへ勝手に移動しない。判定は lint の `duplicate_slugs` と同じにする |
| 見出し | 見出しの存在の確認を、ページの解決と別の規則にする。見出し ID の生成（NFC、重複したときの連番）も中核で決める。`resolve_link()` はページまでしか解決しない |
| 契約の版 | 出力に契約の版（仮称 `protocol_version`）を持たせ、アダプタが互換性を確かめる。未対応の版を受け取ったアダプタは表示せずに止まる |
| 世代 | 出力に世代の識別子と生成日時を持たせる。新しい世代を作り終えてから切り替え、途中の生成物を見せない |
| 能力の宣言 | 検索の方式（`live`、`embedded`、`none`）、RAG、複数 Wiki、変更の反映などを `capabilities` で宣言し、使えない機能は画面に出さない。生成物の情報（世代など）と、それを開くホストの能力を分けて持つ。持ち運べる生成物に、絶対パスの Wiki のルートを入れない |
| 状態の区別 | 「使えない」「古い」「0 件」を区別して返し、画面でも区別して示す |
| 検索の結果 | 方式によらず、`wiki_search.py --json` の結果の形にそろえる |
| Wiki のルート | スキルと同じ順で解決する（ユーザーが指定したパス、プロジェクトの指示、グローバルの指示、現在のプロジェクトの `wiki/`。`SKILL.md` L21）。`wiki/` などの場所を決め打ちしない。スクリプトの既定は、lint と search と同じ `wiki_workspace.default_wiki_or_exit()`（作業領域の設定の `dirs.wiki`、なければ `./wiki`。wiki 0.5.0 から）を使う |
| 埋め込むデータ | `data/*.js` やページに埋め込む JSON は、`</script>`、U+2028、U+2029 などをエスケープする |

### 安全と閲覧専用

| 項目 | 決定 |
| --- | --- |
| 共通の条件 | ADR-0001 の 3 条件と AC-D02 を、3 方式に共通の条件にする。書き込みの API を持たず、未解決リンクをクリックしてもファイルを作らない |
| サーバー | ADR-0002 の対策（127.0.0.1 への固定、起動ごとのトークン、Host ヘッダーの確認）を保つ |
| アプリ | ポートを開かない stdio の IPC を既定にする。外部の URL はアプリの中で開かず、確かめてから OS のブラウザに渡す（S-07） |
| 静的 HTML | `<meta>` の CSP を付ける。書き出し先は「未決の事項」で決める |

### 合格の条件

| 項目 | 決定 |
| --- | --- |
| 交換できることの確認 | 試験用の Wiki で、3 方式のリンクの移動、被リンク、診断の結果が一致することを、実際に動かして確かめる |
| 閲覧専用の確認 | 閲覧の操作の前後で Wiki のファイルのハッシュが変わらないこと、外部への通信が 0 件であること（サーバーでは 127.0.0.1 以外への通信が 0 件）を、3 方式に共通の試験で確かめる |
| HTML のバイト一致 | 生成器の回帰検査にだけ使う。同じ HTML でも、基準の URL、CSP、WebView の権限で動作は変わるので、交換できることの証明には使わない |

### 作る順序

ADR-0002 の「作る順序」を次のように改める。どの方式に決まっても、1〜3 は無駄にならない。

1. `resolve_link()` と `clean_link_target()` を共通モジュールに切り出す
2. 中核、ページの HTML のテンプレート、日本語の CSS を作る
3. 第 1 段階（ページの表示、ナビゲーション、メタ欄、被リンク、関係表、未解決リンク）を、静的に描ける形で完成させる
4. 選んだ方式のアダプタを作る。最初は構成 B のサーバーとする
5. 検索、全体のグラフ、RAG のデータ源を足す

mermaid と `wiki/assets/` の svg の表示は、ADR-0005 のとおり第 1 段階に含めない。

## 理由

- **規則を 2 か所に置くと食い違う。** Python の中でさえ、`clean_link_target()` が 3 か所にある（`wiki_lint.py` L87、`wiki_search.py` L236、`wiki_graph_extract.py` L68）。`wiki_lint.py` は区切る前に NFC にそろえ、ほかの 2 つは区切った後にそろえる。今は結果が同じでも、別々に直せば食い違う。ページの集合も、lint と search ですでに食い違っている（未決の 1）。Obsidian では、規則の違いのために、未解決のリンクをクリックすると空のページができた（決定行列の第4.2節）。表示の方式ごとに規則を書くと、同じことが方式の間で起きる。
- **プロセスの境界は、Python 以外のアプリのために要る。** デスクトップアプリを Rust や TypeScript で書けば、中核を import できない。規則を書き直さずに使うには、子プロセスとして呼ぶしかない。なお、「wiki と rag は Python の版が違うので同じプロセスに載らない」という論は採らない。wiki の `>=3.10` と rag の `>=3.12,<3.13` は 3.12 で重なる。
- **`file://` に合わせれば、ほかの 2 方式はそれを包むだけになる。** `file://` で動く HTML は、サーバーでもアプリでも動く。PoC では、同じ生成物を `file://` とサーバーで開き、5 つのブラウザで同じ結果になった。逆に、サーバーを前提に絶対 URL、クエリのトークン、`fetch` に頼る画面を作ると、静的版とアプリに移すときに作り直しになる。
- **第 1 段階は事前に計算できる。** 第 1 段階の機能は、全ページを読めばどれも事前に描ける。1,000 ページの全変換は 1.26 秒、全体で約 2.3 秒だった（決定行列）。サーバーは「開いたときに 1 ページ描く」、静的版は「全部描く」というように、呼び方が違うだけになる。
- **ナビゲーションを各ページに埋め込むと大きくなる。** 作者の Wiki（56 ページ、日本語の題名）では、1 項目が平均 111.6 バイト、最大 176 バイトだった。1,000 ページの各ページに 1,000 項目を埋め込めば約 112 MB になる。共有の `nav.js` なら約 112 KB の 1 つで済む。
- **重複したスラッグは、今の `resolve_link()` で一意に決まらない。** 閲覧で勝手に一方へ移動すると、lint の結果と食い違う。
- **Wiki の場所は利用者ごとに違う。** ADR-0008 の既定は `~/info-hive/wiki/` だが、作者の環境の Wiki は別の名前のディレクトリにある。場所を決め打ちすると、プラグインとして配れない。
- **受け入れの条件は動作で測る必要がある。** HTML のバイト一致は、生成器が変わっていないことしか示さない。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| ADR-0002 のとおりサーバーを先に作り、静的版とアプリは後で考える | サーバーを前提にした画面は、静的版とアプリに移すときに作り直しになる |
| 画面を SPA にし、データをすべて JSON で取得する | `file://` では JSON を取得できないので、静的版だけ別の作りになる。JavaScript を切ると読めない |
| アプリの言語でリンクの解決などを書き直し、共通の試験データで一致を確かめる | 規則を 2 つの言語で保守することになる。アプリが Python を起動できない場合の最後の手段として残す |
| 画面をネイティブに描く GUI（Qt、Flutter、Avalonia など）でアプリを作る | 本文は HTML なので、結局 Web エンジンが要る。共通の画面を使えず、日本語の CSS とナビゲーションが二重になる。Qt は QtWebEngine で HTML を描けるが、配布物が大きく、LGPL の確認も要る |
| アプリを pywebview（Python）で作る | 中核と同じ言語である利点はある。Windows では pythonnet と .NET、Linux では Qt か GTK が要る。試作の候補として残す |
| アプリを、ローカルの HTTP サーバーを専用の窓で開くだけの殻にする | 実装は最も少ないが、ポートを開くので ADR-0001 の対策がアプリにも要る。stdio の IPC を既定にし、HTTP は予備として選べるようにする |
| 静的 HTML のバイト一致を、交換できることの合格条件にする | 基準の URL、CSP、IPC の可否で動作が変わるので、証明にならない |

決定行列（`docs/research/llm-wiki-browse-decision-matrix.md`）の点と順位は、既製の構成を比べたものである。自作のデスクトップアプリは採点の対象に入っていないので、その点を当てはめない。

## 影響

良い影響：

- 3 方式のどれを採っても、中核、画面、第 1 段階は作り直さずに済む。
- lint、検索、画面で、リンクの解決とページの集合が一致する。

悪い影響と、その対策：

- 中核の契約（JSON の入出力、世代、能力、状態）を、最初から決めて保守する。契約の版で互換性を確かめる。
- 静的版は、検索や RAG が縮小する。能力の宣言で利用者に示す。
- アプリを選ぶと、OS と CPU ごとのビルド、署名、リリースの仕組みが要る。中核を子プロセスとして同梱するなら、それも OS と CPU ごとに要る。「移植性」はソースの移植性にとどまる。
- RAG の統合は、rag の移行（ADR-0012 で決めた、rag の索引を wiki の MCP サーバーに移すこと）が済むまで足せない（「未決の事項」の 4）。

本 ADR を承認したら、次を行う。

- ADR-0002 の状態を「承認（作る順序と書き出しは 0010 で置き換え済み）」に改める。ADR-0002 の本文は書き換えない。
- `docs/adr/README.md` の表の状態と決定日を改める。
- 中核に手を入れる前に、「未決の事項」の 1（ページの集合）を決める。

## 未決の事項

7 件ある。1〜6 は最初の版からの未決、7 は ADR-0013 で生じた。どれもユーザーが決める。各項の「推す案」は提案で、根拠と PoC の結果の詳細は [未決と実装前の PoC](../research/wiki-browse-adr-0010-poc-2026-11-07.md) にある。

### 1. 閲覧の「ページ」の集合

- **事実**：今の版では、lint（`wiki_lint.py` L126〜127、L217〜222）は最上位の `SCHEMA.md`、`index.md`、`log.md`、`README.md` と、最上位の `indexes/`、`graph/`、`raw/`、`.evolution/`、`assets/` を除く。search（`wiki_search.py` L287〜290）は `README.md` と `assets/` を除かず、`.wiki-cache/` を除く。どちらも `.` で始まる名前のファイルを除く。試験用の Wiki では、lint だけが `.wiki-cache/` の Markdown を、search だけが `README.md` と `assets/` の Markdown を含んだ。作者の Wiki（56 ページ）では一致した。search の集合は、MCP の `query` の索引にも使われる（`wiki_index.py` L851）。
- **選択肢**：A. lint の集合を正とし、search をそろえる。B. search の集合を正とし、lint をそろえる。C. browse だけが独自の集合を持つ。
- **推す案**：閲覧の「ページ」とリンクの解決は、lint の集合を正とする。除外の規則を 1 か所に置き、lint と browse の中核がそれを使う。`.wiki-cache/` は lint の側でも除く。`index.md` と `indexes/` はページとして描かず、ナビゲーションの入力としてだけ読む。検索（search と MCP の索引）の対象を同じ集合に縮めるかは、検索の仕様の変更として分けて決める。推すのはそろえること（A）で、評価ゲートで確かめてから入れる。
- **根拠**：F-G06 が求めるのは、閲覧のリンクの解決と lint の一致である。検索の対象までは求めていない。lint の除外のほうが新しく、`assets/` と `README.md` を除く理由がある。検索をそろえれば、検索に出るのに閲覧では開けないページがなくなる。C は「規則を 1 か所に置く」に反する。
- **影響**：どちらも `info-hive-wiki` の変更で、browse の実装の前に行う。

### 2. 書き出し先

- **選択肢**：A. `<WIKI_ROOT>/.wiki-cache/browse/`。B. OS のユーザーの領域。
- **推す案**：B。ADR-0012 の索引と同じ根を使い、`%LOCALAPPDATA%/info-hive/browse/<wiki のハッシュ>/`（macOS と Linux は `$XDG_DATA_HOME/info-hive/browse/<wiki のハッシュ>/`）を既定にする。根とハッシュは `wiki_mcp_common.data_dir()` と `wiki_key()` を使う。人に渡すための書き出しは、引数で場所を選ぶ。
- **根拠**：Wiki に何も足さないので、F-G06 と AC-D02 の範囲を書き換えずに済み、同期のフォルダーにも生成物が入らない。ADR-0012 は索引の置き場所で `.wiki-cache/` を退けた。選択肢レポートの No.81 はキャッシュの領域を選んでいたが、置き場所の規則を ADR-0012 と 1 つにするほうを重く見た。キャッシュの領域を選ぶ案も成り立つ。
- **残ること**：書き出した場所の表示、古い世代と消えた Wiki の分の掃除、世代の切り替えの方法（PoC で確かめていない）、パスの全体の長さの上限。`wiki_key()` は Windows と macOS で常に大文字と小文字を同一視するので、大文字と小文字を区別するフォルダーの `A` と `a` の 2 つの Wiki が同じキーになる。ADR-0012 の索引から引き継ぐ欠陥で、索引と一緒に直す（別の課題）。

### 3. 静的出力のファイル名

- **選択肢**：A. 読める名前を基本にし、必要なときだけ決定的な接尾辞を付ける。B. すべて ASCII の ID にする。
- **推す案**：A。名前の要素ごとに、Windows で使えない文字を替えたとき、末尾の空白と `.` を除いたとき、予約名のとき（先頭にも `_` を付ける）、元の名前が接尾辞の形で終わるとき、ディレクトリの名前が `.html` で終わるとき、UTF-8 で 200 バイト（`.html` と接尾辞を含む）を超えて切り詰めたときに、`~<その要素までの識別子の SHA-256 の先頭 8 桁>` を付ける。大文字と小文字だけが違う出力が衝突したら、衝突した全員に識別子の接尾辞を足す。最後に、出力のパスが重ならないこと（大文字と小文字を同一視して）と、ファイルとディレクトリが同じ場所を取らないことを確かめ、重なれば上書きせずに生成を止める。lint に「大文字と小文字だけが違うページ」の検査を足す。
- **根拠**：ext4 と APFS の名前の上限は 255 バイトで、日本語は 86 文字を超えると作れない。NTFS は 255 文字（UTF-16）なので、バイトで数えれば 3 つの OS で収まる。接尾辞はその要素までの識別子だけから決まり、元の名前が接尾辞の形で終わるときも付けるので、ページを足してもほかのページの名前は変わらない。例外は大文字と小文字だけが違うページを足したときで、lint の検査で起きにくくする。最初の版の規則（接尾辞の形の名前を考えず、重なりを確かめない）には、ページを足すと既存の名前が変わり、上書きまで起きる反例があった。
- **PoC**：作者の Wiki（56 ページ）では、名前を変えたページは 0 件、最も長い要素は 77 バイトだった。試験用の Wiki の 288 バイトの名前は、200 バイトに切り詰めて接尾辞を付け、Chromium、Firefox、WebKit の `file://` とサーバーで、リンクから開けた。上の反例は、直した規則で解けた（`poc/browse/names_check.py`）。

### 4. RAG への経路

- **事実**：rag 0.4.0 の検索の入口は今も MCP の `search` だけで、索引も rag が持つ（`rag_server.py` L150〜166）。ADR-0012 の rag の移行は済んでいない。wiki の MCP サーバーの `query` は、`collection` を渡すと rag が `index_chunks` で入れたチャンクを検索するが、語彙のトークン（`query_tokens`）は呼び出し側が作る（`wiki_mcp_server.py` L304〜325）。サーバーは `allowed_origins=[]` で、トークンは `server.json` にだけある（L295）。
- **選択肢**：A. rag に検索の CLI を足す。B. browse を rag の MCP のクライアントにする。C. 常駐の検索サービスを置く。D. 画面を wiki の MCP サーバーのクライアントにする（ADR-0012 の案）。D'. アダプタ（サーバーのプロセス、アプリの中核）を wiki の MCP サーバーのクライアントにする。E. 中核そのものを MCP のツールにする。
- **推す案**：D'。画面は自分のアダプタ（同じオリジン）にだけ要求し、アダプタが `server.json` を読んでサーバーに接続し、`query` を呼ぶ。wiki のプラグインの中の browse のサーバーは、中継と同じ `ensure_server()` を使い、サーバーが止まっていれば起動し直す。版を固定したアプリは、サーバーを起動も停止もしない。動いているサーバーに接続するだけにし、中継とサーバーの取り決めの版（`PROTOCOL`）とツールの形が合うときだけ `live` にする。第 1 段階の表示は MCP サーバーに依存しない。検索の能力は、サーバーに届けば `live`、届かなければ `embedded` とする。rag の PDF の検索は、rag の移行が済んでから足し、`query(collection=...)` の語彙のトークンを誰が作るかは移行のときに決める。静的版は RAG を持たない。
- **根拠**：ブラウザのページはサーバーに接続できない。PoC では、トークンが正しくても `Origin` の付いた要求は 403 になり、`file://` のページからの `fetch` は失敗した。中継を通した Python からの呼び出しは通った。D を成り立たせるには CORS とトークンの受け渡しを足すことになり、ADR-0001 と ADR-0012 の防御を弱める。browse のサーバーは wiki のプラグインの中にあるので、D' は `wiki_mcp_common` と中継の起動の処理を使い回せ、プラグインの境界をまたがない。中継の `ensure_server()` は、コードの版が違うサーバーを止めて起動し直す（`wiki_mcp_relay.py` L105〜119）ので、版を固定したアプリがこれを使うと、更新されたプラグインとサーバーを止め合う。rag の索引は ADR-0012 で wiki のサーバーに移るので、ADR-0007 の見直しは要らない。A は CLI も結局 wiki のサーバーに頼むことになり、B は rag の台帳を 2 つのプロセスが扱い、C は ADR-0007 と ADR-0012 が退けた。E は第 1 段階の閲覧が、約 1 GB の依存とモデルを読み込むサーバーを前提にすることになる。

### 5. 静的版の検索の範囲

- **選択肢**：A. 題名、要約、タグ、見出しの部分一致。B. A に加えて、本文の bigram の検索を JavaScript に持つ。C. 検索を持たない。
- **推す案**：A。照合は NFC にそろえ、小文字にしてから部分一致で行う。本文の検索は、サーバーとアプリで MCP の `query`（4 の D'）に頼む。
- **根拠**：トークナイザーを JavaScript に二重に持たずに済む。日本語でも部分一致なら分かち書きが要らない。
- **PoC**：`data/search.js` は作者の Wiki で 13,219 バイト（1,000 ページで約 236 KB の見込み）で、5 つのブラウザの `file://` とサーバーで動いた。本文まで埋め込むと、本文だけで 1,000 ページあたり約 2.4 MB になる。

### 6. アプリの技術

- **選択肢**：A. Tauri 2（Rust）。B. Electron（TypeScript）。C. pywebview（Python）。D. ローカルのサーバーを専用の窓で開くだけの殻。条件は最初の版のとおり、埋め込みの Web エンジンを持ち、Windows、macOS、Linux で動き、中核を子プロセスとして起動できることである。
- **推す案**：今は決めない。アプリを作ると決まったら、A を第一候補にし、描画を 3 つの OS でそろえることを重く見るときは B にする。アプリを別のリポジトリ（仮称 `to884/info-hive-viewer`）に置き、中核の版をアプリの側で固定する想定は変えない。版を固定するなら、4 の制約（サーバーを起動も停止もしない）を守る。
- **根拠**：最初の版が分かれ目に挙げた Linux の WebKitGTK での日本語の描画は、PoC の範囲で問題が見つからなかった（試験の段落を幅を変えて描き、禁則の違反 0 件）。任意の本文の組版の全体を保証するものではない。Tauri の独自スキームで、同じ HTML が Windows（`http://wiki.localhost/`）と Linux（`wiki://localhost/`）で基準と同じ結果になった。字幅は OS のフォントで違うので、行の位置はそろわない。C は配布の形が Python の環境に縛られ、D はポートを開くので ADR-0001 の対策がアプリにも要る。

### 7. ソースのページの `raw:` の絶対パス

- **事実**：ADR-0013 で、rag が取り込んだ PDF のソースのページは、`raw:` に絶対パス（例 `C:/Books/x.pdf`）を、`raw_sha256:` に内容の SHA-256 を書く。PDF でないソースの `raw:` は、今も Wiki からの相対パスである。`file:///` のリンクをクリックすると、`file://` のページからは Chromium 系と WebKit で PDF への要求が出た（表示やダウンロードの成功は確かめていない）。`http://127.0.0.1` のページからは 5 つのブラウザすべてで拒まれた。
- **選択肢**：A. 絶対パスをそのまま出す。B. 出さない。C. 中核は値を解釈して持ち、表示は方式と書き出しの目的で変える。
- **推す案**：C。中核の出力に `raw` を `{kind, value, sha256}` で持たせる。サーバーとアプリは絶対パスを文字として表示し、コピーできるようにする（リンクにしない。開く操作を足すなら S-07 に従う）。静的版は、既定の書き出し先では `file:///` のリンクにし、引数で Wiki の外に持ち出す書き出しでは、既定でファイル名と `raw_sha256:` の先頭だけを出す。出力の中には、HTML だけでなく、生成の記録や診断の JSON にも絶対パスを置かない。生成器は、出力に Wiki のルートの絶対パスが残っていないことを確かめる。
- **根拠**：持ち運べる生成物に絶対パスの Wiki のルートを入れない、という本 ADR の規則と同じ扱いになる。PoC の最初の版の生成器は、`raw:` を隠しても、出力の中の生成の記録に Wiki のルートの絶対パスを書いていた。ADR-0013 は、公開する Wiki に絶対パスを載せたくない利用者が出たら見直すとしている。

## 見直す条件

次のどれかが起きたら、本 ADR を見直す。

- 実装の前の PoC の 5 項目のうち、確かめていない部分が前提と違うと分かる。2026年11月7日の PoC の結果は次のとおりで、詳細は [未決と実装前の PoC](../research/wiki-browse-adr-0010-poc-2026-11-07.md) にある。
  - `file://` で開いたページで、`<script src>` による別ファイルの読み込みが主要なブラウザで動く：動いた（Chromium、Firefox、WebKit、Edge、Chrome）。実機の Safari は確かめていない。`fetch` は使わずに済んだ
  - Linux の WebKitGTK で、日本語の CSS（`line-break: strict` など）が崩れずに描ける：描けた。WebKitGTK 2.52.6 で、幅を変えて数えた禁則の違反は 0 件で、Windows の 4 つのエンジンと同じだった。Tauri の WebView として描いたときは確かめていない
  - Tauri の独自スキームの URL の形が OS で違っても、相対リンクだけで閉じた HTML がそのまま動く：動いた（Windows の `http://wiki.localhost/`、Linux の `wiki://localhost/`）。macOS は確かめていない
  - ナビゲーションの 1 項目が約 100 バイトに収まる：作者の Wiki で平均 111.6 バイト。1,000 ページの実際の Wiki では確かめていない
  - 3 方式で、合格の条件の試験が通る：試作のアダプタで、縮めた形で通った（`file://` とサーバーを 5 つのブラウザで、アプリを 2 つの OS で、12 通りの結果が一致した）。一致は契約が 3 方式で同じに働くことを示すが、生成器の誤りは見つけない。実装のアダプタでは、実装のあとに確かめ直す
- 中核を子プロセスとして呼ぶ費用（起動時間、配布）が、アプリで受け入れられないと分かる。
- 3 方式のうち 1 つに決め、ほかの 2 つを作らないと決まる。そのときは、その方式に要らない契約を外してよい。
