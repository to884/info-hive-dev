# ADR-0023：wiki の書く段は、モデルが用意した変更を、wiki ごとの残るロックを持つ Python のプロセスが、日誌で前に進めて当てる

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月15日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0004（Web ページの raw）、ADR-0008（作業領域の構成）、ADR-0019（wiki の根は `SCHEMA.md` で決まる）、ADR-0020（セッションの raw）、[wiki の書く段の設計](../plans/wiki-apply-2026-11-14.md)、[セッションの取り込みの設計](../plans/wiki-session-ingest-2026-11-14.md) |

## 背景

今の取り込み（Web ページ、PDF、セッション）と `/wiki:query`、`/wiki:learn` の保存は、モデルが Claude Code の Write と Edit で、要約ページ、関連ページ、`index.md`、`log.md` を書く。Edit は「読む、直す、書く」で原子的ではなく、2 つの書き込みが数ミリ秒の中で重なると、行が黙って消える（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md)）。lint は、索引に足りない項目と、ログの抜けを見つけない。

書く段は、もとはセッションの取り込みの設計の 4 版目に入っていたが、そのレビューの重大の指摘が集まったので、作者の判断で別の設計に分けた（ADR-0020）。分けた設計は、GPT-6.1 Sol の敵対的レビューを 15 回受け、15 回とも却下だった。作者は 15 回目のあとで、重大の指摘の発生の度合いをもとに、レビューを止めて設計を承認すると決めた（下の「レビューを止めた判断」）。

作者は、次の方針を決めていた（2026年11月14日）。並行して取り込むときは書く段だけをロックし、確認と記事を書く間はロックを持たない。決まった処理はモデルを使わず Python で行う。書き込みは、差分のパッチと Python で書くことを使い分け、パッチが競合したらモデルが直す。Claude Code のツールを通らない書き手の変更は考えない。

## 決定

| 項目 | 決定 |
| --- | --- |
| 書き手 | wiki のページ、索引、ログを書くのは `wiki_apply.py` だけにする。モデルは、利用者のデータのディレクトリの作業用のフォルダーに変更を用意し、wiki のファイルを直接書かない。Python の書き手（評価ループ）は、同じ手順をライブラリ（`apply_plan()`）で呼ぶ |
| 変更の種類 | `new`（新しいページ。行き先がないときだけ、重ねて書かない形で置く）、`edit`（モデルが直すページ。ファイルの全体が用意したときと同じときだけ置き換え、違えば競合にしてモデルが直す）、`ops`（索引とログの決まった操作。ロックの中で今の中身に順に当てる）の 3 つにする。差分の塊を今の中身に合わせて当てる 3 方向の当て方はしない |
| 済んだかの判定 | 今の中身から推さない。書く前に、書くファイルごとの「前」と「後」の中身とハッシュを日誌に書き、日誌だけで決める。日誌の項目は前と後がつねに違う。ロックを取った書き手は、誰であれ、残った日誌を先に前に進め、置けなければ「前」に戻す。当て終えた印は wiki の側に置き、消さない |
| 承認 | 計画のハッシュ（`plan_sha256`）を、`begin` が作る識別子（`plan_id`）を含む計画の全体から作る。`apply` は計画が指すすべてのファイルを 1 回だけ読み、そのバイト列だけを使う。計画の外の入力を取らない |
| ロック（作者の判断、2026年11月15日） | ロックはプロジェクト（wiki）ごとに `.wiki-cache/apply/apply.lock` に持ち、プロセスが落ちても残るファイルにする。利用者が `unlock` で明示して外す。待ちは 3 分で、待ちきれなければ、承認した差分を `.wiki-cache/apply-pending/` に置いて誤りにする。差分が 5 件以上になったら、ユーザーに知らせて状態を確かめてもらう |
| 構造の確かめ | 索引とログの決まった操作は、同梱のパーサーのトークンの並び（種類、段、`hidden`、中身、`attrs`、参照の定義）で、当てたあとの構造を確かめる。行の番号は比べない |
| 書き込みの入口 | 道具のすべての書き込みを `wiki_fsguard.Writer` の 1 つの検査に通す。パスは正規のもの（途中のリンク、再解析点、mount point、輪を拒む）だけを受け、名前の決まりは `casefold()` と NFC で比べる。管理の書き込みは、`.wiki-cache` からの相対パスの決まった形だけにする。名前を公開したら、そのディレクトリを同期してから次の段へ進む |
| raw の守り | 2 つの条件の組で示す。(1) 根から書く先までの道に別名（リンク、再解析点、mount point）がない。(2) wiki の木と、守る raw のルートの木が、物理的にディレクトリを分け合わない。守る raw のルートは、各コマンドの始めに、計画、wiki が使った raw のルートの記録、ページの `raw:` から作る。走査と mount point の列挙は、完全でなければ書かない（作者の判断の 9）。書く段は、wiki の中を指す `raw:` のページを書かない |
| 移す範囲 | `commands/`、`references/`、`SKILL.md`、スクリプトの書き込みの指示と書き手を洗い出した表を移す範囲にし、文書のすべての段落とスクリプトの日本語の文字列の定数に分類を求める機械の検査で閉じる。セッションの取り込み、Web ページと PDF の取り込み、`/wiki:query` と `/wiki:learn` と `/wiki:evolve` の保存、lint の直しと `init`、`upgrade` の順に移す |

## 理由

- 1〜3 回目のレビューの重大の多くは、「済んだかどうかを、今の中身からあとで推す」作りから出た。これはセッションの取り込みの 1〜3 版目の却下と同じ形である。日誌だけで決め、前に進めるだけにすれば、推す箇所がなくなる。この中心の仕組み（日誌、全体のハッシュの `edit`、`ops` の順の当て方、計画のハッシュ、1 回だけ読むこと）は、6 回目ごろから新しい反例を出していない。
- 索引とログは、2 つの取り込みがほぼ同じ場所に足すので、パッチにすると毎回競合する。決まった操作にすれば、競合は見出しがない、2 つある、同じページがすでにある、構造が変わる、のどれかのときだけになる。
- ロックを PC に 1 つにし、wiki の印で管理領域を決める形（3〜11 版目）は、環境変数で管理領域が分かれる、印を移す操作が並ぶ、印の置き方、`adopt` の raw のルート、と崩れ続けた。作者の判断でロックを wiki ごとにすると、ロックの場所が wiki のパスだけで決まり、それらの仕組みが要らなくなった。
- raw を守る形は、「守る raw のディレクトリを集めて照らす」だけでは集め方の漏れで崩れ（13〜14 回目）、「書く道に別名がない」だけでは raw の側の別名で崩れた（15 回目）。2 つを組にした。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| 差分の塊を、文脈が 1 か所に一致すれば当てる（3 方向） | 同じ文脈が 2 か所にあると、違う場所に当たり、承認した差分と当たった場所が違っても機械は気づかない（作者の判断の 1） |
| 計画ごとの日誌を持ち主がやり直す | やり直すまでの間にほかが同じファイルに追記すると、正しく当たった変更と競合を見分けられない |
| ロックと日誌を利用者の PC に 1 つにする（3〜11 版目） | 管理領域の場所が環境変数で変わり、それを補う印の仕組みが崩れ続けた。作者の判断でロックを wiki ごとにした |
| OS のファイルのロック（落ちれば自動で外れる） | 作者は、残るロックのファイルを選び、利用者が明示して外す形にした |
| 走査の失敗を飛ばして書く | その枝の下の bind mount を経由して raw に書きうる（作者の判断の 9） |
| レビューを続ける | 13〜15 回目の重大は、どれもまれな時機か作為的な配置（主に raw の守りの境目）で、実装すれば確実に踏む欠陥は出ていない。作者がレビューを止めた |

## レビューを止めた判断

作者は 15 回目のレビューのあとで、レビューを止めて設計を承認した（2026年11月15日）。判断の材料は、[summary.md](../agent-runs/2026-11-14-wiki-apply/summary.md) の「重大の指摘の発生の度合い」である。実装すれば確実に踏む仕様の矛盾と欠落は、作り直した直後（1〜5 回目と、作者の判断のあとの 11〜12 回目）に集まり、13 回目からは出ていない。

残る危うさは次のとおりで、実装のときの試験とレビューで確かめる。

- 17 版目の直し（raw の木の走査を戻したこと、wiki の中を指す `raw:` を書かないこと、wiki の中の raw の検査をすべての書き込みに当てること）は、レビューを受けていない。
- raw の守りの境目（別名の形）は、レビューを続ければ、まだ見つかる見込みがある。見分けない別名と、どこからも引かれない raw のルートは、設計書の「保証しないこと」に書いた。

## 影響

- `info-hive-wiki` に `wiki_apply.py` と `wiki_fsguard.py` を足し、`wiki_browse_fs.py` の実体の検査を `wiki_fsguard.py` に移す。raw の書き手（`wiki_fetch.py`、`wiki_session.py`、`wiki_evolve.py`、`wiki_encoding.py`）に、raw のルートの役割の検査を入れる。`init_wiki.py` は、ないファイルを重ねて書かない形で作る。
- 移り終えるまで、移っていない書き手との競合は残る。lint のページの分割、統合、名前の変更、削除は、書く段の種類がないので残す。
- 古い構成（raw が wiki の中の `W/raw` にある wiki）は、書く段を使う前に、ADR-0008 の構成（wiki と raw を兄弟に置く）に移す。
- 守れないことは、設計書の「保証しないこと」に並べた。主なものは、人が実際に読んで決めたこと、書く段に加わらない書き手との競合、同じページの別の箇所への並行の直し、見分けない別名、複数の PC からの同時の書き込み、`unlock --force`、どこからも引かれない raw のルートである。

## 見直す条件

- 実装のときの試験かレビューで、17 版目の直しか raw の守りに、実際に起きる欠陥が見つかったとき。
- 書く段に移る範囲が終わり、移っていない書き手がなくなったとき（保証しないことの 2 を狭める）。
- ページの削除と名前の変更を、書く段に入れると決めたとき。
- ロックを外す操作や、待ちきれなかった差分の扱いが、日常の使い方で手間になると分かったとき（作者の判断の 2 を見直す）。
