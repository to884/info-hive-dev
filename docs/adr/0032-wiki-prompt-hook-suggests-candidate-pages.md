# ADR-0032：wiki は、指示ごとに関係しそうなページの候補を語彙で選んで知らせ、読む段のモデルとエフォートを段の表で決める

## 背景

作者が、Claude がタスクを行う前に wiki へ問い合わせる仕組みを求めた。手段として、UserPromptSubmit のフックで `/wiki:query` を呼ぶ、記事を直接参照する、埋め込みで検索する、の 3 つを挙げた。あわせて、wiki を調べるときは、その場で最適なモデルとエフォートを選ぶことを求めた。今の実装では、wiki を引くかどうかは、利用者がコマンドを打つか、モデルが指示のファイルに従うかに任されている。

調べて分かった事実は次のとおりである（[段階 0 の測定](../research/wiki-prompt-hook-stage0-2026-11-17.md)）。

- command のフックは、`/` のコマンドもツールも起動できない。フックから `/wiki:query` は実行できない。
- UserPromptSubmit で終了コード 2 を返すと、利用者の指示が止まる。`uv run` は、スクリプトがないときも Python がないときも 2 を返す（uv 0.12.2）。
- UserPromptSubmit は、サブエージェントの報告（`<agent-message …>`）のような、利用者が打たないターンでも発火する。見分ける欄はない。
- 検索の今のゲート（日本語の被覆率 0.25）は、指示には効かない。80 ページの wiki で「続けて」が 50 ページに当たった。
- 本文の BM25 は `collect_pages` の解析が重く、150 ページで約 1 秒、1,000 ページで約 11 秒かかる。CLI のハイブリッド検索は 1 回 3.5 秒かかる。
- 注入する層は小さく保つべきで、誤りをすべてのセッションに持ち込む（[[エージェントのメモリの階層]]）。wiki には Web から取り込んだ信頼しない文が入る。
- セッションの途中でモデルを変えられるのはサブエージェントだけである。Agent ツールの `model` と `effort` の引数は、エージェントの定義より優先する。

## 決定

| 項目 | 決定 |
| --- | --- |
| 形 | プラグインの `hooks/hooks.json` に、UserPromptSubmit の command のフックを 1 つ置く。起動行は `uv run --quiet --offline --no-python-downloads --script "<wiki_prompt_hook.py>"; exit 0` のシェル形式にする。`; exit 0` で、uv の段の 2 を 0 に変える。exec 形式にはしない。`timeout` は 5 秒、内部の締め切りは 2.5 秒 |
| 失敗 | 何が起きても、何も書かずに終了コード 0 で終わる |
| しないこと | プロンプトの経路で、MCP のサーバーの起動、依存やモデルの取得、`WikiIndex` を開くこと、検索の `--cache` と `--decide`、CLI のハイブリッド検索をしない。wiki と索引に書かず、外部に送らない |
| 飛ばす指示 | 設定で無効、`/` か `!` で始まる、タグで始まる（`<pasted_content>` を除く）、会話の圧縮の要約、短い指示 |
| 引く wiki | 既定はプロジェクトの wiki だけ。設定でユーザースコープの wiki も足せる。2 つの候補は混ぜずに分けて示す。初期化された wiki だけを読む。指示のファイルに書いたパスは読まない |
| ゲート | 順位の上位ではなく、絶対の基準で選ぶ。直接の参照（S1）、題・スラッグ・別名の一致（S2）、識別子の一致（S3）、索引の 1 行の要約の一致（S4）だけを使う。本文の語の一致は使わない。値は評価のデータで決め、`references/prompt-context.md` に書く |
| 出すもの | スラッグ、パス、題、見出し、索引の要約だけを、無害化して出す。本文は出さない。データであって指示ではないと添える。2,000 文字で打ち切る。同じセッションで 40 ターン以内に出したページは出し直さない |
| 埋め込み | 段階 2 で、常駐の MCP サーバーが生きているときだけ使う。サーバーに読み取り専用の口を足し、開いている索引と読み込み済みのモデルだけで答える。サーバーを起動しない。段階 1 では使わない |
| 読む段 | 候補を読む段を、読み取りだけのプラグインのエージェント `wiki:wiki-reader` に任せる。段（R0〜R3）とそのモデルとエフォートは、候補の数、wiki の数、一致の種類から、フックが字句と数で決めて知らせる。R0（候補 1 件）はメインが自分で開く。R3 はメインだけが理由を書いて上げられる。表の値は測定（段階 0 の (f)）で決める |
| /wiki:query | フックは `/wiki:query` の指示では何もしない。`/wiki:query` の確信度では、フックの候補として知ったページを検索の縮退（理由 0F）に数える（ADR-0028 の規則に足す） |
| 設定 | `userConfig` の `prompt_context`（既定で有効）、`prompt_context_user_wiki`（既定で無効）、`prompt_context_delegate`（既定で有効）。環境変数 `INFO_HIVE_PROMPT_CONTEXT*` で一時的に上書きできる |
| 進め方 | 段階 1（語彙と直接の参照）と段階 2（埋め込み）を別のリリースにする。段階 1 を既定で有効にして出すのは、ゲートが評価の合否の基準に届いたときだけにする |

## 理由

- **command のフックにした。** 文書にある面（標準入力の JSON と `additionalContext`）だけで組めて、Claude Code なしで試験できる。`mcp_tool` のフックは、置換と応答の扱いが文書で決まっておらず、中継がサーバーを起動して指示を待たせる。
- **本文を照らさず、題と索引の要約で選んだ。** 索引は「1 行の要約から候補を見つける」ために人と LLM が選んで書く欄である。評価では、本文の語の一致は採られるたびに精度を下げ（当たり 1 件に外れ 2〜4 件）、再現率を上げなかった。本文の解析もやめたので、1,000 ページの wiki でも、題と見出しの走査は 0.15 秒で済む。
- **欄ごとにありふれた語を決めた。** 本文ではありふれた語（`python`、`mcp`）も、題と要約では手がかりになる。
- **読む段を表で決めた。** 判断に任せる決まりより、字句で決まる決まりのほうが守られる（[[エージェントに守らせる決まりの書き方]]）。実機で、「〜なら呼ぶ」という勧めの書き方では、メインがサブエージェントを呼ばずに自分で読んだ。理由を添えて「自分で開かずに呼ぶ」と書くと、書いたとおりの `subagent_type`、`model`、`effort` で呼んだ。任せる利点は、メインの文脈にページの本文を入れないことと、読むのに合うモデルを使うことである。1 ページなら、サブエージェントを起こす費用のほうが大きいので、メインが読む。
- **`/wiki:query` には当てない。** 作者が、確信度の規則（道具を呼んだ順で決める）を崩さないことを選んだ。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| フックから `/wiki:query` を呼ぶ | command のフックはコマンドを起動できない |
| `mcp_tool` のフックで MCP の `query` を呼ぶ | `${prompt}` の置換、JSON の応答の扱いが文書で決まっていない。中継がサーバーを起動し、最大 300 秒待つ。ゲートを掛けられない |
| prompt か agent の型のフック | 応答は `ok` と `reason` だけで、文脈を足せない。毎ターン LLM を呼ぶ |
| `index.md` を毎回まるごと足す | 注入を小さく保てない。関係のないページも毎ターン入る |
| 本文の抜粋を足す | wiki の信頼しない文を毎ターン持ち込む。抜粋を根拠にされやすい |
| CLI のハイブリッド検索 | 1 回 3.5 秒かかり、別のモデルと索引を書く |
| フックから `WikiIndex` を開く | 書き手のロックで最大 60 秒待つ |
| 標準ライブラリで MCP の手順を踏んで `query` を呼ぶ | 開いていない索引を作り、その場で埋め込み、サーバーの待機の時間を延ばす。距離が結果に載らない |
| `async: true` | 結果が次のターンに回る |
| SessionStart でセッションの要約を作る | ADR-0006 と同じ論点で保留している |
| 読む段をいつもメインで行う | 読むのに合うモデルを選べず、メインの文脈が本文で膨らむ |

## 影響

- 指示を送るたびに、0.15〜0.5 秒ほどの遅れが足される。PowerShell しかない Windows では、さらに 0.5 秒ほど足される。
- 候補が出たターンでは、文脈が 1,200〜2,000 文字ほど増える。このプロジェクトの過去の発言 1,557 件では、7.1% のターンで候補が出た。
- rag の利用者にも入る（rag は wiki に依存している）。止めるときは wiki ごとではなく、設定の `prompt_context` を切る。
- `${CLAUDE_PLUGIN_DATA}` に、セッションごとの小さな状態のファイルを置く。
- `/wiki:query` の確信度は、フックの候補から開いたページについて、低い側に寄る（検索し直せば外れる）。
- 段階 2 では、`server.json` の読み手が中継だけではなくなる（`references/mcp-server.md` を改める）。
- 新しいプラグインのエージェント `wiki:wiki-reader` が増える。

## 見直す条件

- 実際の利用で、関係のない候補や遅れが目立つと報告されたとき。
- Claude Code に、利用者が打った指示かどうかを見分ける欄が入ったとき。
- `mcp_tool` のフックの振る舞いが文書で決まったとき。
- 新しいモデルが出たとき。読む段の測定（`tests/wiki/measure_reader_models.py`）を同じ問いで測り直す。
- 150 ページを超える wiki が一般的になったとき。題と見出しの走査の時間を測り直す。
