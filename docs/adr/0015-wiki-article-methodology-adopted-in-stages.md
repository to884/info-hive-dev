# ADR-0015：wiki の記事作成の方法論は、提案を一括で入れず、検査と記録から段階を分けて入れる

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月9日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0006（日々の記録は別のプラグイン `log`）、ADR-0008（番号付きの作業領域）、ADR-0009（グラフ層は wiki に残す）、[記事作成の方法論の提案を導入するかの検討](../research/wiki-article-methodology-adoption-2026-11-08.md)、[記事の単位：Atomic Notes と Evergreen Notes の検討](../research/wiki-note-granularity-2026-11-08.md) |

## 背景

作者は、Codex と Claude に相談して「LLM Wiki 記事作成の方法論 — 使い分けと Skill 設計」（以下「提案」）をまとめた。提案は、きっかけ別のコマンド、Atomic Notes にもとづくページの種類、frontmatter の `id`、`scope`、`status`、`relations`、新しい `type`（`journal`、`graph`、`decision`、`moc`）、`/wiki:decide`、`/wiki:promote`、`/wiki:plan` と `questions.md` などからなる。

提案は info-hive の現状を知らずに書かれている。コマンド名（`/wiki:ingest`、`/wiki:query`、`/wiki:lint`、`/wiki:graph`）は現行と同じだが、中身は同じではない。2026年11月8日に、wiki プラグイン（`info-hive-wiki`）に導入するかを 4 体のエージェントに独立に検討させ、相互レビューと総括を経て、レポートにまとめた。4 体とも「一括では導入しない」という結論に至り、相互レビューでもこの結論は崩れなかった。提案の骨格の多くは現行のプラグインに既にあり、足りないのは「検査」と「記録」である。

同じ日に、提案の区分 2 と重なる記事の単位も、別に 4 体で検討した。結論は、用語とエンティティのページを残し、条件と根拠を保ったまま再利用できる知見だけを `type: "concept"`、`kind: "claim"` のページとして独立させる併用案である。最初は `SCHEMA.md` で選べるオプトインにし、PoC で振り分けの一致を測ってから既定にするかを決める。

作者の wiki（`~/info-hive/W0_Wiki/`）では、次の誤りが実際に起きていた。

- `index.md` の「シンセシス」の見出しの下に、`type: source` のページが 16 本並んでいた。現行の `wiki_lint.py` は `index.md` を走査から外している（`SKIP_TOP_LEVEL_FILES`）ので、これを見つけられない。
- `SCHEMA.md` のタグの体系にないタグ（`Windows`、`MCP`、`Claude Code`）が使われていた。
- source のうち約 28 本は SemaSynth の作業記録で、そこから concept はほとんど作られていなかった。

2026年11月9日に、作者がレポートに残っていた論点を決めた（「作者の決定」の節）。本書は、検討の結論と作者の決定を、設計の決定として固定するためのものである。

## 決定

### 全体の方針

| 項目 | 決定 |
| --- | --- |
| 導入のしかた | 提案を一括では導入しない。要素ごとに、導入する、変えて導入する、導入しない、保留の 4 つに分ける |
| 導入の原則 | 実際に問題が起きた要素から入れる。保留した要素は、具体的な需要が出たときに入れるかを決め直す |
| 判断の根拠 | 採点ではなく、コード、承認済みの ADR、作者の wiki での確認にもとづく。4 体の採点は、変えて導入する要素を変更後の案で、導入しない要素を原案で付けていたので、採る側が高く出るのは最初から決まっていた |
| 承認済みの ADR | 変えない。本書の決定は、どの ADR とも食い違わない範囲にとどめる |

### 導入するもの

| 要素 | 内容 |
| --- | --- |
| lint の 4 つの検査 | `index_type_mismatch`（索引の見出しと、そこに並ぶページの `type` の食い違い）、`unresolved_sources`（`sources:` が実在しない source ページを指している）、`missing_raw`（source の `raw:` の原本がない）、`unknown_tags`（`SCHEMA.md` のタグの体系にないタグ）。`index_type_mismatch` は見出しの直下にある wikilink だけを読み、冒頭の説明文の例示は除く。正式なタグの一覧は `--allowed-tags` で渡す |
| source の `## 主張と行き先` | 取り込みで抜き出した主張ごとに、主張と成り立つ条件、根拠の位置、行き先、理由を source ページの表に残す。行き先の値は英語の識別子 `create`、`update`、`source_only` にする |
| 5 区分の方法論マップ | 提案の区分を、説明と設計レビューのときの見取り図として使う |

lint の 4 つの検査を最初に入れるのは、作者の wiki で実際に起きている誤りを見つけられ、LLM の判断に頼らず、既存のページを壊さないからである。`unresolved_sources` と `missing_raw` は、作者の wiki では今は 0 件で、価値は予防にとどまる。

### 変えて導入するもの

| 提案の要素 | 変えた形 |
| --- | --- |
| 全ページ共通の `status`（`draft`、`reviewed`、`canonical`、`deprecated`） | `kind: "claim"` のページに限り、`experience-pattern` と同じ 3 値（`hypothesis`、`supported`、`superseded`）にする。オプトインで、段階 3 で入れる。矛盾は `status` ではなく、本文の `## 矛盾` で表す |
| Atomic Notes とページの種類 | 記事の単位の検討の併用案に従う。用語ページを残し、再利用できる知見だけを `kind: "claim"` のページに昇格させる。主張の既定の置き場所は、用語ページの中の `###` の節にする |
| `type: moc` | 新しい `type` は作らない。既存の `index.md` と、分割した索引 `indexes/` で担う |
| 「手順と概念を混ぜない」 | 独立して使う長い手順に限って当てはめる。どのページにも当てはめる規則にはしない |
| source の「主張の一覧」 | 一覧という形式ではなく、知見をどこへ反映したか（行き先）を残す形にする。上の `## 主張と行き先` がこれに当たる |
| 必須の節（`## 主な主張` など）の検査 | `SCHEMA.md` で選んだときだけ有効にする。`page-conventions.md` は本文に固定のテンプレートを求めていないので、既定では `## 主な主張` のない source を「欠けている」と数えない |
| きっかけ別のコマンド | 既存のコマンド（`ingest`、`query`、`learn`、`lint`）を、きっかけとの対応表で案内する。新しいコマンドは、既存のコマンドで表せない手順が出てから足す |

### 導入しないもの

| 提案の要素 | 理由 |
| --- | --- |
| `id`（ファイル名と一致させる） | スラッグが既に識別子で、`id` は常に同じ値になる。重複と整合の検査が増えるだけである |
| `scope: common \| project:<name>` | ADR-0008 は、ユーザースコープとプロジェクトを作業領域（保存先）で分けている。ページの属性では、保存先の境界を保証できない |
| 入れ子の `relations`（`broader`、`related`、`answers`） | `wiki_text.py` のパーサーは入れ子の frontmatter を読まず、空の配列にする。`related` は本文のリンクと既存の `mentions` で足りる。ADR-0009 のグラフ層の型付きエッジとも二重になる |
| `type: journal` | ADR-0006 で、日々の記録は wiki と別のプラグイン `log` にすると決めている |
| `type: graph` | グラフはページの種類ではなく、ページから作り直せる派生の索引である（ADR-0009） |
| `type: decision` と `/wiki:decide` | 決定の正本はプロジェクト側の ADR に置き、wiki には source として取り込む |
| 全ページ共通の `status` | 既存の `experience-pattern` の `status` と、値も意味も違う。編集の状態、確からしさ、失効を 1 つの列に混ぜることになる |
| 出典なしの `draft` | 出典のない推測が、wiki の事実のページに流れ込む。現行は出典を必須にしている。「`draft` は出典不要、`reviewed` は出典必須」は KCS そのものではなく、提案独自の設計である |
| `status` を上げる意味の `/wiki:promote` | 上の全ページ共通の `status` を導入しないので、上げる対象がない |
| `/wiki:lint --relations` | 入れ子の `relations` を導入しないので、検査する対象がない |

### 保留するもの

| 提案の要素 | 保留の理由と、入れるかを決め直す時点 |
| --- | --- |
| `questions.md`（Competency Questions） | 置き場所の 3 案すべてに副作用があった。`log.md` に残す案は、追記専用なので「回答済み」を表せない。`indexes/questions.md` に置く案は、`wiki_stats.py` が `indexes/` があるだけで分割済みと判定するので分割の助言が消え、MCP の `list_index` も台帳を索引として返す。wiki のルートに置く案は、lint、グラフ、検索、MCP サーバーの除外の一覧を直す必要がある。答えられなかった問いが実際に繰り返されたら、決め直す |
| `/wiki:plan` | `questions.md` と組で提案されている。`questions.md` と同じ時点で決め直す |
| 主張を独立させる操作としての `/wiki:promote` | 「主張を独立させる」操作と「内容をレビューして承認する」操作を、別のものとして設計し直す必要がある。具体的な需要が出たときに決め直す |
| `broader` の述語 | 根拠なしの型付きエッジ（`requires_evidence: false`）はコードが受け付ける。しかし、`source`、`evidence`、`confidence`、`status` をすべて省いた循環するエッジが、検出 0 件で通ることを 2 体が実際の関数で再現した。`graph-workflow.md` の「全フィールド必須」の契約との食い違いと、循環の検査がないことを先に解いてから決め直す |
| `/wiki:lint --fix` | 現行の lint の契約は「検出するが修正しない」である。1 回の lint で機械的な指摘が 20 件を超えたら決め直す（作者の決定） |
| `reviewed_at` | 具体的な需要が出たときに決め直す |
| `howto` | 具体的な需要が出たときに決め直す |

### 導入の段階

| 段階 | 入れるもの | 始める合図 |
| --- | --- | --- |
| 1 | lint の 4 つの検査（`index_type_mismatch`、`unresolved_sources`、`missing_raw`、`unknown_tags`）と、本書 | 今 |
| 2 | source の `## 主張と行き先` を、記録として残すことだけ。取り込みの手順（references）と `SCHEMA.md.template` を改める。記録した行き先どおりにページを更新することは、まだ求めない | 段階 1 のあと |
| 3 | `kind: "claim"` のページ、`claim` に限る 3 値の `status`、記録した行き先どおりにページを更新する規定。オプトインにする | 記事の単位の PoC に合格したとき |

- 段階 3 の合図に、件数は使わない。「`source_only` 以外の行き先が 10 件たまったら入れる」という案が検討の中で出たが、件数は LLM 自身の未検証の判定を数えているだけで、PoC を迂回できる。
- `ontology.yaml` の `claim` に `maps_from: {type: concept, kind: claim}` を足すことは、段階 3 の `kind` の付与とは別の、さらに後の段階にする。`maps_from` を足すと、`concept:a --depends_on--> concept:b` の主語が `claim:a` に変わる。`depends_on` は主語に `claim` を受け付けないので、型の不一致になる。参照切れを直しただけでは、グラフの移行は終わらない。
- どの段階も、利用者に見える変更なので、wiki プラグインのマイナー版を上げてから入れる。メジャー版が要る要素はない。段階 1 は 0.7.0、段階 2 は 0.8.0 で入れた。段階 3 の版の番号は、実装のプルリクエストで決める。
- 既存のページを一括で分割しない。

### 作者の決定（2026年11月9日）

| 論点 | 決定 |
| --- | --- |
| `--fix` | 今は入れない。1 回の lint で機械的な指摘が 20 件を超えたら決め直す |
| 記事の単位の PoC の規模 | 固定の 3 資料、2 モデル、3 回、現行と変更案の 2 方式で 36 件にする。捏造と条件の脱落が 0 件であることを必須条件にする |
| プロジェクト固有の記録の置き場所 | プロジェクトの wiki に置く。ユーザースコープの wiki（`~/info-hive/W0_Wiki/`）には、プロジェクトを超えて使える知見だけを残す。SemaSynth の記録（source 28 本と raw 34 ファイル）は SemaSynth のプロジェクトの wiki（`C:\works\semasynth-dev\wiki\` と `raw\`）に移した。作者のグローバルな指示（`CLAUDE.md`）も、プロジェクト固有の記録はプロジェクトの wiki に残すよう改めた |
| 空白を含むファイル名 | 改名する。4 本を改名し、被リンクと frontmatter のリストを付け替えた |

PoC の資料は、SemaSynth のプロジェクトの wiki の source から取る。

## 理由

- **足りないのは検査と記録である。** きっかけ別のコマンド、ページの種類、索引、グラフ、`experience-pattern` の `status` のように、提案の骨格の多くは現行のプラグインに既にある。一方で、作者の wiki で起きた索引の分類の誤りと体系の外のタグは、今の lint では見つからない。取り込みで抜き出した知見をどこへ送ったかも、どこにも残らない。
- **lint の検査は、既存のページを変えずに入れられる。** 検査は LLM の判断に頼らず、指摘を出すだけでページを書き換えない。指摘を見て直すかは利用者が決める。
- **記録と更新を分ける。** 主張と行き先を残すことは、4 体が独立に至った唯一の改善策である。ただし効果は測っていない。行き先どおりにページを更新させる規定は、どの判定規則も「モデルが変わっても同じページ割りになる」ことを示せていないので、PoC で一致を測ってから入れる。
- **承認済みの ADR と食い違う要素を採らない。** `type: journal` は ADR-0006 と、`scope` は ADR-0008 と、`type: graph` と入れ子の `relations` は ADR-0009 と食い違う。どれも、提案の目的は既存の仕組みで果たせる。
- **保留は、副作用が先に解けていない要素である。** `questions.md` は置き場所の 3 案すべてに副作用があり、`broader` はグラフ層の契約と食い違う。需要が出る前に入れると、副作用への対処だけが先に要る。

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| 提案を一括で導入する | 承認済みの ADR（0006、0008、0009）と食い違う要素を含む。提案自体にも誤りがある。たとえば「8 コマンド」の一覧表は 6 本で、`status` は 4 値なのに「三段階」と書かれ、`sources` が source ページの ID なのか raw の実体なのかが食い違う |
| 段階 3 の合図を件数にする（`source_only` 以外の行き先が 10 件たまったら） | 件数は LLM 自身の未検証の判定を数えているだけで、PoC を迂回できる。2 体が致命的な欠陥と判定し、案を出した体も反論しなかった |
| `kind: "claim"` のページに `status` を持たせない | 持たせないと、グラフを使わない wiki で、古い主張を機械的に見つける手段がない。持たせない側の 2 体は、この指摘に反論できなかった |
| `kind: "claim"` のページに 4 値の `status`（`disputed` を足す） | 案を出した体が自ら 3 値に縮めた。矛盾は本文の `## 矛盾` で表せる |
| `kind` の付与と `maps_from` の追加を同じ段階にする | `depends_on` が主語に `claim` を受け付けないので、既存のエッジが型の不一致になる |
| lint に `log.md` の書式の検査を足す | `wiki_evolve_loop.py` が正規に出す `- YYYY-MM-DD: ...` の行と、`log.md` の冒頭の前文を誤って検出する。2 体が反例を示した |
| SemaSynth の記録をユーザースコープの wiki に残し、ADR-0008 か作者の指示を改める | 再利用できる知見だけを `concept` に出す運用が前提になる。作者は、記録をプロジェクトの wiki に移すほうを選んだ |
| SemaSynth の記録をタグで区別する | ADR-0008 の「ユーザースコープの作業領域にプロジェクト固有の情報を置かない」という境界を満たさない |

## 影響

- **lint の 4 つの検査は、段階 1 として wiki 0.7.0 で入れた。** `info-hive-wiki` の変更は to884/info-hive-wiki#29（`v0.7.0`）、`tests/` の試験は to884/info-hive-dev#48 で扱った。本書は文書だけを足す。
- **段階 2 では、取り込みの手順と `SCHEMA.md.template` を改める。** wiki 0.8.0（to884/info-hive-wiki#32、to884/info-hive-dev#54）で入れた。主張と行き先の表を足すと source ページが大きさのソフト上限（10,000 文字）を超えるかは、実際の取り込みではまだ確かめていない。#54 の見積もりでは、20 行の表で約 1,800 文字、22 行になり、文字数より行数（100 行）の上限が先に効く。
- **段階 3 では、`page-conventions.md` と `ingest-workflow.md` の改訂と、プラグインのマイナー版の更新を同じ変更にまとめる。** `ontology.yaml.template` への `maps_from` の追加は、その後の別の変更にする。
- **作者の wiki の手直しは、プラグインの段階とは別に行う。** レポートでは、`index.md` の「シンセシス」の欄にある 16 本を「ソース」の欄へ移すこと、`log.md` の 140 行目の規定外の書式を直すことを、段階 0 として挙げている。承認の時点（2026年11月9日）で、`index.md` の「シンセシス」の欄には `type: "synthesis"` のページだけが並んでいる。`log.md` には、規定の操作名にない `update` の行が 2 行残っている。SemaSynth の記録を移したので、行番号は当時と変わった。
- **ADR-0008 との関係。** ADR-0008 は変えない。SemaSynth のプロジェクトの wiki は、ADR-0008 の作業領域（`<プロジェクトルート>/<プロジェクト名>/wiki`）ではなく、プロジェクトルートの直下に置いた。`semasynth/` が既にコードのサブモジュールの名前だからである。ADR-0008 の配置とのずれとして、ここに記録する。
- **ADR-0006 と ADR-0009 との関係。** どちらも変えない。日々の記録は `log` に置き、グラフは派生の索引のままにする。
- **SemaSynth の段階の完了やテスト件数のような記録は、記事の単位では扱いが決まらない。** どこまでを wiki で育てるかは、`SCHEMA.md` に書く必要がある。

## 未決の事項

- **PoC の合格基準。** 知見の recall 90%、配置先の一致率 85%、同じページに置くかの判定の F1 0.90、再処理での重複 0 は提案値で、達成の見込みは分からない。冪等性（同じ wiki に同じ入力を再処理する）と独立一致（同じ初期状態から別のモデル、別の回で同じ配置に至る）は、別の試験として分ける。全件を `source_only` にして一致率を稼ぐ出力が合格しないよう、SemaSynth から出た concept の本数を現行の手順と比べる。
- **主張の根拠の持ち方。** 平坦なキーで持つか、本文の `## 根拠` の節に書くか。rag と連携した PDF の source では `raw:` が絶対パスなので、raw の行番号を根拠の位置にはできない。
- **段階 3 を既定にするか。** オプトインで入れたあと、既定にするかは PoC の結果を見て決める。
- **取り込みでの昇格の判定。** 「条件を保ったまま、別の資料や将来の問いに再利用できるか」は意味の判断のままで、機械化できていない。SemaSynth の記録から concept がほとんど作られない偏りを解けるかは、この判断にかかっている。

## 見直す条件

- 1 回の lint で、機械的な指摘が 20 件を超えた。`--fix` を入れるかを決め直す。

- 保留したそのほかの要素（`reviewed_at`、`howto`）に、具体的な需要が出た。
