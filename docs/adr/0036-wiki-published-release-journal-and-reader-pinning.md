## 決定

公開版を使う wiki では、検証済みの Markdown・索引・互換グラフ・意味レコードと Ossie 文書を、1つの版として公開する。既存の CLI と MCP はこの版の wiki を読み、元の場所にある編集中の Markdown や生成中の索引は検索対象に入れない。

- **用意と承認。** ロックの外で、基準版と定義版を固定し、影響範囲を調べ、成果物を作る。`wiki_apply.apply_plan()` は `plan_id`、wiki、基準版、前後の定義版、相対パスと SHA-256 を含む計画の指紋を照合する。定義版は互換用定義・wiki の判断情報・Ossie Ontology の指紋から算出する。書く内容は承認した成果物のバイト列に限る。隔離試験の ingest は、確認済みのメーカー・品番と出典・引用を含む入力を承認済みとして渡す。試行と基準版の当て直しはロックを持たずに行う。
- **競合。** ロック内で基準版・定義版・完了記録を再検査する。新しい公開があれば古い成果物の公開を拒否する。試験の ingest は、同じ定義で承認入力が同じ場合に限り、最新の記録へ同じ操作を当て直す。メーカー・品番と関係のキーは決定的に計算し、新しい証拠行を既存の主張に結ぶ。定義が変わっていたら入力の再検査に戻す。汎用の適用操作は新しい計画の指紋を必要とする。
- **公開と復旧。** 管理領域は wiki ごとの `.wiki-cache/apply/`。成果物を `staging/` に書き、マニフェストの指紋を公開版 ID にする。ロック内で旧版・新版・計画を日誌に記録し、`releases/<id>/wiki/` に成果物を公開して検査し、最後に `current` を原子的に差し替える。完了記録は計画 ID と指紋を保持する。次の書き手または `recover` は残った日誌を先に完了させる。同じ計画の再実行は完了済みの版を返す。ポインターからたどれない候補を読み手に渡さない。
- **ロックとファイル。** 公開版の書き手は、現行の `wiki_fsguard.WriteGuard` に経路・ファイル・ロックの検査を通す。公開操作では、残る名前のロックファイルと OS の排他を使い、プロセス終了で排他が解けた後も日誌を残す。ライブのファイルを直接変更する ADR-0023 の手順は別の契約を維持する。wiki 内の raw や、記録済みの原本の根と重なる構成は拒否する。ファイルは同期してから公開し、POSIX ではディレクトリの名前も同期する。保留記録を書いた直後の復旧は、NTFS の仮想ディスクを使う隔離 Hyper-V ゲスト OS の強制停止で検証する。検証範囲は仮想マシンまでとする。
- **読む版。** 検索は `release_id` を返す。MCP の `get_page`・`list_index`・`graph`・`lint` と CLI に同じ ID を渡して、本文・索引・グラフを同じ版から取得する。browse のサーバーは起動時の版に固定し、同じ URL 空間で画像を含む内容を返す。版指定と取り下げは元の wiki の公開履歴に対して検査する。取り下げ済みの版は配信しない。公開版の検索は、公開ディレクトリにキャッシュを書かず BM25 で実行する。この段階で固定する引用の範囲はスナップショット内の本文と添付である。

## 初回の基準と公開状態の照合

- 初回用の候補を作る前に `capture_live_base(wiki)` を呼ぶ。ライブのファイルと確定済みのライブ書き込みの記録から指紋を作り、公開計画の `live_base` と承認ハッシュに含める。`apply_plan` は候補を準備した後、共通のロックの内側でその指紋を再照合する。初回の日誌を前に進めるときも、ポインターを置く前に同じ指紋と照合する。
- 新しい公開マニフェストは計画の承認ハッシュを持つ。初回の公開状態の印は wiki 直下の `.wiki-publication` に置く。公開先と完了記録を確かめてから `current` を進め、それと同じ完了記録を `publication-head.json` に置く。日誌は、公開先・完了記録・ポインター・先頭記録を照合してから片づける。
- 公開の印か公開記録が残っている場合、`current` がなくなると読む口と書く段を止める。先頭記録とポインターが同じ版を指し、公開マニフェスト、成果物の指紋、完了記録、履歴が揃うときだけ、その版を読めるか再実行の結果として返せる。ポインターを書いてから先頭記録を書くまでに中断した場合は、日誌が示す成果物と完了記録を照合して `recover` で先頭記録を揃える。切り替え済みのポインターに対する完了記録が欠ける場合は、日誌があっても復旧を進めない。
- 完了済みの旧形式は、公開先と完了記録を唯一の連続した履歴に照合できる場合に読める。次の公開で新形式へ移す。未適用の旧形式の計画は指紋を取り直す。処理途上の旧形式の日誌は、その形式を扱う実装で復旧を済ませる。
- 管理領域を復元するときは、wiki 直下の公開状態の印と管理領域の両方をバックアップの対象にする。公開を続けて先頭を以前の内容に戻す場合、検証済みの以前の内容を新しい版として公開する。

## 公開版への通常保存

- `ingest`・`query`・`learn` は共通の `begin`・下書き・`diff`・`apply` を使う。公開版では `view` が示す版から規約・索引・記事を読み、同じ ID を `begin` に渡す。原本の保存は従来の raw の根で行い、その根を記録する。管理する原本の指紋が記事にある場合は公開ロック内でも照合する。RAG の範囲外の原本はジョブが返した指紋を引き継ぐ。
- 承認時の計画と下書きのバイト列は wiki 内の `.wiki-cache/apply/saves/` に保存する。作業用ディレクトリが消えても、`retry --plan-id … --expect-sha256 …` で同じ内容を再試行できる。承認時に参照した記事、対象ページ、定義が変わった場合は保留する。それ以外の並行公開では、同じ差分を新しい版に当て、索引とログへの追記を保つ。候補の公開と復旧は共通の日誌を使う。
- 保留記録は、本文を同期してから同じディレクトリ内の最終名に移す。Windows では `MoveFileExW` の `MOVEFILE_WRITE_THROUGH` を指定してから次の処理へ進む。POSIX では名前を置いたディレクトリと、初回に `saves/` を置いた親を同期する。新規受付の一時名は計画 ID から決める。排他的にリンクを置いた直後に中断した場合は、受付と共用するロックの内側で同じ実体を指す2つの名前を照合し、一時名だけを外す。この回収を `pending` や `retry`、切り戻しの保留照合で行う。記録を更新するときは、計画ごとのロックで原子的に置き換える。
- 公開候補には、保存の計画 ID と承認ハッシュを含む結果を封印する。再試行は、公開の完了記録と封印した結果を照合し、すでに適用済みならその公開版 ID を返す。これにより、公開ポインターの書き換え前後で中断しても記事、索引、ログを重ねて適用しない。
- Markdown が変わると、互換グラフを再生成して一緒に公開する。既存の Ossie 出力が `WikiArticle` を `sem_articles` に写す構成なら、新規・更新した記事の版を SQLite と JSONL に追加する。形式化済みの主張、根拠、履歴を保つ。通常保存の Markdown から意味上の主張や履歴を自動で確定する処理は、別の承認を要する。

## ライブへの切り戻し

- `plan-return-live` は、初回公開時のライブの指紋、今の公開版の ID、切り戻し前後のファイルと指紋、原本の根をもとに承認用の計画を作る。ライブにだけあるファイルを保持し、他のファイルに最終の公開版を反映する。初回公開で再生成したグラフなど、同じパスの元のライブ内容を上書きするときは `.wiki-cache/apply/return-preimages/<plan_id>/` に元のバイト列を保全する。公開後にライブが別途変わった場合や、公開後の追加先がライブ専用ファイルと重なる場合は停止する。
- `return-live` は共通の適用ロックで公開履歴とライブを照合し、承認済み保存の受け付けと共用するロックで未適用の保存がないことを確かめてから切り戻しの日誌を書く。未適用の承認があれば、適用または明示的な取り消しが済むまで切り戻しを始めない。日誌を置いたあとの新しい公開保存は、承認済みの保留として受け付ける前に止める。
- 切り戻し中の印を残し、ファイルごとの前後の指紋を照合して書き戻す。途中の内容が計画にない場合は公開版を配信したまま停止する。記事・索引・ログの変更はライブ書き込みの完了記録にも記録し、既存の完了記録の世代を引き継ぐ。グラフと Ossie の成果物も同じ切り替えで書き戻し、ライブ側で通常どおり再生成できる。全ファイルと完了記録を確認してから、wiki 直下の印を原子的にライブに切り替える。
- 中断時は同じ承認の `return-live` か `recover` で続きを実行できる。ファイル、状態の印、完了記録に決めた一時名を使い、中断した日誌の一時ファイルを回収する。切り替え後も日誌が残っていればライブ保存を待たせる。日誌を片づけたあとの再試行は完了を返す。切り戻し中の印が残り日誌が失われた場合は、管理領域を復元するまで書き込みを止める。
- 既定の読み取りは切り替えまで最終公開版を使い、その後はライブを使う。公開ポインター、公開版ごとの完了記録、成果物を保持するため、ID を指定した読み取りは切り戻し後も同じ本文と添付を参照する。個別に取り下げられた版の扱いは従来どおりである。

## 切り戻したライブの再公開

- 切り戻しの完了記録にライブの世代とライブ専用ファイルを残す。`plan-republish-live` は前の公開版に載っていたファイル、切り戻し後の完了記録が示すファイル、追加で公開すると指定したファイルから候補を作る。ライブ各世代の変更前後の指紋を照合し、指紋が連続しないパスは公開範囲の明示指定を求める。記事・索引・ログは取得時点のライブのバイト列を使う。既存の意味レコードの履歴を読み継ぎ、ライブで変わった記事を Ossie の記事行に追加する。互換グラフは候補に含まれる記事から生成する。
- 承認する計画には、ライブ全体と完了記録の指紋、親になる公開版、切り戻し記録の指紋、候補の全ファイルの指紋を含める。共通の適用ロックと保留受付のロックの内側で照合し、承認済みの保留があれば処理を待つ。承認後にライブ保存が入った場合は候補を作り直す。
- 再公開の日誌が確定した後はライブ保存を止める。公開ポインターや先頭記録の更新中も、既定の読み取りはライブ、固定した読み取りは従来の公開版を使う。切り戻しの完了記録を履歴へ保存し、候補と記録を照合してから、既定の読み取り先の印を公開版へ切り替える。中断時は `recover`、または同じ承認済み計画で再試行する。以前の切り戻しと公開の計画は、再試行しても新たに適用しない。次の切り戻しは直近の公開開始時のライブ基準を使う。

## 段階

まず合成 wiki で、共通の適用口を使った並行 ingest、公開切替前後の中断、古い定義の拒否、MCP と browse の版固定、既存グラフ・lint の結果を検証する。ライブ wiki の既存 `new`・`edit`・`ops` をすべて移す作業、原本の公開方針、物理的なパージ、長期運用時の保持・回収は、本番の有効化前に扱う。SemaSynth wiki はこの工程で更新しない。
