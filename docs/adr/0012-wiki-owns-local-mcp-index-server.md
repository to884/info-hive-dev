# ADR-0012：wiki が 127.0.0.1 の MCP サーバーを持ち、モデルと索引の唯一の持ち主になる

| 項目 | 内容 |
| --- | --- |
| 状態 | 承認 |
| 決定日 | 2026年11月6日 |
| 決定者 | info-hive の開発者（このリポジトリの作者） |
| 関連 | ADR-0001、ADR-0007、ADR-0010、ADR-0011、[統一の決定のための追加測定](../research/embedding-backend-decision-2026-11-06.html)（§2、§11、§13）、[MCP サーバーの実装の記録](../research/wiki-mcp-server-2026-11-06.md) |

## 背景

ADR-0011 で、wiki と rag は同じモデル（ruri-v3-130m の ONNX）、同じベクトル索引（usearch）、同じ語彙エンジン（Tantivy）を使うと決めた。残るのは、モデルと索引をどのプロセスが持つかである。

stdio の MCP サーバーは、ホストのセッションごとに起動される。セッションが 3 つあれば、モデルは 3 回読み込まれ（R-130 の ONNX で約 737 MiB ずつ、統一の測定）、索引の書き手も 3 つになる。Windows では、別のプロセスがメモリに写像した usearch の索引ファイルを置き換えられない（追加測定 E5 の (a)、20 回とも PermissionError）。Tantivy も、別のプロセスの読み手が reload を続けると commit が失敗した。

ADR-0001 は、127.0.0.1 だけで待ち受け、Wiki を外部に送らず、Wiki を書き換える API を持たないサーバーを認めている。ADR-0007 は、OS の常駐サービスを初期構成に含めないと決めている。

## 決定

| 対象 | 決定 |
| --- | --- |
| 持ち主 | wiki のプラグインが、127.0.0.1 で待ち受ける streamable HTTP の MCP サーバーを持つ。モデルの読み込み、埋め込み、索引の書き込み（初回の再埋め込みを含む）は、このサーバーだけが行う |
| 入口 | wiki に `.mcp.json` を足し、stdio の中継を登録する。中継はロックファイルを取り、`server.json`（ポート、トークン、pid）の指すサーバーが生きていればそれを使い、いなければ起動する。同時に起動された中継が、サーバーを 2 つ起動しないようにする |
| 起動のしかた | サーバーは中継の子として、Windows では窓のない自分のコンソール（`CREATE_NO_WINDOW`）と新しいプロセスグループで起動する。`DETACHED_PROCESS` は使わない（2026年11月11日に改めた。info-hive-wiki#36、理由の節）。起動の前にロックの中で `server.json` を消し、新しく現れた `server.json` を今起動したサーバーのものとみなす。venv の `python.exe` は本体を子プロセスとして起動するので、`Popen` の pid では確かめない。WMI のように、ホストの外からプロセスを起動する方式は使わない |
| 寿命 | 要求がない状態が一定の時間続いたら、サーバーは自分で止まる。次の呼び出しで中継が起動し直す。OS のサービスとしては登録しない |
| 防御 | 127.0.0.1 だけで待ち受ける。起動ごとにトークンを作り、Bearer で確かめる。Host ヘッダーを確かめ、DNS rebinding を防ぐ。認証は ASGI のミドルウェアで書く |
| 応答 | streamable HTTP の応答は、SSE ではなく JSON にする |
| 上乗せの目安 | 関数の直接呼び出しに対する、中継経由の上乗せの p95 は 15 ms 以内とする（最初の目安の 10 ms から緩めた） |
| ツール | `query`、`get_page`、`list_index`、`lint`、`stats`、`graph`、`index_chunks`。`lint` は検査だけで、直す操作は持たない。統一の測定が挙げた `ingest_source` は外す |
| 索引の置き場所 | wiki ごとに `%LOCALAPPDATA%/info-hive/index/<wiki のハッシュ>/`（macOS と Linux は XDG の data ディレクトリ）に置く。wiki の中の `.wiki-cache/` には置かない。`server.json` は `%LOCALAPPDATA%/info-hive/` に置く |
| rag | rag は wiki のサーバーの MCP クライアントになる。rag の子ワーカーは抽出と OCR を行い、チャンクを `index_chunks` でサーバーに渡す。rag の `search` ツールは窓口として残し、中で wiki のサーバーに頼む。wiki が無効なら、検索できないと報告する |
| コマンド | `/wiki:query` などのコマンドは MCP のツールを呼ぶように移す。MCP が使えないときは今の CLI に戻る |

## 理由

- 試作（追加測定 E10）で、中継を 4 つ同時に起動してもサーバーは 1 つだけだった。中継が終わってもサーバーは残り、次の中継はそれを使った。要求がなくなって 20 秒の設定で、サーバーは止まった。
- トークンのない要求と違うトークンの要求は 401、Host ヘッダーを偽装した要求は 421 になった。
- 中継経由の上乗せは、応答を JSON にし、認証を ASGI のミドルウェアで書いた構成で 12.8 ms だった。認証を外しても 12.6 ms で、残りの約 9 ms は Python の MCP の SDK が HTTP で 1 回の呼び出しを処理する費用である。中継の 1 段は約 3 ms だった。実装では、同じ処理の直接呼び出しとの p95 の差が 4.7〜11.2 ms だった（実装の記録）。
- Claude Code のデスクトップアプリ（Claude 4.16336.0.0、CLI 2.1.317）は、stdio の MCP サーバーを KILL_ON_JOB_CLOSE のジョブに入れない。アプリ本体から下のプロセスはすべて 1 つのジョブに入っているが、そのジョブの制限の旗は 0x0（KILL_ON_JOB_CLOSE も BREAKAWAY_OK もない）だった。中継が `DETACHED_PROCESS` で起動したサーバー（ホストから見て孫プロセス）は、セッションが終わった後も残った（実装の記録）。ターミナルから単体で起動した CLI は、測り直していない。測定に使った Python の MCP の SDK はジョブ（KILL_ON_JOB_CLOSE）を使うので、そのクライアントの下では、サーバーは中継の終了とともに止まった。
- 最初は `DETACHED_PROCESS` で起動していたが、Windows では画面（既定のターミナルの窓）が 1 つ出た（info-hive-wiki#36）。コンソールを持たない venv の `python.exe` が本体の `python.exe` を起動するときに、本体に新しいコンソールが作られるためである。窓の題はサーバーの venv の `Scripts\python.exe` のパスで、本体の子に `conhost.exe` が付いていた。`CREATE_NO_WINDOW` で起動すると、サーバーは窓のない自分のコンソールを持ち、本体はそれを引き継ぐので、窓は出なかった（`tests/wiki/check_server_console.py`）。2 つの旗は併せると `CREATE_NO_WINDOW` が無視されるので、置き換えた。入口と中継が終わってもサーバーが残ること、`claude -p` のセッションが終わってもサーバーが残ることは、測り直しても変わらなかった（CLI 2.1.321、`check_claude_spawn.py`）。デスクトップアプリそのものを終えたときは、測っていない。
- 同じ理由で、ホストが入口をコンソールなしで起動すると、入口と中継が起動する `uv` や中継の python でも窓が出る（入口を `DETACHED_PROCESS` で起動して、窓が 4 つ出た）。Claude Code は入口の `uv.exe` にコンソールを付けて起動するので今は当たらないが、ほかのホストに備え、入口、中継、サーバーの子プロセスの起動には、すべて `CREATE_NO_WINDOW` を付ける（`wiki_mcp_common.NO_WINDOW`、`tests/wiki/test_mcp_spawn_flags.py`）。付けたあとは、入口をコンソールなしで起動しても窓は出なかった。
- 追加測定 E10 の補足は「CLI 2.1.316 はサーバーをジョブに入れなかった」と記録していたが、確かめ方に誤りがあった。試作の `job_check_server.py` は `GetCurrentProcess()` の疑似ハンドルを ctypes の既定の int で渡すので、ジョブの中でも入っていないと返す。サーバーがセッションの後も残るという結論は、測り直しでも変わらない。
- 1 つのプロセスが索引を持ち、一時ファイルに保存してから置き換える方式は、Windows でエラーがなかった（E5 の (b)）。書き手を 1 つにすれば、別のプロセスの写像による置き換えの失敗は起きない。
- `ingest_source` は wiki にソースを登録する操作で、ADR-0001 の条件 3（Wiki を書き換える API を持たない）に当たる。`index_chunks` が書くのは wiki の外の索引で、wiki の Markdown は変えない。
- 依存の向き（rag → wiki）と合う。rag は wiki のサーバーに MCP で頼むので、別のプラグインの内部のパスを組み立てない。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| セッションごとの stdio の MCP サーバーがモデルと索引を持つ | 採らない。モデルがセッションの数だけ読み込まれ、索引の書き手が複数になる |
| 共通のコアを両プラグインに複製する、共通のパッケージ `info-hive-core` を作る | 採らない。プロセスの数だけ書き手が増える |
| wiki と rag を 1 つのサーバーにまとめる | 採らない。プラグインの境界と `CLAUDE_PLUGIN_ROOT` の扱いがあいまいになる |
| 中継とサーバーのあいだを、MCP ではなく軽い JSON の HTTP にする | 採らない。上乗せは減る見込みだが測っておらず、目安を 15 ms にすれば今の形で収まる |
| サーバーを WMI で起動し、ホストのジョブの外に出す | 採らない。Claude Code では要らない。ホストの外からプロセスを起動することになる |
| OS のサービスとして常駐させる | 採らない。ADR-0007 の決定に反する |

## 影響

- ADR-0007 のうち、モデルの保持と共有、埋め込みと索引更新の実行場所は、本 ADR で置き換える。PDF の登録を永続ジョブとして受け付けること、抽出と OCR を rag の子ワーカーで行うこと、接続中だけ動いて次の接続で再開することは変えない。ADR-0007 の状態の列を改める。
- ADR-0001 の 3 つの条件を満たす。サーバーを作るときは、待ち受けのアドレスの固定、起動ごとのトークン、Host ヘッダーの確認を実装する。
- ADR-0010 の未決 4（RAG への経路）に、4 つ目の案が加わる。閲覧の画面が wiki の MCP サーバーのクライアントになり、rag の索引も含めて検索する案である。ADR-0010 の状態は変えない。
- サーバーが動いている間は、モデルを読み込んだ分のメモリが常駐する。追加測定では、wiki 規模で 2.53 GiB（private）だった（ADR-0011 の影響を参照）。
- Claude Code のデスクトップアプリでは、サーバーはアプリのジョブの中に入る。ジョブを閉じても止められないので、セッションをまたいで共有できる。アプリを終了したときにジョブの中のサーバーが止まるかは確かめていない。止まっても、次の呼び出しで中継が起動し直す。
- プラグインの `.mcp.json` が中継を登録するので、`wiki` を入れると MCP サーバーも有効になる。初めて呼び出すときに、依存（約 1 GB）とモデル（約 530 MB）を取得する。そのあいだにホストの待ち時間を超えないかは確かめていない（実装の記録の「残った課題」）。

## 見直す条件

- ホストが stdio の MCP サーバーを、閉じると中のプロセスを止めるジョブに入れていると分かったとき。そのホストでは、サーバーをセッションをまたいで共有できない。
- 中継経由の上乗せが 15 ms を超えたとき。
- 索引の書き手を複数のプロセスにする必要が出たとき（ADR-0011 の見直す条件と同じ）。
