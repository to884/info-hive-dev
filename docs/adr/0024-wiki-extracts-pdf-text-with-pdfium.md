## 背景

PDF を wiki に取り込む経路は 2 つあり、本文の取り出し方が違う。

| 経路 | 本文の取り出し方 | 形 |
| --- | --- | --- |
| rag が使えるとき | rag のワーカーが、PDFium（pypdfium2）の文字の層をページごとに取り出し、ページを判定する（`rag_pdf.inspect_page`）。文字化け、スキャン、縦書きと判定したページと、`ocr_mode` が `always` のときのすべてのページは、OCR の結果で本文を置き換える（`extract_pages`） | `## p. <番号>` の見出しとページの本文をつないだ `document.md` |
| rag を使わないとき | `ingest-workflow.md` の手順 2（`commands/ingest.md` では手順 3）で、`pdf-reading` スキルがあればそれを使う。なければ `pdftotext` か `pdfminer` で取り出す | 方式による。ページの区切りは改ページの文字（U+000C）か、ないこともある |

同じ PDF でも、経路によって、ページの区切り、読み順、表の形が変わる。そのため、要約ページの根拠の位置も経路ごとに変わる。

2026年11月15日のベンチマーク（[レポート](../research/markitdown-benchmark-2026-11-15.md)）では、Office で書き出した 4 つの PDF（1 段組みの文書、2 段組みの文書、スライド、表計算）で、次の方式を比べた。

- PDFium の文字の層（`inspect_page` が返す本文をそのまま並べたもの。判定の結果は使っていない。OCR なし）
- pdftotext
- pdfminer
- MarkItDown 0.1.9

PDFium の結果は次のとおりだった。

- 4 つとも、原本の順に読めた割合は 1.0 で、Sol の総合点は 4、4、5、5 だった。意味を変える誤り（致命的）はなかった。
- pdfminer は、2 段組みで文の途中に反対の段を挟み、表計算で費目と値の順を入れ替えた。
- pdftotext は、表をセルの列ごとに並べた。
- 表のセルが 1 行に残った行の数は、PDFium が、1 段組みで 4/5、スライドで 5/5、表計算で 8/9 だった。pdftotext と pdfminer は、どれも 0 だった。2 段組みでは、3 方式とも 0/5 だった。

ただし、このベンチマークには限りがある。

- 試料は、Office で書き出した PDF だけである。組版のソフト（LaTeX、InDesign など）で作った PDF、段の多い PDF、縦書きの PDF は試していない。
- PDFium で読み順が崩れなかったのは、Office が文字を論理的な順に並べて書き、PDFium がその順に返したためと考えられる（推測）。PDFium が版面を解析しているのではなく、ファイルの中の順に文字を返しているだけなら、ほかの PDF では、版面を解析する方式が上回ることもありうる。
- 測った pdftotext は、Git for Windows に入っていた Xpdf 4.00 で、Poppler ではない。
- PDFium の出力では、表は Markdown の表にならず、セルを空白で区切った行になる。ヘッダーとフッターの文字も本文に残る（4 方式とも同じ）。
- 測ったのは文字の層の取り出しだけである。ページの判定、OCR、チャンクの分割は測っていない。
- `pdf-reading` スキルと、Claude Code の Read で PDF を直接読む方法は、比べていない。

## 決定

### 何をそろえ、何をそろえないか

| 対象 | そろえるか |
| --- | --- |
| ページの区切りと番号 | そろえる。どちらの経路でも、PDF の物理ページの順に `p. 1` から番号を付ける。要約ページの根拠の位置（ページ番号）は、経路によらず同じに書ける |
| 文字の層の本文 | そろえる。ただし、同じ `EXTRACT_REVISION` と同じ pypdfium2 の版で取り出したときに限る。比べるのは、改行を `\n` にそろえた文字列であり、ファイルのバイト列ではない（rag の `document.md` は、Windows では CRLF で書かれる） |
| ページの判定 | そろえる。rag の `inspect_page` と同じ判定（`text`、`garbled`、`scan`、`vertical`、`blank`）を、同じ閾値で行う |
| 最終の本文 | そろえない。rag が OCR したページ（`ocr_mode` が `auto` のときは判定が `garbled`、`scan`、`vertical` のページ、`always` のときはすべてのページ）では、rag の本文は OCR の結果になる。wiki は OCR をしないので、そのページの本文は rag と違う |

### 取り出し方と出し方

| 対象 | 決定 |
| --- | --- |
| 対象 | rag を使わない取り込みで、PDF の本文を取り出す段。rag が使えるときの経路（`register_pdf` と `document.md`）は変えない |
| スクリプト | wiki に `wiki_pdf.py` を足す。`uv run --script` で動かす。依存は `pypdfium2` だけにして、版を `==` で固定する。uv は、wiki の MCP サーバーと検索ですでに使っている |
| 取り出し方 | ページごとに PDFium の文字の層を取り出し、`\r\n` と `\r` を `\n` にする。`inspect_page` と同じである |
| 形 | rag の `_write_markdown` と同じつなぎ方にする。ページごとに `## p. <番号>`、空行、ページの本文を並べ、ページのあいだを `\n\n` でつなぐ。ページの本文が改行で終わるときは、そのまま残す |
| 判定と本文 | 判定が `text` のページは、本文を出す。`garbled`、`scan`、`vertical` のページは、本文を出さず、OCR が要ることと判定の種類を書いた 1 行を出す。`blank` のページは、見出しだけを出す |
| 確かめるべきページ | 判定とは別に、`image_coverage` が 0.5 以上のページを、確かめるべきページとして `--json` で返す（0.5 は最初の値で、承認の条件の検証で見直す）。判定が `text` でも、本文の大部分が画像で、文字の層にヘッダーしかないページがありうるためである。この印は判定を変えないので、rag との判定の一致は崩さない |
| 分けて読む | 本文は標準出力に出す。1 回の出力の文字数に上限を設け、続きがあれば、続きの位置を `--from <ページ>:<ページの中の文字の位置>` の形で標準エラーに出す（`wiki_session.py show` と同じ読み方）。1 つのページが上限を超えても、ページの途中から続けられる。`--pages <最初>-<最後>` でページを絞れる |
| `--json` | 全体の要約として、PDF のバイト列の SHA-256、ページの数、判定ごとのページの数、確かめるべきページの数、`EXTRACT_REVISION`、pypdfium2 と PDFium の版を返す。判定ごとのページ番号と、確かめるべきページの番号は、それぞれ先頭の 200 個までにし、それより多ければ、そのことを示す印を付ける。ページごとの詳細（判定、文字数、`image_coverage`、`bad_ratio`、`cjk_ratio`、本文の SHA-256）は、`--pages` で絞った範囲だけを返す。全体の要約の大きさは、ページの数によらず上限がある |
| 写し | raw の PDF は変えず、取り出した本文の写しも作らない。本文は、同じ版の `wiki_pdf.py` を同じ PDF に動かせば、同じものが出る |
| 版の記録 | 取り込みのログの行の下に、`EXTRACT_REVISION` と pypdfium2 の版をサブ行で書く |
| uv がないとき | 止まって、uv が要ることを伝える。pdftotext や pdfminer に黙って戻らない |
| ほかの読み方 | 手順から、`pdf-reading` スキル、`pdftotext`、`pdfminer` を外す。Claude Code の Read で PDF を開くのは、次の 4 つのときだけにする。図や版面を見るとき、確かめるべきページを見るとき、判定が `blank` のページを見るとき、本文に文として読めない箇所があったときである。本文の出典は `wiki_pdf.py` の出力にし、Read の画像から読み取った内容は、そう書き分ける（下の「読めないページの扱い」） |

### 判定は目安である

ページの判定は、rag が OCR に回すページを選ぶための目安であり、読めないページをすべて見つけるものではない。少なくとも次のページを見逃す（Sol のレビューで、`inspect_page` にスタブを与えて確かめた）。

| ページの状態 | 判定 | 起きること |
| --- | --- | --- |
| 本文が全面のスキャン画像で、文字の層にはヘッダーの 29 文字だけがある | `text` | ヘッダーだけが本文として出る。`image_coverage` が高いので、確かめるべきページには入る |
| 文字がアウトライン化され、文字の層も画像もない | `blank` | 見出しだけが出る。確かめるべきページにも入らない |
| 文字の対応表が誤っていて、ふつうの漢字やかなに化けている | `text` | 化けた文字が本文として出る |

そのため、エージェントは判定だけに頼らない。本文を読んで、文として読めない箇所があれば、そのページも読めないページとして扱う。

### 読めないページの扱い

読めないページの扱いは、rag が実際にできることに合わせて、ページの種類ごとに分ける。rag の既定の `ocr_mode` は `auto` で、`auto` が OCR するのは判定が `garbled`、`scan`、`vertical` のページだけである。`register_pdf` には、ページを選んで OCR させる引数がない。

| ページの種類 | rag で取り戻せるか | エージェントがすること |
| --- | --- | --- |
| 判定が `garbled`、`scan`、`vertical` | `auto` のままで OCR される。OCR の結果が空のこともあり、そのときは rag のページの記録に `ocr_empty` が立つ。本文が戻るとは限らない | ページの番号と数をユーザーに伝え、rag で取り込むかを聞く。rag で取り込んだあと、OCR の結果が空のページは、読めなかったページとして扱う |
| 確かめるべきページ（判定は `text`）、判定が `blank` | 既定の `auto` では OCR されない | ページを Read で開いて見る。画像から読み取った内容を要約に使うときは、要約ページに、そのページを画像から読んだことを書く |
| 本文に文として読めない箇所がある（判定は `text`） | 既定の `auto` では OCR されない | 上と同じ |

どの場合も、取り戻さずに続けるときは、要約ページに、読めなかったページと確かめなかったページを書く。

rag の `ocr_mode` を `always` にすれば、すべてのページが OCR される。ただし、次の 3 つのことから、この ADR の手順には入れない。
- `always` にするのは、`configure` でその PC の設定を変えることである。すべてのページを OCR するので時間がかかり、未完了のジョブがあると設定は変えられない。
- rag のジョブは、登録したときの設定をジョブの中に持ち、その設定で動く。設定を変えても、すでにあるジョブ（`retry_job` で再試行するジョブを含む）は、前の設定のまま動く。
- 新しい設定で OCR させるには、設定を変えたあとで、`register_pdf` で新しく登録する必要がある。

ユーザーが `always` を使いたいと言ったときは、この 3 つを伝える。ページを選んで OCR させる仕組みを rag に足すかは、rag の側で決める（この ADR では決めない）。

### rag とそろえ続ける方法

| 対象 | 決定 |
| --- | --- |
| 持ち方 | wiki は rag のスクリプトを読み込まない（rag は wiki に依存し、別のプラグインの内部のスクリプトは呼ばない決まりである）。wiki が、自分の `wiki_pdf.py` に取り出しと判定を持つ |
| 抽出の識別 | 抽出の結果を識別するのは、`EXTRACT_REVISION` と pypdfium2 の版の組である。wiki は、この組を `--json` とログに残す。rag は今、この組を保存した結果に持っていない。抽出の結果の鍵にも、保存したページ（`page-*.json`）にも、索引の方針の指紋（`Config.fingerprint`）にも、pypdfium2 の版が入っていない（ADR-0014）。そのため、pypdfium2 の版を固定するだけでは足りない。固定する前に作った結果が、同じ鍵のまま使い回されるからである。抽出の結果の鍵だけに版を入れても足りない。指紋が同じなので、本文だけを取り出し直し、索引は前の版のまま使う分岐に入るからである。rag の側では、識別を、抽出の結果の鍵、保存したページ、索引の方針の指紋のすべてに入れ、識別が違う保存済みの結果と索引を使い回さないことを決める必要がある。識別を持たない保存済みの結果（今の形式の `page-*.json` と `document.md`、移す前の古い置き場所の結果を含む）は、識別が違うものとして扱う。これを rag の ADR で決めることを、この ADR の承認の条件にする |
| 契約の試験 | info-hive-dev の `tests/` に、次の試験を置く。<br>1. 同じ PDF を `wiki_pdf.py` と rag の `inspect_page` に通し、すべてのページで判定と数値が同じこと、判定が `text` のページで本文の文字列が同じことを確かめる。<br>2. `wiki_pdf.py` の出力そのものを確かめる。判定が `text` 以外のページの本文が出ていないこと、`--from` で分けて読んだ出力をつなぐと一度に出した出力と同じになること（ページの途中で分けた場合を含む）、つなぎ方が rag の `_write_markdown` と同じ文字列になることを確かめる。<br>3. 試料には、ベンチマークの 4 つの PDF に加えて、判定ごとに 1 つ以上のページを持つ PDF と、上の「判定は目安である」の 3 つの状態の PDF を作って使う |
| 試験の限り | 契約の試験で分かるのは、試料の PDF で一致することだけである。試料に現れない変更は見逃しうる。そのため、取り出し方か判定を変えるときは、wiki と rag の両方の `EXTRACT_REVISION` を同じ値に上げ、試料を足してから変える |
| 組み合わせ | wiki と rag は別々に配られ、利用者の手元で版の組み合わせがずれることがある。ずれても、ページの区切りと番号は同じである。文字の層の本文は違いうるが、`--json` とログに残した識別で、違いに気づける |

## 承認の条件

次の 2 つがそろってから、この ADR を承認する。

> 2026年11月15日の検証（[報告](../research/adr-0024-verification-2026-11-15.md)）で、条件 1 は満たさなかった。日本の官公庁の資料（組版のソフト、作成したソフトの記録がないもの）で、読み順が pdftotext と pdfminer を下回った。この ADR を書き直すか、種類で分けるか、取り下げるかは、作者が決める。

1. **公開の PDF での検証。** 試料、比べる方式、見る点は次のとおりにする。
   - **試料:** 誰でも手に入る公開の PDF を使い、作者の書籍は使わない。Office でないソフトで作った PDF を含める。LaTeX で作った論文（arXiv など）、組版のソフトで作った官公庁の資料、段の多い PDF、縦書きの PDF、スキャンの PDF である。
   - **比べる方式:** `wiki_pdf.py` の実際の出力（判定によって本文を出さないページを含む）、Poppler の pdftotext、Xpdf の pdftotext、pdfminer。
   - **見る点:** 読み順、表のセルが 1 行に残るか、ページの区切り、読めないページの検出。読めないページの検出では、目で確かめた読めないページのうち、判定か確かめるべきページの印で拾えたものの数と、拾えなかったものの数を記録する。
   - **判断:** 次の 2 つを確かめる。
     - 読み順と表: `wiki_pdf.py` が、試料のどの PDF でも、読み順と表で pdftotext と pdfminer を下回らないこと。下回る PDF があれば、その種類と程度を記録する。そのうえで、この決定を変えるか、その種類だけ別の扱いにするかを決める。
     - 読めないページ: 試料のすべてのページを目で見て、読めないページを数える。そのうち、判定と確かめるべきページの印のどちらでも拾えなかったページを、1 つずつ記録する。1 つでもあれば、その状態ごとに、次のどれにするかを決めてから承認する。
       - 拾えるようにする。判定を変えるときは、rag と一緒に `EXTRACT_REVISION` を上げる。
       - 手順で拾えるようにする（エージェントが確かめる条件を足す）。
       - その状態の PDF は、この取り出し方では読めないと手順に書く。
2. **rag の側の決定。** rag の ADR で、次の 2 つを決める。
   - 抽出の識別（`EXTRACT_REVISION` と pypdfium2 の版の組）を、rag の抽出の結果の鍵、保存したページ、索引の方針の指紋のすべてに入れ、識別が違う保存済みの結果と索引を使い回さないこと。
   - 識別を持たない保存済みの結果を、識別が違うものとして扱うこと。

## 理由

- **根拠の位置をそろえる。** rag を使っても使わなくても、ページの区切りと番号は同じになる。あとから rag を入れて取り込み直しても、要約ページのページ番号は変わらない。rag が OCR しないページでは、同じ版のもとで文字の層の本文も同じになる。
- **測った範囲では、もっとも良かった。** Office の PDF 4 つで、読み順は、4 つとも PDFium が pdftotext と pdfminer を上回った。表のセルが 1 行に残った行の数では、2 段組みを除く 3 つで上回った。2 段組みでは、3 方式とも 0 だった。
- **依存が小さい。** pypdfium2 は 1 つのパッケージで 8.1 MiB である。pdfminer.six は 5 つのパッケージで 19.5 MiB、MarkItDown は追加の依存を含めて 189 MiB だった。Python 3.12、3.13、3.14 で入って読み込めることを確かめた（2026年11月15日、pypdfium2 5.15.2）。
- **読めないページを黙って要約しない。** 判定と確かめるべきページの印で、読めないページを知らせ、ページの種類ごとに取れる手を決めた。どれだけ拾えるかはまだ測っておらず、見逃しもある（「判定は目安である」）。拾える割合は、承認の条件の検証で測る。
- **写しを作らない。** 本文は、同じ版の `wiki_pdf.py` で PDF から毎回同じものを取り出せる。raw に写しを置くと、PDF と写しのどちらが正本かが分かりにくくなり、抽出の版を上げたときに写しが古くなる。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| wiki が PDFium の取り出しを自分で持ち、契約の試験で rag とそろえる | 採る |
| wiki が PDFium の取り出しを MCP のツールとして持ち、rag がそれを呼ぶ（ADR-0012 と同じ持ち方） | 今は採らない。複数のページの本文と判定をまとめて返せば、呼び出しの数は問題にならない。採らない理由は 2 つある。<br>1. rag のワーカーが、PDF の抽出のたびに wiki の MCP サーバーの起動と版に頼ることになる。<br>2. rag の抽出の経路を書き換えることになり、この ADR の目的（rag を使わない経路をそろえること）に対して変える範囲が大きい。<br>rag の抽出を変えるときに、改めて検討する |
| wiki だけを PDFium に変え、rag とそろえることは決めない | 採らない。2 つの取り出し方が少しずつ離れていき、同じ PDF の本文とページの扱いが経路で変わる |
| 手順を変えず、pdftotext か pdfminer のままにする | 採らない。測った範囲では、読み順と表で PDFium を下回った。どちらを使うかがエージェントの判断に任されていて、手元の `pdftotext` が Xpdf か Poppler かでも結果が変わる |
| MarkItDown で PDF を取り出す | 採らない。測った範囲では、2 段組み、スライド、表計算の PDF で、意味を変える誤りを作った。ページの区切りも出さない |
| 取り出した本文を raw に写して置く（文字コードの変換の `.utf8.` と同じ） | 採らない。同じ版の `wiki_pdf.py` で同じ本文を取り出せるので、写しはいらない。写しを置くと、抽出の版を上げたときに写しが古くなる |
| 判定を wiki の側で厳しくする（画像の多いページを `scan` にするなど） | 採らない。rag と判定がずれ、同じページを rag は OCR せず、wiki は読めないとすることになる。判定を変えるなら、rag と一緒に `EXTRACT_REVISION` を上げて変える。wiki は、判定を変えない「確かめるべきページ」の印で補う |
| Claude Code の Read で PDF を直接読む | 本文の出典にはしない。どのような本文になるかを測っておらず、ページの判定もできない。図や版面と、確かめるべきページを見るときには使う |

## 影響

- **wiki:** 次を変える。手順を変えるので、マイナーの版を上げる。
  - `skills/info-hive/scripts/wiki_pdf.py` を足す。
  - `references/ingest-workflow.md` の手順 2 と、PDF の置き方の説明を直す。
  - `commands/ingest.md` の PDF の説明を直す。
  - `SKILL.md` のスクリプトの一覧に足す。
  - `CHANGELOG.md` に書く。
- **rag:** この ADR では変えない。承認の条件の 2 で、抽出の識別の持ち方を決める。ページを選んで OCR させる仕組みを足すかも、rag の側で決める。`inspect_page` の取り出し方か判定を変えるときは、wiki の `wiki_pdf.py` も同じ `EXTRACT_REVISION` で変える。
- **info-hive-dev:** `tests/` に契約の試験と試料の PDF を置く。ベンチマークの試料（`docs/research/markitdown-benchmark-2026-11-15/corpus/`）を、試験の試料として使えるようにする。
- **取り込み済みの wiki:** 前の手順（pdftotext や pdfminer）で取り込んだ要約ページの根拠の位置は、書き換えない。取り込み直すときは、新しい取り出し方の本文で、根拠の位置を確かめ直す。
- **利用者:** rag を使わない PDF の取り込みでも、uv が要るようになる。初めて動かすときに、uv が pypdfium2 を取ってくる。

## 見直す条件

- 承認の条件の検証で、PDFium がほかの方式を下回る種類の PDF が見つかったとき。
- 判定の見逃しが、取り込みで実際に問題になったとき。
- rag が、PDFium の文字の層でない取り出し方（版面の解析など）に変わるとき。
- pypdfium2 の版を上げて、契約の試験の試料の本文が変わったとき。
- wiki が OCR を持つことになったとき。
