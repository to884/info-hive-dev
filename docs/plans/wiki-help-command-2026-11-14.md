# `/wiki:help [command]` で個別のコマンドのヘルプを出す（2026年11月14日、3 版目）

`/wiki:help` に、コマンド名を 1 つ受け取って、そのコマンドの詳しいヘルプを出す形を足す設計である。今の `/wiki:help` は、`commands/*.md` の frontmatter から全コマンドの 3 行の一覧を出すだけで、引数を受け取らない。

## この変更で閉じることと、閉じないこと

- **閉じること**: `/wiki:help query`（`/wiki:help wiki:query` も同じ）で、そのコマンドの書式、説明、引数の説明と、`docs/commands.md` の該当する節（使用例と詳しい説明）を、書式付きの Markdown で出す。
- **閉じること**: 利用者が書いた引数の文字列を、そのままシェルのコマンド行に入れない。シェルに届くのは、英数字と `-` だけの名前である（2 の決めごと）。
- **閉じないこと**: `/wiki:help /wiki:query` の形は約束しない。Claude Code の対話のセッションは、メッセージの先頭に並んだスラッシュコマンドを、それぞれのコマンドとして展開することがある（公式の文書の「Stack several skills in one message」）。そのとき `/wiki:help` の引数は空になり、`/wiki:query` の手順も読み込まれる。文書と `argument-description` は、`/wiki:` を付けない名前で書くよう案内する。スクリプト（`--command`）は `/wiki:query` も受け付ける。
- **閉じること**: 名前が見つからないときは、近い名前と使えるコマンドの一覧を示して、終了コード 1 で止まる。
- **閉じること**: 引数なしの `/wiki:help` は、今と同じ一覧を出す（`help` の行に `[command]` と、その説明が付くだけ）。`--json` の一覧の形も変えない。
- **閉じないこと**: 詳しいヘルプのための新しい文章や frontmatter のキーは作らない。詳細は `docs/commands.md` の節をそのまま使う（作者の選択）。節の文章の書き直し（移植元の英語の仮引数 `<source>`、`<question>` など）は、この変更に含めない。
- **閉じないこと**: オプションごとの表や、サブコマンドごとのヘルプ（`/wiki:help graph extract`）は作らない。名前は 1 つだけ受け取る。
- **閉じないこと**: rag プラグインなど、ほかのプラグインのコマンドは扱わない。`/rag:...` を渡すと「見つからない」になる。

## 背景

- `wiki_help.py` は `commands/*.md` の frontmatter（`description`、`argument-hint`、`argument-description`）を読み、ワークフローの順に並べて、コマンドごとに 3 行の箇条書きにする（0.6 系で追加、0.10.0 で `browse` を追加してから変わっていない）。
- `docs/commands.md` には、コマンドごとに `` ## `/wiki:<名前> <仮引数>` `` の節があり、使用例のコードブロックと詳しい説明がある。`learn` と `evolve` の節には使用例のコードブロックがない。節の中には、`./workflows.md#ソースを取り込む`、`../skills/info-hive/references/mcp-server.md` のような相対リンクがある。
- `docs/` はプラグインと一緒に配られる（導入済みの `~/.claude/plugins/cache/info-hive/wiki/0.11.0/docs/commands.md` で確かめた）。
- `commands/help.md` には `$ARGUMENTS` がない。Claude Code は、本文に `$ARGUMENTS` がないコマンドに引数を付けると、本文の後ろに `ARGUMENTS: ...` を足すが、今の本文はそれを使う手順を書いていない。

## 決めること

### 1. 詳細の出どころは `docs/commands.md` の節

frontmatter の 3 つの値に加えて、`docs/commands.md` の該当する節の本文を出す。理由:

- 使用例と詳しい説明は、すでに `docs/commands.md` にある。ヘルプ専用の文章を別に書くと、同じ内容を 2 か所で保守することになる。
- 一覧と同じく、出力はスクリプトが決定的に作る。エージェントが文書を読んで要約すると、言い換えや省略が起きる。

コマンドを足したら `docs/commands.md` に節を足す必要がある。これは今も文書の約束だが、試験で確かめるようにする（すべてのコマンドに節があり、警告なしに出ること）。

### 2. 引数の渡し方

- スクリプトに `--command NAME` を足す。`plugin_root` が省略できる位置引数なので、2 つ目の位置引数にはしない（`wiki_help.py query` が `query` をプラグインのルートと読んでしまう）。
- `commands/help.md` は、利用者の引数をそのままシェルに渡さない。`$ARGUMENTS` は文字列を本文に置き換えるだけで、シェルのための引用やエスケープはしない。引用符で囲んでも、引数の中の引用符で外に出られる（1 版目のレビューが、Git Bash と PowerShell の両方で `query'; echo X; #` から別のコマンドが動くことを確かめた）。そこで、シェルに届く文字を、どちらのシェルでも特別な意味を持たない英数字と `-` に限る。
  1. 引数が空（空白だけを含む）なら、今と同じく `--command` なしで実行する。
  2. 空でなければ、前後の空白を除き、先頭の `/` を 1 つ、続く `wiki:` を除く。
  3. 残りが `^[A-Za-z0-9][A-Za-z0-9-]*$` に合うときだけ、引用符なしの `--command=<残り>` で実行する。`=` でつなぐので、値が `-` で始まらない形でも、argparse がオプションと読む余地がない。
  4. 合わないとき（空白、引用符、`$`、`:` などを含む）は、スクリプトを実行せずに「`<引数>` は wiki のコマンド名として読めない。」と 1 行で伝え、引数なしで実行した一覧を示す。
- 2 で `/` と `wiki:` を除くのは、Git Bash がコマンド行の `/` で始まる値（`--command=/wiki:query`）を Windows のパスに書き換えるためでもある。シェルに届く値に `/` と `:` を残さない。
- エージェントが行うのは、この 4 段の機械的な処理だけで、名前を推し量って直さない（`qury` を `query` に直さない）。正規化と照合はスクリプトが決定的に行う。
- スクリプトの側でも、値が空か空白だけのときは一覧の形にし、`/wiki:query` などの形も正規化する（スクリプトを直接呼ぶ利用者と試験のため）。

### 3. 名前の正規化

`normalize_command_name(raw, plugin)` は次の順に処理する。

1. 前後の空白（Unicode の空白を含む）を除く。中に空白があれば「コマンド名は 1 つだけ指定する」で失敗する。
2. 小文字にする。
3. 先頭の `/` を 1 つ除く。
4. `<プラグイン名>:` で始まれば、それを除く。プラグイン名は `plugin.json` の `name`（読めなければ `wiki`）。
5. 残りが空なら「コマンド名がない」で失敗する。
6. 残りに `:` があれば（`rag:query` など、ほかのプラグインの名前）、「`/wiki:` のコマンドだけを扱う」で失敗する。

正規化した名前は、`collect_commands()` が返した一覧の `name` とだけ照らす。名前からファイルのパスを組み立てない（`../` などを渡されても、一覧にないので見つからないだけになる）。

### 4. 見つからないとき

標準エラーに、次を書いて終了コード 1 で止まる。

```text
コマンドが見つからない: qury
近い名前: query
使えるコマンド: init, ingest, query, lint, stats, graph, browse, learn, evolve, upgrade, help
```

近い名前は `difflib.get_close_matches`（既定の閾値）で、なければその行を出さない。`/wiki:help` の本文は、失敗したときはエラーをそのままコードブロックで示す（今のまま）。

### 5. 節の取り出し

`find_doc_section(text, plugin, name)` は、`docs/commands.md` を同梱の Markdown のパーサー（`wiki_pages.new_parser()`。lint と閲覧と同じ markdown-it-py、commonmark、生の HTML は無効、表は有効）で読み、最上位の h1 と h2 の見出しを並べる。見出しの文字（パーサーが閉じの `#` の並びを除いたもの）が次に合うものを、そのコマンドの見出しとする。

```text
^`/<plugin>:<name>(?:[ \t][^`]*)?`$
```

- 節は、見出しの次の行から、次の最上位の h1 か h2 の見出しの手前までとする。h3 以下の見出しは節に含める。コードフェンスの中の `##`、閉じの `#` の並び（`` ## `/wiki:query` ## ``）、Setext の見出し、リストや引用の中のフェンスは、パーサーのとおりに読む。
- 2 版目は、見出しとフェンスを行の正規表現で探していた。リストの中のフェンス（`- ```md` で開き、`  ``` ` で閉じる）では、閉じの行を最上位のフェンスの開きと読み、節が文書の終わりまで延びた（3 版目の試験で見つかった）。節の範囲を、書き換えと同じ自前の読み方で決めると、その読み違えを照らし合わせ（6）で見つけられないので、パーサーに替えた。
- 見出しの行は出さず、本文の前後の空行を除く。節は `Section(body, start, end)` で返し、`start` と `end` は文書の中の本文の行の範囲である（照らし合わせが使う）。
- 同じ名前の節が 2 つあれば、最初を使い、警告する。
- `docs/commands.md` がない、または節がないときは、詳細なしで出し、警告する（終了コード 0）。

### 6. リンクの書き換え

`docs/commands.md` の相対リンクは、チャットに出すと行き先が分からない。GitHub の、導入した版のタグの文書への URL に書き換える。

**リンクの行き先（作者の選択）**: `plugin.json` の `repository`（`https://github.com/<owner>/<repo>` の形）と `version` から、`https://github.com/<owner>/<repo>/blob/v<version>/<プラグインのルートからのパス>` にする。2 版目の `file:///` の URI は、作者がデスクトップアプリの Code タブで確かめたところ、左クリックではアプリの中のブラウザーが開き「セッションの外のフォルダーにある」として開けなかった（右クリックから VS Code では開けた）。また、同梱の markdown-it は、既定で `file:` のリンクをリンクとして読まない（`validateLink`）。GitHub の URL は、左クリックでアプリの中のブラウザーが開き、見出しのアンカーにも移り、導入した版と同じ内容を見せる。代わりに、ネットにつながっている必要があり、タグのない開発中の版（`--plugin-dir` で試すとき）ではリンク先がない（404）。

- `repository` が GitHub の URL でない、または `version` が版の番号でなければ、リンクを書き換えずに節をそのまま出して警告する。
- 宛先は URL として部分に分ける（`urlsplit`）。パスだけ百分率符号化を戻し、`docs/` と結んで `resolve()` し（`..` を畳む）、プラグインのルートからの相対パスにして、`quote(safe="/")` で百分率符号化しなおす（空白と日本語）。ルートの外を指せば、書き換えずに警告する。
- クエリとフラグメントは、書かれたまま付ける（`%23` や `%3F` を区切りに変えない。GitHub の見出しのアンカーと `?plain=1` が効く）。アンカーが見出しと合っているかは確かめない。パスのない宛先（`#frag` だけ）は `docs/commands.md` を指す。
- 画像は、文書のページ（`blob`）ではなく、ファイルそのもの（`https://raw.githubusercontent.com/<owner>/<repo>/v<version>/...`）を指す。クエリとフラグメントもそのまま付く。
- スキームかホストのある宛先（`https:`、`mailto:`、`//host` など）と、`/` で始まる宛先と、空の宛先は変えない。
- 書き換えた行き先のファイルが手元になければ、警告する（リンクは書き換える）。

**書き換えの方法と、その照らし合わせ**: 標準ライブラリとパーサーは、Markdown を読めても、元の文字列の中のリンクの宛先の位置を返さない。そこで、書き換えは文字列の上で行い、その結果をパーサーで確かめる。

1. 書き換え（`rewrite_links()`）: 最上位のコードフェンスの中の行は変えない。ほかの行は、1 行ずつ、インラインコードの中身を伏せた写しで `[text](target)` と `![alt](target)` を探し、元の文字列の宛先だけを置き換える。リンクの文字のエスケープ（`\]`）と 1 段の入れ子の `[]`、インラインコードの開きのエスケープ（`` \` ``）、宛先のバックスラッシュのエスケープと文字参照（`&#35;`）を読む。宛先は `<`、空白、丸かっこを含まないものだけを書き換える。
2. 照らし合わせ（`verify_rewrite()`）: 書き換えの前は、文書の全体をパーサーで読み、節の本文の行にある最上位のブロックのトークンを取る（節の外にある参照リンクの定義も効く）。後は、書き換えた本文だけを読む（チャットに出す形）。両方のトークンの木を、リンクの宛先を除いた形（種類、タグ、入れ子、`info`、`markup`、中身、属性）と、リンクと画像の宛先の並びに分け、形が同じで、どの宛先も期待する宛先と同じであることを確かめる。宛先は復号せずに、そのままの文字列で比べる。期待する宛先は、前の宛先（パーサーが正規化したもの）を `link_url()` で書き換え、同じパーサーの `normalizeLink()` で正規化したもの（変えない宛先は前の宛先そのもの）である。画像の子（代替テキストを読んだトークン）はたどらず、代替テキストは、パーサーが描く文字（`renderInlineAsText()`）で比べる（代替テキストの中のリンクの記法は宛先にならない。画像の `content` は元の記法のままなので、参照リンクの定義が効かなくなって描く文字が変わっても同じになる）。
3. 食い違えば、書き換えずに節をそのまま出し、警告する（コードの例を壊したものや、誤った宛先を出さない）。ただし、そのまま出した節の中で、節の外の参照リンクの定義に頼るリンクは、定義がないので文字になる。今の `docs/commands.md` のすべての節は、警告なしに書き換わり、参照リンクの定義もない（試験で確かめる）。

1 の書き換えは、Markdown の一部の書き方しか読まない。読めない書き方（参照の形のリンク、山かっこや題名のついた宛先、丸かっこを含む宛先、リストや引用の中のフェンスの中のリンクなど）は、2 で見つかる。2 版目は、範囲の外の書き方を、書き換えと同じ自前の正規表現で探していたので、両方が見落とす書き方（引用の中の字下げしたフェンス、節の外の参照リンクの定義）を見つけられなかった（実装の 1 回目のレビュー）。3 版目は、書き換えと独立した読み方（パーサー）で、書き換えの結果そのものを確かめる。

### 7. 出力の形

Markdown（既定）:

```markdown
### `/wiki:query` `<質問>`

LLM Wiki に問い合わせ、蓄積した知識から出典つきで質問に答える。

**引数**: wiki に問い合わせる質問。日本語の質問は分かち書きせずにそのまま書く。

**詳細**

wiki をもとに、出典つきで質問に答える。

（docs/commands.md の節の本文。リンクは書き換えたもの）
```

- 見出しは、一覧と同じく、コマンド名を `code_span()` のインラインコードにし、`argument-hint` があればその後ろにインラインコードで付ける。
- 引数の行は、一覧の 3 行目と同じ値を使う（`argument-description`、引数がなければ「引数はない。」、書式はあるが説明がなければ「（引数の説明は未記入）」）。
- 節がなければ、「**詳細**」から後ろを出さない。
- 出力は改行で終わる。

JSON（`--json --command NAME`）: 一覧の項目と同じキー（`name`、`command`、`description`、`argument_hint`、`argument_description`）に、`details`（書き換えたあとの節の本文か `null`）を足した 1 つのオブジェクトを出す。`--json` だけのときの配列は変えない。
