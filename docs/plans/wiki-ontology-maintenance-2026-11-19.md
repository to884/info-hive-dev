# ユーザーの指示で既存オントロジーを見直し、整理・移行する機能

2026-11-19。状態: 要件・利用体験の設計案。未実装。
利用者の指示: 「ユーザーの指示により既存のオントロジーを見直し整理する機能がほしい。記事を追加し続けると、過去に構築したオントロジーとは概念が乖離する可能性を憂慮している」。
既存の[提供案](wiki-ontology-feature-experience-2026-11-19.md)を拡張する。対象は記事の分類ではなく、顧客・製品などの実体の種類・役割・関係と、それを使う記録である。

## 提供する価値と入口

利用者が「記事が増えたので、今の内容に合わせてオントロジーを見直して」と指示すると、現在の定義と蓄積した記事・対象・関係を比較する。
語彙を増やすだけでなく、定義を整理し、既存の対象や関係を新しい定義へ移す案まで作る。
診断だけで終了せず、根拠、変更前後、影響、試行結果、未確定事項をそろえ、利用者が採用する案を選べる形にする。

入口は提案中の `ontology propose` / `apply` / `status` を共用し、別の操作名を増やさない。
Claude Code は `/wiki:ontology propose`、Codex は `$wiki:info-hive ontology propose` に自然言語の目的を添える想定である。
「見直し・整理」の依頼は既存定義と記録の再編も提案対象にする。`propose` は本番を変更せず、確認した案を `apply` で反映する。
プロジェクト・ユーザーのどちらも1回に1つのwikiを対象とし、解決した場所を提案から適用まで保持する。
記事追加のたびに定義を自動変更する機能や、定期実行を必須にはしない。

## 何を不適合の候補として調べるか

記事の数や語彙の使用率だけで不適合と判定せず、具体的な記述と利用者の問いに照らして調べる。

| 見直す点 | 架空の例 | 提案できる整理 |
| --- | --- | --- |
| 同じ意味の語が並立する | 「顧客企業」と「取引先」が同じ意味で使われている | 適用範囲と条件を比べ、同義なら統合し、別名を残す |
| 1つの語に異なる意味が混ざる | 「製品」がソフトウェアと保守契約の両方を指す | 下位の種類や別の関係へ分け、既存記録を振り分ける |
| 種類と役割が混ざる | A社が顧客でも販売代理店でもある | 会社という同じ対象に役割を併記し、会社を二重化しない |
| 関係の意味が広すぎる | 「利用する」が試用・契約・実利用を区別しない | 根拠が支える関係へ分け、特定できないものは留保する |
| 説明に必要な概念がない | サービス化した製品を旧来の型でしか扱えない | 新しい種類や関係を加え、既存記録も見直す |
| 表示名や語の意味が曖昧 | 同じ呼称が異なる部署で違う意味を持つ | 定義・区別・表示名を明確にする |

同じ記述でも、語彙の不適合、関係の未記録、抽出の誤り、対象の取り違え、現実の時期・版による変化は別の原因である。
たとえば顧客が解約した場合は利用関係の有効期間の変化かもしれず、「顧客」という定義を変える根拠とは限らない。
新しい記事と古い記事を比較し、古い事実を現在の表現で一律に上書きしない。
不適合の候補には引用と判断理由を添え、LLMの推測だけを「乖離を検出した結果」として表示しない。

## 分析する範囲

現在の定義・既存の対象・関係・根拠に加え、新旧の記事を読む。旧定義で整理されたグラフだけを読み直して、未記録の新概念がないと結論しない。
前回の採用記録があれば、その定義の版と分析済み記事の指紋を基準に、追加・変更された記事を重点的に調べる。
前回の記録がない手編集のオントロジーでも、現在の定義を出発点として見直せる。履歴がない部分は不明と示す。
全体の見直しを頼まれた場合は全体を対象として進める。時間・量の上限で終わらなければ、分析済み・未読・失敗・再開位置を示す。
部分分析の案はその範囲の案として提示できるが、「wiki全体が今の定義と整合している」とは報告しない。
型の廃止など既存記録に影響する適用では、分析した少数例とは別に、変更対象とその参照の全範囲を検査する。
読めない依存先や分類を決められない既存記録が残る場合は、後述の旧定義を残す段階移行か、適用を保留する案にする。

## 整理する操作と、データの移行

| 整理 | 定義の変更 | 記録の扱い |
| --- | --- | --- |
| 表示名・説明の改善 | 意味を変えず読みやすくする | 対象の同一性と参照を保つ |
| 型・関係の識別子の改名 | 旧名と新名の対応を記録する | 使っている記録・既知の参照を移行する |
| 型・関係の統合 | 条件が同じ定義をまとめる | 出典・条件・旧定義との対応を残す |
| 型・関係の分割 | 意味や制約を分ける | 個々の根拠から振り分け、曖昧なものを推測で移さない |
| 実体の再分類・役割の整理 | 型や役割を見直す | 同じ顧客・製品としての同一性を保つ |
| 定義の廃止 | 新規利用を止め、必要に応じ旧定義を残す | 利用中の記録や履歴を消して帳尻を合わせない |
| 記録不足・抽出誤りの修正 | 定義が適切なら変更しない | 関係を追加・訂正・取り下げ、出典と変更理由を残す |

型の統合と実体の統合は別である。「顧客企業」と「取引先」を統合しても、A社とB社を1社にまとめない。
同一実体と確認できた重複記録の統合や、誤って一つにした対象の分離は、別の変更項目として根拠・参照・未確定事項を示し、利用者が選んだ場合だけ移行案に含める。
同じ名前という理由だけで実体をまとめない。既存のentityページも照合に含める。
同じ実体の型を変えただけで新しい実体を作らない。IDが型やページ名に依存する既存方式では、IDの維持か旧IDとの明示的な対応を設計し、変更の影響を隠さない。
外部に保存された参照まで自動で把握できるとは保証しない。移行で調べた範囲と、旧ID・旧語をどこまで解決できるかを示す。

分割先を決められない記録があれば、旧定義を廃止予定として残す段階移行を提案できる。
この場合は「部分移行」と報告し、残件数・根拠・次の判断を保持する。旧定義を削除して移行完了にはしない。
意味が異なる古い事実を、単なる名前の別名で新しい関係と同一視しない。
抽出誤りの訂正では、原本を変えず、旧記録と訂正理由・根拠を保持して現在有効な主張を区別する。出典同士が矛盾する場合は、単なる抽出誤りとみなして片方を取り下げない。

## 部分移行のまま利用するとき

部分移行は適用中の一時状態だけでなく、適用後も続く状態として扱う。各記録の採用した定義の版と移行元・移行先・未確定の理由を保持する。
問い合わせは、新分類で確定した記録と、旧定義に残る記録を区別する。同じ実体を二重に数えず、旧定義の事実も出典へたどれる状態で保持する。
影響する問いには未移行の範囲と件数を併記し、旧分類を新分類の確定結果へ無条件に含めたり、黙って結果から落としたりしない。
例: 「契約として確認できたものは12件。移行元の『製品』に未分類が20件あり、契約の総数は未確定」。元の主張の保持と、新分類で件数を確定できることは区別する。
statusはLLMを呼ばず、残している旧定義、残件数、保留理由、次の判断を示す。lintは旧定義を使う残件を移行状態として報告し、未読や無効な参照とは区別する。
通常ingestでも分割先を確定できない場合は、旧型に新たな確定記録を増やさず、根拠付きの未分類候補を残件として保存する。原文の主張は出典側に保持する。
この未分類候補と既存の旧記録、実体の同一性の保留、語彙の見直し案は区別する。新分類の正本を二重に作らない。

## 型と呼び名の解決も一緒に更新する

現行では、明示した `graph.node_type` が優先され、なければ `type`/`kind` と `maps_from` から型が決まる。`kind: 会社` は共通の日本語別名で `company` に正規化される。既定のノードIDも導出した型に依存する。
したがって移行の検査には、対象の型だけでなく、ページの `kind`、明示した型、`maps_from`、ID、wikiの `SCHEMA.md` の該当規約と旧語・別名の対応を含める。
記事の `type: source` を実体の型へ変えるのではなく、実体の正本と、それを記録する規約を整合させる。
共通の `kind` 別名は入力文字列の互換のために残し、あるwikiの整理を理由にプラグイン全体の `会社 → company` を書き換えない。
旧語・別名を採用済みの型や役割へ解決する意味の対応はwikiごとの定義の版に持ち、共通の文字列正規化の後に適用する。意味の解決はそのwikiの採用済み定義を使い、ingest/lint/extract/queryで共用する。
明示した正本の型を優先し、他の対応との矛盾は検査する。旧語が複数の移行先を持つ場合や、手編集との衝突がある場合は、一つへ自動変換せず保留する。
新たに書くときは確認済みの英語の機械用識別子を使い、表示の別名と区別する。`maps_from` を変える案は、それで影響する全ページも移行計画に含める。
このwikiごとの意味の解決と保留は新設する機能であり、現行の共通別名表だけで実装済みとは扱わない。

## 利用者に見せる提案と試行

1. 現在の定義で困る具体例と、整理しなくても解ける例を、出典付きで示す。
2. 「維持」「説明の改善」「追加」「統合」「分割」「再分類」「廃止」の変更前後を並べる。
3. 変更される実体・関係・根拠・参照の件数と、未読・未確定・移行しない範囲を示す。
4. 新旧双方の記事を含む例で隔離して試し、既存の問いと新しい問いの回答・出典がどう変わるかを示す。
5. 選択した案全体について、変更対象と参照の全範囲を検査する。部分選択は依存のそろった案へ組み直してから再試行する。

試行には「1記事に複数の実体」「複数記事に同じ実体」「同名の別対象」「時期が違う関係」「分割先が未確定」の例を含める。
部分移行後の件数・一覧の問い合わせと、未分類が増える取り込みも試す。旧い呼び名や日本語の別名を含む記事を取り込み、採用済み定義で解決できるか、曖昧なら保留できるかを確認する。
一つの総合点で適合を保証せず、構造・型・参照の検査と、引用が意味を支えるかの確認を分ける。
質問の答えが変わった場合は、意図した概念整理による違いと、根拠の欠落や移行漏れを区別する。

## 適用・履歴・継続利用

採用した定義の版、元の定義の指紋、分析範囲、旧定義からの対応、対象・関係・根拠の変更、保留、承認した案をひとまとまりで保持する。
現在の定義と既存記録を移す計画は一体で適用する。語彙だけを変えて既存記録を無効にしない。
案の依存する定義・記録・記事・原本や、参照の範囲が変わっていれば再検査し、表示済みの差分が変わる場合は新しい案を確認する。
表示済みで依存のそろった変更を利用者が選んだだけなら、同じ採用の意思を繰り返し確認しない。依存の組み直しで未表示の変更が必要なら、その最終差分と試行結果を示して採用を求める。
適用中にLLMが未確認の移行先を決めたり、別の変更を追加したりしない。

適用と通常ingestは共通の書く段を使い、ingestが使った定義の版が変わっていれば、書き込む前にその差分を検査し直す。
定義・正本・参照の更新と、グラフ再生成・問い合わせ・lintへの接続が完了するまでは、新旧が混ざった結果を新定義の完了結果として公開しない。
旧エッジIDを参照する `contradicts`・`supersedes` なども移行の検査対象にする。現在のエッジIDは主語・述語・目的語・根拠などに加え、記録するページのパスや、同じ内容の項目の順番にも依存する。ページ移動、関係の別の正本への移し替え、項目の順序変更も含めて、移行前後の項目とID・参照の対応を検査し、再生成だけで参照が直ったとみなさない。
失敗時は適用記録から再開・復旧し、後から行われた編集を無条件に上書きしない。物理的な保存・公開・復旧方式は、ADR-0023と整合する実装設計で決める。
過去の定義と判断・出典は監査に残す。初期の要件として、過去版をそのまま実行する時点指定検索まで提供するとは約束しない。

通常のingestは、採用済みの語彙で実体と関係を記録し、同一性が未確定の帰属を保留する。
新語彙の自動追加や自動的な再編は行わず、ユーザーが再び見直しを指示したときに、現在の定義と蓄積内容を比較する。
前回見送った案はその理由と基準の版を残し、新しい根拠や用途の変化があれば再提案できる。利用者が明示して再検討を求めた場合も、その理由と版を示して再検討する。

## 架空の利用例

> 利用者: 記事が増えたので、顧客と製品の定義を今の内容に合わせて整理して。
>
> wiki: 旧記事では「顧客」を会社の種類にしていますが、新しい記事では同じ会社が顧客と販売代理店の両方として登場します。会社を共通の対象とし、顧客・販売代理店を役割として記録する案です。製品の定義には保守契約も混ざるため、製品と契約に分ける案も作りました。
>
> wiki: A社は同じ顧客番号の会社として維持し、2つの役割を記録します。製品Aは製品のままです。保守Aは契約へ移す根拠がありますが、名称しかない「Aプラン」は判断できません。旧定義を残す部分移行案と、今回確定できる対象・関係の変更を示します。
>
> 利用者: 会社と役割の整理だけ採用して。製品と契約の分割は今回は見送る。
>
> wiki: 部分選択に合わせて依存を組み直しました。最終案は会社の型と役割、それを使う「利用する」の主語の制約の更新です。A社の識別と製品Aの利用関係の根拠を保てることを試行で確認しました。この差分には製品と契約の分割を含みません。この最終案を適用しますか。
>
> 利用者: この案を適用して。
>
> wiki: 定義・対象・関係・参照を移行してグラフを再生成しました。製品と契約の分割は未適用です。以後の取り込みでも、会社の同一性を保って役割を記録します。

## 提供範囲と実装前の条件

「現在のwikiに合わせた見直しと整理」を提供するには、既存語彙と記録の移行まで必要である。第5版までの「初期版は追加だけ、既存の型の変更は対象外」という提供案を変更する。
作る順は診断、提案・試行、追加の適用、既存の定義と記録の移行とする。途中の段階は先行提供と明示し、追加だけをこの要望の完成形とは扱わない。
保存方式、定義の版と実体・関係のID、保留・旧定義の表現、部分移行を扱う問い合わせと集計、wikiごとの意味の解決、エッジ参照の移行、公開の境界、共通の書く段による復旧を実装設計で決める必要がある。
現行のlint/extract/queryやontology.yamlがこの機能を実装済みという意味ではない。実データのオントロジー変更や本番移行は今回行っていない。
