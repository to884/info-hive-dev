## 規則が及ぶ範囲（提案。外の原本の扱いは作者の決定の 4、記事に絞ることは作者の決定の 6）

ADR-0029では、wiki の根の下と、取り込みが raw を置く raw の根（`<RAW_ROOT>`）の下を「守る木」と呼ぶ。raw の根は、古い構成では wiki の根の下の `raw/`、ADR-0008 の構成では wiki の根の隣の `raw/` である。リンクの規則が当たるのは、守る木の中の記事と、記事までの道だけである。書き込みの守り（「規則に反した配置での書き込み」）は、記事に限らず守る木に書くすべてに当たる。

| 項目 | 決定 |
| --- | --- |
| 記事 | 名前の規則で決め、リンクかどうかは定義に入れない。次の 3 つ。(1) ページ: `wiki_pages.is_page_path()` が真の相対パスで、どの要素も名前が `.` で始まらないもの。(2) 索引とその他: 最上位の `index.md`、`indexes/` の下の `.md`（どの要素も名前が `.` で始まらないもの）、最上位の `log.md`、`SCHEMA.md`。(3) raw: source ページの `raw:` が `resolve_raw()` で 1 つに解けた先と、`resolve_raw()` がリンクとして拒んだ候補（外の原本を除く。ディレクトリなら、その下の、名前が `.` で始まらないファイル）。リンクとして拒んだ候補は、記事のまま「拒んだ記事」として `links` に出す（ADR-0029 の 12 回目のレビューの設計書の重大 2）。名前の規則は `wiki_pages.py` の 1 か所に置き、走査、lint、読む口が同じものを使う。走査は、この規則で記事の候補を集め、リンクでないものだけを読み、リンクのものを「拒んだ記事」として `Walk.links` に入れる。10 版目は記事を「変えたあとの走査が返すもの」と決めていたので、リンクは記事に入りえず、wiki の側の `links` がいつも空になる定義だった（親のセッションの指摘の 1） |
| 記事までの道 | 根から記事の候補までの途中のディレクトリも対象にする。記事のファイルそのものがふつうのファイルでも、途中のリンクを通って届けば、記事は木の外の実体である。変えたあとの走査は、途中のジャンクション（と、名前の代理のほかのリパースポイント）にもディレクトリのシンボリックリンクにも降りない。名前の規則で記事の候補を含みうる場所（最上位の除く名前と、名前が `.` で始まる項目の下でない場所）にあるディレクトリのリンクは、`Walk.links` に入れる。`indexes/` そのものも、記事までの道として調べる。raw の側は、raw の根が分かるとき、raw の根から raw の記事までの途中のディレクトリを調べる |
| 対象にしないもの | 記事でないもの。名前の規則で記事にならないもの（最上位の `graph/`、`assets/`、`raw/`、`README.md`、名前が `.` で始まるすべての項目とその下。`.git/`、`.wiki-cache/`、`.evolution/` はこれに当たる）と、`.md` でないファイル（ページの置き場所にあっても）と、どの `raw:` からも指されていない raw の根のファイルである。これらのリンクはlint に出ない。走査は `.md` でないファイルにも `is_symlink()` を呼ぶが、記事でないので報告しない |
| ハードリンク | ハードリンクは、名前のどれかが記事なら、その記事の `st_nlink` が 2 以上になるので見つかる。もう一方の名前が記事でないもの（`.wiki-cache/` の一時ファイルなど）でも、他方の wiki の中のものでも、記事の側で見つかる。問い合わせの設計の 3 回目のレビューの反例（`.wiki-cache/` の `.tmp` と他方の wiki のページのハードリンク）は、他方の wiki のページの側で見つかる |
| 根とその祖先 | wiki の根と raw の根は、それ自体がリンクでもよく、祖先にリンクがあってもよい。wiki をどこに置くかは利用者が決めることで、`wiki_mcp_common.normalize_wiki_root()` が解決する。**リンクの判定は、操作ごとに 1 つの起点を決め、起点より下の要素に当てる。** 起点そのものと、その祖先には当てない。起点より下は、別の分かっている根やその祖先であっても調べる。起点は次のとおりである。ページと索引（走査、読む口、lint の wiki の側）は、wiki の根。raw の候補（`resolve_raw()`、lint の raw の側）は、候補を含む現在の raw の根を明示されたとき、その根から調べる。ほかの候補は、候補を含む wiki の根と記録された過去の raw の根のうち、もっとも外側の根から調べる。過去の根の記録が増えても、すでに調べていた道は検査から外さない。どの根の下でもなければ、起点はなく、候補そのものにだけ当てる。段階3の最初の実装は [セッション取り込みの計画](adr-0029-stage3-session-raw.md) にある。書き込みの部品は、呼ぶ側が渡した根（ADR-0029 の用語の「根」）。走査、読む口、`find_links()`、`resolve_raw()`、書き込みの部品は、どれもこの決まりを使う（ADR-0029 の 14、15 回目のレビューの設計書の重大 1。9 版目は `resolve_raw()` の候補そのものに無条件で当てたので、`raw:` が raw の根そのものを指すと根のリンクを拒んだ。10 版目は、分かっている根とその祖先をすべての操作で外したので、wiki の中に raw の根 `W/topics/raw` を置くと、wiki の根からのページの走査でも、その祖先の `W/topics` のジャンクションを調べなかった）。wiki の中に raw の根を置いた配置では、同じファイルが、wiki の根を起点にするとページとして拒まれ、raw の根を起点にすると raw として読めることがある。ページとして拒んだことは `Walk.links` に出るので、黙っては消えない |
| 相対パスの `raw:` | 取り込みが置いたものとみなす。指す項目そのもの（ディレクトリなら、その下のすべて）を調べる。raw の根が分かっていて、指す項目がその中にあれば、raw の根から指す項目までの途中のディレクトリも調べる。分からなければ、途中のディレクトリは調べない。raw の根を、パスの形から推し量らない。セッションの `raw_ref` は wiki の親からの相対パス（`archive/raw/session.md` など。`wiki_session.raw_ref_of()`）で、raw の根が何段目にあるかはパスから決まらないからである（ADR-0029 の 2 回目のレビュー） |
| 外の原本の見分け方 | 外の原本（作者の決定の 4）は、場所ではなく、ページの印で見分ける。取り込みが写さずに参照する原本は、rag が登録した PDF だけである（ほかのソースは `<RAW_ROOT>` に写す。`commands/ingest.md` の手順 2）。rag の PDF の source ページには `rag_job_id:` と `raw_sha256:` がある（ADR-0013、`references/ingest-workflow.md`）。そこで、`rag_job_id:` のある source ページの絶対パスの `raw:` を外の原本とし、規則の対象外にして、lint の `links` も調べない。指す先がリンクでも、ハードリンクでもよい。拒まず、写さない。外の原本が守る木の中にあれば（`raw/` に置いた PDF を rag で登録したなど）、ほかの raw の記事と同じに調べる。守る木の中かは、「守る木の中か」の比べ方（パスの文字のうえで比べ、根より下を解決しない）で決める。登録したあとで木の中の PDF をシンボリックリンクに置き換えても、`raw:` の文字は木の中なので、リンクとして見つかる（ADR-0029 の 6 回目のレビューの設計書の重大 2） |
| 絶対パスの `raw:`（外の原本でないもの） | 取り込みが置いた raw とみなす。過去に別の raw の根へ置いたもの（セッションの raw は、raw の根が wiki の親の外にあれば絶対パスになる。`wiki_session.raw_ref_of()`）も、今の raw の根の外にあるかによらず、指す項目そのもの（ディレクトリなら、その下のすべて）を調べる。今の raw の根の中にあれば、途中のディレクトリも調べる。2 版目から 4 版目の「既知の木の外を指せば対象外」は、過去の raw の根の raw を外の原本と取り違えた（ADR-0029 の 3 回目のレビュー） |

**外の原本を対象外にする理由。** 原本は wiki の根の下にないので、2 つの wiki を引く問い合わせの補助が比べる範囲の外にある。rag も取り込みも、原本を読むだけで書き換えない。外の原本は、wiki が書かない。読むときも、ページの `raw:` に書かれた絶対パスを読む。別の wiki のページも、同じ絶対パスを `raw:` に書ける。リンクが別名を作っても、絶対パスで直接指すことに比べて、新しく混ざるものはない。ADR-0013 は、ハードリンクの PDF を別名として扱う台帳を決めており、利用者の PDF の置き方に口を出さない。拒めば、ハードリンクを含む利用者の蔵書が登録できなくなる。写せば、原本を複製しないという ADR-0008 と ADR-0013 の決定に反する。

## コマンドごとの当て方（作者の決定の 5 の具体化。提案）

どのコマンドも、記事と記事までの道に、シンボリックリンク、ジャンクション、ハードリンクを作らない。記事を置くときは、新しい名前のふつうのファイルを作るか、名前で置き換える。スクリプトが記事を読むときは、リンクを拒む走査か、記事を読む口（「ページの走査」）を通し、コマンドごとに調べ直さない。記事でないファイル（キャッシュ、グラフの成果物など）も、プラグインのスクリプトは書き込みの部品を通して書く（「規則に反した配置での書き込み」）が、それはリンクの規則ではなく、書き込みの守りである。

表は、コマンドの手順の全体（スクリプトとエージェントの書き込み）で、守る木に置くものを並べる。

| コマンド | 守る木に置くもの | 当て方 |
| --- | --- | --- |
| `/wiki:init` | `SCHEMA.md`、索引、ログ、ディレクトリ、`.wiki-cache/.gitignore`。`setup_wiki.py` を通して、検索のキャッシュとベクトルの索引（`.wiki-cache/` の下） | ふつうのファイルとして作る |
| `/wiki:ingest` | raw、ページ、索引、ログ、画像、グラフの成果物 | ソースのリンクは先の中身を写す（「取り込み」の表） |
| `/wiki:query` | 保存したときのシンセシスのページ、索引、ログ、グラフの作り直し、CLI のキャッシュ | ふつうのファイルとして書く。2 つの wiki を引く問い合わせは書かない。記事のリンクは警告を付けて続け、止めるのは読み手（`pair_read`、`wiki_pair.py`）が共有を見つけたときだけである（問い合わせの設計の 15 版目） |
| `/wiki:lint` | 承認された直し（ページ、索引）と、ログの行 | ふつうのファイルとして書く。指摘 `links` で、規則に反した配置を挙げる。プラグインは直さず、警告として利用者に伝える（作者の決定の 8） |
| `/wiki:learn` | 経験の raw の JSON（`wiki_evolve.py capture`）、ページ、索引、ログ | ふつうのファイルとして書く |
| `/wiki:evolve` | `.evolution/` の下、ページ、索引、ログ。対象のスキルが守る木の中にあれば、そのスキルのファイル | 写すときは `shutil.copy2()`（ハードリンクを作らない）。対象のスキルを守る木の外に置くことは、コードでは確かめていない（`wiki_evolve.py` は `.evolution` の中などを拒むだけである）。中にあれば、ほかの書き込みと同じく規則に従う |
| `/wiki:graph` | `graph/` の下の成果物 | ふつうのファイルとして書く |
| `/wiki:browse` | 書かない（ADR-0017） | 同じ走査で読むので、リンクを通って届くページは描かない |
| `/wiki:stats`、`/wiki:help` | コマンドの手順は書かない | 当てることはない（MCP の索引は下の注） |
| `/wiki:upgrade` | 足りないひな形とファイル。`setup_wiki.py` を通して、検索のキャッシュとベクトルの索引 | ふつうのファイルとして書く |

- **MCP の索引。** MCP のサーバーは、wiki の索引（`WikiIndex`）を使うツール（`query`、`get_page`、`stats`。`State.wiki()` を呼ぶもの）で、データの場所（`INFO_HIVE_DATA_DIR`）の `index/<wiki_key>/` に索引を書く（`wiki_index.py` の 831 行と 853 行付近）。`list_index`、`lint`、`graph` は `WikiIndex` を作らない（ADR-0029 の 5 回目のレビュー）。起動のときも、wiki を受け取る前に、データの場所に `server.lock` と `server.json` を書く（`wiki_mcp_relay.py` の 103〜121 行、`wiki_mcp_common.py` の 734〜743 行）。データの場所が守る木の中なら、表で「書かない」としたコマンドでも守る木に書く。これらの書き手は、道を書き込みの部品で確かめる。台帳の SQLite（`wiki_index.py` の 405 行）と語彙の索引の Tantivy（471 行）は、ライブラリが自分でファイルを開いて書くので、部品が確かめられるのは道までである（「規則に反した配置での書き込み」の「部品を通らない書き手」。親のセッションの指摘の 4）。 書けなかったときは、そのツールの呼び出しを失敗させる（「規則に反した配置での書き込み」の「書けなかったときの振る舞い」）。
- v0.19.5 の同梱の Python のコードで、記事にリンクを作るのは、下の例外の重ねて書かない置き方だけだった（`os.link`、`symlink`、`copytree`、`shutil.copy` を `grep` で探した範囲）。
- 書き込みが規則に反した配置の別名を通らないことは、コマンドごとには確かめない。「規則に反した配置での書き込み」の書き込みの部品に任せる。
- **例外（重ねて書かない置き方の一時的なハードリンク）。** POSIX で、行き先が既にあれば置かない形でファイルを置くとき、一時ファイルから行き先へ `os.link()` で名前を作り、すぐに一時ファイルの名前を消す。そのあいだだけ、リンクの数が 2 になる。これを、置き終えるまでの一時的なものとして規則の例外とする。例外は関数の名前ではなく、この置き方で決める。記事に当たるのは、今の `wiki_session.publish_exclusive()` が置くセッションの raw（`wiki_session.py` の 1218〜1228 行）と、ADR-0023 の書く段が `new` で置くページ（[書く段の設計](wiki-apply-2026-11-14.md) の 586 行）である。書く段のロックのファイル（同じ設計の 332 行）も同じ置き方を使うが、記事でないので規則の外である。置き方は、「規則に反した配置での書き込み」の書き込みの部品の 1 か所に置く。Python の標準ライブラリには、重ねずに名前を変える呼び出し（Linux の `renameat2()` の `RENAME_NOREPLACE`）がなく、置き方を変えると重くなるためである。途中で止まって残ったものは lint の `links` に出る（「今ある wiki と raw の直し方」）。
- **子プロセスと道具のデータ。** プラグインが起こす子プロセスは、利用者の環境変数を引き継ぐ。`/wiki:init` は `uv run --script setup_wiki.py` を起こす（`init_wiki.py` の 168 行付近）。`UV_CACHE_DIR` が守る木の中を指し、uv がハードリンクでパッケージを置く設定（`UV_LINK_MODE=hardlink`）なら、守る木の中にハードリンクが残る（ADR-0029 の 2 回目のレビューの報告による。uv の文書の記述で、手元では試していない）。uv のキャッシュは記事でないので、リンクの規則には反しない（作者の決定の 6）。lint にも出ない。

## リンクとみなすもの（提案）

判定は、項目ごとの `os.lstat()` の結果だけで決める。種類の名前を数え上げず、OS が返す値の条件で書く。

| 種類 | 条件 |
| --- | --- |
| `symlink` | POSIX では `stat.S_ISLNK(st_mode)`。Windows では `st_reparse_tag` が `IO_REPARSE_TAG_SYMLINK`（`0xA000000C`） |
| `junction` | Windows で、`st_reparse_tag` が `IO_REPARSE_TAG_MOUNT_POINT`（`0xA0000003`） |
| `reparse` | Windows で、`st_file_attributes` に `FILE_ATTRIBUTE_REPARSE_POINT` があり、タグの名前の代理のビット（`0x20000000`）が立つ、上の 2 つ以外のもの |
| `hardlink` | `stat.S_ISREG(st_mode)` で、`st_nlink` が 2 以上。ディレクトリのリンクの数は見ない（POSIX のディレクトリは、ふつう 2 以上である） |

- **名前の代理のビットを根拠にする。** Microsoft の文書は、このビットが立つタグを、そのファイルかディレクトリが「システムの中の別の名前の実体を表す」ものと定義し、例として、ディレクトリを別のボリュームと結び付けるマウントしたフォルダーを挙げる（[Reparse Point Tags](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-tags)、[IsReparseTagNameSurrogate](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-isreparsetagnamesurrogate)）。「別名かどうか」を、OS が定義する 1 つのビットで決めるので、知らないタグにも同じ規則が当たる。ビットの位置（29）は、文書の図から読んだ。
- **手元で確かめたこと。** シンボリックリンクのタグは `0xA000000C`、ジャンクションのタグは `0xA0000003` で、どちらも名前の代理のビットが立つ。`DirEntry.is_junction()` はジャンクションで真、シンボリックリンクで偽になる。Windows の `DirEntry.stat()` の `st_nlink` は 0 で、ハードリンクの 2 は `os.lstat()` でしか取れない（Python の文書にも、Windows の `DirEntry.stat()` の `st_ino`、`st_dev`、`st_nlink` はいつも 0 とある）。
- **未確認のこと。** ボリュームのマウントしたフォルダーのタグがジャンクションと同じ `IO_REPARSE_TAG_MOUNT_POINT` であることは、Microsoft の文書で確かめられなかった。手元でも作っていない（作るには管理者の権限が要る）。名前の代理のビットが立つことは、上の文書の例で裏付けられるので、`junction` でなくても `reparse` として見つかる。クラウドのファイルの置き換え（OneDrive など）のタグに名前の代理のビットが立たないこと、WSL が作るシンボリックリンクに立つことも、未確認である。実装の試験で、作れる環境で確かめる。
- **リンクには降りない。** 一覧できないディレクトリと、`os.lstat()` が失敗した項目は、調べられなかったものとして返す。
- **費用。** Windows では、ハードリンクを見つけるために、記事のファイルごとに `os.lstat()` を 1 回ずつ呼ぶ。一覧の情報だけでは足りない。記事に絞ったので、`.git/` や `.wiki-cache/` のファイルには呼ばない。

## 取り込み（作者の決定の 3 の具体化。提案）

| 場合 | 決定 |
| --- | --- |
| 新しい raw に写すソースがリンク | 場所を問わず（守る木の外でも、守る木の中の記事でない場所でも）、リンクを写さず、先のふつうのファイルの中身を、`<RAW_ROOT>` に新しいふつうのファイルとして写す。元のリンクは変えない（ADR-0029 の I3。7 回目のレビューのADR の重大 1） |
| 新しい raw に写すディレクトリのソース | 中のリンクも先の中身を写す。ディレクトリへのリンクなら、先のディレクトリの中身を写す。たどる道筋の上のディレクトリと同じ識別子のディレクトリには降りない（回る道筋） |
| ハードリンクのソース | 中身を新しいファイルとして写す。`os.link()` や、ハードリンクを作るコピーの方法で置かない |
| たどれないリンク | 先がない、回る、権限がなくてたどれないリンクは取り込まず、そのことを報告する |
| 写したあと | `wiki_links.py check <置いた raw>` で、置いた raw にリンクがないことを確かめる |
| 記事になるソースがリンク | 次の 2 つは、置き換えず、取り込まない。(1) 記事（名前の規則で記事に当たるもの）か、記事までの道にリンクがあるソース。読むと ADR-0029 の I2 に反する。(2) raw の根に既にあり、取り込みがその場で `raw:` で指して記事にするソース。どのソースが、どの種類のリンクかを、警告として利用者に伝える（作者の決定の 8）。ソースが守る木の中かは、ADR-0029 の用語の「守る木の中か」で決める。パスの文字のうえで比べ、根より下の要素は解決しない。与えられたパスを、区切りだけそろえた絶対パス（解決しない）にする。途中に `..` を含むパスは、文字のうえで畳むと、`..` より前のリンクをたどったあとの実際の場所と食い違うので、所属を決めない。取り込みと PDF の登録は止め、`..` を含まないパスを利用者に頼む。`raw:` の値の先頭の `..`（`../raw/x.md` など）は、利用者が書いたままの根と、解決した根の両方を基準にして、それぞれ文字で畳む（根がリンクのとき、`根/..` が綴りの親を指すか、リンクの先の親を指すかは OS で違うので、両方を候補にする）。途中の `..` を含む `raw:` は `unknown` にする。そのうえで、根を利用者が書いたままのパスか、根を解決したパスのどちらかの下にあれば、守る木の中とする（根そのものはリンクでもよいので、両方で比べる）。木の中なら、根から最後の名前までの途中の要素と最後の名前に、リンクの判定を当てる。名前や途中のディレクトリを解決してから比べると、途中のジャンクションを通った記事も、木の中のリンクの名前も、木の外に見えてしまう（ADR-0029 の 6 回目のレビュー。親のディレクトリだけを解決する 11 版目の形も、途中のリンクで破れた）。ソースを利用者が別名（`subst` のドライブなど）で書くと、文字のうえで木の外に見え、中身を写す。リンクは作らないので規則には反しないが、同じ中身の raw が増える（「保証しないこと（詳細）」） |
| rag が有効なときの PDF | 原本が守る木の外にあれば、規則の対象外である（作者の決定の 4）。`register_pdf` には、今と同じく利用者が指定したパスを渡し、解決しない。リンクをたどるかどうかは、rag の `pdf_path()` の今の規則に任せる。原本が守る木の中にあるか（`raw/` に置いた PDF など）は、上の行と同じく、パスの文字のうえで根と比べて決める。中にあり、リンクなら、登録せず、警告として伝える。`raw:` は解決したパスなので、木の中のシンボリックリンクの PDF を規則の前に登録していると、`raw:` は木の外の先を指し、リンクの名前はどの `raw:` からも指されない。そのリンクは lint では見つからない（「保証しないこと（詳細）」。親のセッションの指摘の 5）。`raw:` が守る木の中かを決めるときも、同じ比べ方を使う |
| rag が無効なときの PDF | ふつうのソースと同じく `<RAW_ROOT>` に写す |

## rag の `result.raw` と `raw:`（提案）

source ページの `raw:` には、今のまま `result.raw`（rag が解決した絶対パスを `/` 区切りにしたもの）を書く。ADR-0013 の「返す値」と「wiki のソースのページ」の決定は変えない。

- rag の台帳の場所のキー（`locations`）と、検索の結果の `raw` は、解決したパスである（ADR-0013）。`raw:` も同じ形にすれば、source ページと rag の結果が同じ文字列で同じ原本を指す。
- 外の原本は規則の対象外なので、指定したパスを残しても、リンクの規則のためにはならない。
- 解決したパスはリンクの先なので、rag の source ページの `raw:` は、登録したときにはシンボリックリンクを指さない。登録したあとでそのパスがリンクに置き換えられることはありうるので、lint はそれを調べる（「規則が及ぶ範囲」の外の原本の見分け方）。
- ネットワークドライブの PDF では、`raw:` が UNC（`//server/share/book.pdf`）になる。UNC はドライブ文字の割り当てに依らないので、記録としてはむしろ安定している。rag が UNC の入力を拒むのは、モデルが渡したパスで知らないサーバーに接続させないためで（ADR-0013）、記録の形を決めるものではない。`raw:` を `register_pdf` に渡し直す手順はない。
- lint の `missing_raw` は、UNC の `raw:` があるかを調べるときに、そのサーバーに接続する。サーバーは、利用者がドライブ文字を割り当てたものである。この振る舞いは ADR-0013 からある。

問い合わせの設計の 9 版目の第 3.8 節にあった「`raw:` に wiki の外の原本を絶対パスで書くときは、利用者が指定したパスをそのまま使う」と「指定したパスそのものがシンボリックリンクなら、登録も取り込みもしない」は、採らない。マージされた 12 版目（PR #140）には、この 2 文はもうない（親のセッションの指摘の 7）。

## lint の指摘 `links`（提案）

| 項目 | 決定 |
| --- | --- |
| 調べるもの | 記事と記事までの道（上の「規則が及ぶ範囲」の表）。wiki の側は、走査の `Walk.links`（拒んだ記事と、記事の候補を含みうる場所のディレクトリのリンク）を使う。raw の側は、`resolve_raw()` で解けた先に、記事の名前の規則で絞ったリンクの検査（`find_links(path, articles_only=True)`。名前が `.` で始まる項目とその下を見ない）を当てる。記事でないファイルは調べない。lint は wiki の根の全体に `find_links()` を当てない |
| raw の根の渡し方 | CLI の `wiki_lint.py` に `--raw-root`、MCP の `lint` に `raw_root` を足す。`/wiki:lint` は、`/wiki:ingest` の手順 0 と同じ順で `<RAW_ROOT>` を決めて、いつも渡す。渡されなければ、raw の根は推し量らない（場所からスコープを推さないのと同じ）。raw の根は、raw の記事までの途中のディレクトリを調べるためだけに使う。渡されないときは、途中のディレクトリを調べていない `raw:` を、結果の `summary` に挙げる。外の原本は印で見分けるので、raw の根が分からなくても決まる。過去に別の raw の根へ置いた raw は、その根が raw の根の記録にあれば、その根から raw までの途中のディレクトリも調べる。記録にない根の下の raw は、指す項目そのものしか調べず、途中を調べていない `raw:` として `summary` に挙げる（ADR-0029 の 14 回目のレビューの設計書の軽微 1） |
| 出すもの | 項目ごとに、種類（`symlink`、`junction`、`reparse`、`hardlink`）、どちらの根からの相対パスか、`raw:` が指すものなら、そのページ。調べられなかった項目は `links_unchecked` に出す |
| 直さない | lint の検査（`wiki_lint.py`、MCP の `lint`）も `/wiki:lint` の手順も、リンクを置き換えない。`links` の項目を、警告として利用者に伝える（作者の決定の 8）。今の lint の手順の承認された直し（`commands/lint.md` の手順 3）は、`links` には当てない |
| 走査はリンクを拒む | `wiki_pages.walk_markdown()` を、リンクを拒む形に変える（作者の決定の 7）。下の「ページの走査」 |

## 見つける規則の置き場所（提案）

リンクとみなす条件、リンクに降りないこと、調べられないものの扱いは、新しいモジュール `skills/info-hive/scripts/wiki_links.py` に置く。標準ライブラリだけで書き、`python` で動かし、何も書かない。使い分けは次のとおりである（親のセッションの指摘の 2）。

- `is_link(path)` は、1 つの項目がリンクかと、その種類を返す。走査、読む口、書き込みの部品、lint はこれを使う。
- `find_links(path)` は、`path` がリンクか、`path` がディレクトリならその下のすべての項目のうち、リンクであるものと、調べられなかったものを返す。`path` そのものには、「根とその祖先」の行の決まりを当てる。呼ぶ側は起点を渡し、`path` が起点そのものか、その祖先なら、`path` そのものは調べず、その下だけを調べる。起点より下は、別の根であっても調べる。引数 `articles_only` が真なら、記事の名前の規則で絞り、名前が `.` で始まる項目とその下を見ない。`raw:` が指すディレクトリの検査（lint）は `articles_only=True` で使う。取り込みのあとの確かめ（置いた raw の全体に、取り込みがリンクを作っていないことを見る）だけは、絞らずに使う（ADR-0029 の 6 回目のレビューの設計書の重大 3）。wiki の根の全体には当てない。2 つの wiki を引く問い合わせの読み手は `find_links()` を使わない。走査の `Walk.links` を警告として返し、raw は `resolve_raw()` で解いて根の下だけを読む（作者の決定の 9、問い合わせの設計の 15 版目）
- `python "<skill-root>/scripts/wiki_links.py" check <パス>...` は、結果を JSON で出し、リンクも調べられなかったものもなければ終了コード 0、ほかは 1 を返す。

## ページの走査（作者の決定の 7 の 9 の具体化。提案）

検索、MCP の索引、lint、閲覧、グラフ、統計が共通で使う `wiki_pages.walk_markdown()`（`walk_pages()` と `walk_index_files()`）を、リンクを拒む形に変える。

| 項目 | 今（v0.19.5） | 変えたあと |
| --- | --- | --- |
| ジャンクション（と、名前の代理のほかのリパースポイントのディレクトリ） | 降りる | 降りない |
| ディレクトリのシンボリックリンク | 降りない。記録せずに飛ばす（`wiki_pages.py` の 268〜269 行） | 降りない。記事の候補を含みうる場所にあれば、`Walk.links` に入れる（親のセッションの指摘の 1） |
| ファイルのシンボリックリンク | 先がふつうのファイルなら、ページとして読む | 読まない |
| ハードリンクの記事（`st_nlink` が 2 以上） | 読む | 読まない。走査は `.md` の項目に `os.stat()` を既に呼んでいる（`_stat_entry()`）ので、その結果の `st_nlink` で決め、呼び出しは増えない |
| `indexes/` がリンク | 起点として降りる | 降りない |
| wiki の根そのものがリンク | 降りる | 降りる（今のまま。根と祖先のリンクは許す） |
| 名前が `.` で始まる項目（ファイルとディレクトリ、どの深さでも） | ページの側は、ファイルを除き、ディレクトリは最上位の決まった名前（`.evolution`、`.wiki-cache`）だけを除く。索引の側は除かない | ページの側も索引の側も、どの深さでも降りず、読まない。`.git/` と隠しファイルを記事にしないため（作者の決定の 6） |
| 拒んだ項目 | － | `Walk` の新しい欄 `links` に、相対パスと種類を返す |

- 判定は `wiki_links.py` と同じ条件を使う（「見つける規則の置き場所」）。
- **記事を読む口を 1 つにする。** スクリプトが記事を読むのは、走査の結果を通すか、新しい関数 `wiki_pages.article_path(root, rel)` を通すかのどちらかにする。`article_path()` は、根から `rel` までの道と `rel` そのものに、走査と同じ判定を当て、拒むなら `Walk.links` と同じ形の理由を返す。走査を変えるだけでは閉じない。v0.19.5 の MCP の `list_index()` は、索引の一覧は走査で集めるが、最上位の `index.md` の本文（`wiki_index.py` の 979 行）と、名前を指定したときの `indexes/<名前>`（957〜964 行）を、走査を通さずに読む（ADR-0029 の 4 回目のレビュー）。この 2 つを `article_path()` に移す。ほかの直接の読み取りも、実装のときに `read_text`、`read_bytes`、`open` で洗い出して移す。`SCHEMA.md` が初期化された wiki の印かを見る判定（ADR-0019、`wiki_initialized.py`）は、読むのではなく見分けるものなので変えない。エージェントが Read で直接読むことは、止められない（「保証しないこと」）。
- **拒んだことを伝える。** 届け先をツールごとに数え上げず、2 つの決まりで閉じる。(1) wiki を読むスクリプトと MCP のツールの結果には、その wiki の走査が拒んだ項目（`Walk.links`）を、共通の欄 `link_warnings` として必ず付ける。CLI は標準エラーにも出す。拒んだ項目がなければ空にする。(2) 記事を名前で探して見つからなかったとき（MCP の `get_page`、`list_index` の名前の指定など）は、`Walk.links` と `article_path()` を引き、拒んだ項目に当たれば、「ない」ではなく「リンクなので読まない」を理由として返す。v0.19.5 では、`iter_page_files()` は走査の知らせを捨て（`wiki_pages.py` の 324 行付近）、閲覧の `walk_inputs()` は `unlistable` と `unknown` だけを見る（`wiki_browse_fs.py` の 1413 行付近）。`WikiIndex.get_page()` は、集めたページにないと `None` を返し（`wiki_index.py` の 931〜942 行）、`compute_stats()` は走査の `files` だけを数える（`wiki_stats.py` の 119〜200 行。ADR-0029 の 5 回目のレビュー）。これらを、2 つの決まりに合わせて変える。lint は、これに加えて指摘 `links` に出し、閲覧は診断に出す。
- 規則に反した wiki では、直す前から、リンクの先のページが検索、閲覧、lint のページの集合に出なくなる。作者は、それを受け入れて走査で拒むと決めた。黙って消えないように、拒んだ項目を返す。
- ジャンクションに降りないので、今の走査がジャンクションを通った道筋で行っている、回る道筋を止めるための識別子の比べ（`_chain_identities()`）は要らなくなる。
- 一時的なハードリンクの例外（「コマンドごとの当て方」）で置いている間のページは、その間だけ読まれない。
- 検索の対象の集合が変わるので、ADR-0010 のとおり、MCP の `query` の評価ゲートで測り直してから入れる。

## 依存の完全性（作者の決定の 9。ADR-0029 の I4、I5）

走査がリンクの記事を拒むと、その記事は読まれない。読まなかった記事の中身（frontmatter の `raw:`、`sources:`、wikilink）は、どの集計にも入らない。検索や閲覧には、読めた記事の集合で足りる。守りのように「参照がない」ことを根拠に書く操作には、足りない（ADR-0029 の修正案の依頼、[proposal-1.md](../agent-runs/2026-11-16-adr-0029-wiki-links/proposal-1.md) の 1）。

- **反例。** `W/sources/s.md` がハードリンクで、frontmatter に `raw: concepts/original.md` を持つ。書く段は、守る raw を「wiki のすべてのページの frontmatter の `raw:`」から集める（[書く段の設計](wiki-apply-2026-11-14.md) の 673〜684 行）。走査が `s.md` を拒んだ結果から集めると、`concepts/original.md` が守りから抜け、その原本への `edit` を許しうる。
- **走査と集計の結果に持たせるもの。** 走査は、読む前の名前と属性の段で、読めそうな記事（`files`）、リンクで拒んだ項目（`links`）、一覧できなかったディレクトリと調べられなかった項目（`unlistable`、`unknown`）を分けて返す（今の `Walk` に `links` を足す）。`files` は「読める」ことを約束しない。依存を集める関数（守る raw の収集など）は、記事の本文を実際に読む段で `complete` を決める。`complete` は、走査の `links`、`unlistable`、`unknown` が空で、`files` のすべての記事の本文を読んで frontmatter を解釈でき（読み取りの `OSError`、文字コードの誤り、frontmatter の壊れがない）、すべての `raw:` が `resolved` か `missing` だったときだけ真にする。今の `wiki_search.collect_pages()` は、本文の読み取りの失敗と文字コードの誤りを黙って飛ばす（`wiki_search.py` の 273〜289 行）。依存の収集では飛ばさず、`complete` を偽にする（ADR-0029 の 6 回目のレビューの設計書の重大 1）。`missing`（どの基準でもないファイル）は、守る中身がないので `complete` を偽にしない。
- **書く段。** 守る raw の収集の `complete` が偽なら、書く段（`wiki_apply.py`）は書かない。終了コード 1 で、拒んだ項目、読めなかった記事、曖昧な `raw:` を警告として出す。書く段の設計の「解けない `raw:` の値（ないファイル）は飛ばす」は、記録の中の raw の根の下の `missing` にだけ当てる（「`raw:` の解き方」の「守りは記録から作り、解き方に頼らない」）。 **順番。** 完全性は、ロックを取り、残った日誌を前に進めて、日誌に書いた一時ファイルの名前を消したあと（書く段の設計のロックの中の手順 2 と、前に進める手順の 1）に確かめる。ロックの前の収集（同じ設計の 559 行付近）で `complete` が偽でも、その理由が、日誌に書いた一時ファイルと同じ実体の記事のハードリンクだけなら、止めずにロックの中へ進む。止まって残った一時的なハードリンクの後始末に届くようにするためである（ADR-0029 の I7。7 回目のレビューの設計書の重大 1）。日誌の一時ファイルの名前は、リンクの数が 2 以上でも、部品が消してよい（名前を消しても、もう一方の名前の中身は変わらず、置き換えに当たらない）。セッションの raw の一時ファイル（`.wiki-session-*.tmp`）は日誌に載らないので、自動では消さず、警告にその名前を出し、利用者に消してもらう。
- **読むコマンド。** 検索、閲覧、統計、グラフの問い合わせ、lint は止めず、`link_warnings` を付けて続ける。2 つの wiki を引く問い合わせも、警告を付けて続ける。止めるのは、読み手が共有を見つけたときと、確かめられないときだけである（問い合わせの設計の 15 版目）。
- **ほかに完全性が要る操作。** 実装のときに、「参照がない」「ページがない」を根拠に書く操作を洗い出す（グラフの抽出の孤立のノードの削除、lint の承認された直しのうち被リンクを根拠にするものなど）。見つけたものは、同じく `complete` が偽なら書かない。
- **試験。** `s.md` を拒んだあと、書く段が `concepts/original.md` への `edit` を書かないこと（書く段がある版で）。`complete` が偽になる 5 つの場合（リンク、一覧できない、調べられない、本文を読めないか解釈できない、曖昧な `raw:`）で、それぞれ書かないこと。読むコマンドは同じ配置で続け、`link_warnings` を返すこと。 `missing` の `raw:` だけがあるときは、`complete` が真のままであること。 POSIX で、`new` の `os.link()` のあと、一時ファイルを消す前に止めた配置から、次の書く段が日誌を前に進めて一時ファイルを消し、完全性が真に戻って書けること。

## `raw:` の解き方（作者の決定の 9。ADR-0029 の I4）

今の `wiki_lint.missing_raw()` は、相対パスの `raw:` を、wiki の根、wiki の親、ページのディレクトリの 3 つの基準で解き、どれかがあれば「ある」とする（`wiki_lint.py` の 213〜241 行）。参照先を 1 つに決める関数ではないので、リンクの検査と書く段の守りに流用すると、別のファイルを調べたり、守ったりしうる（[proposal-1.md](../agent-runs/2026-11-16-adr-0029-wiki-links/proposal-1.md) の 2。見逃すかは、新しい検査が未実装なので推測）。

- **共通の関数。** `wiki_pages.resolve_raw(meta, page_path, wiki_root, wiki_root_given, allowed_roots=None)` を足し（`wiki_root` は解決した根、`wiki_root_given` は利用者が書いたままの根の綴り。`allowed_roots` を渡すと、その根の下の候補だけを調べる（下の「順番」の (1b)）。下の「基準」が両方を使う。問い合わせの設計の 15 版目の作り直しで見つかった食い違いを直した）、lint（`missing_raw` とリンクの検査）、問い合わせ、書く段の守りが使う。結果は値ごとに、`resolved`（1 つに決まった。そのパス）、`missing`（どの基準でもない）、`ambiguous`（2 つ以上の基準で、別の実体が見つかった。候補のパスを返す）、`unknown`（調べられなかった）、`link`（候補の道か候補そのものがリンクで、中身を読まなかった。拒んだ候補のパスと種類を返す）、`outside`（`allowed_roots` の外で、中身を読まなかった）のどれかと、理由を返す。
- **基準。** 絶対パスは、そのパスだけを見る。相対パスは、基準のディレクトリから候補を作る。基準は、利用者が書いたままの根（MCP の `wiki` に渡された綴り、CLI の引数の綴り）と、解決した根の両方から作る。根はリンクでもよいので、根の親が 2 つに割れうるからである（ADR-0029 の 9 回目のレビューの設計書の重大 1。`C:/view/wiki` が `D:/store/wiki` へのリンクのとき、セッションの `raw_ref_of()` は綴りの親 `C:/view` を基準に書き、MCP は根を `D:/store/wiki` に解決する）。そこで、解き方は根の綴りと解決した根の両方を受け取る。呼ぶ側は、利用者が書いたままの根の綴りを捨てずに渡す。生成元の仕様で基準が決まる形は、その基準だけで解く。セッションの raw（source ページに `session_id:` がある）は、wiki の親（綴りの親と、解決した根の親）を基準にする（`wiki_session.raw_ref_of()`、`wiki_session.py` の 1250〜1256 行）。そのほかの相対パスは、wiki の根、wiki の親、ページのディレクトリ（それぞれ綴りと解決の両方）を基準にする。候補はどれも文字で畳み、OS に `..` をたどらせない。見つかったものが 1 つの実体（同じファイルの識別子）なら `resolved`、別の実体が 2 つ以上なら `ambiguous` にする。候補のあるかないかを確かめられなかった（`PermissionError` など）ものがあれば、ほかに見つかっても `unknown` にする。先頭の `..` は、綴りと解決のそれぞれの根を基準にして畳む。途中に `..` を含む値は `unknown` にする（ADR-0029 の用語の「守る木の中か」）。
- **順番（ADR-0029 の I2、I4。12 回目のレビューの設計書の重大 2）。** 候補ごとに、次の順で調べ、前の段で決まったら後の段に進まない。(1) 候補のパスに `..` が途中にあれば `unknown`。(1b) 呼ぶ側が `allowed_roots` を渡したとき、候補が、そのどれかの下にあるかを、「守る木の中か」と同じ文字のうえの比べ方で確かめ、どの下にもなければ `outside` とし、中身もハッシュも読まない（2 つの wiki を引く問い合わせの読み手が使う。問い合わせの設計の 9 回目のレビュー）。(2) 中身を読む前に、リンクの判定を当てる。外の原本でない候補には、どこにあっても（今の raw の根の外の、過去の raw の根の raw でも）、「根とその祖先」の行の決まりでリンクの判定を当てる。起点は、候補を含むもっとも内側の raw の根（なければ wiki の根）である。候補が起点そのものか、その祖先なら、候補そのものには当てない（`raw: C:/data/raw` が raw の根そのものを指し、その根がリンクでも、`link` にしない）。候補が起点の下にあれば（ADR-0029 の用語の「守る木の中か」と同じ比べ方）、起点の子から候補までの途中の要素にも当てる。どの根の下でもなければ、途中の要素は調べず、`summary` に挙げる（ADR-0029 の 13 回目のレビューの設計書の重大 2。8 版目は守る木の中の候補にだけ当てていた）。リンクなら、その候補は `link` とし、中身を読まない（身元もハッシュも見ない）。(3) 候補があるかを、`os.lstat()` で確かめる（確かめられなければ `unknown`）。(4) 中身を読んで、版と身元を照らす（下）。どれかの候補が `link` なら、`resolve_raw()` の結果は `link`（拒んだ候補のパスと種類を持つ）にし、lint は `links` に、依存の収集は `complete` を偽にする。ハッシュが合わないことで、リンクの候補を `missing` に落とさない。
- **身元と版で確かめる（ADR-0029 の 10、11 回目のレビューの設計書の重大 1。作者の決定の 10）。** 綴りを 2 つ持っても、保存したときと違う綴りで wiki を渡されると、保存したときの「wiki の親」は復元できない。保存したときの綴りは、ページにも raw にも残っていない。そこで、候補がそのページの raw かを、場所ではなく、そのページが記録した中身で確かめる。確かめ方は 2 段である。(1) **版。** ページに raw のバイト列の SHA-256（`raw_sha256:`）があれば、候補の SHA-256 が合うものだけを残す。これで、同じセッションを別の範囲や伏せ字で取り込んだ別の版や、同じ URL の別の取得も区別できる。(2) **身元。** `raw_sha256:` のない既存のページでは、セッションの `session_id:` と raw の frontmatter の `session_id`（`wiki_session.py` の 588 行付近）、Web ページの `url:` と raw の frontmatter の `url`（`wiki_fetch.py` の 1451 行。あれば `final_url`）で、合わない候補を捨てる。身元だけで残った候補は、版を確かめていないので、結果に `version_unverified` を付け、lint は警告する（I4。黙って同じ版とみなさない）。どちらの段でも、合う候補が 1 つなら `resolved`、なければ `missing`、2 つ以上なら `ambiguous` にする。身元も版も持たないページでは、上の基準のとおり、別の実体が 2 つ以上なら `ambiguous` にする。
- **守りは記録から作り、解き方に頼らない（ADR-0029 の 11 回目のレビューの設計書の重大 2。作者の決定の 10）。** 書く段は、wiki の外の raw の親も守る raw の根に入れ、それと作業用の `K` やデータの場所との重なりを拒む（書く段の設計の 667〜684 行）。保存したときの綴りを失って本当の raw を `missing` にすると、その親が守る根から落ち、`INFO_HIVE_DATA_DIR` が過去の raw の根を指す配置を止められない。6 版目の「wiki の外の raw は守りに要らない」は誤りだった。そこで、守る raw の根は、`raw:` を解いた結果からではなく、書き手が残した記録から作る。すべての raw の書き手（`wiki_fetch.py`、`wiki_rawcheck.py`、`wiki_session.py`、`wiki_evolve.py`、PDF を写す取り込み）は、raw を置くたびに、使った raw の根を、利用者が書いたままの綴りと解決したパスの両方で、wiki の raw の根の記録に足す。足し方は、書き手ごとに `W/.wiki-cache/raw-roots.d/<乱数>.json` を、書き込みの部品で、既にない名前として 1 つ作る（中身は raw の根の綴りと解決したパス、書き手、時刻）。置き場所は、書く段の管理領域（`.wiki-cache/apply` と `.wiki-cache/apply-pending`）の外にする。書く段は、管理領域の下に決まった形にないものがあると `unknown_in_cache` で止まるが、`.wiki-cache` の直下のほかのものは見ない（書く段の設計の 393 行。ADR-0029 の 13 回目のレビューの設計書の重大 1。8 版目は `apply/` の下に置いていた）。書く段の決まった形の一覧は変えない。1 つのファイルを読んで書き直さないので、並べて動く書き手のあいだで記録が消えない。読む側は、書く段の設計の `L/raw-roots.json` と、`raw-roots.d/` のすべてのファイルの和を記録とする。書き手は、raw を置く前に記録を足す。記録を足せなければ、raw を置かない（I6 の「道がないもの」）。記録を足したあと、raw を置く前に止まっても、守りが広がるだけで、狭まらない。 **記録の中の、wiki の根の中の根。** 記録の根が wiki の根の中にあるとき（古い構成の `W/raw` など。綴りと解決のどちらかが、ADR-0029 の用語の「守る木の中か」の比べ方で wiki の根の下にあれば）、それを守る raw の根にしない。根にすると、書く段の根の重なりの検査（書く段の設計の 679 行）が `W` との包含を `raw_overlap` として拒み、記録は消えないので、構成を移したあとも書く段が止まり続ける。代わりに、書く段の設計の「wiki の中の raw」（書く先にしないパス。同じ設計の 681 行）の入力に、その根のパスを渡す。ページから引かれる wiki の中の raw と同じ扱いである（PR #147 の Codex のレビュー）。書く段の守る raw の根の作り方は、書く段の設計の 673〜684 行のまま変えない（wiki の外の raw はファイルなら親、ディレクトリならそれ自身を根に足し、wiki の中の raw は根にせず、そのパスだけを守る）。変えるのは、その作り方に渡す入力の 2 つだけである。1 つ目は、記録の入力に下の `raw-roots.d/` を足すこと。2 つ目は、ページから引かれる raw を、`missing_raw()` と同じ解き方ではなく `resolve_raw()` で解き、`resolved` になったものだけを渡すことである（ADR-0029 の 12 回目のレビューの設計書の重大 1。7 版目は作り方を別の形で書き直し、ディレクトリの raw の親まで根にしていた）。記録は、書く段が入る前の取り込みの分を持たないので、本書を入れる版で、`/wiki:upgrade` が今の raw の根を記録に足し、利用者に過去の raw の根があれば足すよう案内する。そのうえで、`raw:` の `missing` は、記録に入っていない場所の raw を守らない理由にしない。記録の外で `missing` になった `raw:` が 1 つでもあれば、`complete` を偽にする（記録が完全でないかもしれないため）。記録の中の raw の根の下で `missing` になったもの（本当に消えた raw）は、`complete` を偽にしない。
- **曖昧なとき。** lint は `raw_ambiguous` として、候補と理由を警告する。書く段は、守りの収集の `complete` を偽にして書かない（「依存の完全性」）。問い合わせで raw を読むときは、どの候補を読むかを決めず、候補を利用者に示す。
- **書き換えない。** 既存の `raw:` を自動で書き換えない（作者の決定の 8、9）。直すのは利用者である。新しく書く `raw:` は、今の取り込みの手順の形（wiki の親からの相対パス、セッションの `raw_ref`、rag の絶対パス）のままにする。そのうえで、すべての種類の source ページに、raw のバイト列の SHA-256 を `raw_sha256:` として書く（今は rag の PDF だけが書く。セッションの raw は`render_sha256`、Web ページの raw は書いた本文のバイト列から取る）。frontmatter のキーが増えるので、利用者に見える変更として CHANGELOG に書く。 **ハッシュの決め方（12 回目のレビューの設計書の軽微 1）。** `raw:` がファイルなら、そのバイト列の SHA-256。ディレクトリなら、その下の名前が `.` で始まらないふつうのファイルを、ディレクトリからの `/` 区切りの相対パスで並べ、1 行ごとに「相対パスとそのファイルの SHA-256 の 2 つを並べた JSON の配列（`json.dumps([相対パス, SHA-256], ensure_ascii=False)`）」を書いて改行で結んだ UTF-8 のバイト列の SHA-256。JSON はタブ、改行、引用符をエスケープするので、名前にタブや改行を含むファイルがあっても、別のファイルの構成と同じ一覧にならない（ADR-0029 の 15 回目のレビューの設計書の軽微 1。10 版目はエスケープしないタブ区切りで、`"a\t<H>\nb"` の 1 つのファイルと、`a` と `b` の 2 つのファイルが同じ一覧になった）。並べる鍵は、走査と同じ（`wiki_pages._sort_key()`。NFC にそろえた相対パス、同じならディスク上の綴り）にし、行に書く相対パスはディスク上の綴りのままにする。NFC にそろえると同じになる別のファイル（合成済みの `が.txt` と、`か` に U+3099 を付けた名前）があっても、綴りで順と行が決まるので、一覧の順に依らず 1 つのハッシュになる（ADR-0029 の 14 回目のレビューの設計書の軽微 2）（リンクに当たれば、ハッシュを取らずに `link`）。`raw:` が複数の値の配列なら、`raw_sha256:` も同じ順の配列にする。数が合わなければ、版を確かめていないものとして `version_unverified` にする。
- **試験。** セッションの source ページの `raw: archive/raw/session.md` を、wiki の親の基準だけで解くこと。wiki の根の基準と wiki の親の基準で別のファイルが見つかる `raw:` が `ambiguous` になること。同じファイルを 2 つの基準で見つけたときは `resolved` になること。今の `missing_raw()` との一致は求めない。新しい解き方は、身元と版を確かめ、根の綴りの両方を基準にし、確かめられない候補を `unknown` にするので、結果が違う場合がある。違いは CHANGELOG に書く（ADR-0029 の 11 回目のレビューの設計書の軽微 1）。`C:/view/wiki` で保存したセッションの raw を、`D:/store/wiki` で読むと、`D:/store/raw/session.md`（`session_id` が違う無関係なファイル、または同じ `session_id` の別の版で `raw_sha256` が違うもの）を `resolved` にしないこと。`raw_sha256:` のない既存のページで、`session_id` だけが合う候補には `version_unverified` が付くこと。書く段の守る raw の根に、記録にある過去の raw の根（`C:/view/raw`）が入り、`INFO_HIVE_DATA_DIR` がそこを指すと `begin` が止まること。 `raw: ../raw`（ディレクトリ）のページがあっても、書く段の守る根は `C:/data/raw` そのもので、`C:/data` にならないこと。raw の根の中の `a.md` が外へのシンボリックリンクのとき、リンクの先を読まず、ハッシュが合っても合わなくても `link` になり、lint の `links` に出ること。ディレクトリの raw と、配列の `raw:` のハッシュが、決めた形で取れること。raw の書き手ごとに `raw-roots.d/` に記録が 1 つ増えること、2 つの書き手が並べて記録しても両方が残ること、記録を作れないと raw を置かないこと、記録のあと raw を置く前に止めても、次の書く段の守る根にその raw の根が入ること。 記録を足したふつうの配置で、書く段の `begin` と `apply` が管理領域の確かめを通ること（`raw-roots.d/` で `unknown_in_cache` にならないこと）。今の raw の根の外の `raw: D:/archive/raw/session.md` がリンクのとき、その中身（frontmatter）を読まずに `link` になり、身元が合っても合わなくても `links` に出ること。 古い構成の `W/raw` が記録にある wiki で、今の raw の根を wiki の外に移したあと、書く段の `begin` が `raw_overlap` で止まらず、`W/raw` の下を書く先にしないこと。 `raw: C:/data/raw` が raw の根そのもの（`D:/archive/raw` へのディレクトリのリンク）を指すとき、`link` にならず、lint の `links` に出ず、`complete` を偽にしないこと。その下の `part.txt` がリンクなら、`link` になること。記録にある過去の raw の根の下の raw で、途中のディレクトリのリンクを挙げること。NFC にそろえると同じになる 2 つの名前のファイルを持つディレクトリで、一覧の順を変えてもハッシュが変わらないこと。 raw の根を wiki の中（`W/topics/raw`）に置き、その祖先の `W/topics` がジャンクションのとき、wiki の根からの走査と `article_path(W, "topics/raw/a.md")` が `topics` のジャンクションで拒み、`Walk.links` に出すこと。同じ配置で、raw の根を起点にした `resolve_raw()` は、raw の根とその祖先を調べないこと。名前にタブと改行を含むファイルを持つディレクトリと、2 つのファイルを持つディレクトリのハッシュが違うこと。

## mount（提案）

bind mount と、POSIX のマウントポイントは、規則の対象にしない。lint も見つけない。2 つの wiki が mount でファイルを分け合うことは、問い合わせの設計の補助が、2 つの根の下の識別子を比べて見つける（設計書の第 4 節の `shared`）。

- 項目ごとの `os.lstat()` では、同じファイルシステムの中の bind mount を見分けられない。見せている先のファイルと同じ識別子を返し、リンクでもない（確かめていない。Linux の bind mount の振る舞いの知識による）。見分けるには、マウントの表（`/proc/self/mountinfo`）を読む必要があり、OS ごとに作りが違う。lint で確かめられない規則は、守られているかが分からない。
- bind mount を作るには管理者の権限が要る。1 つの wiki の中の mount による別名は、利用者が意図して作るものとして、保証しない。
- Windows のボリュームのマウントしたフォルダーは、名前の代理のリパースポイントなので、記事までの道にあれば `links` に出る。POSIX のマウントポイントは出ない。この非対称は受け入れる。Windows で別のボリュームを使うなら、wiki の根か、その祖先にマウントする。
- 「リンクがなければ、2 つの木が分け合うのは入れ子のときだけ」とは言わない。ADR-0029の規則は、2 つの wiki が分かれていることを保証しない。

## 規則に反した配置での書き込み（提案）

規則に反した配置は、lint を流すまで残る。そのあいだの書き込みを、ADR-0029は書き手ごとに直さない。プラグインのスクリプトが守る木に書くものは、すべて 1 つの書き込みの部品を通す。

**部品と、ADR-0023 の `Writer` の関係。** ADR-0023 の `Writer` は、書く段の道具（`wiki_apply.py`）のためのもので、書き込みを 3 つの領域（ページ、wiki の管理、作業用）に分け、wiki の管理の書き込みは決まったパスだけを許す（[書く段の設計](wiki-apply-2026-11-14.md) の 381〜390 行）。raw の書き手（`wiki_fetch.py`、`wiki_rawcheck.py`、`wiki_session.py`、`wiki_evolve.py`）と検索のキャッシュ（`wiki_search.py`、`setup_wiki.py`）の行き先は、どの領域にも入らない。raw の根を `W` として渡すと、raw と `W` の重なりを拒む検査に当たる（同じ設計の 679 行）。そのため、ほかの書き手に `Writer` をそのまま使わせることはできない（ADR-0029 の 2 回目のレビュー）。

そこで、`wiki_fsguard.py` の中を 2 つの層に分ける。

| 層 | 受け持つこと | 使う書き手 |
| --- | --- | --- |
| 書き込みの部品（下の層） | 渡された根から行き先までの道に別名がないことを確かめる（`Writer` の検査の a、b、e と同じ。リンク、リパースポイント、輪、マウントポイント。根の子から行き先までを見て、根そのものは見ない）。行き先の名前が既にあれば、`wiki_links.py` の判定でリンク（ハードリンクを含む）でないことも確かめる。`Writer` の検査 a は `st_nlink` を見ないので、これを足す（ADR-0029 の 5 回目のレビュー）。道か行き先がリンクなら、書かず、置き換えず、警告を返す（作者の決定の 8）。一時ファイルを既にない一意の名前で作る。名前で置き換える。重ねて書かない形で置く（上の例外の置き方） | プラグインのスクリプトのすべての書き手。根は、利用者が設定で決めた場所にする。wiki の根、raw の根、データの場所（`INFO_HIVE_DATA_DIR`。既定は `%LOCALAPPDATA%\info-hive` など）である。ADR-0023 の作業用の `K` と wiki の管理の `L` は、それぞれデータの場所と wiki の根の下にあるので、その根を渡す。根そのものと祖先のリンクは許す。利用者が決めた場所を、利用者の配置のまま使うためである（wiki の根と同じ扱い）。プラグインが守る木の中に決めたディレクトリ（`.wiki-cache` など）は、根として渡さない。部品は根そのものを検査しないので、そうすると、そのディレクトリのリンクや mount を見落とす（ADR-0029 の 3 回目のレビュー）。検索のキャッシュの書き手はwiki の根を渡し、`.wiki-cache` そのものも検査を受ける。データの場所を wiki の中に置いたとき（`INFO_HIVE_DATA_DIR` が `W/.wiki-cache/mcp` など）は、データの場所が根になるので、wiki の根からデータの場所までの道は検査しない。利用者がそこを指したので、そのとおりに書く（「保証しないこと」） |
| `Writer`（上の層） | 書く段の領域と役割の検査（`Writer` の検査の c、d）と、日誌 | `wiki_apply.py` だけ（ADR-0023 のとおり） |

ADR-0023 の決定（書く段の書き込みは `Writer` を通す、領域と許すパス）は変えない。`Writer` の道の検査を下の層に切り出し、ほかの書き手も同じ検査を使う形にする（ADR-0023 は、`wiki_browse_fs.py` の検査も `wiki_fsguard.py` に移すと決めている）。

- **書き手ごとに直さない理由。** 別名を通して書く形は 2 つある。1 つは、行き先の名前そのものがリンクかハードリンクで、それを開いて書く形である。v0.19.5 では、`wiki_search.write_parse_cache()`（`.wiki-cache/search-index.json.tmp`）、`wiki_rawcheck.write_atomic()`（`.wiki-cache/ingest/<スラッグ>/<名前>.tmp`）、`wiki_fetch.write_outputs()`（`<RAW_ROOT>/.<スラッグ>.md.<プロセス ID>.tmp`。シンボリックリンクは外すが、ハードリンクは見ない）、rag の `rag_index.Engine._mark_reviews()`（`<ページ>.md.rag-tmp`）がこの形で書く。もう 1 つは、道の途中のディレクトリがリンクの形である（`.wiki-cache` が外を指すジャンクションなど）。この形では、一時ファイルを一意の名前で作って `os.replace()` で置いても、置く先が外になる。書き手を 1 つずつ見つけて直すと、見つけ漏れた書き手と、直し方が届かない形から破れる。
- **部品に求めること。** 道と行き先の検査に加えて、次を求める。一時ファイルは、既にない一意の名前として作る（既にある名前を開いて書かない）。既にあるふつうのファイル（リンクの数が 1）を置き換えるときは、`os.replace()` で名前そのものを置き換え、既にある名前を開いて中身を書き換えない。行き先がハードリンクなら、上のとおり書かずに警告する。もう一方の名前の中身を守るために名前を置き換えることもしない（作者の決定の 8）。
- **部品を通らない書き手。** ライブラリが自分でファイルを開いて書くもの、つまり `.wiki-cache/` の SQLite のベクトルの索引（`wiki_search.open_vector_index()`）、MCP の索引の台帳の SQLite（`wiki_index.py` の 405 行）と Tantivy（471 行）は、部品は書くのではなく、確かめるだけの操作をする。ライブラリに渡す前に、根から行き先までの道と、行き先のファイルとその付随ファイル（SQLite の `-wal`、`-shm`、`-journal`、Tantivy のディレクトリの中のファイル）に、リンクの判定を当てる。リンクなら `LinkRefused` を返し、呼ぶ側は「書けなかったときの振る舞い」に従う。確かめたあと、ライブラリが開くまでの間に置き換えられることは防げない（ADR-0029 の 9 回目のレビューの設計書の軽微 2）。モデルが使う Claude Code の Edit と、プラグインが起こす子プロセス（uv など）は、部品を通らない。rag の `_mark_reviews()` は、別のプラグインから wiki のページを書く。部品を使うかは、rag の側で別に決める。これらは、規則に反した配置では別名を通して書きうる。書き手を固くするだけでは閉じないので、リンクを置かない規則を主にする。
- **書けなかったときの振る舞い（親のセッションの指摘の 3、7 回目のレビューの設計書の重大 2）。** 部品は、道か行き先がリンクなら、書かずに、種類と場所を持つ誤り（`LinkRefused`）を返す。呼ぶ側は、その書き込みなしで結果を作る道が設計にあるかで振る舞いを分ける。道があるものは、書かずに続け、結果の `link_warnings` に載せる（CLI は標準エラーにも出す）。CLI の検索のパースのキャッシュ（`--cache`）は、キャッシュを使わずに解析して続ける。CLI の意味の検索のベクトルの索引（`.wiki-cache/` の SQLite）は、語彙の検索（`--no-embed` と同じ）に落として続け、意味の検索をしていないことを警告に書く。道がないものは、その操作を失敗させ、理由を知らせる。記事、raw、索引、ログ、グラフの成果物がこれに当たる。MCP の索引（データの場所の `index/<wiki_key>/`）もこれに当たる。`query`、`get_page`、`stats` は `WikiIndex` を作れないと結果を作れない（`wiki_mcp_server.py` の 188 行、`wiki_index.py` の 831 行）ので、そのツールの呼び出しを失敗させ、理由と、CLI の `wiki_search.py --no-embed`（`.wiki-cache/` に書かない）で引けることを返す。MCP の索引を持たずに答える道は、作らない。
- **部品ができるまで。** `wiki_fsguard.py` はまだない（v0.19.5）。部品ができ、上の書き手が移るまで、決まった名前の一時ファイルと道の途中のリンクを通した書き込みは、規則に反した配置で起きうる。書き手の一覧は `grep` で探したもので、すべてとは限らない。移すときは、守る木に書くすべての呼び出しを洗い出す。

## MCP のサーバーの版（提案）

`wiki_links.py` を `wiki_mcp_common.SERVER_FILES` に入れる。MCP の `lint` が `wiki_lint` を通して使うからである。入れないと、`wiki_links.py` だけを変えたときにサーバーの版が変わらず、中継（`wiki_mcp_relay.py`）は古い規則のサーバーを使い続ける。

あわせて、`SERVER_FILES` が足りていることを確かめる試験を足す。サーバーは、`wiki_lint` などをツールの関数の中で読み込む（`wiki_mcp_server.py` の 383 行付近）。そのため、サーバーを読み込んだあとの `sys.modules` を見ても、遅れて読み込むモジュールは出てこない。試験は、`SERVER_FILES` の各ファイルの構文木から、関数の中のものも含めたすべての `import` を拾い、スクリプトのディレクトリにあるモジュールを、たどれるかぎりたどる。たどり着いたモジュールがすべて `SERVER_FILES` に入っていることを確かめる。この形でたどると、今の `SERVER_FILES` にない `wiki_decide.py` も見つかる（`wiki_search.py` が 872 行で関数の中で読み込む。ADR-0029 の 2 回目のレビューが見つけ、ADR-0029の作者もコードで確かめた）。ADR-0029を実装する版で、あわせて入れる。

## 今ある wiki と raw の直し方（提案。直すのは利用者で、プラグインは警告するだけ）

規則を入れた版の lint は、今ある配置のリンクを `links` に挙げ、警告として利用者に伝える。プラグインは直さない（作者の決定の 8）。リンクの先は利用者のデータのことがあり、直すか、どう直すかは利用者が決める。

利用者が手で直すときの目安として、直したあとに成り立つ状態と、その確かめ方を `references/lint-workflow.md` に載せる。手順の並びではなく状態で書くのは、手順が OS、ファイルの属性、リンクの種類で変わるからである。

**直したあとに成り立つ状態。**

1. 直した名前は、ふつうのファイルかふつうのディレクトリで、ファイルならリンクの数が 1 である。
2. 直した名前のバイト列は、直す前にその名前で読んだバイト列と同じである（ディレクトリなら、その下のすべてのファイル）。
3. 直した名前の読み取り専用の属性は、直す前と同じである。
4. リンクの先と、ハードリンクのもう一方の名前は、バイト列も属性も直す前と同じである。先を消さない。
5. lint の `links` に、直した名前が出ない。

**確かめ方。** 直す前に、直す名前ともう一方の名前（分かれば）のバイト列の SHA-256 と、読み取り専用かどうかを控える。直したあとに同じものを取り、上の 2〜4 を照らす。lint を流し直して 5 を確かめる。

**種類ごとの注意。**

| 種類 | 今の振る舞い | 注意 |
| --- | --- | --- |
| ファイルのシンボリックリンク | 今の走査は先の中身をページとして読み、変えたあとの走査は読まない。直すと、変えた走査でもページとして出る | 先の中身を同じディレクトリの新しい名前に写し、`os.replace()` でリンクの名前に置くのが例である。先がないか読めないリンクは、走査が読んでおらず（先のないリンクは飛ばす）、写す中身もない。そのときは、リンクを消すか、利用者が用意したファイルに置き換えるかを、利用者が決める。上の 2 は当てない |
| ジャンクション（マウントしたフォルダーを含む） | 今の走査は降り、変えたあとの走査は降りない。直すと、変えた走査でもページとして出る | 先の中身を写した実のディレクトリを作り、ジャンクションそのものを消してから、その名前に置く。Windows の `rmdir <名前>` はジャンクションだけを消す。`/s` を付けると先を消す |
| ディレクトリのシンボリックリンク | 走査は降りない。中身は今、wiki の一部ではない | 中身を写せば、ページが増え、検索の結果と lint の孤立の判定が変わる。上の 2 は「写す」と決めたときだけ当てる。写すか、リンクを消すだけにするかを、利用者が決める |
| ハードリンク | 中身は既に wiki の一部である | 読み取り専用の属性は、名前ではなくファイルに付くので、2 つの名前で同じである。Windows では、読み取り専用の名前を `os.replace()` で置き換えると `PermissionError` になる。どちらも Windows 11 と Python 3.14.6 で確かめた（片方の名前で読み取り専用にすると、もう片方も読み取り専用になり、もう片方の名前で外すと両方が外れた）。そのため、属性を外してから置き換え、置き換えたあとに、新しいファイルと、もう一方の名前の属性を直す前に戻す（上の 3 と 4） |

- **セッションの raw。** ADR-0020 の raw は読み取り専用で、取り込みの終わりに決定のファイルを消すので、あとから `wiki_session.py write` で作り直せない。直すときは、上の確かめ方で、バイト列と読み取り専用の属性が保たれたことを確かめる。`wiki_session.py verify` は、取り込みのときの `render_sha256` が分かれば、同じことを確かめる（同じバイト列で、読み取り専用のときだけ終了コード 0。`wiki_session.py` の 1675〜1683 行）。
- **プラグインが残したハードリンク。** 重ねて書かない置き方（「コマンドごとの当て方」の例外）が `os.link()` と一時ファイルの名前を消す間で止まると、行き先の記事の `st_nlink` が 2 のまま残り、行き先が `links` に出る。一時ファイルは名前が `.` で始まる（`.wiki-session-*.tmp`、`.wa-*.tmp`）ので、記事ではなく、lint には出ない（ADR-0029 の 5 回目のレビュー）。一時ファイルの名前を消せば直る。セッションの raw では `wiki_session.py inspect` の `temp_files` に出る。書く段では、日誌に書いた一時ファイルの名前を、次にロックを取った書き手が消す（書く段の設計の 593 行）。lint と書き込みが重なったときにだけ出る指摘は、lint を流し直せば消える。lint の警告には、この見分け方を添える。 書く段の一時ファイルは、次の書く段が完全性を確かめる前に消すので、書く段を止めない（「依存の完全性」の順番）。
- **MCP の索引。** 写して置き換えるときに大きさと更新時刻を保つと（`shutil.copy2()`）、MCP の索引は読み直さない（`wiki_index.stat_signature()`）。上の 2 で中身は同じなので、害はない。
- 作者の環境の 2 つの wiki と raw に、今リンクがあるかは確かめていない。規則を入れた版で lint を流して確かめる。


## 検討した選択肢（実装の形）

| 選択肢 | 判断 |
| --- | --- |
| リンクを許し、問い合わせの補助で名前の置き場所を比べる（設計書の 7 版目まで） | 採らない。4 回のレビューで、リンクの種類ごとに穴が見つかった |
| どのコマンドも、動く前に守る木を調べ、リンクがあれば止まる（読み方 B） | 採らない（作者の判断）。Windows ではハードリンクを見つけるのに全ファイルの `os.lstat()` が要り、何度も呼ばれる MCP の `query` のたびに走査することになる。直すまで、読むだけのコマンドも使えなくなる。重ねて書かない置き方の一時的なハードリンクで、同時に動くコマンドが止まる |
| ページの走査は今のままリンクを読み、lint で見つけるだけにする（ADR-0029 の 6 版目まで） | 採らない（作者の決定の 7）。走査がリンクの先を読むあいだは、規則に反した配置の中身が、検索、閲覧、lint のページの集合に入り続ける。走査で拒み、拒んだ項目を返して、黙って消えないようにする |

| 外の原本のハードリンクを拒む | 採らない。ハードリンクを含む利用者の蔵書を登録できなくなる。ADR-0013 の別名の扱いと食い違う。絶対パスで直接指すことに比べて、守れるものが増えない |
| 外の原本を `<RAW_ROOT>` に写す | 採らない。ADR-0008 と ADR-0013 の「原本を複製しない」に反し、大きな蔵書を複製する |
| `raw:` に利用者が指定したパスを書く（rag の `result.raw` を変える） | 採らない。rag の台帳と検索の結果の `raw` が解決したパスなので、source ページとだけ形が食い違う。ADR-0013 を置き換えることになる。外の原本が対象外なら、リンクの規則のためにもならない |
| 判定を `is_symlink()` と `is_junction()` だけにする | 採らない。ほかの名前の代理のリパースポイントを見逃す。マウントしたフォルダーがジャンクションと同じタグかも、文書で確かめられなかった |
| bind mount とマウントポイントも規則で禁じる | 採らない。項目ごとの検査で見分けられず、lint で確かめられない。2 つの wiki の間の共有は、問い合わせの補助が識別子で見つける |
| 守る木の下のすべてを対象にし、何も除かない（ADR-0029 の 5 版目まで） | 採らない（作者の決定の 6）。記事を扱うコマンドの規則が、記事でないファイルを対象にすると、`.git/` のオブジェクトや uv のキャッシュのハードリンクのように、記事に関わらないものを挙げる。記事でないファイルとのハードリンクは、記事の側の `st_nlink` で見つかる。記事でないファイルへの書き込みは、書き込みの部品が守る |
| lint が raw の根を、wiki の隣の `raw/` と推し量る | 採らない。場所から推さない。呼ぶ側が決めて渡す |

  - 取り込み: 記事になるソース（記事か記事までの道にリンクがあるもの、raw の根に既にあり、その場で `raw:` で指すもの）がリンクなら、置き換えず、取り込まず、警告に種類と場所が出ること。記事でない場所（`assets/` など）のリンクのソースは、中身を新しい raw に写し、元のリンクを変えないこと（手で確かめる）。途中に `..` を含むソースのパス（`raw/jump/../../book.pdf` で `jump` がリンク）は、所属を決めずに止まり、PDF の登録もしないこと。lint: `links` を出しても、守る木のファイルを 1 つも変えないこと。
  - `SERVER_FILES` が、サーバーが関数の中で遅れて読み込むものも含め、同梱のモジュールをすべて含むこと。`wiki_links` を `SERVER_FILES` から外すと、この試験が落ちること。
  - lint: `--raw-root` を渡したとき、raw の根そのもの（`archive/raw` がリンクの配置）を挙げず、その下のリンクを挙げること。渡さないとき、途中のディレクトリを調べていない `raw:` が `summary` に出ること。
  - 部品: 検索のキャッシュの書き手が wiki の根を渡し、`.wiki-cache` そのものが bind mount かジャンクションなら書かないこと。
  - 部品: 道の途中のディレクトリがジャンクションかシンボリックリンクなら書かないこと。行き先の名前と、決まった名前の一時ファイルが既にハードリンクとしてあっても、もう一方の名前の中身を変えないこと。
  - 検査を壊して落ちることを確かめる。名前の代理のビットを見ない、`os.lstat()` の代わりに `DirEntry.stat()` の `st_nlink` を見る、記事までの途中のディレクトリを見ない、調べられない項目を無視する、、所属を決める前に `..` を文字で畳む、の 5 つで、それぞれ狙った試験が落ちること。
- 取り込みは、エージェントが手順を当てはめるので、手で確かめる。ファイルへのシンボリックリンクと、リンクを含むディレクトリを取り込み、raw にリンクがなく、先の中身が写っていることを `wiki_links.py check` で確かめる。
- 問い合わせの設計（`docs/plans/wiki-query-two-wikis-2026-11-16.md`）は、13 版目で第 3.8 節を ADR-0029 を指す形に直し、外の原本の扱いと `raw:` の書き方を ADR-0029 に合わせた。
- ほかの ADR との関係:
  - ADR-0013 は変えない。
  - ADR-0017（browse は入力をどこにあっても読む）とは、一部が食い違う。browse は共通の走査で読むので、変えたあとは、リンクを通って届くページを描かない。ADR-0017 の「入力の実体は、置き場所によらず Wiki の内容として読む」のうち、リンクを通って届く実体は、ADR-0029で読まない形に変わる。ADR-0029を承認するときに、ADR-0017 の状態に「一部は 0029 で置き換え済み」と書く。
  - ADR-0019 は、リンクの `SCHEMA.md` も、先がふつうのファイルなら初期化された wiki とみなす。この見分け方は変えない。`SCHEMA.md` は記事なので、そのリンクは `links` に出る。
  - ADR-0020 のセッションの raw の書き手は、raw の根とその祖先がリンクなら書かない（`wiki_session.py` の 1200〜1204 行）。ADR-0029は根と祖先のリンクを許すが、この書き手の検査は緩めない。読み取り専用で重ねて書かない raw を、道の別名を通して置かないための、書き手ごとの厳しい検査として残す。
  - ADR-0023 の書く段（`wiki_fsguard.Writer`、まだない）は、根から書く先までの道に、リンク、リパースポイント、マウントポイントがあれば書かない。ADR-0029は木の中身の規則、ADR-0023 は書く道の検査で、両方が当たる。ADR-0023 はクラウドの置き換えを含むすべてのリパースポイントを道で拒むので、書く段の側がより厳しい。ADR-0029は、`Writer` の道の検査を書き込みの部品に切り出し、プラグインのスクリプトのすべての書き手がそれを使う形にする（「規則に反した配置での書き込み」）。`Writer` の領域と許すパスは変えない。ADR-0023 の書く段のロックと `new` のページの置き方は、ADR-0029の例外（重ねて書かない置き方）に当たる。


## 保証しないこと（詳細）

- **別名で書いたソース。** 守る木の中のファイルを、`subst` のドライブや別の共有名など、根と違う綴りで渡すと、文字のうえで木の外に見え、取り込みは中身を新しい raw に写す。リンクは作らないが、同じ中身の raw が増える。
- **規則の前に登録した、木の中のシンボリックリンクの PDF。** `raw:` は解決したパスなので木の外の先を指し、リンクの名前はどの `raw:` からも指されず、記事にならない。lint では見つからない。今後の登録は、取り込みの表のとおり止まる。

- **作ることは止めない。** 規則は lint と取り込みのあとの確かめで見つけるもので、利用者やほかの道具がリンクを作ることは止めない。走査はリンクを読まないが、エージェントが Read で raw やページを直接読むことは止めない。書き込みの部品ができて書き手が移るまで、プラグインのスクリプト、SQLite、Edit は、リンクの先を書き換えうる。移ったあとも、SQLite、Edit、子プロセスは残る。
- **記事でないファイル。** 記事でないファイル（`.wiki-cache/`、`graph/`、`assets/` など）のリンクは見つけない。記事でないファイルとのハードリンクは、記事の側で見つかる。索引、ログ、`SCHEMA.md` は記事なので、他方の wiki のファイルへのリンクなら lint に出る。
- **データの場所を wiki の中に置いた配置。** データの場所は利用者が決めた根なので、wiki の根からデータの場所までの道（`W/.wiki-cache` など）のリンクは検査しない。そこが他方の wiki を指していれば、MCP の索引と起動のファイルはそこに書かれる。利用者がその場所を指したものとして扱う。
- **mount による別名。** 1 つの wiki の中の bind mount とマウントポイント（Windows のマウントしたフォルダーを除く）は見つけない。
- **raw の根を渡さない lint。** `raw:` の途中のディレクトリは調べない。調べなかったものは `summary` に挙げる。`/wiki:lint` はいつも raw の根を渡すので、これに当たるのは、MCP の `lint` や CLI を直接呼んだときである。
- **外の原本。** 外の原本と、そこへの道のリンクは調べない。外の原本が他方の wiki の木の中を指すことも確かめない。外の原本は `rag_job_id:` の印で見分けるので、利用者が印を手で書き足したり消したりすると、取り違える。
- **過去の raw の根。** 過去に置いた raw の根が raw の根の記録になければ、そこにある raw は、指す項目そのものだけを調べ、そこへの途中のディレクトリは調べない。記録にあれば、途中も調べる。
- **未確認の判定。** マウントしたフォルダー、クラウドの置き換え、WSL のシンボリックリンクの判定は、試験で確かめるまで未確認である。


## OneDrive を調べた記録（作者の決定の 7 の判断の 7）

   - **調べたこと（2026年11月16日）。** 作者の PC（Windows 11、Python 3.14.6）の OneDrive のフォルダーで、`os.walk()` で 20,008 項目、`os.scandir()` で 20,001 項目を、読むだけで調べた。オンライン専用のプレースホルダー（`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`）は 14,033 項目（`scandir` では 7,350 項目）あったが、`os.lstat()` にも `DirEntry.stat()` にも、`FILE_ATTRIBUTE_REPARSE_POINT` は 1 つも出なかった。`is_junction()` と `is_symlink()` も、どれも偽だった。クラウドのファイルの API が、プレースホルダーのリパースポイントを、ふつうのプロセスに見せていないためと考えられる（理由は確かめていない）。
   - **意味。** この PC では、`Writer` と同じくすべてのリパースポイントを拒んでも、名前の代理だけを拒んでも、OneDrive の中の wiki の書き込みは止まらない。どちらを選んでも、ADR-0023 を変えずに済む。ほかの同期の道具（Dropbox、Google ドライブなど）と、プレースホルダーを見せる設定のプロセスでは、確かめていない。そこで「見直す条件」に、同期の道具の中の wiki で書き込みが止まると分かったときを足した。
