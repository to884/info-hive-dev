## 作者の判断（2026年11月14日）

- 並行して取り込むときは、書く段だけをロックする。確認と記事を書く間は、ロックを持たない。
- 書く時間を短くするため、決まった処理はモデルを使わず、Python で行う。
- 書き込みは、差分のパッチを当てるか、Python で書くかを、場合によって使い分ける。パッチが競合したら、モデルが直す。
- Claude Code のツールを通らない書き手（エディター、Codex、ほかのスクリプト）の変更は考えない。

## 解決したい問題

今の取り込み（Web ページ、PDF、セッション）と `/wiki:query`、`/wiki:learn` の保存は、モデルが Edit と Write で、要約ページ、関連ページ、`index.md`、`log.md` を書く。Edit は「読む、直す、書く」で原子的ではなく、2 つの書き込みが数ミリ秒の中で重なると、行が黙って消える。lint は、索引に足りない項目と、ログの抜けを見つけない。

## 4 回目のレビューで崩れた前提

| 指摘 | 崩れた前提 |
| --- | --- |
| 重大 1: 別の節の同じ文を「当て済み」の証拠にする | 今の中身を探せば、変更が当たったかどうかが分かる |
| 重大 2: ブロックの重複の判定が、足す先の節に結びついていない | ブロックがファイルのどこかにあれば、目的の追記は済んでいる |
| 重大 3: 同じファイルへの複数の変更を、それぞれ元の中身から作り、後の変更が先の変更を消す | 変更は互いに独立していて、1 つずつ当てればよい |
| 重大 4: `append` の足す先の見出しが、承認のハッシュに入っていない | 承認のハッシュの項目を列挙すれば、適用の意味がすべて縛られる |
| 重大 6: 作業用のフォルダーそのものがリンクだと、確認の前の記事が raw の側に保存される | 作業用のパスの字面が wiki の中なら、保存先も wiki の中である |
| 重大 7: ロックのファイルを変更の対象にでき、POSIX では自分のロックを壊せる | ロックのファイルは、適用の間ずっと同じ実体である |

重大 1〜3 は、どれも「済んだかどうかを、今の中身からあとで推す」作りから出た。これは、セッションの取り込みの 1〜3 版目の却下に共通した原因（状態をあとから推す）と同じ形である。

## 方針

設計の本体を書くときの出発点である。どれもレビューを受けていない。

- **済んだかどうかを、中身から推さない。** 変更ごとに、用意したときの行き先のハッシュ（前）と、当てたあとのハッシュ（後）を、作業用のフォルダーの日誌に書く。当てるときは、今のハッシュが「前」なら書き、「後」なら済み、どちらでもなければ競合にする。3 方向の当て方と、「当て済み」の推定はやめる。
- **同じファイルへの変更を、1 つにまとめる。** 計画はファイルごとに、最後の中身を 1 つだけ持つ。同じファイルに 2 つの変更を登録したら、先の結果を次の入力にして、用意するときにまとめる。
- **決まった追記は、ロックの中で今の中身から作り直す。** 索引の節の末尾とログの末尾への追記は、ロックを取ってから、今の中身に対して Python で計算する。これは推定ではなく、決まった操作なので、ほかの取り込みが先に書いていても競合にならない。足す先の節は、見出しの行と、その出現の順番で決め、計画のハッシュに入れる。
- **計画のハッシュは、計画の全体を正規化した JSON から作る。** 項目を列挙しない。
- **作業用のフォルダーとロックのファイルは、作る前に実体を検査する。** リンクとジャンクションを拒み、実体が raw のルートの中なら拒み、Git の作業ツリーの中なら、無視されることを確かめる。`.wiki-cache/` の下は、変更の対象にできない。
- **伏せた文字列の検査は、セッションの取り込みの `scan` を使う。**
- **raw の置き場所の全体を守る。** セッションの取り込みの設計の 5 回目から 7 回目のレビューは、wiki の書く先が別名（リンク、ジャンクション、bind mount、UNC の共有）で raw に届くこと、過去に取り込んだ別の raw が書き換えられること、raw のルートをほかの道具が消すディレクトリ（MCP の索引のディレクトリなど）に置けることを挙げた。どれも Web ページの raw にも共通する。パスで重なりを証明する検査は尽くせないので、書く段では、書く先ごとに、書く直前に行き先のファイルの識別子（`st_dev` と `st_ino`、Windows のファイルの ID）を、raw のルートの中のファイルの識別子と照らす形を検討する。
- **raw のルートの役割を確かめる。** raw のルートが、wiki のルート、`.wiki-cache`、MCP の索引のディレクトリ、rag の派生データと重ならないことを、作業領域の設定（ADR-0008）と照らして確かめる。
- **移す順番。** セッションの取り込み、Web ページと PDF の取り込み、`/wiki:query` と `/wiki:learn` の保存の順に移す。すべて移るまで、移っていない書き手との競合は残る。

## 次にすること

- 決まったら、ADR に残す。
