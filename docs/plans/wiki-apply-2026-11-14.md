## 作者の判断（2026年11月14日）

- 並行して取り込むときは、書く段だけをロックする。確認と記事を書く間は、ロックを持たない。
- 書く時間を短くするため、決まった処理はモデルを使わず、Python で行う。
- 書き込みは、差分のパッチを当てるか、Python で書くかを、場合によって使い分ける（両方を使ってもよい）。パッチが競合したら、モデルが直す。

「作者が決めること」の表に、作者が答えた。表の各行に、その答えを書いた。要点は次のとおりである。

## 解決したい問題

今の取り込み（Web ページ、PDF、セッション）と `/wiki:query`、`/wiki:learn` の保存は、モデルが Edit と Write で、要約ページ、関連ページ、`index.md`、`log.md` を書く。Edit は「読む、直す、書く」で原子的ではなく、2 つの書き込みが数ミリ秒の中で重なると、行が黙って消える（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md) の試験 4）。lint は、索引に足りない項目と、ログの抜けを見つけない。

## 取り込みの設計の 4 回目のレビューで崩れた前提

| 指摘 | 崩れた前提 |
| --- | --- |
| 重大 1: 別の節の同じ文を「当て済み」の証拠にする | 今の中身を探せば、変更が当たったかどうかが分かる |
| 重大 2: ブロックの重複の判定が、足す先の節に結びついていない | ブロックがファイルのどこかにあれば、目的の追記は済んでいる |
| 重大 3: 同じファイルへの複数の変更を、それぞれ元の中身から作り、後の変更が先の変更を消す | 変更は互いに独立していて、1 つずつ当てればよい |
| 重大 4: `append` の足す先の見出しが、承認のハッシュに入っていない | 承認のハッシュの項目を列挙すれば、適用の意味がすべて縛られる |
| 重大 6: 作業用のフォルダーそのものがリンクだと、確認の前の記事が raw の側に保存される | 作業用のパスの字面が wiki の中なら、保存先も wiki の中である |
| 重大 7: ロックのファイルを変更の対象にでき、POSIX では自分のロックを壊せる | ロックのファイルは、適用の間ずっと同じ実体である |

重大 1〜3 は、どれも「済んだかどうかを、今の中身からあとで推す」作りから出た。これは、セッションの取り込みの 1〜3 版目の却下に共通した原因（状態をあとから推す）と同じ形である。この設計は、次の 3 つの構造で、推す箇所をなくす。

1. **済んだかどうかは、日誌だけで決める。** 書く前に、書くファイルごとの「前」と「後」のハッシュと、置く中身を、PC に 1 つの日誌に書く。日誌のない状態で、今の中身から「当て済み」を推すことはしない。
2. **前に進めるだけで、推して当てない。** モデルが直したページは、ファイルの全体が用意したときの中身（前）と同じときだけ置き換える。違えば競合にして、モデルが直す。差分の塊を今の中身に合わせて当てる処理はない。
3. **よく重なるファイルには、決まった操作だけを使う。** 索引とログへの追記は、ロックの中で、今の中身に対して Python で計算する。足す先は、見出しの行と出現の順番で決め、計画に入れる。

## 前提にすること

- **Claude Code のツールを通らない書き手は考えない**（作者の判断の 4）。
- **ロックは wiki ごとに 1 つで、その wiki に書く書き手の間だけで効く。** ロックの場所は wiki のパスだけで決まり、プロセスの環境によらない（1 節）。
- **書く段に移っていない書き手は、ロックに加わらない。** 移る順番（12 節）の途中と、10 節の表で「残す」とした手順では、モデルが Edit と Write で wiki を直接書く。その書き込みと、書く段の書き込みが数ミリ秒の中で重なれば、今と同じく行が消えうる（「保証しないこと」の 2）。移っていない書き手が先に書いた変更は、書く段から見ると「用意したあとにほかが書き換えた」ことになり、モデルが直したページなら競合、決まった操作なら今の中身に足すので、どちらも黙って消さない。
- **raw のファイルは、この道具の書き込みの対象にしない。** raw を書くのは、Web ページの `wiki_fetch.py` と `wiki_rawcheck.py`、セッションの `wiki_session.py write`、PDF の rag、経験の `wiki_evolve.py capture` である。この道具は、自分のすべての書き込み（日誌と一時ファイルを含む）の道に別名がないことと、根が raw のルートに重ならないことで、raw に入らないことを示す（7 節）。
- **wiki のファイルは UTF-8 である。** UTF-8 として読めないファイルは書かない（競合として返す）。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| raw の書き込み | raw の書き手は別にある。この道具は raw の側に書かないことを確かめるだけである |
| ページの削除と名前の変更 | 取り込みと保存の手順では使わない。lint の直し（分割、統合、名前の変更）で要るので、別に決める（10 節の表で「残す」） |
| 意味の重複の検出 | 同じ概念を別のスラッグで作ることは防がない |
| グラフの DB の書き込み | `wiki_graph_extract.py` が既存のロック（`.extract.lock`）で書く |
| ページの中身の正しさ | 書く段は、承認された中身をそのまま置く。中身の検査は、ページの frontmatter が読めること（5 節）だけである |
| 複数の PC から同時に書くこと | 同期のツール（OneDrive、Dropbox など）で共有した wiki では、ロックのファイルが PC ごとに作れてしまう（「保証しないこと」の 6） |

## 全体の流れ

| 段 | する人 | 中身 | ロック |
| --- | --- | --- | --- |
| P1 始める | スクリプト | `begin` が、利用者のデータのディレクトリに作業用のフォルダーを作り、計画の識別子（`plan_id`）と、wiki と raw のルートを計画に書く | 持たない |
| P2 用意する | モデルとスクリプト | 新しいページを `new` で、直すページを `edit` で、索引とログの行を `index-add` と `log-entry` で登録する。モデルは作業用のフォルダーの写しだけを Write と Edit で書く | 持たない |
| P3 見せる | スクリプトとモデル | `diff` が計画を検査し、差分と `plan_sha256` を出す。セッションの取り込みでは、ここで `scan` を流す（10 節）。モデルは差分をユーザーに見せ、承認を得る | 持たない |
| P4 当てる | スクリプト | `apply --expect-sha256` が、wiki のロックを取り（3 分まで待つ。待ちきれなければ差分を置いて誤り）、その wiki に残った日誌を前に進め、計画を検査し、日誌を書いてから置き換える | 持つ（短い区間だけ） |
| P5 直す | モデルとスクリプト | 競合なら、`rebase` で用意し直し、P3 からやり直す | 持たない |
| P6 仕上げ | モデルとスクリプト | グラフの lint と抽出のあと、ログのグラフのサブ行を、もう 1 回の P1〜P4 の `log-sub` で書く | P4 だけ |

## 決めること

### 1. ロック、管理領域、書き込みの入口（`wiki_fsguard.Writer`）

**ロックは wiki（プロジェクト）ごとに持つ（作者の判断、2026年11月15日）。** ロック、日誌、待ちきれなかった計画の差分は、wiki の中の `.wiki-cache` の下に置く。モデルが記事の案を書く作業用のフォルダーだけは、wiki と Git の外の、利用者のデータのディレクトリに置く。

```text
W/.wiki-cache/apply/apply.lock                  ロック（下）。その wiki への書き込みは、これ 1 つを取る
W/.wiki-cache/apply/journal/<plan_id>/          日誌（6 節）。その wiki の日誌だけを置く
W/.wiki-cache/apply/journal/discarded/<plan_id>/ 捨てた日誌
W/.wiki-cache/apply/applied/<plan_id>.json       当て終えた印（6 節の 9）
W/.wiki-cache/apply/raw-roots.json               その wiki が使った raw のルートの記録（7 節）
W/.wiki-cache/apply-pending/<plan_id>-<16 桁>/    ロックを待ちきれなかった計画の差分（下）
data_dir()/apply/work/<名前>-<乱数>/             作業用のフォルダー D（利用者ごと）
```

以下、`W/.wiki-cache/apply/` を `L`、`W/.wiki-cache/apply-pending/` を `P`、`data_dir()/apply/work/` を `K` と書く（`data_dir()` は `wiki_mcp_common.data_dir()`）。

- **同じ wiki の書き手は、同じロックを取る。** ロックの場所は wiki のパスだけで決まり、プロセスの環境変数（`INFO_HIVE_DATA_DIR` など）によらない。そのため、環境の違う 2 つのセッションも、同じ wiki に書くときは同じロックを取る（8 回目の重大 1 は、この作りでは起きない）。ほかの利用者のアカウントや、ネットワークのドライブの上の wiki を共有するほかの PC も、ロックのファイルを重ねて作れないファイルシステムなら、同じロックを取る。
- **入れ子の wiki。** 親の wiki の計画から子の wiki のファイルは書けない（3 節。3 回目の重大 1）ので、wiki のどのファイルも 1 つの wiki にだけ属し、1 つのロックで守られる。
- **wiki の間の別名。** 2 つの wiki の間に bind mount などの別名があり、同じファイルを 2 つの wiki のパスから書けるときは、2 つのロックが同じファイルを守れない（「保証しないこと」の 12）。
- **Git の無視。** `.wiki-cache` には、ロックと日誌（当てる前と後の中身）と差分が入る。`begin` と `apply` は、wiki のルートかその祖先に `.git`（ディレクトリかファイル）があれば、`git -C <W> check-ignore -q <W>/.wiki-cache/apply/` と `git -C <W> check-ignore -q <W>/.wiki-cache/apply-pending/`（末尾の `/` で、ディレクトリとして問う）が成功し、`git -C <W> ls-files -- .wiki-cache/apply .wiki-cache/apply-pending` が空であることを確かめる。Git は、無視されたディレクトリの下のファイルを、否定の規則（`!`）でも戻せないので、ディレクトリが無視されれば、その下の日誌と差分も無視される（11 回目の重大 5）。`git` を実行できないときも止める（終了コード 1、`cache_not_ignored`）。`.wiki-cache/.gitignore` がない古い wiki では、`init_wiki.py` と同じ中身（`assets/wiki-cache_gitignore.template`）で作ってから確かめる。作業用のフォルダー `D` も、その祖先に `.git` があれば（`INFO_HIVE_DATA_DIR` で作業ツリーの中に置いたなど）、`D` をディレクトリとして `git check-ignore` にかけ、無視されなければ作らずに止める（`work_not_ignored`）。

**ロックの作り（作者の判断、2026年11月15日）。** ロックは、プロセスが落ちても残るファイルにし、利用者がコマンドで明示して外す。

- **取る。** 持ち主の情報（`lock_id`（`secrets.token_hex(16)`）、`plan_id`、プロセスの番号、ホスト名、取った時刻、wiki のルート、raw のルート）を、`L` に一時ファイルとして書いて fsync し、`L/apply.lock` へ重ねて書かない形で置く（POSIX は `os.link` のあとに一時ファイルを消す。Windows は `os.rename` で、行き先があれば `FileExistsError`）。置けたら取れた。完成したロックのファイルだけが名前を持つので、取る途中で止まっても、ロックは「ない」か「持ち主の情報が読めるもの」のどちらかである。置いたあと、持ち主はそのファイルを開いたままにし、OS のロックをかける。POSIX は `fcntl.flock`（ファイルの全体への助言のロックで、ほかのプロセスの読み取りを妨げない）、Windows は、ファイルの中身より後ろの決まった位置（先頭から 2^30 バイト目）の 1 バイトへの `msvcrt.locking` である（Windows のバイトの範囲のロックは、ロックした範囲の読み取りを、ほかのプロセスに対して拒む。中身の後ろにかければ、持ち主の情報は誰でも読める。11 回目の重大 4）。この OS のロックは、持ち主が生きているかを `unlock` が知るための印で、排他そのものはファイルがあることで決まる。
- **待つ。** ロックのファイルがあれば、0.2 秒ごとに取り直し、`--wait` 秒（既定 180 秒、つまり 3 分）で諦める。諦めたときは、下の「待ちきれなかったとき」に従う。
- **外す。** 持ち主は、OS のロックを外してファイルを閉じ、ロックのファイルを読み直して、`lock_id` が自分のものであることを確かめてから消す。自分のものでなければ（`unlock` で外されたあと、ほかの書き手が取った）、消さない。
- **待ちきれなかったとき。** ロックを取れずに `--wait` 秒が過ぎたら、計画の差分を `P/<plan_id>-<plan_sha256 の先頭 16 桁>/`（以下 `P/<差分の名前>`）に置き、何も書かずに、終了コード 4 の誤りにする（作者の判断）。
  - 置くものは、`plan.diff`（`diff` が出すものと同じ統一差分）と `pending.json`（`plan_id`、`plan_sha256`、`D` のパス、wiki と raw のルート、置いた時刻、待っていたロックの持ち主の情報）である。2 つは組として置く（12 回目の重大 3）。置く前に、記録とページから守る raw のルートを作り直し、根の重なりと、`P` までの道に別名がないことを確かめる（14 回目の重大 3。ロックを持たないので 1c を通らないが、守りは道の別名で決まる。7 節）。`P/.tmp-<乱数>/` に 2 つを書いてそれぞれ fsync し、ディレクトリを同期してから、そのディレクトリを `P/<差分の名前>` へ、重ねて書かない形で名前を変える（POSIX も Windows も、行き先のディレクトリがあれば名前の変更は失敗する）。失敗したら（同じ中身の差分がすでにある）、一時のディレクトリを消す。名前は中身のハッシュを含むので、同じ `plan_id` でも、待つ間に `D` を変えた計画は、別の差分として残る。差分は承認された中身なので、作業用のフォルダーが消えても、利用者はこのファイルを読んで、何を書こうとしていたかを確かめられる。
  - 差分を置いたあと、`P` の下の計画の数を数える。**5 件以上なら、`pending_alert` を出す。** モデルは、それをユーザーに伝え、状態（残っているロックとその持ち主、たまった差分）を確かめてもらう（作者の判断）。`apply` と `begin` は、`P` に 5 件以上あれば、いつでも同じく `pending_alert` を出す。
  - 待ちきれなかった計画は、作業用のフォルダー `D` が残っていれば、同じ `apply` をやり直して当てられる。ロックの中で当て終えたと分かったら（9 と、3 の `already_applied`）、`apply` は、同じ `plan_id` で同じ `plan_sha256` の差分 `P/<差分の名前>` を消す（同じ `plan_id` の、違うハッシュの差分は残す。当たらなかった中身だからである）。ロックの前の 0 で `already_applied` と分かったときは消さない。`wiki_apply.py pending --wiki <W> [--show | --discard <差分の名前>] [--raw-root <R>]` で、たまった差分を見せ、要らないものを消す。`P/.tmp-*` の残り（組を置く途中で止まったもの）は、`pending --show` が見せ、`pending --discard` で消せる。
- **明示して外す（`wiki_apply.py unlock --wiki <W> [--lock-id <id>] [--force]`）。** 利用者が、残ったロックを外すための操作である（作者の判断）。
  - `--lock-id` を付けないと、ロックの持ち主の情報と、持ち主が生きているか（ロックのファイルの OS のロックを、待たずに取れるか）を見せるだけで、何も消さない。
  - 消すときの `Writer` は、ロックの中身の raw のルートで作る。中身が読めない（壊れた）ときは、`--raw-root <R>` を求める（11 回目の重大 3）。
  - `--lock-id` を付けると、今のロックの `lock_id` がそれと同じで、持ち主が生きていないときだけ、ロックのファイルを消す。別の `lock_id` なら（見たあとに持ち主が変わった）、消さない。
  - 持ち主が生きているときは、`--force` を付けたときだけ消す。持ち主がまだ書いている途中なら、2 つの書き手が並びうる（「保証しないこと」の 13）。Windows では、持ち主がファイルを開いたままなので消せず、`--force` でも外せない（持ち主のプロセスを止めてから外す）。
  - 外したあと、次にロックを取った書き手は、6 節の 2 で、その wiki に残った日誌を前に進めてから、自分の計画を書く。落ちた持ち主の書きかけは、ここで最後まで進むか、戻される。

**ロックが生む失敗の形。** 作者の判断で選んだ「残るロックのファイル」は、OS のロック（プロセスが落ちれば OS が外す）にはなかった、次の失敗の形を生む。

| 失敗の形 | 起きる条件 | 扱い |
| --- | --- | --- |
| ロックが残る | 持ち主が落ちた（電源が切れた、強制終了した） | ほかの書き手は 3 分待って差分を `P` に置き、終了コード 4 で止まる。利用者が `unlock` で外すまで、その wiki には誰も書けない。外したあと、次の書き手が日誌を前に進める |
| 差分がたまる | ロックが残ったまま、取り込みが続く | 5 件以上で `pending_alert` を出し、利用者に状態を確かめてもらう。差分は消えないので、`unlock` のあとに、残った作業用のフォルダーから当て直すか、差分を読んで新しい計画にする |
| 生きている持ち主のロックを外す | 利用者が `unlock --force` を使った（POSIX） | 2 つの書き手が並びうる。持ち主が日誌を書いたあとなら、ハッシュが合わなくなった項目は `stuck` になるが、持ち主が日誌を書く前なら、両方の計画が成功を返し、一方の変更が黙って消えうる（11 回目の軽微 1）。`--force` は、持ち主が止まっていることを確かめたときだけ使う（「保証しないこと」の 13） |
| 外す操作と、持ち主が外すことが重なる | 持ち主がファイルを閉じてから消すまでの短い間に、`unlock` が「持ち主はいない」と見てロックを消し、そこへ新しい書き手がロックを取る | 持ち主は、消す前に `lock_id` を読んで確かめるので、新しいロックはふつうは消さない。読むことと消すことの間に、さらに入れ替わると消しうる。持ち主が動いている間に `unlock` を使わない限り起きない（「保証しないこと」の 13） |
| ロックのファイルが読めない | 道具の外で壊された（エディターで開いて保存した、同期のツールが途中まで写した） | 読めないロックも「ある」として待つ。`unlock` は、`--lock-id` なしに `--force` を付けたときだけ消す |
| 同期のツールが、2 台の PC で別々にロックを作る | OneDrive や Dropbox で同期した wiki に、2 台から同時に書く | ロックのファイルは PC ごとに作れてしまい、あとで同期の衝突になる。複数の PC から同時に書くことは範囲に入れない（「保証しないこと」の 6） |
| `.wiki-cache` を消す | 利用者がキャッシュを片付けた | ロック、日誌、差分が消える。持ち主が動いていれば、ロックが消えて並びうる。日誌が消えると、書きかけを前に進められない。書く段に加わらない書き手の操作として扱う（「保証しないこと」の 12） |

**この直しが生む失敗の形（13 版目）。** 11 回目の直しは、次の失敗の形を生む。

| 失敗の形 | 起きる条件 | 扱い |
| --- | --- | --- |
| 当て終えた印がたまる | 取り込みのたびに `L/applied/` に 1 件増える | 1 件は数百バイトである。消さない（消すと、`--keep` で残した計画を 2 回当てうる）。`.wiki-cache` を消すと印も消える（「保証しないこと」の 12） |
| 管理領域に知らないものがある | 利用者や別の道具が `.wiki-cache/apply` の下にファイルを置いた。将来の版の道具が、新しい形のファイルを置いた | `unknown_in_cache` で止まる。新しい形を足すときは、決まった形の一覧と試験を一緒に直す |
| `.gitignore` がファイルだけを無視する | 利用者が `.wiki-cache/.gitignore` を `*.json` のように書き換えた | ディレクトリが無視されないので `cache_not_ignored` で止まる。案内に、テンプレートの中身（`*` と `!.gitignore`）を出す |
| 作業用のフォルダーが Git の中で無視されない | `INFO_HIVE_DATA_DIR` を作業ツリーの中にした | `begin` が `work_not_ignored` で止まる。利用者が `INFO_HIVE_DATA_DIR` を直すか、そのディレクトリを無視する |
| ロックが壊れて raw のルートを読めない | 道具の外でロックが壊された | `unlock --force --raw-root <R>` で消す。利用者が raw のルートを知っている必要がある |
| 中身の後ろへのロックを、ファイルシステムが受けない | ネットワークのドライブなどで、ファイルの終わりより後ろのバイトのロックを拒む | 持ち主の生死が「不明」になり、`unlock` は `--force` のときだけ消す（「まだ確かめていないこと」） |

**`Writer` を作る操作と、raw のルート。** `Writer` は、根の重なりの検査（7 節）に、守る raw のルートを要するので、`Writer` を作る操作は、どれも raw のルートを、次の表の読み元から読む（11 回目の重大 3、12 回目の重大 4）。守る raw のルートは、ここで読んだ raw のルートと、wiki の raw のルートの記録と、ページから引かれる raw の和である（7 節。13 回目の重大 2、14 回目の重大 1、2）。読み元から読めないときは、利用者が渡す `--raw-root` を求め、なければ書かずに終了コード 1 にする。

| 操作 | raw のルートの読み元 | 読めないとき |
| --- | --- | --- |
| `begin`、`diff`、`apply`（と、`apply` の中の日誌の片付け、`P/.tmp-*` の片付け） | 計画（`D/plan.json` か、ライブラリの `Plan`） | — |
| 日誌を前に進めること、戻すこと | 日誌の `manifest.json`。守る raw のルートは、0 で作った和に、日誌の raw のルートを足したもの | 日誌を `stuck` にする |
| `recover` | 扱う日誌の `manifest.json` | `--raw-root` |
| `unlock` | ロックの中身 | `--raw-root`（壊れたロック） |
| `pending` | 差分の `pending.json` | `--raw-root`（`P/.tmp-*` の残り、壊れた記録） |
| `abort`、`list` | 計画（`abort`）。`list` は書かない | `--raw-root`（`plan.json` の壊れた `D`） |
| `raw-roots` | 記録と、`--add` で渡した raw のルート | — |

**書き込みの入口を 1 つにする。** `wiki_apply.py` が行うすべての書き込み（ディレクトリを作る、ファイルを作る、置き換える、消す、ロックのファイルを置く）は、`wiki_fsguard.Writer` のメソッドを通る。`Writer` は、計画の wiki のルート `W`、`L`、`P`、`K`、守る raw のルートと wiki の中の raw のパス、`W` と `K` の下の mount point の一覧（7 節）を持つ。書き込みは「ページの書き込み」「wiki の管理の書き込み」「作業用の書き込み」に分かれ、書き込みのたびに、対象のパス `p` について次を確かめる。1 つでも通らなければ、書かずに `Refused` を送出する（終了コード 1）。

| 検査 | ページの書き込み（`W` の中、`.wiki-cache` の外） | wiki の管理の書き込み（`L` と `P` の中） | 作業用の書き込み（`K` の中） |
| --- | --- | --- | --- |
| a. 途中の要素 | `W` から `p` の親までの、すでにある要素のどれもが、リンクでも再解析点（ジャンクションなど）でもない（`os.lstat()` で、`S_ISLNK` と `FILE_ATTRIBUTE_REPARSE_POINT` を見る。`wiki_browse_fs._is_link()` と同じ判定）。`p` そのものがすでにあれば、それもリンクでも再解析点でもない | `W` から `p` の親までについて、同じ（`.wiki-cache` そのものも含む） | `K` から `p` の親までについて、同じ |
| b. 輪 | `W` の子から `p` の親までの、すでにある要素（`W` 自身は含めない）の実体（`st_dev`、`st_ino`）が、互いに、また `W` とその祖先の実体と、どれも違う（bind mount で `W/indexes` が `W` を指す配置を止める） | 同じ | `K` の子から `p` の親までについて、同じ |
| c. raw | 書く先が、wiki の中の raw（ページの `raw:` が `W` の中を指すパス）と同じでなく、その下でない（7 節。`casefold()` と NFC で比べる） | 同じ（`.wiki-cache` の下を指す `raw:` は始めに止めるが、ここでも当てる。15 回目の重大 3） | 同じ（`K` の下を指す `raw:` は根の重なりで止まるが、ここでも当てる） |
| d. 領域 | `p` の親の実体の祖先の並びに `W` の実体があり、`.wiki-cache` の実体がない | `p` が、`W/.wiki-cache` からの相対パスで、次の決まった形のどれかである（11 回目の重大 2）。`.`（`.wiki-cache` 自身）、`.gitignore`、`apply`、`apply/apply.lock`、`apply/.lock.<乱数>.tmp`、`apply/journal`、`apply/journal/<plan_id>` とその下、`apply/journal/discarded`、`apply/journal/discarded/<plan_id>` とその下、`apply/applied`、`apply/applied/<plan_id>.json`、`apply/applied/.<plan_id>.<乱数>.tmp`、`apply/raw-roots.json`、`apply/.raw-roots.<乱数>.tmp`、`apply-pending`、`apply-pending/<plan_id>-<16 桁>` とその下、`apply-pending/.tmp-<乱数>` とその下。そのうえで、`.wiki-cache` 自身なら親の祖先の並びに `W` の実体があり、ほかは親の祖先の並びに `W/.wiki-cache` の実体がある。**`W/.wiki-cache` から `p` までの段**（`.wiki-cache` 自身を含み、`W` を含まない。`p` がすでにあるディレクトリなら `p` 自身も含む）が、どれも e を満たす（mount point でない。`.wiki-cache/apply/journal` が `W/sources` の bind mount なら止まる。2 回目の重大 4 と同じ形。12 回目の重大 2） | `p` が `K` 自身か、`K/<名前>-<乱数>` とその下である。`K` 自身なら親の祖先の並びに `data_dir()` の実体があり、ほかは親の祖先の並びに `K` の実体がある。どちらも `W` の実体がない。`K` から `p` までの段（`K` 自身を含む。`p` がすでにあるディレクトリなら `p` 自身も含む）が、どれも e を満たす。`K` が `W` と守る raw のルートに重ならないことは、根の重なりの検査（7 節）で確かめる |
| e. mount point | `W` の子から `p` まで（`p` がすでにあるディレクトリなら `p` 自身も）の、すでにあるどのディレクトリも mount point でない（7 節。`st_dev` が親と違う、Linux では `/proc/self/mountinfo` にある）。`W` そのものが mount point なのはよい（15 回目の軽微 1） | 同じ（`W` の子から） | `K` の子から `p` まで、同じ |

**管理領域を作るとき。** `W/.wiki-cache`、`L`、`L/journal`、`L/applied`、`P`、`K` とその祖先（`data_dir()` まで）がなければ、`Writer.bootstrap()` が、上から 1 段ずつ `os.mkdir()` で作り、作ったあとに、その段がリンクでも再解析点でも mount point でもないことを確かめる。d の「祖先の並びに `L`、`P`、`K` の実体がある」は、それらができてからの書き込みに当てる（2 回目の重大 5）。

**管理領域の確かめ。** `begin`、`diff`、`apply`、`recover`、`unlock`、`pending` は、最初に、`W/.wiki-cache`、`L`、`L/journal`、`L/applied`、`P`、`K` と、そこに今ある子のディレクトリを、a〜d で確かめる。根（`.wiki-cache`、`L`、`P`、`K`）も、d の決まった形に入るので、同じ規則で確かめる（4 回目の軽微 2 と 11 回目の重大 2）。決まった形にないものが `.wiki-cache/apply` か `.wiki-cache/apply-pending` の下にあれば、終了コード 1（`unknown_in_cache`）にする（道具が作らないものが、管理領域に紛れ込んでいる）。`.wiki-cache` の直下のほかのもの（検索のキャッシュ、取り込みの作業用の写し）は、ほかの道具のものなので見ない。

**作業用のフォルダー（`begin`）。** `wiki_apply.py begin --wiki <W> --raw-root <R> --name <名前>` は、`K/<名前>-<乱数>/`（以下 `D`）を作り、そのパスを出す。`<名前>` は `wiki_fetch.check_slug()` で検査する。次も確かめ、通らなければ作らない（作ったあとなら消す）で、終了コード 1 にする。

- wiki が初期化されていること（`wiki_initialized.require_or_exit()`）。
- raw のルートが 7 節の `raw_root_problem()` を通ること。
- `.wiki-cache` が Git で無視されること（上）。
- `W` と `K` の下に mount point がないこと、守る raw のルート（計画、記録、ページの `raw:` から作る）と、`W`、`W/.wiki-cache`、`K` が重ならないこと（7 節。`D` を作る前に確かめる。14 回目の重大 2）。

`begin` は、渡された `--wiki` のパスで初期化を確かめたあと、`os.path.realpath()` で解いたパスを `W` にし、`W` でもう一度初期化を確かめる（`wiki_initialized.resolve()` と同じ順。`os.path.abspath()` は使わない。リンクのあとの `..` を字面で消すと、確かめた wiki と違う wiki を指すため。4 回目の重大 1）。`--raw-root` も同じに `realpath()` で解いて `R` にし、`raw_root_problem()` を `R` で確かめる。`begin` は、`D/plan.json` に、計画の識別子 `plan_id`（`secrets.token_hex(16)`）と、`W` と `R`（`/` 区切り）を書き、`W` と `R` を出力にも出す（モデルが、ユーザーに見せる差分の見出しに書く）。`P` に 5 件以上あれば、`pending_alert` も出す。`D` の中身は次のとおりである。`plan.json` を書くのはスクリプトだけで、モデルが書くのは `new/` と `edit/` の下だけである。

```text
D/plan.json          計画（スクリプトだけが書く）
D/new/<相対パス>      新しいページの中身（モデルが Write で書く）
D/base/<相対パス>     直すページの、用意したときの中身（スクリプトが写す。モデルは触らない）
D/edit/<相対パス>     直すページの新しい中身（スクリプトが写し、モデルが Edit で直す）
D/rejected/<相対パス>.diff   競合で用意し直す前の差分（8 節）
```

モデルが Write と Edit で `D` に書く間は、`Writer` を通らない。`D` を作ったあとに、その途中の段をリンクに差し替えることは、書く段に加わる書き手にはできない（`Writer` はリンクを作らない）。加わらない書き手の差し替えは考えない（作者の判断の 4）。`diff` と `apply` は、`D` を読む前に、管理領域の確かめをやり直す。

### 2. 変更の種類と、使い分け

計画の項目は、wiki のファイル 1 つにつき 1 つである。同じファイルに 2 つの項目は作れない（3 節）。項目の種類は 3 つある。

| 種類 | 登録 | 前（用意したときに決める） | 後 | 当て方 |
| --- | --- | --- | --- | --- |
| `new`（新しいページ） | `new --path <P>` | 「ない」 | `D/new/<P>` のバイト列 | 行き先がないときだけ、重ねて書かない形で置く |
| `edit`（モデルが直すページ） | `edit --path <P>` | `D/base/<P>` のハッシュ | `D/edit/<P>` のバイト列 | 今のファイルの全体が「前」と同じときだけ置き換える |
| `ops`（決まった操作） | `index-add`、`log-entry`、`log-sub` | ロックの中で、今のファイルのハッシュ | 今の中身に操作を順に当てた結果 | ロックの中で計算して置き換える |

使い分けは次のとおりである。

| 書く場所 | 種類 | 理由 |
| --- | --- | --- |
| ソースの要約ページ、新しいエンティティとコンセプトのページ、シンセシス、経験のパターン | `new` | 中身の全体をモデルが書く |
| 既存のエンティティとコンセプトのページ（関連ページ）、`SCHEMA.md` のタグの体系 | `edit` | 場所も中身も決まっていないので、モデルが直し、差分を見せる |
| `index.md`、分割した索引（`indexes/<種類>.md`）への項目の追記 | `ops`（`index-add`） | 2 つの取り込みがほぼ同じ場所に足すので、パッチにすると毎回競合する |
| `log.md` の項目 | `ops`（`log-entry`） | 末尾に足すだけである |
| `log.md` のグラフのサブ行 | `ops`（`log-sub`） | 1 回目の適用が返した項目の識別に足す |

作者の判断の 3 の「パッチ」は、`edit` のことである。モデルは写しを Edit で直し、スクリプトは差分を見せ、当てるときは、ファイルの全体が用意したときと同じであることを確かめてから置き換える。差分の塊を今の中身に合わせて当てる（3 方向の当て方）ことはしない。そのため、同じページの別の箇所を 2 つの取り込みが並べて直すと、後の側は競合になり、用意し直しと承認のやり直しが要る。関連ページの直しは、取り込みごとに違うページに当たることが多いので、この費用を取る（「作者が決めること」の 1）。

`edit` の項目と `ops` の項目を、同じファイルに作ることはできない。`index.md` の中身をモデルが直したいとき（項目の要約の書き直し、索引の分割）は、`edit` だけにし、追記もその中で行う。

### 3. パスの規則と、同じファイルの判定

`--path` は wiki のルートからの相対パスで、`/` で区切る。次をすべて満たさなければ、登録を拒む（終了コード 1）。

- 各要素が空でなく、`.` と `..` でなく、`.` で始まらない（`.wiki-cache`、`.evolution`、`.git` を指せない）。
- 各要素が、空白か `.` で終わらず、`:`、`\`、制御文字、`<>"|?*` を含まず、Windows の予約名（`CON`、`NUL`、`COM1` など、拡張子つきを含む）でない。`~` のあとに数字が続く要素（8.3 の短い名前の形）を含まない。
- 文字列が NFC で正規化されている（NFD の入力は拒む。macOS の日本語のファイル名で、同じファイルを 2 つの字面で指さないため）。
- 各要素は、UTF-8 で 200 バイト以下、UTF-16 で 200 単位以下である（NTFS と ext4 の要素の上限 255 に、一時ファイルと写しの余裕を残す。4 回目の重大 3）。パスの全体は、`W` を含めて、Windows では 32,000 文字より短い（長いパスの接頭辞 `\\?\` を使う前提。実装で確かめる）。
- 最後の要素が `.md` で終わる。**最後でない要素は、`.md` で終わらない**（大文字と小文字によらない）。どの行き先も `.md` で終わり、どの途中の要素も `.md` で終わらないので、ある項目の行き先が、別の項目の途中のディレクトリになることはない（1 回目の重大 6）。
- **名前の決まりは、どれも `casefold()` した名前で比べる**（12 回目の重大 5）。大文字と小文字を区別しないファイルシステム（Windows、macOS の既定）では、`LOG.md` と `log.md` は同じファイルなので、決まりを字面で当てると、別の綴りで決まりをすり抜けられる。下の `.md` の終わり、特別なディレクトリ、`SCHEMA.md`、`log.md`、`index.md`、`indexes`、`schema.md` の予約は、どれも、NFC で正規化して `casefold()` した要素で比べる。
- 最初の要素が、`raw`、`graph`、`assets` でない（`wiki_pages.SKIP_TOP_LEVEL_DIRS` のうち、ページを置かないディレクトリ。`indexes` は索引のために許す）。
- `SCHEMA.md` は `edit` だけで、`log.md` は `ops` だけで受け付ける（`casefold()` して比べるので、`LOG.md`、`Log.md` も `log.md` の決まりに当たる）。`index-add --file` の `index.md` と `indexes/` も同じく比べる。
- **印の名前を予約する。** 最後の要素を `casefold()` して `schema.md` になるパスは、ルートの `SCHEMA.md`（`edit`）のほかは、どの階層でも受けない（`reserved_name`）。`wiki_initialized` は、ディレクトリに `SCHEMA.md` という名前のファイルがあれば中身によらず初期化された wiki とみなし（ADR-0019）、大文字と小文字を区別しないファイルシステムでは `schema.md` も同じ名前になる。そのため、ページの名前でディレクトリを子の wiki に変えられないようにする（7 回目の重大 2）。

  **この直しが生む失敗の形。** (1) 大文字と小文字を区別しないファイルシステム（Windows の NTFS、macOS の既定の APFS）で、すでに `sources/schema.md` のようなページがある wiki では、そのディレクトリが子の wiki とみなされ、そこへの書き込みが `nested_wiki` で止まる。書く段には名前の変更がないので、`diff` と `apply` は、印になったファイルのパスを出し、利用者が名前を変えるよう伝える（「保証しないこと」の 11）。(2) 印の名前を予約するのは `SCHEMA.md` だけである。ADR-0019 が印を変えれば、この規則も変える。
- **行き先は計画の wiki にだけ属する。** 行き先のパスの途中の、すでにあるディレクトリ（`W` そのものは除く）が `SCHEMA.md` を持てば（`os.lstat()` で、ふつうのファイルかリンクかによらず、名前があれば）、拒む（`nested_wiki`）。入れ子の wiki のファイルは、子の wiki を計画の wiki にして書く。登録、`diff`、`apply` の 4 で確かめる（3 回目の重大 1）。

**パスは正規のものだけを受ける。** 登録、`diff`、`apply` の 4 は、行き先のパスについて `Writer` の a と b を確かめる。wiki の中のどの途中の要素もリンクでも再解析点でもなく、どの要素の実体も祖先と同じでないので、パスの字面と、`W` から実体をたどった場所が一致する。`W/indexes -> W` の配置で `indexes/log.md` を登録しても、`indexes` がリンクなので拒み、bind mount なら `indexes` の実体が `W` と同じなので拒む（1 回目の重大 2）。そのため、`SCHEMA.md` と `log.md` の規則を、字面で当てて実体にも当てられる。

**同じファイルの判定。** 2 段で行う。

1. **字面。** 登録のとき、パスを `casefold()` したものを計画のキーにする。同じキーの項目がすでにあれば、`ops` どうしならその項目に操作を足し（下）、ほかは拒む。
2. **実体。** `diff` と `apply` の 4 は、行き先がすでにあるものについて、実体を集め、2 つの項目が同じ実体を指せば拒む（大文字と小文字を区別しないファイルシステム、ハードリンク、wiki の中の 2 つのディレクトリの間の bind mount を経由した別名をここで止める）。行き先がない `new` は、親のディレクトリの実体（なければ、すでにある最も近い祖先の実体と、そこからの残りの要素を `casefold()` したもの）と、`casefold()` した名前の組で比べる。

**同じファイルへの複数の操作。** `ops` の項目は、操作の並び（登録した順）を持つ。当てるときは、今の中身に 1 つ目を当てた結果を 2 つ目の入力にする。索引のソースの節とコンセプトの節に 1 行ずつ足す取り込みは、`index.md` の項目 1 つに 2 つの操作を持つ。後の操作が先の操作を消すことはない（取り込みの 4 回目の重大 3）。

### 4. 決まった操作

どの操作も、ファイルを UTF-8 として読み（BOM があれば外して覚える）、改行で行に分け（CRLF の行が 1 つでもあれば CRLF のファイルとして覚える）、行の並びに操作を当て、覚えた改行と BOM で書き戻す。最後の行は改行で終える。足す行は、1 行で、改行と制御文字を含まないものに限る（登録のときに拒む）。

**見出しと節は、同梱のパーサーで決める。** 本文は、frontmatter を lint と同じ分け方（`wiki_lint.parse_frontmatter_raw()` の `FRONTMATTER_RE`）で分けてから、`wiki_pages.new_parser()`（閲覧、lint、検索と同じ markdown-it-py の設定。HTML は読まない）で読む。見出しの行は、最上位の `heading_open` のトークンの行（`map` の始まり）である。フェンスの中の `## ` の行は、パーサーが見出しにしないので、見出しにならない（閉じの規則もパーサーに従う）。見出しの行を比べるときは、ソースの行の末尾の空白と、BOM を除いた字面で比べる。節は、見出しの行の次の行から、同じか上の段（`h1`〜`hN`）の次の見出しの行の前までである。節の「最後の行」は、節の中の最上位のブロックのうち、最後のものの範囲（`map`）の中の、空でない最後の行である（箇条書きの `map` は、後ろの空の行を含むことがあるため。3 回目の軽微 1）。節にブロックがなければ、見出しのブロックの最後の行（`heading_open` の `map` の終わりの 1 つ前。ATX の見出しなら見出しの行、Setext の見出しなら下線の行）が最後の行である（10 回目の軽微 1）。`--section` で比べる見出しの行は、見出しのブロックの最初の行である。

**当てたあとの構造の確かめ。** 行の番号は比べない。ブロックのトークンの並びで比べる（2 回目の重大 1）。

- **並び（`sig`）。** パーサーの出力のブロックのトークン（`inline` の子は除く）を、`(type, tag, nesting, level, hidden)` の組の列にしたもの。`hidden` を入れるので、詰まったリストが緩いリストに変わる追記も、並びが一致しない。`heading_open` の次の `inline` は、その中身（見出しの文）も組に入れる。
- **あるべき並び。** 操作ごとに、当てる前の並びから、当てたあとにあるべき並びを、下の規則で作る。
- 当てた結果をもう一度読み、その並びが、あるべき並びと一致しなければ、競合（`structure_changed`）にする。足した行の文が、足した先の `inline` の中身の最後の行と一致することも確かめる。
- **インラインの確かめ。** `inline` の子のトークンの並び（`type` と `content`）も比べる（4 回目の軽微 1、5 回目の重大 1）。
  - 比べる子の組は `(type, content, attrs)` である（`attrs` は、リンクの `href` など。6 回目の軽微 1）。
  - パーサーが集めた参照の定義の表（`env` の `references`）を、ラベルごとの `(href, title)` の組の表にして、当てる前と同じであること（足した行が参照の定義になって、既存のリンクの行き先を変えることを止める）。表の `map`（定義の行の番号）は比べない。前に足した行があれば動くので、比べるとふつうの追記まで拒む（7 回目の重大 1）。
  - **比べる値の決まり。** どの比較でも、読み方を決める値（トークンの種類、段、`hidden`、中身、`attrs`、参照の定義の行き先と題）だけを比べ、位置（`map`、行の番号）は比べない。位置の正しさは、「あるべき並び」と、足した行の文が足した先の最後の行と一致することで確かめる。
  - 足した先でない、すべての `inline` の子の並びが、当てる前と同じであること（当てる前と後の `inline` は、ブロックの並びの対応で組にする）。
  - 足した先が既存の段落（`log-sub` で、指した項目に段落があるとき）なら、その段落の子の並びが、当てる前の子の並びに、`softbreak` と、足した行だけを同じパーサーで読んだ子の並びを続けたものであること。
  - 足した先が新しいブロック（`index-add` の項目、`log-entry` の見出しと段落）なら、その子の並びが、足した文（`index-add` は `- ` のあと、`log-entry` の見出しは `## ` のあと、サブ行は字下げを除いたものを改行でつないだもの）だけを読んだ子の並びと同じであること。
  - 「足した行だけを読む」ときは、当てる前のファイルを読んだときの参照の定義の表を入れた `env` で読む（足した行が既存の参照の定義を使うリンクを含むとき、ファイルの中と同じ読み方にするため。8 回目の軽微 1）。
  - 一致しなければ、`structure_changed` にする。バッククォート 1 つの追記で前の行がインラインのコードに入ると、前の子の並びが変わるので一致しない。既存の箇条書きに項目を足しても、前の項目の子の並びは変わらないので通る。

| 操作と足す先 | あるべき並び |
| --- | --- |
| `index-add`。節の最後のブロックが箇条書き（`bullet_list`） | その箇条書きの `bullet_list_close` の前に、項目 1 つの組（`list_item_open`、`paragraph_open`、`inline`、`paragraph_close`、`list_item_close`。段は箇条書きの中のもの）を足したもの |
| `index-add`。節の中身が、置き換えの行だけの段落 | その段落の組（`paragraph_open`、`inline`、`paragraph_close`）を、項目 1 つの箇条書きの組（`bullet_list_open` から `bullet_list_close` まで）に置き換えたもの |
| `index-add`。節が空か、最後のブロックが箇条書きでない | 節の最後のブロックのあと（空なら見出しのあと）に、項目 1 つの箇条書きの組を足したもの。足す行の前に空の行を 1 つ入れる |
| `log-entry` | 並びの最後に、`h2` の見出しの組（`heading_open`、`inline`（見出しの文）、`heading_close`）と、サブ行があれば段落の組 1 つを足したもの |
| `log-sub`。指した項目の見出しのすぐあとに段落がある | 並びが変わらないこと（サブ行は、その段落に続く行として同じ段落に入る） |
| `log-sub`。指した項目に段落がない | 項目の見出しの組のすぐあとに、段落の組 1 つを足したもの |

`~~~` で始まるサブ行は、フェンスの組ができるので、並びが一致しない。`<div>` と `| a |` は、HTML を読まない設定と、区切りの行のない表なので、段落の文として入り、並びは一致する。この 2 つは、文としてそのまま表示されるだけで、ほかのブロックを変えないので、通してよい（2 回目の軽微 3）。

**`index-add --apply-dir D --file <索引のパス> [--section "<見出しの行>" [--nth <k>]] --line "<行>"`**

- `<索引のパス>` は、`index.md` か `indexes/` の下の `.md` である。
- `<行>` は `- [[` で始まる 1 行である。最初の wikilink の行き先（`[[x]]` か `[[x|表示]]` の `x`）を、項目の行き先とする。
- `--section` があれば、その見出しの行の `k` 番目（既定は 1）の出現の節の、最後の行のすぐあとに足す。見出しの行の出現が `k` に足りなければ、競合（`section_missing`）にする。出現が 2 つ以上あり、`--nth` を渡していなければ、競合（`section_ambiguous`）にする。`--section` がなければ、ファイルの最後の最上位のブロックを節の最後とみなして足す。
- 節の中のブロックが、テンプレートの置き換えの行（`assets/index.md.template` の 4 つの「（…と追加される）」の行。スクリプトの定数にする）だけの段落なら、その行を消して、そこに足す。
- ファイルの箇条書きの項目に、行き先が同じ項目（項目の最初の wikilink の行き先が同じもの）がすでにあれば、競合（`index_duplicate`）にする。これは「済み」の判定ではない。済んだかどうかは日誌で決め（6 節）、ここでは、同じページを 2 回索引に載せることを止めるだけである。

**`log-entry --apply-dir D --op <操作名> --title "<説明>" [--date YYYY-MM-DD] [--line "<サブ行>" …]`**

- 足すのは、`## [<日付>] <操作名> | <説明>` の見出しの行と、`--line` ごとに 3 文字の空白で字下げしたサブ行である。`<操作名>` は英小文字（`[a-z]+`）に限る（`log.md.template` の一覧と `learn`、`evolve` など）。`<日付>` は、登録のときの手元の日付を既定にし、計画に入る。
- 最後の最上位のブロックの最後の行のあとに、空の行を 1 つ挟んで足す。
- 当てたあと、足した見出しの行が、ファイルの中で同じ字面の見出しの行の何番目の出現か（`nth`）を数え、`apply` の結果に `log_entries`（`heading`、`nth`）として出す。日誌と当て終えた印（`L/applied/<plan_id>.json`）にも残す。

**`log-sub --apply-dir D --entry "<見出しの行>" --nth <k> --line "<サブ行>" …`**

- `<見出しの行>` の `k` 番目の出現の項目（見出しの行から、次の `h1` か `h2` の見出しの行の前まで）の、最後の行のすぐあとに、3 文字の空白で字下げしたサブ行を足す。
- 出現が `k` に足りなければ、競合（`entry_missing`）にする。ファイルの末尾にも、中身の検索にも頼らない。`k` は、1 回目の `apply` が出した `log_entries` の値を渡す（取り込みの 4 回目の重大 2）。
- `log.md` は `ops` だけで受け付け（3 節）、パスは正規のものだけを受けるので、書く段に加わる書き手が、`log.md` の前の位置に見出しの行を差し込むことはない（`log-entry` は末尾にだけ足す）。移っていない書き手が差し込めば、`k` は別の項目を指しうる（「保証しないこと」の 2）。

**分割した索引の件数。** トップの `index.md` に分割したファイルごとの件数を書く今の規則（`scaling-playbook.md` の閾値 2 の手順 3）は、取り込みのたびに同じ行を直すので、`edit` にすると毎回競合する。件数を書かない規則に改めることを推す（「作者が決めること」の 3。決まれば、10 節の表のとおり `scaling-playbook.md` を直す）。

### 5. 計画のハッシュと、差分の表示（`diff`）

`wiki_apply.py diff --apply-dir D [--json]` は、次を行う。ロックは持たない。wiki と raw のルートは、`plan.json` から読む。

1. 管理領域の確かめ（1 節）をやり直す。`plan.json` と、計画が指す `D/new`、`D/edit`、`D/base` のファイルを 1 回だけ読んでメモリに置き、`D/base` のハッシュが計画の `before_sha256` と同じことを確かめ、以下はその写しを使う（差分と `plan_sha256` が、同じバイト列から作られる）。
2. 3 節のパスの規則と、同じファイルの実体の判定を行う。
3. 7 節の raw の検査を、行き先の親のディレクトリ（なければ、すでにある最も近い祖先）について行う。
4. `new` と `edit` の中身を UTF-8 として読めること、frontmatter が lint と同じ分け方（`wiki_lint.parse_frontmatter_raw()`）で読めることを確かめる。frontmatter の `raw:` の値を、7 節と同じ解き方で解き、`W` の中（`.wiki-cache` を含む）を指していれば、終了コード 1（`raw_ref_in_wiki`）にする（15 回目の重大 2）。`ops` の操作を、今の中身に当ててみて（書かない）、競合が出るかを見る。出たら、その理由を出す（`apply` のときの結果とは限らない）。
5. 差分を標準出力に出す。`new` は空からの統一差分、`edit` は `base` から `edit` への統一差分、`ops` は、ファイル、操作の種類、見出しの行と `nth`、足す行である。
6. `plan_sha256` を出す。

**`plan_sha256`** は、次の JSON を、キーを並べ替え、空白を入れず、UTF-8 で書いたバイト列の SHA-256 である。項目を列挙して選ばない。計画の全体と、計画が指すファイルの中身のハッシュを入れる。

```json
{
  "format": "wiki-apply-plan/1",
  "plan_id": "<begin が作った 32 桁の 16 進>",
  "wiki": "<wiki のルートの絶対パス（/ 区切り）>",
  "raw_root": "<raw のルートの絶対パス（/ 区切り）>",
  "items": [
    {"path": "sources/x.md", "kind": "new", "after_sha256": "<D/new/x.md の SHA-256>"},
    {"path": "concepts/y.md", "kind": "edit", "before_sha256": "<D/base の SHA-256>", "after_sha256": "<D/edit の SHA-256>"},
    {"path": "index.md", "kind": "ops", "ops": [{"op": "index-add", "section": "## ソース", "nth": null, "line": "- [[x]]: …"}]}
  ]
}
```

`items` は `path` の順に並べ、`ops` は登録の順を保つ。`plan.json` そのものも、この JSON とほかの記録（作った時刻など）からなるが、ハッシュに入れるのは上の形だけである。

- 操作の引数（見出しの行、`nth`、足す行、日付）はすべて `ops` の中にあるので、承認したあとに足す先を変えると `plan_sha256` が変わる（取り込みの 4 回目の重大 4）。
- `apply` は、wiki と raw のルートを `plan.json` から読み、コマンドの引数では取らない。承認した `raw_root` と違う raw のルートで検査することはない（1 回目の重大 3）。`plan.json` のルートは `begin` が `realpath()` で解いた実体のパスで、`apply` は、そのパスが今も `realpath()` で同じパスに解けることを確かめる（途中にリンクがあとからできたら、終了コード 1）。
- `plan_id` が入るので、別々の `begin` から作った同じ中身の 2 つの計画は、違うハッシュになり、違う日誌になる（1 回目の重大 4）。

モデルは、差分と `plan_sha256` をユーザーに見せ、承認を得てから `apply` に渡す。承認のあとに `D/new` か `D/edit` を書き換えると、`apply` が `plan_sha256` の不一致で拒む。

### 6. 当てる（`apply`）と日誌

`wiki_apply.py apply --apply-dir D --expect-sha256 <plan_sha256> [--wait 180] [--keep] [--json]` は、1 つのプロセスで次を行う。

**ロックの前（wiki の今の状態によらない準備）。**

0. 管理領域の確かめ（1 節）を行う。`plan.json` と、計画が指す `D/new`、`D/edit`、`D/base` のファイルを、**1 回だけ読んでメモリに置く**。`D/base` は、そのハッシュが計画の `before_sha256` と同じことを確かめる（違えば終了コード 1。`rebase` で写し直したあとの `D/base` を、古い計画で読むことを止める。13 回目の重大 1）。承認した中身は、計画が指すすべてのファイルであり、待ちきれなかったときの差分（1 節）も、日誌も、このメモリの写しだけから作る。そのバイト列から `plan_sha256` を作り、`--expect-sha256` と一致しなければ、終了コード 1 にする。計画の wiki の `L/applied/<plan_id>.json` があれば、その `plan_sha256` が今の値と同じなら、何も書かずに、そこに残した結果を出して終了コード 0 にする（`already_applied`。日誌を消したあとでも、当て終えた計画をやり直さない。2 回目の軽微 2）。違えば（当て終えたあとに計画を変えた）、終了コード 1 にする（4 回目の重大 2）。これより後は、`D` のファイルを読み直さず、メモリの写しだけを使う（2 回目の重大 3）。メモリの `plan.json` から wiki と raw のルートを読む。wiki が初期化されていること、raw のルートが `raw_root_problem()` を通ることを確かめる。7 節の守る raw のルートと wiki の中の raw を作り（計画、記録、ページの `raw:`）、`W` と `K` の下の mount point を列挙し、根の重なりを確かめる。`Writer` を作る。3 節のパスの規則を確かめる。

**ロックの中。**

1. **ロックを取る。** 計画の wiki のロック `L/apply.lock` を、1 節の「ロックの作り」に従って取る。`--wait` 秒（既定 180）で取れなければ、1 節の「待ちきれなかったとき」に従い、差分を `P/<差分の名前>` に置いて、何も書かずに終了コード 4 にする（`P` に 5 件以上あれば `pending_alert` を出す）。ロックのファイルは `.wiki-cache` の下にあり、ページの書き込みの対象にならない（3 節。取り込みの 4 回目の重大 7）。
1c. **raw のルートの記録を確かめる。** `L/raw-roots.json` を読み直し、0 のあとにほかの書き手が足した raw のルートがあれば、守る raw のルートに足し、その raw のルートの木を走査して、根の重なりと木の重なりの検査をやり直す（7 節。ロックの中で走査するのは、この場合だけである）。計画の raw のルートが記録になければ、記録に足して置き直す（一時ファイル、fsync、`os.replace`、ディレクトリの同期）。記録に足してから、2 以降の書き込みを行う（7 節）。
2. **残った日誌を見る。** その wiki の `L/journal/` の下の日誌を見る。`manifest.json` のない日誌のディレクトリは、書いている途中で止まったものなので、消す（行き先のディレクトリに一時ファイルはまだ作っていない。7 の前に `manifest.json` を置くため）。状態が `stuck` の日誌が 1 つでもあれば、何も書かずに終了コード 5 にする（`stuck` は `recover` で片付けるまで、その wiki のどの計画も書かない）。状態が `pending` か `prepared` の日誌を、作った順にすべて、下の「前に進める」に従って進める。1 つでも `stuck` になれば、終了コード 5 にする。
3. **この計画は当て終えていないか。** ロックの中で、`D` が今もあり、管理領域の確かめを通ることを確かめる（なければ終了コード 1）。`L/applied/<plan_id>.json` を読み直し、あれば、その `plan_sha256` が今の値と同じなら、同じ `plan_sha256` の差分 `P/<差分の名前>` があれば消して、`already_applied` で終了コード 0、違えば終了コード 1 にする（0 の確かめのあとで、ロックを待つ間に、ほかのプロセスが同じ `D` を当て終えることがあるため。5 回目の重大 3）。印は計画の中身ではないので、0 で読んだ計画の中身を読み直すことにはならない。次に、`L/journal/<plan_id>/` があり、状態が `aborted` なら、消して先へ進む。状態が `done` で、日誌の `plan_sha256` が今の値と同じなら、`L/applied/<plan_id>.json` がなければ 9 と同じに書き、同じ `plan_sha256` の差分 `P/<差分の名前>` があれば消してから、日誌に残した結果を出して終了コード 0 にする（`already_applied`）。`plan_sha256` が違えば（同じ `plan_id` で計画を変えた）、終了コード 1 にする。
4. **行き先を確かめる。** 項目ごとに、3 節の正規のパスの検査（入れ子の wiki の検査を含む）、同じファイルの実体の判定、7 節の raw の検査を行う。どれかが通らなければ、何も書かずにロックを外し、終了コード 1 にする。行き先のパスの途中の要素が、ファイルとしてあれば、競合（`parent_not_dir`）にする。
5. **新しい中身を、すべてメモリの中で作る。** `new` と `edit` の「後」は、0 で読んだメモリの写しである。

| 種類 | 今の行き先 | 結果 |
| --- | --- | --- |
| `new` | ない | 「書く」。前は「ない」 |
| 同上 | ある | 競合（`exists`） |
| `edit` | 全体の SHA-256 が `before_sha256` と同じ | 「書く」 |
| 同上 | ない、または違う | 競合（`changed_since_prepared`） |
| `ops` | あり、UTF-8 として読め、操作がすべて当たり、構造の確かめ（4 節）を通る | 「書く」。前は今の SHA-256、後は計算した結果の SHA-256 |
| 同上 | ない、UTF-8 として読めない、操作が競合、または構造が変わる | 競合（4 節の理由） |

   1 つでも競合があれば、何も書かずにロックを外し、終了コード 3 で、競合した項目のパスと理由を出す。「済み」の判定はない。`new` と `edit` の後の中身の frontmatter の `raw:` が `W` の中を指していれば、競合ではなく終了コード 1（`raw_ref_in_wiki`）にする（5 節の 4 と同じ。0 で読んだ中身なので、0 で確かめてよい。15 回目の重大 2）。

   **変わらない項目は書かない。** 「書く」になった項目のうち、作った「後」のバイト列が今の行き先のバイト列と同じもの（中身を変えない `edit`、写しを元に戻した `edit`）は、書かずに外し、結果を `unchanged` にする。日誌に入れる項目は、どれも「前」と「後」のハッシュが違う（`new` の「前」は「ない」なので、つねに違う）。前に進めることと戻すことは、この不変条件に頼って、行き先のハッシュが「前」か「後」かを判定する（6 回目の重大 1）。書く項目が 1 つもなければ、6〜8 を飛ばし、日誌を作らずに、下の 9 の「書く項目がないとき」へ進む。

6. **日誌を書く。** 書く前に、持ち主の確かめ（下）を行う。`Writer` で `L/journal/<plan_id>/` を作り、項目ごとに、置く中身を `after/<番号>` に、`edit` と `ops` では 5 で読んだ今の中身を `before/<番号>` に書いて fsync する（戻すため。5 回目の重大 2）。最後に、`manifest.json` を一時ファイルに書いて fsync し、`os.replace` で置き、ディレクトリを fsync する（POSIX）。`manifest.json` の中身は、状態 `pending`、`plan_id`、`plan_sha256`、wiki のルートと raw のルート（前に進める書き手が `Writer` を作り直すため。3 回目の重大 3）、作った時刻、`D` のパス、項目ごとの `path`、`kind`、`before_sha256`（`new` は `null`）、`after_sha256`、`after/<番号>`、**一時ファイルの名前**（`.wa-<plan_id の先頭 12 桁>-<番号>.tmp`。行き先と同じディレクトリ。行き先の名前によらず 30 文字に収まる。4 回目の重大 3）、作る親のディレクトリの並び、`log_entries` である。一時ファイルの名前を、作る前に日誌に書く（1 回目の重大 5）。
7. **書く。** 2 段で行う（4 回目の重大 3）。
   - **7a. 用意する。** 項目ごとに、親のディレクトリがなければ `Writer` で作り、日誌に書いた名前の一時ファイルを `Writer` で `O_EXCL` で作って書き、fsync する。1 つでも失敗したら（名前、権限、空き容量）、作った一時ファイルと作ったディレクトリを消し、日誌の状態を `aborted` にして（`before/` と `after/` を消す）、何も置き換えずに終了コード 1 で止める（理由を出す）。`aborted` の日誌は、行き先を 1 つも変えていないので、前に進めない。日誌の状態を `prepared` にして置き換え、fsync する。
   - **7b. 置く。** 置く前に、持ち主の確かめ（下）を行う。項目ごとに、一時ファイルを置く。`new` は重ねて書かない形で置く（POSIX は `os.link` のあとに一時ファイルを消す。Windows は `os.rename` で、行き先があれば `FileExistsError`）。`edit` と `ops` は `wiki_fetch.replace_with_retry()` で置き換える。どの置き換えも、`Writer` の検査を直前に通す。すべての項目を置いたら、行き先のディレクトリ（と、作った親のディレクトリの親）を、公開の順番（下）に従って同期する（12 回目の重大 1）。
   - **7c. 置けなければ戻す。** 7b で 1 つでも置けなければ（読み取り専用のファイル、ほかのプロセスが開いたまま、`Writer` が拒む）、下の「戻す」に従って、置いた項目を「前」に戻し、日誌を `aborted` にして、終了コード 1 で止める（理由 `replace_failed` と、置けなかったパスを出す）。
8. **読み直す。** 書いたファイルを読み、SHA-256 が `after_sha256` と同じことを確かめる。違えば（置き換えの直後にほかが書いた）、日誌を `stuck` にして終了コード 5 にする。
9. **日誌を閉じる。** （書く項目がないときは、日誌がないので、一時ファイルの片付けと `manifest.json` の更新はせず、`L/applied/<plan_id>.json` だけを 9 と同じ手順で書いてロックを外す。結果はすべての項目が `unchanged` である。7 回目の軽微 1）日誌に書いた一時ファイルの名前のうち残っているものを消す。`L/applied/<plan_id>.json`（`plan_id`、`plan_sha256`、項目ごとの結果、`log_entries`）を、`manifest.json` と同じく、隣の一時ファイルに書いて fsync し、`os.replace` で置き、ディレクトリを fsync してから（途中で止まっても、空や途中までの印が残らない）、**そのあとで** `manifest.json` の状態を `done` にして置き換える（3 回目の重大 2）。同じ `plan_sha256` の差分 `P/<差分の名前>` があれば（前に待ちきれなかった計画）消し、ロックを外す。`--keep` がなければ `D` を消す。終了コード 0 で、項目ごとの結果（`written` か `unchanged`）、`log_entries`、ロックを待った秒数、ロックを持った秒数を出す。

**前に進める（2 と、`recover`）。** 日誌を読んだら、まず、どの項目も `before_sha256` と `after_sha256` が違うことを確かめる。同じ項目があれば、その日誌は 6 の不変条件を満たさない壊れたものなので、何もせずに `stuck` にする（ハッシュで「置いたか」を判定できないため）。日誌の raw のルートは記録にある（日誌を書く前に 1c で足してある）ので、0 と 1c で作った集まりで `Writer` を作る（3 回目の重大 3。日誌ごとに走査し直さない。13 回目の軽微 1）。日誌の raw のルートが記録にない（記録を消したあと）ときは、記録に足し、その木を走査して、根の重なりと木の重なりを確かめる。日誌の raw のルートが `raw_root_problem()` か根の重なりの検査を通らなければ、その日誌を `stuck` にする。前に進めるのは、ロックを持つ wiki の日誌だけである（日誌は wiki ごとに `L/journal/` にある）。そのうえで、項目ごとに、次の順で行う（2 回目の軽微 1）。

1. 日誌に書いた一時ファイルの名前が残っていれば、先に消す（`os.link` のあと一時ファイルを消す前に止まったときの、行き先のもう 1 つの名前も、一時ファイルを作ってから置く前に止まったときの一時ファイルも、ここで消える）。
2. 行き先の今の SHA-256 を見て、次の表に従う。

| 今の行き先 | すること |
| --- | --- |
| `after_sha256` と同じ | 置くことはしない（書けていた） |
| `before_sha256` と同じ（`new` は、ないこと） | `after/<番号>` の中身を、日誌に書いた名前の一時ファイル（行き先と同じディレクトリ）に `Writer` で `O_EXCL` で写して fsync し（7a と同じ）、それを 7b と同じに置く。日誌のファイルをそのまま置かない（`.wiki-cache` と行き先が別のファイルシステムのとき、たとえば行き先のディレクトリに別のボリュームが mount されているとき、`os.link`、`os.replace`、`os.rename` が `EXDEV` で失敗するため）。置けなければ、日誌を戻す（下） |
| どちらでもない | 項目を `stuck` にする |

日誌の状態が `pending`（7a より前か、7a の途中で止まった）なら、行き先はまだ 1 つも変わっていないので、前に進めずに、一時ファイルの名前を消して `aborted` にする（持ち主は、同じ `apply` をやり直せば、新しい日誌で始め直す。`plan_id` の日誌のディレクトリは `aborted` を上書きして作り直す）。状態が `prepared` のときだけ、項目ごとに上の表で前に進める。前に進める途中で置けない項目があれば（親のディレクトリを作れない、置けない、`Writer` が拒む）、その日誌を下の「戻す」に従って戻し、`aborted` にする（持ち主の計画は当たらなかったことになる。持ち主が同じ `apply` をやり直すと、3 で `aborted` の日誌を消して初めから当て、同じ理由なら 7c で止まる）。すべての項目が済めば、`L/applied/<plan_id>.json` を 9 と同じ手順（一時ファイル、fsync、`os.replace`）で書いてから、状態を `done` にする。印は wiki の側にあるので、日誌を前に進めた書き手の環境（作業用のフォルダーの置き場）によらず書ける（11 回目の重大 1）。`stuck` が 1 つでもあれば、状態を `stuck` にし、書いた項目と書けなかった項目を出す。

**戻す（7c と、前に進める途中）。** 日誌の項目ごとに、一時ファイルの名前を消してから、行き先の今の SHA-256 を見る。`after_sha256` と同じなら、`edit` と `ops` は `before/<番号>` の中身を、日誌に書いた名前の一時ファイル（行き先と同じディレクトリ）に `Writer` で `O_EXCL` で写して fsync し、それを 7b と同じ形で置く（前に進めるときと同じ理由で、日誌のファイルをそのまま置かない）。`new` は行き先を `Writer` で消す。`before_sha256` と同じ（`new` は、ないこと）なら、何もしない。どちらでもなければ、その項目を `stuck` にする。戻すときに置けない、消せないときも `stuck` にする。日誌は、`stuck` の項目がなければ `aborted`、あれば `stuck` になる。`aborted` にするときは、日誌の「作る親のディレクトリの並び」を逆の順にたどり、7a で作ったディレクトリのうち空のものを `Writer` で消す。`aborted` の日誌は、`before/` と `after/` を消し、`manifest.json`（理由と、置けなかったパスを含む）だけを残す。持ち主が同じ `apply` をやり直したときは、3 で消す。それ以外は、`done` と同じく 14 日を過ぎたら 2 のときに消す。ロックを持ったまま戻すので、`after_sha256` と同じ行き先は、この計画が置いたものである。

**戻すことが生む失敗の形。** 「戻す」（AL）は、6 版目で足した仕組みで、次の失敗の形を新しく生む。どれも、この節の規則か「保証しないこと」で扱う。

| 失敗の形 | 起きる条件 | 扱い |
| --- | --- | --- |
| 持ち主の計画が、ほかのプロセスに取り消される | 持ち主が 7b の途中で止まり、次にロックを取ったプロセスが前に進めようとして置けない | 戻して `aborted` にする。持ち主が同じ `apply` をやり直すと、3 で `aborted` の日誌を消して初めから当て、同じ理由なら 7c で止まる。持ち主は `list` で `aborted` と理由を見られる |
| 戻すことに失敗する | 7b で置けた項目を、戻すときに置けない（置いた直後に属性が変わったなど） | その項目を `stuck` にする。ロックを持ったまま、直前に置けた場所に置き直すので、ふつうは起きない |
| 置いてから戻すまでに、読み手が「後」を読む | MCP の索引や閲覧が、その短い間にファイルを読む | 保証しない（「保証しないこと」の 10）。読み手は次に読み直せば「前」を見る |
| 戻した中身が、加わらない書き手の書いた中身を消す | 置いてから戻すまでの間に、加わらない書き手が同じファイルに「後」と同じ中身を書く | 戻す前にハッシュを見るので、「後」と違う中身なら `stuck` にして消さない。「後」と同じ中身なら区別できずに戻す（中身は同じなので、失うのは書いた事実だけである）。「保証しないこと」の 2 |
| 日誌の不変条件が守られない | 実装の誤りで、前と後が同じ項目が日誌に入る | 日誌を読むときに確かめて `stuck` にする（上）。行き先は変えない |

**公開の順番。** 名前を作る、置き換える、消す操作（`os.link`、`os.rename`、`os.replace`、`os.unlink`、`os.mkdir`、`os.rmdir`）のあとは、その名前を持つディレクトリを同期してから、次の段へ進む（12 回目の重大 1）。POSIX は、ディレクトリを `os.open(..., os.O_RDONLY)` で開いて `os.fsync()` する。Windows は、Python からディレクトリを同期する手段がないので、NTFS がメタデータを記録してから書くこと（ジャーナル）に頼る（「まだ確かめていないこと」）。段の順番は次のとおりで、前の段の名前が残っていない状態で、後の段の名前が残ることはない。

1. 日誌の `before/`、`after/`、`manifest.json` と、`L/journal/<plan_id>/`（6）。
2. 状態を `prepared` にした `manifest.json`（7a）。
3. すべての行き先と、作った親のディレクトリ（7b）。
4. 当て終えた印 `L/applied/<plan_id>.json`（9）。
5. 状態を `done` にした `manifest.json`（9）。

当て終えた印が残っていれば、行き先の名前も残っている。差分の組（1 節）とロックのファイルも、置いたあとにディレクトリを同期する。

**公開の順番が生む失敗の形。** (1) ディレクトリの同期が増えるので、ロックを持つ時間が延びる（行き先のディレクトリの数だけ。実装で測る）。(2) Windows ではディレクトリを同期できず、ネットワークのドライブでは同期が効くかがファイルシステムによるので、電源が切れたときに名前が残る順番は、そのファイルシステムの性質に頼る。

**持ち主の確かめ。** 日誌を書く前（6）と、行き先を置く前（7b）に、ロックのファイルの中身を読み、`lock_id` が自分のものであることを確かめる。違うか、ロックのファイルがなければ（`unlock --force` で外され、ほかの書き手が取ったか、誰かが消した）、何も置かずに止める（終了コード 1、`lock_lost`）。6 の前なら何も書いていない。7b の前なら日誌は `prepared` で残り、次にロックを取った書き手が前に進める（12 回目の軽微 3）。**持ち主の確かめが生む失敗の形。** 確かめと置くことの間に外されると、すり抜ける（`--force` を使った限り残る並び。「保証しないこと」の 13）。ロックの中身を読めない（ほかのプロセスが一時的に開けなくした）ときも `lock_lost` で止まり、やり直すことになる。

**`stuck` になる時。** 次の 4 つだけである（13 回目の軽微 2）。(1) 行き先が「前」でも「後」でもないとき（下）。(2) 戻すことにも失敗したとき（置けなかったファイルを、戻すときにも置けない。7b で置けた項目だけを戻すので、ふつうは戻せる）。(3) 日誌が壊れているとき（前と後が同じ項目がある、`manifest.json` が読めない）。(4) 日誌の raw のルートが `raw_root_problem()` か根の重なりの検査を通らないとき（raw のルートを wiki の中や `data_dir()` の下に移したなど）。日誌の wiki は、前に進める書き手がロックを持つ wiki そのものなので、「初期化されていない」ことはない。計画そのものが置けないとき（5 回目の重大 2 の、作れるが置き換えられないファイル）は、7c か前に進める途中で戻して `aborted` になり、その wiki は止まらない。

**なぜ「どちらでもない」が起きないか。** 日誌は、最初の置き換えより前に fsync してある。書く段に加わる書き手は、同じ wiki に書くときは同じロックを取り、自分の計画を書く前に、その wiki に残った日誌を必ず前に進める（2）。持ち主が落ちてロックが残ったときは、利用者が `unlock` で外すまで、誰も書かない（1 節）。したがって、日誌の持ち主が 7 の途中で落ちたあと、次にロックを取った書き手は、誰であれ、まずその日誌を最後まで進めてから自分の計画を書く。ロックの持ち主が落ちてから、日誌が進められるまでの間に、書く段に加わる書き手が同じファイルを書くことはない。「どちらでもない」は、書く段に加わらない書き手（移っていない手順の Edit と Write、エディター、同期のツールでつないだほかの PC の書き手）か、`unlock --force` で外されたあとも動いていた持ち主が、その間に同じファイルを書いたときにだけ起きる。そのときは、書き手の変更を消さないために、置かずに `stuck` にする（終了コード 5。「保証しないこと」の 2）。

**リンク数を見ない理由。** `os.replace` と `os.rename` は、行き先の名前を新しい実体に付け替えるだけで、もとの実体の中身は変えないので、ハードリンクの別の名前（raw の中のものを含む）の中身は変わらない。そのため、行き先のリンク数は見ない。

**途中で止まったとき。**

- 1 より前に止まれば、何も書いていない。同じ `apply` をやり直せばよい。1 でロックを取ったあと、6 より前に止まれば、wiki のページは何も書いていないが、ロックが残る。利用者が `unlock` で外してから、同じ `apply` をやり直す（12 回目の軽微 1）。
- 6 の途中で止まれば、`manifest.json` がないので、日誌はないものとして消される。何も書いていないが、ロックが残るので、`unlock` のあとにやり直す。以下、6 より後で止まったときも、ロックが残り、`unlock` のあとに次の書き手が日誌を前に進める。
- 7a の途中で止まれば、何も置き換えていない。次に誰かがロックを取ったときに、日誌は `aborted` になり、一時ファイルが消える。同じ `apply` をやり直せば、初めから当てる。
- 7b の途中で止まれば、次に誰かがロックを取ったときに、日誌が前に進められる。残りを置けたなら、日誌は `done` になり、同じ `apply` をやり直すと 3 で `already_applied` になる。残りを置けなかったなら、日誌は戻されて `aborted` になり、同じ `apply` をやり直すと初めから当て、同じ理由なら 7c で `aborted` になる（終了コード 1）。
- 7c の途中で止まれば、日誌は `prepared` のままで、次に誰かがロックを取ったときに前に進められる。前に進めて置けなければ、戻して `aborted` になる。
- 9 の途中で止まれば、日誌は `prepared` のままで、行き先はすべて `after_sha256` と同じなので、前に進めると、一時ファイルの名前を消し、当て終えた印を書いて `done` になる。印を書いたあとに止まったときも同じで、同じ `apply` をやり直すと、0 で `already_applied` になる。

`done` の日誌は、14 日（作者の判断の 5）を過ぎたら、ロックの中で 2 のときに消す（`--keep-journal-days`）。当て終えた印 `L/applied/<plan_id>.json` は消さないので、日誌を消したあとも、当て終えた計画のやり直しは印で止まる（3 回目の重大 2。11 回目の重大 1 の直しで、印を wiki の側に移した）。`D` を消したあとに同じ `apply` を実行すると、0 で `D` がないので終了コード 1 になり、何も書かない。

**`wiki_apply.py recover --wiki <W> [--show | --discard <plan_id>]`** は、その wiki のロックを取って、`stuck` の日誌を見せる。`--discard` は、その日誌を `L/journal/discarded/` に移し、日誌に書いた一時ファイルの名前のうち残っているものを消す。`stuck` の項目の行き先は、モデルがユーザーと、`after/<番号>` と今の中身を見比べて直す（その直しは、新しい計画で行う）。

**ロックを持つ時間。** 2〜9 は、モデルを呼ばず、記録も読まず、ネットにもつながらない区間で、書くファイルの数と大きさの分だけで終わる。ふつうの取り込み（新しいページ 2〜5、直すページ 1〜5、索引とログ）で 1 秒より短い見込みである（実装で測り、結果に出す）。ページの `raw:` を読むこと、mount point の列挙、wiki と raw の木の走査（7 節）は、ロックの前の 0 で行う。ロックの中では、記録を読み直し、0 のあとに足された raw のルートがあったときだけ、その木を走査する（13 回目の軽微 1）。日誌の raw のルートも記録にあるので、日誌を前に進めるときに走査し直すことはない。

**ライブラリとして呼ぶとき。** Python の書き手（`wiki_evolve_loop.py`）は、サブコマンドを通さず、`wiki_apply.Plan` を組み立てて `wiki_apply.apply_plan(plan)` を呼ぶ。中身はメモリで渡し、`D` を作らない（日誌の `D` は `null`）。`D` のない計画では、3 の `D` の確かめと、9 の `D` の削除を行わない。当て終えた印を含め、ほかの手順は同じである。`D` のない計画は、`plan_id` を呼ぶたびに新しくするので、同じ計画を 2 回当てることは、呼び出し側が同じ `Plan` を 2 回渡さない限り起きない。やり直しは新しい `plan_id` で行い、止まった前の計画は、次にロックを取った書き手が日誌から前に進める。呼び出し側は、前の計画の日誌が `done` になったか（`list`）を見てから、残りを足すかを決める。人の承認は、呼び出し側の手順（評価ループの承認）に頼る。

### 7. raw を書き換えないこと：別名のない道と、ルートの重なり

**考え方（16 版目で組み立て直した）。** この道具の書き込みが raw の中身を変えうるのは、書く先のディレクトリが、別名（シンボリックリンク、ジャンクション、bind mount、UNC の共有など）を経由して、物理的に raw のディレクトリになっているときである。15 版目までは、守る raw のディレクトリの実体をすべて集めて、書く先と照らしていた。この形は、raw のルートをすべて知り、ディレクトリをすべて走査できることに頼るので、集め方の漏れ（ディレクトリを指す `raw:`）、集める時の遅れ（`begin` が先に書く）、古い集まりで書くこと（ロックを取らない経路）から、14 回目に 3 通りに崩れた。

16〜17 版目は、守りを 2 つの条件の組で示す。**(1) 根から書く先までの道に別名がない**ので、書く先は `W` か `K` の物理的な木の中にある。**(2) `W` と `K` の木と、守る raw のルートの木が、物理的にディレクトリを分け合わない**ので、`W` か `K` の物理的な木の中に、raw のファイルはない。(1) だけでは足りない。raw のルートの側が wiki のディレクトリの別名（bind mount）になっていると、書く道にも根の祖先の並びにも別名が現れないまま、原本が物理的に wiki の中にある（15 回目の重大 1）。(2) は、守る raw のルートを知り、その木を走査することに頼るので、守る raw のルートは、各コマンドの始め（`begin` を含む）に、計画、記録、ページの `raw:` から作る（下）。

**別名のない道（`Writer` の a、b、e）。** `Writer` を通るすべての書き込みで、根（ページと wiki の管理は `W`、作業用は `K`）から書く先までの、すでにあるどのディレクトリも（書く先がすでにあるディレクトリなら、それも）、次を満たす。

- a. リンクでも再解析点でもない（1 節）。Windows のジャンクション、シンボリックリンク、フォルダーへのボリュームの mount は、どれも再解析点なので、ここで止まる。
- b. 実体が、根より下の道の、ほかの段と同じでない（1 節。輪を止める）。
- e. **mount point でない。** 次の 2 つで見分ける。(1) どの OS でも、そのディレクトリの `st_dev` が親の `st_dev` と違えば mount point である（別のファイルシステムの mount、FUSE の bindfs）。(2) Linux では、それに加えて `/proc/self/mountinfo` を読み、mount point のパスの一覧を作る。同じファイルシステムの中の bind mount は `st_dev` が変わらないので、(1) では見分けられないためである。

**mount point の列挙は、完全でなければ書かない。** 各コマンドの始めに、`W` と `K` の下にある mount point を列挙する。Linux で `/proc/self/mountinfo` を読めないとき（権限、コンテナーの制限）は、何も書かずに終了コード 1（`mount_scan_incomplete`）にする（作者の判断の 9「走査が完全でなければ書かない」の趣旨を、mount point の列挙に当てる）。`W` か `K` の下（`W` と `K` そのものは除く）に mount point が 1 つでもあれば、どこに書くかによらず、終了コード 1（`mount_in_wiki`、mount point のパスを出す）にする。書くたびにも、道の各段を e で確かめる。

14 回目の 3 件は、どれもこの規則で止まる。重大 1（`W/sources` が `R1/bundle` の bind mount）と重大 3（`P` が `R1/pending-area` の bind mount）は、`W` の下の mount point として、始めの列挙で止まる。raw のルートを知っているかどうかによらない。重大 2（`INFO_HIVE_DATA_DIR` で `K` を過去の raw のルートの中に置く）は、下の「根の重なりの検査」で止まる。

**守る raw のルート（根の重なりの検査に使う）。** 各コマンドの始め（`begin` を含む）に、次の和として作る（14 回目の重大 1、2）。

1. 計画の raw のルート、`--raw-root` で渡した raw のルート、ロックや日誌や差分の記録にある raw のルート（1 節の読み元の表）。
2. wiki の raw のルートの記録 `L/raw-roots.json` にある raw のルート（下）。
3. **ページから引かれる raw。** wiki のすべてのページの frontmatter の `raw:` の値を、`wiki_lint.missing_raw()` と同じ解き方（絶対パス、wiki とその親とページの位置を基準にした相対パス）で解く。見つかったものが、`W` の外にあれば、ファイルならその親のディレクトリを、ディレクトリならそれ自身を、raw のルートとして足す（拡張子によらない。ディレクトリを指す `raw:` も拾う。14 回目の重大 1）。`W` の中にあれば（古い wiki の `W/raw/...`、`raw: "original.md"` のように wiki の中に置いた原本）、raw のルートにはせず、その**パスそのもの**（ファイルかディレクトリ）を「wiki の中の raw」に足す（14 回目の軽微）。

ページは毎回読み直す（記録がないときだけでなく）。frontmatter だけを読むので、数百のページで 1 秒より短い見込みである（実装で測る）。解けない `raw:` の値（ないファイル）は飛ばす。ないものは、根に重ならず、書く先にもならない。

**木の重なりの検査（15 回目の重大 1）。** `W` の木（`.wiki-cache` を含む）と `K` の木を、リンクと再解析点をたどらずに走査し、ディレクトリの実体の集まりを作る。守る raw のルートのそれぞれの木も、同じく走査して集まりを作る。2 つの集まりが交われば（同じ実体のディレクトリがあれば）、終了コード 1（`raw_overlap`。交わったディレクトリの両方のパスを出す）にする。raw の側の bind mount（`R` が `W/concepts/originals` の bind mount）は、`R` の実体が `W/concepts/originals` の実体と同じなので、ここで見つかる。走査は作者の判断の 9 のとおり、**完全でなければ書かない**。一覧と `lstat` の失敗を 1 つも飛ばさず、途中で消えたもの（`FileNotFoundError`）のほかの失敗があれば、何も書かずに終了コード 1（`scan_incomplete`）にする。`os.walk` は一覧の失敗を既定で飛ばし、`DirEntry.is_dir()` の失敗をファイルの側に数えるので使わず、ディレクトリごとに `os.scandir()` で一覧を取り、項目ごとに `os.lstat()` で種類と実体を決める（10 回目の重大 2）。同じ実体を 2 回見たら、そこから下に降りない。`W` の木の中に mount point はない（e）ので、`W` の側の集まりは `W` の物理的な木そのものである。

**根の重なりの検査。** 守る raw のルートのそれぞれ `R` について、`R` と `W`、`R` と `W/.wiki-cache`、`R` と `K`、`R` と `data_dir()` が重ならない（一方が他方の中にない、同じでない）ことを確かめ、重なれば終了コード 1（`raw_overlap`。どの raw のルートが、なぜ守る側に入ったか（計画、記録、どのページ）を出す）にする。重なりは、パスを `realpath()` で解いた祖先の実体の並び（`wiki_browse_fs._existing_chain()`）を、両方向に比べて決める（bind mount の別名で `W` が `R` そのものになる配置も、実体が同じなので見つかる）。この検査は、`begin` が `D` を作る前、`apply` が待ちきれなかった差分を置く前を含め、`Writer` を作るたびに行う。`R` が今はない（移した、消した）ときは飛ばす。

**wiki の中の raw。** ページから引かれる raw のうち `W` の中にあるパス（上の 3）は、書く先にしない。書く先が、そのパスと同じか、その下にあれば（`casefold()` と NFC で比べる）、終了コード 1（`raw_in_wiki`）にする（`Writer` の c。管理の書き込みと作業用の書き込みにも当てる。15 回目の重大 3）。ページの `raw:` が `.wiki-cache` の下を指していれば、始めに終了コード 1（`raw_ref_in_cache`）にする。3 節の規則で `raw` の下のパスはもとから受けないので、ふつうの古い構成（`W/raw/`）では、この検査は重ねての守りになる。

**wiki の中の raw を増やさない。** 書く段は、frontmatter の `raw:` が `W` の中を指す `new` と `edit` を書かない（`raw_ref_in_wiki`。5 節の 4、6 節の 5）。そのため、wiki の中の raw は、書く段に加わる書き手の間では増えず、ロックの前に読んだ集まりは、当てる時まで小さくなることしかない（15 回目の重大 2）。増えるのは、書く段に加わらない書き手がページを直したときだけである（「保証しないこと」の 2）。

**raw のルートの記録（`L/raw-roots.json`）。** wiki ごとに、書く段で使った raw のルートを記録する（13 回目の重大 2）。ページから引かれない raw（ページを消した原本、ページを書く前に止まった取り込みの原本）の raw のルートも、根の重なりの検査に入れるためである。

- 中身は、raw のルートの実体のパス（`realpath()`）と実体と、足した時刻と、足した理由（`plan` か `user`）の並びである。消さずに足すだけである。
- `apply` は、ロックの中（6 節の 1c）で、自分の計画の raw のルートを足してから、wiki を書く。足すときに、記録のほかの raw のルートとページから引かれる raw のルートで、根の重なりの検査をやり直す。
- ロックを持たない書き込み（`begin` の作業用のフォルダー、待ちきれなかった差分）は、その時点で読んだ記録とページから作った守る raw のルートで、根と木の重なりを確かめてから書く。記録があとから増えたとき、その新しい raw のルートが、すでに書いた作業用のフォルダーや差分の木と交わっていれば、次にその wiki に書く `apply`（1c）が、木の重なりで止まる。
- 利用者は `wiki_apply.py raw-roots --wiki <W> [--add <R>]` で、記録を見る、足す。消す操作は持たない。

**この組み立て直しが生む失敗の形。**

| 失敗の形 | 起きる条件 | 扱い |
| --- | --- | --- |
| wiki の下に mount point があると書けない | wiki の中に、意図して別のボリュームや bind mount をつないだ（容量のため、コンテナーのボリューム） | `mount_in_wiki` で止まる。mount を wiki の外に出す。wiki の外から wiki を mount するのはよい（`W` そのものは除く） |
| mount point の一覧を読めない | Linux で `/proc` が見えない環境 | `mount_scan_incomplete` で止まる（判断 9 の趣旨）。Linux のほかの OS では、`st_dev` の比べだけで見分ける |
| `st_dev` の変わらない別名を見分けられない OS | FreeBSD の nullfs など、同じ `st_dev` を見せる mount を `/proc` なしで作る OS | 見分けない（「保証しないこと」の 4）。info-hive が想定する Windows、macOS、Linux では、それぞれ再解析点、`st_dev`、`/proc/self/mountinfo` で見分ける |
| 始めが遅くなる | ページが多い wiki で、毎回 `raw:` を読む | frontmatter だけを読む。実装で測り、遅ければ、ページの更新時刻をキーにした読み直しの省略を考える |
| wiki の中の raw を直せない | `raw: "original.md"` のように、wiki の中に原本を置いたページ | その原本は書く段の書き込みの対象にならない（`raw_in_wiki`）。原本を書き換えるのは、書く段の外の、利用者の操作である |
| wiki の中を指す `raw:` のページを書けない | 古い構成（raw が `W/raw` にある wiki）で、新しいソースを取り込む | `raw_ref_in_wiki` で止まる。古い構成の wiki は、ADR-0008 の構成（wiki と raw を兄弟に置く）に移してから書く段を使う。raw のルートを wiki の中に置くことは、もとから `raw_root_problem()` が断っている |
| raw の木の走査で止まる、遅くなる | raw のルートの下に読めないディレクトリがある、raw のルートが大きい | 判断 9 のとおり `scan_incomplete` で止まる。走査はロックの前で行うので、ほかの書き手は待たない。PDF の原本のように `W` の外の大きなディレクトリを指す `raw:` は、その親のディレクトリを raw のルートとして走査するので、長くなりうる（実装で測る。長ければ、`.md` でない原本の親を、木の重なりの検査から外し、根の重なりの検査だけにすることを考える） |
| 記録にもページにもない raw のルートと、根や木が重なる | 書く段に移る前に別の raw のルートに取り込み、その raw を引くページを消した | 根と木の重なりを見分けない（「保証しないこと」の 14）。その raw のルートの木の中に `W` があれば、`W` の中の原本も書き換えうる |

**raw のルートの役割の検査。** `begin`、`diff`、`apply` は、raw のルートの実体が、次のどれとも重ならない（一方が他方の中にない）ことを確かめ、重なれば終了コード 1 にする。wiki のルートと `K` が重ならないことも確かめる。この検査は、raw の書き手（`wiki_fetch.py`、`wiki_session.py write`、`wiki_evolve.py capture`、`wiki_encoding.py --output`）からも呼べるように、共通の関数 `wiki_fsguard.raw_root_problem(wiki, raw_root)` にする（12 節の 1 で、raw の書き手にも入れる）。

- wiki のルート（ADR-0008 は wiki と raw を兄弟に置く）
- wiki のルートの `.wiki-cache`
- `wiki_mcp_common.data_dir()` の全体（MCP の索引、rag の派生データ、作業用のフォルダーの置き場 `K` を含む）

これは、取り込みの 7 回目のレビューの重大 2（raw のルートに MCP の索引のディレクトリを指定できる）の、知られた置き場所を断る検査である。ほかの道具が中身を消すディレクトリをすべて知ることはできないので、そこから先は限界とする（「保証しないこと」の 5）。

**共通のモジュール。** 実体の検査（`identity()`、`_existing_chain()`、`_is_link()`）は、今は `wiki_browse_fs.py` にある。書く段と閲覧で同じ判定を使うため、`wiki_fsguard.py` に移し、`Writer` を足す。`wiki_browse_fs.py` はそれを読み込む。

### 8. 競合したとき（`rebase`）

競合は、用意したあとに、ほかの取り込みか、書く段に加わらない書き手が、同じファイルを書き換えたときに起きる。決まった操作は今の中身に当てるので、索引とログで競合するのは、足す先の見出しがない、2 つある、同じページがすでに載っている、構造が変わる、のどれかのときだけである。

- **`edit` の競合（`changed_since_prepared`）。** `wiki_apply.py rebase --apply-dir D --path <P>` は、`base` から `edit` への差分を `D/rejected/<P>.diff` に書き、今の行き先を `D/base/<P>` と `D/edit/<P>` に写し直す。モデルは、`rejected` の差分を読み、同じ意図の直しを、新しい `edit` の写しに Edit で入れ直す（作者の判断の 3「パッチが競合したら、モデルが直す」）。スクリプトが差分の塊を当て直すことはしない。
- **`new` の競合（`exists`）。** ほかの取り込みが同じ名前のページを作った。モデルは、そのページを読み、名前を変えるか、`edit` に切り替えて既存のページに足すかを、ユーザーと決める。`wiki_apply.py drop --apply-dir D --path <P>` で項目を外してから登録し直す。
- **`ops` の競合。** 理由に応じて、見出しの行、`--nth`、行を直して登録し直す（`drop` のあと `index-add`）。`index_duplicate` なら、その行を外すかをユーザーと決める。`structure_changed` なら、足す行の書き方を直す。

どの場合も、直したら P3（`diff` と承認）からやり直す。`plan_sha256` が変わるので、前の承認は使えない。

### 9. スクリプト

`skills/info-hive/scripts/wiki_apply.py` と `wiki_fsguard.py` を足す。Python 3.12 以上で、標準ライブラリと、同梱のモジュール（`wiki_text`、`wiki_pages.new_parser()`、`wiki_initialized`、`wiki_fetch.check_slug()` と `replace_with_retry()`、`wiki_graph_common._try_lock()`）だけを使う。ファイルの読み書きは、すべてバイト列で行い、UTF-8 を明示する。

```text
python wiki_apply.py begin     --wiki <W> --raw-root <R> --name <名前> [--json]
python wiki_apply.py new       --apply-dir <D> --path <P>
python wiki_apply.py edit      --apply-dir <D> --path <P>
python wiki_apply.py index-add --apply-dir <D> --file <索引のパス> [--section <見出しの行> [--nth <k>]] --line <行>
python wiki_apply.py log-entry --apply-dir <D> --op <操作名> --title <説明> [--date YYYY-MM-DD] [--line <サブ行> …]
python wiki_apply.py log-sub   --apply-dir <D> --entry <見出しの行> --nth <k> --line <サブ行> [--line …]
python wiki_apply.py drop      --apply-dir <D> --path <P>
python wiki_apply.py diff      --apply-dir <D> [--json]
python wiki_apply.py apply     --apply-dir <D> --expect-sha256 <plan_sha256> [--wait 180] [--keep] [--json]
python wiki_apply.py rebase    --apply-dir <D> --path <P>
python wiki_apply.py list      [--wiki <W>] [--json]
python wiki_apply.py recover   --wiki <W> [--show | --discard <plan_id>] [--raw-root <R>] [--json]
python wiki_apply.py abort     --apply-dir <D> [--raw-root <R>]
python wiki_apply.py raw-roots --wiki <W> [--add <R>] [--json]
python wiki_apply.py unlock    --wiki <W> [--lock-id <id>] [--force] [--raw-root <R>] [--json]
python wiki_apply.py pending   --wiki <W> [--show | --discard <差分の名前>] [--raw-root <R>] [--json]
```

- `begin` 以外の `--apply-dir` を取るサブコマンドは、`D` が `K` の直下にあることと、管理領域の確かめ（1 節）を、毎回行う。`W` と `R` は `plan.json` から決める。`--raw-root` を取るのは、`begin` と、計画を持たない操作（`unlock`、`recover`、`pending`、`abort`）である（1 節の「`Writer` を作る操作と、raw のルート」の表。12 回目の軽微 2）。
- **当て終えた計画は凍る。** 計画の wiki に `L/applied/<plan_id>.json` があれば、`new`、`edit`、`index-add`、`log-entry`、`log-sub`、`drop`、`rebase`、`diff` は、終了コード 1 で拒む（4 回目の重大 2）。続けて書くときは、新しい `begin` から始める。
- `new` は、`D/new/<P>` の親のディレクトリを作り、計画に項目を足す。中身はモデルが書く。`edit` は、今の行き先を `D/base/<P>` と `D/edit/<P>` に写す。行き先がなければ拒む。
- `list` は、`K` の作業用のフォルダー（名前、wiki のルート、`plan_id`、作った時刻、項目の数、当て終えた印の有無）と、`--wiki` で指した wiki の日誌（`plan_id` ごとの状態。`pending`、`prepared`、`aborted`、`stuck`、`done` のどれか）、ロックの持ち主、`P` の差分の数を出す。`abort` は、`Writer` で `D` を消す。
- `wiki_apply.Plan` と `wiki_apply.apply_plan()` は、Python の書き手のための入口である（6 節の「ライブラリとして呼ぶとき」）。

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功（`already_applied` を含む） |
| 1 | 引数かファイルの誤り（ハッシュの不一致、パスの規則、実体の検査、raw の検査、管理領域の検査、初期化されていない wiki、排他作成ができないファイルシステム、7a か 7b で置けずに戻した `aborted` を含む） |
| 3 | 競合（何も書いていない） |
| 4 | ロックを 3 分待っても取れない。差分を `P/<差分の名前>` に置いた（wiki のページは何も書いていない） |

## 保証しないこと

1. **人が実際に読んで決めたこと。** モデルが `diff` の差分をユーザーに見せずに `apply` を実行することは、機械では止められない。セッションの取り込みで `scan` を流さずに `apply` を実行することも同じである。手順の遵守に頼る。
2. **書く段に加わらない書き手との競合。** 移っていない手順と、10 節の表で「残す」とした手順（lint のページの分割、統合、名前の変更、削除）のモデルの Edit と Write、エディター、ほかのスクリプト、同期のツールでつないだほかの PC の書き手は、ロックを取らない。その書き込みが、`apply` の 5〜7 の間に同じファイルに入ると、どちらかの変更が消えうる。書く段は、用意したあとの変更を、`edit` なら競合として、`ops` なら今の中身に足して扱い、黙って消さないが、置き換えの瞬間に重なったものは見分けられない。`log-sub` の `nth` も、そうした書き手が前に同じ字面の見出しを差し込めば、別の項目を指しうる。日誌を前に進めるときの「どちらでもない」は、`stuck` にして止める。
3. **同じページの別の箇所への並行の直し。** ファイルの全体で比べるので、競合になり、用意し直しと承認のやり直しが要る。消えはしないが、手間がかかる。
4. **別名を見分ける範囲。** 見分けるのは、リンク、再解析点（Windows のジャンクションとボリュームの mount を含む）、mount point（`st_dev` が親と違うもの、Linux では `/proc/self/mountinfo` にあるもの）である。`st_dev` を変えない mount を `/proc` なしで作る OS（FreeBSD の nullfs など）、UNC の共有のサーバーの側の別名、ディレクトリのハードリンク（古い HFS+ の Time Machine）、`st_ino` が 0 のファイルシステムでの実体の比べは、見分けない。検査のあとに別名を作り替えることは考えない（作者の判断の 4）。
5. **raw のルートの役割。** 知られた置き場所（wiki、`.wiki-cache`、`data_dir()` の全体（MCP の索引、rag の派生データ、書く段の管理領域））と重なることだけを断る。ほかの道具が中身を消すディレクトリに raw のルートを置くことは、見分けない。
6. **複数の PC からの同時の書き込み。** 同期のツールで共有した wiki では、ロックのファイルが PC ごとに作れてしまい、あとで同期の衝突になる。ネットワークのドライブの上の wiki では、ファイルシステムが重ねて作らないことを守れば、ロックのファイルが PC をまたいで効くが、確かめていない。
7. **意味の重複。** 同じ概念を別のスラッグで作ることは防がない。`index_duplicate` は、同じ行き先の項目を 2 回載せることだけを止める。
8. **作業用のフォルダーの文。** 用意した文は、`apply` か `abort` まで、利用者のデータのディレクトリの `K` に残る。日誌の `after/` と `before/` には、当てた中身と当てる前の中身が 14 日残り、待ちきれなかった計画の差分は `P` に残る。どちらも `.wiki-cache` の下で、Git では無視されることを確かめるが、バックアップや同期のツールが拾うことは防がない。
9. **`stuck` の間の停止。** `stuck` の日誌が 1 つでもあると、`recover` で片付けるまで、その wiki のどの計画も書かない（日誌とロックが wiki ごとなので、ほかの wiki は止まらない）。`stuck` になるのは、6 節の「`stuck` になる時」の 4 つ（書く段に加わらない書き手が日誌の進む前に同じファイルを書いた、戻すことにも失敗した、日誌が壊れた、日誌の raw のルートが検査を通らない）だけである（計画そのものが置けないときは、7c か前に進める途中で戻して `aborted` になり、`stuck` にならない）。
10. **戻すことの限界。** 戻すのは、この計画が置いた項目を「前」の中身に置き直すことで、置いてから戻すまでの間に、wiki を読んだ道具（MCP の索引、閲覧）が「後」を読むことは防がない。ロックの中の短い間である。
11. **印の名前のページ。** 大文字と小文字を区別しないファイルシステムでは、書く段に移る前にできた、`schema.md` という名前のページ（大文字と小文字によらない）は、そのディレクトリを子の wiki に変えている。書く段は、そのディレクトリに書かず、名前を変えるよう伝えるだけで、名前を変えない。
12. **wiki の間の別名と、`.wiki-cache` を消すこと。** ロックは wiki ごとなので、2 つの wiki の間に bind mount などの別名があり、同じファイルを 2 つの wiki のパスから書ける配置では、2 つのロックが同じファイルを守れない。利用者が `.wiki-cache` を消すと、ロック、日誌、差分、当て終えた印が消え、動いている持ち主がいれば並びうる。印が消えると、`--keep` で残した計画を、もう一度当てうる。どちらも、書く段に加わらない操作として扱う。
13. **ロックを外す操作。** `unlock --force` で生きている持ち主のロックを外すと、2 つの書き手が並びうる。持ち主がファイルを閉じてから消すまでの短い間に `unlock` が重なると、新しい書き手のロックを消しうる。どちらも、持ち主が動いている間に `unlock` を使わない限り起きない。持ち主が落ちて残ったロックは、利用者が外すまで残り、その間、その wiki には誰も書けない（作者の判断の 2）。
14. **記録にもページにもない raw のルート。** 根と木の重なりの検査に使う raw のルートは、計画、記録、ページの `raw:` から作る。書く段に移る前に別の raw のルートに取り込み、その raw を引くページも消した raw のルートは、どこにも現れないので、その木が `W` や `K` の木と重なっても見分けない。その raw のルートの木の中に `W` があれば、`W` の中に残る原本を、ふつうの `edit` で書き換えうる（15 回目の重大 1 の後半。16 版目の「raw のファイルを書き換えることはない」は誤りだった）。利用者が `raw-roots --add` で足せば、重なりを断る。

## まだ確かめていないこと

- Windows で、UNC の共有を経由したパスの `os.stat` が、ローカルのパスと同じ `st_dev` と `st_ino` を返すか。
- `msvcrt.locking` と `fcntl.flock` が、ネットワークドライブの上でプロセスの間の排他になるか。
- ロックを持つ時間と、ページの `raw:` を読む時間と、mount point の列挙にかかる時間の実測。
- macOS で、bindfs などの mount が、`st_dev` の違いで見分けられるか。
- Claude Code のサンドボックスの中から、`data_dir()` の下（作業用のフォルダー）と、wiki の `.wiki-cache` の下（ロック、日誌、差分）に書けるか。
- ネットワークのドライブ（SMB）の上で、`os.link` と `os.rename` が、ロックのファイルを重ねて作らないことを守るか。
- Windows で、持ち主が開いたままのロックのファイルを、`unlock --force` が消せないこと（共有の削除の許可がない開き方）を、Python の `open` で確かめる。
- Windows の `msvcrt.locking` で、ファイルの終わりより後ろ（2^30 バイト目）の 1 バイトをロックでき、そのあいだに別のプロセスが中身を読めること（12 回目のレビューで、手元の Windows で確かめられた）。ネットワークのドライブで同じことができるか。
- Windows で、ディレクトリを同期する手段がないまま、NTFS のジャーナルが、名前の変更の順番を電源が切れても保つか（公開の順番の 3 と 4）。
- Windows で、ほかのプロセス（ウイルス対策、検索の索引、Obsidian）が行き先を開いているとき、`replace_with_retry()` の 1 秒の試し直しで足りるか。足りなければ、`apply` の 7 の途中で止まり、日誌を前に進めることになる。
- 既存の wiki の `index.md` と `log.md` に、4 節の規則に合わない形（見出しの重複、テンプレートと違う置き換えの行、箇条書きでない索引の項目）がどれだけあるか。
