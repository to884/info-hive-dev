# wiki のページの集合とリンクの規則を 1 か所にまとめる（2026年11月9日）

[ADR-0010](../adr/0010-wiki-browse-separates-core-from-delivery.md) の「承認のあとの作業」の 1 と 2 を、`info-hive-wiki` で行う計画である。browse の実装（`commands/browse.md` など）の前に済ませる。[優先順位の文書（6 版目）](../research/feature-priority-2026-11-06.md)の 1 位に当たる。

最初の版は、Sol の敵対的レビューで却下された（[design-review-1.md](../agent-runs/2026-11-09-wiki-page-set-review/design-review-1.md)）。この版は、その指摘を受けて決め直したものである。指摘と対応の対照は、この文書の最後にある。

## 目的

- 「どのファイルを wiki のページとして数えるか」と「本文のどこから wikilink を拾い、どう解決するか」を、1 つのモジュールに置く。lint、search（とそれを使う MCP の索引）、グラフ、stats、判定レイヤーがそれを使う。のちに browse の中核も使う（ADR-0010 の決定の 1）。
- lint に「大文字と小文字だけが違うページ」の検査を足す（決定の 3）。

## 今の食い違い（wiki 0.8.0、`c23ae5b`）

| スクリプト | 除く最上位のファイル | 除く最上位のディレクトリ | リンクの抜き出し |
| --- | --- | --- | --- |
| `wiki_lint.py` `collect_pages` | `SCHEMA.md`、`index.md`、`log.md`、`README.md` | `indexes`、`graph`、`raw`、`.evolution`、`assets` | 本文全体を正規表現で拾う |
| `wiki_search.py` `collect_pages` | `SCHEMA.md`、`index.md`、`log.md` | `indexes`、`graph`、`raw`、`.wiki-cache`、`.evolution` | 同上 |
| `wiki_graph_extract.py` `collect_pages` | lint と同じ | `indexes`、`graph`、`raw`、`.evolution` | 同上 |
| `wiki_stats.py` | `SCHEMA.md`、`log.md`、`README.md`（`index.md` は行数だけ読む） | lint と同じ | 同上（解決せず、ステムで数える） |

- どれも、名前が `.` で始まるファイルを除く。
- `clean_link_target()` は lint、search、graph の 3 か所にある。lint は区切る前に NFC にそろえ、ほかの 2 つは区切った後にそろえる。`resolve_link()` も 3 か所にあり、中身は同じである。
- search の集合は、MCP の `query` の索引（`wiki_index.py` の `WikiIndex.refresh()`）、`wiki_decide.py`、`setup_wiki.py` も使う。`wiki_graph_lint.py` は `wiki_graph_extract.collect_pages()` を使う。
- `wiki_search.split_sections()` は、`` ``` `` か `~~~` で始まる行のたびにフェンスの内外を反転させる。4 連のバッククォートの中の 3 連、引用やリストの中のフェンスを見分けられない。`wiki_decide.contradiction_pairs()` は、分けたセクションの本文から wikilink を拾う。

## 決めること

### 1. ページの集合

`skills/info-hive/scripts/wiki_pages.py` に置く。標準ライブラリ、`wiki_text.py`、同梱した markdown-it-py（`scripts/_vendor/`）だけを使う。lint と stats は、利用者が何も入れずに動く。

- ページは、wiki のルートからの相対パスが `.md`（拡張子の大文字と小文字は問わない。Windows の `rglob("*.md")` は `Upper.MD` も返し、0.8.0 までもページだった）で終わり、最上位の `SCHEMA.md`、`index.md`、`log.md`、`README.md` と、最上位の `indexes/`、`graph/`、`raw/`、`assets/`、`.evolution/`、`.wiki-cache/` に当たらず、ファイル名が `.` で始まらないファイルである。
- `.` で始まるディレクトリは、名前を挙げたもの（`.evolution/`、`.wiki-cache/`）だけを除く。最初の版の「どの深さでも除く」は採らない。`concepts/.NET/` や `.archive/` のような利用者のページが、リンク切れになり、検索から消えるからである（レビューの重大 5）。`.obsidian/` と `.trash/` の中の Markdown も、今までどおりページとして数える。
- 変わるのは、lint と stats が `.wiki-cache/` を、search が最上位の `README.md` と `assets/` を、グラフが `assets/` と `.wiki-cache/` を、新たに除くことだけである。

### 2. リンクの抜き出し

閲覧の中核は、markdown-it（`commonmark`、`html` は無効、`table` は有効）で本文を描き、本文の文字（`inline` の中の `text` のトークン）の中の `[[...]]` だけをリンクにする（PoC の `gen.py`）。`wiki_pages.extract_wikilinks()` は、**同じ解析器を同梱して**、同じトークンから拾う。

- **同梱するもの**: markdown-it-py 3.0.0 と mdurl 0.1.2（どちらも純粋な Python、MIT ライセンス）を、PyPI の wheel のまま `skills/info-hive/scripts/_vendor/` に置く。SHA-256 を PyPI の公表値と照らし、ライセンスの文書と取得元を `_vendor/README.md` に記録する。`wiki_pages.py` は `_vendor/` を `sys.path` の先頭に足して読み込み、版が `MARKDOWN_IT_VERSION` と違えば止まる。
- **抜き出し**: `_MD.parse(body)` のトークンを順に見て、`inline` の子の `text` の中だけを `WIKILINK_RE` で探す。コードブロック、インラインのコード、参照リンクの定義、リンクの行き先とタイトルの中は、`text` にならないので拾わない。escape と文字参照は、markdown-it が戻した文字から探す（`\[\[x]]` は `[[x]]`、`[[R&amp;D]]` は `[[R&D]]`）。
- **セクションの分け目**: `split_sections` は、markdown-it の `heading_open` のうち、行頭（字下げなし、引用やリストの外）の ATX の見出しの行でだけ分ける（`heading_line_mask`）。コードブロックの中の `# ` と、`#　見出し`（`#` のあとが全角空白）では分けない。行は Markdown と同じく CR と LF だけで分ける（`str.splitlines()` は U+2028 などでも分けるので使わない）。セクションの `links` は、本文全体を 1 度だけ解析した結果から集める（段落や表の行などのリンクを、それが始まる行に置き、セクションの行のものを集める）。セクションの本文を切り出して読み直すと、参照リンクの定義（`[r]: url`）が別のセクションにあるとき、本文全体にはないリンクが生まれるからである（5 回目のレビューの重大 1）。判定レイヤーはこの `links` を使う。`extract_wikilinks(body, headings=False)` は、セクションの分け目の見出しの中のリンクを除いたもので、セクションの `links` を全部集めたものと同じになる。
- **手で写す方式をやめた理由**: 最初の 4 回の実装は、markdown-it のブロックの規則を標準ライブラリで写した。Sol の実装レビューは 4 回とも却下で、そのたびに写し漏れ（区切り線とリストの順、表の終わり、参照リンクの定義の範囲、引用の続き方、リンクのタイトルの中のバッククォートなど）が見つかった。規則は閲覧の解析器そのものなので、写しを保守するより、解析器を同梱するほうが確実である。作者が 2026年11月9日に同梱を選んだ。
- **同梱の確かさ**: 別の場所の `markdown_it` や `mdurl` が先に読み込まれていても、同梱したものに替えて読み込み、読み込んだものが同梱したもので、版が `MARKDOWN_IT_VERSION` と `MDURL_VERSION` と同じことを確かめる。MCP サーバーの版（`code_version`）は `_vendor/` の中身も含めて計算する。検索のパースキャッシュには解析器の名前（`PARSER_ID`）を記録し、変われば作り直す。
- **代償**: プラグインに 78 ファイル、約 400 KB のサードパーティのコードが入る。版を上げるときは `_vendor/README.md` の手順に従い、閲覧の中核と同じ版にそろえる。ページごとに markdown-it で解析するので、正規表現だけのときより遅い。1,000 ページ（1 ページ約 5,000 文字）の wiki で、lint のページの収集は 0.65 秒から 2.2 秒に、stats は 0.38 秒から 1.9 秒に、検索の収集（キャッシュなし）は 0.7 秒から 2.3 秒になった（Windows、温まった状態の 2 回の平均）。検索はキャッシュがあれば変わったページだけを解析する。同じ本文を、リンクの抜き出しとセクションの分割で 2 度解析しないよう、解析の結果を覚えておく。
- **残る違い**: なし。閲覧が同じ版の解析器と同じ設定を使う限り、拾うリンクは同じになる。

### 3. リンクの解決

`clean_link_target()`、`build_link_index()`、`resolve_link()` を `wiki_pages` に移す。規則は今の 3 つと同じである（パスを付けたリンクは、そのパスがちょうどあるときだけ解決する。大文字と小文字を区別する）。`clean_link_target()` は、最初と最後の両方で NFC にそろえる。

### 4. 使う側の変更

| スクリプト | 変更 |
| --- | --- |
| `wiki_lint.py` | `collect_pages` は `iter_page_files` と `extract_wikilinks` を使う。`clean_link_target`、`resolve_link`、`SKIP_TOP_LEVEL_*` は `wiki_pages` から読み込んで、同じ名前で残す（ほかのスクリプトと試験が `wiki_lint.resolve_link` などを使っているため） |
| `wiki_search.py` | 同上。`extract_wikilinks`、`clean_link_target`、`build_link_index`、`resolve_link` も同じ名前で残す。`split_sections` は `heading_line_mask` で見出しを判定し、行を `split_lines` で分ける。解析のキャッシュの `PARSE_CACHE_SCHEMA` を 3 から 4 に上げる（`links` とセクションの中身が変わるため） |
| `wiki_graph_extract.py` | `collect_pages` は `iter_page_files` と `extract_wikilinks` を使う。`clean_link_target`、`resolve_link_slug` は `wiki_pages` のものを使い、名前は残す |
| `wiki_stats.py` | ページの数え方を `is_page_path` にそろえる。`index.md` の行数を読む処理は残す。リンクは `extract_wikilinks` で拾う |
| `wiki_decide.py` | `contradiction_pairs` は、セクションの `links`（本文全体の 1 度の解析から集めたもの）を使う。セクションの本文を読み直さない |
| `wiki_mcp_common.py` | サーバーの版を決めるファイルの一覧（`SERVER_FILES`）に `wiki_pages.py` を足す。足さないと、`wiki_pages.py` だけを直したときに、動いているサーバーが古い規則のまま使われる（レビューの重大 4） |

`wiki_index.stat_signature`（MCP の索引の変更の印）は、ページの走査と同じく拡張子の大文字と小文字を問わずに Markdown を集める（`*.[mM][dD]`）。そうしないと、Linux で `.MD` のページを足したり直したりしても、MCP の索引が気づかない（6 回目のレビューの重大 1）。`collect_index_entries`（lint の索引の検査）と `strip_fences_and_images`（ページの大きさ）は変えない。

### 5. lint の `case_only_duplicates`

- ページの NFC の相対パスと、その途中のディレクトリのパスを集め、大文字と小文字を同一視すると同じになるのに綴りが違うものの組を挙げる。比べるキーは、NFC、`casefold()`、NFC の順にそろえたものである。`casefold()` のあとに NFC でなくなる組（`ΐ` と `Ϊ́`）を取りこぼさないため（レビューの軽微な指摘）。
- 1 件は `{"kind": "file" | "dir", "paths": [...]}` とする。`dir` は `Concepts/` と `concepts/` のように、ディレクトリの名前が違う場合である。
- `summary.case_only_duplicates` に件数を入れる。テキストの報告にも出す。
- NFC にそろえると同じになるだけのもの（正規化の違い）は、ここでは挙げない。今までどおり `duplicate_slugs` が `normalization_collision` として挙げる。
- `Foo.md` と `foo.MD/` のように、ファイルとディレクトリが大文字と小文字だけで違う組は挙げない。`.MD` で終わるものはページではなく、閲覧の書き出しでも `Foo.html` と `foo.MD/` は同じ場所を取らないからである。

### 6. 利用者に見える変化

- **lint**: コードの中の `[[...]]` を、リンク切れにも被リンクにも数えなくなる。`\[\[x]]` はリンクとして数える。`.wiki-cache/` の Markdown を検査しなくなる。`case_only_duplicates` が増える。
- **search と MCP の `query`**: 最上位の `README.md` と `assets/` の中の Markdown が検索に出なくなる。外れるページがある wiki では、BM25 の文書数と文書頻度が変わるので、残ったページどうしの順位も変わりうる。結果の `links` から、コードの中の `[[...]]` が消える。4 連のバッククォートや引用の中のフェンスの中の `#` で、セクションが分かれなくなる。MCP の `get_page` は収集したページだけを返すので、`README.md` を引けなくなる。
- **グラフ**: コードの中の `[[...]]` から `mentions` のエッジを作らなくなる。`assets/` と `.wiki-cache/` の Markdown をノードにしなくなる。0.8.0 で作った `graph/graph.sqlite` などは、`wiki_graph_extract.py` で作り直すまで古いままである。MCP の `graph` も、作り直すまで古い結果を返す。
- **stats**: ページの数が lint と同じになる。リンクの数、平均、`most_linked` から、コードの中の `[[...]]` が消える。
- **判定レイヤー**: 矛盾の候補（`wiki_decide.py contradictions`）から、コードの中のリンクによる組が消える。

版は wiki 0.9.0（マイナー）にする。lint の JSON にキーが増え、検索とグラフの対象が少し変わる。0.x の版なので、マイナー版で入れる。変更履歴には、グラフを作り直すことを書く。

## 範囲の外

- browse の中核と画面（ADR-0010 の作る順序の 2 以降）。
- `wiki_key()` が大文字と小文字を常に同一視する欠陥（ADR-0010 の作業の 5、別の課題）。
