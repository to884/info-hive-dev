## 1. 表示するもの

記事の最初の h1 の直後に、そのページの概要を表示する。
元ページが変わった概要には警告を付ける。
壊れた概要を読めない場合も、記事の本文は閲覧できるようにする。

概要を作るのは `/wiki:overview` であり、browse は作成・修復・削除を行わない。
保存の format は 2 のまま、`assets/overview/<P>.overview.md` も変えない。
概要を検索、索引、被リンク、グラフ、ページ数へ加えない。

サーバーと静的版は、同じ写しと中核から同じ概要の HTML、状態、SVG を作る。
Mermaid は既存の方式に従い、サーバーでは図、静的版ではコードを表示する。
静的版で Mermaid を描く機能は今回追加しない。

## 2. 画面

概要は Fluent 2 の Accordion のクラスを使う `<details>` と `<summary>` で表示する。
見出しの文字は「概要」。本文と同じ幅を使い、図は現在の Card と Image のクラスで表示する。
新しい画面用の JavaScript と、折りたたみ状態の保存は追加しない。

| 状態 | 表示 |
| --- | --- |
| `none` | 概要の枠を出さない |
| `fresh` | 開いた概要を出す。生成日と生成モデルは、文字列として記録がある項目だけをエスケープして添える |
| `stale` | 閉じた概要を出す。summary 内の「概要」の隣に「元のページが更新されている」と文字で示し、開いた中にも警告を置く。本文と図は古いものと分かる形で読める |
| `broken` | 概要の本文と図は出さず、「概要を読めない。/wiki:overview で作り直せる」と MessageBar に出す |
| `page_unreadable` | 概要の本文と図は出さない。元ページも描けないときは、既存のページの読み取りエラーを優先する |
| `page_unknown` | 結び付けを確かめられないので、概要の本文と図は出さない |
| `orphan` | 対応する記事がないので記事への枠は出さない。診断データに記録する |
| 概要の一覧を確認できない | 各記事に「概要の一覧を確認できない」と短い MessageBar を出す。未作成とは表示しない |

元ページの h1 は、Markdown の解析結果で最初の、入れ子でない `heading_open`（h1）とその閉じ字句で決める。
コードの中の `#`、引用やリストの中の h1 は差し込み位置にしない。
h1 がなければ `_body` の先頭に置く。h1 が複数あれば最初の1つだけを使う。
h1 より前に文章があれば、その位置は変えない。
メタ欄、本文の文章、被リンク、関係表、既存の診断の位置は変えない。

概念上の並びは次のとおりである。

```text
メタ欄
_body
  ページの h1
  概要（fresh は開く、stale は閉じる）
  ページの残りの本文
被リンク・関係表・診断
```

本文の見出し ID は、概要を差し込む前に従来どおり付ける。
概要の枠と概要内の見出しには ID を付けない。
本文の「概要」という見出しや、同じ見出しが繰り返されるページでも、リンク先の ID と検索の見出し一覧を変えない。
summary は標準のキーボード操作を使い、フォーカスの輪郭、閉じたときの表示、狭い画面での折り返しを確認する。

## 3. 同じ写しから判定する

概要も `Snapshot` の入力にする。
`Core` は、ページの写しと概要の写しだけから状態を決め、描く途中でファイルシステムへ問い合わせない。
段階1の `status()` や `inspect_wiki()` を `Core` から呼ぶ方法は採らない。これらは現在のディスクを読み直すからである。

元ページの `PageState` は、描けるページの表だけでなく、写しに載った全 `page` 入力から作る。
UTF-8 でないページ、開けなかったページも識別子の有無には数える。
ハッシュは `page_text_sha256` を使い、BOM と改行を正規化した全文を比較する。
本文の frontmatter を除いたハッシュにはしない。

同じ NFC の識別子へ複数のファイルが当たる場合と、別の識別子が同じ `<P>` になる場合は、概要をどちらにも結び付けない。
`PageState("unknown")` と衝突の診断を使い、読める方や先に現れた方を選ばない。
ページの名前の集合が不明なときは、現在の `InputsUnknown` の扱いを維持し、新しい中核を採らない。

状態は `wiki_overview.classify` を使う。
`stale` のハッシュ、frontmatter、図の対応を browse が独自に判定しない。
元ページの更新後に概要だけを描き直すこともせず、新しい `Core` へ切り替える。

## 4. 読むための共通の口

現在の `_scan_sidecars` は、走査と読み取りを一度に行う。
これを、名前と属性を調べる `walk_sidecars` と、1件を読む `read_sidecar` に分ける。
どちらも `wiki_overview` が持ち、既存の status と lint もこの口を使う。
CLI の引数、JSON のキー、既存の所見と終了コードは変えない。

`walk_sidecars(root)` は次を返す。下記の名前は内部 API の提案である。

| 欄 | 内容 |
| --- | --- |
| `files` | 現在の走査で概要の候補とするもの。`key`、`disk_rel`、`size`、`mtime_ns` と、属性を調べられたかを持つ。中身は読まない |
| `unexpected` | ディレクトリ、リンク、規定外の名前など、現在 `unknown_entry` とするもの。相対パスと、取得できた大きさ・更新時刻・種類を持つ |
| `directory_state` | `ok`、`absent`、`unreadable`、`unsafe`。名前の集合を最後まで取れなければ `unreadable` |

`assets` と `overview` の綴り、道の途中のシンボリックリンクと再解析点を、段階1と同じに確かめる。
ファイルは lstat し、リンクと複数のハードリンクを持つものを読まない。
途中の一覧取得、列挙、属性取得で起きる OSError は、既存の `read_os` の意味に合わせて扱う。
列挙が途中で失敗した場合は、その回の部分的な候補を使わない。
名前の集合の不明と、名前は分かるが1件を読めないことを区別する。

`read_sidecar` は、道を再確認してから、上限 8 MiB を読む口で強制する。
読み始めたあとで大きくなっても、上限を超えて読み続けない。
副作用を持たず、`Sidecar("ok", data)`、`Sidecar("absent")`、`Sidecar("unreadable")` のいずれかを返す。
書き手が同時にファイルを原子的に置き換える場合は、読む前後の走査の比較で再試行する。
同じ大きさと更新時刻を意図して復元する変更、検査と操作の間のリンクへの差し替えは、既存の入力検出と段階1と同じ保証外である。

`wiki_browse_fs.walk_inputs` は、既存の入力の後ろに次を足す。

| 入力の種類 | 内容と読み方 |
| --- | --- |
| `overview` | 規定の名前の候補。`read_sidecar` で、バイト列と SHA-256、または読み取り失敗を写しに持つ |
| `overview_entry` | 規定外の項目。属性だけを持ち、中身を読まない。診断と更新検出のために載せる |
| `overview_dir` | 一覧を確認できない、または安全なディレクトリでないという印。中身を読まない |

概要のディレクトリがない場合は入力を足さない。
一覧が読めなくても、通常のページの走査を成功として扱えるなら記事を描く。概要は一覧不明の表示にする。
安全でない名前の項目を、通常のファイルに解決して読むことはしない。
規定のサイドカー名と同じ名前の不正な項目があれば、そのページでは未作成とせず、概要を読めないと表示する。
その他の規定外の項目は全体の診断だけに出し、読める概要を無効にしない。

既存の status/lint では、規定外の項目を `unknown_entry` とする意味を維持する。
一覧不明は引き続き `overview_problems: null` であり、空配列にしない。
共通走査への変更前後で、段階1の全試験と所見の一致を確かめる。

## 5. 本文と図を取り出す

`wiki_overview` に、入出力を行わない `view(name, sidecar, page)` を加える。
戻り値は `state`、`detail` と、表示できる場合の `body`、`figures`、表示用の生成日・モデルである。
`classify` で `fresh` か `stale` と決まった場合だけ、同じバイト列を解析して本文と図を返す。
別の読み取りを挟まず、壊れた概要の一部だけを返さない。
`embedded_figures` と、この口の図の抽出には同じ実装を使う。

本文の開始位置は、サイドカーの組み立ての境界から決める。
既存の `parse_frontmatter_raw` は閉じの `---` のあとを `\s*` で読むため、返された本文には、下書きの先頭の空行が残らない場合がある。
metadata の値の解釈は既存の関数を共用し、本文の切り出しは、その戻り値の本文へ頼らない。
LF に正規化したサイドカーの、frontmatter の閉じの物理行（`---` と任意の半角スペース・タブ）の末尾 LF までをヘッダーとする。
その直後の1個の LF だけを `_assemble` が加えたヘッダーと本文の区切りとして外し、残りの先頭の空白と空行は本文に保つ。
format 2 の書き手はこの区切りを出す。区切りが欠けている手書きのサイドカーは、本文と図の組み立てが不正として拒否する。
これを sidecar 用の純粋な解析処理に置き、通常の記事を読む frontmatter パーサーの規則は変えない。
先頭に空行、タブの行、字下げコード、Unicode の空白を含む65,536バイトの下書き8件でも、提案した境界から取り出した本文が正規化下書きと一致することを確認した（[先頭の検証記録](../agent-runs/2026-11-17-wiki-overview/stage2-leading-envelope-probe.json)）。

format 2 の本文には、64 KiB 以下、h3 以下、wikilink なし、本文中の `svg-figure` なし、という保存規約がある。
本文の構造を検査する純粋な共通関数を設け、`check`、`classify`、`view` の解釈をそろえる。
サイズを数える対象は、下書きのファイルと、サイドカーの区切りを外した本文とで次のように区別する。

- 下書きのファイルは、現在と同じく、BOM の除去と改行の正規化より前のバイト列を64 KiB以下に制限する。
- 構造を検査する本文は UTF-8 の BOM を除き、CRLF と CR を LF にそろえた文字列である。サイドカーでは、書き手が本文の後ろへ加えた2個の LF を、本文の一部に数えない。
- SVG のフェンスがある場合は、フェンスの始まる物理行の直前までを LF も含めて取り出す。現在の行を join する処理は区切りの1個を失うので、LF で区切った行の位置から、その LF も保存した接頭辞を作る。Unicode の改行文字まで分割する `str.splitlines()` は使わない。
- 図なしなら残りの本文全体、図ありならその接頭辞から、末尾が2個の LF で終わる場合だけ、ちょうど2個を外す。`rstrip` で空白や改行をまとめて削らない。この結果を、共通の構造検査と読み取り側の64 KiB検査に渡す。
- 図なし・図あり、下書きの先頭と末尾の空行、先頭の字下げ、BOM、CRLF を組み合わせ、65,536バイトの正常な下書きが保存後も受理されることを試す。65,537バイトの下書きは引き続き拒否する。

書き手が下書きに加える区切りの規約と、ファイルへ書くバイト列は変えない。
正規化前のサイズは保存後には復元できないため、読み取り側では区切りを外した正規化済み本文のサイズを検査する。
この抽出の定義は、段階1が実際に保存した上記16通りの境界値へ当てはめ、正規化した下書きと一致することを確認した（[境界の検証記録](../agent-runs/2026-11-17-wiki-overview/stage2-size-envelope-probe.json)）。
手で改変したサイドカーも、本文の保存規約を破れば `broken/figures` とする。
既存の図の不一致と同じ組み立ての検査として扱い、format の番号と状態の優先順は変えない。
書き手が生成できる、正しい format 2 の概要の状態は変わらない。
この補強は段階2の提案に含み、承認時に段階1の6.5の `broken/figures` の説明へも明記する。
現状の読み取り側が、手で h1、wikilink、64 KiB 超の本文へ変更したサイドカーを `fresh` とすることは、段階1の公開 API で作った一時 wiki で確認した（[検証記録](../agent-runs/2026-11-17-wiki-overview/stage2-body-validation-probe.json)）。
この結果は既存の読み取り側の確認であり、共通化後の検査が通ったという報告ではない。

概要の Markdown は `wiki_pages.new_parser()` で解析する。HTML は既存どおり無効である。
テーブルの位置合わせは、本文と同じ CSS クラスへ変換し、style 属性を残さない。
普通の Markdown のリンクは本文と同じ許可スキームとエスケープを使い、外の URL を自動で読み込まない。
画像は検査済みの `#fig-<名前>` だけを置き換え、svg のフェンスと frontmatter は HTML に出さない。
既存の `_transform_inline` が持つ画像とリンクの規則は共通化し、概要では wikilink の解決と本文のリンクのカウンターを使わない。
概要の字句を本文の `_prepass`、見出し ID、リンク、被リンク、要約の抽出へ渡さない。

検査と字句の描画で予期しない例外が起きたときは、その概要を「表示できない」として診断し、元ページの描画は続ける。
元ページそのものを描けない場合は、既存の `_broken_page` を使う。

## 6. SVG の出力

埋め込み SVG は、検査済みのバイト列を変えずに browse の出力へ写す。
出力の名前は `assets/overview/<SVGのバイト列のSHA-256全文>.svg` とする。
同じ内容の SVG は1つの出力を共有できる。
同じ名前へ異なるバイト列が当たった場合は、その概要の表示を止め、診断する。
`assets/wiki/` の既存の図と、同梱の画面のファイルとは名前空間を分ける。

`Core` は `(ページのP, 図の名前)` から出力名を引く表と、出力名から SVG を引く表を持つ。
`knows`、`asset_bytes`、`render_all` に、この表を接続する。
サーバーは既存の SVG と同じ `image/svg+xml` と `CSP_SVG` で返す。
静的版は、既存の世代の作成処理へ SVG も渡し、作成したファイルの一覧へ載せる。
図だけを wiki や書き出し先へ先に追記する処理は作らない。

画像は `<img>` にし、幅・高さは共通の `svg_size` から取り、手書き SVG の地は明るい配色に保つ。
svg の文字列を HTML の DOM に入れず、svg へのリンクも作らない。
外の参照と script が含まれる場合も、既存の SVG の画像としての隔離を使う。
ページ本体の CSP を緩めず、inline の script と style 属性を増やさない。

内容から URL を決めるので、HTML の取得後に概要が更新されても、古い画像の URL が新しい内容を返すことはない。
要求の間に中核が更新され、古い URL が404になることはある。そのときは再読み込みで新しい世代を取得する。
複数の HTTP 要求を1つの世代へ固定する仕組みは、今回追加しない。

## 7. Mermaid と折りたたみ

概要を `_body` の中へ差し込むので、既存の `figures.js` が、その中の Mermaid も拾える。
専用の2回目の探索や、概要だけのレンダラーは追加しない。
iframe の sandbox、同時数、時間制限、配色の切り替え、失敗時の警告とコードの表示を共用する。
`FRAME_VERSION` と同梱の Mermaid は変えない。

閉じた概要にある図も、現在の探索で描く。
開いたときに SVG と Mermaid が幅0のまま残らないこと、閉じたまま配色を変えたあとで開いても読めることを実際のブラウザで確かめる。
必要な修正は表示寸法と既存の描画処理に限定し、inline style は使わない。
静的版は既存と同じく Mermaid のコードを表示し、実行用の iframe を作らない。

## 8. 更新とキャッシュ

追加する入力も、読み取りの前後で比べる2回の一覧、`signature_of`、`Snapshot.generation` に含める。
サイドカーの作成・削除と、大きさ・更新時刻を変える差し替え、一覧不明への変化を、同じ入力集合から検出する。
内容の読み取り失敗は、実際に写しを採ったときに観測した場合だけ反映できる。
`CORE_VERSION` は上げる。プロトコルの外形は追加だけなので、`PROTOCOL_VERSION` は変えない。

概要を読めなかったため OS のエラーになった入力と、一覧を作れなかった印は `Snapshot.transient` に載せる。
更新時刻が変わらず読み取り権限だけが戻ったときも、既存の `BrowseState._should_retry` で再試行する。
UTF-8 でないものと既知の不正な項目は、入力が変わったときに再試行する。
規定名のハードリンクは読めない概要として一覧に残し、CLI と browse とも `broken/unreadable` にする。署名の属性に拒否の印を含める。リンク数が1に戻ると印が消えるので、サイズと更新時刻が同じでも回復を検出する。
一部の概要が読めなくても、その理由だけで新しいページの本文を古い中核へ戻さない。

正常に読んだ入力が、署名を変えずに読み取り権限だけを失った場合は、その変更だけを理由には読み直さない。
そのため、再読み込みをしても同じ中核を使うことがある。既存の署名による高速な判定の範囲を維持し、権限変更の監視は追加しない。
別の入力の変更などで次の写しを採ったとき、またはサーバーを再起動したときに、新しい読み取り失敗を観測する。
一方、既に失敗を観測して transient に載っている入力は、署名が同じでも既存の間隔で再試行するので、権限回復を反映できる。

`_body_cache` は、その中核の本文と概要を合成した結果を持つ。
別の世代へキャッシュを引き継がず、同じ中核では何回描いても同じ HTML を返す。
描画の失敗後の再試行にも、元の字句から組み直す既存の規則を使う。
概要の状態を描画時の現在時刻やディスクの状態で変えない。

ページの走査が失敗して旧中核を返すときの「表示が古い」という既存の警告と、概要の `stale` は区別する。
旧中核の概要が `fresh` でも、それは旧中核のページに対しての判定である。
既存の全体の警告を隠したり、ディスク上の現在の概要だけを混ぜたりしない。
自動で開いている画面を再読み込みする機能は追加しない。変更の反映は次の取得・再読み込み時である。

## 9. 診断と配布

診断に、相対パスとページの識別子を使う `overview_stale`、`overview_broken`、`overview_page_unknown`、`overview_page_unreadable`、`overview_orphan`、`overview_unlistable`、`overview_unknown_entry`、`overview_render_error` を加える。
一覧不明と衝突は、特定のページを推定せず全体の診断にも載せる。
概要の問題を、本文の `unresolved` や `missing_heading` として報告しない。
`manifest` は `capabilities.overviews: true` と、不完全の欄の `unreadable_overviews`、`overview_scan_unknown` を加える。

`scan_machine_info` は、出力する概要の HTML と SVG にも従来どおり適用する。
図は XML として UTF-8 であることを共通の検査で確かめてから出力する。
入力の種類が増えたあとも、`_machine_needles` が入力の実体を調べること、絶対パスや操作用のトークンを生成器が付け加えないことを確かめる。
CLI と画面の案内、`commands/browse.md`、コマンド一覧、README、Unreleased を段階2に合わせる。
リリース前に origin の最新版を確認して SemVer を決め、存在するプラグインの定義と CHANGELOG をそろえる。
段階1だけのリリースは作らない。

## 11. 承認と次の段取り

この文書は、段階1の保存先と書き手を変えず、読み取る側を追加する提案である。

## 実装レビューで明確にした境界

ADR-0029 により読まなかった記事や途中の道は、不在と区別する。サイドカーのページ識別子と拒否したパスを、ファイル名またはディレクトリの要素の境界で照合する。CLI と browse は `page_unreadable` にし、`remove --orphan` は削除を拒む。記事を読めなかった道に降りて確かめることはしない。識別子を読めず不在を確かめられない場合も、孤立の削除を拒む。

`assets` の綴り違いとリンクは安全な名前空間を確認できない状態として知らせる。概要があるかを調べるために、そのリンクをたどらない。
