# Apache Ossie を採用する info-hive-wiki の設計案

2026-11-19。設計案。info-hive-wiki 0.35.1 と、一方向 PoC で使用した Apache Ossie `0.3.0.dev0`（`0f458de`）を基準にする。採用するのは Ossie の意味定義と交換形式。info-hive は wiki の実体・主張・根拠を管理し、変更の提案、適用、公開を担う。公開ランタイムの選定は消費側の実証で決める。 [引き継ぎ要件](wiki-ontology-ossie-handoff-2026-11-19.md) · [一方向 PoC](../research/2026-11-19-ossie-wiki-export-poc.md)

## 利用者に見える動作

1. `ontology propose` は、対象 wiki の現行定義、実体、主張、新旧の記事を対象に、改名・統合・分割・廃止・再分類の候補を出す。用途と具体的な問いごとに、根拠、影響する記録、保留、試行前後の回答を示す。定義の不適合、抽出誤り、記録不足、対象の取り違え、現実の時期・版の変化を分ける。定義を保ったまま主張だけを訂正・取り下げることもできる。
2. `ontology apply` は、表示して採用された案と入力の指紋を固定して、試行済みの差分を共通の書く段に渡す。同じ最終案の再承認は省く。前提が変わり、変更内容や判断が変わるときは再試行した差分を表示する。
3. `ontology status` は、公開中の版、分析した範囲、記録に反映した範囲、未分類、同一性の保留、移行残件を示す。Claude Code と Codex で共通の操作仕様を使う。提案にはホストの LLM を利用し、適用と検証は確定済みの入力を機械的に処理する。通常の ingest も採用済みの規則を使い、定義の見直しはユーザーが指示したときに始める。

記事で判断できる範囲と原本の確認範囲を区別する。旧要約から必要な区別が失われていれば該当原本へ戻り、確認できなければ未確定とする。分析を再利用するときは、定義の版、用途と問い、参照した記事・原本の指紋が一致することを確かめる。 [設計レビューの検証結果](../agent-runs/2026-11-19-wiki-ontology-maintenance-multi/review-verification.md)

## 正本と ID

wiki ごとに永続的な `wiki_id` を `ontology/wiki.json` に保存する。データを一緒に扱う場合でも `(wiki_id, 種別ごとの ID)` で特定し、プロジェクト用とユーザー用の定義・実体を分ける。同じ ID を持つ複数のルートが同時に選ばれたら `status` で衝突を示し、横断参照・統合を保留する。復元は元の ID を使い、独立した wiki として使う複製には新しい ID を割り当てる。

Ossie 有効化後は、wiki 内の版付き領域 `ontology/` に、Ossie Ontology と判断情報、実体・主張・根拠・履歴の構造化レコードを置く。構造化レコードの初期案は UTF-8 の JSONL。Markdown は記事・引用元・利用者が読む実体ページの正本とし、意味レコードとは ID で対応づける。既存の entity ページは再利用し、未作成のページを識別の条件にしない。Ossie Core・Mapping、検索索引、SQLite などは公開版の入力から再生成する。意味レコードの更新はこの正本に集約し、Markdown の表示や互換グラフはそこから対応づける。本文の版は内容の指紋で参照し、同じ本文は複製を共用できる。

| 記録 | 識別子と保持する情報 |
| --- | --- |
| 実体 | `entity_id` は wiki 内で発行し、名前・型・ページ移動から独立させる。型と分類の版、表示名、別名、識別キー、対応ページ、判定根拠を持つ。メーカーの確定済み `entity_id` と品番の組など、採用済みの識別キーを使う。同一 wiki で確認済みのキーは1実体にだけ割り当てる。キーの構成・正規化・有効範囲は定義の版に含める。メーカーなどキーが参照する実体を先に確定し、確認済みの別名で照合する。メーカーの同一性が不明なら製品も候補として保留する。品番の全角・半角を同じとするかはメーカーの定義・根拠に従う。 |
| 主張 | `claim_id` は同じ命題を追う単位。述語 ID、役割ごとの確定実体、極性、定義が同一性に必要とした契約番号などの識別条件をキーにする。確認済みのキーは wiki 内で一意とし、根拠だけで同じ命題か決められないものは候補にする。分割や、役割・極性などキーの訂正では新しい主張を作り、旧主張と結ぶ。 |
| 主張の版 | `claim_revision_id` ごとに有効期間、適用した定義版、記録日時、根拠とのリンク、編集上の状態を固定する。候補、確定、係争中、取下げ、置換済みを区別する。開始日の訂正や根拠の追加は同じ主張の新版になる。同じ関係が中断後に再開したことが確定した場合は、有効区間を複数保持できる。別契約と分かる場合は別主張になる。 |
| 根拠 | `evidence_id` ごとに出典ページとページ版、引用、参照先と位置、原本の指紋と確認結果、取得方法、承認された開示範囲を記録する。主張の版と根拠を多対多で結び、支持・反証・背景の別をリンクに記録する。同じ命題への別記事の引用は個別に残す。 |
| 履歴 | 改訂・移行の判断を追記し、対象、元と先の版、判断者・日時・理由・根拠を持つ。`supersedes` と `contradicts` は具体的な主張の版を指す。参照先が未確定の場合は旧参照、保留理由、候補を保持し、確定した版から型付き参照を生成する。 |
| 確認範囲 | 問いの対象範囲、定義版、記事の版をキーに、該当あり・該当なし・判定不能、採用記録への反映、確認した原本を記録する。未分析は対象記事集合に確認記録がないことで判定する。保留には候補の実体・述語・期間と、不明な範囲を記録する。 |

有効期間は事実が対象とする時間。記録日時と公開版は、その主張がいつ wiki に載ったかを示す。期間は開始を含み終了を含まない。終了日のない記述は、明示的に継続が確認できた開放端、出典が確認した特定日、時点不明を分ける。特定日の確認はその日だけの確定に使い、時点不明は時点指定の確定件数に加えない。各公開版は `claim_id` ごとに現在の版を最大1つ指定する。確定には、採用済みの定義に合う役割と、追跡できる根拠を要する。対象時点の回答は、その公開版が選んだ版の有効期間を評価する。

参照は新旧の両方を残す。根拠だけの追加で命題と対象期間が同じなら、有効な反証を新版に引き継いで元の参照も保持する。命題・期間・定義が変わる場合は影響する参照を再評価し、確定できないものは保留する。同じ役割・対象・期間の肯定と否定が支持されて競合する場合は、判断が済むまで重なる範囲を係争中にする。

定義には表示名と独立した識別子を与え、定義文を Ossie の `description` に置く。定義文の正本は Ossie とする。info-hive の判断情報には、該当・非該当の条件と例、用途と問い、採用理由、識別規則を同じ定義識別子・定義版に結んで保存する。ラベルだけの改名では識別子を引き継ぎ、旧版の確定主張は定義版の対応を通じて集計できる。役割・条件・識別規則など意味が変わる定義は主張を再評価し、意味の分割には新しい識別子を割り当てる。各公開版から、履歴や保留が参照する旧 Ossie 定義と判断情報にもたどれるようにする。Ossie 文書の `version` は仕様の版とし、wiki の `definition_revision_id` と `release_id` は公開マニフェストで管理する。

## Ossie と info-hive の分担

| 範囲 | Apache Ossie | info-hive |
| --- | --- | --- |
| 型・意味 | 組織、製品、主張の版、根拠などの型、識別、対象の型、役割、宣言できる制約・導出 | wiki 固有の定義の提案・保存、根拠の要否、承認、名寄せ、分類保留と判断履歴 |
| データ交換 | Ontology、テーブル・結合・指標を宣言する Core、データを意味に結ぶ Mapping | 構造化レコードと公開スナップショットの生成、旧 ID の対応、元データとの照合 |
| 検証・回答 | 公式検証器で文書・参照を検査し、対応する消費側で Mapping・式・指標の結果を検証 | 根拠・参照の意味・移行残件の検査、版の固定、対象範囲を示した回答、既存 CLI・MCP・browse との接続 |

最初の用途は、組織と製品の関係を確認する問い。組織を1実体とし、顧客・代理店は組織、対象製品、役割、有効期間を結ぶ主張として表す。A社が製品Aの顧客、製品Bの代理店であるとき、現在の製品Bの顧客一覧に載せるには顧客であることを支持する独立の主張が必要になる。Ossie では主張の版から各役割への型付き関係を定義し、根拠と期間の対応を保つ。関係は集合で、リンクに NULL を含まないため、未確認の役割へのリンクは生成せず、その状態を記録する。 [Ossie の関係と役割](https://github.com/apache/ossie/blob/0f458dee0718b701930bf4597e1d84e427f0c8fc/ontology/ontology.md#relationships)

問いの型、対象製品、公開版、時点で確定済みの主張を選び、顧客数は `entity_id` の重複を除いた数とする。主張数は `claim_id`、根拠数は `evidence_id` で数える。Core には顧客の粒度で一意な行集合を作り、その集計を宣言する。対応エンジンの測定値を独立した SQLite の期待値と比較する。網羅性は公開版・定義版・問いの対象範囲ごとに評価する。未分析、未抽出・未反映、未分類・判定不能、同一性保留、移行残件、期間不明、主張候補、係争中、未確定の反証・訂正が影響し得る場合は「確認済み n 社」と理由を返す。残件の候補と問いの対象を識別子・期間で照合し、無関係と確定した残件を除く。範囲が不明なら関係し得る残件に含める。「0 社」と「確認済み 0 社・未確定あり」を区別する。 [Ossie Core の指標評価](https://github.com/apache/ossie/blob/0f458dee0718b701930bf4597e1d84e427f0c8fc/core-spec/relational_semantics.md#8-measure-evaluation-and-guarantees)

## 既存 wiki の移行

- **初回の読み取り**は Markdown、現行 `graph/ontology.yaml`、既存グラフを入力にする。既存の ID、ページ、型、参照、根拠を照合し、取り込み元の wiki と版を含めて旧 ID と新しい実体・主張の版の対応を残す。同じ入力を再試行するときは記録済みの対応を使い、再採番による重複を防ぐ。型の由来として、明示の `graph.node_type`、プラグイン共通の別名正規化、wiki の `maps_from`、既定の `concept` を記録する。共通の日本語 `kind` の正規化と wiki 固有の意味対応は別に扱う。明示関係は根拠と型を点検して意味レコードに移し、`mentions`、`sourced_from`、`summarizes_raw` は記事案内・出典・原本への関係として保持する。生成された記事リンクも用途に応じて従来の問い合わせに渡す。Markdown のトップレベル `aliases` は名寄せの候補情報として読み、統合には別の根拠を求める。
- **移行案**は定義の変更と、実体や主張の変更を分ける。型を統合しても実体をまとめるかは別に判断する。実体を統合・分割した場合は、該当する主張の役割と識別キーも照合し直す。重複が確定した主張は根拠を保持して対応づけを統合し、判断できない主張は保留する。旧 ID が複数候補に対応する場合、元の参照と出典・引用・役割・期間を照合する。「利用」を「試用」と「契約」に分けたとき、「未契約」の反証先は契約に限る。判定不能なら旧版と保留を残す。
- **複数版の保留**は元の定義版で保持する。例えば v1 の保留が v3 で解決したら、v3 の確定記録に対応づけ、同じ実体を重複作成せず、現行の残件から外す。以前の保留理由と後の根拠を両方残す。版が特定できない記録は保留として扱う。部分移行中の確定件数は現行定義で評価できた範囲を集計し、旧版の記録は元の意味で参照できるようにする。
- **有効化後**は Ossie Ontology を意味定義の正本とし、旧型・述語との対応から互換用の定義とグラフを生成する。既存ページの手編集は差分として取り込み、意味レコードとの衝突を検査する。既存クライアントの ID は互換グラフと対応表で引けるようにし、分割して1件に確定できない ID は、元の記録と候補を返す。未有効化の wiki では既存の書式と動作を維持する。旧配置や手編集の定義は試行時に適用可能性を判定し、`concept` への自動縮退を「型が確定した」扱いにしない。

## 書き込みと公開版

共通の書く段を定めた [ADR-0023](../adr/0023-wiki-apply-uses-journal-and-per-wiki-lock.md) に、意味レコード・定義とグラフの公開、依存先の検査、読み手の版固定を加える関連 ADR が必要になる。`ontology apply`・通常 ingest・再生成を同じ経路に通し、意味レコード、マニフェスト、公開ポインターを含む書き込みを `wiki_fsguard.Writer` の検査対象にする。

1. **試行する。** 公開版を入力として新しいスナップショットを隔離して構築する。定義・レコードの差分、依存するページ・原本・識別キーの指紋、検査結果を記録する。索引・グラフ・Ossie 文書も試行対象にする。
2. **照合して確定する。** wiki ごとのロック内で基準版、計画のハッシュ、定義・記事・確定済みの実体と主張のキーを照合する。「まだ同じキーの記録がない」という前提も検査する。基準が変わっていたらロックを解放し、最新の公開版へ差分を当て直して成果物を再構築する。依存先や問いの対象範囲に変更がなければ、別の ingest を保持したまま同じ承認対象を再試行できる。承認対象の差分・判断・試行結果が変わった場合は最終案を再表示する。技術的な計画ハッシュと承認対象の照合は関連 ADR で定める。古い定義で準備した ingest も最新の規則で検査し直す。同じメーカー・品番や同じ命題が先に確定していれば、候補を作り直し、その記録への根拠の追加として再試行する。
3. **公開する。** 検証済みスナップショットは変更不能とし、`release_id`、定義版、記事の指紋と保存先、構造化レコード、グラフ、索引をマニフェストで結ぶ。競合がなければ、同じロックの下で成果物と日誌を保存し、同一ファイルシステム内で公開先へのポインターを原子的に切り替える。日誌に旧・新マニフェストの指紋と適用計画 ID を記録し、中断後は完全な旧版か完全な新版に復旧する。同じ計画の再試行は完了済みの版に結び、履歴と出典を二重に追加しない。
4. **読む。** query・browse・MCP は候補検索から引用・添付の取得まで公開版を固定する。検索結果に `release_id` を返し、後続の MCP ツールや HTTP リクエストにも渡す。本文・索引・グラフ・browse のサブリソースは同じ版を読み、編集中の Markdown は次の公開候補として扱う。エディターなど、この版の契約に参加しない読み手はライブのファイルを見る。原本を開く場合は指紋を照合し、変わっていれば保存済みの引用の版を示す。必要なデータの版が揃わなければ、新しい版で最初から再試行するか保留する。

旧版を再現できる範囲は、保持されていて公開取り下げの対象外である版に限る。履歴の保持方針は公開導入前に決め、通常の回収では読み手が使用中の版を保持する。機密などを取り下げる場合は対象版の配信を止め、該当本文・根拠と派生した索引などを共通の書く段で取り除く。履歴には内容を復元できる値を含めず、取り下げと再現できない範囲を残す。

## 一方向 PoC に足す検証

現行 PoC は、SemaSynth の 63 ノード・477 関係を全列一致で移し、Ossie の3文書を公式検証器で通過させた。実データには根拠付きの関係が2件、期間や訂正リンク付きの関係は0件だった。ローカルの列参照検証と外部エンジンの実行は別の判定にする。 [実測と検証範囲](../research/2026-11-19-ossie-wiki-export-poc.md)

| 段階 | PoC への追加と合格条件 |
| --- | --- |
| 1. 意味モデル | 既存の `WikiNode`・`WikiEdge` 出力を回帰検査に使い、別出力に実体・主張の版・根拠・履歴・旧 ID 対応を加える。SemaSynth の 63 ノード・477 関係の元 ID と列を保持し、`cites`・`depends_on` の引用2件の対応を照合する。同じ入力を再試行しても対応が増えない。合成 wiki で製品Aは顧客1社・主張1件・根拠2件、代理店関係だけの製品Bは顧客0社。期間不明・係争中の候補がある照会は理由付きの確認済み件数を返し、別 wiki の同名実体や無関係な製品の保留は混ぜない。 |
| 2. 移行の試行 | 隔離した wiki で定義改名・意味分割・遡及訂正・部分移行を試す。改名だけでは件数が変わらず、開始日訂正は同一 `claim_id` の新版になる。根拠追加で有効な反証を失わず、分割後の「未契約」は契約だけを指す。判断不能の参照は保留する。v1 の保留を v3 で解消した後は確定1件・旧残件0件で、以前の保留理由と旧定義にたどれる。 |
| 3. Ossie の消費 | 公式検証器で Ontology・Core・Mapping の正例と壊れた参照の拒否を確認する。実行の合格には、候補エンジンかアダプターで実際に Mapping を適用して、型付きリンク、期間別一覧、根拠結合後の重複しない顧客数、定義した制約違反の検出の4つを独立した期待値と照合することが必要。別 API キーや外部 DB を必須としない実行構成で試す。 |

段階1〜2は入力に書き戻さずに進める。初期提供の問い合わせは info-hive の SQLite 実装で行う。段階3では文書検証と実行結果を別々に記録し、4項目すべてを再現できた構成を外部実行連携の候補にする。Core の指標と SQLite の比較には同じ問い・入力・固定した期待値を使い、未対応の宣言は交換対象として保持して実行は未確認と記録する。これまで確認した版の変換器は独立 Mapping を読み込めなかった。変換経由の場合も消費側で同じ期待結果を求める。

### 公開前の受け入れ試験

PoC の後、関連 ADR と共通の書く段の実装が揃ってから隔離環境で実施する。この試験は本番 wiki を有効化する条件とする。

- 同じ製品・命題の並行 ingest は、実体1件・主張1件・出典2件に着地する。無関係な ingest の変更は再構築後も残り、定義が変わった古い計画は再検査まで公開されない。
- 公開の前後で書き手を中断してから再試行し、完全な旧版か新版で読めること、履歴・根拠が二重に追加されないことを確認する。MCP の検索と取得の間で切り替えても、固定した版の本文と引用を返す。旧版を取り下げた場合は、版を指定しても本文・根拠を配信しない。
- `neighbors`・`edges`・`facts`・`path`、browse、lint の互換契約を固定した入力で比べる。移行対象外の旧 ID・関係・引用とアクセス範囲は同じ結果を求める。移行対象の差分は承認済みの変更と対応表に一致し、曖昧な旧 ID は任意の1件に結ばない。

Opus の設計レビューを受け、開始日訂正や根拠追加での参照継承、件数から外す理由の表示、ロック外での当て直し、公開版の取り下げ、Ossie 実行の合格条件を明文化した。並行実行・移行・外部エンジンでの試験は、この設計案に記した検証項目である。
