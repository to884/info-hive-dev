# ADR-0029 段階3の検索キャッシュ保護

[ADR-0029 の実装計画](wiki-links-2026-11-16.md) に従い、CLI のパースキャッシュと SQLite ベクトル索引を `wiki_fsguard.py` の検査に通す。初期化・アップグレードが置く検索キャッシュ用の `.gitignore` にも同じ検査を当てる。

- パースキャッシュは読み込み前にも経路を検査する。あるキャッシュがリンクなので検査を通らなければ、中身を開かず、記事から解析する。更新には一意の一時名と検査済みの置き換えを使う。更新の時点で拒まれた場合にも、キャッシュを使わずに解析して結果を返す。
- 既定のキャッシュと wiki 内の明示的な `--cache` は wiki の根から検査する。wiki に入るまでの親の別名も認識し、wiki に入ったところで解決を止める。外部に明示したキャッシュは、既存の親を設定された根として扱い、別ボリュームへの保存も許す。キャッシュファイルそのもののリンクは検査する。MCP のパースキャッシュは設定されたデータの根から検査し、記事が同じでキャッシュの更新を省いた場合は直近のキャッシュの警告を返す。
- ベクトル索引は、SQLite 本体と `-journal`・`-wal`・`-shm` の経路を、埋め込みモデルの読み込み前と SQLite を開く直前に検査する。検索では、経路の拒否や接続・初期化・同期中の SQLite の書き込み不能を知らせ、接続を閉じ、既存の BM25 の結果を返す。
- 拒否の場所と種類を `link_warnings` に含め、標準エラーにも代わりに取った動作と理由を出す。成功時の検索 JSON の形は維持する。
- `setup_wiki.py` はパースキャッシュを使えなくても索引の準備を続ける。ベクトル索引の経路検査や SQLite の書き込みで拒まれた場合は語彙検索が使えることを知らせ、`status: lexical` と終了コード 1 を返す。初期化やアップグレードの実行環境が準備済みになる条件は従来の `status: ready` とする。

回帰試験では、通常のキャッシュの作成と再利用、古い固定一時名が存在する場合、リンクされたキャッシュの読み書きと SQLite の接続の拒否を確認する。拒否した検索の順位と出力を、キャッシュなしまたは `--no-embed` の検索と比べる。
