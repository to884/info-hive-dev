## 背景

2026年11月11日に、設計書と実装を調べた。分かったことは次のとおりである。

- Raw の容量を閾値にした対策は、設計書にも実装にもない。`scaling-playbook.md` の閾値は、ページの数、ページの文字数、インデックスの行数だけである。目的は 1 回のクエリで読むコンテキストを一定に保つことで、ディスクの容量は扱っていない。
- `/wiki:stats` は Raw を測らない。Raw がどれだけあるかを知る手段が、プラグインにない。
- 容量を抑える手当ては、入口の制限だけである。PDF は Raw にコピーせず、原本の場所を記録する（ADR-0013）。Web ページは訳文と本文の画像だけを残し、原文の HTML は残さない（ADR-0004）。`wiki_fetch.py` の既定は、ページ 1 つ、画像 1 つにつき 20 MiB まで、画像は 1 ページ 50 枚までである（どちらも引数で変えられる）。
- 名前が `raw` のディレクトリは、ページの集合に入らない（`wiki_pages.py` の `SKIP_TOP_LEVEL_DIRS`）。Raw が大きくなっても、検索の結果と回答の質は変わらない。困るのは、ディスクの空き、バックアップと同期の時間、Raw を Git で管理しているときのリポジトリの大きさである。
- ただし、今の `wiki_stats.py` は、wiki の中の `raw/` の Markdown を読んでから捨てている。`compute_stats()` は `wiki.rglob()` で wiki の全体をたどり、本文を読んだあとで `is_page_path()` を確かめる（`wiki_stats.py` の 123〜136 行）。wiki の中に大きな Raw があると、ページとして数えないファイルを、上限なしに読む。

## 目的

- Raw の大きさ（ファイルの数とバイト数）を、`/wiki:stats` で見られるようにする。
- 大きさが閾値を超えたら警告し、何が場所を取っているかを、手を打てる単位（大きいファイル、ソースごとの画像のディレクトリ）で示す。
- 足す Raw の走査と、`wiki_stats.py` のページの集計が、利用者の意図しない場所（遅いドライブ、大きな書庫、リンクの先）を読まない。MCP の `stats` が集計の前に呼ぶ索引の更新が、wiki の中の `raw/` を列挙する経路は、前提の変更でふさぐ。ページのディレクトリに置いたジャンクションの先は、前提の変更のあとも、ページとしてたどる（Windows では今もページである）。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| Raw の圧縮 | 次の節に書く |
| Raw のファイルの退避と削除 | 原本を消す操作は、測って警告することと別の判断である。source ページの `raw:` が指す先がなくなると、lint の「原本がない」に当たる |
| どのページからも参照されていない原本や画像の検出 | 画像の参照は Raw の Markdown の中にあり、内容を読まないと分からない。今回は内容を読まずに大きさだけを測る。警告のあとの手段として次の段階の候補にする |
| `raw:` が指す先の大きさ（rag に登録した PDF など） | Raw の外にあり、遅いドライブやつながっていないドライブにあることがある。書かれた文字列から件数を数えるだけにし、その先には触れない |
| rag のデータ（抽出の結果、索引） | rag の持ち物である。wiki から rag の中を覗かない。rag の側の状態の表示で扱う（ADR-0014 の「見直す条件」） |
| wiki の中の生成物（`.wiki-cache/`、`graph/graph.sqlite`）と MCP の索引 | 消せば作り直せるので、警告の意味が Raw と違う。MCP の索引の場所は、すでに `stats` の `index.dir` に出ている。大きさを足すかは「作者が決めること」の 4 |
| lint、search、MCP の索引、browse が wiki の中の `raw/` を列挙すること | 前提の変更（[wiki をたどるとき、除くディレクトリに降りない](wiki-walk-excluded-dirs-2026-11-11.md)）で直す。この設計では扱わない |
| wiki の中に `raw` 以外の名前で置いた Raw（`wiki/W1_Raw/` など） | 今の規則では、その中の Markdown はページとして数えられる。ページの集合の規則の問題で、この設計では変えない |

### 圧縮しない理由

- エージェントは Raw を grep し、分けて読む。主張の出所は `raw_ref: "raw/xxx.md#L42"` のように行番号で指す。圧縮すると、どれも使えなくなる。
- lint は source ページの `raw:` の先があるかを確かめる。圧縮してファイル名が変わると、「原本がない」になる。
- 画像（png、jpg、webp）はすでに圧縮された形式なので、zip や zstd で包んでもほとんど縮まない。縮むのはテキストだが、テキストは上の 2 つの理由で圧縮できない。

検証環境の実物の Raw では、Markdown 17 件が 0.19 MiB、png 3 件が 0.74 MiB だった。これは 1 つの Raw の値で、どの Raw でも画像が大半を占めるとは言えない。Web の訳文や利用者が置いたテキストが大半の Raw もありうる。そのため、閾値は合計に付け、内訳は分類ごとに出す（「決めること」の 3 と 4）。

見直す条件は、閾値を超える Raw が実際に現れ、その内訳から圧縮や再圧縮（画像の解像度や形式の変更）が効くと分かったときである。画像の再圧縮は原本を書き換えるので、`commands/ingest.md` の「保存したあとの raw のファイルは書き換えない」との関係を、そのときに決める。

## 決めること

### 1. Raw の場所

`wiki_stats.py` が受け取るのは wiki のディレクトリだけである。Raw の場所は wiki によって違う。

| 例 | wiki | Raw |
| --- | --- | --- |
| プロジェクトの wiki（`init_wiki.py` の既定） | `<プロジェクト>/wiki/` | `<プロジェクト>/raw/` |
| ユーザースコープの既定 | `~/info-hive/wiki/` | `~/info-hive/raw/` |
| 名前を変えた wiki（検証環境の実物） | `~/info-hive/W0_Wiki/` | `~/info-hive/W1_Raw/` と `~/info-hive/We_Raw_en/`。作業領域の設定（`.info-hive/workspace.json`）はない |
| 設計書を原本にする wiki（このリポジトリ） | `wiki/` | `raw/` のほかに、source ページが `raw: "docs/agent-runs/…"` と書いて `docs/` の中を指す |

4 つ目の例から、source ページの `raw:` が指すディレクトリを自動で測ってはならないことが分かる。`docs/` の全体を Raw として数えてしまう。絶対パスの `raw:`（rag の PDF）からたどると、遅いドライブの書庫を走査することになる。

そこで、次のように決める。

**Raw を探す前に、wiki のパスを `Path.resolve()` する。** 隣の `raw/`、中の `raw/`、作業領域の設定を探す起点、リンクの検査の起点は、どれも解決したあとの wiki から決める。MCP は wiki を `normalize_wiki_root()` で解決してから集計に渡し、CLI は渡されたままの `Path` を渡す。wiki がリンクのとき、解決の前と後で「隣の `raw/`」が別のディレクトリになるので、解決のあとにそろえる。今ある出力のキー `wiki`（渡されたままのパス）は変えない。

**引数で渡されたら、それだけを測る。** CLI は `--raw <ディレクトリ>`（繰り返せる）、MCP は `raw`（文字列のリスト）である。`/wiki:stats` のコマンドは、`<RAW_ROOT>` を `/wiki:ingest` と同じ順（ユーザーが明示したパス、もっとも近いプロジェクトの指示、グローバルなエージェントの指示）で探し、指示にあれば渡す。MCP の `raw` が空のリストのときは、渡されなかったものとして扱う。

**引数がなければ、次の順に探し、最初に当てはまった 1 つだけを使う。** 複数を足し合わせない。設定を変えたあとに残った古い `raw/` を、一緒に数えないためである。

1. 作業領域の設定。`find_workspace(<wiki>)` で、wiki のディレクトリから親へさかのぼって探す（カレントディレクトリは使わない）。見つかり、その `dirs.wiki` がこの wiki と同じディレクトリなら、この設定に従う。`dirs.raw` のディレクトリがあればそれを測り、なければ `not_found` にする。下の 2 と 3 には進まない。`dirs.wiki` が別のディレクトリを指す設定は、使わずに 2 へ進む。
2. wiki の隣の `raw/`（`<wiki の親>/raw`）。
3. wiki の中の `raw/`（`<wiki>/raw`。`wiki_pages.py` が除くディレクトリで、lint もここを原本の候補にしている）。

**どれにも当てはまらなければ、測らずに `not_found` を返す。** 0 バイトとは書かない。

**自動で見つけたルートがリンクなら、測らない。** 作業領域の根（2 と 3 では wiki の親と wiki）からルートまでの各階層が、シンボリックリンクでもジャンクションでもないことを確かめる。リンクがあれば `state: "error"` にし、`--raw` で渡すように書く。引数で渡されたルートは、利用者が指した場所なので、リンクでも測る。どちらの場合も、ルートの中にあるリンクはたどらない（「2. 測り方」）。

ルートの検査は次のとおりである。

- ディレクトリでないもの、開けないもの、wiki のルートそのもの、wiki のルートの祖先は、ルートにしない。理由を `errors` に入れる。
- 引数で渡されたルートのうち、使えるものだけを測る。1 つも使えなければ `state: "error"` にする。
- 同じディレクトリかどうかは、`os.path.samefile()`（その時点の `st_dev` と `st_ino`）で比べる。パスの文字列では比べない。文字列の比べ方は、どちらにそろえても誤る。大文字と小文字をそろえる（`os.path.normcase()`）と、Windows の大文字と小文字を区別するフォルダーにある `Raw/` と `raw/` を同じものとして捨てる。そろえないと、大文字と小文字を区別しないファイルシステム（Linux の VFAT、macOS の既定）で、`/mnt/fat/Wiki` と `/mnt/fat/wiki` を別のものとみなし、wiki そのものを Raw として測る。POSIX の `Path.resolve()` は、大文字と小文字をディスク上の名前にそろえない。
- 含むかどうかは、内側の候補から親へ 1 階層ずつさかのぼり、各階層を外側の候補と `samefile()` で比べて決める。wiki のルートの祖先かどうか、別のルートの中にあるかどうかを、これで決める。同じディレクトリは 1 つにし、別のルートの中にあるルートは外側だけを測る。
- `stat` が失敗したとき（権限がないなど）は、文字列の比較に落とさない。同じかどうかを決められないので、そのルートを測らず、理由を `errors` に入れる。失敗したあとで文字列を比べると、大文字と小文字だけが違う別のディレクトリを同じとみなすことがある（走査の計画の「1 版目で崩れた前提」と同じ）。`stat` は成功したが `st_ino` が 0 のとき（識別子を持たないファイルシステム）だけ、`Path.resolve()` したパスの文字列が一致するかで比べる。ADR-0013 がファイルの識別子を採らなかったのは、時間をまたいで記録する鍵にすると、ネットワークドライブで値が変わるからである。ここでは 1 回の実行の中で比べるだけなので、その理由は当たらない。
- 作業領域の設定が壊れているとき（`WorkspaceError`）は、`state: "error"` にして理由を入れる。黙って隣の `raw/` を使わない。ページの統計はそのまま返す。

**`raw:` に書かれた場所を、文字列のまま数えて出す。** source ページの `raw:` を、URL、絶対パス、相対パスに分ける（lint の `missing_raw()` と同じ見分け方）。相対パスは、書かれたままのディレクトリの部分（`../W1_Raw/x.md` なら `../W1_Raw`）ごとに件数を数える。絶対パスは件数だけを数える。URL は数えない。ファイルがあるかは確かめず、`..` も解決しない。ファイルシステムには触れない。ディレクトリの部分は、文字列の操作だけで決める（`pathlib` は使わない。OS で結果が変わるからである）。`\` を `/` に置き換え、末尾の `/` を除き、最後の `/` より前を取る。`/` がなければ `.` にする。検証環境の実物では、何も渡さないと `not_found` になり、`../W1_Raw` が 17 件、`../We_Raw_en` が 1 件と出る。利用者とエージェントは、これを見て `--raw` に渡す場所を決める。

`wiki_workspace.py` には関数を足さない。`find_workspace()` と `Workspace.dir()` をそのまま使う。このファイルは log と rag にも同じものを置く前提だからである（`tests/workspace/` は、今は wiki の実装だけを登録している）。

### 2. 測り方

- `os.scandir()` でたどり、`DirEntry.stat(follow_symlinks=False)` でファイルの大きさ（`st_size`）だけを取る。内容は読まない。
- ルートの中のリンクは、たどらず、数えず、`skipped.links` に数だけ入れる。リンクとは、`DirEntry.is_symlink()` が真のものと、Windows で `st_file_attributes` に `FILE_ATTRIBUTE_REPARSE_POINT` があり、`st_reparse_tag` が `IO_REPARSE_TAG_SYMLINK` か `IO_REPARSE_TAG_MOUNT_POINT`（ジャンクション）のものである。OneDrive などのクラウドのファイルも再解析ポイントだが、タグが違うので、ふつうのファイルとして数える。
- 大きさは論理的な大きさである。ディスクの割り当ての大きさではない。クラウドに置いたままのファイルは、手元の使用量より大きく出る。ハードリンクは別々に数える。
- 名前が `.` で始まるものも数える。場所を取っていることに変わりはないからである。
- 読めないディレクトリとファイルは飛ばし、数を `skipped.unreadable` に入れる。1 つでもあれば `complete: false` にする。そのときの `bytes` は下限で、`level` は「少なくともこの段」を表す。`advice` に `raw_incomplete` を入れる。
- たどる項目（ファイルとディレクトリ。飛ばしたリンクも数える）は、すべてのルートの合計で 100,000 個までにする。超えたら走査をやめ、`state: "too_many"` を返す。**途中までの値は、件数、バイト数、飛ばした数のどれも出さない。** 途中で読めない項目を見つけていても、`raw_incomplete` は出さず、`raw_too_many` だけを出す。読めない項目に先に出会うかどうかも、順序で変わるからである。 `os.scandir()` が返す順序は決まっていないので、途中までの値は実行のたびに変わりうる。超えたかどうかだけなら、順序によらず決まる。上限は `--raw-max-entries`（MCP は `raw_max_entries`）で変えられる。1 未満の値はエラーにする。大きな Raw を測りたい利用者は、上限を上げて測る。
- `--no-raw`（MCP は `measure_raw=false`）で、Raw の走査を飛ばせる。そのときは `state: "skipped"` を返し、ルートを探すこともしない。引数の値の検査（閾値、上限、MCP の `raw` が絶対パスであること）は、飛ばすかどうかより先に行う。不正な値は、`--no-raw` を付けていてもエラーにする。ルートがつながっていないネットワークのドライブにあるときなどに使う。

今の `compute_stats()` が wiki の中の `raw/` の Markdown を読む経路は、前提の変更がふさぐ。前提の変更のあと、`wiki_stats.py`、lint、search、MCP の索引は、最上位の除くディレクトリ（`raw`、`assets` など）に降りない。`--no-raw` を付けたときも付けないときも、ページの集計が wiki の中の `raw/` を列挙することはない。ページの集計がたどるリンクは、ページの集合の規則（前提の変更の「決めること」の 3）に従う。Raw の走査のリンクの扱い（この節）とは別である。

走査の速さは、検証環境で測った（「検証環境の値」の節）。100,000 個は、SSD で約 1 秒、遅い外付けのドライブで約 5 秒に当たる。`wiki_fetch.py` の既定（1 ページに本文 1 つ、画像 50 枚まで、画像のディレクトリ 1 つ）では、1 ページが多くて 52 個なので、100,000 個は少なくとも約 1,900 ページ分である。

### 3. 分類

測ったファイルを、場所と拡張子で 3 つに分ける。

| 分類 | 条件 |
| --- | --- |
| `assets` | ルートの直下の `assets/` の中にあるもの（`wiki_fetch.py` が画像を置く場所） |
| `markdown` | `assets/` の外にあり、拡張子が `.md` のもの（大文字と小文字を問わない） |
| `other` | そのほか（利用者が置いた PDF、HTML、テキストなど） |

大きいものを 2 つの単位で挙げる。どちらも上位 10 件である（`TOP_N` と同じ）。

- 大きいファイル（分類を問わない）。
- 大きい画像のディレクトリ（`assets/` の直下のディレクトリごとの合計。`wiki_fetch.py` は `assets/<ソースのスラッグ>/` に置くので、ソースごとの合計になる）。`assets/` の直下に置かれたファイルは、ディレクトリではなく大きいファイルの側に出る。

並びは、バイト数の多い順、同じならルートのパスの順、それも同じならルートからの相対パスの順にする。どれも文字列のコードポイントの順で比べる。

### 4. 閾値と警告

- 閾値は、測ったルートの合計のバイト数に付ける。ソフトとハードの 2 段で、ページの大きさの `soft`、`hard` と同じ語を使う。
- 既定は、ソフトが 1 GiB（1,073,741,824 バイト）、ハードが 10 GiB である。作者の例の「10 GB」をハードに当てた。値は「作者が決めること」の 1 である。
- 引数で変えられる。CLI は `--raw-soft-bytes` と `--raw-hard-bytes`、MCP は `raw_soft_bytes` と `raw_hard_bytes` である。1 未満の値と、ソフトがハードより大きい組は、エラーにする（lint の MCP は 1 未満だけを拒む。大小の組の検査は、この設計で足すものである）。
- wiki ごとに閾値を変えたいときは、その wiki の `SCHEMA.md` に値を書き、エージェントが引数で渡す。lint の上限と同じ運用である。作業領域の設定（`workspace.json` の `wiki` の部分）には、今回は置かない。検証環境の実物の wiki のように、設定のない wiki があるからである。
- この閾値は、動作の限界ではない。超えても検索とクエリは変わらない。バックアップ、同期、Git の取り回しを見直すきっかけである。開発用の PC の空き容量やドライブの構成からは決めない。

`advice` に足す項目は次のとおりである。今の `scale_advice()` が返す項目（`code`、`message`、任意の `reference`）と同じ形で、今ある項目のあとに足す。`code` は英語のまま残す。

| `code` | 条件 | 文面 |
| --- | --- | --- |
| `raw_soft` | 合計がソフトを超え、ハード以下 | Raw が <ソフト> を超えた。大きいファイルと画像のディレクトリを見直す。 |
| `raw_hard` | 合計がハードを超えた | Raw が <ハード> を超えた。バックアップと同期、Git の管理の対象を見直し、使わない原本の退避を検討する。 |
| `raw_incomplete` | 読めない項目があった | Raw に読めない項目が <数> 個あった。大きさは下限である。 |
| `raw_too_many` | 項目が上限を超えた | Raw の項目が <上限> 個を超えたので、測らなかった。`--raw-max-entries` を上げると測る。 |

`raw_soft` と `raw_hard` には、`reference` に `references/scaling-playbook.md` を付ける。Raw が見つからないこと（`not_found`）は、`advice` に入れない。Raw のない wiki は異常ではないからである。

### 5. 出力

`compute_stats()` の結果に、キー `raw` を足す。今あるキーは変えない。キーは英語のまま残す。

```json
"raw": {
  "state": "measured",
  "roots": [
    {"path": "C:/Users/x/info-hive/W1_Raw", "found_by": "argument", "files": 20, "bytes": 973585}
  ],
  "files": 20,
  "bytes": 973585,
  "complete": true,
  "by_kind": {
    "markdown": {"files": 17, "bytes": 199331},
    "assets": {"files": 3, "bytes": 774254},
    "other": {"files": 0, "bytes": 0}
  },
  "largest_files": [
    {"root": "C:/Users/x/info-hive/W1_Raw", "path": "assets/foo/foo-01.png", "bytes": 401234}
  ],
  "largest_asset_dirs": [
    {"root": "C:/Users/x/info-hive/W1_Raw", "path": "assets/foo", "files": 3, "bytes": 774254}
  ],
  "skipped": {"links": 0, "unreadable": 0},
  "limits": {"soft_bytes": 1073741824, "hard_bytes": 10737418240, "max_entries": 100000},
  "level": null,
  "refs": {
    "relative": 18,
    "absolute": 0,
    "dirs": [{"dir": "../W1_Raw", "refs": 17}, {"dir": "../We_Raw_en", "refs": 1}],
    "dirs_omitted": 0
  },
  "errors": []
}
```

`state` ごとの値は次のとおりである。

| `state` | 意味 | `roots` | `files`、`bytes`、`complete`、`by_kind`、`level`、`skipped` | `largest_files`、`largest_asset_dirs` |
| --- | --- | --- | --- | --- |
| `measured` | 測った | 測ったルート | 値が入る | 値が入る |
| `not_found` | ルートがない | 空 | `null` | 空 |
| `too_many` | 項目が上限を超えた | 見つけたルート（`files` と `bytes` は `null`） | `null` | 空 |
| `skipped` | `--no-raw` | 空 | `null` | 空 |
| `error` | 使えるルートが 1 つもない、自動で見つけたルートがリンク、作業領域の設定が壊れている | 空 | `null` | 空 |

- `limits`、`refs`、`errors` は、どの `state` でも出す。`refs` は読んだページの frontmatter だけから作るので、`skipped` でも出せる。`refs.dirs` は件数の多い順（同じなら `dir` の順）に 10 件までで、残りのディレクトリの数を `dirs_omitted` に入れる。
- `errors` は、`{"path": "<渡されたまま、または見つけたパス>", "reason": "<理由>"}` のリストである。
- `found_by` は、`argument`、`workspace`、`sibling`（wiki の隣の `raw/`）、`inside`（wiki の中の `raw/`）のどれかである。
- `roots[].path` と `root` は、`Path.resolve()` した絶対パスを `/` 区切りにしたものである。`path`（ルートからの相対パス）は、ディスク上の名前を `/` 区切りにしたものである。
- CLI と MCP は、同じ wiki と同じ引数（Raw のルートは絶対パス）に対して同じ結果を返す。カレントディレクトリに依存する値と、走査の順序に依存する値を入れない。

テキストの出力には、「被リンクの多いページ」のあと、「規模のしきい値」の前に、次の節を足す。大きさは、1024 を底にした単位（KiB、MiB、GiB）で書き、合計にはバイト数も添える。

```text
Raw の大きさ:
  ルート:     C:/Users/x/info-hive/W1_Raw（引数）
  合計:       20 件、0.93 MiB（973,585 バイト）
  Markdown:   17 件、0.19 MiB
  assets/:     3 件、0.74 MiB
  そのほか:    0 件
  閾値:       ソフト 1 GiB、ハード 10 GiB

  大きいファイル:
     0.38 MiB  assets/foo/foo-01.png
  大きい画像のディレクトリ:
     0.74 MiB    3 件  assets/foo

  source ページの raw: が指す場所（測ったとは限らない）:
    17 件  ../W1_Raw
     1 件  ../We_Raw_en
```

`not_found` のときは、「Raw のディレクトリが見つからない。`--raw` で渡す。」と書き、`refs.dirs` があれば続けて出す。

### 6. MCP の `stats`

- 引数を `stats(wiki, raw=None, measure_raw=True, raw_soft_bytes=…, raw_hard_bytes=…, raw_max_entries=…)` にする。今の呼び方（`wiki` だけ）は、そのまま動く。
- 索引の扱いは、今のまま変えない。`stats` は索引を開いて wiki の変更を取り込み、`index` に状態を返す。埋め込みは始めない。Raw の走査は、索引に何も足さず、索引から何も読まない。
- Raw の走査は、今と同じ `offload()` の中で走る。
- `raw` に渡すパスは絶対パスにする。相対パスは、サーバーのカレントディレクトリに依存するので、エラーにする。CLI の `--raw` は、相対パスをカレントディレクトリから解決する。

### 7. コマンドと手引きの文面

- `commands/stats.md`: `<RAW_ROOT>` の探し方、`raw` の渡し方、結果の読み方を足す。`raw_soft`、`raw_hard` が出たら、大きいファイルと画像のディレクトリを示し、圧縮はせず、使わない原本の退避をユーザーに相談することを書く。`not_found` で `refs.dirs` があれば、どのディレクトリを Raw として測るかをユーザーに確かめる。
- `references/scaling-playbook.md`: 「Raw の大きさ」の節を足す。ページ数の閾値とは別の軸であること、閾値の意味、圧縮しない理由、超えたときにすること（大きい画像を見直す、Git で管理しているなら大きいファイルの扱いを決める、使わない原本を退避する）を書く。
- `references/mcp-server.md` と `SKILL.md`: `stats` の説明に `raw` を足す。

## 試験

`tests/wiki/` に置く。一時ディレクトリに wiki と Raw を作って確かめる。

Raw を読まないこと:

- wiki の中の `raw/` に Markdown を置き、`compute_stats()` が、`--no-raw` のときも付けないときも、ページの集計のためにその下を列挙せず、内容を読まないことを確かめる（前提の変更の試験と同じ差し替えで、Raw の走査を足したあとも成り立つことを見る）。
- Raw の走査が、ファイルを開かないことを確かめる（同じ差し替えで）。
- `refs` を作るときに、`raw:` の先に触れないことを確かめる（`os.stat`、`Path.exists` を差し替える。存在しないドライブの絶対パスと、存在しない相対パスを書いた source ページを置く）。

ルートの解決:

- 引数、作業領域の設定、隣の `raw/`、中の `raw/` のそれぞれで見つかる。引数があれば、ほかを探さない。
- 作業領域の設定と隣の `raw/` の両方があるとき、設定の側だけを測る。隣と中の両方があるとき、隣だけを測る。
- 作業領域の設定が当てはまり、その `dirs.raw` がないとき、隣の `raw/` があっても `not_found` になる。
- 作業領域の設定の `dirs.wiki` が別の wiki を指すとき、その `dirs.raw` を使わない。設定が壊れているとき、`state` が `error` になり、ページの統計は返る。
- `refs.dirs` の文字列の規則: `book.md` が `.` に、`..\W1_Raw\book.md` と `../W1_Raw/book.md` が同じ `../W1_Raw` に、`../W1_Raw/book/`（末尾の `/`）が `../W1_Raw` になる。OS によらず同じ結果になる。
- 名前を変えた wiki（`W0_Wiki` と `W1_Raw`、設定なし）で、引数がなければ `not_found` になり、`refs.dirs` に `../W1_Raw` が出る。引数で渡すと測る。
- source ページが `raw: "docs/x"` と書いた wiki で、`docs/` を測らない。
- wiki がシンボリックリンクのとき（`/work/wiki -> /store/wiki`、`/work/raw` と `/store/raw` の両方がある）、CLI と MCP が同じルート（`/store/raw`）を選ぶ。
- wiki のルートそのものと祖先を、ルートにしない。同じルートと、含まれるルートを 2 度数えない。引数がすべて使えないとき `error` になる。MCP の `raw=[]` が、渡さないときと同じ結果になる。
- 大文字と小文字だけが違う 2 つのルート（`Raw/` と `raw/`）を、区別するファイルシステムでは別々に測る（Linux の CI で確かめる。区別しない環境では飛ばす）。
- 区別しないファイルシステムで、大文字と小文字だけを変えて書いた wiki のルートと祖先（`--raw` に渡す）を、ルートにしない。同じ Raw を大文字と小文字だけ変えて 2 度渡しても、1 度だけ数える（Windows と macOS の CI で確かめる。区別する環境では飛ばす）。
- Linux の区別しないファイルシステム（VFAT）は CI で用意しにくいので、同一性の判定を、`os.path.samefile` と `os.stat` を差し替えた試験で確かめる。文字列は違うが識別子が同じ 2 つのパスを同じとみなすこと、文字列が大文字と小文字だけ違い識別子が違う 2 つのパスを別とみなすこと、`st_ino` が 0 のときに文字列の比較に落ちること、`stat` が失敗したときに文字列の比較に落ちず、そのルートが `errors` に入ることを見る。

リンク:

- ルートの中のシンボリックリンク（ファイルとディレクトリ）とジャンクションをたどらず、`skipped.links` に数える。
- 自動で見つけたルートそのものがリンクのとき、測らずに `error` になる。作業領域の `dirs.raw` の途中の階層がリンクのときも同じ。引数で渡したリンクは測る。
- リンクを作れない環境では飛ばす。OneDrive のクラウドのファイルは CI で作れないので、タグの見分け（`IO_REPARSE_TAG_SYMLINK`、`IO_REPARSE_TAG_MOUNT_POINT` だけを飛ばす）を、`stat` の結果を差し替えた試験で確かめる。

集計:

- 分類と合計が、作ったファイルのバイト数と合う。日本語のファイル名、NFD の名前、`.` で始まる名前を含める。
- 並びが、ファイルを作る順序と `os.scandir()` の返す順序（差し替えて逆にする）を変えても同じになる。同じ大きさで同じ相対パスのファイルが 2 つのルートにあるとき、ルートのパスの順になる。
- 閾値: 小さい閾値を引数で渡し、`level` と `advice` の `code` を確かめる。1 未満の値と、ソフトがハードより大きい組を拒む。
- 読めない項目: 読めないディレクトリを置き（権限を変えられない環境では `os.scandir` を差し替える）、`complete` が `false`、`advice` に `raw_incomplete` が入ることを確かめる。ルートそのものを開けないとき、そのルートが `errors` に入る。
- 項目の上限: 小さい `--raw-max-entries` を渡し、`state` が `too_many`、`bytes` と `skipped` が `null`、`advice` に `raw_too_many` が入ることを確かめる。読めないディレクトリと上限の超過が同時にあるとき、列挙の順序によらず `raw_too_many` だけが出て、`raw_incomplete` が出ない。1 未満の上限を拒む。`--no-raw` と不正な値を一緒に渡すとエラーになる。`os.scandir()` の返す順序を変えても、結果が同じになる。上限ちょうどの数では `measured` になる。複数のルートで、合計に上限が効く。
- `--no-raw` で `skipped` になり、`os.scandir` が Raw のルートに対して呼ばれない。
- 走査の前後で、wiki と Raw のファイルが変わらない。

MCP とコマンド:

- MCP の `stats` が、`measure_raw=false` のとき、wiki の中の `raw/` に対して `os.scandir` を呼ばない（`WikiIndex.refresh()` と `compute_stats()` を同じプロセスで呼んで記録する）。
- MCP の `stats` が、同じ引数の CLI の `--json` と同じ結果を返す（今ある `test_stats_matches_cli_and_reports_index` を、Raw のある wiki と `raw` の引数で通す）。`index` の報告が今と変わらない。相対パスの `raw` を拒む。
- `check_commands_mcp.py`（実際の Claude Code でコマンドを流す確認）に、`/wiki:stats` が指示にある `<RAW_ROOT>` を `raw` に渡すことの記録を足す。今は wiki の指定先だけを記録している。

## 2 回目のレビューの指摘と対応

[design-review-2.md](../agent-runs/2026-11-11-wiki-raw-size-in-stats/design-review-2.md) の判定も却下だった。1 回目の重大の 7 件のうち、1、5、6、7 は解消、2 は件数とバイト数について解消、3 と 4 は別の欠陥が残る、という評価だった。新しい指摘を、実装と照らして確かめた。
