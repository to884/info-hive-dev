# wiki の閲覧（browse）の第 1 段階とサーバーのアダプタ（2026年11月9日）

[ADR-0010](../adr/0010-wiki-browse-separates-core-from-delivery.md) の作る順序の 2〜4（承認のあとの作業の 3 と 4）を、`info-hive-wiki` で行う計画である。[優先順位の文書（6 版目）](../research/feature-priority-2026-11-06.md)の 2 位に当たる。前提の 1（ページの集合とリンクの規則、wiki 0.9.0）は済んだ。

Sol の敵対的レビューで 3 回却下された（[design-review-1.md](../agent-runs/2026-11-09-wiki-browse-stage1-review/design-review-1.md)、[design-review-2.md](../agent-runs/2026-11-09-wiki-browse-stage1-review/design-review-2.md)、[design-review-3.md](../agent-runs/2026-11-09-wiki-browse-stage1-review/design-review-3.md)）。この版は、その指摘を受けて直したものである。指摘と対応の対照は最後にある。合格の条件は [ADR-0016](../adr/0016-wiki-browse-stage1-accepts-two-delivery-methods.md)（2026年11月9日に作者が決めた）による。

関係表は、グラフの抽出の修正（別の作業。同じスラッグのページの取り違え、ページを区別しない関係のまとめ、パスつきの `sources:`）を前提にする（3）。browse の実装は、その修正が `info-hive-wiki` の main に入ってから始める。

## 目的

- 中核（Wiki を読んで、ページ、ナビゲーション、被リンク、関係表、診断を組み立て、Markdown を HTML に描く）を、Python の 1 か所に置く。
- 第 1 段階（ページの表示、ナビゲーション、メタ欄、被リンク、ページごとの関係表、未解決リンク、日本語の CSS）を、静的に描ける形で完成させる。
- 最初のアダプタとして、必要なときだけ起動するローカルのサーバー（構成 B、ADR-0002）を作り、`/wiki:browse` から開けるようにする。

検索（静的版の部分一致、サーバーの MCP の `query`）、全体のグラフ、RAG は範囲の外で、優先順位の 3 位と 5 位で行う。

## 決めること

### 1. ファイルの構成

`skills/info-hive/scripts/` に置く。

| ファイル | 中身 |
| --- | --- |
| `wiki_browse_core.py` | 中核。Wiki のルートを受け取り、読み取りの写し（4）から、ページの識別子、出力の名前、見出しの ID、リンクの状態、被リンク、関係表、診断、ナビゲーションを組み立て、ページの HTML を描く。`wiki_pages.py`、`wiki_lint.py`、同梱した markdown-it-py を使う |
| `wiki_browse.py` | 入口。`build`（静的に書き出す）、`serve`（サーバーを起動して開く。動いていれば使い回す）、`stop`（止める）、`core`（中核を子プロセスとして呼ぶための JSON の入出力）。PEP 723 の依存は `pyyaml==6.0.3`（関係表のため。グラフの抽出と同じ版）だけで、`uv run --script` で動かす |
| `browse_assets/` | 書き出す画面の部品（`app.js`、`style.css`）。PoC の `poc/browse/static/` を下敷きにし、検索欄を除く |

中核と描画を分けない（1 つのモジュールにする）。ADR-0010 の「表示の側は Markdown を解釈しない」は、アダプタ（サーバー、静的の書き出し、将来のアプリ）が Markdown を解釈しないという意味で、中核が HTML まで描くことは決定のとおりである。

### 2. 読み取りの写し（スナップショット）

中核は、組み立てのはじめに、入力を 1 度だけ読み、その写しだけから組み立てる。lint 用とグラフ用で別々にファイルを読むと、間で編集されたとき、本文と関係表が別の時点の内容になるからである。

- **入力**: `wiki_pages.iter_page_files()` のページ、`index.md`、`indexes/` の Markdown、`graph/ontology.yaml`。
- **Wiki の外を指すもの**（3 回目のレビューの重大 4）: 実体が Wiki のルートの外にあるページ、索引、オントロジー（シンボリックリンク、ジャンクション）も、lint、グラフの抽出、`wiki_pages.iter_page_files()` と同じに読む。browse だけが除くと、リンクの判定が lint と食い違うからである。読むことは閲覧専用に反しない。出力に入れるのは Wiki の中の相対パスから作った識別子だけで、リンクの実体の絶対パスは入れない（5 の検査の対象）。書き込みの側の確かめ（7、8）は、これと別に実体の場所で行う。読んだ入力の実体の場所は、写しに記録し、書き込みから守る対象に入れる（7 の「守る場所」）。
- **読めないもの**: 読めないページは描かず、診断に `read_error` として、識別子だけを挙げる。例外の文字列（絶対パスを含む）は出力に入れない。
- **同じ識別子になる別のファイル**（4 回目のレビューの重大 3）: 識別子（3）が同じになる 2 つ以上のページは、どれも描かず、診断に `id_collision` として、その識別子と、違いの種類（`normalization`: NFC と NFD だけが違う、`extension_case`: `x.md` と `x.MD` のように拡張子の大文字と小文字だけが違う）を挙げる。どちらも Linux では同時に置ける。その識別子へのリンクは `ambiguous` にする。lint は、どちらの組も `duplicate_slugs` に挙げるので、リンクの判定はそれと一致する。識別子を作った直後、出力の名前（3）を作る前に確かめる。
- **世代**: 入力のすべて（相対パスと、バイト列の SHA-256）のハッシュ。frontmatter、索引、オントロジーを変えても世代が変わる。
- **限界**: ファイルを 1 つずつ読むので、読んでいる途中にほかのファイルが編集されると、古いページと新しい索引が混ざることはある。Wiki 全体を同じ瞬間で切り取る写しではない。サーバーは、読む**前に**取った入力の印を、その写しに結び付けて持つ（8）。読んでいる途中の編集は、次の要求で印の違いとして見つかり、作り直される。

### 3. 中核の組み立て

- **識別子**: NFC の POSIX の相対パスから `.md`（大文字と小文字を問わない）を除いたもの（ADR-0010 のデータの契約）。
- **出力の名前**: `export_name()`。PoC の `gen.py` の規則（未決だった事項の決定の 3）を移し、予約名の判定を直す（レビューの重大 5）。Windows の予約名は、`CON`、`PRN`、`AUX`、`NUL`、`CONIN$`、`CONOUT$`、`COM0`〜`COM9`、`LPT0`〜`LPT9` と、上付きの数字の `COM¹`〜`COM³`、`LPT¹`〜`LPT³` とする。最初の `.` より前を、末尾の空白と `.` を除き、大文字と小文字を区別せずに比べる（Python 3.13 の `ntpath.isreserved()` と同じ範囲）。ほかの規則（Windows で使えない文字、末尾の空白と `.`、接尾辞の形の名前、`.html` で終わるディレクトリ、最上位の生成器の名前（`index.html`、`nav.js`、`data`、`assets` と、browse の目印の `.browse-output`、`.browse-generation`。8 回目のレビューの軽微な指摘）、UTF-8 で 200 バイトを超える要素）は PoC のとおりで、変えたら `~<その要素までの識別子の SHA-256 の先頭 8 桁>` を付ける。大文字と小文字だけが違う出力は、衝突した全員に接尾辞を足す。最後に重なりを確かめ、重なれば生成を止める（`NameCollision`）。
- **見出し**: 同梱した markdown-it の `heading_open` から取る（ATX と Setext）。見出しの文字は、Markdown の原文ではなく、表示の文字にする（6 回目と 7 回目のレビューの軽微な指摘）。見出しの `inline` を本文と同じ描き方（wikilink は表示の文字に、画像は代替テキストに）で描き、タグを除き、HTML の文字参照を戻した文字である。`## **Definition**` も `## [[other|Definition]]` も `Definition`、`## ![Definition](diagram.png)` も `Definition` になる。ID は、表示の文字を NFC にして小文字にし、空白を `-` にし、`-` 以外の ASCII の記号（`_` を含む）を除いたものとする。重なれば連番を付ける。`[[slug#見出し]]` の照合も、同じ規則で作った ID どうしで行う。
- **画面の部品の ID**: テンプレートが使う要素の ID（ナビゲーション、本文、メタ欄、被リンク、関係表、診断など）は、`_` で始める（`_nav`、`_main` など）。見出しの ID は `_` を含まないので、見出しが `# nav` でも重ならない。
- **リンク**: 本文の wikilink は、描くときと同じ markdown-it のトークン（`inline` の中の `text`）から拾う（`wiki_pages.extract_wikilinks()` と同じ規則）。状態は `resolved`、`ambiguous`（パスのないリンクで、同じスラッグのページが 2 つ以上。lint の `duplicate_slugs` と同じ判定。どちらにも移動しない）、`unresolved`（クリックしてもファイルを作らない）。`resolved` で `#見出し` の見出しがなければ `missing_heading` を足す。
- **被リンク**: 解決したリンクを逆に引く。自分へのリンクは数えない。
- **関係表**（レビューの重大 1、2 回目の重大 2、3 回目の重大 2 と 3）:
  - オントロジーがあるときだけ作る。グラフの抽出の `parse_frontmatter`、`build_nodes`、`build_edges` を、写しから作ったページに当てはめる。
  - **グラフの抽出に求める契約**: 今の `build_nodes` と `build_edges` は、同じスラッグのページで主語を取り違え（スラッグからノードを引く）、同じ内容の関係をページを区別せずに 1 本にまとめ（`edge_id` に `page` が入らない）、別のスラッグに同じ `graph.node_id` を付けたページの関係を捨て、パスつきの `sources:`（`sources/paper`）から `sourced_from` を作らない。3 回目のレビューは、同じスラッグのページの関係表を隠すだけでは、別のページの「入ってくる関係」に取り違えた主語が残ることを、今の関数で示した。そこで、browse の関係表は、次を満たすように直したグラフの抽出を使う。修正は別の作業（グラフの抽出の修正）で行い、browse の実装はそれが main に入ってから始める。
    1. エッジの主語は、そのエッジを書いたページのノードである。スラッグから引き直さない。
    2. エッジは `page` を持つ。`graph.relationships` の 1 つの項目から、必ず 1 本のエッジができ、別の項目とまとめない。ページの違う同じ内容の関係も、同じページの中で `status` や `valid_from`、`valid_to` だけが違う関係も、それぞれ残る（5 回目のレビューの重大 3。今の `edge_id` は主語、述語、目的語、出典、証拠しか見ないので、期間違いの 2 件が 1 件になる）。エッジの ID の作り方は、グラフ層の出力（sqlite、graphml、`wiki_graph_decide`）に関わるので、グラフの抽出の修正で決める。
    3. 型付きの関係の目的語は、既存のスキーマのとおりノードの ID（`concept:y`。`graph.node_id` か、既定の `<node_type>:<slug>`）として引く。1 つのページのノードに当たれば、そのノードを目的語にする。当たらなければ、今のグラフの抽出と同じに、文字列の目的語（ノードでない値）のエッジにする（ページの関係表では、どのページの入ってくる関係にもならない）。目的語をページへの参照として解くことはしない（グラフの意味を変えないため）。
    4. `sources:` の値（ページへの参照）は、lint の `unresolved_sources` と同じ字句の処理（外側の `[[ ]]` を外す。`[[sources/paper]]` も `sources/paper` も同じに読む）をしてから、`wiki_pages.resolve_link()` と同じ規則で、**ページ**（識別子、つまり相対パス）に解決する。字句の処理と解決は、lint とグラフの抽出が `wiki_pages` の同じ関数を使う（5 回目のレビューの重大 2）。`resolve_link()` はスラッグを返すので、パスつきの参照（`sources/left/paper`）でも、同じスラッグのどのページか分からなくなる。そこで、規則に当たるページの集合を求め、1 つならそのページ、2 つ以上なら曖昧、0 なら未解決とする。曖昧と未解決はエッジを作らず、診断に挙げる。
    5. 別のページが同じ `graph.node_id` を持つときは、どちらかを黙って捨てず、診断に挙げる。そのノードの ID を目的語にした関係は、3 で 1 つのページのノードに当たらないので、エッジを作らず、曖昧として診断に挙げる。
    6. `sources:` の値のうち、4 の共通の関数で 1 つのページに解決し、そのページの `type` が `source` であるものからは、必ず `sourced_from` のエッジができる。lint の `unresolved_sources` は曖昧さを含まない（同じスラッグのページが 2 つでも空になる）ので、合否の条件には直接使わない。その代わり、共通の関数が「未解決」と「`source` でない」とする値の集合が、lint の `unresolved_sources` と一致することを試験で確かめる。
  - この契約は、browse が頼る性質だけを挙げたもので、グラフの抽出の作り方を決めるものではない。契約で足りるか、グラフのほかの利用者に影響しないかは、グラフの抽出の修正の設計と実装のレビューで確かめる。
  - **出ていく関係**は、エッジの `page` で振り分ける。**入ってくる関係**は、目的語のノードを持つページに出す。契約の 1、3、4 から、どちらも別のページの関係が紛れ込まない。
  - **同じ `graph.node_id` のページ**（契約の 5）では、そのノードへの入ってくる関係を出さず、診断に `ambiguous_relations` を挙げる。出ていく関係は、契約の 1 と 2 により、それぞれのページに出せる。
  - 修正の契約が上と違う形になったときは、この節を、その形に合わせて直し、設計のレビューをやり直す。
  - 表に出すのは、型付きの関係と `sourced_from`（`sources:` からの関係）である。`mentions`（本文の wikilink）は被リンクと重なるので出さない。`summarizes_raw` は `raw:` の欄と重なるので出さない。
  - 状態を 3 つに分ける（レビューの軽微な指摘）: オントロジーがない（`relations: "none"`。関係表を出さない）、読めない（`relations: "error"`。関係表の場所に「オントロジーを読めない」と出し、診断に挙げる）、作れた（`relations: "ok"`。関係が 0 件なら「関係はない」と出す）。
- **ナビゲーション**（レビューの軽微な指摘）: `index.md` と `indexes/` を、ページとして描かずに読む。`collect_index_entries` は種類の見出ししか読まないので使わない。規則は次のとおりである。
  - 同梱した markdown-it で解析し、見出しの入れ子（`#` から `######`）をそのままグループの木にする。リストの項目を、その直前の見出しのグループに入れる。最初の見出しより前の項目は、そのファイルの最上位のグループ（`index.md` なら名前のない先頭のグループ、`indexes/` のファイルならそのファイルのグループ）に入れる。入れ子のリストの項目も、同じグループに入れる（リストの入れ子は木にしない）。
  - 項目が指すページは、その項目の段落（入れ子のリストを除く）の**最初の** wikilink で決める（3 回目のレビューの軽微な指摘）。最初の wikilink が `resolved` でなければ、後ろの wikilink を探さず、その項目を状態つきの文字（`ambiguous` か `unresolved`。リンクにしない）として出す。`- [[missing]] — 関連：[[a]]` は、`a` へのリンクではなく、未解決の `missing` の項目になる。wikilink のない項目は出さない。
  - 同じページが複数の場所に載っていれば、それぞれの場所に出す。
  - `indexes/` があれば、ファイルごとに最上位のグループを 1 つ作り（名前は frontmatter の `title`、最初の見出し、ファイル名の順）、その中を上と同じ規則で木にする。`index.md` の項目が `indexes/` のファイルを指すとき（`[[indexes/concepts]]`）は、その項目を、そのファイルのグループへのリンクにする。
  - 索引に載っていないページは、種類（`type`）ごとの「索引にないページ」のグループに入れる。
  - `nav.js` に書き出し、各ページは共有の `nav.js` を読み込む。
- **メタ欄**: `type`、`tags`、`summary`（あれば）、`created`、`updated`、`sources`（解決したものはリンク）、`raw`（4 で扱う）。
- **診断**: `unresolved`、`ambiguous`、`missing_heading` のリンク、`read_error`、`id_collision`、`ambiguous_relations`、グラフの抽出が挙げた関係の診断（契約の 4 と 5）、名前を変えたページ。ページの末尾と `data/diagnostics.js` に出す。
- **本文の wikilink 以外のリンク**（3 回目のレビューの軽微な指摘）: Markdown のリンク（`[文字](URL)`）と自動リンクは、次のように描く。
  - `http:`、`https:`、`mailto:` は外部へのリンクとして描き、`rel="noopener noreferrer"` と外部であることの印を付ける。各ページに `<meta name="referrer" content="no-referrer">` を置く。開くのは利用者がクリックしたときだけで、表示の時点では外への要求が起きない（CSP は読み込みを止めるもので、クリックでの移動は止めない）。
  - それ以外（相対パス、`file:`、ほかのスキーム）は、出力の配置が Wiki の配置と違うのでリンクにせず、文字として出す。markdown-it の既定の `validateLink`（`javascript:`、`vbscript:`、`file:`、画像以外の `data:` を拒む）はそのまま使う。

### 4. `raw:` の扱い（未決だった事項の決定の 7）

- 中核は `raw` を `{kind, value, sha256}` で持つ。`kind` は `absolute`（絶対パス）、`relative`、`url` のどれか。
- `file:` の URL（`file:///C:/Books/private.pdf`）は、`url` ではなく `absolute` にし、`value` はその URL が指すローカルのパスにする（8 回目のレビューの重大 1）。lint の `missing_raw()` は `file:` を URL として見ないが、持ち出す出力の扱いではローカルの絶対パスと同じだからである。`~` で始まる値も `absolute` にする。`url` に入るのは、`file:` 以外のスキームを持つ値だけである。
- 描き方を 4 つに分ける。`text`（値を文字として出し、リンクにしない）、`link`（`file:///` のリンク）、`basename`（ファイル名と `raw_sha256` の先頭 12 桁）、`none`（出さない）。
- `link` にするのは `kind` が `absolute` のときだけである。`relative`（基準が lint でも 3 通りあり、一意に決まらない）と `url`（開くと外への通信になる）は、どの描き方でも文字として出す（`none` なら出さない）。
- サーバーは `text`。静的版は、既定の書き出し先では `link`、`--out` では既定で `basename`。`--raw` で選べる。
- 交換できることの試験（10）は、同じ描き方（`text`）で比べる。

### 5. 絶対パスを出力に入れない（レビューの重大 4）

- 出力（HTML、`nav.js`、`data/*.js`）に入れるのは、識別子、相対パス、題名、本文、メタ欄の値だけである。例外の文字列、Wiki のルート、ホームのパスは入れない。`raw:` の絶対パスは、4 の描き方が `text` か `link` のときだけ入る（利用者が選んだもの）。
- 生成の記録（Wiki のルートの絶対パスを含む）は、出力の外の、作業用のディレクトリ（7）の `build-report.json` に書く（3 回目のレビューの軽微な指摘）。
- 公開の前に、作業中のディレクトリの全ファイルを調べる。探す文字列は、Wiki のルートとホームのディレクトリの絶対パスを、`/` 区切り、`\` 区切り、JSON の文字列の中の `\\` 区切り、HTML のエスケープ、URL の符号化にしたものである。`raw:` の描き方が `text` か `link` のときは、その値だけを許す。見つかれば、作業中のディレクトリを消し、前の世代を残したまま、失敗で終わる（終了コード 1）。

### 6. 画面の契約（ADR-0010 のとおり）

- ページ間のリンクは相対の href だけにする。名前の要素ごとにパーセントエンコードする。
- スクリプトは classic な `<script src>` だけ。`fetch`、ES モジュール、Web Worker を使わない。データは `nav.js` と `data/*.js`（`window.WIKI_NAV` など）にし、`</`、U+2028、U+2029 をエスケープする。
- 各ページの HTML に、本文、メタ欄、被リンク、関係表、診断を事前に描く。JavaScript を切っても読める。`<noscript>` で `index.html` へのリンクを残す。
- CSP を `<meta>` に付ける（`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'`）。外部への通信をしない。
- 生の HTML は出さない（markdown-it の `html: False`）。本文の画像は、第 1 段階では代替テキストだけを出す（ADR-0005 のとおり、svg の表示は第 1 段階に含めない）。
- 出力に `protocol_version`（1）、世代、生成日時、能力（`search: "none"`、`relations`、`rag: false`、`multi_wiki: false`、`live_reload`）を持たせる。各ページの `<html>` に `data-generation` を書く。`app.js` は、知らない `protocol_version` なら表示を止め、`nav.js` の世代がページの世代と違えば「Wiki が更新された。再読み込みする」と出す。

### 7. 静的の書き出し（`wiki_browse.py build`）

- **書き出し先**: 既定は `<data_dir>/browse/<wiki_key>/`（未決だった事項の決定の 2）。`data_dir()` と `wiki_key()` は `wiki_mcp_common` のものを使う。`--out <dir>` で場所を選べる。
- **作業用のディレクトリ**（2 回目のレビューの致命 1）: 書き出しに使う一時のディレクトリ、退避したディレクトリ、ロック、生成の記録は、すべて書き出し先の隣の、browse が持つ作業用のディレクトリ `<出力先>.browse-work/` の中に置く。作業用のディレクトリには目印（`.browse-work`）を置き、目印のない既存のディレクトリは使わない（止まる）。消すのは、作業用のディレクトリの中の、目印（`.browse-generation`）を持つ `tmp-*` と `old-*` だけである。名前の形だけで、作業用のディレクトリの外のものを消すことはしない。
- **守る場所**（4 回目のレビューの重大 4）: 書き込みから守るのは、Wiki のルートと、写し（2）が読んだ入力のすべての実体の場所（ページ、索引、オントロジー。シンボリックリンクとジャンクションを解いたもの）である。Wiki の中のページが書き出し先の中のファイルを指していると、出力を入れ替えたときにページの実体を消してしまうからである。
- **書き出し先の確かめ**（レビューの重大 3）: 書き出し先、作業用のディレクトリを `Path.resolve()`（シンボリックリンクとジャンクションを解いたもの）で求め、守る場所と重なる（中にある、含む、同じ場所）ときは、書かずに止まる。消す直前にも、消すものの実体が作業用のディレクトリの中にあり、守る場所と重ならないことを確かめる。消すときはリンクをたどらない（Python 3.12 以降の `shutil.rmtree` は、シンボリックリンクとジャンクションの先を消さない）。書き出し先は、空のディレクトリか、目印（`.browse-output`）のあるディレクトリでなければ書かない。
- **ほかの書き出しとの入れ子**（5 回目のレビューの重大 1）: 書き出し先と作業用のディレクトリは、ほかの browse のディレクトリ（目印 `.browse-output`、`.browse-work`、`.browse-server` のあるディレクトリ）の中にあっても、それを含んでもならない。確かめ方は次のとおりである。入れ替えで親のディレクトリごと動かすと、子の書き出しの持っているロックのファイルが動き、同じ場所に新しいロックを作れてしまうからである（`extract_lock` の注意書きと同じ理由）。
  - 実体の場所の祖先のディレクトリを根までたどり、自分のもの以外の目印があれば止まる。
  - 書き出し先と作業用のディレクトリの中を、リンクをたどらずに調べ、自分の世代の目印以外の browse の目印があれば止まる。
  - 書き出し先がまだないときは、空か目印のあるディレクトリでなければ書かない規則（上）により、中に別の書き出しを持つディレクトリには書かない。
- **browse の持ち場の分離**（4 回目のレビューの重大 5）: `--out` の書き出し先と、その作業用のディレクトリは、`<data_dir>/browse/` と重なってはならない（中にある、含む、同じ場所）。`<data_dir>/browse/` に書くのは、既定の書き出し先とサーバーの状態だけにする。あわせて、目印の種類（`.browse-output`、`.browse-work`、`.browse-server`）が違うディレクトリは互いに使わない。書き出しは `.browse-server` か `.browse-work` のあるディレクトリを書き出し先にせず、サーバーは `.browse-output` か `.browse-work` のあるディレクトリを状態に使わない。静的の書き出しの入れ替えが、動いているサーバーのロックのディレクトリを動かすことがなくなる。
- **排他**（2 回目のレビューの重大 3）: 作業用のディレクトリの `build.lock` を、OS のファイルのロック（Windows は `msvcrt.locking`、ほかは `fcntl.flock`。`wiki_graph_common.extract_lock` と同じ仕組み）で取る。プロセスが止まれば OS が外すので、古いロックを片付ける処理を持たない。ロックのファイルは消さない。取れなければ、ほかの `build` が動いているとして止まる。
  - **書き出しどうしの排他**（7 回目のレビューの重大 1）: 出力先ごとのロックだけでは、別の出力先の入れ替えが祖先のディレクトリごとロックのファイルを動かし、同じパスに新しいロックを作れてしまう。そこで、どの `build` も、出力先ごとのロックの前に、利用者に 1 つの共通のロック `<data_dir>/browse/build.lock` を取り、終わるまで持つ。書き出しは、出力先が違っても同時に 1 つしか走らない。共通のロックは `<data_dir>/browse/` に置き、`--out` はそこと重ならない（下の持ち場の分離）ので、どの書き出しの入れ替えでも動かない。取れなければ、ほかの書き出しが終わるまで待つ（既定 60 秒。過ぎれば止まる）。入れ子の確かめ、片付け、入れ替えはすべてこのロックの中で行うので、確かめてから入れ替えるまでのあいだに、ほかの書き出しが作業用のディレクトリを作ることはない。
  - 限界: `INFO_HIVE_DATA_DIR` を別々の値にした 2 つのプロセスは、共通のロックを分け合わない。同じ利用者がデータの置き場所を変えて同時に書き出す使い方は想定しない。
- **世代の目印**: どの世代のディレクトリにも、目印 `.browse-generation`（JSON。世代のハッシュ、`published_seq`）を置く。`published_seq` は、作業用のディレクトリの `seq`（書き出すたびに 1 増やす整数。ロックの中でだけ読み書きする）から取る。時刻は使わない（時計が戻ると順が崩れる）。目印のないもの、読めないものは、戻す候補にしない。
  - `seq` は、同じディレクトリの一時のファイルに書いてから `os.replace` で置き換える。途中で止まっても、古い値か新しい値のどちらかが残る。`seq` がない、読めないときは、出力先と作業用のディレクトリの中の目印の `published_seq` のいちばん大きい値に 1 を足した値から始める（4 回目のレビューの軽微な指摘）。
- **世代の入れ替え**（レビューの重大 6、3 回目のレビューの重大 7）:
  1. ロックを取ったあとで、作業用のディレクトリを片付ける。残った `tmp-*` は消す。出力先があれば、目印のある `old-*` をすべて消す。出力先がなく `old-*` があるとき（前の入れ替えの途中で止まったとき）は、目印の `published_seq` がいちばん大きい `old-*` を出力先に戻し、ほかの `old-*` を消す。戻せる `old-*` がなければ、出力先のないまま進める。消せなかったものは残し、次の書き出しの 1 でまた消す。
  2. `tmp-<seq>` に全部を書き、5 の検査をする。
  3. 出力先があれば `old-<seq>`（作業用のディレクトリの中）に名前を変え、`tmp-<seq>` を出力先に名前を変える。
  4. 2 つ目の名前の変更に失敗したら（Windows で、ほかのプロセスが掴んでいるときなど）、`old-<seq>` を出力先に戻し、失敗で終わる。
  5. 成功したら `old-<seq>` を消す。消せなければ残し、次の書き出しの 1 で消す。
  - **入れ替えの直前の確かめ直し**（6 回目のレビューの重大 2）: 3 の名前の変更の直前に、出力先の条件（空か目印がある。祖先と中身にほかの browse の目印がない）をもう一度確かめる。2 つの新しい書き出し（`/exports/site` と `/exports/site/nested`）が同時に始まると、始めの確かめでは互いに見えない。後から始めた子が作業用のディレクトリを作れば、親の出力先は目印のない空でないディレクトリか、中にほかの目印を持つディレクトリになるので、親はここで止まる。`old-*` と `tmp-*` を消す直前にも、その中にほかの browse の目印がないことを確かめ、あれば消さずに止まる（ほかの書き出しの作業中のディレクトリを消さない）。書き出しどうしは共通のロックで 1 つずつ走るので、この確かめ直しは、browse の外で利用者がディレクトリを作ったときのためのものである。
  - どの時点で止まっても、出力先か、`published_seq` のいちばん大きい `old-*` のどちらかに、最後に公開した世代が残る。1 で戻すのはそれである。
- **書き込みの直前の確かめ**（3 回目のレビューの重大 6、6 回目のレビューの重大 1）: ディレクトリを作る、ファイルを開いて書く、名前を変える、消す、の各操作の直前に、その操作の対象の実体の場所（`Path.resolve()`。まだないものは、親の実体の場所に名前を足したもの）を求める。対象が守る場所の中にあるか、同じ場所なら止まる。対象が守る場所を含むときも止まる（名前を変える、消す操作で、守る場所ごと動かさないため）。親のディレクトリについては、守る場所の中にないことだけを確かめ、親が守る場所を含むこと（`C:/work` の下に Wiki と書き出し先が並ぶ配置）は拒まない。親の実体の場所を毎回解くのは、その下の子がジャンクションなら Wiki の中に書けるからである。この確かめは 1 つの関数にまとめ、書き出しとサーバーのすべての書き込みがそれを通る。守る場所は、7 の冒頭の「守る場所」（サーバーでは、今の中核の写しが読んだ入力の実体の場所）である。確かめてから書くまでのあいだに、別のプロセスがジャンクションに差し替える競合は防げない（利用者の手元の操作を前提にした限界）。
- 既定の書き出し先（`<data_dir>/browse/<wiki_key>/`）にも、同じ規則を当てはめる。`data_dir` は環境変数 `INFO_HIVE_DATA_DIR` で変えられるので、Wiki と重なれば止まる（2 回目のレビューの重大 5）。
- 出力の先頭のページは `index.html`（ナビゲーションの全体）。

### 8. サーバー（`wiki_browse.py serve`、構成 B）

- 127.0.0.1 だけで待ち受け、ポートは OS に選ばせる。起動ごとのトークンを URL のパスの先頭に置く（`/<token>/w/<wiki_id>/…`）。`wiki_id` は `wiki_key()`。
- Host ヘッダーが `127.0.0.1:<port>` でなければ 421、トークンが違えば 404 を返す。閲覧の口は GET と HEAD だけを受け付け、ほかは 405（操作の口は下の「1 つの Wiki に 1 つのサーバー」）。パスはパーセントデコードしたあとで `/` で分け、`..`、空の要素、`\`、NUL を含めば 404 にする。返すのは、中核が知っている出力の名前（ページ、`index.html`、`nav.js`、`data/*.js`、画面の部品）だけで、ファイルシステムは見ない。
- **開いたときに描く**（ADR-0002 の既定）。起動時に中核を組み立て、ページは要求されたときに、その時点の中核から描く。描く関数は静的の書き出しと同じものを使う。
- **作り直し**（レビューの重大 2 と 6、3 回目のレビューの崩れる前提）: 要求のたびに、入力の印（`.md` と `graph/ontology.yaml` のパス、大きさ、更新時刻）を取り、今の中核に結び付けた印と比べる。
  - 変わっていれば、新しい中核を別に組み立て、組み立て終えてから入れ替える。新しい中核に結び付けるのは、組み立ての**前に**取った印である。読んでいる途中に編集されても、次の要求の印はそれと違うので、また作り直される。読んだあとの印を結び付けると、古い内容に新しい印が付き、作り直しが起きなくなる。
  - 組み立ては、同時に 1 つだけ走らせる。走っているあいだに印が変わっても、新しく始めず、終わってから印を取り直して、違えばもう 1 度組み立てる。入れ替えは、今の中核より後に始めた組み立ての結果だけを受け付ける。古い組み立てが後に終わって新しい中核を戻すことはない。
  - 組み立てのあいだの要求には、前の中核で答える（途中の状態を見せない）。1 つの要求は、1 つの中核の写しだけを使う。
  - 組み立てに失敗したら、前の中核を使い続け、「古い」状態にする（6 回目のレビューの軽微な指摘、ADR-0010 の「古い」の区別）。サーバーは、古い状態のあいだに描くページの先頭に「Wiki の最新の内容を読めなかったので、前の内容を表示している」と、失敗の種類（例外の文字列は入れない）を事前に描き、`data/diagnostics.js` にも載せる。HTML と `nav.js` の世代は一致したままなので、世代の不一致の表示とは別に出す。次に組み立てに成功すれば、古い状態を解く。静的の書き出しは、失敗すれば前の世代を残し、コマンドの終了コードと報告で失敗を知らせる（静的版はもともと書き出した時点の写しなので、画面に古さを出さない）。
  - 大きさと更新時刻を変えずに中身だけを変えた編集は見逃す（MCP の索引の変更の印と同じ限界）。
  - **読めなかったページの読み直し**（8 回目のレビューの重大 2）: 今の中核に `read_error` のページがあるときは、印が同じでも、作り直しを求める。Windows の共有違反のように、ファイルを変えずに読めるようになることがあるからである。何度も作り直さないよう、前の組み立てを始めてから 5 秒たつまでは求めない。読めるようになれば、次の組み立てでページが戻り、`read_error` が消える。
- **終了**: 操作がない状態が一定の時間（既定 30 分）続いたら終了する。`--idle-timeout` で変えられる。
- **状態の置き場所**（2 回目のレビューの重大 5、3 回目のレビューの重大 6）: サーバーの状態（ロックと記録）は `<data_dir>/browse/<wiki_key>.server/` に置く。状態のディレクトリ、`server.lock`、`server.json` の書き込みは、どれも 7 の「書き込みの直前の確かめ」を通す。状態のディレクトリには目印 `.browse-server` を置き、7 の「browse の持ち場の分離」に従う。`data_dir` が Wiki と重ならなくても、`<wiki_key>.server/` が Wiki へのジャンクションなら、実体の場所が Wiki の中なので止まる。止まったときは何も書かず、別の場所を指すよう案内する。閲覧の操作で、Wiki の中にファイルを作らない。
- **1 つの Wiki に 1 つのサーバー**（2 回目のレビューの重大 4）: サーバーは、生きているあいだずっと、状態のディレクトリの `server.lock` を OS のファイルのロックで持つ。ロックのファイルは消さない。
  - 記録（`server.json`）には、ポート、閲覧のトークン、**操作のトークン**、インスタンスの ID（起動ごとの乱数）、開始の時刻を書く。作者だけが読める権限にする。操作のトークンは閲覧のトークンと別にし、閲覧の URL とページには出さない（ブラウザの履歴に残る閲覧の URL から止められないようにする）。操作の要求は `stop` と `serve` だけが送る。サーバーの記録（標準エラー）には、要求のパスを書かず、方法、口の種類（閲覧か操作か）、状態の番号だけを書く。閲覧と操作のトークンが記録に残らないようにする（8 回目のレビューの軽微な指摘）。PID は使わないので書かない。
  - サーバーは、操作の口として `GET /<操作のトークン>/control/status`（インスタンスの ID と `wiki_key` を返す）と `POST /<操作のトークン>/control/stop`（応答を返してから終了する）を持つ。Host の確認は閲覧と同じにする。どちらも Wiki のファイルを変えない。閲覧のページの HTML とスクリプトは、操作のトークンを知らない。
  - `serve` は、まずロックを取ろうとする。取れたら、ほかのサーバーは動いていないので、ロックを持ったまま起動し、記録を書く。取れなければ、動いているサーバーがあるので、記録を読み（書き終わるまで少し待つ）、`control/status` に要求する。応答のインスタンスの ID が記録と一致すれば使い回す。応答しない、一致しないなら、使い回せないと報告して止まる（新しくは起動しない）。2 つの `serve` が同時に始まっても、ロックを取れるのは 1 つだけである。
  - `stop`（3 回目のレビューの重大 5）は、ロックが取れるか（サーバーが動いていないか）を先に見る。取れなければ、記録を読み、`control/status` でインスタンスの ID を確かめてから、`control/stop` を送る。そのあと、ロックが取れるようになる（そのプロセスが終わる）まで待つ。一定の時間（既定 10 秒）で取れなければ、止められなかったと報告し、記録を消さない。ロックが取れたら記録を消す。OS のプロセスを外から終わらせること（`os.kill`）はしない。止めるのは、操作のトークンとインスタンスの ID を知っている要求だけなので、ポートやプロセスの番号が使い回されても、別のプロセスを止めることはない。応答しないサーバーは止められないと報告し、利用者に任せる（操作がないときの終了で、いずれ終わる）。
- 起動したら、1 行目に `{"url": …, "port": …, "reused": …}` を JSON で出し、既定のブラウザで開く（`--no-open` で開かない）。Claude Code のデスクトップアプリでは、エージェントがブラウザペインで開ける。
- 応答に CSP、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer` を付ける。エラーの応答には、パスや例外の文字列を入れない。

### 9. `/wiki:browse` のコマンドと中核の子プロセスの入出力
