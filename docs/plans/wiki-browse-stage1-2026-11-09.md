## 目的と範囲

- 中核（Wiki を読んで、ページ、ナビゲーション、被リンク、関係表、診断を組み立て、Markdown を HTML に描く）を、Python の 1 か所に置く。
- 第 1 段階（ページの表示、ナビゲーション、メタ欄、被リンク、ページごとの関係表、未解決リンク、日本語の CSS）を、静的に描ける形で完成させる。
- 最初のアダプタとして、必要なときだけ起動するローカルのサーバー（構成 B、ADR-0002）を作り、`/wiki:browse` から開けるようにする。

範囲の外は最後に挙げる。

## 前提

- **wiki 0.9.2（グラフの抽出の修正、to884/info-hive-wiki#34）。** 2026年11月11日に main に入り（`be117ad`）、リリースされた。関係表（3.6）とリンクの解決（3.3）が、0.9.2 の次の関数を使う。
  - `wiki_pages.link_candidates()`、`build_page_index()`、`classify_source_ref()`、`ref_values()`
  - `wiki_graph_extract.build_nodes(pages, ontology, diagnostics)`（`(nodes, page_node_ids, aliases)` を返す。`page_node_ids` のキーはディスク上の相対パス）と `build_edges(pages, page_node_ids, diagnostics)`（エッジの `page` は NFC の相対パス）
- 0.9.2 のグラフの抽出は、次を満たす（その修正の設計と実装のレビューで確かめた。browse はこれを前提にし、ここでは確かめ直さない）。
  1. エッジの主語は、そのエッジを書いたページのノードである。
  2. `graph.relationships` の 1 項目から 1 本のエッジができ、ページや期間の違う関係をまとめない。
  3. 型付きの関係の目的語はノードの ID で引く。同じ ID のページが 2 つ以上あればエッジを作らず、診断（`ambiguous_object`）に挙げる。
  4. `sources:` と本文の wikilink は `link_candidates()` でページに解決し、1 つに決まるときだけエッジにする。決まらない `sources:` は診断（`ambiguous_source`、`unresolved_source`）に挙げる。
  5. 同じ `graph.node_id` のページは、同じノードを指し、診断（`duplicate_node_id`）に挙がる。
- PoC（`poc/browse/`）の生成器、画面の部品、試験を下敷きにする。PoC のサーバーは生成済みのファイルを配るだけなので、8 の作りの裏付けにはならない。

## 守ること

仕組みと試験は、次の 9 つを守るためにある。以下の節で「守ること 1」のように引く。

1. **閲覧専用。** browse は、領分の外では、自分が作ったファイルとディレクトリのほかを、書き換えない、名前を変えない、消さない。例外は、書き出しのために空のディレクトリを取り除くことだけである。Wiki のルートの下には、何も作らない。未解決リンクをクリックしてもファイルを作らない。領分と守る範囲は、[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 2 にある（[ADR-0017](../adr/0017-wiki-browse-changes-only-what-it-created.md)。2026年11月14日に言い換えた）。
2. **lint と同じ判定。** ページの集合、リンクの解決、`sources:` の解決は、lint と同じ関数で決める。browse の未解決リンクの一覧は、同じ内容に対する `wiki_lint.py` の `broken_links` と一致する。これは、すべてが分かるときに成り立つ。分からないことがあるときは、守ること 9 を先にする（[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 4.1）。
3. **1 つの出力は 1 つの写しから。** 静的版の 1 つの世代と、サーバーの 1 つの応答は、1 度の読み取りで作った 1 つの写しだけから作る。
4. **生成器は絶対パスを出力に入れない。** 例外は、利用者が選んだ `raw:` の表示だけである。
5. **表示で外へ通信しない。** 外への移動は、利用者が外部リンクをクリックしたときだけ起き、`Referer` を付けない。
6. **方式を交換できる。** サーバーと静的版は、同じ中核の同じ関数でページを描く。リンクの移動、被リンク、関係表、診断の結果が一致する。
7. **サーバーは手元からしか使えない。** 127.0.0.1、Host の確認、起動ごとのトークン、中核が知っている名前だけを返す。
8. **途中の生成物を見せず、失敗したら前のものが残る。** 静的版は世代を作り終えてから切り替える。サーバーは作り終えた中核だけで答える。
9. **状態を区別して示す。** 「使えない」「古い」「0 件」を、データでも画面でも区別する。

## 1. ファイルの構成

`skills/info-hive/scripts/` に置く。

| ファイル | 中身 |
| --- | --- |
| `wiki_browse_core.py` | 中核。写し（2）を作り、そこからページ、リンク、被リンク、関係表、ナビゲーション、診断を組み立て（3）、ページの HTML を描く。書き込みはしない |
| `wiki_browse_fs.py` | 入出力の層（6）。browse のファイルの入出力は、読み書きとも、このモジュールの口を通る |
| `wiki_browse.py` | 入口。`build`（7）、`serve` と `stop`（8）、`core`（9）。PEP 723 の依存は `pyyaml==6.0.3`（グラフの抽出と同じ版）だけで、`uv run --script` で動かす |
| `browse_assets/` | 画面の部品（`app.js`、`style.css`）。PoC の `poc/browse/static/` から検索欄を除いたもの |

既存のスクリプトには、振る舞いを変えない切り出しを 3 つ行う。

- `wiki_pages.py`: 設定済みのパーサーを作る関数 `new_parser()` と、wikilink の行き先と別名を取り出す正規表現を公開する。lint が使う今のパーサーも `new_parser()` で作る（3.3）。
- `wiki_lint.py`: 索引のファイル（`index.md` と `indexes/` の Markdown）を並べる部分を関数にする。browse が同じ集め方をするためである（2）。
- `wiki_graph_extract.py`: `read_ontology(path)` を、文字から読む `parse_ontology(text)` と、ファイルを読む部分に分ける（2）。

中核は HTML まで描く。ADR-0010 の「表示の側は Markdown を解釈しない」は、アダプタ（サーバー、静的の書き出し、将来のアプリ）が解釈しないという意味である。

## 2. 写し（スナップショット）

中核は、入力を 1 度だけ読み、その写しだけから組み立てる（守ること 3）。

- **入力の集合**: `wiki_pages.iter_page_files()` のページ、索引のファイル（lint の `collect_index_entries` と同じ集め方）、`graph/ontology.yaml`。`index.md`、`log.md`、`SCHEMA.md`、`README.md` と `raw/`、`assets/` などは、lint と同じくページではない。
- **手順**:
  1. **読む前に**、入力の印を取る。印は、入力の集合を含む上位の集合（Wiki の下のすべての Markdown と、オントロジー）の、ディスク上の相対パス、大きさ、更新時刻をまとめたハッシュである。シンボリックリンクとジャンクションのディレクトリもたどる（`indexes/` がリンクでも lint は中の索引を読む。印は入力を含む上位の集合であればよい）。同じディレクトリは 1 度だけ走査し、ページでも索引でもない最上位のディレクトリ（`raw/`、`assets/` など）は走査しない。走査で一覧を作れないディレクトリがあれば、印を取れないとする（`rglob` は黙って飛ばすので、そのままでは「0 ページの正常な Wiki」と区別できない。守ること 9）。そのうえで入力の集合を並べる。入力の集合だけを並べるとき（守る場所を決めるときなど）も、同じ範囲の一覧を作れることを先に確かめる。入力でない最上位のディレクトリを読めなくても、閲覧の起動、作り直し、停止は止めない。
  2. 各ファイルを 1 度だけ、バイト列として読む。読めたファイルについて、実体の識別（6.2）と、バイト列の SHA-256 を記録する。
  3. バイト列を、lint とグラフの抽出の `read_text(encoding="utf-8-sig")` と同じ文字にする。`utf-8-sig` で読み、改行（CR LF と CR）を LF にそろえる（`io.TextIOWrapper` の `newline=None`）。バイト列をそのまま `decode()` すると CR が残り、CR だけの改行のファイルで frontmatter の切り分けが lint と変わる。
- **ページの辞書**: 同じ文字から、2 つの辞書を作る。ファイルは読み直さない。
  - lint の形: `wiki_lint.parse_frontmatter_raw()` と `canonical_meta()`、`wiki_pages.extract_wikilinks()`。メタ欄、題名、リンクの解決に使う。描く本文は、この形の `body`（lint がリンクを拾う本文と同じ文字）である。
  - グラフの形: 関係表にだけ使う。`wiki_graph_extract.parse_frontmatter()`（PyYAML）の結果から、入れ子の `graph` の欄だけを取り、ほかの最上位の欄（`type`、`kind`、`sources`、`raw` など）は、lint の形の値を使う。そのうえで、グラフの抽出と同じ `normalize_refs()` をかける。
  - 最上位の欄を lint の形にそろえるのは、2 つのパーサーが同じ frontmatter を違う値に読むことがあるからである。`sources: [true]` は、lint では文字の `true`（`true.md` に解決する）、PyYAML では真偽値（`True` という未解決の出典）になる。別々の値を使うと、メタ欄では解決した出典が、同じページの関係表と診断では未解決になる。メタ欄、`sources` の解決、関係表の `sourced_from` は、どれも lint の値で決める（守ること 2）。lint のパーサーは入れ子の欄を読まないので、`graph` だけは PyYAML の値を使う。
  - どちらも `rel_path`（NFC）、`disk_rel_path`、`slug` を、lint の `collect_pages` と同じ規則で持つ。
- **Wiki の外を指す入力**: シンボリックリンクやジャンクションで実体が Wiki の外にあるファイルも、lint と同じに読む（守ること 2）。出力には Wiki の中の相対パスだけを使う。実体の場所は、書き込みから守る対象に入れる（6.1）。
- **読めない入力**: 開けない、UTF-8 でない入力は、種類（`os` か `decode`）だけを記録する。例外の文字列は絶対パスを含むので、どこにも入れない（守ること 4）。読めないページは描かず、診断（`read_error`）に識別子を挙げる。写しは「読めなかった入力がある」ことを持つ（8.3 の読み直しに使う）。
- **世代**: 入力のすべて（ディスク上の相対パスと、バイト列の SHA-256。読めないものはその旨）と、中核の版から作るハッシュ。本文、frontmatter、索引、オントロジーのどれを変えても変わる。
- **限界**: ファイルを 1 つずつ読むので、読んでいる途中の編集で、古いページと新しい索引が混ざることはある。印を読む前に取るので、サーバーでは次の要求で違いが見つかり、作り直される（8.3）。

## 3. 中核の組み立て

### 3.1 識別子と、その衝突

- **識別子**は、NFC の POSIX の相対パスから `.md`（大文字と小文字を問わない）を除いたものである（ADR-0010 のデータの契約）。
- **読めたページ**だけを組み立ての対象にする。lint も、読めないページを除いてから重複とリンクを判定する。
- 読めたページのうち、識別子が同じになる 2 つ以上のページは、どれも描かず、診断に `id_collision` として、識別子とディスク上の相対パスを挙げる。Linux では、NFC と NFD だけが違う名前、`x.md` と `x.MD`、`a\b.md` と `a/b.md`（`\` を `/` にそろえるので同じになる）を、同時に置ける。衝突の原因は列挙せず、識別子が同じかどうかだけで決める。
- リンクの解決（3.3）には、これらのページも入れる（lint と同じ集合で解決するため）。衝突したページのスラッグは同じとは限らない（`a\b.md` は `a\b`、`a/b.md` は `b`）ので、リンクが衝突したページ 1 つだけに当たることがある。その扱いは 3.3 で決める。
- 別のディレクトリの同じスラッグのページ（`concepts/x.md` と `entities/x.md`）は、識別子が違うので、どちらも描く。

### 3.2 出力の名前

`export_name()`（未決だった事項の決定の 3）。PoC の `gen.py` の規則を移し、次を直す。

- **Windows の予約名**: `CON`、`PRN`、`AUX`、`NUL`、`CONIN$`、`CONOUT$`、`COM0`〜`COM9`、`LPT0`〜`LPT9`、上付きの数字の `COM¹`〜`COM³`、`LPT¹`〜`LPT³`。最初の `.` より前を、末尾の空白と `.` を除き、大文字と小文字を区別せずに比べる（Python 3.13 の `ntpath.isreserved()` と同じ範囲）。
- **相対パスにする**: 空の要素、`.`、`..` は `_` に替える（Linux の `\tmp\a.md` は、`/` にそろえると先頭が空の要素になり、そのままでは絶対の出力の名前になる）。書き出しは、名前が書き出し先の下に収まることを、書く直前にもう一度確かめる。
- **生成器の名前**: 最上位の `index.html`、`nav.js`、`data`、`assets` と、どの階層でも `.browse-` で始まる名前（6.4 の目印）は、ページの出力に使わない。
- ほかの規則（Windows で使えない文字、末尾の空白と `.`、接尾辞の形の名前、`.html` で終わるディレクトリ、UTF-8 で 200 バイトを超える要素）は PoC のとおりである。名前を変えたら `~<その要素までの識別子の SHA-256 の先頭 8 桁>` を付ける。大文字と小文字だけが違う出力は、衝突した全員に接尾辞を足す。
- 最後に、全部の出力の名前に重なりがないことを確かめる。接尾辞を付けた名前どうしが重なったとき（SHA-256 の先頭 8 桁が同じになる識別子は、作ろうと思えば作れる）は、重なった全員の接尾辞の桁を、重なりがなくなるまで 4 桁ずつ増やす。それでも重なれば、組み立てを失敗にする（`NameCollision`）。

### 3.3 描画とリンク

- **パーサー**: `wiki_pages.new_parser()`（同梱の markdown-it-py 3.0.0、commonmark、生の HTML は無効、表は有効）で作る。lint のリンクの抜き出しと同じ設定なので、同じ本文から同じトークンができる（守ること 2）。browse は、これに wikilink を描く規則だけを足す。
- **wikilink**: `inline` の中の `text` のトークンを、`wiki_pages` の正規表現で、文字と wikilink に分ける。`wiki_pages.extract_wikilinks()` が拾うものと、描画が wikilink として描くものは、同じ場所から同じ正規表現で取るので一致する。コードの中の `[[...]]` は wikilink にしない。
- **解決**: 行き先を `wiki_pages.link_candidates()` に渡し、当たるページの数で決める。索引は、読めたページ全部（`build_page_index()`）から作る。
  - 1 つで、そのページが描かれている: `resolved`。そのページへの相対の href にする。
  - 2 つ以上、または、1 つだがそのページが `id_collision` で描かれていない: `ambiguous`。行き先のページを 1 つに決めて表示できない、という状態である。どこにも移動しない文字として、状態を示して描く。
  - 0: `unresolved`。リンクにせず、状態を示して描く。クリックしても何も起きない（守ること 1）。
  - lint の `broken_links` は「当たるページが 0」のリンクなので、`unresolved` の一覧はそれと一致する。`ambiguous` は、lint では解決するが、browse が表示できるページを 1 つに決められないリンクである。
  - 被リンク、ナビゲーション、メタ欄の `sources`、関係表の相手も、同じ規則で「描かれているページ 1 つ」に決まるときだけリンクにする。
- **見出しへのリンク**（`[[slug#見出し]]`）: `resolved` で、行き先のページに合う見出し（3.4）がなければ `missing_heading` を足し、ページの先頭へのリンクにする。
- **wikilink 以外のリンク**:
  - `http:`、`https:`、`mailto:` の Markdown のリンクと自動リンクは、外部へのリンクとして描く。`rel="noopener noreferrer"` と、外部であることの印を付ける。各ページに `<meta name="referrer" content="no-referrer">` を置く（守ること 5）。
  - それ以外（相対パス、ほかのスキーム）は、出力の配置が Wiki の配置と違うので、リンクにしない。リンクの文字に、行き先を括弧に入れた文字を添える。markdown-it の既定の `validateLink`（`javascript:`、`vbscript:`、`file:`、画像以外の `data:` を拒む）は変えない。
  - Markdown のリンクの文字の中に wikilink があるとき（`[ [[a]] ](https://example.invalid/)`）は、外側をリンクにせず、上の「それ以外」と同じに描く。中の wikilink は、その状態のとおりに描く。リンクの入れ子を作らず、未解決の wikilink が外側のリンクでクリックできるようになることもない。
  - 画像は、代替テキストだけを出す（ADR-0005 のとおり、図の表示は第 1 段階に含めない）。
- 本文、題名、メタ欄の値、別名は、どれも HTML として解釈されないようにエスケープする。
- 出力の HTML に、インラインの `style`、インラインのスクリプト、イベントの属性を出さない（CSP の `style-src 'self'` と `script-src 'self'` に合わせる）。パーサーは、配置を指定した表（`| :--- | ---: |`）のセルに `style="text-align:…"` を付けるので、描画でこれをクラス（`ta-left`、`ta-center`、`ta-right`）に替える。

### 3.4 見出しと ID

- 見出しは、パーサーの `heading_open` から取る（ATX と Setext）。
- **見出しの文字**は、表示される文字である。見出しを本文と同じに描き、タグを除き、文字参照を戻したものとする。`## **Definition**`、`## [[other|Definition]]`、`## ![Definition](diagram.png)` は、どれも `Definition` になる。
- **鍵**: 見出しの文字を NFC にして小文字にし、空白を `-` にし、`-` 以外の ASCII の記号（`_` を含む）を除く。空になれば `section` とする。
- **ID**: 鍵をそのまま使う。同じページで使った ID と重なれば、使っていない ID になるまで連番を付ける（`## 例`、`## 例`、`## 例-1` は `例`、`例-1`、`例-1-1`）。
- **照合**: `[[slug#見出し]]` の `見出し` から同じ規則で鍵を作り、**鍵**が一致する最初の見出しの **ID** へ移動する。`[[対象#例-1]]` は、見出しの文字が `例-1` である 3 つ目の見出し（ID `例-1-1`）を指す。
- **画面の部品の ID** は、`_` で始める（`_nav`、`_main` など）。見出しの ID は `_` を含まないので、重ならない。

### 3.5 被リンク

`resolved` のリンクを逆に引く。自分へのリンクは数えない。同じページからの複数のリンクは 1 件にまとめる。

### 3.6 関係表

- オントロジーの状態を 3 つに分ける（守ること 9）。
  - ない: `relations: "none"`。関係表を出さない。
  - 読めない、または中身が誤っている: `relations: "error"`。関係表の場所に「オントロジーを読めない」と出し、診断に挙げる。ファイルを開けなかった場合だけ、写しの「読めなかった入力がある」に入れる（中身の誤りは、読み直しても変わらない）。
  - 作れた: `relations: "ok"`。そのページの関係が 0 件なら「関係はない」と出す。
- 作り方: 写しのグラフの形のページ（読めたページ全部。`id_collision` のページも含める。グラフの抽出と同じ入力にするため）を、`build_nodes()` と `build_edges()` に渡す。
- **出ていく関係**: エッジの `page` が、そのページであるもの。
- **入ってくる関係**: 目的語のノードを持つページが、そのページだけであるもの。主語の側は、エッジの `page` のページである。
- 同じ `graph.node_id` を持つページが 2 つ以上あるとき（グラフの抽出の診断 `duplicate_node_id`）は、そのノードへの入ってくる関係をどのページにも出さない。出ていく関係は、それぞれのページに出す。
- 表に出すのは、型付きの関係と `sourced_from` である。`mentions`（本文の wikilink）は被リンクと重なり、`summarizes_raw` はメタ欄の `raw` と重なるので出さない。
- 表の欄は、向き、述語、相手、状態（`status`）、期間（`valid_from`、`valid_to`）、確からしさ（`confidence`）、出典（`source`）、証拠（`evidence`）である。相手と出典は、描かれているページ 1 つに決まればリンクにし、決まらなければ文字で出す。
- グラフの抽出が挙げた診断は、次のページの診断に載せる。診断の中のページは、識別子に直して出す。
  - `ambiguous_object`、`ambiguous_source`、`unresolved_source`、`order_dependent_edge_ids`: 診断の `page`（NFC の相対パス）のページ。
  - `duplicate_node_id`: `page` を持たず、`pages`（ディスク上の相対パスの並び）を持つ。その `pages` のそれぞれのページに載せる。入ってくる関係を出さない理由の表示を兼ねる。
  - 載せる先のページが描かれていないとき（`id_collision`）は、全体の診断（`data/diagnostics.js`）にだけ載せる。

### 3.7 ナビゲーション

索引のファイルを、ページとしては描かずに読む。lint の `collect_index_entries` は種類の見出ししか読まないので、使わない。

- 索引を同じパーサーで解析し、見出しの入れ子（`#` から `######`）をグループの木にする。リストの項目は、直前の見出しのグループに入れる。最初の見出しより前の項目は、そのファイルの最上位のグループに入れる。入れ子のリストの項目も同じグループに入れる（リストの入れ子は木にしない）。
- 項目が指すものは、その項目の段落（入れ子のリストを除く）の**最初の** wikilink で決める。後ろの wikilink は見ない。
  - 行き先が `indexes/` の索引のファイル（`[[indexes/concepts]]`）なら、そのファイルのグループへのリンクにする。
  - そうでなければ、3.3 の規則で解決する。`resolved` ならページへのリンク、`ambiguous` と `unresolved` なら状態つきの文字にする。`- [[missing]] — 関連：[[a]]` は、未解決の `missing` の項目になる。
  - wikilink のない項目は出さない。
- 同じページが複数の場所に載っていれば、それぞれの場所に出す。
- `indexes/` があれば、ファイルごとに最上位のグループを 1 つ作る。名前は、frontmatter の `title`、最初の見出し、ファイル名の順で決める。
- 索引に載っていない、描かれているページは、種類（`type`）ごとの「索引にないページ」のグループに入れる。
- 読めない索引のファイルは、診断（`read_error`）に挙げ、そのファイルの分を空にする。
- 結果を `nav.js` に書き、各ページは共有の `nav.js` を読み込む。

### 3.8 メタ欄と `raw:`

- 題名は、frontmatter の `title`、なければスラッグ（検索と同じ）。
- メタ欄に出すのは、`type`、`tags`、`summary`、`created`、`updated`、`sources`、`raw` である。値は lint の形の辞書から取る。
- `sources` の値は、`wiki_pages.classify_source_ref()` で解決する。描かれているページ 1 つに決まればリンクにし、そうでなければ文字にする。
- **`raw:`**（未決だった事項の決定の 7）: 中核は `{kind, value, sha256}` で持つ。
  - `kind` は、`absolute`、`relative`、`url` のどれかである。ドライブ名つきのパス、`/`・`\`・`~` で始まる値（lint の `missing_raw()` が絶対パスとするもの）と、`file:` の URL は `absolute` にする。`file:` の URL は、指しているローカルのパスを `value` にする。`url` は、`file:` 以外のスキームを持つ値である。残りは `relative` である。
  - 描き方は 4 つある。`text`（値を文字で出す）、`link`（`file:///` のリンクにする）、`basename`（ファイル名と `raw_sha256` の先頭 12 桁だけを出す）、`none`（出さない）。`link` でも、`~` で始まる値はホームに展開せず、文字で出す（生成器が機械の情報を出力に足さないため。[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 8）。
  - `link` と `basename` が効くのは `absolute` だけである。`relative`（基準が 3 通りあり、一意に決まらない）と `url`（開くと外への通信になる）は、`none` 以外では文字で出す。
  - 既定は、サーバーが `text`、既定の書き出し先への静的版が `link`、`--out` への静的版が `basename` である。`--raw` で選べる。

### 3.9 診断

- 種類: `unresolved`、`ambiguous`、`missing_heading`（リンク）、`read_error`、`id_collision`、`renamed`（出力の名前を変えた）、グラフの抽出の診断（3.6）、`relations_error`、`stale`（8.3）。
- 各ページの末尾に、そのページの診断を事前に描く。全体は `data/diagnostics.js` に置く。
- 診断に入れるのは、種類、識別子、リンクの行き先、相対パスだけである（守ること 4）。

## 4. 画面の契約（ADR-0010 のとおり）

- ページ間のリンクは相対の href だけにする。名前の要素ごとにパーセントエンコードする。
- スクリプトは classic な `<script src>` だけにする。`fetch`、ES モジュール、Web Worker を使わない。データは `nav.js` と `data/*.js`（`window.WIKI_NAV` など）に置き、`</`、U+2028、U+2029 をエスケープする。
- 各ページの HTML に、本文、メタ欄、被リンク、関係表、診断を事前に描く。JavaScript を切っても読める。`<noscript>` に `index.html` へのリンクを置く。
- CSP を `<meta>` に付ける（`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'`）。
- `data/manifest.js` に、`protocol_version`（1）、世代、生成日時（サーバーでは、その世代の中核を組み立てた時刻）、能力（`search: "none"`、`relations`、`rag: false`、`multi_wiki: false`、`live_reload: false`）を置く。生成日時はここにだけ置き、ページの HTML には入れない（同じ写しからは同じ HTML ができ、回帰の検査に使える）。
- 各ページの `<html>` に `data-generation` を書く。データのファイル（`nav.js`、`data/manifest.js`、`data/diagnostics.js`）は、どれも自分の世代を持つ。`app.js` は、知らない `protocol_version` なら表示を止める。読み込んだデータのファイルのどれか 1 つでも、世代がページの世代と違えば、「Wiki が更新された。再読み込みする」と出す。サーバーでは、ページとデータを別々の要求で取るので、そのあいだに作り直しが入ると、世代の違うものが混ざる。`data/manifest.js` だけを比べると、入力を変えて元に戻したときに、ナビゲーションだけが別の世代のまま、印なしで残る。
- 先頭のページは `index.html`（ナビゲーションの全体）である。

## 5. 絶対パスの検査（守ること 4）

2026年11月14日に、[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 5 と 8 に合わせて書き換えた。利用者が書いたかを推し量る仕組み（描画が出した文字の記録）はなくした。

- **作り方で守る**: 写しは、内容（入力ごとの種類、相対パス、文字か読めない理由、世代）だけを持ち、`Path` と、機械の絶対パス（Wiki のルート、ホーム、`data_dir`）を持たない。中核は、内容だけを受け取る。生成器は、機械の情報（絶対パス、トークン）を出力に足さない。出力に機械の情報が入るのは、入力の実体の中身にあるときだけである。だれがその中身を書いたかは問わない。
- **生成の記録**は、ファイルに書かない。標準出力に 1 行で出す。
- **公開の前の検査**（静的版）: 作った世代の全ファイルから、Wiki のルート、ホーム、`data_dir`、Wiki の外にある入力の実体の絶対パスと、`<data_dir>/browse/` の下のすべての状態のディレクトリの記録のトークンを探す。`/` 区切り、`\` 区切り、JSON の文字列の中の `\\` 区切り、HTML のエスケープ、URL の符号化のそれぞれの形で探す。見つかれば、ファイルの名前を挙げて警告を出す。書き出しは止めない。記録があるのに読めないときは、「トークンが含まれていないかを確かめられなかった」と警告を出す。
- Wiki のページが `server.json` を指していると、操作のトークンがページに描かれる。静的の書き出しでは、書き出したファイルに残り、持ち出すと渡る。検査が警告を出す。トークンは起動ごとに変わり、サーバーが終われば使えない。
- 生成器が機械の情報を入れないことは、試験（11 の「絶対パス」と、構造の直しの設計の 8 の作りの確かめ）で確かめる。試験用の Wiki、ホーム、`data_dir`、Wiki の外に置く入力の実体を、それぞれ別の目印になる文字を含むディレクトリにし、本文にはどの文字も書かず、静的版の全ファイルとサーバーの全応答と、組み立てたあとの中核の値に、どの文字もないことを確かめる。

## 6. 入出力の層と書く側（守ること 1）

2026年11月14日に、[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 2、3、6 に合わせて書き換えた。Wiki と入力の実体を調べて守る作り（守る場所、実体の重なりの判定）をやめ、「browse は、領分の外では、自分が作ったものだけを置き換え、消す。Wiki のルートの下には作らない」作りにした。詳しい規則は、その設計にある。

- **層**: browse のファイルの入出力は、すべて `wiki_browse_fs.py` の決まった口（`os.lstat`、`os.stat`、識別子の関数、`os.scandir`、`os.open` と読み書き、ファイルを作る口、`os.mkdir`、`os.rename`、`os.replace`、`os.unlink`、`os.rmdir`、`os.path.realpath(…, strict=True)`、ロック）を通す。`wiki_browse.py` と `wiki_browse_core.py` は、入出力を呼ばない。試験が、構文木で確かめる。
- **失敗の読み替え**: 層の 1 つの関数だけが、OS の失敗を「ない」と「分からない」に分ける。呼ぶ側は、「分からない」を空、偽、既定の値に直さない。「ない」という答えから、あとの書き込みが安全だと決めない。
- **Wiki のルートと重ならないこと**: 書き込みの口が、どれも、名前を足す、変える、消すディレクトリが Wiki のルートでもその下でもないこと、動かすディレクトリが Wiki のルートでもその祖先でもないことを、識別子で確かめる。どの口も、名前そのものに働き、最後の名前のリンクをたどらない。ファイルを作る口は、Windows では `CreateFileW` に `FILE_FLAG_OPEN_REPARSE_POINT` を付けて呼ぶ。
- **領分**: `<data_dir>/browse/` の全体（既定の書き出し先、状態のディレクトリ、作業用のディレクトリ、共通のロック）と、`--out` の書き出し先の隣の `<名前>.browse-work/`。領分の中に利用者が手で置いたものは守らない。領分の根の名前そのものがリンクなら、使わずに止まる。根より下では、どの操作もリンクを通らない。`<data_dir>` そのものは、どうたどって届いてもよい。
- **目印**: 作業用（`.browse-work`）と状態のディレクトリ（`.browse-server`）は、目印を持つ。既定の書き出し先の作業用と状態のディレクトリの目印には、Wiki のルートの識別子を書き、触れるたびに照らす。目印がなく、空でもないディレクトリは、使わない。
- **消し方と作り方**: 名前を 1 つずつ消す。リンクはたどらずに外す。属性は変えない（読み取り専用のファイルは、警告を出して残す）。分からなければ止め、警告を出して残す。ロックの名前に利用者が置いたリンクは、たどらずに外してから作る。
- **入れ子**: 書き出し先と作業用のディレクトリを、ほかの browse のディレクトリと、browse のデータの場所の中には作らない（0.10.0 と同じ）。
- Python が import のときに書くバイトコードは層を通らないので、`wiki_browse.py` は、先頭で、標準ライブラリ以外を import する前に `sys.dont_write_bytecode = True` にする。
- **限界**: 代替データストリーム、拡張属性、アクセス制御の一覧、マウント、調べてから操作するまでの競合、利用者が書き換えた一覧は、守る範囲の外である（構造の直しの設計の 2.2、11）。

## 7. 静的の書き出し（`wiki_browse.py build`）

2026年11月14日に、[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 6.3、6.4、7 に合わせて書き換えた。

- **書き出し先**: 既定は `<data_dir>/browse/<wiki_key>/`（未決だった事項の決定の 2）。`--out <dir>` で選べる。`--out` の親のディレクトリがなければ、何も作らずに止まる。`data_dir()` と `wiki_key()` は `wiki_mcp_common` のものを使う。
- **読む**: 書き込みの前に、写し（2。構造の直しの設計の 4.2 の 2 回の走査）を採り、すべてのページを描く。読んでいるあいだに Wiki が変われば、3 回までやり直し、変わり続ければ失敗で終わる。そのあと、公開の前の検査（5）をする。
- **門**: `--out` の書き出し先は、ない、空、一覧（`.browse-generation`。ファイルとディレクトリの名前、ファイルの大きさと SHA-256）と照らして世代の全体が合う、のどれかのときだけ置き換える。そうでなければ、理由を挙げて止まる。0.10.0 の書き出し（一覧に名前とハッシュがない）は、消してからやり直すよう知らせる。既定の書き出し先は領分なので、門を通さず、前の世代を読まない。
- **手順**:
  1. 領分の根に入る（`--out` の書き出しも、共通のロックを取るので入る）。書き出し先とその親を確かめる。書き出し先の名前そのものが、ないか実のディレクトリでなければ止まる。共通のロック `<data_dir>/browse/build.lock` を取る（取れなければ 60 秒待つ）。作業用のディレクトリを使い、そのロックを取る（取れなければ止まる）。
  2. 作業用の残り（`tmp-N`、`del-N`、0.10.0 の `seq` と `build-report.json`）を消す。
  3. 書き出し先が「ない」か「空」で、`old-N` があれば、名前の番号がいちばん大きい `old-N` を、戻せるとき（名前そのものが実のディレクトリで、`--out` ならその場で門を通る）だけ戻す。番号を決めるのに一覧は読まない。
  4. 門（上）。
  5. 通し番号を、作業用にある名前（`tmp-N`、`old-N`、`del-N`）の番号のいちばん大きいものに 1 を足して決める。
  6. `tmp-N` を作り、一覧を書き、世代のファイルを排他で作る。
  7. 入れ替える。書き出し先が空なら取り除き、世代なら `old-N` に退避する。`tmp-N` を書き出し先の名前にする（**確定の点**）。付け替えに失敗したら、`old-N` を戻す。
  8. 確定のあと、`old-N` を `del-N` に付け替えてから消す。失敗しても、警告を出し、終了コードは 0 にする。
  9. 生成の記録を標準出力に出す。出せなくても、警告を標準エラーに出そうとし、終了コードは 0 にする。
- どの手順のあとで止まっても、書き出し先か、作業用の `old-N` に、最後に公開した世代が残る（守ること 8）。終了コードは、書き出し先にある世代だけで決める。
- 標準出力には、成功したときに `{"out": …, "generation": …, "pages": …, "warnings": …}` を 1 行で出す。思わない例外でも、種類だけの短い知らせと、0 でない終了コードで終わる。スタックトレースは `--debug` を付けたときだけ出す。

## 8. サーバー（`wiki_browse.py serve` と `stop`、構成 B）

### 8.1 待ち受けと要求の扱い（守ること 7）

- 127.0.0.1 だけで待ち受け、ポートは OS に選ばせる。
- **閲覧の口**: `/<閲覧のトークン>/w/<wiki_key>/<出力の名前>`。
  - Host ヘッダーが `127.0.0.1:<port>` と一致しなければ 421。トークンは時間の一定な比較で確かめ、違えば 404。GET と HEAD 以外は 405。
  - パスは、クエリを除き、パーセントデコード（UTF-8 として正しくなければ 404）してから `/` で分ける。`..`、`.`、空の要素、`\`、NUL を含めば 404。
  - 返すのは、今の中核が知っている出力の名前（ページ、`index.html`、`nav.js`、`data/*.js`）と、同梱の画面の部品だけである。要求のパスからファイルシステムを引かない。
- 応答に、CSP、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer` を付ける。エラーの応答には、パスも例外の文字列も入れない。
- サーバーの記録（標準エラー）には、方法、口の種類、状態の番号だけを書く。要求のパスは書かない（トークンを残さない）。

### 8.2 開いたときに描く

起動後の最初の要求で中核を組み立て、ページは要求されたときに、その時点の中核から描く。描く関数は静的の書き出しと同じである（守ること 6）。1 つの要求は、1 つの中核だけを使う（守ること 3）。

### 8.3 作り直し

閲覧の口への、画面の部品を除く要求のたびに、次を行う。操作の口（8.4）のうち `control/status` と `control/stop` は、中核を使わず、この手順を通らない。中核がなくても、組み立てに失敗していても、組み立ての途中でも、すぐに答える。

1. 入力の印（2）を取る。今の中核の印と同じで、下の「もう一度試す」にも当たらなければ、今の中核で答える。
2. そうでなければ、組み立てのロックを取る。組み立ては同時に 1 つしか走らない。ほかの要求が組み立てていれば、終わるのを待つ（上限 30 秒）。待ったあとで印を取り直し、今の中核と同じなら、それで答える。
3. 新しい写しと中核を組み立て、組み立て終えてから入れ替える。新しい中核に結び付けるのは、読む前に取った印である。そして新しい中核で答える。

- 変更のあとの最初の要求が、新しい内容で答えられる。組み立ての途中の中核は、どの要求にも使わない（守ること 8）。
- **「古い」と示す条件**（守ること 9）: 答えに使う中核の印が、その要求で取った印と違うとき、その答えは古い。組み立てに失敗して前の中核を使い続けるときと、待ちが上限を超えて今の中核で答えるときの、どちらも当てはまる。古い答えでは、ページの先頭に「Wiki の最新の内容を表示できていない。前の内容を表示している」と事前に描き、診断（`stale`）にも載せる。理由（組み立ての失敗か、組み立て中か）の種類だけを出し、例外の文字列は出さない。
- **中核がまだないとき**: 最初の組み立てに失敗したとき、最初の組み立てを待って上限を超えたときは、答えに使う中核がない。閲覧の口は、503 と、理由の種類だけの短い説明を返す（`Retry-After` を付ける）。このときも、`stop` と使い回しの確かめは働く。
- **知らない名前への要求**: トークンは合っているが、今の中核にない名前への要求には、404 と、「ページが見つからない。Wiki が更新されたかもしれない」という短い説明と、`index.html` へのリンクを返す。前の世代のページやナビゲーションから、名前の変わったページをたどったときの行き先になる。
- **もう一度試す**: 次のどちらかのあいだは、印が今の中核と同じでも、組み立てを試みる。
  - 前の組み立てが失敗している。失敗の原因になった変更を取り消して、印が前と同じに戻った場合に、古い状態を解くためである。
  - 今の中核の写しに「読めなかった入力がある」。Windows の共有違反のように、ファイルを変えずに読めるようになることがあるからである。ページ、索引、オントロジーのどれにも当てはまる。
- **同じ印では、5 秒は試さない**: 前に組み立てを試みた印と同じ印での組み立ては、その試みを始めてから 5 秒たつまで始めない。印が変わったまま組み立てが失敗し続けるときも、上の「もう一度試す」のときも、この 1 つの規則で、失敗する組み立ての繰り返しを抑える。印が変われば、すぐに試みる。
- 大きさと更新時刻を変えずに中身だけを変えた編集は、見逃す（MCP の索引の変更の印と同じ限界）。
- **入力の名前の集合が分からないとき、読んでいるあいだに Wiki が変わったとき**（2026年11月14日に足した。[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 4.1、4.2）: 新しい中核を採らない。前の中核を「古い」と示して使い、なければ 503 を返す。次の要求で、またやり直す。入力の印は、写しと同じ 1 つの入力の一覧（ページ、索引、オントロジー）から作る。
- **ページの中身を読めないとき**: そのページがない Wiki と同じに描き、読み取りの印（「読めない」、診断の `read_error`、中身に依る一覧の「不完全」）を足す。索引のファイルとオントロジーも同じ規則である。
- **1 ページを描けないとき**: そのページに「このページを描けない」と出し、単位は失敗にしない。描画は中核を変えないので、同じ中核からもう一度描ける。
- 0.10.0 にあった、状態のディレクトリと入力の重なりを見てサーバーを終わらせる仕組みは、なくした。Wiki のページが browse の状態のファイルを指していても、Wiki の内容として読んで描き、サーバーは動き続ける。

### 8.4 1 つの Wiki に 1 つのサーバー

- **状態の置き場所**: `<data_dir>/browse/<wiki_key>.server/`。目印、`server.lock`、`server.json` を置く。書き込みは 6 を通る。このディレクトリの名前そのものがリンクなら止まる。目印と記録には Wiki のルートの識別子を書き、記録を読む側（使い回し、`stop`）は、それと、記録の `instance` がその口で答えているサーバーと同じかを、いつも確かめる（[構造の直しの設計](wiki-browse-structure-2026-11-11.md)の 7.1）。
- **ロック**: サーバーは、生きているあいだ、`server.lock` を OS のファイルのロックで持つ。プロセスが止まれば OS が外す。
- **記録**（`server.json`）: ポート、閲覧のトークン、操作のトークン、インスタンスの ID（起動ごとの乱数）、開始の時刻。PID は書かない。POSIX では、状態のディレクトリを 0700、記録を 0600 で作る（wiki の MCP サーバーの記録と同じ）。Windows では、`data_dir` の場所のアクセス権に頼る。既定の場所は利用者のプロファイルの中である。`INFO_HIVE_DATA_DIR` で別の場所にしているときは、起動のときに「ほかの利用者が読める場所なら、記録のトークンを読まれる」と標準エラーに警告を出す（限界に挙げる）。
- **操作の口**: `/<操作のトークン>/control/…`。Host の確認は閲覧と同じである。操作のトークンは、閲覧の URL にもページにも出さない（ブラウザの履歴に残る URL からは止められない）。
  - `GET …/control/status`: インスタンスの ID と `wiki_key` を返す。
  - `GET …/control/locate/<パーセントエンコードした行き先>`: 行き先を 3.3 の規則で解決し、状態と、`resolved` ならページの出力の名前を返す。行き先は、符号化した 1 つの要素として受け取り、8.1 のパスの確かめ（`/`、`..`、`\` を拒む）を通さない。ファイルのパスとして使わず、中核の解決に渡すだけだからである。`[[concepts/a]]` と同じに、区切りの違う行き先や先頭に `/` のある行き先も解決できる。この口だけは中核を使うので、8.3 の手順を通る。答えに使う中核がなければ、状態を `unavailable` として返す（`serve` は `index.html` の URL を出す）。
  - `POST …/control/stop`: 応答を返してから終了する。
- OS のプロセスを外から終わらせること（`os.kill`）はしない。

### 8.5 `serve` の流れ

1. 領分の根と状態のディレクトリに入り（6。なければ作って目印を置く）、`server.lock` を取ろうとする。
2. **取れた**（動いているサーバーはない）: 前の記録が残っていれば消す。待ち受けを始め、記録を書き、4 に進む。中核は、最初の要求で組み立てる。
3. **取れなかった**（動いているサーバーがある）: 記録を読み、`control/status` のインスタンスの ID が記録と一致するのを待つ（200 ミリ秒おき、上限 10 秒。起動の途中のサーバーは、記録を書き終えていないことがある）。一致すれば使い回す。待っているあいだ、毎回 `server.lock` も取り直してみる。取れたら、相手は終了している（`stop` が後片付けのあいだだけロックを持っていた場合など）ので、2 に進んで自分が起動する。上限まで待っても、一致もせずロックも取れなければ、使い回せないと報告して止まる。
4. URL を決める。`--page <行き先>` があれば、`control/locate`（自分が起動したサーバーなら、中核を組み立てて同じ規則）で解決する。`resolved` ならそのページ、そうでなければ `index.html` にする。
5. 標準出力の 1 行目に `{"url": …, "port": …, "reused": …, "page": <状態>}` を出す。`--no-open` がなければ、既定のブラウザで開く。

- 2 つの `serve` が同時に始まっても、ロックを取れるのは 1 つだけである。
- **終了**: 要求のない状態が続いたら終了する（既定 30 分。`--idle-timeout` で変えられる）。操作の口への要求も、要求に数える。使い回しを確かめた直後に終了することを避けるためである。

### 8.6 `stop` の流れ

1. 領分の根と状態のディレクトリを、何も作らずに確かめる（6）。根か状態のディレクトリがないか、目印のない空のディレクトリなら、動いていない。`server.lock` を作らずに開き、ほかが持っていなければ、動いていない。
2. 取れなければ、記録を読み、`control/status` でインスタンスの ID を確かめてから、`control/stop` を送る。起動の途中で記録がまだないときは、`serve` の 3 と同じに待つ。
3. ロックが外れる（プロセスが終わる）まで待つ（既定 10 秒）。外れたら、その instance の記録が残っていれば消す（Windows で、読んでいるほかのプロセスがいるとサーバー自身が消せないため）。外れなければ、止められなかったと報告し、記録を残す。

止めるのは、操作のトークンとインスタンスの ID が合う相手だけである。ポートやプロセスの番号が使い回されていても、別のプロセスは止めない。応答しないサーバーは、止められないと報告して利用者に任せる（要求がなければ、いずれ終了する）。

## 9. コマンドと、中核の子プロセスの入出力

- **`commands/browse.md`**: 引数は `[slug]` と `--stop`。Wiki のルートを、ほかのコマンドと同じ順で決める。`uv run --script "${CLAUDE_PLUGIN_ROOT}/skills/info-hive/scripts/wiki_browse.py" serve <WIKI_ROOT> [--page <slug>]` を裏で起動し、1 行目の URL を利用者に示す。`--stop` なら `stop` を実行する。検索語は第 2 段階で扱う。
- `/wiki:help`、`docs/commands.md`、`README.md`、`SKILL.md`、`CHANGELOG.md` を更新する。コマンドは 10 本から 11 本になるので、マーケットプレイスの説明の本数も直す。`eval/check_encoding.py` に新しいスクリプトを足す。
- **`wiki_browse.py core`**（ADR-0010 の「中核の呼び方」）: 標準入力から 1 行に 1 つの JSON の要求を読み、1 行に 1 つの JSON の応答を返す。入出力は UTF-8 を明示する。第 1 段階の要求は 2 つである。
  - `{"op": "manifest", "wiki": <パス>}`: ナビゲーション、能力、世代、診断、ページの一覧。
  - `{"op": "page", "wiki": <パス>, "id": <識別子>, "raw": <描き方>}`: そのページの HTML。
  - 応答に `protocol_version` と世代を入れる。応答にも、守ること 4 が当てはまる。同じプロセスの中では、入力の印が変わらず、写しに「読めなかった入力がある」こともないときだけ、写しを使い回す。読めなかった入力があれば、次の要求で読み直す。
  - 第 1 段階では、試験だけがこれを使う。アプリのアダプタを作るときに、必要な要求を足す（ADR-0016）。

## 11. 試験

守ることごとに並べる。`tests/wiki/test_browse.py`（標準ライブラリと PyYAML）と、`tests/wiki/browse/`（Playwright。PoC の `test.mjs` と `kinsoku.mjs` を移す）に置く。シンボリックリンク、ジャンクション、大文字と小文字の扱いに依る試験は、その OS でだけ流す。

**閲覧専用（守ること 1）**

- 静的の書き出し、サーバーでの閲覧、`stop` の前後で、Wiki のディレクトリのファイルの一覧と各ファイルのハッシュが変わらない（新しいファイルができないことも含む）。ブラウザの試験でも同じことを確かめる。
- 書き出し先が、Wiki の中、Wiki を含む場所、Wiki と同じ場所、Wiki の中を指すシンボリックリンクのとき、何も書かずに止まる。
- 大文字と小文字を区別しないファイルシステムで、Wiki の綴りを変えたパスの中を書き出し先にすると止まる。
- `C:/work/wiki` と `C:/work/view` のように、Wiki と書き出し先が同じ親の下に並ぶ配置で、書き出せる。
- Wiki のページが、書き出し先、作業用のディレクトリ、サーバーの状態のディレクトリの中のファイルを指すシンボリックリンクのとき、`build`、`serve`、`stop` が、ロックのファイルも作らずに止まり、そのファイルが残る。サーバーの起動のあとでそうなったときは、次の作り直しでサーバーが終了する。
- 作業用のディレクトリやサーバーの状態のディレクトリ、その中の子が、Wiki へのジャンクションのとき、何も書かずに止まる。`INFO_HIVE_DATA_DIR` が Wiki の中のときも止まる。
- 生成の記録や `server.json` の場所に、Wiki のページのハードリンクを置いても、ページの中身が変わらない。
- まだない書き出し先への最初の書き出しで、作業用のディレクトリに、目印がロックのファイルより先にできる。
- 目印のない空でないディレクトリ、サーバーの状態のディレクトリ、`<data_dir>/browse/` の中、ほかの書き出し先の中（`/exports/site/nested`）、ほかの書き出し先を含む場所を `--out` にすると止まる。
- 目印のない `tmp-*`、`old-*` を消さない。
- プラグインを Wiki の中に置き（`__pycache__` のない状態）、`build`、`serve`、`stop`、`core` を実際のプロセスとして動かしても、Wiki の中のファイルの一覧が変わらない。

**lint と同じ判定（守ること 2）**

- 試験用の Wiki と `eval/retrieval/ja/corpus/wiki/` で、`unresolved` の一覧が `wiki_lint.py` の `broken_links` と一致する。
- 写しの文字が、どの入力でも `read_text(encoding="utf-8-sig")` と同じになる（BOM、CR LF、CR だけの改行）。CR だけの改行のファイルで、frontmatter の `sources: ["[[missing]]"]` が本文のリンクにならず、メタ欄が読める。
- 描画が wikilink として描いたものが、ページごとに `wiki_pages.extract_wikilinks()` と一致する（表の中の `[[a|b]]`、コードの中の `[[...]]`、escape、文字参照を含む）。
- 同じスラッグのページへのパスのないリンクが `ambiguous` になり、パスつきのリンクは `resolved` になる。
- 識別子の衝突（NFC と NFD、`x.md` と `x.MD`、`a\b.md` と `a/b.md`。Linux）で、どちらも描かれず `id_collision` になる。衝突したページへのリンクは、当たるページが 1 つでも（`[[b]]`）`ambiguous` になり、描かれていないページへの href ができない。`x.MD` だけが読めないときは、`x.md` が描かれ、リンクが `resolved` になる。
- 全部の href（本文、被リンク、ナビゲーション、メタ欄、関係表）の行き先が、出力にある。
- Wiki の外を指すページ、索引、オントロジーを、lint と同じに読む。
- `sources:` の `paper`、`sources/paper`、`[[sources/paper]]` が、lint と同じに解決する。
- `sources: [true]`（`true.md` がある）と `sources: [null]` で、メタ欄、関係表の `sourced_from`、診断が食い違わず、lint の `unresolved_sources` と一致する。

**1 つの写し（守ること 3）と作り直し**

- 本文、frontmatter、索引、オントロジーを変えると、次の要求が新しい内容で答えられ、世代が変わる。
- 組み立ての途中に入力を変えると、次の要求で作り直される。
- 同時の要求で、組み立てが重ならず、どの応答も 1 つの世代の内容だけでできている。
- ページを取ったあとで入力を変え、`nav.js` を取ったあとで入力を元に戻してから `data/manifest.js` を取ると（Linux では `A.md` の追加と削除で、`a` の出力の名前が変わる）、画面に「Wiki が更新された」が出る。前の世代のナビゲーションからたどった、今はない名前への要求が、`index.html` へのリンクのある 404 になる。
- ページ、索引、オントロジーの読み取りを一時的に失敗させ、ファイルを変えずに戻すと、5 秒の後の要求で戻る。中身の誤ったオントロジーでは、作り直しを繰り返さない。
- 組み立てを失敗させる変更のあと、ページの先頭に「古い」の表示が出る。直すと消える。変更を取り消して印が元に戻った場合も、5 秒の後の要求で消える。
- 組み立てが長引いて待ちの上限を超えた要求（試験では上限を短くする）が、「古い」の表示つきで答えられる。最初の組み立てでは 503 になる。
- 印が変わったまま組み立てが失敗し続けるとき、5 秒のあいだは組み立てを繰り返さない。

**絶対パス（守ること 4）**

- 試験用の Wiki、ホーム、`data_dir`、Wiki の外に置く入力の実体（ページ、索引、オントロジー）を、それぞれ別の目印になる文字を含むディレクトリにして、静的版の全ファイル、サーバーの全応答（エラーの応答を含む）、`core` の応答、サーバーの記録に、どの文字もない。読めないページ、読めないオントロジー、Wiki の外を指す入力を含めて確かめる。
- 生成器が Wiki のルートを出力に入れるように細工すると、公開の前の検査が見つけて失敗し、前の世代が残る。Windows の例外の文字列、JSON の `\\`、URL の符号化の形を含める。
- 本文にホームのパスを書いたページ（そのまま、コードの中、`C\:/…` のように escape した形）があっても、書き出しが成功し、警告が出る。
- `raw:` の 4 つの描き方。`file:///C:/Books/private.pdf` と `~/x.pdf` が `absolute` になり、`basename` と `none` でパスが出ない。
- サーバーの記録に、閲覧と操作のトークンが出ない。

**外への通信（守ること 5）と交換できること（守ること 6）**: ブラウザの試験。同じ試験用の Wiki を、静的の書き出し（`file://`、`--raw text`）とサーバーで開く。1 件でも外れれば、終了コードを 1 にする。

- ナビゲーション、リンクの移動、被リンク、関係表、診断、`ambiguous` と `unresolved` の表示が、2 方式で同じになる（ADR-0016 の交換できることの確認）。
- 表示の時点で、外部への要求と CSP の違反が 0 件である。
- 本文の外部リンクをクリックしたときだけ外への移動が起き、その要求に `Referer` が付かない（移動は Playwright で横取りし、外には出さない）。
- JavaScript を切っても、本文、メタ欄、被リンク、関係表、診断が読め、`<noscript>` のリンクで移動できる。
- `<script>` を含む題名、メタ欄、別名、見出しが、文字として表示され、実行されない。
- 配置を指定した表が、指定のとおりに表示され、CSP の違反が起きない。どの出力にも `style` の属性がない。
- 日本語の組版（選択肢のレポートの合格の目安）: `eval/retrieval/ja/corpus/wiki/` の全ページが開け、日本語のファイル名と `[[slug#見出し]]` で移動できる。行頭に句読点や閉じ括弧が来ない。長い URL やコードが本文の幅からはみ出さない。幅を変えて確かめる。

**サーバーの安全（守ること 7）と起動、停止**

- 待ち受けのソケットのアドレスが 127.0.0.1 である。ループバックでないアドレス（その PC のほかのネットワークのアドレス）からは接続できない。
- 起動し直すと、閲覧のトークンと操作のトークンが、どちらも前と違う値になる。
- トークンの違い、Host の違い、GET と HEAD 以外、`..` とその符号化、`\`、NUL、正しくない UTF-8、中核の知らない名前を拒む。
- 2 つの `serve` を、状態のディレクトリがまだない状態から同時に始めると、サーバーは 1 つだけ起動し、もう一方は使い回す。起動の途中のサーバーに `stop` を送ると、記録を待ってから止める。`stop` が後片付けでロックを持っているあいだに始めた `serve` が、ロックを取り直して起動する。
- `--page` に、解決するリンク、曖昧なリンク、未解決のリンクを渡したときの URL と状態。
- 閲覧のトークンでは `control/stop` が通らない。インスタンスの ID が違う相手（止めたあとで同じポートに起動した別のサーバー）に、`stop` が停止を送らない。2 つの `stop` を同時に走らせても、誤った相手を止めない。応答しないサーバーを、止められないと報告する。
- 最初の組み立てが失敗している（`NameCollision` を起こす入力）、または組み立ての途中のサーバーに、`stop` と使い回しの確かめが働く。`control/locate` は `unavailable` を返す。
- 要求がなければ終了する。使い回しの確かめが、終了までの時間を延ばす。
- POSIX で、状態のディレクトリが 0700、記録が 0600 である。Windows で、`INFO_HIVE_DATA_DIR` を指定したときに警告が出る。

**途中を見せない（守ること 8）**

- 入れ替えの各手順のあとで止めたとき、次の書き出しで前の世代が戻る（作業用のディレクトリに `tmp-*` と `old-*` が目印つきで残っていても、入れ子として拒まない）。消せなかった `old-*` が残っていても、次の書き出しができる。空のディレクトリを書き出し先にできる。`old-*` が 3 つ残ったとき、`published_seq` のいちばん大きいものが戻り、ほかが消える。目印のない `old-*` は戻さない。`seq` が空のファイルのとき、目印から続きの値で始まる。
- 親（`/exports/site`）と子（`/exports/site/nested`）と、同じ子をもう 1 つ、どれもまだない状態から同時に始めても、1 つずつ走り、入れ子になる側が止まり、ほかの書き出しのファイルが消えない。
- 絶対パスの検査や `NameCollision` で失敗したとき、前の世代が残る。

**状態の区別（守ること 9）と中核の規則**

- オントロジーがない、読めない、関係が 0 件、関係がある、のそれぞれの表示。
- 関係表: 同じスラッグの `concepts/x.md` と `entities/x.md` で、関係を書いていないページに関係が出ない。両方に同じ関係を書くと、それぞれに出る。同じページの中で `status` と期間だけが違う 2 つの関係が、2 本とも出る。同じ `graph.node_id` のページで、入ってくる関係が出ず、どちらのページにも `duplicate_node_id` の診断が出る。`sources/left/paper.md` と `sources/right/paper.md` があるとき、`sources: ["paper"]` は診断（`ambiguous_source`）に出る。2 つのページは既定のノード ID（`source:paper`）を共有するので、`sources: ["sources/left/paper"]` の関係は出ていく側にだけ出て、どちらのページにも入ってくる関係としては出ない（両方に `duplicate_node_id` が出る）。別々の `graph.node_id` を持つ同じスラッグのページでは、パスつきの `sources:` の関係が、指したページだけに入ってくる関係として出る。
- 出力の名前: PoC の `names_check.py` の反例に、`COM¹`、`LPT²`、`CONIN$`、`COM0`、`.browse-generation/a.md` を足す。接尾辞の 8 桁が同じになる 2 つの長い名前（13 回目のレビューの例）で、桁が増えて重ならない名前になる。PoC の `review_checks.py` の場面（生成し直したときの残り、生成器のファイルとの衝突）。
- 見出し: `## **Definition**`、`## [[other|Definition]]`、`## ![Definition](diagram.png)` に `[[a#Definition]]` で移動できる。`## 例`、`## 例`、`## 例-1` で、`[[対象#例-1]]` が 3 つ目に移動する。`# nav` の見出しが画面の部品と重ならない（同じ ID の要素が 1 つしかない）。
- ナビゲーション: 任意の見出しの `index.md`、最初の見出しより前の項目、分割した `indexes/`、`[[indexes/concepts]]` の項目、`- [[missing]] — 関連：[[a]]`、索引にないページ、読めない索引。
- 外部リンク（`https:` に `rel="noopener noreferrer"` が付く。相対パスと `file:` がリンクにならない）。`[ [[missing]] ](https://example.invalid/)` で、外側がリンクにならず、`<a>` の入れ子ができない。
- `core` の 2 つの要求の入出力。読み取りを一時的に失敗させたあと、ファイルを変えずに戻すと、同じプロセスの次の要求でページが戻る。

**CI と速さ**

- 新しいワークフロー `wiki-browse.yml` で、`tests/wiki/test_browse.py` とブラウザの試験（Chromium）を、`windows-latest` と `ubuntu-latest` の両方で流す。5 つのブラウザ（Chromium、Firefox、WebKit、Edge、Chrome）での確認は、手で流す試験に残す。
- 起動の速さ: 1,000 ページの合成 Wiki で、`uv run --script wiki_browse.py serve` の実行から、Chromium で最初のページの描画が終わるまでを測り、5 秒以内であることを確かめる（選択肢のレポートの合格の目安）。uv の環境ができていない初回は別に記録する。

## 限界

- 写しは、Wiki 全体を同じ瞬間で切り取ったものではない（2）。
- 大きさと更新時刻を変えない編集は、サーバーが見逃す（8.3）。
- 確かめてから書くまでのあいだの、ジャンクションへの差し替えは防げない（6.5）。
- `INFO_HIVE_DATA_DIR` の違う 2 つのプロセスは、共通のロックを分け合わない。入れ子の書き出し先に同時に書く使い方は、想定しない。
- `INFO_HIVE_DATA_DIR` を、ほかの利用者が読める場所に向けると、その利用者が `server.json` のトークンを読み、同じ PC から閲覧と停止ができる。Windows ではアクセス権を設定し直さず、警告だけを出す（8.4）。wiki の MCP サーバーの記録（ADR-0012）と同じ扱いである。この変数は検証用で、共有の場所に向ける使い方は想定しない。警告だけにすることは、2026年11月11日に作者が決めた。
- Python と uv の実行環境（uv のキャッシュ、仮想環境）が Wiki の中にある配置は扱わない。browse が止めるのは、自分のプロセスのバイトコードの書き込みだけである（6）。
- サーバーが終了すると、開いていたタブのリンクは動かなくなる。もう一度 `/wiki:browse` を実行する（ポートとトークンは変わる）。
- 公開の前の検査は、本文にパスのあるページに生成器が同じパスを入れた場合を見逃す（5）。
- `index.md`、`log.md`、`SCHEMA.md`、`README.md` は、ページとして表示しない。これらへのリンクは、lint と同じく未解決になる。

## 範囲の外

- 検索（静的版の部分一致と、サーバーの MCP の `query`）、全体のグラフ、RAG、複数 Wiki の切り替え（優先順位の 3 位と 5 位）
- mermaid と svg の図の表示（ADR-0005）
- デスクトップアプリのアダプタと、アプリでの確認（ADR-0010 の決定の 6、ADR-0016）
- 変更の自動の反映（`live_reload`）
- lint とグラフの抽出が、同じ frontmatter の最上位の欄を違う値に読むこと（`sources: [true]`）。browse は lint の値にそろえる（2）が、`/wiki:graph` の出力とグラフの lint は、PyYAML の値のままである。グラフ層の別の課題とする
- `wiki_key()` が大文字と小文字を常に同一視する欠陥（ADR-0010 の作業の 5、別の課題）
- 静的版の古い世代と、消えた Wiki の分の掃除（未決だった事項の決定の 2 の残ること）
