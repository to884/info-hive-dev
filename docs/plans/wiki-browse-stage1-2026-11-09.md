# wiki の閲覧（browse）の第 1 段階とサーバーのアダプタ（2026年11月9日）

[ADR-0010](../adr/0010-wiki-browse-separates-core-from-delivery.md) の作る順序の 2〜4（承認のあとの作業の 3 と 4）を、`info-hive-wiki` で行う計画である。[優先順位の文書（6 版目）](../research/feature-priority-2026-11-06.md)の 2 位に当たる。前提の 1（ページの集合とリンクの規則、wiki 0.9.0）は済んだ。

最初の版は Sol の敵対的レビューで却下された（[design-review-1.md](../agent-runs/2026-11-09-wiki-browse-stage1-review/design-review-1.md)）。この版は、その指摘を受けて直したものである。指摘と対応の対照は最後にある。

## 目的

- 中核（Wiki を読んで、ページ、ナビゲーション、被リンク、関係表、診断を組み立て、Markdown を HTML に描く）を、Python の 1 か所に置く。
- 第 1 段階（ページの表示、ナビゲーション、メタ欄、被リンク、ページごとの関係表、未解決リンク、日本語の CSS）を、静的に描ける形で完成させる。
- 最初のアダプタとして、必要なときだけ起動するローカルのサーバー（構成 B、ADR-0002）を作り、`/wiki:browse` から開けるようにする。

検索（静的版の部分一致、サーバーの MCP の `query`）、全体のグラフ、RAG は範囲の外で、優先順位の 3 位と 5 位で行う。

## 決めること

### 1. ファイルの構成

`skills/info-hive/scripts/` に置く。

| ファイル | 中身 |
| --- | --- |
| `wiki_browse_core.py` | 中核。Wiki のルートを受け取り、読み取りの写し（4）から、ページの識別子、出力の名前、見出しの ID、リンクの状態、被リンク、関係表、診断、ナビゲーションを組み立て、ページの HTML を描く。`wiki_pages.py`、`wiki_lint.py`、同梱した markdown-it-py を使う |
| `wiki_browse.py` | 入口。`build`（静的に書き出す）、`serve`（サーバーを起動して開く。動いていれば使い回す）、`stop`（止める）、`core`（中核を子プロセスとして呼ぶための JSON の入出力）。PEP 723 の依存は `pyyaml==6.0.3`（関係表のため。グラフの抽出と同じ版）だけで、`uv run --script` で動かす |
| `browse_assets/` | 書き出す画面の部品（`app.js`、`style.css`）。PoC の `poc/browse/static/` を下敷きにし、検索欄を除く |

中核と描画を分けない（1 つのモジュールにする）。ADR-0010 の「表示の側は Markdown を解釈しない」は、アダプタ（サーバー、静的の書き出し、将来のアプリ）が Markdown を解釈しないという意味で、中核が HTML まで描くことは決定のとおりである。

### 2. 読み取りの写し（スナップショット）

中核は、組み立てのはじめに、入力を 1 度だけ読み、その写しだけから組み立てる。lint 用とグラフ用で別々にファイルを読むと、間で編集されたとき、本文と関係表が別の時点の内容になるからである。

- **入力**: `wiki_pages.iter_page_files()` のページ、`index.md`、`indexes/` の Markdown、`graph/ontology.yaml`。
- **Wiki の外を指すもの**: 実体の場所（`Path.resolve()`）が Wiki のルートの外にあるページ（シンボリックリンク、ジャンクション）は読まず、診断に `outside_wiki` として挙げる。
- **読めないもの**: 読めないページは描かず、診断に `read_error` として、識別子だけを挙げる。例外の文字列（絶対パスを含む）は出力に入れない。
- **NFC で同じになる別のファイル**: NFC と NFD だけが違う名前の 2 つのページ（Linux で置ける）は、どちらも描かず、診断に `normalization_collision` として挙げる。その識別子へのリンクは `ambiguous` にする（lint の `duplicate_slugs` の `normalization_collision` と同じ扱い）。
- **世代**: 入力のすべて（相対パスと、バイト列の SHA-256）のハッシュ。frontmatter、索引、オントロジーを変えても世代が変わる。
- **限界**: ファイルを 1 つずつ読むので、読んでいる途中にほかのファイルが編集されると、古いページと新しい索引が混ざることはある。Wiki 全体を同じ瞬間で切り取る写しではない。サーバーは次の要求で作り直すので、混ざった状態は長く残らない。

### 3. 中核の組み立て

- **識別子**: NFC の POSIX の相対パスから `.md`（大文字と小文字を問わない）を除いたもの（ADR-0010 のデータの契約）。
- **出力の名前**: `export_name()`。PoC の `gen.py` の規則（未決だった事項の決定の 3）を移し、予約名の判定を直す（レビューの重大 5）。Windows の予約名は、`CON`、`PRN`、`AUX`、`NUL`、`CONIN$`、`CONOUT$`、`COM0`〜`COM9`、`LPT0`〜`LPT9` と、上付きの数字の `COM¹`〜`COM³`、`LPT¹`〜`LPT³` とする。最初の `.` より前を、末尾の空白と `.` を除き、大文字と小文字を区別せずに比べる（Python 3.13 の `ntpath.isreserved()` と同じ範囲）。ほかの規則（Windows で使えない文字、末尾の空白と `.`、接尾辞の形の名前、`.html` で終わるディレクトリ、最上位の生成器の名前、UTF-8 で 200 バイトを超える要素）は PoC のとおりで、変えたら `~<その要素までの識別子の SHA-256 の先頭 8 桁>` を付ける。大文字と小文字だけが違う出力は、衝突した全員に接尾辞を足す。最後に重なりを確かめ、重なれば生成を止める（`NameCollision`）。
- **見出し**: 同梱した markdown-it の `heading_open` から取る（ATX と Setext）。ID は NFC にして小文字にし、空白を `-` にし、ASCII の記号を除く。重なれば連番を付ける。
- **リンク**: 本文の wikilink は、描くときと同じ markdown-it のトークン（`inline` の中の `text`）から拾う（`wiki_pages.extract_wikilinks()` と同じ規則）。状態は `resolved`、`ambiguous`（パスのないリンクで、同じスラッグのページが 2 つ以上。lint の `duplicate_slugs` と同じ判定。どちらにも移動しない）、`unresolved`（クリックしてもファイルを作らない）。`resolved` で `#見出し` の見出しがなければ `missing_heading` を足す。
- **被リンク**: 解決したリンクを逆に引く。自分へのリンクは数えない。
- **関係表**（レビューの重大 1）:
  - オントロジーがあるときだけ作る。グラフの抽出の `parse_frontmatter`、`build_nodes`、`build_edges` を、写しから作ったページに当てはめる。
  - **出ていく関係**は、エッジが持つ `page`（そのエッジを書いたページの相対パス）で振り分ける。主語（`subject`）では振り分けない。
  - **入ってくる関係**は、目的語のノードが 1 つのページだけに対応するときに出す。
  - **同じスラッグのページ**（`duplicate_slugs` に挙がるページ）では、関係表を出ていく側も入ってくる側も出さず、診断に `ambiguous_relations` を挙げる。グラフの抽出が、同じスラッグのページのノードを取り違え（`build_nodes` がスラッグからノードを引く）、同じ内容の関係をページを区別せずに 1 本にまとめる（`edge_id` に `page` が入らない）ので、正しい表を作れないからである（2 回目のレビューの重大 2）。グラフの抽出の修正は別の課題で、直ったら関係表も出す。
  - 表に出すのは、型付きの関係と `sourced_from`（`sources:` からの関係）である。`mentions`（本文の wikilink）は被リンクと重なるので出さない。`summarizes_raw` は `raw:` の欄と重なるので出さない。
  - 状態を 3 つに分ける（レビューの軽微な指摘）: オントロジーがない（`relations: "none"`。関係表を出さない）、読めない（`relations: "error"`。関係表の場所に「オントロジーを読めない」と出し、診断に挙げる）、作れた（`relations: "ok"`。関係が 0 件なら「関係はない」と出す）。
- **ナビゲーション**（レビューの軽微な指摘）: `index.md` と `indexes/` を、ページとして描かずに読む。`collect_index_entries` は種類の見出ししか読まないので使わない。規則は次のとおりである。
  - 同梱した markdown-it で解析し、見出しの入れ子（`#` から `######`）をそのままグループの木にする。リストの項目の最初の wikilink（解決したもの）を、その直前の見出しのグループに入れる。入れ子のリストの項目も、同じグループに入れる（リストの入れ子は木にしない）。
  - 同じページが複数の場所に載っていれば、それぞれの場所に出す。
  - `indexes/` があれば、ファイルごとに最上位のグループを 1 つ作り（名前は frontmatter の `title`、最初の見出し、ファイル名の順）、その中を上と同じ規則で木にする。`index.md` の項目が `indexes/` のファイルを指すとき（`[[indexes/concepts]]`）は、その項目を、そのファイルのグループへのリンクにする。
  - 索引に載っていないページは、種類（`type`）ごとの「索引にないページ」のグループに入れる。
  - `nav.js` に書き出し、各ページは共有の `nav.js` を読み込む。
- **メタ欄**: `type`、`tags`、`summary`（あれば）、`created`、`updated`、`sources`（解決したものはリンク）、`raw`（4 で扱う）。
- **診断**: `unresolved`、`ambiguous`、`missing_heading` のリンク、`read_error`、`outside_wiki`、`ambiguous_relations`、名前を変えたページ。ページの末尾と `data/diagnostics.js` に出す。

### 4. `raw:` の扱い（未決だった事項の決定の 7）

- 中核は `raw` を `{kind, value, sha256}` で持つ。`kind` は `absolute`（絶対パス）、`relative`、`url` のどれか。
- 描き方を 4 つに分ける。`text`（値を文字として出し、リンクにしない）、`link`（`file:///` のリンク）、`basename`（ファイル名と `raw_sha256` の先頭 12 桁）、`none`（出さない）。
- `link` にするのは `kind` が `absolute` のときだけである。`relative`（基準が lint でも 3 通りあり、一意に決まらない）と `url`（開くと外への通信になる）は、どの描き方でも文字として出す（`none` なら出さない）。
- サーバーは `text`。静的版は、既定の書き出し先では `link`、`--out` では既定で `basename`。`--raw` で選べる。
- 交換できることの試験（10）は、同じ描き方（`text`）で比べる。

### 5. 絶対パスを出力に入れない（レビューの重大 4）

- 出力（HTML、`nav.js`、`data/*.js`）に入れるのは、識別子、相対パス、題名、本文、メタ欄の値だけである。例外の文字列、Wiki のルート、ホームのパスは入れない。`raw:` の絶対パスは、4 の描き方が `text` か `link` のときだけ入る（利用者が選んだもの）。
- 生成の記録（Wiki のルートの絶対パスを含む）は、出力の外（`<出力先>.build-report.json`）に書く。
- 公開の前に、作業中のディレクトリの全ファイルを調べる。探す文字列は、Wiki のルートとホームのディレクトリの絶対パスを、`/` 区切り、`\` 区切り、JSON の文字列の中の `\\` 区切り、HTML のエスケープ、URL の符号化にしたものである。`raw:` の描き方が `text` か `link` のときは、その値だけを許す。見つかれば、作業中のディレクトリを消し、前の世代を残したまま、失敗で終わる（終了コード 1）。

### 6. 画面の契約（ADR-0010 のとおり）

- ページ間のリンクは相対の href だけにする。名前の要素ごとにパーセントエンコードする。
- スクリプトは classic な `<script src>` だけ。`fetch`、ES モジュール、Web Worker を使わない。データは `nav.js` と `data/*.js`（`window.WIKI_NAV` など）にし、`</`、U+2028、U+2029 をエスケープする。
- 各ページの HTML に、本文、メタ欄、被リンク、関係表、診断を事前に描く。JavaScript を切っても読める。`<noscript>` で `index.html` へのリンクを残す。
- CSP を `<meta>` に付ける（`default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; base-uri 'none'; form-action 'none'`）。外部への通信をしない。
- 生の HTML は出さない（markdown-it の `html: False`）。本文の画像は、第 1 段階では代替テキストだけを出す（ADR-0005 のとおり、svg の表示は第 1 段階に含めない）。
- 出力に `protocol_version`（1）、世代、生成日時、能力（`search: "none"`、`relations`、`rag: false`、`multi_wiki: false`、`live_reload`）を持たせる。各ページの `<html>` に `data-generation` を書く。`app.js` は、知らない `protocol_version` なら表示を止め、`nav.js` の世代がページの世代と違えば「Wiki が更新された。再読み込みする」と出す。

### 7. 静的の書き出し（`wiki_browse.py build`）

- **書き出し先**: 既定は `<data_dir>/browse/<wiki_key>/`（未決だった事項の決定の 2）。`data_dir()` と `wiki_key()` は `wiki_mcp_common` のものを使う。`--out <dir>` で場所を選べる。
- **作業用のディレクトリ**（2 回目のレビューの致命 1）: 書き出しに使う一時のディレクトリ、退避したディレクトリ、ロック、生成の記録は、すべて書き出し先の隣の、browse が持つ作業用のディレクトリ `<出力先>.browse-work/` の中に置く。作業用のディレクトリには目印（`.browse-work`）を置き、目印のない既存のディレクトリは使わない（止まる）。消すのは、作業用のディレクトリの中の、目印（`.browse-generation`）を持つ `tmp-*` と `old-*` だけである。名前の形だけで、作業用のディレクトリの外のものを消すことはしない。
- **書き出し先の確かめ**（レビューの重大 3）: 書き出し先、作業用のディレクトリ、Wiki のルートを `Path.resolve()`（シンボリックリンクとジャンクションを解いたもの）で比べ、どれかが Wiki と重なる（中にある、含む、同じ場所）ときは、書かずに止まる。消す直前にも、消すものの実体が作業用のディレクトリの中にあり、Wiki と重ならないことを確かめる。書き出し先は、空のディレクトリか、目印（`.browse-output`）のあるディレクトリでなければ書かない。
- **排他**（2 回目のレビューの重大 3）: 作業用のディレクトリの `build.lock` を、OS のファイルのロック（Windows は `msvcrt.locking`、ほかは `fcntl.flock`。`wiki_graph_common.extract_lock` と同じ仕組み）で取る。プロセスが止まれば OS が外すので、古いロックを片付ける処理を持たない。ロックのファイルは消さない。取れなければ、ほかの `build` が動いているとして止まる。
- **世代の入れ替え**（レビューの重大 6）:
  1. ロックを取ったあとで、作業用のディレクトリに残った `tmp-*` を消す。出力先がなく `old-*` だけがあるとき（前の入れ替えの途中で止まったとき）は、その `old-*` を出力先に戻してから進める。
  2. `tmp-<pid>` に全部を書き、5 の検査をする。
  3. 出力先があれば `old-<pid>`（作業用のディレクトリの中）に名前を変え、`tmp-<pid>` を出力先に名前を変える。
  4. 2 つ目の名前の変更に失敗したら（Windows で、ほかのプロセスが掴んでいるときなど）、`old-<pid>` を出力先に戻し、失敗で終わる。
  5. 成功したら `old-<pid>` を消す。消せなければ残し、次の書き出しの 1 で消す。
- 既定の書き出し先（`<data_dir>/browse/<wiki_key>/`）にも、同じ規則を当てはめる。`data_dir` は環境変数 `INFO_HIVE_DATA_DIR` で変えられるので、Wiki と重なれば止まる（2 回目のレビューの重大 5）。
- 出力の先頭のページは `index.html`（ナビゲーションの全体）。

### 8. サーバー（`wiki_browse.py serve`、構成 B）

- 127.0.0.1 だけで待ち受け、ポートは OS に選ばせる。起動ごとのトークンを URL のパスの先頭に置く（`/<token>/w/<wiki_id>/…`）。`wiki_id` は `wiki_key()`。
- Host ヘッダーが `127.0.0.1:<port>` でなければ 421、トークンが違えば 404 を返す。GET と HEAD だけを受け付け、ほかは 405。パスはパーセントデコードしたあとで `/` で分け、`..`、空の要素、`\`、NUL を含めば 404 にする。返すのは、中核が知っている出力の名前（ページ、`index.html`、`nav.js`、`data/*.js`、画面の部品）だけで、ファイルシステムは見ない。
- **開いたときに描く**（ADR-0002 の既定）。起動時に中核を組み立て、ページは要求されたときに、その時点の中核から描く。描く関数は静的の書き出しと同じものを使う。
- **作り直し**（レビューの重大 2 と 6）: 要求のたびに、入力の印（`.md` と `graph/ontology.yaml` のパス、大きさ、更新時刻）を比べる。変わっていれば、新しい中核を別に組み立て、組み立て終えてから入れ替える。組み立てのあいだの要求には、前の中核で答える（途中の状態を見せない）。組み立てに失敗したら、前の中核を使い続け、`data/diagnostics.js` に失敗を載せる。1 つの要求は、1 つの中核の写しだけを使う。大きさと更新時刻を変えずに中身だけを変えた編集は見逃す（MCP の索引の変更の印と同じ限界）。
- **終了**: 操作がない状態が一定の時間（既定 30 分）続いたら終了する。`--idle-timeout` で変えられる。
- **状態の置き場所**（2 回目のレビューの重大 5）: サーバーの状態（ロックと記録）は `<data_dir>/browse/<wiki_key>.server/` に置く。`data_dir` が Wiki と重なる（`INFO_HIVE_DATA_DIR` を Wiki の中に向けたときなど）ときは、何も書かずに止まり、別の場所を指すよう案内する。閲覧の操作で、Wiki の中にファイルを作らない。
- **1 つの Wiki に 1 つのサーバー**（2 回目のレビューの重大 4）: サーバーは、生きているあいだずっと、状態のディレクトリの `server.lock` を OS のファイルのロックで持つ。ロックのファイルは消さない。
  - `serve` は、まずロックを取ろうとする。取れたら、ほかのサーバーは動いていないので、ロックを持ったまま起動し、記録（`server.json`。PID、ポート、トークン、開始の時刻。作者だけが読める権限）を書く。取れなければ、動いているサーバーがあるので、記録を読み（書き終わるまで少し待つ）、その URL に要求して応答すれば使い回す。応答しなければ、使い回せないと報告して止まる（新しくは起動しない）。2 つの `serve` が同時に始まっても、ロックを取れるのは 1 つだけである。
  - `stop` は、ロックが取れるか（サーバーが動いていないか）を先に見る。取れなければ、記録の PID に終わるよう求め（`os.kill`）、ロックが取れるようになる（そのプロセスが終わる）まで待つ。一定の時間（既定 10 秒）で取れなければ、止められなかったと報告し、記録を消さない。ロックが取れたら記録を消す。PID が別のプロセスに使い回されていても、ロックを持っていなければ終わるよう求めない（ロックが取れる時点で、サーバーは動いていない）。
- 起動したら、1 行目に `{"url": …, "port": …, "reused": …}` を JSON で出し、既定のブラウザで開く（`--no-open` で開かない）。Claude Code のデスクトップアプリでは、エージェントがブラウザペインで開ける。
- 応答に CSP、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`、`Referrer-Policy: no-referrer` を付ける。エラーの応答には、パスや例外の文字列を入れない。

### 9. `/wiki:browse` のコマンドと中核の子プロセスの入出力

- `commands/browse.md` を足す。引数は `[slug]` と `--stop`。Wiki のルートを、ほかのコマンドと同じ順で決め、`uv run --script "${CLAUDE_PLUGIN_ROOT}/skills/info-hive/scripts/wiki_browse.py" serve <WIKI_ROOT> [--page <slug>]` を裏で起動し、1 行目の URL を利用者に示して開く。`--stop` なら `stop` を実行する。検索語は第 2 段階で扱う。
- `/wiki:help`、`docs/commands.md`、`README.md`、`SKILL.md`、`CHANGELOG.md` を更新する。コマンドは 10 本から 11 本になるので、マーケットプレイスの説明の本数も直す（`info-hive-marketplace`）。`eval/check_encoding.py` に新しいスクリプトを足す。
- **中核の子プロセスの入出力**（`wiki_browse.py core`）: Python 以外のアプリから呼べるように、標準入力から 1 行に 1 つの JSON の要求を読み、1 行に 1 つの JSON の応答を返す。第 1 段階の要求は、`{"op": "manifest", "wiki": <path>}`（ナビゲーション、能力、世代、診断、ページの一覧）と、`{"op": "page", "wiki": <path>, "id": <識別子>, "raw": <描き方>}`（そのページの HTML）の 2 つである。応答には `protocol_version` と世代を入れ、5 の規則（絶対パスを入れない）を当てはめる。

### 10. 版

wiki 0.10.0（マイナー）。新しいコマンドとスクリプトを足すが、既存の使い方を壊さない。0.9.1（ひな形のパスの修正、別のセッション）とは、`plugin.json` と `CHANGELOG.md` だけが重なる。あとからマージする側が取り込み直す。

### 11. 試験

- **開発リポジトリの `tests/wiki/test_browse.py`**（標準ライブラリと PyYAML）:
  - `export_name` の規則（PoC の `names_check.py` の反例に、`COM¹`、`LPT²`、`CONIN$`、`COM0` を足す）
  - PoC の `review_checks.py` の 4 つの場面（生成し直したときの残り、生成器のファイルとの衝突、見出しの ID の重なり、コードの中の `[[...]]`）
  - リンクの状態と、未解決リンクの一覧が `wiki_lint.py` の `broken_links` と一致すること
  - 被リンク、関係表（オントロジーがない、読めない、ある。同じスラッグのページで関係が別のページに出ないこと）、ナビゲーション（任意の見出しの `index.md`、分割した `indexes/`、索引にないページ）
  - `raw:` の 4 つの描き方と、5 の検査（Windows の例外の文字列、JSON の `\\`、URL の符号化を含む反例で、漏れを見つけて失敗し、前の世代が残ること）
  - 書き出し先の確かめ（Wiki の中、Wiki を含む場所、同じ場所、シンボリックリンク）、排他、世代の入れ替えの途中で止まったときの復旧
  - Wiki の外を指すページを読まないこと
  - 閲覧の前後で、Wiki のディレクトリの**ファイルの一覧と各ファイルのハッシュ**が変わらないこと（新しいファイルができないことも含む）
  - サーバー: トークン、Host、GET 以外、`..` とその符号化、`\`、存在しないパス、要求ごとの作り直し（本文、索引、オントロジーの変更）、作り直しの途中の要求、操作がないときの終了、使い回しと停止。エラーの応答に絶対パスがないこと
  - 中核の子プロセスの JSON の入出力
- **交換できることの確認**（ADR-0010 の合格の条件。2 回目のレビューの重大 6）: ADR-0010 は、3 つの方式（サーバー、アプリ、静的 HTML）で、リンクの移動、被リンク、診断の結果が一致することを、実際に動かして確かめるとしている。第 1 段階で作るのは、サーバーと静的 HTML の 2 つである。アプリは、ADR-0010 の決定の 6 で「今は決めない」とした。そこで、第 1 段階の合格の条件は、**作った 2 つの方式**を実際のブラウザで動かして一致を確かめることとし、アプリでの確認は、アプリを作るときの合格の条件に回す。中核の子プロセスの出力の比較は、交換できることの証明には使わない（ADR-0010 の L83 のとおり、回帰の検査にだけ使う）。**この読み方は、作者に確かめてもらう**（PR に書く）。
- **ブラウザでの確認**: PoC の `test.mjs`（Playwright）を `tests/wiki/browse/` に移す。同じ試験用の Wiki を、静的の書き出し（`file://`）とサーバーで開き、ナビゲーションの読み込み、リンクの移動、被リンク、診断、`ambiguous` と未解決のリンクの表示が同じになることを確かめる。閲覧の前後で Wiki のファイルの一覧とハッシュが変わらないこと、外部への要求と CSP の違反が 0 件であることも確かめ、1 件でもあれば失敗にし、終了コードを 1 にする（レビューの重大 7）。
- **CI**（2 回目のレビューの軽微な指摘）: `tests/wiki/test_browse.py` と、ブラウザでの確認（Chromium だけ）を、新しいワークフロー `wiki-browse.yml` で、`windows-latest` と `ubuntu-latest` の両方で流す（選択肢のレポートの合格の目安の「OS」）。5 つのブラウザ（Chromium、Firefox、WebKit、Edge、Chrome）での確認は、手で流す試験に残す。
- **起動の速さ**: 1,000 ページの合成 Wiki で、`uv run --script wiki_browse.py serve` の実行から、ブラウザ（Playwright の Chromium）で最初のページの描画が終わるまでを測り、5 秒以内であることを確かめる（選択肢のレポートの合格の目安）。uv の環境ができていない初回は別に記録する。
