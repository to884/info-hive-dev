# browse の木で、ページを最初のタグでまとめる（2026年11月16日）

`/wiki:browse` のナビゲーションの木で、索引の見出し（「コンセプト」「ソース」など）の直下に並んでいたページを、ページの最初のタグの値ごとのグループにまとめる。木は「コンセプト › 取り込み › ページ」の形になる。

## 1. 守ること

探しやすさの設計の 1 節と、Fluent 2 の設計の 1 節は、そのまま守る。この設計で特に関わるものを挙げる。

| | 内容 |
| --- | --- |
| 同じ写しから同じ木 | 索引のページ、`nav.js`、`data/search.js` は、同じ `Core` の同じ木から作る。サーバーと静的版は同じ関数で描く |
| 入力の中身から作る | タグのグループは、ページの frontmatter の `tags` だけから作る。生成器は機械の情報を足さない |
| ID の契約 | グループの ID は `_g` と英小文字か数字だけからなり、木の中で重ならない。利用者の文字（タグの値）を ID に入れない（探しやすさの設計の 5 回目のレビューの重大 2） |
| 2 つ目の段は ID を作らない | N2〜N8 は、これまでどおり新しい ID を作らない。ID を作るのは、この設計で足す 3 つ目の段（N9）だけである |
| 画面の契約 | この設計は `app.js` と `style.css` を変えない。木のデータの形（2.3 の `WIKI_NAV`）も変えない（同じ版で、[左のペインの木の設計](wiki-browse-tree-2026-11-16.md)が `app.js` と `style.css` の木を Fluent 2 の Tree に描き直す。木のデータは同じものを読む） |

## 2. 木を組む規則 N9

### 2.1 段の位置

木は、これまでの 2 つの段（N1、N2〜N7）のあとに、3 つ目の段（N9）を当てて組む。件数（N8）は、N9 のあとに数える。N8 の定義は変えない。

```text
N1（1 つ目の段）→ N2〜N7（2 つ目の段）→ N9（3 つ目の段）→ N8（件数）→ 組み終えた木の性質の確かめ
```

N8 を N9 のあとに置くのは、N9 で作るタグのグループにも件数が要るからである。N9 は親のグループの、ページの集合を変えないので、親のグループの件数は、N9 を当てる前と同じになる（2.4）。

### 2.2 規則

| | 規則 |
| --- | --- |
| N9-1 対象 | 2 つ目の段のあとの木で、ページの項目（`state` が `resolved` の項目）を 1 つ以上、自分の項目として持つグループのすべてに当てる。グループの名前や出どころでは選ばない。N4 の「索引」、`index.md` の見出しのグループ、`indexes/` のファイルのグループ、その中の見出しのグループ、N7 の「索引にないページ」の種類ごとの子のグループの、どれにも同じに当てる。ページの項目を持たないグループ（子のグループとグループへの項目だけを持つもの）は変えない |
| N9-2 タグの値 | ページの最初のタグは、`page_tags()` の最初の値である。`page_tags()` は、frontmatter の `tags` を `ref_values()` で読み（文字 1 つも配列も読み、前後の空白を落とし、空の値を除く）、NFC にそろえる。索引の一覧の行の `span.tag` と同じ値である。値がなければ、そのページはタグを持たない |
| N9-3 まとめ方 | 対象のグループの、ページの項目を、項目の並びのまま、最初のタグの値ごとに子のグループ（タグのグループ）に移す。タグの値は、NFC にそろえた文字が同じものを同じとみなす。大文字と小文字は区別する。タグを持たないページの項目は、「タグなし」のグループに移す。「タグなし」のグループと、値が「タグなし」の文字のタグのグループは、別のグループである（ID で見分ける） |
| N9-4 いつも挟む | 対象のグループのページがどれもタグを持たないときも、「タグなし」のグループを 1 つ作って移す（作者の決定） |
| N9-5 残す項目 | ページの項目でないもの（グループへの項目、未解決と曖昧の項目）は、タグを持たないので、元のグループの項目に、元の並びのまま残す |
| N9-6 並び | 元のグループの子は、タグのグループを先に、元の子のグループ（見出しのグループ）を後に並べる。タグのグループどうしは、元のグループの項目の並びで、そのタグを最初のタグに持つページの項目が初めて現れた順に並べ、「タグなし」はいつも最後に置く。タグのグループの中の項目は、元の項目の並びのままにする |
| N9-7 名前と要約 | タグのグループの名前は、タグの値（NFC）である。「タグなし」のグループの名前は「タグなし」である。要約は空の文字にする |
| N9-8 繰り返さない | N9 は、2 つ目の段のあとの木のグループにだけ、1 度だけ当てる。N9 で作ったタグのグループには当てない（タグのグループは子を持たず、ページの項目だけを持つ） |

画面では、項目が子のグループより前に描かれる（`app.js` の `treeGroup()`）。そのため、未解決と曖昧の項目と、グループへの項目は、タグのグループの上に出る。

### 2.3 グループの ID

| グループ | ID |
| --- | --- |
| タグのグループ（「タグなし」を含む） | `_gt` と、1 から始まる通し番号 |

- 番号は、N9 を当てる木を深さ優先でたどり（親のグループ、その子のグループの順）、タグのグループを作った順に付ける。
- 1 つ目の段の ID は、`_g` と数字だけのもの（見出しのグループと「索引にないページ」）と、`_gf` と数字のもの（索引のファイルのグループ）である。`_gt` で始まる ID は、そのどちらとも作りの上で重ならない。
- タグの値を ID に入れない。タグの値には空白も、ID の文字の外の文字も入りうる。`data-groups` を空白で区切って読み戻せることと、`#group=<ID>` の形（`_g` と英小文字か数字だけ）を保つためである。
- ほかの ID と同じく、索引やタグを書き換えると番号は変わる。`#group=_gt…` を含む URL を保存しておくと、書き換えたあとは別のグループを指すことがある（探しやすさの設計の 2.2 と同じ限界）。

### 2.4 組み終えた木の性質

探しやすさの設計の 2.1 の末尾の 5 つの性質に、次の 3 つを足す。実装は、`nav.js` を書く前に確かめ、成り立たなければ組み立てを失敗にする（`NavInvariantError`）。

- N9 の前とあとで、木に載ったページの集合が同じである。
- N9 の前に、あるグループ G がページ P の項目を持っていたなら、N9 のあとは、G の子のタグのグループのうちちょうど 1 つが P の項目を持つ。そのタグのグループの名前は、P の最初のタグ（なければ「タグなし」）である。G 自身はページの項目を持たない。
- タグのグループは、子のグループを持たず、ページの項目だけを持つ。

1 つ目の性質から、親のグループの件数（N8）は、N9 を当てる前の件数と同じになる。2 つ目の性質から、ページの祖先のグループ（`data-groups`）は、N9 の前の祖先のグループに、タグのグループを 1 つずつ足したものになる。

## 3. 参照の実装

`tests/wiki/browse_nav/nav_model.py` に、N9 を中核と別に書く。中核の N9 を呼ぶと、試験が自分自身と比べることになるので、2 つ目の段と同じく、参照の実装が自分で持つ。

- 1 つ目の段は、これまでどおり書き換える前の中核（`core_before.py` の `StageOneCore`）を呼ぶ。
- 2 つ目の段（N2〜N7）と N8 は、これまでの参照の実装を使い、N8 の前に参照の実装の N9 を当てる。
- ページの最初のタグは、参照の実装がページの frontmatter から読む。読み方は `wiki_pages.ref_values()` と NFC を使う。`ref_values()` は frontmatter の読み方の契約で、N9 の規則ではないので、共有してよい。
- `CASES` のページの作り方（`page()`）に、`tags` を書けるようにする。これまでの例は、どのページもタグを持たないので、木の形は「グループ › タグなし › ページ」に変わる。その出力を、探しやすさの設計の 2.1 の表と比べ直す。2.5 の例を `CASES` に足す。

## 4. 振る舞いが変わる点

| 変わる点 | 今 | 直したあと |
| --- | --- | --- |
| 木の段 | 索引の見出しのグループの直下にページ | 見出しのグループの下にタグのグループ、その下にページ。タグのないページは「タグなし」 |
| 記事のページのサイドバー | 今のページを含む見出しのグループを開く | 今のページを含むタグのグループと、その祖先を開く（`app.js` の規則のまま） |
| 索引のページの左の木 | 見出しのグループの名前と件数 | タグのグループの行が増える。押すと、そのタグのグループに絞る（`#group=_gt…`） |
| 索引の順（`data-order`、一覧の既定の並び） | 索引の行の順 | 同じ見出しの中では、タグのグループの順（2.2 の N9-6）、その中で索引の行の順。木を深さ優先でたどる規則（探しやすさの 4.1）は変えない |
| グループの階層（`fx-path`、`data/search.js` の `group_path`） | 「コンセプト」 | 「コンセプト › 取り込み」。いちばん下にタグのグループの名前が付く |
| `data-groups` | ページを持つグループと祖先の ID | タグのグループの ID が 1 つずつ増える |
| グループの件数 | — | 見出しのグループの件数は変わらない（2.4）。タグのグループに件数が付く |
| ページに決まらない索引の行（4.4） | — | 変わらない。未解決と曖昧の項目は元のグループに残る |
| 要約 | — | 変わらない。索引の行の要約は項目が持ったまま移る |
| `nav.js` | `protocol_version: 2` | 2 のまま。データの形と、項目、グループ、件数の意味は変わらず、`app.js` はタグのグループを、見出しのグループと同じに描く。古い `app.js` が新しい `nav.js` を読んでも、同じに描ける |

## 6. 版

利用者に見える変更なので、マイナー版を上げる。番号はマージの前に `origin/main` とタグを見て決める。2026年11月16日の時点で main は 0.21.1 で、0.22.0 は下書きの [to884/info-hive-wiki#71](https://github.com/to884/info-hive-wiki/pull/71) が名乗っている。

## 7. 限界

- **最初のタグだけで決める。** 2 つ目より後のタグは木に使わない。タグの並びに意味を持たせていない wiki では、まとまりが書き手の意図とずれることがある。タグで絞るには、これまでどおり索引のページのタグの選択を使う。
- **タグの値は文字のまま比べる。** NFC のほかは正規化しないので、`windows` と `Windows`、`取り込み` と `取込` は別のグループになる。
- **「タグなし」という値のタグは、「タグなし」のグループと同じ名前で並ぶ。** ID は別で、別のグループとして数える。画面の名前では見分けられない。
- **木が 1 段深くなる。** 字下げは 4 段目で止まる（Fluent 2 の設計の 4 節）。`indexes/` の見出しが深い wiki では、タグのグループが字下げの止まった段に入る。
- **タグのグループの ID は安定しない。** 索引かタグを書き換えると、`#group=_gt…` の行き先が変わることがある。

## 範囲の外

- 2 つ目より後のタグや、タグの組み合わせで木を作ること
- タグの段を挟むかどうかを、利用者が画面や引数で切り替えること
- タグの値の別名や表記ゆれをまとめること
