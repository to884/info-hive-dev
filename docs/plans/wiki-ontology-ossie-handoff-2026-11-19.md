# Apache Ossie の採用検討へ引き継ぐオントロジーの要件と設計課題

2026-11-19。対象プロジェクト: `C:/Works/info-hive-dev`。

info-hive-wikiで、wikiの内容に合うオントロジーを提案・適用し、記事の蓄積に応じて既存の定義と記録を整理・移行する機能を検討している。別セッションで検討中のApache Ossieを、この要件と未解決事項に照らして評価してほしい。
このセッションではApache Ossie自体の機能評価はしていない。名称はユーザーの指定どおりに記載しており、正式な製品名・リポジトリURL・対象バージョンは採用検討側で確認する。

## ユーザーの指示

> オントロジーは記事単位ではなく、「顧客」、「製品A」くらいの粒度にしたい

> ユーザーの指示により既存のオントロジーを見直し整理する機能がほしい。記事を追加し続けると、過去に構築したオントロジーとは概念が乖離する可能性を憂慮している

その前提として、プロジェクトスコープとユーザースコープそれぞれのwikiに合ったオントロジーを提案・適用する機能と、大まかな利用体験を検討してきた。

## 維持する要求と設計方針

- **実体を知識の単位にする。** A社・製品Aなどを識別し、記事は主張の根拠として扱う。1記事から複数実体、複数記事から同じ実体への対応が必要である。
- **wikiごとに定義と識別を持つ。** プロジェクトとユーザーのwikiは個別に扱い、別wikiの同名対象を自動統合しない。
- **ユーザーの指示で再検討する。** 現在の定義と新旧の記事を比較し、追加だけでなく、改名・統合・分割・廃止・再分類を提案する。
- **定義と既存記録を一緒に移行する。** 実体の同一性、関係、根拠、既知の参照、判断履歴を保つ。型の統合と実体そのものの統合は区別する。
- **確定できないものを保留する。** 同名だけでは統合せず、根拠から移行先を決められない記録は旧定義とともに保持できるようにする。
- **採用後の取り込みにも同じ規則を使う。** 提案・適用・通常のingestで、語彙と実体の識別規則を共用する。
- **原因を区別する。** 定義の不適合、抽出誤り、記録不足、対象の取り違え、現実の時期・版による変化を混同しない。定義を変えない訂正・取り下げも扱う。
- **根拠を伴う提案と試行を見せる。** 用途と具体的な問いに照らして判断し、「最適」を自動で保証する機能にはしない。

通常の取り込みでオントロジーを毎回自動再編する機能や、定期実行は必須ではない。利用中のホストのLLMを使い、追加のAPIキーを必須にしない方針である。外部グラフDBや専用UIも必須にはしていない。

## 現行実装と検討中の機能を区別する

調査時点のinfo-hive-wikiはv0.35.1である。

現行のextractは、基本的に1ページから1ノードを作り、関係の主語もそのページのノードになる。対象ごとのentityページを用意すれば、実体の粒度を表現できる。
現行のingestにも、LLMが既存ページを調べ、必要なentityページを作成・更新する手順がある。ソースの`entities:`と実体ページの`sources:`で、多対多の対応を記述できる。
extract自体は記述済みデータの機械的な変換であり、本文から実体を発見したり、同一性を判断したりする処理ではない。

既存の正本はMarkdownと`graph/ontology.yaml`で、生成物にはSQLite・JSONL・GraphMLがある。
明示的な`graph.node_type`が優先され、なければ`type`/`kind`と`maps_from`から型を導出する。明示的な`graph.node_id`がなければ、既定IDは型とスラッグに依存する。
日本語のkindの別名はプラグイン共通で正規化されるため、wiki固有の意味の対応と混同しない設計が必要である。

提案中の入口は、wikiプラグイン内の`ontology propose / apply / status`である。Claude CodeとCodexで操作の正本を共用する想定だが、これらの見直し・整理機能は未実装である。
本セッションでは本番のオントロジーやデータの移行は行っていない。

## 利用者に提供したい流れ

1. 「記事が増えたので、今の内容に合わせてオントロジーを整理して」と指示する。
2. 現在の定義と蓄積した記事・実体・関係を調べ、根拠付きの変更前後の案を示す。
3. 既存記録への影響と、隔離した試行での問い合わせ結果を確認する。
4. ユーザーが採用した最終案を固定して適用し、検査とグラフ再生成まで行う。
5. 未処理・未確定・部分移行の範囲を表示し、以後のingestにも採用済みの規則を使う。

表示済みで依存のそろった案をユーザーが採用しただけなら、同じ承認を繰り返し求めない。依存の組み直しで未表示の変更が必要なら、その最終差分と試行結果を示す。

## 最後の敵対的レビューで確認した重要課題

Opus 5.5、Fable 5.2、GPT-6.2 Sol、GPT-6.2 Astraで独立にレビューし、全モデルが要修正と判定した。以下は主担当が指摘を反証・照合した結果である。
最新の提供案は第7版だが、この最後のレビュー結果はまだ設計書へ反映していない。

| 課題 | 満たすべき例・条件 |
| --- | --- |
| 役割の相手・対象・期間 | A社は製品Aの顧客、製品Bの代理店である。A社の実体は1つとし、代理販売だけを根拠に製品Bの顧客一覧へ入れない |
| 問い合わせの網羅性 | 未抽出、同一性の保留、移行残件を区別する。少数事例だけ記録した件数をwiki全体の総数として答えない |
| 集計の単位 | 同じ利用事実を2記事が支えても顧客数は1社。根拠の本数・主張の件数・実体の数を区別する |
| 主張の分割後の参照 | 旧「利用する」を「試用」と「契約」へ分けたとき、「未契約だった」が否定するのは契約だけである。参照先の存在確認だけでは足りない |
| 連続する部分移行 | v1の保留を残してv3へ進んだ後、新しい根拠で最新版の記録1件へ確定し、旧残件0件となる。以前の保留理由も追える |
| 公開する版の一貫性 | 候補検索から根拠の記事を読むまで、問い合わせが旧グラフと新しい記事を混ぜない。版が揃わなければ再試行・保留する |
| 並行ingestでの同一性 | 同じメーカー・品番の製品を同時に取り込んでも、完了時に実体1件・出典2件になる。書き込みの直列化だけに頼らない |

さらに、採用済みの概念には、名前と機械用識別子に加えて、定義文、適用条件、該当例・非該当例、用途と問い、採用理由を保存する必要がある。これを次回の意味の比較の基準にする。
旧要約で必要な区別が失われている場合は、該当原本へ戻るか判定不能とし、記事と原本それぞれの確認範囲を示す。毎回すべての原本を通読する要求ではない。
型や定義の版が不明な記録を、黙って現行版の確定記録にしない条件も必要である。

## Ossieの採用検討で決めること

以下の意味と受け入れ条件を満たすか確認したうえで、保存形式やライブラリの使い方を選ぶ。

1. 型・役割・関係・時間条件をどう表現し、一覧・件数・制約の意味をどう定めるか。
2. 実体・主張・根拠をどう区別し、それぞれにどのIDと履歴を与えるか。
3. 定義の版、旧定義、未分類、同一性の保留、複数回の移行をどう表現するか。
4. 実体の正本をページに置くか、別の記録として持つか。既存entityページとIDをどう再利用・対応付けするか。
5. Ossieに任せる定義管理・検証・推論などの範囲と、info-hive側で担う抽出・名寄せ・移行・承認・公開制御の境界。
6. Markdown・既存グラフ・通常ingest・lint・query・browse・MCPをどこまで変更する必要があるか。
7. 新規導入だけでなく、旧配置や手編集の定義を持つ既存wikiへどう適用するか。

「顧客」を型として残すか役割として表すかは未決定である。ユーザーが指定した粒度を、特定の形式的なクラスへの固定と解釈しない。
固定IDへの変更も有力な案だが、必須とは決定していない。旧IDとの明示的な対応を保持する方式も評価対象である。
役割専用の構成物や版管理が現行にないこと自体は、将来機能を実現できないという根拠にはしない。採用候補が上の意味と継続運用をどう満たすかを評価する。

## 共通の書く段との関係

ADR-0023は、wikiごとのロックと日誌を持つ共通の書く段を定めているが、`wiki_apply.py`は未実装である。
現行ADRの操作は`new`・`edit`・索引とログの`ops`で、グラフDBの更新は範囲外である。読み手が更新途中の内容を見ることも防いでいない。
オントロジーの移行で必要な依存先の検査と公開版の一貫性について、ADRの拡張または関連ADRが必要になる。専用の別の書き手を増やして迂回する方針にはしていない。
物理的なページ削除・改名や、正本の単一ファイルへの集約が、すべての方式で必須という判断もしていない。
