次は「理由をたどる」

どの版が、何を直した？
その判断は、何を根拠に選んだ？
どこまで確認できた？

定義を書くだけでは、関係は増えません。
記事から根拠付きの関係を選び、記録する作業が必要です。

現在の本番定義は 12 種類・15 述語。候補を適用した場合は 18 種類・26 述語になります。

03 / 追加する 6 つの対象

記事を、出来事そのものと混ぜない。

▦

構成要素

component

PDF の読み取り、Web raw 作成などの責務。

◈

製品の版

release

rag 0.5.1。外部ツールの版も同じ形で。

↗

変更

change

コード、文書、設定、プロンプトの変更。

△

問題

issue

どの条件で、期待と何が違ったか。

◎

評価

evaluation

何をどう測り、何が未確認か。

▤

管理対象物

artifact

README、設定ファイル、リリース本文など。

製品・概念・出典・設計判断は既存の種類を使います。リリース報告書は source のまま残し、必要な対象だけを別ページにします。

04 / 実際の記事なら、こう結ぶ

「修正した」と「全部確認した」は別。

例：PDF の先頭の改行による拒否

観測したのは rag 0.5.0、先頭に 1 バイトの改行がある PDF 2 件。

出荷した版rag 0.5.1
delivers→
変更前置きを許容
fixes→
観測した問題2 件の拒否
◎ 確認した経路

実 PDF 2 件を直接抽出。70 ページと 18 ページのテキストを観測。

△ 未確認の経路

MCP の登録から索引化まで。修正済みでも、ここまで成功したとは言わない。

前置きは 1024 バイト以下が対象。任意の不正 PDF を受け付ける修正ではありません。評価は evaluates で変更に結び、条件・結果・限界を本文に残します。

05 / 適用する順番

まず 1 事例を、最後まで通す。

語彙を確定

候補 YAML と採用規則を確認し、本番の定義へ反映。

  • 既存の定義を残す
  • 現在の型・関係の互換性を確認

対象を用意

PDF の事例から、必要な版・変更・問題・評価のページを作る。

  • 1 ページ＝1 ノード
  • ID は題名を変えても保つ

根拠で結ぶ

主語のページに関係を記述。原文を読んで採用する。

  • 述語・目的語・出典・引用
  • 確信度・状態・版と条件

検査して使う

lint → 引用と範囲の確認 → グラフ再生成 → 質問で検証。

  • 型だけの合格で終えない
  • 有用な事例から少しずつ広げる
現在は「設計を知識として取り込んだ」段階です。
候補 YAML の本番適用と、試料の対象・関係の投入は行っていません。
06 / LLM と保存先の分担

提案する処理と、保存する正本を分ける。

人／LLM記事を読み、関係候補を出す
→
確認 → Markdown既存 ID と照合し、根拠を読んで記録
→
JSONL／SQLite採用済みの記述から再生成する

extract に LLM 呼び出しを混ぜません。LLM を使わず、人が関係を書く方法も同じ検査を通せます。外部グラフ DB は、この段階では必須ではありません。

07 / 誤読しないための約束

「版」「評価」「出典」を、最後まで持つ。

版を端点にする

過去の依存は「wiki 0.23.0 → yt-dlp 2026.8.19」。現在の全版への依存には広げない。

評価 ≠ 合格

レビューや試験があるだけでは成功としない。対象の版・方法・未確認の点も読む。

グラフから本文へ

所有ページ、評価ページ、出典を開く。CLI は notes を表示せず、引用を切り詰める。

current は最新版・未解決・合格の印ではありません。判断の全件一覧や承認状態の機械的な絞り込みには、追加実装が必要です。現状は索引・台帳・JSONL と本文で確認します。

Opus の初回レビューは条件付きで採用可。版の識別・文書の変更先・引用と範囲を修正し、ローカルで再検証しました。修正後の独立再レビューは未実施です。
