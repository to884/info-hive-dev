## 今の画面で探しにくいところ

400 ページの合成の Wiki を今の版（0.13.0）で書き出して確かめた（`docs/agent-runs/2026-11-13-wiki-browse-findability/baseline/`）。

- 索引のページ（`index.html`）は、索引のファイルの見出しとリンクの入れ子をそのまま並べる。要約、種類、更新日がない。
- サイドバーは、どのページでも同じ木の全体を出す。今のページの強調、折りたたみ、件数がない。索引のページでは、同じ木が `#_nav` と `#_index` の 2 か所に出る。
- 分割した索引（`indexes/`）を指す `index.md` の行は、「indexes/source」のように索引のファイルの名前で出る。
- 索引のファイルの h1 が 1 段の入れ子になり、「コンセプトの索引」の下に「コンセプト」が出るように、同じ名前が二重に出る。
- 幅 40rem 以下では、木の全体が本文の上に縦に並び、記事に届くまで長く送ることになる。
- 検索がない（`capabilities.search` は `none`）。

要約の置き場所も確かめた。このリポジトリの `wiki/`（8 ファイル）と評価のコーパス（27 ファイル）で、frontmatter に `summary` を持つページは 0 件だった。ページのテンプレート（`assets/page.md.template`）にも `summary` の欄はない。要約は、`assets/index.md.template` が決めている索引の行 `- [[ページ]]: 1 行の要約` にある。今の `_nav_item()` は、この行の、最初の wikilink のあとの文字を捨てている。`title`、`type`、`tags`、`updated` は、ほぼすべてのページにあった。

## 2. ナビゲーションの木

### 2.1 木を組む規則

今の `Core._nav()` を、次のように直す。索引のファイルを読む順（`index.md`、`indexes/` のファイルを相対パスの順）と、項目を段落の最初の wikilink で決めることは変えない。

| | 規則 | 今 |
| --- | --- | --- |
| N1 | 索引のファイルの最初の h1 は、グループにしない。その下の項目は、ファイルのグループに入れる | h1 も 1 段のグループになる |
| N2 | 索引のファイルのグループの名前は、frontmatter の `title`、最初の h1、ファイル名の順で決める | 同じ |
| N3 | `index.md` は、包みのグループにしない。`index.md` の見出しのグループは、いちばん上に並べる。`index.md` の、最初の見出しより前の項目は、「索引」という名前のグループにまとめて先頭に置く | `index.md` 全体が名前のないグループになり、その下に h1 のグループが入る |
| N4 | `index.md` の `indexes/` への行は、分割した索引のファイルのグループを並べる順と、そのグループの要約を決める。行のある場所には、グループへの項目を置く。項目の名前は、行き先のグループの名前にする | 項目の名前は、wikilink の別名か行き先の文字（`indexes/source`）。並びは、ファイルの相対パスの順 |
| N5 | `index.md` のどこからも指されていない `indexes/` のファイルは、N4 で並べたものの後に、相対パスの順に置く | 同じ（相対パスの順） |
| N6 | 索引にない、描かれているページは、「索引にないページ」のグループに、種類ごとの子のグループとして入れる。子のグループの名前は、`source`、`entity`、`concept`、`synthesis` を「ソース」「エンティティ」「コンセプト」「シンセシス」にし、ほかの値はそのまま、値のないものは「種類なし」にする | 子のグループの名前は `type` の値そのもの |
| N7 | グループの件数は、そのグループと子孫のグループの項目のうち、描かれているページの、重ならない数である | 件数はない |

N3 と N4 は、索引のページの一覧の「索引の順」（4.2）も決める。

### 2.2 グループの ID

グループの ID は、今と同じく、索引のファイルのグループには `_g` とディスク上の相対パスのハッシュを、見出しのグループには `_g` と通し番号を付ける。ID は、木（`nav.js`）、索引のページの一覧の `data-groups`、URL の `#group=<ID>` で同じものを使う。

通し番号の ID は、索引を書き換えると変わる。`#group=` を含む URL を保存しておくと、索引を書き換えたあとは別のグループを指すことがある。世代が変われば `app.js` が「再読み込みする」と知らせるので、この設計では ID を安定させない（11）。

### 2.3 `nav.js` の形

`WIKI_NAV` の形を次のようにし、`protocol_version` を 2 に上げる。

```js
window.WIKI_NAV = {
  protocol_version: 2, generation: "…",
  groups: [{ id: "_g…", title: "コンセプト", summary: "…", count: 138,
             items: [{ state: "resolved", id: "concepts/bm25", path: "concepts/bm25.html", label: "BM25", anchor: "…" },
                     { state: "group", group: "_g…", label: "エンティティの索引" },
                     { state: "unresolved" | "ambiguous", label: "…" }],
             children: [ … ] }]
};
```

- 足すのは、グループの `count` と `summary`、ページの項目の `id`（ページの識別子）である。`id` は、記事のページの `#_article` の `data-page-id` と比べて、今のページを見つけるのに使う。出力の名前と URL で比べると、サーバーのトークンや `file://` の違いを吸収しなければならない。
- 要約は `nav.js` に入れない。1,000 ページで約 112 KB の `nav.js` を、全ページが読むからである（ADR-0010）。要約は、索引のページと `data/search.js` にだけ置く。
- 契約の版を上げるのは、`group` の項目の `label` の意味と、グループの並び（N1、N3、N4）が変わるからである。`app.js` と `nav.js` は同じ版の browse が作るので、版の違いで止まるのは、古いタブに新しいデータが届いた場合だけである。

## 3. サイドバー（左のペイン）

### 3.1 記事のページ

`#_nav` の中を、上から次の順にする。

1. スコープの表示 `#_scope`。今と同じである
2. 索引へのリンク `.nav-home`。今と同じである
3. 検索欄（5.3）と、検索の結果の場所
4. グループの木

木は、グループごとに `<details>` を作り、`<summary>` にグループの名前と件数を置く。

- 今のページを含むグループと、その祖先のグループだけを開く。ページが複数のグループに載っていれば、そのすべてを開く。
- 今のページの項目に `aria-current="page"` とクラス `is-current` を付けて強調する。読み込んだときに、強調した項目が見えるところまで木をスクロールする（`scrollIntoView`）。ページ全体はスクロールしない。
- グループの `<summary>` に、「一覧」のリンク（`index.html#group=<ID>`）を置く。押すと、索引のページの一覧を、そのグループに絞って開く。リンクは、`<summary>` にポインターかフォーカスがあるときと、絞っているグループのときだけ見せる（`visibility` で隠すので、場所は動かない）。
- 未解決と曖昧の項目は、今と同じく `span.wl.wl-<状態>` で出す。
- グループへの項目（N4）は、`index.html#group=<ID>` へのリンクにする。
- 開閉の状態は保存しない（11）。

### 3.2 索引のページ

索引のページでは、木をグループの名前と件数までに畳む。ページの項目は出さず、ページの名前は右の一覧にだけ出す。

- 先頭に「すべてのページ」を置き、その下にグループの入れ子を `ul` で並べる。各行は `#group=<ID>` へのリンクで、押すと右の一覧をそのグループに絞る（4.3）。
- 絞っているグループの行に、`aria-current="true"` とクラス `is-current` を付ける。
- 索引のページの左には検索欄を置かない。右の一覧の絞り込みの欄が、検索欄を兼ねる（4.3）。

### 3.3 狭い幅

幅 48rem 以下では、`#_nav` を本文の上に置き、木を `<details class="drawer">`（「メニュー」）に入れて閉じておく。記事のページの検索欄は、畳まずに見せる。48rem より広いときは、`app.js` が `matchMedia` で `drawer` を開き、「メニュー」の `<summary>` は CSS で隠す。

今の切り替えの幅は 40rem である。サイドバーの幅を 16rem から 17rem に広げるので、本文の幅が 30rem を割らないように、切り替えを 48rem に上げる。

### 3.4 JavaScript を切ったとき

今と同じく、`#_nav` には `<noscript>` の「索引へ」のリンクだけが出る。索引のページの一覧（4）は、JavaScript なしで読める。

## 4. 索引のページ（右）

### 4.1 骨組み

`render_index()` が、次の骨組みを事前に描く。

```html
<main id="_main">
  <header id="_ixhead"><h1>索引</h1><p class="ix-stats">400 ページ</p></header>
  <div id="_filters" class="fx-bar"><noscript><p class="state">絞り込みと検索には JavaScript が要る。一覧は索引の順に並んでいる。</p></noscript></div>
  <p id="_count" class="fx-count" aria-live="polite">400 件</p>
  <ul id="_index" class="fx-list">
    <li class="fx-row" data-type="concept" data-tags="検索&#31;ランキング" data-updated="2026-04-18"
        data-title="BM25" data-order="12" data-groups="_g3 _g7">
      <div class="fx-path">コンセプト › 検索</div>
      <div class="ix-line"><a class="ix-title" href="concepts/bm25.html">BM25</a>
        <span class="badge t-concept">コンセプト</span><time datetime="2026-04-18">2026-04-18</time></div>
      <p class="ix-summary">クエリの語が文書にどれだけ現れるかをもとに、文書の関連度を点数にする方法</p>
      <div class="ix-tags"><span class="tag">検索</span><span class="tag">ランキング</span></div>
    </li>
    …
  </ul>
  <section id="_index_unresolved">…</section>   <!-- 4.4。あるときだけ -->
  <section id="_diagnostics">…</section>       <!-- 今と同じ -->
</main>
```

- 一覧の 1 行は、描かれているページ 1 つである。同じページが索引の複数の場所に載っていても、行は 1 つにする。
- 行の並びは「索引の順」である。2.1 の木を深さ優先でたどり、ページが最初に現れた順に並べ、索引にないページはその後に、N6 のグループの順に置く。`data-order` は、この順の番号である。
- `ix-title` のリンクの文字は、ページの題名だけにする。種類、更新日、要約、タグは、リンクの外に置く。今の試験は、`#_index a` の文字が題名と同じであることを使っている。
- `fx-path` は、そのページが最初に現れたグループの階層（いちばん上のグループからの名前）である。名前のないグループは飛ばす。索引にないページは「索引にないページ › 種類」になる。
- `data-groups` は、そのページを項目に持つグループと、その祖先のグループの ID を、すべて空白で区切ったものである。
- `data-tags` は、タグを U+001F で区切る。タグの文字に空白や `,` が入っていても、区切りと取り違えない。
- 種類の印（`badge`）の文字は、N6 と同じ規則で決める。クラスは `t-<type>` とし、`type` の値が英小文字の識別子でなければ `t-other` にする。
- 更新日は、`updated` の値を文字のまま出す。日付として解釈しない。値がなければ `time` を出さない。

### 4.2 要約

行と検索に出す要約は、次の順に最初にあるものを使う。

| 順 | 出どころ | 取り方 |
| --- | --- | --- |
| 1 | frontmatter の `summary` | lint の形の値（`canonical_meta()`）。メタ欄に出すものと同じ |
| 2 | 索引の行 | そのページを指す項目のうち、索引の順で最初のものの、段落の最初の wikilink より後ろの文字。表示の文字（`inline_text()` と同じ規則）にし、先頭の `:`、`：`、`—`、`–`、`-` と空白を除く。空なら次の行を見る |
| 3 | 本文の冒頭 | 本文の最初の段落（見出し、リスト、引用、表の中の段落を除く）の表示の文字の、最初の `。` まで。`。` がなければ 120 字まで |
| 4 | なし | `ix-summary` を出さない |

- 1 を先にするのは、ページ自身が書いた要約で、メタ欄の「要約」と食い違わないようにするためである。
- 3 は、索引のない Wiki でも行に中身が出るように足す。試作では、評価のコーパス（`index.md` がない）の 27 ページのすべてに、意味の通る一文が出た。
- どの出どころから取ったかは、`data/search.js` に持たせる（5.1）。画面では区別しない。

### 4.3 絞り込みと並べ替え

`app.js` が、`#_filters` に次の部品を作る。

| 部品 | 働き |
| --- | --- |
| 検索欄 | 5 の照合で、当たるページだけを残す。語を空白で区切ると、すべての語に当たるページだけになる |
| 種類のボタン | 「すべて」と、一覧にある種類ごとのボタン。押したボタンに `aria-pressed="true"` を付ける。1 つだけ選べる |
| タグの選択 | 「タグ: すべて」と、一覧にあるタグ（件数つき、文字の順）。1 つだけ選べる |
| 並べ方 | 「索引の順」「更新の新しい順」「題名の順」 |
| グループの印 | `#group=<ID>` で絞っているとき、「グループ: 名前 ×」を出す。押すとグループの絞り込みを外す |

- 絞り込みは、検索、種類、タグ、グループのすべてを満たす行だけを残す。外した行には `hidden` を付ける。
- 並べ替えは、行の要素を並べ直す。「更新の新しい順」は `data-updated` の文字の大きい順、同じなら索引の順である。値のない行は最後に置く。「題名の順」は `localeCompare(…, "ja")` で、同じなら索引の順である。
- 件数は「400 件中 27 件」と出す。何も絞っていないときは「400 件」にする。
- グループの絞り込みは、URL の `#group=<ID>` で決める。`hashchange` で読み直すので、記事のページの「一覧」のリンクと、左の木のどちらから来ても同じに絞れる。知らない ID なら、絞り込みをせず、印も出さない。
- 検索で絞っているときも、並びは選んだ並べ方に従う。当たりの強さの順には並べない（右の一覧は、条件で絞った表であるため）。当たりの強さの順は、記事のページの検索の結果（5.3）で使う。
- 絞り込みの状態は保存しない。検索欄の文字も URL に入れない。

### 4.4 ページに決まらない索引の行

一覧はページだけを並べるので、索引の行のうち、未解決と曖昧の項目は一覧に出ない。そこで、そういう行があるときだけ、一覧の後に `#_index_unresolved`（見出し「ページに決まらない索引の行」）を置き、グループの階層と、`span.wl.wl-<状態>` の項目を並べる。今の索引のページでも、これらは状態つきの文字で出ている。

## 5. 検索

### 5.1 `data/search.js`

```js
window.WIKI_SEARCH = {
  protocol_version: 2, generation: "…", incomplete: false,
  fields: ["path", "id", "title", "summary", "summary_from", "type", "tags", "headings", "updated", "group_path"],
  rows: [["concepts/bm25.html", "concepts/bm25", "BM25", "クエリの語が…", "index", "concept",
          ["検索", "ランキング"], [["語の頻度と希少さ", "語の頻度と希少さ"], …], "2026-04-18", ["コンセプト", "検索"]]]
};
```

- 行は、描かれているページ 1 つに 1 行で、識別子の順に並べる。読めないページと `id_collision` のページは入れない。
- `headings` は、h2 から h6 の見出しの `[ID, 表示の文字]` である。ID と文字は、第 1 段階の設計の 3.4 の `assign_heading_ids()` の結果を使う。h1 は題名と重なることが多いので入れない。
- `summary_from` は、4.2 の出どころ（`frontmatter`、`index`、`lead`、`none`）である。
- `incomplete` は、写しに読めないページがあるとき（構造の直しの 4.1）に真にする。
- 書き方は、今のデータのファイルと同じ `js_data()` を使い、`</`、U+2028、U+2029 をエスケープする。
- 大きさは、ADR-0010 の PoC の見込み（1,000 ページで約 236 KB）に、見出しの ID とグループの階層が加わる。実装の段で 1,000 ページの合成の Wiki で測り、記録する（9）。

### 5.2 照合

ADR-0010 の決定 5 のとおり、NFC にそろえ、小文字にして、部分一致で照らす。

- 問い合わせを空白（全角の空白を含む）で区切り、語のすべてが、どれかの欄に当たる行を残す。
- 照らす欄は、題名、タグ、見出し、要約の 4 つである。本文は照らさない。
- 語ごとの点は、当たった欄のうちいちばん高いものとし、行の点は語の点の和とする。

| 当たり方 | 点 |
| --- | --- |
| 題名の先頭 | 12 |
| 題名の途中 | 8 |
| タグと等しい | 6 |
| タグの途中 | 4 |
| 見出し | 3 |
| 要約 | 2 |

- 点の高い順、同じなら題名の文字（UTF-16 の符号の順）で並べる。`localeCompare` を使わないのは、ブラウザで順が変わらないようにするためである。
- 照合の関数は `window.__browse.search(q)` として出す。返す値は、`wiki_search.py --json` の結果の欄にそろえた `{rel_path, title, type, tags, updated, score, snippet, heading_path, href}` の並びである（ADR-0010 のデータの契約）。`rel_path` はページの識別子に `.md` を付けたもの、`snippet` は題名のほかで当たった欄の文字、`heading_path` は見出しに当たったときのその見出しである。試験はこの関数で照合を確かめる。

### 5.3 記事のページの検索欄

- 入力すると、木を隠し、その場所に結果を出す。結果は最大 30 件で、件数を先に出す。結果の 1 件は、題名（当たった文字に `<mark>`）、種類の印、グループの階層である。
- 見出しに当たった結果は、その見出し（`#<ID>`）へのリンクにする。
- 欄を空にするか Esc を押すと、結果を消して木に戻る。Enter で最初の結果を開く。どのページでも `/` を押すと、欄に移る（ほかの入力欄にいるときは除く）。
- `<mark>` は、文字を分けて要素を作り、`textContent` で入れる。`innerHTML` は使わない。

### 5.4 読み込み

`data/search.js` は、ページを開いたときには読まない。検索欄か索引のページの絞り込みの欄に、初めてフォーカスが入ったときに、`<script src>` の要素を足して読む。読み終わるまでに打った文字は、読み終わったときに照らす。

- 記事のページを開くたびに、数百 KB を読まないためである。
- 読めなければ（`onerror`）、欄を使えなくし、「検索の索引を読めない」と出す。
- 読んだ `WIKI_SEARCH` の `protocol_version` が 2 でなければ、同じく使えなくし、「この画面は、検索の索引の版に対応していない」と出す。
- 世代がページの世代と違えば、今のほかのデータと同じく「Wiki が更新された。再読み込みする。」と出す（`state.mismatch` に `WIKI_SEARCH` を足す）。照合はそのまま行う。

### 5.5 状態の表示

| 状態 | 表示 |
| --- | --- |
| 索引を読めない、版が違う | 欄を使えなくし、理由を欄の下に出す |
| 0 件 | 「当たるページはない」 |
| `incomplete` が真 | 結果の下に「読めないページがあるので、結果は不完全」と出す。索引のページの件数の横にも出す |
| 世代が違う | ページの先頭の知らせ（今と同じ） |
| JavaScript なし | 検索欄を出さない。索引のページの `noscript`（4.1） |

## 6. データのファイルと、2 つの方式

- `DATA_FILES` に `data/search.js` を足す。`Core.knows()`、`render_data()`、静的の書き出し、サーバーが返す名前は、`DATA_FILES` から決まるので、ほかに名前を数え上げる場所がないかを実装の段で確かめる。
- `manifest()` の `capabilities.search` を `"embedded"` にする。サーバーも `embedded` にする。`live`（MCP の `query`）は、優先順位 3 位の残りの作業として別に出す。
- 索引のページは、今と同じく `data/diagnostics.js` も読む。`data/search.js` は、`<script src>` で書かず、5.4 のとおり後から読む。
- `nav.js`、`data/manifest.js`、`data/diagnostics.js` の `protocol_version` も 2 にそろえる。`app.js` は、3 つと `WIKI_SEARCH` のどれでも 2 でなければ止まる。

## 7. 画面の部品と CSS

- `style.css` の色を、`:root` の変数にし、`prefers-color-scheme: dark` で変数を差し替える。記事のページの本文、メタ欄、被リンク、関係表、診断の見た目は、色の値を含めて今と同じにする。

- 画面の部品の ID は、今と同じく `_` で始める（`_filters`、`_count`、`_index`、`_ixhead`、`_index_unresolved`、`_q`）。

## 10. 順序

構造の直しが `info-hive-wiki` の main に入ってから始める。

1. この設計を、構造の直しが入ったあとのコードと照らし直す。`Recorder` がなくなったこと、内容と読み取りの情報が分かれたこと、「不完全」の印の持ち方を確かめ、食い違いがあれば設計を直す。
2. 木を組む規則（2）と `nav.js` の形を直し、試験を書き換える。
3. 索引のページ（4）と要約（4.2）を描く。
4. `data/search.js`（5.1）と、2 つの方式の扱い（6）を足す。
5. `app.js` と `style.css` を、試作（`poc/browse-findability/assets/`）から移す。試作の `proto.js` は、記事のページの検索の結果と、索引のページの絞り込みを持つ。移すときに、5.4 の後からの読み込み、5.5 の状態の表示、`window.__browse.search()` を足す。
6. ブラウザの試験と起動の速さを流し、5 つのブラウザで手で確かめる。

版は、利用者に見える機能を足すので、マイナー版を上げる。番号はマージの前に決める。

## 11. 限界

- **グループの ID は、索引を書き換えると変わる。** 保存した `#group=` の URL は、別のグループを指すことがある（2.2）。
- **木の開閉と、絞り込みの状態は、ページを移ると消える。** 記事のページの木は、移った先のページのグループだけを開く。
- **検索は本文を照らさない。** 本文の検索は、サーバーとアプリで MCP の `query` に頼む（ADR-0010 の決定 4 と 5）。この設計では作らない。
- **要約の 3 番目（本文の冒頭）は、本文の書き方に頼る。** 最初の段落が定義の文でないページでは、要約にならない文が出る。
- **索引のページの一覧は、全ページを 1 つの HTML に持つ。** 1,000 ページで数百 KB になる見込みである。実装の段で測り、起動の速さの合格の目安を超えるなら、一覧の事前の描き方を見直す。
- **JavaScript を切ったとき、索引のページはグループで絞れない。** 一覧は索引の順に並び、各行にグループの階層が出るので、分類はたどれる。

## 範囲の外

- 記事のページの本文の見た目（題名の見出し、目次、メタ欄の作り）
- サーバーの `live` の検索、本文の検索、RAG
- サーバーの 404 のページの見た目
- 木の開閉の保存と、グループの ID の安定化
