# wiki ごとのオントロジー提案・適用機能の提供案

2026-11-19。第 7 版。状態: 提案。対象: wiki プラグインの利用者向けの入口と、大まかな利用の流れ。
ここに示すコマンドと動作は未実装である。
語彙そのものの設計や、トランザクションなどの詳細な実装方式は別途設計する。

## 提供する価値

利用者が「この wiki で知りたいこと」を伝えると、記事の内容に合う対象の種類と関係を提案し、少数の記事で試してから適用できる。
「最適」を自動で保証する機能とはせず、用途・根拠・具体的な質問に照らして適した案を選べる機能にする。
利用者は YAML を書く必要がなく、必要な対象・関係と実際の記述例を日本語で判断する。
記事の蓄積によって概念が定義に合わなくなった場合は、利用者の指示で既存のオントロジーを見直し、統合・分割・再分類と既存記録の移行も提案する。
この見直しを機能の提供範囲に含める。詳細は[既存オントロジーの見直し・整理](wiki-ontology-maintenance-2026-11-19.md)に置く。

## グラフの単位は記事ではなく実体

利用者の指定により、顧客や製品など、記事が説明する対象を知識グラフの単位にする。
「顧客・製品・利用する」は種類と関係の定義、「顧客X・製品A」は個別の対象、記事は根拠という役割に分ける。
1 記事に複数の対象を記録でき、同じ製品Aが複数記事に登場しても同じ対象 ID を参照できる設計を求める。
同名だけで自動統合せず、根拠と識別情報から同一性を確認する。
対象ごとのページを利用者に手作業で作らせることは、提供する機能の前提にしない。
記事の再分類と、対象の型・役割・同一性の変更は区別する。
詳細な要件は [実体を単位にする方針](wiki-ontology-entity-granularity-2026-11-19.md) に置く。

## 入口は wiki プラグイン内の 1 操作

別プラグインではなく、既存の wiki に `ontology` 操作を追加する案を推奨する。
`SCHEMA.md` が担う記事・タグ・運用の規約と、`graph/ontology.yaml` の種類・関係の定義は区別する。
`init` や `upgrade` に記事の分析・語彙の適用まで詰め込まず、既存 wiki にも必要なときだけ使う独立した入口にする。

| 用途 | Claude Code の入口案 | Codex の入口案 |
| --- | --- | --- |
| 案を作る・見直す | `/wiki:ontology propose` | `$wiki:info-hive ontology propose` |
| 確認した案を適用する | `/wiki:ontology apply` | `$wiki:info-hive ontology apply` |
| 利用状況・適用状況と保留中の案を見る | `/wiki:ontology status` | `$wiki:info-hive ontology status` |

引数なしの `ontology` は status と同じ診断・状態の表示にする。
この段では LLM を呼ばず、記録済みの実体・関係・根拠の状態や、保留中の案を確認できる。
部分移行があれば、残している旧定義・残件数・保留理由・次の判断も表示する。
未抽出の対象をこの診断だけで発見できるとは説明せず、記録がないことを実体が存在しないことと混同しない。
診断は記事の現在の記述を対象にし、古い生成物だけを現在の状態として使わない。読めなかった範囲も表示する。
自然言語の「この wiki に合う知識のつなぎ方を提案して」「ユーザーの wiki に登場する対象の種類と関係を見直して」でも同じ手順を始める。
明示的に提案を求められた場合は診断から提案まで進め、診断だけで止めたり、同じ目的を聞き直したりしない。
`propose` の中で試行結果まで見せるので、利用者に内部の処理段階ごとのコマンドを覚えさせない。
`apply` は任意の YAML を投入する入口ではなく、確認済みの提案を対象とする。

## 対象の wiki を決める

一度の提案・適用は 1 つの wiki に限る。
プロジェクトとユーザースコープで別々の定義と提案を持ち、片方の型・関係・記事を他方へ自動で持ち込まない。

| 利用者の指定 | 動き |
| --- | --- |
| 「このプロジェクトの wiki」 | プロジェクトの指示・作業領域の設定から対象を解決する |
| 「ユーザーの wiki」または `--user` | ユーザースコープの指示・作業領域の設定から対象を解決する |
| 明示した wiki のパス | その場所を対象にする |
| スコープもパスも指定がない | 既存の解決順を使い、選んだ対象を表示する |
| 対象が見つからない・曖昧 | 推測で別の wiki を使わず、対象を確認する |

スコープ・パスの明示がなければ、既存の graph と同様に、明示パス、もっとも近いプロジェクトの指示、グローバルな指示、作業領域の設定、現在のプロジェクトの既定の場所という順で決める。
プロジェクトとユーザーの wiki が両方存在するだけでは、毎回選択を求めない。
指示が曖昧で 1 つに解決できない場合だけ、どちらを対象にするか尋ねる。
利用者には最初に「対象: プロジェクト／ユーザー、wiki の場所」を表示する。
提案から適用までは同じ対象を保持し、apply 時に現在のディレクトリから対象を選び直さない。
設定や実体が変わって同じ対象と確かめられなければ、変更せずに対象を確認し直す。
`SCHEMA.md` のない場所には案を適用せず、既存の初期化の入口を案内する。

初期化済みでも `graph/ontology.yaml` がない場合は、未採用の既定のひな形を基に案を作る。
その場合の適用は「グラフの導入と、この案の適用」と表示し、必要なひな形・規約の追加も差分に含める。
以後は記事の変更ごとにグラフ再生成が必要になることを示し、その運用を利用者が選んだ場合だけ導入する。
導入を見送れば既存 wiki を変えず、候補は未適用として残す。
これは新しい ontology 操作に設ける導入経路であり、既存の graph コマンドが定義なしで動くようになる案ではない。

## 初めて使うときの流れ

### 0. 利用状況を確認する

記録済みの対象・関係・根拠の件数、根拠のない関係、保存済みの同一性が未確定な候補を見てから、提案へ進める。
既存IDの重複は構造上の問題として表示し、名前や別名の一致は同一性を確かめる候補として表示する。字面の一致を実体の重複と断定しない。
未抽出・未判定の範囲は不明とし、同一性の保留の記録がない場合も「曖昧さがない」とは判定しない。
未使用の型が多い、型付き関係の比率が低い、ひな形のまま、という数値は観測事実として示す。
それだけで「この wiki に合っていない」と採点したり、変更を促す警告にしたりしない。
根拠があっても関係がまだ書かれていないだけなのか、語彙そのものが不足しているのかを、問いと実例で切り分ける。
初期版では専用操作から利用できるようにし、stats・lint からの短い案内は後続の利用支援として検討する。

### 1. 欲しい答えを伝える

最初に内容を読み、分野と既存の種類・関係を把握して、答えたい質問を 2〜3 個提示する。
利用者はそのまま使うか、言い換える。
既存の語彙の意味と粒度が問いに適している場合は再利用を優先する。見直しの依頼では、その意味と粒度自体も新旧の記事で検討する。
依頼に目的が書かれていれば、同じ質問を繰り返さない。
例: 「どの版で何が直ったか」「何を根拠に方式を選んだか」「どこまで確認したか」。

プロジェクト wiki では開発・運用の問いが中心になる場合がある。
ユーザー wiki は複数分野が混ざり得るため、全記事へ単一の専門分野の型を強制せず、共通の種類と必要な分野の追加を提案する。
どちらも内容から判断し、「プロジェクトなら開発用」と固定しない。

### 2. 提案を見る

最初の画面は YAML ではなく、次を示す日本語の提案にする。

- 対象 wiki と、今回答えやすくする質問。
- 維持・追加・修正・統合・分割・廃止する種類や関係。それぞれの意味と変更の理由。
- どの記事のどの記述を根拠にしたかと、実際のつながりの例。
- 具体的な対象と、既存の entity ページを含む既存対象との同一性の候補。同名でも別対象の可能性がある場合はその留保。
- 変更するファイルの数・場所と、今回整理しない範囲。
- 既存の対象の分類・ID・関係・参照に影響する件数。再編する案には移行先・根拠・未確定の記録と旧定義を残す範囲も示す。
- 読んだ記事の範囲。全件か一部か、未読・失敗・上限による中断があるか。

詳細を開けば候補 YAML と差分も見られる。
「既存の語彙で足りる」「根拠が足りないため追加しない」も正常な提案結果にする。
記事がほぼない場合は、利用目的からの仮案と明記し、記事に裏づけられた提案と区別する。
読み取りの失敗や途中終了を「変更不要」と表示しない。

### 3. 少数の記事で試す

候補の定義と、根拠が明確な少数の事例を隔離した場所で試す。
利用者には「この版 → この変更 → この問題」の図、対応する記事・引用と、答えたい問いへの試しの回答を見せる。
定義だけを加えても対象間の事実は増えないため、具体的な対象・関係・根拠を記録する差分も試行の対象に含める。
同じ対象を複数の記事が述べる例と、1 記事が複数の対象を述べる例も試す。
新しい関係を作る場合は、目的語や出典も存在する依存のそろった事例にする。

試行中は本番の記事・定義・グラフを変えず、通常の検索や問い合わせへ候補を混ぜない。
意味の確認は少数事例で行い、既存の全記事と対象記録に対する分類・ID・型付き関係・参照への影響は別に検査する。
追加では意図しない変更がないことを、再編では選んだ移行計画どおりの変更と参照の整合を確認する。後者が未完了なら適用へ進まない。
型・参照の検査と、根拠が関係の意味・条件を支えるかの確認を分けて示す。
試しの回答も出典と照合し、lint の合格だけで「内容に適合した」と説明しない。
大きい wiki の分析・試行は範囲と進捗を表示し、中断した場合は未完了として再開できるようにする。

### 4. 選んで適用する

利用者の選択は「この案を適用」「一部を変える」「見送る」を基本にする。
変更を求められたら最終的な対象・語彙・関係・根拠の記録で再び試す。未表示の変更を含む差分へ変われば、その結果と最終差分を示して採用を求める。表示済みで依存のそろった変更を選んだだけなら、同じ採用の意思を繰り返し確認しない。
部分選択で参照先や型が欠ける場合は、必要な追加も含めた案を出し直す。
表示・確認した案を固定し、適用の途中で LLM が別の関係を追加しない。
対象の wiki・定義・案が依存する対象記録とすべてのページ（編集する記事、出典、目的語、参照する原本）が試行後に変わっていたら、その案を黙って当てず再確認する。
追加されたページによる ID の重複や参照の変化も、適用の前に検査し直す。

通常の追加の適用単位は「語彙の追加＋選んだ少数事例の対象・関係・根拠」である。
既存語彙で足りる場合は「定義を変えず、選んだ事例の関係だけを追加」も適用単位にする。
ここでいう追加は、既存のノードの種類・IDと既存の関係の意味を変えない追加に限る。
通常の追加では新しい種類による自動の対応付けで既存記事を再分類せず、具体的な実体の型として使う。再編で対応付けを変える場合は、その影響も確認済みの移行計画に含める。
実体ごとのページか別の正本かは実装設計で選び、保存方式によって実体の粒度を変えない。
どちらの保存方式でも、確認済みの既存実体のIDを再利用するか明示的に対応付け、同じ実体を新しいIDで二重管理しない。同一性が未確定なら保留する。
YAML の項目を足しただけでも、既存記事の種類や ID が変わる場合は追加として通さず、既存記録の移行を伴う案として扱う。
見直し・整理の適用単位は「定義の変更＋それを使う既存対象・関係・根拠・参照の移行」とする。型や関係の改名・統合・分割・廃止、実体の再分類を提供範囲に含める。
定義が適切で原因が記録不足や抽出誤りの場合は「定義を変えず、対象・関係・根拠の記録を追加・訂正・取り下げ」も適用単位とする。根拠と訂正履歴を残す。
型の統合と実体そのものの統合は区別する。同じ実体としての識別を保ち、IDが変わる必要があれば旧IDとの対応と互換性の範囲を示す。
振り分けられない記録があれば、旧定義を残す部分移行か保留とする。旧定義を削除して移行済みとは扱わない。
部分移行後の問い合わせは確定分と旧定義に残る分を区別し、影響する問いに未移行の範囲・件数と総数を確定できないことを示す。status・lintでも移行状態を扱い、ingestで移行先を決められない新規記述は根拠付きの未分類候補として保留する。
利用者が語彙だけを適用する場合も、その最終の組み合わせで互換性と再生成を試し、再確認してから適用する。既存記録を無効にする定義だけの変更は適用しない。
完了時には「定義のみ適用、対象・関係の新たな記録は未実施」と明示する。
原本は変更せず、既存ページは必要箇所だけを編集し、索引とログを更新する。

### 5. 結果を確かめる

反映後に検査し、グラフを作り直して、試した問いと出典の対応を確かめる。
完了報告には対象 wiki、採用した定義、記録した対象・関係・根拠、変更したファイルと未処理の範囲を示す。
「定義の適用」「選んだ事例の対象・関係の記録」「グラフ再生成」を別々に報告し、一部だけ終わった状態を完了としない。
失敗時は変更済み・未変更・復旧済みを区別する。上書き前の版と適用記録を残し、無条件の巻き戻しで後の編集を消さない。
詳細な適用・復旧方式は実装設計で決めるが、途中失敗を曖昧にせず回復できることを提供条件にする。

## 利用者との会話の例

以下は利用体験を説明する架空の顧客・製品の例であり、このプロジェクトの実データではない。

> 利用者: この wiki の顧客と製品の関係を整理して。
>
> wiki: 対象はプロジェクトの wiki です。「どの顧客がどの製品を利用するか」を答えられる案を作ります。既存の「会社」「製品」を使い、顧客としての役割と「利用する」関係を提案します。
>
> wiki: 営業メモ1から「A社」「製品A」「製品B」を、営業メモ2から「A社」「製品A」を見つけました。両メモと既存の会社・製品ページで顧客番号・製品番号がそれぞれ一致するため、A社と製品Aは既存の対象を参照する案です。「製品Aを利用する」は両メモを根拠として記録できます。製品Bへの言及は確認できましたが、利用の記述は未確認です。定義とこの対象・関係・根拠を適用しますか。
>
> 利用者: その案で適用して。
>
> wiki: A社・製品A・製品Bの記録と、A社が製品Aを利用する関係、2件の根拠を適用し、検査・グラフ再生成まで終えました。他の記事からの対象・関係の記録は未実施です。以後の取り込みでも同じ対象の識別規則と採用済みの語彙を使い、判断できない帰属は保留します。

会話の例は将来の動作を示すもので、現在その機能が動くことを示すものではない。

## 記事が増えた後

`ontology propose` を再び実行すると、現在の定義を出発点として差分を提案する。
「今の内容に合わせて見直し、整理して」という指示では、新旧の記事を比べ、語彙の不足だけでなく概念の重複・粒度・役割・関係の意味も検討する。
語彙の不適合、記録不足、抽出の誤り、現実の時期や版の変化を区別し、根拠を伴う再編と既存データの移行を提案する。記事が増えたことだけで不適合とは判定しない。
前回見送った案は、新しい根拠や目的の変更がなければ繰り返さない。ただし利用者が明示して再検討を求めた場合は、前回の理由と基準の版を示して再検討する。
通常の ingest も、採用済みの語彙と同じ対象の識別・根拠・同一性の保留の規則を使う。既存の entity ページも照合し、選んだ保存方式へ実体を主語にして関係を記録する。
同名だけでは既存対象へ統合せず、判別できない帰属は候補として保留する。未確定の候補を確定した知識として問い合わせへ混ぜない。
この接続は初期版に含め、新しい語彙を毎回自動で追加する機能とは分ける。
既存の語彙で表せない内容を ingest 時に自動で見直し候補へ蓄積する機能は、初期版には含めない。
初期版の見直しでは、利用者が再び propose を実行した時点で記事と現在の定義を調べる。
status が示す語彙の見直し案は、その wiki で明示的に作った提案であり、未実装の語彙の自動蓄積の結果ではない。同一性の保留や部分移行の未分類候補とは区別する。
自動的に対象を変えたり、別スコープの語彙を反映したりしない。

## 初期版で提供する範囲

独立した `ontology` 操作、明示した wiki ごとの提案、隔離した少数事例の試行、確認した差分の適用と結果の報告、通常の ingest との対象識別・根拠の記録の共用を一組にする。
利用者の指示による既存定義の整理と、実体の再分類を含む既存データの移行も必要な提供範囲とする。
作る順は診断、提案・試行、追加の適用、既存定義と記録の移行とする。途中段階の先行公開は可能だが、追加のみの適用を見直し・整理機能の完成とは報告しない。
記事を読む LLM は利用中のホストを使い、追加の API キーやモデルを必須にしない。
現行の Markdown と ontology.yaml を保持し、新たな実体・関係・同一性の判断・根拠も再生成で失われない正本として管理する。
現行の ingest もLLMが既存ページを調べ、必要な entity ページを作成・更新する。`entities:` と `sources:` で複数記事・複数対象の対応も記述でき、実体間の出典付き関係の形式も既存である。
extract はその記述を変換する処理であり、本文からの発見や名寄せを行わない。新機能では既存の仕組みを基礎に、同一性の保留と検証、提案と通常の ingest が使う規則、選んだ正本への記録を整合させる。
既存の lint/extract/query がそのまま実体の抽出・名寄せまで行えるとは扱わず、保存方式と合わせて接続方法を決める。外部グラフ DB や専用 UI は必須にしない。
Claude Code と Codex は同じ操作の正本を使い、入口だけを変える。

適用・復旧は ADR-0023 の共通の書く段と整合させ、ontology だけの別の書き手を増やさない方針を優先する。
ただし、wiki_apply.py は現在未実装で、ADR の決定に ontology.yaml の扱いも明記されていない。
必要な扱いを設計へ加えて共通の書く段を実装し、定義・記事・索引・ログ・生成物の完了の境界を確かめてから apply を提供する。
ingest の共通規則への接続まで確かめるまでは、採用後の取り込みも備えた機能が完成したとは報告しない。
再編では定義の版と移行記録を保持し、ingestが古い定義で作った差分の検査も共通の書く段で行う。エッジIDを参照する関係も移行し、新旧混在の問い合わせを新定義の完了結果として公開しないことを提供条件にする。
適用後も旧定義を残す部分移行では、その版と残件を明示した問い合わせを提供する。混在を隠したまま完全移行済みと扱わない。
実体の型の解決は明示型、kindと日本語の互換別名、maps_from、IDの依存も含めて検査する。SCHEMA.mdの該当規約とwikiごとの意味の対応を整合させ、共通のkind別名表を特定wikiの意味に変更しない。旧語や別名の意味の解決は採用済みのwikiの定義を使ってingest/lint/extract/queryで共用する。
これは利用者に YAML の手編集や既存 ADR の仕組みの利用を要求するものではなく、プラグイン側の提供条件である。

複数 wiki の一括変更、無人での継続的な語彙変更、OWL の論理推論は初期版に含めない。
既存語彙の変更を伴う移行は、根拠・影響・試行・確認済みの案と履歴を備えたうえで提供する。
質問の利用実績からの改善提案や browse 上の編集画面は、初期版の利用を確かめた後の拡張とする。
