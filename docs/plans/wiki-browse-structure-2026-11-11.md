## 1 版目のレビューで崩れた前提

1 版目は、4 つの構造（守る場所、失敗の境界、絶対パスの検査、試験）を別々に直そうとした。レビューは、その下にある前提を崩した。反例を塞ぐ前に、前提を書き出し、同じ前提に頼る箇所をコードから探した。

| 崩れた前提 | レビューの反例 | 同じ前提に頼っていた、ほかの箇所 |
| --- | --- | --- |
| 調べられないことは、ないこととして扱ってよい | 一覧の確かめのあとの `rglob` が失敗を黙って飛ばし、入力が欠けたまま守る場所を決める | 退避した世代の目印を読めないと、片付けが「戻せる世代はない」として、最後に公開した世代を消す（`cleanup`）。入れ子の確かめが、一覧を作れないディレクトリを飛ばす（`markers_below`）。属性を読めないと「リンクでない」とする（`_is_link`）。5 回目と 6 回目の重大な指摘も、この前提だった |
| 入力の走査の一本化は、後回しにできる | 守りが今の入力を調べ直しても、調べる走査が不完全なら、守りから外れる | 入力の印、写し、守る場所が、別々の走査から作られている |
| 読むだけなら、browse の状態のファイルとの重なりは害がない | Wiki のページが `server.json` を指すと、操作のトークンがページに描かれる | 生成の記録（Wiki のルートの絶対パスを含む）を指すページも、同じである |
| 例外を捕まえる範囲と、公開が確定する境界は同じである | 公開したあとの記録の書き込みで失敗すると、0 でない終了コードなのに、前の世代はもう消えている | サーバーの中核の入れ替えと、生成日時の記録も、確定の点が決まっていない |
| 応答の番号で、正しく劣化したかを判定できる | 入力が欠けた新しい中核を採用しても、404 と 200 なので合格になる | 入力でない場所の失敗で閲覧が止まっても、503 なので合格になる |
| 入出力は、決めた境界の中でだけ起きる | 画面の部品を、要求のたびにファイルから読む。読めないと 500 になる | 注入する呼び出しを一覧で決めると、一覧にない呼び出し（`DirEntry.stat` など）が抜ける |

## 原則

直しは、次の 8 つの原則にまとめる。それぞれが、上の前提を 1 つなくす。

| | 原則 | なくす前提 |
| --- | --- | --- |
| P1 | 分からないことを、ないこととして扱わない | 調べられないことは、ないこととして扱ってよい |
| P2 | browse の入出力は、1 つの層を通る | 入出力は、決めた境界の中でだけ起きる |
| P3 | 入力は、1 回の走査の 1 つの結果から作る | 走査の一本化は後回しにできる |
| P4 | browse は、自分の持ち場にある実体を、入力として読まない | 読むだけなら、状態のファイルとの重なりは害がない |
| P5 | 守りは、壊す操作のたびに、自分で今の入力を調べる | 守る場所は、呼ぶ側が要所で決め直せばよい |
| P6 | 仕事の単位は、すべて済むか、前のままかのどちらかで終わる | 例外を捕まえる範囲と、確定の境界は同じである |
| P7 | 描く側は、絶対パスを持たない | 出力から絶対パスを探して、だれが書いたかを推定できる |
| P8 | 試験は、結果を 2 つの参照の状態と比べる | 応答の番号で、正しく劣化したかを判定できる |

## 2. 入出力の層（P1、P2）

browse のファイルの入出力（属性を調べる、一覧を作る、リンクを解く、読む、作る、置き換える、名前を変える、消す、ロックを取る）は、すべて `wiki_browse_fs.py` の関数を通す。`wiki_browse.py` と `wiki_browse_core.py` は、`os`、`pathlib`、`shutil`、`open` の入出力を直接呼ばない。

- **「ない」と「分からない」を分ける。** 層の関数は、対象がないとき（`FileNotFoundError`、`NotADirectoryError`）だけ「ない」を返す。それ以外の失敗（アクセス権、共有違反、入出力の誤り）は、「分からない」として例外（`Unknown`）にする。呼ぶ側は、「分からない」を空、偽、既定の値に直さない。
- **一覧は、完全か、失敗かのどちらかである。** 一覧を作る関数は、項目ごとの種類（ファイル、ディレクトリ、リンク）と属性を、その場で取って返す。途中で分からなくなったら、一覧の全体を失敗にする。
- **起動のときに読むものは、起動のときに読む。** 同梱の画面の部品（`app.js`、`style.css`）は、`serve` と `build` の始めに 1 度だけ読む。読めなければ、起動しない。要求の処理は、Wiki の入力のほかにファイルを読まない。
- **層の外に入出力がないことを、試験で確かめる。** browse の 2 つのモジュールの構文木をたどり、入出力の呼び出しが層の外にないことを確かめる。試験の注入（8）は、この層で行うので、注入の一覧に抜けができない。

lint とグラフの抽出の関数は、文字を受け取って解釈するものだけを使う（`parse_frontmatter_raw`、`extract_wikilinks`、`read_frontmatter`、`build_nodes`、`build_edges`）。ファイルを読む関数（`iter_page_files`、`index_files`、`collect_pages`）は使わない。

## 3. 入力の走査（P3）

Wiki のディレクトリは、仕事の単位（6）ごとに 1 度だけ走査する。入力の集合、入力の印、Wiki の外にある実体は、その 1 回の結果から作る。別の走査で確かめ直すことはしない。

- **たどり方**: lint が今使っている `rglob` と同じにする。ディレクトリには降りる。ただし、シンボリックリンクのディレクトリには降りない（Windows のジャンクションには降りる）。最上位の `indexes` は、それ自身がリンクでも降りる（lint は `indexes/` を起点に列挙する）。同じディレクトリには 2 度降りない（輪で止まらない）。ページでも索引でもない最上位のディレクトリ（`raw`、`assets` など）には降りない。
- **入力の種類**: ページかどうかは `wiki_pages.is_page_path()` で決める。索引は、最上位の `index.md` と、`indexes` の下の `.md` である。索引の拡張子の大文字と小文字の扱いは、lint の `index_files()` と同じにする（OS によって違うので、試験で確かめる）。オントロジーは `graph/ontology.yaml` である。
- **結果**: 入力ごとに、種類、ディスク上の相対パス、NFC の相対パス、大きさ、更新時刻、実体の識別、実体が Wiki の外にあるか、を持つ。走査が完全でなければ、結果はない（P1）。
- **lint と同じ集合になること**は、今は試験で確かめる。リンク、ジャンクション、大文字の拡張子、`.` で始まる名前、除くディレクトリを組み合わせた試験用の木で、走査の結果が `iter_page_files()` と `index_files()` に一致することを、Windows と Linux で確かめる。
- **wiki の走査の計画との関係**: 別の計画（[wiki をたどるとき、除くディレクトリに降りない](wiki-walk-excluded-dirs-2026-11-11.md)。設計の案の段階）が、`wiki_pages.walk_markdown()` に lint の走査をまとめる。それが入ったら、browse の走査は `walk_markdown()` に乗り換え、lint と同じ集合になることが、試験ではなく作りで決まる。その計画には、索引のファイルの列挙も `walk_markdown()` で行うことと、一覧を作れなかった場所を必ず知らせることを求める（今の案は、索引の `rglob` を変更の対象の外にしている）。

## 4. browse の持ち場と、入力（P4）

browse が書く場所（持ち場）は、`<data_dir>/browse/` の下と、目印（`.browse-generation`、`.browse-work`、`.browse-server`）のあるディレクトリの下である。

- 走査で見つけた入力の実体が、持ち場の中にあるとき、その入力を読まない。描かず、診断（`browse_area`）に識別子を挙げる。持ち場の中かどうかは、実体の祖先のディレクトリをたどり、目印のあるディレクトリか `<data_dir>/browse/` に当たるかで決める。
- 持ち場には、操作のトークン（`server.json`）、Wiki のルートの絶対パス（生成の記録）、browse が作った HTML がある。どれも、Wiki のページとして描くものではない。
- これで、サーバーを途中で終わらせる仕組み（`shutdown_requested`）が要らなくなる。今は、状態のディレクトリが入力と重なったら、サーバーを終わらせている。直したあとは、その入力を読まないので、サーバーは動き続けてよい。
- 持ち場の中の入力の実体は、読まないが、守る（5）。利用者が書き出し先に自分のファイルを置き、Wiki のページからそれを指していることがあるからである。

## 5. 書き込みの守り（P5）

- `Guard` は、Wiki のルートを持つ。守る場所（Wiki のルートと、Wiki の外にある入力の実体）は、`Guard` が 3 の走査で自分で調べる。
- **壊す操作**（すでにあるものを置き換える、名前を変える、消す）の直前に、`Guard` が守る場所を調べ直す。**作る操作**（まだないパスに作る）は、前に調べた結果で確かめる。どちらの操作かは、`Guard` が対象の有無で決める（「ない」と「分からない」は P1 で分かれる。分からなければ止まる）。置き換えは、一時のファイルを作る操作と、置き換える操作の 2 つとして、それぞれ確かめる。
- **持ち場の単位で確かめる。** 壊す操作の対象が持ち場 D の中にあるとき、D の中に守る場所の実体が 1 つでもあれば、D の中では壊す操作をしない。Wiki のページが状態のディレクトリの目印（`.browse-server`）を指しているときに、同じディレクトリの `server.json` を消すことも、これで拒む。
- 走査が完全でなければ、守る場所が分からないので、書かずに止まる（P1）。
- 呼ぶ側の決め直し（`set_protected`、`_refresh_guard`、`external_inputs` の呼び出し。今 8 か所）をなくす。
- 残る限界: 調べてから操作するまでのあいだに入力が変わる競合（元の設計の 6.5 と同じ）。

## 6. 仕事の単位と、確定の点（P6）

browse の仕事を、次の単位に分ける。どの単位も、「すべて済んで確定する」か「前のまま」かのどちらかで終わる。確定の点より前の失敗は、前の状態を残す。確定の点より後の処理は、失敗しても単位を失敗にしない。

| 単位 | 確定の点 | 確定の前の失敗 | 確定の後の処理 |
| --- | --- | --- | --- |
| 静的の書き出し | 新しい世代を書き出し先の名前にする、名前の変更 | 前の世代が書き出し先に残る。終了コードは 0 でない | 退避した前の世代を消す。失敗したら警告を出し、次の書き出しで消す。終了コードは 0 |
| サーバーの中核の組み立て | 今の中核の入れ替え（生成日時は中核が持つ） | 前の中核を「古い」と示して使う。なければ 503 | なし |
| サーバーの起動 | 記録（`server.json`）の置き換え | 何も残さない。残っていた前の記録は、そのまま | 待ち受け |
| サーバーの終了と `stop` | 記録の削除 | 記録が残る。次の `serve` と `stop` が片付ける | なし |

- **静的の書き出し**: 生成の記録は、確定の前に書く（今は、公開と前の世代の削除のあとで書いている）。確定の前の手順は、走査、写し、中核、全ページの描画、世代のファイル、検査、記録の順である。
- **終了コードの意味**: 0 なら、書き出し先は新しい世代である。0 でなければ、書き出し先は前の世代である（入れ替えの途中で止まったときは、次の書き出しが前の世代を戻す）。
- **復旧**: 書き出し先と作業用のディレクトリの状態から、最後に確定した世代を決める。目印を読めない世代があるとき（分からない）は、どれも消さず、戻さずに止まる（P1）。今は、読めない目印を「候補でない」として、その世代を消す。
- **部分の失敗**: 関係表の全体と、1 ページの描画は、失敗してもその部分だけを「使えない」と示す。単位は失敗にしない。
  - 1 ページの描画に失敗したら、そのページの場所に「このページを描けない」と出す。静的の書き出しは、生成の記録と警告に載せて続ける。サーバーは、そのページの応答にだけ出す（開いたときに描くので、描くまで分からない）。
  - 描画は、中核を変えない。途中で失敗しても、同じ中核からもう一度描ける（今は、描く前に中核から字句を取り除くので、失敗のあとは描けない）。
- **要求の境界**: サーバーの 1 つの要求の全体を囲み、ヘッダーのそろった 500 を返す。ここに来るのは、不具合だけである。入出力の失敗は、上の単位か部分で受け止める。
- **コマンドの出口**: 思わない例外でも、種類だけの短い知らせと、0 でない終了コードで終わる。スタックトレースは、`--debug` を付けたときだけ出す。

## 7. 描く側は、絶対パスを持たない（P7）

- 写しを 2 つに分ける。**内容**は、入力ごとの種類、相対パス、文字（読まなければその理由）、世代である。`Path` と、機械の絶対パス（Wiki のルート、入力の実体、ホーム、`data_dir`）を持たない。**読み取りの情報**は、入力の印、読めなかった入力の有無である。
- `Core` は、内容だけを受け取る。今、中核が絶対パスに触れる 4 か所（スラッグと索引の題名をファイル名から取る 2 か所、グラフのページの `path` の欄、`raw:` の `~` の展開）のうち、前の 3 つは相対パスから作る。
- `raw:` が `~` で始まるときは、`link` の描き方でもリンクにせず、文字で出す。`C:/…` や `/…` のように書かれた絶対パスは、今までどおりリンクにする。
- `Recorder` と、利用者が書いたかの推定をなくす。
- **公開の前の検査**: 作った世代から、Wiki のルート、ホーム、`data_dir`、Wiki の外にある入力の実体の絶対パスを探す。見つかれば、ファイルの名前を挙げて警告を出す。書き出しは止めない。
- 内容に絶対パスが入るのは、利用者が入力（本文、題名、`raw:` など）に書いたときだけである。browse の持ち場のファイルは読まない（P4）ので、生成の記録を指すページから入ることもない。
- **作りの確かめ**: 入力のどこにも絶対パスを書いていない Wiki を、目印の文字を含むディレクトリに置く。内容と、組み立てたあとの `Core` の値をすべてたどり、目印の文字と `Path` がないことを確かめる。

## 8. 試験（P8）

### 8.1 参照の状態と比べる

確かめは、応答の番号ではなく、結果の全体を、2 つの参照の状態と比べる。

- **N（新しい状態）**: 今の入力で、何も失敗させずに得た結果。
- **P（前の状態）**: 入力を変える前に得た結果。

| 場面 | 許す結果 |
| --- | --- |
| サーバーへの要求 | 応答の全体が N と同じ。または、P と同じで「古い」の表示がある。前の中核がないときだけ、503 |
| 静的の書き出し | 終了コードが 0 で、書き出し先の木が N と同じ。または、0 でなく、書き出し先の木が P と同じ（次の書き出しで P に戻る場合を含む） |
| `serve` と `stop` | 記録とロックの状態が、確定の前か後かのどちらか。サーバーは 2 つ動かない。次の `serve` と `stop` は成功する |

- 「入力が欠けた新しい結果」は、N とも P とも違うので、失敗になる。
- **入力でない場所の失敗は、結果を変えない。** 入力でないパス（`raw/`、`assets/`、Wiki の外の関係のない場所）への呼び出しを失敗させたときは、結果が N と同じでなければならない。古い表示も 503 も許さない。
- どの場面でも、次を確かめる。
  - Wiki と、Wiki の外にある入力の実体について、ファイルの一覧、中身のハッシュ、属性が変わらない。
  - 層が記録した書き込みの対象が、すべて持ち場の中にある。
  - どの応答と出力にも、操作のトークンと、目印の文字（Wiki のルート、ホーム、`data_dir`、外の入力の場所）がない。

### 8.2 3 つの探索

層（2）の呼び出しの N 回目に手を入れ、N を 1 から、手を入れる機会がなくなるまで増やす。

| 探索 | N 回目にすること | 見つける種類 |
| --- | --- | --- |
| 失敗 | その呼び出しを「分からない」にする | 失敗を空として扱う。境界の外の失敗。確定の点の前後の取り違え |
| 変化 | その呼び出しの直前に、Wiki を変える（ページを編集する、消す、ページを状態のファイル、書き出し先のファイル、作業用のファイルへのリンクにする） | 守りが古い。変更に気づかない。持ち場のファイルを読む |
| 解釈 | 解釈の入口（Markdown の解析、YAML の読み取り、URL の解析、1 ページの描画）の N 回目を例外にする | 部分の失敗が全体を止める。描画の失敗のあとで描けない |

解釈の探索では、結果が N と、失敗させた部分（そのページ、または関係表）だけが違うことを確かめる。

### 8.3 初期の状態と、敵対的な入力

探索は、次の一覧のそれぞれに対して走らせる。一覧は、データとして持ち、足せるようにする。過去のレビューの反例は、すべてここに入れる。

- **初期の状態**: 書き出し先がない、空、前の世代がある。退避した世代が 1 つ、複数、目印が壊れている。書き出し先に利用者のファイルがある。世代の中に Wiki のページのハードリンクがあり、読み取り専用である。記録が残っている、壊れている。
- **Wiki の配置**: リンクのディレクトリ、ジャンクション、リンクの `indexes`、輪になったリンク、入力でない最上位のディレクトリ、Wiki の外を指すページ。
- **敵対的な入力**: 名前（区切りの文字を含む名前、予約名、識別子の衝突、接尾辞の重なり）、frontmatter（誤った日付、型の違う値、`node_types: []`）、`raw:`（`~`、`file:`、解釈できない URL）、本文（入れ子のリンク、配置つきの表、見出しの中のリンク）。

### 8.4 対照

8.1 の確かめのそれぞれに、対照を付ける。守ることをわざと破った実装（試験の中で差し替える）で同じ探索を走らせ、確かめが失敗することを確かめる。

| 確かめ | 対照 |
| --- | --- |
| 結果が N か P | 一覧の失敗を空として返す。入力が欠けた中核を採用させる |
| 入力でない場所の失敗は結果を変えない | 入力でないディレクトリも走査させる |
| Wiki と入力の実体が変わらない | 守りの確かめを素通りにする。消すときに属性を変える |
| 書き込みが持ち場の中 | 出力の名前を絶対パスにする |
| 終了コードと書き出し先が合う | 確定のあとの処理の失敗を、単位の失敗にする |
| トークンと目印の文字がない | 持ち場のファイルを読ませる。索引に Wiki のルートを書き足す |
| 2 方式の結果が一致（ブラウザ） | 片方の方式で被リンクを空にする |

### 8.5 過去の重大な指摘との対応

過去 7 回の重大な指摘 17 件が、どの道具で見つかるかを挙げる。実装の最初の段（10 の 1）で、0.10.0 より前の、それぞれの指摘を直す前のコードに対して道具を走らせ、実際に見つかることを確かめる。見つからない指摘があれば、道具が足りない。

| 指摘 | 道具 |
| --- | --- |
| 1-1 絶対の出力の名前で別の書き出しを上書き | 敵対的な入力（名前）と、書き込みが持ち場の中の確かめ |
| 1-2 消すときに属性を変える | 初期の状態（ハードリンク、読み取り専用）と、属性の比較 |
| 1-3 描かないページの未解決リンクが消える | 敵対的な入力（識別子の衝突）と、lint との一致 |
| 1-4 絶対パスの検査の誤り | 推定をなくす（7）。目印の文字の確かめ |
| 1-5 誤った形のオントロジーで全体が止まる | 敵対的な入力（frontmatter）と、解釈の探索 |
| 1-6 空の書き出し先で前の世代を消す | 初期の状態（空の書き出し先と退避した世代）と、N か P の確かめ |
| 2-1 `~` の `raw:` で書き出しが失敗 | 敵対的な入力（`raw:`） |
| 2-2 解釈できない URL で応答なし | 敵対的な入力（`raw:`）と、解釈の探索 |
| 2-3 重なりを見つけても終わらない | 変化の探索（状態のファイルへのリンク）と、トークンの確かめ |
| 3-1 終了の後片付けが古い守りで記録を消す | 変化の探索（終了と `stop` の各呼び出しの直前） |
| 3-2 YAML の誤った日付で全体が止まる | 敵対的な入力（frontmatter）と、解釈の探索 |
| 4-1 ロックを待つあいだに入力になった記録を消す | 変化の探索（起動の各呼び出しの直前。ロックを取る呼び出しを含む） |
| 4-2 入力の印の失敗が 500 | 失敗の探索 |
| 5-1 一覧の失敗で 0 ページの正常な Wiki になる | 失敗の探索と、N か P の確かめ |
| 6-1 属性を読めないと守りから外す | 失敗の探索と、書き込みが持ち場の中の確かめ |
| 6-2 リンクの `indexes` の更新に気づかない | Wiki の配置（リンクの `indexes`）と、変化の探索（編集） |
| 7-1 入力でないディレクトリの失敗で止まる | 入力でない場所の失敗は結果を変えない、の確かめ |

変化の探索は、1 つのスレッドの中で、呼び出しの直前に Wiki を変える。2 つのスレッドが本当に同時に動く競合（3-1 の元の形）は、同じ順序を 1 つのスレッドで作って確かめる。調べてから操作するまでの競合は、限界である（5）。

## 9. 振る舞いが変わる点

| 変わる点 | 今 | 直したあと |
| --- | --- | --- |
| browse の持ち場にある実体を指すページ | 読んで描く。状態のディレクトリと重なれば、サーバーが終わる | 読まずに、診断に挙げる。サーバーは動き続ける |
| `raw:` が `~` で始まる | `link` の描き方で、ホームを展開したリンクにする | 文字で出す |
| 出力に絶対パスがある | 生成器が入れたと推定したら、書き出しを失敗にする | 警告を出して続ける |
| 1 ページの描画の失敗 | 書き出しの全体が失敗する。サーバーは 500 | そのページに「描けない」と出して続ける |
| 公開したあとの片付けの失敗 | 0 でない終了コードになることがある | 警告を出し、終了コードは 0 |
| 目印を読めない世代があるときの復旧 | その世代を消す | 消さずに止まる |
| スタックトレース | 出る | `--debug` のときだけ出る |

今の試験のうち、これらを前提にしているものは、期待を書き換える（`~` の `raw:` がリンクになる、描画の例外が 500 になる、重なればサーバーが終わる、生成器のパスで書き出しが失敗する、の 4 種類）。

## 10. 順序

1. 入出力の層の形（2）と、試験の道具（8）を作る。0.10.0 に対して走らせ、違反を記録する。あわせて、過去の指摘を直す前のコードで、道具が指摘を見つけることを確かめる（8.5）。
2. 層に P1 を入れ、入力の走査（3）を 1 つにする。
3. 持ち場の入力を読まない（4）。守りを直す（5）。
4. 仕事の単位と確定の点（6）をそろえる。
5. 描く側を分ける（7）。
6. 1 で記録した違反が消えたことを確かめ、元の設計の該当の節を書き換える。

各段で、その段までに期待を書き換えた試験、2 方式のブラウザの試験、起動の速さ（1,000 ページで 5 秒以内）が通ることを確かめる。

## 11. 限界

- 調べてから操作するまでのあいだに、入力が変わる競合（5）。
- 走査の結果が lint の `rglob` と同じ集合になることは、wiki の走査の計画が入るまで、試験で確かめる（3）。
- 探索は、層の呼び出しの N 回目に 1 つだけ手を入れる。2 つの失敗が重なる場合は、探さない。
