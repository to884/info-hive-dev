## 背景

今のプラグインには、セッションの会話を取り込む手段がない。`/wiki:ingest` は文字起こしを `.md` か `.txt` のソースとして受け付けるが、Claude Code が残すセッションの記録は JSONL で、会話のほかに大量の記録を含む。

2026年11月14日に、検証環境の PC にある 1 つのプロジェクトの記録（61〜63 ファイル）の構造を調べた。会話の文は読み出していない。値は「検証環境の値」の節にまとめた。

- 記録の種類は 21 ある。`uuid` を持つのは `user`、`assistant`、`attachment`、`system` の 4 種類だけで、ほかの 17 種類（`custom-title`、`last-prompt`、`queue-operation` など）は持たない。会話のつながり（`parentUuid`）に入るのは、`uuid` を持つ記録だけである。
- 人の発言は、`origin.kind` が `human` の `user` の記録にある。ただし、Claude が作業している間に人が打った発言は、`attachment` の `queued_command` として届き、あとに `user` の記録として現れない（11 件を確かめた）。`queued_command` は 239 件あり、`origin.kind` は作業の通知 129、なし 73、ほかのセッションからの伝言 26、人 11 だった。
- `promptSource` は話者の判定に使えない。人の発言 632 件のうち 607 件が `sdk` だった（3 版目は、`sdk` を `claude -p` の印とみなしていたが、誤りだった）。
- `origin` のないファイル 7 件は、どれも `claude -p` のセッションだった。1 ファイルは、ファイル名の ID と最初の記録の `sessionId` が違い、2 つの ID の記録を含んでいた。
- `isMeta` の記録の `origin` は、なし 145、伝言 110、作業の通知 1 だった。スキルの本文の読み込みと、ほかのセッションからの伝言が、同じ `isMeta` で届く。
- アシスタントの記録は、内容のブロック 1 つにつき 1 件である。ブロックの種類は `tool_use` 13,602、`thinking` 7,900、`text` 3,486、`server_tool_use` 97、`advisor_tool_result` 84 だった。
- アシスタントの本文（`text`）の記録 3,491 件について、`parentUuid` をたどると、返答の宛先は、人 1,481、作業の通知 674、キューに入った入力 545、`isMeta` 334、`origin` のない記録 259、伝言 113、圧縮の要約 85 だった。たどれないものは 0 件だった。3 版目の規則（`attachment` を境界にしない）では、キューに入った入力への返答 545 件が、前のターンの返答に混ざる。
- `parentUuid` の枝分かれ 2,743 か所は、どれも並列のツールの呼び出しによるもので、巻き戻しは見つからなかった。
- 会話を圧縮しても、圧縮の前の記録は消えない。
- 記録には、利用者が意図せず残した情報（環境変数の一覧の出力に含まれたメールアドレスなど）が入る。セッションの題名やブランチの名前に、顧客の名前が入ることもある。
- 記録の形式は公開された仕様ではない。12 日間で 5 つの版（2.1.309〜2.1.321）が現れた。
- Claude Code 2.1.321 の本体のコードには、本文の `${CLAUDE_SESSION_ID}` をセッションの ID に置き換える箇所がある。プラグインのコマンドの本文がそこを通るかは、確かめていない。記録を残す日数の設定 `cleanupPeriodDays` があり、期間を過ぎた記録は消える。

wiki の書き込みについても調べた（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md)）。

- 取り込みの手順 5〜8 で、要約ページ、関連ページ、`index.md`、`log.md` を書くのはモデルで、Claude Code の Write と Edit のツールを使う。排他はない。ロックを持つのは、グラフの抽出（`.extract.lock`）と閲覧だけである。
- Claude Code の Write は、読んだあとに変わったファイルを書き直すのを拒む。Edit はディスクの今の内容に当たるので、先に足されたほかの行を消さない。しかし、Edit も中では「読む、直す、書く」で原子的ではない。10 ミリ秒ごとに書き換えるプロセスと並べると、Edit が成功と報告した行が消え、相手の 1,500 行のうち 7 行も消えた。どちらにも誤りは出なかった。
- lint は、索引に足りない項目と、ログの抜けを見つけない。

## 目的

- 1 回の `/wiki:ingest` で、Claude Code のセッションの会話を、raw の原本と、記事の形のソースの要約ページとして wiki に入れる。
- モデルの思考は、raw にも wiki にも入れない。
- 秘密の情報と個人の情報は、人の確認を経ずに、Git で管理される場所（raw のルート、wiki）に入らない。確認の前の会話の文は、ディスクに置かない。
- raw は、記録の範囲、引数、抽出器の版、人の決定から、スクリプトが決まった手順で作る。同じ入力からは、どの PC でも同じバイト列ができる（時差は引数として入力に含む）。記録の SHA-256 で出所を確かめられるのは、元の記録が残っている間だけで、記録が消えたあとは raw が唯一の原本になる（ADR-0004 と同じ割り切り）。
- 取り込んだあとの raw は変えない。
- 決まった処理（抜き出し、伏せ字、raw の生成、ハッシュ、raw の書き込み、伏せた文字列の検査）は、モデルを使わず Python で行う。モデルが行うのは、判断の要る処理（伏せる候補を探す、記事と関連ページの文を書く）だけである。
- 開発用の PC の置き場所や記録の形に、仕様を合わせない。記録の形が変わっても、漏れる側に倒れない。

## 前提にすること

- **Claude Code のツールを通らない書き手は考えない**（作者の判断の 6）。
- **wiki への書き込みは、既存の取り込みと同じ水準にとどめる。** 要約ページ、関連ページ、`index.md`、`log.md` は、手順 6〜7 のとおり、モデルが Claude Code の Write と Edit で書く。排他はない。Write は読んだあとに変わったファイルを拒み、Edit は今の内容に当たるので、ふだんの使い方では行は消えない。ただし、2 つの書き込みが数ミリ秒の中で重なると、行が黙って消えうる（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md)）。これは今の Web ページと PDF の取り込みと同じである。wiki 単位のロックを持つ書く段は、[分けた設計書](wiki-apply-2026-11-14.md)で決め、決まったら、セッションの取り込みもほかの取り込みと一緒にそちらへ移す。
- raw の書き込みだけは、この設計のスクリプトが、重ねて書かない形（排他作成）で行う。`write` は raw を上書きしない。モデルがあとで Write と Edit で書く wiki の場所が、リンク、ジャンクション、bind mount、UNC の共有などの別名で raw と重なることは、パスの検査では尽くせない（5 回目と 6 回目のレビュー）。そこで、パスで重なりを証明するのをやめ、raw のファイルそのものを守る。`write` は書いた raw を読み取り専用にし（9 節の手順 8）、S10 の `verify` が raw のバイト列を照らして、変わっていれば止める。Windows では、読み取り専用の raw への Write と Edit が失敗することを確かめた。POSIX では防げない見込みで、`verify` で見つけるだけになる（「保証しないこと」の 12）。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| wiki の書き込みの排他（ロック）と、差分のパッチによる書き込み | 4 回目のレビューの重大の指摘がすべてここに出た。[wiki の書く段の設計](wiki-apply-2026-11-14.md)に分けた（作者の判断の 7） |
| サブエージェントの記録 | 本体と別のファイルで、量が多い。見つけたファイルの数だけを報告する |
| デスクトップアプリの Export の zip | 中の構成を確かめていない。展開した JSONL のパスを渡せば使える |
| Claude Code 以外のエージェントの記録 | 形式が違う。`inspect` が認めずに止まる |
| `claude -p` のセッション | 人の発言が記録されない。終了コード 2 で止まる |
| ツールの結果の中身 | 雑音と秘密の情報の大半がここにある。ツールの呼び出しは 1 行の要約だけを残す |
| 日本語でないセッションの翻訳 | 需要が出たら決める |
| セッションの終わりにフックで自動で取り込むこと | 取り込みは、依頼されたソースだけを明示して行う |
| 取り込んだあとの raw の書き直し（`--force`） | ADR-0004 の不変性と食い違う。範囲や決定を変えたら、別版のスラッグにする |
| 意味の重複の検出 | 同じ概念を別のスラッグで作ること、同じセッションを別のスラッグで 2 回取り込むことは防がない |

## 決めること

### 1. 入口

- 引数は `session`（実行中のセッション）、`session:<ID>`、`session:<パス>`、`<パス>.jsonl` である。引数が既存のファイルのパスなら、キーワードより先にファイルとして扱う。
- 新しいコマンドは足さず、`/wiki:ingest` の引数で受け付ける（ADR-0015）。
- `.jsonl` は、キーワードの有無によらず `inspect` にかける。`verdict` が `session` でなければ止まる。ふつうの取り込みに進むのは、ユーザーが明示して頼んだときだけである。
- `verdict` が `session` になる条件は、範囲の中に「人の発言」（4 節の区分 H）が 1 件以上あり、読めた行がどれも JSON のオブジェクトで、`uuid` のある記録が `type` を持つことである。読めない行（3 節）は、判定から外して数える。`promptSource` は見ない。
- 実行中のセッションの ID は、`commands/ingest.md` の本文に `${CLAUDE_SESSION_ID}` と書いて得る。置き換わらなければ、ユーザーに ID かパスを聞く。

### 2. 記録の場所と ID

- ID からパスへの変換は `locate` だけが行う。ほかのコマンドは、すべて `--transcript <パス>` を取り、`--session-id` は任意である（3 回目の軽微 2）。
- `locate` は、`<設定のディレクトリ>/projects/*/<ID>.jsonl` を 1 階層だけ探す。設定のディレクトリは `CLAUDE_CONFIG_DIR`、なければ `~/.claude` である。ID は小文字の UUID でなければ拒む。設定のディレクトリより下のシンボリックリンクとジャンクション（`projects`、その下のディレクトリ、ファイル）はたどらない。0 件か 2 件以上ならエラーにする。プロジェクトのディレクトリの名前は組み立てない。
- `session_id` は、ファイル名（拡張子を除く）が UUID ならそれ、範囲の中の `sessionId` が 1 種類ならそれ、どちらでもなければ `--session-id` を求めて止まる。`--session-id` を渡したら、記録のどこかの `sessionId` にあることを確かめる。決めた ID と違う `sessionId` の記録があれば、`mixed_session_ids` の警告を出す（記録は残す）。

### 3. 範囲

- 範囲は、ファイルの先頭から、`--before <uuid>`（記録そのものの `uuid` キーが最初に一致した記録の、行の先頭）まで、または最後の改行までである。改行で終わらない最後の行は読まない。
- `source_sha256` と `source_bytes` は、範囲のバイト列から取る。ファイルの大きさの上限は既定で 256 MiB とする。
- UTF-8 か JSON として読めない行は飛ばし、`broken_lines` に数えて警告する。読めない行が、返答の宛先をたどる途中にあれば、宛先は「不明」になる（4 節）。

### 4. 分類と返答の宛先

**`uuid` のない記録は、読み飛ばす**（作者の判断の 1）。種類ごとに `ignored` に数える。観測した 17 種類（`custom-title`、`last-prompt`、`queue-operation`、`file-history-snapshot`、`api-request` など。スクリプトの定数にする）にない種類が `uuid` なしで現れたら、読み飛ばしたうえで `unknown_uuidless_type` の警告を出す。会話の入力が `uuid` のない新しい形で届くと、境界と印が失われる。これは限界として認める（「保証しないこと」の 3）。

`uuid` のある記録は、次の表で分ける。表にないものは、すべて境界 X である。

| 区分 | 条件 |
| --- | --- |
| 人の発言 H | `user` で、`origin.kind` が `human`、かつ `isMeta`、`isCompactSummary`、`isSidechain` のどれも真でない。または、`attachment.type` が `queued_command` で、`attachment.origin.kind` が `human`、かつ `prompt` が文字列 |
| 中断 I | `user` で `origin` がなく、本文が `[Request interrupted by user]` か `[Request interrupted by user for tool use]` と完全に一致する |
| アシスタント A | `assistant` で、`isSidechain` と `isApiErrorMessage` が真でない |
| 透過 T | 本文が `tool_result` のブロックだけの `user`。`attachment` のうち、観測した文脈の差し込みの種類の一覧（スクリプトの定数）にあり、`queued_command` でなく、`origin` を持たないもの。`system` のうち、`subtype` が `stop_hook_summary`、`informational`、`api_error` のもの |
| 境界 X | それ以外のすべて。`origin.kind` が `human` でない `user`、`isMeta`、`isCompactSummary`、知らない `type`、一覧にない `attachment`、`human` でない `queued_command`、`prompt` が文字列でない `queued_command`、`system` の `compact_boundary` と `local_command` と知らない `subtype` を含む |

- **アシスタントのブロック。** `text` は残す。`tool_use` と `server_tool_use` は 1 行の要約にする（5 節）。ほかのブロック（`thinking`、`redacted_thinking`、`advisor_tool_result`、知らない種類）は除く。
- **返答の宛先。** 本文を持つ A の記録ごとに、`parentUuid` をたどる。たどる途中で通ってよいのは、A と T の記録である。H、I、X のどれかに着いたら、それが宛先である。親が範囲にないか、範囲の中の読めない行に当たったら、宛先は「不明」である。たどった回数が範囲の記録の数を超えたら、循環とみなして「不明」にし、`reply_unresolved` の警告を出す（4 体のレビューで D と C が指摘した、A の区分を通れない規則の欠落を直した）。
- **ターン。** H と I は、つねにターンになる。宛先が X か「不明」の A があれば、その宛先の位置に印のターンを 1 つ置く（宛先として参照されない X には印を置かない）。続く A の本文は、宛先が同じ間だけ 1 つのターンにまとめる。
- **印の文。** 宛先の区分ごとに、スクリプトが決めた文だけを使う。例は「（バックグラウンドの作業の通知。内容は除いた）」「（ほかのセッションからの伝言。内容は除いた）」「（スキルの本文などの差し込み。内容は除いた）」「（人の発言でない記録。内容は除いた）」「（返答の対象の記録が範囲にないか、読めない）」。

### 5. 本文の加工と、ツールの要約

人の発言の本文は、次の順に加工する。

1. 本文の先頭に続く `<system-reminder>`〜`</system-reminder>` の塊を除き、`stripped_reminder` の警告を出す。`--keep-reminders` で除かない。
2. 本文が `<command-name>`、`<command-message>`、`<command-args>` の要素と空白だけなら、「コマンド: `/<名前> <引数>`」の 1 行にする。
3. 本文の全体が既知のアプリの要素 1 つ（今は `<create-pr-command>` だけ）なら、中身を除いた 1 行にする。
4. ほかはそのまま残す。本文が `<` で始まれば、`leading_tag` の警告を出す。
5. 画像のブロックは「［画像］」の 1 行にする。`text` と `image` のほかのブロックは除き、`user:block:<種類>` に数える。
6. 空になった発言は、「（人の発言。内容は除いた）」の印のターンにする。

1〜3 は本文の形で意味を決める規則で、人が同じ形の文を資料として書いたときと見分けられない。限界として認める（「保証しないこと」の 4）。

ツールの呼び出しは、ツールごとに決めた入力の項目を 1 つだけ使い、`[ツール] <名前> <値>` の 1 行にする（`Read`、`Edit`、`Write`、`NotebookEdit` は `file_path`、`Grep` と `Glob` は `pattern`、`Bash` と `PowerShell` は `description`、`WebFetch` は `url`、`WebSearch` は `query`、`Agent` は `description`、`Skill` は `skill`、ほかは名前だけ）。値は改行を空白に変え、120 文字で切る。`--tools none` で残さない。

### 6. 自動の伏せ字

残す本文、ツールの要約、`cwd`、`git_branch` に、次の規則で伏せ字をかける。規則は記録と引数だけで決まり、実行する PC の値は使わない。

| 種類 | 規則 | 置き換え |
| --- | --- | --- |
| メールアドレス | `ローカル部@ドメイン` の形 | `［メール］` |
| ホームのディレクトリ | `<ドライブ>:` のあとに 1 つ以上の `\` か `/`、`Users`、区切り、名前（大文字と小文字を区別しない）。`/Users/<名前>`、`/home/<名前>` | `~` |
| 秘密の値 | 既知の接頭辞の値（`sk-`、`ghp_`、`gho_`、`github_pat_`、`xoxb-` など、`AKIA` で始まる 20 文字、`eyJ` で始まる 3 つに分かれた JWT）、`-----BEGIN … PRIVATE KEY-----` の塊、`token`、`secret`、`password`、`api_key` などの名前に続く `=` や `:` の値 | `［伏せ字］` |

これを当てた結果を「土台」と呼び、その SHA-256 を `base_sha256` とする。

### 7. raw の形

- 文法は 3 版目と同じである。frontmatter、空の行、ターンの並び。各ターンは、見出しの行、空の行、本文（フェンスか印の文）、空の行である。LF だけで改行し、最後は 1 つの LF で終わる。UTF-8 で書く。
- 見出しは `## T<n> ユーザー（<時刻>）`、`## T<n> Claude（<モデル>、<時刻>、T<m> への返答）`、`## T<n> 印（<時刻>）` のどれかである。宛先が「不明」なら `不明への返答` と書く。
- フェンスは、本文の中の最も長いバッククォートの並びより 1 つ長くし、3 以上にする。情報の文字列は `text` である。
- フェンスの外に置くのは、スクリプトが決めた語、整形した時刻、ターンの番号、形を検査したモデルの名前（英数字と `._:-[]` だけの 64 文字以内。外れたら `不明`）だけである。題名の見出しは置かない。
- 確認で消したターンは、見出しを残し、本文を「（確認で消した）」の印の文にする。番号と「T<m> への返答」を保つためである。
- frontmatter は平らなキーで、値は文字列か数である。`title`、`source_kind`（`"claude-code-session"`）、`session_id`、`cwd`、`git_branch`、`started_at`、`ended_at`、`claude_code_versions`、`source_sha256`、`source_sha256_of`（`"jsonl-range"`）、`source_bytes`、`cut_before`、`extracted_by`、`tools`、`keep_reminders`、`utc_offset`、`turns`、`excluded_records`（`"種類=数, …"`）、`auto_redactions`、`manual_redactions`、`dropped_turns` をこの順に書く。**実行の時刻は書かない**（3 回目の軽微 3）。
- 時刻は `--utc-offset`（既定は `+00:00`）で直す。`/wiki:ingest` は、ユーザーの時差を渡す。時差を変えると別のバイト列になり、別の取り込みになる。
- 書く前に、スクリプトは自分の出力から frontmatter を分け（`wiki_text.parse_frontmatter_text()`。lint の `collect_pages()` と同じ分け方）、本文だけを同梱のパーサー（`wiki_pages.new_parser()`）で読み、2 段目の見出しがターンと 1 対 1 に対応し、フェンスが、本文を持つターン（印のターンを除く）と 1 対 1 に対応し、印のターンの本文が 1 つの段落であることを確かめる。通らなければ書かない。

### 8. 確認と決定

- **`show`** は、土台に決定を当てた、raw と同じバイト列を、ターンの範囲（`--turns T1-T20`）を指定して標準出力に出す。ファイルは書かない。1 回に出す量は `--max-chars`（既定 20,000 文字）までで、超えるときは、続きを出す `--from <ターン>:<文字の位置>` を標準エラーに出す（`--json` なら `next` のキー）。標準出力には raw のバイト列だけを出し、続きの案内を混ぜない。1 つのターンが長いとき（検証環境では 138,780 文字の本文があった）も、文字の位置で分けて出す。ホストのツールが長い出力をファイルに退避することがあるので、1 回の出力を小さく保つ（「保証しないこと」の 5）。モデルは全体を分けて読み、伏せる候補をユーザーに示す。何を伏せるかはユーザーが決める。
- **決定のファイル**は `<WIKI_ROOT>/.wiki-cache/session/<乱数>.json` で、`decide init` が作る。中身は `format`、`extracted_by`、`session_id`、`source_sha256`、`source_bytes`、`cut_before`、`options`、`base_sha256`、`spans`（ターンの番号か `cwd` か `git_branch` と、その中の開始と終わりの位置）、`drop`（消すターンの番号）である。**伏せる文字列そのものは書かない。** 位置だけなので、このファイルがコミットされても秘密は漏れない。**名前にはスラッグを入れない（実装の 4 回目のレビューのあとの変更。承認（2026年11月14日、作者））。** 名前にスラッグを入れると、秘密を含むスラッグや、あとで `mark` する顧客の名前を含むスラッグが、伏せる前にディスクのパスに残る（[impl-review-4.md](../agent-runs/2026-11-14-wiki-session-ingest/impl-review-4.md) の重大 3）。置いてある決定のファイルがどの取り込みのものかは、名前ではなく中身（`session_id`、`source_sha256`、`cut_before`）で見分ける。`decide init` も、書く前にスラッグを題名と同じ規則で確かめる。
- **`decide mark --target <T5|cwd|git_branch> --text <文字列> (--nth <k> | --all) [--all-turns]`** は、土台の中の完全一致を探して位置に変え、`spans` に足す。一致がなければ拒む。`--nth` も `--all` もなく 2 か所以上に一致すれば、曖昧なので拒む。
- **`decide drop --turn <T9>`** は、消すターンを足す。
- **`show --meta`** は、`base_sha256`、`render_sha256`（raw の全体のバイト列の SHA-256）、文字数、ターン数、`manual_redactions`（重なりをまとめた区間の数）、`dropped_turns`、残った警告を出す。モデルはこれを示し、ユーザーの承認を得る（S5）。
- 題名とスラッグに、伏せた区間の文字列か、自動の伏せ字の規則に当たる文字列が入っていれば、`show --meta` と `write` のどちらも拒む。題名は 1 行で、制御文字と書式の文字を含まず、前後に空白がなく、120 文字以内でなければならない。スラッグは `wiki_fetch.check_slug()` で検査する。
- 確認の前の文は、標準出力と、いま動いているセッションの記録（`~/.claude` の下）にしか現れない。`decide mark --text` に渡した文字列も、いま動いているセッションの記録に残る（「保証しないこと」の 5）。

### 9. raw を書く（`write`）

`write` は、`show` と同じ引数に `--wiki <W> --raw-root <R> --slug <S> --decisions <F> --expect-sha256 <render_sha256>` を足して呼ぶ。1 つのプロセスで次を行う。

1. wiki が初期化されていることを `wiki_initialized` で確かめる。raw のルートがなければ、作らずに止まる（ADR-0019）。スラッグを `wiki_fetch.check_slug()` で確かめる。
2. 記録の範囲を読み直し、`source_sha256` と `base_sha256` が決定のファイルの値と一致することを確かめる。
3. raw のバイト列を作り、`--expect-sha256` と一致することを確かめる。題名とスラッグを 8 節の規則で確かめる。
4. 行き先を確かめる。
   - raw のルートの直下で、raw のルートとその途中の階層がシンボリックリンクでもジャンクションでもない（`wiki_rawcheck.py` が作業用のフォルダーに使っているものと同じ検査）。`<R>/<S>.md` がすでにあれば、それ自体もリンクでなく、ふつうのファイルである。そうでなければ、終了コード 1 にする。
   - よくある誤った配置を、先に断る。raw のルートと wiki のルートの実体のパス（`os.path.realpath()`）が、一方が他方の中にあれば、終了コード 1 にする（raw のルートを `W/sources` にすると、S9 で書く要約ページが raw と同じファイルになる。5 回目のレビューの重大 1）。これは利用者の設定の誤りを早く知らせるための検査で、別名による重なりをすべて見つけるものではない。守るのは手順 8 と S10 の `verify` である。
5. `<R>/<S>.md` があれば、バイト列を比べる。同じなら `identical` で終了コード 0、違えば `conflict` で終了コード 3 にする。raw がなく `<W>/sources/<S>.md` があれば、`slug_taken` で終了コード 3 にする。
6. raw のルートに `.wiki-session-<乱数>.tmp` を書き、fsync する。重ねて書かない形で置く。POSIX では `os.link` のあとに一時ファイルを消す。Windows では `os.rename`（行き先があれば `FileExistsError`）を使う。`FileExistsError` なら 5 に戻る。リンクも名前の変更も重ねて書かない形でできないファイルシステムでは、書かずに終了コード 1 にする。途中で止まったら、一時ファイルを消す。
7. 書いたファイルを読み直し、バイト列が一致することを確かめる。`raw_ref`（raw のファイルの、wiki の親からの相対パス。親の下になければ絶対パス。どちらも `/` 区切り）を作り、`missing_raw()` に `sources/<S>.md` のページとして渡して、見つかることを確かめる。
8. 書いたファイルを読み取り専用にする。今のモードから書き込みの権限をすべて外す（`os.chmod(path, mode & ~0o222)`。Windows では、書き込みの権限を外すと読み取り専用の属性が付く。POSIX では、読み取りの権限は今のまま残る）。`identical` のときも、読み取り専用でなければ読み取り専用にする。Windows では、読み取り専用のファイルへの Claude Code の Write と Edit は、リンクやジャンクションを経由しても `EPERM` で失敗し、中身も一時ファイルも残らなかった（2026年11月14日、Claude Code 2.1.321 で確かめた）。Claude Code のツールは一時ファイルに書いてから名前を変えるので、POSIX では、ディレクトリに書ければ読み取り専用のファイルも置き換わる見込みである（確かめていない）。

**同じ取り込み**とは、作った raw のバイト列が、`<R>/<S>.md` のバイト列と一致することである。出力を変える入力（範囲、ID、引数、抽出器の版、決定、題名、時差）は、自動的に同一性に含まれる。2 つのセッションが同じスラッグに同時に書けば、先に置いた側が勝ち、負けた側は `identical` か `conflict` になる。

### 10. wiki の変更の確認（`scan` と、中身を見せる手順）

wiki への書き込みは、既存の手順 6〜7 のとおりモデルが行う。その前に、次の 2 つを行う（作者の判断の 2 の軽い形）。

**機械の検査（`scan`）。** `wiki_session.py scan --transcript <P> [共通の引数] --decisions <F> [--allow <文字列>]` は、標準入力から、wiki に書く予定の文（新しいページの全文、直す箇所の新しい文、索引とログの行、新しいファイルのパス）を受け取り、次の 2 つを探す。

- **伏せた文字列。** 決定で伏せた区間の元の文字列と、自動の伏せ字が置き換えた元の文字列（メールアドレスの全体とローカル部、秘密の値、ホームのディレクトリの名前の部分）を、記録と決定からメモリの中で作る。ディスクにもコマンドの引数にも出さない。比べるときは、両方を NFKC で正規化し、大文字と小文字をそろえる。自動の伏せ字から作る文字列のうち、正規化して 4 文字より短いもの（短いメールのローカル部、短い名前）は、ありふれた文字列に当たるので使わず、`skipped_short` に数だけを出す（4 回目のレビューの重大 5）。決定で人が伏せた区間は、短くても使う。
- **自動の伏せ字の規則に当たる文字列。** 6 節の規則である。

見つかったら、何行目の何文字目かと、規則の名前（`manual`、`auto_email`、`auto_secret`、`auto_home`、`pattern_*`）だけを出す。文字列は出さない。終了コード 1 にする。`--allow` で渡した文字列（`write` が出した `raw_ref` など、人が承認した値）は、その文字列の全体と一致する部分だけを除く。

**書いたあとのファイルの全体を照らす（実装の 2 回目のレビューのあとの変更。承認（2026年11月14日、作者））。** 直す箇所の新しい文だけを照らすと、新しい断片と既存の文がつながって、伏せた文字列が戻る（`顧客Bについて。` の `B` を `A` に直すと `顧客A` になる。[impl-review-2.md](../agent-runs/2026-11-14-wiki-session-ingest/impl-review-2.md) の重大 2、[原因の構造](../agent-runs/2026-11-14-wiki-session-ingest/impl-root-causes.md)）。そこで、S8 では直す箇所の新しい文ではなく、直したあとのページの全文を `scan` に渡す。wiki への書き込みをすべて終えたあと（S10。S9 の書き込み、ログのサブ行、手順 7 のエッジのあと）に、`scan --path <書いたファイル>…` で、ディスクにある書いたあとのファイルの全体をもう一度照らす（実装の 3 回目のレビューの軽微の指摘で、S9 の直後から、最後の書き込みのあとに移した）。見つかったら、そのファイルを直してユーザーに伝える。書いたあとの照合は、承認した中身と書いた中身の食い違い（保証しないことの 7）も、書いた結果の上で見つける。

`scan` は助言の検査であり、wiki への書き込みを止める仕組みではない。見つかったら、モデルはその場所を直して `scan` をやり直す。正しい文が当たったとき（誤検出）は、場所と規則の名前をユーザーに示し、ユーザーが書いてよいと言ったときだけ書く。`scan` を流さずに書くことは、手順の遵守に頼る（「保証しないこと」の 1）。

**中身を見せる。** `scan` を通ったら、モデルは、新しいページの全文、直す箇所ごとの前と後、索引とログに足す行を、まとめてユーザーに見せ、承認を得る。承認された中身だけを、Write と Edit で書く。書いたあとで、モデルは書いたページを読み直し、承認した中身と食い違っていれば、ユーザーに伝える。

`scan` に渡す文は、伏せる前の会話の文ではなく、確認を終えた raw から書いた文なので、いま動いているセッションの記録に残っても、確認の前の文がディスクに出たことにはならない。ただし、モデルが伏せた文字列を書き戻していれば、その文はセッションの記録に残る（「保証しないこと」の 5）。

### 11. 途中で止まったとき、取り込み直すとき

- raw は上書きしない。`--force` はない。範囲や決定を変えたら、別版のスラッグ（`<スラッグ>-<YYYYMMDD>`）にする。
- **取り込みが済んだかは、スクリプトは判定しない。** `inspect --wiki <W> --raw-root <R> --slug <S>` は、raw の有無と、raw の frontmatter の `session_id`、`source_sha256`、`cut_before`、要約ページの有無、残っている一時ファイル（`.wiki-session-*.tmp`）を、情報として出す。そこから先は、Web ページの W2 と同じく、モデルが wiki を見てユーザーに聞く。
- `write` の前に止まったら、raw はない。決定のファイルが残っていれば、`base_sha256` が今の土台と一致する限り、続きから使える。一致しなければ拒む。
- `write` のあとに止まったら、raw がある。もう一度 `write` を流すと `identical` になり、S7 から続けられる。

### 12. スクリプト

`skills/info-hive/scripts/wiki_session.py` を足す。Python 3.12 以上で、標準ライブラリと、同梱の markdown-it-py（自己検査だけ）を使う。raw の生成は、純粋な関数 `render()` にする。

```text
python wiki_session.py locate  --session-id <ID> [--json]
python wiki_session.py list    [--limit 20] [--json]
python wiki_session.py inspect --transcript <P> [--session-id <ID>] [--before <uuid>] [--wiki W --raw-root R --slug S] [--json]
python wiki_session.py show    --transcript <P> [共通の引数] --title <T> [--decisions <F>] [--turns T1-T20]
                               [--from <ターン>:<文字の位置>] [--max-chars 20000] [--meta] [--json]
python wiki_session.py decide  init|mark|drop|list --decisions <F> ...
python wiki_session.py write   --transcript <P> [共通の引数] --title <T> --decisions <F>
                               --wiki <W> --raw-root <R> --slug <S> --expect-sha256 <render_sha256> [--json]
python wiki_session.py verify  --raw-root <R> --slug <S> --expect-sha256 <render_sha256> [--json]
python wiki_session.py scan    --transcript <P> [共通の引数] --decisions <F> [--allow <文字列> …] [--path <書いたファイル> …] [--json]  < 書く予定の文
```

共通の引数は `[--session-id <ID>] [--before <uuid>] [--tools summary|none] [--keep-reminders] [--utc-offset +09:00]` である。

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功（`write` の `identical` を含む） |
| 1 | 引数かファイルの誤り（ハッシュの不一致、曖昧な `mark`、行き先の検査、排他作成ができないファイルシステム、`scan` で見つかったことを含む） |
| 2 | セッションとして認めない（人の発言が 0 件を含む） |
| 3 | `conflict` か `slug_taken` |

- `inspect` の出力のキー: `verdict`、`reason`、`session_id`、`range`（`before`、`source_sha256`、`source_bytes`）、`human_tail`（最後の 5 件の人の発言の `uuid`、時刻、伏せ字をかけた先頭 40 文字）、`title_candidate`、`turns`、`excluded`、`ignored`、`redactions`、`warnings`、`broken_lines`、`subagent_files`、`raw`（`exists`、`session_id`、`source_sha256`、`cut_before`）、`source_page_exists`、`temp_files`。
- 警告の `code`: `stripped_reminder`、`leading_tag`、`broken_lines`、`unknown_uuidless_type`、`reply_unresolved`、`mixed_session_ids`、`possible_rewind`。
- `show --meta` の出力のキー: `base_sha256`、`render_sha256`、`chars`、`turns`、`manual_redactions`、`dropped_turns`、`warnings`。
- `write` の出力のキー: `raw_state`（`created`、`identical`、`conflict`、`slug_taken`）、`raw_path`、`raw_ref`、`render_sha256`。
- `scan` の出力のキー: `findings`（`line`、`column`、`rule`。`--path` のときは `path` も）、`skipped_short`。`column` は、正規化で切れない塊の先頭の位置。
- `decide list` の出力のキー: `session_id`、`source_sha256`、`cut_before`、`spans`、`drop`。
- `verify` の出力のキー: `raw_path`、`sha256_matches`、`read_only`。
- `show` の出力のキー（`--json`）: `text`、`next`（続きの `--from` の値。なければ `null`）。

### 13. `commands/ingest.md` に足す手順

手順 2 に、ソースが `session`、`session:…`、`.jsonl` なら S1〜S10 に進む、と足す。

- **S1.** 記録のパスを決める。実行中のセッションなら、`${CLAUDE_SESSION_ID}` を `locate` に渡す。置き換わらなければ、ユーザーに聞く。`inspect` を実行し、`verdict` が `session` でなければ止まる。実行中のセッションなら、`human_tail` から取り込みの依頼の `uuid` を確かめて `--before` にする。
- **S2.** 題名とスラッグをユーザーと決める。`inspect --wiki --raw-root --slug` で、raw と要約ページと一時ファイルの有無を見る。あれば、11 節に従ってユーザーに聞く。
- **S3.** `decide init` を実行し、`show --turns` で全体を分けて読む。
- **S4.** 伏せる候補とターンを示し、ユーザーが決めたものを `decide mark` と `decide drop` に入れる。顧客の名前のように、記事に書き戻されては困る文字列は、ターンを消すだけでなく `mark` でも伏せる（`scan` が守るのは `mark` した文字列だけである）。
- **S5.** `show --meta` の件数、警告、`render_sha256` を示し、承認を得る。
- **S6.** `write` を実行する。終了コード 3 なら、別版のスラッグにするかをユーザーに聞く。
- **S7.** 手順 4（要点の話し合い）と手順 5（関係するページを洗い出す）を行う。要約ページの全文、関連ページの直し、`## 主張と行き先` の表（手順 6 と `ingest-workflow.md` の 7b）、索引とログの行、手順 7 の型付きのエッジを、会話の中で用意する。まだファイルに書かない。要約ページの `raw` には `write` が出した `raw_ref` を、`session_id` にはセッションの ID を書く。根拠の位置はターンの番号で書く。ログのサブ行には `manual_redactions` と `dropped_turns` を書く。伏せると決めた文字列を書かない。
- **S8.** 用意した文の全部を `scan` に渡す（`--allow` には `raw_ref` を渡す）。見つかったら直して、やり直す。通ったら、中身をユーザーに見せて承認を得る。
- **S8 の変更（承認（2026年11月14日、作者））。** 直す箇所の新しい文ではなく、直したあとのページの全文を渡す（10 節）。
- **S9.** 承認された中身だけを、手順 6 のとおり Write と Edit で書く。**変更（承認（2026年11月14日、作者））:** wiki への書き込みをすべて終えたあと（S10 の `verify` の前）に `scan --path` で書いたファイルの全体を照らし、見つかったら直してユーザーに伝える（10 節）。
- **S10.** 手順 7（グラフの lint と抽出、ログのグラフのサブ行）を行う。wiki への書き込み（S9、ログのサブ行、手順 7 のエッジ）をすべて終えたら、書いたファイルのすべてを `scan --path` で照らす（10 節。グラフのエッジは、ソースの引用を含みうる）。wiki への書き込みを終えたら、`verify --raw-root <R> --slug <S> --expect-sha256 <render_sha256>` を実行する。raw のバイト列が変わっていたり、読み取り専用でなくなっていたりしたら、終了コード 1 になる。そのときは、wiki の書き込みが別名を経由して raw を書き換えた見込みが高いので、手順 8 で必ずユーザーに伝える。raw は記録と決定から作り直せる（`show` の出力が同じバイト列になる）ので、戻し方をユーザーと決める。手順 8（報告）を行い、決定のファイルを消す。

## 保証しないこと

1. **人が実際に読んで決めたこと。** モデルが `show` の中身や wiki の変更をユーザーに示さずに進めること、`scan` を流さずに書くことは、機械では止められない。手順の遵守に頼る。
2. **規則と人の両方が見落とした個人の情報。** `mark` は完全一致で探す。`scan` は、伏せた文字列そのものを、NFKC と大文字と小文字をそろえた一致で探すだけで、言い換え、ローマ字、略称は見つけない。自動の伏せ字から作る 4 文字より短い文字列は探さない。`drop` で消しただけのターンの中の名前は探さない（S4）。
3. **`uuid` のない新しい形で届く入力。** 読み飛ばすので、内容は漏れないが、境界と印が失われ、前後の返答が 1 つのターンにつながる。知らない種類なら `unknown_uuidless_type` の警告で気づける（作者の判断の 1）。
4. **本文の形で決める規則。** 先頭の `<system-reminder>`、コマンドの要素、`<create-pr-command>` を、人が同じ形で書いたときと見分けられない。警告と引数で戻せるのは `<system-reminder>` だけである。
5. **いま動いているセッションの記録。** `show` の出力、`decide mark --text` の文字列、伏せる候補の相談、`scan` に渡した文は、いま動いているセッションの記録（`~/.claude` の下）に残る。ホストのツールが長い出力をファイルに退避するとき（Claude Code は、設定のディレクトリの下のセッションごとの `tool-results` に置く。このセッションでも起きた）も、同じ場所に残る。`show` は 1 回の出力を `--max-chars` までにして退避を起こしにくくするが、なくしはしない。設定のディレクトリが Git の作業ツリーの中にある配置では、そこから漏れうる。あとでその範囲を取り込むときは、もう一度、伏せ字と確認を通る。
6. **wiki の書き込みの競合。** 要約ページ、関連ページ、索引、ログは、既存の取り込みと同じく排他なしで書く。2 つの書き込みが数ミリ秒の中で重なると、行が黙って消えうる。lint はそれを見つけない。[書く段の設計](wiki-apply-2026-11-14.md)で扱う。raw は排他作成で守る。
7. **承認した中身と書いた中身の一致。** モデルが Edit と Write で書くので、承認した中身と書いた中身が同じであることは、機械では縛らない。モデルが書いたあとに読み直して確かめる。S10 の `scan --path` は、書いたあとのファイルの全体を照らすので、伏せた文字列が書いた結果に入ったことは見つける。ただし、これは書いたあとの照合なので、見つかったときには、その文字列はすでに wiki の作業ツリーのファイルに入っている。コミットの前に直す（Git の履歴に入ったあとは、10 のとおり人が直す）。
8. **取り込みの手順の完了。** 手順 7 と手順 8 が済んだかは、人の判断に頼る。
9. **意味の重複。** 同じ概念を別のスラッグで作ることと、同じセッションを別のスラッグで 2 回取り込むことは防がない。
10. **書いたあとに見つかった秘密。** 人が raw と要約ページを消し、Git の履歴も直す。プラグインは自動では直さない。
11. **一時ファイルの残り。** 電源が切れたときなど、確認済みの文の一時ファイルが raw のルートに残りうる。`inspect` が見つけて報告する。
12. **wiki の書き込みが別名を経由して raw に届くこと。** wiki の中のリンク、ジャンクション、bind mount、UNC の共有などの別名で、S9 の書く先が raw と同じファイルになる配置は、パスの検査では尽くせないので、`write` は見分けない（よくある誤り、つまり 2 つのルートの実体のパスの包含だけを断る）。Windows では、raw を読み取り専用にしたので、Claude Code の Write と Edit は raw を書き換えられない。POSIX では、Write と Edit が名前の変更で読み取り専用のファイルを置き換えうるので、防げない見込みである。その場合も、**今回の取り込みの raw** が変われば、S10 の `verify` が見つける。見つけるのは書いたあとで、そのときには raw のファイルはすでに変わっている。**`verify` が見るのは今回の raw 1 つだけである。** 別名を経由して、過去に取り込んだ別の raw が書き換えられても、`verify` は気づかない（7 回目のレビューの重大 1）。これは今の Web ページと PDF の取り込みにもある穴で、[書く段の設計](wiki-apply-2026-11-14.md)で、書く先ごとの実体の検査として扱う。
13. **raw のルートの置き場所と、ほかの道具による削除。** `write` は、raw のルートが何のためのディレクトリかを見分けない。raw のルートを、MCP の索引のディレクトリ（`<INFO_HIVE_DATA_DIR>/index/...`）や `.wiki-cache` のように、ほかの道具が中身を消すディレクトリにすると、その道具が raw を消しうる（7 回目のレビューの重大 2。POSIX では、親のディレクトリに書ければ、読み取り専用のファイルも消せる）。raw のルートの置き場所を守ることは、Web ページの raw にも共通する raw の置き場所の全体の問題で、この設計では扱わない。`/wiki:init` が作る `raw/` か、作業領域の設定（ADR-0008）の raw のディレクトリを使う前提である。

## 試験

`tests/wiki/` に置く。記録は、手で作った JSONL と、合成の記録を作る生成器を使う。実物の記録は入れない。

- **抜き出しの性質。** 生成器で、知らない `type`、`uuid` のない知らない種類、一覧にない `attachment`、`queued_command`（人、通知、`prompt` が文字列でないもの）、`isMeta` の伝言、壊れた行、親がアシスタントの連鎖、循環する `parentUuid`、思考に入れた目印、秘密の目印を混ぜる。確かめるのは、(1) 思考の目印がどこにも出ない、(2) 各ターンの「T<m> への返答」が、素朴に書いた参照の実装で求めた宛先と一致する、(3) frontmatter を除いた本文で、2 段目の見出しがターンと、フェンスが本文のあるターンと 1 対 1 になる、(4) `HOME`、`TZ`、記録の置き場所を変えても同じバイト列になる、の 4 つである。**対照**として、3 版目の規則（`attachment` を境界にしない）と、除くものを並べる方式に差し替えると、(2) と (1) が落ちることを確かめる。
- **ディスクの走査。** `inspect`、`show`、`decide`、`scan` の前後で、wiki、raw のルート、作業ツリーの全部のファイルを走査し、本文の目印がどこにもないこと、決定のファイルに `mark` に渡した文字列がないことを確かめる。対照として、写しを書く実装に差し替えると落ちることを確かめる。
- **縛り。** `show --meta` のあとに範囲の行を書き換えると、`write` が拒む。決定のファイルを書き換えると拒む。曖昧な `mark` と一致のない `mark` を拒む。題名に伏せた文字列が入っていれば拒む。
- **raw の排他。** 2 つのプロセスが違うバイト列を同じスラッグに同時に書くことを 200 回繰り返し、1 つだけが `created` になり、raw がその側のバイト列と一致することを確かめる。対照として、`os.replace` で置く実装に差し替えると、上書きが起きることを確かめる。公開の直前と直後で例外を起こし、前なら raw も一時ファイルも残らず、後なら、もう一度 `write` すると `identical` になることを確かめる。raw のルートか途中の階層をリンクかジャンクションにすると、`write` が拒む（リンクを作れない環境では飛ばす）。すでにある `<R>/<S>.md` がリンクなら、中身が同じでも `identical` にせず拒む。raw のルートを `<W>/sources` にした配置と、wiki のルートを raw のルートの中にした配置で、`write` が終了コード 1 で拒み、何も書かない。
- **読み取り専用と `verify`。** `write` のあとの raw が読み取り専用になる。Windows では、wiki の中のジャンクション（`<W>/indexes` が raw のルートの親を指す配置を含む）を経由して Claude Code の Write と Edit で raw を書こうとすると失敗し、raw が変わらないことを、`check_commands_mcp.py` と同じく実際の Claude Code で確かめる。POSIX では、シンボリックリンクを経由して raw を名前の変更で置き換えると、`verify` が終了コード 1 になる（Claude Code を使わず、同じ方式の書き込みを Python で再現する）。raw を書き換えずに読み取り専用の属性だけを外しても、`verify` が終了コード 1 になる。
- **自己検査。** 唯一の人の発言を `drop` した記録、印のターンだけが続く記録で、自己検査が通る（フェンスを本文のあるターンだけで数える）。
- **`show` の分け方。** 1 つのターンが `--max-chars` を超える記録で、`--from` を順にたどると、つないだ標準出力が raw と同じバイト列になり、続きの案内は標準エラーにだけ出る。
- **`scan`。** 用意した文に、人が伏せた文字列そのもの、全角にしたもの、大文字にしたもの、自動の伏せ字が置き換えたメールアドレスと秘密の値を入れると、場所と規則の名前だけを出して終了コード 1 になり、標準出力に文字列が出ない。`a@example.com` を含む記録で、要約ページの frontmatter（`raw:`、`tags:` など）が当たらず、`skipped_short` が 1 になる。`--allow` に渡した `raw_ref` が、ホームのディレクトリの規則に当たっても見つからない。人が伏せた 2 文字の名前は、短くても見つかる。
- **実物での確認**（手元で行い、コミットしない）。検証環境の記録で `inspect` と `show --meta` を流し、印の数、`reply_unresolved`、`unknown_uuidless_type`、`write` にかかる時間を記録する。
- `check_commands_mcp.py` の `CLI_NAMES` に `wiki_session.py` を足す。`claude -p` で `/wiki:ingest session` を流し、`${CLAUDE_SESSION_ID}` が置き換わって `locate` に渡り、人の発言がないので終了コード 2 で止まることを記録する。
