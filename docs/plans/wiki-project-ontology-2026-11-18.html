1. 設計の結論

この wiki には「何を作り、なぜ選び、どの版で直し、どこまで確かめたか」を追えるオントロジーが合う。 製品や人物の一般的な関係よりも、構成要素・変更・問題・判断・評価・出荷のつながりを優先する。 既存の product、concept、source、decision を使い、component、release、change、issue、evaluation、artifact の 6 種類を追加する。 11 述語を追加し、既存の depends_on の主語・目的語に component と release を加える。 完全版は 18 種類・26 述語になるが、既存の 12 種類・15 述語はすべて残す。 自前・外部の製品と版を同じ方法で区別し、文書・設定・公開文面の変更先は artifact で表す。

記事と、記事が述べる対象を分ける。 たとえば pdfのヘッダーの判定の修正-rag-0.5.1 は出典のまま残し、rag 0.5.1、PDF の拒否、受け付け条件の変更、直接抽出の評価を別々の対象として記述する。 1 ページを複数のノードにする変更は、現行の「主語はそのページのノード」という契約を変えるため採らない（グラフの抽出の契約）。

4. ノードの種類と境界

種類 定義と配置 分けるもの 識別子の例
product（既存） プラグイン、外部道具、モデルの製品単位。entities/ 版は外部製品でも release に分ける product:info-hive-wiki、product:yt-dlp
component（追加） 製品内で責務を持つ構成要素。entities/ browse や Web raw の段と、個々のファイル・画面ラベル component:wiki-web-raw
release（追加） 製品の特定版。自前・外部を同じ形で扱う。entities/ 公開日時・導入確認・版の報告書。存在を知っても公開日時まで確定したとはしない release:rag-0.5.1、release:yt-dlp-2026.8.19
change（追加） 範囲を特定した変更。コード・文書・設定・プロンプトを含む。entities/ 問題、判断、評価、出荷。実施と提案は本文で明記する change:rag-pdf-prefix-1024
issue（追加） 条件と期待との差を観測した問題。entities/ 原因の仮説や一般的な教訓。GitHub issue がなくても作れる issue:rag-pdf-prefix-rejected
decision（既存） 何を選び、なぜ選んだかという具体的な判断。concepts/ ADR 文書全体、未採用の案、実装の完了 decision:adr-0027-captions
evaluation（追加） 対象・版・方法・結果・限界を持つ評価の実施。entities/ 試験コード、予定、成功の保証。比較・レビュー・手動確認も含む evaluation:rag-051-pdf-direct
artifact（追加） 変更を管理する文書・設定・ファイル・公開文面。entities/ 要約する source ページ、責務としての component artifact:rag-readme、artifact:dev-adr-0013
concept（既存） 再利用する概念・方式・手順・条件付きの教訓。concepts/ 特定の版の障害そのもの 既存の concept:ingestに使うモデル を維持
source（既存） 原本を要約した根拠の記事。sources/ その記事が報告する製品・出来事・判断 既存 ID を維持

synthesis は既存の統合ページとして残す。 person、company、paper なども、今後外部記事を取り込む用途のため残す。 claim は原子的な主張と矛盾を管理する必要が生じた段階で使い、この段階では全文章を claim に変換しない。 raw の種類も残すが、現行の summarizes_raw の目的語はパスの文字列であり、raw ノードに変わるわけではない。

新しい 6 種類には explicit_only: true を記載し、maps_from は設けない。 現行のスクリプトが自動の対応付けをしないのは、maps_from がないためである。 explicit_only はエージェントへの指示であり、ランタイムで強制するフラグではない。 既存の graph-workflow の「目的語だけでページを持たない」という説明とは使い方が異なるため、採用時はページを持つ明示型の規約に合わせて説明を更新する。 記事タイトルやタグから型を自動で付けず、graph.node_type で明示する。 トップレベルの type は現行の entity または concept を使い、新しい type や kind の列挙値は導入しない。 これにより、既存の concept や source の対応付けを変えない。

5. 関係の定義

追加する関係はすべて source と evidence を必須にする。 方向は、関係を書いたページを主語とする。 反対向きの述語や、推移的なエッジを二重に保存しない。

述語 主語 → 目的語 採用する意味 採用しない読み方
part_of component/artifact → product/component 構成要素・管理対象物の所属 ファイル名に同じ語がある、単なる利用
release_of release → product その製品の、その出荷の単位 その記事が製品に言及した
delivers release → change その版に含めて出荷した変更 計画した、マージした、導入された別の版
changes change → component/artifact 直接変更した責務または文書・設定の範囲 間接的に関係がありそうな機能
affects issue → product/component/release 指定した条件で問題を観測した対象。既知の版は release を使う すべての版・環境に問題がある
fixes change → issue 根拠の条件の問題を解消した実施済みの変更 案、回避策、評価しただけ、全経路の安全保証
implements change → decision 具体的な設計判断を実装した ADR 全体の充足や評価合格
motivated_by decision → issue/evaluation その判断をした理由として明記された 先に起きた、同じ記事にある
selects decision → product/concept/release 判断が選んだ製品・方式・特定版 選択したので実装・出荷も済んだ
evaluates evaluation → product/component/release/change/decision/artifact その対象を評価した 成功した、現在の版も同じ、すべて検証した
applies_to concept → product/component 明記した条件で手順・教訓が当てはまる 一般知識からの連想

depends_on は既存の product/concept 同士の組を残し、両側に component と release を追加する。 特定版で固定した依存は release:wiki-0.23.0 → depends_on → release:yt-dlp-2026.8.19 → release_of → product:yt-dlp とする（E13）。 将来版を上げても製品の ID は同じままで、旧版の依存を現行製品の無版の依存と読まない。 ADR-0027 の「版を固定して yt-dlp を使う」という判断の selects は product を指し、実装で選んだ数値の版を永続的な判断の値として補わない。 旧 chose は人物・組織を主語とする関係として残し、判断を主語とする selects と混ぜない。 誰が決めたかを根拠なしに人物ノードへ補完しない。

本文リンクの mentions と、ページ単位の出典 sourced_from は引き続き自動生成する。 related_to、tested_by、verified_by、causes、better_than は追加しない。 前者は既存の探索リンクで足り、後者は成功・因果・比較条件を省略して誤読されやすいためである。

6. 識別と粒度

ID は題名を変えても保つ。 製品はプラグイン・道具・モデルの識別単位、構成要素は製品名を含む責務の名前、版は製品名と版の組で決める。 release ごとに release_of の目的語は 1 製品に限る。 wiki と rag の 0.5.1、通常の query と別製品の query を混同しない。 外部モデルの Sonnet 5.5 も製品名と版に分け、公開日を出典なしに補わない。 artifact はリポジトリとパス、文書の識別子、または管理対象の URL で区別する。 同じ ADR 番号を別リポジトリの文書に使っていても同じノードにしない。 変更は PR・コミット・変更範囲、評価は実施日・対象版・方法を本文に残し、再試験を同じ評価で上書きしない。 ADR の番号が同じでも判断が複数なら、decision:adr-0027-captions のように選択の単位で分ける。 ファイルパス、タグ、見出し、試験の assert ごとの自動ノード化は行わない。

1 つのページが複数の役割を持っていても、ノード ID と node_type は 1 つにする。 たとえば現行の ingestに使うモデル は concept のまま残し、日付と選択を持つ decision を別に作る。 同じ対象を別の記事から言及する場合も、対象ページを増やさず同じ ID を指す。 concept の手順・条件と、特定時点の decision は異なる対象である。 既存の概念ページの記述を新しい判断の根拠として重複生成せず、過去の選択は source の報告から作る。 別名は検索の補助であり、現行のグラフ CLI が別名から ID を自動で解決するとは扱わない。

記事に登場しただけでは対象ページを作らない。 Q1〜Q8 の少なくとも 1 つに必要で、定義・根拠・区別する対象が書けることを採用条件とする。 レビュー 17 回の集合は、まず source の報告として残す。 対象が各回で変わる集合を、出荷した最終 change の evaluation として登録しない。 対象版・判定が特定できた各回を、必要な問いの範囲で別ノードにする。 PR の一部を change として採録するときは、対象を狭く命名し、含めない変更を本文に書く。 出荷版のページにも変更一覧が「抜粋」か「対象範囲の全件」かを記し、関係がないことを変更の不存在と読ませない。 初回は対象 33 件の隔離試料にとどめ、採用時は有用な問いから必要分だけを選ぶ。 記事が約 150 件またはインデックスが 300 行を超える見込みなら、追加前に SCHEMA のインデックス分割を計画する。

7. 根拠、状態、時間、結果

型付きの関係には predicate、object、source、evidence、confidence、status を書く。 このプロファイルでは、対象の版・条件・限界を notes にも書く。 source は現行の lint に合わせてソースページのスラッグ、object はページパスや wikilink ではなく、対象のノード ID にする。 引用はソース本文に存在する文字列を使い、周辺の文も読んで対象と範囲を確認する。 引用が存在しても、関係の意味が正しいとは限らない。

対象の本文には、次の情報を通常の Markdown として残す。 これらを新しい frontmatter 属性として保存・検索する機能は、この候補には含めない。

対象 本文に残す情報
release 製品、版、タグ・コミット、公開日、導入確認の対象版と未確認の点
change 提案か実施済みか、変更範囲、PR・コミット、対象の版
issue 期待と観測の差、再現条件、影響する版、原因の仮説と確定事項の区別
decision 選択、理由、適用範囲、判断日、採用・保留・撤回、見直す条件
evaluation 対象版・コミット、方法・試料・環境、観測した結果、未実施・限界、原記録
artifact リポジトリ、パスまたは文書の識別子・URL、変更対象の範囲。正確なパスが不明なら推測で埋めない

関係の status と対象の実施状態を混ぜない。 current はその主語・目的語・範囲について有効な関係であり、「最新版」「問題が未解決」「試験に合格」を表さない。 版のノードに結び付いた事実は、その固定版について変わらなければ current のまま保持する。 たとえば issue → affects → release:rag-0.5.0 は、0.5.1 で修正されても 0.5.0 については真である。 これを issue → affects → product:info-hive-rag という無版の現在の障害へ書き換えない。 同様に、固定した依存は release:wiki-0.23.0 → release:yt-dlp-2026.8.19 とし、現在の構成要素への依存に一般化しない。 historical は、版を端点に持たない継続的な関係などで、適用が終了したことが根拠で確定した場合に使う。 過去の記事であるという理由だけでは historical にしない。 proposed は未採用の関係候補、disputed は異論のある関係、superseded は差し替えられた関係として使う。 proposed fixes で修正案を記録せず、実施前は本文に案として置く。 confidence は抽出した関係と根拠の対応への評価であり、評価対象の品質の点数ではない。

valid_from と valid_to を使う場合は関係の適用期間を表し、記事の created/updated、取り込み日、試験の実施日で埋めない。 境界を確定できなければ省略し、分かる版と日付を本文・notes に残す。 SemVer の大小だけで公開順、導入版、supersedes を生成しない。 G2 の status=current のフィルターだけでは「現在の製品に関する問い」を答えられない。 現在を問われたときは対象の版を先に特定して、その版に適用できる根拠を読む。 G2 の過去の照会で期間の両端を必須とする規則は維持し、境界の不明な historical は時点の真偽の判定に使わない。 期間が不明な記録を調べる場合は、全件の記録と本文を読む探索として明示し、過去の時点に有効だったという答えを生成しない。 古い根拠を削除せず、食い違いが同じ条件についてのものかを確かめる。 実際に youtubeの字幕の取り込みの設計-2026-11-15 は冒頭で出荷を追記した一方、後段に実装前の留保が残るため、記事全体を 1 つの状態として読めない。

  1. グラフを JSON で引き、対象 ID、関係を記述したページ、出典を特定する。
  2. 主語のページの frontmatter と本文を開き、版・条件・採録範囲を確認する。
  3. 入ってくる evaluates の評価ページを開き、対象版・方法・結果・未確認事項を読む。
  4. 出典記事の該当箇所を開き、E04 の直接抽出と E05 の MCP→索引化の未確認を併記する。

notes の内容は本文にも残すので、JSON の解析だけに限界の発見を依存しない。 CLI/MCP の構造化された notes の表示改善は追加実装の項目であり、この候補の実装済み機能ではない。 youtubeの字幕の取り込みの実装とリリース-wiki-0.23.0 の 17 回は、対象版が各回で異なるため、今回の試料では evaluation へ昇格させていない。

9. 生成と保存

保存先は Markdown の対象ページと、graph/ontology.yaml とする。 型付きの関係は主語のページの graph.relationships に保存し、JSONL と SQLite は現行の抽出器で再生成する。 候補の YAML はデータモデルを制約するもので、本文から対象を見つけたり、推論したりする処理ではない。 グラフ DB を追加しなくても、この範囲を保存・照会できる。 外部グラフ DB を導入する場合も、ここで決めた ID・型・関係・根拠を投影し、対象の識別を DB 固有の ID に置き換えない。

人やホストの LLM が記事から候補を作り、既存 ID と照合してから採用する。 LLM を使わない場合も、人が同じ候補の形を書き、同じ検査を通せる。 抽出器には LLM 呼び出しを加えず、採用済みの記述を決定的にコンパイルする。 この分担は オントロジー候補の生成と採用の分離 と 既存のグラフ改善設計 の G3〜G4 に合わせる。 後から加わった スキーマの導出と事実の抽出の分離 も、この段階を分ける方針を裏づける実装例として参照した。 myKG にある自動統合・孤立ノードの推論・OWL の継承を、この候補の動作へ加えるものではない。

11. 移行と検証

適用は次の順で進める。

  1. この候補をレビューし、種類・関係・粒度・採用規則を確定する。
  2. 候補 YAML を指定して、現行の全記事の解釈が変わらないことを確かめる。
  3. PDF ヘッダー、Web raw のモデル選択、YouTube 字幕の 3 事例から、必要な対象だけを別ページにする。
  4. 出典を読んで関係を採用し、通常 lint と引用・条件・状態の確認を通す。
  5. インデックスと log を更新し、グラフを再生成する。Q1〜Q8 の回答を出典と照合する。
  6. 役に立った種類・関係を browse/query/セッションの記録へ広げる。全記事を一括で構造化しない。

既存ページを残すので、候補を取り下げても現行の記事・リンクを戻す必要はない。 適用後に取り下げる場合は、追加した graph 記述と対象ページを個別に扱い、関係が残る状態で述語だけを削除しない。 wiki 用のプロファイルであり、配布プラグインの既定オントロジーに全利用者向けの種類を加える設計ではない。 プラグインのバージョン変更は、この設計だけでは行わない。
