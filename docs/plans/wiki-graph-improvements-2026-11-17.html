info-hive-wiki / 改善設計

wiki のグラフ機能の現状と改善設計

状態: 提案更新: 2026年11月17日対象: 0.30.0 を名乗る作業ツリー

現在の実装・隔離した試料での観測と、これから実装する設計を区別して記載しています。

Markdown を正本とする現在の構成を維持し、グラフの鮮度と検索条件を機械で確かめた上で、根拠を持つ型付き関係を増やす。 グラフDBへの移行を先行させず、SQLite の索引、既存の抽出器、browse の関係表を改善する。 本書は提案であり、プラグインの実装や版は変更していない。

1. 対象と根拠

対象は info-hive-wiki のグラフの生成、検証、問い合わせ、browse、取り込み手順である。 2026年11月17日の作業ツリーは 0.30.0 を名乗り、HEAD は 69f614dfd08abc6c9a1a54e7a82526b6f196fa27 だった。 未コミットの変更を含むため、公開版 0.30.0 全体の検証結果とは区別する。 確認した主要ファイルの SHA-256 は 観測記録 に残した。

前提は 調査レポート、移植計画、ADR-0009 に従う。 グラフは wiki プラグイン内の任意の索引とし、検索や lint のために常駐する新しいサービスを追加しない。 以前の ADR に書かれた不具合は、現行コードと照合してから不足に数えた。 個別ファイルの一時書き込み、出力先ごとの排他、オントロジーがない場合の共通の扱いは、既に実装されている。

既存知識として [[グラフの抽出の契約]]、[[エッジの識別子]]、[[既存リンクからのグラフ検索]]、[[オントロジー候補の生成と採用の分離]] を参照した。 これらの記録と現行コードが異なる場合、現状の記述には現行コードと再現結果を採用した。

2. 現状では、グラフの保存より関係の整備が遅れている

実 wiki の記事をメモリ内で読み、索引を書き換えずに再集計した。 結果は84ページ、84ノード、439エッジだった。 内訳は mentions が307、sourced_from が77、summarizes_raw が55で、型付き関係と別名は0件だった。 通常のグラフ lint による検出も0件だった。 これは当該プロジェクトの一時点の状態であり、プラグインの利用者全体を代表しない。 記録は project_snapshot.json にある。

機能が存在することと、問い合わせに使える関係が登録されていることを分けて測る必要がある。 現在は、記事と出典をたどるグラフとして機能する一方、型付き関係の抽出品質や検索への寄与を実データから評価できない。 辺の本数を増やすことを目標にせず、代表的な関係の問いに答えるために不足する主張を整備する。

4. 全体構成

処理を、入力の読み取り、関係候補の生成、主張の採用、決定的なコンパイル、照会に分ける。 extract は、採用済みの Markdown をコンパイルする現在の役割を保つ。 LLM や GiNZA の呼び出しを extract 内へ混ぜない。

保存用の GraphSnapshot は、不変のノード、エッジ、別名、診断、入力ダイジェストを持つ。 browse も既に読み取ったバイト列から同じ構築関数へ渡す。 照会ポリシーは SQLite 専用の条件文に閉じ込めず、メモリ上の辺にも適用できる共通定義にする。 これにより、CLI と browse が同じ内容・同じ条件を使った場合に、同じ採否を得られる。

入力バイト列の収集と鮮度の確認は標準ライブラリと既存の wiki_pages の範囲に置き、PyYAML を使う解析・コンパイルと分離する。 query は、DB 内の検証済みの定義と入力ファイルのハッシュを使い、PyYAML を import しない。 現在の、問い合わせだけなら python と標準ライブラリで動く契約を保つ。

5. G1：入力の完全性と鮮度を確認する

5.1 入力を読み飛ばして成功にしない

新しい collect_snapshot() は、既存の wiki_pages.walk_pages() を使い、unlistable と unknown を保持する。 ファイルごとの UTF-8 読み取り失敗も、相対パスと理由のコードを持つ診断にする。 独自のディレクトリ走査を作らず、既存の除外・リンク・正規化の契約を維持する。

extract --strict では、走査・読み取りの不完全さ、読めない graph、IDの衝突、曖昧な参照、必須値の欠落、未知の述語、型不一致、壊れた参照、期間の誤りを公開前に止める。 孤立したノードなどは警告にとどめる。 既存の extract の引数なしの挙動は移行期間中は保ち、生成メタデータの validation_state を issues にする。 取り込みと通常の更新手順は --strict を使うよう変更する。 既存の permissive な DB は、後述する型付き照会には使わず、ナビゲーションとして表示する。

lint は既存の検出名を維持し、missing_confidence、missing_status、invalid_valid_from、invalid_valid_to、invalid_valid_range を追加する。 期間は実在する YYYY-MM-DD の日付に限り、両端がある場合は valid_from < valid_to とする。 明示型の関係の必須欄と、暗黙に生成する辺の欄を同じ規則で誤検出しない。

5.2 DB に、入力との対応を記録する

SQLite に graph_build と graph_inputs の表を加える。 graph_build は build_id、schema_version、compiler_digest、input_digest、wiki_root、built_at、validation_state、件数を持つ。 graph_inputs は記事と ontology ごとのディスク上の相対パス、内容の SHA-256、入力種別を持つ。 ダイジェストは文字列の単純連結ではなく、型と長さが区別できる正規化した JSON を UTF-8 でハッシュする。 ディスク上のパスを識別用に残し、表示用の NFC パスと混同しない。

compiler_digest の対象はグラフの読み取り・構築・正規化に使うモジュールと同梱 Markdown パーサーである。 対象の一覧を実装内に定義し、その一覧の変更も試験する。 実行開始時に記録した実装のダイジェストと、公開・照会時のファイルのダイジェストが変わった場合は、同じ実装として処理を続けない。 常駐する MCP でコードの変更を検出した場合は、プロセスを再起動する必要がある状態として返す。 クエリの日時や画面の配色はコンパイルの入力に含めない。 raw の内容は、グラフの形の鮮度とは分けて G3 の根拠の検証で扱う。

新しい status は、入力の追加・変更・削除、ontology と compiler の変更を内容で比較する。 最初の実装では、確認を省くために mtime とサイズだけを信用しない。 読み取り開始・終了時の走査と内容の対応を照らし、不一致は unstable にする。 ファイル群全体に対するトランザクションではないため、同時編集下での完全な一点のスナップショットとは呼ばない。 同じ内容に戻った変更を含む、確認の間に観測できない履歴までは保証しない。

状態 意味 型付き照会の扱い
disabled ontology がない グラフを使わない
missing DB がない 明示的な作り直しを案内
legacy 版・入力メタデータのない DB ナビゲーションのみ。作り直しで移行
fresh 比較した記事・ontology・compiler が一致 検証状態と検索条件をさらに確認
stale 入力の追加・変更・削除などを検出 型付き照会を停止。古い結果の本文確認で代用しない
unreadable 入力を完全に調べられない 型付き照会を停止
unstable 確認中の変更を観測 有限回の再試行後、書かずに返す

CLI と MCP の status は、索引を書き換えない。 読むたびに自動で extract を呼ぶ機能は加えない。 関係の問いでは status を確認し、使えなければ本文検索へ戻り、グラフを使えなかった理由を回答に残す。 fresh は、元資料の内容が真実であることや、根拠を意味的に検証したことを表さない。

別の status 呼び出しが fresh だったことだけを、後の照会の許可にしない。 型付き照会は、自分が開いた SQLite 接続で読み取りトランザクションを開始し、その接続から得た graph_build に対して入力を照合する。 その後に読む辺と応答メタデータも同じ接続・トランザクションから取得する。 照会後にも入力を照らし、変更を観測した場合は結果を通常の成功として返さず unstable にする。 応答は確認時点の入力ダイジェストを示し、回答時に根拠本文を開いた際も、その版を照合する。

wiki_root は既存の wiki の根を検証する処理から得た正規の絶対パスで記録し、入力の相対パスだけで別の wiki の DB と同一視しない。 明示した --db でも根と入力の照合を必要とする。 wiki の移動・複製後は strict な作り直しで新しい根に結び付ける。 2つの wiki の物理的な分離は既存の根の検査で行い、グラフのパス文字列比較だけで代替しない。

5.3 SQLite の公開と、複数形式の書き出しを分ける

問い合わせ用の SQLite を、公開の単位にする。 一時 DB に全表・メタデータを書き、整合を確認し、接続を閉じてから既存の置き換え関数で公開する。 ここまでに失敗した場合は、前の問い合わせ用 DB を残す。 現在の出力先の OS ロックを継続して使う。

JSONL・GraphML は、公開 DB の一つの読み取りトランザクションから書き出す。 新しい一貫した書き出し先は graph/exports/<bundle_id>/ とし、ノード・エッジ・GraphML・manifest.json をまとめる。 bundle_id は書き出すたびに作る UUID とし、同じ DB を異なる形式で書き出しても公開済みの bundle を上書きしない。 manifest は形式ごとのハッシュ、件数、元の build_id、入力ダイジェスト、書き出し器の版を持つ。 全ファイルを完成させた後、graph/exports/current.json を一回の置き換えで公開する。 読み手はポインターを一度だけ読み、その bundle の manifest とファイルを照合する。 ポインターが指す bundle を書き換えない。

索引と書き出しの成功は、index_state と export_state に分けて報告する。 書き出しだけが失敗した場合、新しい DB と前の完全な書き出し bundle を残し、異なる build_id を表示する。 「どの形式も前のまま」と報告しない。 書き出しの読み手が使用中の bundle を自動で削除する GC は初期実装に含めず、ディスク使用量を表示する。

既存の nodes.jsonl、edges.jsonl、graph.graphml は移行期間中の互換出力として残す。 複数の互換ファイルを一緒に読む用途の不可分性は保証せず、bundle へ移行するよう明記する。 --formats と --out を即時に廃止しない。 SQLite を永続化しない --formats jsonl,graphml は、同じ GraphSnapshot から bundle を生成できるようにする。 この場合も、manifest とポインターを公開の単位にし、存在しない DB があると装わない。

6. G2：検索の目的と辺の採否を明示する

6.1 互換のナビゲーションと、型付き関係の照会

既存の4コマンドに view=navigation|typed を加える。 既定の navigation は既存の辺を一覧・探索する動作を保つ。 テキストの facts は「記録された関係」と表示し、現在の確定事実という見出しにしない。 機械用のコマンド名 facts は維持する。

typed は意味を持つ主張の候補を探すモードであり、本文を読まずに回答する機能ではない。 fresh かつ完全な入力を strict に検証した DB を必要とする。 共通のフィルターを適用してから、近傍・辺・逆向きの辺・BFS を計算する。 経路を計算してから不適切な辺を取り除く実装にはしない。 そうすると、採用可能な別経路を訪問済みとして捨てるおそれがあるためである。

条件 navigation の既定 typed の既定
辺の生成元 すべて explicit_graph_frontmatter
述語 すべて 暗黙の3述語を除き、ontology で定義されたもの
status すべて current
期間 絞らない 問い合わせ日が [valid_from, valid_to) に入る
確信度 絞らない 有効な3値を返す。任意の下限を追加指定できる
目的語 raw の文字列なども返す 一意のノードに解決できるもの
否定・条件 記録と検証状態を表示 G3 の否定は除外。条件があるものは既定では経路に使わない
根拠 生の欄と検証状態を返す 必須値・参照を満たす。G3 以降は根拠の版・引用の照合も条件にする

期間の片端が未記入の場合、その端では範囲を制限しない。 これは保存された主張のフィルターの規則であり、関係が無期限に正しいとの判断ではない。 valid_to の排他的な解釈は新しい検索ポリシーとして明記し、既存の無条件ナビゲーションを変更しない。 日付はホストの地域設定に依存させず、API に渡した as_of または設定した wiki の日付を使い、応答に採用した日を返す。

過去の問いでは as_of と対象の statuses を明示する。 historical・superseded を型付き照会へ加える場合は、有効な開始日と終了日を必要とする。 期間不明の過去の記述は、ナビゲーションで発見し、本文で確かめる。 proposed・disputed は型付きの回答用の経路へ入れず、ナビゲーションで確認する。 supersedes の辺を見つけたことだけで、相手のすべての関係を自動で失効させない。

G2 の query_policy_version=1 は、構造と期間を検証した候補を返す。 G3 の根拠の版を持たない既存関係には evidence_state=legacy_unverified を明示する。 G3 では、根拠の版・引用の所在まで条件にする query_policy_version=2 を追加し、この状態を除外する。 既存の版1の条件を変更せず、呼び出し側が policy_version=2 を指定する。 G3 の /wiki:query の手順は版2を明示し、使えない場合は本文検索へ戻し、版1へ黙って緩和しない。 既存の低水準の呼び出しは版1を既定として継続でき、どちらの版も本文の確認を省けない。

6.2 API と探索の上限

CLI の例は次のとおりである。 いずれも新しい引数・コマンドの設計例で、現行では未実装である。

/wiki:graph status
/wiki:graph resolve --name "略語"
/wiki:graph neighbors --node concept:例 --view typed
/wiki:graph path --from concept:a --to concept:b --view typed --max-depth 4
/wiki:graph edges --subject concept:a --view typed --predicate depends_on --as-of 2026-11-17

MCP の graph に status と resolve を追加する。 resolve には name を渡し、既存コマンドには view、policy_version、statuses、as_of、min_confidence、max_edges、max_nodes を追加する。 互換の結果の欄を保ち、meta に build_id、input_state、query_policy_version、applied_filters、truncated、truncation_reason を加える。 predicate は近傍・facts・path にも同じ意味で適用する。 CLI と MCP の引数検証を共通関数へ寄せ、深さ・件数の0以下や過大な値を同じように扱う。

初期値は max_depth=6、max_nodes=1000、max_edges=10000 を設計上の上限候補とする。 性能の実測値から導いた値ではないため、G5 で調整する。 探索を途中で止めた場合、「経路が存在しない」とは返さず、上限内で探索が完了しなかったことを返す。 経路が見つかっても、各辺の関係型が異なる経路を一つの意味の関係に読み替えない。

resolve は ID 完全一致、ページのパス、title・slug・aliases の候補を返す。 候補が複数なら ambiguous とし、canonical: true を曖昧性を消す理由にしない。 埋め込みや LLM による自動統合は加えない。 /wiki:query は、IDを推測して呼び直す手順から resolve → status → typed neighbors → 本文確認 へ変更する。 2つの wiki を使う問い合わせでも、IDは wiki ごとに解決し、結果に根の識別子を付け、ノードIDだけで統合しない。

--db で明示した旧 DB は、読み取り専用のナビゲーションとして扱える。 型付き照会では、その DB の入力台帳を指定 wiki と照合できることを必要とし、オントロジーの確認を省く抜け道にしない。 browse は同じ検索ポリシーを用い、どのスナップショットを表示しているか、関係が除外された理由を示す。 ブラウザでの表示は既存 CSP を維持し、インラインスクリプトや style 属性を追加しない。

7. G3：主張の識別と根拠の版を残す

7.1 生成されたエッジIDと、保存する主張IDを分ける

既存の id の計算を維持し、新しい関係に assertion_id: assertion:<UUID> を任意で付ける。 採用した関係を最初に記述するときに UUID を作り、その後の引用や状態の編集では同じ値を保持する。 コピーして別の主張として記述する場合は新しい UUID にする。 wiki 内の重複は lint のエラーにし、canonical で重複を許可しない。

contradicts と supersedes は、新しい主張IDでも参照できるようにする。 既存のノードID、ソースのスラッグ、24桁のエッジIDの参照は引き続き読める。 既存の関係を一斉に書き換えず、長期参照が必要な関係から移行する。 UUID の追加を、既存のエッジIDを変えるための値には含めない。 変更前後の意味が別の主張になった場合は、新しい主張IDを付け、必要なら古い主張を参照する。

7.2 根拠の参照を一意に解き、引用を照合する

source は既存の文字列を保持したまま、一意に解決した source_page を生成結果へ加える。 読み方は wiki_pages の既存の参照解決へそろえ、同じスラッグのソースが複数ある場合は曖昧とする。 新規に書くときは sources/ページ名 の相対パスを推奨する。

新しい型付き関係には、次のメタデータを加える。 値は形式を示す例で、架空の関係を表す。

graph:
  relationships:
    - assertion_id: "assertion:00000000-0000-4000-8000-000000000001"
      predicate: depends_on
      object: "concept:例B"
      source: "sources/例の仕様"
      evidence: "例Aの実行には例Bが必要である。"
      evidence_ref:
        representation: source_body_v1
        sha256: "<参照したソース本文の SHA-256>"
        locator: "要件/段落3"
      polarity: positive
      qualifiers: []
      confidence: high
      status: current

source_body_v1 は、UTF-8 の BOM を除き、改行を LF にそろえ、既存パーサーが返す frontmatter を除いた本文を UTF-8 でハッシュする表現とする。 空白の圧縮や Unicode の NFC 化はしない。 証拠を含む source ページ自身に関係を書いても、frontmatter の SHA-256 が自分自身を含む循環を作らないために、ファイル全体のハッシュと区別する。 引用はこの本文の連続する文字列として照合し、位置は補助情報として扱う。 複数箇所に一致した場合、位置で一意に決められなければ ambiguous_quote とする。

根拠の状態は verified_quote、source_changed、missing_source、quote_not_found、ambiguous_quote、legacy_unverified に分ける。 verified_quote が意味するのは、採用時に記録した本文の版と引用の所在が一致することまでである。 引用が関係を意味的に支持するかは、採否の判断として別に記録する。 入力を作り直しただけで、現在のハッシュを採用時のハッシュとして書き戻さない。 版2の既定の型付き照会へ入る根拠の状態は verified_quote に限る。 source 本文を再照合する処理は、DB の input_state=fresh と別に行い、両方の状態を応答に残す。

現行の raw_ref は保持する。 元資料の本文からしか取れない引用は、source 本文の照合を通ったことにはしない。 raw の照合は、取り込み時に確定した RAW_ROOT と原本の版への参照がある場合に限って後続の拡張で扱う。 既存の raw パスを、wiki の親ディレクトリや任意の外部ファイルへ推測で解決しない。

7.3 否定・条件・複数の支持を失わない

polarity は positive|negative、qualifiers は条件の文字列の配列とする。 既存の関係は、旧形式で記述された肯定の宣言として読めるが、根拠の未検証状態は残す。 条件がある辺は、通常の肯定の経路探索へ無条件に入れない。 初期実装では条件の論理的な充足を判定せず、条件付きの記述として本文確認へ渡す。

記述ごとのエッジを保持する現在の契約を維持し、同じ三つ組を保存時に一つへ潰さない。 閲覧用にまとめる場合だけ、主語・述語・目的語・極性・条件をキーとし、主張IDの集合を付ける。 有効期間は各主張に残し、採用日について支持する主張があるかを評価する。 同じ raw から作った複数の wiki 記事を、独立した複数ソースによる支持として数えない。

記事の削除後は、完全な入力から全体をコンパイルし直すことで、その記事の主張だけを除く。 別の記事の支持が残る関係を、集約キーだけで削除しない。 根拠の source ページを削除した場合は、残る関係を lint エラーとし、新しい strict DB を公開しない。 古い DB は stale として型付き照会を止めるため、削除された主張が現在の回答に戻る経路を塞ぐ。

8. G4：LLM が生成した候補を、直接の正本にしない

8.1 候補を生成する範囲

最初の対象は、既存ページを主語・目的語にでき、既存 ontology の述語を使える関係に限る。 新しい実体や述語の候補は unresolved として分離し、自動でページや語彙を増やさない。 既存の取り込みがページを作った後、改めて候補を検証する。 patch を書く対象ページのノードIDと候補の主語IDを照らし、異なる主語の関係をそのページへ記述しない。 候補を合わせるために、既存ページの graph.node_id を変更しない。

候補生成には、Claude Code または Codex の実行中のホスト LLM を使う。 新しいモデルサーバーや API キーを必須にしない。 wiki_graph_candidates.py prepare が、許可する述語・型、既存ID、ソース本文の版、対象の段落、request_id を機械的に組み立てる。 モデルが返した JSON の自己申告で、入力の版や実行モデルの情報を確定しない。 信頼できる実行側が持つ request の記録へ結び付ける。

モデルは候補の主語ID、述語、目的語ID、引用、条件、極性、時間を返す。 根拠がなければ空の配列を返せるようにする。 共起や埋め込みの近さを、因果・依存の証拠として使わない。 非LLMの比較対象として、明示構造のみと GiNZA＋規則を評価できるが、GiNZA を標準依存へは加えない。

8.2 検証、採否、反映を分ける

候補は wiki/.wiki-cache/graph-candidates/ に保存し、通常のページ走査とグラフの生成から除外する。 この台帳は一時的な作業記録であり、採用済み知識の正本にしない。 未採用・棄却候補を graph.sqlite の通常の辺へ混ぜない。

状態は proposed → validated → selected → accepted を基本とし、rejected、unresolved、stale を別に持つ。 validated は型、参照、引用の所在、入力の版を通った状態であり、意味的な支持の採用を表さない。 selected は、既存の取り込みで与えられた編集権限の範囲内で、ホストのエージェントまたは利用者が内容を確認して選んだ状態とする。 候補一件ごとに新しいユーザー承認を必須にする設計にはしない。

最初の実装では、候補用 CLI に Markdown を自動で上書きする apply を追加しない。 render-patch が対象ページ、前提の内容ハッシュ、追加する関係だけを出し、ホストが既存の編集手順で反映する。 その後の verify-applied は、主張ID、関係の内容、根拠の版を読み直し、実際に反映された場合だけ accepted を記録する。 書く前に accepted と記録しない。 同時編集の強いトランザクション保証を、この工程が追加すると主張しない。

入力が変わった候補は stale とし、そのまま反映しない。 引用元と ontology が同じで、参照先も現在一意と確認できる場合は、決定的な再検証で新しい検証記録を作れる。 引用元や語彙が変わった場合は、元の candidate を変更せず、新しい request から生成・判断し直す。 候補 JSON に指示文が混じっても、データとして扱い、コマンドやファイルの行き先として実行しない。

採用された関係と根拠のメタデータは Markdown に残るため、候補キャッシュを削除してもグラフを再構築できる。 意味的な採否の記録は、採用の理由と生成 request の識別子を関係の notes または専用の由来欄に残す。 同じ LLM に検証をさせた場合は、独立した人のレビューと区別して記録する。

既存の D2 判定は任意の補助として残す。 バックエンドが使えず処理を通した failed_open を、候補が支持されたという判定へ変換しない。 引用が本文に見つかったことも、意味的な支持の採否に代用しない。

12. 移行と残る判断

古い DB は legacy としてナビゲーションに使え、Markdown からの strict な作り直しで新しい内部表へ移行できる。 新しい前方互換の欄を持たない既存の主張は、未検証の状態を表示したまま保持する。 主張IDや根拠の版を勝手に書き足して、過去に確認済みだったようには扱わない。 元の Markdown と ontology を保つため、問題があれば以前の版で索引を作り直せる。

互換出力をいつ廃止するかは、利用する読み手の移行率を測った上でリリース単位に決める。 G3 を提供するリリースでは、通常の関係問い合わせの手順を版2へそろえ、既存データで使えない関係は本文検索で扱う。 条件の異なる結果を同じポリシーの成功として返すことは許さない。 SemVer の版は実装・マージ前に origin/main と最新タグを確認して決め、両方の plugin.json と CHANGELOG をそろえる。

本設計では、他 wiki 間の関係統合、全文書を対象にする自由なオントロジー生成、専用グラフDBの常駐、GraphRAG のコミュニティ要約、一般的なグラフ可視化画面は追加しない。 これらは G5 の測定や具体的な利用要件が得られた場合に、独立した設計として扱う。

13. 設計の確認記録

現状の不足は、ソースを読んだ推定だけでなく、再現スクリプト と観測 JSON に結び付けた。 元の wiki・raw・索引・プラグインは変更していない。 Opus 5.5 に敵対的レビューを依頼したが、5時間の利用上限により生成前に停止した。 独立した Opus レビューは未実施であり、再試行していない。 実行結果は status 記録 に保存した。 自己点検では、照会と鮮度を同じ DB 接続へ結び付けること、書き出しの単位と DB の版を分けること、根拠の条件をポリシーの版で区別することを補った。
