# frontmatter のパーサーが読む YAML の書き方を広げる（wiki 0.9.6）

2026-11-11。対象は `info-hive-wiki` の `skills/info-hive/scripts/wiki_text.py` の `parse_frontmatter_text()` と、同じ行の読み方を使う `top_level_keys()`、`unquoted_string_keys()` である。wiki 0.9.5（`docs/plans/wiki-graph-frontmatter-values-2026-11-11.md` の 5）が範囲外に残した課題を扱う。0.9.5（`info-hive-wiki` の 426d6bf。main の a896b6a）を元にする。

Sol の設計レビュー（`docs/agent-runs/2026-11-11-wiki-frontmatter-parser/design-review-1.md`、却下）を受けて、2.1、2.3、2.5、2.6、2.7、2.9、2.10、3、4、5 を改め、2.11 を足した。実装のレビュー（同じディレクトリの `review-1.md`、`review-2.md`、`review-3.md`。どれも却下）を受けて、2.1、2.2、2.3、2.11、3、4、5 を改めた。

## 1. 課題

`parse_frontmatter_text()` は、lint、検索、索引、統計、取得、MCP、グラフの最上位の欄（0.9.5 から）が共有する。YAML としては正しいのに、このパーサーが読まない書き方がある（426d6bf と PyYAML 6.0.3 で実測。YAML の値は、型に直さない `BaseLoader` のもの）。

| 書き方 | 例 | 今の値 | YAML の値 |
| --- | --- | --- | --- |
| 字下げのない配列 | `sources:` の次の行が `- paper` | `[]` | `["paper"]` |
| 字下げ 4 つの配列 | `    - paper` | `[]` | `["paper"]` |
| 複数行の `[...]` | `sources: [a,` 改行 `  b]` | `"[a,"` | `["a", "b"]` |
| 引用符つきのキー | `"type": x` | キーごと読まない | `type` が `"x"` |
| コロンの前の空白 | `type : x` | キーごと読まない | `type` が `"x"` |
| `\"` と `\\` のほかのエスケープ | `title: "a\tb"` | `\` と `t` の 2 文字（書かれた文字） | タブ |
| ブロックのスカラー | `raw: >` 改行 `  raw/a.md` | `">"` | `"raw/a.md\n"` |

エスケープのほかは、値を失う。配列は空になり、キーは欄ごと消え、ブロックのスカラーは記号 1 文字になる。lint はその欄がないものとして検査し、検索の絞り込み（`--type`、`--tag`）にも掛からない。グラフは 0.9.5 から同じに読まなくなり、`type`・`kind`・`sources`・`raw` についてだけ診断 `unread_field` で知らせている。エスケープは値を失わないが、YAML を読むほかの道具（Obsidian のプロパティ、PyYAML）と違う文字になる。

こう書かれる経路は、手書きのほかに、YAML を書き出す道具がある。PyYAML の `yaml.dump()` の既定は、配列を字下げなしで書き、日本語を 16 進のエスケープ（`消` を `\u6D88`）で書く。Go の yaml.v3 の既定は字下げ 4 つである。移植元の llm-wiki は、出典の一覧を `json.dumps()` の既定（`ensure_ascii=True`）で書くので、日本語のパスが 16 進のエスケープになる（`docs/porting-plan.html` の「評価ループが frontmatter を壊す」）。移植元で作った wiki を持ち込むと当たる。

このプラグイン自身の書き手（`format_fm_value()`。`json.dumps(…, ensure_ascii=False)`）も、タブや改行、制御文字を含む値をエスケープで書く。今のパーサーはこれを戻さないので、書いた値と読んだ値が違う。

## 2. 決めたこと

### 2.1 範囲と決まり

5 つとも読む。PyYAML には依存しない。lint と検索は標準ライブラリだけで動く。PyYAML は、開発リポジトリの試験で値を照らす相手にだけ使う。

ページの規約（`references/page-conventions.md`）は変えない。書くときは、今までどおり文字列を二重引用符で囲み、配列を 1 行の `[...]` で書く。スクリプトとひな形の書き方も変えない。広げるのは読む側だけである。

決まりは 3 つある。

1. **YAML として正しい書き方のうち、2.2 から 2.6 に挙げたものは、YAML が読む値と同じ文字列、またはその配列にする。** 型には直さない（`true`、`2024`、`null` は今までどおり文字）。比べる相手は、PyYAML の `yaml.load(fm_text + "\n", Loader=yaml.BaseLoader)` である。下の表の箇所は、YAML の値と違ってよい。
2. **0.9.5 がキーの行として読んでいた行は、今も同じキーの行として読む。** 新しい読み方（複数行の `[...]`、ブロックのスカラー、ブロックの配列）が、その行を値の一部として取り込むことはない。0.9.5 が読んでいた欄を、欄ごと失うことはない。
3. **0.9.5 と値が変わるのは、3 の表の書き方だけである。** YAML として誤りの書き方は、3 の表にあるものを除いて、今までと同じ値になる。

2 と 3 は、Sol の指摘（`]` を書き忘れた配列が、後ろの `type:` と `title:` を飲み込む）を受けて足した。最初の設計は「YAML として誤りの書き方は、今までの読み方を変えない」とだけ書いていたが、読む範囲を括弧と引用符だけで決めていたので、守れていなかった。

YAML の値と違ってよい箇所:

| 書き方 | このパーサー | YAML |
| --- | --- | --- |
| 同じキーを 2 度書いた配列 | 2 つをつなぐ | 後のものだけ |
| 値のないキー（`sources:`） | 空の配列 `[]` | `null`（`BaseLoader` は `""`） |
| 入れ子（`graph:` の下のマッピング、配列の要素の `[[a]]` や `a: 1`） | 読まない。要素は書かれた文字（`"[[a]]"`） | 入れ子の値 |
| `key:value`（コロンのあとに空白なし） | `key` が `"value"` | 1 つの文字列（欄にならない） |
| 引用符のない文字列の中の `'`・`"`（`[it's, fine]`） | 引用符の始まりとして読む | 文字 |
| 値の前後の空白 | Unicode の空白をすべて除く（全角の空白、U+00A0 を含む） | 空白とタブだけを除く |
| コメントの始まり | Unicode の空白のあとの `#` もコメントにする（`消費税`、全角の空白、`# メモ` は、値が `消費税`） | 空白とタブのあとの `#` だけ。全角の空白のあとの `#` は値の一部 |
| 行の区切り | LF と CRLF | PyYAML は、U+0085、U+2028、U+2029 でも分ける |
| 1 行の値の、閉じた引用符の直後の `#`（`"a"#c`） | コメントにしない | コメント |
| `]` で終わる行の `[...]` で、行末の `]` が、空白のないコメント（`[a,# メモ ]`）、引用符（`[a, "b]`）、入れ子の括弧の中にあるもの | 1 行の配列（後ろの行は見ない） | 後ろの行まで続く配列 |
| 対にならないサロゲートのエスケープ | 2.5 | サロゲートの文字 |

どれも 0.9.5 までの読み方で、変えない。値の前後の全角の空白を除き、全角の空白のあとの `#` をコメントにするのは、日本語の入力で入りやすい空白を許すためである。新しく読む書き方（字下げの違う配列の要素、複数行の `[...]`）でも、同じ読み方にそろえる。Sol の実装レビューの 3 回目は、複数行の `[...]` と字下げ 4 つの配列で、U+00A0 のあとの `#` がコメントになることを指摘した。0.9.5 が読んでいた 1 行の値と字下げ 2 つの配列も同じに読むので、新しい書き方だけを YAML に合わせると、同じ値が書き方で違う読み方になる。そろえるほうを選び、この表に書いた。

### 2.2 ブロックの配列は、字下げを問わない

値のないキーの次の、空行でもコメントだけの行でもない最初の行で、形を決める。

- その行が `- ` で始まる（字下げは 0 以上のいくつでもよい）なら、その字下げの配列である。同じ字下げの `- ` の行を要素にする。それより深い行（要素の中の入れ子、要素の続きの行）は読まない。字下げのない行で、その配列の要素でないものが来たら、配列は終わる。
- その行が字下げのあるほかの行（`  node_id: x` など）なら、入れ子か、次の行に書いた値である。字下げのない行まで読まない。値は今までどおり空の配列 `[]` になる。

`-` のあとは空白か行末にする（`-x` は要素ではない。`-` のあとのタブは、PyYAML も誤りにする）。`-` だけの行は、空の文字列の要素にする（YAML は `null`、`BaseLoader` は `""`）。

今の読み方（値のないキーのあと、次に読めるキーの行が来るまでの、`  - ` で始まる行をすべて要素にする）から変わるのは、次の 4 つである。

- 字下げが 2 つでない配列を読む（目的）。
- 値のないキーの次の行が `- ` の行でないとき、そのあとの字下げ 2 つの `  - x` を要素にしない。`graph:` の下に `  aliases:` と `  - "a"` を書くと（YAML として正しい。配列を親のキーと同じ字下げで書く形）、今は最上位の `graph` が `["a"]` になる。YAML の値は入れ子のマッピングで、このパーサーは入れ子を読まないので、`[]` にする。グラフは 0.9.5 で lint の形の `graph` を捨てているので、影響しない。lint の `unquoted_strings` が、この形の `graph` を挙げなくなる。`sources:` の次に `  junk`、その次に `  - a` と書いた形（YAML では 1 つの文字列）も、`["a"]` から `[]` になる。
- 配列を、字下げのない行で終える。今は、読まないキーの行を挟んでも続けるので、`sources:` と `  - "a"` のあとに `source-url:` と `  - "b"` を書くと、`sources` が `["a", "b"]` になる。YAML では `b` は `source-url` の要素で、`sources` は `["a"]` である。`["a"]` にする（Sol の実装レビューの指摘。最初の実装は、この変化を 3 の表に書いていなかった）。`sources: ["a", "b"]` から `sourced_from` を 2 本作っていたグラフは、1 本になる。キーでも要素でもない行（`???`）を挟んだ形も、同じに変わる。
- 字下げ 2 つの `  -`（空白なしで行が終わる）を、空の要素として読む。今は、行末に空白があれば空の要素、なければ無視である。参照の欄（`sources` など）は `ref_values()` が空の要素を捨てるので、結果は変わらない。

### 2.3 複数行にまたがる `[...]`

値が `[` で始まり、`]` で終わらず、その行で括弧が閉じていないとき、閉じる `]` の行までを 1 つの配列として読む。

**`]` で終わる行は、0.9.5 までと同じに、1 行の配列として読む。後ろの行は見ない。** 行末の `]` が、空白のないコメントの中（`sources: [a,# メモ ]` 改行 ` b]`）、引用符の中（`[a, "b]`）、入れ子の括弧にあるとき、YAML は後ろの行まで続く配列として読むが、このパーサーは 1 行の配列のまま読む（2.1 の表）。Sol の実装レビューの 1 回目は、この形が YAML と違うことを指摘した。そこで、`]` で終わる行でも先に複数行の読み方を試すようにしたところ、2 回目に、0.9.5 が読めていた 1 行の配列が、後ろのコメントの行を取り込む反例が出た（`sources: [it's]` 改行 `# don't ]`。引用符の読み方が YAML と違うため）。0.9.5 が読めていた値を変えないこと（決まりの 3）を優先し、`]` で終わる行には手を入れない。YAML と違う値になる形は、行末の `]` がコメントか引用符の中にある複数行の配列という、ごく限られた書き方である。

- 行をまたぐところは空白 1 つにして、1 行に書いたときと同じ読み方（`_fm_split_items()`）で要素に分ける。
- 括弧が閉じているかどうかは、YAML と同じに見る。引用符は値の先頭でだけ始まり、引用符のない値の途中の `'` と `"` は文字である（`[x y's,` 改行 ` z]` は、2 行目で閉じる）。要素に分けるときは、1 行の配列と同じく、`'` を引用符の始まりとして読む（2.1 の表）。
- 各行のコメントを捨てる。YAML と同じく、`#` がコメントになるのは、行頭、空白のあと、`,`・`[`・`]`・`{`・`}` のあと、閉じた引用符のあとである（`[a,# コメント`）。`a#b` の `#` は値の一部で、引用符の中の `]`、`,`、`#` も値の一部である。空行は飛ばす。
- 続きの行の字下げは問わない（PyYAML も、括弧の中では字下げを見ない。字下げのない `]` も読む）。
- 次のときは、今までどおり 1 行目だけの文字列として読み、次の行から普通に読む。
  - 1 行目で括弧が閉じている（`title: [下書き] 題名`）。
  - **閉じる前に、字下げのないキーの行（このパーサーがキーの行として読む行）が来る。** `]` を書き忘れたものとして扱う。`tags: [a,` 改行 `type: source` 改行 `title: X]` は、0.9.5 と同じく `tags` が `"[a,"`、`type` が `"source"`、`title` が `"X]"` になる。決まりの 2 を守るための条件である。
  - frontmatter の終わりまで閉じない。
  - 閉じた `]` のあとに、コメントでない文字が続く。
- 値が `[` で始まり `]` で終わる 1 行は、今の読み方を 1 文字も変えない。

キーの行で止めるので、YAML として正しいのに読まない形が、上の `]` で終わる行のほかに、もう 1 つ残る。続きの行が字下げのないキーの形の配列である（`sources: [a,` 改行 `b: c]`。YAML では、2 つ目の要素が 1 組のマッピングになる）。字下げのない行に `https://x/y` と書いた要素も、今のパーサーがキー `https` の行として読むので、同じく止まる。どちらも、要素を字下げして書けば読む。グラフは、YAML の配列より少ない数しか読めないので、`unread_field` に挙げる。

閉じない `[` のたびに frontmatter の終わりまで探すと、行の数の 2 乗の時間がかかる（Sol の測定で、`k0: [`、`k1: [` … を 2,000 行並べると約 2.8 秒）。キーの行で止めるので、探す範囲は次のキーの行までになり、全体で行の数に比例する。

### 2.4 キー

キーの行を、次の 3 つの形で読む。どれも、行頭に字下げがなく、キーの中身は今までどおり `\w+`（日本語を含む）である。

- `type: x`（今までどおり）
- `"type": x`、`'type': x`
- `type : x`、`"type" : x`（コロンの前の空白。タブは読まない。PyYAML もタブは誤りにする）

コロンのあとに空白がない形（`type:x`）は、今も引用符のないキーで読んでいる。YAML では欄にならないが、今の読み方を変えない。引用符つきのキーでも同じに読む。

同じキーを、引用符つきと引用符なしで 2 度書くと、同じキーを 2 度書いたのと同じになる（文字列は後の値、配列はつなぐ）。0.9.5 が読んでいた欄と同じキーを、読めなかった形でもう 1 度書いていたページは、その欄の値が変わる（`type: "a"` のあとに `"type": "b"` を書くと、`"a"` から、YAML と同じ `"b"` になる）。

### 2.5 二重引用符の中のエスケープ

YAML 1.2 が決めているエスケープを、YAML の意味の文字にする。

- 1 文字のもの: `\0`、`\a`、`\b`、`\t`（と `\` のあとのタブ）、`\n`、`\v`、`\f`、`\r`、`\e`、`\` のあとの空白、`\"`、`\/`、`\\`、`\N`（U+0085）、`\_`（U+00A0）、`\L`（U+2028）、`\P`（U+2029）
- 16 進のもの: `\x` と 2 桁、`\u` と 4 桁、`\U` と 8 桁

**値の中に、戻せないエスケープが 1 つでもあれば、その値の全体を 0.9.5 までと同じに読む**（`\"` と `\\` だけを戻し、ほかの `\` は書かれた文字のまま残す）。戻せないエスケープは 2 種類ある。

- YAML にないエスケープ（`\d`、16 進の桁が足りない `\u`、末尾の `\`）。YAML としては誤りの値で、PyYAML は frontmatter の全体を読めない。`"\d+\n"` は、`\n` も改行にせず、書かれた文字のまま読む。`"C:\Users\new.pdf"` も同じである（`\U` のあとが 16 進 8 桁でない）。決まりの 3 を守るための条件である。Sol の指摘（最初の設計は、戻せるものだけを戻していたので、`"\d+\n"` の `\n` だけが改行に変わった）を受けて改めた。
- UTF-8 に書けない文字になるもの。対にならないサロゲート（`\uD83D` だけ）と、U+10FFFF を超える値である。PyYAML は、前者をサロゲートの文字にし（それを UTF-8 で書き出すと `UnicodeEncodeError` になる。実測）、後者で `ValueError` を出す。このパーサーは、UTF-8 に書けない文字を値に入れない。

`\uD83D\uDE00` のように、上位と下位のサロゲートを `\u` で続けて書いたものは、1 文字（U+1F600）にまとめる。JSON の書き方で、`json.dumps()` の既定が BMP の外の文字をこう書く。まとめるのは、この `\u` を 2 つ続けた形だけである（`\U0000D83D\U0000DE00` は、対にならないサロゲートとして扱う）。PyYAML は、サロゲート 2 つの文字列にする。

一重引用符は、今までどおり `''` だけを戻す。

**変わる値。** この節だけが、今読めているページの値を変える。二重引用符の中に、`\"` と `\\` のほかのエスケープを書いていて、そのすべてが YAML の決めているエスケープである値である。規約（`\` は `\\` と書く）にない書き方である。

| 書いた値 | 今 | 0.9.6 |
| --- | --- | --- |
| `消費税` を 16 進のエスケープで書いた値（PyYAML や `json.dumps` の既定） | エスケープの文字のまま | `消費税` |
| `"a\tb"`（`format_fm_value()` が書く） | `\` と `t` | タブ |
| `"C:\books\new.pdf"`（`\` を重ねていない） | 書かれたままのパス | `\b` が後退、`\n` が改行 |
| `"$\theta$ の推定"`（同上） | 書かれたまま | `\t` がタブ |
| `"C:\Users\new.pdf"`、`"\d+\n"`、`"$\theta$ と $\sigma$"`（YAML にないエスケープを含む） | 書かれたまま | 書かれたまま（変わらない） |

3 行目と 4 行目は、今のこのパーサーでは作者の意図どおりに読めている値が、変わる。それでも YAML の意味にする理由:

- その値は、YAML を読む道具（Obsidian のプロパティ、PyYAML、0.9.4 までのグラフ）では、今も制御文字である。このパーサーだけが別の値を見ている。0.9.5 が直したのと同じ種類の食い違いである。
- 1 行目と 2 行目は、今のこのパーサーでは壊れて見える値である。日本語が 16 進のエスケープのままだと、題名で検索に当たらず、`sources:` はページに解決しない。移植元の llm-wiki が書く形なので、持ち込んだ wiki で起きる。
- 自分の書き手が書いた値を、自分で読み戻せる（`parse(format_frontmatter(meta)) == meta` が、制御文字を含む値でも成り立つ）。
- 3 行目は、`raw:` なら lint の `missing_raw` が挙げる（その名前のファイルがない）。取り込みの手順は、`\` を `\\` と書くと決めている（`commands/ingest.md`、`tests/wiki/test_frontmatter_raw.py`）。
- 5 行目のとおり、`\` を重ねていない値の多くは、YAML にないエスケープを含むので変わらない。Windows のパスは `\U`（`Users`）、`\P` と `\D` のほかの大文字、`\w`、`\s`、`\d` などを含めば変わらず、LaTeX は `\s`（`\sigma`）、`\p`（`\pi`）、`\m`（`\mu`）、`\l`（`\lambda`）などを含めば変わらない。

検討して採らなかった案:

- 読まない（今のまま）。値は失わないので、後退は起きない。ただし 1 行目と 2 行目が残り、YAML を読む道具との食い違いも残る。
- 16 進のエスケープ（`\x`、`\u`、`\U`）だけを読む。`\t` と `\n` を残せば、Windows のパスと LaTeX の多くは変わらない。ただし YAML の値とも今の値とも違う 3 つ目の読み方になり、`format_fm_value()` が書く `\t`、`\n` を読み戻せない。`"C:\x64\bin"` は変わる。
- 制御文字になるエスケープを lint が挙げる検査を足す。検出結果のキーが増え、MCP の `lint` の形も変わる。今回は足さず、範囲外に残す（6）。

手元の wiki（このリポジトリの `wiki/` と、作者のユーザースコープの wiki）とプラグインの試験データには、二重引用符の中に `\"` と `\\` のほかの `\` を書いた値は 1 つもなかった（4）。

### 2.6 `|` と `>` のブロックのスカラー

コメントを除いた値が、ブロックのスカラーの見出し（`|`、`>`、`|-`、`>+`、`|2`、`>1-` など）だけのとき、続く字下げのある行を、YAML と同じ値に読む。

- 字下げの決め方（最初の空でない行の字下げ。数字で指定してもよい）、`|` が改行を残すこと、`>` の折りたたみ（字下げどおりの行どうしは空白 1 つ、空行は改行、深く字下げした行は改行を残す）、末尾の改行（`-` は除く、`+` は残す、指定がなければ 1 つ残す）を、PyYAML の `scan_block_scalar()` と同じにする。
- frontmatter の最後の行にも改行があるものとして読む。PyYAML に frontmatter の本文だけを渡すと、最後の行に改行がないので、ブロックのスカラーが最後の欄のときだけ末尾の改行が付かない。位置で値が変わらないように、`fm_text + "\n"` を読んだ値にそろえる。
- 値は 1 つの文字列である。`title: >` 改行 `  長い題名` は `"長い題名\n"` で、末尾に改行が付く。YAML の値のとおりにする。改行を付けないなら `>-` と書く。
- 中身の行は字下げがあるので、キーの行を取り込むことはない（決まりの 2）。
- 配列の要素に書いたブロックのスカラー（`- |`）は読まない。要素は書かれた文字（`"|"`）になる。

今の値は記号（`">"`、`"|-"`）なので、読めているページの値を変えない。見出しと同じ文字だけの値（`sep: |`）を文字として読んでいたページは変わるが、YAML でも、それは文字ではなくブロックのスカラーである。

**末尾の改行が付いた値の使われ方。** 改行を除いて使う欄と、そのまま比べる欄がある。

- `sources`、`raw`: `ref_values()` が前後の空白を除くので、改行が付いても解決する（`sources: >` で `sourced_from` ができる）。
- `type`、`kind`: 日本語の別名（`ソース`）は、前後の空白を除いて英語に直すので当たる。英語の値（`source`）は、改行が付いたままなので当たらない。`type: >` 改行 `  source` は、`type` が `"source\n"` のページになり、`missing_raw` などの `type == "source"` の検査に掛からない。PyYAML で読んでいた 0.9.4 までのグラフも同じ値だった。`>-` と書けば当たる。lint の `unquoted_strings` は、ブロックのスカラーの欄を挙げる（2.8）。
- `title`、`tags`: 改行が付いたまま、検索の出力、索引、ノードに入る。

### 2.7 読まないまま残す書き方

- 次の行に書いた値（`title:` 改行 `  "x"`、`sources:` 改行 `  [a, b]`、`-` 改行 `  a`）。値は `[]`、要素は空のまま。
- 複数行にまたがるスカラー（引用符のない値や二重引用符の値の続きの行。配列の要素の続きの行を含む）。1 行目だけを読む。PyYAML の `yaml.dump()` は、80 桁を超える英語の値を空白で折り返すので、この形を書く。値の後ろが落ちる。今回の 5 つに入っていないので、範囲外に残す（6）。
- 入れ子、アンカー（`&`、`*`）、タグ（`!!str`）、マージキー（`<<`）、`? key` の形のキー、`\w+` でないキー（`source-url`）、エスケープを含むキー。
- 続きの行が字下げのないキーの形の、複数行の `[...]`（2.3）。
- 複数行の `[...]` の中の、要素の途中の空行（YAML は改行にする）と、行末の `\` での継続。空白 1 つでつなぐ。

### 2.8 同じ行の読み方を使う関数

行の読み方を 1 つの関数（`_fm_entries()`）にまとめ、3 つの関数がそれを使う。

- `parse_frontmatter_text()`: 値の辞書。
- `top_level_keys()`: キーの行として読んだ行のキーを、引用符を外して返す。複数行の `[...]` の中の行と、ブロックのスカラーの中の行は、キーの行に数えない。
- `unquoted_string_keys()`（lint の `unquoted_strings`）: 字下げの違う配列と複数行の `[...]` の要素も、1 行のときと同じに調べる。ブロックのスカラーは、二重引用符で囲まれていない文字列として挙げる（今も、記号の `>` を引用符のない文字列として挙げている）。

`fullwidth_colon_keys()` は、行頭の `キー：` を見るだけなので変えない。`wiki_help.py`（コマンドの frontmatter。`_fm_unquote()` を使う）は、エスケープの読み方が同じに変わる。プラグインのコマンドの frontmatter には `\` がない。

グラフの `_unread_fields()` の判定は変えない。YAML のノードと、このパーサーの結果（`top_level_keys()` と値の辞書）を比べる作りなので、読めるようになった書き方では、診断が出なくなる。

| 書き方 | 0.9.5 | 0.9.6 |
| --- | --- | --- |
| 字下げのない配列、字下げ 4 つの配列、複数行の `[...]` | `unread_field` | 出ない。`sourced_from` ができる |
| `"type": x`、`type : x`、その形で 2 度目を書いた欄 | `unread_field` | 出ない |
| アンカー（`sources: &s [a]`）、マージキーだけで来た欄 | `unread_field` | `unread_field`（変わらない） |
| 次の行に書いた `[a, b]`、`? sources`、エスケープを含むキー | `unread_field` | `unread_field`（変わらない） |
| 続きの行が字下げのないキーの形の `[...]` | `unread_field` | `unread_field`（変わらない） |

この診断は、キーを書いた回数と配列の要素の数を比べる。値の中身は比べない（0.9.5 の設計 2.4）。数が合ったまま値が違う読み方（たとえば、2.1 の表の箇所）は、今までどおり挙がらない。値を比べる診断は、範囲外に残す（6）。

`wiki_graph_extract.py` は、説明の文面と、GraphML の書き出し（2.11）を直す。

### 2.9 キャッシュ

`wiki_search.py` のパースキャッシュ（`PARSE_CACHE_SCHEMA`）は、ファイルの SHA-256 が同じなら、保存した `meta` を使う。パーサーを変えても、ファイルが変わらなければ古い値のままになる。4 から 5 に上げる。CLI の検索（`.wiki-cache/`）と、MCP のサーバー（`wiki_index.py` が同じ `collect_pages()` を使う）の両方に効く。

索引は作り直さない。索引の項目はセクションごとで、項目のハッシュは、題名を含む検索用の本文（`searchable_text`）から作る。パースキャッシュを読み直して題名が変われば、ハッシュが変わり、その項目だけが入れ替わる。`wiki_index.py` の fingerprint は変えない。

### 2.11 GraphML に書けない文字

エスケープを YAML の意味で読むと、値に制御文字が入りうる（`title: "a\0b"` の NUL）。Sol の指摘のとおり、GraphML の書き出し（`write_graphml_file()`）は、それをそのまま書く。書き出しは成功するのに、XML として読めないファイルになる。JSONL と SQLite は、同じ値を持てる。

これは、エスケープがなくても起きる。0.9.5 のパーサーは、ファイルに直接書いた制御文字（U+0001 など）を値として読むので、同じ壊れた GraphML ができる。0.9.4 までは、PyYAML がエスケープを制御文字にしていた。

GraphML に書く文字列で、XML 1.0 に書けない文字（タブ、LF、CR のほかの制御文字、サロゲート、U+FFFE、U+FFFF）を置き換える。JSONL と SQLite には、元の値のまま書く。値を読む側（パーサー）では、YAML の値を変えない。

- 値（題名、種類、述語、出典など）は、書けない文字を U+FFFD にする。
- ID（ノードとエッジの ID、エッジの両端）は、別の ID と同じ文字列にならないように書く。書けない文字を U+FFFD と `{16 進のコード}` に、ID の中の U+FFFD を U+FFFD 2 つにする。XML に書ける文字だけで、U+FFFD を含まない ID は変えない。値と同じに U+FFFD 1 つに置き換えると、`graph.node_id` が NUL を含むノードと U+FFFD を含むノードが同じ ID になり、GraphML の中で 1 つのノードになって、その間のエッジが自分を指す（Sol の実装レビューの指摘）。
- 値の中の CR は、XML を読む側が LF にする。置き換えない。

## 3. 変わること（利用者から見て）

ページの規約どおりに書いたページ（文字列は二重引用符、エスケープは `\"` と `\\` だけ、配列は 1 行の `[...]` か字下げ 2 つの `  - `）は、どの道具の値も変わらない。

変わるのは、次の書き方のページである。lint、検索、統計、MCP、グラフの最上位の欄が、同じに変わる。

| 書き方 | 今（0.9.5） | 0.9.6 |
| --- | --- | --- |
| 字下げが 2 つでないブロックの配列 | `[]` | 配列 |
| 複数行にまたがる `[...]`（1 行目が `]` で終わらず、続きの行に、字下げのないキーの行がないもの） | 1 行目だけの文字列 | 配列 |
| `"type": x`、`'type': x`、`type : x` | 読まない | 読む。同じキーの欄がほかにあれば、2 度書いたのと同じになる |
| 二重引用符の値で、`\"` と `\\` のほかのエスケープがあり、すべて YAML のエスケープであるもの | 書かれた文字 | YAML の意味の文字 |
| `\|`、`>` のブロックのスカラー | 記号だけの文字列 | YAML の値 |
| 値のないキーの次の行が `- ` の行でないときの、あとの字下げ 2 つの `  - x` | そのキーの要素になる | ならない |
| 配列のあとに、字下げのない、読まない行（`source-url:` など）を挟んだ、あとの字下げ 2 つの `  - x` | 前のキーの要素になる | ならない |
| 字下げ 2 つの `  -`（行末に空白なし） | 無視 | 空の要素 |

YAML として誤りの書き方のうち、値が変わるのは、この表に当たるものである。たとえば、`]` を書き忘れた `tags: [a,` のあとに、キーの行を挟まずに、字下げした行と対にならない `]` があると、`tags` は `"[a,"` から、そこまでの配列になる（ほかの欄は変わらない）。

読めるようになった欄には、今まで掛からなかった検査が掛かる。たとえば、字下げのない `sources:` は、lint の `unresolved_sources` と `unquoted_strings` の対象になり、`"type": x` と書いていたページは、`type` のないページではなくなる。ブロックのスカラーで書いた `type` は、末尾の改行のために、決まった値に当たらない（2.6）。

グラフは、`unread_fields` に挙がっていた欄を読むようになり、`sourced_from`、`summarizes_raw`、ノードの種類が変わる。グラフ層を使っている wiki は、`wiki_graph_extract.py` で作り直す。GraphML は、XML に書けない文字が U+FFFD になる（2.11）。

8. キャッシュ: 古い形式（4）のパースキャッシュに、同じ SHA-256 で古い `meta` を入れておくと、読み直す。
9. 閉じない `[` を 40,000 行並べても、行の数に比例する時間で終わる。
10. GraphML: エスケープで書いた NUL と、ファイルに直接書いた制御文字のある題名で、書き出した GraphML を XML として読める。ノードの値は元のまま。`graph.node_id` が NUL、U+0001、U+FFFD を含む 3 つのノードが、GraphML でも別の ID のノードで、その間のエッジが自分を指さない。

`tests/wiki/test_graph_frontmatter_values.py`（0.9.5）は、読めるようになった書き方の期待値を反転する。`unread_field` が出ず、`sourced_from` ができ、lint も同じページに解決する。アンカー、マージキー、次の行に書いた `[a, b]`、`? sources`、エスケープを含むキー、続きの行が字下げのないキーの形の `[...]` では、引き続き出る。`tests/wiki/test_frontmatter_raw.py` の、`\` を重ねていない Windows のパスの試験は、「2 つのパーサーが違う値に読む」から「どちらも同じ（壊れた）値に読む」に変え、YAML にないエスケープを含むパスが書かれた文字のまま読めることを足す。

プラグインの `eval/scripts/test_frontmatter.py`（標準ライブラリだけ。プラグインの CI が動かす）にも、5 つの書き方の試験を足す。

既存の試験も通す: `tests/wiki/`、`tests/graph/`、プラグインの `eval/scripts/`、`eval/decisions/`、`eval/retrieval/`、`skills/info-hive/scripts/test_link_resolution.py`。

## 6. 範囲外

- 複数行にまたがるスカラー（引用符のない値と二重引用符の値の続きの行）と、次の行に書いた値を読むこと。
- YAML が制御文字に読むエスケープ（`"$\theta$"` の `\t`）を、lint が挙げること。
- `unread_field` を、値の中身の比較、`type`・`kind`・`sources`・`raw` のほかの欄、グラフを使わない wiki の lint に広げること。
- `title:` に値がない（`[]` になる）ページで、検索の `collect_pages()` が文字列と配列を足して止まること（今もある）。
- `type` と `kind` の値の前後の空白（ブロックのスカラーの末尾の改行を含む）を除いて比べること。
