# 今の取り込みと MarkItDown の抽出の比較（2026-11-15）

wiki と rag の取り込みで MarkItDown を使うかを決めるために、今の取り込みの抽出と MarkItDown 0.1.9 を比べた。比べた軸は、速度、機械的な指標、Sol（GPT-6.1 Sol）による品質の判定である。計測のスクリプト、試料、出力、判定の全文は [markitdown-benchmark-2026-11-15/](markitdown-benchmark-2026-11-15/) にある。

## 結論

今回の試料は、Office で作った小さな架空の文書だけである（「制約」の節を参照）。結論は、その範囲での観測として読む。

- **PDF では、MarkItDown が rag の PDFium の抽出（OCR なし）を下回った。** Office が書き出した 4 つの PDF のすべてで、PDFium がもっとも良かった。Sol の総合点は 4、4、5、5 で、原本の順に読めた割合はすべて 1.0 だった。MarkItDown には、意味を変える誤り（Sol の言う「致命的」）が 3 つの PDF で 5 つあった。
  - 2 段組みの PDF では、左右の段を同じ行に並べた表を作った。
  - スライドの PDF では、左右の本文を語の途中で交互につないだ。
  - 表計算の PDF では、電気代の列を空にして、値を隣の列に入れた（列のそろった表の行は 3/7）。
  MarkItDown は、ページの区切りも出さない。
- **Office の形式（DOCX、PPTX、XLSX、XLS）と EPUB には、MarkItDown が使える。** どれも Sol の総合点は 5 で、網羅率と順に読めた割合は 1.0、表の列もすべてそろった。今の wiki には、これらの形式を取り込む手順がない。XLSX と XLS では、式の計算済みの値（合計）も読めた。ZIP も総合 5 だったが、中身が DOCX、CSV、JSON の試料しか試していない。
- **HTML は、今の `wiki_fetch.py` のほうが良い。** 本文はどちらも欠けなかった。MarkItDown はナビ、広告、Cookie の案内、フッターを残し（Sol の雑音 2）、`wiki_fetch.py` は本文だけを残した（雑音 5）。
- **CSV、JSON、XML は、どちらでも差がない。** 今の手順は、文字コードを確かめてそのまま読む。MarkItDown は、CSV を表にし、JSON と XML は元のバイト列のまま返す。どちらも総合 5 で、Shift_JIS の CSV もどちらも正しく読んだ。
- **MarkItDown の費用は、起動にかかる時間にある。** Python の起動は 0.06 秒、`import markitdown` までで 3.3〜3.8 秒かかった。変換そのものは 1 回 0.34 秒以下である。依存の大きさは、本体だけで 97 MiB、今回使った追加の依存を入れると 189 MiB になる。

Sol の総合点は「LLM がこの出力だけを読んで要約ページを書くときに使えるか」を判定したもので、rag の検索とチャンクの分け方への向き不向きは評価していない。

形式ごとに使い分けると、次のようになる。

| 形式 | 使う方式の候補 | 理由 |
| --- | --- | --- |
| PDF | rag の PDFium の抽出（wiki もこれにそろえる） | Office の PDF では、読み順、表の行、ページの目印がもっとも良かった |
| DOCX、PPTX、XLSX、XLS、EPUB | MarkItDown | 今は手順がない。どれも総合 5 |
| ZIP | MarkItDown（中身の形式ごとに確かめる） | DOCX、CSV、JSON の ZIP は総合 5。PDF を含む ZIP では、PDF と同じ問題が出るはずだが、試していない |
| HTML | 今の `wiki_fetch.py` | 本文の外の雑音を除く |
| CSV、JSON、XML | 今の手順（どちらでもよい） | 差がない。今の手順は依存がない |

## 計測の方法

### 速度

- **変換**: 1 回目（import と初期化を含む）を除いた 5 回の中央値。
- **起動込み**: Python のプロセスを起こし、計測のスクリプトを読み込んで 1 回だけ変換し、終わるまでの時間。3 回の中央値。pdftotext と wiki_fetch は、変換のたびに子プロセスを起こすので、2 つの値の差が小さい。
- **MarkItDown の起動の内訳**: 「Python の起動だけ」「`import markitdown` まで」「`MarkItDown()` の作成まで」「1 回目の変換まで」の 4 段に分けた。各段は前の段を含み、それぞれ 3 回の中央値をとった。

### 機械的な指標

出力と正解は、比べる前に同じ形にそろえる。NFKC にそろえ、Markdown の記号（`| * # _ > \` と逆引用符）を空白にし、数字の桁区切りのコンマを除き、続いた空白を 1 つにまとめる。空白は消さずに残し、数値どうしの境目を保つ。正解の文字列を探すときは、文字のあいだに空白 1 つ（PDF の行の折り返しなど）を許す。数字で始まる正解は、前に数字か小数点が続く位置には当てない。数字で終わる正解は、後ろに数字か小数点が続く位置には当てない。これで、「3000」が「30000」や「30001500」に当たらない。

- **網羅率**: 正解の文字列のうち、出力に見つかったものの割合。
- **順に読めた割合**: 正解の並びのうち、出力の中で原本の順に並べられる最長の部分列の長さを、正解の全体の数で割ったもの。正解ごとに、出力の中で当たった位置のどれを使ってもよい。欠けた文も分母に入れるので、段の混線で照合できなくなった文は、この値を下げる。前のほうの入れ替わり 1 つで、後ろの全部を落とすことはしない。
- **1 行に残った表の行**: 正解の表の行（見出しの行を含む）のうち、すべてのセルが、出力の同じ 1 行に正解の順で見つかった行の数。出力の 1 つの行は、正解の 1 つの行にしか数えない。表を 1 行につないだ出力を、全部の行が残ったとは数えないためである。
- **列のそろった表の行**: Markdown の表のうち、2 行目が区切りの行（`|---|`）のものを取り出す。その中で正解の見出しの行と同じセルが並ぶ行を探し、それより後ろで、本体の行のセルが見出しと同じ列にそのまま入っている行の数を数える。見出しの行は、表の 1 行目でなくてよい（MarkItDown は DOCX の表の前に空の見出しの行を足す）。見出しを残して本体だけ右へずれた表や、値が隣の列に入った表は数えない。表を出さない出力は「表なし」とする。
- **位置の目印**: 改ページの文字（U+000C）、`## p. N`、`<!-- Slide number: N -->`、シートの見出し、ZIP の中のファイルの見出しを、それぞれ数える。
- **自己試験**: 計測のスクリプトは、指標を使う前に、2 回のレビューで挙がった反例を正しく数えることを、15 個の assert で確かめる。反例は次のとおりである。
  - 表を 1 行につないだ出力。
  - 見出しを残して本体を右へずらした表。
  - 値が隣の列に入った表。
  - 区切りの行のない「|」の行。
  - 空の見出しの行のあとに本当の見出しがある表。
  - 10 倍にした数値と、区切りなしにつないだ数値。
  - 先頭の 1 つが後ろへ移っただけの並び。
  - 同じ値が何度も出てくる表。
  - 混線した文。

### Sol の判定

出力を試料ごとに A〜D の記号に置き換えて、方式の名前を伏せた。それを、原本、正解、[判定の依頼](markitdown-benchmark-2026-11-15/judge/task.md)と一緒に渡した。網羅、読み順、構造、雑音、位置、総合の 6 つの軸を 1〜5 で採点させ、意味を変える誤りを「致命的」として挙げさせた（effort high、読み取り専用）。

- 判定のあいだは、方式の名前が分かる出力と結果のファイルを、worktree の外に移した。
- 依頼には、画面に見えない改ページの文字（U+000C）をページの区切りとして数えるように書いた。
- 判定と出力を結び付けるために、`judge/manifest.json` に写しごとの SHA-256、対応表の SHA-256、それらのダイジェストを書いた。Sol には、読んだダイジェストを判定の JSON の `judge_digest` に書かせた。集計のスクリプトは、ダイジェスト、写し、出力、対応表がすべて一致するときだけ集計する。

- **rag（PDFium）**: 4 つとも、順に読めた割合が 1.0 で、致命的な誤りもなかった。2 段組みでも、左の段を読み終えてから右の段に進んだ。Office が書き出す PDF は、文字を論理的な順に並べていて、PDFium はその順に文字を返すので、読み順が崩れなかったのだろう（推測）。ほかのソフトが作った PDF や、組版の凝った書籍で同じ結果になるかは、この試料からは分からない。表は Markdown の表にならず、セルを空白で区切った行として残る。
- **MarkItDown**: 1 段組みの文書では、表を Markdown の表にしようとしたが、列のそろった行は 0/4 だった。表がページをまたいだため、1 ページ目の部分は表にならず、2 ページ目の部分には見出しの行がなく、セルの中の改行で行も割れた。2 段組み、スライド、表計算の PDF では、結論に挙げた致命的な誤りがあった。表計算の PDF では、文字列はすべて残り（網羅率 1.0、1 行に残った表の行 9/9）、列だけがずれた（列のそろった表の行 3/7）。表の形をしていても列がずれていると、表がない出力より誤解を招く。
- **pdftotext と pdfminer**: 本文はほぼ残る。ただし、表をセルの列ごとに並べ、段落と箇条書きを 1 行につなぐ。pdfminer は、2 段組みで文の途中に反対の段を挟み（致命的 2）、表計算の PDF で費目と値の塊の順を入れ替えた（致命的 1）。
- **ページの目印**: pdftotext と pdfminer は改ページの文字でページを区切り、rag は `## p. N` の見出しで区切る。MarkItDown は区切りを出さない。PDF のフッターにページ番号が印刷されていれば、その文字が本文に残るだけである（handbook.pdf の「ページ 1」など）。Sol の位置の点が、文書の PDF では 5、スライドと表計算の PDF では 3 と 2 になったのは、このためである。
- **ヘッダーとフッター**: 4 方式とも、ヘッダーの「社外秘・試料」とフッターのページ番号を本文に残した（Sol の雑音 3）。

後ろの段のほうが短いことがあるのは、測るたびのばらつき（0.5 秒ほど）のためである。起動の時間のほとんどは `import` で、初期化と 1 回目の変換の時間は、ばらつきより小さい。試料が小さい（1〜5 ページ）ので、変換の時間の差は数十ミリ秒にとどまる。差が大きいのは起動のほうで、何度も変換するなら、プロセスを使い回す必要がある。

### 依存の大きさ

Python 3.12 の空の環境に入れたときの `site-packages` の大きさである。測り方は [scripts/measure_footprint.py](markitdown-benchmark-2026-11-15/scripts/measure_footprint.py) に、パッケージの一覧は [footprint.json](markitdown-benchmark-2026-11-15/footprint.json) にある。

| 入れたもの | 大きさ | パッケージの数 |
| --- | --: | --: |
| markitdown 0.1.9（追加の依存なし） | 97.0 MiB | 19 |
| markitdown[docx,pdf,pptx,xls,xlsx] 0.1.9 | 188.6 MiB | 37 |
| pdfminer.six 20260107 | 19.5 MiB | 5 |
| pypdfium2 5.15.2 | 8.1 MiB | 1 |

今の wiki の抽出（`wiki_fetch.py`、`wiki_encoding.py`）は、標準ライブラリだけで動く。MarkItDown を入れると、wiki が初めて 100 MiB 近い依存を持つことになる。

## 制約

- 試料は小さく、すべて Office で作った。書籍の PDF（組版のソフトが作るもの、縦書き、注、段の多いもの）は試していない。ほかのソフトが作った DOCX、マクロ、結合したセル、画像の多い PPTX も試していない。PDF について「rag の PDFium が良い」と言えるのは、Office が書き出した PDF までである。
- pdftotext は Xpdf 4.00 で測った。Poppler の pdftotext では、読み順と表の結果が違うかもしれない。
- wiki の手順では、PDF を `pdf-reading` スキルがあればそれで読み、なければ pdftotext か pdfminer で読む。実際の取り込みでは、Claude Code の Read が PDF を直接読むこともある。その場合のテキストは比べていない。
- 機械的な指標は、正解の文字列が、出力のどこに、どの順で、どの列にあるかを見る。文の意味が保たれているかまでは見ない。意味の取り違えは Sol の判定で見た。
- Sol の判定は、指標を直したあとの 1 回を集計に使った。点のぶれは測っていない。出力の書き方（`## p. N` など）から、方式を推測できた可能性もある。最初の判定（[judge-1](../agent-runs/2026-11-15-markitdown-benchmark-review/judge-1/)）では、改ページの文字を見落とし、pdftotext と pdfminer の位置を 2 点にしていた。改ページの文字を数えるように依頼を直して、判定をやり直した。総合点が違ったのは、2 段組みの pdftotext（2 から 3）と pdfminer（1 から 2）だけである。致命的な誤りの数は、表計算の PDF の pdfminer（0 から 1）と MarkItDown（1 から 2）で増えた。どの PDF でも PDFium の総合点がもっとも高く、2 段組みと表計算の PDF で MarkItDown がもっとも低いことは、2 回とも同じだった。
- 速度は 1 台の PC で測った。試料は C の SSD に置き、D ドライブの遅い外付けのディスクは使っていない。

## 次に決めること

1. wiki の PDF の手順（pdftotext か pdfminer）を、rag と同じ PDFium の抽出にそろえるか。今回の試料では、読み順と表の両方で PDFium が上回った。決める前に、書籍などの Office でない PDF でも同じ傾向になるかを確かめる必要がある。
2. MarkItDown を、Office の形式、EPUB、ZIP の取り込みだけに使うか。起動にかかる約 3.5 秒と、約 190 MiB の依存を、どこで負うかも決める。wiki のスクリプトにするか、プロセスが続く rag のワーカーに置くかである。
3. 書籍の PDF で同じ比較をするか。作者の電子書籍を使うと、本文が外部（Sol）に送られる。

## 再現の手順

`export_office.ps1` は Office の COM を使うので、Office の入った Windows で動かす。

```powershell
cd docs/research/markitdown-benchmark-2026-11-15
uv run --script scripts/make_corpus.py
pwsh -NoProfile -File scripts/export_office.ps1
uv run --script scripts/run_bench.py
python scripts/prepare_judge.py <worktree の外の対応表のパス> --discard-judgement
# 判定のあいだ、outputs/、results.json、summary.* を worktree の外に移し、Sol に判定させる
python <ask-codex のスクリプト> ask --task-file judge/task.md --model sol --effort high --out judge/sol-result.md
# outputs/ などを戻し、対応表を judge/mapping.json に写す
python scripts/aggregate.py
python scripts/measure_footprint.py <作業用のディレクトリ>
```

- `prepare_judge.py` は、前の判定（`judge/sol-result.md`）か対応表が残っていると止まる。`--discard-judgement` を付けると、それらを消してから写し、`judge/manifest.json` を書き直す。
- `aggregate.py` は、次の 4 つがすべて一致するときだけ集計する。
  - 判定の `judge_digest`
  - `manifest.json` のダイジェストと、そこに書かれた SHA-256
  - `judge/` の写しと `outputs/` の出力
  - `judge/mapping.json`

  写し直したあとに、前の写しを読んだ判定が書かれても、ダイジェストが違うので止まる。
- `run_bench.py --metrics-only` は、保存した出力から指標だけを計算し直す。速度、出力、計測したときの版の記録（`versions`）は変えず、計算し直した環境を `metrics_env` に別に残す。`--startup` は、MarkItDown の起動の時間を段ごとに測り直す。

今回の書き出しでは、Word のところで 2 回つまずいた。

- `Documents.Open` に読み取り専用の引数を渡すと、自動化の Word が応答しなくなった。
- Windows PowerShell 5.1（`powershell -File`）で動かすと、`Documents.Open` が `null` を返した。

PowerPoint、Excel、ZIP は、`export_office.ps1` で書き出せた。2 つの PDF（handbook.pdf と handbook-2col.pdf）は、pwsh 7 の `Start-Job` の中で同じ Word の呼び出し（引数はパスだけ）を実行して書き出した。`pwsh -File` で最後まで通るかは確かめていない。
