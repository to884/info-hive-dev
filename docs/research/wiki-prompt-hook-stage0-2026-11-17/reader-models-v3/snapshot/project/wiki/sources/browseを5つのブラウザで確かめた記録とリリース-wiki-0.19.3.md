# browse を 5 つのブラウザで確かめた記録と wiki 0.19.3 のリリース

0.18.0 と 0.19.0 で残していた「Chromium のほかのブラウザでの確かめ」を 0.19.1 で行い、そこで見つかった `/favicon.ico` の 404 を直して、wiki 0.19.3 として出した記録である。原本は `docs/agent-runs/2026-11-15-wiki-browse-cross-browser/` にある。確かめの手順と注意は [[browseの画面の確かめ方]] にまとめてある。

## 経緯

1. ブラウザの試験（`browse.test.mjs`、`findability.test.mjs`）を、Firefox、WebKit、Edge、Chrome で、静的とサーバーの両方の方式で流した。5 つのブラウザで画面を撮って見比べ、見た目の違いはなかった。
2. Firefox の静的の方式で 4 件が落ちた。Firefox の Playwright が `file://` の要求を捕まえないためで、試験の道具の制約だった。0.19.0 で「確かめてはいない」とした 3 件は、これが原因だった。
3. 製品の Chrome と Edge のサーバーの方式で 1 件ずつ落ちた。ページが `<link rel="icon">` を持たないので `/favicon.ico` を要求し、404 になっていた。Playwright に同梱の Chromium は要求しないので、CI では見えなかった。
4. 作者が直すことを決めた。ページと 404 の HTML の `<head>` に `<link rel="icon" href="data:,">` を出した。CSP は変えていない。
5. Sol の敵対的レビューは 1 回で、致命と重大は 0 件だった。503 と 500 のテキストの画面に要求が残るという指摘（推測）は、製品の Chrome と Edge で測って確かめた。残るが、その画面は応答そのもののエラーがもともとコンソールに出る。どの画面でも出さないには、トークンのない `/favicon.ico` にサーバーが答える必要があり、要求の境界（構造の直しの設計 8.1）を変える。0.19.3 の約束は、ふつうに描いたページと 404 の HTML にとどめた。
6. 版は 0.19.3 にした。0.19.2 は、別のセッションが同じ日に出していた。
7. 子の PR（to884/info-hive-wiki#66）の CI 4 つと、子の head を指した親の PR（to884/info-hive-dev#122）の CI 11 が通ってから、子をマージした（`5bd4ec5`）。
8. 親の参照をマージコミットに付け替えて push したが、親の CI の `pull_request` の実行が始まらなかった。そのあいだに main に別の PR（to884/info-hive-dev#123）が入り、`wiki/log.md` が競合していたためである。GitHub は、競合のある PR では `pull_request` のワークフローを走らせない。先に `workflow_dispatch` で 3 つのワークフローを流したが、競合を解いて push したあとの CI を待ってから親をマージした。付け替えたあとに CI が始まらないときは、まず PR の競合を確かめる。
9. 注釈付きのタグ `v0.19.3` を `5bd4ec5` に付け、GitHub リリース `v0.19.3` を作った。本文は CHANGELOG の 0.19.3 の節である。
10. 使い捨ての設定でマーケットプレイスから入れ、0.19.3 が入ることを確かめた。v0.19.2 から v0.19.3 までに変わった 4 つのファイルの SHA-256 が、すべてタグの中身と一致した。入った `wiki_browse.py` で Wiki を書き出し、ページに宣言が出ることを確かめた。
