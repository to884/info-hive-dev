# capture の記録の改行と sha256 の直し（wiki 0.19.2）と、0.19.1 と 0.19.2 のリリースの記録

`wiki_evolve.py capture` が Windows で経験の raw（`raw/experiences/<id>.json`）を CRLF で書き、返す `sha256` とファイルのバイト列の SHA-256 が食い違う件を直し、wiki 0.19.2 として出した記録である。プラグインの PR は to884/info-hive-wiki#65、親の PR は to884/info-hive-dev#121 で、試験は `tests/wiki/test_wiki_evolve_newlines.py` にある。このページは作業の記録から書いた。原因の性質は [[pythonの書き戻しの改行]] にある。

## 経緯

1. ベンチマークの作業で `/wiki:learn` を実行したとき、インストール済みの wiki 0.11.0 の `capture` が保存した 5 つの JSON が、すべて CRLF だった。返した値とファイルの値は、5 つとも違った（to884/info-hive-dev#120 の経験の記録）。その作業から、直しを別のセッションに頼んだ。
2. 原因は、`capture` と実験の記録（`event()`）が `path.open('x', encoding='utf-8')` で、文字のモードで改行を指定せずに書いていたことである。`wiki_evolve*.py` を探すと、ファイル単位の `propose --target` も、候補を `read_text` で読んで `write_text` で書き戻していた。Windows では LF の候補が CRLF になって実験に入り、`apply` でそのままスキルに入る。
3. 直しは、上書きしない `'xb'` でバイト列を書く `create()` を足し、`capture` と `event()` で使う形にした。`capture` が返す `sha256` は、ファイルの実際のバイト列の SHA-256 にした。`propose` は候補をバイト列のまま写す。
4. すでに CRLF で保存された記録は、raw が変更不可なので書き直さない。同じ ID で渡したときは、中身をバイト列で比べ、LF の形か、すべての改行を CRLF にした形のどちらかと等しければ受け入れる。返す値は CRLF のバイト列の値なので、0.19.1 までが返した値とは違う（CHANGELOG に書いた）。一部だけ CRLF、CR だけ、BOM 付き、末尾の改行なしは断る。`encode()` は文字列の中の改行を `\n` とエスケープするので、改行はどれも JSON の行の区切りであり、CRLF の形は 1 つに決まる。
5. 試験は、`io.open` と `open` を包み、改行の指定がない文字のモードの書き込みに `newline='\r\n'` を渡して、Windows の書き込みを真似る。Windows でなくても、直す前のコードが落ちる（追加した直後の 10 件のうち 8 件）。Python 3.12〜3.14 の `Path.write_text` と `Path.open` は `io.open` を通るので、この差し替えで捉えられる（Sol が 3.12 と 3.13 のソースで確かめた）。
6. GPT-6.1 Sol の敵対的レビューは「採用可（確信度は中）」で、致命的・重大な指摘はなかった。軽微な指摘の 1 つは、`propose` のレビュー用の差分（`change.diff`）が `read_text` で改行をそろえてから作るので、改行だけが違う候補ではハッシュが変わるのに差分が空になる、というものだった。改行をそろえずに読み、`change.diff` と `proposal.json` もバイト列で書くようにした。直したあとの試験では、文字のモードで書いた `change.diff` が CRLF の行を `\r\r\n` にしていたことも分かった。`wiki_evolve.py` に文字のモードの書き込みがないことを構文木で確かめる試験を足した。直す前のコードでは 5 か所すべてを見つけた。レビューのあとの変更は、Sol に見せ直していない。
7. 作業のあいだに to884/info-hive-wiki#64 が 0.19.1 として main に入ったので、版は 0.19.2 にした。子のブランチに main を取り込み（force push はしない）、CHANGELOG の 0.19.2 の節を 0.19.1 の上に置いた。親の PR も、#118 と #119 が main を進めるたびに main を取り込んだ。サブモジュールの参照は、こちらの子のコミットが main の参照を含むので、競合せずに解けた。
8. リリースを頼まれたとき、0.19.1 は main に入っていたが、タグもリリースもなかった。#65 を先にマージすると、0.19.1 を出すセッションが main の先頭に v0.19.1 を付けるおそれがあった。作者の決定で、こちらで v0.19.1 を #64 のマージコミット `6d712a8` に付けてリリースしてから、#65 をマージした。
9. #65 をマージコミット `727615e` でマージし、子のリモートのブランチを消した。注釈付きのタグ `v0.19.2`（本文は「v0.19.2: capture の記録を LF で書き、返す sha256 をファイルの値にそろえた」）を `727615e` に付け、GitHub リリース `v0.19.2` を作った。本文は CHANGELOG の 0.19.2 の節である。
10. 使い捨ての設定でマーケットプレイスから入れ、0.19.2 が入ることを確かめた。v0.19.0 から v0.19.2 までに変わった 5 つのファイル（0.19.1 の `wiki_browse.py` と `wiki_browse_fs.py` を含む）の SHA-256 が、すべてタグの中身と一致した。入った `wiki_evolve.py` で使い捨ての wiki に `capture` を実行し、ファイルが LF で、返した `sha256` がファイルの値と一致することを確かめた。

## 決めたこと

- `wiki_evolve_loop.py`、`wiki_evolve_agent.py`、`wiki_evolve_api.py`、`wiki_evolve_stream.py` の文字のモードの書き込みは直さなかった。返す・記録するハッシュは書いたあとのバイト列から取るので、`capture` のような食い違いはない。ただし Sol は、評価ループに 2 つの不具合が残ることを再現した。候補のファイルと `PURPOSE.md` を文字のモードで書くので、Windows では文字列として同じ中身でも `fingerprint()` が変わる。`publish_learning` は、課題の文に CR があると、書いたあとに読み直した文字列が本文と一致せず、2 回目の呼び出しで止まる（どの OS でも起きる）。別の作業にした。

## 残したこと

- 子の #65 をマージしたとき、親の #121 の CI は 6 件が通り、5 件が実行中だった。[[リリースの確かめ方]] は、子をマージする前に親の CI が通ったことを確かめると決めている。待たずにマージした。
