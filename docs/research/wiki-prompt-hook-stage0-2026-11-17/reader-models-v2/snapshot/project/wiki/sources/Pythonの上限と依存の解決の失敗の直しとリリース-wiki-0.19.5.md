# Python の上限と依存の解決の失敗の直しと wiki 0.19.5 のリリース

利用者向け文書の段階 2 の確認（新しい Windows 11 の VM、確認 3）で見つけた不具合を直し、wiki 0.19.5 として出した記録である。原本は `docs/agent-runs/2026-11-15-wiki-python-upper-bound/` にあり、決定は ADR-0026 にある。

## 不具合

Python の入っていない PC に wiki 0.19.4 を入れると、MCP サーバーが起動しなかった。uv で動くスクリプトの宣言は `requires-python = ">=3.12"` で、上限がなかった。uv 0.13.8 は、使える Python がないと、宣言に合う中でいちばん新しい CPython 3.15 を取る。MCP サーバーの依存の `onnxruntime==1.31.1` には 3.15 の wheel がなく、依存を解決できなかった。開発用の PC には 3.12 があったので、表に出なかった。

あわせて 2 つの問題があった。中継は、依存を解決できない失敗を「環境が作りかけで壊れている」と取り違えて入れ直した。理由は `server.log` にしか残らず、利用者が読む `launch.log` には残らなかった。

ADR-0018 は「3.14 まで試験が通っている」ことを理由に上限を付けなかった。ところが uv が実際に選ぶのは、試験より後に出た、誰も試していない版だった。

## 直し方

- uv で動く 8 本のスクリプトの宣言を、プラグインの CI の行列の範囲の `">=3.12,<3.15"` にそろえた。宣言と行列（YAML として読む）が食い違うと、info-hive-dev の `tests/wiki/test_python_version.py` が落ちる。
- 範囲のすべての minor の版で、8 本の依存が入るかを、`tests/wiki/check_script_python_range.py` が CI（`wiki-mcp.yml`）で確かめる。プラグインの CI の行列は両端しか試さず、MCP サーバーの依存を入れないためである。
- 入れ直しても直らない失敗を `UvSetupError` にまとめ、依存を解決できない失敗を `UvResolveError` にした。入れ直さずに止まる。
- 環境を用意できなかった理由は、どれも uv の出力の要約と一緒に `launch.log` に書く。待ちきれなかったときと、色付きの出力も扱う。

## uv の誤りの書き方は版で違う

Codex の自動レビューの指摘で、uv の版による違いが分かった。依存を解決できないとき、uv 0.7.22 と 0.12.2 は木の形（`× No solution found when resolving dependencies:` と `╰─▶ 理由`）で書き、0.13.8 は `error:` と `cause:` で書く。開発用の PC の uv 0.12.2 も木の形だった。uv の出力を見分けるときは、両方の形の本物の出力で試験する。

## レビューとリリース

1. Sol の敵対的レビューを 3 回受けた。1 回目の重大は、ふつうの失敗の理由が `launch.log` に残らないことだった（出力を捨てて終了コードだけを渡していた）。2 回目の重大は、親の PR がサブモジュールの古い参照を指したままで、親の CI が直したプラグインを試していないことだった。3 回目は採用可だった。
2. 親の PR（to884/info-hive-dev#130）は、別の PR（#127）が同じ日に ADR-0025 を使ってマージされたので競合した。こちらの ADR を 0026 に付け替えた。
3. 子の PR（to884/info-hive-wiki#68）の CI 4 つと、子の head を指した親の PR の CI 11 が通ってから、子をマージした（`2452f59`）。
4. 注釈付きのタグ `v0.19.5` と GitHub リリースを作り、`claude plugin update wiki@info-hive` で 0.19.5 が入ることを確かめた。
5. 親の参照をマージコミットに付け替えて、親をマージした。
