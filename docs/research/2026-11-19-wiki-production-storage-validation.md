# wiki 公開版の本番ストレージ・復旧試験

2026-11-19。公開版の本番有効化は保留する。VM の突然停止で、成功応答を返す前の承認済み保存1件を保留記録から再試行できなくなった。バックアップ以降に成功応答を返した別の保存1件は、バックアップへの復元で失われた。また、切り戻し・再公開の履歴がある場合、ファイルを元と同じパスに新しく作ったディレクトリへ復元しても、切り戻し記録の実体照合によって既定版と固定版が停止した。

## 試験環境

- 前回の生成器を使用。ライブ192記事、公開195記事・212ファイル、原本160件。全件合成データ。公開、ライブへの切り戻し、ライブでの保存、再公開の順に履歴を作った。
- 本番候補の構成を Windows のローカル NTFS・NVMe SSD と想定し、ホストの C:（ディスク0）に隔離 wiki を作った。別の物理ディスクであることを `Get-Partition` の番号で確かめ、USB 接続の NTFS ディスク（O:、ディスク1）をバックアップ先にした。
- 承認後の `wiki_public_save` と本体の成果物生成を使った。モデルの生成時間、承認待ち、外部データベース、ネットワーク上のストレージは測定対象外。作業用の `INFO_HIVE_DATA_DIR` も隔離した。

## 負荷と待ち時間

前回の並行度を引き継ぎ、1・4・8件を同時に保存した。既存原本への参照付きの `ingest`・`learn` と `query` の保存計画を準備してから開始した。初回応答は保存開始から承認済み操作の応答まで。ロック待ちは、各操作が取得に成功した `apply.lock` の待ち時間の合計。1並行の両標本は `query`。固定版の検索と根拠ページ取得は、同じ解決済み公開版で実行した。

| 同時保存 | 初回で保留 | 初回応答の最大 | ロック待ちの最大 | 全件反映まで（2回） | 固定版の読み取り |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0/2 | 26.91秒 | 0.01秒 | 21.89・26.97秒 | 10件成功、最大11.40秒 |
| 4 | 2/8 | 105.06秒 | 29.24秒 | 134.19・146.43秒 | 33件成功、最大10.71秒 |
| 8 | 8/16 | 262.04秒 | 124.22秒 | 364.62・462.61秒 | 68件成功、最大27.25秒 |

26件を一度ずつ反映し、記事・索引・ログと原本の指紋を照合した。全件反映の時間には、初回に保留になった操作を同じ承認で順に再試行する時間が入る。読み取りの標本には、その組の最終照合と重なった回もある。試験は同じ Windows ホストで他の処理が動く中で行った。少数の標本の観測値であり、本番の分位点や許容時間への適合は未判定。

別の8並行試験では、2件が同じ既存ページを編集する計画を混ぜた。208.22秒で全員の初回応答が返り、3件が反映、5件が保留になった。再試行後の464.57秒で7件が反映された。同一ページの競合1件は、差分の確認と再承認を求めて保留を維持し、変更は記事・索引・ログのいずれにも反映されなかった。既定版46件、固定版31件の検索・根拠取得が成功し、最大はそれぞれ15.27秒と16.64秒だった。

## プロセスの中断とファイル復元

Windows ホスト上で、保存プロセスを下記の位置で強制終了した。3件とも、旧版を指定した検索と根拠取得ができ、再試行を繰り返しても記事・索引・ログの反映は一度だった。再計測中は別の合成負荷も走っていた。

| 強制終了した位置 | 終了操作から `recover` の応答 | 再試行2回と固定版の照合まで |
| --- | ---: | ---: |
| 承認済み保存の保留記録の直後 | 1.39 秒 | 44.87 秒 |
| 公開の日誌を書いた直後 | 4.28 秒 | 19.92 秒 |
| 公開ポインターを書いた直後 | 3.79 秒 | 18.96 秒 |

`recover` は書き込み途中の日誌を処理する。承認済み保存の保留を見つけて再開するには、`pending` の ID と承認ハッシュを得て `retry` を実行する。計測はこの手順をすぐに実行できる条件での所要時間であり、障害を発見して担当者が対応するまでの時間や、自動復旧の実績は含まない。

ファイルのバックアップは書き込みのない状態で、wiki 全体（公開履歴、ポインター、完了記録、保留保存、Ossie 成果物を含む）と原本をコピーした。整合性は全ファイルの SHA-256 で照合した。外部の未承認下書きや作業ディレクトリ、ACL の復元、稼働中のスナップショットの一貫性はこの試験の範囲外。新規ディレクトリの停止を確認したのは、切り戻し・再公開の履歴を含む状態。他にも保留保存・ライブの計画などにパスと実体を照合する箇所がある。元ディレクトリ内の復元に進む前に、退避した元ディレクトリを元の位置へ戻した。

| 事象 | 観測した結果 |
| --- | --- |
| バックアップ取得 | wiki 1,750ファイル・原本160件。別ディスクへのコピーに2.03秒。 |
| `current` の名前を消失 | 整合性エラーで停止。ライブには切り替わらなかった。 |
| 同じパスに新しいディレクトリを作って復元 | コピーと SHA-256 の照合に4.98秒。既定版・固定版ともに切り戻し記録の実体照合で停止したため、サービス再開には至らなかった。 |
| 元のディレクトリの中身を復元 | 中身の退避・コピーに2.45秒。復元開始から既定の版 ID と2つの固定版の検索・根拠照合まで30.86秒。保留済み保存の再試行と一意性・原本の確認まで101.90秒。新規の保存はこの復元経路で試していない。 |
| バックアップ後に成功応答した保存 | 試験側が応答後に別ディスクへ書いた公開版の完了記録6件と、復元後の5件を突き合わせた。バックアップ以降の成功応答1件が欠落し、製品は再試行に「承認済みの保存の記録がありません」と返した。バックアップ完了から故障までは、試験で設けた66.66秒。 |
| 旧固定版を取り下げ | 旧 ID の読み取りが明示的に停止し、既定の現行版 ID は解決できた。 |

## 仮想マシンの突然停止とディスクイメージ復元

同じ SSD 上の専用 NTFS VHDX に、同規模の wiki を構築した。Windows PE を初回だけ正常終了してから負荷をかけ、承認済み保存の各停止点をゲストが表示した時点で、ホストから `Stop-VM -TurnOff` を実行した。ホストと NVMe SSD への給電は続いた。この試験はゲスト OS の突然停止と仮想ディスクの動作を観測するもので、物理 SSD の電源断とは条件が異なる。[Microsoft の `Stop-VM` コマンド](https://learn.microsoft.com/ja-jp/powershell/module/hyper-v/stop-vm?view=windowsserver2025-ps)

| VM を止めた位置 | 停止操作から再起動・照合まで | 結果 |
| --- | ---: | --- |
| 承認済み保存の保留記録の直後 | 26.42秒 | 旧固定版と原本は照合できた。保留記録が再起動後に見つからず、`retry` は実行できなかった。保存の成功応答前の停止。 |
| 公開の日誌を書いた直後 | 33.78秒 | `recover` が完了させる日誌はなく、保留記録からの再試行で1回だけ反映した。旧固定版を読めた。 |
| 公開ポインターを書いた直後 | 33.73秒 | 日誌を復旧し、再試行での重複はなかった。旧固定版を読めた。 |

保留記録が失われた停止点の修正と、同規模での再検証は [承認済みの公開保存を突然停止後に回収する](2026-11-19-wiki-approved-save-power-recovery.md) に記録した。

3回とも原本160件の指紋は一致した。試験データ生成直後に停止させた予備試行では、一部の原本が初回の再起動後に一致しなかった。上表の試験では、合成原本の作成をアプリの保存試験から切り離し、生成後に一度正常終了した。

VM の正常終了後、172 MB の VHDX を別の物理ディスクへコピーしてハッシュを照合した（1.14秒）。戻した VHDX のコピーと照合は0.57秒、復元開始から再起動して内容を確認するまでは29.61秒。復元した NTFS 上で wiki 実体の ID が一致し、切り戻し後のライブ保存を含む再公開版、旧固定版、原本を確認した。交換 SSD や別ホストへの復元、物理電源断直後のイメージ取得、復元完了後の新規保存はこの試験の範囲外。

## 公開範囲と版の保持案

| 対象 | 案 |
| --- | --- |
| 既定の公開範囲 | 承認済みの Markdown、検索・閲覧用の索引、承認した根拠の抜粋と出典識別子。添付と Ossie の出力先に載せる項目は許可リストで承認する。 |
| 管理者の範囲 | 原本全文、ライブ専用ページ、下書き、承認・復旧の管理記録。ファイルシステムのアクセス権を公開利用者と分ける。グラフ・Ossie・添付、根拠の参照先から公開外情報が得られないことを、実アカウントで確かめる。 |
| 読み取れる公開版 | 現行版、直前の切り戻しに必要な版、利用中の引用が固定している版を保持する。その他は直近90日分と直近30版の和集合を初期案とし、容量と復元の実測から見直す。復元時点より新しい固定版が欠落した場合は明示的なエラーを返し、該当の版を回収してから再開する。 |
| 取り下げと削除 | 取り下げ記録を独立した領域にも保存する。復元後に取り下げを再適用し、照合が済むまで公開を止める。利用者には固定版の取り下げを明示する。本文や派生成果物の物理削除は、履歴の検証・固定引用・保存の再試行に必要なデータを確認してから行う。 |
| バックアップ | 管理者だけがアクセスできるバックアップを日次30本・週次12本から検討する。消去義務がある場合は、該当データを含むバックアップの保管可否と安全に消去できる期限を別途決める。成功応答の消失を許容しない運用では、応答前に変更を復元できるデータと完了記録を独立障害領域へ永続化し、復元後に突合する。 |

取り下げ前のバックアップを元のディレクトリへ戻すと、取り下げた固定版を再び検索でき、根拠も取得できた。別ディスクへ試験側が記録した版 ID を使って取り下げを再適用すると、固定版の解決は再び拒否された。この順序を復元手順に含める必要がある。[取り下げと復元の追加試験](../../raw/wiki公開版の取り下げと復元-2026-11-19.json)

## 有効化の判断

1. 新しいディスクやディレクトリに復元する経路を決め、再公開後の既定版・固定版・後続保存まで通す。案は、同じ実体 ID・ドライブ文字・パスを保つボリュームイメージを本番候補の構成で実証するか、検証済みバックアップに対して実体を明示的に再ひも付けする機能を実装すること。切り戻し記録、保留保存、ライブ計画・日誌、作業中の承認済み計画を含めて照合する。
2. 突然停止後も承認済み保存を回収できるようにする。公開版とライブでの保存、切り戻し、取り下げは独立した記録と照合し、消失を検知する運用を整える。障害検知と担当者の初動を含めて復旧目標を決め、対象構成での停止と、交換ディスクまたは別ホストへの復元を計測する。
3. 本番アカウントで公開範囲を確かめ、版の保持と削除の方針、許容する待ち時間を承認する。書き手の並行度に加えて、同一ページ編集、原本追加、検索の同時利用を含む日常負荷で測る。
