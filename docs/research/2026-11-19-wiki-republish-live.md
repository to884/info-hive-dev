# 切り戻し後の再公開と本番有効化の判断

切り戻し後のライブ wiki から、前の公開版を親にして再公開する。ライブの承認済み保存は記事・索引・ログの確定後の内容を使う。完了記録で世代を照合し、保存操作を重ねて実行せずに反映する。互換グラフは公開候補から生成する。Ossie は既存の意味レコードを保ち、ライブで変わった記事の確定時点の内容を追加する。ライブ期間中の各適用は既存のライブ完了記録でたどれる。

## 運用

```powershell
uv run --with pyyaml==6.0.3 python "<wiki_apply.py>" plan-republish-live --wiki "<WIKI_ROOT>" --raw-root "<RAW_ROOT>" --out "<候補ディレクトリ>" > "<計画.json>"
python "<wiki_apply.py>" republish-live --wiki "<WIKI_ROOT>" --source "<候補ディレクトリ>" --plan "<計画.json>" --expect-sha256 "<plan_sha256>"
python "<wiki_apply.py>" recover --wiki "<WIKI_ROOT>"
```

以前の公開範囲と、切り戻し後の共通の書く段が確定したファイルを候補に入れる。別途採用する添付などは `--include` で指定する。旧形式の記録で公開範囲を判定できないパスは、確認して `--include` または `--exclude` を指定する。以前からライブ専用のファイルは、ライブで編集しても公開範囲に加わらない。公開対象を直接編集した場合は明示指定と差分の確認を求める。承認後にライブが変わった場合や、ライブに承認済みの保留が残っている場合は、再公開を止める。

再公開の日誌を記録したあと、以前の公開版 ID は引き続き有効である。成果物と完了記録を照合する間、既定の読み取りはライブを使う。状態の印を切り替えた後は新しい公開版が既定になる。途中で中断したら、同じ承認を再試行するか日誌を復旧する。

## 検証結果

| 試験 | 結果 |

| 変更と履歴の引き継ぎ | 作り直した公開版で、5件が記事・索引・ログ・Ossie SQLite の記事行に一度ずつ入った。以前の Ossie の675行を保持した。原本160件のバイト列が一致した。 |
| 中断と再試行 | 同規模の試験ではポインター更新後に強制終了し、候補の元フォルダーを退避してから復旧した。別の隔離 wiki で、完了記録・ポインター・先頭記録・切り戻し記録の退避・状態の印に関する7箇所で中断させ、同じ承認の再試行と続く切り戻し・再公開を確かめた。 |
| 固定した読み取り | 切り替え前の既定の読み取りはライブを参照した。再公開後も、版 ID を指定した MCP の引用、起動済み browse の本文と添付は、当初の公開版を参照した。 |
| 公開範囲 | ライブ専用記事を編集しても、再公開の候補と Markdown の差分に入らなかった。通常保存の前にログへ手で追記しても、各保存の変更前後の指紋を照合して検出した。公開する場合は明示指定を要求する。 |

Opus のレビューに基づき、ライブ専用の範囲、取り消した保留の再試行、変更前後の指紋の照合、履歴へ移した切り戻し記録の参照を修正した。変更前後の指紋を追加した後の追跡レビューで、直編集が後続の通常保存に混ざって自動で公開される経路が解消されたことを確認した。

新規4件と既存26件の試験が通った。同規模の試験全体は約205秒だった。データ生成、並行保存、再公開候補の複数回の作成、強制終了と復旧を含む。

SemaSynth wiki は指紋の照合にだけ使い、83ファイルの追加・削除・内容の差分は0件だった。

## 本番有効化

[前回の有効化条件](2026-11-19-wiki-production-readiness.md) に照らし、本番の既定への切り替えは保留とする。隔離環境で切り戻しから再公開までの機能を確認した。本番のストレージ上での突然停止、状態記録と成果物を含むバックアップからの復元、復旧点と復旧時間、既定の運用負荷における待ち時間、Markdown・添付・原本の公開範囲と版の保持期間の確認が残る。今回の中断試験はプロセスの強制終了と、状態ファイルの退避による故障注入で行った。

後続の計測と再判定は [本番ストレージ・復旧試験](2026-11-19-wiki-production-storage-validation.md) に記録した。
