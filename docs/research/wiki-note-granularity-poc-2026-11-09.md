## 1. 結論の要約

36 件（3 資料 × 2 モデル × 3 回 × 2 方式）を走らせ、すべて計画を得た。合否を決める一致率は、候補を人が対応づけるまで出せない。機械で確かめられた範囲では、次のことが言える。

- **出典への忠実さは、引用の照合の範囲で問題がなかった。** 36 件の引用 1,925 本は、すべて原本にそのままあった。ただし、引用が原本にあることは、主張が引用から言えることまでは保証しない。必須条件「捏造 0 件」の判定は人の確認に残る。
- **併用案は、全件を `source_only` にして一致を稼いではいなかった。** SemaSynth の 2 資料で、併用案は 1 回あたり 4〜10 本の concept のページを作る計画を出した。現行は、R で 1 本ずつ、V で Opus が 0 本、Sol が 2〜5 本だった。`source_only` の割合は、併用案と現行でほぼ同じだった（R 0.38 と 0.33、V 0.64 と 0.60）。
- **既存のページを更新する先は、文字列で比べても揃った。** O（W0 の既存の用語ページがある）では、更新する既存ページの集合の Jaccard が、併用案で 6 件のどの組でも 1.0、現行で平均 0.83 だった。
- **新しく作るページの名前は、モデルどころか回ごとにも揃わない。** SemaSynth で新規ページのスラッグが文字列で一致した割合は、併用案で 0.02〜0.10 だった。同じ主張を指していそうなページも、題名の言い回しが毎回違う。同じページかどうかは、人の対応づけ（`page_cluster`）でしか決まらない。
- **モデルの差が、方式の差と同じくらい大きい。** 候補の数（O で Opus 21〜34、Sol 34〜58）、`source_only` の割合（V の現行で Opus 0.79、Sol 0.41）、提案を題名でどう扱うか（第 4.5 節）がモデルで割れた。

手順書を書き起こすとき、レポートが決めていない点を 1 つ補った。再利用できる主張を、用語ページの `###` の節に置くか、`kind: "claim"` のページに昇格させるかの分け方である。「ある用語の性質や使い分けとして読むのが自然なら節、1 つの問いに条件つきで答える判断として単独で引かれるならページ」とした。また、レポートの題名の例は R と V から作られていたので、答えを先に示さないよう消費税の例に差し替えた。

根拠の行に条件を表す語（「では」「場合」「前提」「only」など）があるのに `conditions` が空の候補を、「脱落の疑い」として数えた。現行の Opus に多い（R で 25 件、V で 22 件）。ただしこれは語の有無を見ただけで、脱落の判定ではない。必須条件「脱落 0 件」は、人が `conditions_kept` の列で判定する。

### 4.5 文字列で見える食い違い（人が確かめる点）

対応づけの代わりにはならないが、題名の文字列から次のことが見える。どれも人の対応づけで確かめる。

- **同じ判断を 1 ページにするか 2 ページにするか。** R の併用案では、6 件とも「バイト一致」を含む題名の主張ページを作った。そのうち 5 件は「同一環境ではバイト一致、異なる環境では値と型の一致」を 1 ページにし、Sol の 3 回目だけが同一環境と異なる環境を別々の 2 ページにした。レポートの第 6.1 節が「1 つの判断」の例に挙げた、まさにその分け方で割れている。
- **提案を題名でどう扱うか。** V（レビューを受けて計画に反映した記録）で、Opus は計画への反映を `decision` とし、題名を断定の文にした（`会計期間は検証対象の期間マスタではなく指定年度の暦と照合する`）。Sol は同じ箇所を `proposal` とし、題名の末尾に「案」「提案する」を付けた（`期間マスターと明細の同時変更に備え指定年度の暦と照合する案`）。原本は、計画に反映しただけで製品の欠陥はまだ直していない、と断っている。どちらが手順書の「提案や仮説を、題名で確定した事実に変えない」に合うかは、人が判断する。
- **題名とスラッグが長い。** 主張ページ 43 本のスラッグは平均 40 文字、最長 64 文字だった。手順書の目安（60 文字程度）を超えるものがある。英字は命名の規則どおり小文字になり、`pythonのaudit-hookによる通信禁止は…` のように読みにくい。パイロットで気づき、結果を見る前に記録した点である。
- **同じプロジェクトの別の source を更新する。** 現行では、SemaSynth の別の source ページを更新先にする候補が 63 件あった（V で 49 件、R で 14 件。併用案では 0 件）。V では `semasynth管理会計サンプル-2026-11-06` が 26 件で最も多い。現行の手順 6 が許す更新だが、記録の source に知見を足していくことになり、source に溜まる偏りを強める方向である。

## 5. 人の対応づけ

合否を決める指標（知見の recall と precision、配置先の一致率、同居の F1）は、候補どうしの対応づけがないと出せない。レポートの第 8 節の決まりどおり、対応づけは人が行う。推測では埋めていない。

| 表 | 行数 | 埋める列 |
| --- | ---: | --- |
| O の候補 | 445 | `cluster_id`、`faithful`、`conditions_kept` |
| R の候補 | 221 | 同上 |
| V の候補 | 404 | 同上 |
| 新規ページ（O、R、V） | 12、42、57 | `page_cluster` |

- 表は実行を伏せた ID（`R-01` など）で並べ、根拠の行の順にした。同じ行を根拠にした候補が隣り合う。
- 人が埋める版は、リポジトリの外（`%USERPROFILE%\info-hive-dev-private\2026-11-09-wiki-note-granularity-poc\mapping\`）にあり、原文の行番号つきの写しも同じ場所にある。リポジトリには、候補の本文（知見、条件、引用）を落とし、行き先と根拠の行だけを残した写しを置いた。このリポジトリは公開で、O は Medium の会員限定記事、R と V はリモートのない SemaSynth のプロジェクトの記録だからである。モデルは知見を原文に近い言い回しで書くので、引用だけを伏せても原文が漏れる。
- 埋め方は [mapping/README.md](../agent-runs/2026-11-09-wiki-note-granularity-poc/mapping/README.md) にある。埋めたあと `scripts/metrics_from_mapping.py` を走らせると、資料と方式ごとの必須条件、一致率、合格の目安との比較が `metrics/agreement.md` に出る。
- 1,070 行は多い。負担を減らすなら、R（221 行）を先に対応づけると、併用案の判定規則が別モデルで揃うかの最初の答えが出る。R は短く、併用案と現行で concept の本数の差が最もはっきりしている。

## 6. 限界

- **一致率は、実際の取り込みより高めに出る。** 全ファイルを依頼文に埋め込んだので、`ingest-workflow.md` の手順 4 の「どのページを読むかを選ぶ」部分を試していない。読んだページ数は、モデルの自己申告だけである。対応づけで出る一致率は、上限の目安として読む。
- **埋め込みに変えた理由。** Codex の Windows のサンドボックスが `runner handshake task failed` でコマンドを起動できなかった。Claude Code の Bash のサンドボックスの中からも、ユーザーのターミナルからも同じだった。サンドボックスを外す起動は、権限の判定で拒まれた。前日の 4 体の検討では同じ Codex が動いていたので、原因は今日のこの PC の状態にある可能性がある。調べていない。
- **O は取り込み直しに近い。** O から作ったコンセプト（`sources:` に O を含む）は残した。O については「既存の用語ページに足すか、新しく作るか」の判断を見ていることになる。
- **R と V の source ページは抜いたが、ほかの source からのリンクは残った。** `semasynth会計データの再検証-2026-11-06` などが、R と V の内容に触れている。
- **現行の対照は、出力の形を併用案と揃えてある。** 知見を列挙させ、条件を書かせる形そのものが、現行の判断を変えている可能性がある。
- **併用案の手順書は、レポートにない分け方を 1 つ補った。** 一致しなかったときに、レポートの併用案が悪いのか、補った規則が悪いのかは分けられない。
- **冪等性（同じ wiki への再処理）は試していない。** レポートの第 8 節が分けた 2 つの試験のうち、独立一致だけを走らせた。

## 7. 次の一手

1. 人が R、V、O の順に候補を対応づけ、`metrics_from_mapping.py` で合否を出す。必須条件（捏造 0 件、条件の脱落 0 件）を先に見る。
2. 対応づけの前でも決められる点がある。第 4.5 節の「提案を題名でどう扱うか」は、モデルが割れた。採るなら、手順書に「計画に反映しただけで実装していないものは `proposal` とする」のような区分の規則を足す必要がある。
3. 合格したら、段階 3（`kind: "claim"` と、行き先どおりの更新）に進む。そのとき、主張ページの題名とスラッグの長さの上限、用語ページを作る基準（第 4.3 節で回ごとに違った）を決める。
4. Codex のサンドボックスが直ったら、ツールで読む形で R だけを走らせ直し、埋め込みとの差（読むページの選び方の揺れ）を測る。
