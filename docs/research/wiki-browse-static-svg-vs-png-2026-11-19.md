# 静的表示の SVG と resvg で生成した PNG の比較

既存の連続描画で使った 50 図を、明暗の 2 配色で SVG に書き出した。
各 PNG は、比較に使う SVG を resvg 0.50.0 に渡して生成した。
各 SVG の幅と高さを整数に切り上げ、その図の PNG の画素寸法と一致させた。
resvg には `YuGothR.ttc` を指定し、システムフォントの自動読み込みを省いた。
元の図、フォント、変換器、画像ファイルのハッシュとバイト数を記録した。 [前回の連続描画の要約](../../wiki/sources/browseの静的描画の調査記録-2026-11-19.md) · [画像の記録](../agent-runs/2026-11-19-wiki-static-svg-vs-png/images/manifest.json)

## 測定条件

Windows 版 Playwright WebKit 26.0 を使い、同じローカル HTML（`file://`）から SVG または PNG を `<img>` で表示した。
各ケースでは専用ブラウザの同じ文書とタブを維持し、50 枚を明、暗の順に表示する操作を 10 周繰り返した。
各配色の 50 枚をすべてデコードしたことを確認した。
暗色のデコード後の最初の採取が終わってから 5 秒待ち、暗色を表示したまま各周の待機後の標本を取った。
手動 GC を要求せず、同一配色の画像 URL を次の周でも使った。
初回の実行順は SVG、PNG とし、2 回目は逆順にした。

先頭図の時間は、ページ内の配色切り替え処理を始めてから、0 番の画像の `decode()` が完了するまでとした。
この時間には 50 枚の画像要素の作成とファイル読み込みの待ちが含まれる。
この版の WebKit では、PNG の `img.decode()` はビットマップのデコード後に解決する。SVG ではラスタライズが完了する前にも解決し得る。
画面外の画像にも `decode()` を呼ぶため、時間とメモリはこの条件での観測値である。 [測定に使った WebKit の実装](https://github.com/WebKit/WebKit/blob/db897909f7c31d9b38793374c66427b6a4cb3dd3/Source/WebCore/loader/ImageLoader.cpp#L550-L575)
測定前に画像の照合のために全ファイルを読み、OS のファイルキャッシュを消去せずにブラウザを起動した。
メモリは専用ブラウザとその子プロセスの合計を測った。
ピークには、表示を始めてから 10 周目の待機が終わるまでに得た標本の最大値を使った。
採取の間隔は 100 ミリ秒の待ち時間にプロセス列挙と記録にかかる時間を加えた値である。
表示中に連続して取得した標本の採取間隔の中央値は、ケースごとに約 0.79〜1.00 秒だった。
ワーキングセットの合計には、プロセス間で共有したページが重複して含まれ得る。 [集計スクリプト](../agent-runs/2026-11-19-wiki-static-svg-vs-png/analysis/analyze-figure-followup.py)

## 観測したピークメモリ

単位は MiB。各ケースで観測したそれぞれの最大値を 2 回分示す。
下の増分は、ケース内で私有コミットの標本最大から描画前の値を引いたものである。

| 指標 | SVG 1 回目 | SVG 2 回目 | PNG 1 回目 | PNG 2 回目 |
| --- | ---: | ---: | ---: | ---: |
| 描画前の私有コミット | 797.42 | 765.47 | 796.96 | 797.85 |
| ピークの私有コミット | 861.12 | 827.93 | 830.13 | 831.36 |
| 描画前からの増分 | 63.70 | 62.46 | 33.17 | 33.52 |
| ピークのワーキングセット合計 | 216.37 | 213.78 | 202.90 | 201.92 |

PNG は描画前からのピーク増分が両方の反復で約 30 MiB 小さかった。
SVG 2 回目では描画前の GPU プロセスが他の 3 回より約 32 MiB 小さく、私有コミットの絶対値にはこの差も含まれる。
監視の合間に生じた短いピークは観測していない場合がある。 [4 ケースの集計](../agent-runs/2026-11-19-wiki-static-svg-vs-png/ten-rounds/summary.json)

単位は MiB。各列は同じ方式の 2 回分の中央値である。

| 周 | 私有コミット SVG | 私有コミット PNG | ワーキングセット SVG | ワーキングセット PNG |

| 1 | 842.28 | 813.88 | 207.54 | 194.59 |
| 2 | 842.10 | 809.70 | 209.66 | 196.28 |
| 3 | 841.79 | 809.94 | 210.33 | 196.71 |
| 4 | 842.84 | 810.39 | 211.44 | 197.17 |
| 5 | 841.80 | 810.66 | 211.46 | 197.69 |
| 6 | 842.20 | 811.48 | 211.96 | 198.61 |
| 7 | 841.99 | 827.83 | 212.69 | 199.66 |
| 8 | 842.43 | 827.82 | 213.39 | 200.17 |

待機後の `WebKitWebProcess` の PID は各ケースで 10 周とも同じだった。
PNG の 1 回目では、6 周目から 7 周目にかけて同じ Web プロセスの私有コミットが 204.1 MiB から 236.9 MiB へ増えた。
この増分の用途は未測定である。
全ケースの私有コミットは 862 MiB 未満で、前回の閲覧時 Mermaid 描画で観測した GiB 単位の周ごとの増加は、今回の 10 周では見られなかった。 [採取した各ケースの原標本](../agent-runs/2026-11-19-wiki-static-svg-vs-png/ten-rounds/results.json)

## 先頭の図のデコード完了までの時間

初回のばらつきを確かめるため、50 図を明暗で表示する最初の 1 周だけを、新しいブラウザでさらに 2 回ずつ測った。
表の単位はミリ秒で、各行に 2 回分の値を示す。

| 測定 | SVG 明 | SVG 暗 | PNG 明 | PNG 暗 |
| --- | ---: | ---: | ---: | ---: |
| 10 周測定の第 1 周 | 348、789 | 368、802 | 4,450、176 | 1,604、215 |
| 第 1 周だけの追加測定 | 209、177 | 234、206 | 213、138 | 156、170 |
| 10 周測定の 2〜10 周目の中央値 | 12.5 | 12.0 | 14.5 | 14.0 |

PNG の 1 回目で生じた 4,450 ミリ秒の待ち時間は、後の 3 回では再現しなかった。
その原因と、初回表示で一方が安定して速いかは分からない。
同じ URL を再表示した 2 周目以降は、先頭図のデコード完了までの中央値が 12.0〜14.5 ミリ秒に収まった。 [追加測定の集計](../agent-runs/2026-11-19-wiki-static-svg-vs-png/first-round/summary.json)

## 書き出した画像のサイズ

| ファイルの合計 | SVG | PNG |
| --- | ---: | ---: |
| 明 50 枚 | 635,890 B | 141,333 B |
| 暗 50 枚 | 646,640 B | 146,402 B |
| 合計 | 1,282,530 B | 287,735 B |

この図セットでは PNG のファイル合計が 77.6% 小さかった。
SVG には Mermaid が各図に出力する CSS が含まれる。
表は生成された画像ファイルのサイズを合計したもので、共通の HTML と CSS や HTTP 圧縮後の転送量は含めていない。

resvg は 100 枚の変換を完了した。
変換時には `@keyframes`、`:root`、矩形の幅、フィルターについて警告が出た。
最初の図を両形式・両配色で表示して日本語ラベル、図形、矢印を目視したところ、文字の濃さと縁に差があった。 [明色 SVG](../agent-runs/2026-11-19-wiki-static-svg-vs-png/images/proof-light-svg.png) · [明色 PNG](../agent-runs/2026-11-19-wiki-static-svg-vs-png/images/proof-light-png.png) · [暗色 SVG](../agent-runs/2026-11-19-wiki-static-svg-vs-png/images/proof-dark-svg.png) · [暗色 PNG](../agent-runs/2026-11-19-wiki-static-svg-vs-png/images/proof-dark-png.png)

## 保存先と再集計

リポジトリのルートで以下を実行すると、保存済み標本から 10 周測定と初回の追加測定の集計を再生成できる。

```powershell
$run = 'docs/agent-runs/2026-11-19-wiki-static-svg-vs-png'
python -X utf8 -B "$run/analysis/analyze-figure-followup.py" "$run/ten-rounds/results.json"
python -X utf8 -B "$run/analysis/analyze-figure-followup.py" "$run/first-round/results.json"
```

再測定用 ZIP には明暗の SVG と PNG 計 200 枚、元の入力と表示用ファイル、代表図の画像、マニフェストを保存した。ZIP を展開したディレクトリを `STATIC_IMAGE_FIXTURE` に指定する。画像のデコードと標本の採取には、当時の測定スクリプトから静的画像の処理を切り出したものを使う。測定の実行手順は wiki にある。 [再測定スクリプト](../../poc/browse-static-image/performance-experiment.mjs) · [11 月 18 日の測定レビュー](../agent-runs/2026-11-19-wiki-static-svg-vs-png/2026-11-18-repeat-tab-review.md) · [再測定用 ZIP](../agent-runs/2026-11-19-wiki-static-svg-vs-png/static-image-assets-r2-20261119.zip) · [wiki の手順](../../wiki/concepts/browseの静的画像表示とメモリ.md) · [報告書の原本](../agent-runs/2026-11-19-wiki-static-svg-vs-png/original-report.md)
