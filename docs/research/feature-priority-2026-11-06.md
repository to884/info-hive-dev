# 機能実装の優先順位（2026年11月9日、6 版目）

info-hive のプラグイン（`info-hive-wiki`、`info-hive-rag`）と開発用のリポジトリについて、残っている作業を洗い出し、取りかかる順番を提案する。

この文書は 6 版目である。5 版目（同じ日）で 1 位と 6 位に置いた作業（ADR-0015 の承認と段階 2）は済み、2 位の後片付けもほぼ済んだ。この版では、作者の判断で、browse を rag の移行より先にした。前の版は Git の履歴で読める。ファイル名の日付は最初の版のものである。

## 結論

browse を、検索と全体のグラフまで先に作る。そのあとで rag の移行に入り、最後に browse の RAG のデータ源をつなぐ。全量の OCR は、その間ずっと並行して回す。

| 順位 | 項目 | 種類 | 規模 | 理由 |
| --- | --- | --- | --- | --- |
| 1 | browse の下ごしらえ（ページの集合とリンクの規則の共通化、大文字と小文字だけが違うページの検査） | 実装 | 中 | ADR-0010 が、browse の実装の前に済ませると決めている。検索の対象が変わるので、rag の移行の前に済ませると測り直しが 1 回で済む |
| 2 | browse の第 1 段階とサーバーのアダプタ（ADR-0010 の作る順序の 2〜4） | 実装 | 中〜大 | 承認済みで、PoC も済んだ。rag の移行に依存しない |
| 3 | browse の検索と全体のグラフ | 実装 | 中 | 検索は wiki の MCP サーバーの `query` を使うので、rag の移行を待たない |
| 4 | rag の移行（ADR-0012） | 実装 | 大 | RAG の品質の測り直し、全量の索引の E2E、browse の RAG を止めている |
| 5 | browse の RAG のデータ源 | 実装 | 小〜中 | 4 のあとでなければ足せない（ADR-0010 の決定の 4） |
| 6 | 全量の OCR の続き | 実行 | 大（主に待ち時間） | rag 0.5.0 で無駄が出なくなった。1〜5 と並行できる |
| 7 | 記事の単位の PoC の判定と、ADR-0015 の段階 3 | 判定＋実装 | 中 | PoC は走らせた。人の対応づけと合格基準の確定が残る |
| 8 | wiki のひな形のスクリプトのパス | 修正 | 小 | ひな形が書き出すコマンドの例のパスが、どこから実行しても解決しない |
| 9 | 知識を使うための機能（コンテキストの切り出し、出典のチェーン、鮮度の lint） | 実装 | 中 | どれも着手の条件がある。動かす対象のデータがまだ少ない |

1 が main に入ってから 4 に入る。1 と 4 は、どちらも wiki の検索まわり（`wiki_search.collect_pages()` と、それを使う `wiki_index.py`）や wiki の MCP サーバーに触れるので、同時に進めると同じファイルで衝突しうる。6 は、どの作業ともファイルが重ならない。7 と 8 は、browse と rag のどちらとも独立していて、いつ進めてもよい。

## 判断の基準

次の順に重みを置いた。前の版と同じである。

1. すでに規則に反している、または利用者に影響が出ているもの
2. ほかの作業を止めているもの
3. 承認済みで、すぐ着手できるもの
4. 作業の無駄が出るおそれ（あとで作り直しになる作業は後ろに回す）
5. 規模（同じ順位なら小さいものを先にする）

5 版目は、基準 2 で rag の移行を browse より上に置いた。この版では、作者の判断で browse を先にした。そう判断できる理由は次のとおりである。

- rag の移行が止めている作業（RAG の品質の測り直し、全量の索引の E2E、browse の RAG）は、どれも利用者に届いていない。rag 0.5.0 は今の LanceDB の構成で動いているので、移行が遅れても基準 1 には当たらない。
- browse は承認済みで PoC も済み、すぐ着手できる（基準 3）。
- browse の下ごしらえで、検索の対象のページを lint と同じ集合にそろえる。rag の移行のあとには RAG の品質を測り直すので、検索の対象を先に決めておけば、測り直しが 1 回で済む（基準 4）。

## 項目ごとの状態

### 1. browse の下ごしらえ

【記述】[ADR-0010](../adr/0010-wiki-browse-separates-core-from-delivery.md) は、承認のあとの作業を次の順に進めると決めている。browse の実装（`commands/browse.md` など）は、1 と 2 のあとに始める。

1. `info-hive-wiki` で、ページの集合の除外の規則とリンクの抜き出し方を 1 か所にまとめ、lint と search をそろえる（決定の 1）。検索の対象が変わるので、MCP の `query` の評価ゲートを測り直す。
2. lint に「大文字と小文字だけが違うページ」の検査を足す（決定の 3）。

【確認済み】決定の 1 の要点は次のとおりである。

- 閲覧の「ページ」とリンクの解決は、lint の集合を正とする。`.wiki-cache/` は lint の側でも除く。`index.md` と `indexes/` はページとして描かず、ナビゲーションの入力としてだけ読む。
- コードスパンとコードブロックの中の `[[...]]` は、lint でも閲覧でもリンクとして数えない。今の lint は数える。
- 検索（search と MCP の索引）の対象も同じ集合にそろえる。`clean_link_target()` は `wiki_lint.py`、`wiki_search.py`、`wiki_graph_extract.py` の 3 か所にあり、NFC にそろえる順が違う。

利用者に見える変更（lint の指摘と検索の結果が変わる）なので、wiki のマイナー版を上げてから入れる。検索の対象が変わるので、評価ゲート（`tests/wiki/run_mcp_gate.py`）で確かめる。

### 2. browse の第 1 段階とサーバーのアダプタ

【記述】ADR-0010 の作る順序の 2〜4 に当たる。

- 中核、ページの HTML のテンプレート、日本語の CSS を、`poc/browse/gen.py` を下敷きに作る。`poc/browse/test.mjs` と `review_checks.py` の手順を、実装の試験に移す。
- 第 1 段階（ページの表示、ナビゲーション、メタ欄、被リンク、関係表、未解決リンク）を、静的に描ける形で完成させる。mermaid と `wiki/assets/` の svg の表示は、ADR-0005 のとおり第 1 段階に含めない。
- 最初のアダプタは構成 B（必要なときだけ起動するローカルのサーバー）にする。

【確認済み】`info-hive-wiki/commands/` に `browse.md` はまだない。PoC は済んでいる（[記録](wiki-browse-adr-0010-poc-2026-11-07.md)）。書き出し先は、ADR-0012 の索引と同じ根の `<data_dir>/browse/<wiki のハッシュ>/` を既定にする（決定の 2）。

ADR-0013 で、ソースの要約ページの `raw:` は PDF の絶対パスになった。持ち運べる生成物に絶対パスの Wiki のルートを入れないこと、`raw:` の扱いは、ADR-0010 の決定に従う。

### 3. browse の検索と全体のグラフ

【記述】ADR-0010 の作る順序の 5 のうち、RAG を除いた部分である。

- 検索の結果は、方式によらず `wiki_search.py --json` の結果の形にそろえる。
- 検索は、アダプタ（browse のサーバー）が wiki の MCP サーバーの `query` を呼ぶ形にする（決定の 4 の D'）。画面は自分のアダプタにだけ要求する。サーバーに届けば `live`、届かなければ埋め込みの索引（`embedded`）にする。静的版は RAG を持たない。
- 使えない機能は、能力の宣言（`capabilities`）で画面に出さない。

PoC では、埋め込みの索引（`data/search.js`）は作者の Wiki で 13,219 バイト（1,000 ページで約 236 KB の見込み）で、5 つのブラウザの `file://` とサーバーで動いた。

### 4. rag の移行

【記述】ADR-0012 で、rag は wiki のサーバーの MCP クライアントになると決めた。rag の子ワーカーは抽出と OCR を行い、チャンクを `index_chunks` でサーバーに渡す。rag の `search` ツールは窓口として残し、中で wiki のサーバーに頼む。wiki が無効なら、検索できないと報告する。

【確認済み】

- wiki 0.4.0 で、MCP のツール `index_chunks` を足した。
- rag 0.5.0（`0ca80c7`）は、今も `scripts/rag_index.py` で LanceDB を使う。`index_chunks` を呼ぶ箇所はない。
- ADR-0013 で、台帳の SQLite（`catalog.sqlite`、`jobs-v2.sqlite`）は移行のあとも rag が持つと決めた。
- ADR-0014 で、抽出と OCR の結果を `data_dir` の `extracted/<内容の SHA-256>/<ocr_mode>-<ocr_dpi>-<OCR_REVISION>-<EXTRACT_REVISION>/` に置くようにした。索引の方式を変えても、この結果は使い回せる。

これを待っている作業:

- 全量の索引の E2E（`docs/plans/rag-full-ocr-auto-ann-2026-11-04.md` の段階 7〜8）
- RAG の品質の測り直し（回答できない質問の棄却、融合の重みと候補数、縦書きの誤判定、リランカーの遅さ）
- browse の RAG のデータ源（5）

進め方の案:

1. rag から wiki のサーバーにつなぐ方法を決める。rag の MCP サーバーが、wiki の中継に MCP のクライアントとして接続する。別のプラグインの内部のパスは組み立てない（ADR-0012 の理由）。
2. 子ワーカーの索引の書き込みを `index_chunks` に替える。PDF の登録を永続ジョブとして受け付け、次の接続で再開する仕組み（ADR-0007）は変えない。
3. `search` を wiki のサーバーに頼む形に替え、LanceDB の依存を外す。
4. 0.5.0 の台帳と索引から移す手順を決める。抽出の結果はそのまま使い、埋め込みと索引だけを作り直す。

設計を決めるので、ADR-0012 を補う ADR を書くか、ADR-0012 の「影響」に追記するかを先に決める。

【要確認】rag の MCP サーバーから wiki の中継に接続するとき、wiki のサーバーの初回の起動（依存の導入とモデルの取得で、手元の測定では約 107 秒）を、rag のジョブがどう待つか。

### 5. browse の RAG のデータ源

【記述】ADR-0010 の決定の 4 で、rag の PDF の検索は、rag の移行が済んでから足すと決めた。`query(collection=...)` の語彙のトークン（`query_tokens`）を誰が作るかは、移行のときに決める。静的版は RAG を持たない。

### 6. 全量の OCR の続き

【確認済み】`docs/research/rag-full-pipeline-2026-11-04/full-ocr-progress.json` では、対象 22,335 ページのうち、終わったのは 201 ページ（完了 166、空 35）である。この途中経過は、0.3.0 の方針の指紋で、PoC の経路で作ったものである。PoC のデータは、リポジトリの外の `../info-hive-dev-data/rag-poc-data` に移した（to884/info-hive-dev#56）。

rag 0.5.0 で、OCR の結果は埋め込みの方針と切り離された。今 OCR を進めても、4 で索引の方式を変えたときに無駄にならない。

【要確認】PoC の経路で作った 201 ページ分の途中経過を、0.5.0 の `extracted/` に引き取れるか。0.5.0 が引き取るのは 0.4.0 の作業領域の結果であり、PoC の出力は対象に含まれていない。引き取れなければ、201 ページはやり直しになるが、全体の 1% に満たない。

計画の約束（OS の電源を切らない、PDF の原本を動かさない、派生データを C の SSD に置く）は今も守る。

### 7. 記事の単位の PoC の判定と、ADR-0015 の段階 3

【確認済み】PoC は 36 件をすべて走らせた（to884/info-hive-dev#52、[結果](wiki-note-granularity-poc-2026-11-09.md)、[実行の記録](../agent-runs/2026-11-09-wiki-note-granularity-poc/README.md)）。状態は「合否は人の対応づけ待ち」である。機械で出せる指標は次のとおりだった。

- 36 件の引用 1,879 本は、すべて原本にそのままあった。必須条件の「捏造 0 件」は、主張が引用から言えるかを人が確かめるまで決まらない。
- 併用案は、全件を `source_only` にして一致を稼いではいなかった。SemaSynth の 2 資料で、併用案は 1 回あたり 3〜9 本の concept を作る計画を出し、現行は 0〜3 本だった。
- 新しく作るページのスラッグは、併用案で 0〜0.07 しか一致しない。同じページかどうかは、人の対応づけ（`page_cluster`）でしか決まらない。
- モデルの差が、方式の差と同じくらい大きかった。

残りの作業は、人の対応づけ、合格基準の確定（ADR-0015 の未決の事項）、合否の判定である。段階 3（`kind: "claim"` のページ、`claim` に限る 3 値の `status`、行き先どおりの更新）は、合格したときに入れる。件数を合図にはしない（ADR-0015）。

### 9. 知識を使うための機能

【記述】[LLM Wiki で蓄積した情報の活用方法の検討](wiki-knowledge-utilization-2026-11-06/brainstorm-diverge-converge.md) は、次の 3 つを着手の条件つきの候補にしている。

| 候補 | 着手の条件 |
