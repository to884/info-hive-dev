### 2. OCR の結果を、埋め込みの方針と切り離して保存する

【済み】[ADR-0014](../adr/0014-rag-keeps-extraction-independent-of-embedding.md)（2026年11月8日に承認）で決め、rag 0.5.0（to884/info-hive-rag#6、`v0.5.0`）として出した。

- OCR の途中経過と抽出した本文は、`data_dir` の `extracted/<内容の SHA-256>/<ocr_mode>-<ocr_dpi>-<OCR_REVISION の先頭 12 文字>-<EXTRACT_REVISION>/` に置く。wiki をまたいで共有するので、同じ PDF を 2 つの wiki に取り込んでも OCR は 1 回で済む。
- 埋め込みのモデルや分割の設定を変えても、OCR はやり直さない。前の索引は、抽出と最初の埋め込みのバッチが通ってから空にする。取り込み直す PDF の一覧は `status` で返す。
- 0.4.0 の作業領域にある抽出の結果は、そのまま引き取る。後始末は、文書ごとのロックを取ってから、使われていない結果だけを消す。
- Sol の敵対的レビューを 7 回受けた（`docs/agent-runs/2026-11-07-adr-0014-review/`）。直さずに受け入れた制約は、ADR-0014 の「残した制約」にある。

以下は 4 版目を書いた時点の状態と計画である。

【確認済み】OCR の途中経過（`page-*.json`）と抽出した本文（`document.md`）は、`<wiki の作業領域>/extracted/<generation>/` に置く。`generation` は、`doc_id`（内容の SHA-256）と `Config.fingerprint` から作る（`rag_index.py`）。`fingerprint` には、埋め込みのモデルと版、次元、分割の大きさと重なり、OCR の設定、トークナイザーの方針が入っている。

このため、埋め込みのモデルや分割の設定を変えると、OCR もすべてやり直しになる。0.4.0 で `fingerprint` の方針の名前を `rag-v2` にしたので、全量の OCR の途中経過（約 200 ページ）も、製品の経路からは使えなくなった。

やること:

- OCR と抽出の結果の鍵を、内容の SHA-256、OCR の版（`OCR_REVISION`）、`ocr_mode`、`ocr_dpi` だけにする。埋め込みと分割は、その結果を使って作り直せるようにする。
- 置き場所を wiki ごとにするか、`data_dir` で共有するかを決める。同じ PDF を 2 つの wiki に取り込むと、今は OCR を 2 回する。
- 古い版を消すときの後始末（`extracted/` の削除）も、新しい鍵に合わせる。

ADR-0012 の rag の移行でも、OCR の結果は「索引の方式によらず使い回せる」前提で進め方を組んでいる（3 版目の 3 と 4）。今の作りはこの前提を満たしていない。

### 3. `/rag:setup` で `ocr_mode` と `ocr_dpi` を変えられるようにする

【済み】rag 0.5.0 で、`configure` が `ocr_mode` と `ocr_dpi` を受け付けるようになった。結果の `reingest_required` と `extraction_changed` で、取り込み直しと OCR のやり直しが要るかを返す。`commands/setup.md` は、変えると取り込み直しになることを説明してから変える。2 が済んだので、OCR をやり直すのは `ocr_mode` か `ocr_dpi` を変えたときだけである。

以下は 4 版目を書いた時点の状態である。

【確認済み】`configure` が受け付けるのは、`data_dir`、`embedding_model`、`retrieval`（`reranker`、`rerank_limit`、`min_rerank_score`、`search_nprobes`、`search_refine_factor`）だけである。`ocr_mode`（`auto`、`always`、`off`）と `ocr_dpi`（72〜300）は、設定ファイル（`config.json`）を直接書き換えるしかない。

どちらも変えると `fingerprint` が変わり、取り込み済みの PDF はすべて入れ直しになる。`embedding_model` を変えるときと同じく、`/rag:setup` で説明してから変える。2 が済めば、`ocr_dpi` を変えたときだけ OCR をやり直せばよくなる。

### 5. rag の移行

【記述】ADR-0012 で、rag は wiki のサーバーの MCP クライアントになると決めた。rag の子ワーカーは抽出と OCR を行い、チャンクを `index_chunks` でサーバーに渡す。rag の `search` ツールは窓口として残し、中で wiki のサーバーに頼む。wiki が無効なら、検索できないと報告する。

【確認済み】

- wiki 0.4.0 で、MCP のツール `index_chunks` を足した。
- rag 0.4.0 は、今も `scripts/rag_index.py` で LanceDB を使う。`index_chunks` を呼ぶ箇所はない。
- ADR-0013 で、台帳の SQLite（`catalog.sqlite`、`jobs-v2.sqlite`）は移行のあとも rag が持つと決めた。

これを待っている作業:

- 全量の OCR と索引の E2E（`docs/plans/rag-full-ocr-auto-ann-2026-11-04.md` の段階 6〜8）
- RAG の品質の測り直し（回答できない質問の棄却、融合の重みと候補数、縦書きの誤判定、リランカーの遅さ）
- browse の RAG との連携（ADR-0010 の未決 4）

進め方の案:

1. rag から wiki のサーバーにつなぐ方法を決める。rag の MCP サーバーが、wiki の中継に MCP のクライアントとして接続する。別のプラグインの内部のパスは組み立てない（ADR-0012 の理由）。
2. 子ワーカーの索引の書き込みを `index_chunks` に替える。PDF の登録を永続ジョブとして受け付け、次の接続で再開する仕組み（ADR-0007）は変えない。
3. `search` を wiki のサーバーに頼む形に替え、LanceDB の依存を外す。
4. 0.4.0 の台帳と索引から移す手順を決める。2 が済んでいれば、OCR の結果と抽出した本文を使い回し、埋め込みと索引だけを作り直せる。

【要確認】rag の MCP サーバーから wiki の中継に接続するとき、wiki のサーバーの初回の起動（依存の導入とモデルの取得で、手元の測定では約 107 秒）を、rag のジョブがどう待つか。

### 7. browse

【記述】ADR-0002（承認）は、必要なときだけ起動するローカルサーバーを決めている。ADR-0010（提案、決定日は未定）は、Wiki を解釈する中核を Python の 1 か所に置き、サーバー、アプリ、静的 HTML を薄いアダプタにする案である。【確認済み】`commands/browse.md` はまだない。ADR は 0001〜0013 のうち、0010 だけが提案のままである。

ADR-0010 の未決は 6 件ある。

1. ページ集合（lint と search で違う。ADR は lint の集合を正とする案を推している）
2. 書き出し先
3. 静的出力のファイル名
4. RAG への経路。ADR-0012 で 4 つ目の案（閲覧の画面を wiki の MCP サーバーのクライアントにし、rag の索引も含めて検索する）が加わった。wiki の MCP サーバーはできたので、この案を軸に決め直せる
5. 静的版の検索の範囲
6. アプリの技術

実装前の PoC で確かめる項目は 5 件あり、どれもまだ確かめていない。第 1 段階（静的に描く閲覧）は 5 に依存しない。検索と RAG との連携は 5 が済んでからにする。

ADR-0013 で、ソースの要約ページの `raw:` は PDF の絶対パスになった。静的に書き出すときに、利用者のフォルダーの構成を載せるかどうかも決める。

### 8. MCP の起動の速さ

【確認済み】Windows の手元の測定では、壊れていない環境での `initialize` は、wiki 0.4.1 の 1.7〜1.8 秒から、0.4.2 で 2.3〜2.5 秒に延びた。0.4.2 では、中継とサーバーが起動の最初に各パッケージの dist-info の `RECORD` と照らしてファイルを確かめ、主な依存を import するので、その分が延びた。新しい版を初めて起動するとき（`--ensure`）は、新しい環境を作るので約 107 秒かかった。

縮める案（たとえば、確かめた結果を環境ごとに覚えておき、環境が変わったときだけ照らし直す）は、壊れた環境を見逃さないことを保ったまま行う。0.4.1 と 0.4.2 で直した壊れ方を、`tests/wiki/test_mcp_server.py` の RepairTests が確かめている。

### 10. 知識を使うための機能

【記述】[LLM Wiki で蓄積した情報の活用方法の検討](wiki-knowledge-utilization-2026-11-06/brainstorm-diverge-converge.md) は、次の 3 つを着手の条件つきの候補にしている。

| 候補 | 着手の条件 |
| --- | --- |
| コンテキストの切り出し（焦点から k ホップ、行数の予算） | 実際の wiki で 2 ホップの被覆率を測ってから |
| 出典のチェーン（主張 → ページ → source → raw） | ページ単位なら今も動く。主張単位は `raw_ref` を書く規約を先に置いてから。PDF は `raw_sha256:` で、別の PC の取り込みとも結べるようになった |
| 鮮度の lint（`valid_to` を過ぎた `current`、`superseded` を指す参照） | synthesis と時間のフィールドがたまってから。報告だけにして書き換えない |

【確認済み】作者の wiki（`~/info-hive/W0_Wiki/`）の Markdown のファイルは、concepts が 17、entities が 1、sources が 32、synthesis が 1 である。同じ検討は、機能を足す前に SCHEMA.md の 3 つの習慣（設計の前の query と synthesis の保存、取り込みのときの差分の報告、作業の終わりの learn）を 2〜4 週間回すことを勧めている。

## 後回しでよいもの

- `/wiki:evolve` の API のランナー。レビュー済みの価格表が 2026-10-13 に期限切れになり、レビューし直すまで実行を拒否する（`evolution-workflow.md`）。日本語の評価スイートも確かめていない。

- 日々の記録のプラグイン `log`（ADR-0006）。wiki のどの作業にも依存せず、wiki もこれに依存しない。いつ始めてもよい。
- ADR-0013 で受け入れた限界の見直し。大きさと更新時刻が同じで中身だけ違う場所を出典として返しうること、`register_pdf` の確認を省くとモデルが利用者の指定と違う PDF を渡しても人は見ないこと、wiki を公開すると `raw:` の絶対パスが見えること。ADR-0013 の「見直す条件」に当たったら見直す。
