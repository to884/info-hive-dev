# 機能実装の優先順位（2026年11月6日）

info-hive の wiki プラグインと rag プラグインについて、残っている作業を洗い出し、取りかかる順番を提案する。

## 結論

最初に、すでに配布してしまった 2 つのバージョンのリリースの後始末をする。次に、埋め込みの仕組みを統一するかどうかを決める。この判断が rag の残りの作業の形を変えるからである。判断を待つ間は、承認済みで判断に左右されない Web ページの取り込みと、グラフの後始末を進める。

| 順位 | 項目 | 種類 | 規模 | 理由 |
| --- | --- | --- | --- | --- |
| 1 | wiki 0.2.0 と rag 0.3.0 のリリースの後始末（2026-11-06 に対応済み） | 修正 | 小 | 利用者に届いているのに、タグ、GitHub リリース、導入確認がない。AGENTS.md のリリース規則に反している |
| 2 | 埋め込みとベクター DB の統一（案 A／B）を決める | 判断 | — | rag の全量 OCR の残り（段階 6〜8）と索引のコードが、この判断で作り直しになるかが決まる |
| 3 | Web ページの取り込み（計画の PR 2） | 実装 | 中 | ADR-0004 は承認済み。2 の判断にも browse にも依存しない |
| 4 | グラフ層の後始末（ADR-0009）と作業領域の残り（ADR-0008） | 実装 | 小〜中 | 承認済みの ADR の宿題。回帰テストがない |
| 5 | 統一案の実装（wiki の MCP 化、rag の移行）と全量の E2E | 実装 | 大 | 2 の結論が出てから着手する |
| 6 | ADR-0010 の承認と browse の PoC、第 1 段階 | 判断＋実装 | 中〜大 | 未決が 6 件、未確認の PoC が 5 件ある。先にページ集合を決める |
| 7 | RAG の品質の課題（回答できない質問の棄却、融合の重み、縦書きの誤判定） | 改善 | 中 | 5 で検索の基盤が固まってから測り直す |

3 と 4 は 2 の判断と並行して進められる。PR 3（知識ページの図、ADR-0005）は PR 2 と並行できるので、3 と同じ順位に置いてよい。

### 一つの判断が二つの作業を左右する

wiki を 127.0.0.1 で待ち受ける MCP サーバーにするかどうかは、二つの別の作業に同時に効く。

- 統一レポートの案 B では、rag は検索と索引の更新を wiki の MCP サーバーに頼む。wiki の MCP 化が rag の移行の前提になる（`embedding-backend-unification-2026-11-05.html` の 13 節）。
- ADR-0010 の未決 4「RAG への経路」も、今の入口が MCP しかないことから ADR-0007 の見直しにつながる。

このため、順位 2 の判断では「wiki を MCP にするか」まで一緒に決めると、rag の移行と browse の第 3 段階（RAG との連携）の両方の前提がそろう。

## 判断の基準

次の順に重みを置いた。

1. すでに規則に反している、または利用者に影響が出ているもの
2. ほかの作業を止めている判断
3. 承認済みで、判断待ちに左右されず、すぐ着手できるもの
4. 作業の無駄が出るおそれ（あとで作り直しになる作業は後ろに回す）
5. 規模（同じ順位なら小さいものを先にする）

### 2. 埋め込みとベクター DB の統一

2026-11-06 に決めた。追加の測定（E1〜E11）を [統一の決定のための追加測定](embedding-backend-decision-2026-11-06.html) にまとめ、決定を [ADR-0011](../adr/0011-shared-embedding-and-index-stack.md)（埋め込み、索引、語彙検索の組）と [ADR-0012](../adr/0012-wiki-owns-local-mcp-index-server.md)（wiki の MCP サーバー）に残した。語彙検索は Sudachi への統一ではなく、Tantivy にそろえて wiki には bigram、rag には Sudachi のトークンを入れる形になった。以下は調査の時点の記述である。

【記述】`docs/research/embedding-backend-unification-2026-11-05.html` は、wiki と rag の両方を ruri-v3-130m（ONNX、fp32）、usearch の HNSW（f16）、Tantivy にそろえる案を推している。

| 指標（全量） | 推奨の組 | 今の rag | 今の wiki の組 |
| --- | --- | --- | --- |
| 検索の p95 | 96.2 ms | 282 ms | 6,693 ms |
| 索引の容量 | 1,055 MiB | 3,730 MiB | — |
| 再現率 | 0.758 | 0.725 | 0.464 |

- torch をやめると、導入の容量が約 7.7 GB から約 0.8 GB に減る。
- 案 A（そろえるだけ）と案 B（wiki を MCP サーバーにして、モデルと索引の唯一の持ち主にする）の確定は「別の作業」とされている。今の wiki の CLI では、検索 1 回に約 3.1 秒かかる。

【確認済み】rag の実装は torch と LanceDB のままである。`scripts/rag_indexes.py` の IVF_SQ の自動作成と世代の BITMAP 索引は LanceDB 専用である。

【推測】全量 OCR と自動 ANN の計画（`docs/plans/rag-full-ocr-auto-ann-2026-11-04.md`）の段階 6（全量への反映）は 1% 未満しか進んでいない（22,335 ページ中 166 ページが完了）。統一案を採るなら、索引はどのみち作り直しになる。段階 6 を再開する前に、この判断を済ませたほうがよい。OCR の結果（ページごとの Markdown）は索引の方式によらず使い回せる見込みがあるので、OCR だけを先に回す選択肢もある。

決めること:

- 案 A と案 B のどちらを採るか。採らないなら、LanceDB のまま段階 6〜8 を終える。
- 案 B を採るなら、ADR を書く。ADR-0007 で未決だった「モデルの保持と共有」もここで決まる。
- 融合しても dense 単独を上回らないので、融合の重みと候補数を見直す（レポートの残課題）。

### 7. RAG の品質の課題
