# 機能実装の優先順位（2026年11月7日）

info-hive のプラグイン（`info-hive-wiki`、`info-hive-rag`）と開発用のリポジトリについて、残っている作業を洗い出し、取りかかる順番を提案する。

この文書は 3 版目である。2026-11-06 の 2 版目で 1 位から 4 位に置いた作業（0.2.1 のリリースの後始末、グラフ層の後始末、MCP サーバーと検索の基盤の移行、Web ページの取り込みと図）は、wiki の 0.2.1 から 0.4.2 で片付いた。そこで、rag の移行を中心に置いて書き直した。前の版は Git の履歴で読める。ファイル名の日付は最初の版のものである。

## 結論

最初に小さな後片付けと ADR-0008 の残りを済ませる。そのあと、本命の rag の移行に入る。全量の OCR は rag の移行と並行して、裏で回す。browse の第 1 段階も rag の移行を待たない。

| 順位 | 項目 | 種類 | 規模 | 理由 |
| --- | --- | --- | --- | --- |
| 1 | 後片付け（マーケットプレイスの公開範囲、CI のコメント、使い終えた worktree とブランチ） | 修正 | 小 | wiki をパブリックにしたことと、今の状態がずれている。放っておくと次の作業の邪魔になる |
| 2 | ADR-0008 の残り（`wiki_lint.py` と `wiki_search.py` の既定の wiki） | 実装 | 小 | 承認済みで、すぐ着手できる。CHANGELOG に「まだ `./wiki` のまま」と書いてある |
| 3 | rag の移行（ADR-0012） | 実装 | 大 | 今いちばん多くの作業を止めている。wiki の `index_chunks` はできたが、rag はまだ使っていない |
| 4 | 全量の OCR の続き | 実行 | 大（主に待ち時間） | 22,335 ページのうち約 200 ページで止まっている。結果は索引の方式によらず使えるので、3 と並行できる |
| 5 | browse（ADR-0010 の承認、PoC、第 1 段階） | 判断＋実装 | 中〜大 | 12 の ADR のうち、これだけが提案のまま。第 1 段階は 3 を待たない |

| 7 | 検索のしきい値 0.193 の測り直し | 測定 | 小 | 「基盤を移したあとに測る」とされていた条件を満たした |

1 と 2 は小さいので、3 に入る前に済ませる。4 は 3 と、5 の第 1 段階は 3 と並行して進められる。

## 判断の基準

次の順に重みを置いた。前の版と同じである。

1. すでに規則に反している、または利用者に影響が出ているもの
2. ほかの作業を止めているもの
3. 承認済みで、すぐ着手できるもの
4. 作業の無駄が出るおそれ（あとで作り直しになる作業は後ろに回す）
5. 規模（同じ順位なら小さいものを先にする）

前の版から変えた点は 2 つある。wiki の MCP サーバーができたので、それを待っていた rag の移行が「ほかの作業を止めているもの」の筆頭に上がった。wiki をパブリックにしたことで生じたずれを、後片付けとして先頭に置いた。

### 2. ADR-0008 の残り

【確認済み】

- `wiki_lint.py` の位置引数 `wiki` と `wiki_search.py` の `--wiki` は、今も既定が `Path("wiki")` である。0.3.0 で、ほかのスクリプトは設定の `dirs.wiki` を使うようにしたが、この 2 つは残した（CHANGELOG の 0.3.0 の Changed）。
- 設定の読み込みの一致テストは `tests/workspace/` に置いた。`assets/<slug>-NN.svg` の相対パスの不具合は 0.3.0 で直した。ADR-0008 の wiki 側の残りは、上の 2 つだけである。

MCP のツールは引数で wiki を受け取るので、この変更は CLI だけに効く。MCP が使えないときの戻り道も CLI なので、そろえておく価値がある。

### 3. rag の移行

【記述】ADR-0012 で、rag は wiki のサーバーの MCP クライアントになると決めた。rag の子ワーカーは抽出と OCR を行い、チャンクを `index_chunks` でサーバーに渡す。rag の `search` ツールは窓口として残し、中で wiki のサーバーに頼む。wiki が無効なら、検索できないと報告する。

【確認済み】

- wiki 0.4.0 で、MCP のツール `index_chunks` を足した。collection ごとに wiki とは別の索引に入れ、文書ごとに古い世代の行を消す。語彙検索のトークンは呼び出し側が作る。
- rag は 0.3.0 のままで、`scripts/rag_index.py` と `scripts/rag_server.py` が今も LanceDB を使う。`index_chunks` を呼ぶ箇所はない。
- rag の `plugin.json` は、`dependencies` に `wiki@info-hive` を宣言している。

これを待っている作業:

- 全量の OCR と索引の E2E（`docs/plans/rag-full-ocr-auto-ann-2026-11-04.md` の段階 6〜8）
- RAG の品質の測り直し（回答できない質問の棄却、融合の重みと候補数、縦書きの誤判定、リランカーの遅さ）
- browse の RAG との連携（ADR-0010 の未決 4）

進め方の案:

1. rag から wiki のサーバーにつなぐ方法を決める。rag の MCP サーバーが、wiki の中継に MCP のクライアントとして接続する。別のプラグインの内部のパスは組み立てない（ADR-0012 の理由）。
2. 子ワーカーの索引の書き込みを `index_chunks` に替える。PDF の登録を永続ジョブとして受け付け、次の接続で再開する仕組み（ADR-0007）は変えない。
3. `search` を wiki のサーバーに頼む形に替え、LanceDB の依存を外す。
4. 既存の LanceDB の索引から移す手順を決める。OCR の結果と抽出した本文は使い回し、埋め込みと索引だけを作り直す。

【要確認】rag の MCP サーバーから wiki の中継に接続するとき、wiki のサーバーの初回の起動（依存の導入とモデルの取得で、手元の測定では約 107 秒）を、rag のジョブがどう待つか。

### 4. 全量の OCR の続き

【確認済み】`docs/research/rag-full-pipeline-2026-11-04/full-ocr-progress.json` では、対象 22,335 ページのうち、終わったのは 201 ページ（前回までの 168 ページと、最後の実行の 33 ページ）である。`merge-progress.json` では、重複を除いた 905 文書のうち、索引に入れる準備ができたのは 196 文書（93,816 チャンク）である。

【確認済み】計画（`rag-full-ocr-auto-ann-2026-11-04.md`）の段階 1〜3（OCR の子プロセス、ページごとの確定と再開、GPU の点検）には、同じフォルダーに記録のファイルがある（`ocr-worker-pilot.json`、`ocr-interruption.json`、`gpu-ocr-pilot.json` など）。段階 4〜5 の LanceDB の索引の自動保守は、3 の移行で役目を終える。

OCR の結果（ページごとの Markdown）は、索引の方式によらず使い回せる。3 を待たずに、OCR だけを先に回せる。計画の約束（OS の電源を切らない、PDF の原本を動かさない、派生データを C の SSD に置く）は今も守る。

### 5. browse

【記述】ADR-0002（承認）は、必要なときだけ起動するローカルサーバーを決めている。ADR-0010（提案、決定日は未定）は、Wiki を解釈する中核を Python の 1 か所に置き、サーバー、アプリ、静的 HTML を薄いアダプタにする案である。【確認済み】`commands/browse.md` はまだない。ADR は 0001〜0012 のうち、0010 だけが提案のままである。

ADR-0010 の未決は 6 件ある。

1. ページ集合（lint と search で違う。ADR は lint の集合を正とする案を推している）
2. 書き出し先
3. 静的出力のファイル名
4. RAG への経路。ADR-0012 で 4 つ目の案（閲覧の画面を wiki の MCP サーバーのクライアントにし、rag の索引も含めて検索する）が加わった。wiki の MCP サーバーはできたので、この案を軸に決め直せる
5. 静的版の検索の範囲
6. アプリの技術

実装前の PoC で確かめる項目は 5 件あり、どれもまだ確かめていない。

第 1 段階（静的に描く閲覧）は 3 に依存しない。検索と RAG との連携は 3 が済んでからにする。

### 6. MCP の起動の速さ

【確認済み】Windows の手元の測定では、壊れていない環境での `initialize` は、0.4.1 の 1.7〜1.8 秒から、0.4.2 で 2.3〜2.5 秒に延びた。0.4.2 では、中継とサーバーが起動の最初に各パッケージの dist-info の `RECORD` と照らしてファイルを確かめ、主な依存を import するので、その分が延びた。新しい版を初めて起動するとき（`--ensure`）は、新しい環境を作るので約 107 秒かかった。

縮める案（たとえば、確かめた結果を環境ごとに覚えておき、環境が変わったときだけ照らし直す）は、壊れた環境を見逃さないことを保ったまま行う。0.4.1 と 0.4.2 で直した壊れ方（`METADATA` の欠け、モジュールの本体の欠け、同時の入れ直し）を、`tests/wiki/test_mcp_server.py` の RepairTests が確かめている。

### 7. 検索のしきい値 0.193 の測り直し

【記述】移植計画の P3。前の版は「検索の基盤が変わるので、移したあとに測り直す」として後回しにした。

【確認済み】wiki 0.4.0 で、検索の基盤は ruri-v3-130m の ONNX、usearch、Tantivy の BM25 と RRF に移った。測り直しの条件は満たした。新しい基盤の点数の分布で、しきい値がまだ要るのか、要るならいくつにするのかを測る。

### 8. 知識を使うための機能

【記述】[LLM Wiki で蓄積した情報の活用方法の検討](wiki-knowledge-utilization-2026-11-06/brainstorm-diverge-converge.md) は、次の 3 つを着手の条件つきの候補にしている。

| 候補 | 着手の条件 |
| --- | --- |
| コンテキストの切り出し（焦点から k ホップ、行数の予算） | 実際の wiki で 2 ホップの被覆率を測ってから |
| 出典のチェーン（主張 → ページ → source → raw） | ページ単位なら今も動く。主張単位は `raw_ref` を書く規約を先に置いてから |
| 鮮度の lint（`valid_to` を過ぎた `current`、`superseded` を指す参照） | synthesis と時間のフィールドがたまってから。報告だけにして書き換えない |

【確認済み】作者の wiki（`~/info-hive/W0_Wiki/`）の Markdown のファイルは、concepts が 17、entities が 1、sources が 32、synthesis が 1 である。前の版の時点（23 ページ、synthesis は 0 件）より増えたが、synthesis はまだ少ない。同じ検討は、機能を足す前に SCHEMA.md の 3 つの習慣（設計の前の query と synthesis の保存、取り込みのときの差分の報告、作業の終わりの learn）を 2〜4 週間回すことを勧めている。
