## 1. 結論の要約

**提案は一括では導入しない。提案の骨格の多くは現行のプラグインに既にあり、足りないのは「検査」と「記録」である**（提案）。4 体が独立にこの結論に至り、相互レビューでも崩れなかった。

| 区分 | 要素 |
| --- | --- |
| 導入する | lint に索引の分類の検査、出典の参照の検査、正式なタグの検査を足す。source ページに「主張と行き先」の記録を足す。5 区分の方法論マップは、説明と設計レビューの見取り図として使う |
| 変えて導入する | `status` は `kind: "claim"` のページに限り、`experience-pattern` と同じ 3 値（`hypothesis`、`supported`、`superseded`）にする。「手順と概念を混ぜない」は、独立して使う長い手順に限る。MOC は新しい `type` ではなく、既存の `index.md` と分割した索引で担う |
| 導入しない | `id`、`scope`、入れ子の `relations`、`type: journal`、`type: graph`、`type: decision`、全ページ共通の `status`、出典なしの `draft`、`/wiki:decide`、`status` を上げる意味の `/wiki:promote`、`/wiki:lint --relations` |
| 保留 | `questions.md`（Competency Questions）、`/wiki:plan`、`broader` の述語、`/wiki:lint --fix`、`reviewed_at`、`howto` |

最初に入れるのは、lint の 3 つの検査（マイナー版 0.7.0）である。作者の wiki で実際に起きている誤りを見つけられ、LLM の判断に頼らず、既存のページを壊さないからである。

**承認済みの ADR は変えない。** 方法論の整理と「問題が起きたら入れる」原則は、新しい ADR（記事の作成と保守の方法論）に書く。

## 2. 提案と現行の対応

提案は info-hive の現状を知らずに書かれている。コマンド名（`/wiki:ingest`、`/wiki:query`、`/wiki:lint`、`/wiki:graph`）は現行と同じだが、中身は同じではない。4 体には、名前の一致を導入済みの根拠にしないよう求めた。C の分解（42 要素）から、判断に効くものを抜き出す。

| 提案の要素 | 現行 | 判定 | 理由 |
| --- | --- | --- | --- |
| 区分 1 のきっかけ別のコマンド | 一部（`ingest`、`query`、`learn`、`lint`） | 変える | 既存のコマンドを、きっかけとの対応表で案内する。入口は、既存のコマンドで表せない手順が出てから足す |
| 区分 2 の Atomic Notes とページタイプ | 一部 | 変える | 直前の検討の結論（用語ページ + 選別した主張ページ）に従う |
| `id` をファイル名と一致させる | ない | 導入しない | スラッグが既に識別子で、`id` は常に同じ値になる。重複と整合の検査が増えるだけ |
| `scope: common \| project:<name>` | ない | 導入しない | ADR-0008 は作業領域（保存先）で分ける。ページの属性は保存先の境界を保証しない |
| 全ページ共通の `status` | 一部（`experience-pattern` だけ） | 導入しない | 既存の `status` と値も意味も違う。編集の状態、確からしさ、失効を 1 つの列に混ぜることになる |
| `relations`（`broader`、`related`、`answers`） | 一部（本文の wikilink、`mentions`、型付きエッジ） | 導入しない | 入れ子の frontmatter はパーサーが読まない。`related` は本文のリンクと既存の `mentions` で足りる。ADR-0009 の型付きエッジと二重になる |
| `type: journal` | ない | 導入しない | ADR-0006（日々の記録は別のプラグイン `log`）に反する |
| `type: graph` | グラフ層がある | 導入しない | グラフはページの種類ではなく派生の索引である |
| `type: decision` と `/wiki:decide` | グラフのノード型だけある | 導入しない | 決定の正本はプロジェクト側の ADR に置き、wiki には source として取り込む |
| `type: moc` | `index.md`、`indexes/` | 変える | 新しい `type` は要らない |
| `status: draft` の記事は出典なしでよい | ない | 導入しない | 出典のない推測が wiki の事実のページに流れ込む。現行は出典を必須にしている |
| `/wiki:promote` | ない | 保留 | 「主張を独立させる」操作と「内容をレビューして承認する」操作を、別のものとして設計し直す必要がある |
| `questions.md` と `/wiki:plan` | 一部（lint の不足の提案） | 保留 | 置き場所の 3 案すべてに副作用があった（第 5 節） |
| source の「主張の一覧」 | 一部（「主な主張」を要約する規約） | 変えて導入 | 一覧という形式ではなく、知見をどこへ反映したか（行き先）を残すことに価値がある |
| 出典を lint で検査する | ない | 導入 | 規約はあるが、実装が追いついていない（第 3 節） |
| Diátaxis、KCS、SKOS | ない | 部分的に参照 | 原典の性質と、提案独自の簡略化を分けて扱う（第 6 節） |

**採点は採否の決め手にならなかった。** 4 体とも、変えて導入する要素は変更後の案で、導入しない要素は原案で採点していた。採る側が高く出るのは最初から決まっていたことになる。採否を支えたのは点数ではなく、コード、ADR、作者の wiki での確認である。

## 3. 最初に入れる lint の 3 つの検査

| 検査 | 見つけるもの | 作者の wiki での現状 |
| --- | --- | --- |
| `index_type_mismatch` | 索引の見出し（「ソース」「シンセシス」など）と、そこに並ぶページの `type` の食い違い | 「シンセシス」の欄に `type: source` のページが 16 本ある（事実。4 体が独立に実測）。現行の `wiki_lint.py` は `index.md` を走査から外している（事実。126 行目の `SKIP_TOP_LEVEL_FILES`）ので、見つけられない |
| `unresolved_sources`、`missing_raw` | `sources:` が実在しない source ページを指していないか。source の `raw:` の原本があるか | 現在 0 件で、価値は予防にとどまる。既定の必須キーに `sources` はない（事実。278 行目の `DEFAULT_REQUIRED_FM`） |
| `unknown_tags` | `SCHEMA.md` のタグの体系にないタグ | `Windows`（2 ページ）、`MCP`、`Claude Code` が体系の外にある（事実） |

実装上の注意は 2 つある。

- `index_type_mismatch` は、見出しの直下にある wikilink だけを読む。冒頭の説明文の `[[消費税]]` のような例示は除く。
- 正式なタグの一覧は `--allowed-tags` で渡す形にする。

**A が出したログの書式の検査は採らない。** `wiki_evolve_loop.py` が正規に出す `- YYYY-MM-DD: ...` の行と、`log.md` の冒頭の前文を誤って検出する（C と D が反例を示した）。

## 4. source の「主張と行き先」

4 体が独立に至った唯一の改善策である。ただし、効果は測っていない（要確認）。

source ページに `## 主張と行き先` の節を置き、取り込みで抜き出した主張ごとに、行き先と理由を短い表で残す。行き先の値は英語の識別子（`create`、`update`、`source_only`）にする。

| 候補 | 主張と成り立つ条件 | 根拠の位置 | 行き先 | 理由 |
| --- | --- | --- | --- | --- |
| c1 | 同一環境では生成物のバイト一致を確かめる | 原本の該当節 | `update` | 環境の条件を省かない |
| c2 | 異なる Python と SQLite では、値、型、CSV の一致を確かめる | 原本の該当節 | c1 と分けて判断 | 一致の条件が違う |

（C の作例。`semasynth再現性の検証-2026-11-06` の 14〜18 行をもとにした候補で、raw の原文とは照合していない）

**段階を分ける。** 記録を残すだけの規定は段階 2 で入れる。記録した行き先どおりにページを更新させる規定は、直前の検討の PoC に合格してから入れる。B は「`source_only` 以外の行き先が 10 件たまったら入れる」という合図も出したが、C と D はこれを致命的な欠陥と判定した。件数は LLM 自身の未検証の判定を数えているだけで、PoC を迂回できるからである。B は反論していない。

## 5. 割れた論点の決着

| 論点 | 決着 | 根拠 |
| --- | --- | --- |
| `kind: "claim"` のページに `status` を持たせるか | 持たせる。3 値、`claim` に限る、オプトイン、PoC の合格後 | C と D は持たせない立場だったが、B の「持たせないと古い主張を機械的に見つける手段がない」に反論できなかった。直前の検討の総括にも残っていた論点である。矛盾は `status` ではなく本文の `## 矛盾` で表す |
| グラフの移行 | `kind` の付与と、`ontology.yaml` への `maps_from` の追加を別の段階にする | `maps_from` を足すと `concept:a --depends_on--> concept:b` の主語が `claim:a` に変わる。`depends_on` は主語に `claim` を受け付けないので、型の不一致になる（C が実際の関数で再現）。参照切れを直しただけでは移行は終わらない |
| `questions.md` の置き場所 | 導入しない。答えられなかった問いが実際に繰り返されたら再検討する | 3 案とも欠陥があった。`log.md` に `gap` の行を残す案（A）は、追記専用なので「回答済み」を表せない。`indexes/questions.md`（D）は、`wiki_stats.py` が `indexes/` があるだけで分割済みと判定するため分割の助言が消え（事実）、MCP の `list_index` も台帳を索引として返す。wiki のルートに置く案（B）は、lint、グラフ、検索、MCP サーバーの除外の一覧を直す必要がある |
| `broader` を根拠なしの型付きエッジにする案（A） | 保留 | `requires_evidence: false` はコードが受け付ける。しかし C と D が実際の関数で、`source`、`evidence`、`confidence`、`status` をすべて省いた循環するエッジが検出 0 件で通ることを再現した。`graph-workflow.md` の「全フィールド必須」の契約との食い違いと、循環の検査がないことを先に解く必要がある |
| 必須の節（`## 主な主張` など）を検査するか | `SCHEMA.md` で選んだときだけ有効にする | `page-conventions.md` は本文に固定のテンプレートを求めていない（D）。`## 主な主張` のない source 32 本を「欠けている」とは数えない |

## 6. 提案自体の誤りと、原典との違い

採否の判断とは分けて記す（C の一覧から抜粋）。

- 「8 コマンド」とあるが、一覧表は 6 本で、`graph` を足しても 7 本である。
- `/wik:lint`、`/wiki promote`、`<pathっurl>`、`syntesis` は誤記。
- `status` は 4 値（`draft`、`reviewed`、`canonical`、`deprecated`）なのに、ロードマップでは「三段階」とある。
- スキーマの正本を `SKILL.md` に置くという記述と、フェーズ 0 で `CLAUDE.md` に書くという記述が食い違う。
- `answers` は、例では `relations` の中にあり、説明の表では独立したフィールドとして扱われている。
- `sources` は、例では source ページの ID なのに、検査の説明では「raw/ に実体があるか」になっている。間に source ページの `raw:` を解決する段がない。
- `/wiki:plan` の後続の操作に、定義されていない `answer` コマンドが出てくる。
- 最初のテンプレートが source、concept、journal の 3 種なので、取り込みが作る entity に対応するテンプレートがない。
- 原典との違い: SKOS の `broader` は推移的ではなく、循環の禁止は SKOS からは自動では決まらない。KCS の記事の状態は、出典の有無だけでは決まらない。「`draft` は出典不要、`reviewed` は出典必須」は KCS そのものではなく、提案独自の設計である（C が原典を参照）。

## 8. 作者の判断が要る点

### 作者の決定（2026年11月9日）

| 論点 | 決定 | 実施の状況 |
| --- | --- | --- |
| SemaSynth の記録の置き場所 | (a) を選んだ。SemaSynth のプロジェクトの wiki（`C:\works\semasynth-dev\wiki\` と `raw\`）に移す。ADR-0008 は変えず、グローバルな指示を改める | 移動済み。source 28 本と raw 34 ファイルを移し、W0 は 30 ページになった。W0 から SemaSynth へのリンク 3 か所は文に直した。両方の wiki で lint の指摘は 0 件。グローバルの `CLAUDE.md` も、プロジェクト固有の記録はプロジェクトの wiki に残すよう改めた |
| 空白を含むファイル名 | 改名する | 改名済み。`bm25のidfの式の違い`、`windowsでのtantivyのcommitの失敗`、`claude-codeのstdioのmcpサーバーとジョブオブジェクト`、`llm-wikiで蓄積した情報の活用方法`。被リンクと frontmatter のリストを付け替えた |

置き場所は ADR-0008 の作業領域（`<プロジェクトルート>/<プロジェクト名>/wiki`）ではなく、プロジェクトルートの直下にした。`semasynth/` が既にコードのサブモジュールの名前だからである。

以下は、決定の前に整理した論点である。

| 論点 | 内容 |
| --- | --- |
| SemaSynth の記録 28 本の置き場所 | ADR-0008 は「ユーザースコープの作業領域にプロジェクト固有の情報を置かない」と決めている。一方、作者の全体指示は「どのプロジェクトの作業でも `~/info-hive/W0_Wiki/` に残す」と求めている。衝突は提案とではなく、作者の 2 つの決定の間にある。選択肢は、(a) プロジェクトの wiki などに移す（ADR は変えない。ユーザースコープの source は 9 本に減る）、(b) 残して ADR-0008 か全体指示を改める（再利用できる知見だけを `concept` に出す運用が前提）、(c) タグで区別する（ADR-0008 の境界を満たさないので勧めない） |
| 空白を含むファイル名 4 本 | `concepts/` に 3 本、`synthesis/` に 1 本。改名するなら、被リンクの移し替えと同時に行う |
| `--fix` | 現行の lint は「検出するが修正しない」が契約である。差分の承認つきで機械的な修正だけを許すかは作者が決める。1 回の lint で機械的な指摘が 20 件を超えたら再検討する |
| PoC の規模 | 固定の 3 資料、2 モデル、3 回、現行と変更案の 2 方式で 36 件を起点にする。一致率 85% などの値は暫定値で、達成の見込みは分からない。捏造と条件の脱落は 0 件を必須条件にする |

## 9. 確認できなかったこと

- 主張の表を足すと、source ページが大きさのソフト上限を超えるか（A の推測）。
- Foam が日本語のファイル名の `[[slug]]` を解決するか。
- lint を作者の wiki で実際に走らせた体はなく、件数はすべてファイルの読み取りと集計による。
- SKOS、Diátaxis、KCS の外部文書を参照したのは C と D だけである。
