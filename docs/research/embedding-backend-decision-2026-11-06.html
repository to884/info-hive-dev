埋め込みと索引の統一を決めるための追加測定

統一の測定（2026-11-05 のレポート）が推した組（案 A）と wiki の MCP サーバー（案 B）について、決定に足りなかった 9 点を E1〜E11 の測定で確かめた。

1. 要約: 閾値を外れた 3 点のうち、1 点は決まり、2 点は測り直した

モデル（ruri-v3-130m の ONNX fp32）とベクトル索引（usearch HNSW f16）は、測定の結果でも変わらない。融合も残す。変えるのはパラメーターだけで、RRF を k=30、語彙の重み 0.5 にする。最初の測定では次の 3 点が計画の閾値を外れたので、計画の停止の規則に従って ADR-0011 と ADR-0012 を書く前で止めた。その後 2026-11-06 に 1 点を決め、残りの 2 点は測り直した。

2. 決めたことと、残る判断

再埋め込み: 目安の 20 分を緩める（決定）

目安の 20 分を緩め、初回だけ時間がかかることを upgrade の案内に書く。区間ごとの推定では、rag の長さのチャンク 8,275 件で 57 分、wiki の長さのセクションなら 24 分 だった。無作為の 1,000 行で測ると実測は推定の 1.36 倍だったので、rag の長さで約 77 分になる。wiki の長さの値にも同じ比を掛けると約 33 分だが、この比は natural の行で測ったもので、wiki のセクションでは確かめていない。1 ページの更新は 0.26 秒で、目安の 5 秒に収まる。

語彙検索: 案 2（Tantivy に wiki の bigram を登録する）はゲートを通った

Sudachi（SplitMode C、normalized_form）に替えると、ja のセクションの MRR が 0.901 から 0.849 に下がった。下がったのは filter、paraphrase、two-char の種類である。そこで案 2 を測った。語彙のスコアを Tantivy の BM25 で出し、トークンは wiki の bigram のまま渡す構成である。en と ja のゲートをどちらも通り、ページ・セクション・ハイブリッドの recall@10、MRR、偽陽性の割合は、wiki の BM25 と小数第 3 位まで同じだった。個々のスコアは k1（wiki 1.5、Tantivy 1.2）の違いで変わり、下位の順位が入れ替わることはあった。

  • 案 2（提案）: 語彙のエンジンを Tantivy にそろえ、wiki の索引には bigram、rag の索引には Sudachi のトークンを入れる。エンジンと索引の扱い（書き込みの規則、世代の削除）は 1 つにまとまり、トークンの作り方だけが索引の集まりごとに違う。
  • 案 1: wiki は今の純 Python の BM25 のまま、rag だけ Sudachi + Tantivy にする。

MCP の上乗せ: 測り直しても 10 ms を超えた

同じ日に 3 通りで測り直した。ログを止めても上乗せはほとんど変わらず、応答を SSE から JSON にすると 13.9 ms まで下がった。HTTP のサーバーへ直接 MCP で呼ぶだけで 10.1 ms かかり、中継の 1 段は 3.9 ms である。

  • 案 2: 試作のサーバーの認証は starlette の BaseHTTPMiddleware で書いている。これを ASGI のミドルウェアに書き直すなど、HTTP の MCP そのものの費用を減らせるかを測る。
  • 案 3: 目安の 10 ms を緩める。

E6 のメモリの提案値（wiki 規模 1.0 GiB、全量 2.5 GiB）は、モデルを読み込んだ構成ではどの索引でも超えた。FAISS も収まらないので索引の選択は変わらず、提案値のほうを見直す（§12）。

11. 書き込みの安全性（E5）: 単一の書き手なら安全、Tantivy は入れ直しが要る

  • (a) 別のプロセスが view で開いている索引ファイルの置き換えは、20 回とも PermissionError で失敗した（成功 0 回）。Windows では、メモリに写像されたファイルを置き換えられない。
  • (b) 1 つのプロセスが索引を読み込み、追記、一時ファイルへの保存、os.replace を繰り返した。wiki 規模 200 回、全量 5 回で、保存・置き換え・検索のエラーは 0、最終の件数も一致した。保存の最大は wiki 規模 0.07 秒、全量 2.8 秒。読み書きのロックは書き手を優先する形にした。読み手を優先する形では、検索が途切れないと書き手がロックを取れず、測定が 6 時間止まった。
  • (c) 版ごとのファイルと manifest の付け替えは、強制終了 20 回の後も壊れた版はなかったが、書き手が manifest.json の置き換えで PermissionError になった。読み手が manifest.json を開いている間は置き換えられないためと考える。この方式を Windows で使うなら、書き手と読み手の両方に入れ直しが要る。
  • (d) 別のプロセスの読み手が reload を続けると、Tantivy の commit 2,637 回のうち 1,297 回が失敗した。同じプロセスの読み手（d2）でも 3,509 回のうち 1,034 回が失敗し、最後に残った文書は 2,300 件（追加したのは 228,150 件）だった。

読み手がいなくても失敗するかを、書き手だけで確かめた。

サーバーの起動のしかたで 2 つの問題が出た。1 つ目は、venv の python.exe が本体を子プロセスとして起動するので、Popen が返す pid と、サーバーが記録した pid が一致しないこと。起動の前にロックの中で server.json を消し、新しく現れた server.json を今起動したサーバーのものとみなすようにした。2 つ目は、MCP の SDK（mcp 1.30.0）の stdio_client が中継を KILL_ON_JOB_CLOSE のジョブに入れること。DETACHED_PROCESS も CREATE_BREAKAWAY_FROM_JOB も、エラーにはならなかったがサーバーはジョブに残り、中継の終了とともに止まった。WMI（Win32_Process.Create）に起動させるとジョブの外に出た。

このジョブは、測定に使った Python の MCP の SDK のものである。Claude Code（CLI 2.1.316）でも起きるかを、標準ライブラリだけで書いた最小の MCP サーバーを claude -p に登録して確かめた。サーバーはジョブに入っていなかった。DETACHED_PROCESS で起動した孫は、claude が終わった後も残った（サーバー自身は claude とともに終わった）。Claude Code の下では、サーバーを DETACHED_PROCESS で起動すれば足りる。デスクトップアプリは測っていない。

14. 最終の採点（E11）: usearch が速く、FAISS が小さい

15. OCR と fingerprint: 抽出用と索引用に分ける

今の rag の fingerprint はモデルを含むので、モデルを替えると 22,335 ページの OCR からやり直すことになる。統一の測定のレポートの §12 はこの前提で移行の手間を見積もっていた。ADR-0011 では fingerprint を 2 つに分ける。抽出用は OCR の方式、dpi、revision から作り、抽出結果の再利用に使う。索引用はモデル、実行系、チャンクの切り方、索引の種類から作り、埋め込みと索引だけを作り直す判断に使う。この分け方は設計で、今回は測っていない。

16. ADR との整合

  • ADR-0001: 127.0.0.1 だけで待ち受け、起動ごとのトークンと Host の確認を入れた試作で、トークンなしは 401、Host の偽装は 421 になった。wiki を書き換える API を持たない条件 3 に当たるので、案 B のツールから ingest_source を外す。
  • ADR-0007: サーバーは使われなければ止まり（idle で 0 になった）、OS のサービスとして登録しない。Claude Code の下では DETACHED_PROCESS で起動すれば足り、WMI のようにホストの外からプロセスを起動する方式は使わない。
  • ADR-0010: 未決 4（RAG の経路）に、wiki の MCP サーバーに検索と索引の更新を頼む案を加える。状態は変えない。
