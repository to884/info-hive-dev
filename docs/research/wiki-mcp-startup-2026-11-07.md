# MCP の起動の速さ（2026年11月7日）

優先順位の文書（`feature-priority-2026-11-06.md`）の 6 位「MCP の起動の速さ」の記録である。wiki 0.4.2 で、壊れていない環境での `initialize` が延びた。その原因を調べ、wiki 0.6.1 で縮めた。

## 結論

- 延びた原因は、中継とサーバーが起動の最初に行う環境の確かめ（`wiki_mcp_common.env_problems`）だった。dist-info の `RECORD` の各行（中継の環境で約 1,650 行、サーバーの環境で約 3,800 行）を、1 行ずつ `Path.stat()` で確かめていた。Windows ではファイルを 1 つずつ開くので遅く、ウイルス対策の検査も重なる。
- 0.6.1 では、site-packages を `os.scandir` で 1 回なめ、ディレクトリの一覧からファイルの大きさを読む。一覧で決められない行と、大きさが `RECORD` と違う行だけを、1 つずつ確かめ直す。
- 確かめた結果を覚えておく方式（キャッシュ）は採らなかった。毎回すべての行を `RECORD` と照らすので、壊れた環境を見逃さない範囲は 0.4.2 と同じである。
- 修正前（0.6.0）と修正後を同じ条件で交互に測ると、`initialize` の中央値は 1,290 ms から 1,173 ms に、サーバーが止まっている状態からの `tools/list` は 2,019 ms から 1,757 ms に縮んだ。

## 原因の内訳

同じ PC で、環境の確かめだけを、プロセスの中で繰り返して測った。

| 環境 | ファイル | 0.6.0 の確かめ | `os.scandir` でなめる時間 | 0.6.1 の確かめ |
| --- | --- | --- | --- | --- |
| 中継 | 1,650 | 約 360 ms（1 回目は 1,115 ms） | 約 47 ms | 約 90 ms |
| サーバー | 3,775 | 7 分を超えても終わらなかった（rag の検証と CPU を取り合っていた） | 約 100 ms（1 回目は 152 秒） | 約 140 ms（1 回目は 22 秒） |

- 1 回目の値はディスクのキャッシュが冷えていたときのもので、ほかのセッションが rag の OCR を流していた。温まった状態の値と分けて読む。
- 0.6.1 の確かめの値は、レビューで直す前の版で測った。直したあとも、ディレクトリを 1 回なめて照らす作りは同じである。
- `RECORD` の読み取りと解析は、中継の環境で約 12 ms だった。
- 中継の `import mcp` は、それだけで 1.5〜1.7 秒かかった（`-X importtime`）。0.4.1 も中継は `mcp` を import していたので、0.4.2 で延びた分ではない。0.4.2 で足した import のうち、`filelock` と `psutil` は合わせて約 80 ms だった。`httpx` と `mcp.client` は `import mcp` が読み込むので、増えていない。
- 1 つずつ確かめ直した行は、中継の環境で 11 行、サーバーの環境で 19 行で、どれも site-packages の外の `Scripts/*.exe` だった。

## 起動の速さの比べ方

`tests/wiki/bench_mcp_startup.py` で、0.6.0（`36a4089`）のスクリプトと作業ツリー（0.6.1）のスクリプトを交互に（ABAB…）7 回ずつ起動した。結果は [`wiki-mcp-startup-2026-11-07/startup.json`](wiki-mcp-startup-2026-11-07/startup.json) にある。

- .mcp.json と同じく、入口（`wiki_mcp_launch.py`）を `uv run --script` で起動した。版ごとにデータの置き場所を分け、埋め込みはテスト用のもの（モデルを読み込まない）にした。
- 版ごとの最初の 1 回は、uv の環境を作る時間を含むので捨てた。
- Windows 11、16 論理 CPU、uv 0.12.2、Python 3.12.13。測る前の 1 秒の CPU の使用率は 18〜32% だった。rag の OCR と検証のプロセスは動いていなかった。
- スクリプトの写しと一時ディレクトリは C ドライブ（SSD）に置いた。D ドライブに置くと、修正前の版だけ読み込みが遅くなり、条件がそろわない。

| 測ったもの | 0.6.0 の中央値 | 0.6.1 の中央値 | 0.6.0 の p95 | 0.6.1 の p95 |
| --- | --- | --- | --- | --- |
| `initialize`（サーバーは止まっている） | 1,290 ms | 1,173 ms | 1,316 ms | 1,253 ms |
| `tools/list`（サーバーの起動を含む） | 2,019 ms | 1,757 ms | 2,280 ms | 1,808 ms |
| `initialize`（サーバーは動いている） | 1,276 ms | 1,159 ms | 1,394 ms | 1,181 ms |
| `tools/list`（サーバーは動いている） | 114 ms | 113 ms | 127 ms | 123 ms |

- `initialize` は中継の確かめの分（約 120 ms）、サーバーが止まっていたときの `tools/list` はサーバーの確かめの分（さらに約 140 ms）縮んだ。サーバーが動いているときの `tools/list` は変わらない。
- 優先順位の文書にある 0.4.2 の 2.3〜2.5 秒は、別の時に別の方法で測った値である。今回の 0.6.0 の 1.29 秒とは条件が違うので、直接は比べない。0.4.1 との差を同じ条件で測り直してはいない。
- 残りの約 1.2 秒の多くは、uv の起動（`uv run`、`uv sync`、`uv python find`）と中継の `import mcp` である。どちらも 0.4.1 からある。

## 壊れた環境を見逃さないこと

- 欠けたファイル: ディレクトリの一覧にない行は、すべて 1 つずつ `stat()` で確かめるので、0.6.0 と同じく見つかる。
- 大きさの違うファイル: 一覧の大きさが `RECORD` と違えば、`stat()` で確かめ直してから報告する。
- 一覧を使わない行: site-packages の外（`../../Scripts/` など、`..` を含む行）、シンボリックリンク、名前の大文字と小文字が一覧と違う行。`..` を含むパスは、POSIX ではシンボリックリンクをはさむと、文字列の上の正規化と実際の場所が食い違う。
- 扱わないこと: Windows のディレクトリの一覧の大きさは、同じファイルを別のハードリンクから書き換えると、古いまま残ることがある（Microsoft の説明）。uv は環境のファイルをその場で書き換えず、入れ直すときは消してから置くので、この確かめでは扱わない。
- 試験: `tests/wiki/test_mcp_server.py` の RepairTests（`METADATA` の欠け、モジュールの本体の欠け、遅れて import するモジュールの欠け、同時の入れ直し）は、Windows で通った。偽の site-packages で確かめる `EnvProblemsTests` を足した（`..` をはさむシンボリックリンクの試験は、POSIX だけで動く）。

## レビュー

GPT-6.1 Sol に、変更の敵対的レビューを頼んだ。指摘のうち、シンボリックリンク（リンク自体の大きさで一致してしまう）、`..` を含む行、大文字と小文字を区別する NTFS のディレクトリの 3 つは直した。ハードリンクの古い大きさは、上の「扱わないこと」に書いた。`.pyc` のような `RECORD` にないファイルまでなめる点は、`__pycache__` をなめないようにし、大きさは照らす行だけで読むようにした。
