# 初回公開と公開状態の整合性

[本番有効化判定](2026-11-19-wiki-production-readiness.md)の条件①②を実装した。初回の候補を作る前にライブの基準を採取し、公開の直前に共通ロックの内側で再照合する。公開済みの wiki では、ポインター、完了記録、公開先の指紋が揃う場合に読み取りや再実行を受け付ける。

## 実装

- 初回は `capture_live_base(wiki)` → 候補の作成 → `build_plan(..., live_base=...)` → 承認 → `apply_plan` の順に進める。途中で確定したライブ変更は候補の作り直しに戻す。保留の保存と最初の日誌の作成は共通の `pending.lock` で直列化し、未反映の承認済み差分があれば初回切り替えを拒む。
- wiki 直下の `.wiki-publication`、`current`、`publication-head.json`、公開版ごとの完了記録とマニフェストを照合する。最新版の成果物を照合し、指定した履歴の版も読み取り前に照合する。管理領域全体を失っても、公開の印が残ればライブへの切り替えは起きない。前もって起動していたライブ版 browse も、切り替え後に配信を止める。
- 公開変更の日誌を用意し、成果物を配置して検証し、完了記録を保存したあと `current` を進める。先頭の記録を置いて照合が済んだ時点で日誌を閉じる。その途中で停止しても、候補と承認が揃っていれば `recover` で続けられる。ポインターが進んだ段階で完了記録や公開先が欠ける場合は停止する。先頭を切り替える前に安全に打ち切れる候補は隔離し、直前まで使っていた読み口を保つ。
- ライブの日誌とは別に処理中の印を置く。新しいライブ完了記録には成果物の指紋と順序があり、最後の完了記録を先頭の記録と照合する。再実行では、後続の計画が変更したファイルに後続の指紋を使う。
- 完了済みの旧公開形式は、現在位置と完了記録につながる履歴を照合できる場合に読める。次の公開で新形式に移す。以前に作った未適用の初回計画は再作成と再承認が必要である。旧公開版を別のパスに移した場合は、承認時のパスが一致する環境で照合する。

## 検証範囲

先の試験と同じく、ライブは192記事・160原本、公開側は195記事を含む212ファイルの合成 wiki を使用した。電源断の模擬はプロセスの強制終了と、隔離領域でファイルの名前や内容を退避・復元する故障注入で行った。対象機器の実際のストレージ障害と復旧時間の評価は、本番有効化前の試験に残る。

| 検査 | 結果 |
| --- | --- |
| 初回の基準が変わる | 最初のロックを出たあとに確定したライブの新規ページを検出し、初回切り替えを拒否した。公開日誌と公開状態の印を作らず、ライブの変更を保持した |
| 承認が保留される | 公開直前のロック待ちでライブ差分を保留した。その初回切り替えは拒否し、保留をライブへ反映して基準を採り直すと、新版に両方のライブ更新が含まれた |
| 公開状態が欠ける | ポインター、公開の印、先頭記録、完了記録、成果物、管理領域をそれぞれ欠かせて試した。該当の読み取りと再実行が停止した。ポインターと先頭記録を同時に前版へ戻した場合も、履歴との食い違いを検出した |
| 公開中に停止する | 完全な候補を準備した段階、ポインター直後、先頭記録直後から復旧できた。完了記録か成果物を失わせると停止し、診断に使う日誌を残した。未公開の候補とステージの破損は隔離できた |
| ライブの完了と内容が食い違う | 日誌を失った部分適用、完了記録を書いた後に索引だけが戻った状態、先頭の完了記録が消えた状態で停止した。ロールバックの後片づけで中断した場合は再度の復旧で完了した |
| 従来の読み書き | 整合した旧公開形式を読み、新形式へ移せた。切り替え後とポインター欠損時に、ライブで起動済みの browse が HTTP 410 を返した。回帰試験26件が通った |

Opus の初回レビューで、保留保存と初回公開の競合、旧形式の移行途中、初回候補の隔離、ロールバックの削除順を見直した。再レビューで4件の修正を確認し、残った破損ステージの隔離も195記事の別試行で確かめた。

SemaSynth wiki は全83ファイルの SHA-256 を前後で照合し、差分は0件だった。通常の保存を公開経路につなぐ条件③と、ライブへ戻すときの書き戻しを定める条件④は本番有効化の前に残る。
