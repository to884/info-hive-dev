## 1. 結論の要約

**Atomic Notes と Evergreen Notes は、変えて採る。「1 主張 1 ページ」の全面採用は採らない**（提案）。

- 用語とエンティティのページ（今の `concept` と `entity`）は残す。
- そのうえで、条件と根拠を保ったまま再利用できる知見だけを選び、`type: "concept"`、`kind: "claim"` のページとして独立させる。題名は主張の文にする。
- 主張の既定の置き場所は、用語ページの中の `###` の節にする。独立したページに昇格させるのは、条件を満たしたものだけにする。
- 最初は `SCHEMA.md` で選べるオプトインにし、PoC で振り分けの一致を測ってから既定にするかを決める。

4 体とも、全面的な 1 主張 1 ページを最下位にし、併用の方向は相互レビューでも崩れなかった。ただし、4 体が示したどの判定規則も「モデルが変わっても同じページ割りになる」ことを示せていない。採るのは方向であり、提示された規則そのものではない。

## 2. 問いと前提

作者の問いは「記事の単位を決める手法として、Atomic Notes と Evergreen Notes を検討してほしい」である。直前の確認で、次のことが分かっていた（事実）。

- 現行の「アトミックなページ」は、「1 つのページは 1 つのことを扱う」と大きさの上限（ソフト 10,000 文字、ハード 25,000 文字）で決まっている（`SKILL.md`、`page-conventions.md`）。単位は 1 コンセプトであり、1 つの考え（主張）ではない。
- 何を独立したページにするかは「目安」で決まり、モデルの判断に任されている（`ingest-workflow.md` の手順 7）。
- 作者の wiki は source 37、concept 17、entity 1、synthesis 1 である。source のうち約 28 本は SemaSynth の作業記録で、そこから concept はほとんど育っていない。一方で `編集要求の復元世代を最終適用まで保持する` のように、題名が主張の形をした concept も自然に生まれている。

## 3. 原典の確認

C と D が原典を取得して確かめ、B の取得で一部を訂正した（事実。出典は各成果の参照の節）。

| 原則 | 原典での位置づけ | LLM が保守する wiki で保てるか |
| --- | --- | --- |
| 1 ノート 1 アイデア（atomic） | 独立して再利用できる関心事を分ける。短さそのものは目的ではない。Matuschak は、細かくしすぎるとリンク網が断片化すると書いている | 単位を「1 文」ではなく「1 つの判断」にすれば保てる |
| concept-oriented | 著者、本、出来事ではなく、概念を軸に知識を溜める | 保てる。source を入口にし、複数の source が同じ知見を更新する |
| densely linked | 関係を考えてリンクする | 保てる。リンク数のノルマは置かない |
| 題名を主張の文にする | 推奨されているが、Matuschak は用語の定義などを例外にしている。「問い」を例外とする C と D の記述は、B の取得で否定された | 主張ページだけに適用し、用語、entity、source には強いない |
| 時間をかけて育つ | プロジェクトをまたいで追記、修正する | 取り込み、query、lint を見直しの契機にすれば保てる |
| 自分のために書く、書くことで理解する | 人の思考の実践を含む | 保てない。LLM の出力から作者の理解は推定できない |
| literature note と permanent note を分ける | 資料に従う記録と、資料を越えて使う知見を区別する | 保てる。`source` と `concept` を機能で分ける |

Luhmann の一次資料で確認できたのは、固定の番号、相互参照、索引である。「1 ノート 1 アイデア」を Luhmann の直接の指示とする根拠は見つからなかった。Ahrens の該当箇所は一次資料で未確認である（要確認）。

**結論として、全面的な 1 主張 1 ページは、Evergreen Notes の必須条件ではない。**

## 4. 既存の種類との対応

| 現行 | Atomic / Evergreen での役割 | 扱い（提案） |
| --- | --- | --- |
| raw | 原資料 | 変更不可のまま |
| `source` | literature note | 要約を続ける。抽出した知見をどこへ送ったか（作成、更新、source に残す）を記録する |
| `entity` | 参照ノート | 現行どおり。属性ごとに主張ページを作らない |
| 用語の `concept` | 定義ノート、structure note（MOC） | 定義を持ち、関係する主張を束ねる入口を兼ねる |
| 主張の形の `concept` | evergreen note | `kind: "claim"` を付けて区別する |
| `concept` の `kind: "experience-pattern"` | 経験則 | `/wiki:learn` だけが作る。取り込みから作らない（D の試案はこの契約を壊していた） |
| `synthesis` | 問いへの統合ノート | 現行どおり |
| `index.md`、`indexes/` | 目録 | 昇格した主張ページだけが 1 行を得る |

欠けているのは新しいページの種類ではない。**source から知見へ昇格させる判定手順**と、**何を source に残し何を送ったかの記録**である。実行日時、テスト件数、特定コミットの受け入れのような記録は、source に残るのが正しい。

## 5. 単位の候補と採点

4 体とも次の 4 候補を、共通の基準（知識の再利用と成長 25、判定の再現性 20、規模とコスト 20、既存設計との整合 20、移行と実装の軽さ 15）で採点した。

| 候補 | 4 体の評価 |
| --- | --- |
| ① 現行のまま（1 コンセプト 1 ページ + 大きさ） | 安定性とコストを重くすると首位になる。source に溜まる偏りは解けない |
| ② 1 主張 1 ページ（全面 evergreen） | 4 体とも最下位。37 本 × 3 主張で 111 ページ増え、計 167 ページで分割の閾値 150 を超える。この試算は誰も反証していない |
| ③ 併用（用語ページ + 選別した主張ページ） | A、C、D が首位、B も同じ方向（案 E）。推す案 |
| ④ 主張をページ内の単位で持つ | 最も軽い。ページにならない主張はインデックスに載らない |

**採点の差は判断の誤差の内側にある。** 首位と次点の差は 4 体で 0.15〜0.35 点で、どの体も重みや素点を少し動かせば首位が入れ替わることを自分で示した。採点で単位は決められない。決めるのは PoC の一致率である。

## 6. 推す案

### 6.1 単位の定義

C の定義が相互レビューで残った。

> 1 つの問いに対し、条件つきの答え、説明、判断を示し、その根拠、適用範囲、反例を同じ場所で更新できる単位。

「1 文」を単位にした A と B の定義は、題名の 40 字制限のために条件を削る規則（B）や、条件を見ない同一性判定と結びつき、知識の意味を変える反例を出した。たとえば「同一環境ではバイト一致、異なる環境では論理一致」は 2 文に分けられるが、判定方法を選ぶ 1 つの判断である。

### 6.2 入れ物は 2 層

| 層 | 入れ物 | 引き方 |
| --- | --- | --- |
| 既定 | 用語ページの中の `###` の節（1 節 1 主張） | 検索だけ。`split_sections` は ATX 見出しで切るので、節がそのまま検索の 1 単位になる（事実）。`## 主張` の下の箇条書きは、何行あっても 1 セクションにしかならない（事実） |
| 昇格 | `type: "concept"`、`kind: "claim"` のページ | インデックスの 1 行と検索の両方 |

### 6.3 取り込みでの判定（C の手順を骨格にした案）

1. ソースから知見の候補を出す。候補ごとに主語、条件、述べていること、根拠の位置、事実か提案か仮説かを書く。
2. 進捗、1 回の数値、固有の対象の属性、用語の定義を除く。進捗は source に、属性は entity に、定義は用語ページに送る。
3. 同じ条件と意味を扱う既存のページや節を探し、本文まで読む。あれば更新を優先する。照合では題名の似かたより、**対象、条件、肯定か否定か、断定の強さ**を優先する。
4. 条件を保ったまま、別の資料や将来の問いに再利用できるかを判断する。「いつか役立ちそう」だけでは昇格させない。
5. 根拠と適用範囲をソースの範囲内で書けるかを確かめる。書けなければ source に残す。
6. 行き先（`create`、`update`、`source_only`）と理由を source に記録する。

**手順 4 は意味判断のままで、機械化できていない**（要確認）。SemaSynth の偏りを解けるかは、この判断 1 つにかかっている。A の昇格条件 P1〜P5、B の Q2、D の昇格条件 3 も同じ穴を持っていた。

### 6.4 題名とスラッグ

- 用語、entity、source は名詞の題名のまま。主張ページだけ「何が、どんな条件で、どうなる（どう扱う）」の文にする。
- 提案や仮説を、題名で確定事実に変えない。条件を削って短くしない。60 文字程度を見直しの目安にするが、上限にはしない。
- 文章を推敲しただけで、スラッグを変えない。
- 作者の wiki から作った例（C の成果。根拠は raw の行）:
  - `同一環境と異なる環境では再現性の判定を分ける`
  - `再生成の同等性と配布物の改変検出を区別する`
  - `検証対象と独立した期待値で会計データを検証する`
  - `ハッシュによる改変検出は基準manifestの信頼を前提とする`
  - `実行環境の識別には日時と絶対パスを含めない`

### 6.5 frontmatter とグラフ

- **区別は `kind: "claim"` で表す。** `derive_node_type` は `(type, kind)` の組を `type` だけより先に照合する（事実。`wiki_graph_extract.py` 245〜258 行）。オントロジーの `claim` に `maps_from: {type: concept, kind: claim}` を 1 項目足せば、スクリプトを変えずに `claim` ノードができる。C の `note_role` はどのスクリプトも読まないので採らない。
- **frontmatter は平坦なキーだけにする。** `wiki_text.py` のパーサーは入れ子を読まず空の配列にする（B、C、D が同じ入力で確認）。根拠を `evidence[].quote` のような入れ子で持つ案は使えない。
- 根拠の照合先は source の本文に限る。B の作例では、`evidence` の引用が raw にも source にもなく、wiki の言い換えにだけ出ていた。

## 7. 相互レビューで崩れた主張

いずれも議論ではなく、測定や実装への入力で示された。

1. **「主語、述語、肯定か否定か」だけの同一性判定は、適用条件を落とす**（C と D が A と B に）。D は、A の PoC の照合（bigram の Jaccard 0.5）で、条件だけが違う 2 文が 0.72 で一致と数えられることを示した。誤った統合は「2 本以上の source」という昇格条件を満たしてしまう。
2. **同じプロジェクトの複数の記録は、独立した裏づけではない**（D）。B の例は、条件の違う 2 件（C ドライブの一時領域とリポジトリ内）を 1 文にまとめ、2 ソースの裏づけと数えていた。A と B はこれが自分の規則に当たると認めた。
3. **モデルが概念名を発明する。** A の試案のハブ `合成データの検証` という文字列は、source に 0 回しか出ない（B、C、D が独立に確認）。
4. **B の「滞留」lint（本文 1,500 文字以上）は、対象にしたい SemaSynth の 28 本のうち 26 本を除外する**（D と C が実測）。

## 8. 試し方（PoC）

D の設計が最も残った。

- **2 つの試験を分ける。** 同じ wiki に同じ入力を再処理して重複や改名が起きないか（冪等性）と、同じ初期状態から別のモデル、別の回で同じ配置に至るか（独立一致）は別物である。保存した判定表を読み直して 1 つ目に合格しても、2 つ目の合格にはならない。
- 作者の wiki の固定スナップショットと、ソース 3 本（オントロジー連載 1 回分と SemaSynth の記録を含む）を使う。実際の wiki には書かない。
- 現行、併用、ページ内の主張の 3 案を、2 モデル × 3 回 × 3 ソースで実行し、配置の計画を出す（54 件）。候補の対応づけは人が行う。
- 指標は、知見の抽出の precision と recall、配置先の一致率、同じページに置くかの判定の F1、重複率、再処理での増分、根拠と条件の保持率、コスト（トークン、読んだページ数、増えたページ数）。
- **出典への忠実さと条件の保持は、加重点で相殺させない必須条件にする**（C と D）。
- 全件を `source_only` にして一致率を稼ぐ出力が合格しないよう、SemaSynth から出た concept の本数を、現行手順の対照と比べる（B と C）。
- 合格の目安（知見の recall 90%、配置先の一致率 85%、F1 0.90、再処理での重複 0）は提案値で、達成の見込みは分からない（要確認）。54 件は人手の負担が大きく、B は 4 回、C は 18 回を提案した。
- **規模は決定済み**（作者、2026年11月9日）。固定の 3 資料、2 モデル、3 回、現行と変更案の 2 方式で 36 件とする（[wiki-article-methodology-adoption-2026-11-08.md](wiki-article-methodology-adoption-2026-11-08.md) の第 8 節）。SemaSynth の記録は SemaSynth のプロジェクトの wiki に移したので、PoC の資料もそちらの source から取る。

## 9. 移行

**移行は、索引の分類を直すところから始める**（D）。作者の `index.md` では、「シンセシス」の見出しの下に 17 項目あり、そのうち 16 本は `type: source` のページである（事実。A の 15 本は誤り）。今の lint はこれを見つけられない（B が lint を走らせて 0 件を確認）。

そのあとは段階的に進める。既存の 56 ページを一括で分割しない。空白を含む既存のスラッグ 3 件の改名も、主張の単位の導入と抱き合わせない（D）。

## 10. 残る論点と作者の判断が要る点

| 論点 | 内容 |
| --- | --- |
| オプトインか既定か | オプトインなら既存の利用者に影響がなく PoC を待てる。ただし作者自身の wiki でも `SCHEMA.md` を書き換える手間がかかる |
| 主張ページの `status` | A は `experience-pattern` と同じ 3 値、B は `disputed` を足した 4 値、D は流用しない立場。流用しないと、グラフを使わない wiki で古い主張を query から外す手段がない |
| 根拠の持ち方 | 平坦なキー（`claim`、`scope`）か、本文の `## 根拠` 節か。raw の行番号を根拠の位置にする案は、rag 連携の PDF では `raw:` が絶対パスで、行を定義できない（A） |
| グラフの移行 | `maps_from` を足すと、既存の `concept:x` が `claim:x` に変わり、他のページの明示エッジの目的語は自動では直らない。`depends_on` は `claim` を受け付けない。作者の wiki に該当があるかは未確認 |
| wiki の対象範囲 | SemaSynth の段階の完了やテスト件数は、記事の単位では解けず、`log` プラグイン（ADR-0006）の対象かもしれない。どこまでを wiki で育てるかを `SCHEMA.md` に書く必要がある（C、D） |
| 評価基準 | 「既存設計との整合」と「移行の軽さ」で重みが 35 あり、現行が構造的に有利になる（B、D）。「判定の再現性」は採点ではなく PoC の一致率で置き換えるべき（A、B） |
