## 1. 結論の要約（提案）

1. **ページは、ファイル名のほかにも、いくつもの名前で wiki の中の位置を持つ。** スラッグ（ファイル名の幹）、パス、グラフの `node_id` と `aliases`、エッジの ID、図のファイル名、raw のパスである。写す機能の中心は、ファイルの複製ではなく、**この名前ごとに、写す先で同じ名前がないかを確かめ、写す元を指す参照を 1 件ずつ「一緒に写す」か「切る」かに決め、その結果の全体を、写す前に 1 回の承認で見せること**である（第 3 節）。
2. **名前が同じでも、同じものとはみなさない。** 写す先に同じスラッグのページがあっても、写す元の参照をそのページに結び付けるのは、利用者が参照ごとに選んだときだけにする。既定は「切る」である。
3. **2 つの向きは対称ではない。** プロジェクトからユーザースコープへ写すと、プロジェクトの資料がどのプロジェクトからも読める場所に移る。ユーザースコープからプロジェクトへ写すと、個人のメモとその原本が Git に入り、チームに共有されうる。ページの差分を見せても、raw の中身までは見せきれないので、**raw を写すのは、利用者がファイルごとに選んだときだけ**にする（第 4 節）。
4. **推奨は、写す処理（決まった処理）と、任意の書き直し（モデル）を、同じ用意の中で行い、最後の中身を 1 回で承認する形である（第 5 節の案 B）。** 書き直しを写したあとの別の段にすると、書き直す前の中身が写す先に先に入る。書き直しは、作業用のフォルダーに用意した写しに対して行い、承認する差分は書き直したあとのものにする。ページは書く段（ADR-0023）の `new`、索引とログは `ops` で書き、写す先のページを上書きしない。
5. **写さずに済む使い方もある。** 「プロジェクトの作業中にユーザースコープの知識も引きたい」だけなら、`/wiki:query` で 2 つの wiki を明示して検索する（案 E）ほうが、重複も食い違いも生まない。写す機能とは独立に決められる。
6. **初めの範囲は狭くする。** `graph:` の欄は写さず（写す先でグラフを抽出し直す）、図のあるページは写さない（書く段の `new` は `assets/` に書けない）。どちらも、写す先の名前を壊す経路と、書く段の外の書き込みを増やさないためである（第 7 節）。

## 2. 問題と前提

### 2.1 依頼

ユーザースコープの wiki の記事をプロジェクトの wiki に写す機能と、その逆の機能を検討する（2026年11月15日の依頼）。

### 2.2 今の仕組み（確定）

| 項目 | 今の仕組み | 写す機能への影響 |
| --- | --- | --- |
| wiki の根の決め方 | 各コマンドは、明示したパス、プロジェクトの指示、グローバルな指示、作業領域の設定の `dirs.wiki`、現在のプロジェクトの `wiki/` の順に、**1 つの** `<WIKI_ROOT>` を探す。`SCHEMA.md` がなければ止まる（ADR-0019） | 写す機能は根を **2 つ** 決める。それぞれに同じ規則と `SCHEMA.md` の確かめを当てる |
| スコープの決め方 | wiki が指示や設定で何として登録されているかで決め、場所から推し量らない。手がかりがないか食い違えば決めない（browse のスコープの設計） | 写す先は「`user` の wiki」「`project` の wiki」と指して選ぶので、この規則をそのまま使える。決まらなければ止める |
| リンクの解決 | wikilink は、パスのない形はスラッグで、パスつきの形はそのパスがあるときだけ解決する。大文字と小文字を区別する。`title` や `aliases` では解決せず、ページの中身も見ない（`wiki_pages.resolve_link()`）。共通のパーサーは、コードのブロック（`fence`、`code_block`）の中の `[[...]]` を数えない（コードで確かめた）。インラインのコードの中も数えないことは、レビューの報告による | 写す先に同じスラッグの別のページがあると、参照は黙ってそのページに結び付く |
| `raw:` の解決 | 絶対パスはそのまま、相対パスは wiki の根、wiki の親、ページのディレクトリのどれかを基準に見つかればよい。ファイルでもディレクトリでもよい（`wiki_lint.missing_raw()`）。別の wiki の中のファイルを絶対パスで指すことも拒まない | 相対パスは、写した先では別の場所を指すか、何も指さない。写す元の raw が写す先の wiki の中にあることもありうる |
| `sources:` の lint | 書かれた値が解決するかだけを見る。`sources:` を書かないページは挙げない（`wiki_lint.py` の 570 行付近） | 参照を切って `sources:` が空になっても、lint は何も言わない。根拠のないページになったことは、写す処理が自分で知らせる |
| グラフ | `node_id` が同じページは 1 つのノードにまとまり、目的語に同じ ID のページが 2 つあればエッジを作らない（`wiki_graph_extract.build_nodes()`、729 行付近。コードで確かめた）。エッジの ID にはページのパスが入る（`edge_id()`。wiki の根を含まない相対パスで、別の wiki に同じパスで置くと同じ ID になることは、レビューの報告による）。関係には `raw_ref`（`raw/x.md#L42`）も書ける。MCP の `graph` は `graph.sqlite` を読み取り専用で開き、作り直さない | `node_id` が同じページを写すと、写す先の既存の関係が消えうる。グラフは写したあとに抽出し直さないと、写したページが現れない |
| 検索の索引 | MCP の `query` は、呼ばれるたびに `index.refresh()` でファイルの集まりの変化を取り込む | 写したページは次の検索で現れる。何もしなくてよい |
| 書き込み | 今はモデルが Edit と Write で書く。ADR-0023 で `wiki_apply.py` の `new`、`edit`、`ops` に移すと決めたが、まだ実装していない。`new` と `edit` のパスは `.md` で終わり、最初の要素が `raw`、`graph`、`assets` でないものに限る（設計書の 3 節）。書く段は raw を書かない | ページと索引とログは書く段で書ける。図と raw は書く段の外になる |
| ロック | 書く段のロックは wiki ごと（`.wiki-cache/apply/apply.lock`） | 写す先の wiki のロックを取る。写す元は読むだけだが、写す元が raw として引くファイルを、写す先への書き込みが変えないことは別に確かめる（第 6.2 節の手順 2） |
| wiki ごとの違い | `SCHEMA.md` のページの種類、タグの体系、命名の言語、分割した索引（`indexes/`）、ADR-0008 の番号つきの構成（`W1_Raw` など） | 写す元で通るページが、写す先の lint で通らないことがある |

### 2.3 想定する使い方

| 向き | 例 |
| --- | --- |
| プロジェクト → ユーザー | プロジェクトの作業で得た、ほかのプロジェクトでも役に立つ教訓（Windows の Python の改行、Git Bash のパス変換など）を、どのプロジェクトからも読める wiki に残す |
| ユーザー → プロジェクト | ユーザースコープに貯めた知識のうち、そのプロジェクトに要るものを、チームが Git で共有するプロジェクトの wiki に入れる |

ユーザーのグローバルな指示は、「そのプロジェクトだけに当てはまる記録（進捗、受け入れ、プロジェクト固有の設計判断）はプロジェクトの wiki に残す」と書いている。プロジェクト → ユーザーの向きは、この区別をあとから正す操作でもある。

## 3. 写すときに確かめる名前と参照（確定）

### 3.1 名前（写す先で同じものがないかを確かめる）

| 名前 | どこで決まるか | 写す先に同じものがあると起きること |
| --- | --- | --- |
| スラッグ | ファイル名の幹。大文字と小文字だけの違い、NFC の違いも同じとみなす（`case_only_duplicates`、`duplicate_slugs`） | 写す先の wiki の中の、そのスラッグへの既存の参照が曖昧になる |
| パス | wiki の中の相対パス | 書く段の `new` が競合にする（上書きはしない） |
| グラフのノードの ID | `graph.node_id`。なければ `type` と `kind` とスラッグから決まる既定の ID。`graph.aliases` も同じ名前の空間にある | 2 つのページが 1 つのノードにまとまり、そのノードを目的語にする写す先の既存の関係が、曖昧になって消える（レビューで再現した） |
| エッジの ID | ページの相対パスと関係の中身から決まる | 写す先でそのエッジの ID を `contradicts`、`supersedes` で指す関係が、別のエッジを指しうる |
| 図のファイル名 | `assets/<スラッグ>-NN.svg` | 初めの範囲では写さない（第 7 節） |
| raw のパス | 写す先の raw のルートの中のパス | 同じ名前で中身が違えば止める |

**名前が同じでも、同じものとはみなさない。** 写す先の同じスラッグのページが、写す元の参照の指すものと同じかは、名前からも題名からも決められない（同じ「認証基盤」でも、別の会社の別のシステムを書いたページでありうる）。

### 3.2 参照（写す元のページから外を指すもの）

| 参照 | 書かれる場所 | 写す先で起きること | 扱いの候補 |
| --- | --- | --- | --- |
| 本文の wikilink | 本文の `[[x]]`、`[[x\|表示]]`、`[[dir/x]]`（コードの中は除く） | 写す先に `x` がなければリンク切れ。別のページの `x` があれば、**黙ってそのページに結び付く** | 一緒に写す、切る（ただの文字にする）、写す先の同じ名前のページを指すと利用者が参照ごとに選ぶ |
| frontmatter の参照 | `sources:`、`entities:`、`concepts:` | 同上。切って空になっても lint は挙げない | 同上。切った参照は出所の記録に残す |
| 本文のふつうのリンク | `[文](../concepts/x.md)` のような相対パスのリンク | 写す先に同じパスのファイルがなければ切れ、あれば別のページを指しうる。このリポジトリの wiki には実例がない（2026年11月15日に検索した） | wikilink と同じに扱う |
| raw の原本 | source ページの `raw:` | 相対パスは別の場所を指すか、何も指さない | source ページと一体で扱う（第 3.3 節） |
| グラフ | `graph:` の欄の全体（`node_id`、`aliases`、`relationships` の `object`、`source`、`evidence`、`raw_ref`、`contradicts`、`supersedes`） | 第 3.1 節の名前の衝突に加え、`raw_ref` は写す元の raw を指したまま残り、`supersedes` はエッジの ID が変われば切れる | 初めの範囲では写さない（第 7 節） |
| 図 | 本文の `../assets/<スラッグ>-NN.svg` | ファイルがなければ `missing_assets` | 初めの範囲では、図のあるページを写さない |
| タグ | `tags:` | 写す先のタグの体系になければ、`--allowed-tags` の lint が挙げる | 写す先の体系に足す（`SCHEMA.md` の `edit`）、そのタグを外す、そのまま |
| ページの種類 | `type:` | 写す先の `SCHEMA.md` にない種類なら、置くディレクトリも索引の節もない | 止める（写す先のスキーマを先に直す） |
| 索引とログ | `index.md` か `indexes/<種類>.md`、`log.md` | 写す先に項目がなければ、lint とクエリから見えにくい | 写す先に `index-add` と `log-entry` を足す。写す元の項目とログは写さない |
| 経験とパターン | `/wiki:learn` の raw の JSON、パターンのページ、`.evolution/` | 評価の履歴は写す元の wiki にある | 初めの範囲に入れない |

### 3.3 写す範囲の決め方

「一緒に写す」を続けると、閉包が大きくなる。そこで、範囲を次のように決める。

- 利用者が選んだページを **選んだページ** とする。選んだページの参照（第 3.2 節）のうち、利用者が「一緒に写す」としたページを **依存ページ** とする。
- 依存ページ自身の参照は、すべて切る。依存ページの依存ページは作らない。
- source ページと、その `raw:` の原本は一体である。source ページを写すときは、原本を写すか、source ページを写さないかのどちらかにする。原本を写さずに source ページだけを写すことはしない（`raw:` が何も指さないページになるため）。
- 原本がディレクトリなら、写すのは利用者がファイルごとに選んだものだけである。選ばれなかったファイルは、写したディレクトリに入らない。

**このリポジトリの wiki での例。** コンセプト「git-bashのパス変換」は、`sources:` で 2 つの source ページ（wiki 0.11.1 と 0.12.1 のリリースの記録）を指す。source ページの `raw:` は `docs/agent-runs/...` で、wiki の親（リポジトリの根）を基準にしたリポジトリの中のディレクトリである。ユーザースコープに出典ごと写すと、リリースの記録 2 件と、エージェントの作業記録が入る。出典を切ると、根拠を写す先でたどれないページになる。

## 4. 向きによる違い（提案）

| 観点 | プロジェクト → ユーザー | ユーザー → プロジェクト |
| --- | --- | --- |
| 中身が届く先 | 自分だけが読む、Git に入らない場所（ふつう） | Git に入り、チームと公開先に届きうる場所 |
| 漏えいの危うさ | 顧客名、社内の事情、未公開の設計がプロジェクトの外に出る。ほかのプロジェクトの作業で、エージェントがそれを引用しうる | 個人のメモ、ほかのプロジェクトから昇格した記述、ホームの下の絶対パス（`C:/Users/<名前>/...`）がリポジトリに入る |
| ページの差分で見せきれないもの | raw の中身（顧客との会話、作業記録の全体） | 同左。要約が一般的な記述でも、原本に非公開の情報がありうる |
| raw の既定 | source ページを写すときだけ、ファイルごとに選んで写す | 写さない（source ページも写さず、コンセプトとシンセシスを出典を切って写す）。写すなら、ファイルごとに選び、Git に入ることを確かめる |
| 写す前に見せること | 写すページの全文の差分、写す raw のファイルの一覧と大きさと SHA-256、プロジェクトに固有の記述が残ることの注意 | 同左に加え、絶対パスの有無と、Git に入る場所であることの注意 |

どちらの向きも、利用者が明示して始めたときだけ写す。エージェントの指示（グローバルな指示の「長く残す価値のある知見を残す」など）から、写す操作を自分で始めることはしない。

**raw の中身は、機械では確かめきれない。** 写す処理が保証するのは、利用者が選んだファイルが、選んだときのバイト列のまま写ることだけである（第 6.2 節の手順 7）。選んだファイルの中に非公開の情報がないかは、利用者が読んで決める（第 9 節の保証しないこと）。

## 5. 選択肢

| 案 | 中身 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. そのまま写す | 選んだページのファイルを写す先に複製し、索引とログに足す。参照は直さない | 作るのが最も簡単 | 第 3 節のリンク切れ、別のページへの黙った結び付き、グラフのノードの合流がそのまま起きる |
| **B. 名前と参照を確かめて写す** | 第 3 節の名前を写す先と照らし、参照ごとに「一緒に写す」「切る」を決めて写す。任意で、用意した写しをモデルが書き直し、その結果を 1 回で承認する | 写したあとに参照が切れず、写す先の既存の名前を壊さない。何が動くかを写す前に見せられる | 確かめと選ぶ手間がかかる。書き直しを使えば、その部分は決まった処理でない |
| C. raw を写して取り込み直す | source ページの raw だけを写す先の raw のルートに写し、写す先で `/wiki:ingest` を流す | 写す先のスキーマ、タグ、関連ページに合ったページができる | 取り込みの費用がかかる。raw を持たないページ（コンセプト、シンセシス）は写せない。raw そのものがプロジェクトの記録なら、取り込み直しても記録の要約になる |
| D. モデルが一般化して書き直す | 写す元のページを読み、写す先のための新しいページをモデルが書く | プロジェクトに固有の記述を外せる | 毎回の結果が違う。出典を写さなければ、写す先から根拠をたどれない |
| E. 写さずに 2 つの wiki を引く | `/wiki:query` で、ユーザースコープとプロジェクトの wiki を明示して両方を検索し、回答でどちらの wiki のページかを分けて示す | 重複と食い違いが起きない。書き込みがない | 「プロジェクトの wiki に知識を入れて Git で共有したい」には答えない。今の `query.md` の禁止（黙って混ぜない）との関係を整理し直す必要がある |
| F. 参照だけを置く | 写す先に、写す元のページを指す短いページを置く | 中身が重ならない | 写す元を読めない人と PC では何も読めない。ユーザー → プロジェクトでは役に立たない |

### 5.1 評価（提案）

| 軸 | A | B（書き直しなし） | B（書き直しあり） | C | D | E | F |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 写したあとに参照が切れない | × | ○ | ○ | ○ | △（出典を切る） | ―（写さない） | × |
| 写す先の既存の名前を壊さない | × | ○ | ○ | ○ | ○ | ― | △ |
| 決まった処理で、結果を予め見せられる | ○ | ○ | △（承認する差分は見せるが、中身は毎回違う） | △ | × | ○ | ○ |
| 写す先の規約（スキーマ、タグ）に合う | × | △（合わない点を一覧で見せる） | △ | ○ | ○ | ― | △ |
| プロジェクトに固有の記述を外せる | × | × | △（コンセプトとシンセシスだけ。source ページと raw は外せない） | × | △（同左） | ― | ― |
| 書く段（ADR-0023）との整合 | `new` と `ops` | `new` と `ops` | `new` と `ops` | 取り込みと同じ | `new` | 書かない | `new` と `ops` |
| ほかの人と PC で読める | ○ | ○ | ○ | ○ | ○ | × | × |
| 作る量 | 小 | 中 | 中 | 小 | 小 | 中 | 小 |

どの案も、すべての軸を満たさない。B は、参照と名前を壊さないことを決まった処理で保証できる唯一の案で、書き直しを足すと「決まった処理」を一部あきらめる代わりに、コンセプトとシンセシスからプロジェクトに固有の記述を外せる。source ページと raw の固有の記述は、どの案でも外せない。外したいなら、写さない（ユーザー → プロジェクトの既定、第 4 節）。

E は、写す必要がない使い方では B より安全である。どちらを先に作るかは作者が決める（第 8 節の 1）。

## 6. 推奨する形（提案）

### 6.1 コマンド

```
/wiki:copy <スラッグ>... --to user|project
```

- 写す元は、今の規則で決まる wiki（第 2.2 節）にする。`--to` で写す先のスコープを決め、写す先の根は browse のスコープの設計と同じ手がかりで決める。手がかりが 1 つも当てはまらないか、食い違えば止める。写す元と写す先のスコープが同じなら止める。
- 2 つの根が同じディレクトリか、一方が他方の中にある（入れ子の wiki）か、別名で重なるなら止める。この確かめは書く段の `wiki_fsguard` の検査を使う。

### 6.2 流れ

1. **両方の根を決め、`SCHEMA.md` を確かめる。** どちらかがなければ、何も書かずに止まり、その wiki の初期化を提案する。
2. **計画を作る（読むだけ）。** `wiki_copy.py plan --from <W1> --to <W2> --raw-to <R2> --slug ... --json` が、選んだページと、依存ページの候補（第 3.3 節）を集め、次を返す。
   - 第 3.1 節のすべての名前について、写す先で同じものがあるか。グラフの名前は、`graph:` を外した写し（手順 4 と同じ規則で作ったもの）について確かめる。`graph:` を外しても、既定のノードの ID（種類とスラッグから決まる）が、写す先のページの `node_id` か `aliases` と同じになりうるからである。写す先の wiki と写しを合わせて抽出（`wiki_graph_extract` の関数）し、写す先の既存のノードとエッジがすべて残ることを比べて決める。
   - 参照ごとの状態：写す先にある、写す先にない、写す先に同じ名前の別のページがある。
   - 写す raw の候補のファイルごとの写す先のパス、大きさ、SHA-256。相対パスの `raw:` が、wiki の根、wiki の親、ページのディレクトリのうち 2 つ以上の基準で見つかるときは、どれが原本か決められないので、そのページを写せないものにする（lint は 1 つ見つかれば通すが、写す処理は 1 つに決める必要がある）。
   - **写す raw の原本の守り。** 原本（写す元のパスで解決したもの）が、写す元の wiki の木、写す先の wiki の木、写す先の管理領域（`.wiki-cache`、`data_dir()`）のどれかの中にあれば、そのページを写せないものにする。写す先への書き込み（ページ、索引、ログ）が、写す元の原本を書き換えないためである。書く段の raw の守り（ADR-0023）は写す先の wiki のページから raw を集めるので、写す元のページだけが引く原本は、ここで守る。
   - 写す先のスキーマにない種類、タグの体系にないタグ。
   - 写せないページ：図がある、写す先の種類がない、raw の原本が上の守りに当たる、グラフのノードが合流する。
   - 向きごとの注意（第 4 節）。
3. **利用者が決める。** 参照ごとに「一緒に写す」「切る」「写す先の同じ名前のページを指す」を決める。既定は「切る」である。「写す先の同じ名前のページを指す」を選ぶときは、写す元と写す先のページの題名と最初の段落を並べて見せる。名前が衝突した選んだページは、写さない（既定）か、別のスラッグにする。別のスラッグにしたときは、同じ計画で写すページの中の参照も書き換える。写す raw をファイルごとに選ぶ。写す先のページを上書きしたり統合したりはしない。
4. **写しを用意する（決まった処理）。** 作業用のフォルダーに、書き換えたページを置く。
   - 「切る」とした本文の wikilink は、`[[x|表示]]` を `表示` に、`[[x]]` を `x` にする。位置は共通のパーサーのトークンで決め、コードの中は書き換えない。frontmatter の参照の項目は外す。
   - `raw:` を、写す先の raw のパスに、写す先の wiki の既存のページと同じ基準で書き換える。
   - `graph:` の欄を外す。外したことは出所の記録（6.3）に残す。
   - 参照を切って `sources:` が空になった source 以外のページは、計画に「根拠を写す先でたどれない」と載せる（lint は挙げないため）。
5. **書き直す（任意。モデル）。** 利用者が求めたときだけ、モデルが作業用のフォルダーの写しを直し、プロジェクトに固有の記述を外す。書き直したあと、手順 2 の名前の確かめ（グラフの名前を含む）と、手順 4 の確かめ（参照、`graph:` がないこと）を、書き直した写しにもう一度流す。source ページは書き直さない（1 つの資料の要約という役割を保てないため）。
6. **差分を見せて承認を受ける。** 書く段の `diff` で、写す先に置くページの全体と、索引とログの操作を見せる。写す raw のファイルの一覧（パス、大きさ、SHA-256）を、同じ承認に含める。計画のハッシュに raw の一覧を入れる（要確認：書く段の計画の形に、書く段の外の入力の一覧を入れる欄を足すか、`wiki_copy` の計画を別に持ってハッシュでつなぐか）。
7. **raw を写す。** 写す先の raw のルートに、重ねて書かない形で写す。写す前に、原本のバイト列の SHA-256 が承認した値と同じことを確かめ、違えば何も写さずに止める。写す先に同じ名前で同じ SHA-256 のファイルがあれば、それを使う。違えば止める。raw の書き手と同じ `raw_root_problem()` の検査を通す。
8. **ページ、索引、ログを当てる。** 書く段の `apply` で、ページを `new`、索引を `index-add`、ログを `log-entry`（操作名 `copy`）で書く。
9. **写す先でグラフを抽出し直し、lint を流す。** 写す先にグラフ層があれば、`wiki_graph_extract` を流す（グラフの手順は、ページを足したら必ず抽出すると決めている）。lint とグラフの lint の結果を報告する。

raw を先に写し、ページを後に書く。ページを書けずに止まっても、残るのは使われない raw だけで、ページが無い raw を指すことは起きない。残った raw は、もう一度写すときに同じ SHA-256 として使われる。

### 6.3 出所の残し方

| 残し方 | 中身 | 長所 | 短所 |
| --- | --- | --- | --- |
| ログだけ | 写す先の `log.md` に `## [日付] copy \| <題名>` と、サブ行に写す元のスコープ、スラッグ、SHA-256、切った参照、外した `graph:` を書く | frontmatter のキーを増やさない | ページを見ただけでは写したものと分からない。食い違いを機械で探しにくい |
| frontmatter とログ | ログに加えて、ページに `copied_from: "<スコープ>:<スラッグ>"`、`copied_sha256: "<写す元のファイルの SHA-256>"`、`copied: YYYY-MM-DD` を書く | 写す元と比べて、食い違いを機械で探せる（将来の `lint` か `copy --check`） | 新しい frontmatter のキーになる。AGENTS.md の方針 B により、日本語の別名、`SCHEMA.md` の「日本語の別名」、lint の既知のキー、`/wiki:upgrade` の案内を直す必要がある |

`copied_from` のスコープの値には、パスを書かない。ほかの PC と Git で意味を持たず、ホームの下のパスは利用者の名前を含むからである。プロジェクトを見分けたいときは、作業領域の設定の `id`（`kind: project` で必須）を使い、`project:<id>:<スラッグ>` とする。設定がなければ `project:<スラッグ>` とする。

ログの操作名に `copy` を足すと、ログの操作の一覧（`log.md` のテンプレート）と、ログを読む手順（グラフの抽出が古いかを `ingest` の行で見るなど）の両方を直す必要がある。第 6.2 節の手順 9 で抽出を必ず流すので、写す処理の側は古さの判定に頼らない。

### 6.4 写したあとの食い違い

写した 2 つのページは、それぞれの wiki で別々に直されていく。初めの範囲では、同期しない。frontmatter に出所を残す形を採ったときだけ、写す元の今の SHA-256 と `copied_sha256` を比べて「写す元が直された」と知らせる機能を、あとで足せる。写す元の直しを写す先に当てるには、書く段の `edit` で差分を見せることになる（3 方向の当て方はしない）。

## 7. 範囲に入れないこと（提案）

| 入れないこと | 理由 |
| --- | --- |
| `graph:` の欄を写すこと | `node_id`、`aliases`、エッジの ID、`raw_ref`、`supersedes` の書き換えの規則がそれぞれ要り、どれかを誤ると写す先の既存の関係を黙って消す。写す先でグラフを抽出し直し、型付きの関係が要るなら写す先で書き足す |
| 図のあるページ | 書く段の `new` は `assets/` に書けない。書く段の外で書くと、承認と日誌に入らない書き込みが増える。書く段に図の種類を足すかは、書く段の設計の見直しとして別に決める |
| 移す（写して元を消す） | 書く段にページの削除の種類がない（ADR-0023） |
| 写す先のページの上書きと統合 | 上書きは写す先の変更を黙って消しうる。統合はモデルの書き直しで、決まった処理ではない |
| 依存ページの依存ページ | 閉包が wiki の大半になりうる（第 3.3 節） |
| 経験、パターン、`.evolution/` | 評価の履歴が写す元の wiki に結び付いている |
| 自動の同期 | 第 6.4 節。食い違いの通知だけを、あとで検討する |
| rag の索引と PDF の登録 | rag の原本は絶対パスで指し、写さない（ADR-0013）。写す先の wiki で rag を使うなら、写す先で `register_pdf` を呼ぶ。絶対パスの `raw:` を持つ source ページは、ユーザー → プロジェクトでは写せないものにする |
| 複数の PC の間で写すこと | 書く段が範囲に入れないことと同じ |

## 8. 作者が決めること

1. **進めるか、どれから作るか。** 写す機能（B）を作るか。写さずに 2 つの wiki を引く機能（E）を先に検討するか。
2. **時期。** 書く段の段 2（`wiki_apply.py` とセッションの取り込み）のあとに作るか（提案）。書く段の前に Write で作り、移っていない書き手として書く段の設計の 10 節の表に加えるか。
3. **コマンドの名前。** `/wiki:copy` か、向きを名前にした 2 つのコマンド（`/wiki:promote` と `/wiki:import` など）か。
4. **出所の残し方。** ログだけか、frontmatter にもキーを足すか（第 6.3 節）。足すなら、キーの名前と日本語の別名。
5. **source ページと raw。** プロジェクト → ユーザーで source ページを写す既定を「raw をファイルごとに選んで写す」にするか、「source ページは写さず、出典を切る」にするか。raw がリポジトリの中のディレクトリ（`docs/agent-runs/...`）のときの写す先の名前。
6. **書き直し（第 6.2 節の手順 5）を初めの範囲に入れるか。**
7. **名前が同じページを同じものとみなす条件。** 本書は「利用者が参照ごとに選んだときだけ」とした。出所の記録（`copied_from`）が一致するときに自動で同じとみなすかは、出所を frontmatter に残すと決めたときに決める。
8. **raw の承認の結び付け方。** 写す raw の一覧を、書く段の計画のハッシュに入れるか、別の計画にしてハッシュでつなぐか（第 6.2 節の手順 6）。
9. **図とグラフを、あとで範囲に入れるか。** 入れるなら、書く段に図の種類を足すことと、グラフの名前の書き換えの規則を、別の設計にする。

## 9. 保証しないこと（提案）

1. **raw の中身。** 選んだファイルを選んだときのバイト列のまま写すことは確かめるが、そのファイルに非公開の情報がないかは確かめない。
2. **名前を同じものとみなした参照の意味。** 利用者が「写す先の同じ名前のページを指す」を選んだ参照が、同じものを指しているかは、機械では確かめない。
3. **写す元を読む間の書き込み。** 写す元のロックは取らない。計画を作る間に写す元が直されると、計画は直す前か後のどちらかの中身を使う。承認した差分は、計画が読んだ中身から作るので、承認と写す中身は食い違わない。
4. **書く段に加わらない書き手。** 写す先に、書く段に加わらない書き手が同時に書くときの限界は、書く段の「保証しないこと」の 2 と同じである。
5. **書く段の保証しないことの全体。** 写す先への書き込みは書く段を通るので、書く段の「保証しないこと」をそのまま引き継ぐ。

## 11. まだ確かめていないこと（要確認）

- 写す raw の一覧を承認に結び付ける形（第 8 節の 8）。
- 写す先が ADR-0008 の番号つきの構成（`W1_Raw` など）か、古い構成（raw が wiki の中）のときの raw の写す先。ADR-0023 は、古い構成を書く段の前に移すとしている。
- グラフの名前の比べ方（写す先と写すページを合わせて抽出し、既存のエッジがすべて残ることを確かめる）が、写す先の wiki の大きさで実用の時間に収まるか。
