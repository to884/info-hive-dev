# RAG PoC の追加検証

2026 年 11 月 4 日。追加検証を完了し、確定した結果の照合を [verification-summary.json](verification-summary.json) に保存した。
OS の電源断と再起動は行わず、macOS は利用者の指定により対象から外した。

全量のテキスト層 761,915 チャンクに対し、世代の絞り込み索引を加えた条件では、CPU の実 MCP 検索の p95 がリランカーなしで約 679 ms、tiny で約 954 ms だった。
xsmall は約 1,397 ms で、1 秒未満の目標を満たさなかった。
全量の OCR と ANN の自動更新を含む取り込み E2E は未検証であり、OCR の読み順と回答可否の判定にも課題が残る。

## 検索評価

利用者は質問 60 問の文面修正 13 件と正解ページ候補の追加 11 件を含む修正案を全件確認し、採用を承認した。
承認の文言とレビューした CSV のハッシュは [human-review.json](human-review.json) に保存した。
CSV が別のアプリケーションで開かれていたため、CSV 自体は上書きせず、承認済みの質問を別の JSON に保存した。
この承認は提示した質問と根拠候補を対象とし、全資料の全ページについて関連性を網羅的に判定したものではない。

評価用の索引には、実 PDF 11 冊の全 2,895 ページと固定評価用の wiki 27 文書から、自動分割した 8,275 チャンクを投入した。
正解の位置に合わせた追加チャンクは作っていない。
PDF の本文は既存のテキスト層から抽出したもので、OCR の再実行結果は加えていない。
この索引の投入は、製品 Engine の検索形式へ抽出済み本文を入れたものであり、11 冊の PDF 取り込み E2E とは別の試験である。

[natural-mcp-results.json](natural-mcp-results.json) は、製品の実 MCP に 119 問を渡した結果である。
正例は固定 wiki の 47 問と承認済みの PDF 60 問、負例は資料に存在しない識別子の定義を問う 12 問とした。
Ruri v3 30m とリランカーは CPU で動かし、スレッド設定は 4 とした。
文書ベクトルの構築には GPU を使った。

| リランカー | p50 / p95 ms | ページ再現率 | nDCG | RSS 合計の最大標本値 |
| --- | --- | --- | --- | --- |
| なし | 149 / 187 | 0.8972 | 0.7252 | 1.04 GB |
| tiny int8、上位 8 件 | 356 / 424 | 0.8972 | 0.7443 | 1.48 GB |
| xsmall int8、上位 8 件 | 818 / 1,043 | 0.8972 | 0.7758 | 1.51 GB |

時間には MCP 通信、質問の埋め込み、分かち書き、検索、順位融合、リランクを含む。
回答生成と初回のモデル準備は含まない。
初回検索までの時間は、各条件で約 67 秒、23 秒、24 秒だった。
計時中は全量抽出と GPU 埋め込みのプロセスを一時停止し、終了後に再開した。
別途起動していた OCR の初期化プロセスは存在したため、完全に無負荷の PC での測定ではない。

ページ再現率は、製品 `search` が返す上位 30 **チャンク内**に含まれる正解ページの割合を質問ごとに求めた平均である。
nDCG は、その範囲でページの重複を除いた上位 10 ページで計算した。
旧 PoC の「200 候補から上位 30 ページを選ぶ」指標とは条件が異なるため、数値の差をモデルの劣化と解釈しない。
RSS は親プロセスと MCP、その子ワーカーの値を 50 ms 間隔で合算した標本の最大値であり、共有ページの重複を含み、瞬間ピークは保証しない。

今回の条件では xsmall の順位精度が最も高いが、p95 は 1 秒目標を超えた。
PDF の 60 問だけを集計すると、ページ再現率は各条件とも 0.8167、xsmall の nDCG は 0.6788 だった。
[追加の誤り点検](natural-error-audit.json) では 10 問で正解ラベルを一つも取得せず、2 問で複数ラベルの一部を取得しなかった。
前者のうち 2 問には未判定の別ページに根拠があり、残る 8 問には点検した上位結果に根拠が見つからなかった。
正解ラベルは変更していない。
リランカーの生のスコアだけで正解なし質問を棄却する方法も、保持した負例の大半を受理しており、十分な棄却能力を確認できなかった。
閾値は資料ごとに固定分割した開発側で調整し、保持側では再調整していない。
負例は不在識別子に限定した人工的な質問であり、一般的な分野外質問の評価を代替しない。

## 同時接続

[concurrency-results.json](concurrency-results.json) は、二つの実 MCP 接続で行った試験を記録する。
8 回の同時投入の重複抑止、wiki ごとのジョブの分離、別 wiki のジョブへのアクセス拒否、別接続からのキャンセルを確認した。
索引化中の検索は待機し、その間の進捗取得は約 14 ms で応答した。
索引化後には検索が完了し、8 件の同時検索要求も約 1.21 秒で全件完了した。

モデルを保持するワーカーは一つで、保持する接続を強制終了した後も、残る接続が新しいワーカーを起動して検索できた。
完了済みのジョブを再実行せず、キャンセル済みの別 wiki のジョブも再開しなかった。
ここで確認したのは索引化と検索の直列実行、および受付と制御の応答であり、索引化と検索を同時に計算する実装ではない。

[配布用 uv 起動の制御試験](controls-results.json) 5 件と、[検索設定の MCP 試験](retrieval-config-results.json) 4 件も成功した。
検索設定だけを変えても埋め込みモデルとフィンガープリントを維持し、未知の設定を拒否し、空の索引でも棄却情報を返すことを確認した。
新規キャッシュへの SciPy 展開は共有違反で 2 回失敗したが、C ドライブの準備済みキャッシュでは起動と実埋め込みまで確認できた。
既存の D ドライブ側の環境では、MCP の import が `_path_stat` で長く待機したため、準備済み C ドライブ側の環境で試験を完了した。
初回準備が安定する条件の特定は、今回の機能試験とは分けて扱う。

## OCR

[ocr-complex-results.json](ocr-complex-results.json) は、製品の OCR 起動経路で固定版 NDLOCR-Lite を実行した結果である。
既知の日本語文字列を使い、段組み、表、数式、低解像度、画像の縦書き、テキスト層を持つ縦書きの 6 ページを描画してから照合した。
参照文字列は自作したもので、実資料を人が全文転記した正解データではない。

段組みと表では、参照した全行の文字列が出力に含まれたが、読み順が変わった。
NFKC と空白除去後の全文 CER（文字誤り率）は、段組みが約 48%、表が約 73% だった。
これは順序の違いも誤りとして数えた値である。
数式の CER は約 6.9% で、一部の記号を誤認した。
低解像度と 2 種類の縦書きでは、この短い参照文字列の CER は 0 だった。
複雑な表の構造復元や任意の低解像度資料についての成功は保証しない。

実資料では、描画画像 2 ページから短い抜粋を独立に転記して、以前の OCR 出力と照合した。
[real-ocr-excerpts.json](real-ocr-excerpts.json) の完全一致は、低解像度の広告が 3 行中 1 行、別の広告が 10 行中 7 行だった。
見出しの全文には判読が曖昧な箇所があったため、確実に読める短い範囲を参照文字列に採用した。
転記は Codex による画像確認であり、人手による全文正解や全文 CER の測定ではない。
縦書きと分類された広告は目視では横書き中心で、分類の偽陽性が残る。

最初の試行では既存環境の ONNX 初期化が約 905 秒進まず、検証用のプロセスだけを停止した。
C ドライブの独立キャッシュの準備でも `os error 5 / 32` の一時的な共有違反があり、再試行後に準備できた。
準備済みのライブラリでの直接実行結果は [ocr-direct-results.json](ocr-direct-results.json) として分けて保存した。
保存先や準備状態の違いだけを、初期化遅延の原因と断定しない。

## OS

[os-results.json](os-results.json) に実施範囲と中断理由を残した。
Windows では、保存時の共有違反と長い埋め込み入力を含む単体試験 11 件が成功した。
Linux は Ubuntu 24.04 / WSL 2、Python 3.12.3 で、最初の既存試験 6 件に加え、現在の単体試験 11 件が成功した。
新規起動が `Wsl/Service/CreateInstance/ERROR_TIMEOUT` で失敗していたが、利用者の手元で起動した後に再接続できた。
その後、検証用環境の Pygments に NUL を含むソースを検出し、同じ 2.21.0 を再導入した。
実 MCP は OCR の中断から復帰したが、埋め込み 0/42 のまま待機上限に達した。
親監視や MCP を介さない単独の `import torch` でも SIGSEGV が再現し、Transformers のパッケージ情報が空だったため、旧環境を保持したまま独立した環境を準備し直した。
この時点では、POSIX の親監視に原因を絞る証拠は得られていない。
[環境診断](linux/environment-failure.json) に、観測した SIGSEGV、OOM 記録がないこと、取得した終了コードと推定値の区別を残した。
新しい環境への配置も一時ファイルの `os error 2` で失敗したため、別名の環境で配置を一つずつ行った。
この並列度には uv の [`UV_CONCURRENT_INSTALLS`](https://docs.astral.sh/uv/configuration/environment/#uv_concurrent_installs) を使った。
配置は約 14 分 45 秒で完了し、`sync` 後の実ライブラリの読み込みと単体試験 11 件が成功した。
この環境で実 MCP の中断・再開 18 項目がすべて成功した。
OCR の初期化時と埋め込みバッチの保存後に MCP を強制終了し、同じジョブを 3 回の接続で再開して、42 ページと 42 チャンクを重複なく公開した。
配布用 uv 起動の制御試験は、全量索引を作成中のキャンセル応答が約 8 秒で、2 秒未満の条件を満たさなかった。
[当初の失敗](linux/controls-during-build-results.json) を保持し、計測条件を分けて再試験した。
全量計測が終わった後の [再試験](linux/controls-results.json) では、キャンセル応答が約 42 ms となり、明示再試行の実埋め込みを含む 5 項目がすべて成功した。
同時負荷だけを遅延の原因と断定することは避ける。
OS や WSL の停止・再起動コマンドは実行していない。
WSL では uptime の変化と unclean shutdown の記録も観測したが、発生原因は確定していない。

## 変更した実装

製品に任意の CPU リランカーと、リランク済み候補の閾値、作成済み ANN 索引の探索設定を追加した。
既定のリランカーは `off` のままとし、モデルや索引基盤の最終採用は決めていない。
検索結果では生の `rerank_score` を順位融合の `score` と分けて返す。
リランカーの入力上限は 512 トークンで、長い入力の切り詰めは README に記載した。

検証結果の JSON 保存でも Windows の共有違反が発生したため、一意な一時ファイルからの原子的な置き換えに短い再試行を加えた。
元の JSON を維持したまま再試行し、最後に新しい値へ置き換わることを試験した。
全量処理では 2,048 トークンの固定上限を超える 7 チャンクを検出して停止した。
モデルの設定では 8,192 トークンを扱えることを確認し、製品と補助処理をモデル本来の文脈長へ変更した。
入力上限の事前検査と長さに応じたバッチ制御を加え、[実モデルの試験](native-context-results.json) では 2,129 トークンが処理に渡ることと単位長のベクトル出力を確認した。
追加後の Windows と Linux の単体試験は各 11 件が成功した。
保存済みベクトルは入力ハッシュを照合して再利用し、語彙検索の準備も同じ正規化処理であることを AST とハッシュで確認して再開した。
コミット、push、リリースは行っていない。
