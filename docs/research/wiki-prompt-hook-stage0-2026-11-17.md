## (d) 発火の形

記録するだけの試験用のプラグインを `--plugin-dir` で読み込み、`claude -p`（Haiku）で確かめた。

- `additionalContext` はモデルに届く（足した合言葉にモデルが答えた）。起動行の `uv run …; exit 0` は Claude Code の中でも動く。
- スラッシュコマンドでは、`prompt` に打ったままの 1 行が入る（`/wiki-probe:ping hello`）。
- サブエージェントの中では発火しない。サブエージェントの報告が戻るときに、`<agent-message from=…>` で始まる `prompt` で発火する。
- `userConfig` の既定の値は、設定していなければ環境変数（`CLAUDE_PLUGIN_OPTION_*`）で届かない。既定はスクリプトの側で持つ。
- `--plugin-dir` のプラグインのデータの場所は `<名前>-inline` になる。
- マーケットプレイスの `wiki@info-hive` と `--plugin-dir` の `wiki` を同時に読むと、`--plugin-dir` の側のフックが登録される（`Plugin "wiki" from --plugin-dir overrides installed version`）。
- `--output-format stream-json` の記録には、UserPromptSubmit のフックの出来事は出ない。届いたかは `--debug-file` の `Hook UserPromptSubmit ... provided additionalContext (N chars)` で確かめる。
- `/loop` と他のセッションからの知らせは `-p` では再現できなかった。どちらもタグで始まる形で届くとみて、タグで始まる指示を飛ばす。
- デスクトップアプリで窓が出るかは、作者が目で確かめる。

## (f) 読む段のモデルとエフォート

### 旧測定と第2版の扱い

旧形式 `reader-models/` は、Read の呼び出ししか保存しておらず、成功した読み取りを確認できない。第2版では原本の wiki、評価データ、読むエージェント、測定コードを固定し、呼び出しと成功の応答を ID で照合した。未読引用、存在しないリンク、同名ページのスコープの曖昧さも分けた。

利用上限による最初の429は履歴に残した。作者の指定どおり2026-11-17 23:30（Asia/Tokyo）以降に再開し、13問を各2回、6組とR0の直接読む回を合わせた158回を完了した。第2版のCLIの換算費用は $9.5300。記録は `reader-models-v2/` に残す。

ただし、初回の Opus レビューで、未読であることを明記した出典の紹介まで未読引用に数えること、ファイル名に現れた字句で正答を過大評価することが指摘された。また、初期化の記録には共有の自動メモリのパスがあり、混入を排除できなかった。第2版だけでは表を確定せず、下の第3版を最終判定に使う。

### 第3版の固定条件と採点

記録は `reader-models-v3/`。wiki は指定コミットの固定コピー、ユーザー側の同名ページは測定専用の合成データである。この同名ページの問いは読む段を比較するための統制された入力であり、フックの実際の候補選択の再現ではない。

- 実行側を `reader_measurement_runtime.py` に分離した。実行側、固定したページ全体、読むエージェント、問い、設定のハッシュを入力の指紋に含める。採点器の変更は採取条件を変えない。実際の CLI の版を各回の初期化の記録に保存し、再採点では当時の入力を検証する。
- `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` と `autoMemoryEnabled:false` で自動メモリを無効にし、実際の `memory_paths` でも混入がないことを検査する。指示ファイルの除外、MCP の空の構成、設定の読み込み元の制限も固定する。`DISABLE_AUTOUPDATER=1` で測定中の更新を止める。これらは [Claude Code のメモリの公式文書](https://code.claude.com/docs/en/memory) と [環境変数の公式文書](https://code.claude.com/docs/en/env-vars) に従う。
- 同じ13問、6組、各2回とR0の直接読む2回、計158回を測る。読むエージェントはMCPとフックのない最小プラグインへ写し、Read、Glob、Grepを渡す。Fable の alias が実際に選んだモデルは記録の ID で区別し、5.1 と決め付けない。
- 通信、指定モデル、費用・時間の計量の失敗は履歴を残して再試行できる。回答の形式の失敗はモデルの品質の失敗として数え、成功するまで繰り返して選別しない。
- 問いごとの期待する命題は、新しい回答を得る前に `reader_questions.json` の `assertions` に固定した。字句の一致は診断値として残し、最終判定には使わない。
- `grade_reader_models.py bundle` が回答のモデル報告の節を除き、モデル名、費用、回の名前を伏せる。採点者には問い、期待する命題、回答、実際に開いたページとその本文を渡す。命題は supported / omitted / wrong、引用は実際に根拠にしたものと未読の出典の明示を意味で区別する。採点した写しと元の回答の SHA-256 を対応付け、改変や欠測を拒む。
- 全組がそろったあと、意味で支えられた命題の割合が最良の組の95%以上で、誤った命題、根拠のない追加の主張、引用の誤り、必読ページの欠落、形式の失敗がない組から、平均費用が最小のものを選ぶ。これはこの問いと6組の範囲の選定であり、未知のwikiや全モデルの最適性の証明ではない。

第3版の158回を完了した。全件が有効な観測で、CLIは2.1.325、memory_pathsは空、形式の失敗は0だった。全測定のCLIの換算費用は$9.774664。以下の二人の採点と裁定でモデル表を選定した。

### 暫定表での Agent ツールの経路

`verify_reader_delegation.py` で R1、R2（2つのwiki）、R3 の代表例を1回ずつ Agent ツールから呼んだ。記録した引数は `subagent_type=wiki:wiki-reader`、R1/R2はhaiku/low、R3はsonnet/low。全件が戻り、modelUsage は Haiku 5.5 と Sonnet 5.5 の実行を示し、メインの Read は0件だった。記録は `reader-models-v3/delegation-provisional.json` と `delegation-validation-provisional.json`。

親の Opus の起動と3呼び出しを含む合計は $0.225474。これは Read の代替経路の契約の確認であり、MCP get_page の費用や、全組の親子合計費用の比較ではない。単独の読む段での費用の順位を、あらゆる実際の Agent の総費用の最安と読み替えない。R0は既存のメインが1ページを開くという運用方針を維持し、新規CLIの測定を既存のメインの追加費用の根拠にはしない。

## Sol のレビュー後に変えた範囲

- 入力の囲みを一方向に走査して除き、直接参照も含むすべての一致で同じ問い合わせ文を使う。
- 親の Python から解析の子を期限で停止する。起動の形が変わったため、上記の所要時間は変更前の値である。
- 所在を省略しない JSON にし、2,000 文字に収まった候補だけで、読む段と既出記録を決める。
- 評価の道具も、選別時の集合ではなく、実際に出力に入る集合を数える。

開発用と確認用は同じ wiki の問いを位置で分けたもので、確認用で見つけた誤りも調整に使っている。独立した未知の wiki への検証とはみなさない。貼り付け、閉じない囲み、長い所在、複数スコープの同名ページ、状態の競合は、別途合成の回帰試験で確かめる。文字の置換だけで命令文を無害にできるとは主張しない。

修正後の全評価は、出力に収まった候補を数えて再現率 0.889、精度 0.893、負例3群の発火はいずれも 0 で合格した。Git Bash と uv を通す起動の再測定（合成の9ページ、ウォームアップ後に各10回）では、短文の p95 は 214.0 ms、検索は 517.5 ms だった（`review-fixes-timing.json`）。150ページや未知の wiki での再測定を代替する値ではない。

Opus 5.5 の初回レビューは解除後に完了した（`docs/agent-runs/2026-11-17-wiki-prompt-hook-review/opus-live-review.md`）。判定は「条件付きで採用可」、重大7件。既読保存前の出力、再採点と測定の分離、意味の採点、品質失敗の扱い、委譲した報告の確信度、実際のAgent経路を修正・検証した。最終表を添えた再レビューは下に記録する。

既読状態は、解析の子から書かず、親が追加コンテキストを実際に出力して flush したあとに保存する。親子の締め切りには共通の単調時計の絶対時刻を使う。状態のキーはスコープ・wikiの実体のパス・相対パスの組に変え、同一セッションで別のwikiに移ったときの同名ページの誤抑制を防いだ。

`/wiki:query` で読むエージェントの報告だけを受け取っても、メインによる既読には数えない。メイン自身が本文を開くまでは未読の上限「低」を当てる。フック由来の0Fの上限も、同じwikiの同じページが意味検索に出るまで残す。


### 出力と状態の分離後の所要時間

`publication-timing.json` は、150ページの合成wikiをGit Bashとuvから起動し、ウォームアップ後に各10回測ったもの。短文のp95は1425.5 ms、検索のp95は5321.5 ms、候補が実際に届いたのは検索10回中3回だった。終了コードは全回0。測定時には別作業のCPU負荷が続いており、それらのプロセスは停止していない。

これは2.5秒の内部期限が、シェル、uv、Python自体の起動やOSのスケジューリングまで含む上限ではないことを示す。この時点では高負荷のPCで5秒の外側の期限に収まることを確認できず、リリース前の未解決事項とした。後続の起動処理の修正と合成負荷による検証は、[並列性能の記録](wiki-prompt-hook-performance-2026-11-18.md)に分けた。旧版の9ページのp95 517.5 msも、ここでの5.3秒も、現在の起動行の測定値ではない。


並列のモデル測定が終わった後に、同じ150ページ・各10回を `bench_prompt_publication.py` で再測定した（`publication-after-matrix-timing.json`）。短文p95は210.2 ms、検索p95は639.3 ms、検索の候補到達は10/10、終了コードは全回0、標準エラーはなかった。この条件では1秒の目安を満たす。ただし完全なアイドル状態を確認したものではなく、先の遅さの原因をCPUだけに切り分けたわけでもない。これは並列性能の修正前の記録である。


### 意味の採点と裁定の結果

Opus 5.5/high が全158回答を採点した。初回の採点の生の結果は `semantic-grades-opus.json`。Opusは採点後に改行の形式の確認のためsummary.jsonとmanual-spotcheck.jsonを開いたと報告しており、指定した読み取り範囲を超えている。完全な匿名性が守られた証拠とは扱わない。

独立した2人目としてGPT-6.1 Sol/mediumに全158回答を依頼した。CLIはツール起動が壊れていて採点できなかったため、その試行は未実施として残し、アプリ内サブエージェントで完了した。Solには、別の隔離した一時ディレクトリの13問だけを渡し、モデルの対応表、費用、先行採点、リポジトリは渡していない。IDは予測できない乱数へ替え、答えと根拠の二節へ形式をそろえた。入力13ファイルのSHAはすべて一致した。結果は `semantic-grades-sol.json`、入力の写しは `blind-sol/`、対応は `second-judge-map.json` に保存した。

命題の判定は598/610で一致した。差のあった命題、およびどちらかが引用の誤りや根拠のない主張を挙げた回答の全30件を、Codexが元の本文と照合して裁定した。記録は `semantic-adjudications.json`。追加された時制の断定、本文にある比較をないとする否定、無効なリンク名を実際の本文と解決規則で確かめた。期待命題の曖昧な言い方は、当初の「本文を優先する」という規則に従って `rubric-clarifications.json` に線引きを記録した。凍結した元の命題、入力、回答、二人の採点は書き換えていない。

最終の採点を `semantic-grades.json`、採点と入力・裁定の結び付きを `semantic-provenance.json`、選定を `model-selection.json` に保存した。写しの13問、命題、本文、全回答の対応を元の入力と照合し、空のmanifest、欠測、採点後の改変、CLI版の混在を拒む。ハッシュが示すのは写しと記録の整合性であり、採点者が実際に読んだことや判断の正しさそのものの証明ではない。
