# 全量の OCR を rag 0.5.0 の形で進める（2026年11月9日〜）

検証用の全量データ（重複を除いた 905 文書、`auto` が OCR に回すと見積もった 22,335 ページ）の OCR を、rag 0.5.0 の製品の関数で進め、2026年11月12日 20:32 に終えた。結果は、ADR-0014 が決めた鍵と形で残すので、のちの rag の移行（ADR-0012）でそのまま使える。数日かかる見込みだったので、裏で回し、止めても再開できるようにした。

この文書は、方針、PoC の結果を引き取れるかの判断、回し方と再開の手順、進み具合と最終の結果の記録をまとめる。進み具合の写しは [rag-full-ocr-v050-2026-11-09/](rag-full-ocr-v050-2026-11-09/) にある。

## 結論

- 2026年11月4日の PoC の経路（`poc/rag/full_pipeline/full_ocr.py`）では続けない。製品の `rag_pdf.extract_pages()` を文書ごとに呼ぶ、新しいスクリプト `poc/rag/full_pipeline/product_ocr.py` で回す。
- 結果は `<data_dir>/extracted/<内容の SHA-256>/auto-150-e57f7c6bd9cf-extract-v1/` に、製品と同じ `page-<6 桁>.json` と `document.md` として残す。全ページ（テキストのページも含む）のファイルを作るので、のちに同じ `data_dir` で取り込むと、製品は OCR も抽出もせずにファイルを読み直すだけで済む。ただし、`ocr_mode` が `auto`、`ocr_dpi` が 150 のままで、rag が `OCR_REVISION` と `EXTRACT_REVISION` を変えていないときに限る。どれかが変われば鍵が変わり、製品はこの結果を使わない。
- PoC で保存した 233 ページは、ファイルとしては引き取らず、製品の経路でやり直す。PoC のコードが 0.5.0 と違うためである（後述）。やり直した結果を PoC の本文と比べた。233 ページのすべてが一致した。PoC の結果を引き取っても、同じ本文になっていたことになる。
- 止めても、保存済みのページを変えずに再開できることを、実際に強制終了して確かめた。
- 905 文書のうち 903 文書を終えた。製品の判定で OCR に回ったのは 22,335 ページで、2026-11-04 の目安と文書ごとに一致した。動いていた時間は合わせて約 24 時間だった。テキストだけの 2 文書は、ファイルの先頭に改行が 1 バイトあるため、0.5.0 の `read_pdf()` が PDF でないとして拒み、失敗した（後述）。

## 方針

### 製品の関数をそのまま呼ぶ

| 項目 | 決定 |
| --- | --- |
| 抽出 | 製品の `rag_pdf.extract_pages(data, config, config.extraction_dir(doc_id))` を文書ごとに呼ぶ。ページの判定（`inspect_page()`）、OCR、`page-*.json` の形は製品のままである。手で同じ形を書く方法は採らない。製品と食い違うおそれがあるからである |
| `document.md` | 製品の `Engine._write_markdown()` で書く。製品は検索できるテキストがない文書では書かないので、それに合わせる |
| OCR の実行環境 | 製品の既定（`uv run --no-project --script rag_ocr.py`）。`uv_cache_dir` は `data_dir/uv-cache`。初回に uv が解決した版は、NDLOCR-Lite 1.3.0（`e57f7c6`）、onnxruntime 1.31.1、numpy 2.2.2、opencv-python-headless 4.11.0.86、pillow 13.0.0、pypdfium2 4.30.0 だった |
| OCR の対象 | 計画の 22,335 ページを選んで渡すのではなく、0.5.0 の `inspect_page()` に決めさせる。22,335 は 2026-11-04 のネイティブ抽出で数えた目安で、製品の判定で数え直した数は、終わったあとに記録する |
| 排他 | 製品の取り込みと同じく、文書ごとのロック `<data_dir>/extracted/<SHA-256>.lock` を取る。同じ `data_dir` を MCP が使っても競合しない |

| コードの固定 | 開発リポジトリが固定した rag のコミット（`0ca80c7`、0.5.0）のスクリプトを、`git archive` で作業領域に写して使う。worktree を消したり、サブモジュールを進めたりしても、走っている処理の読むコードは変わらない。再開のときに rag のコードの SHA-256 か抽出の鍵が前回と違えば、結果を混ぜないよう止まる |

## PoC の結果を引き取れるか

PoC の台帳（`full-ocr-20261104/ocr.sqlite`）には、OCR を済ませたページが 233 ページ（文字が得られたもの 198、得られなかったもの 35、7 文書）あった。`full-ocr-progress.json` の 201 ページ（166 と 35）は、最後の実行の途中の値で、古い。

ファイルとしては引き取らないことにした。PoC が記録したコードの SHA-256 が、0.5.0 のどれとも一致しないからである。

| ファイル | PoC（`ocr-policy.json`） | rag 0.5.0（`0ca80c7`） |
| --- | --- | --- |
| `rag_ocr.py` | `6ab90c5f8ede…` | `502f4227396…` |
| `rag_ocr_client.py` | `323c83366875…` | `0da60feaa2ae…` |
| `rag_pdf.py` | `0755ea37a471…` | `3be8d5480eff…` |

改行を CRLF にしても一致しない。rag のリポジトリでは、この 3 つのファイルは 2026-11-05 の最初のコミット（`54d3a06`）から 0.5.0 まで変わっていないので、PoC はコミット前の作業中のコードで動いていた。PoC の OCR の実行環境も、製品の uv の環境でなく、PoC 用に用意したライブラリ（`poc/rag/remaining/ocr_local_runtime.py`）だった。PoC の `full_ocr.py` 自身も、コードの SHA-256 が変わると再開を拒む。

代わりに、製品の経路でやり直した本文の SHA-256 を、PoC の台帳の `text_sha256` と比べる（`product_ocr.py compare`）。一致すれば、PoC の経路と製品の経路は同じ本文を返すことになり、引き取っても同じだったと言える。全体の 1% に満たないので、やり直しの費用は小さい。

| 時点 | 比べたページ | 一致 | 不一致 | まだ処理していない |
| --- | --- | --- | --- | --- |
| 2026-11-09 20:05 | 14 | 14 | 0 | 219 |
| 2026-11-10 00:31 | 196 | 196 | 0 | 37 |
| 2026-11-10 00:45 | 222 | 222 | 0 | 11 |
| 2026-11-11 08:58 | 233 | 233 | 0 | 0 |

7 文書をすべて処理し、PoC で OCR した 233 ページの本文は、すべて SHA-256 まで一致した。製品が OCR に回したページも、PoC の対象のページと同じだった（`not_ocr_in_product` が 0）。PoC の経路（準備したライブラリ、作業中のコード）と製品の経路（uv が解決した環境、0.5.0）は、同じ本文を返す。引き取っても結果は同じだったことになる。

## 回し方

コマンドは、開発リポジトリのチェックアウト（worktree でもよい）から実行する。Python は `.rag-venv` を使う。

起動（セッションから切り離して裏で動かす。WMI の `Win32_Process.Create` から `cmd` を介して起動するので、起動したセッションやターミナルを閉じても止まらない）:

```bash
C:/Works/info-hive-dev/.rag-venv/Scripts/python.exe -X utf8 poc/rag/full_pipeline/product_ocr.py start
```

進み具合:

```bash
C:/Works/info-hive-dev/.rag-venv/Scripts/python.exe -X utf8 poc/rag/full_pipeline/product_ocr.py status
```

止める（`STOP` を置き、処理中の文書の子プロセスを止める。保存済みのページは残る。処理中のページだけがやり直しになる）:

```bash
C:/Works/info-hive-dev/.rag-venv/Scripts/python.exe -X utf8 poc/rag/full_pipeline/product_ocr.py stop
```

再開は、起動と同じコマンドである。台帳で処理中だった文書を未処理に戻し、保存済みのページを読み直して続ける。PC を再起動したあとも同じである。失敗した文書をやり直すときは `--retry-failed` を付ける。並列の数とスレッドの数は `--workers` と `--threads` で変えられる（既定は 3 と 2）。

PoC の結果との比較:

```bash
C:/Works/info-hive-dev/.rag-venv/Scripts/python.exe -X utf8 poc/rag/full_pipeline/product_ocr.py compare
```

### 注意

- 2026年11月10日 00:45 から終わりまで、直した版のスクリプト（このリポジトリの `product_ocr.py` と同じもの）で動かした。`start` は、起動のたびにこのスクリプトを作業領域の `bin/` に写して使う。

- PC がスリープすると処理も止まる。復帰すると続くが、処理中だった文書は失敗になりやすい。製品の OCR の待ち時間（30 分）がスリープの時間も数えるので、復帰した直後に時間切れになるからである（2026-11-10 に 3 文書がこれで失敗した）。復帰したら `status` で失敗した文書を見て、あれば一度止めて `start --retry-failed` で起動し直す。終わるまで PC をスリープさせない設定にしておくのが確実である。
- 電源を切ったり再起動したりしたあとは、`start --retry-failed` で再開する。
- 2026-11-04 の目録の 922 件のうち、OneDrive のオンラインだけだった 8 件は、固定した 914 件（905 文書）に入っていないので対象にしない。対象の PDF が読めなければ、その文書を失敗として記録し、自動ではやり直さない。
- 進み具合の数（`ocr_pages.saved`）は、製品が OCR したと記録して保存したページの数である。済んだ文書は台帳から、済んでいない文書は保存したファイルから数える。目安の 22,335 との差は、ページの判定の違いによる。
- `rate_ocr_pages_per_hour_last_hour` と `eta_hours_estimate` は、直近 1 時間（起動から 1 時間たつまでは起動から）の OCR の速さで出した目安である。テキストのページの多い文書を処理しているあいだは遅く見える。
- ページのファイルは、製品の `write_json` と同じく、一時ファイルに書いてから置き換える。`fsync` はしないので、電源が落ちたときに保存したばかりのページが壊れないことまでは確かめていない（計画で電源は切らない）。壊れたページがあると、製品も読み直せない。そのときは、そのページのファイルを消して起動し直す。

どの回も、製品が使い回せない形のファイルを残す経路、原本を書き換える経路は見つからなかった。指摘はどれも、進み具合の数と起動の管理に関するものだった。

## 残したこと

- 先頭に改行のある 2 文書は、rag の `read_pdf()` を直したあとに取り込み直す。この作業では rag のコードを変えない。
- スリープからの復帰で文書が失敗しても、自動ではやり直さない。製品の OCR の待ち時間は rag のコードにあり、ここでは変えない。
- のちの rag の移行（ADR-0012）で、この `extracted/` を使うときの手順は、移行の作業で決める。
