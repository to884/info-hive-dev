2026年11月20日追記：この試験で残ったキャッシュ管理の 2 件は、[後続の修正と検証](rag-cache-retirement-2026-11-20.md)で対応した。
以下の件数・ハッシュ・制約は、全量試験時点の記録として残す。

2026年11月19日に開始し、20日に結果を集計した。
全量テーブルを使う Windows の実 MCP 試験は 45 項目を通過した。
ANN の初回作成、追加時の更新、差し替えの公開直後で MCP を強制終了し、3 回とも同じジョブ ID で再開した。
最終の 783,645 行について、ANN・全文・世代の全索引で未索引行は 0、旧世代・重複行・保留した後始末も 0 だった。
OS の電源断・再起動や WSL の停止は行っていない。

最終監査も成功した。
905 文書・245,346 ページの抽出ファイルを読み直し、文書ごとの保存ハッシュと一致した。
以下の結果は、今回の未コミットの製品修正を含む状態に対するものである。

当時 PDF ヘッダーの判定で失敗したテキストだけの 2 文書は、現在の製品関数で別の作業領域へ抽出できた。
この 2 文書では追加の OCR は発生しなかった。

| 原本の登録場所 | 914 箇所 |
| 保存済みページを使った入力 | 245,346 ページ |

元の OCR の本文と旧ベクトルは読み取りだけに使った。
原本の PDF は元の場所に残した。
準備時の語彙は、現在の製品の `tokenize` で全件を処理し直した。
Ruri-v3-130m の固定版 `e3114c6ee10dbab8b4b235fbc6dcf9dd4d5ac1a6`、512 次元 FP32 を使い、新規ベクトルを CUDA で計算した。
入力を切り詰めず、モデルの上限 8,192 トークン以内で処理した。

全量の本文・ベクトル・公開台帳を、検証用の製品形式のテーブルへ一括投入した。
この準備が終わった時点では、索引は一つもなかった。
その後、検証用 PDF を実 MCP の `register_pdf` で取り込み、製品の処理から全量テーブルの索引を作成・更新した。
905 文書を個別に MCP で最初から取り込んだ試験とは区別する。

実 MCP の全量試験は Windows で実施した。
Linux は Ubuntu 24.04 / WSL の小規模な実 MCP 試験 11 項目と回帰試験を実施した。
両 OS とも準備済み Python から製品の `rag_server.py` を起動し、stdio で接続した。
配布用の `uv run` 起動や、Claude Code の `/wiki:ingest` を再試験する範囲は含めていない。

## 自動保守と停止・再開

| 停止箇所 | 停止後に確認した状態 | 再開後の結果 |
|---|---|---|
| ANN の初回作成中 | ジョブは `paused`、未公開。テーブル版 400 のままで ANN は未作成 | 同じジョブの 2 回目で完了。版 401、783,557 行を全索引が網羅 |
| PDF 追加による索引更新中 | ジョブは `paused`、追加文書は未公開。版 403 のまま | 同じジョブの 2 回目で完了。版 407、783,601 行を全索引が網羅 |
| 差し替えの公開確定後、旧世代の削除前 | 新版だけが公開済み。旧 440 行と後始末の台帳が残る | 同じジョブの 2 回目で完了。版 428、旧行と台帳を回収し、783,645 行を全索引が網羅 |

初回と追加の停止では、pending、段階、進捗、テーブルの版と索引統計を停止後に確認した。
どちらも索引変更の未コミット中であり、再開時の履歴とも一致した。
索引コミット直後の復帰については、実 LanceDB を使う回帰試験で確認している。

初回は 40 ページ・440 チャンク、追加は 4 ページ・44 チャンク、差し替えは 44 ページ・484 チャンクの検証用 PDF を使った。
停止対象は、この試験が起動した MCP とその子孫に限定した。
親の終了後に子ワーカーも終了したことを確認した。
差し替えでは公開トランザクション確定後の入口だけを待機させるテスト用フックを使い、停止位置を固定した。
通常の製品へフックは組み込んでいない。

3 回の再開では、保存したベクトルのハッシュを照合した。
さらに再開側で文書の埋め込み計算を禁止するフックを有効にし、再計算が起きれば試験が失敗するようにした。
初回と追加については、抽出済みページのハッシュと更新日時も変わらなかった。

差し替え直後は物理的に残った旧 440 行が検索結果へ出ないことを、ワーカー停止中の共通コアで確認した。
再接続後の実 MCP 検索でも、新版の参照と旧版の除外を確認した。
依存する wiki ページには `review_required: true` が付いた。
最後に同一 PDF を再登録した新しいジョブが `unchanged` で終わり、テーブルの版と索引の部品数が増えなかった。

最終の索引は、FTS、世代 Bitmap、cosine 距離の IVF_SQ である。
IVF_SQ は 886 パーティションを持つ。
全量での差し替えは小さな削除なので自動更新となり、再学習は起きていない。
削除に伴う ANN の自動再構築は、Linux の小規模な実 MCP 試験で確認した。

## 検索とベクトルの照合

- 保存済み OCR の本文から作った既知ページ検索 3 件で、文書・ページ・本文・原本の場所・SHA-256・wiki の出典ページが対応した。
- 既存ベクトルと新規ベクトルから各 8 件を選び、CPU で計算した参照値と照合した。cosine 類似度の最小値は浮動小数点の精度で 1.0 だった。
- 既知ベクトル 8 件について、FTS を使わない ANN 単独検索と全件走査を比較した。全件で対象自身が見つかり、上位 10 件の集合が一致した。

検索の `nprobes` は 128、`refine_factor` は 4、reranker は無効にした。
製品の既定の `nprobes` は 20 なので、この結果を既定設定の検索精度と同一視しない。
これらは既知本文・既知ベクトルによる整合性試験であり、人が作った質問による検索品質評価ではない。
書籍の本文は証跡に複製せず、検索結果の本文はハッシュと文字数に置き換えた。

## 元データと再開済み成果物の最終監査

4 スレッドで全抽出 JSON を読み、ファイル名・内容・ページ番号・文書ごとの OCR 件数を照合した。
全体でも 245,346 ページ、22,335 OCR ページ、空の認識結果 753 ページを確認した。
文書台帳は準備時と同じ JSON の式でハッシュ化し、保存値と一致した。
抽出ファイルの集約ハッシュは、別項目として記録した。

原本 914 箇所のサイズと更新日時は固定目録と一致した。
原本全体をもう一度読み直す内容ハッシュ検査は行っていない。
今回新たに抽出したテキストだけの 2 原本は、準備時に内容のハッシュも固定値と照合した。

既存のベクトルファイル全体の SHA-256 は変わらなかった。
新規埋め込みの中断前に確定していた 79,900 ベクトルは、対応表とバイナリの先頭部分のハッシュが再開後も一致した。
最終の公開台帳は 907 文書で、チャンク数の和がテーブルの 783,645 行と一致した。
試験用の 4 ジョブはすべて完了し、試験が起動した子ワーカーの残留はなかった。

## 検証中に修正した不具合

公開直後に止まると、旧世代の行を消す対象が失われ、再開後も旧行が残る不具合を再現した。
修正前の小規模試験では 4 行が残留した。
公開と同じ SQLite トランザクションで、後始末の対象を `retired_documents` に記録するようにした。
再開時に旧行の削除と索引保守を終え、最後に対象の記録を消す。

敵対的レビューでは、退役した文書 A を途中まで再登録した後に別文書 C を公開すると、A の行だけが消え、再開位置が残る別の反例も見つかった。
修正前は A が 4 行中 3 行しか公開されなかった。
行を削除する前に再開位置を無効にして確定し、同じ文書を再登録するときは新しい再開位置を作る前に後始末を終える順序へ直した。
索引全体をリセットする場合も、後始末の台帳を整合させた。

5 件の実 LanceDB の回帰試験でこれらの反例を確認した。
最終の Windows 回帰試験は 75 件成功、Linux は 75 件中 73 件成功・Windows 専用 2 件スキップだった。
Linux の実 MCP 試験は 11 項目すべて成功した。
Opus 5.5 の製品修正に対する 3 回目のレビューは `APPROVED` だった。
最終監査の並列化では、台帳の JSON と抽出ファイルに別のハッシュの式を使っているのに比較した誤りを確認し、修正した。
台帳とファイルを別々に照合する監査の再レビューも `APPROVED` となり、実行結果も成功した。

次のキャッシュ管理の Minor 2 件は残している。

- 退役文書の再登録では、冒頭の後始末で抽出結果を消し、OCR を再実行する場合がある。
- 後始末を保留した状態で索引をリセットすると、退役した文書の未使用の抽出キャッシュが残る場合がある。

今回の全量試験では、元の 903 文書の OCR を再実行する経路は使っていない。
詳細は [指摘への対応](rag-full-ann-2026-11-19/review-response.md)と[レビュー 3](rag-full-ann-2026-11-19/opus-review-3.md)にある。

## 時間・メモリと再現

全量テーブルへの投入は約 245 秒、実 MCP の 45 項目は約 819 秒かかった。
MCP 試験のプロセスとその子孫の RSS の和の最大は約 5.06 GiB だった。
RSS は 100 ms ごとに採り、共有ページを重複して数える。
索引の処理だけの時間や、OS 全体のメモリ使用量とは区別する。

最終監査は約 372 秒だった。
wiki ごとの製品保存先は、保持した過去の版を含めて約 14.18 GB（13.21 GiB）だった。
`index_cleanup_age_days=3650` で今回の版を残した値であり、現在の ANN 索引だけの容量ではない。

新規埋め込みは準備の途中で停止・再開した。
最後の再開分 74,716 入力は約 1,159 秒、CUDA の最大割り当ては約 2.08 GiB だった。
この時間は 154,616 入力すべてを最初から計算した時間ではない。

データの作業領域は `C:\Works\info-hive-dev-data\rag-poc-data\full-ann-20261119` に置いた。
`poc/rag/full_ann/` の `prepare.py`、`embed.py`、`stage.py`、`verify_mcp.py`、`finish.py` の順に実行する。
準備・埋め込み・投入・MCP 検証にはそれぞれ専用のロックがあり、同じ段階の重複起動を拒否する。
別の再試験では `RAG_FULL_ANN_WORK` で新しい作業領域を選ぶ。
原本、以前の PoC、元の OCR キャッシュの削除は行わない。
