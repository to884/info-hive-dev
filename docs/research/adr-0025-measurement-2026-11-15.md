# ADR-0025 の承認の条件の測定（2026-11-15）

[ADR-0025](../adr/0025-pdf-text-layer-with-pdfminer-vertical.md)（PDF の文字の層を pdfminer の縦書きの検出ありで取り出す）の承認の条件のうち、1（時間とメモリ）、2（ページの対応）、3（確かめるべきページの割合）を測った。測っている途中で、pdfminer が同じ PDF からプロセスによって違う本文を返すことが分かった。その原因と直し方も書く。

## 結論

| 条件 | 結果 | 判断 |
| --- | --- | --- |
| 1. 時間 | 平均は 0.29〜0.35 秒/ページで、0.5 秒以下。ただし 546 ページ中 43 ページは 0.5 秒を超え、最大は 7.9〜9.9 秒だった | 条件の文が平均か、ページごとかを決めていない。作者の判断が要る（下の「条件 1 の読み方」） |
| 1. メモリ | 最大 419 MB で、1 GB 以下 | 満たす |
| 2. ページの対応 | 合成の 12 ページ、防衛白書の 546 ページのどちらでも、PDFium と pdfminer が同じページを指した | 満たす。判定に使った 10 ページで、本文を毎回同じにする直しの前後を比べる作業が残る |
| 3. 印の割合 | 防衛白書で 546 ページ中 86 ページ（16%） | 条件が測る 33 ページ（24%）とあわせて、3 割以下 |
| 4. 契約の試験 | まだ | 実装のときに行う |
| 本文が毎回同じか（新しく分かったこと） | 直さない pdfminer では、6 回の取り出しで 5 ページの行の並びが変わった。直した版は 3 回とも同じだった | ADR-0025 に、直し方と契約の試験 7 を足した |

ADR-0025 の状態は「提案」のままにする。

## 試料と環境

| 試料 | 中身 | 取り方 |
| --- | --- | --- |
| `defense-white-paper-2025.pdf` | 防衛省 令和 7 年版防衛白書 全編。546 ページ、66,399,163 バイト。InDesign で組んだ横書きの資料で、図と表が多い | `scripts/fetch_corpus.py`。URL と SHA-256 は `sources.json` にある。作者の承認を得てダウンロードした |
| `synthetic-pages.pdf` | ページの対応を確かめるための合成の 12 ページ（下の表） | `scripts/make_synthetic.py`（reportlab 4.4.4、pypdf 6.1.3） |

PDF と取り出した本文は、リポジトリに入れない（`.gitignore`）。結果の JSON には、数とページの番号と SHA-256 だけを書いた。

測った PC は、Windows 11、AMD64 Family 23 Model 113（論理 CPU 16）、RAM 32 GB、Python 3.12.13 である。版は pdfminer.six 20260107、pypdfium2 5.15.2。これは検証の PC の値で、製品の仕様ではない。

## 条件 1: 時間とメモリ

`scripts/measure_time.py` で測った。判定（rag 0.5.3 の `rag_pdf.inspect_page`）と、pdfminer の取り出し（文書を 1 回だけ読み、ページごとに本文を受け取る）を、同じプロセスで続けて走らせた。2 回目は、ほかの処理と重ならないように 1 つだけで走らせた。

| 値 | 1 回目 | 2 回目（1 つだけで走らせた） |
| --- | --- | --- |
| 判定の平均（秒/ページ） | 0.023 | 0.022 |
| 取り出しの平均（秒/ページ） | 0.325 | 0.270 |
| 判定と取り出しの合計の平均 | 0.348 | 0.292 |
| 合計の中央値 | 0.122 | 0.100 |
| 合計の 95 パーセンタイル | 1.25 | 1.11 |
| 合計の最大 | 9.86 | 7.89 |
| 0.5 秒を超えたページ | － | 43（7.9%） |
| 1 秒を超えたページ | － | 30 |
| 546 ページの合計 | 189.7 秒 | 159.6 秒 |
| メモリの最大 | 418.9 MB | 419.5 MB |

- 遅いページは同じだった（373、295、175、116 ページが 7〜10 秒）。0.5 秒を超えた 43 ページで、合計の時間の 66% を占めた。
- `extract_text(page_numbers=[i])` をページごとに呼び直す方法は、どのページでも 1 回 0.9〜2.1 秒かかった。呼ぶたびに文書を読み直すためである。0.5 秒以下に収まるのは、文書を 1 回だけ読む方法だけである。ADR-0025 の「役割の分け方」に、この方法を使うことを書いた。
- 文書を 1 回だけ読む方法の本文は、文書全体を `extract_text` で取り出して改ページの文字で分けたものと、546 ページ中 543 ページ（1 回目）、542 ページ（2 回目）で同じだった。違ったページは、下の「本文が毎回同じか」の原因による。

### 条件 1 の読み方

ADR-0025 の条件は「1 ページあたりの時間が 0.5 秒以下」で、平均か、すべてのページかを書いていない。

- **平均と読むと:** 満たす（0.29〜0.35 秒）。
- **すべてのページと読むと:** 満たさない（43 ページが超える）。

ページごとの上限は、図の多いページがある限り、pdfminer では守れない。取り込みにかかる時間を見積もる目的なら、平均で足りる。そこで、条件の文を「1 ページあたりの平均の時間が 0.5 秒以下で、遅いページの数と最大を記録する」に直すことを提案する。直すかは作者が決める。

## 条件 2: ページの対応

`scripts/check_pages.py` で確かめた。

### 合成の PDF

各ページに `MARKER-Pnn`（nn はページの番号）を書き、PDFium と pdfminer の本文に、そのページの目印だけが入るかを見た。ページツリーは入れ子にした（/Pages のノードが 5 つ、深さ 2）。

| ページ | 中身 | 結果 |
| --- | --- | --- |
| 1、2 | ふつうのページ | 両方とも正しい目印 |
| 3、4、5 | /Rotate 90、180、270 | 両方とも正しい目印 |
| 6 | 中身を 90 度回して描いたページ | 両方とも正しい目印。PDFium の判定は `vertical` になった |
| 7 | 注釈（FreeText）だけのページ | 両方とも本文なし（判定は `blank`）。どちらも注釈の文字を取り出さない |
| 8 | 白紙 | 両方とも本文なし |
| 9 | CropBox で下半分を隠したページ | 両方とも正しい目印。どちらも、CropBox の外の文字（`HIDDEN-P09`）を本文に入れた |
| 10、11 | 親の /Pages から /Rotate 90 を受け継ぐページ | 両方とも正しい目印 |
| 12 | 横長のページ | 両方とも正しい目印 |

12 ページすべてで、両方のエンジンが同じページを指した。次の 3 つは、対応の問題ではないが、取り込みに関わるので ADR-0025 の実装で扱う。

- 注釈の文字は、どちらのエンジンも取り出さない。
- CropBox の外の文字は、どちらのエンジンも取り出す。
- 中身を 90 度回したページは、判定が `vertical` になる。rag はそのページを OCR に回す。

### 防衛白書

| 値 | 結果 |
| --- | --- |
| ページの数 | PDFium、pdfminer とも 546 |
| ページツリー | /Pages のノードが 123、深さ 3。回転したページはない |
| ページごとの本文の似かた（空白を除いた 2 文字組の Jaccard 係数） | 中央値 0.918、最小 0.743 |
| 似かたが 0.5 未満のページ | 0 |
| 判定 | `text` 543、`garbled` 2、`blank` 1 |

似かたの低いページがなかったので、前後のページとずれていないかの確かめ（`best_offset`）は使わなかった。回転したページは、合成の PDF だけで確かめた。

## 条件 3: 確かめるべきページの割合

条件が測るのは、検証の公開の 33 ページである（24%）。参考に、防衛白書の 546 ページでも数えた。

| 理由 | ページの数 |
| --- | --- |
| `image_coverage` が 0.5 以上 | 81 |
| pdfminer の本文に U+FFFD がある | 5 |
| pdfminer の本文に `(cid:<数>)` がある | 0 |
| 印の付いたページ（重なりを除く） | 86（16%） |

## 本文が毎回同じか

条件 1 の測定で、文書全体の取り出しと、ページごとの受け取りの本文が、数ページで違った。違うページは、走らせるたびに変わった。

`scripts/diff_text.py` を 3 つのプロセスで走らせ、ページごとの本文の SHA-256 を比べた。

| 比べたもの | 違ったページ |
| --- | --- |
| プロセス a と b（ページごとの受け取り） | 229、263 |
| プロセス a と c | 229 |
| プロセス b と c | 229、263 |
| 同じプロセスの中での、文書全体の取り出しとの違い | a: 8、229、247、351。b: 229、247、263、351。c: 229、351 |

どれかで違ったのは 5 ページ（8、229、247、263、351）である。違うページでは、文字の数も、行の集まりも同じで、行の並びだけが違った。

### 原因

`pdfminer.layout.LTLayoutContainer.group_textboxes` は、テキストボックスの組を、距離の近い順にヒープからまとめる。ヒープの要素は `(skip_isany, dist, id(obj1), id(obj2), obj1, obj2)` で、距離が同じ組の順は `id(obj)`、つまりメモリーの番地で決まる。番地はプロセスごとに変わる。

### 直し方を試した

`scripts/stable_text.py` で、`group_textboxes` を呼ぶあいだだけ、`pdfminer.layout` の中の `id` を「初めて見た順の番号」に置きかえた。3 つのプロセスで取り出すと、546 ページの本文の SHA-256 がすべて同じだった。直した版と、直していない版（プロセス a）が違ったのは、229 ページだけだった。

### 限り

- 確かめたのは 1 つの PDF で、3 回ずつである。違いの出なかったページが、いつも同じとは言えない。
- 直した版の時間は測っていない（ADR-0025 の条件 1 に、測ることを足した）。
- Sol が判定した本文は、直していない pdfminer の出力である。判定した 10 ページで直した版と違うかは、まだ確かめていない（条件 2 に足した）。

## ADR-0025 に足したこと

この測定と、作者の指示（2026-11-15）にもとづいて、ADR-0025 に次を足した。

- **本文を毎回同じにする:** 距離の同じ組の順を決まった順にする。その版を抽出の識別に入れる。契約の試験 7 で、別のプロセスで同じ本文になることを確かめる。
- **OCR の確信度とページの確認:** 作者の指示で足した。認識器（PARSeq）の出力はロジットだった（合成の行の画像で確かめた）。そこで softmax から文字ごとの確率を数え、行の確信度を文字の確信度の最小値とする。確信度の低いページは、要約の前にユーザーに見てもらい、「そのまま使う」「直す」「却下する」「あとで」から選んでもらう。閾値は承認の条件 5 で決める。
- **作者の資料の時間の見積もり:** 22,000 ページで 1.8〜2.1 時間とした（平均から）。
