# ADR-0010 の未決と実装前の PoC（2026年11月7日）

ADR-0010（`/wiki:browse` の中核と表示の方式の分離、状態は提案）を承認できる状態にするための材料である。未決の 6 件に、ADR-0013 で生じた `raw:` の絶対パスの扱いを 7 件目として加え、それぞれの選択肢と推す案をまとめた。あわせて、ADR-0010 が「見直す条件」に挙げる実装前の PoC の 5 項目を確かめた。

未決はユーザーが決める。ここに書く「推す案」は提案であり、決定ではない。

試作は [poc/browse/](../../poc/browse/README.md) に、測定の結果は [wiki-browse-adr-0010-poc-2026-11-07/](wiki-browse-adr-0010-poc-2026-11-07/) に置いた。

## 結論

- PoC の 5 項目は、どれも前提どおりだった。確かめていないのは、macOS（Safari と WKWebView）と、1,000 ページの実際の Wiki である。
- 同じ生成物を、`file://`（5 つのブラウザ）、127.0.0.1 のサーバー（5 つのブラウザ）、Tauri の独自スキーム（Windows の WebView2、Linux の WebKitGTK）の 12 通りで開き、同じ手順の結果がすべて一致した。Tauri の URL は Windows で `http://wiki.localhost/`、Linux で `wiki://localhost/` と違ったが、相対リンクだけの HTML はそのまま動いた。
- Linux の WebKitGTK でも、`line-break: strict` の禁則の違反は 0 件だった。ADR-0010 がアプリの技術の分かれ目に挙げた懸念は、Tauri を退ける理由にならない。
- `file://` で開いたページは、classic な `<script src>` で別のファイルを読めた。Chromium、Firefox、WebKit（Playwright の版）、Edge 156、Chrome 156 の 5 つで、`file://` とサーバーの 10 回の結果がすべて一致した。CSP の `script-src 'self'` も `file://` で違反を出さなかった。
- ナビゲーションの 1 項目は、作者の Wiki（56 ページ）で平均 111.6 バイト、最大 176 バイトだった。「約 100 バイト」はおおむね正しい。各ページに埋め込めば 1,000 ページで約 112 MB、共有の `nav.js` なら約 112 KB になる。
- 閲覧の画面（ブラウザのページ）は、wiki の MCP サーバーのクライアントになれない。`Origin` ヘッダーの付いた要求は、トークンが正しくても 403（`Invalid Origin header`）になり、`file://` のページからの `fetch` は失敗した。トークンも `%LOCALAPPDATA%/info-hive/server.json` にしかない。MCP のクライアントになれるのは、アダプタの側（サーバーの Python のプロセス、アプリが起動する中核）である。中継を通した Python からの呼び出しは通った。
- 未決 1 のページの集合は、ADR-0010 を書いたあとで違いが変わっていた。今は、lint だけが `.wiki-cache/` の Markdown を含み、search だけが最上位の `README.md` と `assets/` を含む。search の集合は MCP の `query` の索引にも使われるので、そろえる変更は browse だけの話ではない。

### 1. `file://` と classic なスクリプト

試験用の Wiki（`make_fixture.py`）を中核の試作（`gen.py`）で書き出し、同じ出力を `file://` と、サーバーの試作（`serve.py`、`http://127.0.0.1:<port>/<token>/w/fixture/`）で開いた。`test.mjs` が、各ブラウザで同じ手順を踏んだ。

1. `index.html` を開き、ナビゲーションの「ナレッジグラフ」をクリックする（下の階層への移動。`../nav.js` を読む）
2. 本文の「オントロジー#定義」のリンクで、日本語の見出しのアンカーへ移る
3. 戻って、空白を含む名前のページ（`entities/山田 太郎.html`）へ移り、被リンクを見る
4. 検索の欄に「知識表現」を入れる（`data/search.js` を動的に読む）
5. 未解決のリンクをクリックしても移動しないことを見る

| 確かめたこと | 結果（10 回とも同じ） |
| --- | --- |
| `nav.js`、`data/capabilities.js`、`app.js` の読み込み | どのページでも読めた |
| 動的に足した `<script src="../data/search.js">` | 読めた。検索の結果は 2 件 |
| 日本語の見出しのアンカー（`#%E5%AE%9A%E7%BE%A9`） | `id="定義"` の要素に移った |
| 未解決のリンク、`ambiguous` のリンク | `<a>` にならず、クリックしても移動しない |
| 本文の `<script>` | エスケープされて文字として出た（`html: False`） |
| CSP の違反 | 0 件（`file://` でも `script-src 'self'` が別ファイルのスクリプトを許した） |
| Wiki の外への要求 | 0 件（`file:` と `127.0.0.1` のほかへの要求なし） |
| Wiki のファイルのハッシュ | 試験の前後で同じ |

ADR-0010 の「`fetch` は移植性のある前提にできない」は、そのまま正しい。今回は `fetch` を一度も使わずに、ナビゲーション、検索、能力の宣言を動かせた。

### 2. WebKitGTK の日本語の CSS

WSL の Ubuntu 24.04 に、Tauri が Linux で使う WebKitGTK 4.1（2.52.6）と `fonts-noto-cjk` を入れ、Python の GObject から WebView を動かした（`webkitgtk_probe.py`、`webkitgtk_kinsoku.py`）。

`gen.py` の出力（`concepts/ナレッジグラフ.html`）を `file://` で開くと、次のとおりだった。

| 確かめたこと | 結果 |
| --- | --- |
| `../nav.js` などの classic なスクリプトの読み込み | 読めた。ナビゲーションは 8 項目 |
| 動的に足した `data/search.js` | 読めた。「知識表現」で 2 件 |
| CSP の違反 | 0 件 |
| 計算された CSS | `line-break: strict`、`word-break: normal`、`overflow-wrap: anywhere`、`text-autospace: normal` |
| 長い URL のはみ出し | なし |

スクリーンショット（[webkitgtk.png](wiki-browse-adr-0010-poc-2026-11-07/webkitgtk.png)）では、豆腐（字の欠け）はなく、`text-autospace` で和欧の間に空きが入った。

禁則は、目で見るのではなく数えた。`static-test/kinsoku.html` は、行頭に来てはならない文字（句読点、閉じ括弧、長音、小書きの仮名、中黒、感嘆符、疑問符）と、行末に来てはならない開き括弧を多く含む段落を、幅 8em から 30em まで 0.25em ずつ変えて描き、各行の先頭と末尾の文字を調べる。対照として、同じ段落を `line-break: anywhere` でも描いた。

| エンジン | `strict` の行頭の違反 / 行末の違反 / 行数 | 対照（`anywhere`）の行頭 / 行末 / 行数 |
| --- | --- | --- |
| Chromium 141 | 0 / 0 / 4,173 | 924 / 122 / 4,093 |
| Edge 157 | 0 / 0 / 4,173 | 924 / 122 / 4,093 |
| Firefox 142 | 0 / 0 / 4,178 | 967 / 125 / 4,099 |
| WebKit 26（Playwright） | 0 / 0 / 4,176 | 966 / 129 / 4,097 |
| WebKitGTK 2.52.6 | 0 / 0 / 5,316 | 1,306 / 145 / 5,167 |

- 対照で多くの違反を数えたので、測り方は違反を見つけられる。`strict` ではどのエンジンも 0 件だった。
- WebKitGTK の行数が多いのは、フォント（Noto Sans CJK JP）の字幅が Windows のフォントと違うためである。行の位置はエンジンの間でそろわないが、禁則の規則は同じに働いた。
- 最初の版の試験の段落は、行頭に来てはならない文字が 13 字続く部分を含んでいた。幅 8em ではその途中で割るしかなく、どのエンジンでも違反が出た（Windows の 4 つで 48 件、WebKitGTK で 168 件）。段落を直してから上の表の値になった。行頭禁則の文字が長く続く本文では、`strict` でも割られることがある。
- 最初に使った行の測り方は、折り返しの境目の文字を前の行に数えていた（境目の文字は、前の行の末尾にも幅 0 の矩形を返す）。幅のある最後の矩形を使うように直した。

### 3. Tauri の独自スキーム

`poc/browse/app/` に Tauri 2 の最小のアプリを作った。`register_uri_scheme_protocol` で独自スキーム `wiki` を登録し、`gen.py` の出力をそのまま返す。窓は `WebviewUrl::CustomProtocol("wiki://localhost/index.html")` で開いた。手順は `test.mjs` と同じで、ページに差し込んだ駆動スクリプトが進め、結果を同じオリジンへの画像の要求で集めた（Tauri の IPC は使わない）。

| 項目 | Windows | Linux（WSL2、WSLg） |
| --- | --- | --- |
| WebView | WebView2 157.0.4341.42 | WebKitGTK 2.52.6 |
| 実際の `location.href` | `http://wiki.localhost/index.html` など | `wiki://localhost/index.html` など |
| 基準（`file://` の Chromium）との一致 | 一致（差分なし） | 一致（差分なし） |
| CSP の違反、外部への要求、GET でない要求 | 0、0、0 | 0、0、0 |

- 両方とも Tauri 2.12.5（wry 0.57.1、tao 0.37.2）の debug ビルドで、1 回ずつ動かした。
- 日本語と空白を含むパスは、パーセントエンコードされた形でハンドラーに届いた。ハンドラーが UTF-8 でデコードしてファイルを返した。
- `../nav.js` のような上の階層への相対の読み込み、動的に足した `<script>`、日本語の見出しのアンカーは、どちらの OS でも動いた。
- Windows の WebView2 は `favicon.ico` を要求し、404 になった。生成物の問題ではない。
- ハンドラーの側では、URL の形の違いを意識しなくてよかった。パスの部分だけを見ればよい。
- 駆動スクリプトの最初の版は、`load` と `pageshow` の両方で段階を進めて結果がずれた。1 つの文書で 1 段階だけ進めるように直した。試験の側の誤りで、生成物の問題ではない。

### 4. ナビゲーションの大きさ

`gen.py` は `nav.js` を、ページごとに `[出力のパス, 題名, type]` の配列で書く。

| Wiki | ページ | `nav.js` | 1 項目の平均 / 最大 / 最小 | `data/search.js`（題名、要約、タグ、見出し） | 生成の時間 |
| --- | --- | --- | --- | --- | --- |
| 試験用 | 8 | 747 B | 83.1 / 239 / 55 B | 1,051 B | 0.02 秒 |
| 作者の Wiki | 56 | 6,331 B | 111.6 / 176 / 44 B | 13,219 B | 0.40 秒 |

1,000 ページに伸ばすと、`nav.js` は約 112 KB、`data/search.js` は約 236 KB になる。各ページにナビゲーションを埋め込むと、合計で約 112 MB になる。ADR-0010 の「約 100 MB」の見積もりは、日本語の題名でもほぼ当たっている。共有の `nav.js` を推す理由は変わらない。

### 5. 3 方式の合格の条件

ADR-0010 の合格の条件は、試験用の Wiki で、3 方式のリンクの移動、被リンク、診断の結果が一致すること、閲覧の前後で Wiki のハッシュが変わらないこと、外部への通信が 0 件であることである。実装のアダプタはまだないので、試作のアダプタで縮めた形で確かめた。

| 方式 | 環境 | 回数 | 結果 |
| --- | --- | --- | --- |
| `file://` | Chromium、Firefox、WebKit、Edge、Chrome | 5 | 基準と一致 |
| サーバー（`serve.py`） | 同じ 5 つ | 5 | 基準と一致 |
| アプリ（Tauri） | WebView2、WebKitGTK | 2 | 基準と一致 |

- 比べたのは、ナビゲーションの読み込みと項目数、本文のリンクの状態と行き先、被リンク、診断、本文の `<script>` のエスケープ、見出しのアンカー、検索の結果、未解決のリンクをクリックしても移動しないことである。
- `file://` とサーバーの 10 回では、Wiki のファイルのハッシュが試験の前後で同じだった。アプリは生成物だけを配り、Wiki を読まない。
- 外部への要求は、どの方式でも 0 件だった。ただし、外部のリンク（`https://example.com/`）をクリックしたときに、アプリが OS のブラウザに渡すこと（S-07）は試していない。

確かめていないこと:

- 実装の中核とアダプタでの試験。今回の結果は、契約（相対リンク、classic なスクリプト、共有の `nav.js`、`data/*.js`、CSP）が 3 方式で成り立つことを示すが、実装がそれを守ることは示さない。
- macOS（Safari と WKWebView）。
- 各環境 1 回だけの実行。

## 未決ごとの選択肢と推す案

ADR-0010 の未決の 6 件と、ADR-0013 で生じた 7 件目である。どれも、決めるのはユーザーである。

| 未決 | 推す案 | 主な根拠 |
| --- | --- | --- |
| 1. ページの集合 | lint の集合を正とし、`wiki_search.collect_pages()` を lint の `collect_pages()` と同じ除外にそろえる。そろえるときに、`.wiki-cache/` を両方で除く | F-G06 は lint との一致を求める。search の集合は MCP の `query` の索引にも使われる |
| 2. 書き出し先 | ADR-0012 の索引と同じ根（`%LOCALAPPDATA%/info-hive/`、macOS と Linux は XDG の data）の下の `browse/<wiki のハッシュ>/` を既定にし、引数で変えられるようにする | Wiki に何も足さない。ADR-0012 は `.wiki-cache/` を退けて同じ判断をした |
| 3. 静的出力のファイル名 | 読める名前を基本にし、変えたときだけ `~<識別子の SHA-256 の先頭 8 桁>` を付ける。1 つの名前の要素を UTF-8 で 200 バイトに収める | 作者の Wiki では名前を変えるページが 0 件。接尾辞は順序によらないので、ページを足してもほかのページの名前が変わらない |
| 4. RAG への経路 | ADR-0012 の案を採る。ただし MCP のクライアントは画面ではなくアダプタの側（サーバーのプロセス、アプリの中核）にする。静的版は RAG を持たない | ブラウザのページはサーバーに接続できない（`allowed_origins=[]`、トークンは `server.json` にだけある） |
| 5. 静的版の検索の範囲 | 題名、要約、タグ、見出しの部分一致にする。本文の検索は、サーバーとアプリで MCP の `query` に頼む | `tokenize()` を JavaScript に二重に持たずに済む。作者の Wiki で `data/search.js` は 13 KB |
| 6. アプリの技術 | 今は決めない。アプリを作ると決まったら、Tauri 2 を第一候補にする | WebKitGTK の日本語の描画は禁則の違反 0 件で、懸念が晴れた。独自スキームで同じ HTML が Windows と Linux で動いた |
| 7. `raw:` の絶対パス | 中核は `raw:` の値を解釈して出力に持たせ、表示は方式ごとに決める。Wiki の外に持ち出す書き出しでは、既定でファイル名と `raw_sha256:` だけを出す | http のページからは `file://` のリンクを開けない（5 つのブラウザで確認）。持ち運ぶ生成物に絶対パスを入れない、という ADR-0010 の規則と同じ扱いになる |

### 未決 1：ページの集合

| B. search の集合を正とし、lint をそろえる | 検索の結果が変わらない | lint が `README.md` と `assets/` の Markdown をページとして検査し、孤立ページなどを報告するようになる |
| C. browse だけが独自の集合を持つ | ほかに影響しない | 3 つ目の集合ができる。ADR-0010 の「規則を 1 か所に置く」に反する |

A を推す。そろえるときは、2 つの関数を残して除外を合わせるより、1 つの関数（またはその除外の定数）を両方から使う形にする。`.wiki-cache/` は lint の側にも足す。`.wiki-cache/` は search の解析のキャッシュの置き場所であり、ページを置く場所ではない。この変更は `info-hive-wiki` の変更で、browse の実装の前にする。

`index.md` と `indexes/` は、どちらの集合にも入らない。中核はこれらをページとして描かず、ナビゲーションの入力としてだけ読む（`list_index` と同じ扱い）案を推す。PoC の `gen.py` はまだ読んでいない。

### 未決 2：書き出し先

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. `<WIKI_ROOT>/.wiki-cache/browse/` | Wiki と一緒に見つけやすい | Wiki のフォルダーに生成物が入る。OneDrive などで同期していると、生成物も同期される。ページ数と同じ数の HTML が Wiki の中に増える。F-G06 と AC-D02 の「Wiki を変更しない」の範囲に、派生データを除くと書き足す必要がある |
| B. OS のユーザーの領域の下（推す） | Wiki に何も足さない。ADR-0012 の索引と同じ根（`wiki_mcp_common.data_dir()`）と、同じ Wiki のハッシュ（`wiki_key()`）を使えるので、新しい場所の規則が要らない | 場所が見えにくい。`/wiki:browse` が書き出した場所を表示する必要がある。古い世代と、消えた Wiki の分を掃除する規則が要る |

B を推す。具体的には `%LOCALAPPDATA%/info-hive/browse/<wiki のハッシュ>/`（macOS と Linux は `$XDG_DATA_HOME/info-hive/browse/<wiki のハッシュ>/`）とする。

- ADR-0012 は、索引の置き場所で同じ選択をし、`.wiki-cache/` を退けた。
- 選択肢レポートは、静的 HTML の書き出し先の既定として No.81（OS のユーザーキャッシュ）を選んでいる。B は「キャッシュ」ではなく ADR-0012 と同じ data の領域になる。消しても作り直せる点はキャッシュと同じだが、置き場所の規則を 1 つにするほうを重く見た。キャッシュの領域（`%LOCALAPPDATA%` の下の別の名前、`$XDG_CACHE_HOME`）を選ぶ案も成り立つ。
- Windows のパスの長さ: B の根（作者の環境で `C:\Users\<名前>\AppData\Local\info-hive\browse\<16 桁>\`）に、200 バイト（日本語 63 文字と接尾辞）の名前を置いても 151 文字で、260 文字に収まる。

人に渡すための書き出しは、引数（例 `--out <ディレクトリ>`）で場所を選ぶ。そのときの `raw:` の扱いは未決 7 で決める。

世代の切り替え（ADR-0010 の「新しい世代を作り終えてから切り替える」）は、B の下に世代ごとのディレクトリを作り、作り終えてから入口の小さな HTML を差し替える形が考えられる。Windows では、開いているファイルを含むディレクトリの名前を変えられないことがあるためである。PoC では確かめていない。

### 未決 3：静的出力のファイル名

`gen.py` の `export_name()` は、次の規則で名前を決めた。

- ページの識別子（NFC の POSIX の相対パスから `.md` を除いたもの）の、各要素をそのまま名前にする
- 次のときだけ、要素の末尾に `~<識別子の SHA-256 の先頭 8 桁>` を付ける
  - Windows で使えない文字（`<>:"\|?*` と制御文字）を `_` に替えたとき
  - 末尾の空白と `.` を取り除いたとき、Windows の予約名（`CON`、`NUL` など）のとき
  - UTF-8 で 200 バイト（`.html` と接尾辞を含む）を超えたので切り詰めたとき
  - 大文字と小文字だけが違う出力が衝突したとき（衝突した全員に付ける）

| Wiki | ページ | 名前を変えたページ | 最も長い要素 |
| --- | --- | --- | --- |
| 試験用 | 8 | 1（96 文字、288 バイトの名前を 200 バイトに切り詰めた） | 200 B |
| 作者の Wiki | 56 | 0 | 77 B |

名前の上限は OS で数え方が違う。NTFS は 1 要素 255 文字（UTF-16）、ext4 と APFS は 255 バイトである。日本語は UTF-8 で 1 文字 3 バイトなので、86 文字を超える名前は Windows では作れても、Linux と macOS では作れない。上限をバイトで数えるのはこのためである。WSL の Ubuntu の Linux 側のファイルシステムで、99 文字（291 バイト）の名前のファイルは `File name too long`（errno 36）で作れず、200 バイトに切り詰めた名前は作れた。

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. 読める名前と、必要なときだけの接尾辞（推す） | URL とファイル名が読める。作者の Wiki ではすべて読める名前のまま。接尾辞は識別子だけから決まるので、ページを足してもほかのページの名前は変わらない | 大文字と小文字だけが違うページを足すと、すでにあったページの名前にも接尾辞が付き、URL が変わる |
| B. すべて ASCII の ID | OS の間の衝突がない | URL とファイル名が読めない。ファイルを直接開く使い方ができない |

A を推す。大文字と小文字だけが違うページの例外は、lint に検査（仮称 `case_only_duplicates`）を足して、起きにくくする案を推す。NTFS と APFS の既定では、そうした 2 つのファイルは同じフォルダーに置けないので、起きるのは Linux などで作った Wiki だけである。

### 未決 4：RAG への経路

前提の事実:

- rag 0.4.0（6a760b9）の検索の入口は、今も MCP の `search` だけである（`rag_server.py` L150〜166）。この `search` は、子ワーカーに検索を頼み、最大 600 秒まで結果を待つ形のままで、索引も rag が持っている。ADR-0012 の rag の移行（優先順位の文書の 3）は済んでいない。
- wiki の MCP サーバーの `query` は、`collection` を渡すと `index_chunks` で入れたチャンクを検索する。そのときは、呼び出し側が作った語彙のトークン（`query_tokens`）を渡す（`wiki_mcp_server.py` L304〜325）。rag は Sudachi でトークンを作り、wiki のサーバーは Sudachi の辞書を持たない（MCP サーバーの実装の記録）。トークンを渡さなければ、語彙の検索は空になり、意味の検索だけが動く（`wiki_index.py` L680、L1104）。
- wiki の MCP サーバーは、Host が `127.0.0.1:<port>` の要求だけを受け、`allowed_origins=[]` を設定している（`wiki_mcp_server.py` L295）。トークンは `%LOCALAPPDATA%/info-hive/server.json` にだけある。

`mcp_origin_probe.py` で確かめた。wiki 0.6.0 の中継を、作者の環境と別の data_dir で起動し、stdio で `initialize`、`tools/list`、`tools/call`（`list_index`）を送ったあと、`server.json` のポートとトークンで HTTP の要求を直接送った。

| 要求 | 結果 |
| --- | --- |
| 中継経由の `list_index`（アダプタが MCP のクライアントになる経路） | 通った。7 つのツールが見えた |
| Bearer のトークンあり、`Origin` なし | 200 |
| Bearer のトークンあり、`Origin: null`（`file://` のページが送る値） | 403 `Invalid Origin header` |
| Bearer のトークンあり、`Origin: http://127.0.0.1:1`（別のポートのアダプタのページ） | 403 `Invalid Origin header` |
| `Origin: null` の CORS の事前要求（OPTIONS） | 403 |
| トークンなし | 401 |
| Chromium の `file://` のページから、トークンを付けて `fetch` | `TypeError: Failed to fetch` |

ブラウザは、別のオリジンへの `fetch` に必ず `Origin` を付けるので、ページのスクリプトはこのサーバーを呼べない。トークンをページに渡しても変わらない。中継の `initialize` は 24.3 秒、`tools/list`（サーバーの起動を含む）は 30.7 秒かかった。新しい data_dir で依存の確認から始めたためで、MCP サーバーの実装の記録の 1.7 秒、2.4 秒とは条件が違う。

選択肢:

| 案 | 中身 | 判断 |
| --- | --- | --- |
| A. rag に検索の CLI を足す | 画面から CLI を起動する | 採らない。ADR-0012 のあと、モデルと索引は wiki のサーバーが持つので、CLI も結局 wiki のサーバーに頼むことになる |
| B. browse を rag の MCP のクライアントにする | browse が rag の stdio の MCP サーバーを自分で起動する | 採らない。ホストのセッションとは別の rag のサーバーが起動し、ADR-0007 の「接続中だけ動く」子ワーカーと台帳を 2 つのプロセスが扱う |
| C. 常駐の検索サービスを置く | | 採らない。ADR-0007 と ADR-0012 が退けた |
| D. 画面を wiki の MCP サーバーのクライアントにする（ADR-0012 の案） | 画面のスクリプトが `query` を呼ぶ | そのままでは成り立たない。ブラウザのページは接続できない（上の実測）。成り立たせるには、サーバーに CORS とトークンの受け渡しを足すことになり、ADR-0001 と ADR-0012 の防御を弱める |
| D'. アダプタを wiki の MCP サーバーのクライアントにする（推す） | browse のサーバー（Python）とアプリの中核が、`server.json` を読んでサーバーに接続し、`query` を呼ぶ。画面は自分のアダプタ（同じオリジン）にだけ要求する | 推す。browse は wiki のプラグインの中にあるので、`wiki_mcp_common` と中継の起動の処理を使い回せ、プラグインの境界をまたがない |
| E. 中核そのものを MCP のツール（例: ページの HTML を返す）にする | | 採らない。第 1 段階の閲覧が、約 1 GB の依存と約 530 MB のモデルを読み込むサーバーを前提にすることになる |

D' を推す。あわせて次を決める。

- 第 1 段階（ページの表示）は MCP サーバーに依存しない。中核はサーバーを起動せずに動く。検索は能力の宣言で示す。サーバーとアプリは、MCP サーバーに届けば `search: live`、届かなければ `data/search.js` を使う `embedded` に落とす。
- アダプタは、中継と同じく、サーバーが止まっていれば起動し直す。最初の検索は、サーバーの起動（約 2.4 秒）とモデルの読み込み（約 3.6 秒）を待つ（MCP サーバーの実装の記録の測定）。
- rag の PDF の検索は、rag の移行（優先順位の 3）が済んでから足す。移行で、`query(collection=...)` の語彙のトークンを誰が作るかを決める。browse から呼ぶときは、意味の検索だけにする（トークンを渡さない）か、rag が使うトークナイザーを wiki の側でも再現できる形にするかを、そのときに選ぶ。
- 静的版は RAG を持たない（`rag: false`）。

ADR-0007 の見直しは要らなくなる。rag の索引は ADR-0012 で wiki のサーバーに移るので、browse は rag のプロセスに触れない。

### 未決 5：静的版の検索の範囲

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. 題名、要約、タグ、見出しの部分一致（推す） | トークナイザーが要らない（日本語でも `indexOf` で部分一致になる）。PoC で 5 つのブラウザで動いた。作者の Wiki で 13 KB、1,000 ページで約 236 KB | 本文だけにある語では見つからない |

### 未決 6：アプリの技術

ADR-0010 は「アプリを採るときに決める」とし、Linux の WebKitGTK での日本語の描画を分かれ目に挙げた。PoC で、その分かれ目は Tauri を退ける理由にならないと分かった。WebKitGTK 2.52.6 は、禁則の違反が 0 件で、`file://` の読み込み、CSP、ナビゲーション、検索も Windows のエンジンと同じに動いた。

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. Tauri 2（Rust） | 配布物が小さい。独自スキームで同じ HTML を配れる（PoC の 3）。ポートを開かない | OS ごとに WebView が違う（WebView2、WKWebView、WebKitGTK）。字幅が違うので、行の位置はそろわない（禁則の規則は同じに働いた）。Rust のビルドと、OS ごとの署名が要る |
| B. Electron（TypeScript） | Chromium で描画が 3 つの OS でそろう | 配布物が大きい。Chromium の更新に追随する |
| C. pywebview（Python） | 中核と同じ言語で、子プロセスが要らない | Windows では pythonnet と .NET、Linux では Qt か GTK が要る。配布の形が Python の環境に縛られる |
| D. ローカルのサーバーを専用の窓で開くだけの殻 | 実装が最も少ない | ポートを開くので、ADR-0001 の対策がアプリにも要る |

推す案は、今は決めないことである。アプリを作ると決まったとき、A を第一候補にする。理由は、PoC で WebKitGTK の懸念が晴れたこと、独自スキームで同じ HTML が Windows と Linux で動いたこと、配布物が小さいことである。B は、描画を 3 つの OS でそろえることを重く見るときの代わりになる。アプリは別のリポジトリに置き、中核を子プロセスとして呼ぶ、という ADR-0010 の想定は変えない。

### 未決 7：`raw:` の絶対パス（ADR-0013 で生じた）

ADR-0013 で、rag が取り込んだ PDF のソースのページは、`raw:` に PDF の絶対パス（`/` 区切り、例 `C:/Books/x.pdf`）を、`raw_sha256:` に内容の SHA-256 を書くようになった。PDF でないソースは、今も Wiki からの相対パス（作者の Wiki では `../W1_Raw/...`）である。ADR-0013 の影響は、Wiki を公開すると利用者名を含むフォルダーの構成が見えることを挙げている。

PoC（`test.mjs`）で、`raw:` を `file:///` のリンクにしたページを、5 つのブラウザで開いてクリックした。

| ページ | Chromium、Edge、Chrome | Firefox | WebKit |
| --- | --- | --- | --- |
| `file://` のページ | PDF を要求した | 要求は観測されなかった（ブロックかダウンロードの扱いかは確かめていない） | PDF を要求した |
| `http://127.0.0.1` のページ | 拒まれた（`Not allowed to load local resource`） | 拒まれた（`Security Error: ... may not load or link to file:///...`） | 拒まれた（`Not allowed to load local resource`） |

選択肢:

| 案 | 中身 | 判断 |
| --- | --- | --- |
| A. 絶対パスをそのまま出す | どの方式でも全文を表示し、リンクにする | 採らない。サーバーではリンクが動かない。人に渡す書き出しに PC のフォルダーの構成が入る |
| B. 出さない | `raw:` を表示しない | 採らない。手元で読むときに原本の場所が分からない |
| C. 中核は値を解釈して持ち、表示は方式と書き出しの目的で変える（推す） | 下の表 | 推す |

| 方式 | 推す表示 |
| --- | --- |
| サーバー | 絶対パスを文字として表示し、コピーできるようにする。リンクにはしない（ブラウザが開かない。OS にファイルを開かせる API は S-07 と衝突するので作らない） |
| アプリ | サーバーと同じ。開く操作を足すなら、S-07 の「確かめてから OS に渡す」に従う |
| 静的版（既定の書き出し先） | 自分の PC の中だけで見るので、絶対パスを表示し、`file:///` のリンクにする（Chromium 系と WebKit では開ける） |
| 静的版（`--out` で Wiki の外に持ち出す書き出し） | 既定では、ファイル名と `raw_sha256:` の先頭だけを出す。引数（例 `--raw full`）で絶対パスも出せるようにする |

中核の出力では、`raw` を `{kind: "absolute" または "relative", value, sha256}` のように持たせ、表示はアダプタと書き出しの設定で決める。持ち運べる生成物に絶対パスの Wiki のルートを入れない、という ADR-0010 の能力の宣言の規則と同じ扱いになる。相対の `raw:`（`../W1_Raw/...`）は Wiki の外を指すので、どの方式でも文字として表示する。

## ADR-0010 の改訂案で直したこと

状態は「提案」のまま、決定日も「未定」のままにした。

- 背景：2026年11月7日に今の版で事実を確かめ直し、PoC をしたこと、ADR-0012 と ADR-0013 の影響を足した。
- 理由：`clean_link_target()` は 2 か所ではなく 3 か所にある（`wiki_graph_extract.py` L68 が加わった）。ナビゲーションの大きさを実測の値にした。
- 影響：RAG の統合の前提を、rag の設計の変更から、ADR-0012 で決めた rag の移行に改めた。
- 未決の事項：7 件それぞれを、事実、選択肢、推す案、根拠の形に書き直した。7 件目（`raw:` の絶対パス）を足した。
- 見直す条件：PoC の 5 項目に結果を書き、確かめていない部分（macOS、実装のアダプタ）を残した。
- 参照：36a4089 と 6a760b9 の行番号を足した。最初の版の行番号は、確かめた版を添えて残した。

## 承認のあとの作業

ADR-0010 が承認されたら、次の順に進める。browse の実装（`commands/browse.md` など）は、ここから別に始める。

1. 未決 1 の決定に従い、`info-hive-wiki` でページの集合をそろえる。MCP の `query` の評価ゲートを測り直す。
2. `resolve_link()` と `clean_link_target()` を共通のモジュールにまとめる（ADR-0010 の「作る順序」の 1）。
3. 中核、テンプレート、日本語の CSS と、第 1 段階を、`poc/browse/gen.py` を下敷きに作る。`poc/browse/test.mjs` の手順を、実装の試験に移す。
4. 最初のアダプタ（サーバー）を作る。検索の `live` は、未決 4 の決定に従って足す。
