wiki と rag の埋め込みモデル・ベクター DB を統一する

埋め込みモデル 6 種とベクター DB 13 方式の組を、検索スピード、DB の容量、精度の 3 つのスコアで実測して比べた。

1. 要約

wiki と rag の両方を、cl-nagoya/ruri-v3-130m（ONNX fp32）+ usearch（HNSW、f16）+ Tantivy（BM25）にそろえる。 全量 761,915 チャンクで 3 つのスコアがすべて 7 点以上になった組は 2 つあった。この組はそのうち最小の点が最も高い（9.0 点）。 もう 1 つの FAISS IVF_SQ8 + Tantivy（8.8 点）も要件を満たす。2 つの差は 60 問のうちの約 1 問と十数 ms で、実質的に同等である。

採用の規則: 3 つとも 7 点以上
  • 精度を決めるのは語彙検索のエンジンで、速度と容量を決めるのはベクトルの索引である。同じ R-130 の dense でも、LanceDB の全文検索と Qdrant の BM25 は語彙だけの再現率@30 が 0.322 で、Tantivy（IDF を BM25 にそろえたもの）は 0.456 だった。この差がそのまま組の精度の差になった。
  • モデルは Ruri v3 に限られる。e5 系は PDF の質問で現行から 0.05 以上下がる（e5-small 0.700、e5-large 0.758、ruri-v3-130m 0.892）。Ruri v3 は ONNX に書き出せ、torch と同じ出力（cosine ≥ 0.9999998）を torch の半分の時間で出す。wiki も torch を入れずに Ruri を使える。
  • wiki は 127.0.0.1 の MCP サーバーとして常駐させる。今の wiki は検索のたびに uv run --script で起動し、1 回に約 3.1 秒かかる（小さい wiki の複製で測った）。常駐すれば、クエリの埋め込み（21 ms）と DB を合わせて数十 ms で済む。モデルと索引は 1 つのサーバーが持ち、rag はそのサーバーに検索と索引の更新を頼む。
  • Qdrant は全量で最も速い（76.2 ms）が、容量が 5,541 MiB と大きく、BM25 の精度も低い。サーバーのバイナリの配布と起動の管理も要る。sqlite-vec は総当たりなので全量で 3,914 ms かかり、rag の規模に合わない。

2. 目的と要件

info-hive-wiki は fastembed + multilingual-e5-small + sqlite-vec、info-hive-rag は sentence-transformers（torch）+ ruri-v3-130m + LanceDB を使っている。利用者の PC に埋め込みモデルとベクター DB が 2 組ずつ並ぶ。依頼は、どちらかに統一するか、別の方式に移すかを決めることである。

スコア指標閾値（3 点）
検索スピード製品の CPU 実行系でのクエリ埋め込みの p95 + DB の p95（dense 200 件 + 語彙 200 件 + RRF）。CPU 4 スレッド、72 問1 秒
DB の容量ベクトル索引 + 全文索引 + id と世代のディスク容量30 GB × 件数 / 761,915
精度融合した上位 30 件のページ再現率（人手で承認した 60 問）現行（R-130 × LanceDB）− 0.05

点数は、最良の値を 10 点、閾値を 3 点として間を補間し、下限を 1 点とした（速度と容量は対数、精度は直線）。3 つとも 7 点以上の組を採り、なければ最小の点が最も高い組を採る。各 DB のクエリ時のつまみは、厳密解に対する dense の recall@30 が 0.95 に届く最も速い設定に合わせ、同じ取りこぼしの水準で速度を比べた。届かなかった組は「目標未達」とし、採用の判定から外した。

計測は 2 段階で行った。段階 1 では全組を 100,682 チャンクの部分集合で測り、段階 2 では上位の組と現行の組を全量 761,915 チャンクで測った。wiki の MCP 化は必須の要件として、設計を第 13 節に書く（実装は次の作業）。導入の重さは副次の情報として添える。

60 問の正解ラベルは 4 文書から作ったもので、網羅的ではない。1 問の違いは再現率 0.017 にあたり、精度の 1〜2 点の差は 1 問の差と同じ程度でしかない。

4. 候補

埋め込みモデルは e5-small（E-s）、e5-large（E-l）、ruri-v3-30m / 130m / 310m（R-30 / R-130 / R-310）、static-embedding-japanese（S-ja、速度の参考）の 6 種である。ベクター DB は次の 13 方式を、Windows ネイティブ・Python 3.12 で 10,000 件の投入と検索が通ることを確かめてから測った。

  • sqlite-vec（f32、int8、bit + float32 の再スコア）
  • LanceDB IVF_SQ（現行 rag）
  • Qdrant 1.20 サーバー（HNSW の f32、SQ、BQ。BM25 は sparse ベクトル + IDF modifier）、Qdrant のローカルモード
  • usearch（HNSW の f16、i8）
  • FAISS（IVF_SQ8、HNSW）
  • Chroma（HNSW）

全文検索を持たない DB（sqlite-vec、usearch、FAISS、Chroma、Qdrant のローカルモード）は、SQLite FTS5 か Tantivy を語彙側に組み合わせた。どちらも同じ Sudachi の語を使うので、分かち書きの差は入らない。

除外した候補:

  • Milvus Lite: Windows に対応しない
  • Milvus standalone、Weaviate: Windows では Docker か WSL が要る
  • DuckDB VSS、hnswlib: 索引全体を RAM に載せる（japanese-pdf-local-rag-options.md:110）
  • Typesense、Meilisearch: 既存調査の除外理由（同 :108-109）
  • PostgreSQL + pgvector: 別のデータベースサーバーの導入と管理が要り、プラグインの配布に合わない（同 :416）

5. モデルの精度（8,275 チャンク、119 問）

dense は厳密解、語彙は全モデル共通の Sudachi + FTS5 BM25、RRF（k = 60、候補 200 件）で測った。精度の差がモデルだけから出るようにするためである。

6. 実行系（CPU 4 スレッド）

Ruri v3（ModernBERT）は ONNX に書き出せた。onnx-community の fp32 の重みに元のリポジトリのトークナイザーを足すと、torch と同じ出力（cosine ≥ 0.9999998、上位 30 件の一致 1.0）になる。fp16 の ONNX は CPU の ONNX Runtime で読み込めず、int8 は出力が崩れる（R-130 で cosine 0.92、上位 30 件の一致 0.71）。

8. 語彙検索: FTS5 と Tantivy

エンジン部分集合 p95全量 p95全量 最悪全量 容量
SQLite FTS5459 ms5,759 ms40,445 ms1,434 MiB
Tantivy3.3 ms18.8 ms21.8 ms203 MiB

FTS5 は上位 k 件で打ち切る仕組みを持たず、「の」「は」を含む OR の検索で一致したすべての行の BM25 を計算する。全量では p95 が 1 秒の閾値を大きく超えるので、FTS5 を語彙側に使う組は全量で採れない。Tantivy は block-max WAND で打ち切り、全量でも数十 ms で返す。

IDF のそろえ方。Tantivy の IDF は log(1 + (N − n + 0.5) / (n + 0.5)) で常に正なので、頻出語も点を稼ぐ。BM25 と FTS5 の IDF は log((N − n + 0.5) / (n + 0.5)) で、半数以上の行にある語はほぼ 0 になる。語ごとに 2 つの IDF の比を重みとして掛けると、全量の語彙だけの再現率@30 が 0.306（README に記録）から 0.456 に上がり、FTS5 の 0.461 とほぼ同じになった。自由に選べる値はない。頻出語を文書頻度で切る案も試したが、評価の質問で値を選ぶことになるので採らなかった。そろえる前の値でも Tantivy の組は 3 つとも 7 点以上で、判定は変わらない。

usearch と FAISS の選び方

13. wiki の MCP 化の設計（実装は次の作業）

トランスポート

stdio の MCP サーバーは、ホストのセッションごとに起動される。エージェントが 3 つあればモデルが 3 回読み込まれ（R-130 ONNX で約 737 MiB ずつ）、索引の書き手も 3 つになる。そこで、127.0.0.1 の streamable HTTP の MCP サーバーを必要なときに起動し、使われない状態が続いたら止める形を第一候補にする。ADR-0002（/wiki:browse）と同じ形で、実行方式の比較の案 9「MCP とデーモン」にあたる。stdio しか話せないホストのために、HTTP サーバーへ中継する小さな stdio の入口も置く。

形モデルの読み込み判断

置き場所、Claude Code 以外からの起動、同時アクセス

  • 索引は wiki ごとに %LOCALAPPDATA%/info-hive/index/<wiki のハッシュ>/（macOS と Linux は XDG の data ディレクトリ）に置く。ユーザースコープとプロジェクトスコープの wiki はハッシュで分ける。wiki の中の .wiki-cache/ には索引を置かない。
  • サーバーはポートとトークンを %LOCALAPPDATA%/info-hive/server.json に書く。Codex などの CLAUDE_PLUGIN_ROOT を持たないホストは、明示的なパスと wiki ルートの引数で stdio の入口を起動し、入口が HTTP サーバーを見つけるか起動する。
  • 索引の書き手はサーバーだけにする。M5 では、SQLite と Qdrant 以外の DB はどれも、別プロセスで書いた行が開き直すまで見えなかった。usearch は書き込み自体が失敗した。書き手を 1 つにすれば、この問題は起きない。
  • 世代の絞り込みは、取り込みのときに古い世代の行を消して（remove）避ける。検索のたびに generation IN ... を付ける方式は usearch と FAISS では測っていない。

15. ADR 案（確定は別の作業）

ADR 案 A: 埋め込みモデルとベクター DB を wiki と rag で統一する

決定埋め込みは cl-nagoya/ruri-v3-130m を ONNX fp32（ONNX Runtime）で動かす。ベクトル索引は usearch HNSW f16、語彙検索は Sudachi + Tantivy（IDF を BM25 にそろえる）、融合は RRF（k = 60、候補 200 件）とする。wiki と rag は同じ実装を使う。
理由全量で 3 つのスコアがすべて 7 点以上（9.4 / 9.0 / 10.0）。現行の rag より検索が 2.9 倍速く、容量は 3.5 分の 1 で、精度は同等以上。torch が要らなくなる。
代替FAISS IVF_SQ8 + Tantivy（同等の点）。Qdrant（速度は最良、容量とサーバー管理が重い）。
見直す条件評価の質問を増やして精度の差が逆転する。usearch の Windows での保存が単一の書き手でも安定しない。wiki の規模で R-130 の再埋め込みの時間が受け入れられない。

ADR 案 B: wiki は MCP サーバーを持ち、モデルと索引を 1 つにする

決定wiki は 127.0.0.1 の streamable HTTP の MCP サーバーを必要なときに起動する。サーバーはモデルと索引の唯一の持ち主で、rag は MCP でサーバーに検索と索引の更新を頼む。stdio の入口を併せて置く。
理由他のエージェントから wiki を問い合わせ、操作できるようにする（必須の要件）。今の CLI の検索 1 回約 3.1 秒が数十 ms になる。モデルの二重読み込みと索引の書き手の競合がなくなる。ADR-0007 で未決だった「モデルの保持と共有」を決める。
影響rag の MCP サーバーは索引を持たず、PDF の抽出、OCR、チャンク化、ジョブの管理に絞る。ADR-0001 の 3 条件（127.0.0.1 への固定、トークン、書き込み API の制限）を守る。
