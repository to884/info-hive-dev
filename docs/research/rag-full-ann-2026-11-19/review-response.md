# レビュー 1 の照合と対応

- 停止後の未完了状態の検査不足は確認した。停止後のジョブの段階、進捗、pending、テーブルの版と索引統計を照合する。未コミット、部分コミット、コミット後かつ記録前の中断を分け、再開後の history と保存済みベクトルのハッシュ・埋め込みカーソルも比較する。
- 検証手順の途中終了でチェックが欠ける欠陥は確認した。必須の検査名を明示し、検証ドライバーと最終集計の両方で全件を必須にする。証跡がないまま検証ジョブの印だけが残った場合は停止する。この偽陽性を捕捉する回帰試験も追加した。
- 公開直後の旧世代の残留は、実 LanceDB の 4 行の表で再現した。修正前は再開後も旧行が 4 行残った。`cleanup-before-fix.log` が根拠である。公開と同じ SQLite トランザクションに後始末の対象を残し、完了後に対象を消す形へ修正した。公開後の停止、通常の後始末の失敗、元の内容の再公開の 3 ケースを回帰試験にした。修正後の既存試験と合わせた 70 件が Windows で通過した。
- 全量の差し替え試験では、通常の実 MCP にテスト用の `sitecustomize` を渡し、公開がコミットされた後始末の入口だけで待機する。そこで MCP 親を終了し、旧行が残ること、新版だけが公開されたこと、後始末の台帳が残ることを確認する。フックを外して同じジョブを再開する。
- 旧 embed のプロセスが新しいロックを持たないという指摘は確認した。旧プロセスを終了してから新しい版を起動した。確定済み 79,900 ベクトルの入力の対応とバイナリのハッシュを保存し、再開後に照合する。並行する embed は起動していない。旧 seed と新規の双方から CPU 参照値との照合も行う。
- SQLite の読み取りによる補助ファイルの更新は確認した。データ本体は変わっていない。以後、固定した DB では WAL が空であることを条件に `immutable=1` を使う。動いている prepared.sqlite の読み取りは通常の WAL を読む。
- OCR が起動した場合に元の uv キャッシュを使う経路はコード上で確認した。専用 WORK の uv キャッシュに分けた。対象のテキストだけの 2 原本は、オフラインや recall の属性を持たないことを読み込み前に確認している。スクリプトにも属性による拒否を加えた。
- OCR 検索で本文の照合が不足していた点は確認した。返された本文、原本の場所、出典ページを照合する。さらに語彙検索を通さない ANN と全件走査を既知ベクトルで比較する。nprobes=128 を計画と報告に明記する。
- 起動経路と対象の版の記述不足は確認した。固定コミットは v0.5.3 より 5 コミット先であり、今回の後始末の修正を加えた状態として扱う。製品 stdio MCP の入口を準備済み Python から起動する。Windows のパッケージの版は `environment-windows.json` に保存した。
- OCR との互換性は、0.5.0 の固定スクリプトの `extract_pages` と `chunks_for` の AST が、現在の関数と一致することで確認した。今回の製品修正前後でも、PDF 読み込みから埋め込み保存までの AST、埋め込み、語彙処理、LanceDB のスキーマが同一であることを確認した。`index-fix-adoption.json` にハッシュを保存した。

## レビュー 2 の反例と修正

後始末を保留した文書 A を再登録し、埋め込みの途中で止め、別文書 C を公開すると、後始末が A の行を消しても埋め込みカーソルが残る反例を確認した。
修正前は A の再開後に 4 行中 3 行しか公開されなかった。
根拠は `retirement-cursor-before-fix.log` にある。

行の削除前に既知の全世代のカーソルを無効にし、コミットする順序に変えた。
また、同じ文書を再登録するときは、新しいカーソルを作る前にその文書の後始末を終える。
索引全体のリセット時にも、行の消失と後始末の台帳を整合させた。
5 件の実 LanceDB による回帰試験と、Windows・Linux の各 75 件の試験で確認した。

## レビュー 3 の判定と残る制約

Opus 5.5 の 3 回目の敵対的レビューは `APPROVED` だった。
Critical と Major はなく、次の Minor 2 件が残る。

- 退役した文書を再登録する経路では、冒頭の後始末が抽出キャッシュを消すため、OCR を再実行する場合がある。
- 後始末を保留した状態で索引をリセットすると、退役文書の未使用の抽出キャッシュが残る場合がある。

どちらも今回の全量 ANN 試験とは別のキャッシュ管理の制約として残した。
全量試験中の製品コードは固定し、これらを未検証のまま修正して混在させていない。
レビュー本文と、実行結果の照合は `opus-review-2.md`、`opus-review-3.md`、`index-fix-adoption-log.json` を参照。

## 最終読み取り監査のレビュー

小ファイルの読み取りを 4 スレッドへ変えた後、別の式で作った全体ハッシュを比較していた誤りをレビューで確認した。
`prepare.py` の `documents_digest` は文書台帳全体の JSON をハッシュ化した値であり、抽出結果のハッシュを文書順につないだ値とは異なる。
指摘どおり、このままでは正常なデータも最終監査で失敗するため、誤りのある読み取り監査だけを終了した。
完了済みの MCP 試験と製品コードは変更していない。

台帳は準備時と同じ JSON の式でハッシュ化し、ファイルは文書ごとの保存ハッシュと照合する形へ直した。
ファイルの全体ハッシュは別項目で記録する。
文書ごとの OCR・空ページ数、ページ番号、document.md の存在、全体の空ページ数も照合する。
`audit-formula-preflight.json` で実 DB の台帳の式が準備時と一致することを、全ページを読み直す前に確認した。
この修正により、台帳の同一性と各ファイルの同一性を別々に検査する。
結果は `opus-review-audit.md` と `opus-review-audit-fixed.md` に残す。
修正後の監査は再レビューで `APPROVED` となり、2026年11月20日 00:12 に全ページの実行も成功した。
`integrity-audit.json` が文書台帳と各ファイルの照合、79,900 ベクトルの再開後の一致を示す。
