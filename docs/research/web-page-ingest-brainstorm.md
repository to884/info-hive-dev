# Web ページの取り込み方法の検討（発散と収束）

作成日：2026年11月3日
対象：wiki プラグイン（`info-hive-wiki`）の `/wiki:ingest`
方法：brainstorm-diverge-converge スキル。案を出し切ってから（発散）、まとめて（クラスタ）、基準で選ぶ（収束）
状態：検討の結果を要件定義書と ADR-0004、ADR-0005 に反映した。実装は別のタスクで行う

## 1. 問題の設定

### 何を決めるか

`/wiki:ingest` は引数に URL を受け付けるが（`commands/ingest.md` L3）、Web ページを取りに行く手順、HTML から Markdown への変換、翻訳、画像の扱いはどこにも書かれていない。今の指示は「Obsidian Web Clipper の出力が理想」と言うだけで（`references/ingest-workflow.md` L19）、ユーザーが手で Markdown を用意する前提になっている。画像は「内容上欠かせないものだけを読む」とあるだけで（同 L33）、wiki に残す手段はない。wiki の記事に図を入れる決まりもない。

この検討では、Web ページを `raw/` に取り込み、`wiki/` の記事を書くまでの各段階について、どの方法を採るかを決める。

### 決まっている制約

次の 8 点はユーザーと決めた。発散の段階でも覆さず、収束の基準「決定との整合」で使う。

| 項目 | 決定 |
| --- | --- |
| frontmatter | 文字列の値は、要素ごとに二重引用符で囲む。日付と数値は囲まない |
| raw/ の本文 | HTML の本文（見出し、段落、表、コード）を Markdown に変えて保存する。ナビや広告は除く |
| 翻訳 | 日本語でないページは日本語に訳し、raw/ には訳文だけを置く。原文は保存しない |
| 原本の記録 | 訳文の先頭に URL、取得日時、原文 HTML の SHA-256、翻訳したモデル名を記録する。要件 F-I03 をこれに合わせて改める |
| 画像 | 画像があれば取り込み、画像の直後に `> Claude Fable 5.1 補足: …` の形で図の説明を書く。モデル名は表示名で書く。説明は、あとで別の LLM が読んで内容が分かるように書く |
| wiki/ の図 | 図表で説明できるときは図表を足し、同じ形式で説明を添える。図は mermaid のコードブロックで本文に書き、mermaid で描けないものだけ `wiki/assets/*.svg` に置いて `![説明](assets/x.svg)` で参照する。png は使わない |
| 取得の手段 | プラグインに Python スクリプトを足す案と、エージェントのツールだけで行う案を、この文書で比べて決める |
| 成果物 | この文書、要件定義書の追記、ADR。実装はしない |

### 評価の基準

| 基準 | 重み | 何を見るか |
| --- | --- | --- |
| 決定と要件との整合 | 3 | 上の 8 点と、要件定義書の F-I*、§7、S-01 に合うか |
| 実装のしやすさ | 2 | スクリプトは標準ライブラリを優先する決まり（`CONTRIBUTING.md` L33）。依存パッケージは `uv run --script` で固定した既存の仕組みに乗せられるか |
| 日本語の品質 | 2 | 訳文と説明が、あとで別の LLM と人が読んで内容を取り違えないか |
| 検索と lint への影響の小ささ | 1 | 索引に雑音が入らないか。lint の既存の指摘を誤らせないか |
| エージェントが違っても同じ結果になるか | 1 | D-01 は Claude Code だけを使うと決めている。ただしスキルは他のエージェントでも動くので、差が出にくいほうを高くする |

点は 1〜10 で付け、重みをかけて合計する。満点は 90。

## 2. 発散：出した案

判断を保留して、小問題ごとに案を並べた。番号は通し番号である。

### 取得の手段

1. Claude Code の WebFetch でページを読み、モデルが Markdown に書き起こす
2. Claude Code のブラウザのツール（built-in browser）でページを開き、`get_page_text` の結果をモデルが整える
3. 標準ライブラリの `urllib.request` で HTML を取る Python スクリプト `wiki_fetch.py` を足す
4. `uv run --script` で `trafilatura` を固定して、本文抽出と Markdown 化まで行う
5. `uv run --script` で `readability-lxml` と `markdownify` を固定して使う
6. ユーザーが Obsidian Web Clipper で保存した Markdown を受け取る（今の指示のまま）
7. スクリプトで取り、JavaScript で描画されるページだけブラウザのツールに切り替える
8. `curl` や `wget` を子プロセスで呼ぶ
9. 取得は WebFetch、画像のダウンロードとハッシュだけスクリプトで行う

### 本文の抽出と Markdown への変換

10. 標準ライブラリの `html.parser` で、`<article>`・`<main>` を優先し、`nav`・`footer`・`aside`・`script`・`style` を捨てる自前の変換器を書く
11. 文字数と段落の密度で本文の塊を推定する（readability の考え方を自前で簡略に実装する）
12. モデルが HTML をそのまま読んで Markdown を書く
13. スクリプトで粗く Markdown にし、残った雑音（共有ボタン、関連記事）をモデルが削る
14. 表は Markdown の表に、表にできない複雑な表は HTML のまま残す
15. コードブロックは言語名を `class` から拾ってフェンスに付ける
16. 見出しの階層を保ち、`<h1>` はページの題名として frontmatter に移す
17. リンクは絶対 URL に直して残す
18. 脚注・注釈は本文の末尾にまとめる

### 翻訳

19. モデルが段落ごとに訳し、見出し・コードブロック・URL・識別子は変えない
20. 文書全体を一度に訳す
21. 固有名詞と識別子は英語のまま残し、初出に短い訳語を添える（`page-conventions.md` の題名の決まりに合わせる）
22. 専門用語の対訳表を wiki の `concepts/` に持ち、訳のぶれを減らす
23. 訳文の先頭に「訳したモデル名」を書き、人が訳した文と区別できるようにする
24. ページの言語は、スクリプトが `<html lang>` と日本語の文字の割合を報告し、モデルが最終的に決める
25. 日本語と英語が混ざるページは、英語の部分だけ訳す
26. 訳文と原文を 1 ファイルに並べる（決定に反する。比較のために残す）

### 画像の取り込みと説明

27. 本文の中の画像だけを `raw/assets/<ソースのスラッグ>/` にダウンロードし、元の拡張子を保つ
28. ファイル名は `<スラッグ>-01.png` のように出現順の連番にする
29. 元の URL を Markdown の title 属性に残す（`![alt](assets/x/x-01.png "https://…")`）
30. 32px 以下の画像、`data:` の URI、トラッキング用の画像は捨てる
31. 装飾の画像（著者のアイコン、ロゴ）はモデルが判断して捨て、捨てたことを raw に書かない
32. 画像の直後に `> Claude Fable 5.1 補足: ` を付けた説明を書く。説明は、何の図か、軸や凡例、読み取れる数値、本文との関係を 2〜5 文で書く
33. 元の alt テキストが意味のある説明なら、それも訳して説明に含める
34. グラフの数値は OCR で抜き出す
35. 画像のダウンロードに失敗したら、元の URL と「未取得」を書き、説明は書かない
36. Web 上の svg は raw/assets に保存するだけにし、wiki/ には写さない（S-01）

### 出所の記録と再取り込み

37. raw の Markdown の先頭に frontmatter を置き、`url`、`title`、`fetched_at`、`source_sha256`、`source_lang`、`translated_by`、`fetched_by` を書く
38. frontmatter の代わりに、本文の先頭に表で書く
39. 出所は wiki のソースページの `x_wiki.provenance` にだけ書く
40. ハッシュは取得した原文 HTML に対して取る。訳文に対しては取らない
41. 再取り込みのときは `source_sha256` を比べ、同じなら何もしない。違えば `<スラッグ>-<YYYYMMDD>.md` を別版として置く（F-I08）
42. ブラウザのツールで取ったページは、描画後の DOM の文字列に対するハッシュである旨を `source_sha256_of` に書く

### wiki の図表

43. 流れ、順序、状態、関係は mermaid（flowchart、sequenceDiagram、stateDiagram、erDiagram、classDiagram、timeline）で本文に書く
44. 比較は Markdown の表で書く
45. mermaid で描けない配置の図（アーキテクチャの箱の並びなど）だけ、モデルが svg を手で書いて `wiki/assets/<ページのスラッグ>-<n>.svg` に置く
46. 図表の直後に `> Claude Fable 5.1 補足: ` の説明を置き、図を見ずに内容が分かるようにする
47. svg は Web から写さない。モデルが描いたものに限る
48. 図の文字は日本語で書き、識別子だけ英語にする
49. mermaid のブロックと画像の行は、ページのサイズの判定から除く
50. `/wiki:browse` で mermaid を描く（mermaid.js の同梱）と `wiki/assets/` の配信は、将来の作業として ADR-0002 の第一段階から外しておく

### frontmatter の引用符の徹底

51. `page-conventions.md` に「文字列は要素ごとに二重引用符で囲む。日付と数値は囲まない」と書く
52. `wiki_lint.py` に、引用符のない文字列を指摘する `unquoted_string` を足す
53. 手書きのパーサー（`wiki_lint.py`、`wiki_search.py`）を、引用符の中のカンマで分けないように直し、行末のコメントを捨てる
54. テンプレートと `wiki_evolve_loop.py` の書き手を、引用符つきに直す
55. 評価用コーパスの既存ページを、スクリプトで一括して引用符つきに直す
56. 引用符の有無を lint で指摘するだけにし、パーサーは直さない

**出した案の数**: 56

## 4. 収束：採点と選択

クラスタごとに、競合する案だけを採点した。互いに補い合う案（たとえば 15 と 16）は採点せず、選んだ案の中に含めた。点は「決定と要件との整合（×3）、実装のしやすさ（×2）、日本語の品質（×2）、検索と lint への影響（×1）、エージェントが違っても同じか（×1）」の順である。

### A. 取得の手段

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 3. `urllib` のスクリプト | 9 | 8 | 7 | 8 | 9 | 74 |
| 7. スクリプトを基本にし、描画が要るページだけブラウザのツール | 9 | 7 | 7 | 8 | 7 | 70 |
| 1. WebFetch だけ | 4 | 9 | 6 | 7 | 3 | 52 |
| 2. ブラウザのツールだけ | 5 | 8 | 6 | 7 | 3 | 54 |
| 4. `trafilatura` を固定 | 8 | 5 | 8 | 8 | 9 | 67 |
| 9. 取得は WebFetch、画像とハッシュはスクリプト | 6 | 6 | 6 | 7 | 4 | 53 |

点の理由は次のとおり。

- WebFetch は、取得した HTML そのものを返さない。小さなモデルが要約した結果を返すので、原文 HTML の SHA-256 を取れず、画像もダウンロードできない。決定「原本の記録」と「画像の取り込み」に合わないので、整合を 4 にした。ブラウザのツールも、ページの文字列は取れるが、ファイルを保存する手段がない。
- どちらのツールも Claude Code にしかない。D-01 は Claude Code だけを使うと決めているので致命的ではないが、Codex や Cursor でスキルを使う人は手順を再現できない。
- `trafilatura` は本文抽出の品質が高いが、依存が大きく、新しい補助の処理は標準ライブラリを優先する決まりに合わない。実装を 5 にした。
- 案 7 は、JavaScript で描画されるページへの備えとして価値があるが、2 つの経路ができるので、取得のたびにどちらを使ったかを記録する必要がある。第一段階では案 3 だけにし、案 7 は「スクリプトが本文を取れなかったときの手順」として `ingest-workflow.md` に書く。

**選んだ案**: 3。標準ライブラリの `urllib.request` と `hashlib` で HTML を取り、SHA-256 を計算し、画像をダウンロードする `wiki_fetch.py` をプラグインに足す。描画が要るページは案 7 の手順で補う。

案 7 でブラウザを使うときは、ユーザーがふだん使っているブラウザを使う（ユーザーの指示、2026-11-03）。認証情報がそこに入っているので、ログインが要るページも取れる。ツールが用意する別のブラウザは使わない。Playwright などをスクリプトに足す場合も、そのブラウザのプロファイルにつなぐ方法を確かめる（O-15）。

### B. 本文の抽出と変換

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 13. スクリプトで粗く変換し、残った雑音をモデルが削る | 9 | 7 | 8 | 8 | 7 | 72 |
| 10. `html.parser` の自前変換だけ | 8 | 7 | 6 | 7 | 9 | 66 |
| 12. モデルが HTML を読んで書く | 7 | 9 | 7 | 7 | 4 | 64 |
| 5. `readability-lxml` と `markdownify` を固定 | 8 | 5 | 8 | 8 | 9 | 67 |

- 自前の変換器だけでは、サイトごとの作りの違い（共有ボタン、関連記事、クッキーの案内）を取り切れない。モデルが最後に見ることで、日本語の品質を保てる。
- モデルが HTML を直接読む案は、トークンを多く使い、ページごとに結果がぶれる。
- 案 14〜18 は、選んだ案の変換器が守る規則として取り込む。

**選んだ案**: 13。`wiki_fetch.py` は `html.parser` で `<article>`・`<main>` を優先して本文を取り、`nav`・`header`・`footer`・`aside`・`script`・`style`・`noscript` を捨て、見出し・段落・リスト・表・コードブロック・リンク・画像を Markdown にする。`<h1>` は frontmatter の `title` に移す。モデルは、残った雑音を削ってから翻訳に進む。

### C. 翻訳

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 19. 段落ごとに訳し、見出し・コード・URL・識別子は変えない | 9 | 8 | 8 | 8 | 7 | 74 |
| 20. 全体を一度に訳す | 8 | 9 | 6 | 8 | 6 | 68 |
| 26. 原文と訳文を 1 ファイルに並べる | 2 | 8 | 5 | 4 | 7 | 43 |

- 段落ごとに訳すと、構造が崩れず、長いページでも 25% のコンテキストの上限（`commands/ingest.md` L16）を守れる。
- 案 21（固有名詞は英語のまま、初出に訳語）、23（訳したモデル名を記録）、24（言語の判定はスクリプトが材料を出し、モデルが決める）、25（混在ページは英語の部分だけ訳す）は、選んだ案の規則として取り込む。案 22 の対訳表は、wiki が育ってから考える。

**選んだ案**: 19。訳文の規則は `page-conventions.md` の題名と引用の決まりに合わせる。見出し、コードブロック、URL、識別子、固有名詞の英語表記は変えない。

### D. 画像の取り込みと説明

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 27〜32 の組み合わせ（本文の画像を連番で保存、title 属性に元 URL、小さい画像は捨てる、直後に補足） | 9 | 7 | 8 | 7 | 7 | 72 |
| 34. OCR で数値を抜く | 5 | 3 | 7 | 7 | 5 | 47 |
| 画像を保存せず、説明だけ書く | 3 | 9 | 6 | 8 | 7 | 54 |

- 決定は「画像があれば取り込む」なので、保存しない案は整合が低い。
- OCR は依存が大きく、グラフの数値はモデルが画像を見て説明に書けば足りる。
- 装飾の画像（案 31）は、スクリプトが本文の外にあるものと小さいものを捨て、残った中の装飾はモデルが判断して捨てる。捨てた画像のことは raw に書かない。
- 説明の書き方（案 32、33）は要件に書く。何の図か、軸や凡例、読み取れる数値、本文との関係を 2〜5 文で書き、元の alt テキストが意味を持つなら訳して含める。

**選んだ案**: 27〜33 と 35、36 の組み合わせ。

### E. 出所の記録と再取り込み

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 37. raw の先頭に frontmatter | 9 | 8 | 7 | 7 | 9 | 73 |
| 38. 本文の先頭に表 | 7 | 8 | 7 | 7 | 8 | 66 |
| 39. ソースページの `x_wiki.provenance` にだけ書く | 5 | 6 | 7 | 7 | 8 | 56 |

- raw の Markdown に frontmatter を置けば、再取り込みのときにスクリプトが `source_sha256` を読んで比べられる（案 41、F-I08）。表では機械で読みにくい。
- ソースページにだけ書くと、raw のファイルだけを見たときに出所が分からない。
- raw は lint の対象外なので（`wiki_lint.py` L107〜108）、frontmatter を置いても lint の指摘は増えない。Foam には `RAW_ROOT` を索引から除く設定が要るが、これは要件 §3.3 にすでにある。
- 案 40（ハッシュは原文 HTML に対して取る）と 42（ブラウザのツールで取ったときは、何に対するハッシュかを書く）は、選んだ案の項目に含める。

**選んだ案**: 37。キーは英語で、文字列の値は二重引用符で囲む。

```yaml
---
url: "https://example.com/articles/attention"
title: "Attention Is All You Need"
fetched_at: "2026-11-03T10:15:00+09:00"
source_sha256: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
source_sha256_of: "html"
source_lang: "en"
translated_by: "Claude Fable 5.1"
fetched_by: "wiki_fetch.py 0.1"
---
```

`fetched_at` は日時を含むので、日付だけの `created` と違い、文字列として引用符で囲む。

### F. wiki の図表

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 43〜48 の組み合わせ（mermaid を本文に、svg は assets に、直後に補足、文字は日本語） | 9 | 7 | 8 | 6 | 8 | 71 |
| mermaid だけ | 7 | 8 | 7 | 7 | 8 | 66 |
| svg だけ | 6 | 6 | 7 | 7 | 7 | 58 |

- 決定は「mermaid を本文に、svg は別ファイル」なので、組み合わせの案が整合で勝る。
- 検索と lint への影響は、どの案でも残る。mermaid のソースは索引に入り（`wiki_search.py` L360〜399）、ページのサイズに数えられる（`wiki_lint.py` L182、L192）。案 49（サイズの判定から除く）は、実装への影響として挙げる。
- `/wiki:browse` では今の設計では表示されない（ADR-0002 は生の HTML を出力せず、`wiki/assets/` を配信しない）。案 50 のとおり、将来の作業として要件に書き添える。

**選んだ案**: 43〜48 の組み合わせ。

図を描く手段について、ユーザーから補足があった（2026-11-03）。図を作るときは、まず利用できるスキルの一覧を見て、図表を作るスキルがあれば用途に合うものを使い、なければモデルが mermaid か svg を直接書く。プラグインは外部のスキルに依存しないので、手順にスキル名は書かない。スキルの出力は、選んだ形式に変換して説明を添える。確実に特定のスキルを使わせたいときは、wiki を置くプロジェクトの `CLAUDE.md` にスキル名を書く（F-W07）。

### G. frontmatter の引用符

| 案 | 整合 | 実装 | 日本語 | 検索・lint | 同じ結果 | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 51〜55 の組み合わせ（決まりを書き、lint で指摘し、パーサーと書き手を直し、既存ページも直す） | 9 | 6 | 8 | 9 | 9 | 73 |
| 56. lint で指摘するだけ | 7 | 9 | 8 | 5 | 9 | 66 |

- パーサーを直さないと、`authors: ["Smith, J."]` が 2 要素に分かれるままで、引用符を標準にした意味が薄れる。
- 既存ページ（評価用コーパス）を直さないと、lint の新しい指摘が最初から大量に出て、本当の問題が埋もれる。

**選んだ案**: 51〜55 の組み合わせ。
