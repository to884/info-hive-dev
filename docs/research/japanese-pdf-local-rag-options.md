## 1. 結論の要約

1. **最初に決めるべき数値は「PDF 容量あたりのテキスト量」である。** 100GB の PDF から取れるテキストが 5GB（5%）なら、方針書どおりの構成でも 10〜30GB に収まる。20GB（20%）なら、方針書の構成は約 110GB になり要件を大きく超える（第3節）。PDF の容量とテキスト量は比例しないため、サンプルでの実測が必須である。
2. **方針書の構成要素のうち、CPU で 1 秒の要件を最も脅かすのはリランカー bge-reranker-v2-m3 である（推定）。** 日本語ベンチマークでも、より小さい日本語特化リランカーに負けている。製品は GPU がなくても動く必要があるので、CPU で速い japanese-reranker-xsmall-v2 への置き換えを提案する。
3. **埋め込みモデルは bge-m3 より Ruri v3 130m（512 次元）が要件に合う。** JMTEB v2 の検索スコアが bge-m3 より高く、次元が半分なので容量とメモリも小さい。ライセンスは Apache-2.0 である。ただし CPU だけでは、130m での全量の埋め込みに数日から数週間かかりうる（推定）。構築時間は PC の性能とテキスト比率で大きく変わるので、製品では埋め込みモデルを設定で選べるようにし、構築を始める前に所要時間の見積もりを示す。既定のモデルは PoC の結果で決める。検証環境（8 コアの Ryzen 7 3800XT）の試算では、テキスト比率がおよそ 3% 以下なら 130m、8% 程度までなら 70m が、1 週間の目標に収まる（第6.7節）。
4. **3 層のハード絞り込み（上位 50 文書に限定）は、L1 で取りこぼした文書を回復できない。** L1 は加点に使い、L2 は全チャンクをハイブリッド検索する 2 層構成を提案する。L1 の要約は LLM で生成せず、見出し・目次・冒頭文や info-hive の source ページから作る。
5. **融合は線形重み（BM25 70：Vector 30）より RRF（順位融合）を標準にする。** スコアの尺度合わせが不要で、重みの調整対象が減る。
6. **索引基盤は、組み込み型の LanceDB を第一候補、Qdrant を次点とし、両方を PoC で比べる。** Qdrant は機能が最も揃うが、別プロセスの運用が要る。また、大規模時のディスク再スコアは Linux 前提の資料しかない。
7. **方針書の GraphRAG 不採用と、検索経路から Agent を外す方針は、採点でも支持される。**
8. **回答の生成は Claude Code だけで行い、機密モードは設けない（2026年11月2日にユーザーが決定）。** ローカル LLM が要らないので、16GB の予算をすべて検索に使える。検索結果の上位チャンクの本文は、Claude Code を通じて PC の外へ送られる。外に送れない文書は、索引に入れないことで扱う（第7.1節）。
9. **製品は GPU がなくても動くようにし、PC 固有の仕様は決めない（2026年11月2〜3日にユーザーが決定）。** info-hive は他の PC でも動くプラグインなので、CPU の性能、ドライブの構成、原資料の場所は PC ごとに違う。これらは設定と既定値で扱い、この PC（検証環境）の値は PoC の見積もりと判定にだけ使う（第2.2節）。GPU を前提にした構成 C は既定にしない。検索の 1 秒の要件は CPU 前提で試算済みなので変わらない。影響が大きいのは、索引の構築時間である（第6.7節）。
10. **商用で利用する（同日にユーザーが決定）。** 非商用ライセンスの sarashina、jina、YomiToku などは候補から外した。推奨構成の部品は商用で使えるライセンスを選んだ。ライセンスの確認結果は第2.5節にまとめた。Lindera の辞書はすべて商用で使える。NDLOCR-Lite の学習済みモデルは DINOv3 License の用途制限を受けるが、利用者は制限の対象に当たらない（2026年11月3日にユーザーが確認）。縦書きとスキャンの標準 OCR として使い、モデルはプラグインに同梱せず初回利用時に公式リポジトリから取得する。PDF のテキスト抽出は、AGPL の PyMuPDF に代えて pypdfium2 を第一候補にする。
11. **PDF を 1 件ずつ手で取り込む場合は、索引に追記して更新する。** 1 件あたりの処理は数十秒から 1 分程度の見込みで、初回構築にかかる時間の制約は事実上なくなる（推定）。代わりに、索引への反映、索引の作り直し、古い版の削除という保守の処理がときどき要る。埋め込みモデルを後から替えると全文書の埋め込み直しになるので、最初に慎重に決める（第6.8節）。
12. **原資料は移動も複製もせず、参照先を記録する（2026年11月3日にユーザーが決定）。** 原資料のフォルダ（ルート）は利用者が設定し、索引には PDF の内容ハッシュと、ルートからの相対パスを記録する。検証環境のルートは My eBooks で、PDF が 922 件、98.2GB ある。1 件の平均が 109MB と大きいので、スキャンした書籍や雑誌が多いとみられ、構築時間の大半を OCR が占める可能性がある（推定）。原資料を複製しないので、要件定義書の原資料の保存に関する記述と食い違う（第6.9節）。
13. **原資料が遅い場所にあっても動くようにする。** 検証環境では、原資料のある D ドライブが USB 接続の外付け RAID 0 で、順次読み込みは毎秒約 19MB だった（2026年11月3日にユーザーが指摘）。製品では、派生データの保存先を原資料と別に設定でき、検索のときは原資料を読まない。PDF は先頭から 1 回だけ順に読んでメモリに載せ、解析はメモリ上で行う。検証環境では、派生データを C ドライブの NVMe SSD に置き、全 PDF を読む時間は約 1.5 時間と見込む（第6.9節）。

推奨構成は第6.6節の「構成 B（組み込み・軽量）」である。次の作業は第7節の PoC 計測である。

## 2. 問題定義と評価基準

### 2.1 問題

約 100GB の日本語 PDF を、ローカル PC 上で検索できるようにする。info-hive は Markdown を正本とし、索引を再生成可能な派生データとして扱う（要件定義書 第3.3節）。この前提に合う検索方式を選ぶ。

**判断対象**：方針書の各構成要素を維持するか、代替案に置き換えるか。代替案のうち、PoC で計測する候補を 2〜3 構成に絞る。

### 2.3 評価基準

各選択肢を 1〜10 点で採点し、重みを掛けて合計する（満点 160）。

| 基準 | 重み | 定義 |
| --- | --- | --- |
| 速度 | 3 | ウォーム状態で検索応答 1 秒以内に収まる見込み。取り込み系の軸では索引構築のスループットとして読む |
| メモリ | 3 | 検索時の常駐メモリの小ささ |
| 容量 | 2 | ディスク上の索引の小ささ |
| 精度 | 3 | 日本語検索の品質。JMTEB v2・JQaRA・JaCWIR・MIRACL-ja の公開値を優先し、ない場合は仕組みから判断する |
| 運用 | 2 | Windows ネイティブで動くか、依存の軽さ、CPU のみで成立するか、ライセンス、構築の手間 |
| 拡張 | 1 | 100GB から数倍への増加や、Web・コードなど他形式への流用のしやすさ |
| 統合 | 2 | info-hive との適合。Markdown 正本から再生成できるか、Claude Code だけで運用できるか、プラグインとして配布できるか |

その軸の性能に影響しない基準は 5 点（中立）とした。

### 2.4 必須条件による除外

採点の前に、次の条件を満たさない候補を除外した。

| 除外した候補 | 理由 |
| --- | --- |
| クラウド API の埋め込み・OCR（Azure Document Intelligence、Google Document AI など） | ローカル運用の要件に反する |
| Nougat | 公式 FAQ で日本語非対応と明記 |
| olmOCR | VRAM 12GB 以上が必要で、8GB GPU では動かない |
| Typesense | 索引を全件 RAM に置く。Windows は WSL のみ |
| Meilisearch | BM25 ではなく独自の順位付け規則を使い、ハイブリッドの融合設計と合わない |
| DuckDB VSS、hnswlib | 索引全体を RAM に載せる必要があり、数百万件以上では 16GB と両立しにくい |
| Chroma（ローカル版） | 疎ベクトル・BM25・RRF の検索 API がクラウド限定 |

商用で利用すると決まったので、次の候補も除外した。

| 除外した候補 | ライセンス |
| --- | --- |
| sarashina-embedding v1/v2、comsat-embed-ja | 非商用 |
| jina-embeddings v3〜v5、jina-reranker v2/v3 | CC BY-NC など非商用 |
| YomiToku | CC BY-NC-SA 4.0。商用には有償の Pro ライセンスが要る |
| marker / surya の重み | 改変 OpenRAIL-M。無償で使えるのは収益 500 万ドル未満などの条件を満たす場合に限る |

PyMuPDF（AGPL-3.0）と poppler（GPL）は、商用のプラグインに組み込むと、配布物全体にソースコードの提供などの条件がかかる。PyMuPDF は Artifex の商用ライセンスを購入すれば使える。本書は、ライセンス費用をかけない前提で、テキスト層の抽出に pypdfium2（Apache-2.0 または BSD-3）、表の抽出に pdfplumber（MIT）を第一候補にする。PyMuPDF は、PoC で品質と速度を比べる基準としてだけ使う。配布しない社内での比較なので、AGPL の条件はかからない。

- 学習済みモデルはプラグインに同梱せず、初回利用時に国立国会図書館の公式リポジトリから取得する。info-hive が再配布者にならないので、再配布の条件を負わない。Meta がライセンスを改定しても、利用者は取得元で最新の条件を確かめられる。

- CC BY 4.0 に従い、国立国会図書館の表記を配布物と画面に残す。
- 利用者の範囲が変わり、原子力・防衛関連の組織が加わる場合は、この判断を見直す。その場合は PaddleOCR か Tesseract で縦書きを賄う。

## 3. 容量の試算（採点の前提）

### 3.1 仮定

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| UTF-8 の 1 文字あたりバイト数 | 2.6 | 和文 3 バイトと ASCII の混在を仮定 |
| チャンク | 800 字、重なり 150 字（実質 650 字ごと） | 方針書の 500〜1000 字・100〜200 字の中央値 |
| HNSW グラフ | 1 件あたり 154 バイト（m=16） | Qdrant 公式の容量計画の式 |
| BM25 索引 | テキスト量の 0.5〜1.0 倍 | 公開値がないため幅で置いた（推定） |
| PDF に占めるテキストの割合 | 1%〜20% | 公開値なし。PDF の容量の大半は画像と埋め込みフォントで、テキスト量とは比例しない |

### 3.2 テキスト比率ごとの規模

| テキスト比率 | テキスト量 | チャンク数 | 1024 次元 float32 | 1024 次元 int8 | 1024 次元 1bit | 512 次元 float16 | HNSW グラフ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1% | 1GB | 約 60 万 | 2.4GB | 0.6GB | 0.08GB | 0.6GB | 0.09GB |
| 2% | 2GB | 約 120 万 | 4.8GB | 1.2GB | 0.15GB | 1.2GB | 0.18GB |
| 5% | 5GB | 約 300 万 | 12.1GB | 3.0GB | 0.38GB | 3.0GB | 0.46GB |
| 10% | 10GB | 約 590 万 | 24.2GB | 6.1GB | 0.76GB | 6.1GB | 0.91GB |
| 20% | 20GB | 約 1,180 万 | 48.5GB | 12.1GB | 1.51GB | 12.1GB | 1.82GB |

ColBERT 系（トークンごとに 128 次元のベクトルを持つ方式）は、テキスト 5% の場合で float16 なら約 380GB、2 ビットに圧縮しても約 47GB になる（推定。1.3 文字を 1 トークンと仮定）。容量要件と両立しないため、一次検索には使えない。

### 3.3 試算からわかること

- **方針書の量子化の発動条件 A（500 万ベクトル以上）は、テキスト比率が約 8% 未満なら発動しない。** 実際に効く制約はディスク容量で、主な原因は float32 の原ベクトルと、payload に複製したチャンク本文である。
- **本文の複製をやめると容量が大きく減る。** 抽出済み Markdown は info-hive の派生データとして保存するので、索引には文書 ID とオフセットだけを持てばよい（選択肢 86）。
- **テキスト比率 20% の場合は、どの構成でも工夫が要る。** 次元の削減、原ベクトルの int8 保存、BM25 索引の圧縮のいずれかが必要になる。

## 6. 収束：評価と選定

### 6.1 採点の進め方

- C1〜C6 のうち、互いに置き換え可能な選択肢を軸ごとに採点した。軸は C1 を「抽出・OCR」と「チャンク化」に、C5 を「階層・絞り込み」「融合・リランク」「クエリ処理・キャッシュ」に分けた計 10 軸である。
- 補助的な手段（5〜11、14、18、23、26、35、36、43、47、49、77、78）は、どの構成でも採れるので採点せず、第6.6節の構成案に組み込んだ。
- C7（82〜85）は互いに競合する選択肢ではなく、どの構成を選んでも行う検証なので、採点せず第7節の計画に入れた。
- 公開値のない項目は、仕組みから判断した点数である。極端な点数（1〜2、9〜10）の根拠は、各表の下に書いた。

### 6.2 軸別の採点

#### 抽出・OCR（速度は索引構築のスループット）

| 順位 | No. | 選択肢 | 速度 | メモリ | 容量 | 精度 | 運用 | 拡張 | 統合 | 加重合計 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 2 | ページ単位ルーティング（テキスト層＋必要ページだけ日本語 OCR） | 7 | 8 | 8 | 8 | 6 | 8 | 8 | 121 |
| 2 | 1 | 全ページをテキスト層抽出のみ | 9 | 9 | 8 | 4 | 8 | 5 | 7 | 117 |
| 3 | 4' | 全ページを日本語特化 OCR | 2 | 6 | 8 | 6 | 5 | 6 | 7 | 88 |
| 4 | 3 | 全ページを VLM 系パーサで Markdown 化 | 2 | 5 | 8 | 7 | 4 | 7 | 7 | 87 |

- 1 の速度 9：PyMuPDF は 7,031 ページを 8.01 秒で処理する（約 1.1ms/ページ）。精度 4 は、スキャンと縦書きのページを取りこぼすため。
- 3 と 4' の速度 2：OCR や VLM はページあたり秒単位で、100GB 全量では日〜週の単位になる（推定）。3 の精度は、MinerU の日本語の編集距離 0.588 が PaddleOCR-VL の 0.086 より大きく劣ることも踏まえた。
- **選定：2。** 全ページをまず高速に検査し、文字数・CJK 比率・U+FFFD や私用領域の文字の比率・画像の被覆率・縦書きの有無を記録する。その結果で「良好なテキスト層」「文字化け」「スキャン」「縦書き」に分け、後の 3 つだけを OCR に回す。テキスト層の抽出は pypdfium2、表は pdfplumber を使う。OCR は NDLOCR-Lite（CC BY 4.0、CPU で動き、縦書きに対応）を標準にし、横書きの表には PaddleOCR（Apache-2.0）を使う。NDLOCR-Lite の学習済みモデルは同梱せず、初回利用時に公式リポジトリから取得する（第2.5節）。pypdfium2 の速度は公開値がないので、PoC で PyMuPDF と比べて測る。

#### 字句・疎検索

| 順位 | No. | 選択肢 | 速度 | メモリ | 容量 | 精度 | 運用 | 拡張 | 統合 | 加重合計 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 20 | 形態素解析（Sudachi/Lindera）＋BM25 | 8 | 8 | 7 | 6 | 7 | 7 | 7 | 115 |
| 2 | 21 | 文字 bigram＋BM25 | 8 | 7 | 5 | 6 | 8 | 7 | 7 | 110 |
| 3 | 22 | 形態素と bigram の二重フィールド | 7 | 7 | 4 | 7 | 6 | 7 | 7 | 104 |
| 4 | 24 | japanese-splade（学習型疎ベクトル） | 6 | 6 | 6 | 9 | 5 | 6 | 6 | 103 |
| 5 | 27 | SQLite FTS5 trigram | 7 | 8 | 5 | 3 | 9 | 4 | 8 | 102 |
| 6 | 25 | bge-m3 の sparse 出力 | 7 | 6 | 6 | 5 | 7 | 6 | 6 | 98 |

- 24 の精度 9：JQaRA の nDCG@10 は BM25 の 0.458 に対し、japanese-splade-base-v1 は 0.644 である。MIRACL-ja でも 0.369 に対し 0.604 である。
- 27 の精度 3：trigram は 3 文字未満の語（「京都」など）に一致しない。
- 25 の精度 5：JQaRA で 0.509 と、BM25 よりは高いが SPLADE に大きく劣る。

| 順位 | No. | 選択肢 | 速度 | メモリ | 容量 | 精度 | 運用 | 拡張 | 統合 | 加重合計 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 30' | Ruri v3 30m（256 次元） | 9 | 9 | 9 | 6 | 8 | 6 | 7 | 126 |
| 2 | 31 | static-embedding-japanese | 10 | 9 | 9 | 4 | 9 | 6 | 7 | 125 |
| 3 | 30 | Ruri v3 130m（512 次元） | 8 | 8 | 7 | 8 | 8 | 7 | 7 | 123 |
| 4 | 29 | Ruri v3 310m（768 次元） | 6 | 6 | 5 | 8 | 8 | 7 | 7 | 107 |
| 5 | 28 | bge-m3 dense 1024 次元（現行） | 5 | 5 | 4 | 6 | 7 | 7 | 7 | 91 |

JMTEB v2 の検索タスク（nDCG@10、11 タスク平均）の値：Qwen3-Embedding-4B 0.778、Ruri v3 130m 0.764、310m 0.763、70m 0.747、30m 0.733、bge-m3 0.725。

- 31 の速度 10：CPU で multilingual-e5-small の 126 倍速い。精度 4 は、JQaRA が 0.470 と BM25 並みで、ハイブリッドに加えても補完効果が小さいため。
- 32 の精度 9 と速度・メモリ 2：検索スコアは最上位だが、4B パラメータでは CPU での索引構築とクエリ埋め込みが重い（推定）。
- 34 の容量 1：第3.2節のとおり、テキスト 5% でも 2 ビット圧縮で約 47GB になる。精度 9 は JQaRA 0.642。
- **選定：30（Ruri v3 130m、512 次元）。** 加重合計は 30m が 3 点上だが、両者とも 1 秒の要件を満たす。要件を満たした後の速度差の価値は小さい。精度の重みを 5 にすると 130m が逆転する（第6.3節）。方針書が「高い検索精度」を要件に挙げているので、130m を選ぶ。30m は CPU が非力な環境向けの代替とする。
- 製品は GPU を前提にしないので、130m は CPU だけでの索引の構築に数日以上かかりうる（推定、第6.7節）。この採点の速度は検索時の速度で、構築時間は運用の点数にしか反映していない。構築時間は PC の性能で変わるので、製品では埋め込みモデルを設定で選べるようにする。既定のモデルは PoC の後に決める（第6.7節）。
- bge-m3 を外す理由は、日本語検索で Ruri v3 130m より低く、次元が 2 倍、パラメータが約 4 倍だからである。dense・sparse・ColBERT を 1 モデルで出せる利点はあるが、sparse は JQaRA 0.509 で、BM25 と SPLADE の間にとどまる。

#### ディスク容量（推定）

計算式：テキスト量から第3.1節の仮定でチャンク数 N を出し、ベクトル N×次元×バイト数、HNSW N×154 バイト、PQ 符号 N×64 バイト、BM25 はテキスト量の 0.5〜1.0 倍とした。構成 A の payload は本文×1.5（Qdrant の式）である。SPLADE は 1 チャンクあたり非ゼロ 200 項×8 バイトと仮定した。

| 構成 | テキスト 5%（約 300 万チャンク） | テキスト 20%（約 1,180 万チャンク） |
| --- | --- | --- |
| 方針書のまま（bge-m3 の float32 原本＋int8＋本文を payload に保存） | 27〜30GB | 109〜119GB |
| A（原本を持たず int8 のみ、本文は外出し） | 6〜9GB | 24〜34GB |
| B（float16 の 512 次元原本＋PQ） | 6〜8GB | 23〜33GB |
| C（float16 の 768 次元＋int8＋SPLADE） | 15〜17GB | 58〜68GB |

これとは別に、抽出済み Markdown（重なりを除いた本文）がテキスト量と同程度必要になる。info-hive の派生データとして別に数える。

- テキスト 20% の場合、B は原本を int8 にすると約 6GB 減り、30GB を切る。
- C は 20% では要件を超えるので、SPLADE を外すか次元を下げる必要がある。

#### 常駐メモリ（推定）

モデルのメモリはパラメータ数×バイト数で概算した。回答生成は Claude Code で行うので、ローカル LLM は含めない。

| 構成 | 索引 | 埋め込み | リランカー | 合計 |
| --- | --- | --- | --- | --- |
| A（5%） | int8＋HNSW 3.5GB | bge-m3 2.3GB（float32） | small-v2 0.5GB 未満 | 約 6〜7GB |
| A（20%） | 13.9GB | 2.3GB | 0.5GB 未満 | 約 17GB |
| B（5%） | PQ 0.2GB＋キャッシュ 1〜3GB | Ruri 130m 0.5GB | xsmall-v2 0.2GB 未満 | 約 2〜4GB |

### 6.6 推奨、次点、保留

**推奨：構成 B（組み込み・軽量）**

- 常駐メモリは全条件で約 2〜5GB の見込みで、3 構成のうち最も小さい。同じ PC で VS Code や Claude Code を動かしても、16GB に余裕が残る。
- 容量は 20% でも原本を int8 にすれば 30GB を切る。
- 応答時間は CPU のみで 1 秒以内の見込みだが、余裕は小さい。リランク件数で調整する。
- Windows ネイティブで動き、プロセス内に収まるので、info-hive のプラグインに同梱しやすい。
- 弱点は、LanceDB の日本語全文検索の性能が大規模で未検証なこと、Qdrant より量子化と配置の選択肢が少ないことである。

**次点：構成 A（方針書の改良、Qdrant）**

- 機能が最も揃い、方針書からの変更が少ない。
- PoC で B と並べて計測する。LanceDB の全文検索や再スコアの性能が不足した場合に切り替える。
- 方針書のままの bge-m3 と bge-reranker-v2-m3 は採らず、表の変更を入れた形で比べる。

**拡張先：構成 C（精度優先）**

- 製品は GPU がなくても動く必要があるので、既定の構成にはしない。GPU のある PC 向けの拡張として残す。

- GPU があり、テキスト比率が低い（10% 程度まで）場合に、B から段階的に移る。
- テキスト 20% では、ディスクが 58〜68GB になり、容量の要件を超える。
- リランカーを ruri-v3-reranker-310m に替える、SPLADE を加える、の順で効果を測る。

**保留（条件が変われば再検討）**

- 選択肢 22（形態素と bigram の二重フィールド）：評価で未知語の取りこぼしが多いとわかった場合
- 選択肢 24（japanese-splade）：GPU で索引を構築でき、容量に余裕がある場合
- 選択肢 68（Agent による再帰検索）：1 秒の要件の外に置く「深掘り検索」として。info-hive は Claude Code 上で動くので、Claude Code が検索 API を繰り返し呼ぶ形は自然に実装できる
- 選択肢 7（図の VLM キャプション）：図の内容を問う質問が多い場合
- 有償ライセンスを購入する候補（PyMuPDF の Artifex 商用版、YomiToku Pro）：pypdfium2 の速度や NDLOCR-Lite の精度が不足した場合

### 6.7 CPU だけでの索引構築

製品は GPU を前提にしないので、最も時間がかかるのはチャンクの埋め込みである。検索時の 1 秒の要件とは別に、全量の構築に何日かかるかが問題になる。本節は 100GB を最初にまとめて取り込む場合を扱う。1 件ずつ取り込む場合は第6.8節で扱う。

#### 埋め込みの構築時間（推定）

計算式：1 チャンク約 615 トークン（800 字を 1.3 字/トークンで換算）、計算量はトークンあたり「語彙の埋め込み表を除くパラメータ数×2」とした。CPU の実効性能は、16 コアのデスクトップで 1 TFLOPS、8 コアのノート PC で 0.3 TFLOPS と仮定した。いずれも公開の実測値がないための仮定で、実際とは 2〜3 倍ずれうる。

| モデル | 埋め込み表を除くパラメータ | デスクトップ・テキスト 5%（300 万件） | デスクトップ・20%（1,180 万件） | ノート PC・5% | ノート PC・20% |
| --- | --- | --- | --- | --- | --- |
| Ruri v3 30m | 約 11M | 約 11 時間 | 約 2 日 | 約 1.5 日 | 約 6 日 |
| Ruri v3 70m | 約 31M | 約 1.3 日 | 約 5 日 | 約 4 日 | 約 17 日 |
| Ruri v3 130m | 約 80M | 約 3.5 日 | 約 13 日 | 約 11 日 | 約 45 日 |
| Ruri v3 310m | 約 236M | 約 10 日 | 約 40 日 | 約 34 日 | 約 132 日 |

JMTEB v2 の検索スコアは、130m が 0.764、70m が 0.747、30m が 0.733 である。

#### 対策

1. **PoC で構築速度（件/秒）を実測し、モデルを決める。** 判断の規則は次項のとおりである。
2. **初回の構築を分割して、早く使い始める。** BM25 索引を先に作れば、密ベクトルの構築中も字句検索だけで使える。よく使う文書から順に埋め込むこともできる。
3. **構築を中断・再開できるようにする。** チェックポイントを残して夜間や休日に実行する。2 回目以降は、内容ハッシュによる差分更新（選択肢 76）で追加・変更分だけを処理する。
4. **計算量を減らす。** チャンクの重なりを 150 字から 50 字に減らすと、埋め込むトークン数が約 13% 減る。ONNX の int8 量子化でも速くなるが、倍率は未確認である。
5. **GPU を前提にした選択肢は外す。** japanese-splade（選択肢 24）は、130m 程度の計算を全チャンクにもう一度かけることになるので対象外にする。
6. **社内に GPU のある別の PC があれば、初回の構築だけをそこで行う手もある。** 同じ埋め込みモデルを使えば、索引はそのまま持ち込める。

スキャンページの OCR（NDLOCR-Lite、横書きの表は PaddleOCR）も CPU で行う。CPU での速度は公開値がなく、OCR が必要なページ数にも左右されるので、PoC で測る。

#### 検証環境での判定（1 週間の目標）

検証環境では、初回構築を 1 週間以内に終える目標を置く（2026年11月2日にユーザーが決定）。これは検証環境の判定基準で、製品の要件ではない。上限には抽出・OCR・BM25 索引の作成も含むので、埋め込みに使える時間を 5 日とし、残り 2 日を抽出・OCR・BM25 に充てる。この配分は仮の値で、PoC で抽出と OCR の時間を測ってから見直す。

規則：**実測した構築速度で、埋め込みが 5 日以内に終わる最も大きいモデルを選ぶ。** 上の試算を当てはめると、次のようになる（推定）。

#### 製品での扱い

構築時間は PC の性能で数倍変わるので、製品ではモデルを固定せず、次のように扱う（提案）。

- 埋め込みモデルは設定で選べるようにし、既定値を 1 つ決める。既定値は、検証環境での結果と、検証環境より性能の低い PC を想定した見積もりの両方を見て、PoC の後に決める。
- 初回の構築を始める前に、少量のチャンクで構築速度を測り、その PC での所要時間の見積もりを示す。見積もりが長い場合は、小さいモデルや、BM25 索引を先に作って使い始める方法を提案する。
- 構築は中断と再開ができるようにする（対策 3）。
- 索引ごとに埋め込みモデルの名前と版を記録する。モデルを替えた場合は、埋め込み直しが必要であることを示す。

### 6.8 PDF を 1 件ずつ取り込む場合の索引更新

第6.7節は、100GB を最初にまとめて取り込む場合の話である。PDF を 1 件ずつ手で取り込む（インジェストする）場合は、取り込みのたびに索引へ追記する。索引全体を作り直す必要はない。ただし構成 B の LanceDB では、追記を続けると検索の速度と精度が下がるので、保守の処理をときどき行う。本節の LanceDB の挙動は文書にもとづく整理で、実機では確かめていない（要確認）。

#### 取り込みのたびに行う処理

1. 内容ハッシュを照合する。同じ PDF なら処理を飛ばす。更新版なら、古い版のチャンクを削除してから追加する。
2. テキストを抽出し、チャンクに分け、埋め込みを計算する。
3. ベクトル表と BM25 索引に行を追加する。L1 の見出し情報も同時に追加する。

この流れは、info-hive の Ingest 手順（要件定義書 第5.1節）に 1 つの手順として組み込める。手順 1 は、要件定義書の再投入の判定（F-I08）と同じ処理である。

1 件あたりの時間は、検証環境の PC で数十秒から 1 分程度の見込みである（推定）。100 ページで 1 ページ約 1,000 字の PDF なら、約 150 チャンクになる。埋め込みは、第6.7節の構築速度で Ruri v3 130m なら約 37 秒、70m なら約 14 秒、30m なら約 5 秒かかる。検証環境の D ドライブからの読み込みが、平均的な 109MB の PDF で約 6 秒加わる。スキャンページの OCR が必要な場合は、さらに時間が加わる。

#### ときどき行う保守の処理

| タイミング | 処理 | 理由 |
| --- | --- | --- |
| 索引に未反映の行が一定数を超えたとき | optimize を実行する | 追加した行は、索引に反映するまで全件走査で検索される。追記のたびに小さなファイルが増えるので、まとめる必要もある |
| データ量が、前回の索引作成時の数倍になったとき | IVF-PQ の索引を作り直す | IVF の区分けと PQ の符号表は、作成時のデータで学習する。少ないデータで作った索引のままでは、データが増えた後の精度が下がる |
| 定期的に | 古い版を削除する | LanceDB は追記と削除のたびに版を残すので、ディスクの使用量が増え続ける。削除した行も、ファイルをまとめるまで領域を占める |

各タイミングの具体的な件数や倍率は、PoC で決める。

#### 少量のうちは ANN 索引を作らない

最初の数百件の PDF は、全件走査で十分速い。512 次元・float16 のベクトルは 1 件 1KB なので、30 万チャンクの走査は数十 ms、100 万チャンクでも約 100ms と見込む（推定）。そこで、チャンク数が 30 万〜100 万件に達した時点で、初めて IVF-PQ の索引を作る。テキスト比率 5% の想定では、これは約 500〜5,000 件の PDF に当たる。

#### 一括で取り込む場合との違い

| 項目 | 一括で取り込む場合 | 1 件ずつ取り込む場合 |
| --- | --- | --- |
| 初回構築の時間 | 埋め込みモデルの選択を制約する（第6.7節） | 計算量の合計は同じだが取り込みごとに分散するので、制約は事実上なくなる。検証環境でも、テキスト比率にかかわらず 130m を選べる |
| 埋め込みモデルの変更 | 次の一括構築で替えられる | 替えると、それまでに取り込んだ全文書を埋め込み直す。蓄積が増えるほど負担が大きいので、最初に慎重に決める |
| 融合（RRF） | 調整不要 | 調整不要。RRF は順位で統合するので、文書が増えて BM25 の値の分布が変わっても影響を受けない。線形重みなら、分布が変わるたびに重みの調整が要る |
| BM25 の統計 | 構築時に計算される | 単語の出現頻度などの統計は検索のたびに索引から計算されるので、統計だけを作り直す処理は要らない |
| 検索できるまでの時間 | 全量の構築が終わるまで待つ | 取り込んだ文書から順に検索できる |

#### プロセスをまたぐ更新に注意する

取り込みを MCP サーバーとは別のプロセスで行うと、MCP サーバーが追加された行を見られないことがある。LanceDB は既定では、ほかのプロセスによる更新を確認しない。対策は 2 つある。

- 取り込みと検索を同じ MCP サーバーで行う
- 版の確認間隔を設定し、検索のたびに最新の版を読むようにする

どちらにするかは、PoC で挙動を確かめてから決める。

#### 一括と逐次の併用

重要な文書だけを手で 1 件ずつ取り込み、残りを夜間にまとめて取り込むこともできる。どちらの経路も同じ索引に追記し、同じ保守の処理を使う。

### 6.9 原資料の参照

原資料の PDF は、利用者が設定するフォルダ（以下、原資料のルート）から取得する。取り込み（インジェスト）では PDF を移動も複製もせず、参照先のパスを記録する（2026年11月3日にユーザーが決定）。検証環境のルートは `D:\Users\toshiki\OneDrive - Mokumoku.Net\Documents\My eBooks` である。

#### 検証環境のフォルダの現状

2026年11月3日に、ファイルの属性だけを読んで調べた。ファイルの中身は読んでいないので、ダウンロードは発生していない。

| 項目 | 値 |
| --- | --- |
| フォルダ全体 | 35,395 ファイル、107GB |
| PDF | 922 件、98.2GB |
| PDF 1 件の大きさ | 平均 109MB、最大 1,177MB |
| クラウドにしか実体がない PDF（OneDrive のオンライン専用） | 8 件、0.1GB |
| 「常にこのデバイスに保持する」設定の PDF | 5 件 |
| 最も長いパス | 187 字。Windows の既定の上限（260 字）を超える PDF はない |
| PDF 以外の主なファイル | ZIP 75 件（6.2GB）、ISO 4 件、EXE 252 件など |

- 対象は拡張子が `.pdf` のファイルだけにする。ZIP の中にある PDF は取り込まない。
- 1 件の平均が 109MB と大きい。フォルダ名には古い雑誌の名前が多く、スキャンした書籍や雑誌が多いとみられる（推定）。スキャンが多ければ、テキスト比率は第3節の想定より低くなり、ベクトルの容量は小さくなる。その代わり、構築時間の大半を OCR が占める。NDLOCR-Lite の CPU での速度は未確認なので、PoC で測る。
- フォルダ全体の属性の走査には 5 分以上かかった。変更の検出でフォルダ全体を頻繁に走査するのは避ける。

#### 記録する内容

取り込んだ PDF ごとに、次の項目を文書台帳に記録する。台帳は原資料のフォルダではなく、info-hive の側に置く。

| 項目 | 用途 |
| --- | --- |
| 内容ハッシュ（SHA-256） | 文書の ID。改名や移動があっても同じ文書と判定できる |
| 原資料のルートからの相対パス | ファイルを開く場所。ルートの絶対パスは PC ごとの設定に置き、台帳には相対パスだけを書く。別の PC でパスが変わっても、設定を変えるだけで済む |
| ファイルの大きさと更新日時 | 変更の検出。大きさか更新日時が変わったファイルだけ、ハッシュを計算し直す |
| 取り込み日時、ページ数、抽出と OCR の状態 | 取り込みの履歴と、未処理のページの把握 |

#### 書き込まない場所

- 原資料のフォルダには何も書き込まない。抽出したテキストや索引の付属ファイルも置かない。
- 抽出済みの Markdown と索引（10〜30GB）の保存先は、原資料のルートと別に設定できるようにする。既定は、OS が用意する利用者ごとのアプリケーションデータの場所（Windows では `%LOCALAPPDATA%`）とする。原資料のフォルダや、OneDrive などのクラウド同期の対象には置かない。同期の対象に置くと、再生成できるデータがクラウドとの同期を占有する。検証環境では C ドライブの NVMe SSD に置く。

#### 原資料が変わったときの扱い

原資料を複製しないので、利用者がファイルを改名・移動・編集・削除すると、記録と実物がずれる。取り込みのたびと、利用者が指示したときに、記録と実物を照合する。

| 変化 | 判定 | 処理 |
| --- | --- | --- |
| 改名・移動 | 同じハッシュのファイルが別のパスにある | 台帳のパスだけを更新する。埋め込み直しは要らない |
| 内容の変更 | 同じパスのファイルのハッシュが変わった | 新しい版として取り込み直し、古い版のチャンクは索引から外す。古い版の本文は手元に残らないので、台帳にはハッシュと取り込み記録だけを残し、本文は参照不能と記録する |
| 削除 | パスにもハッシュにも一致するファイルがない | その文書のチャンクを検索から外す。台帳の記録は残し、参照不能と記録する |
| オンライン専用への切り替え（OneDrive などのクラウド同期） | ファイルの属性が変わった | 処理は不要。開いたときに同期サービスがダウンロードする |

- 出典を開く操作では、台帳の相対パスから PDF の該当ページを開く。ファイルが見つからなければ、参照不能と表示する。
- 原資料がクラウド同期の対象にある場合は、同期サービスの版の履歴で古い版を復元できる可能性がある。検証環境の OneDrive で、保持される期間と info-hive から利用できるかは未確認である。
- オンライン専用のファイルは、取り込みの時点で同期サービスがダウンロードする。検証環境の OneDrive では、オンライン専用の PDF はいまは 8 件だけである。同期サービスが空き容量のためにファイルをオンライン専用に戻すと、出典を開くたびにダウンロードが起きる。頻繁に参照するなら、原資料のフォルダを常にローカルに保持する設定にするよう、利用者向けの説明に書く。

#### 原資料の置き場所が遅い場合への対策

原資料は、外付けドライブ、ネットワークドライブ、クラウド同期のフォルダなど、遅い場所にあることがある。検証環境でも、原資料のある D ドライブは USB 接続の外付け RAID 0 で、アクセスが遅い（2026年11月3日にユーザーが指摘）。Windows 上のディスク名は「H/W RAID 1」と表示されるが、これは外付けケースの名前で、構成はユーザーによれば RAID 0 である。

| 検証環境での測定 | 結果 |
| --- | --- |
| 順次読み込み（57MB の PDF を 1 件、4MB ずつ） | 約 19MB/秒 |
| フォルダ全体（35,395 ファイル）の属性の走査 | 5 分以上 |

測定は 1 件だけなので、PoC で複数のファイルと読み方で測り直す。この速度なら、全 PDF（98.2GB）を 1 回ずつ読む時間は約 1.5 時間である（推定）。埋め込みにかかる日数に比べて小さいので、順に読む限り、原資料の置き場所の遅さは構築時間の主因にならない。遅さが効くのは、読み位置が飛ぶ処理と、多数のファイルを調べる処理である。

| 対策 | 内容 | 理由 |
| --- | --- | --- |
| 派生データを原資料と別の場所に置く | 索引、文書台帳、抽出済みの Markdown、OCR の一時データ、モデルのファイルの保存先を設定で指定する。既定は利用者ごとのアプリケーションデータの場所とする。検証環境では C ドライブの NVMe SSD（空き 258GB）に置く | 検索と構築の読み書きを、原資料の置き場所の速さに左右させない |
| 検索のときは原資料を読まない | 検索結果の本文は、抽出済みの Markdown から取る。原資料を読むのは、利用者が出典の PDF を開くときだけにする | 1 秒の要件が、原資料の置き場所の速さに左右されない |
| PDF は 1 回だけ順に読む | 各 PDF を先頭から順に読んでメモリに載せ、ハッシュの計算、テキストの抽出、OCR をメモリ上で行う。最大の PDF（1,177MB）もメモリに載る。ディスクには複製しないので、原資料を複製しないという決定にも反しない | PDF の解析は読み位置が飛ぶので、遅いディスク上で直接解析すると、順次読み込みよりはるかに遅くなる |
| 原資料は並列に読まない | 原資料を読む処理は、既定で 1 本にする。速いドライブ向けに、本数を設定で増やせるようにする。読み込みと、CPU で行う OCR・埋め込みは、パイプラインで重ねる | ハードディスクや外付けドライブでは、複数の読み込みが重なると読み位置が行き来して、さらに遅くなる |
| フォルダ全体を走査しない | 変更の検出は、台帳に登録した PDF だけについて、大きさと更新日時を確かめる。新しい PDF は利用者が 1 件ずつ指定して取り込むので、新しいファイルを探す走査は要らない | 検証環境では、全体の走査に 5 分以上かかった |

検証環境の D ドライブは RAID 0 で冗長性がないので、ディスクが 1 台故障すると D のデータをすべて失う。原資料は OneDrive に同期されているので復元できる。派生データは C に置くので、D の故障の影響を受けない。

#### 要件定義書との食い違い

要件定義書は、原資料を `raw/` などに保存する前提で書かれている。今回の決定とは次の箇所が食い違う。

| 要件定義書の箇所 | 現在の記述 | 食い違い | 改訂案 |
| --- | --- | --- | --- |
| 第3.3節（配置と正本） | プロジェクトの `raw/` を `RAW_ROOT` にする配置例 | 原資料はリポジトリの外にある | `RAW_ROOT` に `My eBooks` を指定できるようにする。パスは `RAW_ROOT` からの相対パスで記録する |
| F-I03 | 原資料を保存し、取得日時・由来・内容ハッシュを記録する | 原資料を保存（複製）しない | 「原資料の参照先と内容ハッシュを記録する。原資料は移動も複製もしない」に改める |
| 第7節（出典の追跡） | 原資料の保存版までたどる。取り込み後に内容を変えず、新しい版は別版として記録する | 利用者が原資料を変更・削除しうる。古い版は残らない | 古い版のハッシュと取り込み記録を残し、本文は参照不能と記録する |
| 第10.1節 | 原本を Git に含めるか、別保管にして参照とハッシュを Git で管理するかは未決 | 別保管（参照）に決まった | 決定済みにする。「Wiki の版から原資料を復元できる」という条件は、「ハッシュで同一性を確かめられる」に改める |
| AC-P11 | 保存した原本のハッシュが一致する | 保存した原本がない | 参照先のファイルのハッシュが台帳と一致すること。一致しなければ検出して報告すること |

### 7.2 PoC の手順

1. **サンプルを選ぶ。** My eBooks の 922 件から、無作為に 1〜5GB 分を選ぶ。複製はせず、台帳に参照先を記録して使う。縦書き・スキャン・表の多い資料が含まれることを確認する。
2. **テキスト比率を測る。** 全ページの高速検査で、ページの種類の比率、テキスト量/GB、チャンク数を出す。あわせて、pypdfium2 と PyMuPDF の抽出速度と、日本語テキストの品質（文字化け、読み順）を比べる。第3節の試算をこの値で更新し、20% に近ければ構成 B の int8 化を最初から入れる。
3. **評価セットを作る。** サンプルから質問・期待するページ・根拠の箇所を 100〜300 件作る。日本語のみ、英語の識別子、混在表記、型番・数値、概念的な質問を含める。LLM で合成して人が確認してよい。最終の回答精度の参考に JDocQA も使う。
4. **構成 B と A を構築する。** 同じチャンクと同じ評価セットで、次の値を測る。

| 計測項目 | 合格の目安 |
| --- | --- |
| 検索応答の p50 / p95（ウォーム） | p95 が 1 秒以内 |
| 検索プロセスの常駐メモリの最大値 | 16GB 以下（同じ PC で動く VS Code と Claude Code の分を残す） |
| 索引のディスク容量（100GB に換算） | 30GB 以下 |
| Recall@30（リランク前）、nDCG@10（リランク後） | 評価セットで決める。構成間の比較に使う |
| 索引の構築時間（100GB に換算） | 運用で許せる範囲を決める |

5. **揺れた選択を確定させる。** 使う PC で Ruri v3 130m・70m・30m の埋め込み速度（件/秒）を測り、全量の構築日数を出す。埋め込みが 5 日以内に終わる最も大きいモデルを選ぶ（第6.7節）。そのうえで、int8 と 1.5〜2 ビットの量子化、リランク件数（20 件か 30 件）、RRF の重みを、評価セットで比べる。
6. **1 件ずつの取り込みを確かめる。** PDF を 1 件ずつ追加しながら、次の値を測る（第6.8節）。
   - 1 件あたりの取り込み時間
   - 索引に未反映の行が増えたときの検索時間。optimize を実行する件数の目安を決める
   - 全件走査の検索時間がチャンク数に応じてどう伸びるか。IVF-PQ の索引を初めて作る件数を決める
   - optimize と索引の作り直しにかかる時間
   - 別のプロセスで追加した行が、MCP サーバーの検索に現れるまでの時間
7. **結果を設計書に反映する。** 方針書を改訂し、要件定義書の O-12 を更新する。採用の理由は ADR として `docs/adr/` に残す。
