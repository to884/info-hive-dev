## 1. 結論の要約

1. **最初に決めるべき数値は「PDF 容量あたりのテキスト量」である。** 100GB の PDF から取れるテキストが 5GB（5%）なら、方針書どおりの構成でも 10〜30GB に収まる。20GB（20%）なら、方針書の構成は約 110GB になり要件を大きく超える（第3節）。PDF の容量とテキスト量は比例しないため、サンプルでの実測が必須である。
2. **方針書の構成要素のうち、CPU で 1 秒の要件を最も脅かすのはリランカー bge-reranker-v2-m3 である（推定）。** 日本語ベンチマークでも、より小さい日本語特化リランカーに負けている。CPU のみで運用するので、japanese-reranker-xsmall-v2 への置き換えを提案する。
3. **埋め込みモデルは bge-m3 より Ruri v3 130m（512 次元）が要件に合う。** JMTEB v2 の検索スコアが bge-m3 より高く、次元が半分なので容量とメモリも小さい。ライセンスは Apache-2.0 である。ただし CPU のみでは、130m での全量の埋め込みに数日から 2 週間程度かかる見込みである（推定）。初回構築の上限は 1 週間なので、130m・70m・30m のうち、実測で埋め込みが 5 日以内に終わる最も大きいモデルを選ぶ。運用する PC はデスクトップなので、試算では、テキスト比率がおよそ 7% 以下なら 130m、それを超えて 19% 程度までなら 70m が収まる。チャンクの重なりを 50 字に減らすと、境目はそれぞれ約 9% と約 22% に上がる（第6.7節）。
4. **3 層のハード絞り込み（上位 50 文書に限定）は、L1 で取りこぼした文書を回復できない。** L1 は加点に使い、L2 は全チャンクをハイブリッド検索する 2 層構成を提案する。L1 の要約は LLM で生成せず、見出し・目次・冒頭文や info-hive の source ページから作る。
5. **融合は線形重み（BM25 70：Vector 30）より RRF（順位融合）を標準にする。** スコアの尺度合わせが不要で、重みの調整対象が減る。
6. **索引基盤は、組み込み型の LanceDB を第一候補、Qdrant を次点とし、両方を PoC で比べる。** Qdrant は機能が最も揃うが、別プロセスの運用が要る。また、大規模時のディスク再スコアは Linux 前提の資料しかない。
7. **方針書の GraphRAG 不採用と、検索経路から Agent を外す方針は、採点でも支持される。**
8. **回答の生成は Claude Code だけで行い、機密モードは設けない（2026年11月2日にユーザーが決定）。** ローカル LLM が要らないので、16GB の予算をすべて検索に使える。検索結果の上位チャンクの本文は、Claude Code を通じて PC の外へ送られる。外に送れない文書は、索引に入れないことで扱う（第7.1節）。
9. **CPU のみで運用する（同日にユーザーが決定）。** GPU を前提にした構成 C は対象外にした。検索の 1 秒の要件は CPU 前提で試算済みなので変わらない。影響が大きいのは、索引の構築時間である（第6.7節）。
10. **商用で利用する（同日にユーザーが決定）。** 非商用ライセンスの sarashina、jina、YomiToku などは候補から外した。推奨構成の部品は商用で使えるライセンスを選んだ。ライセンスの確認結果は第2.5節にまとめた。Lindera の辞書はすべて商用で使える。NDLOCR-Lite の学習済みモデルは DINOv3 License の用途制限を受けるが、利用者は制限の対象に当たらない（2026年11月3日にユーザーが確認）。縦書きとスキャンの標準 OCR として使い、モデルはプラグインに同梱せず初回利用時に公式リポジトリから取得する。PDF のテキスト抽出は、AGPL の PyMuPDF に代えて pypdfium2 を第一候補にする。
11. **PDF を 1 件ずつ手で取り込む場合は、索引に追記して更新する。** 1 件あたりの処理は数秒から 1 分程度の見込みで、1 週間の上限は事実上なくなる（推定）。代わりに、索引への反映、索引の作り直し、古い版の削除という保守の処理がときどき要る。埋め込みモデルを後から替えると全文書の埋め込み直しになるので、最初に慎重に決める（第6.8節）。

推奨構成は第6.6節の「構成 B（組み込み・軽量）」である。次の作業は第7節の PoC 計測である。

## 2. 問題定義と評価基準

### 2.1 問題

約 100GB の日本語 PDF を、ローカル PC 上で検索できるようにする。info-hive は Markdown を正本とし、索引を再生成可能な派生データとして扱う（要件定義書 第3.3節）。この前提に合う検索方式を選ぶ。

**判断対象**：方針書の各構成要素を維持するか、代替案に置き換えるか。代替案のうち、PoC で計測する候補を 2〜3 構成に絞る。

### 2.2 制約と前提

| 項目 | 内容 | 区分 |
| --- | --- | --- |
| データ量 | 日本語 PDF 約 100GB | 確定 |
| 検索応答 | 1 秒以内。本書では「質問の受付からリランク後の上位 10 件が出るまで」と解釈し、LLM の回答生成は含めない | 確定（解釈は提案） |
| メモリ | 16GB 以下。索引・埋め込みモデル・リランカーの合計で評価する。回答生成は Claude Code で行うので、ローカル LLM は含めない | 確定 |
| 回答生成 | Claude Code が、検索結果の上位チャンクと出典を受け取って回答する。ローカル LLM と機密モードは設けない | 確定（2026年11月2日） |
| 利用形態 | 商用で利用する。非商用ライセンスの部品は使わない | 確定（2026年11月2日） |
| 索引容量 | 10〜30GB 程度。抽出済み Markdown は info-hive の派生データとして別に数える案も示す | 確定 |
| 実行環境 | Windows 11 のデスクトップ PC。CPU のみで運用し、GPU は使わない。CPU のコア数とメモリの種類（DDR4／DDR5）は未確認 | 確定（2026年11月2日） |
| 初回構築 | 抽出・OCR・BM25・埋め込みを合わせて 1 週間以内 | 確定（2026年11月2日） |
| 運用 | Claude Code と info-hive プラグインから使う。Markdown が正本、索引は再生成可能 | 確定（要件定義書 D-01〜D-04） |

### 2.3 評価基準

各選択肢を 1〜10 点で採点し、重みを掛けて合計する（満点 160）。

| 基準 | 重み | 定義 |
| --- | --- | --- |
| 速度 | 3 | ウォーム状態で検索応答 1 秒以内に収まる見込み。取り込み系の軸では索引構築のスループットとして読む |
| メモリ | 3 | 検索時の常駐メモリの小ささ |
| 容量 | 2 | ディスク上の索引の小ささ |
| 精度 | 3 | 日本語検索の品質。JMTEB v2・JQaRA・JaCWIR・MIRACL-ja の公開値を優先し、ない場合は仕組みから判断する |
| 運用 | 2 | Windows ネイティブで動くか、依存の軽さ、CPU のみで成立するか、ライセンス、構築の手間 |
| 拡張 | 1 | 100GB から数倍への増加や、Web・コードなど他形式への流用のしやすさ |
| 統合 | 2 | info-hive との適合。Markdown 正本から再生成できるか、Claude Code だけで運用できるか、プラグインとして配布できるか |

その軸の性能に影響しない基準は 5 点（中立）とした。

### 2.4 必須条件による除外

採点の前に、次の条件を満たさない候補を除外した。

| 除外した候補 | 理由 |
| --- | --- |
| クラウド API の埋め込み・OCR（Azure Document Intelligence、Google Document AI など） | ローカル運用の要件に反する |
| Nougat | 公式 FAQ で日本語非対応と明記 |
| olmOCR | VRAM 12GB 以上が必要で、8GB GPU では動かない |
| Typesense | 索引を全件 RAM に置く。Windows は WSL のみ |
| Meilisearch | BM25 ではなく独自の順位付け規則を使い、ハイブリッドの融合設計と合わない |
| DuckDB VSS、hnswlib | 索引全体を RAM に載せる必要があり、数百万件以上では 16GB と両立しにくい |
| Chroma（ローカル版） | 疎ベクトル・BM25・RRF の検索 API がクラウド限定 |

商用で利用すると決まったので、次の候補も除外した。

| 除外した候補 | ライセンス |
| --- | --- |
| sarashina-embedding v1/v2、comsat-embed-ja | 非商用 |
| jina-embeddings v3〜v5、jina-reranker v2/v3 | CC BY-NC など非商用 |
| YomiToku | CC BY-NC-SA 4.0。商用には有償の Pro ライセンスが要る |
| marker / surya の重み | 改変 OpenRAIL-M。無償で使えるのは収益 500 万ドル未満などの条件を満たす場合に限る |

PyMuPDF（AGPL-3.0）と poppler（GPL）は、商用のプラグインに組み込むと、配布物全体にソースコードの提供などの条件がかかる。PyMuPDF は Artifex の商用ライセンスを購入すれば使える。本書は、ライセンス費用をかけない前提で、テキスト層の抽出に pypdfium2（Apache-2.0 または BSD-3）、表の抽出に pdfplumber（MIT）を第一候補にする。PyMuPDF は、PoC で品質と速度を比べる基準としてだけ使う。配布しない社内での比較なので、AGPL の条件はかからない。

## 3. 容量の試算（採点の前提）

### 3.1 仮定

| 項目 | 値 | 根拠 |
| --- | --- | --- |
| UTF-8 の 1 文字あたりバイト数 | 2.6 | 和文 3 バイトと ASCII の混在を仮定 |
| チャンク | 800 字、重なり 150 字（実質 650 字ごと） | 方針書の 500〜1000 字・100〜200 字の中央値 |
| HNSW グラフ | 1 件あたり 154 バイト（m=16） | Qdrant 公式の容量計画の式 |
| BM25 索引 | テキスト量の 0.5〜1.0 倍 | 公開値がないため幅で置いた（推定） |
| PDF に占めるテキストの割合 | 1%〜20% | 公開値なし。PDF の容量の大半は画像と埋め込みフォントで、テキスト量とは比例しない |

### 3.2 テキスト比率ごとの規模

| テキスト比率 | テキスト量 | チャンク数 | 1024 次元 float32 | 1024 次元 int8 | 1024 次元 1bit | 512 次元 float16 | HNSW グラフ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1% | 1GB | 約 60 万 | 2.4GB | 0.6GB | 0.08GB | 0.6GB | 0.09GB |
| 2% | 2GB | 約 120 万 | 4.8GB | 1.2GB | 0.15GB | 1.2GB | 0.18GB |
| 5% | 5GB | 約 300 万 | 12.1GB | 3.0GB | 0.38GB | 3.0GB | 0.46GB |
| 10% | 10GB | 約 590 万 | 24.2GB | 6.1GB | 0.76GB | 6.1GB | 0.91GB |
| 20% | 20GB | 約 1,180 万 | 48.5GB | 12.1GB | 1.51GB | 12.1GB | 1.82GB |

ColBERT 系（トークンごとに 128 次元のベクトルを持つ方式）は、テキスト 5% の場合で float16 なら約 380GB、2 ビットに圧縮しても約 47GB になる（推定。1.3 文字を 1 トークンと仮定）。容量要件と両立しないため、一次検索には使えない。

### 3.3 試算からわかること

- **方針書の量子化の発動条件 A（500 万ベクトル以上）は、テキスト比率が約 8% 未満なら発動しない。** 実際に効く制約はディスク容量で、主な原因は float32 の原ベクトルと、payload に複製したチャンク本文である。
- **本文の複製をやめると容量が大きく減る。** 抽出済み Markdown は info-hive の派生データとして保存するので、索引には文書 ID とオフセットだけを持てばよい（選択肢 86）。
- **テキスト比率 20% の場合は、どの構成でも工夫が要る。** 次元の削減、原ベクトルの int8 保存、BM25 索引の圧縮のいずれかが必要になる。

## 4. 発散：選択肢の全リスト

判断を保留して列挙した。方針書で非採用とされた案も、比較のために含めた（「方針書では非採用」と注記）。

1. 全ページのテキスト層だけを抽出する（OCR しない）
2. ページごとにテキスト層の有無と文字化けを判定し、必要なページだけ OCR に回す
3. 全ページを VLM 系パーサ（MinerU、Docling、marker）でレイアウト解析して Markdown にする
4. 日本語特化 OCR（NDLOCR-Lite、YomiToku）を縦書き・スキャン資料に限って使う
5. 表を Markdown 表または CSV として本文と別のチャンクにし、表専用の索引を持つ
6. 図はキャプションの文だけを索引に入れる
7. 図に VLM でキャプションを生成して索引に入れる
8. 抽出結果を PDF 単位の Markdown キャッシュとして保存し、再索引時に抽出をやり直さない
9. 内容ハッシュで重複 PDF と版違いを検出し、版として束ねる
10. ヘッダ、フッタ、ページ番号、目次、索引ページを除去する
11. NFKC、全角半角、長音、旧字体の正規化を抽出時に一度だけ行う

## 6. 収束：評価と選定

### 6.1 採点の進め方

- C1〜C6 のうち、互いに置き換え可能な選択肢を軸ごとに採点した。軸は C1 を「抽出・OCR」と「チャンク化」に、C5 を「階層・絞り込み」「融合・リランク」「クエリ処理・キャッシュ」に分けた計 10 軸である。
- 補助的な手段（5〜11、14、18、23、26、35、36、43、47、49、77、78）は、どの構成でも採れるので採点せず、第6.6節の構成案に組み込んだ。
- C7（82〜85）は互いに競合する選択肢ではなく、どの構成を選んでも行う検証なので、採点せず第7節の計画に入れた。
- 公開値のない項目は、仕組みから判断した点数である。極端な点数（1〜2、9〜10）の根拠は、各表の下に書いた。

- 1 の速度 9：PyMuPDF は 7,031 ページを 8.01 秒で処理する（約 1.1ms/ページ）。精度 4 は、スキャンと縦書きのページを取りこぼすため。

- **選定：2。** 全ページをまず高速に検査し、文字数・CJK 比率・U+FFFD や私用領域の文字の比率・画像の被覆率・縦書きの有無を記録する。その結果で「良好なテキスト層」「文字化け」「スキャン」「縦書き」に分け、後の 3 つだけを OCR に回す。テキスト層の抽出は pypdfium2、表は pdfplumber を使う。OCR は NDLOCR-Lite（CC BY 4.0、CPU で動き、縦書きに対応）を標準にし、横書きの表には PaddleOCR（Apache-2.0）を使う。NDLOCR-Lite の学習済みモデルは同梱せず、初回利用時に公式リポジトリから取得する（第2.5節）。pypdfium2 の速度は公開値がないので、PoC で PyMuPDF と比べて測る。

| 7 | 44' | 量子化なし（float32） | 6 | 5 | 4 | 9 | 9 | 3 | 7 | 103 |

- 44 の精度 9：スカラー量子化の誤差は通常 1% 未満（Qdrant）。英語モデルの例では int8 で 97%、再スコアで約 99% を保つ。
- 45 の精度 7：英語モデルでは再スコアありで 96.45% を保つ。ただし Qdrant は 1 ビットについて「1,000 次元未満では精度の低下が大きい」としている。512 次元のモデルでは 1.5〜2 ビットか int8 が安全である。日本語モデルでの低下幅の公開データはない（要確認）。
- 86 の統合 10：要件定義書の「Markdown が正本、索引は派生データ」の方針とそのまま一致する。
- 48 の容量 10・精度 4：ベクトルが L1 の数十万件だけになるが、チャンク単位の意味検索を失う。
- **選定：44 を既定とし、33（小次元モデルの選択）と 86 を組み合わせる。** 45 と 46 は、テキスト比率が高く容量やメモリが足りない場合に追加する。方針書の量子化の発動条件（件数、20GB、RAM の 50%、500ms）は、「最初から int8 にする」に置き換える。第3.3節のとおり、件数の条件はほぼ発動しないためである。

#### ディスク容量（推定）

計算式：テキスト量から第3.1節の仮定でチャンク数 N を出し、ベクトル N×次元×バイト数、HNSW N×154 バイト、PQ 符号 N×64 バイト、BM25 はテキスト量の 0.5〜1.0 倍とした。構成 A の payload は本文×1.5（Qdrant の式）である。SPLADE は 1 チャンクあたり非ゼロ 200 項×8 バイトと仮定した。

| 構成 | テキスト 5%（約 300 万チャンク） | テキスト 20%（約 1,180 万チャンク） |
| --- | --- | --- |
| 方針書のまま（bge-m3 の float32 原本＋int8＋本文を payload に保存） | 27〜30GB | 109〜119GB |
| A（原本を持たず int8 のみ、本文は外出し） | 6〜9GB | 24〜34GB |
| B（float16 の 512 次元原本＋PQ） | 6〜8GB | 23〜33GB |
| C（float16 の 768 次元＋int8＋SPLADE） | 15〜17GB | 58〜68GB |

これとは別に、抽出済み Markdown（重なりを除いた本文）がテキスト量と同程度必要になる。info-hive の派生データとして別に数える。

- テキスト 20% の場合、B は原本を int8 にすると約 6GB 減り、30GB を切る。
- C は 20% では要件を超えるので、SPLADE を外すか次元を下げる必要がある。

| B（20%） | PQ 0.8GB＋キャッシュ 1〜3GB | 0.5GB | 0.2GB 未満 | 約 3〜5GB |

### 6.6 推奨、次点、保留

**推奨：構成 B（組み込み・軽量）**

- 常駐メモリは全条件で約 2〜5GB の見込みで、3 構成のうち最も小さい。同じ PC で VS Code や Claude Code を動かしても、16GB に余裕が残る。
- 容量は 20% でも原本を int8 にすれば 30GB を切る。
- 応答時間は CPU のみで 1 秒以内の見込みだが、余裕は小さい。リランク件数で調整する。
- Windows ネイティブで動き、プロセス内に収まるので、info-hive のプラグインに同梱しやすい。
- 弱点は、LanceDB の日本語全文検索の性能が大規模で未検証なこと、Qdrant より量子化と配置の選択肢が少ないことである。

**次点：構成 A（方針書の改良、Qdrant）**

- 機能が最も揃い、方針書からの変更が少ない。
- PoC で B と並べて計測する。LanceDB の全文検索や再スコアの性能が不足した場合に切り替える。
- 方針書のままの bge-m3 と bge-reranker-v2-m3 は採らず、表の変更を入れた形で比べる。

**拡張先：構成 C（精度優先）**

- CPU のみで運用すると決まったので、現時点では対象外である。GPU を追加した場合の拡張先として残す。

- GPU があり、テキスト比率が低い（10% 程度まで）場合に、B から段階的に移る。
- テキスト 20% では、ディスクが 58〜68GB になり、容量の要件を超える。
- リランカーを ruri-v3-reranker-310m に替える、SPLADE を加える、の順で効果を測る。

**保留（条件が変われば再検討）**

- 選択肢 22（形態素と bigram の二重フィールド）：評価で未知語の取りこぼしが多いとわかった場合
- 選択肢 24（japanese-splade）：GPU で索引を構築でき、容量に余裕がある場合
- 選択肢 68（Agent による再帰検索）：1 秒の要件の外に置く「深掘り検索」として。info-hive は Claude Code 上で動くので、Claude Code が検索 API を繰り返し呼ぶ形は自然に実装できる
- 選択肢 7（図の VLM キャプション）：図の内容を問う質問が多い場合
- 有償ライセンスを購入する候補（PyMuPDF の Artifex 商用版、YomiToku Pro）：pypdfium2 の速度や NDLOCR-Lite の精度が不足した場合

### 6.7 CPU のみでの索引構築

CPU のみで運用するので、最も時間がかかるのはチャンクの埋め込みである。検索時の 1 秒の要件とは別に、全量の構築に何日かかるかが問題になる。本節は 100GB を最初にまとめて取り込む場合を扱う。1 件ずつ取り込む場合は第6.8節で扱う。

#### 埋め込みの構築時間（推定）

計算式：1 チャンク約 615 トークン（800 字を 1.3 字/トークンで換算）、計算量はトークンあたり「語彙の埋め込み表を除くパラメータ数×2」とした。CPU の実効性能は、16 コアのデスクトップで 1 TFLOPS、8 コアのノート PC で 0.3 TFLOPS と仮定した。いずれも公開の実測値がないための仮定で、実際とは 2〜3 倍ずれうる。

| モデル | 埋め込み表を除くパラメータ | デスクトップ・テキスト 5%（300 万件） | デスクトップ・20%（1,180 万件） | ノート PC・5% | ノート PC・20% |
| --- | --- | --- | --- | --- | --- |
| Ruri v3 30m | 約 11M | 約 11 時間 | 約 2 日 | 約 1.5 日 | 約 6 日 |
| Ruri v3 70m | 約 31M | 約 1.3 日 | 約 5 日 | 約 4 日 | 約 17 日 |
| Ruri v3 130m | 約 80M | 約 3.5 日 | 約 13 日 | 約 11 日 | 約 45 日 |
| Ruri v3 310m | 約 236M | 約 10 日 | 約 40 日 | 約 34 日 | 約 132 日 |

JMTEB v2 の検索スコアは、130m が 0.764、70m が 0.747、30m が 0.733 である。

#### 対策

1. **PoC で構築速度（件/秒）を実測し、モデルを決める。** 判断の規則は次項のとおりである。
2. **初回の構築を分割して、早く使い始める。** BM25 索引を先に作れば、密ベクトルの構築中も字句検索だけで使える。よく使う文書から順に埋め込むこともできる。
3. **構築を中断・再開できるようにする。** チェックポイントを残して夜間や休日に実行する。2 回目以降は、内容ハッシュによる差分更新（選択肢 76）で追加・変更分だけを処理する。
4. **計算量を減らす。** チャンクの重なりを 150 字から 50 字に減らすと、埋め込むトークン数が約 13% 減る。ONNX の int8 量子化でも速くなるが、倍率は未確認である。
5. **GPU を前提にした選択肢は外す。** japanese-splade（選択肢 24）は、130m 程度の計算を全チャンクにもう一度かけることになるので対象外にする。
6. **社内に GPU のある別の PC があれば、初回の構築だけをそこで行う手もある。** 同じ埋め込みモデルを使えば、索引はそのまま持ち込める。

スキャンページの OCR（NDLOCR-Lite、横書きの表は PaddleOCR）も CPU で行う。CPU での速度は公開値がなく、OCR が必要なページ数にも左右されるので、PoC で測る。

#### 1 週間の上限に収まるモデル

初回構築の上限は 1 週間である（2026年11月2日にユーザーが決定）。上限には抽出・OCR・BM25 索引の作成も含むので、埋め込みに使える時間を 5 日とし、残り 2 日を抽出・OCR・BM25 に充てる。この配分は仮の値で、PoC で抽出と OCR の時間を測ってから見直す。

規則：**実測した構築速度で、埋め込みが 5 日以内に終わる最も大きいモデルを選ぶ。** 上の試算を当てはめると、次のようになる（推定）。

| PC とテキスト比率 | 選ぶモデル | 埋め込みの日数 | 備考 |
| --- | --- | --- | --- |
| デスクトップ・5% | Ruri v3 130m | 約 3.5 日 | |
| デスクトップ・20% | Ruri v3 70m | 約 4.5 日 | 重なりを 50 字に減らした場合。150 字のままでは約 5.2 日で上限を少し超える |
| ノート PC・5% | Ruri v3 70m | 約 4.4 日 | 130m は約 11 日で超える |
| ノート PC・20% | Ruri v3 30m | 約 5.2 日 | 重なりを 50 字に減らした場合。それでも上限を少し超える。1 週間には収まるが、抽出と OCR の時間を詰める必要がある |

運用する PC はデスクトップと決まった（2026年11月2日）。ノート PC の行は参考として残す。デスクトップ PC で、埋め込みが 5 日以内に終わるテキスト比率の上限は次のとおりである（推定）。

| モデル | 構築速度（推定） | 5 日で処理できるチャンク数 | テキスト比率の上限（重なり 150 字） | テキスト比率の上限（重なり 50 字） | JMTEB v2 検索 |
| --- | --- | --- | --- | --- | --- |
| Ruri v3 130m | 約 10 件/秒 | 約 440 万件 | 約 7% | 約 9% | 0.764 |
| Ruri v3 70m | 約 26 件/秒 | 約 1,140 万件 | 約 19% | 約 22% | 0.747 |
| Ruri v3 30m | 約 77 件/秒 | 約 3,320 万件 | 50% 超 | 60% 超 | 0.733 |

- テキスト比率の実測（第7.2節の手順 2）と、使う PC での構築速度の実測（手順 5）がそろったら、この表を実測値で作り直してモデルを決める。
- 想定したのは 16 コアのデスクトップ CPU である。使う PC のコア数がこれより少なければ、上限のテキスト比率はほぼ比例して下がる。
- 2 回目以降は差分更新なので、1 週間の上限は初回の構築だけに適用する。

### 6.8 PDF を 1 件ずつ取り込む場合の索引更新

第6.7節は、100GB を最初にまとめて取り込む場合の話である。PDF を 1 件ずつ手で取り込む（インジェストする）場合は、取り込みのたびに索引へ追記する。索引全体を作り直す必要はない。ただし構成 B の LanceDB では、追記を続けると検索の速度と精度が下がるので、保守の処理をときどき行う。本節の LanceDB の挙動は文書にもとづく整理で、実機では確かめていない（要確認）。

#### 取り込みのたびに行う処理

1. 内容ハッシュを照合する。同じ PDF なら処理を飛ばす。更新版なら、古い版のチャンクを削除してから追加する。
2. テキストを抽出し、チャンクに分け、埋め込みを計算する。
3. ベクトル表と BM25 索引に行を追加する。L1 の見出し情報も同時に追加する。

この流れは、info-hive の Ingest 手順（要件定義書 第5.1節）に 1 つの手順として組み込める。手順 1 は、要件定義書の再投入の判定（F-I08）と同じ処理である。

1 件あたりの時間は、デスクトップ PC で数秒から 1 分程度の見込みである（推定）。100 ページで 1 ページ約 1,000 字の PDF なら、約 150 チャンクになる。埋め込みは、第6.7節の構築速度で Ruri v3 130m なら約 15 秒、70m なら約 6 秒かかる。スキャンページの OCR が必要な場合は、さらに時間が加わる。

#### ときどき行う保守の処理

| タイミング | 処理 | 理由 |
| --- | --- | --- |
| 索引に未反映の行が一定数を超えたとき | optimize を実行する | 追加した行は、索引に反映するまで全件走査で検索される。追記のたびに小さなファイルが増えるので、まとめる必要もある |
| データ量が、前回の索引作成時の数倍になったとき | IVF-PQ の索引を作り直す | IVF の区分けと PQ の符号表は、作成時のデータで学習する。少ないデータで作った索引のままでは、データが増えた後の精度が下がる |
| 定期的に | 古い版を削除する | LanceDB は追記と削除のたびに版を残すので、ディスクの使用量が増え続ける。削除した行も、ファイルをまとめるまで領域を占める |

各タイミングの具体的な件数や倍率は、PoC で決める。

#### 少量のうちは ANN 索引を作らない

最初の数百件の PDF は、全件走査で十分速い。512 次元・float16 のベクトルは 1 件 1KB なので、30 万チャンクの走査は数十 ms、100 万チャンクでも約 100ms と見込む（推定）。そこで、チャンク数が 30 万〜100 万件に達した時点で、初めて IVF-PQ の索引を作る。テキスト比率 5% の想定では、これは約 500〜5,000 件の PDF に当たる。

#### 一括で取り込む場合との違い

| 項目 | 一括で取り込む場合 | 1 件ずつ取り込む場合 |
| --- | --- | --- |
| 1 週間の上限 | 埋め込みモデルの選択を制約する（第6.7節） | 計算量の合計は同じだが取り込みごとに分散するので、事実上なくなる。テキスト比率にかかわらず 130m を選べる |
| 埋め込みモデルの変更 | 次の一括構築で替えられる | 替えると、それまでに取り込んだ全文書を埋め込み直す。蓄積が増えるほど負担が大きいので、最初に慎重に決める |
| 融合（RRF） | 調整不要 | 調整不要。RRF は順位で統合するので、文書が増えて BM25 の値の分布が変わっても影響を受けない。線形重みなら、分布が変わるたびに重みの調整が要る |
| BM25 の統計 | 構築時に計算される | 単語の出現頻度などの統計は検索のたびに索引から計算されるので、統計だけを作り直す処理は要らない |
| 検索できるまでの時間 | 全量の構築が終わるまで待つ | 取り込んだ文書から順に検索できる |

#### プロセスをまたぐ更新に注意する

取り込みを MCP サーバーとは別のプロセスで行うと、MCP サーバーが追加された行を見られないことがある。LanceDB は既定では、ほかのプロセスによる更新を確認しない。対策は 2 つある。

- 取り込みと検索を同じ MCP サーバーで行う
- 版の確認間隔を設定し、検索のたびに最新の版を読むようにする

どちらにするかは、PoC で挙動を確かめてから決める。

#### 一括と逐次の併用

重要な文書だけを手で 1 件ずつ取り込み、残りを夜間にまとめて取り込むこともできる。どちらの経路も同じ索引に追記し、同じ保守の処理を使う。

## 7. 次のステップ

### 7.1 先に決める事項（ユーザーの判断）

| 事項 | 選択肢 | 影響 |
| --- | --- | --- |
| 回答生成 | **決定済み**：Claude Code だけで行い、機密モードは設けない | 検索 API は、上位チャンクの本文と出典（文書名、章、節、ページ番号）を返す |
| Claude Code に送ってよい資料の範囲 | 全資料を送ってよい／送れない資料がある | 上位チャンクの本文が PC の外に送られる。送れない資料がある場合は、索引に入れない。要件定義書の S-03 と O-10 と同じ判断になる |
| 商用利用 | **決定済み**：商用で利用する | 非商用ライセンスの部品を除外した。残っていたライセンスの確認も終えた（第2.5節） |
| 利用者に原子力・防衛関連の組織が含まれるか | **決定済み**：含まれない | NDLOCR-Lite を標準の OCR として使う。利用者の範囲が変わったら見直す（第2.5節） |
| GPU | **決定済み**：CPU のみ | 構成 C は対象外。索引の構築時間への対策を入れた（第6.7節） |
| 索引の初回構築に許容できる日数 | **決定済み**：1 週間まで | 埋め込みを 5 日以内に終えられる最も大きいモデルを選ぶ（第6.7節） |
| 運用する PC | **決定済み**：デスクトップ | CPU のコア数とメモリの種類（DDR4／DDR5）を確認する。構築日数の見積もりに使う |

### 7.2 PoC の手順

1. **サンプルを選ぶ。** 100GB から無作為に 1〜5GB を抜き出す。縦書き・スキャン・表の多い資料が含まれることを確認する。
2. **テキスト比率を測る。** 全ページの高速検査で、ページの種類の比率、テキスト量/GB、チャンク数を出す。あわせて、pypdfium2 と PyMuPDF の抽出速度と、日本語テキストの品質（文字化け、読み順）を比べる。第3節の試算をこの値で更新し、20% に近ければ構成 B の int8 化を最初から入れる。
3. **評価セットを作る。** サンプルから質問・期待するページ・根拠の箇所を 100〜300 件作る。日本語のみ、英語の識別子、混在表記、型番・数値、概念的な質問を含める。LLM で合成して人が確認してよい。最終の回答精度の参考に JDocQA も使う。
4. **構成 B と A を構築する。** 同じチャンクと同じ評価セットで、次の値を測る。

| 計測項目 | 合格の目安 |
| --- | --- |
| 検索応答の p50 / p95（ウォーム） | p95 が 1 秒以内 |
| 検索プロセスの常駐メモリの最大値 | 16GB 以下（同じ PC で動く VS Code と Claude Code の分を残す） |
| 索引のディスク容量（100GB に換算） | 30GB 以下 |
| Recall@30（リランク前）、nDCG@10（リランク後） | 評価セットで決める。構成間の比較に使う |
| 索引の構築時間（100GB に換算） | 運用で許せる範囲を決める |

5. **揺れた選択を確定させる。** 使う PC で Ruri v3 130m・70m・30m の埋め込み速度（件/秒）を測り、全量の構築日数を出す。埋め込みが 5 日以内に終わる最も大きいモデルを選ぶ（第6.7節）。そのうえで、int8 と 1.5〜2 ビットの量子化、リランク件数（20 件か 30 件）、RRF の重みを、評価セットで比べる。
6. **1 件ずつの取り込みを確かめる。** PDF を 1 件ずつ追加しながら、次の値を測る（第6.8節）。
   - 1 件あたりの取り込み時間
   - 索引に未反映の行が増えたときの検索時間。optimize を実行する件数の目安を決める
   - 全件走査の検索時間がチャンク数に応じてどう伸びるか。IVF-PQ の索引を初めて作る件数を決める
   - optimize と索引の作り直しにかかる時間
   - 別のプロセスで追加した行が、MCP サーバーの検索に現れるまでの時間
7. **結果を設計書に反映する。** 方針書を改訂し、要件定義書の O-12 を更新する。採用の理由は ADR として `docs/adr/` に残す。
