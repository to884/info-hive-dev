# RAG PoC 検証サマリ

同日追記：残項目の [追加検証](rag-validation-remaining-2026-11-04/README.md) を実施し、結果を記録した。
利用者が PDF の質問 60 問の修正案を承認し、正解箇所に合わせた追加チャンクを使わない 8,275 チャンクで再評価した。
製品リランカーを組み込んだ MCP 込みの p95 は、なし 187 ms、tiny 上位 8 件 424 ms、xsmall 上位 8 件 1,043 ms だった。
複数 MCP 接続の制御と引き継ぎ、表・数式などの OCR も追加で確認した。
ローカル PDF 914 件、約 105 GB のテキスト層を抽出し、重複を除く 905 文書、761,915 チャンクの全量索引を作成した。
Ruri v3 130m、IVF_SQ、公開世代の Bitmap 索引を使った条件では、容量は約 4.02 GB、実 MCP の CPU 検索 p95 はリランカーなし 679 ms、tiny 上位 8 件 954 ms、xsmall 上位 8 件 1,397 ms だった。
全量の正例 60 問に対するラベル付きページの再現率は 0.7250 で、正解ラベルは 4 文書由来である。
全資料の関連ページを網羅的に判定した評価ではない。
Linux でも単体 11 件、実 MCP の中断・再開 18 件、配布用 uv 起動の制御 5 件が成功した。
全量の OCR、ANN の自動作成・継続更新を含む全資料の取り込み E2E、CPU での全量埋め込み時間は未検証である。
OS 電源断と macOS は今回の対象外とした。
以下は追加検証前のサマリとして残す。

実施日：2026年11月4日（日本時間）。
対象：info-hive-rag の候補比較と、その後の製品修正・統合検証。

**MCP＋共通コア＋永続ジョブの構成で、PDF の登録、OCR、埋め込み、中断後の再開、wiki の要約作成まで確認した。**
検索候補の比較では CPU で p95 が 1 秒未満となる条件があったが、100 GB 全体での性能・容量と、モデル・索引基盤の最終採用は未確定である。

検証環境は Windows 11、Python 3.12.13、Ryzen 7 3800XT（8 コア）、メモリ 32 GiB。
検索候補の比較には CPU を 4 スレッドで使った。

| 検証対象 | 範囲と結果 |
| --- | --- |
| 実資料の抽出 | PDF 11 件、約 1.16 GB、2,895 ページを抽出。pypdfium2 の抽出本文は UTF-8 で約 6.83 MB、元 PDF の約 0.59%（OCR 追加分を除く）。原本 11 件のハッシュは検証前後で一致 |
| 検索候補 | Ruri v3 30m / 70m / 130m、リランカー、LanceDB / Qdrant を比較。検索評価は実資料全体の索引ではなく、最大 602 チャンクの小規模データを使用 |
| 索引の更新・保存 | 両基盤で計 6 件が成功。LanceDB の別プロセスからの追記反映、全文検索、最適化、重複抑止と、Qdrant の重複抑止・再起動後の保持を確認 |
| 製品の中断・再開 | 自作の日本語 PDF 42 ページ（テキスト 40、横書き・縦書きスキャン各 1）を実 OCR・実モデルで処理。OCR 起動時と埋め込みバッチ保存後に MCP サーバーを強制終了し、同じジョブ ID から再開。42 チャンクを重複なく公開し、出典付き検索まで確認 |
| Claude Code の取り込み | `/wiki:ingest` で登録して会話を終了。次の独立したセッションで同じジョブを再開し、抽出本文を読んで source ページ、index、log を作成。原本のコピー・内容変更なし |

製品修正後の確認は、回帰試験 6 件、製品 MCP 統合 18 件、配布用 uv 起動の制御 5 件、Claude Code の取り込み 6 件、計 **35 件が成功**した。
wiki→rag の接続不足と PDF API の `TypeError` に加え、索引公開時の SQL の値数、Pillow の依存宣言不足も修正した。

検索の比較結果は次のとおり。
同じ 107 問、602 チャンクを使い、語彙検索とベクトル検索を順位融合した後にリランクした。
表のリランカーはすべて int8 で、候補比較用 PoC の処理である。
**製品本体にはリランカーをまだ組み込んでいないため、この表を製品全体の性能とは扱わない。**

| Ruri v3 | リランカー・対象件数 | p95 ms（LanceDB / Qdrant） | Recall@30 | nDCG@10 | Python peak RSS |
| --- | --- | --- | --- | --- | --- |
| 30m | tiny、20 件 | 673 / 665 | 0.9439 | 0.7680 | 1.33 GiB |
| 70m | tiny、20 件 | 523 / 525 | 0.9626 | 0.8165 | 1.97 GiB |
| 130m | tiny、20 件 | 677 / 675 | 0.9813 | 0.8068 | 2.45 GiB |
| 30m | xsmall、8 件 | 749 / 744 | 0.9439 | 0.8460 | 1.21 GiB |

Recall@30 は、質問ごとに正解ページのうち上位 30 件で見つかった割合を求めた平均である。
nDCG@10 は上位 10 件の順位を評価する指標で、1 に近いほどよい。
両基盤の品質指標は、この比較では同じ値だった。
p95 はクエリの埋め込み、検索、順位融合、リランクの実測時間の和であり、MCP 通信、クエリの分かち書き、回答生成、初回の準備を含まない。
RSS は単一の Python プロセスの最大値で、Qdrant や複数セッションを含む合計ではない。

この暫定セットでは、30m＋xsmall 上位 8 件の nDCG が最も高く、130m＋tiny 上位 20 件の Recall が最も高かった。
602 チャンクの文書埋め込みは、30m が約 81 秒、70m が約 157 秒、130m が約 449 秒だった。
別の固定 47 問の比較では、xsmall の上位 30 件リランクは int8 でも p95 が約 2.7〜2.8 秒かかり、tiny への変更ではリランク前より順位が悪化する例もあった。
モデルの大きさ、リランクの件数、取りこぼしを併せて評価する必要がある。

検索評価の 107 問のうち 60 問はエージェントが作った暫定質問で、人手による妥当性確認は済んでいない。
その 60 問中 49 問は英語資料への日本語の質問で、正解根拠を含むようにチャンクを加えている。
正解のない 6 問も集計から除外したため、一般的な日本語 PDF の精度、自動チャンク分割、関連資料がない質問の棄却は、この結果から判断できない。

現在の実装では、検索と索引化を同じ子ワーカーで直列に処理する。
索引化中の検索は待機するが、MCP の受付と進捗確認は継続できる。
キャンセル済みと失敗したジョブは自動再試行せず、明示的な再試行で保存済み処理を再利用する。
初回の実行環境準備には約 595 秒かかり、Claude Code の再開から要約作成までのセッションは約 250 秒だった。
これらは検索の p95 とは別の時間である。

次の採用判断には、以下の検証が残る。

- 人手で確認した質問と正解なしの質問による再評価、および製品本体へのリランカー統合後の測定。
- 約 100 GB 全体の索引構築、索引容量 10〜30 GB、合計メモリ 16 GB 以下、MCP 通信を含む検索性能。大規模 ANN と圧縮索引も未検証で、LanceDB / Qdrant の採用順位は未決。
- 実資料の OCR 精度と縦書き判定。横書きの広告を縦書きと判定した例があり、表、数式、低解像度の資料も確認が必要。
- 複数セッションの同時負荷、検索と索引化の同時実行、ほかの OS、OS 電源断時の復旧。

根拠と再現手順は、[候補比較の記録](rag-poc-2026-11-04/README.md)、[検索の実測表](rag-poc-2026-11-04/measurements.md)、[製品修正後の統合検証](rag-pdf-job-integration-2026-11-04/README.md) にある。
