# Windows 版 WebKit での SVG／PNG の再測定

2026年11月19日、17:58:05〜18:04:44（日本時間）。親リポジトリの `main` の `4d7a40f` から作った worktree で、保存済みのフローチャート50図を SVG と PNG で各10周・2反復表示した。描画前からのピーク私有コミット増分の中央値は SVG **62.27 MiB**、PNG **35.23 MiB** だった。PNG の増分は SVG より 27.04 MiB（43.4%）小さく、前回と同じ傾向が両反復で確認できた。 [前回の報告](wiki-browse-static-svg-vs-png-2026-11-19.md)

## 条件とデータ

- Windows 11 x64（ビルド 26300）、AMD Ryzen 7 3800XT、Node.js 24.15.0、Playwright 1.56.1、Windows 版 WebKit 26.0（リビジョン 2215）。OS・CPU・物理メモリの記録、Playwright と Playwright Core のパッケージのハッシュが前回と一致した。WebKit の337ファイルも前回の控えと SHA-256 が一致した。
- 前回と同じ ZIP の画像を使った。各ケースで専用ブラウザを起動し、同じ文書で明暗それぞれ50枚を表示した。暗色の表示後に5秒待ち、手動 GC は要求しなかった。1回目は SVG → PNG、2回目は PNG → SVG。全4ケースで10周を完走し、周ごとの文書 ID と待機後の Web プロセスの PID をケース内で維持した。
- 今回は保存済みの再測定スクリプトを使った。観測ピークは、各ケースの10周で採取した安定標本の私有コミット合計の最大値である。採取処理の待ち時間は100 ms。前後の連続した安定標本の実測間隔の中央値は、前回がケースごとに 0.79〜1.00 秒、今回が 0.59〜0.67 秒だった。システムのコミット余力は最低 17.6 GiB で、停止条件には達しなかった。

前回と今回の原標本を同じ集計スクリプトで集計した。 [今回の実行記録](../agent-runs/2026-11-19-wiki-static-svg-vs-png-remeasurement/results.json) · [今回の集計](../agent-runs/2026-11-19-wiki-static-svg-vs-png-remeasurement/summary.json) · [前回の集計](../agent-runs/2026-11-19-wiki-static-svg-vs-png/ten-rounds/summary.json) · [再測定スクリプト](../../poc/browse-static-image/performance-experiment.mjs)

## 先頭画像の `img.decode()`

単位はミリ秒。初回の各セルは反復順の2値。2〜10周目の各セルは両反復の18値の中央値である。

前回の PNG で観測した明色の4,450 msは今回の2反復で再現しなかった。今回は初回の明色で速い形式が反復によって入れ替わり、暗色では両反復とも PNG の値が小さかった。値は WebKit の `img.decode()` が解決するまでの時間である。PNG はビットマップのデコード後に解決し、SVG はラスタライズの完了前にも解決し得る。初回の画面表示速度はこの試験からは確定できない。 [前回の初回追加測定](../agent-runs/2026-11-19-wiki-static-svg-vs-png/first-round/summary.json) · [測定条件の説明](wiki-browse-static-svg-vs-png-2026-11-19.md#測定条件)
