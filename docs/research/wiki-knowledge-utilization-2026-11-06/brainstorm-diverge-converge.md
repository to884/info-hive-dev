## 1. 結論の要約

**スコープ B（今の wiki の使い方）を先に始め、スコープ A（次に足す機能）は順位表ではなく「着手条件つきの候補」として持つ。** これが 4 体の成果とレビューを通して残った結論である（提案）。

理由は 2 つある。第一に、作者の wiki は 23 ページで、型付きエッジは `authored` 5 本、synthesis は 0 件、経験のページは 0 件、`valid_from`・`valid_to`・`contradicts`・`supersedes`・`raw_ref` はすべて 0 本である（事実、第 3.3 節）。グラフや synthesis を前提にした機能は、今は動かす対象がない。第二に、4 体の A の順位表は、対象データが 0 件の機能に「今も効く」点を付ける、実装不要の運用案が「整合」と「軽さ」で機能案を押し上げる、といった偏りを 4 体とも持っていた（第 6.2 節）。順位をそのまま採ると、材料がない機能を先に作ることになる。

### スコープ B：SCHEMA.md に書いて今日から回す 3 つの習慣（提案）

| 習慣 | 作業の切れ目 | 使う既存の機能 | 条件 |
| --- | --- | --- | --- |
| B1 設計の前に `/wiki:query` で選択肢、採用条件、反例、未確認事項を引き、再利用する判断を `synthesis/` に残す | 設計の前と、質問のあと | query の手順 6（保存の提案）。保存の基準「3 か月後に見つけたいか」も既存 | 保存するページには `type`、`title`、`tags`、`created`、`updated` と `sources` を書く。query-workflow の例だけでは lint が欠落を報告する（第 3.4 節） |
| B2 取り込みの報告に、既存の主張との差分（更新・矛盾・補強・新規）を付ける | 取り込みのあと | ingest の手順 5（候補ページを読む）と手順 8（矛盾の報告） | 矛盾には `矛盾あり` タグと留保の文を付ける。型付きエッジの候補も検討し、見送ったことも log に書く（補助規約） |

## 3. 前提の整理

### 3.1 wiki プラグインが提供するもの（事実）

コマンドは `/wiki:<名前>` で呼ぶ。init、ingest、query、graph、learn、evolve、lint、stats、upgrade、help の 10 本である。活用に関わるのは次の点である。

- **query** は `index.md` → 候補ページ →（見つからなければ）`wiki_search.py` のハイブリッド検索 →（関係を問う質問なら）`wiki_graph_query.py` の順に調べ、`[[wikilink]]` を出典に付けて答える。手順 6 で回答の synthesis への保存を提案する。保存の基準「3 か月後に似た質問をしたとき、これを見つけたいと思うか」は既にある（`query-workflow.md` 104 行）。rag の `search` は呼ばない。
- **ingest** は手順 7 で、`ontology.yaml` があり、ソースが明示的に裏づける場合に限って型付きエッジを追加し、graph の lint と extract を行う（`commands/ingest.md` 21 行、`ingest-workflow.md` 手順 8b）。型付きエッジの段は既にある。差分になり得るのは「毎回候補を検討し、見送りも記録する」という頻度の規約だけである。
- **graph** の `neighbors` は 1 ホップで予算がなく、`path` は出辺だけをたどる幅優先探索で、`status` や `valid_to` を見ない（`wiki_graph_query.py` 102〜173 行）。extract は `valid_from`、`valid_to`、`raw_ref`、`contradicts`、`supersedes` を `metadata_json` に保存しているので、鮮度の判定に使う材料は索引にある（`wiki_graph_extract.py` 343 行）。
- **lint** の古さの判定は「`updated` が 90 日より前で、被リンクが 3 以上」だけである（`wiki_lint.py` 324〜328 行）。グラフの lint は `status` の値の種類しか見ない。
- **learn** は観測した事実と原因の仮説を分けて記録し、`kind: experience-pattern` のページにまとめる。**evolve** は `.evolution/` に実験記録を残す。API のランナーは、レビュー済みの価格表が 2026-10-13 に期限切れで、レビューし直すまで実行を拒否する（`evolution-workflow.md` 117 行）。
- 検索は 1 回約 3.1 秒（`uv run --script` の起動とモデルの読み込みを含む、13 ファイルの標本での CLI の観測値）。統一レポートの「数十 ms」は常駐プロセス内のウォーム検索で、MCP の通信を含まない。どちらも統一レポートの記述で、本書では測り直していない（要確認）。

### 3.2 述語と型の制約（事実）

型付きの述語は 12 個で、主語と目的語の型が決まっている。concept どうしに使えるのは `depends_on` だけである。`cites` は source・paper・synthesis → paper・source、`contradicts` は claim・source・synthesis どうし、`supersedes` は claim・source・decision どうしに限られる。`decision`、`claim`、`raw` は `explicit_only` でページを持たないので、これらを目的語にすると lint がリンク切れを出す。

### 3.5 wiki の中身から借りた考え（事実）

作者の wiki の concept ページから、活用の案の源になる考えを借りた。[[コンテキストグラフ]]（焦点から 2〜3 ホップの射影をエージェントの作業記憶にし、構造・意味・時間で採点し、予算を超えた分を退去させる）、[[グラウンディング]]（行動の前に前提条件を検査し、取得・推論・検証を往復する）、[[コンテキストエンジニアリング]]（ウィンドウに入れる量と鮮度の設計）、[[名前付きグラフ]]（出所と時点の来歴）である。ただし、記事の 2〜3 ホップや重みの値は説明用で、選ぶ根拠は示されていない。

## 5. 発散：統合した 53 案

4 体が出した 149 案を、同じ発想のものはまとめて 53 案にした。括弧内は出した体と、その体の案番号である。この節では評価しない。★ は新しい実装なしで回る運用案で、収束 B の対象にした。

### I 作業の文脈に知識を差し込む

1. ★セッションの開始時に、今回の目的と制約を添えて定型の質問を `/wiki:query` に投げる（A2、B3・5、C2、D1）
2. セッション開始ブリーフをフックで自動生成する。ブランチ名や変更ファイルを焦点に、予算内の要約を渡す（A1、B1）
3. 目的・焦点・予算つきのコンテキストの切り出し。k ホップの近傍を構造・意味・時間で採点し、行数の予算で切る（A21・1、B2、C1、D17）
4. ★設計の前に、計画と wiki の決定やパターンの食い違いを問う（A4、B3、C2、D1）
5. ★不具合のときに症状から経験のパターンを引き、原因仮説と反証の手順を作る（A5、B4、C18、D11）
6. ★レビューの観点を、`experience-pattern` の反例と適用範囲から作る（A6、B18、D11）
7. ★前提になる概念から読む「学習の順路」を neighbors と本文から組む（A22、C15、D6）
8. ★次のセッションへの引き継ぎ（確定した判断、残った問い、参照先）を作る（D9）

### II 検証、鮮度、矛盾、出典

9. 回答に出典チェーン（主張 → ページ → source → raw）または根拠の束を自動で添える（B7、C3、D18。A11 は運用版）
10. ★回答で、wiki の要約で言えることと raw まで確かめたことを分け、`confidence` と `status` を添える（A14、B13、C24、D4）
11. ★重要な主張だけ raw の原文まで照合する（A11、B15、C24、D4）
12. synthesis の陳腐化・再確認候補の検出。`sources_consulted` の参照先が保存後に変わったら知らせる（A10、B8、C5、D19）
13. 型付きエッジの時間の整合 lint。`valid_to` 超過の `current`、`superseded` を指す参照、source より古い派生ページ（A9、B8、D13）
14. ★矛盾と未決の台帳。手で synthesis に置く版と、lint が `contradicts` と `矛盾あり` タグから自動生成する版（A12、B10・11、C9、D24）
15. ★検証状態（unverified / machine-checked / human-reviewed）の規約と集計（B13・14）
16. 行動前の前提条件の検査。計画の前提を決定、`experience-pattern`、見直す条件に照らし、成立・不成立・不明で返す（A3、B9、C31、D23）
17. 時点と状態を指定した事実の取得（`facts --as-of`）（A23、C11、D22）
18. Web ソースを取り直し、版の差分を取る。O-14（A15、B42）

### III 取り込みのときに構造と理解を育てる

20. ★取り込みごとに型付きエッジの候補を検討し、見送ったことも log に書く（B39）
21. 型付きエッジの候補の文をスクリプトで抽出し、人が承認する（A17、B40）
22. ★分野の述語を `ontology.yaml` に足す。上位オントロジーに anchor してから coin する（A18、B41）
23. オントロジーの述語から、資料への確認質問（誰が提案したか、何に依存するか）を作る（D25）
24. ★日本語と英語の `aliases` を充実させる（A20）
25. ★取り込みのあとに「次にどの判断で使うか」を 1 つ決める（C7）

### IV グラフ上の推論と鳥瞰

26. ★関係を問う質問に `neighbors` と `path` を使う習慣（A25、D6）
27. 依存関係の影響範囲の分析。方向と述語を限定して到達する候補と確認順を出す（C14）
28. オントロジー変更の影響検査。述語や型を変える前に不適合になるエッジを示す（C13）
