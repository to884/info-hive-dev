# wiki の MCP サーバーと検索の基盤の実装の記録（2026年11月6日）

ADR-0012（wiki の MCP サーバー）と ADR-0011（埋め込み、ベクトル索引、語彙検索）を、`info-hive-wiki` に実装した。範囲は、優先順位のレポート（`feature-priority-2026-11-06.md`）の「3. MCP サーバーと検索の基盤の移行」の段階 1、2、4 である。段階 3（`lint`、`stats`、`graph`）と段階 5（コマンドを MCP のツールに移す）は含めない。

測定の JSON は [wiki-mcp-server-2026-11-06/](wiki-mcp-server-2026-11-06/) に、試験と測定のスクリプトは `tests/wiki/` に置いた。

## 結論

- 評価ゲート（en と ja）は、ADR-0011 の構成で合格した。基準値（今の e5-small の構成）からの低下はなく、ハイブリッドの MRR は en で 0.721 から 0.731、ja で 0.954 から 0.963 に上がった。
- 中継経由の `query` は p95 で 35〜38 ms、今の CLI のハイブリッド検索（1 回ごとに起動）は p95 で 3.6〜3.9 秒だった。
- 中継経由の上乗せ（同じ処理の直接呼び出しとの p95 の差）は 4.7〜11.2 ms で、ADR-0012 の目安（15 ms）に収まった。
- Claude Code のデスクトップアプリは、アプリ本体から下のプロセスを 1 つのジョブに入れている。そのジョブには KILL_ON_JOB_CLOSE がなく、`claude -p` が終わったあともサーバーは残った。
- 試作のジョブの確かめ方に誤りがあった。ADR-0012 の「CLI はサーバーをジョブに入れなかった」は、測り直しが要る（後述）。

## 作ったもの

| 段階 | ファイル（`info-hive-wiki/`） | 中身 |
| --- | --- | --- |
| 1 | `.mcp.json`、`wiki_mcp_relay.py`、`wiki_mcp_server.py`、`wiki_mcp_common.py` | stdio の中継と、127.0.0.1 の streamable HTTP のサーバー。ロックで 1 つだけ起動し、トークンと Host ヘッダーを ASGI のミドルウェアで確かめ、JSON で応答し、要求がない状態が 15 分続くと止まる |
| 2 | `wiki_index.py`、ツール `query`、`get_page`、`list_index` | ruri-v3-130m の ONNX、usearch、Tantivy（wiki の bigram）、RRF。索引は wiki の外に置く |
| 4 | ツール `index_chunks` | rag がチャンクを渡す口。collection ごとに wiki と別の索引に入れ、文書ごとに古い世代を消す |

`wiki_search.py` の CLI は変えていない。MCP が使えないときの戻り道として、そのまま動く。

### ADR からの細部の判断

ADR の決定は変えていないが、実装の細部で次の判断をした。どれも定数か小さな変更で戻せる。

| 判断 | 理由 |
| --- | --- |
| ベクトルが 50,000 件以下の索引は、HNSW ではなく総当たりで探す（usearch の `exact=True`）。HNSW の索引は ADR のパラメーターで作り、それより大きい索引で使う | HNSW のグラフは作るたびに少し変わり、評価セットの 103 件の索引でも、作り直すと 32 問中 13 問で意味の検索の順位が変わった。総当たりにすると 0 問になった |
| サーバーは `uv sync --script` で依存を入れ、`uv python find --script` で見つけた python を `DETACHED_PROCESS` で起動する | ADR の「venv の python.exe を子として起動する」に合わせた。`uv run` を子にすると、コンソールの窓が出るおそれがある |
| 索引のディレクトリごとに OS のファイルロックを取る | 止まりかけのサーバーが索引を閉じ終える前に、次のサーバーが同じ索引を開くことを防ぐ（書き手を 1 つにする ADR-0011 の規則の補強） |
| `index_chunks` の語彙のトークンは呼び出し側（rag）が作る | wiki のサーバーに Sudachi の辞書を持たせないため。rag は今も Sudachi で分かち書きしている |
| 中継は、接続が切れたら待っている呼び出しを取り消し、つなぎ直して 1 回だけやり直す | mcp 1.30 のクライアントは、サーバーが止まると待っている要求に応答を返さず、待ち続けた |
| 要求の本文の上限を 64 MiB にした | mcp の既定の 4 MiB では、ベクトルつきの `index_chunks` が数百件で上限に当たる |
| 待機で止まるまでの既定を 900 秒にした | ADR は「一定の時間」とだけ決めている。`INFO_HIVE_MCP_IDLE_SECONDS` で変えられる |

## 評価ゲート

`tests/wiki/run_mcp_gate.py` で、`eval/retrieval/run_eval.py` の `--gate` と `--baseline` を、新しい基盤で動かした。page はページ単位の BM25（今の CLI のまま）、section は Tantivy の語彙だけ、hybrid は Tantivy と埋め込みの融合である。

| セット | 方式 | recall@10 | MRR | fp_rate | 基準値の recall@10 / MRR | E8 の r130-tantivy の MRR |
| --- | --- | --- | --- | --- | --- | --- |
| en | page | 0.630 | 0.630 | 0.000 | 0.630 / 0.630 | 0.630 |
| en | section | 0.630 | 0.630 | 0.000 | 0.630 / 0.630 | 0.630 |
| en | hybrid | 0.963 | 0.731 | 0.000 | 0.926 / 0.721 | 0.698 |
| ja | page | 0.972 | 0.922 | 0.000 | 0.972 / 0.922 | 0.922 |
| ja | section | 0.972 | 0.901 | 0.000 | 0.972 / 0.901 | 0.901 |
| ja | hybrid | 1.000 | 0.963 | 0.000 | 1.000 / 0.954 | 0.963 |

- どちらのセットも、ゲート、基準値、キャッシュの一致の 3 つに合格した。
- 融合を E8 が測った wiki の既定（k 60、重み 1.0、候補 50）にすると、en の hybrid の MRR は 0.698 で、E8 の値と同じになった。ADR-0011 の設定（k 30、重み 0.5、候補 200）で 0.731 に上がる。
- 最初の測定では、ADR の設定の en の MRR が 0.731 と 0.699 に揺れた。原因は HNSW の作り直しによる順位の揺れで、総当たりにしてからは揺れない。

## 速さ

`tests/wiki/bench_mcp_latency.py` で、評価セットのクエリ全部を 3 回ずつ流した（en 96 回、ja 159 回）。CLI は各セットの先頭 15 問。Windows 11、16 論理コアの 1 台の PC で測った。

| セット | 中継経由の MCP 中央値 / p95 | 直接呼び出し 中央値 / p95 | 上乗せの p95 | 今の CLI（ハイブリッド）中央値 / p95 | 今の CLI（語彙だけ）中央値 / p95 |
| --- | --- | --- | --- | --- | --- |
| en | 30.0 / 35.3 ms | 21.0 / 24.2 ms | 11.2 ms | 3,489 / 3,625 ms | 205 / 242 ms |
| ja | 29.9 / 38.0 ms | 22.3 / 33.3 ms | 4.7 ms | 3,679 / 3,927 ms | 213 / 218 ms |

- 直接呼び出しは、サーバーの `query` と同じ処理（wiki の変更の確認と検索）を同じプロセスで呼んだ値である。中央値の差は en、ja とも約 8〜9 ms で、試作の値（MCP の SDK の 1 回の処理が約 9 ms）と合う。
- 優先順位のレポートの「今の CLI の検索は 1 回に約 3.1 秒」に対し、この測定では 3.5〜3.7 秒（中央値）だった。大きくは違わない。
- 中継で呼び出しのたびにサーバーの生存を確かめていた最初の版は、上乗せの p95 が 20〜32 ms だった。確かめるのを、前の呼び出しから 1 秒以上空いたときだけにして収めた。
- 埋め込みのスレッド数を 4 に絞っても、上乗せは減らなかった（18〜22 ms、生存の確認を減らす前の測定）。

### 起動とメモリ

| 項目 | 値 |
| --- | --- |
| 中継の initialize（サーバーはまだ起動しない） | 1.7 秒 |
| 最初の tools/list（サーバーの起動、依存の確認、待ち受けまで） | 2.4 秒 |
| 最初の query（モデルの読み込みと、en の 103 セクションの埋め込み） | 3.6 秒 |
| モデルを読み込んだサーバーのメモリ | RSS 0.96 GiB、private 1.47 GiB |

- 依存（約 1 GB）とモデル（約 530 MB）は取得済みの状態で測った。初めて使うときの取得の時間は測っていない。
- uv がスクリプトの環境を作った直後の最初の import は、1〜3 分かかった（DLL の初回の読み込みと考えられる）。2 回目からは上の値になる。
- メモリは、追加測定 E6 の 2.53 GiB（private）より小さい。この測定のセクションは短く、onnxruntime が大きな領域を確保しなかったためと考えられる。長い文書の wiki では増える。

## 試験

`tests/wiki/test_wiki_index.py`（13 件）と `tests/wiki/test_mcp_server.py`（10 件）がすべて通った。

- ADR-0001 の 3 条件: トークンのない要求と違うトークンの要求は 401、Host ヘッダーが `127.0.0.1:<ポート>` でない要求（`localhost` を含む）は 421、待ち受けは 127.0.0.1 だけで、ほかのアドレスからは接続できない。
- 中継を 4 つ同時に起動しても、サーバーは 1 つだった。中継が終わってもサーバーは残り、次の中継がそれを使った。
- サーバーが待機で止まったあと、同じ中継からの呼び出しでサーバーを起動し直した。呼び出しの途中でサーバーを止めても、中継がつなぎ直してやり直した。
- コードの版が違うサーバーは止めて起動し直した。
- 索引の更新の途中で止まった状態（dirty の印、usearch のファイルの欠落、Tantivy の文書の欠落）から、次に開いたときにそろえ直した。Tantivy の commit の失敗は rollback して入れ直した。

## デスクトップアプリでの起動

`tests/wiki/check_claude_spawn.py` を、デスクトップアプリのセッションの中から実行した。デスクトップアプリ（Claude 4.16336.0.0、MSIX）は、アプリ本体（Claude.exe）の子として CLI（claude.exe 2.1.317）を動かし、stdio の MCP サーバーはその CLI の子として起動される。スクリプトは、同じ CLI で `claude -p` を 1 回実行し、中継を `--mcp-config` で登録した。

| 項目 | 結果 |
| --- | --- |
| デスクトップアプリのジョブ | アプリ本体から下のプロセスがすべて 1 つのジョブに入っている（約 120 プロセス）。制限の旗は 0x0 で、KILL_ON_JOB_CLOSE も BREAKAWAY_OK もない |
| 中継とサーバーの起動 | `claude -p` が中継を起動し、中継がサーバーを起動した。`list_index` の結果が返った |
| `claude -p` の終了後 | サーバーは残った。サーバーはデスクトップアプリのジョブに入っている |

- サーバーはジョブから抜けられない（BREAKAWAY_OK がない）が、ジョブを閉じても止められない（KILL_ON_JOB_CLOSE がない）。セッションをまたいでサーバーを共有できる。
- デスクトップアプリを終了したときに、ジョブの中のサーバーが止まるかは確かめていない。止まっても、次の呼び出しで中継が起動し直す。
- 新しいデスクトップアプリのセッションを開き、プラグインの `.mcp.json` から起動する経路そのものは確かめていない。マーケットプレイスは `info-hive-wiki` の main を配るので、ブランチの版をアプリに入れられなかった。`claude -p` は同じ CLI の同じ起動の経路を通る。

### 試作のジョブの確かめ方の誤り

試作の `poc/rag/decision/mcp_probe/job_check_server.py` は、`GetCurrentProcess()` の疑似ハンドル（-1）を ctypes の既定の int で渡している。64 ビットのハンドルが切り詰められ、ジョブの中にいても `in_job: false` を返す。同じ場所で型を指定して測ると `in_job: true` になった。`claude-job-check.json` と ADR-0012 の理由の「Claude Code（CLI 2.1.316）は stdio の MCP サーバーをジョブに入れなかった」は、この誤りの上にある可能性が高い。

ただし、結論（サーバーがセッションの後も残る）は今回の測定でも変わらない。ジョブに入ってはいるが、KILL_ON_JOB_CLOSE がないためである。ADR-0012 の文言を直すかは、ユーザーの判断に任せる。

もう 1 つ、uv の venv の python.exe（起動用のプログラム）は、本体の python を KILL_ON_JOB_CLOSE と SILENT_BREAKAWAY_OK のジョブに入れる。ジョブを自分のプロセスから測ると、このジョブが見える。`check_claude_spawn.py` は子プロセスから測り、その外側のホストのジョブを記録している。

## 残った課題

- 初めて使うときは、サーバーの依存（約 1 GB）を取得するあいだ、中継の最初の `tools/list` が返らない。ホストの待ち時間を超えると、そのセッションではツールが見えないおそれがある。取得の時間と、Claude Code の待ち時間は確かめていない。
- 初回の再埋め込みは、wiki 規模で長くかかる（ADR-0011）。サーバーは裏で埋め込みながら、語彙検索と埋め込み済みの分で答える。大きな wiki での時間は測っていない。
- サーバーが止まるときに uvicorn が `ASGI callable returned without completing response` を 1 行ログに出す。中継が開いたままにする GET の流れを切るときのもので、動作には影響しない。
- macOS と Linux では動かしていない。置き場所（XDG）と POSIX の起動（新しいセッション）は書いたが、確かめていない。
- 段階 3（`lint`、`stats`、`graph`）、段階 5（コマンドの移行）、rag の移行は、この作業に含めていない。
