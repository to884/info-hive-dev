作成日：2026年11月3日（日本時間）
対象：info-hive に足す、日々の予定、タスク、メモを扱う機能（プラグイン `daily`、コマンド `/daily:*`）
手法：brainstorm-diverge-converge（発散 → クラスタ → 収束）。採点は筆者と、基準と重みだけを渡した別のエージェントの 2 者で独立に行い、平均した

## 1. 結論の要約

この検討は、日々の記録を info-hive でどう扱うかを決め、次の ADR と設計書の入力にするために行った。主な結論は、単一の方法論を選ぶのでなく、記録の仕方と整理の仕方を別の方法論から借りて組み合わせ、整理の側をエージェントに任せることである（提案）。

1. **器は Daily Notes、書き方は Interstitial Journaling にする。** 1 日 1 ファイルを開き、作業の切れ目に時刻付きの一行を書く。2 者の採点で、この 2 つと Engineering daybook、Bullet Journal の 4 つが上位を占めた（Interstitial Journaling 109 点、Daily Notes 107 点、満点 130 点）。GTD、PARA、Zettelkasten は 49〜71 点で下位だった。書く時点で分類先を決める作業を求めるので、入力が重くなる。
2. **整理の工程は、Bullet Journal と GTD から借りてエージェントの仕事にする。** 未完了のタスクを翌日に写す Bullet Journal の Migration と、GTD の収集箱と週次レビューを、`plan`、`close`、`tidy`、`review` の各コマンドが担う。人は書くだけで、構造は後から LLM が整える。
3. **作業メモは `- [ ] 10:45-11:30 内容 @wait(理由)` の 1 行で書く。** 状態の正本は Markdown 標準のチェックボックス `[ ]` `[x]` で、補助の状態は行末の `@タグ` で持つ。開始時刻だけがある行を「進行中」とみなすので、進行中を表す記号は要らない。GitHub Flavored Markdown（GFM）のタスクリストが認めるのは空白と `x` だけで、`[/]` や `[>]` はただの文字として表示される（事実、第9節）。
4. **wiki とは別のプラグイン `daily` にする。** wiki の lint は、被リンクのないページを全て「孤立」として報告する（`wiki_lint.py` の 280 行目）。日付ノートを wiki に入れると、孤立の指摘が毎日 1 件ずつ増える。検索結果にも作業ログが混ざり、`index.md` は 150 ページで分割する規約（`SKILL.md` の 94 行目）に、日付ノートだけで 150 日ほどで達する。
5. **最初の段階で作るコマンドは `log`、`start`、`stop`、`plan`、`close` の 5 つにする。** `tidy` と `review` を次の段階に、ノウハウを取り出すコマンドを最後に回す。日付ノートは raw に近い一次資料とし、残す価値のあるものはユーザーが `notes/` で手を入れてから、`/wiki:ingest` で wiki に入れるかを決める。この扱いは 2026年11月3日に決定者が決めた（第7.1節）。

## 2. 問題定義と評価基準

### 2.1 問題

info-hive の `wiki` プラグインは、取り込んだ資料から知識のページを作る。一方で、その日の予定、手を付けたタスク、思いついたことを書き留める場所はない。日々の記録を、軽い入力で 1 日 1 ファイルに残し、後から LLM が整理できるようにしたい。

**判断対象**：次の 4 つを決める。

- (a) どの方法論、または組み合わせを採るか
- (b) 1 日 1 ファイルの形式
- (c) エージェントによる入力支援のコマンドの範囲
- (d) `wiki` に足すか、別のプラグインにするか

### 2.2 要件と制約

| 項目 | 内容 | 区分 |
| --- | --- | --- |
| 書き散らし | 書き散らしても、後で LLM が整理できる | 確定 |
| 入力 | 記入が負担にならないシンプルな入力 | 確定 |
| 支援 | エージェントによる入力支援の機能を足す | 確定 |
| ファイル | 1 日が 1 ファイル | 確定 |
| 作業メモ | 開始時刻、終了時刻、タスクの状態、一行のタスクの内容を書く | 確定 |
| 入力経路 | Claude Code のデスクトップ版アプリから入力する | 確定 |
| 正本 | Markdown が正本で、索引や集計は再生成できる派生データ | 事実（wiki と同じ原則） |
| 文字列 | 本文と見出しは日本語。frontmatter のキー、`type` の値、`--json` のキーは英語 | 事実（AGENTS.md の方針 B） |
| 実行環境 | Python 3.10 以上と uv だけで動く。入出力は UTF-8 を明示する | 事実（wiki と同じ） |
| PC 固有の値 | 保存先のパスなどは既定値と設定で扱い、仕様に書かない | 確定（2026年11月2〜3日の方針） |

### 2.3 必須条件による除外

次の条件を満たさない案は、採点の前に除いた。

- 1 日 1 ファイルの Markdown で、エディタで素のまま読める
- 作業メモの 1 行で、開始時刻、終了時刻、状態、内容を表せる
- Claude Code のチャットから、スラッシュコマンドで入力できる

この条件で、YAML のリストに記録する案（発散の 31）と、CSV や JSONL を正本にする案（32）を除いた。どちらも人がエディタで読み書きしにくい。方法論は、日付を器にしないもの（GTD、PARA など）も、整理の工程の部品として使える可能性があるので除かずに採点した。

### 2.4 評価基準

| 基準 | 重み | 何を見るか |
| --- | --- | --- |
| 書き散らし耐性 | 3 | 構造を崩して書いた入力でも、LLM が後から整理できるか |
| 入力の軽さ | 3 | 1 行書くのに要る判断と文字数 |
| エージェント支援との相性 | 2 | 整理、繰り越し、集計の手順を機械的に決められるか |
| 作業メモの表現力 | 2 | 開始、終了、状態、内容を自然に書けるか |
| 1 日 1 ファイルとの適合 | 2 | 日付を器にする設計と合うか |
| 実装の単純さ | 1 | 解析のスクリプトと手順の量 |

重みは、要件の 6 項目のうち最初の 2 つ（書き散らしと入力の軽さ）を最も重く見た。どちらも依頼の冒頭に置かれている。実装の単純さは、wiki の部品を流用できるので差がつきにくいと見て、重みを 1 にした。

## 3. 前提の整理

### 3.1 wiki プラグインの現状（事実）

- ページの `type` は `source`、`entity`、`concept`、`synthesis` の 4 つである。日付ノート、タスク、予定、収集箱（inbox）を表す型も語彙もない。
- `log.md` は `ingest`、`query`、`lint`、`schema`、`shard` の操作を記録するログで、lint と検索の対象から外れている。
- `wiki_lint.py` は `wiki/` の下の `.md` を再帰的に読む。外すのは `SCHEMA.md`、`index.md`、`log.md`、`README.md` と、`indexes/`、`graph/`、`raw/`、`.evolution/` の下だけである（107〜108 行目）。
- 被リンクが 1 つもないページは、全て孤立として報告される（280 行目）。更新の止まったページの判定は、90 日以上更新がなく、被リンクが 3 以上のときだけ働く（338 行目）。日付ノートはほとんど孤立の判定にかかる。
- `type` の値は集合と照らして検査していない。`wiki_text.py` の別名表で英語に直すだけなので、`type: daily` と書いても lint は通る（別のエージェントが読んで報告した）。
- `wiki_search.py` は、上の除外を除く全てのページを BM25 と埋め込みで検索する。`--type`、`--tag`、`--since` で絞り込める。
- `init_wiki.py` の `SUBDIRS`、`page.md.template`、`SCHEMA.md.template`、`ontology.yaml.template` は、4 つの `type` を前提に書かれている。
- `index.md` は約 300 行か約 150 ページで分割する規約がある（`SKILL.md` の 94 行目、`wiki_stats.py` の 191〜193 行目）。

### 3.2 プラグインを足す手順（事実）

ADR-0003 と AGENTS.md に手順がある。`to884/info-hive-<名前>` のリポジトリを作ってこのリポジトリのサブモジュールにし、`info-hive-marketplace/.claude-plugin/marketplace.json` に 1 項目を足す。コマンド名には必ずプラグイン名が付くので、プラグイン名 `daily` のコマンドは `/daily:log` の形になる。

### 3.3 規模の仮定

1 日に書く行は 10〜40 行、1 年で 365 ファイルと推定した。行数は PoC で実測する。ファイル 1 つは数 KB に収まるので、走査と検索の速さは問題にならない。

## 4. 発散：選択肢の全リスト（52 案）

この節では評価をせずに案を並べた。

### A. 整理の枠組み（方法論）

1. GTD。収集、処理、整理、見直し、実行の 5 段階と、週次レビュー
2. PARA。Projects、Areas、Resources、Archives の 4 分類
3. Zettelkasten。走り書きを恒久ノートに書き直し、リンクでつなぐ
4. Daily Notes。Roam Research、Obsidian、Logseq の流儀で、1 日 1 ページに書き、日付でリンクする
5. Bullet Journal。短い記号で書く Rapid Logging、未完了を写す Migration、Index、Future Log
6. Interstitial Journaling。タスクとタスクの合間に、時刻付きの短いメモを書く
7. Org-mode の流儀。見出しをタスクにし、`TODO` キーワードと `CLOCK:` 行で状態と時間を記録し、clocktable で集計する
8. Time blocking と Time boxing
9. Pomodoro
10. 個人の Kanban。列を状態にし、同時に進める数を制限する
11. Eisenhower マトリクス
12. Ivy Lee メソッド。翌日にやる 6 件を前の晩に決める
13. 1-3-5 ルール
14. Commonplace book（抜き書き帳）
15. LYT と MOC（Maps of Content）
16. Johnny.Decimal
17. GTD の週次レビューだけを切り出して使う
18. 日報の三部構成。朝の予定、夕方の実績、所感
19. Engineering daybook や lab notebook。追記するだけで、書き直さない
20. Logseq のジャーナル。アウトライナーとブロック参照
21. 5 年日記。過去の同じ日の記録を並べて見せる
22. OKR や週次目標

### B. 行の文法（時間と状態の書き方）

23. todo.txt。`(A)` の優先度、`+project`、`@context`、`due:`
24. TaskPaper。アウトラインと `@tag(値)`
25. Dataview の流儀のインライン属性（`key:: value`）
26. Obsidian Tasks の流儀の絵文字によるメタデータ（📅 ⏳ ✅）
27. タスクリストの記号を増やす（`[ ]` `[x]` `[>]` `[-]` `[/]`）
28. Markdown の表に開始、終了、件名を書くタイムシート
29. 開始と終了を別の行に書く（`- 09:12 ▶ 内容`、`- 10:40 ■`）
30. 1 行に時間の範囲を持たせる（`- [x] 09:12-10:40 内容`）
31. frontmatter の `tasks:` に YAML のリストで持つ
32. CSV や JSONL を正本にし、Markdown は表示用にする

### C. 入力経路

33. `/daily:log <一行>` で、今の時刻を付けて追記する
34. `/daily:start <内容>` と `/daily:stop` で時間を計る
35. 自由な文を渡すと、LLM が記法に沿った行に書き直す
36. 書き散らし用の節を置き、整理のコマンドで振り分ける
37. 朝の対話で、前日の未完了の繰り越しを提案する
38. 夕方の対話で、終了時刻を埋め、未完了を繰り越しの候補にする
39. Git のコミットログから作業メモの下書きを作る
40. Claude Code のフック（SessionStart、Stop）で自動的に記録する
41. VS Code の Foam の日付ノートのテンプレートと共用する
42. クリップボードや音声の文字起こしを取り込む
43. 予定をカレンダーの ICS ファイルから取り込む
44. 曜日ごとの定期タスクのテンプレート

### D. LLM による整理と見直し

45. `tidy`。書き散らしを分類し、状態を更新する
46. `review --week`。週次レビューの下書きを作る
47. 未完了のタスクを自動で繰り越す（Bullet Journal の Migration）
48. 繰り返し出る概念を `/wiki:ingest` に渡して wiki に入れる
49. タイムシートの集計（Org-mode の clocktable に当たるもの）
50. 月ごとの索引や Future Log を作る

### E. プラグインの配置

51. `wiki` に `type: daily` を足す
52. 別のプラグインを作り、wiki とは必要なときだけ連携する

## 5. クラスタ：7 つのテーマ

案は、書き手がいつ何をするかで分けた。方法論の層（1〜3）、1 行の書き方の層（4）、書く経路の層（5）、書いた後の層（6）、置き場所の層（7）である。

| テーマ | 含む案 | 性格 |
| --- | --- | --- |
| 1. 書く前に分類を決める枠組み | 1, 2, 3, 15, 16, 17, 22 | 分類先や目標を先に決める。整理の質は高いが、入力のたびに判断が要る |
| 2. 日付を器にする記録法 | 4, 5, 6, 18, 19, 20, 21 | 今日のファイルに順に書く。分類は後に回せる |
| 3. 実行と優先順位の技法 | 8, 9, 10, 11, 12, 13 | どれを先にやるかを決める。記録の形式は決めない |
| 4. 1 行の文法 | 23〜32 | 状態と時間を 1 行にどう書くか |
| 5. 入力の経路 | 33〜44 | 誰が、いつ、どこから書くか |
| 6. LLM による整理と見直し | 45〜50 | 書いた後に構造を与える |
| 7. プラグインの配置 | 51, 52 | wiki との関係 |

テーマ 1 と 2 は対になる。テーマ 1 は書く前に構造を決め、テーマ 2 は書いた後に構造を与える。要件の「書き散らしても後で整理できる」は、テーマ 2 とテーマ 6 の組み合わせを指している。

## 6. 収束：評価と選定

### 6.1 採点の進め方

方法論の 16 件を、6 つの基準で 1〜10 点で採点した。筆者のほかに、別のエージェント（Claude Code の Plan エージェント）に要件、基準、重みだけを渡し、筆者の採点を見せずに採点させた。そのエージェントは klog（プレーンテキストで時間を記録する形式）を候補に加え、Logseq ジャーナル、Ivy Lee、Pomodoro は採点しなかった。2 者が採点した項目は平均し、片方だけの項目はその点を使った。合計は重みをかけた和で、満点は 130 点である。

### 6.2 採点の結果

| 方法論 | 書き散らし ×3 | 入力 ×3 | 支援 ×2 | 表現力 ×2 | 1日1ファイル ×2 | 単純さ ×1 | 合計 | 2 者の合計 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Interstitial Journaling | 8.5 | 8.5 | 7.5 | 8 | 9.5 | 8 | **109** | 114 / 104 |
| Daily Notes | 9 | 9 | 7 | 5 | 10 | 9 | **107** | 107 / 107 |
| Engineering daybook | 9 | 8.5 | 6.5 | 6 | 9 | 9 | **104.5** | 107 / 102 |
| Bullet Journal | 8 | 8 | 8.5 | 6 | 9 | 7 | **102** | 103 / 101 |
| Logseq ジャーナル | 8 | 8 | 6 | 6 | 10 | 5 | 97 | 筆者のみ |
| TaskPaper | 6 | 7.5 | 8 | 7.5 | 5.5 | 7 | 89.5 | 88 / 91 |
| 日報の三部構成 | 5.5 | 5.5 | 8 | 6 | 10 | 8 | 89 | 94 / 84 |
| klog | 4 | 7 | 8 | 9 | 7 | 5 | 86 | 別のエージェントのみ |
| todo.txt | 5.5 | 7.5 | 8 | 6 | 3.5 | 7.5 | 81.5 | 80 / 83 |
| Ivy Lee | 3 | 8 | 7 | 4 | 8 | 8 | 79 | 筆者のみ |
| Org-mode の TODO と CLOCK | 5.5 | 4.5 | 7 | 10 | 5 | 4 | 78 | 81 / 75 |
| Time blocking | 3 | 4.5 | 6.5 | 6.5 | 8 | 6 | 70.5 | 74 / 67 |
| GTD | 7 | 5.5 | 8 | 3.5 | 3 | 4 | 70.5 | 70 / 71 |
| Pomodoro | 3 | 6 | 5 | 5 | 6 | 7 | 66 | 筆者のみ |
| 個人の Kanban | 4 | 5.5 | 6.5 | 6 | 2.5 | 5.5 | 64 | 68 / 60 |
| PARA | 4.5 | 4 | 6.5 | 2 | 2 | 4.5 | 51 | 49 / 53 |
| Zettelkasten | 4.5 | 4 | 6.5 | 1.5 | 2 | 3.5 | 49 | 56 / 42 |

「2 者の合計」は、筆者 / 別のエージェントの順に書いた。

点の根拠のうち、結論を左右したものを挙げる。

- **Interstitial Journaling は、作業メモの要件にいちばん近い。** 時刻付きの一行を順に書くので、開始と終了が時刻の並びから分かる。状態は書かないので、表現力は 8 点にとどまる。
- **Daily Notes は器としては満点に近いが、作業メモの文法を持たない。** 表現力は 2 者とも 5 点だった。器を Daily Notes にし、中の書き方を Interstitial Journaling で補う、という組み合わせの理由はここにある。
- **Bullet Journal は、エージェント支援で最も点が高い（8.5 点）。** 未完了を写す Migration は、前日のファイルの未完了の行を今日に写す処理として、そのまま書ける。紙の手帳では人が書き写すが、エージェントが代わりにやれば入力の負担にならない。
- **Org-mode は表現力が 10 点で、要件に完全に合う。** 一方で、`CLOCK: [2026-11-03 火 09:12]--[2026-11-03 火 10:40] =>  1:28` のような行は手で書くには長く、Markdown でもない。入力と単純さで点を落とした。
- **GTD、PARA、Zettelkasten は、書く時点で分類先を決めさせる。** 1 日 1 ファイルとの適合も 2〜3 点だった。ただし GTD は、書き散らし耐性（7 点）とエージェント支援（8 点）が高い。「収集箱に何でも入れ、後で処理する」という考え方は、整理の工程として借りる価値がある。

2 者の点が 2 点以上違ったのは、次の項目である。

- Zettelkasten の入力の軽さは、筆者が 5 点、別のエージェントが 3 点だった。別のエージェントは「書く時点で 1 つの考えに絞る作業が要る」点を重く見た。
- 日報の作業メモの表現力は、筆者が 7 点、別のエージェントが 5 点だった。筆者は「夕方の実績」に時刻を書ける点を見て、別のエージェントは形式が時刻を求めない点を見た。
- Org-mode の 1 日 1 ファイルとの適合は、筆者が 6 点、別のエージェントが 4 点だった。Org-mode は時間の記録がタスクの下に付くので、日付ごとのファイルにすると同じタスクが複数の日に分かれる。

いずれも上位 4 案の順位には影響しない。

| 全ての重みを 1 にする | Interstitial 50 | Daily Notes 49 | daybook 48 | Bullet Journal 46.5 | TaskPaper 41.5 |
| 作業メモの表現力の重みを 4 にする | Interstitial 125 | Daily Notes 117 | daybook 116.5 | Bullet Journal 114 | TaskPaper 104.5 |
| 筆者の点だけを使う | Interstitial 114 | Daily Notes 107 | daybook 107 | Bullet Journal 103 | Logseq 97 |
| 別のエージェントの点だけを使う | Daily Notes 107 | Interstitial 104 | daybook 102 | Bullet Journal 101 | TaskPaper 91 |

表現力の重みを 4 に上げると、klog（104 点）と TaskPaper（104.5 点）が 5 位まで上がる。どちらも時間と状態の書き方に強い。そこで、1 行の文法には TaskPaper の行末の `@タグ` を借り（第6.5節）、klog の「時刻の範囲で 1 行を始める」書き方も取り入れた。

### 6.4 組み合わせの構成

上位 4 案は互いに排他ではなく、受け持つ層が違う。書く層と整理する層に分けて組んだ。

| 層 | 借りる方法論 | 何をするか |
| --- | --- | --- |
| 器 | Daily Notes | 1 日 1 ファイル。日付がファイル名と frontmatter に入る |
| 書く | Interstitial Journaling、Engineering daybook | 作業の切れ目に時刻付きの一行を足す。書き直さず、追記していく |
| 1 行の文法 | Markdown のタスクリスト、TaskPaper、klog | 状態は `[ ]` `[x]`、時刻は行頭、補助の状態は行末の `@タグ` |
| 整理する | Bullet Journal の Migration、GTD の収集箱と週次レビュー、日報の夕方の実績 | 繰り越し、書き散らしの振り分け、ふりかえりの下書きをエージェントが作る |

この組み合わせを、次点と代替の構成と比べた。

| 構成 | 要件を満たすか | 利点 | 欠点 |
| --- | --- | --- | --- |
| 推奨：上の組み合わせ | 全て満たす | 書くときは時刻と一行だけで済む。標準のタスクリストを壊さない | 整理のコマンドが 4 つ要る |
| 次点：日報の三部構成だけ | 作業メモの要件を満たさない | 朝と夕方に書くだけで、さらに軽い | 開始と終了の時刻が残らない |
| 代替：記号を増やしたタスクリスト | 全て満たす | Bullet Journal に近く、状態が一目で分かる | GFM では `[/]` や `[>]` がただの文字になる（第9節）。ユーザーの決定で採らない |

### 6.5 1 日 1 ファイルの形式（提案）

> 2026年11月3日に、決定者がこの形式を [ADR-0006](../adr/0006-daily-journal-is-separate-plugin.md) で次のように改めた。最新の形は ADR-0006 にある。この節は、検討した時点の案として残す。
>
> - 作業メモとタスクを別の節に書く。作業メモは一行で簡潔に書き、詳細はタスクの側に書く
> - タスクの節を「前日からの繰り越し」「本日のタスク」「次回への繰り越し」の 3 つの小節に分ける
> - その日に起きた問題や突発的な出来事を書く節を足す
> - テンプレートを Foam の置き場 `.foam/templates/daily-note.md` に置く

ファイル名は `<保存先>/YYYY-MM-DD.md` にする。保存先の既定は第7.1節で決める。

```markdown
---
type: daily
title: "2026-11-03"
date: 2026-11-03
tags: []
created: 2026-11-03
updated: 2026-11-03
---

## 予定
- 10:00-11:00 定例

## タスク
- [x] 09:12-10:40 browse 設計の調査 #info-hive
- [ ] 10:45- daily プラグインの方法論を検討
- [ ] 問い合わせの返信 @wait(返信待ち) @from(2026-11-02)

## メモ
- 09:40 lint の孤立判定は、被リンクがないページ全てが対象だった
- 時刻のないメモも書いてよい

## ふりかえり
（夕方に close が下書きし、人が直す）
```

作業メモ 1 行の文法は次のとおりである。

```text
- [ ] HH:MM-HH:MM 一行の内容 #タグ @状態タグ
  ^^^ ^^^^^^^^^^^ ^^^^^^^^^^ ^^^^^ ^^^^^^^^^
  状態 時刻（省略可） 内容       任意   任意。行末にまとめる
```

- 状態の正本はチェックボックスで、`[ ]` が未完了、`[x]` が完了である。
- 時刻は行頭に置く。`10:45-` のように終了がない行は進行中とみなす。時刻を書かない行も書ける。
- 補助の状態は行末の `@タグ` で書く。使うのは `@wait(理由)`（待ち）、`@drop`（やめた）、`@from(YYYY-MM-DD)`（繰り越し元の日付）、`@moved(YYYY-MM-DD)`（繰り越し先の日付）の 4 つに絞る。繰り越した元の行は `[ ]` のまま `@moved` を付けるので、集計では未完了に数えない。
- `## 予定` には時刻だけの行を書く。チェックボックスは付けない。予定は「やったかどうか」を記録するものではないからである。
- `## メモ` は、時刻があってもなくてもよい自由な欄である。GTD の収集箱に当たる。

frontmatter は wiki の必須の 5 項目（`type`、`title`、`tags`、`created`、`updated`）に `date` を足した。キーと `type` の値は英語にする（方針 B）。そろえておくと、`wiki_search.py --wiki <保存先>` で日付ノートを検索したり、`wiki_lint.py` の frontmatter の検査を流用したりできる見込みがある。流用できるかは【要確認】で、PoC で試す。節の見出し（予定、タスク、メモ、ふりかえり）は日本語の固定の名前にし、スクリプトはこの見出しで節を探す。

### 6.6 エージェントによる入力支援のコマンド（提案）

表は、ADR-0006 の形式（作業メモとタスクを分け、問題・突発事項の節を足した形）に合わせて改めた。初版の表との違いは、`start` と `stop` の書き先を作業メモの節にしたこと、問題と突発事項を書くコマンドを足したこと、`promote` を `notes/` への書き出しに替えたことである。名前に「仮」と付けたコマンドは、名前を設計書で決める。

| コマンド | 何をするか | 段階 |
| --- | --- | --- |
| `/daily:log <一行>` | 今の時刻を付けて `## メモ` に追記する。どの節に書くかを人に選ばせないので、いちばん手間が少ない | 1 |
| `/daily:start <内容>` | `## 作業メモ` に、開始時刻だけの `[ ]` の行を足す | 1 |
| `/daily:stop [内容の一部]` | 作業メモの進行中の行に終了時刻を書き、`[x]` にする。進行中が複数あれば、どれかを聞く | 1 |
| `/daily:todo <一行>` | `### 本日のタスク` に `[ ]` の行を足す。詳細は、その行の下に箇条で書き足せる | 1 |
| `/daily:issue <一行>`（仮） | 今の時刻を付けて `## 問題・突発事項` に追記する | 1 |
| `/daily:plan` | 前日の `### 次回への繰り越し` と、前日のタスクの未完了の行を、`@from(前日)` を付けて今日の `### 前日からの繰り越し` に写す。写さずに `@drop` にする行がないかを聞く | 1 |
| `/daily:close` | 終了時刻のない作業メモを一覧にして埋めるよう促す。未完了のタスクを `### 次回への繰り越し` に移すかを聞き、`## ふりかえり` に 3 行の下書きを書く | 1 |
| `/daily:tidy` | `## メモ` の書き散らしから、タスク、作業メモ、問題・突発事項、`notes/` のノートに移す候補を示す。元の行は消さず、移した先を書き添える | 2 |
| `/daily:review [--week]` | 期間の記録から、週次レビューの下書きと、タグごとの作業時間の集計を出す | 2 |
| `/daily:note`（仮） | 日付ノートに繰り返し出るノウハウや決めたことを、`<保存先>/notes/` にノートとして書き出す。ユーザーが編集し、wiki に入れるかは `/wiki:ingest` で決める | 3 |

繰り越しは小節の位置で分かるので、初版で提案した `@moved` のタグは要らなくなった。

段階 1 のうち、`log`、`start`、`stop`、`todo` は時刻と行の操作だけなので、スクリプトで決まった処理として書ける。`plan` と `close` は、スクリプトが未完了の行を拾い出し、どうするかの判断を対話でエージェントが聞く形にする。書き込みは全てスクリプトが行い、LLM がファイルを直接書き換えないようにする。行の書き方が崩れないようにするためである。

### 6.7 配置：別のプラグインにする（提案）

| 観点 | wiki に `type: daily` を足す | 別のプラグイン `daily` |
| --- | --- | --- |
| lint | 被リンクのない日付ノートが毎日、孤立として報告される。除外の分岐を足す必要がある | wiki の lint に影響しない。「N 日以上繰り越した未完了」のような、日付ノート向けの検査を作れる |
| 検索と索引 | 知識の検索に作業ログが混ざる。`index.md` が 1 年で 365 項目増え、150 ページの分割の規約に日付ノートだけで 150 日ほどで達する | 混ざらない。日付ノートだけを検索するときは `wiki_search.py` に保存先を渡す |
| 既存コードの変更 | `init_wiki.py` の `SUBDIRS`、テンプレート 4 つ、`ontology.yaml` の対応表を直す | 要らない |
| 書き込みの頻度 | wiki は ingest のたびに厳選して書く。1 日に何十回も追記する使い方と合わない | 追記を前提に設計できる |
| 利用者 | wiki を使う人だけが使える | 日付ノートだけを使う人も入れられる |
| wiki との連携 | 同じスキルの中なので楽 | `promote` から `/wiki:ingest` への片方向の連携で足りる |
| リリース | wiki の版に相乗りする | `to884/info-hive-daily` として独立に版を管理する（ADR-0003 の手順） |

筆者は、別のプラグインにするのがよいと考える。wiki は「どのページも被リンクを持ち、取り込むたびに厳選して書く」ことを健全と見なす設計で、毎日追記される日付ノートはこの前提と合わない。wiki に足すと、lint と検索の両方に例外を足し続けることになる。wiki との関係は、「日付ノートは raw に近い一次資料で、残す価値のあるものだけが wiki に入る」と整理する。

### 6.8 次点と保留

- **次点**：日報の三部構成だけを採る案。入力は最も軽いが、開始と終了の時刻が残らず、作業メモの要件を満たさない。
- **保留**：次の案は、最初の 2 段階には入れず、使い方が固まってから見直す。
  - カレンダーの ICS ファイルからの取り込み（43）。予定をカレンダーで管理している人は二重に書かずに済むが、カレンダーの種類ごとの対応が要る
  - フックによる自動の記録（40）。セッションの開始と終了を自動で書けるが、作業の区切りとセッションの区切りは一致しない
  - Git のコミットログからの下書き（39）
  - 5 年日記の表示（21）
  - 音声の文字起こしの取り込み（42）

### 7.1 決定した事項
