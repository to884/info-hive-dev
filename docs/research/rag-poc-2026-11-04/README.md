# RAG PoC 検証記録

実施日：2026年11月4日（日本時間）。
同日追記：製品側の接続不足と PDF API の不備を修正し、実 OCR・埋め込みの中断と再開、および Claude Code からの取り込みを [追加の統合検証](../rag-pdf-job-integration-2026-11-04/README.md) で確認した。以下は修正前の PoC の記録として残す。
対象：[ADR-0007](../../adr/0007-rag-uses-mcp-core-and-persistent-jobs.md) の全体構成と、[候補調査](../japanese-pdf-local-rag-options.md) の P0〜P4。

## 判断の範囲

本記録は、採用した構成を開発用 PoC で検証した結果である。
製品プラグインの完成や、約 100 GB の全資料に対する性能達成を意味しない。
ジョブ制御用の共通コアは `poc/rag/` に置き、既存の製品試作とは区別した。

一次 PoC では、MCP、共通コア、永続ジョブによる中断と再開は成立した。
一方、製品試作には wiki からの接続不足と PDF API のエラーがあり、取り込みの E2E は通っていない。
検索では CPU で 1 秒未満となる組み合わせがあったが、リランカーを小さくすると精度が下がる例も見つかった。
この結果だけでモデルや索引基盤の既定値を確定しない。

検証では原資料の PDF を参照しただけで、移動、複製、書き換えを行っていない。
抽出テキスト、モデル、実行時の台帳と索引は、原資料の外のアプリケーションデータ領域と、Git の対象外にした `.rag-poc-data/` に置いた。

## 実行環境

Windows、Python 3.12.13、CPU のみで実施した。
CPU は Ryzen 7 3800XT（8 コア、16 スレッド）、物理メモリは 32 GiB である。
埋め込みとリランクのスレッド数は 4、埋め込みバッチは 8、チャンクは上限 800 文字、埋め込み入力上限は 2,048 トークンとした。
モデルの commit SHA、ライブラリの版、索引の保存先は、個別の結果 JSON と [環境記録](environment.json)、[依存関係の固定一覧](../../../poc/rag/requirements-lock.txt) に残した。

MCP の試験には Python SDK の stdio クライアントを使った。
Claude Code の実セッションを操作した E2E 試験とは区別する。
Windows 上のプロセスツリーを強制終了し、再接続後に処理が復旧することを試した。

## ジョブ制御

[結果 JSON](protocol-results.json) の P0・P1 に属する 14 件は成功した。
抽出対象は自作の日本語 PDF 10 ページで、処理済みページのハッシュを保存した。
この試験で疑似的な出力を使ったのは、受付、進捗、公開世代の切り替えの検証であり、意味検索の精度や埋め込み速度の測定ではない。

| 確認したこと | 結果 |
| --- | --- |
| 共通コア、CLI、MCP で同じ入力から同じジョブを追跡 | 成功 |
| 同期 MCP が同じジョブの完了を返す | 成功 |
| 受付時は `queued` で、未完了の結果を公開しない | 成功 |
| 32 回の同時投入でジョブを重複作成しない | 成功 |
| 異なる wiki のジョブを分離 | 成功 |
| プロセス内ワーカーの強制終了と再接続 | 2 ページ目のチェックポイントから再開し、10 ページ完了 |
| 子ワーカーを含むプロセスツリーの強制終了と再接続 | 同上。保存済みのページを再計算しないことも確認 |
| 明示的なキャンセルを、次の起動で自動再開しない | 両方式で成功 |
| 新しい世代の処理に失敗しても旧世代を公開し続ける | 成功 |
| 失敗した処理を明示的に再試行 | 成功 |
| 元の PDF の内容ハッシュが変わらない | 成功 |

P0 の MCP 状態取得は、20 回の呼び出しで p95 約 3.93 ms だった。
これは状態取得の通信と台帳参照の時間であり、検索処理の時間ではない。
両ワーカー方式とも今回の制御試験には通ったが、複数セッションが実モデルを保持する場合のメモリと CPU 競合は、この試験では確認していない。
実モデルによる検索測定とジョブ制御の試験は独立しており、OCR・埋め込み・索引更新を同じ永続ジョブに接続した統合試験は未実施である。

## 製品試作で失敗したこと

P2 の 2 件は失敗した。

1. `wiki` の PDF 取り込み手順から `rag` の登録処理へ接続するコード・指示がなく、実際の取り込みを起点とする処理はまだつながっていない。
2. 製品試作の MCP `ingest_pdf` を呼ぶと、`PdfPage` を `with` で扱う箇所で `TypeError` になった。
   使用した pypdfium2 5.14.0 の `PdfPage` と `PdfTextPage` は、この使い方をサポートしない。

PoC の抽出とジョブ制御では `contextlib.closing` で資源を閉じて検証を続けた。
製品コードの修正は行っていないため、この PoC の成功をそのまま製品の成功とは扱わない。

## 実資料と抽出

ローカルで参照できる 914 件から、seed `20261104` で順序を決め、11 件、1,156,835,555 bytes、2,895 ページを選んだ。
メモリ使用を抑えるため 350 MiB を超える PDF は選択対象から外した。
この除外と、クラウド上だけにある資料の除外により、全資料を無条件に代表するサンプルにはなっていない。
参照台帳は実行用のローカル領域に保存し、書籍の原本は複製していない。
検証終了後に 11 件の SHA-256 を再照合し、すべて抽出時と一致した。
[原本の照合結果](source-integrity.json) を参照。

| 項目 | pypdfium2 | PyMuPDF |
| --- | --- | --- |
| 抽出と計測の所要時間 | 38.82 秒 | 38.27 秒 |
| 空白を除く抽出文字数 | 3,868,484 | 3,875,116 |
| U+FFFD の個数 | 1 | 0 |

所要時間には Python 側の計測処理を含み、pypdfium2 側は派生テキストの JSONL 書き出しも含む。
純粋なネイティブ API の速度だけを揃えた比較ではない。
また、同じファイルを読んだ後の測定であり、ファイルシステムのキャッシュが効いた状態である。

PyMuPDF の `sort=True` の出力には空白が多かったため、総文字数で容量や品質を比べると差を過大評価する。
空白を除いた文字数の差は約 0.17% だったが、文字の内容や読み順が正しいことを全ページで確認したわけではない。
pypdfium2 の抽出テキストは UTF-8 で 6,825,316 bytes、元の PDF 容量の約 0.59% だった。
OCR で追加されるテキスト量はこの比率に含まない。

詳細は [抽出結果](extraction-results.json) と [再現スクリプト](../../../poc/rag/extract_sample.py) にある。

## OCR とページ分類

自作の横書きスキャン 1 ページと縦書きスキャン 1 ページを、NDLOCR-Lite の固定 commit で処理した。
NFKC 正規化と空白除去後の CER は、両ページで 0 だった。
2 ページの処理全体は、準備済み環境からの起動を含めて約 21.03 秒だった。
これは書籍全体や、表、数式、低解像度の資料に対する OCR 精度の証明ではない。

製品試作のページ検査には、資源の解放だけを補う PoC アダプターを挟んで実資料を分類した。
分類はヒューリスティックによるもので、人手の全ページ正解ラベルとの比較ではない。
2,895 ページの内訳は `text` 2,500、`scan` 341、`vertical` 53、`blank` 1 だった。
`vertical` とされた代表ページを目視すると、主に横書きの広告であり、53 ページすべてを「本当に縦書き」と数えることはできない。

実資料のスキャン広告 1 ページと、この分類が疑わしい広告 1 ページにも NDLOCR-Lite を実行した。
終了コードは 0、出力はそれぞれ 805 文字と 894 文字で、バッチ全体は約 48.29 秒だった。
正解の全文を書き起こしていないため、実資料の CER は未測定である。
ページ分類の誤りと、OCR の認識精度を別々に検証する必要がある。
[実資料の OCR 実行結果](real-ocr-results.json) を参照。
[OCR 結果](ocr-results.json) と [ページ分類結果](routing-results.json) を参照。

## 検索評価の方法

第 1 段階では、既存 wiki の固定正解セットから正例 47 問を使い、30 個の wiki チャンクと実 PDF の 512 チャンク、合計 542 チャンクで比較した。
同じ Ruri 30m のベクトルを再利用して、リランカーの変更を比べた。

第 2 段階では、実 PDF の 60 ページからエージェントが暫定の質問を作り、正例を 107 問に増やした。
各根拠文字列が対象ページにあることを全件検査し、該当箇所を含むチャンクを加えて 602 チャンクで比較した。
質問の大半は技術書と技術資料で、60 問中 49 問は英語の資料に対する日本語の質問である。
質問の曖昧さ、他ページも正解になる可能性、回答に十分な根拠があるかの人手確認は未実施である。
正解の根拠を含むように 800 文字のチャンクを加えたため、製品の自動チャンク分割まで含めた評価ではない。

元の固定セットに含まれる正解なしの 6 問は、今回の Recall と nDCG の集計から除いた。
関連資料がない質問の棄却と、Claude Code による回答生成の正しさは検証していない。

両エンジンで同じチャンクと埋め込みを使った。
LanceDB は Sudachi で分かち書きしたフィールドの native BM25、Qdrant は同じ Sudachi 語彙から計算した BM25 疎ベクトルを使い、密ベクトルの順位と RRF で統合した。
BM25 の実装は完全には同一でない。
同じページの複数チャンクを重複して評価しないよう、ページラベルでまとめて Recall@30 と nDCG@10 を計算した。

時間は、クエリの埋め込み、検索と RRF、リランクの各実測時間の和である。
MCP の通信、Sudachi によるクエリの分割、回答生成、初回のモデル取得は含まない。
エンジンの測定順は固定で、反復・交互測定による有意差の検定は行っていない。
本データ件数での予備測定として扱う。

## 検索の実測

### リランカーの変更：固定 47 問、542 チャンク

Ruri 30m の文書ベクトルを揃え、上位 30 件をリランクした。
品質指標は両エンジンで同じ値だった。

| リランカー | LanceDB p95 | Qdrant p95 | Recall@30 | nDCG@10 |
| --- | --- | --- | --- | --- |
| xsmall FP32 | 3,691 ms | 3,296 ms | 1.0000 | 0.9315 |
| xsmall int8 | 2,795 ms | 2,655 ms | 1.0000 | 0.9071 |
| tiny int8 | 1,040 ms | 983 ms | 1.0000 | 0.8154 |

この条件では xsmall を単純に int8 化するだけでは 1 秒に届かなかった。
tiny は速くなったが、nDCG はリランク前の 0.8483 より低かった。
固定 47 問のうち改善した質問が 10 問、悪化した質問が 13 問あり、「リランクを加えると必ず精度が上がる」とは扱えない。

### 埋め込みモデルの変更：正例 107 問、602 チャンク

tiny int8 で上位 20 件をリランクした。同じコーパスと質問で比較した。

| Ruri v3 | 次元 | 埋め込み 602 件 | LanceDB p95 | Qdrant p95 | Recall@30 | nDCG@10 | Python peak RSS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 30m | 256 | 80.55 秒 | 673 ms | 665 ms | 0.9439 | 0.7680 | 1.33 GiB |
| 70m | 384 | 157.48 秒 | 523 ms | 525 ms | 0.9626 | 0.8165 | 1.97 GiB |
| 130m | 512 | 448.63 秒 | 677 ms | 675 ms | 0.9813 | 0.8068 | 2.45 GiB |

品質指標は両エンジンで同じ値だった。
Python の RSS は 50 ms 間隔で測った単一プロセスの最大値で、Qdrant やほかのセッションを含む合計最大値ではない。
Qdrant の終了直前の RSS は各条件で約 0.08 GiB だったが、最大値の計測ではない。

この暫定セットでは、130m は Recall が高く、70m は nDCG が高かった。
70m の検索が 30m より短かった理由には、検索候補とリランク対象の長さの違いが含まれうる。
エンコーダー単体の速度順位をこの p95 から判断しない。
すべてのチャンクが 2,048 トークン以内で、最大は 774 トークン、切り捨ては 0 件だった。

実 PDF の暫定 60 問だけで見ると、Recall@30 は 30m が 0.9000、70m が 0.9333、130m が 0.9667 だった。
内訳は [質問群別の集計](subgroup-results.json) を参照。
英語資料への日本語質問が多く、一般的な日本語 PDF 全体の順位とは限らない。

### 追加条件：xsmall の対象を 8 件に制限

同じ 107 問で、Ruri 30m と xsmall int8 を使い、リランクを上位 8 件に限定した。
9 件目以降は RRF の順を残し、nDCG@10 の集計ではその続きも使った。

| 条件 | LanceDB p95 | Qdrant p95 | Recall@30 | nDCG@10 |
| --- | --- | --- | --- | --- |
| 30m + xsmall int8、上位 8 件 | 749 ms | 744 ms | 0.9439 | 0.8460 |

今回の 107 問では、この追加条件がリランク後の nDCG で最も高かった。
ただし 30m の検索段階での取りこぼしは残る。
小さいリランカーへの変更だけでなく、リランクの対象件数を制限する方針も、次の比較に残す価値がある。
人手で確認した評価セットと、大きい索引で再測定するまで既定値にはしない。

個別の測定と追加条件は [実測比較表](measurements.md)、[集計 JSON](summary.json) にまとめた。
47 問と 107 問の表はコーパスも異なるため、直接の精度比較には使わない。

## ベクトルの保存精度

3 モデルの同じ 107 問で、密ベクトルの全件走査について float32、float16、行ごとの scalar int8 丸めを比べた。
float16 は、今回の Recall@30 と nDCG@10 が float32 と同じだった。
int8 は Recall が変わらず、nDCG の変化の絶対値は最大約 0.004 だった。

int8 は復元後に正規化して走査したので、圧縮索引の容量や速度を測ったものではない。
ANN、IVF-PQ、Qdrant の 1.5〜2 bit 量子化の採用可否は判断しない。
[結果 JSON](vector-precision.json) を参照。

## 索引の更新と保存

[索引制御の 6 件](backend-contracts.json) は成功した。
LanceDB は、読み取り側の版の確認間隔を 0 にすると、別プロセスで追記した行をベクトル検索と全文検索の両方で取得できた。
`optimize` 後も行が残り、同じ ID の merge で行が重複しないことを確認した。
Qdrant は同じ ID の upsert と、プロセスを停止して再起動した後のデータ保持を確認した。

Qdrant 1.20.0 の Windows 公式バイナリを loopback の専用ポートで起動し、終了時にそのプロセスを停止した。
長いアプリケーションデータ配下のパスでは collection 作成が IO error 3 で失敗し、C ドライブの短い保存先へ変更すると成功した。
パス長だけを変数にした試験ではないので、原因は確定していない。

542 チャンクの第 1 段階では、LanceDB のファイルサイズは約 2.27 MB、Qdrant は約 906.54 MB だった。
Windows の割り当てサイズも確認した。
この差には初期の確保領域が含まれるため、PDF 100 GB に対する容量をこの比率から線形に換算しない。
[サイズ記録](index-allocation.json) を参照。

## 未確認の項目

- 約 100 GB 全体の索引構築、容量 10〜30 GB、数百万チャンクでの ANN 検索。
- IVF-PQ と、Qdrant の 1.5〜2 bit 量子化の精度と検索性能。
- 人手で確認した実資料の正解セットによる精度判定。
- 表、数式、図、低解像度、文字化けしたテキスト層に対する抽出と OCR の品質。
- 実際の wiki 取り込みから回答生成までを含む製品 E2E。
- 実 OCR と埋め込みを行うジョブの中断、索引書き込み途中の障害、取り込み中に原本が変わった場合の復旧。
- 索引構築と検索の同時実行、複数の Claude Code セッションによるモデル保持、初回依存関係の取得を含む MCP 起動。

## 次の検証に進む条件

製品化に向けては、まず wiki の PDF 登録と短いジョブ登録 API を接続し、pypdfium2 の資源解放方法を直す。
そのうえで、実 OCR・埋め込み・索引更新を永続ジョブにつなぎ、Claude Code の実セッションから中断と再開を確認する。
今回、両ワーカー方式の制御試験が通ったため、プロセス方式の確定には実モデルの同時利用とメモリ計測が必要である。

検索候補としては、70m / 130m による取りこぼしの低減と、xsmall の対象件数の制限を継続して比較する。
人手で確認した実資料の質問、正解のない質問、大きい索引での測定が揃ってから、既定のモデルと索引基盤を決める。
今回の測定だけでは、LanceDB と Qdrant の採用順位は確定しない。
