# /wiki:query の確からしさの未測定の規則を Sonnet 5.5 で測った記録（2026-11-16）

wiki プラグイン 0.21.1 の `/wiki:query` が付ける確からしさ（ADR-0028）のうち、[前回の測定](wiki-query-confidence-sonnet-2026-11-16.md)では問いを作れなかった規則を、Claude Sonnet 5.5 で測った。試験用の小さな wiki を作り、15 問を 3 回ずつ流した。見たのは、期待の判定との一致、3 回のぶれ、理由が規則どおりか、上げる方法が要因に合っていたかである。

測った規則は、規則の正本 `skills/info-hive/references/query-confidence.md` の次の部分である。

- シンセシスのページを根拠に数えないこと。前提をたどって決め直し、見つからなければ答えない。
- 上限: 矛盾（低）、`status: superseded`（低）、時期や版の不明（中）、グラフのエッジの `confidence: low`（低）と `medium`（中）。
- 検索の縮退の上限と、理由ごとの上げる方法。理由は、ページ単位の検索、`--no-embed`、埋め込みモデルを使えない、埋め込みの途中の 4 つである。
- 複数の結論で確からしさが違うときの書き方。

## 結論

- **判定のラベルは 45 回中 40 回で期待と合った。** 3 回とも同じになった問いは 15 問中 11 問だった。ぶれたのは R08（エッジの medium）、R11 と R12（MCP の検索の縮退）、R15（複数の結論）である。
- **外れた 5 回のうち、規則の外れは 1 回だけだった。** R15 の 1 回で、決まった 1 行を「設定ファイルの場所は高。上限は低」と崩した。残りの 4 回は、事前に `alt` として書いた読みの幅に当たった。どれも規則に書かれていないことが分かれ目になっていた（下の 2 つ）。
- **グラフのエッジを根拠に数えるかが、規則から決まらない。** グラフの問いの 6 回で、`graph` の MCP も CLI も一度も呼ばれなかった（48 回中 0 回）。エッジは、人物のページの frontmatter で読まれていた。同じ主張がソースの要約ページにもある R08 では、3 回中 2 回が「根拠はエッジではなくソースの要約ページ」として `confidence: medium` を上限に数えず、「高」にした。
- **`Grep` で見つけたページの扱いが、規則にない。** 検索の縮退の上限は、wiki の検索（MCP か CLI）だけを数えている。R11 と R12 の 1 回ずつは、`Grep` でページを見つけ、「インデックスから直接見つけた」と書いて「高」にした。`Grep` は 48 回中 38 回で使われた。
- **規則どおりに決まった規則も多い。**
  - シンセシス（R01、R02）、矛盾（R03）、superseded（R04、R05）、時期や版の不明（R06）は 15 回とも期待どおりだった。
  - `--no-embed` とページ単位の検索（R09、R10）も 6 回とも期待どおりで、上げる方法も理由ごとに合っていた。
  - インデックスから見つかる対照（R13）は、縮退した検索を使った回も含めて 3 回とも「高」だった。
- **規則の正本は 48 回とも読まれた。** 0.21.1 で手順 6b からパスを書いて Read させた直しは、この wiki でも効いている。
- **規則の直しの案を作者に示す。** 直しは作っていない（下の「規則の直しの案」）。

### 理由が規則どおりか

ラベルが合った 40 回のうち 39 回は、理由も規則どおりだった。合わなかったのは R07 r3 の 1 回である。この回は「グラフのエッジの `confidence: low` の行には当てはまらない」と書き、表にない「前提の性質」で「低」にした。ラベルだけが合っている。

規則どおりだった主な点は、次のとおりである。

- **シンセシス（R01、R02）**: 7 回とも、シンセシスのページを根拠に数えないと書いた。R01 は管理者ガイドで前提を確かめ、シンセシスに書かれた「低」を引き継がなかった。R02 は 3 回とも廃止の予定を答えず、確からしさも付けず、取り込むとよい資料を挙げた。

### 複数の結論の書き方

R14 と R15 の 6 回は、どれも結論ごとの確からしさの違いを書いた。ただし、規則の「それぞれの結論のそばに『（確からしさ: 高）』のように書く」に従い、結論のそばに書いたのは R14 r3 の 1 回だけだった。残りの 5 回は、理由の箇条の中に「理由（設定ファイルの場所）: … 高」のように書いた。R15 r1 は、決まった 1 行そのものを結論ごとの書き方に崩した（上の表）。

### グラフの使い方

`commands/query.md` の手順 5b は、関係を問う質問で `graph/graph.sqlite` があれば、ページを読む前にグラフに問い合わせるとしている。R07 と R08 の 6 回とも、グラフに問い合わせなかった。5 回は人物のページを開き、frontmatter の `graph.relationships` でエッジの `confidence` を読んだ。R07 r3 は `graph` のツールを読み込んだが呼ばず、人物のページも開かなかったので、エッジを見ていない。

規則の上限の行は「根拠のグラフのエッジが `confidence: low`」である。グラフに問い合わせない回では、どのエッジが「根拠」なのかが読み手によって変わる。R07 では、ソースの記述が「だったと思う」という記憶なので、エッジを根拠に数えても数えなくても「低」か「中」になり、3 回とも「低」だった。R08 では、ソースの要約ページが主張をそのまま述べているので、エッジを根拠に数えるかどうかで「中」と「高」に分かれた。

### そのほかに見えたこと

- **`Grep` が広く使われた。** 48 回中 38 回で `Grep` を使った。多くは、矛盾する記述がほかにないかの確かめだった。答えのページを見つけるのに使った回もある（R11 r2、R12 r2）。
- **利用者のグローバルの指示が回答に出た。** 5 回（R05 r2、R09 r1、R09 r3、R10 r2、R12 r2）が「作業前の `git fetch` は、git リポジトリではないので行っていない」と書いた。`~/.claude/CLAUDE.md` の「作業の準備」が、子の `claude -p` にも読み込まれたためである。判定には関わっていない。
- **CLI のグラフの文字の出力では、入ってくるエッジの `confidence` が出ない。** `wiki_graph_query.py neighbors` の文字の出力は、出るエッジには `confidence=` を付けるが、入ってくるエッジには付けない。`--json` と MCP の `graph` は、どちらのエッジにも `confidence` を含む。今回はグラフが使われなかったので、判定には関わっていない。
- **MCP の warning に、モデルのファイルの絶対パスが入る。** 「埋め込みモデルを使えない」の warning は、onnxruntime の例外の文をそのまま含み、モデルのファイルの絶対パスが出る。`wiki_search.py` の `embedding_failure_label` はパスを出さないようにしているが、MCP のサーバーは例外の文をそのまま使っている。
- **wiki は変わらなかった。** 48 回とも、実行の前後で wiki のハッシュが同じだった。

## 測っていない規則と、測り方の限り

- **縮退の 2 つの理由は、利用者の指示としてだけ測った。** `--no-embed` とページ単位の検索（R09、R10）は、問いの文で指示した。モデルが自分の判断でこれらを選んだときの判定は測っていない。
- **埋め込みの途中の状態は、モデルを用意している warning で起こした。** `index.state: embedding` で、モデルは使える状態（warning「索引を埋め込んでいる途中」）は起こしていない。上げる方法の表では、どちらも理由 4 である。
- **時期や版の上限は、「根拠に時期や版が書かれていない」の側だけを測った。** 「`log.md` やほかのページのより新しい記述と食い違う」の側は、矛盾の上限と重なるので問いを作っていない。
- **仮説の上限（`status: hypothesis`）、エッジの `status: proposed` と `disputed`、`status: historical` は測っていない。** 仮説の上限は前回の Q05 で測った。
- **wiki が小さい。** 14 ページなので、エージェントは候補のページをほとんど読めた。大きな wiki では、インデックスから候補を見つけられない場面が増えるはずである。
- **モデルは Sonnet 5.5 だけで、1 問 3 回である。**

## 規則の直しの案（作者の判断を待つ）

直しは作っていない。ADR-0027 の実装（0.22.0）が同じ `query-confidence.md` に動画の上限の行を足す予定なので、入れるときは順番を決めてから進める。

1. **どのエッジを「根拠のグラフのエッジ」とするかを決める。**
   - 案: 結論が人やものの関係を述べ、その関係が型付きのエッジとして wiki にあるなら、そのエッジを根拠に含める。エッジは、このクエリで読んだページの frontmatter の `graph.relationships` にあるか、グラフへの問い合わせの結果にあるものとする。ソースの要約ページが同じ主張を述べていても、エッジの `confidence` と `status` の上限を当てる。
   - 理由: エッジの確からしさは、取り込んだときにソースの強さを判断した記録である。ソースの要約ページだけを根拠にして「高」にすると、その記録が使われない。逆に「エッジは根拠に数えない」と決める道もある。どちらにするかは作者に決めてほしい。どちらでも、R08 のぶれはなくなる。
   - あわせて、手順 5b がグラフを使わせていない（6 回中 0 回）。5b を「関係を問う質問では、ページを読む前に `graph` の `neighbors` を呼ぶ」と言い切るか、frontmatter で読むことも認めるかを決める。
2. **`Grep` で候補を見つけたときの扱いを決める。**
   - 案 A: `Grep` と `Glob` は wiki の検索ではないので、答えのページを見つけるのに使わない、と手順 4 に書く。矛盾の確かめに使うのは認める。
   - 案 B: `Grep` で答えのページを見つけたときは、意味の検索を使わなかった検索として、検索の縮退（中）に数える。上げる方法は「MCP の `query` で検索し直す」にする。
   - どちらでも、回答には候補をどう見つけたか（インデックス、検索、`Grep`）を正しく書かせる。R11 r2 と R12 r2 は、`Grep` で見つけたのに「インデックスから見つけた」と書いた。
3. **検索の縮退の上限は、ページを読んでも外れないことを書く。** 上限の表のあとに、次の 1 文を足す。「検索の縮退は、ほかの関係するページを見落としたかもしれないことを表す。見つけたページの本体を読んで確かめても、この上限は外れない」。R12 r0 は、抜粋だけの行と取り違えて下げなかった。上限の目的が書かれていないことが、取り違えの一因と見ている。
4. **複数の結論の書き方に例を足す。** 「書き方」の節に、2 つの結論の例を足す。それぞれの結論の文の終わりに「（確からしさ: 高）」を置き、最後の決まった 1 行には回答全体の確からしさ（もっとも低いもの）を書く例である。あわせて「結論ごとに確からしさが違っても、決まった 1 行は 1 つの値で書く」と書く。R15 r1 の崩れと、6 回中 5 回が理由の中にだけ書いたことへの対応である。
5. **（小さい直し）上げる方法の表の後半を、要因ごとに漏れなく書かせる。** superseded、時期や版の不明、エッジの行では、`/wiki:lint` か `/wiki:graph lint` の提案が抜けやすかった。行の中で「取り込む」と「lint で確かめる」を別の文に分けると、抜けにくくなると見ている。必須ではない。

規則の外のこととして、次の 2 つは別の直しになる。

- `wiki_graph_query.py` の `neighbors` の文字の出力に、入ってくるエッジの `confidence` も出す。
- MCP のサーバーの「埋め込みモデルを使えない」の warning から、例外の文に含まれるパスを除く（`wiki_search.py` の `embedding_failure_label` と同じ扱いにする）。
