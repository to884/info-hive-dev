# /wiki:query の確からしさの未測定の規則を Sonnet 5.5 で測った記録（2026-11-16）

wiki プラグイン 0.21.1 の `/wiki:query` が付ける確からしさ（ADR-0028）のうち、[前回の測定](wiki-query-confidence-sonnet-2026-11-16.md)では問いを作れなかった規則を、Claude Sonnet 5.5 で測った。試験用の小さな wiki を作り、15 問を 3 回ずつ流した。見たのは、期待の判定との一致、3 回のぶれ、理由が規則どおりか、上げる方法が要因に合っていたかである。

測った規則は、規則の正本 `skills/info-hive/references/query-confidence.md` の次の部分である。

- シンセシスのページを根拠に数えないこと。前提をたどって決め直し、見つからなければ答えない。
- 上限: 矛盾（低）、`status: superseded`（低）、時期や版の不明（中）、グラフのエッジの `confidence: low`（低）と `medium`（中）。
- 検索の縮退の上限と、理由ごとの上げる方法。理由は、ページ単位の検索、`--no-embed`、埋め込みモデルを使えない、埋め込みの途中の 4 つである。
- 複数の結論で確からしさが違うときの書き方。

## 結論

- **判定のラベルは 45 回中 40 回で期待と合った。** 3 回とも同じになった問いは 15 問中 11 問だった。ぶれたのは R08（エッジの medium）、R11 と R12（MCP の検索の縮退）、R15（複数の結論）である。
- **外れた 5 回の内訳は、事前に書いた読みの幅が 2 回、事前に書いていない経路が 2 回、規則の外れが 1 回だった。**
  - 事前に書いた読みの幅（`alt`）に当たったのは、R08 の 2 回である（下の「グラフのエッジ」）。
  - 事前に書いていない経路は、R11 と R12 の 1 回ずつである。`Grep` でページを見つけ、回答には「インデックスから見つけた」と道具の記録と違うことを書いた（下の「`Grep`」）。
  - 規則の外れは R15 の 1 回で、決まった 1 行を「設定ファイルの場所は高。上限は低」と崩した。
  - 4 回の分かれ目は、どれも `query-confidence.md` に書かれていないことだった。
- **グラフのエッジを根拠に数えるかが、規則から決まらない。** グラフの問いの 6 回で、`graph` の MCP も CLI も一度も呼ばれなかった（48 回中 0 回）。エッジは、人物のページの frontmatter で読まれていた。同じ主張がソースの要約ページにもある R08 では、3 回中 2 回が「根拠はエッジではなくソースの要約ページ」として `confidence: medium` を上限に数えず、「高」にした。
- **`Grep` で見つけたページの扱いが、`query-confidence.md` にない。** 検索の縮退の上限は、wiki の検索（MCP か CLI）だけを数えている。R11 と R12 の 1 回ずつは、`Grep` のあとで初めて答えのページを開き、「インデックスから直接見つけた」と書いて「高」にした。`Grep` は 48 回中 38 回で使われた。「grep や glob で探してはならない」という規則は `SKILL.md` にあるが、`SKILL.md` を読んだ回は 48 回中 0 回で、`commands/query.md` にはこの規則がない。
- **規則どおりに決まった規則も多い。**
  - シンセシス（R01、R02）、矛盾（R03）、superseded（R04、R05）、時期や版の不明（R06）は 15 回とも期待どおりだった。
  - `--no-embed` とページ単位の検索（R09、R10）も 6 回とも期待どおりで、上げる方法も理由ごとに合っていた。
  - インデックスから見つかる対照（R13）は、縮退した検索を使った回も含めて 3 回とも「高」だった。
- **規則の正本は 48 回とも読まれた。** 0.21.1 で手順 6b からパスを書いて Read させた直しは、この wiki でも効いている。
- **規則の直しの案を作者に示した。** 案 1（エッジ）は、作者が「ソースの要約ページが直接述べていればエッジを上限に数えない」（A）を選び、手順 5b では関係を問う質問にグラフを必ず呼ばせると決めた。案 2（`Grep`）は、`Grep` で答えのページを見つけたら検索の縮退に数える（B）と決めた。案 3 と 4 も入れると決めた。小さい直しの 5 は判断していない。直しは作っていない（下の「規則の直しの案」）。

### 理由が規則どおりか

ラベルが合った 40 回のうち 39 回は、理由も規則どおりだった。合わなかったのは R07 r3 の 1 回である。この回は「グラフのエッジの `confidence: low` の行には当てはまらない」と書き、表にない「前提の性質」で「低」にした。ラベルだけが合っている。

規則どおりだった主な点は、次のとおりである。

- **シンセシス（R01、R02）**: 本番の 6 回と試しの 1 回のどれも、シンセシスのページを根拠に数えないと書いた。R01 は管理者ガイドで前提を確かめ、シンセシスに書かれた「低」を引き継がなかった。R02 は 3 回とも廃止の予定を答えず、確からしさも付けず、取り込むとよい資料を挙げた。
- **superseded（R04、R05）**: R04 は 3 回とも「今のことを問うのに、根拠が置き換えられた記述」を挙げた。R05 は 3 回とも「過去の時点を問うので上限に当たらない」と書いた。条件の「質問が今のことを問うのに」が読み分けられている。
- **縮退の対照（R13）**: R13 r3 は縮退した MCP の検索も使ったが、「インデックスから見つけた後の補足だったので、縮退の上限は適用しない」と書いた。

### グラフの使い方

`commands/query.md` の手順 5b は、関係を問う質問で `graph/graph.sqlite` があれば、ページを読む前にグラフに問い合わせるとしている。R07 と R08 の 6 回とも、グラフに問い合わせなかった。5 回は人物のページを開き、frontmatter の `graph.relationships` でエッジの `confidence` を読んだ。R07 r3 は `graph` のツールを読み込んだが呼ばず、人物のページも開かなかったので、エッジを見ていない。

規則の上限の行は「根拠のグラフのエッジが `confidence: low`」である。グラフに問い合わせない回では、どのエッジが「根拠」なのかが読み手によって変わる。R07 では、ソースの記述が「だったと思う」という記憶なので、エッジを根拠に数えても数えなくても「低」か「中」になり、3 回とも「低」だった。R08 では、ソースの要約ページが主張をそのまま述べているので、エッジを根拠に数えるかどうかで「中」と「高」に分かれた。

### そのほかに見えたこと

- **`Grep` が広く使われた。** 48 回中 38 回で `Grep` を使った。多くは、矛盾する記述がほかにないかの確かめだった。答えのページを見つけるのに使った回もある（R11 r2、R12 r2）。
- **利用者のグローバルの指示が回答に出た。** 5 回（R05 r2、R09 r1、R09 r3、R10 r2、R12 r2）が「作業前の `git fetch` は、git リポジトリではないので行っていない」と書いた。`~/.claude/CLAUDE.md` の「作業の準備」が、子の `claude -p` にも読み込まれたためである。判定には関わっていない。
- **CLI のグラフの文字の出力では、入ってくるエッジの `confidence` が出ない。** `wiki_graph_query.py neighbors` の文字の出力は、出るエッジには `confidence=` を付けるが、入ってくるエッジには付けない。`--json` と MCP の `graph` は、どちらのエッジにも `confidence` を含む。今回はグラフが使われなかったので、判定には関わっていない。
- **MCP の warning に、モデルのファイルの絶対パスが入る。** 「埋め込みモデルを使えない」の warning は、onnxruntime の例外の文をそのまま含み、モデルのファイルの絶対パスが出る。`wiki_search.py` の `embedding_failure_label` はパスを出さないようにしているが、MCP のサーバーは例外の文をそのまま使っている。
- **wiki は変わらなかった。** 48 回とも、実行の前後で wiki のハッシュが同じだった。

## 測っていない規則と、測り方の限り

- **縮退の 2 つの理由は、利用者の指示としてだけ測った。** `--no-embed` とページ単位の検索（R09、R10）は、問いの文で指示した。モデルが自分の判断でこれらを選んだときの判定は測っていない。
- **埋め込みの途中の状態は、モデルを用意している warning で起こした。** `index.state: embedding` で、モデルは使える状態（warning「索引を埋め込んでいる途中」）は起こしていない。上げる方法の表では、どちらも理由 4 である。
- **時期や版の上限は、「根拠に時期や版が書かれていない」の側だけを測った。** 「`log.md` やほかのページのより新しい記述と食い違う」の側は、矛盾の上限と重なるので問いを作っていない。
- **仮説の上限（`status: hypothesis`）、エッジの `status: proposed` と `disputed`、`status: historical` は測っていない。** 仮説の上限は前回の Q05 で測った。
- **wiki が小さい。** 14 ページなので、エージェントは候補のページをほとんど読めた。大きな wiki では、インデックスから候補を見つけられない場面が増えるはずである。
- **モデルは Sonnet 5.5 だけで、1 問 3 回である。**

## 規則の直しの案（案 1 は A、案 2 は B、案 3 と 4 は入れると決まった。5 は判断していない）

直しは作っていない。ADR-0027 の実装（0.22.0）が同じ `query-confidence.md` に動画の上限の行を足す予定なので、入れるときは順番を決めてから進める。

1. **どのエッジを「根拠のグラフのエッジ」とするかを決める。（作者の判断: A。2026-11-16）**
   - 案 A（数えない）: エッジの上限（`confidence`、`status`）は、結論をエッジから導いたとき（グラフへの問い合わせの結果を根拠にしたとき）だけ当てる。ソースの要約ページか raw ソースがその主張を直接述べていれば、そのページで出発点を決め、エッジの `confidence` は上限に数えない。
   - 案 B（数える）: 結論が述べる関係が型付きのエッジとして wiki にあれば（読んだページの frontmatter の `graph.relationships` か、グラフへの問い合わせの結果）、そのエッジを根拠に含め、ソースの要約ページが同じ主張を述べていても上限を当てる。
   - A の理由: `graph-workflow.md` は `confidence` を必須とするだけで、high、medium、low の選び方を決めていない。数えると、決め方のない取り込みのときの判断が、規則で決めた判定を下げる。正本は Markdown で、グラフはそこから作る索引である。ソースの記述が弱いとき（R07 の「だったと思う」）は、エッジを数えなくても「判断を加えた導き方」で「中」に下がる。
   - B の理由: エッジの `confidence` は、取り込んだ人がその関係を弱いと見た唯一の記録で、数えないと捨てられる。
   - 作者は A を選んだ。今のモデルの振る舞い（R08 の 2 回が「根拠はエッジではなくソースの要約ページ」とした）も A に近い。A で R08 の期待は「高」になり、R07 は「中」になる（ソースの記憶の記述から言い出した人を決めるのは判断を加えた導き方）。どちらも、直したあとに測り直して確かめる。
   - 手順 5b: 今は、グラフを使わせていない（6 回中 0 回）。A では、エッジの上限はグラフへの問い合わせの結果を根拠にしたときだけ効く。作者は、5b を「関係を問う質問では、`graph/graph.sqlite` があれば、ページを読む前に必ず `graph` の `neighbors` を呼ぶ」と言い切ることを選んだ（2026-11-16）。
   - 書く文の例（`commands/query.md` の 5b）: 「関係を問う質問（『X とつながっているものは？』『Y を言い出したのは誰？』など）では、`<WIKI_ROOT>/graph/graph.sqlite` があれば、ページを読む前に必ず MCP の `graph`（`command="neighbors"`）を呼ぶ。ページの frontmatter の `graph.relationships` を読むことで、これに代えてはならない。グラフの結果で開くページを選び、主張はページで確かめる。」
   - 測り直しで見ること: 関係の問いでグラフを呼んだ回の数。グラフを呼んだうえで、ソースの要約ページが直接述べる関係にエッジの上限を当てなかったか（A）。
2. **`Grep` で候補を見つけたときの扱いを決める。（作者の判断: B。2026-11-16）**
   - 前提: `SKILL.md` の「インデックスを先に読むナビゲーション」は、すでに「wiki をやみくもに grep や glob で探してはならない」としている。ただ、`SKILL.md` を読んだ回は 48 回中 0 回で、エージェントが読む `commands/query.md` と `query-confidence.md` にはこの規則がない。新しい規則を作るより、既にある規則をエージェントに届ける直しになる。0.21.1 で規則の正本を Read させて届いたのと同じ形である。
   - 案 A: `Grep` と `Glob` は wiki の検索ではないので、答えのページを見つけるのに使わない、と `commands/query.md` の手順 4 に書く。矛盾の確かめに使うのは認める。
   - 案 B: `Grep` で答えのページを見つけたときは、意味の検索を使わなかった検索として、検索の縮退（中）に数える。上げる方法は「MCP の `query` で検索し直す」にする。
   - どちらでも、回答には候補をどう見つけたか（インデックス、検索、`Grep`）を正しく書かせる。R11 r2 と R12 r2 は、`Grep` で見つけたのに「インデックスから見つけた」と書いた。
   - 作者の判断: B（縮退に数える。2026-11-16）。`Grep` は禁じず、答えのページを `Grep` か `Glob` で見つけたときは、意味の検索を使わなかった検索として「中」を上限にする。矛盾の確かめや、答えがないことの確かめに `Grep` を使うのは、候補を見つけたことに当たらないので上限に数えない。
   - 書く文の例（`query-confidence.md`）: 検索の縮退の上限の行の条件を「インデックスから候補のページを見つけられず、検索か `Grep`・`Glob` に頼り、意味の検索を wiki 全体には使っていなかった」に広げる。縮退の理由の表の先頭に「0 | 語彙だけの道具（`Grep`、`Glob`）で答えのページを見つけた | 道具の呼び出しで、そのページを開く前に `Grep` か `Glob` の結果にそのページが出ていた」を足す。上げる方法の表に「検索の縮退（0. `Grep` で見つけた） | MCP の `query` で検索し直す。同じページが見つかり、ほかに関係するページがなければ、上限は外れる」を足す。
   - `SKILL.md` の「grep や glob で探してはならない」とは、向きが違う。`SKILL.md` は勧めとして残し、守られなかったときの判定を `query-confidence.md` が決める、という分け方になる。
   - 測り直しで見ること: R11 と R12 で `Grep` で見つけた回が「中」になるか。回答に見つけ方を道具の記録どおりに書くか。
3. **検索の縮退の上限は、ページを読んでも外れないことを書く。（作者の判断: 入れる。2026-11-16）** 上限の表のあとに、次の 1 文を足す。「検索の縮退は、ほかの関係するページを見落としたかもしれないことを表す。見つけたページの本体を読んで確かめても、この上限は外れない」。R12 r0 は、抜粋だけの行と取り違えて下げなかった。上限の目的が書かれていないことが、取り違えの一因と見ている。
4. **複数の結論の書き方に例を足す。（作者の判断: 入れる。2026-11-16）** 「書き方」の節に、2 つの結論の例を足す。それぞれの結論の文の終わりに「（確からしさ: 高）」を置き、最後の決まった 1 行には回答全体の確からしさ（もっとも低いもの）を書く例である。あわせて「結論ごとに確からしさが違っても、決まった 1 行は 1 つの値で書く」と書く。R15 r1 の崩れと、6 回中 5 回が理由の中にだけ書いたことへの対応である。
5. **（小さい直し）上げる方法の表の後半を、要因ごとに漏れなく書かせる。** superseded、時期や版の不明、エッジの行では、`/wiki:lint` か `/wiki:graph lint` の提案が抜けやすかった。行の中で「取り込む」と「lint で確かめる」を別の文に分けると、抜けにくくなると見ている。必須ではない。

規則の外のこととして、次の 2 つは別の直しになる。

- `wiki_graph_query.py` の `neighbors` の文字の出力に、入ってくるエッジの `confidence` も出す。
- MCP のサーバーの「埋め込みモデルを使えない」の warning から、例外の文に含まれるパスを除く（`wiki_search.py` の `embedding_failure_label` と同じ扱いにする）。

## 再現の手順

`wiki-query-confidence-rules-2026-11-16/scripts/` にスクリプトがある。前回の測定のスクリプトを写し、作業ディレクトリ、MCP の条件、wiki の変更の確かめ方を変えた。

```bash
export QC_PLUGIN_DIR=<v0.21.1 の info-hive-wiki を取り出したディレクトリ>
export QC_WIKI_BASE=<リポジトリの外の空のディレクトリ>
python build_fixture.py
uv run --with mcp==1.30.0 python probe_mcp.py ready "同期の再試行は何回まで" 3
uv run --with mcp==1.30.0 python probe_mcp.py broken "同期の再試行は何回まで" 1
uv run --with mcp==1.30.0 python probe_mcp.py preparing "同期の再試行は何回まで" 1
python run_all.py --reps 0 --only R01,R11,R12
python run_all.py
python aggregate.py
python export_summary.py
```

`build_fixture.py` は、利用者の置き場所（`%LOCALAPPDATA%\info-hive\models`）にある埋め込みモデルを写す。ready の条件は、最初の呼び出しで索引の埋め込みが始まり、3 回目で `index.state: ready` になった。本番の前に、`ready` になるまで `probe_mcp.py ready` を呼んでおく。`runs-summary.json` では、セッションの一時の場所のパスを `<SCRATCH>` に置き換えている。

`export_summary.py` の判定は手で付けたもので、判定したときのログの SHA-256 を `judged-logs.json` に記録している。測り直すとログのハッシュが変わるので、`export_summary.py` は書き出さずに止まる。回答を読んで判定（`J`）を付け直し、`python export_summary.py --bind` でハッシュを記録し直す。`run_one.py` は、`claude` が失敗した回を完了にせず、ログを `<問い>-r<回>.failed-<時刻>.jsonl` に退避する。`run_all.py` は、退避したログを含む記録先のすべてのログの費用から数え始める。生の stream-json は `runs/` に置き、git では無視する。判定を付けた全回の要約は [runs-summary.json](wiki-query-confidence-rules-2026-11-16/runs-summary.json) にある。
