# PDF 取り込みと永続ジョブの統合検証

実施日：2026年11月4日（日本時間）。

## 修正と判断

wiki の取り込みコマンド、info-hive スキル、その参照ワークフローに、PDF を `register_pdf` へ渡す手順を追加した。
PDF 原本をコピーせず、返されたジョブ ID を保持する。
`completed` の抽出 Markdown を読んでから、wiki の要約ページを作る。
コマンドと自然言語の両方に同じ分岐を記載し、閲覧だけの依頼は登録しない。

製品 rag に、SQLite の登録台帳と子ワーカーを追加した。
受付時はファイル属性を確認してジョブを保存し、PDF の読み込み、抽出、OCR、埋め込み、索引公開は接続中のワーカーが進める。
同じ保存先のワーカーはファイルロックで一つにする。
接続がなくなると子孫の OCR プロセスも停止し、次回接続で未完了ジョブを再開する。
キャンセルと失敗は自動再試行しない。

この実装は、[前回の PoC](../rag-poc-2026-11-04/README.md) の独立した制御コアとは異なり、製品の抽出・OCR・埋め込み・索引更新を同じジョブにつないで検証した。
子ワーカーは停止とネイティブライブラリの扱いを分離するために使った。
検索も同じワーカーで実行し、MCP の受付は検索ライブラリとモデルの読み込みを待たない。
同じ設定の検索と索引化はモデルを再利用するが、ワーカー内では直列に進める。
長い索引化の途中に投げた検索は待機する。複数セッションの負荷と大規模性能は、今回の検証範囲に含めない。

## 解消した不具合

| 不具合 | 修正 |
| --- | --- |
| wiki から rag への接続がない | PDF 登録と状態確認の MCP 呼び出しを、コマンドとスキルの手順へ追加 |
| `PdfPage` と `PdfTextPage` を `with` で扱うと `TypeError` | `contextlib.closing` で明示的に閉じる |
| 索引公開の SQL が 9 列に 10 個の値を渡す | 列名を明示し、値数を一致させる |
| 配布用の環境で OCR 画像を描画できず `No module named 'PIL'` | Pillow を配布用の依存宣言へ追加 |
| Windows で接続監視中に NumPy の初期化が長く待機する | 子ワーカーはブロックする stdin 読み取りを避け、`PeekNamedPipe` で親の消失を検知 |
| MCP の最初の検索で NumPy / SciPy の初期化待ちが受付に影響する | 検索もモデルを持つ子ワーカーへ渡し、MCP では重いライブラリを読み込まない |
| 長い完了待ちがほかの MCP 操作を妨げる | `job_status` の `wait_seconds` は async の待機とし、30 秒以下に制限 |

停止箇所の調査には py-spy 0.4.3 を使い、実プロセスのスタックで NumPy と SciPy の拡張モジュールの初期化待ちを確認した。
Windows の修正は、この環境で待機を再現した箇所に対するものである。
OCR 子プロセスの stdin も `DEVNULL` に分離したが、それだけではネイティブ初期化の待機はなくならなかった。
uv の既定キャッシュ `C:/Users/.../AppData/Local/uv/cache` は、この PC では実体が D ドライブと同じボリュームにあり、開発用 venv の C ドライブとは異なった。
配布用環境の初回読み込みには数分かかることもあり、すべての待機の原因を stdin の競合だけとは断定しない。
最終実装では、待機中も MCP の受付と進捗確認ができるように処理を分離した。

## 製品 MCP の統合試験

Windows 11、Python 3.12.13、CPU のみで実施した。
埋め込みは Ruri v3 30m の固定 commit、4 スレッド、バッチ 1 を使い、OCR は NDLOCR-Lite の固定 commit を使った。
埋め込みには実モデルを使い、検索 API からの出典取得までを検証した。

入力は自作の日本語 PDF 42 ページである。
40 ページのテキスト層に、横書きスキャンと縦書きスキャンを各 1 ページ加えた。
検証用 wiki、台帳、索引は `.rag-poc-data/` に隔離し、元の利用者の wiki や書籍は変更していない。

[pipeline-results.json](pipeline-results.json) の **18 件が成功**した。

1. `register_pdf` が永続ジョブを返し、`ingest_pdf` の別名からの重複投入も同じ ID を返した。
2. 40 ページのテキストを保存し、OCR を起動した時点で MCP サーバーだけを強制終了した。テスト側から子ワーカーや OCR を手動で kill せず、子孫が停止することを確認した。
3. 再接続で同じジョブを再開した。保存済み 40 ページの内容ハッシュと更新時刻は変わらず、2 ページの実 OCR を完了した。
4. 実モデルの最初の埋め込みバッチを保存した後、もう一度 MCP サーバーだけを強制終了した。
5. 3 回目の接続で同じジョブが完了した。42 ページを再抽出せず、42 チャンクを重複なしに公開した。
6. 公開後に製品 MCP の `search` から本文、出典の source ページ、PDF ページ番号を取得した。
7. 横書き・縦書き OCR の結果に期待した日本語文があることと、原本 PDF の SHA-256 が変わらないことを確認した。

登録はこの実行で約 26.8 ms だった。MCP 起動と依存関係・モデルの読み込み時間は含まない。
OCR 起動時に中断した試験であり、認識器の特定の演算命令の途中を狙ったものではない。

## Claude Code からの取り込み

Claude Code 2.1.316 に両プラグインを読み込み、`/wiki:ingest` と自然言語による続行を実行するハーネスを用意した。
最初は OAuth セッション失効で停止したが、利用者の再認証後に実行した。
実行環境で不足していた Pillow を追加した後、[claude-results.json](claude-results.json) の **6 件が成功**した。

1. `/wiki:ingest` が、実際のプラグイン MCP `mcp__plugin_rag_rag__register_pdf` を呼び、ジョブ ID と `queued` を返して会話を終了した。
2. 最初の終了後、台帳は `paused` だった。次の独立したセッションでは、自然言語の続行依頼から `wiki:info-hive` スキルが使われた。
3. 同じジョブ ID が自動再開され、実行回数 2 で `completed` になった。`wait_seconds=30` で待機し、後半のセッションは約 250 秒かかった。
4. エージェントが抽出済み Markdown を読み、`raw` の名前付き参照と `rag_job_id` を含む source ページを作成した。
5. `index.md` と `log.md` を更新した。原本のコピーはなく、元の PDF のハッシュも一致した。

この試験では、製品プラグインの `.mcp.json` にある `uv run --script` をそのまま使った。
API だけの試験と、実際の Claude Code が手順を解釈する試験の両方を確認した。

