# 敵対的レビューの指摘と対応

初回レビューは Critical・Major なし、Minor 4 件で `APPROVED` だった。
今回の再利用と回収に関わる反例を調べ、3 件を回帰試験で再現した。
`review-counterexamples-before-fix.log` に OCR 再実行、回収対象の消失、共有違反での中断を残した。
初回の 81 件と実 MCP 17 項目の証跡は `first-pass/` に保存した。

## 回収対象の消失

`_prune_previous` が取り込み直しの一覧を先に外し、削除がロックで保留になった後に再試行しない反例を確認した。
一覧を変える前に回収対象と旧形式の世代を SQLite に確定するようにした。
既存の対象があれば世代を合わせ、行の削除待ちの状態は上書きしない。
削除は `_finish_retirements` に集約した。

## 別 wiki の中断中ジョブ

再登録を 1 バッチ後に止め、別 wiki で同じ資料を差し替えると、保存済み OCR を消す反例を確認した。
未完了の内部ジョブも使用中とみなすようにした。
世代は参照先の wiki の `policy.json` の指紋から求め、自分の設定を使わない。
回帰試験は wiki ごとに違う分割サイズを使い、再開時の OCR を禁止している。

## 共有違反と走査の費用

一時的な `PermissionError` で回収を打ち切る反例を確認した。
共有領域と旧形式の削除が失敗したときは記録を残して後で再試行し、ほかの回収対象の処理を続けるようにした。
ロックの試験も、中断中ジョブがある間はロック解除後も保持し、ジョブ完了後に回収する契約へ更新した。

共有先を文書ごとに調べる費用と、status への件数追加は変更していない。
参照を一括取得して再利用すると、その後に別 wiki が公開した文書を見落とすおそれがあるため、抽出ロック内での現在の判定を維持する。
今回の合格条件は OCR 再利用・回収・再開の整合性であり、多数の共有参照の性能は測定していない。

## 試験の判定

- 禁止フックの読み込みを各ジョブの実ワーカー PID と対応づけ、全 11 禁止接続の一致を必須にした。
- 製品の全スクリプトのハッシュを開始時と終了時に記録し、一致を必須にした。
- 実 MCP に、退役したスキャン文書を設定変更と同時に戻す経路を追加した。埋め込み保存後の一度の失敗から同じジョブを明示的に再試行する。
- 旧台帳の並行移行では SQLite の trace callback と barrier を使い、2 接続が旧スキーマの確認後に BEGIN IMMEDIATE へ同時に進む順序を固定した。ALTER は 1 回だけであることを検査する。

## 再レビューの判定と範囲の明記

再レビューも Critical・Major なしの `APPROVED` だった。
追加した 3 反例は Windows・Linux の 84 件で通過し、実 MCP の最終 21 項目も親側で確認した。

キャンセルした内部ジョブが OCR を保持する指摘は、現在の保持方針の制約として記録した。
`Jobs.retry` は失敗とキャンセルの両方を明示的に再試行できるため、今回は再試行用の OCR を保護する。
キャンセルをキャッシュ破棄とみなす変更や、放棄の推測による削除は行わない。

MCP の中断が `completed=1,total=1` の保存後・公開前だった指摘は正しい。
この試験を複数バッチ途中の埋め込みの実証として扱わず、レポートと集計に境界を明記した。
複数バッチ途中の再開と別 wiki の干渉は、実 LanceDB とスタブ OCR・埋め込みを使う回帰試験の範囲である。
