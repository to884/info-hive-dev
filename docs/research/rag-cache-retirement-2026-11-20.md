# RAG の OCR 結果の再利用と不要キャッシュの回収

2026年11月20日追記：修正を rag 0.5.4 として公開した。
[PR #13](https://github.com/to884/info-hive-rag/pull/13)、[リリース](https://github.com/to884/info-hive-rag/releases/tag/v0.5.4)、[マーケットプレイスの導入確認](../agent-runs/2026-11-20-rag-0.5.4/claude-marketplace.json)を参照。
以下の「未コミット」は検証時点の状態を表す。

2026年11月20日、前の[全量 ANN 検証](rag-full-ann-2026-11-19.md)で残ったキャッシュ管理の 2 件を修正した。
実 OCR・実モデルを使う Windows の実 MCP 試験 21 項目と、Windows・Linux の回帰試験が成功した。
再登録時は保存済み OCR のファイルを保持し、索引リセット後は不要な抽出結果を回収できた。
OS の電源断・再起動、WSL の停止は行っていない。

## 修正

| 問題 | 修正後の動き |
|---|---|
| 退役文書を再登録する前に、再利用する OCR 結果まで削除していた | 抽出ロックを先に取り、その文書の索引行だけを後始末する。共有・旧形式の抽出結果は再利用する |
| 索引リセットで回収記録が消え、退役文書のキャッシュが残っていた | 回収記録を保持する。索引行の削除待ちから、キャッシュだけの回収待ちに移す |

退役の台帳に `rows_pending` を追加した。
行の削除前に埋め込みの再開位置を無効にし、行の削除と索引保守が済んだら `rows_pending=0` を確定する。
キャッシュだけの回収では、行と再開位置を変更しない。
旧 2 列の台帳は、行の削除待ちとして移行する。
取り込み直しの一覧から外す文書も、一覧を変更する前に同じ回収台帳へ確定する。

索引をリセットするときも、今取り込んでいる文書の抽出結果を保持する。
ほかの wiki に公開された文書、取り込み直し待ちの文書、抽出ロックがある文書のキャッシュは消さない。
回収を保留した場合は記録を残し、後の取り込みや明示的な索引保守で再試行する。
別 wiki の中断中ジョブも、相手の方針と世代から使用中と判定する。
一時的な共有違反と旧形式の削除失敗では、記録を保持して後で再試行する。

## 修正前の再現と回帰試験

修正前は次の 2 件が失敗した。
証跡は [before-fix.log](rag-cache-retirement-2026-11-20/before-fix.log) にある。

- 保存済み OCR がある文書の再登録で OCR の呼び出しを禁止すると、再実行して失敗した。
- 退役文書の後始末を保留してから索引をリセットすると、不要な抽出キャッシュが残った。

修正後は、次の追加ケースも通過した。

- 旧 2 列の台帳を複数の接続から開いて移行しても、回収対象を失わない。
- 別 wiki の参照中は保持し、最後の参照がなくなってから回収する。
- ロックで回収を保留した後に再試行しても、新しい索引行と再開位置を消さない。
- 分割サイズを変えて再登録する途中で埋め込みを止め、別文書を公開した後も、OCR 結果と埋め込みの再開位置を使える。

追加レビューでは、取り込み直し一覧から外した後のロック、別 wiki の中断中ジョブ、削除時の共有違反の 3 反例も再現して修正した。
`review-counterexamples-before-fix.log` に修正前の失敗を残した。

Windows は 84 件成功、Linux は 84 件中 82 件成功・Windows 専用 2 件スキップだった。
回帰試験は実 LanceDB を使い、埋め込みと OCR の一部をスタブに置き換えている。
次の MCP 試験では実際の OCR と埋め込みを使った。

## 実 MCP の結果

画像だけの日本語 PDF 2 件と、文字層を持つ差し替え用 PDF を作り、13 ジョブを登録した。
21 項目が成功した。

| 確認対象 | 結果 |
|---|---|
| 初回の OCR | 2 件のスキャンで実 NDLOCR-Lite を呼び、空でない結果を保存 |
| 退役後の再登録 | 保存済みページと `document.md` のハッシュ・更新日時が一致 |
| 再利用経路の OCR | 子ワーカーで OCR の呼び出しを禁止して成功。禁止した経路での呼び出しは 0 回 |
| 未使用のキャッシュ | 索引リセット後に、共有領域の文書ディレクトリを回収 |
| 旧形式・別の抽出条件の結果 | 試験用に置いた旧形式ディレクトリと別キーのディレクトリも回収 |
| 現在の文書 | リセット前後で抽出結果のハッシュ・更新日時を保持 |
| 別 wiki の参照 | 参照中は保持し、回収記録をキャッシュだけの段階で保留 |
| 最後の参照の消失 | キャッシュを回収し、次の同一文書の登録で残った回収記録も解消 |
| 設定変更を伴う退役文書の再登録 | OCR のハッシュ・更新日時を保持。埋め込み保存後のテスト例外から同じジョブ ID の 2 回目で完了 |
| 最終状態 | 13 ジョブ完了。両 wiki の公開台帳と行数が一致し、回収待ちの記録は 0 |

OCR の総呼び出しは、新しいスキャンに対する 2 回だけだった。
テスト用の `sitecustomize.py` で OCR の呼び出しとフックの読み込みを記録した。
再利用する接続の子ワーカーに禁止フックが入ったことも検査した。
後始末の保留は、公開後の製品処理の入口に一時的な例外を注入して再現した。
これらのフックを製品には組み込んでいない。

索引リセットは、分割サイズを 500 → 550 → 600 → 700 文字へ変えて起動した。
OCR の方針・解像度・抽出の版は変えていない。
OCR 条件が変わった場合に古い結果を再利用する変更ではない。
旧形式の回収試験は、今回の実 OCR の JSON を旧形式の場所に配置した検証用の構成である。

今回の実 MCP の中断位置は、全 1 チャンクを保存した後、索引の公開前である。
テスト例外でジョブを失敗させ、`retry_job` で同じ ID を再試行した。
複数バッチの途中から続きを埋め込む経路は、回帰試験で確認した。

未完了の内部ジョブは、失敗・キャンセル後も明示的に再試行できるため、OCR の保持対象として扱う。
放棄されたかどうかを自動判定して消す機能や、キャンセル時にキャッシュを破棄する変更は含めていない。
参照の残る多数の共有文書の走査性能も、今回は測定していない。
