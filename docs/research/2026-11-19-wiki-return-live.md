# 公開後の変更をライブ wiki に書き戻す

[本番有効化の条件](2026-11-19-wiki-production-readiness.md) の④に当たる。公開後の保存を含む最後の公開版を書き戻し、既定の検索と保存をライブへ切り替える。版 ID を指定した引用や browse は、切り戻す前と同じ公開版を使い続ける。

## 運用

```powershell
python "<wiki_apply.py>" plan-return-live --wiki "<WIKI_ROOT>" --raw-root "<RAW_ROOT>" > "<計画.json>"
python "<wiki_apply.py>" return-live --wiki "<WIKI_ROOT>" --plan "<計画.json>" --expect-sha256 "<plan_sha256>"
python "<wiki_apply.py>" recover --wiki "<WIKI_ROOT>"
```

初回公開時のライブと、最後の公開版の両方を照合する。承認済みの未適用の保存があれば、再試行か明示的な取り消しが済むまで切り戻しを待つ。切り替えの記録を始めたあとは、新しい公開保存の受け付けを止める。ライブだけのファイルを保持し、公開版の追加・更新・削除を反映する。ライブに別途変更が入った場合や、公開後の追加先がライブ専用ファイルと重なる場合は停止する。初回の公開で内容が変わったファイルは、元のライブ側のバイト列を保全してから書き戻す。

切り戻し中の読み取りは公開版を使う。書き戻したファイルと完了記録が揃ったら、wiki の既定の読み取りをライブへ切り替える。途中で止まった場合は `recover` か同じ承認の `return-live` を使う。済んだ切り戻しを再試行すると `already_returned` が返り、その後のライブ保存は保持される。

## 検証結果

前回と同じ公開195記事・212ファイル、ライブ192記事、原本160件の隔離 wiki で、各保存が使う CLI と実際の公開処理を試した。

| 試験 | 確認した結果 |
| --- | --- |
| 並行保存 | 4件を同じ公開版から開始した。未適用の承認がある間は切り戻しが停止した。初回に3件が公開され、保留の1件は同じ承認で再試行できた。先頭が変わる前に作った切り戻し計画も拒否した。 |
| 書き戻しと再試行 | 17ファイルを書き戻した。4件は記事・索引・ログ・Ossie SQLite の記事行に一度ずつ入り、古い公開保存の再試行は同じ公開版 ID を返した。切り戻しの再試行後も新しいライブ保存が残った。ライブ専用ページ、初回公開で内容が変わったライブのグラフ、原本160件を照合した。 |
| 強制終了と破損 | 同規模の wiki では最初のファイルを書いた直後に強制終了し、`recover` で再開した。別の隔離 wiki では日誌、状態の印、ファイル、完了記録、切り替え直後の計7箇所で中断させた。日誌だけを退避したときは復旧が停止し、戻すと再開した。 |
| 読み取りの継続 | 書き戻し途中の既定の検索は公開版を使い、完了後はライブを使った。版を指定した MCP の引用、起動済み browse の HTML・添付は切り戻し後も同じ公開版を参照した。 |

新規4件と既存113件の試験が通った。同規模の試験の全体は約226秒だった。初回レビューで指摘された状態の印・完了記録の一時ファイルを復旧対象に加え、初回公開時に内容が変わったライブファイルを保全するようにした。再レビューで重大な指摘はなく、グラフ抽出の出力先の判定と手順の案内を修正した。

日誌を開始した後にファイルが計画と食い違えば、公開の読み取りを続けたまま書き込みを止める。管理ファイルや原本が失われた場合は、それらの復元と照合が必要になる。本番の切り替え、切り戻し後の再公開、実機の電源断は今回の対象外とした。

SemaSynth wiki には指紋照合の読み取りだけを行った。前後の83ファイルに2件の差分があり、変更元は未確認である。
