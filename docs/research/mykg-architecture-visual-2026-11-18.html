Pass 1 の内側は「バッチの案 → 機械的な統合 → LLM の整合化 → 品質レビュー」。案を作るバッチ数は既定で最大 50。超えると標本を選ぶ。スキーマ検証の失敗時に LLM に修正を求める経路もある。MinerU は一時的な uv 管理の Python 3.12 環境で動く。

孤立ノードの補正が上限に達すると、更新済みの型・関係の定義にグラフが追いつかない場合がある。部分的なのは Pass 2 の読み直しで、下流は全体を再実行する。人のレビューを有効にしていれば再び承認待ちになる。補った関係の印は orphan_inferred。

設計を理解するときの 3 つの留保

検証が停止条件とは限らない

スキーマの検証は警告で継続する場合がある。人のレビューも任意。高度な OWL の論理推論は対象外。

混合バッチは出所が粗くなる

複数文書をまとめると、出所の過剰付与や変更・削除後の残存が起こりうる。厳密さが必要ならファイルを混ぜない。

保存形式と探索の表現は違う

メモリ上の DiGraph は、同じ向き・同じ両端の複数の関係を独立した多重エッジとして保持しない。JSONL の全関係とは区別する。

出典と確認した範囲

README・設計文書・主要実装の読解に基づく。抽出精度・性能・LLM 費用の測定は行っていない。図は資料をもとに再構成した。
