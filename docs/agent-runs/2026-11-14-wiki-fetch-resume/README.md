# wiki_fetch.py の取得の前の再開のレビュー（2026-11-14）

設計書: [docs/plans/wiki-fetch-resume-before-fetch-2026-11-14.md](../../plans/wiki-fetch-resume-before-fetch-2026-11-14.md)

`ask-codex` スキルで、GPT-6.1 Sol（effort high）に敵対的レビューを頼んだ記録である。各回の依頼は `*-task.md`、結果は同じ名前の `.md` にある。

| 回 | 対象 | 判定 | 主な指摘 |
| --- | --- | --- | --- |
| 設計 1 | 1 版の設計 | 却下（高） | 再開で警告が消える。`fetch.json` を `fetched.md` と照らさない |
| 実装 1 | 2 版の実装 | 却下（高） | 同じ原文を別の設定で取った `fetch.json` を見分けられない。`freeze` の報告を読む段を飛ばす |
| 実装 2 | 3 版の実装 | 却下（高） | 別の取得の `cleaned.md` を照らさない。`fetched.md` が同じ別の取得の `fetch.json` |
| 実装 3 | 4 版の実装 | 却下（高） | 0.14.0 の写しを続ける互換の経路で、別の設定の旧版の記録を見分けられない。旧版の記録に `source_sha256_of` がない |
| 実装 4 | 5 版の実装 | 却下（高） | 新版の写しの保証は崩せず。旧版で DOM から始めた取り込みを URL で呼ぶと、終了コード 3 で、旧版の写しを続けられないことが伝わらない |

実装 1 は、依頼の差分のファイルを worktree の外に置いたので、Sol は差分を読めなかった（ファイルを直接読んで確かめた）。実装 2 からは、差分を `impl-2.diff`、`impl-3.diff`、`impl-4.diff` として、このフォルダーに置いた。実装 3 の 1 回目の実行は PC の再起動で止まったので、`main`（to884/info-hive-wiki#54 を含む）をマージしてから、同じ依頼でやり直した。

4 版で、保証を「取得の出自」から「写しの組の整合」に定め直した。実装 2 の 2 つ目の指摘は、この定義では欠陥でない（設計書の「前提」と「改訂の履歴」）。

5 版で、0.14.1 までの版の写しを続ける互換を捨てた。実装 3 の重大 2 件は、これで構造ごとなくなった（実装 4 で崩されなかった）。6 版で、旧版の写しがあることを、取得の結果によらず知らせるようにした。6 版はレビューにかけていない。
