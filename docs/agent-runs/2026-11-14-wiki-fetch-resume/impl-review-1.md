## 致命的・重大な欠陥

1. **重大：同じ HTML を異なる設定で処理した取得記録を区別できず、別の取得の警告・削除記録を返す。**

   再現手順：

   - MediaWiki の HTML を用意する。本文は、`<td class="metadata">` に約 1,400 文字を入れた表とする。
   - 取得 A：通常の設定で取得する。表が削除され、`chars: 0`、「本文が空」の警告、表を消した `removed_by_rule` が出る。A の raw と写しを保存する。
   - 取得 B：同じ URL・同じ HTML を、`--keep-noise --force` で取得する。`chars: 1417`、`warnings: []`、`removed_by_rule: []` になる。
   - A の raw と `fetched.md` を戻し、`fetch.json` だけ B にする。部分復元を仮定した状態である。
   - 同じ URL で再実行する。

   実コードを動かすと、**取得呼び出し 0 回、終了コード 0、`fetch_skipped: true`、`chars: 1417`、`warnings: []`** になった。実際の raw は題名しかない。削除記録も消えるため、W3 では本文の欠落も誤削除も分からない。さらに通常どおり `translated_by` を記入すると、`freeze` と `check` はともに警告なしで通った。

   A と B の取得時刻を **08:00 と 09:00** に固定し、frontmatter が異なることも確認した。設計書で範囲外としている「同じ秒の取り直しで frontmatter が同じ」という限界には依存しない。

   原因は、JSON との照合対象が `url`・`final_url`・`source_sha256` だけで、抽出結果の異なる取得でもすべて一致することである。

   根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py:298–325`、同 `338–340`、`wiki_fetch.py:1267–1268`、同 `1358–1360`。設計書 `docs/plans/wiki-fetch-resume-before-fetch-2026-11-14.md:45` と、`info-hive-wiki/CHANGELOG.md:14` の保証は、この反例では成立しない。

2. **重大：`freeze` の警告を確認する前に中断すると、再開で確認手順を飛ばす。既存の `frozen` 経路にも共通する。**

   再現手順：

   - 十分に長い本文を取得し、原文の約半分を削除する。
   - `freeze` を実行し、その出力を確認する前に中断する。
   - URL だけで再開する。

   検証では、`freeze` は **800 / 1522 文字を削除した警告**を返し、`cleaned.md` を作った。再開は `work_stage: frozen`、`warnings: []` を返し、削除した行も返さなかった。

   W2 は `frozen` なら W6 へ進む。一方、W5 が要求する「消したものを読み、本文を消していないか確かめる」は未実施のままである。`cleaned.md` の存在は固定処理の完了を示すが、警告や削除内容の確認済みを示さない。

   根拠：`wiki_rawcheck.py:654–668`、同 `335–343`、`info-hive-wiki/commands/ingest.md:33,40`。今回初めて導入された欠陥とは断定しないが、取得前の再開でも残っている。

## 崩れる前提

- **原文の取得元とハッシュが一致すれば、取得結果も同じである。**  
  同じ HTML を `--keep-noise` など異なる設定で処理すれば崩れる。別取得の JSON でも、照合する三つの値は一致する。

- **`cleaned.md` があれば、W5 の確認も済んでいる。**  
  `freeze` がファイルを書いた直後、出力を確認する前に中断すると崩れる。

- **取得後の再開でも、返す取得元と作業用の写しが対応する。**  
  別 URL が同じ HTML を返す場合や、同じ `--html-file` に別の `--page-url` を指定した場合に崩れる。取得後の枝は今回の URL・最終 URL と、以前の写しの `work_stage`・取得結果を組み合わせて返す。

## 見落としと軽微な問題

- **軽微：取得後の再開では、テキスト出力から警告と削除記録が消える。**  
  短い本文を取得後、同じ内容を `--html-file` で渡すと、JSON の `warnings` には警告が戻る。しかし `render_text` は「内容は前回と同じなので、書き込まなかった」だけで戻る。取得前の再開とは表示が異なる。根拠：`wiki_fetch.py:1438–1443`。既存枝に残る問題であり、JSON を使う W2 には直接影響しない。

- **軽微：frontmatter の `final_url` の型不正を、欠落と同じに扱う。**  
  raw と `fetched.md` の両方へ `final_url: []` を入れ、JSON の `final_url` が `url` と同じなら、再開可能になることを確認した。`fm.get("final_url") or fm.get("url")` により、空配列を拒否せず代替するためである。取得器が通常生成する状態ではない。根拠：`wiki_rawcheck.py:321`。

- **軽微：追加試験は、別取得との衝突を一つずつ異なる値にする場合しか検査していない。**  
  `test_fetch_json_of_another_fetch_is_not_resumed` は三つの識別値を個別に変えるため、重大 1 の「三つとも同じ、抽出結果だけ違う」状態を見逃す。取得後の警告試験も JSON の確認だけで、テキスト表示を検査していない。根拠：`tests/wiki/test_wiki_web_check.py:1622–1651`。

- **軽微：返却項目の検査が実装の定数に依存する。**  
  `for key in wiki_rawcheck.RESUME_KEYS` では、実装から `encoding`・`content_root`・`chars`・`dropped_images` を落とすと、それらの検査も消える。これらは直前の独立した返却項目の検査にも入っていない。根拠：同 `1514–1515,1618–1619`。

## 検証した事実

- **一致：** 通常の取得前の再開では、保存された取得時の警告が返り、ネット取得は呼ばれない。
- **一致：** `fetch.json` の正式名への変更は raw の書き込み後にある。書き込み順自体は維持されている（`wiki_fetch.py:1417–1422`）。
- **一致：** W3 の DOM による取り直しには `--force` が追加されている。
- **食い違い：** CHANGELOG の「`fetch.json` だけが別の取得のものでも、その値を返さない」は重大 1 で成立しない。
- **確かめられず：** 指定された `impl-1.diff` は `PermissionError` で読めなかった。サブモジュールの Git 差分も取得できず、変更前との厳密な比較と、0.14.0 の実物の写しとの互換性は確認していない。
- 反例はファイル操作をメモリへ差し替え、実際の `build`・変換器・`freeze`・`check` を実行した。リポジトリは変更しておらず、既存試験一式は実行していない。

## 崩せなかった点

- URL の frontmatter 往復は、ASCII 全文字、引用符、バックスラッシュ、制御文字、U+0085・U+2028・U+2029・U+FEFF・絵文字を含む検証では崩せなかった。

- W3 の `--force` が実行される場合、古い写しへの再開だけを繰り返すループは見つからなかった。
