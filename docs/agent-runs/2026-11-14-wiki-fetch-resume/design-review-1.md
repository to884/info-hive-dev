## 判定

**却下。確信度：高。** 取得に失敗した内容を警告なしで再開する反例と、別の取得の `fetch.json` を使って誤った URL・ハッシュを返す反例を確認した。いずれも、設計の条件 1〜7 を満たす。

## 致命的・重大な欠陥

1. **重大：本文を取得できなかった状態が、警告なしで再開され、後段の検査も通る。**

   再現手順：

   - URL から「記事を読み込んでいます」という短い日本語の本文だけを取得する。初回出力には「本文が短い」という警告が入り、raw と写しが作られる。
   - W3 で警告を確認する前に中断する。
   - 同じ URL・スラッグで再実行する。

   実装は取得せず、`warnings: []`、`work_stage: "fetched"` を返す。W2 の指示どおりなら W4 へ進み、W3 のブラウザによる本文取得を飛ばす。

   メモリ上で実際の変換器と検査器を動かした結果、読み込み待ちの文だけで `freeze` と `check` がともに終了コード 0、警告なしになった。サーバーがすでに完全な本文を返す状態でも、取得呼び出しは 0 回だった。取得前の再開を通さず比較すると、同じ入力条件で終了コード 3 になる。

   既存の取得後の再開枝にも警告を失う問題はある。ただし今回の変更は、原文が変わって従来なら停止した場合まで、警告なしで先へ進める。「更新を知らせない」という意図とは別に、**初回取得の失敗を知らせなくなる**。

   根拠：設計書の出力指定 `warnings: []`（48 行目）、`wiki_fetch.py:1215–1224`、同 `1389–1392`、`commands/ingest.md:33`、同 `36–37`。

2. **重大：`fetch.json` と raw／`fetched.md` の取得元・ハッシュを照合していない。**

   反例の状態：

   - raw と `fetched.md` は取得 A のもので、frontmatter は完全一致する。
   - `fetch.json` だけが取得 B のものになっている。
   - 今回の位置引数には B の URL を渡す。

   部分的なバックアップ復元などで、この組み合わせが生じた場合を仮定した。単一の取得器を通常どおり順番に動かすだけで発生するとは主張しない。

   実コードでこの状態を与えると、次の結果になった。

   ```text
   raw の URL／SHA-256：A／aaaa…
   出力の URL／SHA-256：B／bbbb…
   終了コード：0
   fetch_skipped：true
   work_dir：true
   取得呼び出し：0 回
   ```

   `work_dir_matches_raw` が比較するのは raw と `fetched.md` だけである。`resumable_fetch` は JSON の `url` と `source_sha256` の型しか検査しない。このため、A の内容に B の取得情報を組み合わせて返せる。

   `fetch.json` を最後に置く順序は、正常に書いた時点の整合性を保証する。しかし、部分復元後にも三者が同じ取得であることまでは保証しない。取得前に戻ることで、従来は新しく取得したバイト列から返していたハッシュまで、食い違った JSON に依存する。

   根拠：設計書の条件 5〜7（38〜40 行目）、`wiki_rawcheck.py:263–274`、同 `281–294`、`wiki_fetch.py:1215–1224`。

## 崩れる前提

- **「写しがそろっていれば、本文取得の確認は済んでいる」**  
  raw と写しを書いた直後、W3 より前に中断すれば崩れる。写しの完成は、本文を取得できたことや警告を確認したことを表さない。

- **「raw と `fetched.md` の一致で、`fetch.json` も同じ取得と分かる」**  
  JSON だけが別の世代から復元された場合に崩れる。

- **「frontmatter の一致で、手で戻した raw を見分けられる」**  
  frontmatter が同じ版へ本文だけ戻した場合には見分けられない。コード自身も、同じ秒の取り直しでは frontmatter が同じになり得ると明記している（`wiki_rawcheck.py:266–268`）。後段の検査が拒否する場合はあるため、それだけで誤った取り込み完了になるとは断定しない。

## 見落としと軽微な問題

- **軽微：JSON の型検査が、後続処理の必要条件を満たしていない。**  
  正しい文字列の `url`・`source_sha256` があっても、`images: null` と `cleaned.md` があれば再開可能と判定し、`remaining_images` で `TypeError` になることを確認した。取得へのフォールバックにはならない。根拠：`wiki_rawcheck.py:291–311`、同 `224`。既存枝にも関連する問題で、今回初めて発生する欠陥とは扱わない。

- **軽微：`--html-file` の除外理由は成立するが、W3 の再試行はそのまま成功しない。**  
  URL 取得で空の raw を作ったあと、W3 の指定どおり DOM を渡すと、ハッシュが違うため終了コード 3 になる。W2 はこれを「ページが更新された」と扱い、ユーザーへの確認に進む。これは既存の詰まりであり、今回の回帰とは判定しない。根拠：設計書54行目、`commands/ingest.md:34,37`、`wiki_fetch.py:1249–1264`。

- **軽微：試験計画と追加済み試験に、上記の反例がない。**  
  特に「W3 前の中断」「raw／`fetched.md` と JSON の世代不一致」「必須キー以外の型不正」が抜けている。`ResumeBeforeFetchTest` の不正 JSON 試験は、配列、URL 欠落、URL の型違いを検査しているが、これらは検査していない（`tests/wiki/test_wiki_web_check.py:1608–1620`）。

## 検証した事実

- **一致：** レビュー中に、設計に対応する実装と `ResumeBeforeFetchTest` が追加された。指摘は追加後のコードでも確認した。
- **一致：** `fetch.json` は raw の書き込み後に正式名へ変更される。今回の再開処理も、この書き込み順を変更していない。
- **一致：** `check --finish` は誤りや未承認の警告が残れば写しを保持する（`wiki_rawcheck.py:1015–1023`）。
- **食い違い：** 「取得器の書いた形」という検査は、取得情報の相互整合性や、後続処理で使う値の型を保証していない。
- 反例はファイル操作をメモリ上へ差し替え、実際の `build`・変換処理・`freeze`・`check` を呼んで検証した。リポジトリは変更していない。既存試験一式は実行していない。

## 崩せなかった点

- `--force` と `--html-file` は取得前の再開から明示的に除外されている。
- JSON の URL が今回と違う場合、取得前には戻らず、従来の取得処理へ進む。
- raw の frontmatter が写しと異なる場合、取得前の再開は成立しない。
- raw の書き込み前に停止した `--force` の写しを、完成した写しとして扱う反例は見つからなかった。
- `unchanged: true` と `fetch_skipped: true` の組み合わせ自体が、現在の W2 の分岐を誤らせる反例は見つからなかった。問題は、再開対象の判定と警告の欠落にある。
