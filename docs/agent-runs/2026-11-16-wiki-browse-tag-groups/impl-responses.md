## 試験の結果（2026年11月16日、Windows、Python 3.14.6、Chromium）

プラグインは 0.21.1（`4ffecc5`）の上の変更で流した。main の 0.21.2 は query の文書だけの変更で、browse のファイルに触れない。

| 試験 | 結果 |
| --- | --- |
| `tests/wiki/test_browse.py` | 100 件、OK（4 件は skip） |
| `tests/wiki/test_browse_server.py` | 58 件、OK（1 件は skip） |
| `tests/wiki/test_browse_fs.py` | 33 件、OK |
| `tests/wiki/browse_nav/nav_model.py` | 全例で 2.4 の性質を満たす |
| `findability.test.mjs` | 失敗 0 件（Tree の作り、キーボード、ローヴィング、押す操作、見た目、深い段、コントラストを含む） |
| `browse.test.mjs` | 失敗 0 件 |
| `startup.test.mjs` | 1,000 ページで中央値 1,877 ms（目安 5,000 ms）。索引のページは 2,162 ms |

最終のレビューのあと、直した試験で、`findability.test.mjs` を Chromium、Firefox、WebKit の 3 つで流した（静的とサーバーの両方の方式）。Chromium と WebKit は失敗 0 件、Firefox はサーバーの方式で失敗 0 件だった。Firefox の静的の方式の 3 件（検索の索引の後読み、読めない検索の索引、遅れて届く検索の索引）は、Firefox の Playwright が `file://` の要求を捕まえないことによる、前から記録されている試験の道具の制約である（`wiki/concepts/browseの画面の確かめ方.md`）。

WebKit では、最初に「Index のページで葉を押したあと、Tab で木の外に出る」が落ちた。WebKit はリンクを押してもフォーカスを移さないので、ローヴィングの同期（`focusin`）が働かず、Tab の入口が押した葉にならなかった。`app.js` で、葉を押したときにもその葉にフォーカスを移すようにした。そのうえで、マウスで押した直後のリンクからの Tab は、WebKit ではフォーカスが動かない（ブラウザの決まり）ので、試験は、木の後ろの入力欄から Shift+Tab で戻って押した葉に入り、そこから Tab で木の外に出ることを確かめる形にした。Edge と Chrome では流していない。

main（0.24.0）を取り込んだあと、`test_browse.py` は 100 件 OK だった。

このリポジトリの `wiki/` を worktree の版で開き、記事のページと索引のページの左のペインを、light と dark の両方で Playwright（Chromium）で撮った（`shots/`。記事のページ、枝にポインターを置いた状態、索引のページ、幅 360 の「メニュー」）。

撮った画面で、子の枝の行にポインターを置くと、祖先の枝の「一覧」まで出る不具合を見つけた。同梱の CSS は、項目（`TreeItem`）のホバーで actions を出すためである。「一覧」を出す条件を、その行（`TreeItemLayout`）自身のホバーと、その項目か「一覧」のフォーカスに絞り（設計の 6.4）、試験を足した。この直しのあと、`findability.test.mjs` は失敗 0 件だった。

画面を見た作者の決定で、3 点を直した（設計の「作者が決めたこと」）。件数のバッジを名前のすぐ隣に置いた。字下げを Fluent 2 のサイトの形（1 段目と 2 段目の名前がそろい、3 段目から 1 段ずつ下げる）にした。1 段は最初 34px にし、そのあと作者の決定で 18px に寄せた。バッジを tint にし、地を `colorNeutralBackground6` に替えて、暗い配色でも黒く沈まないようにした（比は light 4.96、dark 5.63）。試験に、バッジが名前の右端から 12px 以内にあることと、字下げの形を足した。直したあと、`test_browse.py` は 100 件 OK、`findability.test.mjs` は失敗 0 件だった。`shots/` の画面は、この直しのあとに撮り直した。
