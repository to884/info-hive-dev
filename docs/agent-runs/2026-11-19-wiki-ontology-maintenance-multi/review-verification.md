## 修正対象と確認した点

### V1 / P1: 役割の相手・製品・期間と、問い合わせの意味

対象: M27、M124–136、G22。指摘元: A重大3、B重大1、D重大1。

反証: G22は役割の扱いを実際の資料に照らして決めるとしており、全wikiに同じ意味モデルを固定する要件ではない。現行実装に役割専用の欄がないことだけでは、将来機能の要件の矛盾とはならない。
ただし、A社が製品Aの顧客・製品Bの販売代理店である場合、相手・対象・時期を持たない役割ラベルでは、製品Bの顧客一覧までA社を含める読みが可能になる。Mの役割の例はこの期待結果を定めていない。

修正する内容: A社の実体は1つ、製品Aの顧客には入る、代理販売だけを根拠に製品Bの顧客には入らない、期間が変わった場合の回答を定める。宣言・関係・導出・複数型のどれを使うかは、この意味を満たす方式として実装設計で選ぶ。
「顧客を役割にしたらユーザー要件に違反する」という断定は採用しない。ユーザーは粒度を指定しており、形式的なクラスへの固定は求めていない。

### V2 / P1: 主張の分割では、矛盾・訂正の参照先の意味を再判断する

対象: M53–68、M114。指摘元: C重大3、D重大4。

反証: M114はIDと参照の対応を検査すると明記しており、リンク切れを見落とした設計ではない。
しかし旧「利用する」を試用と契約に分割した場合、「未契約だった」が否定するのは契約だけである。旧IDから新ID2つへの機械的な対応では、どちらへの矛盾かを決められない。
現行lintの`wiki_graph_lint.py:290–297`は参照先の存在を検査するだけで、この意味を確かめないことをローカルで確認した。

修正する内容: 参照する側の引用・対象・期間を照合して、矛盾や訂正の対象を決める。特定できなければ旧主張と未確定の参照を保持し、関係の意味を保てない変更は保留する。参照先が存在することと、正しい主張を指すことを分ける。

### V3 / P1: 問い合わせの網羅性には、未抽出・同一性の保留・移行残件を含める

対象: F139–175、F179–190、M70–78、G63。指摘元: B重大3、C重大2。

反証: G63には既存記事をproposeで発見する経路があり、繰り返しpropose/applyすることは可能である。「既存記事を記録する操作が全くない」との断定は強すぎる。またM73は同じ実体の二重計上を禁じ、M74は影響する問いへの注記を要求している。
残る不足は、少数事例のみ適用した後の通常の回答で、未抽出の記事と同一性の保留による不完全さをどう示すかである。移行残件だけの注記では、「顧客は何社か」を少数の記録だけで答える問題が残る。

修正する内容: 分析済みと記録済みを区別し、既存記事へ採用済み定義を適用していく利用の流れと、問い合わせの対象範囲・網羅性を示す。同一の利用事実を2記事が支えても顧客数は1社、無関係な製品の保留をその問いの残件へ混ぜない、という受け入れ例を置く。根拠の本数・主張の件数・実体の数を区別する。

### V4 / P1: 連続する部分移行と、版が不明な記録の扱い

対象: M65–78、M118–120。指摘元: D重大3、B中1。

反証: M72は記録の版・移行元・移行先・理由を保持するため、複数回の移行を絶対に表せないわけではない。
ただし、v1の保留を残したままv2からv3へ再編し、後の根拠でv1の保留が解消したとき、どの版へ確定し、現在の実体と重複しないことをどう確認するかは未記載である。

修正する内容: v1のAプランをv3の保守契約1件として確定し、旧版残件は0件、元の保留理由と後の根拠を両方たどれる例を定める。版のない記録を黙って現行版で確定済みとみなさず、基準の確認か保留へ送る。
初期提供を全件移行だけにする案は選択肢だが、必須の修正とは判断しない。採るなら残件が永続するときの次の見直しの扱いも明示する。

### V5 / P1: 公開する版と、共通の書く段に必要な拡張

対象: M107–116、F205–211。指摘元: A重大1、B重大2、C重大4。

反証: MとFは現行の書く段をそのまま使えるとは説明していない。未実装と追加設計の必要性を明記している。物理的なページの削除・改名や、正本を単一ファイルに集約することも、すべての方式で必須ではない。
一方、ADR-0023はグラフDBを範囲外とし、読み手が途中の内容を読むことも防がない。詳細設計のP4とP6は正本更新とグラフ生成を分けている。したがって「新旧混在を完了結果として公開しない」を実現する追加の契約が必要なことは確認できた。

修正する内容: 1回の問い合わせが候補検索から引用の読み取りまで同じ公開版を見るか、版が揃わなければ回答を再試行・保留することを明示する。書かない依存先の変化も検査する条件、移行中のextract、古い定義で用意したingestを扱う条件を、ADR-0023の拡張または別の関連ADRの検討事項として明記する。
ステージングとポインタ切り替えは有力な実装案だが、このレビューだけで唯一の方式には決めない。任意の外部編集や複数PCまでの保証を新たに追加しない。

### V6 / P1: 並行ingestで実体の新規作成を確定する条件

対象: M112–119、F135–144、G89–93。指摘元: C重大1。

反証: 同じ実体を二重管理しない方針は既存の要件にある。確定した識別情報から同じIDを導く方式なら、反例の「異なるIDを準備する」は起きない可能性がある。
しかし、その方式も、対象が未登録だと判断した前提をcommit時に確かめ直す規則も未決定である。ADR-0023は意味の重複の検出を明示的に範囲外としており、書き込みの直列化だけでは自動的に解決しない。

修正する内容: 同じメーカー・品番を持つ対象を2つのingestが並行作成しても、完了時に実体は1つ、出典は2つとなる受け入れ条件を置く。同一性を確定する仕組みは実装設計で選び、曖昧な意味の同一性すべてを機械判定できるとは約束しない。

### V7 / P2: 採用済み定義の意味・適用基準を保存する

対象: M21–35、M106。指摘元: B中3。

反証: 定義と判断を保持する要件は存在する。したがって意味を保存することが禁止された設計ではない。
ただし、現行の型はラベルと`maps_from`だけでも記述できる。見直し時に再利用する正本に、定義文、該当・非該当の条件、用途と問い、採用理由を含めることを明記すると、見直しごとにラベルから意味を推し直す余地を減らせる。

### V8 / P2: 記事で見た範囲と原本で確かめた範囲を区別する

対象: M37–45、M108。指摘元: C重大5、D重大2。

反証: ユーザーが求めている出発点はwikiの記事であり、全原本を毎回読み直すことは指示されていない。Fも「最適」を保証していない。記事が正しくても原本にしかない事実を全件発見できることは、当然の保証には含めない。
それでも、必要な区別が旧要約で失われている場合に、要約だけを全件読んだ結果を原本全体の判定と取り違えない条件は必要である。現行ingestの要約と独立ページ化は情報を選別する（ingest-workflow.md:353、378）。

修正する内容: 記事・原本それぞれの確認範囲を示し、問いに必要な区別を記事で確かめられなければ該当原本へ戻るか判定不能とする。再分析の再利用には、記事の指紋だけでなく定義の版・問い・確認した原本も含める。

### V9 / P2: 型を解けないときの縮退と、旧構成の適用可否

指摘元: B中2、C重要6。

型: 現行extractとlintは、導出できない型を`concept`へ落とし、未知の明示型を専用に検出する項目もない（extract:555、lint:131–176）。通常の記事ナビゲーションの既定と、移行中の実体の型が未確定であることを区別する検査が必要である。現在のlintを無変更で使えるとの誤認を避ける。
構成: ADR-0023は`wiki/raw`を持つ旧構成を、書く段の利用前に移すとしている。SCHEMA.mdの存在だけでapply可能と判断せず、対象を選んだ段階で共通の書く段の適用条件を示す。自動で原本を移動することは、このレビューから追加しない。

### V10 / P3: 表示済みの案を採用したときの確認回数

指摘元: D軽微。F133は表示済みで依存のそろった選択への再確認を省くが、F151は語彙だけなら一律に再確認する読みが残る。
最終差分と試行結果を表示・採用済みかどうかで統一する。選択済みの同じ案を再承認させない。

## 断定を棄却した点・任意の改善

- **固定IDへ変更しなければ要件が必ず破綻する（A重大2）: 棄却。** M62・114は旧IDとの対応と参照の移行を認め、現行も明示したnode_idを保持する（extract:546–555）。ハッシュで変わることと、対応を保持できないことは同義ではない。固定IDは実装コストを減らす案として評価する。V2の参照の意味の問題は別に修正する。
- **ページ削除・改名がすべての移行で必須、別正本は必ず単一ファイルで競合する（A/B）: 棄却。** 正本の保持・対応の記録・廃止の表現や分割した正本などを選べる。公開・依存検査に不足があるV5は残る。
- **部分移行を初期版から外すべき（A）: 選択肢。** V3・V4・V5を満たす必要はあるが、完全移行に限定することだけが解決ではない。
- **ingestで乖離の印を自動収集しないのは欠陥（A中2、Bの判断事項）: 任意の最適化。** 手動で見直しを始め、未完了を明示して再開する経路がある。新しい語彙の自動採用と兆候の収集は区別できるが、ユーザーの要件から必須とはしない。
- **機械が保証することと意味判断（A中3）: 一部対応済み。** M100–102・F125–127は構造検査と意味確認を区別する。実装設計では、固定した案の適用・版の検査と、LLMや利用者の意味判断の責任を引き続き分ける。
- **前回のOpusレビューが先送りをすべて許して承認した（B）: 事実として棄却。** 直前の[Opusレビュー](../2026-11-19-wiki-ontology-maintenance/opus-review.md)の判定はREJECTEDである。
- 保存方式、部分移行の提供段階、ID方式、一覧と件数の決定的な計算、記事ナビゲーションと実体グラフの表示、規模と所要時間は次の設計判断に残す。未決定という理由だけで要件不成立とはしない。

- 反例は架空データによる机上検証であり、再現試験や並行実行試験はしていない。設計と実装の問題を同一視しない。発生頻度も測定していない。
