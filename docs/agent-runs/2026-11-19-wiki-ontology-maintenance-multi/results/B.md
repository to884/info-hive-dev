## 結論

**判定: 要修正（REJECTED）。重大 3 件、中 4 件、作者の判断が要る点 5 件。**

3 文書は禁止事項（「〜しない」）は厚く書けていますが、次の 3 点が決まっておらず、どの保存方式を選んでも今の文面のままでは成り立ちません。

1. **「役割」に定義がない（重大）。** 要件 1 が名指しする「顧客」と、見直しの中心例が、現行のオントロジーに存在しない構成物に依存しています。
2. **適用の一体性と「新旧混在を公開しない」が、承認済みの ADR-0023 と今の読み手の仕組みでは満たせない（重大）。** 「ADR-0023 と整合する実装設計」では済まず、ADR-0023 の改訂が前提になります。
3. **採用後に、既存記事から実体を記録していく操作がない（重大）。** 実体の粒度のグラフは「少数事例＋新規の取り込み」でしか育たず、問い合わせの網羅性の注記もありません。要件 1 は例示の範囲でしか満たされません。

指摘の基準は次のとおりです。「実装設計で決める」と先送りした項目は、(a) どの保存方式でも 2 つの要件が同時に成り立たない場合と、(b) 承認済みの ADR か文書化済みの挙動を変えないと満たせない場合だけ欠陥として数えました。それ以外の先送りは指摘にしていません。

直す方向は、反例ごとの追記ではなく次の 4 つの構造の決定です。

- 役割の意味モデルを決める（宣言か、関係からの導出か）。
- 整合を「書く順序で防ぐ」のではなく、「extract と lint が版の不整合を検出する」形にする。
- 未抽出・移行の残件・同一性の保留を、1 つの「網羅性の状態」として問い合わせに注記する。
- 承認の単位を「対応の規則」と「記録ごとの判断」に分ける。

## 根拠

以下、maintenance を M、feature-experience を F、entity-granularity を G と略し、行番号はタスクの写しのものです。コードは読んで確かめただけで、実行はしていません。

### 重大 1: 「役割」が未定義で、中心例を検査も試行もできない

- **設計の依存**
  - M27 は「会社という同じ対象に役割を併記」とします。
  - M126〜132 の例は、顧客を型から役割へ移し、「『利用する』の主語の制約の更新」を適用します。
  - 一方、G22 は「どう併記するかは…オントロジー設計で決める」と先送りしています。
- **現行の実装**
  - ノードの型は 1 ページに 1 つです（`wiki_graph_extract.py` 502〜522 行の `derive_node_type` は文字列を 1 つ返す）。
  - 述語の制約は、その 1 つの型と `subject_types` の照合だけです（`wiki_graph_lint.py` 253 行）。
  - `wiki_graph_*.py`、`assets/ontology.yaml.template`、`assets/SCHEMA.md.template`、`graph-workflow.md` を `role|役割|deprecated|廃止|version` で検索して 0 件でした。役割、廃止予定、版のどれも構成物がありません。
- **なぜ保存方式の問題ではないか**
  - 役割を「実体への宣言」とするか「関係からの導出（製品を利用する会社＝顧客）」とするかで、「顧客は何社か」の答えが変わります。
  - M33 は解約を「利用関係の有効期間の変化」とします。宣言型なら、関係が失効したあとも役割が残り、役割と関係が食い違います。これは機能自身が新しい乖離の源を作ることになります。
  - 導出型なら、「顧客」は定義ではなく問い合わせになり、M132 の「主語の制約」は書けません。
  - 誰に対する顧客か、期間を持つかも未定です。
- **基準 (b) に当たる理由**: propose で利用者が承認する対象そのものであり、現行の構成物では表せません。

### 重大 2: 一体の適用と公開の境界が、ADR-0023 と読み手の仕組みで成り立たない

**書き手の側**

- ADR-0023 の変更の種類は `new`・`edit`・`ops` だけで、`ops` は索引とログ専用です（23 行）。
- 「ページの分割、統合、名前の変更、削除は、書く段の種類がないので残す」と明記されています（62 行。見直す条件は 70 行。計画書 `wiki-apply-2026-11-14.md` の 290 行と 785 行も同じ）。
- `edit` はファイル全体の一致が条件で、競合は「モデルが直す」です（23 行）。
- F205〜207 が認めている不足は、「`wiki_apply.py` が未実装」と「`ontology.yaml` の扱いが未記載」の 2 点だけです。

保存方式ごとにたどると、どちらも ADR の改訂が要ります。

| 保存方式 | 何が足りないか |
| --- | --- |
| 実体ページ方式 | 実体の統合と分離（M60）に、ページの削除か改名が要る。書く段に種類がない |
| 別の正本方式 | 全取り込みが同じファイルを直すので、`edit` の全体一致が並行の取り込みで毎回競合する。ADR-0023 が索引に `ops` を作った理由（35 行）と同じ状況になる |

加えて、競合を「モデルが直す」ことは、M110 の「適用中に LLM が…別の変更を追加したりしない」と衝突します。ADR-0023 は 15 回の却下を経た設計なので、「整合する実装設計で決める」（M115）ではなく、前提条件として表に出すべきです。

**読み手の側**

- M113 は「完了するまで新旧混在を公開しない」とします。
- しかし適用はページを 1 つずつ書き、`apply.lock` は書き手しか止めません。
- `extract_lock` が排他するのは extract どうしだけです（`wiki_graph_common.py` 165〜193 行）。
- 別セッションの問い合わせは、グラフが古ければ extract を走らせます（`graph-workflow.md` 161 行）。取り込みの手順 8b も走らせます（`ingest-workflow.md` 440 行）。どちらも適用の途中で、混在したグラフを生成物として公開できます。
- Markdown を直接読む問い合わせ、MCP の `get_page`、browse には関門がありません。
- ADR-0023 は、ツールを通らない書き手と複数 PC からの書き込みを保証の外に置いています（16 行、64 行）。別ブランチで旧定義のまま書かれた取り込みが git のマージで入る経路には、M112 の版の検査が届きません。直近の履歴にも取り込みの PR があります（#184）。

**直す方向**: 混在を書く順序で防ぐ約束をやめます。記録に定義の版を持たせ、extract と lint が版の不整合を決定的に検出して残件として報告する形にします。M72〜78 がすでに採った「部分移行は続く状態」と同じ構造に寄せられます。

### 重大 3: 採用後の遡及の記録がなく、網羅性が問い合わせに現れない

- **設計の記述**
  - 適用の単位は「語彙＋選んだ少数事例」です（F139）。
  - 会話例は「他の記事からの対象・関係の記録は未実施」で終わります（F175）。
  - 既存記事からの発見は propose、新規は ingest です（G63）。
  - 残りの既存記事を、採用した定義で記録する操作はどこにも書かれていません。M29 の「既存記録も見直す」は、記録済みのものだけが対象です。
- **実データ**（`wiki/graph/nodes.jsonl` と `edges.jsonl` を集計）

  | 項目 | 件数 |
  | --- | --- |
  | ノード | 108（source 77、concept 31、entity 0） |
  | 型付きエッジ | 10（すべて `cites`） |
  | `contradicts`・`supersedes` | 0 |

  この wiki の実体の層はゼロから始まります。移行の経路は実データで一度も試せません。
- **帰結**
  - 新しい型を足しても、旧記事は読み直されません。「古い記事だけ旧い概念のまま」という、利用者が憂慮する乖離の裏返しが、機能の正常な動作として生じます。
  - 未確定の扱いが 3 種類あり、問い合わせでの扱いが揃っていません。

    | 未確定の種類 | 問い合わせでの扱い |
    | --- | --- |
    | 移行の残件 | 件数つきで注記する（M74） |
    | 同一性の保留 | 混ぜないだけで、注記の規定がない（F186、G105） |
    | 未抽出 | status に出るだけ（F40） |

    「顧客は何社か」は、少数事例の数を黙って答えることになります。
- **直す方向**
  - 記事ごとに「どの版で抽出済みか」を持ちます。M40 の「分析済み記事の指紋」で、どのみち必要になる情報です。
  - 利用者の指示による遡及の記録を、同じ apply の経路に置きます。
  - 3 種類の未確定を、1 つの網羅性の注記の規則にまとめます。

### 中 1: 同じ識別子を狭めた意味で使い回すとき、印のない記録の既定がない

### 中 3: 乖離を測る基準が正本に求められていない

- 基準がなければ、見直しのたびに LLM がラベルだけから意味を推すことになります。

### 中 4: 承認の単位が「規則」と「記録ごとの判断」に分かれていない

  | --- | --- | --- |
