## 結論

判定は **却下（REJECTED）** です。重大 3 件、中 3 件、軽微 1 件を挙げます。

要件の方向は、作者の 2 つの要望に沿っています。1 つは実体を単位にすること、もう 1 つは利用者の指示で見直しと移行をすることです。ただし、次の 3 つの前提が成り立たないか、決まっていません。どれも「実装設計で決める」に送れる性質ではなく、この 3 文書で決め直す必要があります。

1. **【重大 1】共通の書く段（ADR-0023）は、この移行を運べない。** 文書は「ADR-0023 と整合させる」と書いています。しかし実際には、ADR-0023 にない機能を少なくとも 4 つ前提にしています。
   - ページの改名と削除
   - 読んだだけのファイルの変化の検出
   - 読み手から途中の状態を隠すこと
   - グラフの再生成を含む完了の境界

   これは整合ではありません。ADR-0023 は 15 回のレビューを経て承認されたもので、それを改訂することが前提条件になっています。
2. **【重大 2】識別子が「中身のハッシュ」なので、移行の要件と必ず衝突する。** エッジの ID には `status`、`valid_to`、`notes`、ページのパス、項目の順番が入ります。ノードの既定 ID には型が入ります。一方、文書は次の操作で「同一性と参照を保つ」ことを求めています。
   - 訂正
   - 取り下げ
   - 有効期間の変更
   - 再分類

   今の方式では、これらの操作をすると、保つべき記録の ID がその場で変わります。移行の後で検査する方式では、この衝突は解けません。ID を作った時点で固定する方式に変える必要があります。この決定は、段階 3（追加の適用）より前に要ります。
3. **【重大 3】「役割」が定義されていないのに、すべての例が役割に頼っている。** 今のオントロジーでは、1 つのノードに型が 1 つだけで、述語の制約も型でしか書けません。それなのに、会話例は「会社＋顧客という役割」を前提にしています。その結果、作者が挙げた単位の「顧客」が、型ではなく役割に降格されています。これで要件どおりの粒度になるのか、作者の判断が要ります。

構造の直し方として、次を推奨します。

- (a) 定義の版を「ステージングで組み立て、1 つのポインタで切り替える」形にし、ADR-0023 の拡張として先に設計する。
- (b) 実体とエッジに、作成時に固定する ID を持たせる。中身のハッシュは、旧データの互換用に限る。
- (c) 初期版の移行は「全件を移すか、保留するか」に限る。適用後も続く部分移行は外す（maintenance:45 にある「保留」の案を既定にする）。

(c) にすれば、中 1（部分移行の集計）の大半が消えます。

## 根拠

### 重大 1：書く段の前提不足（実装すれば確実に踏む）

ADR-0023 の書く段には、次の制約があります。

- 種類は `new`、`edit`、`ops` の 3 つだけです（ADR-0023:23、wiki-apply 設計:416、538-540）。ページの削除と改名は「書く段の種類がないので残す」とされています（ADR-0023:62、wiki-apply 設計:290、785）。
- `edit` はファイル全体のハッシュで比べます。同じページの別の箇所が並行して直されると、競合として扱われ、用意と承認をやり直すことになります（保証しないこと 3、wiki-apply 設計:887）。
- 計画に入るのは、書くファイルの `new`、`edit`、`base` だけです（wiki-apply 設計:559）。読んだ範囲では、書かずに前提として読んだファイルのハッシュを確かめる項目はありません。
- 置いてから戻すまでの間に、読み手が「後」を読むことは防ぎません（保証しないこと 10、wiki-apply 設計:894）。
- グラフの DB は、`wiki_graph_extract.py` が別のロック（`.extract.lock`）で書きます（wiki-apply 設計:292）。
- 書く段に移っていない書き手はロックを取りません（保証しないこと 2）。

これに対して、文書は次の要求をしています。

- ページの移動、関係の別の正本への移し替え（maintenance:114）。実体の統合と分離（maintenance:60）。これには改名と削除が要ります。
- 案が依存する定義、記録、記事、原本が変わったら、再検査すること（maintenance:108、experience:136）。ingest が使った定義の版が変わったら、書く前に検査し直すこと（maintenance:112、experience:209）。これには、読んだだけのファイルの変化を検出する仕組みが要ります。ingest の計画は `ontology.yaml` を書かないので、今の計画の形式では、版の変化に気づけません。
- 新旧が混ざった結果を、新しい定義の完了結果として公開しないこと（maintenance:113、experience:209）。グラフの再生成が別のロックで動き、読み手も隔離されていないので、ADR-0023 のままでは成り立ちません。

さらに、一度に数百ページを `edit` する移行の計画は、利用中の wiki ではほかの取り込みと競合しやすくなります。そのうえ、依存が変われば再確認を求める規則（maintenance:108-109）があるので、利用が活発な wiki では移行が収束しない恐れがあります。これは推測で、実データでは確かめていません。

experience:206 は「`ontology.yaml` の扱いが ADR に明記されていない」としか書いていません。上に挙げた 4 つの欠落には触れていません。

### 重大 2：中身のハッシュによる識別（確実に踏む）

コードでは次のようになっています。

- `edge_id()` は、主語、述語、目的語、出典、証拠、ページ、variant を SHA-256 にかけます（wiki_graph_extract.py:617-627）。
- variant には `VARIANT_FIELDS = ("confidence", "status", "valid_from", "valid_to", "notes", "raw_ref")` と、項目の番号が入ります（wiki_graph_extract.py:631、759-774）。
- ノード ID は、`graph.node_id` がなければ `<node_type>:<slug>` です（wiki_graph_extract.py:546-555）。
- 関係の項目に、明示的な ID の欄はありません。scripts を `rel.get("id")` で検索しても見つかりません。

このため、次のことが起きます。

- 取り下げや訂正で `status` を `superseded` にする操作（maintenance:57、68）と、解約で `valid_to` を入れる操作（maintenance:33）は、残すべき記録のエッジ ID を変えます。その記録を指す `contradicts` と `supersedes` は切れます。
- 型を改名すると、`graph.node_id` のないすべての実体の ID が変わります。主語のエッジの ID も、他ページの `object:` に書いた文字列も、すべて古くなります。
- 解決できない目的語は、extract では黙って文字列の目的語のエッジになります（wiki_graph_extract.py:682-683）。lint では警告されます。
- 同じ ID のページが 2 つあると、そこを指すエッジは作られません（wiki_graph_extract.py:746-750）。

maintenance:114 にあるエッジ ID の説明そのものは、コードと合っています。問題は、これを「検査の対象」として扱っていることです。原因は「同一性＝中身」という作りにあるので、検査では直りません。

作る順の問題もあります。experience:197 と maintenance:141 では、作る順が「追加の適用 → 移行」です。ID の方式を決めないまま段階 3 を出すと、型に依存する ID が増え続けます。その分、後の移行の負担が大きくなります。

### 重大 3：役割の定義がない（作者の判断が要る）

- 雛形の `ontology.yaml.template` にあるのは `node_types` と `predicates` だけで、役割の概念はありません。
- lint は、主語の型を `subject_types` だけで照らします（wiki_graph_lint.py:253）。
- ノードの型は 1 つだけです（wiki_graph_extract.py:577）。

一方で、例はすべて役割を前提にしています（maintenance:27、126-132、experience:169）。granularity:22 は、役割の決め方を「実際の資料に照らした設計で決める」として先送りしています。

maintenance:132 の「『利用する』の主語の制約の更新」は、型の制約しか書けない今の仕組みでは、主語を `company` に広げることになります。そうすると、販売代理店でしかない会社も「利用する」の主語として通ってしまい、顧客という役割による制約は書けません。

また、作者の要件は「『顧客』くらいの粒度」です。役割にした場合、「顧客の一覧」が型として引けなくなるかもしれません。それで要件を満たすのかは、作者が確かめる必要があります。

### 中 1：部分移行の件数を、機械が保証できない

maintenance:73-75 は、「確定 12 件、未分類 20 件、総数は未確定」のような集計を求めています。しかし `wiki_graph_query.py` のサブコマンドは `neighbors`、`edges`、`path`、`facts` だけで、集計はありません（wiki_graph_query.py:271-283、graph-workflow.md:156）。`/wiki:query` は LLM が文章で答えます。

さらに、記録ごとに「採用した定義の版」を持つ（maintenance:72）と、取り込み、lint、extract、query、閲覧、検索、MCP、rag のすべてが版を意識する必要があります。

結論 (c) の代わりに部分移行を残すなら、旧い型を `deprecated` のノード型として `ontology.yaml` に残す形が簡単です。そうすれば、型ごとの数え方という既存の仕組みに載せられます。

### 中 2：乖離を見つける手がかりがない

採用済みの語彙で表せない事実は、出典側に残すだけです（granularity:107）。ingest 時に見直しの候補を蓄える機能も、初期版から外しています（experience:188）。その結果、見直しの際は新旧の記事を読み直すしかありません（maintenance:39-42）。しかし、分析する量の上限は決まっていません（experience:220）。

大きな wiki では全体の見直しが終わらず、「整合している」と報告できないまま終わる可能性があります（maintenance:43）。作者が心配している「乖離」を安く見つける手がかりがないことになります。

語彙を自動で足すのではなく、ingest 時に「語彙外の記述あり」という印だけを残せば、maintenance:40 の「重点的に調べる」が実際に効くようになります。

### 中 3：機械が保証することと、手順の遵守に頼ることが区別されていない

次の「〜しない」は、どれも LLM の振る舞いです。

- 推測だけを乖離として表示しない（maintenance:35）
- 黙って落とさない（maintenance:74）
- 適用中に別の変更を足さない（maintenance:110、experience:135）

ADR-0023 は「人が実際に読んで決めたこと」を、保証しないことの 1 として分けています（wiki-apply 設計:885）。

このうち「適用中に足さない」は、`plan_sha256` で機械的に保証できます。それ以外は手順の遵守に頼るしかありません。文書でどちらなのかを書き分ける必要があります。

### 軽微 1：見積もりの規模が見えない

maintenance:142 は、実装設計で決める事項を 8 つ挙げています。これに ADR-0023 の改訂が加わります。それでも、どこまでを作れば作者の要望を満たしたと言えるのか、最小の範囲が示されていません。

### 過去のレビューとの重なり

上の指摘が過去のレビューと重なっていないかを確かめました。`docs/agent-runs/2026-11-19-wiki-ontology-maintenance/review-response.md` と、`-entity-granularity/review-response.md` を読んでいます。そこで扱われているのは、部分移行後の query、型の解決、会話例、訂正、パスと順番による ID の変化、再依頼、既存の ingest の説明、診断の指標です。書く段の欠落、ハッシュに入る欄と保持の要件の衝突、役割の定義、作る順は扱われていません。

## 検討した代替案

- **「実装設計で決める」に送って承認する。** 採りませんでした。重大 1 と 2 は、この文書が掲げる提供条件（新旧が混ざった結果を公開しない、同一性を保つ）が成り立つかどうかを決めます。後で決めると要件を書き直すことになります。
- **エッジ ID の説明（maintenance:114）を誤りとして指摘する。** 採りませんでした。コードと合っています。指摘すべきなのは説明ではなく、ID を中身から作るという作りです。
- **部分移行を残し、記録ごとに版を持たせる。** 採りませんでした。すべての読み手に影響が及びます。旧い型を `deprecated` のノード型として残す案か、保留を既定にする案のほうが簡単です。
- **ontology 専用の書き手を作り、ADR-0023 を迂回する。** 採りませんでした。experience:205 の方針（書き手を増やさない）に反します。ADR-0023 が解いた行の消失を、もう一度起こすことになります。
- **役割を「下位の型」にする。** 1 つの会社が顧客と販売代理店を兼ねる場合（maintenance:27）を表せません。役割を「期間付きの関係」として表すと、既存の `valid_from` と `valid_to`、出典、証拠をそのまま使えます。ただし重大 2 と絡むので、推奨は作者の判断を待つ形にとどめます。

## 前提と不確実性

- 実際の wiki の規模、移行の競合の頻度、移行が収束しないことは、実データで確かめていない推測です。
- wiki-apply 設計は、計画の形式の節（416、538-540、559）と「保証しないこと」だけを読みました。読んだ範囲には、書かずに読んだだけのファイルを確かめる項目がありませんでした。ほかの節に例外がある可能性は残ります。
- `wiki_apply.py` は未実装です（scripts を検索して確認しました）。ADR-0023 の実装と並行して拡張する余地があるかは、作者が決めることです。
- 作者が決めること:
  1. 「顧客」を型として残すか、役割にするか。
  2. 部分移行を初期版に入れるか。
  3. 固定 ID への切り替えと旧 ID の互換を、どこまで保つか。
  4. ADR-0023 を改訂するか。
- `git fetch` の結果は次のとおりです。origin/main は `1a66519` でローカルと同じです。wiki の最新タグは `v0.35.1` です。開いている PR は #187（ADR-0029 段階 3、Draft）と #143（ADR-0025 段階 2）です。対象の 3 文書は未追跡で、これらの PR と同じファイルには触れていないので、競合の恐れは低いと判断しました。ただし #187 が書く段や保護の周辺に触れるなら、重大 1 の前提が変わる可能性があります。中身は確かめていません。
