# レビューの目的

`docs/plans/wiki-apply-2026-11-14.md` は、`info-hive-wiki` の wiki のページ、索引、ログへの書き込みを、モデルの Edit と Write から、wiki ごとのロックを持つ Python のプロセス（`wiki_apply.py`）に移す設計の 12 版目である。実装はまだない。

1〜11 版目（`design-v1.md`〜`design-v11.md`）のうち 1〜10 版目は、あなたの 1〜10 回目のレビュー（`design-review-1.md`〜`design-review-10.md`。どれも `docs/agent-runs/2026-11-14-wiki-apply/` にある）で却下された。11 版目は 10 回目の指摘を直したもので、レビューを受けていない。12 版目は、11 版目に作者の判断（2026年11月15日）を入れたものである。設計書では、この設計のレビューを「N 回目」、セッションの取り込みの設計のレビューを「取り込みの N 回目」と呼び分けている。経緯は `summary.md` にある。

## 12 版目の主な変更（作者の判断による作り直し）

作者は「作者が決めること」の 1〜10 に答えた（設計書の「作者の判断（2026年11月15日）」の節と、「作者が決めること」の表の右の列）。設計に大きく効くのは判断 2 である。

- **ロックはプロジェクト（wiki）ごとに持つ。** ロックと日誌を `W/.wiki-cache/apply/` に置く。作業用のフォルダー `D` だけは、wiki と Git の外の `data_dir()/apply/work/` に残す。
- **ロックは、プロセスが落ちても残るファイルにする。** 持ち主の情報（`lock_id` など）を書いた一時ファイルを、重ねて書かない形で `apply.lock` に置いて取る。持ち主は開いたままにして OS のロックをかけ、これは `unlock` が持ち主の生死を知るための印に使う。持ち主は `lock_id` を確かめてから消して外す。
- **待ちは 3 分（`--wait 180`）。** 待ちきれなければ、計画の差分を `W/.wiki-cache/apply-pending/<plan_id>/` に置いて、終了コード 4 の誤りにする。差分が 5 件以上なら `pending_alert` を出し、モデルがユーザーに状態を確かめてもらう。
- **`unlock --wiki <W> [--lock-id <id>] [--force]` で明示して外す。** 持ち主が生きていなければ `--lock-id` で外せる。生きていれば `--force` のときだけ（POSIX のみ）。
- **外したもの。** ロックの場所が wiki のパスだけで決まるので、9〜11 版目の管理領域の印（AW）、印の不変条件と `adopt`（BA）、印の置き方（BB）、raw のルートを印に記録すること（BD）を外した。8〜10 回目の重大の多くは、この印の仕組みから出ていた。
- **戻したもの。** 管理領域が wiki の中に戻るので、`.wiki-cache` が Git で無視されることの確かめ、管理領域の段が wiki のページのディレクトリの別名でないことの確かめ（1 節の `Writer` の d）、管理領域を 1 段ずつ作ること（`bootstrap`）を戻した。
- 判断 5 で日誌を残す日数を 14 日に、判断 8 で `schema.md` の予約、判断 9 で走査が完全でなければ書かない、判断 10 で `unlock --force` を許す、と決まった。
- 1 節に「ロックが生む失敗の形」の表を、「保証しないこと」に 12（wiki の間の別名と `.wiki-cache` を消すこと）と 13（ロックを外す操作）を書いた。

## 確かめてほしい点

1. **ロックの作り（1 節と 6 節の 1）。** 残るロックのファイル、`lock_id` の確かめ、待ち、待ちきれなかったときの差分、`unlock` の 3 つの使い方から、書く段に加わる書き手だけで、2 つの書き手が並ぶ、成功を返した変更を失う、日誌を前に進めずに書く、差分を失う反例を探す。特に、取る・外す・`unlock` と、日誌を前に進めること（6 節の 2）の順番を見てほしい。
2. **「ロックが生む失敗の形」の表と、保証しないことの 12、13 が、失敗の形を尽くしているか。** 表にない失敗の形があれば挙げてほしい。
3. **外した仕組みの穴。** 印と `adopt` を外したことで、8〜10 回目に挙がった形の反例が、別の形で戻っていないか。日誌と管理領域が wiki ごとになったことで、1〜3 回目に挙がった形（管理領域の別名、Git の無視、初めて作るとき、入れ子の wiki）の反例が戻っていないか。
4. 1〜11 版目で入れた構造（`Writer` の a〜d、正規のパス、計画のハッシュと `plan_id`、入力を 1 回だけ読むこと、日誌と前に進めることと戻すこと、構造の確かめ、移す範囲の機械の検査）が、12 版目の作り直しのあとも成り立つか。
5. 「指摘との対照」の表の「生じない」が、本当に生じないか。
