## 作者の判断（2026年11月14日）

- 並行して取り込むときは、書く段だけをロックする。確認と記事を書く間は、ロックを持たない。
- 書く時間を短くするため、決まった処理はモデルを使わず、Python で行う。
- 書き込みは、差分のパッチを当てるか、Python で書くかを、場合によって使い分ける（両方を使ってもよい）。パッチが競合したら、モデルが直す。
- Claude Code のツールを通らない書き手（エディター、Codex、ほかのスクリプト）の変更は考えない。

## 解決したい問題

今の取り込み（Web ページ、PDF、セッション）と `/wiki:query`、`/wiki:learn` の保存は、モデルが Edit と Write で、要約ページ、関連ページ、`index.md`、`log.md` を書く。Edit は「読む、直す、書く」で原子的ではなく、2 つの書き込みが数ミリ秒の中で重なると、行が黙って消える（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md) の試験 4）。lint は、索引に足りない項目と、ログの抜けを見つけない。

## 4 回目のレビューで崩れた前提

| 指摘 | 崩れた前提 |
| --- | --- |
| 重大 1: 別の節の同じ文を「当て済み」の証拠にする | 今の中身を探せば、変更が当たったかどうかが分かる |
| 重大 2: ブロックの重複の判定が、足す先の節に結びついていない | ブロックがファイルのどこかにあれば、目的の追記は済んでいる |
| 重大 3: 同じファイルへの複数の変更を、それぞれ元の中身から作り、後の変更が先の変更を消す | 変更は互いに独立していて、1 つずつ当てればよい |
| 重大 4: `append` の足す先の見出しが、承認のハッシュに入っていない | 承認のハッシュの項目を列挙すれば、適用の意味がすべて縛られる |
| 重大 6: 作業用のフォルダーそのものがリンクだと、確認の前の記事が raw の側に保存される | 作業用のパスの字面が wiki の中なら、保存先も wiki の中である |
| 重大 7: ロックのファイルを変更の対象にでき、POSIX では自分のロックを壊せる | ロックのファイルは、適用の間ずっと同じ実体である |

重大 1〜3 は、どれも「済んだかどうかを、今の中身からあとで推す」作りから出た。これは、セッションの取り込みの 1〜3 版目の却下に共通した原因（状態をあとから推す）と同じ形である。この設計は、次の 3 つの構造で、推す箇所をなくす。

1. **済んだかどうかは、日誌だけで決める。** 書く前に、書くファイルごとの「前」と「後」のハッシュと、置く中身を、wiki 単位の日誌に書く。日誌のない状態で、今の中身から「当て済み」を推すことはしない。
2. **前に進めるだけで、推して当てない。** モデルが直したページは、ファイルの全体が用意したときの中身（前）と同じときだけ置き換える。違えば競合にして、モデルが直す。差分の塊を今の中身に合わせて当てる処理はない。
3. **よく重なるファイルには、決まった操作だけを使う。** 索引とログへの追記は、ロックの中で、今の中身に対して Python で計算する。足す先は、見出しの行と出現の順番で決め、計画に入れる。

## 前提にすること

- **Claude Code のツールを通らない書き手は考えない**（作者の判断の 4）。
- **書く段に移っていない書き手は、ロックに加わらない。** 移る順番（12 節）の途中では、モデルが Edit と Write で wiki を直接書く手順が残る。その書き込みと、書く段の書き込みが数ミリ秒の中で重なれば、今と同じく行が消えうる（「保証しないこと」の 2）。移っていない書き手が先に書いた変更は、書く段から見ると「用意したあとにほかが書き換えた」ことになり、モデルが直したページなら競合、決まった操作なら今の中身に足すので、どちらも黙って消さない。
- **raw は、この道具では書かない。** raw を書くのは、Web ページの `wiki_fetch.py` と `wiki_rawcheck.py`、セッションの `wiki_session.py write`、PDF の rag、経験の `wiki_evolve.py capture` である。この道具は、raw を書き換えないことを守る側にだけ立つ（7 節）。
- **wiki のファイルは UTF-8 である。** UTF-8 として読めないファイルは書かない（競合として返す）。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| raw の書き込み | raw の書き手は別にある。この道具は raw の側に書かないことを確かめるだけである |
| ページの削除と名前の変更 | 取り込みと保存の手順では使わない。lint の直しで要るなら、別に決める |
| 意味の重複の検出 | 同じ概念を別のスラッグで作ることは防がない |
| グラフの DB の書き込み | `wiki_graph_extract.py` が既存のロック（`.extract.lock`）で書く |
| ページの中身の正しさ | 書く段は、承認された中身をそのまま置く。中身の検査は、ページの frontmatter が読めること（9 節）だけである |
| 複数の PC から同時に書くこと | 同期のツール（OneDrive、Dropbox など）で共有した wiki では、ファイルのロックが PC をまたがない（「保証しないこと」の 6） |

## 決めること

### 1. 作業用のフォルダー（`begin`）

`wiki_apply.py begin --wiki <W> --raw-root <R> --name <名前>` は、`<W>/.wiki-cache/apply/work/<名前>-<乱数>/`（以下 `D`）を作り、そのパスを出す。`<名前>` は `wiki_fetch.check_slug()` で検査する。作る前と作ったあとに、次を確かめる。どれかが通らなければ、作らない（作ったあとなら消す）で、終了コード 1 にする。

1. wiki が初期化されていること（`wiki_initialized.require_or_exit()`）。
2. `<W>/.wiki-cache`、`<W>/.wiki-cache/apply`、`<W>/.wiki-cache/apply/work` が、どれもリンクでも再解析点（ジャンクションなど）でもない、ふつうのディレクトリであること（`os.lstat()` で、`S_ISLNK` と `FILE_ATTRIBUTE_REPARSE_POINT` を見る。`wiki_browse_fs._is_link()` と同じ判定）。なければ `os.mkdir()` で作り、作ったあとにもう一度確かめる。
3. 作った `D` の実体の祖先の並び（`wiki_browse_fs._existing_chain()`。実体は `st_dev` と `st_ino`）に、wiki のルートの実体があること。raw のディレクトリの実体（7 節の集まり）がないこと。
4. wiki のルートかその祖先に `.git`（ディレクトリかファイル）があれば、Git の作業ツリーの中とみなし、`git -C <W> check-ignore -q <D>` が成功し、`git -C <W> ls-files -- .wiki-cache/apply` が空であることを確かめる。`git` を実行できないときも止める。`.wiki-cache/.gitignore` がない古い wiki では、`init_wiki.py` と同じ中身（`assets/wiki-cache_gitignore.template`）で作ってから確かめる。

`D` の中身は次のとおりである。`plan.json` を書くのはスクリプトだけで、モデルが書くのは `new/` と `edit/` の下だけである。

```text
D/plan.json          計画（スクリプトだけが書く）
D/new/<相対パス>      新しいページの中身（モデルが Write で書く）
D/base/<相対パス>     直すページの、用意したときの中身（スクリプトが写す。モデルは触らない）
D/edit/<相対パス>     直すページの新しい中身（スクリプトが写し、モデルが Edit で直す）
D/rejected/<相対パス>.diff   競合で用意し直す前の差分（5 節）
```

### 2. 変更の種類と、使い分け

計画の項目は、wiki のファイル 1 つにつき 1 つである。同じファイルに 2 つの項目は作れない（3 節）。項目の種類は 3 つある。

| 種類 | 登録 | 前（用意したときに決める） | 後 | 当て方 |
| --- | --- | --- | --- | --- |
| `new`（新しいページ） | `new --path <P>` | 「ない」 | `D/new/<P>` のバイト列 | 行き先がないときだけ、重ねて書かない形で置く |
| `edit`（モデルが直すページ） | `edit --path <P>` | `D/base/<P>` のハッシュ | `D/edit/<P>` のバイト列 | 今のファイルの全体が「前」と同じときだけ置き換える |
| `ops`（決まった操作） | `index-add`、`log-entry`、`log-sub` | ロックの中で、今のファイルのハッシュ | 今の中身に操作を順に当てた結果 | ロックの中で計算して置き換える |

使い分けは次のとおりである。

| 書く場所 | 種類 | 理由 |
| --- | --- | --- |
| ソースの要約ページ、新しいエンティティとコンセプトのページ、シンセシス、経験のパターン | `new` | 中身の全体をモデルが書く |
| 既存のエンティティとコンセプトのページ（関連ページ）、`SCHEMA.md` のタグの体系 | `edit` | 場所も中身も決まっていないので、モデルが直し、差分を見せる |
| `index.md`、分割した索引（`indexes/<種類>.md`）への項目の追記 | `ops`（`index-add`） | 2 つの取り込みがほぼ同じ場所に足すので、パッチにすると毎回競合する |
| `log.md` の項目 | `ops`（`log-entry`） | 末尾に足すだけである |
| `log.md` のグラフのサブ行 | `ops`（`log-sub`） | 1 回目の適用が返した項目の識別に足す |

作者の判断の 3 の「パッチ」は、`edit` のことである。モデルは写しを Edit で直し、スクリプトは差分を見せ、当てるときは、ファイルの全体が用意したときと同じであることを確かめてから置き換える。差分の塊を今の中身に合わせて当てる（3 方向の当て方）ことはしない。そのため、同じページの別の箇所を 2 つの取り込みが並べて直すと、後の側は競合になり、用意し直しと承認のやり直しが要る。関連ページの直しは、取り込みごとに違うページに当たることが多いので、この費用を取る（「作者が決めること」の 1）。

`edit` の項目と `ops` の項目を、同じファイルに作ることはできない。`index.md` の中身をモデルが直したいとき（項目の要約の書き直しなど）は、`edit` だけにし、追記もその中で行う。

### 3. パスの規則と、同じファイルの判定

`--path` は wiki のルートからの相対パスで、`/` で区切る。次をすべて満たさなければ、登録を拒む（終了コード 1）。

- 各要素が空でなく、`.` と `..` でなく、`.` で始まらない（`.wiki-cache`、`.evolution`、`.git` を指せない）。
- 各要素が、空白か `.` で終わらず、`:`、`\`、制御文字、`<>"|?*` を含まず、Windows の予約名（`CON`、`NUL`、`COM1` など、拡張子つきを含む）でない。`~` のあとに数字が続く要素（8.3 の短い名前の形）を含まない。
- 文字列が NFC で正規化されている（NFD の入力は拒む。macOS の日本語のファイル名で、同じファイルを 2 つの字面で指さないため）。
- 最後の要素が `.md` で終わる。
- 最初の要素が、`raw`、`graph`、`assets` でない（`wiki_pages.SKIP_TOP_LEVEL_DIRS` のうち、ページを置かないディレクトリ。`indexes` は索引のために許す）。
- `SCHEMA.md` は `edit` だけで受け付ける。`log.md` は `ops` だけで受け付ける。

同じファイルの判定は、2 段で行う。

1. **字面。** 登録のとき、パスを `casefold()` したものを計画のキーにする。同じキーの項目がすでにあれば、`ops` どうしならその項目に操作を足し（3 節の下）、ほかは拒む。
2. **実体。** `diff` と `apply` は、行き先がすでにあるものについて、実体（`st_dev`、`st_ino`）を集め、2 つの項目が同じ実体を指せば拒む（大文字と小文字を区別しないファイルシステム、ハードリンク、短い名前を経由した別名をここで止める）。行き先がない `new` は、親のディレクトリの実体と、`casefold()` した名前の組で比べる。

**同じファイルへの複数の操作。** `ops` の項目は、操作の並び（登録した順）を持つ。当てるときは、今の中身に 1 つ目を当てた結果を 2 つ目の入力にする。索引のソースの節とコンセプトの節に 1 行ずつ足す取り込みは、`index.md` の項目 1 つに 2 つの操作を持つ。後の操作が先の操作を消すことはない（4 回目の重大 3）。

### 4. 決まった操作

どの操作も、ファイルを UTF-8 として読み（BOM があれば外して覚える）、改行で行に分け（CRLF の行が 1 つでもあれば CRLF のファイルとして覚える）、行の並びに操作を当て、覚えた改行と BOM で書き戻す。最後の行は改行で終える。足す行は、1 行で、改行と制御文字を含まないものに限る（登録のときに拒む）。

**見出しの行と節。** 見出しの行は、フェンス（` ``` ` か `~~~` で始まる行で開き、同じ記号で同じか長い並びで閉じる）の外にあり、1〜6 個の `#` と空白で始まる行である。見出しの行を比べるときは、行の末尾の空白を除いた字面で比べる。節は、見出しの行の次の行から、同じか上の段（`#` の数が同じか少ない）の次の見出しの行の前までである。節の「最後の行」は、節の中で空でない最後の行である。節の中に空でない行がなければ、見出しの行が最後の行である。

**`index-add --apply-dir D --file <索引のパス> [--section "<見出しの行>" [--nth <k>]] --line "<行>"`**

- `<索引のパス>` は、`index.md` か `indexes/` の下の `.md` である。
- `<行>` は `- [[` で始まる 1 行である。最初の wikilink の行き先（`[[x]]` か `[[x|表示]]` の `x`）を、項目の行き先とする。
- `--section` があれば、その見出しの行の `k` 番目（既定は 1）の出現の節の、最後の行のすぐあとに足す。見出しの行の出現が `k` に足りなければ、競合（`section_missing`）にする。出現が 2 つ以上あり、`--nth` を渡していなければ、競合（`section_ambiguous`）にする。`--section` がなければ、ファイルの空でない最後の行のすぐあとに足す。
- 節の中の空でない行が、テンプレートの置き換えの行（`assets/index.md.template` の 4 つの「（…と追加される）」の行。スクリプトの定数にする）だけなら、その行を消して、そこに足す。
- ファイルのどこかに、行き先が同じ項目の行（`- [[x]]` か `- [[x|` で始まる行）がすでにあれば、競合（`index_duplicate`）にする。これは「済み」の判定ではない。済んだかどうかは日誌で決め（6 節）、ここでは、同じページを 2 回索引に載せることを止めるだけである。

**`log-entry --apply-dir D --op <操作名> --title "<説明>" [--date YYYY-MM-DD] [--line "<サブ行>" …]`**

- 足すのは、`## [<日付>] <操作名> | <説明>` の見出しの行と、`--line` ごとに 3 文字の空白で字下げしたサブ行である。`<操作名>` は `log.md.template` の一覧（`ingest`、`query`、`lint`、`schema`、`shard`）と、`learn` などテンプレートにない値の英小文字（`[a-z]+`）に限る。`<日付>` は、登録のときの手元の日付を既定にし、計画に入る。
- ファイルの空でない最後の行のあとに、空の行を 1 つ挟んで足す。
- 当てたあと、足した見出しの行が、ファイルの中で同じ字面の見出しの行の何番目の出現か（`nth`）を数え、`apply` の結果に `log_entries`（`heading`、`nth`）として出す。日誌にも残す。

**`log-sub --apply-dir D --entry "<見出しの行>" --nth <k> --line "<サブ行>" …`**

- `<見出しの行>` の `k` 番目の出現の項目（見出しの行から、次の `## ` の見出しの行の前まで）の、空でない最後の行のすぐあとに、3 文字の空白で字下げしたサブ行を足す。
- 出現が `k` に足りなければ、競合（`entry_missing`）にする。ファイルの末尾にも、中身の検索にも頼らない。`k` は、1 回目の `apply` が出した `log_entries` の値を渡す（4 回目の重大 2）。
- 1 回目と 2 回目の間に、ほかの取り込みが同じ字面の見出しの行を前に差し込むことは、書く段に加わる書き手ではできない（`log-entry` は末尾にだけ足す）。移っていない書き手が差し込めば、`k` は別の項目を指しうる（「保証しないこと」の 2）。

**分割した索引の件数。** トップの `index.md` に分割したファイルごとの件数を書く今の規則（`scaling-playbook.md` の閾値 2 の手順 3）は、取り込みのたびに同じ行を直すので、`edit` にすると毎回競合する。件数を書かない規則に改めることを推す（「作者が決めること」の 3）。

### 5. 計画のハッシュと、差分の表示（`diff`）

`wiki_apply.py diff --apply-dir D [--json]` は、次を行う。ロックは持たない。

1. 1 節の 2〜3 の実体の検査を、`D` に対してやり直す。
2. 3 節のパスの規則と、同じファイルの実体の判定を行う。
3. 7 節の raw の検査を、すでにある行き先について行う（`apply` でもやり直す）。
4. `new` と `edit` の中身を UTF-8 として読めること、frontmatter が `wiki_text.parse_frontmatter_text()` で読めることを確かめる。`ops` の操作を、今の中身に当ててみて（書かない）、競合が出るかを見る。出たら、その理由を出す（`apply` のときの結果とは限らない）。
5. 差分を標準出力に出す。`new` は空からの統一差分、`edit` は `base` から `edit` への統一差分、`ops` は、ファイル、操作の種類、見出しの行と `nth`、足す行である。
6. `plan_sha256` を出す。

**`plan_sha256`** は、次の JSON を、キーを並べ替え、空白を入れず、UTF-8 で書いたバイト列の SHA-256 である。項目を列挙して選ばない。計画の全体と、計画が指すファイルの中身のハッシュを入れる。

```json
{
  "format": "wiki-apply-plan/1",
  "wiki": "<wiki のルートの絶対パス（/ 区切り）>",
  "raw_root": "<raw のルートの絶対パス（/ 区切り）>",
  "items": [
    {"path": "sources/x.md", "kind": "new", "after_sha256": "<D/new/x.md の SHA-256>"},
    {"path": "concepts/y.md", "kind": "edit", "before_sha256": "<D/base の SHA-256>", "after_sha256": "<D/edit の SHA-256>"},
    {"path": "index.md", "kind": "ops", "ops": [{"op": "index-add", "section": "## ソース", "nth": null, "line": "- [[x]]: …"}]}
  ]
}
```

`items` は `path` の順に並べ、`ops` は登録の順を保つ。`plan.json` そのものも、この JSON とほかの記録（作った時刻など）からなるが、ハッシュに入れるのは上の形だけである。操作の引数（見出しの行、`nth`、足す行、日付）はすべて `ops` の中にあるので、承認したあとに足す先を変えると `plan_sha256` が変わる（4 回目の重大 4）。

モデルは、差分と `plan_sha256` をユーザーに見せ、承認を得てから `apply` に渡す。承認のあとに `D/new` か `D/edit` を書き換えると、`apply` が `plan_sha256` の不一致で拒む。

### 6. 当てる（`apply`）と日誌

`wiki_apply.py apply --apply-dir D --raw-root <R> --expect-sha256 <plan_sha256> [--wait 60] [--keep] [--json]` は、1 つのプロセスで次を行う。

**ロックの前（wiki の今の状態によらない準備）。**

0. wiki が初期化されていることを確かめる。`D` の実体を確かめる（1 節の 2〜3）。`plan.json` と `D` の中身から `plan_sha256` を作り直し、`--expect-sha256` と一致しなければ、終了コード 1 にする。3 節のパスの規則を確かめる。7 節の raw のディレクトリの実体の集まりを作る。

**ロックの中。**

1. **ロックを取る。** `<W>/.wiki-cache/apply/apply.lock` を、リンクでないことを確かめてから開き（POSIX では `O_NOFOLLOW` を付ける）、`wiki_graph_common._try_lock()`（Windows は `msvcrt.locking`、POSIX は `fcntl.flock`）で取る。取れなければ 0.2 秒ごとに試し、`--wait` 秒（既定 60）で終了コード 4 にする。取れたら、開いたファイルの実体（`os.fstat()`）と、パスの今の実体（`os.lstat()`）が同じことを確かめる。違えば（取る間に置き換えられた）、閉じて取り直す。ロックのファイルは消さない（`wiki_graph_common.extract_lock` と同じ理由）。ロックのファイルは `.wiki-cache` の下にあり、3 節の規則で変更の対象にできない（4 回目の重大 7）。
2. **残った日誌を前に進める。** `<W>/.wiki-cache/apply/journal/` の、状態が `pending` の日誌を、作った順にすべて、下の「前に進める」に従って進める。1 つでも `stuck` になれば、何も書かずに終了コード 5 にする。
3. **この計画の日誌があるか。** `journal/<plan_sha256>/` があり、状態が `done` なら、何も書かずに、日誌に残した結果を出して終了コード 0 にする（`already_applied`）。2 で進めたものも、ここで `done` になっている。
4. **行き先を確かめる。** 項目ごとに、3 節の同じファイルの実体の判定と、7 節の raw の検査を行う。どちらかが通らなければ、何も書かずにロックを外し、終了コード 1 にする。行き先がリンクか再解析点なら、競合（`target_is_link`）にする。行き先のファイルのリンク数（`st_nlink`）が 2 以上なら、競合（`target_has_other_names`）にする。
5. **新しい中身を、すべてメモリの中で作る。**

| 種類 | 今の行き先 | 結果 |
| --- | --- | --- |
| `new` | ない | 「書く」。前は「ない」 |
| 同上 | ある | 競合（`exists`） |
| `edit` | 全体の SHA-256 が `before_sha256` と同じ | 「書く」 |
| 同上 | ない、または違う | 競合（`changed_since_prepared`） |
| `ops` | あり、UTF-8 として読め、操作がすべて当たる | 「書く」。前は今の SHA-256、後は計算した結果の SHA-256 |
| 同上 | ない、UTF-8 として読めない、または操作が競合 | 競合（4 節の理由） |

   1 つでも競合があれば、何も書かずにロックを外し、終了コード 3 で、競合した項目のパスと理由を出す。「済み」の判定はない。

6. **日誌を書く。** `journal/<plan_sha256>/` を作り、項目ごとに、置く中身を `after/<番号>` に書いて fsync する。最後に、`manifest.json`（状態 `pending`、作った時刻、`D` のパス、項目ごとの `path`、`kind`、`before_sha256`（`new` は `null`）、`after_sha256`、`after/<番号>`、`log_entries`）を一時ファイルに書いて fsync し、`os.replace` で置き、ディレクトリを fsync する（POSIX）。`manifest.json` のない日誌のディレクトリは、書いている途中で止まったものなので、2 で消す。
7. **書く。** 項目ごとに、行き先と同じディレクトリに一時ファイルを書いて fsync し、置く。`new` は重ねて書かない形で置く（POSIX は `os.link` のあとに一時ファイルを消す。Windows は `os.rename` で、行き先があれば `FileExistsError`）。`edit` と `ops` は `wiki_fetch.replace_with_retry()` で置き換える。親のディレクトリがなければ、`os.mkdir()` で作り、作ったあとに 7 節の raw の検査をやり直す。
8. **読み直す。** 書いたファイルを読み、SHA-256 が `after_sha256` と同じことを確かめる。違えば（置き換えの直後にほかが書いた）、日誌を `stuck` にして終了コード 5 にする。
9. **日誌を閉じる。** `manifest.json` の状態を `done` にして置き換え、ロックを外す。`--keep` がなければ `D` を消す。終了コード 0 で、項目ごとの結果（`written`）、`log_entries`、ロックを待った秒数、ロックを持った秒数を出す。

**前に進める（2 と、`recover`）。** `pending` の日誌の項目ごとに、行き先の今の SHA-256 を見る。

| 今の行き先 | すること |
| --- | --- |
| `after_sha256` と同じ | 何もしない（書けていた） |
| `before_sha256` と同じ（`new` は、ないこと） | `after/<番号>` を 7 と同じに置く |
| どちらでもない | 項目を `stuck` にする |

すべての項目が済めば、状態を `done` にする。`stuck` が 1 つでもあれば、状態を `stuck` にし、書いた項目と書けなかった項目を出す。

**なぜ「どちらでもない」が起きないか。** 日誌は、最初の置き換えより前に fsync してある。書く段に加わる書き手は、自分の計画を書く前に、残った日誌を必ず前に進める（2）。したがって、日誌の持ち主が 7 の途中で落ちたあと、次にロックを取った書き手は、誰であれ、まずその日誌を最後まで進めてから自分の計画を書く。ロックの持ち主が落ちてから、日誌が進められるまでの間に、書く段に加わる書き手が同じファイルを書くことはない。「どちらでもない」は、書く段に加わらない書き手（移っていない手順の Edit と Write、エディター）が、その間に同じファイルを書いたときにだけ起きる。そのときは、書き手の変更を消さないために、置かずに `stuck` にする（終了コード 5。「保証しないこと」の 2）。

**途中で止まったとき。**

- 6 より前に止まれば、何も書いていない。同じ `apply` をやり直せばよい。
- 6 の途中で止まれば、`manifest.json` がないので、日誌はないものとして消される。何も書いていない。
- 7 の途中で止まれば、次に誰かがロックを取ったときに、日誌が前に進められる。同じ `apply` をやり直すと、3 で `already_applied` になる。
- 9 の途中で止まれば、日誌は `pending` のままで、行き先はすべて `after_sha256` と同じなので、前に進めると何もせずに `done` になる。

`done` の日誌は、30 日を過ぎたら、ロックの中で 2 のときに消す（`--keep-journal-days`）。`D` は日誌が `done` になってから消すので、`already_applied` を返すのは、9 の途中で止まって `D` が残ったときである。`D` を消したあとに同じ `apply` を実行すると、0 で `D` がないので終了コード 1 になる。そのときは `list` で、その `plan_sha256` の日誌が `done` かを見る。

**`wiki_apply.py recover --wiki <W> [--show | --discard <plan_sha256>]`** は、ロックを取って、`stuck` の日誌を見せる。`--discard` は、その日誌を `journal/discarded/` に移す。`stuck` の項目の行き先は、モデルがユーザーと、`after/<番号>` と今の中身を見比べて直す（その直しは、新しい計画で行う）。

**ロックを持つ時間。** 1〜9 は、モデルを呼ばず、記録も読まず、ネットにもつながらない区間で、書くファイルの数と大きさの分だけで終わる。ふつうの取り込み（新しいページ 2〜5、直すページ 1〜5、索引とログ）で 1 秒より短い見込みである（実装で測り、結果に出す）。raw のディレクトリの走査（7 節）は、ロックの前の 0 で行う。

### 7. raw を書き換えないこと

`os.replace` と `os.rename` は、行き先のパスの最後の要素を置き換えるだけで、その要素がリンクでも、リンクの先のファイルの中身は変えない。ハードリンクの別の名前の中身も変えない。そのため、書く段が raw のファイルの中身を変えうるのは、**行き先の親のディレクトリが、別名（シンボリックリンク、ジャンクション、bind mount、UNC の共有など）を経由して、raw のディレクトリそのものになっているとき**だけである。この設計が確かめるのは、次の 1 点に限る。

> 書く直前に、行き先の親のディレクトリの実体と、その祖先の実体（`wiki_browse_fs._existing_chain()`。パスを `os.path.realpath()` で解いてから、各祖先の `st_dev` と `st_ino` を取る）が、raw のルートの下のどのディレクトリの実体とも一致しないこと。

- **raw のディレクトリの実体の集まり。** ロックの前（6 節の 0）に、`--raw-root` のディレクトリから、リンクと再解析点をたどらずに（`os.walk(..., followlinks=False)` と、再解析点の除外）、raw のルートと、その下のすべてのディレクトリの実体を集める。raw のルートがリンクか再解析点なら、たどった先も集める。ディレクトリの数は、Web ページの取り込みの画像のフォルダー（`assets/<スラッグ>/`）の数とほぼ同じで、数百から数千と見込む。`stat` を 1 回ずつ呼ぶだけなので、1 秒より短い見込みである（実装で測る）。
- **確かめる時。** `diff`（すでにある行き先）、`apply` の 4（全部の行き先）、`apply` の 7 で親のディレクトリを作ったあと。
- 6 回目のレビューの重大 1（`W/indexes` が raw の親を指すリンク）は、行き先 `W/indexes/raw/old.md` の親を `realpath` で解くと raw のルートになり、一致する。重大 2（bind mount）は、`W/indexes/raw` の実体が raw のルートの実体と同じなので、一致する。UNC の共有を経由した別名は、Windows の `os.stat` が返すボリュームのシリアル番号とファイルの ID が、ローカルのパスと同じになるかを確かめていない（「まだ確かめていないこと」）。
- `st_ino` が 0 のファイルシステムでは、`wiki_browse_fs.identity()` と同じく、大文字と小文字をそろえた実体のパスで比べる。この場合、bind mount と UNC の別名は見分けられない（「保証しないこと」の 4）。

**raw のルートの役割の検査。** `begin`、`diff`、`apply` は、raw のルートの実体が、次のどれとも重ならない（一方が他方の中にない）ことを確かめ、重なれば終了コード 1 にする。この検査は、raw の書き手（`wiki_fetch.py`、`wiki_session.py write`、`wiki_evolve.py capture`）からも呼べるように、共通の関数 `wiki_fsguard.raw_root_problem(wiki, raw_root)` にする（12 節の 1 で、raw の書き手にも入れる）。

- wiki のルート（ADR-0008 は wiki と raw を兄弟に置く）
- wiki のルートの `.wiki-cache`
- MCP の索引のディレクトリ（`wiki_mcp_common.data_dir()` の下の `index`）と、rag の派生データ（`data_dir()` の下の rag のディレクトリ）

これは、7 回目のレビューの重大 2（raw のルートに MCP の索引のディレクトリを指定できる）の、知られた置き場所を断る検査である。ほかの道具が中身を消すディレクトリをすべて知ることはできないので、そこから先は限界とする（「保証しないこと」の 5）。

**共通のモジュール。** 実体の検査（`identity()`、`_existing_chain()`、`_is_link()`）は、今は `wiki_browse_fs.py` にある。書く段と閲覧で同じ判定を使うため、`wiki_fsguard.py` に移し、`wiki_browse_fs.py` はそれを読み込む。

### 8. 競合したとき（`rebase`）

競合は、用意したあとに、ほかの取り込みか、書く段に加わらない書き手が、同じファイルを書き換えたときに起きる。決まった操作は今の中身に当てるので、索引とログで競合するのは、足す先の見出しがない、2 つある、同じページがすでに載っている、のどれかのときだけである。

- **`edit` の競合（`changed_since_prepared`）。** `wiki_apply.py rebase --apply-dir D --path <P>` は、`base` から `edit` への差分を `D/rejected/<P>.diff` に書き、今の行き先を `D/base/<P>` と `D/edit/<P>` に写し直す。モデルは、`rejected` の差分を読み、同じ意図の直しを、新しい `edit` の写しに Edit で入れ直す（作者の判断の 3「パッチが競合したら、モデルが直す」）。スクリプトが差分の塊を当て直すことはしない。
- **`new` の競合（`exists`）。** ほかの取り込みが同じ名前のページを作った。モデルは、そのページを読み、名前を変えるか、`edit` に切り替えて既存のページに足すかを、ユーザーと決める。`wiki_apply.py drop --apply-dir D --path <P>` で項目を外してから登録し直す。
- **`ops` の競合。** 理由に応じて、見出しの行、`--nth`、行を直して登録し直す（`drop` のあと `index-add`）。`index_duplicate` なら、その行を外すかをユーザーと決める。

どの場合も、直したら P3（`diff` と承認）からやり直す。`plan_sha256` が変わるので、前の承認は使えない。

### 9. スクリプト

`skills/info-hive/scripts/wiki_apply.py` と `wiki_fsguard.py` を足す。Python 3.12 以上で、標準ライブラリと、同梱のモジュール（`wiki_text`、`wiki_initialized`、`wiki_fetch.check_slug()` と `replace_with_retry()`、`wiki_graph_common._try_lock()`）だけを使う。ファイルの読み書きは、すべてバイト列で行い、UTF-8 を明示する。

```text
python wiki_apply.py begin     --wiki <W> --raw-root <R> --name <名前> [--json]
python wiki_apply.py new       --apply-dir <D> --path <P>
python wiki_apply.py edit      --apply-dir <D> --path <P>
python wiki_apply.py index-add --apply-dir <D> --file <索引のパス> [--section <見出しの行> [--nth <k>]] --line <行>
python wiki_apply.py log-entry --apply-dir <D> --op <操作名> --title <説明> [--date YYYY-MM-DD] [--line <サブ行> …]
python wiki_apply.py log-sub   --apply-dir <D> --entry <見出しの行> --nth <k> --line <サブ行> [--line …]
python wiki_apply.py drop      --apply-dir <D> --path <P>
python wiki_apply.py diff      --apply-dir <D> [--json]
python wiki_apply.py apply     --apply-dir <D> --raw-root <R> --expect-sha256 <plan_sha256> [--wait 60] [--keep] [--json]
python wiki_apply.py rebase    --apply-dir <D> --path <P>
python wiki_apply.py list      --wiki <W> [--json]
python wiki_apply.py recover   --wiki <W> [--show | --discard <plan_sha256>] [--json]
python wiki_apply.py abort     --apply-dir <D>
```

- `begin` 以外の `--apply-dir` を取るサブコマンドは、`D` が `<W>/.wiki-cache/apply/work/` の直下にあり、1 節の 2〜3 を満たすことを、毎回確かめる。`plan.json` に書いた wiki のルートから `W` を決める。
- `new` は、`D/new/<P>` の親のディレクトリを作り、計画に項目を足す。中身はモデルが書く。`edit` は、今の行き先を `D/base/<P>` と `D/edit/<P>` に写す。行き先がなければ拒む。
- `list` は、`work/` の作業用のフォルダー（名前、作った時刻、項目の数）と、日誌（`pending`、`stuck`、`done` の数）を出す。`abort` は、`D` を消す（途中の段がリンクでないことを確かめる。`wiki_rawcheck.remove_work_dir()` と同じ形）。

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功（`already_applied` を含む） |
| 1 | 引数かファイルの誤り（ハッシュの不一致、パスの規則、実体の検査、raw の検査、Git で無視されない作業用のフォルダー、初期化されていない wiki、排他作成ができないファイルシステムを含む） |
| 3 | 競合（何も書いていない） |
| 4 | ロックを取れない（何も書いていない） |
| 5 | 前に進められない日誌がある（`stuck`）。`recover` で見る |

- `diff --json` の出力のキー: `plan_sha256`、`items`（`path`、`kind`、`added_lines`、`removed_lines`、`ops`）、`probe_conflicts`（`path`、`reason`）、`diff`（統一差分の文字列）。
- `apply --json` の出力のキー: `state`（`applied`、`already_applied`、`conflict`、`busy`、`stuck`）、`results`（`path`、`kind`、`state`）、`conflicts`（`path`、`reason`）、`log_entries`（`heading`、`nth`）、`lock_wait_seconds`、`lock_held_seconds`。
- 競合の理由（`reason`）: `exists`、`changed_since_prepared`、`section_missing`、`section_ambiguous`、`entry_missing`、`index_duplicate`、`not_utf8`、`missing`、`target_is_link`、`target_has_other_names`。raw との重なりは競合ではなく、終了コード 1 の誤り（`raw_overlap`）にする。

### 10. 手順の書き換え

**`commands/ingest.md` の手順 6〜7（Web ページ、PDF、ふつうのファイル）。**

- **6.** `begin` で作業用のフォルダーを作る。要約ページを `new` で、新しいエンティティとコンセプトのページを `new` で、関連ページの直しを `edit` と写しの Edit で、索引の項目を `index-add` で、ログの項目（見出しの行と、更新したページのサブ行）を `log-entry` で用意する。モデルは、`D/new` と `D/edit` の下だけを Write と Edit で書き、wiki のファイルを直接書かない。`## 主張と行き先` の表は、要約ページの中に書く（手順 7b）。`diff` の差分と `plan_sha256` をユーザーに見せ、承認を得て、`apply` を実行する。終了コード 3 なら 8 節に従い、4 なら少し待ってやり直すかをユーザーに聞き、5 なら `recover --show` の結果をユーザーに伝える。
- **7.** 型付きのエッジは、6 の `new` と `edit` の中身（ページの frontmatter の `graph.relationships[]`）に入れる。グラフの lint と抽出は今のとおり行う。ログのグラフのサブ行は、Edit で書かず、もう 1 回の `begin`、`log-sub --entry <6 の log_entries の heading> --nth <同じく nth>`、`diff`、承認、`apply` で書く。

**セッションの取り込み（`wiki-session-ingest-2026-11-14.md` の S7〜S9）。**

- **S7** は、会話の中で用意する代わりに、`D` に用意する。用意する文は、確認を終えた raw から書いたもので、確認の前の会話の文ではない。`D` は Git で無視されることを確かめてある（1 節）。

- **S9** は `apply` にする。
- `scan` で見つかった文は、直すまで `D` の中に残る（Git で無視されたディスクの上である）。`abort` で消せる。

**`commands/query.md` の手順 8 と `commands/learn.md`。** シンセシスと経験のパターンのページを `new` で、関連ページを `edit` で、索引を `index-add` で、ログを `log-entry` で書く。

**`references/ingest-workflow.md`、`page-conventions.md`、`SKILL.md`、`scaling-playbook.md`。** 索引とログを書く箇所の文面を、上の操作に合わせる。インデックスを分割する作業（`shard`）は、索引の全体を書き直すので、`edit` で行う（取り込みと重なれば、どちらかが競合になる）。

## 保証しないこと

1. **人が実際に読んで決めたこと。** モデルが `diff` の差分をユーザーに見せずに `apply` を実行することは、機械では止められない。セッションの取り込みで `scan` を流さずに `apply` を実行することも同じである。手順の遵守に頼る。
2. **書く段に加わらない書き手との競合。** 移っていない手順のモデルの Edit と Write、エディター、ほかのスクリプトは、ロックを取らない。その書き込みが、`apply` の 5〜7 の間に同じファイルに入ると、どちらかの変更が消えうる。書く段は、用意したあとの変更を、`edit` なら競合として、`ops` なら今の中身に足して扱い、黙って消さないが、置き換えの瞬間に重なったものは見分けられない。`log-sub` の `nth` も、そうした書き手が前に同じ字面の見出しを差し込めば、別の項目を指しうる。日誌を前に進めるときの「どちらでもない」は、`stuck` にして止める。
3. **同じページの別の箇所への並行の直し。** ファイルの全体で比べるので、競合になり、用意し直しと承認のやり直しが要る。消えはしないが、手間がかかる。
4. **別名による raw の重なりを見分ける範囲。** 確かめるのは、書く直前に、行き先の親とその祖先の実体が、raw のディレクトリの実体と一致しないことだけである。`st_ino` が 0 のファイルシステムでは、パスで比べるので、bind mount と UNC の別名を見分けない。UNC の共有を経由した別名が、同じ実体として見えるかは確かめていない。検査のあとに別名を作り替えることは考えない（作者の判断の 4）。
5. **raw のルートの役割。** 知られた置き場所（wiki、`.wiki-cache`、MCP の索引、rag の派生データ）と重なることだけを断る。ほかの道具が中身を消すディレクトリに raw のルートを置くことは、見分けない。
6. **複数の PC からの同時の書き込み。** 同期のツールで共有した wiki では、ファイルのロックが PC をまたがない。ネットワークドライブの上のロックは、ファイルシステムの実装に頼る。
7. **意味の重複。** 同じ概念を別のスラッグで作ることは防がない。`index_duplicate` は、同じ行き先の項目を 2 回載せることだけを止める。
8. **作業用のフォルダーの文。** 用意した文は、`apply` か `abort` まで `.wiki-cache/apply/work/` に残る。Git で無視されることは確かめるが、バックアップや同期のツールが拾うことは防がない。
