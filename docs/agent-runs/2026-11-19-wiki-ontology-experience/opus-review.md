### [Major] グラフ層がない wiki（`graph/ontology.yaml` がない wiki）での動きが決まっていない

**対象**
- 本書の「対象の wiki を決める」の 46 行目
- 「記事が増えた後」の 125 行目
- 「4. 選んで適用する」の 96〜99 行目

**根拠**
- 本書の前提の確認は「`SCHEMA.md` のない場所には案を適用せず」（46 行目）だけです。
- 既存の規約では、グラフ層が有効かどうかは `ontology.yaml` があるかだけで決まります（`skills/info-hive/references/graph-workflow.md:9-12`）。ないときは「オントロジーのファイルをでっち上げてはならない」とし、`/wiki:upgrade` を勧めます。
- 初期化でも「グラフは後回しにする」などを選べます（`references/retrieval-setup.md:29`）。
- `ontology.yaml` ができると、取り込みの手順 8b（型付きの関係の追加、lint、毎回の extract）が必ず動くようになります（`references/ingest-workflow.md:434-442`）。

**問題**
`SCHEMA.md` はあるが `ontology.yaml` がない wiki に `propose` を実行すると、次の点が決まっていません。
- 125 行目の「現在の定義を出発点として差分を提案する」の出発点がありません。
- `apply` が `ontology.yaml` を新しく作るのか、`/wiki:upgrade` へ案内して止まるのかが分かりません。

作る実装になれば、利用者は「語彙を足した」つもりでいても、その後のすべての取り込みで extract とグラフの更新が必須に変わります。運用上の負担が、断りなく変わることになります。止める実装になれば、グラフを後回しにした利用者は入口で行き止まり、何をすればよいか分かりません。本書の想定の中心には「既存 wiki にも必要なときだけ使う」（17 行目）利用者がいます。その人たちに起きやすいのに、扱いが書かれていません。

**検証方法**
1. `graph-workflow.md:9-12` と `ingest-workflow.md:434-442` を読む。
2. 本書を `ontology.yaml` で検索し、ない場合の記述がないことを確かめる。
3. 対象の wiki を決める節の表（35〜41 行目）にも、この状態の行がないことを確かめる。

**修正の方向性**
対象の wiki を決める節に「`ontology.yaml` がない」状態を加え、次のどちらかに決めます。
- (a) 適用は upgrade の後に限る。
- (b) 提案の画面で「グラフ層を有効にし、以後の取り込みで extract が必須になる」ことを変更内容として明示し、承認を得る。

あわせて、提案の出発点を「既定のひな形」と「定義なし」のどちらにするかも決めます。

### [Major] 「語彙の追加」が既存ページの種類とノード ID を暗黙に変えうるのに、変更しない範囲として扱っている

**対象**
「4. 選んで適用する」の 96〜98 行目。「既存ページの型の付け替えは初期版の対象外」「定義のみ適用、既存記事の整理は未実施」とあります。

**根拠**
- ノードの種類は `node_types[*].maps_from` で、ページの `type`/`kind` から決まります（`graph-workflow.md:82`）。
- ノード ID の既定は `<node_type>:<slug>` です（同 `:74`）。
- 既存の規約に「`maps_from` を変えたときも、ノードの種類と ID が変わる」とあります（同 `:127`）。
- ひな形のノードの種類は、どれも `type`/`kind` から対応づけられています（`assets/ontology.yaml.template:12-44`）。

**問題**
「製品の版」を `kind: release` から対応づける種類として追加すると、すでに `kind: release` を持つページは、記事を 1 行も編集しなくても次のようになります。
- 種類と ID が `release:<slug>` に変わります。
- ほかのページの `graph.relationships[].object` に古い ID が書かれていれば、目的語のリンク切れになり、lint で一斉に指摘されます。

本書はこれを「追加」に含め、「定義のみ適用」なら既存の記事は変わらないと報告させます。実際には既存のノードが変わるので、完了の報告（104〜105 行目）が事実と食い違います。また、98 行目の「語彙だけを適用する」選択肢は、試行とは別の組み合わせです。そのため、この影響を試行で確かめないまま適用されるおそれもあります。

**検証方法**
1. `graph-workflow.md:74, 82, 127` を照らし合わせる。
2. 一時の複製の wiki で、既存の `kind` に当たる `maps_from` をひな形に加える。
3. `wiki_graph_extract.py` を実行し、前後の `nodes.jsonl` の ID を比べる。

**修正の方向性**
次の 3 点を本書に入れます。
- 「追加」の定義を、既存のノードの種類・ID を変えない追加に限る。
- ノードの種類と ID が変わる既存のページを、提案の画面の「変更するファイルと範囲」（68 行目）に件数とともに示す。
- 語彙だけを適用する場合も、その影響を含めた最終の組み合わせで再び試行してから適用する。

**修正の方向性**
