## 崩れる前提

- **R1 の選定は、2 人の採点者の判断が分かれた 1 件の裁定で決まっている。**
  - haiku-medium の R1 の意味の割合は 0.95 ちょうどで、閾値 `0.95 * 1.0` と等しいので通ります。この組を外しているのは、A010（`r1-schema__haiku-medium__1`）の引用誤り 1 件だけです。
  - A010 の誤りは、ページの題を `[[...]]` のリンクに書いたことです。絶対パスは正しく、そのページは開かれています。
  - Opus はこれを「推測」と注記して指摘し、Sol は指摘していません。裁定者は `resolve_link` が `None` を返すことで誤りと確定しました。`link-resolution-check.json` と一致するので、裁定自体は規則どおりで誤りではありません。
  - A010 の `citation_errors` を空にして `finalize` をメモリの中で再実行すると、R1 は `haiku-medium`（平均 0.0024 ドル）に替わります。今の sonnet-low（0.0389 ドル）の約 1/16 です。R1 を 1 問ずつ 2 回だけ測った結果では、モデルの間の差というより、表記の 1 件と閾値の等号が R1 を決めています。
- **R3 の effort の選択は、その 1 問の 2 回に頼っている。** sonnet-low（意味 1.0、0.0502 ドル）を外しているのは、A132 と A102 の根拠のない主張です。ページの 38 行目「PDFium の抽出が pdftotext、pdfminer、MarkItDown より読み順と表で良い」と、回答の「pdfminer と PDFium の品質の直接比較など、答えにない」が矛盾しています。この裁定は正しいと確かめました。ただ、R3 で low より medium を選ぶ根拠は、この 1 問の 2 回だけです。sonnet-medium は 31/32 の 0.96875 です。もう 1 件 omitted が付けば 0.9375 に下がり、R3 は条件を満たす組がなくなります。A009 を supported にしても選定は変わらないことは確かめました。
- **裁定者は伏せられていない。** `semantic-adjudications.json` の `adjudicator` は「Codex main」で、対応表を作り、以前の製品の値を決めた実装者自身です。選定に効いた争いはどれも厳しい側の判断で決まりました。
  - A010：Opus 側
  - A132：Sol 側
  - A022 と A035：Opus 側。R2 の sonnet-medium を外したが、費用はほぼ同じで選定は変わらない

  一方で A145（haiku-low）と A146（opus-high）は寛容な側で裁定しています。モデル名で偏ったという証拠は見つかりませんでした（推測の域を出ない）。
- **Sol が採点したことの証拠は、自己申告の記録だけ。** `semantic-grading-sol-app.json` は main が書いた要約です（`agent: /root/semantic_second_judge`）。モデルの ID を観測できる生の記録はありません。ハッシュが結んでいるのはファイルの同一性で、採点者が誰かではありません。
- **エフォートが渡ることに頼っている。** 製品のエージェントの既定は `effort: low` です（`agents/wiki-reader.md`）。R3 の medium は、メインが Agent ツールに `effort` を渡すことで初めて効きます。文書にある古い CLI（2.1.292 より前で、`model` だけを渡す場合）や、メインが `effort` を省いた場合、R3 は sonnet/low で動きます。これは誤りで外した組です。

## 見落としと軽微な問題

- **【軽微】採点者が 2 人いることの検査は、決して失敗しない。** `reconcile_reader_grades.py:66` は `judge_models` を `["claude-opus-5-5", "gpt-6.1-sol"]` の定数で書きます。`finalize` の `len(set(provenance["judge_models"])) < 2` の検査（`grade_reader_models.py:105`）は、この出力に対しては失敗しようがありません。「複数採点者の来歴を拒む」と言えるのは、`files` に 2 つ以上あるかの検査までです。
- **【軽微】`verify-product` が見るのは `TIERS` だけ。** `ProductDecisionTests` はエージェントの既定と prompt-context.md の表も確かめますが、CHANGELOG と、prompt-context.md の本文にある数値（97.5% など）は確かめません。どちらも手で一致させてあり、今は合っています。
- **【軽微】伏せた写しでも inline の回答を見分けられる。** 前回の指摘のとおり、inline の 2 件は見出しの形で判別できます。R0 は選定に使わない（`selected=null`）ので、影響はありません。
- **【軽微】A145 と A146 は選定に効かない。** A145 は haiku-low の R1 で、意味の割合 0.9 なのでもともと対象外です。A146 は opus-high の R2 で、最安ではありません。

## 崩せなかった点

- `finalize` は次の場合をすべて拒みます。
  - 13 問の写しがそろっていない
  - 問いと命題が固定した入力と違う
  - 写しの回答や開いたページが元の記録と違う
  - 本文が凍結した wiki と違う
  - 採点が欠けている
  - CLI の版が混ざっている
  - 組がそろっていない
- 裁定が要るもの（判断の違いとすべての指摘）は、すべて理由付きで裁定されていて、余分な裁定もありません。
- R2 の選定（sonnet-low）は、どの争いをどちらに裁定しても変わりません。haiku の 2 組は意味の割合で閾値を下回っています。
- R0 は選ばない（`selected=null`、`main-inherit`）という方針が、製品の段の表と一致しています。
