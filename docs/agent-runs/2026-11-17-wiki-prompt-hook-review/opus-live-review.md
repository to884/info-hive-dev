## 判定

**条件付きで採用可**（確信度: 中）。フックの選別と表示の骨格は崩せませんでした。ただし採点と選定の条件に重大な欠陥が 4 つあり、このまま再採点して表を確定すると、根拠を誤った表になります。4 つは次のとおりです。

- 正直な「開いていない」の申告を未読の引用として数える
- 入力から事実の字句が写る
- 採点のコードが測定の条件のハッシュに含まれる
- 形式の失敗を再測できない

フックにも、表示しなかった候補を既出に記録する経路が残っています。

## 致命的・重大な欠陥

### 1. 【重大】根拠の節で「開いていない」と申告したリンクを、未読の引用として数える

- **主張:** `score()` は「根拠」の節の行にある `[[...]]` を、文脈を見ずにすべて引用として数えます。そのため、出典を開いていないと正直に書いたモデルが `unopened` で失格します。
- **実測（v2 の記録を読み取りで採点した結果）:** R0 で未読の引用が出たのは次の 5 件です。
  - `r0-memory__haiku-low__2`
  - `r0-memory__haiku-medium__2`
  - `r0-memory__opus-inline__1`
  - `r0-memory__sonnet-low__1`、`__2`

  `haiku-low__2` の該当行は「出典は [[components-of-agent-memory]]（2026-11-06 の記事）とされているが、そのページは開いていない。」です。`opus-inline__1` の該当行は「元は [[managed-agents-cma-dreaming-with-a-dynamic-workflow]]」です。どちらも根拠にした引用ではありません。
- **結果:** 選定の条件 `cell["unopened"] == 0` によって、R0 では 7 組のうち 4 組が字句の段階で外れます。外れた組には、境目の基準になる opus-inline も含まれます。意味の読み合わせは対象に残った組しか見ないので、この誤りはあとで直りません。
- **根拠:**
  - `tests/wiki/measure_reader_models.py:269-291`：行の中の役割を区別していない
  - `info-hive-wiki/agents/wiki-reader.md:27`：開いていないページを根拠にしない、と求めるだけで、触れることは禁じていない

### 2. 【重大】採点のコードと CLI の版が測定の条件に含まれ、採点だけを直すと既存の記録を集計できない

- **主張:** `cmd_summary()` は `prepare()` を呼び、`spec` をその場で作り直します（`:350-351`、`:63-69`）。`spec` に入る値は次のとおりです。
  - `harness_sha256`：`measure_reader_models.py` 全体のハッシュ。`score()` と `page_keys()` を含む
  - `data_sha256`：fixture のハッシュ
  - `cli_version`：`claude --version` を毎回実行して得る
- **確かめた事実:** 今の `measure_reader_models.py` のハッシュは `experiment.json` の `harness_sha256` と一致しました。凍結した写しの `measurement-source.py` とも一致しました。
- **結果:**
  - 既知の `page_keys` の不具合をこのファイルで直した時点で、summary も `--retry-failed` での再開も「測定の条件が変わった。別の --out を使う」で止まります。
  - Claude Code が自動更新されて版が 2.1.325 から変わっただけでも同じように止まります。
  - これを避けるために `experiment.json` の `spec` を手で書き換えると、来歴の保証そのものが壊れます。
- **今の構造で来歴を保つために必要な条件:** 測定の入力の指紋（prompt、agent、snapshot、argv）と、採点器の版を分けて記録することです。`summary.json` には `fingerprint` しか記録されていません。どの採点器で数えたかは残らないので、旧採点と新採点の summary を見分けられません。

### 3. 【重大】入力に含まれる字句を正解の事実にしているため、49 件のうち 4 件が必ず一致する

- **主張:** `answer = norm(section(result, "答え", "根拠"))` で照らしますが、根拠の行には読む段がパスを書き写します（`wiki-reader.md:38`）。問いやパスにある字句が、そのまま事実の一致になります。
- **該当する事実（v2 の記録での一致率）:**

  | 問い | 事実 | 写る元 | 一致率 |
  | --- | --- | --- | --- |
  | `r1-powershell` | `-First` | 問いの文 | 8/8 |
  | `r1-pdfheader` | `0.5.1` | 候補のパス `…判定の修正-rag-0.5.1.md` | 9/9。うち 1 件は根拠の節のパスだけで一致 |
  | `r1-rag051` | `0.11.1` | 候補のパス `…-wiki-0.11.1.md` | 10/10 |

- **結果:** どの組もこの 4 件の床を持つので、正しさの差が縮みます。r1-powershell では 3 件のうち 1 件が無条件に一致します。そのため「最良の 95% 以上」に弱い組が入りやすくなります。
- **根拠:**

### 4. 【重大】形式の失敗は再測できず、その種類の推奨が永久に `incomplete` になる

- **主張:** `--retry-failed` が再測するのは `exit != 0` か `is_error` の回だけです（`:188`）。次の失敗は `exit == 0` のまま `ok=False` になります。
  - `## 答え` の見出しがない、または見出しが「## 回答」のように違う
  - `model_usage` に別のモデルが混ざる
  - `duration_ms` がない

  一方、推奨の条件は全組について `fail == 0` です（`:397-399`）。1 回の形式の失敗で、その種類の推奨は `incomplete` のまま止まり、測定の欠けと区別できません。避けるには記録を消すか動かすしかなく、来歴が壊れます。
- **もう一つの問題:** 形式を守れないことはモデルの品質の差です。それなのに、品質の悪い組を外す扱いではなく、その種類の測定全体を止める扱いになっています。
- **現状:** v2 の 126 件では `ok=False` は 0 件でした。まだ起きていない潜在の欠陥です。

### 5. 【重大】既出を記録したあとで期限切れになると、表示しなかった候補が 40 ターン出なくなる

- **子プロセスの中の経路:** `build_context()` は `save_state()`（`wiki_prompt_context.py:864`）のあとで `check_deadline()`（`:865`）を呼びます。ここで `TimeoutError` になると `None` を返しますが、`state["shown"]` はすでに保存されています。
- **親と子の期限のずれ:** 子の期限は子自身の `started`（`wiki_prompt_hook.py:26,41-42`）から 2.5 秒です。親の期限は親の起動時刻からの 2.5 秒です（`:52,81-89`）。子の期限は、Python の起動の遅れの分だけ親より後ろにずれます。子がこの間に保存を終えると、出力は親が捨てます（タイムアウトで止めるか、`:89` の経過時間の判定で捨てる）。
- **結果:** 候補は表示されないのに既出として記録され、40 ターン抑えられます。目的の「表示した候補だけで既出記録を決める」に反します。大きい wiki で走査が 2.5 秒に近づくほど起きやすくなります。

### 6. 【重大】読む段に任せた回答の確信度が、query-confidence.md で決まらない

- **主張:** R1 と R2 では、メインは自分でページを開きません（フックの読み方の行と SKILL.md:107）。しかし `query-confidence.md` の見つけ方の決め方は、すべて「そのページを初めて開いたとき」と道具を呼んだ順で決めます（`:91-97`）。サブエージェントが開いたページについては定めがありません。
- **確かめた事実:** `wiki-reader` とサブエージェントの語は、`query-confidence.md` に一度も出てきません（grep で確かめた）。
- **結果:** メインが読む段の報告だけで答えたとき、どの表で判断するかが決まりません。候補は次の 3 つです。
  - 「検索の抜粋だけを見て、ファイルを読んでいない」（低）
  - 理由 0F（中）
  - インデックスから見つけた（上限なし）

  どれを選ぶかでラベルが揺れます。
- **もう一つの食い違い:** HEADER の「根拠にする前にページを開いて読む」（`wiki_prompt_context.py:647`）と、読み方の行の「自分で開かずに」（`:661`）が逆のことを言っています。

### 7. 【重大】R0 の費用の比較が、実際の R0 と R1 の分かれ目を測っていない

- **実測（記録の値）:**
  - inline は新しい opus のセッションで、費用の中央値は 0.126 ドル（0.099〜0.153）
  - haiku-low の中央値は 0.0019 ドル
- **何が測れていないか:** 実際の R0 は、キャッシュ済みの長い文脈にページを足すときの追加の費用です。実際の R1 と R2 は、サブエージェントの費用に、メインが依頼を書く出力と報告を読む入力の費用を足したものです。どちらも測っていません。
- **結果:** 「条件を満たす組のうち最安のもの」という規則では、R0 にも読む段が選ばれる方向に偏ります。これは「1 ページならメインが読む」という段の表（`wiki_prompt_context.py:536`）の前提と矛盾し、表の R0 は測定で裏付けられません。
- **残りの差:** 測定の経路は MCP なしの Read で、`--agent` を本体として動かします。実際の経路は Agent ツールと `get_page` です。この差は docstring に書いてありますが、モデル表を実際の経路に当てはめる根拠はありません。

## 崩れる前提

- **1 問 2 回で順位を決めてよい。** R0 は 1 問 4 件の事実を 2 回測るだけです。1 回で 1 件落とすと平均は 0.875 になり、95% の基準を下回ります。R1 でも、10 回のうち 2 回、事実を 1 件ずつ落とせば外れます。ばらつきで選ばれる、と見るべきです。
- **page_keys の既知の不具合は 1 問だけに効く。** 実際には `r1-pdfheader` の 9 件のほかに、`r1-rag051` でも 1 件が曖昧になっています（リンクでたどった同名のページ）。直すときに、問いの候補のスコープだけで照らすようにすると、別の wiki のページを引いた回は `invalid` になり、`ambiguous` ではなくなります。
- **報告の形で、wiki の区別が付く。** `wiki-reader.md:38` の形は `[[スラッグ]]（パス）` で、パスは相対です。同名のページがあると、測定でも本番でも、メインはどちらの wiki のページかを見分けられません。曖昧になる原因は採点器だけでなく、エージェントの仕様にもあります。
- **fixture の候補は、フックが出すものと同じである。** 確かめた結果、12 問はフックの出す候補の集合と一致しました。一致しなかったのは `r2-two-wikis` です。

## 崩せなかった点

- 読み取りの成功の判定は崩せませんでした。Read の `tool_result` が成功したものだけを数え、Glob、wiki の外のファイル、別のスコープの同名ページは数えません。
- 同じ回の重複や計画にない回は summary で止まり、欠けた問いを重複の記録で埋められません。
- 利用上限に当たると、バッチは新しい回を入れずに止まります。
- 候補の選別は、表示できた集合で段を決めます（`render`）。
- 所在は JSON で、省略せずに渡しています。
- 測定の回の `INFO_HIVE_PROMPT_CONTEXT=0` で、フックの候補は混ざりません。

`✶ Insight ─────────────────────────────────────`
- 「字句が一致したら合格」という採点は、問いや候補のパスにある語を正解に選ぶと、答えをなぞるだけで点が入ります。正解の事実を選ぶときは、入力に現れない語に限る必要があります。
- 測定の入力の指紋と採点器の版を同じハッシュに入れると、採点を直すたびに実測が使えなくなります。「何を測ったか」と「どう数えたか」は、別々に記録しておくと来歴を保てます。
- 別プロセスに期限を掛けるときは、子に時刻を渡さず子の起動から数え直すと、ずれが生まれます。そのずれの間に副作用（ここでは既出の記録）が確定するのが問題の本体です。
