## 判定

**採用可。確信度：中。** 確認できた作業ツリーの変更では、境界値の誤りや、`EXTRACT_REVISION` 据え置きによるキャッシュ混同は崩せなかった。wiki 側の案内には食い違いが残る。指定された `change.diff` は権限エラーで読めず、PDFium を使う試験も再実行できていない。

## 致命的・重大な欠陥

なし。

## 崩れる前提

- **「ヘッダー判定を通れば PDFium でも開ける」**
  
  これは成立しない。例えば `b" " * 1024 + b"%PDF-"` は今回の判定を通るが、PDF 本体を欠く。今回一致しているのはヘッダー開始位置の上限であり、PDF 全体の受理条件ではない。さらに PDFium の探索対象は４バイトの `%PDF` で、今回の `%PDF-` とは厳密には異なる。ただし、この厳しさは旧実装にもあった。[PDFium の実装](https://raw.githubusercontent.com/chromium/pdfium/main/core/fpdfapi/parser/fpdf_parser_utility.cpp)

- **「更新すると、旧版で失敗したジョブも自動再開する」**
  
  成立しない。旧版でヘッダー拒否されたジョブは `failed` のまま残り、`recover()` と `claim()` の対象にならない。明示的な再試行または再登録が必要。ただし、再試行は可能で、再登録も失敗済みジョブを再利用しないため、行き止まりではない。根拠：`rag_jobs.py:69`、`:116`、`:160`、`:206`。

## 見落としと軽微な問題

1. **軽微：wiki の取り込み手順が新しい受理条件と矛盾する。**
   
   `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:18` は、依然として「先頭が `%PDF-` の通常のファイルだけを受け付け」と説明している。入力が `b"\n%PDF-1.5..."` の場合、rag は受理する一方、取り込みを担当するエージェントへの案内では対象外になる。実際に登録を省くかはエージェント次第だが、記述の食い違いは確認できた。

2. **軽微：追加試験は、1024 バイト境界での PDFium との一致を検証していない。**
   
   `tests/rag/test_jobs.py:255` の境界試験は `read_pdf()` までで終了する。PDFium に渡して抽出する試験は、前置きが改行１バイトの場合だけ（`:242`）。したがって、PDFium 側の境界が変わっても、追加２件が通る可能性がある。現時点の境界不一致を示す指摘ではなく、回帰検出の穴である。

3. **軽微：CHANGELOG の入力例が Markdown 上で正確に伝わらない。**
   
   `info-hive-rag/CHANGELOG.md:13` のコードスパンには、文字列 `\n` ではなく実際の改行が入っている。Markdown のコードスパンでは改行が空白に正規化されるため、表示上は改行１バイトの反例を表せない。

## 検証した事実

- **境界：一致。** 対象の関数を取り出し、ファイル入出力をメモリ上で置換して実行した。オフセット 0、1、1019、1020、1023、1024 は受理され、1025 は拒否された。返すバイト列も変化しなかった。PDFium の公開ソースも `offset <= 1024` まで探索する。ここでいう 1024 はゼロ起点のオフセット。
- **登録・MCP：判定の重複なし。** `Jobs.register()` は `Config.pdf_path()` によるパス・属性確認だけを行う。`rag_server.py:125` は登録処理へ委譲し、別のヘッダー条件を持たない。
- **抽出の版：据え置きの論理に反例なし。** `rag_index.py:495` の読み込み・判定後に SHA-256 を計算し、抽出キャッシュを選び、抽出を行う。旧判定で拒否されたバイト列が、この通常経路で抽出結果を残すことはない。前置きを足した PDF は、前置きのない PDF と別の `doc_id` になる。
- **追加試験の退行検出：確認できた範囲では成立。** 境界試験の既存メソッドをメモリ上のファイルで実行すると現実装では通り、判定だけを旧 `startswith()` に戻すと受理側３ケースがエラーになった。改行１バイトの試験も、コード上は旧判定で抽出前に失敗する。ただし、この試験全体は未実行。
- **バージョン・文書：** `plugin.json` は `0.5.1`。既存入力への処理を変えない受理条件の修正として、パッチ版とする判断は崩せなかった。README と ADR-0013 は変更後の条件を記載している。
- **確認できず：** 指定された `change.diff`、実データ２件の抽出、67 件の試験結果。環境に `pypdfium2`、`filelock`、`numpy`、`lancedb` などがなく、作者側の結果を独立には再現していない。

## 崩せなかった点

- `find(..., 0, 1024 + 5)` による開始位置の上限。
- `EXTRACT_REVISION` を上げずに既存の抽出結果・索引を維持する判断。
- 失敗済みジョブを再試行・再登録した際に、旧ヘッダー判定が台帳から復活する可能性。
- 0.3.0 の旧保存領域が今回のキャッシュへ混入する可能性。旧領域は開かない実装だった。
