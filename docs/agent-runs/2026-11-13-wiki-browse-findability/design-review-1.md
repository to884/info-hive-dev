試作のコードをメモリ上で動かし、IME の変換確定中の Enter でもページへ移動すること、NFD の題名では強調箇所がずれることを再現しました。ファイルは変更していません。ブラウザを使う試験は実行環境がないため、未検証として明記します。
## 判定

**却下。確信度：高。** 通常の入力で作者が決めた見出し検索を満たせず、索引の木にも所属先を一意に決められない箇所があります。試作には、日本語入力と複数グループへの所属で、設計の約束を破る動作があります。

## 致命的・重大な欠陥

致命的な欠陥は確認していません。重大な欠陥は次の4件です。

1. **重大・設計：H1 にしかない語を検索できない。**

   5.1 は検索用の見出しを h2〜h6 に限定しています。しかし、frontmatter の題名と H1 が同じであるという制約はありません。

   反例は、題名が「運用手順」、タグが「運用」、要約が「日常の操作を扱う。」、本文が次のページです。ほかの必須メタデータは通常どおり付けます。

   ```markdown
   # 起動失敗

   一般的な操作の説明。
   ```

   「起動失敗」は実在する見出しですが、設計どおりに検索データを作ると、照合する4欄のどこにも入りません。検索結果は0件になります。

   現行パーサーと `assign_heading_ids()` を実際に呼び、H1 の ID が存在し、設計の抽出条件では見出しが空になることを確認しました。作者の決定「題名、要約、タグ、見出しの部分一致」に対する、失敗も競合もない反例です。

   根拠：[設計の作者決定と検索対象](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/docs/plans/wiki-browse-findability-2026-11-13.md:219)、`wiki_lint.py` の検査には題名と H1 の一致を要求する規則がありません。

2. **重大・設計：最初の H1 を省いた後、`index.md` の直下の項目をどこへ所属させるか決まらない。**

   次の索引で成立します。

   ```markdown
   # 索引
   - [[a]]

   ## 分類
   - [[b]]
   ```

   N1 では `a` はファイルのグループに入ります。一方、N3 では `index.md` の包みをなくし、「最初の見出しより前」の項目だけを「索引」グループに入れます。`a` は最初の見出しより**後**なので、この条件に入りません。

   「省いた H1 を最初の見出しとして数えない」「ファイル直下の項目だけは別グループとして残す」などの補足を置かなければ、`a` の所属、件数、`data-groups` を決められません。これは見た目の好みではなく、設計だけで実装するという条件を満たさない欠落です。

   試作も規則の裏付けになりません。試作は最初だけでなく**すべての H1** を無視します。次の入力をメモリ上で処理すると、`a` と `b` の両方が「旧節」に入りました。

   ```markdown
   # 表題
   ## 旧節
   - [[a]]
   # 別章
   - [[b]]
   ```

   根拠：[設計 N1・N3](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/docs/plans/wiki-browse-findability-2026-11-13.md:58)、[試作の H1 処理](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/poc/browse-findability/proto.py:129)。

3. **重大・試作：IME の変換確定で、意図せずページへ移動する。**

   検索結果がある状態で、日本語入力中の Enter を押すと、変換確定用のイベントでも最初の結果へ移動します。ハンドラーは `e.key === "Enter"` だけを見ており、変換中かどうかを見ません。

   試作の実際のハンドラーに、`{key: "Enter", isComposing: true, keyCode: 229}` を渡すと、`location.href` が結果の URL に変わることを Node 上で確認しました。Escape も同様に、変換中であっても検索欄を空にします。

   日本語の検索語を確定する通常操作で発生します。設計10の移植時に追加すると明記されている機能にも、この扱いはありません。

   根拠：[試作のキーハンドラー](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/poc/browse-findability/assets/proto.js:103)、設計5.3・10の5。

4. **重大・試作：同じページが複数グループに載っていても、最初の所属先しか開かない。**

   `a` をグループ `_g1` と `_g2` の両方に載せ、記事 `a` を開きます。設計3.1は両方のグループを開く約束ですが、`pathTo()` は最初の一致で戻ります。その返り値だけから `openIds` を作っています。

   根拠：[設計の全所属先を開く規則](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/docs/plans/wiki-browse-findability-2026-11-13.md:106)、[試作の経路探索](C:/Works/info-hive-dev/.claude/worktrees/wiki-browse-findability/poc/browse-findability/assets/proto.js:131)。

## 崩れる前提

- **H1 は題名と重なる。** 題名と異なる H1、または複数の H1 があるページで崩れます。「重なることが多い」は、検索対象から除く根拠になりません。
- **H1 を消しても項目の所属は自明である。** `index.md` の最初の H1 と次の見出しの間に項目があると、N1 と N3 の接続が不足します。
- **Enter は結果を開く指示である。** 日本語 IME の変換確定でも届きます。
- **現在のページへの経路は1本である。** 同じページの複数掲載は、設計自身が許しています。
- **正規化後の文字位置を原文へそのまま使える。** NFD の結合文字や、小文字化で文字数が変わる文字で崩れます。
- **同じ Core から作れば、ブラウザ上でも ID の対応が保たれる。** HTML と `nav.js` の取得間に再生成が入れば別世代になります。通知は対応関係を復元しません。ただし、世代違いと ID の変動は明記された限界なので、これ自体を重大には数えていません。

## 見落としと軽微な問題

- **軽微：正規化した題名の強調位置が誤る。**
