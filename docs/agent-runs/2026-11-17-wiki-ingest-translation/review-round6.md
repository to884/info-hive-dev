## 判定

**条件付きで採用可**（確信度: 中）。R5 の重大1の反例（区切りが「。」「！」「？」「;」「\n」のもの）は塞がっていました。ただし、和文の学術文で句点に使う全角ピリオド「．」で区切ると、同じ反例が CLI を通り `completed: true`・`warnings: []` で完了します。「句点での混在を拒否する」という説明と、文書に書いた限界のどちらにも当てはまらない見逃しです。

## 致命的・重大な欠陥

### 1. 【重大】全角ピリオド「．」で区切った中国語の文が検出されず、`done` の条件を満たして完了する

- **主張**: 文の区切りの正規表現 `[。！？!?;；\n]+|\.(?=\s|$)` は、NFKC で「．」(U+FF0E) を「.」に変えたあとに適用されます。そのため「．」の直後に空白がなければ文が分かれません。和文の学術文や技術文は「，．」を句読点に使うので、これは句点です。小数点を除外する目的に対して、除外の範囲が広すぎます。
- **再現手順**: 親の試験ハーネス `TranslationReviewContractTest` を一時ディレクトリで継承して実行しました。リポジトリには書き込んでいません。
  - 原文: `This article explains search. The system retrieves documents using existing links.`
  - raw: `この記事では検索についての詳しい説明をしていきますので、ぜひ最後まで読んでください．系统使用现有链接检索文档．`
  - `--finish --accept-warnings` の結果: 終了コード 0。`completed: true`、`errors: []`、`warnings: []`、`pending_reviews: 0`、`work_dir_removed: true` でした。
  - 区切りを「。」にした同じ入力は `translation_review_required` で拒否されます（対照として確認）。
- **根拠**:
  - `info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の `translation_text`（NFKC で正規化する）と `translation_block` の `out_units = re.split(r"[。！？!?;；\n]+|\.(?=\s|$)", out)`。
  - 段落全体のかなの比率は 35% 以上なので、比率の条件でも拾われません。
  - 原文が英語なので、漢字の類似の照合（`original` が 8 字以上）も働きません。
- **文書との食い違い**: `web-raw.md:17` と計画の 19 行目は「小数点は文の区切りにしない」と書いています。実装は、空白が続かないピリオドをすべて区切りにしていません。計画の 39 行目の限界の例は「日本語の助詞を混ぜた同一文」だけで、助詞を含まない独立した中国語の文は、記載した限界の外にあります。
- **試験の漏れ**: `test_foreign_han_sentence_is_not_diluted_by_other_japanese_sentences` の区切りは `("。", "！", "？", ";", "\n")` だけで、「．」と半角の「.」（空白なし）が抜けています。

## 崩れる前提

- **「和文の句点は『。』である」**: 学術文の「，．」や、英文式の `.` を空白なしで続ける混在文では崩れます。上の反例で実証しました。
- **「文の境界は、句点・感嘆符・疑問符・セミコロン・改行のどれかで表れる」**: 次の区切りでは崩れます。同じ入力で区切りだけを変え、CLI で確かめました。いずれも完了扱いになります。
  - 「：」: `…ください：系统使用现有链接检索文档。` は `completed: true`、`warnings: []`。
  - 「…」: 同様に `completed: true`。
  - 「，」「、」「——」「」」「）→」「|」、全角空白、「・」: 関数単位で候補が 0 件でした。
  - これらは「同一文内」と言い張れなくはありません。ただし文書の限界は「日本語の助詞を混ぜた形」に限って例示しており、助詞のない中国語の文が丸ごと残る場合は例示の外です。
- **「中国語の文にはかなが含まれない」**: `系统使用ソフト现有链接检索文档。` のように、カタカナの製品名などを 1 語含むだけで、その文は候補から外れます（関数単位で候補 0 件）。推測ではなく確かめた結果ですが、実際の記事でどれだけ起きるかは確かめていません。
- **「`has_japanese_letters` は候補と同じ範囲を見ている」**: 実際はブロック全体の `out_text` で判定します。日本語の文と中国語の文が混ざる段落では、中国語の候補にも常に真が付き、`japanese_text` などの種類でも形式上は通ります。文書は「確認者が読む」と明記しており、意図した制約の範囲内です（重大ではない）。

## 見落としと軽微な問題

- **【軽微】ピリオドの条件の範囲**: `\.(?=\s|$)` は小数点だけでなく、`e.g.検索` や `v1.2.系统` のような空白のないピリオドもすべて区切りから外します。文書の「小数点」という説明より広く、欠陥1の原因でもあります。
- **【軽微】文の候補の限界の書き方**: `web-raw.md` の追記「かなの比率によって検出しない」は、文単位の新しい規則（かなが 1 字でもあれば外れる）が原因の見逃しを表していません。実際の原因は比率ではなく「かなの有無」で、計画の 39 行目も同じ書き方です。
- **【軽微】改行を含む `text`**: `review_id` は改行を空白にした `src_text` と `out_text` から作り、`text` は改行を残した `inline_text(..., newline="\n")` から作ります。照合は一貫していて壊れません。ただし確認者は JSON に `\n` を含む全文をそのまま写す必要があります。既存の 2 件の試験（623 行目と 747 行目）は、この変更に合わせて期待値を書き換えています。

## 崩せなかった点

- 「。」「！」「？」「;」「；」「\n」で区切った段落内の、かなを含まない漢字の文は、ほかの日本語の文に薄められずに候補になります。`--accept-warnings` でも解除できません。
- 「〇」だけでは、`has_japanese_letters` を真にできません。
- `done` の条件、一括受理の禁止、`pending_reviews` による未完了の判定は、今回の差分で緩んでいません。`apply_translation_review` に変更はありません。
- 漢字の多い見出しや表のセルが頻繁に候補になる点は、文書が通常の経路として明記しており、記載と動作が一致しています。処理の負担は残る限界ですが、記載の範囲内です。

`✶ Insight ─────────────────────────────────────`
- NFKC は全角の「！？；．」を半角に変えます。そのため、正規化のあとの文字クラスで「小数点を除く」条件を書くと、全角ピリオドの句点まで巻き込みます。区切りは正規化の前の文字で判定するか、`\d\.\d` だけを除く形にしないと、和文の「，．」の書き方と衝突します。
- 文単位の「かなを含まない」という条件は二値なので、カタカナの語が 1 つ入るだけで外れます。比率の条件より、文字 1 つで結果が変わりやすい作りです。
