## 判定

**条件付きで採用可**（確信度：中）

前回の重大な指摘のうち、(2) の done の受理条件は文書と監査の両方で塞がっています。(1) は、ブロック全体が中国語の場合は塞がりました。しかし、比率をブロック単位で測るため、日本語の段落に混ざった中国語の文は警告なしで完了します。また、ほぼすべての日本語の見出しが確認の対象になるため、委譲先の `done` の経路は実際にはほとんど通りません。

## 致命的・重大な欠陥

### 1. 重大：日本語の段落に混ざった中国語の文が、確認なしで完了する
- **主張**：35% の比率はブロック全体で 1 回だけ計算しています（`wiki_rawcheck.py` の `translation_block`、`if han and kana / (kana + han) < 0.35`）。かなが多い日本語の文が同じブロックにあると、中国語の文の分が薄まり、検出から漏れます。
  - 後段の文字列の分割は、かな・漢字以外の文字だけを数えます。漢字だけの文は対象外です。
  - 漢字の照合は、原文に漢字が 8 字以上ある単位だけを照らします。原文が英語ならこの照合は動きません。
- **反例**（`translation_block` を直接呼んで確かめた）：
  - 原文 `This article explains search. The system retrieves documents using existing links.`、訳 `この記事では検索について説明します。系统使用现有链接检索文档。` → 比率 0.38、結果 `(True, [])`。確認の対象は 0 件です。
  - 原文 `The engine searches links.`、訳 `引擎は搜索链接します。`（簡体字の語に日本語の助詞を付けたもの）→ 比率 0.40、`(True, [])`。
- **根拠**：計画の 41 行目は、漏れる場合として「検出の閾値より短い語を日本語で区切った形など」だけを挙げています。上の 1 例目は、漢字 12 字の完全な中国語の文です。前回の (1)「英語から中国語への誤変換」と同じ種類の欠陥が、ブロック内に混ざった形で残っています。この限界は文書にもありません。

### 2. 重大：正しい日本語の見出しや表のセルのほとんどが確認の対象になり、委譲先の `done` がほぼ通らない
- **主張**：日本語の見出し、表のセル、短いリストの項目は、かなの割合が 35% 未満になるのがふつうです。これらはすべて `translation_review_required` になります。委譲先は `japanese_text` の記録を作ると `reviewed_passages > 0` になり、`done` を返せません（`web-raw.md` 71 行目、`agents/web-raw.md` 30 行目、`verified_agent_completion`）。その結果、見出しのある記事はほぼすべて `warnings` の経路に進みます。
- **反例**：`検索拡張生成の概要` は比率 0.11 で対象になります（実測）。`概要` は 0.0 です。試験の正例でも `題名`、`項目 1`、`項目 2`、`(未取得)` に確認の記録を足す必要があり（patch の `check_japanese` の追加）、ふつうの正例が素通りできなくなったことの裏付けです。
- **崩れる結果**：
  - 「対象ごとに具体的な理由」を求め、汎用の理由による一括受理を禁じています（`web-raw.md` 43 行目）。一方で、数十件の見出しへの理由はどれも「日本語に訳した見出し」になり、事実上の一括受理になります。
  - 親の確認件数が記事ごとに数十件になります。その中に `系统概述` のような中国語の見出しが `japanese_text` として紛れても、気づけないおそれがあります。欠陥 1 と合わせると、検出の信号が雑音に埋もれる構造です。

## 崩れる前提

- **ブロック単位の文字比率で、ブロック内の言語を代表できる**：段落の中で日本語と中国語が混ざると崩れます（欠陥 1）。
- **確認の対象は少数の例外にとどまる**：漢字の多い日本語の見出しや表がある記事では崩れます（欠陥 2）。その場合、`done` の受理条件の強化は「委譲先が `done` を返す場面がほぼなくなる」ことで守られている状態になります。
- **`has_japanese_letters` が「日本語の説明を添えた」ことの証拠になる**：漢字を 1 字でも含めば真になります（`any(script_counts(...))`）。今回の新しい対象は漢字のブロックなので、中国語だけのブロックでもこの条件は常に満たされます。`japanese_text`、`quotation`、`term` のどれでも形式上は通ります。意味を保証しないことは明記されていますが、この判定は今回の対象に対して何も止めていません。
- **Codex の自己確認**：誤訳したモデル自身が `japanese_text` と書けば完了します。これは文書で明記済みで、仕様どおりです。

## 見落としと軽微な問題

- **軽微**：`is_han` は `〇` を漢字に数えます。そのため `〇` に英文を続けたブロックでも `has_japanese_letters` が真になり、`quotation` の保持が通ります（コードを読んで確かめた。実行はしていない）。中黒と長音符を除いた修正と同じ種類の抜け道で、試験は `・` と `ー` しか見ていません。漢字を 1 字足しても同じことができるので、実際の影響は小さいです。
- **軽微**：同じ反例で、`〇` だけのブロックは比率 0 で対象になります。数字の代わりに使う `〇` が、確認の対象を増やします。
- **軽微**：監査は、main が最後に写しを消した回の `decisions` が、委譲先が報告した警告に由来するかを照らしません。main が自分で確認の記録を作って完了させても通ります。ただし `prepare` のログと順序を監査しないことは明記されており、その範囲内です。

## 崩せなかった点

- 委譲先が確認済みの保持を自分で受理して `done` を返す経路です。`completed: true` には `--accept-warnings` が必要で、`agent_accepted` で違反になります。`--accept-warnings` を付けなくても、`verified_agent_completion` で落ちます。
- 確認の受領の偽造です。`review_id` の重複、型の不正、`kind` の不正、`decisions` と警告の ID の不一致は、すべて不合格になりました（`verified_completion` の ID 集合の照合）。
- ブロック全体が中国語の場合です。短文、言い換え、英語から中国語への誤変換、仮名を含む原文の照合のどれも、`translation_review_required` になりました（新しい試験と実測）。
