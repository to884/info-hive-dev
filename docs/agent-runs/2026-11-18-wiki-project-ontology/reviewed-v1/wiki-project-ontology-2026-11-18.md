# info-hive の記事から設計したプロジェクト用オントロジー

作成・更新: 2026-11-18（Asia/Tokyo）。状態: 提案。対象: このプロジェクトの `wiki/` のスナップショット。
正本はこの設計書、機械用の完全な候補は [YAML](wiki-project-ontology-2026-11-18.yaml)、検査記録は [verification.json](../agent-runs/2026-11-18-wiki-project-ontology/verification.json) に置く。
実 wiki のオントロジー、記事、グラフは変更していない。

## 1. 設計の結論

この wiki には「何を作り、なぜ選び、どの版で直し、どこまで確かめたか」を追えるオントロジーが合う。
製品や人物の一般的な関係よりも、構成要素・変更・問題・判断・評価・出荷のつながりを優先する。
既存の `product`、`concept`、`source`、`decision` を使い、`component`、`release`、`change`、`issue`、`evaluation` の 5 種類を追加する。
11 述語を追加し、既存の `depends_on` の主語・目的語に `component` を加える。
完全版は 17 種類・26 述語になるが、既存の 12 種類・15 述語はすべて残す。

記事と、記事が述べる対象を分ける。
たとえば [[pdfのヘッダーの判定の修正-rag-0.5.1]] は出典のまま残し、rag 0.5.1、PDF の拒否、受け付け条件の変更、直接抽出の評価を別々の対象として記述する。
1 ページを複数のノードにする変更は、現行の「主語はそのページのノード」という契約を変えるため採らない（[[グラフの抽出の契約]]）。

```text
リリース ──release_of──→ 製品 ←──part_of── 構成要素
    │                                      ↑      ↑
 delivers                               changes  affects
    ↓                                      │      │
   変更 ─────────fixes───────────────────→ 問題
    │
 implements
    ↓
 設計判断 ──motivated_by──→ 評価 ──evaluates──→ 変更・構成要素・製品・版・判断
    │
 selects
    ↓
 製品・方式                     概念 ──applies_to──→ 製品・構成要素

各ページ ──sourced_from──→ 出典記事 ──summarizes_raw──→ 原本のパス
各型付きの関係は別途 source と evidence を持つ。
```

## 3. 答えたい問い

| ID | 問い | 探索する関係 | 答えを出す条件 |
| --- | --- | --- | --- |
| Q1 | rag 0.5.1 は、どの問題をどんな変更で直したか | `release → delivers → change → fixes → issue` | 修正の対象条件を出典で確認する |
| Q2 | その変更を、どの条件・経路まで確かめたか | `evaluation → evaluates → change` を逆に引く | 評価の本文で版・方法・限界を読む |
| Q3 | Web raw の段に Sonnet を選んだ理由は何か | `decision → selects → product` と `motivated_by → evaluation` | 比較対象・回数・対象工程を確認する |
| Q4 | ADR-0027 の判断を実装し、出した版は何か | `change → implements → decision` と `release → delivers → change` | 判断は ADR 内の具体的な選択を指す |
| Q5 | browse・query・取り込みの問題と変更を探したい | `issue → affects → component ← changes ← change` | 構成要素は責務の単位でそろえる |
| Q6 | 過去の教訓や手順が、どの機能に当てはまるか | `concept → applies_to → component/product` | 適用条件を本文・notes に残す |
| Q7 | どの構成要素が、どの製品・外部道具に依存するか | `part_of`、`depends_on` | 過去の版の依存を現在の全版に広げない |
| Q8 | どの判断は承認だけで、実装・出荷をまだ記録していないか | 判断から `implements` と `delivers` の逆参照を確認 | 「記録なし」とだけ答える。未実装の断定には本文が必要 |

上の経路は探索の形であり、現行の CLI がこの連鎖を 1 回で意味的に検索できるという約束ではない。
現行の `neighbors` と `edges --predicate` を組み合わせれば、記録した関係を段階的に引ける。
一般の `path` は暗黙のエッジや古い関係も通るため、最短経路をそのまま Q1〜Q8 の根拠にしない。

## 4. ノードの種類と境界

| 種類 | 定義と配置 | 分けるもの | 識別子の例 |
| --- | --- | --- | --- |
| `product`（既存） | プラグイン、外部道具、モデル。`entities/` | 製品と出荷版。比較したモデルの版は必要なら製品の別 ID にする | `product:info-hive-wiki`、`product:claude-sonnet-5-5` |
| `component`（追加） | 製品内で責務を持つ構成要素。`entities/` | `browse` や Web raw の段と、個々のファイル・画面ラベル | `component:wiki-web-raw` |
| `release`（追加） | 製品と版を特定した出荷の単位。`entities/` | リリースの報告書、main の先頭、実際の導入 | `release:rag-0.5.1` |
| `change`（追加） | 範囲を特定した変更。コード・文書・設定・プロンプトを含む。`entities/` | 問題、判断、評価、出荷。実施と提案は本文で明記する | `change:rag-pdf-prefix-1024` |
| `issue`（追加） | 条件と期待との差を観測した問題。`entities/` | 原因の仮説や一般的な教訓。GitHub issue がなくても作れる | `issue:rag-pdf-prefix-rejected` |
| `decision`（既存） | 何を選び、なぜ選んだかという具体的な判断。`concepts/` | ADR 文書全体、未採用の案、実装の完了 | `decision:adr-0027-captions` |
| `evaluation`（追加） | 対象・版・方法・結果・限界を持つ評価の実施。`entities/` | 試験コード、予定、成功の保証。比較・レビュー・手動確認も含む | `evaluation:rag-051-pdf-direct` |
| `concept`（既存） | 再利用する概念・方式・手順・条件付きの教訓。`concepts/` | 特定の版の障害そのもの | 既存の `concept:ingestに使うモデル` を維持 |
| `source`（既存） | 原本を要約した根拠の記事。`sources/` | その記事が報告する製品・出来事・判断 | 既存 ID を維持 |

`synthesis` は既存の統合ページとして残す。
`person`、`company`、`paper` なども、今後外部記事を取り込む用途のため残す。
`claim` は原子的な主張と矛盾を管理する必要が生じた段階で使い、この段階では全文章を claim に変換しない。
`raw` の種類も残すが、現行の `summarizes_raw` の目的語はパスの文字列であり、raw ノードに変わるわけではない。

新しい 5 種類はすべて `explicit_only: true` とする。
記事タイトルやタグから型を自動で付けず、`graph.node_type` で明示する。
トップレベルの `type` は現行の `entity` または `concept` を使い、新しい `type` や `kind` の列挙値は導入しない。
これにより、既存の `concept` や `source` の対応付けを変えない。

## 5. 関係の定義

追加する関係はすべて `source` と `evidence` を必須にする。
方向は、関係を書いたページを主語とする。
反対向きの述語や、推移的なエッジを二重に保存しない。

| 述語 | 主語 → 目的語 | 採用する意味 | 採用しない読み方 |
| --- | --- | --- | --- |
| `part_of` | component → product/component | その責務を持つ構成要素の所属 | ファイル名に同じ語がある、単なる利用 |
| `release_of` | release → product | その製品の、その出荷の単位 | その記事が製品に言及した |
| `delivers` | release → change | その版に含めて出荷した変更 | 計画した、マージした、導入された別の版 |
| `changes` | change → component | 直接変更した責務の範囲 | 間接的に関係がありそうな機能 |
| `affects` | issue → product/component | 指定した条件で問題を観測した対象 | すべての版・環境に問題がある |
| `fixes` | change → issue | 根拠の条件の問題を解消した実施済みの変更 | 案、回避策、評価しただけ、全経路の安全保証 |
| `implements` | change → decision | 具体的な設計判断を実装した | ADR 全体の充足や評価合格 |
| `motivated_by` | decision → issue/evaluation | その判断をした理由として明記された | 先に起きた、同じ記事にある |
| `selects` | decision → product/concept | 判断が選んだ製品または方式 | 選択したので実装・出荷も済んだ |
| `evaluates` | evaluation → product/component/release/change/decision | その対象を評価した | 成功した、現在の版も同じ、すべて検証した |
| `applies_to` | concept → product/component | 明記した条件で手順・教訓が当てはまる | 一般知識からの連想 |

`depends_on` は既存の product/concept 同士の組を残し、両側に component を追加する。
利用の事実を出典で確認し、版を特定できる場合は `notes` と対象の本文に記す。
試料では `component:wiki-youtube-ingest → depends_on → product:yt-dlp-2026-8-19` を記録した（E13）。
旧 `chose` は人物・組織を主語とする関係として残し、判断を主語とする `selects` と混ぜない。
誰が決めたかを根拠なしに人物ノードへ補完しない。

本文リンクの `mentions` と、ページ単位の出典 `sourced_from` は引き続き自動生成する。
`related_to`、`tested_by`、`verified_by`、`causes`、`better_than` は追加しない。
前者は既存の探索リンクで足り、後者は成功・因果・比較条件を省略して誤読されやすいためである。

## 6. 識別と粒度

ID は題名を変えても保つ。
製品はプラグイン・道具・モデルの識別単位、構成要素は製品名を含む責務の名前、リリースは製品名と版の組で決める。
wiki と rag の `0.5.1`、通常の `query` と別製品の query を混同しない。
変更は PR・コミット・変更範囲、評価は実施日・対象版・方法を本文に残し、再試験を同じ評価で上書きしない。
ADR の番号が同じでも判断が複数なら、`decision:adr-0027-captions` のように選択の単位で分ける。
ファイルパス、タグ、見出し、試験の assert ごとの自動ノード化は行わない。

1 つのページが複数の役割を持っていても、ノード ID と node_type は 1 つにする。
たとえば現行の [[ingestに使うモデル]] は concept のまま残し、日付と選択を持つ decision を別に作る。
同じ対象を別の記事から言及する場合も、対象ページを増やさず同じ ID を指す。
別名は検索の補助であり、現行のグラフ CLI が別名から ID を自動で解決するとは扱わない。

記事に登場しただけでは対象ページを作らない。
Q1〜Q8 の少なくとも 1 つに必要で、定義・根拠・区別する対象が書けることを採用条件とする。
評価の 17 回のような集合は探索の入口として 1 ノードにできるが、本文で集合と明記する。
各回の対象版・判定を比較する問いでは、元の記録から各回を別ノードに分ける。

## 7. 根拠、状態、時間、結果

型付きの関係には `predicate`、`object`、`source`、`evidence`、`confidence`、`status` を書く。
このプロファイルでは、対象の版・条件・限界を `notes` にも書く。
`source` は現行の lint に合わせてソースページのスラッグ、`object` はページパスや wikilink ではなく、対象のノード ID にする。
引用はソース本文に存在する文字列を使い、周辺の文も読んで対象と範囲を確認する。
引用が存在しても、関係の意味が正しいとは限らない。

対象の本文には、次の情報を通常の Markdown として残す。
これらを新しい frontmatter 属性として保存・検索する機能は、この候補には含めない。

| 対象 | 本文に残す情報 |
| --- | --- |
| release | 製品、版、タグ・コミット、公開日、導入確認の対象版と未確認の点 |
| change | 提案か実施済みか、変更範囲、PR・コミット、対象の版 |
| issue | 期待と観測の差、再現条件、影響する版、原因の仮説と確定事項の区別 |
| decision | 選択、理由、適用範囲、判断日、採用・保留・撤回、見直す条件 |
| evaluation | 対象版・コミット、方法・試料・環境、観測した結果、未実施・限界、原記録 |

関係の `status` と対象の実施状態を混ぜない。
`current` は現在採用している関係の記録であり、「製品の最新版」「問題が未解決」「試験に合格」を表さない。
過去の出荷と製品の結び付きも、現在採用している記録なら `current` として保持できる。
`historical` は過去の期間・版だけに適用する関係、`proposed` は未採用の関係候補、`disputed` は異論のある関係、`superseded` は差し替えられた関係として使う。
`proposed fixes` で修正案を記録せず、実施前は本文に案として置く。
`confidence` は抽出した関係と根拠の対応への評価であり、評価対象の品質の点数ではない。

`valid_from` と `valid_to` を使う場合は関係の適用期間を表し、記事の created/updated、取り込み日、試験の実施日で埋めない。
境界を確定できなければ省略し、分かる版と日付を本文・notes に残す。
SemVer の大小だけで公開順、導入版、`supersedes` を生成しない。
古い根拠を削除せず、食い違いが同じ条件についてのものかを確かめる。
実際に [[youtubeの字幕の取り込みの設計-2026-11-15]] は冒頭で出荷を追記した一方、後段に実装前の留保が残るため、記事全体を 1 つの状態として読めない。

## 8. 実記事に基づく記述例

次は試料の `change:rag-pdf-prefix-1024` に相当する、採用前の記述例である。
対象の issue/component と、参照する出典を先に用意する。
既存のリリース記録の frontmatter を change に置き換える例ではない。

```yaml
---
type: "entity"
title: "PDF の前置きを 1024 バイトまで受け付ける変更"
tags: ["rag"]
sources: ["pdfのヘッダーの判定の修正-rag-0.5.1"]
created: 2026-11-18
updated: 2026-11-18
graph:
  node_id: "change:rag-pdf-prefix-1024"
  node_type: "change"
  relationships:
    - predicate: "fixes"
      object: "issue:rag-pdf-prefix-rejected"
      source: "pdfのヘッダーの判定の修正-rag-0.5.1"
      evidence: "`%PDF-` の前にあるバイトが 1024 バイト以下なら受け付けるように直した。上限は PDFium にそろえた"
      confidence: "high"
      status: "current"
      notes: "rag PR #7。前置き 1024 バイト以下の拒否条件を解消。MCP→索引化は未確認。"
---
```

この例なら「ヘッダーの拒否を直した」と「全経路を動作確認した」を分けて答えられる。
評価の `evaluates` を逆にたどり、E04 の直接抽出の観測と E05 の未確認の経路を提示する。
[[youtubeの字幕の取り込みの実装とリリース-wiki-0.23.0]] の 17 回のレビューにも `evaluates` を使えるが、「却下」の結果は本文・notes から読む。

## 9. 生成と保存

保存先は Markdown の対象ページと、`graph/ontology.yaml` とする。
型付きの関係は主語のページの `graph.relationships` に保存し、JSONL と SQLite は現行の抽出器で再生成する。
候補の YAML はデータモデルを制約するもので、本文から対象を見つけたり、推論したりする処理ではない。
グラフ DB を追加しなくても、この範囲を保存・照会できる。
外部グラフ DB を導入する場合も、ここで決めた ID・型・関係・根拠を投影し、対象の識別を DB 固有の ID に置き換えない。

人やホストの LLM が記事から候補を作り、既存 ID と照合してから採用する。
LLM を使わない場合も、人が同じ候補の形を書き、同じ検査を通せる。
抽出器には LLM 呼び出しを加えず、採用済みの記述を決定的にコンパイルする。
この分担は [[オントロジー候補の生成と採用の分離]] と [既存のグラフ改善設計](wiki-graph-improvements-2026-11-17.md) の G3〜G4 に合わせる。

## 10. 現行実装で検査できる範囲

| 検査・動作 | 現状とこの設計での扱い |
| --- | --- |
| 種類の割り当て、述語の主語型・目的語型、対象と出典の参照 | 既存の extract/lint で候補を扱える |
| 根拠の欄、値の列挙 | 通常 lint は空の confidence/status の必須検査を十分にしない。採用時に別途確かめる |
| 引用の実在 | 通常 lint の合格だけでは保証しない。今回の試料は全引用を直接照合した |
| 関係の真実性、同じ型の別対象との取り違え、範囲の妥当性 | 本文と根拠を読んで確認する。YAML からは保証できない |
| `part_of` の循環・自己参照、release の製品一意性 | この設計の採用規則。現行 lint の強制検査ではない |
