## 判定

**条件付きで採用可。** 候補 YAML は既存の 12 種類・15 述語を変えておらず、型と述語の骨格は使えます。ただし、外部道具の版の扱い、status の規則、`changes` の目的語の範囲、`notes` の見え方、試料の根拠の付け方に欠陥があり、このまま実 wiki に展開すると Q1・Q3・Q5・Q7・Q8 が誤った答えか不完全な答えになります。

欠陥の多くは YAML の型・述語そのものではなく、設計書の採用規則と試料の関係にあります。YAML まで直す必要があるのは、`changes` の目的語の範囲と、版を持つ外部道具の表し方の 2 つです。確信度は中です。

## 致命的・重大な欠陥

### 1. 重大：外部道具・モデルの版を `product` として別 ID にしているため、版を上げると Q7 と `selects` が壊れる

- **主張**
  - §4 は、比較したモデルの版を「必要なら製品の別 ID」としています。試料では `product:yt-dlp-2026-8-19` と `product:claude-sonnet-5-5` がこれにあたります。
  - 一方、自前の製品の版は `release` で表します。
  - 版の product を製品本体につなぐ述語がありません。`release_of` の主語は release に限られます。`depends_on`、`affects`、`selects` の目的語に release は入りません（YAML L147–156、L223–229、L253–259）。
- **反例**
  - wiki の次の版で yt-dlp を上げると、新しいノード `product:yt-dlp-2026-x-y` を作ることになります。
  - 「yt-dlp に依存する構成要素」という問いは、版ごとの ID をすべて知らないと引けません。別名は解決されず、型でノードを一覧するコマンドもありません（指摘 6）。
  - 旧版の `depends_on` は status が `current` のまま残ります。主語の `component:wiki-youtube-ingest` は版を持たないので、旧版への依存が現在の構成要素の依存として読まれます。これは Q7 の「過去の版の依存を現在の全版に広げない」に反します。
  - ADR-0027 の判断は「版を 1 つに固定する」です（E15 の引用に版の値はありません）。ところが `selects` は特定の版のノードを指しているので、版を上げた後は判断が古い版を選んだように読めます。
  - さらに、この `selects` の目的語の版の値は、notes に「版の値は E13 で特定する」とあるとおり、`source` と別の記事から借りています。関係の出典だけでは目的語を特定できません。
- **根拠**
  - `evidence_and_pilot.json` L516–536、L503–511
  - `wiki/sources/youtubeの字幕の取り込みの設計-2026-11-15.md` L28
  - 現行の `wiki_youtube.py` L4 は `yt-dlp==2026.8.19` で、今のところ一致しています。版を上げたときの破綻は構造から導いた結論です。

### 2. 重大：§7 の status の規則が、既存のグラフ改善設計 G2 と両立しない

- **主張**
  - §7 は `historical` を「過去の期間・版だけに適用する関係」と定義する一方、過去の出荷との結び付きは `current` で保持できるとしています。
  - 試料は版に縛られた関係をすべて `current` にしています。
    - `affects`：notes に「rag 0.5.0」
    - `part_of`：notes に「rag 0.5.0〜0.5.1 の観測」
    - `depends_on`：notes に「wiki 0.23.0 の固定」
  - G2 は、型付きの照会の既定を `status=current` にし、`historical`・`superseded` を照会に含めるには開始日と終了日を必要とします（`docs/plans/wiki-graph-improvements-2026-11-17.md` L210、L223）。
  - §7 は、`valid_from`・`valid_to` を記事の日付で埋めることを禁じ、境界を確定できなければ省くとしています。
- **反例**
  - 0.5.1 で直った `issue:rag-pdf-prefix-rejected --affects--> component:rag-pdf-reader` について、書く人が取れる選択は 2 つしかありません。
    - `current` のまま残す：G2 の既定の照会で、直った問題が現在の問題として出ます。
    - §7 の定義どおり `historical` にする：日付を書けないので、G2 の照会から消えます。
  - どちらを選んでも Q5 の答えが壊れ、書く人によって値が分かれます。

### 3. 重大：試料の判断 `decision:web-raw-sonnet-20261113` は、日付と範囲の組み合わせが出典と食い違う

- **主張**
  - 試料は、2026-11-13 の判断を「Web raw の段に限る」としています（本文は「決定日: 2026-11-13。対象: Web raw の段」、notes も同じ趣旨）。
  - 出典の主張の表（L80）は「`/wiki:ingest` には Sonnet 5.5 を使い続ける」です。
  - 概念ページ L14 によれば、2026-11-14 まではグローバルの指示で取り込み全体を Sonnet にしていました。それを消し、raw の段だけをエージェントに分けたのは 11-14 と 0.15.0 です。
- **何が壊れるか**
  - 試料は、2 つの判断（11-13 の全体の継続と、11-14 の範囲の縮小）を 1 つのノードにまとめています。
  - 範囲を縮めた判断は記録されず、`supersedes` も使われていません。
  - Q3 では、範囲を決めた日を誤って答えます。
- **自分の規則との矛盾**
  - 判断の中身（理由、受け入れた弱点、見直す条件）は既存の概念ページ `concept:ingestに使うモデル` にあります。
  - その概念ページを残したまま decision のページを作るのは、§6 L143 の「同じ対象を…対象ページを増やさず同じ ID を指す」に反します。
- **根拠**
  - `wiki/sources/ingestのモデルの比較-2026-11-13.md` L14、L80
  - `wiki/concepts/ingestに使うモデル.md` L12–14
  - 試料 `pilot-wiki/concepts/decision--web-raw-sonnet-20261113.md`

### 4. 重大：根拠の引用を複数の関係で使い回しており、引用から関係を確かめられない

- **観測**
  - E12 は 5 本の関係の根拠になっています（`part_of`、`changes`、`implements`、`release_of`、`delivers`）。E10 は 4 本、E01・E02・E03・E08 は各 2 本です。
  - E12 の文は「ADR-0027 を承認し、実装を求めた。この記録は、その実装と…0.23.0 のもの」です。この文は次のことを述べていません。
    - 構成要素がどの製品に属するか
    - どの構成要素を変えたか
    - 具体的な判断を実装したこと。E12 が述べるのは ADR 全体の実装で、YAML L244 が否定している読み方そのものです。
  - よりよい引用は同じ記事にありました。L18–19 はスクリプトを #74 で足したこと、L60 は v0.23.0 のタグが #74 のマージコミットを指すことを述べています。
  - `motivated_by` の引用は `selects` と同じ「結論として、Sonnet 5.5 を使い続けることにした」です。notes の根拠は「同じ報告のモデル比較を受けた結論」で、§5 が採用しない読み方「同じ記事にある」に近いものです。
- **反例**
  - E12 の引用のまま、述語を `changes` から `implements` に入れ替えても、目的語を同じ型の別ノードに変えても、どの検査も通ります。
  - 移行の手順 4「出典を読んで関係を採用」の手本として、この試料は使えません。

### 5. 重大：issue の範囲と `fixes` の範囲が一致せず、Q1 に誤った答えを返す

- **主張**
  - issue の題名は「先頭に改行のある PDF が拒否される」で、出典 L19 の観測にあたります。
  - ところが `affects` の根拠 E01 は、一般の条件「先頭がちょうど `%PDF-` でないと拒む」です。
  - 修正 E02 が受け付けるようにしたのは、前置きが 1024 バイト以下の場合だけです。前置きが 1024 バイトを超える PDF は 0.5.1 以降も拒まれます（`pdfのヘッダーの書き方の修正-rag-0.5.2-0.5.3.md` L20 のエラーメッセージ）。
- **反例**
  - Q1 を issue の `affects` の根拠から答えると、「先頭が %PDF- でないと拒む問題を解消した」となり、範囲を広げすぎます。
  - issue を E01 の一般の条件と読めば `fixes` は過大です。改行の場合と読めば、`affects` の根拠が広すぎます。
  - 設計書の issue の定義（「条件と期待との差」）は、どちらの読み方かを決めていません。

### 6. 重大：Q8 と、一覧が必要な問いは、現行の CLI と MCP で答えられない

- **観測**
  - `wiki_graph_query.py` のコマンドは `neighbors`、`edges`（`--subject` が必須）、`path`、`facts` の 4 つだけで、MCP の `graph` も同じです（L266–278、MCP L433）。
  - 型でノードを一覧するコマンドも、述語だけでエッジを一覧するコマンドもありません。
- **何が壊れるか**
  - Q8 には、すべての decision を一覧することが必要で、答えられません。
  - 判断の状態（承認・保留・撤回）は本文にしかないので、「承認だけ」と「提案」「撤回」を区別できません。
  - §3 L75 の「`neighbors` と `edges --predicate` を組み合わせれば段階的に引ける」が成り立つのは、起点の ID を知っている場合だけです。
- **確かめたこと**：逆向きの検索は `facts` で動きました。試料で `change:rag-pdf-prefix-1024` の入るエッジ 2 本を確かめました。

### 7. 重大：限界を書いた `notes` が、CLI の既定の出力に表示されない

- **観測**
  - `render_edge_row`（`wiki_graph_query.py` L105–116）は notes を表示せず、証拠も 140 文字で切ります。
  - 試料に対して `facts --about change:rag-pdf-prefix-1024` をテキスト出力で実行すると、`fixes` は confidence=high、status=current と表示され、「MCP から索引化までの成功は未確認」は出ませんでした。

### 8. 重大：`changes` の目的語が component に限られ、文書だけの変更や他のリポジトリの変更を表せない。試料は変更の範囲を少なく記録している

- **E06 で書けない**

- **0.23.0 の記録が少ない**

  - 出典 L22–27 によれば、同じ PR で `wiki_fetch.py`、lint と MCP の `lint`、`walk_markdown`、取り込みの手順、`query-confidence.md` も変えています。

## 崩れる前提

- **「関係の status と対象の状態を分ければ足りる」**：G2 の既定の照会（`current` だけ、`historical` には日付が必要）を入れると崩れます（指摘 2）。
- **「範囲と限界は notes に書けば読み手に届く」**：CLI のテキスト出力と、既定の証拠の切り詰めで崩れます（指摘 7）。
- **「1 つの引用で 1 つの関係を支持できる」**：まとめの 1 文から複数の述語を作ると崩れます（指摘 4）。
- **「外部道具の版は product の別 ID で表せる」**：依存先の版を上げた時点で崩れます（指摘 1）。
- **「変更の範囲は component で表せる」**：文書、設定、他のリポジトリの変更で崩れます（E06、指摘 8）。
- **「1 つの出典の記事が、1 つの時点の判断を表す」**：後の記事が範囲を狭めたり変えたりすると崩れます（Sonnet の例、指摘 3）。
- **「ID を知っていれば辿れる」**：一覧が必要な問い（Q8）と、別名からの検索で崩れます（指摘 6）。
- **「Q1〜Q8 のどれかに必要という採用条件が、対象ページの増加を抑える」**：問いの範囲が広く、ほとんどの対象が条件を満たします。これは推測ですが、試料では出典 6 件から対象ページ 20 件を作りました。同じ割合で 60 件の出典に広げると、SCHEMA が定めるインデックスの分割の閾値（約 150 ページ）を超えます。現在は 91 ページで、`index.md` は 117 行です。
- **「`explicit_only: true` が型の自動付与を防ぐ」**：この欄を読むスクリプトはありません。自動で付かないのは、`maps_from` を書いていないからです（軽微の 1 つ目）。

## 見落としと軽微な問題

- **`explicit_only` と `description` の扱い（軽微）**
  - どちらも、スクリプトが読む箇所はありません（grep で確かめました）。
  - `references/graph-workflow.md` L76 は、`explicit_only` の型を「wiki のページを持たない、目的語だけの種類」と説明しています。候補では、その種類にページを持たせています。
  - `type: entity` で `kind` も `graph.node_type` もないページは、型が決まらず（`derive_node_type` が `None` を返す）、`concept` として扱われます。型の制約がある関係を持っていなければ、lint は指摘しません。
- **既存の概念ページの候補更新（軽微）**
  - 試料の `ingestに使うモデル.md` は、H1 が 2 重になっています。
  - frontmatter も書き換わっています。tags と sources は 1 行の配列からブロックの配列になり、created と updated は引用符付きの文字列になりました。
  - 「`str_replace` で必要な箇所だけを更新する」という規則に反します。`build_candidate.py` は、手順 3 の生成には使えません。
- **互換性の検査の効力（軽微）**
  - 現行の wiki には型付きのエッジが 0 本あり、`graph.node_type` を書いたページもありません。そのため、「グラフが完全に同じ」という結果は、述語の定義をどう変えても成り立ちます。
  - 互換性を実際に保証しているのは、`verify_candidate.py` L38–45 の、既存の定義が等しいことの assert です。
- **17 回のレビューの評価（軽微）**
  - 本文には「評価対象: 開発中の実装の各版」とあるのに、`evaluates` は出荷した change を指しています。
  - §4 は評価の定義に「対象版・コミット」を求めており、17 回をまとめたノードはこれを満たしません。
  - 「却下」は本文にしか書かれておらず、edge の notes にはありません。
- **`delivers` の根拠 E03（軽微）**：「#7 をマージ…のあと、v0.5.1 をリリースした」という時系列の文です。版に含まれたことは、前後関係から推しています。
- **`applies_to` の出典（軽微）**：出典は 11-13 の比較です。この構成要素（エージェント `wiki:web-raw`）ができたのは 0.15.0（11-14）で、概念ページ L14 によれば、それより前の raw の段は取り込みを進めるモデルが行っていました。
- **`--decide` の記載漏れ（軽微）**：引用がソースにあるかを判定モデルで照らす `wiki_graph_lint.py --decide` がありますが、§10 は触れていません。
- **lint の検出範囲（開示済み）**：一時スクリプトで反例を試しました。
  - lint が通したもの：`proposed` の `fixes`、空の confidence、`part_of` の自己参照、wiki の版が rag の変更を出荷する誤り、`source` と引用の食い違い。§10 と `known_unchecked` の開示と一致するので、欠陥には数えていません。
  - 未定義の `node_type` の書き誤りは、関係を持つページでは `subject_type_mismatch` として検出されました。

## 崩せなかった点

- **YAML の互換性**：既存の 12 種類・15 述語の定義は、`depends_on` に component を足したことを除いて、すべて同じです。本番記事の解釈は変わりません。
- **向きの規約**：新しい述語の主語はすべて、関係を書くページです。逆向きの述語や推移的なエッジは足していません。1 ページ 1 ノードの契約も守っています。
- **観測した改行の事例の `fixes`**：E02（修正）と E04（直した `read_pdf` に実データを通した）で支持されています。`release:rag-0.5.1` の `release_of` も支持されています。
- **wiki 0.15.0 のタグと導入した版の区別**：本文で正しく分けています。
- **§10 の開示**：lint で意味や真偽を保証できないことを、正しく開示しています。

```text
使用した MCP サーバー: なし
使用した Agent Skills: なし
```
