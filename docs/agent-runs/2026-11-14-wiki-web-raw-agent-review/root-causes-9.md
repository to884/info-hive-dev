# 9 回目のレビューの指摘の原因と直し方

対象: 8 回目の指摘を直した版。判定は却下（確信度は高）。重大の 4 件は、どれも確かめのスクリプトにあった。プラグインの手順（取り直したら W3 に戻る決まりの切り分け、`--html-file` で同じ内容を渡す場合、`"unchanged": true` で写しがない場合）は崩されなかった。

## 根の原因

4 件とも、シェルのコマンドと Markdown を、確かめのスクリプトの中の正規表現で読み直していたことから出た。読み方を 1 つ直すと、別の書き方で次の反例が出る（引用符の中の `;`、別のフォルダーの `index.md`、リストの中の補足、原文の引用、オプションの名前の検索）。そこで、自前で読み直すことをやめ、プラグインの出力と、ディスクの上のファイルの中身で決めるようにした。

## 直し方

| 指摘 | 直し方 |
| --- | --- |
| 1. 引用符の中の `;` や `&`、スクリプトの名前のあとの行の継続で、正しい W8 を落とす | W8 は、呼び出しのコマンドに `wiki_rawcheck`、`check`、`--finish` が書かれ、結果が通って写しを消した形であることで決める。シェルの区切りや引用符は読まない（`names_finish`） |
| 2. Bash で別のフォルダーの `index.md` に書いても、索引を更新したことになる | 索引とログは、コマンドから書き込み先を推し量らず、ファイルの中身で決める。`index.md` に、メインが Edit か Write で書いた要約ページへのリンクがあること、`log.md` に取り込みの行と「raw:」のサブ行があること。プロジェクトは空から始めた前提なので、中身は今回の取り込みが書いたものである。リダイレクトの読み取り（`bash_write_targets`）は除いた |
| 3. リストの中の補足を見落とし、原文の引用を補足と取り違える | 表示名は、W8 の `check --json` の結果の `translated_by` と `caption_names` から取る（`wiki_rawcheck.py` が、画像と Markdown の木から補足を見分けた名前）。W8 を文字の出力で動かしたときは判定せず、`display_names_verified` を false にする |
| 4. `--accept-warnings` を検索しただけで違反になる | オプションを付けて check を動かし、check の出力を受け取った呼び出しだけを違反とする |
| 軽微: 残してある結果の JSON が古い | 3 件とも、今のスクリプトで確かめ直した結果に差し替えた（費用と時間は取り込んだときの値を残した） |

試験に、9 回目の反例を作り物の記録で足した（正しい取り込みが通るもの 5 つと、違反を通さないもの 2 つ）。

## 確かめ直した結果

| 記録 | 結果 | 表示名 |
| --- | --- | --- |
| `trial-cqrs.json`（0.15.0 より前の版） | 18/18 | check の結果から確かめた（Claude Sonnet 5.5） |
| `trial-bloom.json`（0.15.0 より前の版） | 18/18 | check の結果から確かめた（補足: Claude Sonnet 5.5、訳さないページ） |
| `trial-0161-cqrs.json`（0.16.1 の版） | 17/17 | W8 を `--json` なしで動かしたので、判定していない |

## 残る限界

手順の W8 のコマンドには `--json` がない。そのため、エージェントが付けなければ、表示名は確かめのスクリプトでは判定されない（呼び出す側の手順 6 が、raw の表示名を見て確かめる）。手順の W8 に `--json` を足せば、いつも判定できるようになる。これはプラグインの手順の変更なので、この直しには含めていない。
