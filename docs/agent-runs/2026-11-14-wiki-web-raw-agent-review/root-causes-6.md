# 6 回目のレビューの指摘の原因と直し方

対象: 5 回目のレビューと PR #103 の指摘を直した版。判定は却下（確信度は高）。4 件とも、コードと手順の文で根拠を確かめた。

## 1. 「本文が短いまま続ける」の承認が、別の本文に効く（重大）

- 反例: 承認したあと、エージェントが W3 の `--keep-noise --force` か W5 の `--force` で自分で取り直すと、承認が残ったまま本文が変わる（空になることもある）。
- 原因: `root-causes-5.md` は、「`--force` なしで raw が別の本文に置き換わる経路がない」ことを理由に、承認をハッシュで結ぶ案を採らなかった。しかし、この理由は呼び出す側が依頼に書く `fetch.force` しか見ておらず、エージェントが手順の中で自分で付ける `--force` を落としていた。承認が依頼の中の文で、どの本文への承認かを持たないことが、根の原因である。
- 直し方: 承認を本文に結んだ。エージェントは、`needs_browser` の問いに、その本文の `fetched_sha256`（最後に実行した `wiki_fetch.py` の出力の値）を入れる。呼び出す側は、`conditions` に「本文が短いまま続ける（fetched_sha256: <値>）」と書く。エージェントは、最後の `wiki_fetch.py` の出力の値と同じときだけ、この承認を効かせる。途中から続けるときの出力にも `fetched_sha256` が要るので、`wiki_rawcheck.RESUME_KEYS` に足した（写しの `fetch.json` にはもともと入っている）。

## 2. 前の要約ページが残ると、今回の書き込みの失敗を合格にする（重大）

- 原因: 記録を読むとき、道具の結果の `tool_use_id` と `is_error` を捨てていて、呼び出しが成功したかが分からなかった。
- 直し方: 結果を呼び出しの id で引けるようにした（`results_of`、`succeeded`）。「メインが書いた」は成功した呼び出しだけで数える。「書いてはいけない」は、失敗した呼び出しも数える（書こうとしたことが違反なので）。

## 3. スクリプトの実行を、コマンドの文字列から読み切れない（重大）

- 原因: 誰が実行したかを、コマンドの文字列の形から決めていた。引用符、変数、別の呼び出しで組み立てたパスは読めず、`echo` の表示は実行と取り違える。Bash の書き込みと同じ問題で、文字列からは完全には読めない。
- 直し方: 実行者は、その人に届いた道具の結果がスクリプトの出力の形をしているかで決める（`FETCH_OUT`、`FREEZE_OUT`、`check_finished`）。W8 も、`check` が通って作業用の写しを消したという結果で決める。スクリプトの名前を含むコマンドは、合否を決めない一覧（`bash_to_review`）に出す。作業用の写しの `fetch.json` は取得の出力と同じ形なので、それを `cat` で読んだ結果も実行に数える（厳しい側に倒す）。
- 実際の取り込みの記録 2 件（`trial-cqrs.json`、`trial-bloom.json` のセッション）を、直したスクリプトで確かめ直し、どちらも 15/15 で通った。

## 4. `..` やリンクを含む書き込み先を見逃す（重大）

- 原因: プロジェクトのパスだけを `resolve()` し、書き込み先は文字列の前方一致で比べていた。
- 直し方: 書き込み先も `norm()`（相対パスはプロジェクトから読み、`resolve()` する）を通してから比べる。

## 軽微

- 内部の取り直しまで見る試験がない、という指摘: 承認の効く条件（最後の `wiki_fetch.py` の出力の値と同じ）を手順の文に書き、静的な試験で見る。モデルが手順に従うかは、静的な試験では確かめられない。取り込んだあとの版での実地の確かめで見る。
