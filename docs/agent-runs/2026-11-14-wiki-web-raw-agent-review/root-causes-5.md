# 5 回目のレビューの指摘の原因と直し方

対象: main（0.14.1、#57）を取り込んだときに `references/web-raw.md` へ移した W2/W3 の文、問いの種類 `old_work_dir`、`needs_browser` の「本文が短いまま続ける」。判定は却下（確信度は高）。

## 1. 続ける答えでも取り直す（重大）

- 反例: `needs_browser` で HTML を保存して `fetch.html_file` と `fetch.force: true` で呼び直し、また短いので「今の本文で続ける」と答える。表のとおり `fetch` を変えずに `conditions` だけを足すと、W2 がまた `--html-file … --force` で取り直す。
- 原因: 依頼の `fetch.force`、`fetch.html_file`、`fetch.page_url` は 1 回の取得への指示なのに、呼び出す側が依頼を写して呼び直すので、次の呼び出しにも残る。この穴は「本文が短いまま続ける」だけのものではない。`needs_browser` で取り直したあとに `warnings` で呼び直すと、同じように取り直して訳を消す。この穴は main を取り込む前からあった。
- 直し方: 呼び出す側の手順 4 に、呼び直すたびにこの 3 つを戻し、表や手順がその呼び直しで指示したときだけ設定する、という規則を置いた。`--force` も `--html-file` もなければ、`wiki_fetch.py` は途中の写しから続けて raw を上書きしない（`build` の再開の条件は `not html_file and not args.force`。`test_dom_take_resumes_without_fetch` が、DOM で取ったあとの URL だけの呼び出しで取得しないことを確かめている）。これで、「続ける」の承認が向かう本文は、承認したときの raw に限られる。`fetch.force` を `true` にするときは、前の本文への答えである「本文が短いまま続ける」も消す。
- 本文のハッシュで承認を結ぶ案は採らなかった。戻す規則のもとでは、`--force` なしで raw が別の本文に置き換わる経路がないためである。

## 2. old_work_dir の問いが本当の誤りを隠す（軽微）

- 反例: 0.14.1 までの版の写しがあり、`--html-file` のファイルがないか取得に失敗すると、W2 が `old_work_dir` を先に見て問いを返す。`fetch.force` を `true` にして呼び直しても、元の誤りは残る。
- 直し方: 終了コード 0 と 3 では `old_work_dir` を先に見て、終了コード 1 と 2 では誤りを先に `failed` で返す（`error.message` に古い写しがあることも書く）ことにした。誤りを直して呼び直すと、`old_work_dir` の問いになる。

## 3. 試験が文の有無しか見ていない（軽微）

- 静的な試験に、手順 4 の戻す規則、`needs_browser` の行が `fetch` を残せと書いていないこと、`old_work_dir` の行が終了コード 1 と 2 の誤りを先に返すことを足した。スクリプトの側の挙動（戻した依頼で取得せずに続ける）は、`test_wiki_web_check.py` の既存の試験が確かめている。依頼の往復そのもの（モデルが手順に従うか）は、静的な試験では確かめられない。取り込んだあとの版での実地の確かめで見る。
