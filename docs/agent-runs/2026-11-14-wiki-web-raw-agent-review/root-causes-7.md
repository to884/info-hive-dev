# 7 回目のレビューの指摘の原因と直し方

対象: 6 回目の指摘を直した版。判定は却下（確信度は高）。重大の 4 件とも、コードと手順の文で根拠を確かめた。PR #58 と #103 は、この指摘を直す前に作者がマージしたので、直しは新しい PR で出す（プラグインは 0.16.1）。

## 1. W5 の取り直しが W3 を通らない（重大、プラグイン）

- 反例: 承認した本文で W4 に進み、W5 で消しすぎに気づいて `--force` で取り直すと、手順は「W4 からやり直す」とあった。新しい本文（短いか空）について、W3 の確かめも承認の照らし合わせもせずに進めた。
- 原因: 承認は W3 で照らし合わせるのに、取り直しの行き先が文ごとにばらばらで、W3 を通ることが決まりになっていなかった。承認をハッシュに結ぶ作りは、W3 を通るかぎり崩されていない（レビューの「崩せなかった点」）。
- 直し方: W1〜W8 の頭に、`wiki_fetch.py` を実行したら（どの段の取り直しも）、その出力を W2 の扱いで読み、W3 を通ってから W4 に進む、という決まりを置いた。W3 の `--keep-noise --force` と W5 の `--force` の文をそれに合わせた。取り直しの文に「W4〜W8 から続ける」と書かないことを、静的な試験で確かめる。承認は本文の `fetched_sha256` に結んであるので、呼び直すときに承認を消す手順は除いた（仕組みを減らした）。

## 2〜3. 確かめのスクリプトが、なかったことを主張していた（重大）

- 反例: 出力を捨てた PowerShell での `freeze`（2）、前の `check` の出力を `cat` で表示した W8、メインが代わりに終えた W8（3）が、15/15 で通った。
- 原因: 5〜7 回目に、見つけ方（コマンドの文字列、結果の形）を変えても反例が出続けたのは、「ほかの担当は動かさなかった」という、記録からは示せない主張を合否にしていたためである。Bash の書き込みについては、同じ理由で、もう合否から外してあった。
- 直し方: 合否は、あったことを示す証拠だけにした。
  - `wiki:web-raw` が取得と `freeze` の出力を受け取ったこと。
  - W8 は、`wiki:web-raw` が自分で `wiki_rawcheck.py check … --finish` を動かし、その結果が通って写しを消した形であること。前の出力を表示しただけの呼び出しは、コマンドの形で除く。警告を受け入れる流れでメインが `--accept-warnings` で終えたときも通し、どちらが終えたかを `w8_finished_by` に書く。
  - ほかの担当の実行は、結果の形から見えたものを `other_script_runs` に出すだけにした。メインとほかのサブエージェントの Bash と PowerShell のコマンドは、絞り込まずにすべて `bash_to_review` に出す。実際の取り込みの記録 2 件では、7 件と 13 件で、人が読める量だった。
  - スクリプトの説明の頭に、前提（手順に従って動いたセッションの記録であること。プロジェクトは空のフォルダーから始めたものであること）を書いた。

## 4. 拡張パスの接頭辞と、リンクになった wiki と raw（重大）

- 直し方: `norm()` で Windows の拡張パスの接頭辞（`\\?\`、`\\.\`、`\\?\UNC\`）を外してから解き、解いたあとに残った接頭辞も外す。比べる側の `wiki` と `raw` も、それぞれ `norm()` で解く。シンボリックリンクの試験は、Windows では権限が要るので作っていない。

## 軽微

- `is_error` のない失敗と、前の要約ページへの部分的な `Edit`: 前提（空のフォルダーから始めた取り込み）の外なので、直さずに説明に書いた。

## 確かめ

直したスクリプトで、実際の取り込みの記録 2 件（`trial-cqrs.json`、`trial-bloom.json` のセッション）を確かめ直し、どちらも 15/15 で通った（W8 を終えたのは `wiki:web-raw`、ほかの担当の実行は見えなかった）。
