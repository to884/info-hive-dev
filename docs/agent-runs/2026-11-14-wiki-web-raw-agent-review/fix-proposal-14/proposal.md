## 修正案

### 重大1：JSONL の境界と、証拠の完全性を分けて扱う

**変更場所：B:88–104、393–406、466–482、614以降。**

決まりを次のようにします。

1. JSONL は LF だけで分割する。CRLF の CR は JSON の許容する空白として扱う。
2. UTF-8 の復号失敗、非空レコードの JSON 解析失敗、トップレベルがオブジェクトでない場合を黙って捨てない。
3. エラーにはファイルとレコードの行番号を付ける。
4. 入力に欠落・破損があれば、解析不能として `ok=False` にする。部分的な解析結果だけで合格を返さない。
5. サブエージェントの記録は一度だけ読み、出来事と先頭時刻を同じ読み込み結果から作る。

骨組みは次のとおりです。`load_object()` は後述する共通の厳密な JSON 読取関数です。

```python
def read_jsonl(path):
    text = decode_utf8(path.read_bytes(), origin=str(path))
    records = []
    for number, line in enumerate(text.split("\n"), 1):
        if not line.strip(" \t\r"):
            continue
        records.append(load_object(line, origin=f"{path}:{number}"))
    return records
```

Unicode 全般を対象にする `strip()` も避けます。レコードの外側で許容する空白と、本文中の文字を混ぜないためです。

さらに `finish_runs()` では、対象呼び出しを先に列挙し、対応結果がないものを診断に残します。

```python
for tool in finish_candidates:
    result = results.get(tool["id"])
    if result is None:
        incomplete.append({"id": tool["id"], "reason": "missing_result"})
        continue
    runs.extend(parse_check_result(result))
```

ここで欠落を「警告を受け入れた違反」と断定しません。**違反なしと判定する証拠が足りない**として不合格にします。

結果があるものの検査出力がない場合は、引数エラーなどもありえます。直ちに違反とはしません。ただし、検査 JSON の候補を見つけて解析に失敗した場合まで、単なる「回なし」に落としてはいけません。解析結果と解析エラーを別に返す構造にします。

既存の「呼び出し全体が `is_error` でも、先に出た検査結果を読む」という決まり（B:461–463）は維持します。

### 軽微1：本文の衝突検査と、結果の認識条件を共有する

**変更場所：B:263–269、337–348、387–390。**

`"final_url": ` を、別の独立した禁止文字列に置き換える方法では再びずれます。**出力を認識するための文字列の形を一か所に定義し、結果の認識と本文の衝突検査から使います。**

概念上は次の構造です。

```python
Signature(
    name="fetch_json",
    pattern=r'"final_url": "[^"]*",\s*"source_sha256": "',
    result_position="anywhere",
)
Signature(
    name="fetch_saved",
    pattern=r"保存した: ",
    result_position="line_start",
)
```

- 結果の認識では、現在の行頭条件を適用する。
- 本文の衝突検査では、字下げや引用によって表示位置が変わることを考慮し、位置の条件を外して同じ形を探す。
- JSON の取得結果については、二つのキーの並びを必要とする。

この並びは、実際の生成箇所 F:1301–1303、1329–1330 とも一致します。

したがって、

```json
{"final_url": "https://example.com/", "status": 200}
```

だけを含む記事は、この理由では拒否しません。一方、現在の `FETCH_OUT` が取得結果として認識する並びは引き続き拒否します。

check の見出し・終端行を個別に衝突検査する保守性は、今回そのまま残します。複数の行や出力が組み合わさる問題まで、取得結果の軽微な修正に便乗して緩めません。

すべての試験を実際の `main()` 呼び出しにする必要はありません。代表となる正常系で生成側との対応を検証し、解析の単体試験は小さな入力を使います。

T:402、616、732–735、756 なども、**正常な JSON 出力を意図しているケース**は更新します。文字出力の互換解析や、最後が文字出力なら W8 を通さない試験は、意図を明示して残します。

文字列の分け方は用途別に決めます。

- **外側の JSONL**：LF。
- **検査結果の文字出力**：現在の LF と CRLF の処理を維持する（B:365–368）。

## 採らない案

1. **生成側をすべて `ensure_ascii=True` にする。**  
   今回の Unicode による切断は避けられます。しかし、外側の Claude Code の保存方法はこのスクリプトの管理外です。既存の正当な JSONL も直りません。解析失敗の黙殺も残るため、読み取り側の対策の代わりにはしません。

2. **`splitlines()` を `split("\n")` にするだけ。**  
   小さく、今回の二つの反例には有効です。実験でも確認しました。ただし、別の解析失敗や結果の欠落で、再び残った証拠だけから合格にできます。境界の修正として採用し、証拠の完全性の対策も合わせます。

実行専用の監査ログをプラグインに追加すれば、将来は結果の文への依存を減らせます。ただし、過去の Claude Code JSONL を調べる今回の用途を置き換える案にはしません。
