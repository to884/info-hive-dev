判定はREJECTED（Major 2件、Minor 4件）。以下は修正前に反証した判断である。

1. 部分移行後のquery/status/ingest: 旧記録を保つことと、新分類で確定した件数に算入することは同義ではないので、既存記録を保てば必ず誤答するという二択は成立しない。しかし旧記録を保持したまま新分類の網羅性をどう示すかは未定義であり、指摘の中心は採用する。部分移行を持続する状態として扱い、確定分と旧定義に残る分、件数の下限と未確定、通常ingestで増える未分類候補を区別する。
2. 型の解決とSCHEMA: `derive_node_type()`は明示的な`graph.node_type`を最優先するため、kindと共通別名が常に型を決定するという一般化は棄却する。`SCHEMA.md`と共通別名、maps_from、明示型、IDの依存関係を確かめ、移行の検査と書き手の参照先の説明が不足している点は採用する。共通の日本語kind正規化をwiki固有の意味へ書き換える解決は採らない。文字列の互換とwikiごとの採用済み語彙の解決を分け、後者をingest/lint/extract/queryで共用し、SCHEMAの該当規約と対応表も移行へ含める。
3. 部分選択の会話例: 本文は再試行・確認を要求するが、例に最終案の表示がない点は採用する。組み直しで差分が変わった場合の表示と採用を例に加える。元から表示済みの依存の閉じた差分を利用者が採用しただけの場合まで、同じ承認を繰り返し求める要件にはしない。
4. 抽出誤り・記録不足への操作: 追加では不足を直せるが、既存の誤った関係の訂正は提供案で明示していない。定義を変えない記録の訂正・取り下げを含め、根拠と変更履歴を残す。原本の改変や、矛盾する出典の片方を無条件に捨てる操作とは区別する。
5. パス・順序によるエッジID変更: 「型や述語など」は変更理由を限定していないため、明示的な対象外とはいえない。しかし既存の[[エッジの識別子]]とgraph-workflowはパスと順序への依存を記すので、検査例として明記する。
6. 見送り案の再検討: 自動的な繰り返しを抑える意図はあるが、本文は利用者の明示的な再依頼まで抑制する読みができる。利用者の再依頼を優先する例外を両文書へ記す。

実装前の要件・利用体験の修正として扱い、保存形式や公開切り替えの詳細実装はこの変更で完成済みとはしない。
