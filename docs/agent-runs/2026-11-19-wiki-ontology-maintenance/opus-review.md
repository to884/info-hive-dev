### [Major] 部分移行のあとの問い合わせと ingest の扱いが決まっていない

対象
- `docs/plans/wiki-ontology-maintenance-2026-11-19.md` 45、64〜65、83、88 行
- `docs/plans/wiki-ontology-feature-experience-2026-11-19.md` 147、183、206 行

根拠
- 部分移行は、適用して終わる正規の結果として認められています。旧定義を「廃止予定」として残し、残件を保持します（maintenance 64〜65 行）。
- 一方で、次の 2 つも求めています。
  - 「語彙だけを変えて既存記録を無効にしない」（83 行）
  - 「新旧が混ざった結果を新定義の完了結果として公開しない」（88 行、feature 206 行）
- 88 行は「グラフ再生成・問い合わせ・lint への接続が完了するまで」という、適用中の話です。部分移行は新旧が混在した状態のまま長く続きますが、その間の問い合わせの扱いを述べた箇所はありません。
- feature 183 行の「未確定の候補を問い合わせへ混ぜない」が対象にしているのは、同一性の候補だけです。分類が決まらずに旧定義に残った記録は含まれていません。

問題
例として、「製品」を製品と契約に分け、「Aプラン」など 20 件が旧「製品」に残った場合を考えます。
- 残件を確定した知識として扱う場合: 「契約の一覧」「製品の数」を尋ねると、残件が黙って漏れるか、二重に数えられます。利用者は気づかないまま誤った答えを受け取ります。
- 残件を未確定として扱う場合: 移行の前は答えられた事実が答えから消えます。83 行の「既存記録を無効にしない」に反します。

どちらを選んでも、利用者が恐れている「定義と内容の乖離」が、見えない形で残ります。さらに、部分移行の最中に新しい記事を ingest したときの規則もありません。廃止予定の型は新規利用を止める（56 行）ので、分けた先を決められない記述が出てきても、行き先がありません。

検証方法
1. maintenance と feature から「部分移行」「廃止予定」「旧定義を残す」を検索する。
2. 見つかった箇所に、適用後の query、lint、status、ingest の振る舞いが書かれているかを確かめる。
3. 架空の例「製品／契約の分割で 20 件が残る」をたどり、「契約は何件か」への答えが要件から一意に決まるかを確かめる。

修正の方向性
部分移行を、適用中ではなく持続する状態として定義します。要件として次の 4 点を加えます。
1. 問い合わせ: 残件が含まれる問いには「この型には未移行の記録が N 件ある」と出典付きで示す。残件を新しい型の答えに黙って含めることも、黙って外すこともしない。
2. status: 引数なしの status で、LLM を呼ばずに、残件の件数、旧定義、次に判断すべきことを表示する。
3. ingest: 部分移行の最中に、廃止予定の型に当たる記述が出たときの規則を決める。分けた先を判断できなければ保留し、残件に加える。旧型での新規記録はしない。
4. 試行と検査: 部分移行の後に問い合わせをする事例と、ingest をする事例を、maintenance 76 行の試行の例に加える。

### [Major] 型の識別が SCHEMA.md とプラグイン共通の kind の別名にも依存するのに、移行の範囲に入っていない

対象
- `docs/plans/wiki-ontology-maintenance-2026-11-19.md` 25、52、82〜94 行
- `docs/plans/wiki-ontology-feature-experience-2026-11-19.md` 28 行

根拠
現行の仕組みでは、実体の型は次の 3 層で決まります。
1. ページの frontmatter の `type`/`kind` の値。日本語の別名は、プラグイン共通の `scripts/wiki_text.py:73`（`"会社": "company"`）で英語に直す。別名の表は `SCHEMA.md.template` 117〜124 行にもあり、各 wiki の `SCHEMA.md` に写される。
2. `ontology.yaml` の `node_types[*].maps_from`（`ontology.yaml.template` 13〜23 行、例: `company` ← `type: entity, kind: company`）。
3. ノード ID の既定値 `<node_type>:<slug>`（graph-workflow.md「node_id の形式」）。

ingest をする LLM は、`SCHEMA.md` の規約に従って `kind` を書きます。feature 28 行は `SCHEMA.md` と `ontology.yaml` を「区別する」としています。しかし maintenance の移行の範囲（82〜88 行）に挙がっているのは「定義・正本・参照」だけで、`SCHEMA.md`、ページの `kind` の値、kind の別名の層は挙がっていません。maintenance 25 行は「同義なら統合し、別名を残す」と書きますが、型の別名をどこに持つのかは書かれていません。

問題
- 「company と取引先を統合」「product を product と contract に分割」を適用しても、`SCHEMA.md` の表とプラグイン共通の別名（`会社` → `company`）が古いままだと、どうなるか。採用後の ingest は旧い `kind` を書き続けます。その結果、廃止した型の記録が再び増えるか、新しい型に別名がなく日本語で書けなくなります。
- 別名の対応はプラグインの全 wiki に共通です。wiki ごとのオントロジーで型を改名・統合すると、ある wiki では `会社` が廃止予定の型に解決されてしまいます。maintenance 93 行の「通常の ingest は採用済みの語彙で記録する」は、この層を直さない限り成り立ちません。
- 再分類で `node_type` が変わると、明示した `node_id` のないページは ID も変わります。61 行はこれに触れていますが、`kind` の値と `maps_from` のどちらを直すのかが決まっていません。`maps_from` を直すと、その `kind` のページがすべて一括で再分類されます。これは feature 141 行の「自動の対応付けで既存記事を再分類しない」とぶつかります。

検証方法
1. `wiki_text.py` の kind の別名の表と、`SCHEMA.md.template` 117〜124 行を確かめる。
2. 架空の wiki で `ontology.yaml` の `company` を `organization` に統合したと仮定する。新しい記事を `kind: 会社` で取り込むと、どの node_type になるかを `maps_from` の規則からたどる。
3. maintenance の 47〜66 行と 80〜95 行に、`SCHEMA.md` と kind の別名の扱いが書かれているかを検索する。

修正の方向性
- 型の同一性を 3 層（ページの `kind` と別名、`maps_from`、`node_type`/`node_id`）で捉えることを要件に明記する。
- 再編の差分には `SCHEMA.md` の規約と、型の別名（旧名から新名への対応）の更新を含める。
- 型の別名は wiki ごとに持つことを要件にする。プラグイン共通の別名と食い違うときにどちらを優先するかも決める。
- 「採用後に旧い語で書かれた新しい記事を ingest し、新しい型に解決される」ことを試行と検査の例に加える。
