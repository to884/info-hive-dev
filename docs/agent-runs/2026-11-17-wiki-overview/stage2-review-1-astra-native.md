## 1. 正常に保存された本文のサイズ

図なしで `a` を65,536個並べた下書きを、段階1の公開 API で保存した。check は ok、write は written、現在の状態は fresh だった。
保存後に抽出した本文は65,538バイトになった。書き手が本文の後に改行を2個加えるためである。
抽出した本文に同じ上限検査をそのまま適用すると、正常な既存概要を broken/figures にしてしまう、という設計上の推論が成り立つ。
共通検査が数える本文と、組み立て用の区切りを定義する必要がある。

## 2. 署名を変えない権限喪失

正常に読めた概要をキャッシュした後、一覧取得と lstat は可能なまま、ファイル内容の読み取り権限だけを失う場合がある。
名前・種類・サイズ・更新時刻が同じなら署名も変わらない。既存の get は、署名が同じで transient が空なら中核を返し、読み直さない。
この分岐を模擬入力で動かすと take_snapshot は0回で、同じ中核が警告なしで返った。OS の権限変更そのものを実測したものではない。
既に観測済みの失敗からの回復は再試行できるが、最初の権限喪失の検出まで保証する設計文は広すぎる。
