## 判定

**却下。確信度：高。** PowerShell で引数から別のコマンドを実行でき、下書きの検査にも、合格後に存在しない図を参照する反例がある。SVG の検査についても、依存先の実装が設計の期待を満たしていない。

以下、「設計書」は `docs/plans/wiki-overview-2026-11-17.md`、「ADR」は `docs/adr/0031-wiki-page-overview-lives-in-a-sidecar.md` を指す。

## 致命的・重大な欠陥

### 1. 致命・D：PowerShell の引用符を閉じる文字が禁止されていない

利用者の引数を次にする。

```text
test”; Write-Output SHELL_ARG_EXECUTED; #
```

`”` は U+201D であり、8.1 節が禁じる ASCII の `"`、`$`、バッククォート、`!`、改行のどれも含まない。ところが、PowerShell はこれを二重引用符の終わりとして扱う。

設計どおり引用して、読み取りだけの実験を行った。

```powershell
python -c "import sys;print(repr(sys.argv[1:]))" --page="test”; Write-Output SHELL_ARG_EXECUTED; #"
```

実際の出力は次だった。

```text
['--page=test']
SHELL_ARG_EXECUTED
```

ページの存在確認より前に、後続コマンドが実行される。引数に `=` を付けても防げない。

**根拠：** 設計書 8.1 節、235〜237 行。既存の `wiki/concepts/コマンドの引数の渡し方.md` が採用している許可文字方式とは**食い違う**。

### 2. 重大・D：画像の「数と行き先」の一致では、書き換える行を特定できない

`draft/overview.md` を次にし、有効な `draft/a.svg` を置く。

````text
`
![code](a.svg)
`

text ![real](a.svg)
````

同梱の markdown-it で確認した結果は次のとおり。

- パーサーが見つける画像は、最後の段落の `a.svg` が 1 個。
- フェンス外の画像だけの行は、複数行のコードスパン内にある `![code](a.svg)` が 1 行。
- 数も行き先も一致するため、規定の `image_form` 検査を通る。

6.4 節どおり画像だけの行を作り直すと、書き換わるのは**コードとして表示される行**である。本物の画像は `a.svg` を参照したまま残る。一方、wiki に置く図の名前は `overview-<P>-<C>.svg` なので、参照先が存在しない概要になる。

これは書き込みの中断も同時実行も必要としない。

**根拠：** 設計書 7 節、217・225 行、6.4 節、191 行、ADR「理由」37 行。同梱の `wiki_pages.new_parser()` と `wiki_text.lines_outside_fences()` で**反例を確認した**。

### 3. 重大・B：依存先の SVG 検査は、XML 全体が壊れていても成功する

次の SVG は閉じタグがなく、XML として不正である。

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="720" height="300"><g>
```

別ブランチの現在の実装に渡すと、次を返した。

```text
is_utf8_svg(...) = True
svg_size(...) = (720, 300)
```

標準ライブラリの XML パーサーでは `no element found` になる。

`is_utf8_svg` は文字コードなどを調べる関数であり、`svg_size` は根の開始タグを読んだ時点で解析を打ち切る。したがって、この 2 関数の成功から「UTF-8 の XML として有効な図」とは判断できない。モデルが SVG を途中まで書いた場合でも、設計上の検査を通り、表示できない図が保存される。

**根拠：** 設計書 7 節、222〜226 行、13 節。依存先の  
`C:/Works/info-hive-dev/.claude/worktrees/browse-figures/info-hive-wiki/skills/info-hive/scripts/wiki_browse_core.py` の `is_utf8_svg`（190 行）、`_svg_root_attrs`（220 行）、`svg_size`（251 行）。依存先の現在のコードで**確認した食い違い**であり、将来マージされる版は未確定。

### 4. 重大・C：作業用フォルダーが wiki の外になる保証がない

次の設定は、既存の `data_dir()` がそのまま受け付ける。

```text
INFO_HIVE_DATA_DIR=<WIKI_ROOT>/cache
```

この場合、作業用ファイルは次に置かれる。

```text
<WIKI_ROOT>/cache/overview/work/<wiki_key>/<work_id>/page.md
<WIKI_ROOT>/cache/overview/work/<wiki_key>/<work_id>/draft/overview.md
```

どちらも `wiki_pages.is_page_path()` がページと判定することを確認した。モデルが wiki の中へ下書きを書き、ページの写しと下書きが検索・lint・統計などの入力にもなる。

設計には、この設定を拒否する条件がない。

**根拠：** 設計書 4 節の 1・6、6.1 節の作業場所。  
`info-hive-wiki/skills/info-hive/scripts/wiki_mcp_common.py:47–57`、`wiki_pages.py:49–57`。`data_dir()` が wiki 外を保証するという前提は**成立しない**。

### 5. 重大・B：曖昧な候補から、ルート直下のページを選び直せない

次の 2 ページがあるとする。

```text
foo.md
concepts/foo.md
```

`prepare --page="foo"` は曖昧となり、候補の識別子は `foo` と `concepts/foo` になる。しかし、利用者が `foo` を選び直しても、再び同じ 2 件に当たる。

`foo.md` も同じ結果であり、`/foo` は `clean_link_target()` が先頭の `/` を落とすため区別できない。`./foo` は索引のキーに一致しない。設計の指定方法には、ルート直下の候補を一意に選ぶ表現がない。

**根拠：** 設計書 6.1 節、146〜148 行、8.1 節、239 行。  
`info-hive-wiki/skills/info-hive/scripts/wiki_pages.py:488–538`。実際の `build_page_index()` と `link_candidates()` で**確認した**。既存の wikilink 規則とは一致するが、「候補を示して選んでもらう」という操作が完結しない。

### 6. 重大・C：サイドカーの写像が、ファイルとディレクトリで衝突する

次の 2 ページは、既存のページ判定で両方とも許される。

```text
foo.md
foo.overview.md/bar.md
```

対応するサイドカーは次になる。

```text
assets/overview/foo.overview.md
assets/overview/foo.overview.md/bar.overview.md
```

最初のパスを通常ファイルとして作ると、次のパスでは同じ場所をディレクトリとして使えない。逆順でも衝突する。ハッシュの衝突や NFC の衝突とは無関係であり、どちらかのページの概要を書けなくなる。

**根拠：** 設計書 5.2 節、ADR「置き場所」23 行。  
`info-hive-wiki/skills/info-hive/scripts/wiki_pages.py` の `is_page_path` と `walk_markdown`。既存のページ集合に対して、配置の規則が常に成立するという前提は**崩れた**。

## 崩れる前提

- **禁止した文字以外は、二重引用符の中で安全である。** PowerShell の `”` で崩れる。
- **画像の個数と参照先が一致すれば、同じ画像を照合している。** コードスパン内の行と、段落中の本物の画像を取り違える。
- **SVG の符号化確認と寸法取得が成功すれば、表示できる XML である。** 根の開始タグより後が壊れていても成功する。
- **利用者データの場所は wiki の外にある。** `INFO_HIVE_DATA_DIR` に wiki 内の場所を指定すると崩れる。
- **候補の識別子を渡せば、その候補を選べる。** ルート直下と下位ディレクトリでスラッグが重なると崩れる。
- **ページのパスをサイドカー用に写せば、階層も共存できる。** `.overview.md` で終わるディレクトリがあると崩れる。

## 見落としと軽微な問題

- **軽微：読めない元ページの状態が未定義。**  
  5.5 節は「存在しない」を `page_sha256=None` で表すが、存在していても文字コードや読み取りエラーでハッシュを取れない場合がある。既存の `wiki_lint.collect_pages()` は、その場合も `read_error` 付きのページとして残す。これを `None` にすると `orphan` と誤認し、例外にすると概要検査が lint 全体を止めうる。設計には、この分岐の契約がない。根拠：設計書 5.4〜5.5 節、`wiki_lint.py:335–355`。

- **軽微：`remove` の削除範囲が、予約した名前より広い。**  
  5.3 節は完全な `overview-<16桁>-<12桁>.svg` を概要の図とする。一方、6.5 節の `remove --page` は接頭辞 `overview-<P>-` だけで削除する。`overview-<P>-backup.svg` は予約した形に当たらないのに削除対象になる。

- **軽微：`remove` の中断時の順序が未定義。**  
  6.4 節は `write` の順序だけを定め、6.5 節はサイドカーと図の削除順を定めない。図から削除する実装も記述に反せず、その途中で止まれば参照切れの概要が残る。これは設計の欠落であり、未実装のため実際の順序は確かめられない。

- **軽微：同時書き込みの結果は、単なる後勝ちに限られない。**  
  A・B がそれぞれ図を置き、A→B の順でサイドカーを置いた後、A が「自分の新しいサイドカーが参照しない図」を消すと、B の図を削除できる。11 節で同時書き込みは保証外なので追加の重大欠陥には数えないが、記載された失敗の説明は弱い。

- **軽微：SVG のバイト列について仕様が矛盾する。**  
  6.4 節は「LF、UTF-8、BOM なし」と「下書きのバイト列をそのまま置く」を同時に要求する。依存先の検査は BOM や CRLF を許すため、両方は満たせない。

- **軽微：「常に標準出力へ JSON 1 個」と既存の初期化検査が一致しない。**  
  `require_or_exit()` は未初期化時に標準エラーへ文章を書き、終了コード 1 で終了する。標準出力は空になることを確認した。根拠：設計書 6 節、`wiki_initialized.py:122–128`。

- **軽微：`assets/overview/` がなければ、残った図も検査されない。**  
  9 節冒頭の早期終了に従うと、直下に `overview-<P>-<C>.svg` が残っていても `figure_unused` は空になる。同節の `figure_unused` の条件とは整合しない。

## 検証した事実

| 主張 | 結果 |
| --- | --- |
| 既存のページ走査は `assets/` を名前で除外する | **一致。** 検索、索引、グラフ、統計の走査経路も確認した |
| 8.1 節の制限で PowerShell へ安全に渡せる | **食い違い。** U+201D による後続コマンドの実行を確認した |
| `image_form` が段落内の画像を拒否する | **食い違い。** コードスパンとの取り違えを同梱パーサーで確認した |

対象機能は未実装なので、新しい `write`・`remove`・lint の実行結果は未検証。実験は既存関数の呼び出しとメモリー上の処理で行い、リポジトリのファイルは変更していない。

## 崩せなかった点

- `prepare` が一度読んだバイト列を写しとハッシュの両方に使う構成では、生成中のページ変更を、誤って新しい概要として記録する反例は見つからなかった。
- 単独の書き手で、参照を書き換える処理が正しいという条件では、「図を置く→サイドカーを置き換える→旧図を消す」という順序自体は崩せなかった。
- 既存の `assets/` 除外を使って、サイドカーをページ集合から外す点は崩せなかった。
