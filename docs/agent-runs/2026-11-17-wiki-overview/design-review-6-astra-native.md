## 致命的・重大な欠陥

### 1. 重大・C：`os.replace` の原子性から、電源断後の旧版／新版の存続までは保証できない

**対象：** [設計書249行](C:/Works/info-hive-dev/.claude/worktrees/wiki-overview/docs/plans/wiki-overview-2026-11-17.md:249)、253行、376行、[ADR 38行](C:/Works/info-hive-dev/.claude/worktrees/wiki-overview/docs/adr/0031-wiki-page-overview-lives-in-a-sidecar.md:38)。設計書72行は、ディレクトリの `fsync` を不要と明記している。

規定された操作は、一時ファイルへの書き込みと `fsync`、別ディレクトリへの `os.replace` である。この操作の原子性と、電源断後にもファイル名が残ることは、別の保証になる。

Python の公式文書は、成功した `os.replace` を原子的な操作と説明するが、電源断後の存続までは規定していない。[Python 3.12 `os.replace`](https://docs.python.org/3.12/library/os.html#os.replace)

Linux の `fsync(2)` は、ファイルの同期について、ディレクトリエントリがディスクに到達したことを必ずしも保証しないと明記している。該当箇所は DESCRIPTION の “does not necessarily ensure that the entry in the directory containing the file has also reached disk.” であり、続けてディレクトリへの明示的な同期を区別している。[Linux man-pages `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html)

**具体的な操作順：**

1. まだ概要のないページに、初回の `write` で概要 A を保存し、`written` が返る。
2. ディレクトリの変更が永続化される前に、`--refresh` で概要 B に置き換える。
3. 電源断が起きる。

この設計には、A の名前を確定させる同期も、B の名前を確定させる同期もない。したがって、A と B のどちらの名前も復旧後に存在しない結果を、記載された API の契約から排除できない。「どちらか一方が、壊れずに残る」という376行の保証が成立しない。

**適用範囲と検証の限界：** これは、Linux の一次資料と設計された操作順から導いた保証不足である。電源断を実測した結果ではなく、特定のファイルシステムで毎回消えると主張するものでもない。Windows／NTFS の電源断後の挙動は、今回独立に検証していない。設計は対象 OS・ファイルシステムを限定せず保証しているため、Linux 側だけでも記述は過大である。

## 崩れる前提

- **ファイルを1つにすれば、`os.replace` の原子性だけで、電源断後にも旧版か新版が残る。** 単一ファイル化は本文と図の世代不一致をなくすが、ファイル名の永続化まで保証しない。
- **`prepare` がページを読めたなら、`write` の最後に新旧のハッシュを比較できる。** 生成中の文字コード変更や読み取り権限の変更で、この前提は崩れる。

## 見落としと軽微な問題

### 軽微：`prepare` 後に元ページが読めなくなる場合、`write` の確定状態と応答が未定義

**対象：** [設計書245行](C:/Works/info-hive-dev/.claude/worktrees/wiki-overview/docs/plans/wiki-overview-2026-11-17.md:245)〜251行。関連する契約は155行、189行、238行。

具体的には、正常な UTF-8 のページで `prepare` を終えた後、同じパスのページを UTF-8 で読めない内容に変更し、`write` を呼ぶ。

`write` の手順2は、ページが走査結果にあり、識別子が一致することを確認する。この状態でもファイルは走査に載る。その後の手順には、現在のページの読み取り失敗を処理する分岐がない。一方、最後の応答には、現在のページのハッシュから求める真偽値 `page_changed` が必要であり、155行のハッシュ関数は非 UTF-8 に対して例外を送出する。

記載順に処理すると、サイドカーの置き換えと作業フォルダーの削除が済んでから、成功応答を作れなくなる。先に読み取りを行う解釈も可能だが、保存前に止まるのか、保存済みとして知らせるのかが仕様から決まらない。

**検証の区別：** 非 UTF-8 の入力が既存の正規化関数で `UnicodeDecodeError` になることは実測した。新しい `write` は未実装なので、保存後に例外が発生することを実測したわけではない。指摘は、明記された手順と応答契約の欠落である。

## 崩せなかった点

- `remove --orphan` を `PageState` だけで判定する修正により、元ページのない壊れたサイドカーにも削除経路がある。
- `check` に組み立て後の再解析を含めたため、前回の未閉鎖フェンスの反例は公開前に検出できる。
- `remove` の `removed`／`absent` と終了コードは明記された。
- 本文と SVG が1つのファイルになったことで、別ファイルの所有記録、Git 搬送、図の配置順に関する以前の反例は成立しない。
- 不完全な走査を元ページの不在と扱わず、削除を止める方針は整合している。
- `begin` を要求ファイルへの Write より先に置く手順と、ページ名をシェルへ渡さない方針は崩せなかった。
- 別名ジャンクションは明示された既知の制限であり、新規指摘として数えていない。
- 開発 PC 固有のスキル名や絶対パスを、配布プラグインの必須条件にする記述は見つからなかった。
