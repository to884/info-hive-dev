## 目的と作者の決定

Claude Code プラグイン `wiki` に、ページの内容だけから図を中心にした初心者向けの概要を作る `/wiki:overview` を足す。作者は、概要を1つのサイドカーに置き、SVG もそのファイル内の `svg-figure <名前>` フェンスに埋め込む案 B を採用した。本文からは `![説明](#fig-<名前>)` で参照する。エディターや GitHub では図がソースになることも承認済み。

この設計の対象は「段1：作って wiki に置く側」。browse に差し込む「段2」は別途設計する。段2が未設計であること自体を段1の欠陥と数えず、段1が渡す契約の不足や矛盾を調べる。

- サイドカーは `wiki/assets/overview/<P>.overview.md` の1ファイルで、git に入れる。最終ファイルを書くのは `wiki_overview.py` だけ。
- モデルは走査が除く `wiki/.wiki-cache/overview/work/` に下書きを置く。「wiki の外」という以前の依頼文ではなく、現在の設計書を正とする。
- ページのハッシュで新しさを判断する。概要をページ数、検索、グラフ、統計に混ぜない。
- 下書き検査と組み立て後の再解析を通してから、1つのサイドカーを置き換える。
- ページ名はシェルのコマンド行に埋めず、スクリプトが経路を確かめて返した要求ファイルにモデルの Write で書く。
- 開発PCにだけあるスキル名や絶対パスを、配布するプラグインの必須条件にしない。

## 重点的に崩す点

1. `classify` の優先順と、作成・状態表示・lint・削除から使うときの整合性。壊れたサイドカー、元ページの不在、読めないファイル、不完全な走査、NFC と大小文字、識別子の衝突を扱えるか。
2. 第5回の3件の修正が成立するか。`remove --orphan` をサイドカーの中身でなく PageState で決めること、`check` が組み立てと再解析まで行うこと、`remove` の `removed` / `absent` の出力。
3. `begin`、要求ファイル、`prepare`、`check`、`write`、`status`、`remove` の契約の抜けと矛盾。対象がなくなる・読めなくなる・変わる場合、再試行、下書き・作業フォルダーの片付け、JSON と終了コード。
4. `svg-figure` の解析と図の参照。階層0のフェンス、名前、閉じフェンス、本文とSVGの境界、参照と `figures` の対応、改行と BOM、XML と大きさ、組み立て前後で意味が変わる入力。反例は同梱 markdown-it で確かめる。
5. ファイルを1つにしたことで約束する途中停止・電源断への保証が、実際に使うOS操作から導けるか。経路検査、Windows の再解析点、ハードリンク、綴り、別ボリューム、既存ファイルに関する前提。
6. 現在の走査、lint、検索、グラフ、統計、browse、MCP と整合するか。ADR-0029 に明示的に回した別名ジャンクションは既知の制限として扱い、同じ反例を新規指摘と数えない。ただし、範囲外に置いたことが現在の保証を矛盾させるなら、その箇所を示す。
7. 手引きとコマンドから利用者の要求が伝わるか。仕様だけで成立しない通常の使い方がないか。未実装の機能を実行済みと主張しない。

## 報告

所定の「判定」「致命的・重大な欠陥」「崩れる前提」「見落としと軽微な問題」「検証した事実」「崩せなかった点」の順に報告する。

各指摘に、対象文書の正確な行番号と具体的な入力・状態・操作順を付ける。仕様から導いた反例と実行して確かめた事実を区別し、推測は推測と書く。既知の制限や修正済みの指摘を増やさない。欠陥がなければ「崩せなかった」とする。

重大な指摘には、発生の度合いを A（仕様の矛盾か欠落で実装すれば必ず踏む）、B（日常の使い方で起きうる）、C（まれな時機や名前）、D（作為的な配置が要る）で添える。設計案や修正案は出さず、欠陥と根拠を報告する。
