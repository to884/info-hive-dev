## 判定

**却下。確信度：高。** Windows の `os.stat()` は、識別子が非ゼロのまま内部失敗を隠すため、循環検出をすり抜けます。また、索引の集合には、7 の表にない変更があります。

## 致命的・重大な欠陥

### 1. 【重大】`os.stat()` の内部失敗で識別子の形式が変わり、知らせなしに循環へ降りる

口の表は、Windows の内部失敗を受ける条件として、識別子取得時の `st_ino == 0` を挙げています。しかし、**内部失敗後も `st_ino` が非ゼロで返る経路があります。**

CPython 3.14.6 の `win32_xstat_slow_impl()` は、`GetFileInformationByHandleEx(..., FileIdInfo, ...)` が失敗しても、そのエラーを検査せず処理を続けます。その場合、変換処理は `st_dev` に64ビットの `VolumeSerialNumber` ではなく、別の構造体の32ビットの `dwVolumeSerialNumber` を使います。`st_ino` も非ゼロの値を返せます。したがって、同じディレクトリでも識別子の組が変わります。[CPython の失敗を捨てる分岐](https://github.com/python/cpython/blob/v3.14.6/Modules/posixmodule.c#L2091)、[識別子の変換処理](https://github.com/python/cpython/blob/v3.14.6/Python/fileutils.c#L1027)。

反例は次です。

```text
wiki/
  a.md
  sub/
    b.md
    loop/ → wiki（ジャンクション）
```

`loop` の識別子取得だけで上記の内部失敗が起き、ほかの取得は成功する条件を置きます。例えば、同じ実体への取得結果が次の組になります。

```text
wiki:      (0x1234567800000001, 42)
sub/loop:  (0x0000000000000001, 42)
```

試作へこの戻り値を与えた結果は次のとおりでした。

```text
通常:
  a.md
  sub/b.md

loop の識別子だけ内部フォールバック:
  a.md
  sub/b.md
  sub/loop/a.md

unlistable=[]
unknown=[]
```

`identity()` は `st_ino` のゼロだけを調べるため、形式の変わった識別子を正常と扱います。循環と知らせの契約、および「内側で扱われる失敗が結果を変えない」という W1 が破れます。

この形式差は架空ではありません。今回の Windows 実機で、同じディレクトリへの両 API の正常な取得結果を読むと、ボリューム識別子はそれぞれ `0xeeb6dbfbb6dbc26f` と `0xb6dbc26f` でした。ただし、**ネイティブ API の失敗自体は実機へ注入していません。** 循環の再現は、ソースから求めた戻り値を使うメモリ上の差し替えです。

根拠： [計画:105](/C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:105)、同119・181–186行、[試作の `identity()`](/C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-walk-excluded-dirs/walk_v4.py:82)、同151–165行。探索は外側の `os.stat()` に例外を入れるだけなので、この内部経路には届きません。

### 2. 【重大】索引から通常ファイル以外が消える変更を、許容差として列挙していない

現行の `index_files()` は、`indexes/` の下を `rglob("*.md")` した結果に、通常ファイルかどうかの確認をかけません。新設計は `S_ISREG` に限ります。

**失敗が一度も起きない反例**は、Linux での次の配置です。

```text
wiki/index.md
wiki/indexes/pipe.md  ← FIFO
```

作成手順は `mkfifo wiki/indexes/pipe.md` です。現行関数は FIFO の名前を返し、新設計は返しません。これは、7 の表の「`.md` で終わる名前のディレクトリを返さない」には入りません。

実物の現行関数と試作を、メモリ上で FIFO の種類を与えて比較すると、例外注入なしで次の差が出ました。

```text
現行: ['index.md', 'indexes/pipe.md']
試作: ['index.md']
```

先のないファイルのシンボリックリンクにも、同じ未記載の差があります。

```text
現行: ['indexes/broken.md', 'indexes/ok.md']
試作: ['indexes/ok.md']
```

したがって、第二の約束の「7 の表の違いだけ」は成立しません。FIFO の例は、消失や権限失敗を理由に対象外にできません。

期待値にも、この見落としが残っています。`expected_old_index()` は、新しい集合へ大文字拡張子とディレクトリの差だけを戻します。上の切れたリンクの木では、実際の旧関数が返す `indexes/broken.md` を、旧関数の期待値が含みません。既存の木では、切れたリンクを `indexes/` の下に置いていないため発覚していません。

根拠： [現行 `index_files()`](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_lint.py:137)、[計画の通常ファイル判定](/C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:160)、同223–233・249行、[旧集合の期待値](/C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-walk-excluded-dirs/walk_v4.py:419)。

## 崩れる前提

- **A：「内部失敗後に成功が返っても、識別子取得ならゼロで検出できる」**  
  `FileIdInfo` の取得失敗では、非ゼロの識別子を別形式で返せます。外側への例外注入とゼロ識別子の試験では検出できません。

- **B：「成功した非ゼロの `(st_dev, st_ino)` は、取得経路が違っても同じ形式である」**  
  Windows の32ビットと64ビットのボリューム識別子への切り替えで崩れます。文字列への退避をなくしても、この前提は残ります。

- **C：「旧索引との差は、新しい通常ファイル集合から、列挙済みの二種類だけを戻せば計算できる」**  
  FIFO、ソケット、切れたファイルリンクなどを含む入力で崩れます。`expected_old_index()` がその前提を持っています。

前提 D について、新たな反例は見つかりませんでした。
