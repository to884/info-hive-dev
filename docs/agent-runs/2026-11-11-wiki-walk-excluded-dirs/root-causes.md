## 崩れた前提

5 回のレビューと要望の指摘は、4 つの前提に分かれる。

### A. 標準ライブラリの関数を 1 つ呼べば、失敗は外へそのまま出てくる

いくつもの OS の呼び出しをまとめた関数は、内側で失敗を読み替える。どれが、どの失敗を、どう読み替えるかは、関数と Python の版で違う。

| 回 | 反例 | そのときの対応 | 残ったもの |
| --- | --- | --- | --- |
| 走査 1 回目の重大 2 | `rglob` は、3.10 で `EIO` を送出する。1 版目は、どの `OSError` も飛ばした | エラーの種類で分けた | `rglob` を使わなくしたが、ほかのまとめた関数は残った |
| browse の要望 R3、R4 | `Path.is_file()` は、権限のエラーを、3.12 と 3.13 で送出し、3.14 で偽にする | `pathlib` の入出力をやめ、口を一覧にした | 口の一覧に、`os.path.realpath()` を入れた |
| browse 3 回目の重大 4 | 比べるための `os.stat()` の失敗を、自分のコードが文字列の比較に読み替えていた | 読み替えを 1 か所に通した | ― |
| 走査 2 回目の重大 2 | `os.path.realpath(strict=True)` が、内側の確かめの失敗を握りつぶす | （まだ） | ― |

2 版目は、この前提を「`pathlib` を使わない」と狭く読んだ。崩れているのは、`pathlib` ではなく、**内側でいくつもの呼び出しをして、失敗を自分で扱う関数**の全部である。`os.path.realpath()`、`os.path.samefile()`、`os.walk()`、`Path` の入出力がそうである。`DirEntry.is_dir()` も、リンクの先を調べるときに「ない」を偽に読み替える。

### B. パスの文字列で、同じものかどうか、どちらが先かを決められる

| 回 | 反例 |
| --- | --- |
| Raw 1 回目の重大 4 | `normcase()` が、大文字と小文字を区別するフォルダーの別のルートを同じとみなす |
| Raw 2 回目の重大 1 | 解いたパスの文字列をそのまま比べると、区別しないファイルシステム（VFAT、macOS の既定）で、同じディレクトリを別とみなす |
| browse 3 回目の重大 4 | 識別に失敗したあとの文字列の比較が、`B` と `b` を同じとみなす |
| 走査 2 回目の重大 2 | `\\?\` が付いたパスと付かないパスが、同じ実体なのに別の文字列になる |
| 走査 1 回目の軽微 2、2 回目の重大 1 | 並びの鍵にした文字列（NFC、`\` の置き換え）で、別の名前が同じ鍵になる。順が、鍵の作り方の細部で変わる |

同じかどうかについては、対応のたびに、文字列の比べ方を別の比べ方に替えるか、識別子が取れないときの逃げ道として残してきた。逃げ道が残るかぎり、そこに落ちる経路が次の反例になる。

並びについては、「今と同じ」と書きながら、今の鍵を自分で書き直した。書き直した鍵が、今の鍵と違っていた。

### C. 照らす相手は、自分で書いた写しでよい

| 回 | 反例 |
| --- | --- |
| 走査 1 回目の軽微 3、4 | 試作が、設計の本文の並びの鍵と、名前の判定の順を実装していなかった |
| 走査 2 回目の重大 1 | 「今の実装の写し」が、今の実装と違っていた（`posix_rel()` の `\`） |
| 走査 2 回目の軽微 1 | 探索の決まりが、失敗を入れない実行の結果の「一部であること」と「知らせの下にあること」だけで、正しい結果を言っていない |
| browse 3 回目の重大 4 のあとの自分の確認 | 探索が、文字列の比較に落ちる誤りを見つけなかった。たまたま答えが合っていたからである |
| 走査 2 回目の軽微 2 と重大 2 | 探索が失敗を入れられるのは、差し替えた関数の入口だけである。関数の内側と、一覧の途中には届かない |

比べる相手を自分で書くと、対象と同じ読み違いが相手にも入る。基準を「対象の出力より弱い条件」で書くと、条件を満たす誤った実装が通る。

### D. 別の文書が、こちらの書いたとおりに動く

| 回 | 反例 |
| --- | --- |
| 走査 2 回目の重大 3 | 「たどる間の消失は、browse が 2 回たどって受ける」は、browse の設計書に書かれていなかった |
| 走査 1 回目の重大 1 | browse の印が読む入力（`index_files()`）と、走査が返す集合が、別の関数だった |
| Raw の設計 | 走査の計画の節の番号と、関数の動きを、先取りして書いた。走査の計画が変わるたびに、Raw の設計を直している |

相手の文書がまだ決めていないことを、こちらの正しさの根拠にした。

## 構造を変える案

前提をなくす向きに、4 つを変える。どれも案で、作者はまだ決めていない。

### 1. 口を、内側で失敗を扱わない呼び出しだけにする（A）

- 口を、`os.scandir()`（開く、項目を 1 つ取り出す、閉じる）、項目の `is_symlink()`、`is_dir()`、`stat()`、`os.stat()` だけにする。`os.path.realpath()` を口から外す。
- `DirEntry.is_dir()` は、リンクの先が「ない」ときに偽を返す。これは 2 の読み替えの「ない」と同じ向きなので、口に残す。残す理由を、口の一覧に書く。
- 口に残した呼び出しのそれぞれについて、内側で読み替える失敗がないことを、CPython のソースの箇所を挙げて書く。挙げられない呼び出しは、口に入れない。

### 2. 同じかどうかを、識別子だけで決める。取れなければ「分からない」にする（A、B）

- 同じディレクトリかどうかは、`os.stat()` の `st_dev` と `st_ino` だけで決める。パスの文字列は、どの場合にも比べない。
- 識別子が 0 のとき、`stat` が権限で失敗したときは、「分からない」として、そのジャンクションを `unknown` に入れ、降りない。文字列の比較への逃げ道を、なくす。
- 循環の検出を、解いたパスの祖先をさかのぼる方式から、**道筋の識別子と比べる方式**に替える。ジャンクションを 1 つでも通った道筋では、入ろうとするディレクトリの識別子が、起点からそこまでに通ったディレクトリのどれかと同じなら、降りない。`realpath()` も `dirname()` も要らない。
- 代償が 2 つある。識別子を返さないファイルシステムを先にするジャンクションに、降りなくなる（今は降りる。知らせは出る）。ジャンクションの先が wiki の祖先のとき、今の案は降りないが、この方式は 1 度降りて、その中の wiki には降りない（祖先のほかの中身が、ページとして入る）。どちらも、ページの集合が変わる場合なので、作者が決めることに入れる。

### 3. 並びの鍵を書き直さず、今の関数をそのまま使う（B、C）

- 並びの鍵は、今の `wiki_text.posix_rel()` の戻り値にする。同じ鍵になる名前の順だけを、ディスク上の綴りで決める。鍵を、設計書の文で言い直さない。
- 「今と違う」と挙げるのは、今の鍵が同じになる名前の組の順だけである。NFC で同じになる組と、`\` と `/` で同じになる組の両方が、ここに入る。

### 4. 照らす相手を、実物と、木から計算した答えにする（C）

- **今の実装との照合**は、写しではなく、実物で行う。`info-hive-wiki` の決まったコミット（0.10.0）の `wiki_pages.py` と `wiki_lint.py` を、そのまま読み込んで呼ぶ。
- **探索の答え**を、対象の出力からではなく、木の作りから計算する。試験は、木を「どのディレクトリに、どのファイルがあるか」の表で持つ。N 回目の呼び出しがどの場所への呼び出しかは、差し替えが記録する。失敗を入れたときの正しい結果（ファイルの集合、`unlistable`、`unknown`）を、表と場所から計算し、走査の結果と**等しいこと**を確かめる。「一部であること」では確かめない。
- 対照に、次の 2 つを足す。知らせを 1 つ出して全ページを捨てる実装。識別に失敗したときに文字列の比較へ落とす実装。
- 差し替えを、口の呼び出しの全部に当てる。一覧を開くとき、項目を 1 つ取り出すとき、閉じるときを、別々に数える。
- 口を 1 にしぼると、内側で別の呼び出しをする関数が口になくなるので、差し替えの届かない場所がなくなる。口の一覧にない入出力がないことを、構文木の試験で確かめる（2 版目にもある）。

### 5. こちらの文書は、こちらの約束だけを書く（D）

- 走査の計画は、「たどる間になくなったものは、ないものとして返す。たどる間の変化を受けるのは、呼び出し元である」とだけ書く。browse がどう受けるかは、browse の設計書への参照にとどめ、根拠にしない。
- ほかの文書（Raw の大きさの設計）が走査の計画を指すときは、節の番号ではなく、関数の名前と、返すものの約束を指す。

## 3 版目の前に確かめること

案の 2 は、今まで試していない方式である。設計書を書き直す前に、試作で確かめる。

- 道筋の識別子と比べる方式で、循環の 4 つの形と、輪でない 3 つの形（下を指す、外を指す、別名）が、期待どおりになるか。
- Windows で、ディレクトリごとの `os.stat()` が、識別子を返すか（`DirEntry.stat()` は `st_ino` を 0 で返すことを、2 版目の実測で確かめてある）。ネットワークのドライブや exFAT では、確かめる手段がこの PC にあるか。
- 案の 4 の「木から計算した答え」で、2 版目の試作をかけ直し、文字列の比較へ落とす対照と、全ページを捨てる対照が、どちらも見つかるか。

## 作者に確かめたいこと

- 案の 2 の代償（識別子のないファイルシステムを先にするジャンクションに降りなくなること、wiki の祖先を指すジャンクションの扱いが変わること）を受け入れるか。受け入れない場合は、文字列の比較を逃げ道として残すことになり、前提 B が残る。
- この向きで 3 版目を書くか。ほかの向き（たとえば、循環の検出をやめ、ジャンクションに降りないことにする。作者が決めることの 1 の「ほかの選択肢」）も、前提 A と B をまとめてなくす。Windows でページの集合が変わるが、口は `os.scandir()` と `os.stat()` だけになり、識別の話がすべてなくなる。

### 直し方

- **C**: 答えだけでなく、**走査が呼ぶはずの口の呼び出しの集合と、それぞれの役割**も、木から計算する。失敗を入れない実行で、走査の呼び出しの集合がそれと等しいことを確かめる。失敗を入れたときの答えは、役割から計算する。走査の記録は、どの呼び出しに失敗を入れたかを知るためにだけ使う。3 版目の試作を対照にすると、兄弟への余分な呼び出しが「木から決まらない呼び出し」として見つかる。
- **B**: 今と違ってよい並びを、場合を数え上げずに、**今の関数ごとの鍵で同じになる組の中の順**と規則で書く。照合も、集合が同じで、各位置の今の鍵が同じであることで確かめる。
- **A**: 口の表のどの行にも、内側で扱う失敗と、それが結果を変えない理由を、ソースの箇所で書く。閉じるときの失敗は、走査が閉じる前に一覧を最後まで取り出すので、結果を変えない。示せたので、口に残す。差し替えで閉じるときに失敗を入れることは、意味がないのでやめる。
- **D に近いもの**: 使う側の変更の表に、走査の外に残る OS の呼び出しを書く（`compute_stats()` の `indexes` の確かめ）。

| 指摘 | 確かめた結果 | 残っていた前提 | 及ばなかった理由 |
| --- | --- | --- | --- |
| 重大 1: Windows の `os.stat()` は、Python 3.12 以降、識別子の取得（`GetFileInformationByHandleEx` の `FileIdInfo`）に失敗しても、それを捨てて続ける。そのとき `st_dev` は 64 ビットではなく 32 ビットの値になり、`st_ino` は 0 にならない。同じディレクトリが別の識別子に見え、同じ場所を回る道筋を見逃す。知らせは出ない | 3.12.13 と 3.14.6 の `win32_xstat_slow_impl` と `_Py_attribute_data_to_stat` で確かめた。3.10 の `os.stat()` は、いつも 32 ビットの値を返す（実物で `0xb6dbc26f`、3.14 は `0xeeb6dbfbb6dbc26f`） | A | 4 版目は、口の表の `os.stat()` の行に、内側の読み替えとして「開けないときに一覧の情報で答える」ことだけを書き、識別子の取得の失敗を捨てる分岐を見ていなかった。識別子を取る役割の規則（識別子が 0 なら分からない）は、その分岐の 1 つにしか当たらない。W1 は「示せる呼び出しだけを口に入れる」と決めたが、`os.stat()` は、識別子を取る役割について示せていなかった |
| 重大 2: 今の `index_files()` は、`rglob("*.md")` が返す名前を、種類を確かめずに返す。先のないリンク、ディレクトリへのリンク、FIFO も返す。4 版目は、ふつうのファイルだけを返すので、違いの表にない違いが出る | Windows（先のないリンク、ディレクトリへのリンク）と Linux（加えて FIFO）の実物で確かめた | C | 試作の `expected_old_index()` は、今の集合を、新しい集合から挙げた 2 つの違いを戻して作っていた。今の関数の規則から、木の上で直接計算していなかった。違いの表に挙げた場合しか、照合が見られなかった |

### 直し方

- **A（重大 1）**: 識別子を取る役割を、`os.stat()` から外す。案は 3 つあった。作者は 2026年11月11日に案 1（Win32 から直接取る）に決めた。5 版目は、それで書いた。
  - 案 1: 識別子を、Win32 の呼び出しから直接取る（`ctypes` で `CreateFileW`、`GetFileInformationByHandleEx(FileIdInfo)`、`CloseHandle`）。どの失敗も `OSError` で受け取る。ジャンクションは Windows にしかないので、識別子を取るのも Windows だけである。[file_id_probe.py](file_id_probe.py) で、3.10 と 3.14 で働くことを確かめた（ジャンクションを通しても同じ識別子になる。ないパスで `FileNotFoundError`、拒まれるパスで `PermissionError` になる）。口に入れるのが自分の関数になるので、W1 を、内側の読み替えのない呼び出しで満たせる。`FileIdInfo` を持たないファイルシステムでは、「分からない」として降りない（作者が受け入れた代償と同じ）。
  - 案 2: ジャンクションに降りない。識別子が要らなくなる。Windows でページの集合が変わる（作者は 2026年11月11日に採らなかった）。
  - 案 3: 限界として書く。一時的に `FileIdInfo` の取得が失敗すると、同じ場所を 1 周余分にたどり、知らせなしに重なったページを返すことがある。W1 を弱めることになる。
- **C（重大 2）**: 今の集合を、今の関数の規則（`index.md` がファイルなら、そのあと `indexes` を起点に `rglob("*.md")` が返す名前のすべて）で、木から直接計算する。違いの表は、「索引の側で、ふつうのファイルでない名前を返さない」と規則で書き、作者が決めることの 3 に含める。

### 4 回のレビューを通して

レビューのたびに、前提 A は、より奥の呼び出しで見つかった。`rglob`、`Path.is_file()`、`realpath()`、`scandir` を閉じるとき、`os.stat()` の識別子の取得である。どれも、標準ライブラリの関数が、内側で失敗を別の結果に読み替えるものだった。「どの呼び出しが内側で何を読み替えるか」を、ソースで 1 つずつ確かめて塞ぐやり方では、確かめ漏れが次の反例になる。案 1 は、識別子という、循環の検出の正しさが直接かかる値だけは、読み替えの入らない自分の関数で取る、という向きの直しである。残る口（`os.scandir()`、項目の 3 つの問い合わせ、ファイルかどうかを見る `os.stat()`）は、読み替えがあっても、結果は「ない」か「ファイルである」の向きにしか変わらず、その向きは設計が受けている。

## 5 版目の前に、自分で見つけたこと

5 版目を書いたあと、レビューに出す前に、失敗を入れずに作れる木で、今の実装との違いを探した。重大な後退が 1 つ見つかった。

**自分を指すシンボリックリンクが 1 つあるだけで、5 版目は走査ごと送出する。** 今の実装は、そのリンクを飛ばして、ほかのページを返す。Windows の 3.10、3.12、3.14 と、Linux の 3.12 のすべてで確かめた（[results.md](results.md) の最後の節）。lint、search、MCP の索引が、輪になったリンクが 1 つあるだけで止まる。

原因は、`DirEntry.is_dir()` と `os.stat()` が、輪になったリンクで `OSError`（Linux は `ELOOP`、Windows はエラー 1921）を送出し、5 版目の読み替えが、それを「そのほか」として送出することである。今の実装は、`pathlib` の `_ignore_error` で、その失敗を無視している。

| 今の実装が「ない」と読む失敗 | 3.10〜3.12 の `pathlib` | 3.14 |
| --- | --- | --- |
| errno | `ENOENT`、`ENOTDIR`、`EBADF`、`ELOOP` | どの `OSError` も（`glob` と `os.path.isfile` が、すべて無視する） |
| Windows のエラー | 21（`ERROR_NOT_READY`）、123（`ERROR_INVALID_NAME`）、1921（`ERROR_CANT_RESOLVE_FILENAME`） | 同上 |

### 崩れた前提

**E. 失敗は、障害のときにだけ起きる。** 5 版目の失敗の分け方（ない、権限、そのほか）は、「そのほか」を障害とみなして送出する。しかし、失敗の中には、木の状態として、障害なしに必ず起きるものがある。輪になったリンク（`ELOOP`、1921）、正しくない名前（123）、準備のできていないドライブを指すジャンクション（21）である。これは、前提 D（別の文書がこちらの書いたとおりに動く）の裏返しでもある。今の実装が何を「ない」と読むかを、ソースから表にせずに、こちらの分け方を決めた。

### 直し方の案

作者は 2026年11月11日に、次の推奨どおりに直すと決めた。6 版目は、それで書いた（設計の「決めること」の 2 の表）。長いパスは、この PC（`LongPathsEnabled` が 1）では、今の実装も 6 版目も返した。無効な環境は確かめていない。

- 失敗の種類ごとに、今の実装がどう扱うかを、ソースから表にする（上の表）。設計の「決めること」の 2 の表と並べ、行ごとに「ない」「分からない」「送出」を決める。推奨は次のとおりである。
  - 解けないリンク（`ELOOP`、1921）と、正しくない名前（123）: 「ない」。先のないリンクと同じく、ページにならない。今の実装と同じである。
  - 準備のできていないドライブ（21）: 「分からない」。中身があるかどうかが分からないからである。今の実装は「ない」にしている。
  - `EBADF`: 「分からない」。木の状態としては起きないはずで、起きたら障害だが、今の実装が無視しているので、送出はしない。
  - そのほか: 今のとおり送出する（3.14 の今の実装は無視するが、障害を索引の削除に変えないため）。
- 木の表に、「解けないリンク」（自分を指すリンク、互いに指し合うリンク）の種類を足す。答えの計算では、先のないリンクと同じに扱う。
- 探索が入れる失敗の種類を、上の表の行から取る。今は 3 つ（ない、権限、`EIO`）だけである。
- 同じ表で、Windows のパスが長すぎる場合（エラー 3、206 が `FileNotFoundError` になるか）も確かめる。そうなら、実在するページが知らせなしに「ない」になる。今の実装も同じだが、限界として書く。
- W1 の境界を書く。W1 が見るのは CPython の内側までで、`win_file_id()` が呼ぶ Win32 の API の内側と、たどる間に木が変わることは、対象の外である。

### 収束の状況

重大な指摘の数は、1 回目から 2、3、3、2 件だった。指摘は、回を追うごとに狭く、奥の呼び出しになっている。しかし判定は 4 回とも却下である。どの条件でレビューを止めるかを、作者に決めてもらう。たとえば、「確かめた OS と版で、第一と第二の約束を破る反例が出なければ、残りの指摘は限界として書いて、承認に回す」という条件である。

## 5 回目のレビュー（[design-review-5.md](design-review-5.md)、6 版目、却下）と、止める条件

5 回目は、また別の Sol のセッションに頼んだ。作者は、このレビューに止める条件を付けた。「確かめた OS と Python の版で、第一と第二の約束（失敗のないときの約束）を破る反例が出なければ、残りの指摘は限界として書いて、承認に回す」である。

### 判断を作者に戻す

作者の条件どおりに読むと、止める条件に当たる反例はない。残りは限界として書いて、承認に回す。ただし、重大 1 は、設計書の口の表に誤った説明（W1 を満たしているという主張）を残す。小さく直せる案がある。

- **重大 1 の案**: Windows で、一覧に載った項目に `os.stat()` が `S_IFBLK` を返したら、「分からない」として `unknown` に入れる。一覧に載る項目がボリュームや物理ディスクであることはないので、`S_IFBLK` は、この読み替えの分岐からしか出ない。口の表の説明も、それに合わせて直す。
- **重大 2 の案**: 限界として書く（たどる間に木が変わる場合で、確かめていない環境でもある）。直すなら、`is_symlink()` と `is_dir()` をやめ、項目の `stat(follow_symlinks=False)` と、リンクの先の `os.stat()` で種類を決める。どちらも失敗を読み替えない。ただし、試作と探索を作り直すことになる。
- **軽微の案**: 記述を直す。
