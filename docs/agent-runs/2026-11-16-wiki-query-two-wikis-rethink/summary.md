# 2 つの wiki を引く問い合わせの設計の見直し の総括

## 推奨

分離の確かめを、エージェントが呼ぶ補助から、2 つの根を受け取る読み手（MCP の新しいツールと CLI）の中に移す。ただし、比較の範囲は 14 版目のまま（記事、降りたディレクトリ、`graph/`、MCP の索引、`.wiki-cache/` の下全体）を両側で対称に保ち、入力と正規化後の実体の一致検査も残す。書かれたままで相互レビューに耐えた成果は 1 つもないので、この推奨は 4 体の原則と攻撃から出た条件の合成であり、15 版目として書いたうえで Sol のレビューにかける必要がある。

## 批評で動いたこと

- **4 体とも結論の一部を改めた。** A は、比較から外した `graph/` を戻し、raw の読み口を足した。B は、`SCHEMA.md` と `log.md` の読み口の欠落と N2（他方の `raw/` などを一方の記事の場所に bind mount する配置）を限界に足した。C は、自分の案も「無条件の実体分離」としては耐えないと認め、保証を対象集合・経路・時点に限定した。D は、CLI 側の比較範囲が自案でも明確でないと認め、自案の推奨を保留した。
- **最も鋭い反論は D の A-1 で、決定的だった。** 同じ実体が一方では記事、他方では派生データになる配置（`U/concepts/policy.md` に `P/graph/ontology.yaml` をファイル単位で bind mount）では、派生データを比べない案（A）は `disjoint` を返し、他方のオントロジーの中身を記事の本文として返す。A が相互レビューで出した修正（`graph` の操作のときだけ `graph/` を比べる）でも閉じない。14 版目はこの配置を検出するので、範囲を狭める案は 14 版目からの後退である。同じ論理は B の読み手ごとの非対称（CLI は `.wiki-cache/` だけ、MCP は索引ディレクトリだけ）にも当たる（D の B-1）。これらは仕様からの導出で、実 OS では未再現である。
- **次に効いた 3 件。** (1) C と D が独立に指摘した、1 回だけ正規化する形は、NFC 前後の名前が別のディレクトリのときに未登録の第三の wiki を開く（C は実関数とメモリ上のモデルで確認）。消せるのは再正規化の不動点だけで、入力の実体と正規化後の実体の一致は残さねばならない。(2) C が実関数で確認した、CLI の既存引数 `--db` は比べた場所と別の DB を開く。検査するパスと開くパスを同じ値から得る条件が要る。(3) C と D が独立に見つけた、14 版目が正規化後の `roots` だけを渡す規則は、ADR-0029 の実装の設計 160 行（利用者が書いたままの綴りと解決した根の両方を渡す）と食い違う。A と B がファイルで照合して一致を確認した。これは 14 版目への新しい反例である。
- **反証されずに残った注意。** B は、4 体の収れんが依頼文の例（記事を読む MCP のツールに 2 つの根を渡す）に乗った結果である可能性を挙げた。`--both` を MCP だけに限る案や、初期化時に wiki の識別子を書いて読み手が照らす案は、どの成果も本気で展開していない。

## 推奨案が残る理由

- **確かめる者と読む者を同じにする構造は、4 体の攻撃で崩れなかった。** A の分類では、6〜8 回目の共有に関わる重大の 3 件が「確かめる者と読む者が別」、1 件が「開くものの数え上げ」から出ている。B の分類でも写しのずれが 7 件で最多である。識別子の比べ方そのものは 3〜7 回目で崩れていない。相互レビューで「崩せなかった点」として 3 体以上が独立に確認したのは、新しいツール名で古いサーバーを止めること（B が mcp 1.30.0 の `func_metadata.py` で知らない引数が捨てられることを確認、A が同じファイルで一致を確認）と、`State.wiki()` より前に確かめること（`WikiIndex` のコンストラクターが `wiki.json` を書き、`WriterLock` を取ることを A、B、C、D が確認）である。
- **比較範囲を保つ根拠は 3 つあり、どれも反証されていない。** D の A-1 と B-1（役割はパスごとに決まる）、B が引いた ADR-0029 の I7（bind mount の共有は問い合わせの設計が識別子で見つける、と明記。確認済み）、C が実関数で確認した、ハッシュが一致しても解析キャッシュが本文とメタデータを供給しうること。A の「派生データは順位しか変えない」は無条件の事実としては成立しない。
- **すべての読み取りを入口に通す必要は、A の F-a で確定した。** `commands/query.md` の 14、15、19 行は読む道具を指定せず、`SCHEMA.md`、`index.md`、`log.md` は `wiki_pages.py:36` でページから外れ、`get_page` では読めない。B が一致を確認した。`SCHEMA.md`、`log.md`、`ontology.yaml`、索引、ページ、被リンク、グラフを入口の操作にする。これにより、エージェントの義務は「2 つを引く間は wiki のファイルを入口以外で開かない」に集約される。
- **14 版目を続ける案は、却下ではなく選択肢として残る。** 8 回目の重大は度合い C と D で、リポジトリの規則では作者に聞く段階にある。ただし続ける場合も、F-a、`roots` と `resolve_raw()` の綴りの食い違い、補助とサーバーのデータの場所の環境差（推論）の 3 点は直しが要り、いずれも補助が読み手の写しを持つことから出ている。

## エージェントごとの要約

**エージェント A** は、読み手に確かめを移す案 B を推し、比較範囲を記事・ディレクトリ・根に絞って派生データを外した。8 回の崩れを「代用品」「確かめる者と読む者が別」「数え上げ」の 3 種に分けた分析と、F-a（`SCHEMA.md`・`log.md` に読み手がない）、F-f（`stats` の版はディスクから計算する）の事実は有効で、他の 3 体が一致を確認した。当たっていた指摘は、D の A-1（記事と派生データをまたぐ同一実体）、C と D の正規化による登録先の変更、B の `.wiki-cache/` の bind mount とハードリンクで他方に書く経路、`graph/` の共有で `evidence` の文が返ること、`os.stat()` の識別子で足りるとした費用の見積もり（`wiki_pages.py:121-122` が否定）、raw と ontology の読み口の欠落、索引を開く順の未記述である。A 自身は graph と raw を戻したが、A-1 は残る。

**エージェント B** は、`_both` の 4 ツールと CLI の `--other` を推し、新しいツール名の根拠を FastMCP のコードで確認し、`State.wiki()` の前に確かめる順序と `WriterLock` の衝突を明記した。17 件の重大の分類表は有用である。当たっていた指摘は、D の B-1（CLI 側が他方の MCP 索引を比べず、`parse-cache.json` を記事として読む配置を見逃す）、D の B-2（MCP が使えないとき索引とページを読む CLI の入口がない）、C の `--db`（既存引数が比べた場所と別の DB を開く）、A の `SCHEMA.md`・`log.md`・raw を Read に残したこと（B 自身が読み口の欠落と認めた）、経緯の数え方の不整合である。

**エージェント C** は、両根を必須とする専用入口 `pair_read` を推し、14 版目の比較範囲を残し、元の綴り・解決後の根・識別子の 3 値を保持する形を書いた。14 版目の `roots` と `resolve_raw()` の食い違い、補助とサーバーの環境差（推論と明記）は新しい有効な指摘である。相互レビューでは実関数とモックで `--db`、正規化、解析キャッシュを確認し、根拠の質が最も高かった。D は確定した重大を示せず、A と B は条件付き採用とした。当たっていた指摘は、「計画にない場所を開いたら失敗させる」に実装の当てがないこと（A）、案 A を批判した再帰走査の止まり方を自案も引き継いでいること（A）、実装量 800〜1,600 行に内訳がないこと（B）、サーバーで raw を読むと任意の絶対パスを読む口になること（B）、N2 の未記載（B）である。

**エージェント D** は、共通の読み取り層を推し、保証を「現在の配置の分離」「読み取りの一致」「出典の正しさ」に分けて識別子で守れるのは前 2 つだけと限った。依存先の宣言を開くコードと同じ箇所に置く条件、順序、元の綴りの保持、ontology を Read に残さない点は、A と B が崩せなかった。当たっていた指摘は、実装量を「中〜大」とだけ書いたこと（A、B）、既存索引の作り直しが `WriterLock` と裏の埋め込みスレッドと衝突すること（A）、「検索の候補の本文を読み直す」仕組みが見出しの道筋と本文で版が食い違う行を生み、問いの外の仕組みであること（B。未反証なので合成には入れない）、保存データの宣言がファイル名の数え上げに戻る小さな形（A）である。D 自身は、CLI 側の比較範囲が自案で明確でないとして推奨を保留した。

## 残るリスクと未確定事項

- **14 版目を続けるか、15 版目で作り直すか。** 続けるなら、F-a、綴りの食い違い、環境差の 3 点を直し、レビューを止めた状態で進める。作り直すなら、上の合成を 15 版目として書き、Sol のレビューにかける。wiki の記録では、作り直しの直後に度合い A の指摘が出やすい。
- **raw をどこで読むか。** サーバーの入口で読むと、`raw:` が wiki の外の任意の絶対パスを指せるので、サーバーが任意のファイルを読む口になる（B の指摘、未反証）。Read に残すと、リンクの raw で `resolve_raw()` の拒否を迂回する（A の指摘）。読む範囲を wiki と raw の根の下に限るか、Read に残して限界として書くかを決める必要がある。
- **派生データの比較範囲と費用。** 対称に保つと、呼び出しのたびに 2 つの wiki の走査と、中身が動く索引ディレクトリ（30 秒ごとの `vectors.usearch.tmp`）の走査が入る。断続的に `null` になる懸念（A）は推測で、測定が要る。`graph/` の下の大きな木へのジャンクションで止まる問題は、ADR-0029 の作者の決定 9（記事でないリンクだけでは止めない）との関係を書く必要がある。検査結果の使い回し（C の案 C）は失効管理の状態を増やすので、測る前には足さない。
- **決定 8 の読み方。** 「補助を足す」を、エージェントが呼ぶ CLI に限るなら、読み手の部品として置く案は採れない。4 体とも文面に制約がないと読んだが、作者の確認が要る。
- **CLI の戻り道を残すか、`--both` を MCP だけに限るか。** 残すなら、CLI にも索引・ページ・規約・ログの読み口が要り、`--db` などの既存引数は `--other` と併用できないようにする。MCP だけに限るなら、決定 4（CLI のキャッシュ）の前提が外れ、`.wiki-cache/` の比較と書き込みが消えるが、MCP が使えないときは 1 つずつの問い合わせになる。
- **実装量。** 見積もりは成果間で 2〜4 倍割れており（A：合わせて 400〜700 行、B：480〜640 行、C：800〜1,600 行、D：見積もりなし）、どれも根拠が薄い。入口の操作の範囲を決めたあとに、部品ごとの内訳を出す必要がある。
- **どの案でも残る限界。** N2、記事と `graph.sqlite` をハードリンクで結ぶ作為的な配置（C）、問い合わせ中の配置変更、MCP の古い本文（署名はパス・大きさ・更新時刻のみ）、識別子の限界、外の原本、エージェントが入口を使わないこと。これらは「保証しないこと」として ADR か設計書に書く。
- **他セッションとの競合。** 親リポジトリの origin/main は PR #158 まで進み、この worktree の基点より先にある。`info-hive-wiki` の origin/main は v0.25.0 で、引用したスクリプトに差分はないが、文書の言い回しが変わっている。マージの前にリベースと「事実の版」の書き直しが要る。
