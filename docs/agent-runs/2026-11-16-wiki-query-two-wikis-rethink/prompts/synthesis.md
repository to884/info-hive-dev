## 結論

**前提を変えます。** 共有の確かめを、補助（`wiki_roots.py`）とエージェントの手順から外し、**記事を読む読み手そのもの**に移します。読み手は、読むのと同じ呼び出しの中で、自分が開いた根、降りたディレクトリ、読んだ記事の実体の識別子を、同じ呼び出しで走査したもう一方の wiki の識別子と比べます。重なれば本文を返しません（以下、案 B）。

- **読み手の形。** 2 つを引く問い合わせの読み取りは、すべて 2 つの根を受け取る読み手を通します。MCP の新しいツール `pair_read`（仮）と、CLI の `wiki_pair.py`（仮）です。
  - どちらも、根を登録の文字列のまま受け取ります。そろえ方は MCP と同じ `normalize_wiki_root()` で、自分で 1 回だけそろえます。
  - 古いサーバーや古いプラグインには、このツールもスクリプトもありません。そのため、ADR-0029 の実装が入っているかは、結果の欄ではなく、道具があるかで決まります。古い道具を呼べば失敗して止まります。
- **比べる範囲。** 比べるのは、記事、走査が降りたディレクトリ、根の 3 つに絞ります。派生データ（MCP の索引、`.wiki-cache/`、`graph/`）は比べません。
  - コードで確かめると、派生データが変えるのは検索の順位と候補だけです。回答に使う本文は、いつも記事のバイト列から作られます（根拠の F-b）。

  - 8 回目の重大 2 は「保証しないこと」に移ります。この範囲の絞り方は、作者の判断が要ります。
- **残すもの。** 14 版目の識別子の比べ方は残します（`same`、`shared`、`key_collision`、`null`、`disjoint` の判定、識別子の取り方、確かめられなければ止めること）。この比べ方は 3〜7 回目で崩れていません。登録をスコープごとに読むこと、どちらにも書かないこと、出典を wiki ごとに分けること、定型文、ADR-0029 に頼ること、作者の決定 1〜12 もそのまま残します。
- **消えるもの。** 根のそろえ方の不動点、`link_warnings` の欄で読み手の版を確かめること、記事でない 3 つの場所の数え上げ（リンクをたどって下をすべて集める形）がなくなります。
- **エージェントの義務。** 14 版目では少なくとも 5 つありました。補助を呼ぶ、`roots` を全部の呼び出しに渡す、結果ごとに欄を見る、拒んだ記事を使わない、ページを `get_page` で読む、です。案 B では 1 つになります。「wiki を読む呼び出しを、すべて 2 つの根の形にする（Read、Grep、Glob で wiki のファイルを開かない）」だけです。

**推奨する理由。** 8 回の崩れを種類で分けると、次のようになります。

- 代用品で確かめた形（1〜5 回目）は、識別子の比較という構造の変更で閉じ、そのあと出ていません。
- 書き込みの数え上げ（1 回目）も、「書かない操作」にする構造の変更で閉じ、そのあと出ていません。
- 繰り返し崩れたのは、確かめる者と読む者が別であること（6 回目、7 回目、8 回目の 1）と、読み取りの数え上げ（3 回目、8 回目の 2）の 2 種類だけです。どちらも、補助の中に読み手の写しを持つ作りです。14 版目は、この写しをさらに 2 つ足しました。

  - 回る道筋の止め方という、新しい端ができる。
- **変えるファイルと量。** `wiki_roots.py`（新規。【推測】300〜450 行）と試験（第 4 節の一覧。【推測】500〜700 行）、手順の文書 9 つ程度（第 4 節の表）です。F-a の直しで、`query-workflow.md` と、`SCHEMA.md` を読む口が増えます。
- **費用（式）。** C_A ＝ T_proc ＋ Σ_W (N_W ＋ D_W ＋ M_W)・c_id ＋ k・walk(1 つの wiki)。
  - N_W は記事の候補の数、D_W は降りたディレクトリの数、M_W は 3 つの場所の下の項目（リンクの先を含む）の数です。
  - c_id は識別子を 1 つ取る費用で、Windows ではファイルを開きます。
  - k は読み手を呼ぶ回数、T_proc は補助のプロセスの起動です。
- **作者の決定と ADR-0029。** 決定 1〜12 をそのまま満たします。決定 9 は、記事でない場所を 3 つに絞ることで満たします。ADR-0029 の I7（2 つの wiki の共有は識別子で見つける）も満たします。

#### 案 B（推奨）：読み手が確かめる

- **中身。**
  - **誰が。** 記事を読む読み手そのものです。MCP の新しいツール `pair_read`（仮）は、引数に `user` と `project` の 2 つの根、読む側の `target`、`command` を取ります。`command` は `query`、`get_page`、`list_index`、`article`（`SCHEMA.md`、`log.md`）、`graph` です。CLI の `wiki_pair.py`（仮）は、同じ `command` に `backlinks` を足します。どちらも同じプロセスで、同じ部品を呼びます。部品は、14 版目の補助の比べ方を移したものです。
  - **いつ。** 呼び出しのたびに、読むのと同じ呼び出しの中で確かめます。
  - **何を（根）。** 2 つの根を、登録の文字列のまま `normalize_wiki_root()` で 1 回だけそろえます。MCP も CLI も同じ関数を使います。
  - **何を（識別子）。** 両方の wiki を ADR-0029 の走査でたどり、根、降りたディレクトリ、記事の識別子を集めます。読む側では、実際に開いた記事のハンドルから識別子を取り、走査で集めたものと同じかを照らします（F-d の、走査と読み取りの間の置き換えへの手当て）。
  - **何を（判定）。** 根が同じなら `same`、`wiki_key()` が一致すれば `key_collision`、識別子が重なれば `shared` です。調べられない項目があるか、識別子が取れなければ `null` です。どれでも本文を返さずに失敗します。`disjoint` のときだけ、本文、`relation`、`link_warnings` を返します。
  - **索引の署名。** MCP の索引の署名に、識別子を足します（F-h）。
  - **派生データ。** 検索の順位とグラフの行は、候補を選ぶ手がかりにだけ使います。回答の前提はいつも、`pair_read` で読んだ記事です。
  - **任意。** `query` と `list_index` は、1 回の呼び出しで 2 つの wiki の結果を `{user: …, project: …}` の形で返すこともできます。順位を混ぜないこと（第 3.3 節）が構造の上で守れ、呼び出しの数も減ります。
- **守れること。**
  - 読み手が実際に読んだ記事が、同じ呼び出しで集めた他方の根、ディレクトリ、記事と同じ実体でないこと。入れ子、bind mount、`subst`、同じボリュームの別のパス、ファイルの bind mount を見つけます。
  - 確かめと読み取りで、版、そろえ方、走査が同じであること。同じプロセスの同じ関数なので、構造の上でそうなります。
  - 古い読み手を呼べないこと。古いサーバーにはツールがなく、古いプラグインにはスクリプトがなく、CLI は知らない引数で止まります（F-g）。
  - 呼び出しの間に配置が変わっても、次の呼び出しで確かめ直すこと。
  - 【推測】共有していた配置を外したあとに MCP が返す古い本文。置き換えた記事は識別子が変わるので、署名が変わって読み直します。同じ実体の上書きで大きさと時刻を戻した場合だけは残りますが、そのときの中身は一方の wiki 自身の前の版です。
- **守れないこと。**
  - 2 つの根の形を通らない読み取り（Read、ふつうの `get_page`、2 つ目の根の渡し忘れ）。
  - 派生データの共有による、順位と候補の誤り。
  - 1 つの呼び出しの中で、他方を走査したあとに起きる変化。
  - N2。
  - 識別子の限界（ネットワークのドライブ）。
  - 外の raw。
  - 登録の読み違い。
- **新しく生む失敗の形。** 直しで足す仕組みごとに、表に並べます。

  | 足す仕組み | 生みうる失敗 | 手当て |

  - `info-hive-wiki` のコード:
    - `wiki_pair.py`（新規。部品と CLI。`SERVER_FILES` に入れる。【推測】250〜400 行）

- **費用（式）。** C_B ＝ Σ_{i=1..k} [walk(target_i) ＋ walk(other_i) ＋ (N_A ＋ D_A ＋ N_B ＋ D_B)・c'_id]。
  - walk は、`refresh()` のたびに既に走る走査（`wiki_index.py:815-852`）です。

#### 案 C：2 つを引く読み取りを、CLI の 1 つのスクリプトに限る

- **中身。** 案 B の `wiki_pair.py` だけを作り、2 つを引く問い合わせでは MCP を使いません。誰が、いつ、何を確かめるかは、案 B と同じです。
- **守れること。** 案 B と同じです。CLI は毎回ディスクの今の版で動くので、版の問題が初めから起きません。
- **守れないこと。** 案 B と同じものに加えて、MCP の意味の検索が使えません。CLI の意味の検索は uv の依存を使い、モデルが違い、`.wiki-cache/` に書きます。語彙だけにすると、`query-confidence.md` の「検索の縮退」の上限が当たります。
- **新しく生む失敗の形。**
  - 呼び出しごとにプロセスを起動し、意味の検索ではモデルを読み込むので遅い。
  - 使える MCP のツールで、エージェントが読んでしまう（義務は案 B と同じ 1 つ）。
- **変えるファイルと量。** `wiki_pair.py`、`wiki_pages.py`、文書です。MCP と `SERVER_FILES` は変えません。【推測】案 B より、コードで 100〜200 行少なくなります。
- **費用（式）。** C_C ＝ Σ_i [T_proc ＋ walk(A) ＋ walk(B) ＋ 解析（キャッシュで軽くなる） ＋ 検索（意味の検索ならモデルの読み込み）]。
- **作者の決定と ADR-0029。** 決定は変えません。第 3.3 節の「MCP の `query` を wiki ごとに呼ぶ」は提案なので、変えられます。決定 4（CLI のキャッシュを書く）とも食い違いません。

### 4. 案 B を推す理由

1. **繰り返し崩れた 2 種類を、構造で断てる。** 乙と丙（読み取り）は、補助の中に読み手の写しを持つ作りから出ていました。そろえ方、版、開く場所の一覧の 3 つです。wiki の「照合の中に実物の写しを作らない」「実物に尋ねる」（`wiki/concepts/敵対的レビューで設計を直す進め方.md`）と同じ直し方で、YouTube の字幕の実装でも、この形にするとその種類の指摘は出なくなりました。この設計の中でも、1 回目の書き込みの指摘を「書かない操作」という構造で直したら、二度と崩れていません。
2. **崩れなかった部分を残せる。** 識別子の比べ方は、3〜7 回目で崩れていません。案 B は比べ方を残し、置き場所だけを変えます。
3. **8 回目の重大 2 は、中身の取り違えではない。** F-b のとおり、派生データの共有で変わるのは順位と候補で、回答に使う本文は記事から来ます。比べる範囲から外せば、数え上げの一覧そのものが要らなくなります。ただし、グラフは手順の規則による保証です（F-c）。
4. **エージェントの義務が減る。** 5 つ以上から 1 つになります。規則がエージェントに届くかは、文書のレビューでは確かめられません。Sonnet 5.5 で 33 回流したとき、規則の正本を開いた回は 0 回でした（同じ wiki ページ）。義務の数を減らすほうが、文書を正しくするより効きます。
5. **案 A を続けない理由。** 8 回目の重大は度合い C と D で、リポジトリの進め方では「限界として書き、作者の判断に回す」段階にあります。これは案 A の強い理由として認めます。それでも変えるのは、次の 2 つのためです。
   - F-a は、記事のリンクがあれば必ず踏む仕様の欠落で、案 A のままでも直しが要ります。
   - 13 版目と 14 版目の直しはどちらも写しを足す形で、毎回その端から次の指摘が出ています。
6. **案 C より案 B を選ぶ理由。** 2 つを引く問い合わせでも、MCP の意味の検索が使えます。版の確かめは、ツールの有無で決まるので、案 C とほぼ同じくらい確かです。部品は同じなので、案 C を先に入れてから MCP のツールを足す順にもできます。

## 検討した代替案

- **案 A（14 版目を続ける）。** 理由は根拠の 4 の 5 に書きました。F-a の直しと、写しを足し続けることが残ります。
- **案 C（CLI だけで読む）。** 最初の一歩としては有力です。主な形にしない理由は、MCP の意味の検索を使えず、検索の縮退の上限が当たりやすいことです。
- **今のツールに、2 つ目の根の引数を足す。** 古いサーバーが知らない引数を黙って捨てるかを、確かめていません（FastMCP の扱いは未確認）。捨てるなら、確かめのない結果が返ります。新しいツール名なら、確かめなくても古いサーバーでは止まります。
- **サーバーに版を聞く（`stats` の `server.version` など）。** F-f のため、場所を変えずに更新した古いサーバーを新しいと見ます。
- **他方の木のすべてと比べる（読んだもの(A) ∩ 全部(B)）。** N2 も見つかります。ただし、B の `.git/` や `raw/` まで毎回走査する費用がかかります。また、A の部分木を B の `assets/` に bind mount した配置のように、B が読まないものでも止まり、作者の決定の 9 の趣旨から外れます。作者が N2 も閉じたいときに選ぶ延長として残します。
- **派生データの共有も止める（14 版目の範囲を保つ）。** 案 B の中で、派生データを開く口ごとに識別子を記録し、他方の同じ場所と比べる形にできます。ただし、口の数え上げが残り、呼び出しごとに他方の派生データを開く費用がかかります。作者が範囲を保つと決めたときの形です。
- **wiki ごとに別のサブエージェントで引き、回答だけをまとめる。** 文脈の混ざりは減りますが、一方の読み手が他方の実体を読む問題は解きません。
- **2 つの根の形で引いた wiki に、ふつうの呼び出しが来たらサーバーが拒む。** サーバーはセッションをまたいで共有される（F-e）ので、ほかのセッションの 1 つの wiki の問い合わせまで止めます。
- **共有も警告にして続ける（作者の決定 12 を変える）。** 出典の区別を誤った回答を返すことになり、問い合わせの目的に反します。

## 前提と不確実性

**依存している仮定**
- ADR-0029 の走査、`article_path()`、`link_warnings` が、実装の設計どおりに入ること。`955c15a` には、どれもありません。
- 【推測】古いサーバーは、知らないツールの呼び出しをエラーにすること。Claude Code のツールの一覧が、つないだ時点で決まること。どちらも確かめていません。
- 【推測】Windows の `os.stat()` の `st_dev` と `st_ino` で識別子が足りるか。足りなければ、記事ごとにファイルを開く費用がかかります。費用はどの案も測っていません。
- エージェントが 2 つの根の形だけで読むか。実際のモデルで流して確かめる必要があります。
- N2 と、案 B の失敗の形は、実装がないので仕様からの推論です。

**作者の判断が要る点**

## 結論

2 つの wiki が実体を分け合っていないことは、**記事を実際に読む側（MCP のサーバーと、戻り道の CLI）が、両方の根を受け取る呼び出しごとに、自分が開くものの識別子を自分で集めて比べる**形で守るのがよい。推奨は案 3「読み手が確かめる」である。14 版目の形（エージェントが別プロセスの補助を呼び、結果の欄で読み手の版を確かめる）は続けない。

理由の中心は 1 つである。6 回目以降に出た、2 つの wiki の共有に関わる重大 4 件は、すべて「確かめる側が持つ、読む側についての写し」（どの根を開くか、どの走査を使うか、どの場所を開くか）が読む側の実際とずれたことから出た。1〜5 回目の共有に関わる重大 6 件は、比べる対象の代理（根のパス、走査するページ、ディレクトリ、リンクの列挙）が性質とずれたもので、12 版目で識別子の比較に替えてからは出ていない。14 版目は写しを 3 つ（開く場所の一覧、`Walk.links` の欄、不動点の根）持ち、どれも同じ型で崩れうる。読む側が自分で確かめれば、写しそのものが要らない。

案 3 の中身は次のとおりである。

- MCP のサーバーに、**新しい名前のツール** `list_index_both`、`query_both`、`get_page_both`、`graph_both` を足す。どれも 2 つの根 `a`、`b` を受け取り、呼び出しのたびに (1) 自分の `wiki_root()` で両方をそろえ、(2) 索引を開く前に、自分の走査（ADR-0029 の、リンクを拒む走査）で両側の記事と降りたディレクトリ、自分が開く `graph/` の下、自分の索引ディレクトリ `index/<wiki_key>/` の下の識別子を集め、(3) 1 つでも重なれば検索せずに `relation`（`same`、`shared`、`key_collision`、`null`）と理由を返し、(4) `disjoint` のときだけ索引を開いて両側の結果と、側ごとの `link_warnings`、入力をそのまま返す `roots.given` と解決したパス `roots.resolved` を返す。
- 新しい**パラメータ**ではなく新しい**ツール名**にする。mcp 1.30.0 の FastMCP は、ツールの引数モデルに `extra` の設定がなく、知らない引数を黙って捨てると読める（根拠の表）。古いサーバーに接続したままでは、引数の追加だと確かめが飛ばされるが、知らないツール名なら呼び出しが `Unknown tool` で止まる。ただし、古いサーバーの一覧には `_both` が無いので、「`_both` が無いときは単一のツールに戻らず、CLI の `--other` を使うか、接続し直しを案内する」の規則が要る。この規則はエージェントの規則であり、守れないことに入れる。
- 戻り道の CLI（`wiki_search.py`、`wiki_graph_query.py`）には `--other <根>` を足し、同じ共通部で、読む呼び出しの中で確かめる。CLI はディスク上の今の版が毎回動くので、版の問題はない。
- 共通部は `wiki_roots.py` に置き、サーバーと CLI が import する。診断のために `check <a> <b>` の CLI も残す。作者の決定の 8（根の下を識別子で比べる補助を足す）は、エージェントが呼ぶ形から、読み手が使う部品の形で満たす。
- 手順は、`--both` では `_both` のツールだけを使い、索引とページも Read でなく `list_index_both` と `get_page_both` で読む。最初の呼び出しは `list_index_both`。Read で開くのは、その結果の `roots.resolved` の下の `SCHEMA.md`、`graph/ontology.yaml`、`log.md`、raw に限る。「補助を呼ぶ」「`roots` を全呼び出しに渡す」「結果の欄を確かめる」の 3 つの規則は消える。

作者の決定（第 6 節の 1〜12）と ADR-0029 の作者の決定（1〜10）は、案の中では変えていない。変えると良くなるものは「前提と不確実性」の「作者の判断が要る点」に分けて書いた。決定 8 を「エージェントが呼ぶ CLI」と狭く読むなら、案 3 は採れない。そのときは案 1 をレビューを止めた状態で進めるのが、重大が C と D になったときの規則に合う。

| `index/<wiki_key>/` の下 | MCP の `WikiIndex` | 順位が変わる。書き込みが他方の索引を壊す。本文は入らない | `_both` が自分の索引ディレクトリの下を比べる。読み手の中 |
| `.wiki-cache/` の下 | CLI の戻り道 | 順位が変わる。`.tmp` の別名で他方の記事を上書きする（3-3、4-1）。読みでは本文は入らない | CLI の `--other` が比べる。書く側は ADR-0029 の I6 |
| 被リンク（`--backlinks`） | CLI だけ（手順 5） | 他方のページのリンクを一方のものとして数える | CLI の `--other` で、読む呼び出しの中 |
| `log.md` | エージェントの Read（時系列の質問） | 他方の記録を一方のものにする | 記事として識別子に入る。Read は `roots.resolved` の下（エージェントの規則） |
| raw | エージェントの Read（手順 3、ソースの質問） | 他方の原本を一方のものにする | どの案も比べない（第 5 節） |

ここから 2 つが言える。(1) 本文が混ざる経路は、記事と `graph.sqlite` である。索引ディレクトリと `.wiki-cache/` は順位と書き込みの安全の問題で、書き込みは ADR-0029 の I6（書き込みの部品がリンクの行き先に書かない）が別に守る。(2) 案 3 で読み手の中に入る読みは、索引、ページ、検索、グラフ、被リンクである。`SCHEMA.md`、`ontology.yaml`、`log.md`、raw の Read は手順の規則に頼る。14 版目は、索引とページの Read も規則に頼っていた。

### 4. 推奨する案 3 の内容

**中身（誰が、いつ、何を確かめるか）。**

- 誰が：記事を読むプロセス。MCP のサーバー（`_both` の 4 ツール）と、CLI（`wiki_search.py --other`、`wiki_graph_query.py --other`）。
- いつ：両方の根を受け取る呼び出しのたび。前の呼び出しの判定を使い回さない。確かめは `State.wiki()`（索引を開く）より前に行う。索引を開いてから確かめると、`key_collision` の配置で 2 つ目の `WriterLock` が時間切れになり、`wiki.json` も他方の根で上書きされるためである。
- 何を：側ごとに、根の識別子、走査（`walk_pages()`、`walk_index_files()`、`article_path()` で読む最上位の `log.md` と `SCHEMA.md`）が読んだ記事と降りたディレクトリの識別子、`graph/` の下の全項目（たどる形）、その読み手が開く保存場所の下の全項目（MCP は `index/<wiki_key>/`、CLI は `.wiki-cache/`）。2 つの側の集合が 1 つでも重なれば `shared`。それより前に、同じディレクトリなら `same`、識別子が取れないか一覧できない項目があれば `null`、`wiki_key()` が同じなら `key_collision`。順序は 14 版目と同じ（`null`、`same`、`shared`、`key_collision`、`disjoint`）。止めるのは共有だけで、記事のリンクは `link_warnings` で続ける。ADR-0029 の決定 5 が採らなかった「コマンドごとに木を調べて止まる形」ではない。
- そろえ方：読み手が `wiki_root()` で 1 回そろえ、そろえた根を自分で読む。エージェントは、登録の文字列を毎回そのまま渡す。14 版目の不動点の 3 識別子のうち、「入力をそろえずに解決したディレクトリ」と「そろえた根」の識別子の一致だけを読み手に残す（NFC の双子で別のディレクトリを開いていないかを知らせ、`null` にする）。「そろえた根をもう一度そろえる」比較は、そろえた根を再入力しないので要らない。
- 走査：確かめのための走査は、索引を開く前に行うので `refresh()` の走査と別になる。走査の結果を `refresh()` に渡して 2 度目を省く形は実装で決める。`wiki_pages.walk_markdown()` に識別子を取る任意の引数を足す（Windows では記事ごとに `win_file_id()`、POSIX は `os.stat()` の `st_dev`、`st_ino`）。

**守れること。**

- 読み手の版の不一致（8-1）：古いサーバーは `_both` を持たず、呼べば `Unknown tool` で止まる。欄の確かめが要らない。
- そろえ方の不一致（6-1、7-1）：そろえるのは読み手の 1 回だけ。CLI も `--other` のときは同じ `normalize_wiki_root()` でそろえる。
- 開く場所の写し（3-1、4-1、8-2）：読み手が自分の走査の結果と自分の保存場所から集める。手順に新しい読み取りを足すとき、別の一覧を直す必要がない。
- 確かめと読みの時刻差：1 呼び出しの中に縮む。
- 記事のリンク：ADR-0029 の走査が拒み、側ごとの `link_warnings` で返す。止めない（決定 12）。
- `same`、入れ子、bind mount、`subst`、別ドライブ文字、`graph/` や索引のジャンクションとハードリンク：識別子の重なりで見つかる（14 版目と同じ範囲）。

**守れないこと（保証しないこと）。**

- 古いサーバーに接続したままのとき、ホストのツールの一覧にも `_both` が無く、単一のツール（`query`、`get_page`）は呼べる。「`_both` が無いときは単一のツールで 2 つを引かない。CLI の `--other` を使うか、接続し直しを案内する」はエージェントの規則である。
- エージェントの Read：`roots.resolved` の下の `SCHEMA.md`、`ontology.yaml`、`log.md`、raw に限る規則に頼る。索引やページを Read で読むこと、`--both` で単一のツールを使うことは止めない。
- `get_page_both` の `side` の取り違え：b の同名スラッグを a の出典と称する誤りは、結果の `wiki` の欄で見分けられるが、エージェントがそれを見ることに頼る。
- raw の場所、MCP の古い本文、識別子の限界、`INFO_HIVE_DATA_DIR` を wiki の中に置いた配置：14 版目の第 5 節と同じ。
- 索引ディレクトリと `.wiki-cache/` の読み：比べはするが、分け合っても本文は入らない。比べる理由は書き込みの安全と、作者の決定 8 の「開くものを比べる」である。

### 5. 推奨する理由

1. **写しをなくす。** 6 回目以降の共有の重大 4 件と、3・4 回目の 2 件は、確かめる側の写し（P1〜P3）から出た。読み手が確かめれば、写しは存在しない。これは [[敵対的レビューで設計を直す進め方]] の「実物に尋ねる」「照合の中に実物の写しを作らない」に当たる。
2. **古い読み手を、呼び出しの側で止める。** 新しいツール名は、古いサーバーで必ず失敗する。引数の追加や欄の確かめでは、黙って通るか、エージェントの確かめに頼る。残るのは「一覧に無ければ単一のツールに戻らない」の 1 規則である。
3. **エージェントの規則を減らす。** Sonnet の測定で、規則は中身ではなく置き場所と指し方で届くかが決まった。「`_both` のツールを使う」「Read は `roots.resolved` の下だけ」の 2 つは、補助を呼び、`roots` を渡し、欄を見る形より届きやすい。
4. **索引とページの読みを読み手の中に入れる。** 14 版目では索引とページの Read も規則に頼っていた。案 3 では、本文が混ざる経路のうち、残るのは `SCHEMA.md`、`ontology.yaml`、`log.md`、raw の Read だけになる。
5. **ADR-0029 との境界が明確になる。** リンクの記事は走査が拒み、共有は読み手が識別子で見つけ、書き込みは I6 が守る。3 つの守りがそれぞれ 1 か所にある。

## 検討した代替案

### 案 1：今の形を続ける（14 版目）

- **中身。** エージェントが `wiki_roots.py check A B` を呼び、`disjoint` のときだけ `roots` を全呼び出しに渡し、読み手の結果に `link_warnings` 欄があることを確かめる。
- **守れること。** 開く場所の下の識別子の重なり（入れ子、mount、`subst`、リンク）。記事のリンクは警告して続ける。
- **守れないこと。** 補助と読み手の一致（版、そろえ方、場所の一覧）は推定で、P1〜P3 を仮定として持ち続ける。エージェントの Read、時刻差、raw。
- **新しく生む失敗の形。** (1) 欄の確かめは版の代理で、`graph` の結果の欄は走査と無関係に付く（欄があるが何も確かめていない形）。将来欄の名前や形を変えると、確かめの意味が変わる（C）。(2) 不動点の 3 識別子は NFC の双子に合わせたもので、別名の別の種類（大文字と小文字を区別する NTFS のディレクトリ、8.3 形式の短い名前）が出れば識別子を足す形になる（D）。(3) `roots` を渡す規則と CLI のそろえない使い方の差（C）。(4) 開く場所の一覧の保守（B。手順を直すたびに）。
- **変えるファイル・量。** 設計書の第 4 節のとおり。補助 300〜400 行、試験 300 行、文書 10 件。
- **費用。** 問い合わせごとに Python のプロセス 1 回、両 wiki の走査 1 回ずつと記事ごとの識別子、3 つの場所の下の全項目の識別子。MCP の `refresh()` の走査は別に 2〜6 回。
- **決定との関係。** 4、8、12 をそのまま満たす。
- **採らない理由。** 8 回目の重大は C と D で、プロジェクトの規則では「止めるかを作者に聞く」段階にあり、続ける選択は正当である。決定 8 を狭く読むなら、この案をレビューを止めた状態で進めるのが筋である。しかし 13・14 版目で足した 3 つの仕組み（場所の一覧、欄の確かめ、不動点）は、どれも「読み手の写し」で、崩れ方の型が 3・4・6・7・8 回目と同じである。写しをなくす案 3 のほうが、残る危うさの種類を減らす。

### 案 2：確かめを読み手のプロセスに移すが、呼び出しは分ける（MCP のツール `check_roots`）

- **中身。** 共通部 `wiki_roots.py` をサーバーが import し、ツール `check_roots(a, b)` を足す。サーバーが自分でそろえ、自分の走査と自分の索引ディレクトリで集めて比べる。エージェントは最初に呼び、以後は登録の文字列をそのまま既存のツールに渡す。CLI は `--other` で読む呼び出しの中で確かめる。
- **守れること。** 版の不一致（古いサーバーに `check_roots` がない）、そろえ方の不一致（同じ関数で同じ文字列）、索引の中身の写し。案 3 と同じ。
- **守れないこと。** 確かめと読みの時刻差が問い合わせ全体に広がる。エージェントが `check_roots` を飛ばす、または `check_roots` の出力のパスを既存のツールに渡す（7 回目の形が戻る）。索引とページの Read は規則のまま。
- **新しく生む失敗の形。** (1) 「登録の文字列を渡し、出力の `roots` は Read にだけ使う」という、文字列の使い分けの規則（C。エージェントは出力のパスを写しやすい）。(2) MCP は別呼び出し、CLI は呼び出しの中、という非対称。(3) `check_roots` が無い古いサーバーで、単一のツールが呼べる（案 3 と同じ規則が要る）。
- **変えるファイル・量。** `wiki_roots.py`（共通部）、`wiki_mcp_server.py`（ツール 1 つ、30〜50 行）、`SERVER_FILES`、CLI 2 つの `--other`、試験の `TOOLS` と配置の試験、文書は案 3 と同じ。案 3 より 100 行ほど少ない。
- **費用。** 問い合わせごとに走査 1 回ずつ（サーバー内、プロセスの起動なし）と MCP の往復 1 回。案 3 より軽い。
- **決定との関係。** 案 3 と同じ。
- **採らない理由。** 案 3 との差は「前の呼び出しの判定を使うか」と「索引とページの読みを読み手に入れるか」である。レビュー 6〜8 は、確かめる側と読む側の間の受け渡し（パス、版）で崩れた。案 2 は受け渡しを「同じプロセス、同じ文字列」に減らすが、文字列の使い分けという受け渡しが残る。案 3 は受け渡しをなくす。費用を重く見るなら、案 3 の形で `list_index_both` の判定を同じサーバーの中で短時間使い回す折衷もありうる（「作者の判断が要る点」の 4）。

### 案 4：保証を縮める（`same`、入れ子、`key_collision` と ADR-0029 のリンクだけ）

- **中身。** 根の識別子と祖先の識別子の列で `same` と入れ子を決め、ADR-0029 の走査でリンクを拒む。mount と `subst` は保証しない。
- **守れること。** 日常の配置（同じ wiki、入れ子）。
- **守れないこと。** bind mount、`subst`、別ドライブ文字（5 回目の致命がそのまま）。
- **新しく生む失敗の形。** 5 回目の再現。
- **変えるファイル・量。** 補助 100 行と文書。

- **決定との関係。** 作者の決定 8（根の下を識別子で比べる）に反する。採るなら決定の変更が要る。

## 前提と不確実性

### 依存している仮定

- ADR-0029 の実装（リンクを拒む走査、`Walk.links`、`article_path()`、`resolve_raw()`、書き込みの部品）が先に入る。14 版目と同じ前提で、まだコードはない。
- `_both` のツールの呼び出しごとの走査と識別子の取得が、ふつうの規模（数百ページ）で受け入れられる。費用は式で示したが、時間は測っていない。
- FastMCP が知らない引数を捨てることは、`ArgModelBase` の `model_config` と pydantic の既定からの導出で、実行して確かめていない。ホストの側（Claude Code）がツールのスキーマで引数を検査するかは分からない。どちらでも「新しいツール名なら呼び出しが止まる」は変わらないが、「一覧に無いので単一のツールに戻る」経路は規則で止めるしかない。
- 同じプロセスで同じ索引ディレクトリを 2 度開くと `WriterLock` が失敗することは、`msvcrt.locking` と `flock` の振る舞いの読みからの導出で、実行して確かめていない。どちらに転んでも、確かめを索引を開く前に置く結論は変わらない。
- エージェントが `--both` で `_both` のツールを使い、Read を `roots.resolved` の下に限ること。実際のモデルで流して確かめる必要がある。
- Windows の `win_file_id()` と POSIX の `(st_dev, st_ino)` が、2 つの wiki を置くファイルシステムで安定して取れる。

### 確かめられなかったこと

- 実際に 2 つの wiki で `_both` の形を動かした記録はない。案の判定（`relation` の値）は、現行コードと設計からの導出である。
- 確かめの走査の結果を `refresh()` に渡して 2 度目を省けることは、`stat_signature()` と `collect_pages()` が同じ `walk_pages()` を使うことからの推測である。
- `list_index_both` が新たに増やすページの走査（今の `list_index` はページを走査しない）の費用は、問い合わせの初めの 1 回なので小さいと推測する。

### 作者の判断が要る点

1. **決定 8 の「補助」の読み。** 「エージェントが呼ぶ CLI」に限るなら、案 3 も案 2 も採れない。読み手が使う部品として置き、診断用の `check` の CLI を残す形で満たすと読んだ。狭く読むなら、案 1 をレビューを止めた状態で進める。

4. **呼び出しごとの確かめの費用を受け入れるか。** 受け入れないなら、`list_index_both` の判定を同じサーバーの中で短時間（同じ `(a, b)` に対する次の `list_index_both` まで）使い回す折衷がある。その場合、確かめと読みの時刻差は問い合わせ全体に戻る。

6. **ADR-0010 の評価ゲート。** `_both` は単一の `query` の結果の集合を変えないので測り直しは要らないと考えるが、ADR-0029 の実装（検索の対象の集合が変わる）の測り直しと合わせて判断する。

## 結論

**読み手が2つの根を受け取り、共通の補助で分離を確かめてから中身を返す形を推奨する（以下、案B）。** `wiki_roots.py` と識別子の集合比較は残すが、エージェントが別プロセスで得た検査結果を、別の読み手に引き継ぐ構造を改める。

実装上は、2つの根を必須とする専用のMCPツールとCLIの入口を設ける。検索だけでなく、記事・索引・規約・ログ・被リンク・グラフの読み取りも、この入口を通す。既存ツールに任意の引数を足すだけでは、引数の付け忘れや旧ツールへの切り替えが残る。

推奨理由は、識別子比較の強さを保ちつつ、これまで繰り返し崩れた次の前提を減らせるためである。

- 補助と読み手が、同じ根・同じデータの場所を使っている。
- 補助が新しければ、接続済みの読み手も新しい。
- 補助が別に持つ「開く場所の一覧」が、実際の読み取りと一致している。

ただし、**「回答に使う全内容が他方のwikiに由来しない」という無条件の保証にはしない。** 現設計は、外部rawの共有、索引が保持する古い本文、検査後の配置変更、会話に既に入った内容を保証から外している。案Bでも、その範囲は別に残す。作者の決定を変えずに保証できるのは、定めた読み取り経路と対象集合についての実体分離である。〔D:240–256、A:94–101〕

**3. コードが示す、責任を読み手へ寄せる理由**

次はコードで確認できる事実である。

- MCPは `wiki_root()` で根を正規化し、`State.wiki()` が根ごとの索引を保持する。CLI検索とCLIグラフ問い合わせは、渡された根を同じようにはNFC化しない。〔M:90–108、188–195、S:1147–1156、G:230–244〕
- MCP索引の場所は、読み手の環境に対する `data_dir()` と `wiki_key()` で決まる。〔C:47–57、84–94、I:831–836〕
- 索引はSQLite、usearch、Tantivyを別々に開く。usearchはファイルをメモリへ読み込む。〔I:403–426、444–473〕
- 中継は既存セッションを使い続ける。コードの版の比較は `ensure_server()` にあるが、既存セッションの再利用経路は生存状態を見る。〔T:103–115、234–244〕
- 現在の `get_page()` は、収集済みの通常ページから選ぶ。`SCHEMA.md`、索引、ログなどの読み取りを、これだけで置き換えることはできない。被リンクは現状CLIにしかない。〔I:931–979、P:49–57、Q:14–16、F:51–59〕

**推論:** 補助とMCPで環境が異なれば、同じ関数を呼んでもMCP索引の場所が異なりうる。14版目の結果の欄の確認は、その一致までは確かめない。これは今回実際に再現した欠陥ではなく、コードの接続から見える前提である。

また、14版目は後続呼び出しに正規化後の `roots` を渡す。一方、ADR実装設計の `resolve_raw()` は、利用者が書いたままの根の綴りと、解決後の根の両方を必要としている。**推論:** 正規化後の根だけを引き継ぐと、rawの候補を作る情報が不足する場合がある。案Bでは、この2つを最初から別の値として保持する。〔D:86、L:159–162〕

**4. 推奨する案Bの具体像**

以下は提案であり、API名は仮称である。

1. **専用の入口を作る。**  
   MCPに `pair_read`、CLIに対応する入口を設ける。両方とも、ユーザースコープとプロジェクトの2つの根を必須にする。検索、ページ、索引、規約・ログ、被リンク、オントロジー、グラフ、必要なrawの読み取りを扱う。

2. **読み手の中で共通補助を呼ぶ。**  
   `wiki_roots.py` を標準ライブラリだけの共通部品とし、診断用の `check` も残す。読み手自身の環境と資源の場所を使い、中身を読む・索引を作るより前に検査する。別プロセスの `disjoint` を実行許可証としては使わない。

3. **根を一度確定し、内部では確定済みの値を渡す。**  
   元の綴り、解決後の根、実体の識別子を保持する。内部の検索処理などへは、再正規化する公開入口を経由せずに渡す。初期実装では14版目の正規化による実体変更の拒否を残し、名前の扱いを同時に変更しない。

4. **読み取り対象を、その場所を決めるコードと結び付ける。**  
   記事はADRの走査結果と実際に降りたディレクトリから得る。索引・グラフ・キャッシュの場所は、それを開くコードと同じ関数から得る。派生データは、その場所の下全体を比較する。自前の読み取り処理が、この計画にない場所を開こうとしたら失敗させる。

5. **結果を返す前に判定を完了する。**  
   `shared`、`key_collision`、判定不能なら本文を返さない。記事のリンクは本文を返さず、wiki別の警告を付けて続ける。旧サーバーに専用ツールがなければ、対応したCLIへ切り替えるか再接続を案内し、旧来の単一wikiツールで2回読む形へは戻らない。

この設計でも、資源の範囲を定義する必要は消えない。消すのは、**読み手とは別に補助が持つ一覧と、その一致をエージェントが維持する責任**である。ライブラリに渡す場所の宣言漏れや、内部で共通経路を迂回する読み取りは、新しい失敗の形として残る。

**守れること**

対象集合を \(F_u, F_p\) とし、識別子で比較する。

\[
F_u \cap F_p = \varnothing
\quad\text{かつ}\quad
wiki\_key(u) \ne wiki\_key(p)
\]

読み手がこの検査で確定した対象だけを使い、配置と識別子が安定していれば、その対象内で同じ実体を両スコープのものとして扱わない。リンクの記事は集合から外すだけでなく、ADRの理由付き警告として残す。

**守れないこと**

外部rawの排他的な所属、過去の索引本文の来歴、問い合わせ中の配置変更、モデルが別のReadや既存の会話内容を使うことは保証しない。OS全体のファイルアクセスを制限する仕組みではない。

**変更ファイルと量の目安**

共通の文書変更は14版目の第4節を引き継ぐ。そのうえで、主に次を変える。

**問い合わせごとの費用**

\(N\) を両方の比較対象の項目数、\(q\) を専用入口の呼び出し回数、\(T_{\text{base}}\) を検索や本文取得の費用とする。検査結果を呼び出し間で保存しない初期案では、

\[
T_B \approx T_{\text{base}} + q\,T_{\text{scan}}(N),\qquad
T_{\text{scan}}(N)=O(N)
\]

となる。メモリは検査中に \(O(N)\)。14版目より検査回数は増える。初期実装では、この費用と引き換えに、セッション識別子・有効期限・再接続時の失効管理を導入しない。

## 検討した代替案

**案A：14版目の分担を続ける**

- **誰が・いつ・何を確かめるか:** エージェントが問い合わせ前に補助を呼び、補助が両根の対象集合を比較する。その後、エージェントが各読み手の結果の `link_warnings` を確認する。
- **守れること:** 列挙した対象集合が完全で、読み手と根・環境が一致し、手順が守られれば、その時点の共有を検出できる。14版目はR8の内部ファイルの漏れを明示的に直している。
- **保証しないこと:** 補助の省略、欄の確認漏れ、環境差、一覧の追加漏れ。raw・古い本文・配置変更の限界も残る。
- **新しい失敗の形:** 再帰走査が、開かない子ファイルの共有や読めない項目でも停止する。新しい資源の場所を読み手だけに足すと、補助が追従しない。警告欄が、意味の異なる将来の実装でも存在する可能性がある。
- **変更量:** 14版目の一覧どおり、新規の補助1ファイルと文書群が中心。**推定**で本番コード約250〜500行、試験約300〜600行。ADR実装は含めない。
- **費用:** \(T_A \approx T_{\text{base}}+T_{\text{scan}}(N)\)。検査は原則1回。
- **決定との関係:** 作者の決定・ADRに最も直接沿う。
- **採らない理由:** 小さく実装できる利点はあるが、今回見直すべき「検査と使用の別管理」が残る。14版目が実装不能という判断ではなく、保守時にも同じ種類の前提を守り続ける負担を重く見た。

**案C：問い合わせの開始時に両根を検査し、読み手がセッションとして保持する**

- **誰が・いつ・何を確かめるか:** `begin_pair` のような入口で読み手が両根を検査し、根・環境・対象の情報をメモリ上に保持する。後続操作はそのセッションの識別子を必須にする。
- **守れること:** 案Bと同じ対象について、同じ検査済みの根と環境を後続処理へ引き継げる。別プロセスの補助と結果を照合する必要がない。
- **保証しないこと:** セッション開始後の配置変更や本文の鮮度は、別の再検査・固定機構がなければ保証できない。「セッションがある」ことを「内容のスナップショットがある」こととは扱えない。
- **新しい失敗の形:** 別の問い合わせの識別子の誤用、閉じ忘れ、再接続後の再利用、期限切れ、資源解放漏れ。検査状態を保存する仕組み自体が、新しいレビュー対象になる。
- **変更量:** 案Bに加え、サーバー内のセッション管理とCLIへの切り替え規則が必要。**推定**で本番コード合計約1,200〜2,300行、試験約800〜1,500行。
- **費用:** 再検査しない場合は、\(T_C \approx T_{\text{base}}+T_{\text{scan}}(N)+O(q)\)。CLIへ切り替える際は、新しい読み手で検査し直す。
- **決定との関係:** 補助とADRの規則を残せば、作者の決定を変更せず採れる。
- **採らない理由:** 現時点では検査時間の実測がない。費用を減らす必要が確認される前に、検査結果の寿命と失効を管理する仕組みを増やす理由が弱い。

全wikiの全ファイルを比較する案は、今回の採用候補に入れなかった。記事でない無関係なリンクまで対象に戻すため、ADRの決定6・9に逆行する。リンクの種類をさらに禁止する案も、bind mountなどを残す作者の決定を変えずには採れない。〔A:28、32、39、D:396–399〕

## 前提と不確実性

**保証の前提として残るもの**

案Bでも、安定した識別子、問い合わせ中の関連配置の安定、ADR-0029を実装した読み取り経路、指定された入口をエージェントが使うことに依存する。Pythonの内部処理や外部ライブラリが、宣言した経路を迂回しないことも実装で確かめる必要がある。

また、同じ内容の別ファイルは共有ではない。反対に、別々のファイルに以前写した内容が入っていても、識別子比較では由来を判別しない。きっかけの検討が避けようとした「複製後の食い違い」と、今回の「現在の実体の共有」は別問題である。〔D:220、X:23–27、161〕

**作者の判断が要る点**

1. **読み取りコードを変更する案Bを採るか。**  
   これは第6節の決定の変更ではないが、14版目の「読み手のコードを変えない」という提案を変更する。実装量と検査回数を増やす代わりに、検査と使用を同じ読み手にまとめる。

2. **反復走査の費用をどこまで受け入れるか。**  
   時間の絶対値は未測定。Windowsでは識別子の取得にファイルを開くため、項目数だけでは待ち時間を決められない。まず案Bで測り、費用が問題になった場合に案Cを再検討するのが妥当と考える。

3. **古い索引本文を、将来も保証外にするか。**  
   これは作者の決定1〜12を変えずに別途改善できる。現在の `stat_signature()` はパス・大きさ・更新時刻だけを使うため、案Bへの移動だけでは直らない。識別子や内容の検証を索引の更新条件に加えるかは、検索全体の変更として判断する。〔I:815–825、850–853〕

4. **回答全体の完全な分離まで求めるか。**  
   求めるなら、定型文による先行読み込みを残す決定2や、raw・外部原本の扱いの再検討が必要になる。先行読み込みを制限すれば問い合わせの要求と会話の内容を近づけられるが、今の便利な自動参照が変わる。外部原本の排他的な所属まで求めれば共有原本を使いにくくなる。**今回の推奨案では、これらの決定変更を使っていない。**

**確かめられなかったこと**

- 14版目とADR-0029の予定実装の通し動作、実際の問い合わせ時間、モデルが専用入口を守る割合は未確認。
- 過去のレビューのモック検証は記録として参照し、今回再実行していない。
- `~/info-hive/W0_Wiki/index.md` は、この実行環境では存在を確認できなかった。プロジェクトの `wiki/index.md` と指定されたページを参照した。
- [[2つのwikiの分離の確かめ方]] は、リンクがあれば停止する旧段階の説明を含む。14版目や承認済みADRと食い違う箇所は、経緯の資料として扱った。〔W1:30–39〕

ファイル変更、ビルド、禁止された他エージェントの成果の閲覧は行っていない。

## 結論

**分離の検査を、2つの根を必須で受け取る共通の読み取り層へ移す案を推奨する。** MCP と CLI はその層を呼び、検査した対象を同じ呼び出しの中で読む。エージェントが別プロセスの補助を先に実行し、その合格結果と、後から受け取った `link_warnings` の有無を組み合わせる構成はやめる。

作者の決定8に従い、`wiki_roots.py` は追加する。ただし、独立した「読むものの一覧」を持つ検査器にはせず、読み取り層も使う識別子比較の部品と、その診断用 CLI にする。記事のリンクは ADR-0029 に従って読まず、警告を付けて続ける。

変えるべき前提は、14版目の「検索とページを読むコードを変えない」である。この制約は設計書第1節の実装方針であり、第6節の作者の決定1〜12には含まれていない。読み手を変えないために、補助と手順が読み手の動作・設定・版を外から再現する必要が生まれている。［D14:26、262–277］

ただし、**「回答に関わるすべての中身が、物理的にも由来としても独立している」という無条件の保証にはしない。** 外の原本、検査後の配置変更、識別子の不安定なファイルシステム、過去の索引、会話に入った情報は別の問題である。作者の決定を保つ限り、保証は対象と時点を限定して書く必要がある。

## 根拠

以下では、コード・文書で確認したものを「事実」、そこから導いた評価を「推論」、新しい構成を「提案」と記す。参照略号のパスと該当箇所は末尾に示す。

**1. まず、保証するものを分ける**

事実として、14版目の補助は、現在の配置にある記事・走査したディレクトリ・グラフ・キャッシュ・MCP 索引の識別子を比較する。一方で、raw の共有、索引に残った過去の本文、検査後の変更を保証から外している。［D14:182–202、247–255］

したがって、少なくとも次の3つは別の性質である。

| 性質 | 今の設計が確かめようとしていること | それだけでは分からないこと |
|---|---|---|
| 現在の配置の分離 | 両側の対象ファイル・ディレクトリの識別子が重ならない | 索引が以前に何を読んだか |
| 読み取りの一致 | 検査した根・対象を、実際の読み手も使う | 検査後の差し替え、別経路の直接読み取り |
| 回答の出典の正しさ | 読んだ記事を、読んだ側のスコープに結び付ける | モデルの誤引用、共通の原本、過去の会話からの混入 |

推奨案の中心は、上の2行を同じ実装で成立させることにある。最後の行までファイル識別子だけで保証することはできない。

比較対象も「プロセスが開く全ファイル」ではない。コード、埋め込みモデルなどは両側で共有してよい。対象は、**wiki ごとの記事と、その wiki の検索・読解に使う保存データ**である。外の原本は、ADR-0029 の例外として別に扱う。同じ内容の独立したコピーも、同じ実体とはみなさない。［D14:41、220、249–251、ADR:26、48、67］

推論として、問題は識別子比較そのものより、**比較する対象・根・設定・実装を、実際の読み手の外で再構成していること**に集中している。第8回では、版の確認も対象集合も、代理として見たものが実物と一致しなかった。これは [[敵対的レビューで設計を直す進め方]] の「照合の中に実物の写しを作らない」という記録とも対応する。［同ページ:16–25］

**4. 推奨案B：読み手が2つの根を受け、検査と読み取りを一体で行う**

以下は提案であり、実装済みの説明ではない。

1. **登録の解釈は今の手順に残す。**  
   エージェントはユーザースコープとプロジェクトの登録を独立に集める。読み取り層には、スコープを付けた2つの根を渡す。位置からスコープを推測しない。

2. **入口で根を確定し、以後は内部の値として渡す。**  
   元の綴り、解決した根、実体の識別子を一緒に保持する。入力を正規化することで別実体に移る場合は拒む。後段は解決済みの値を受け取り、文字列に戻して NFC 化し直さない。raw の解決には元の綴りも渡す。

3. **読む側が、自分の依存先を定義する。**  
   記事は ADR-0029 の走査・読む口を使う。検索の保存データは検索側、グラフ DB とオントロジーはグラフ側が提供する。検査用のパスと実際に開くパスを、同じ対象オブジェクトから得る。  
   SQLite などが自分で開く付随ファイルも、その接続処理の依存先に含める。Tantivy のように内部ファイルが動く保存領域は、その保存領域を管理する部品が子ファイルまで扱う。共通の親ディレクトリやモデルファイルを、両 wiki の専有データとして比較しない。

4. **両側を検査してから、本文の取得や索引の生成・更新に進む。**  
   `wiki_roots.py` の共通関数で識別子集合を比較する。リンクの記事は集合から除き、警告として残す。共有・キー衝突・検査不能なら、両側を引く操作は結果を返さない。  
   `State.wiki()` を先に呼んではならない。現在の `WikiIndex` はコンストラクターでディレクトリ、`wiki.json`、DB などを作るためである。［Server:188–195、Index:831–836、403–426］

5. **検査した対象を、そのまま実行に渡す。**  
   本文・索引・`SCHEMA.md`・`log.md`・被リンク・グラフ・オントロジー・必要時の raw 読み取りを、この入口の操作として提供する。特に、オントロジーだけをエージェントの直接 Read に残さない。現在の手順はその内容からノードの種類を決める。［Query:16–18］  
   新しい読み取りを足す際は、対象の宣言と開く処理を同じ箇所に足す。未登録の wiki データを直接開く経路がないことを、接続試験で確かめる。

6. **旧サーバーで成功できない入口にする。**  
   たとえば、新しい MCP ツール `read_pair` を設け、2つの根と操作を必須にする。旧 `query` に任意の引数を足すだけの形は避ける。旧サーバーに入口がなければ、再接続か、同じ読み取り層を使う新しい CLI へ進む。従来の単独ツールを2回呼ぶ形には戻さない。  
   `link_warnings` は拒否の通知として残し、読み手の版を推定する証拠には使わない。

7. **キャッシュと回答に使う本文を区別する。**  
   保持済みの索引を使う場合、その根・保存先が今回の検査対象に結び付くことを読み手自身が確認する。結び付きを確認できない既存オブジェクトを、そのまま再利用しない。  
   検索で得た候補を回答の証拠として返す際は、現在の許可された記事を読み直し、本文とメタデータをその読み取りから作る。古い検索抜粋を、そのまま新しい本文の証拠にしない。索引の古さによる候補漏れや順位の古さまで、これで直るとは主張しない。

この案でも、数え上げが完全になくなるわけではない。違いは、**外部補助が読み手の知識を複製するのをやめ、依存先の定義と実際の読み取りを同じ変更箇所に置くこと**にある。新しい入口から検査なしの経路へ抜けられる実装なら、移した効果はない。

**守れることと残る限界**

安定した識別子が得られ、検査と読み取りの間に配置が変わらず、対象の定義が実際の読み取りを覆う条件で、対象となる現在の実体の共有を拒める。補助とサーバーの環境差、再正規化、旧サーバーの成功結果の誤採用を、手順だけに頼らず減らせる。

一方、OS 全体の読み取りを強制する仕組みではない。エージェントが従来ツールや直接 Read を使うこと、外部プロセスによる変更、識別子の不正確さ、共有原本、古い索引による候補漏れは残る。

**新しく生む失敗の形**

| 追加する仕組み | 新しい失敗 | 設計・試験で押さえる点 |
|---|---|---|
| 共通の読み取り層 | 一部の操作だけが従来の読み方へ抜ける | ページだけでなく、索引・規約・ログ・被リンク・グラフ・raw を接続試験の対象にする |
| 依存先の定義 | 定義したパスと開くパスが別々に計算される | 同じ対象オブジェクトを検査と実行に渡す |
| 保存領域の扱い | 無関係な `.wiki-cache/` 全体を比較して過剰に止める | 検索が管理する保存データと、それ以外のファイルを分ける |
| 既存索引の再利用 | 現在のパスと、すでに開いている DB・保持済みデータが食い違う | 再利用の条件を明示し、結び付きを確認できなければ再利用しない |
| 複数の根と操作の受け渡し | スコープと根、結果の対応が入れ替わる | 結果のスコープを読み取り層が付け、呼び出し側に推測させない |
| CLI への縮退 | 検査不能を「MCP の障害」として旧 CLI へ逃がす | 通信障害・非対応と、共有・検査不能を別の結果にする |
| 検査の繰り返し | 全走査の費用がページを読むたびに増える | 複数操作を一度に渡せる形にする。最初から期限付き検査証や常駐セッションは追加しない |

**問い合わせごとの費用**

`N` を両 wiki の対象記事・ディレクトリ数、`C` を使う保存データの対象項目数、`k` を読み取り層への呼び出し回数とする。

- 14版目の事前検査は、おおむね `O(N + C)` のメタデータ処理を1回行い、その後に検索・読み取りを行う。
- 推奨案を毎回検査する形で始めると、検査は最大で `O(k × (N + C))`。実際には操作ごとの依存先と一括呼び出しで減らせる。
- Windows の識別子取得はファイルを開く処理を含む。件数に比例する I/O を、定数時間とは扱えない。［Pages:148–174］
- 本文の読み直しには、返す候補の本文量に比例する費用が加わる。
- 検索は引き続き wiki ごとに行う。モデルの保持は共有できるが、検索量も読み込む文量も常に「ちょうど2倍」とは限らない。

たとえば `N + C = 10,000`、`k = 6` なら、単純な毎回全検査は約 `60,000` 項目分、事前1回は約 `10,000` 項目分の検査になる。これは計算例であり、作者の wiki の実測値ではない。速度を理由に検査結果を使い回す前に、一括呼び出しで足りるかを測るべきである。

## 検討した代替案

**案A：14版目の形を続ける**

- **誰が・いつ・何を確かめるか**  
  問い合わせの前に外部補助が対象の識別子を比較する。その後、エージェントが各結果の `link_warnings` を確認する。記事以外の3つの場所は子ファイルまで調べる。
- **守れること**  
  対象集合・設定・版が読み手と一致し、配置が変わらない条件なら、既知の共有反例を検出できる。第8回への修正方針自体には合理性がある。
- **保証しないこと**  
  補助と読み手の一致、結果確認の実行、古い本文、raw の共有、検査後の変更。既存の限界に加え、保存先の環境差にも注意が要る。
- **新しく生む失敗**  
  読む場所が増えた際の補助更新漏れ、広いディレクトリ走査による過剰な停止、リンク先の大きな木への走査、結果欄だけを保った不完全な互換実装。
- **変更と量**  
  `wiki_roots.py` 新規、親の試験、D14の文書一式。ADR の実装を除けば**小〜中**。検索本体の変更は最少。
- **費用**  
  `O(N + C)` の事前検査1回と、両 wiki の検索・読み取り。記事でない場所の全走査が大きくなる場合がある。
- **決定との関係**  
  作者の決定と整合する。採用には新しい決定の変更は要らない。

**採らない理由：** 最少変更ではあるが、第8回で崩れた「外部から実際の読み手を推し量る」という依存が残る。今後の保守で、読み手と補助の2か所を同期し続ける必要がある。

**案C：`--both` 専用の短命な CLI 読み取り器に統一する**

- **誰が・いつ・何を確かめるか**  
  新しい CLI が毎回2つの根を受け、同じプロセス内で補助を呼び、記事・検索・被リンク・グラフ・raw を読む。2つを引くときは既存 MCP の `WikiIndex` を使わない。
- **守れること**  
  常駐 MCP の旧版、MCP の保存先の環境差、MCP のメモリに残った本文を、この問い合わせの経路から外せる。現在の CLI の `collect_pages()` は記事のバイト列を読み、SHA-256 を確認してパースキャッシュを再利用する。MCP の「パス・サイズ・更新時刻が同じなら読み直さない」経路との差がある。［Search:264–294、Index:815–853］
- **保証しないこと**  
  raw の共有、OS の識別子の限界、同時変更、キャッシュの過去の生成過程、エージェントの迂回。CLI にしただけで、グラフや SQLite の依存先が自動で検査されるわけではない。
- **新しく生む失敗**  
  専用 CLI と単独問い合わせの機能差、MCP と異なる検索順位、モデルの繰り返し起動、CLI 出力の取りこぼし。毎回新しいプロセスでも、ディスクのキャッシュは残る。
- **変更と量**  
  `wiki_roots.py`、専用 CLI、`wiki_pages.py`、`wiki_search.py`、`wiki_graph_query.py`、必要に応じグラフ共通部品。文書は共通の変更に加え、`--both` で CLI を使う例外を書く。**中**。MCP サーバー・中継の変更を減らせる。
- **費用**  
  メタデータ検査に加え、検索では両 wiki の記事バイト列の読み取りが発生する。意味検索のモデルはプロセスごとに準備する。現コードはバックエンド取得時に `TextEmbedding` を生成するため、両 wiki で再利用するなら明示的な変更が要る。［Search:582–608、746–754］
- **決定との関係**  
  作者の決定1〜12を維持できる。MCP を優先する現在の実装方針を変更するが、CLI キャッシュを禁止したり、BM25 に固定したりはしない。

**採らない理由：** 構成を小さくできる有力案だが、既存 MCP と CLI はモデル・索引方式が異なる。CLI への固定は、分離の検査に加えて検索品質と待ち時間を変える判断になる。［Workflow:23、33］  
まず読み取り層を共通化する案Bなら、現在の検索を保ちながら検査責任を移せる。測定の結果、MCP を統合する費用が大きすぎる場合は、案Cを次点とする。

## 前提と不確実性

**作者の判断が要る点**

1. **保証の対象を、現在の wiki 記事と検索用データの分離として明記するか。**  
   本提案はその範囲である。raw を含む「回答に使うすべての実体」の分離を求めるなら、別の設計が要る。外の原本をリンクで参照してよいという決定を、本提案では変更しない。原本の共有まで拒む案は、作者の決定11・ADR決定4との関係を改めて決める必要がある。

2. **読み手を変更する実装量を受け入れるか。**  
   案Bは、小さな補助だけを足す実装ではない。代わりに、補助の合格と実際の読み取りの一致を、毎回エージェントに委ねる部分を減らせる。

3. **キャッシュの古さを、どこまで今回直すか。**  
   推奨案には、回答の証拠として返す本文・メタデータを現在の記事から取得することを含める。索引全体の鮮度、過去に共有していたベクトル、候補漏れまで閉じるなら、索引の生成元と版の記録・再構築方針が別に必要になる。識別子だけを索引の署名に足しても、同じ実体への上書きまでは検知できない。

4. **検査費用の上限をどう置くか。**  
   最初は呼び出しごとの検査と操作の一括実行を勧める。高速化のための検査結果の使い回しは、期限、無効化、サーバー再起動、CLI への引き継ぎという新しい状態を増やす。測定前には採用しない。

5. **保証を超える仕組みを求めるか。**  
   外部プロセスとの同時変更まで防ぐには、ファイルハンドルの保持、スナップショット、アクセス制限などが必要になる。会話への読み込みそのものを制限するなら、定型文を残す決定2も見直し対象になる。いずれも本提案では採用していない。

### 判定

### 致命的・重大な欠陥

1. **重大（度合い D）：`SCHEMA.md`、`log.md`、raw を Read で読むので、リンクの記事から他方の中身が入る。**
   - **反例。** A の `SCHEMA.md`（または `log.md`）が、B の同じファイルへのファイルのシンボリックリンクだとします。ハードリンクでも同じです。
     1. ADR-0029 の走査はこれを拒み、識別子の集まりに入れず、`link_warnings` に回します（実装の設計の「ページの走査」）。
     2. `list_index_both` は `disjoint` を返します。
     3. B の手順は「`roots.resolved` の下の `SCHEMA.md`、`log.md` を Read で開く」です。Read はリンクの先を読むので、B の規約を A の規約として当て、B の `log.md` を A の記録として使います。`log.md` はグラフの鮮度の判定にも使われます（`graph-workflow.md:161`）。
     4. raw でも同じことが起きます。A の source ページの `raw:` が指す `A/raw/x.md` が、B の raw へのリンクだとします。`resolve_raw()` なら `link` として拒みますが、Read は先を読みます。
   - **B 自身の記述との矛盾。** B の第 3 節の表は、`SCHEMA.md` と `log.md` を「記事として識別子に入る」としています。リンクの記事では、これは成り立ちません。「Read は `roots.resolved` の下に限る」という規則も、根の下にあるリンクには効きません。
   - この攻撃は、私の成果の raw の扱いにも当たります（自分の成果の見直しを参照）。
2. **軽微：呼び出しのたびに `graph/` と索引のディレクトリの下をすべて、リンクをたどって比べる。**
   - B の原則は「読み手が自分の開くものを比べる」です。それなのに、グラフを開かない `query_both` や `get_page_both` でも、`graph/` の下を比べる書き方になっています。
   - `graph/` の下に、無関係な大きな木へのジャンクションが 1 つあると、毎回その木全体を走査するか、一覧できない項目で `null` になって止まります。これは ADR-0029 の作者の決定の 9（記事でないリンクだけでは止めない）とぶつかります。14 版目にも同じ形があります。
3. **軽微：「確かめと読みの時刻差は 1 呼び出しの中に縮む」は、MCP の `query` では成り立たない。**
   - 返す抜粋は、メモリ上の写し（`by_locator`）から作られます（`wiki_index.py:912-914`）。
   - 写しは、署名（パス、大きさ、更新時刻のみ。`wiki_index.py:815-825`）が変わったときだけ読み直されます。そのため、前の配置で読んだ本文が、今回の確かめのあとに返ることがあります。B 自身も P9 で限界として残しています。
   - 大きさと更新時刻をそろえる作為が要るので、度合いは D です。
4. **軽微：経緯の事実と数え方が食い違っている。**
   - 結論の「12 版目で識別子の比較に替えてからは出ていない」は誤りです。識別子での比較は、2 回目のレビューのあと（設計書の第 8 節の 2 回目の表）から使っています。3 の 1、4 の 1、5 の 1 は、一部の集合の識別子を比べる形で崩れたものです。

5. **軽微：索引のディレクトリを比べる理由のうち「書き込みの安全」は、ADR-0029 と重なる。**
