## 結論

Critical と Major に当たる問題は見つかりませんでした。運用の穴にあたる Minor が 4 件あります。

初回レビューの Major（24 枚を超えると行末の枠端画像が捨てられる問題）は、`audit.fit` で解消されています。v44 の小点の判定が二閾値の片方しか見ていなかった Minor も、`strict_points.physical` で直っています。

**確かめたこと（問題なし）**
- **必須画像の保持**: `fit` は、主画像、行頭と行末の枠端、該当する段落の画像、横座標の全区間を、捨ててよい画像の集合から外しています。捨てるのは補助の拡大だけです。必須の画像だけで 24 枚を超える場合は、横座標の末尾から 2 枚ずつ縦に重ねて 1 枚にまとめます。それでも超えれば例外で止まり、黙って欠けることはありません。
- **束の作成中の照合**: `packets.prepare` の切り詰め（`name_list[1:1+discarded]`）は、`fit` が 24 枚以下に抑えるので働きません。束を作る段では `verify` フックが、送る画像の集合が `fit` の結果と一致することを照合します。このフックは `counts` を `ident` ごとに持ちます。束が満杯でやり直したとき（`G03` の失敗のあと `G01` で再試行するなど）に古い値が残っても、同じ `ident` が次に使われたときに上書きされるので、照合は崩れません。
- **結合した横座標の扱い**: 区間ごとの画像には `横座標 i` の見出しがあり、目盛りの値は枠の左端からの絶対値です（`v35-coordinate-pilot/ruler.py:28-41`）。重ねても区間の取り違えは起きません。`verify_delivery` は `07+08` の形の名前を解析して、`1..len(segments(3w))` がすべてそろっていることを確かめます。
- **縦書きの行の枚数**: v27 の 103 行では、添付の最大が 19 枚でした。v47 で枠の画像 2 枚を外し、枠端の 2 枚を足しても 19 枚で、上限に届きません。
- **450 DPI の小点（strict_points.py）**: 閾値 140 と 186 のそれぞれで候補がちょうど 1 個あり、両者が 2 画素以内で重なることを求めています。`preflight.check_rounds` の対照を手で追いました。閾値 140 では点が 2 個に分かれます。閾値 186 では値 170 の帯が一方の点とつながり、幅 36 画素の成分になって候補から外れます。このため v44 の判定は通り、strict の判定は止めます。曖昧な場面を正しく突いた対照です。隔離描画と、符号を 2022 と 30FB に限る `glyph` は、v44 の `confirm` をそのまま使っています。v44 の結果にある実例は 2 件だけで、2 件とも strict の判定で受理されています。
- **固定のハッシュ**: `preflight-complete.json` の `inputs` に記録された 12 件のハッシュは、すべて現在のファイルと一致しました。初回レビューの Minor で挙げた v24 の `run.py`、v27 と v10 の `diagnose.py` も `audit.inputs` に入っています。`point_ink.py` は v19 の `inputs()` で固定されています。

### [Minor] 正式の入口が `audit.py` であることを、どこでも強制していない

対象
- `v47-reference-audit/run.py` の `main`（そのまま実行できる）
- `protocol.md` と `method.json`（`audit.py` の記載がない）
- `audit.py:192-205`

根拠
- `run.py` を直接実行して `prepare` すると、ロック（`population-lock.json`）の `inputs` に `audit.py`、`strict_points.py`、`preflight-complete.json` が入りません。
- v27 の `verify_methods`（`v27-reference-audit/run.py:151-155`）は、ロックに記録したハッシュを照らすだけです。そのため、`run.py` で作ったロックでも後の段は通ります。
- `run.py source` で実行すると、`raster_file` は v44 の判定のままです。二閾値それぞれを求める strict の判定が使われません。
- `verify_delivery(core.sha(path))` は、ファイルのハッシュを自分自身と比べています。このため `expected` の照合は何も確かめていません。配布物との結び付けは、`transport.check(args.sha256)` だけが担っています。

問題
v27 と同じ手順で `run.py` を実行すると、枠端の保持と strict の小点判定が外れたまま、正式の抽出に進めてしまいます。ロックの中身を見れば後から気付けますが、気付いたときには標本を一度引いたあとです。

検証方法
1. `run.py prepare` の経路で `core.inputs` が `run.inputs` になることを、コードで追う。
2. そのとき `PREFLIGHT` の検査を通らないことを確かめる。

修正の方向性
- `protocol.md` か `method.json` に、正式の入口が `audit.py` であることを明記する。
- `audit.py` の後続の操作で、ロックの `inputs` に `audit.py` と `preflight-complete.json` が入っていることを確かめてから進める。`run.py` を変えずに済む。
