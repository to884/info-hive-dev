### [Major] v76 の実対照は判定する大きさの範囲の外にあり、150 DPI の判定は本当の丸と対象を分けていない

対象
- `v76-leading-shape-pilot/run.py` 116行目（大きさの絞り込み）、33行目（判定の閾値）、134行目（対照の数の検査）
- `v76-leading-shape-pilot/result.json` の `cases`
- `development-result.md` の「出典で確定した4候補…に丸以外の判定は出なかった」

根拠
- **大きさの範囲:** 116行目は、出典で確かめていない候補を、長い辺が 9〜10px のものに限っています。ところが `confirmed-source-mark` の 4 件の粗い箱は、どれも 5×5 か 5×6 です（131–136、192–197）。9〜10px の対照は disaster-p0064（`image-only`）の 1 件だけで、これは出典で確かめた丸ではありません。
- **対照の数:** 4 件の対照は、実質 2 種類です。p0267/36 と p0265/11 は、粗い密度がまったく同じ `[[0.25,0.3333,0.5,0.6667],[0.5,0.5,0.8333,0.6667]]` です。p0133/3（v27）と p0133/2（v64）も同じ値です。どれも disaster の資料で、対象の defense-p0500 の字形は対照に入っていません。134行目は、対照が 1 件あれば通ります。
- **150 DPI の分離:** 本当の丸の p0267 と p0265 は、閾値 160 で左上が 0.25 になり、条件の 0.28 以下を満たします。対角の右下も 0.6667 で、0.58 以上を満たします。つまり本当の丸が、一方の濃さでは「丸でない」と判定されています。対象の defense-p0500/84 も、閾値 192 では右下が 0.25 です。同じ 0.25 が本当の丸と対象の両方に出ているので、150 DPI では両者を分けられていません。分けているのは 450 DPI だけです（対象は 0.08〜0.09、対照はすべて 0.63 以上）。
- **左上が出やすい偏り:** 5px の箱では、左上が 2×2、右下が 3×3 になり、右下に中心の画素が入ります。そのため、左上が薄い判定が構造的に出やすくなります。

問題
- 判定を受けるのは、出典で確かめていない 9〜10px の候補です。その大きさの本当の丸で、規則を試した例がありません。
- 450 DPI の `focused()` が、隣の画やかすれと連結した成分を選ぶ場合があります。そのとき 150 DPI 側では、上のとおり本当の丸でも条件を満たし得ます。両方の解像度がそろって「丸でない」となれば、本当の丸が除かれます。
- それでも「出典で確定した4候補に反例なし」と書けば、丸を守る根拠として過大です。

検証方法
1. `result.json` の `cases[*].coarse` の辺の長さを数え、確定対照の大きさが 9〜10px に入らないことを確かめる。
2. p0267 の `coarse_density[0]` に、33行目の条件（`v<=.28 and quarters[3-i]>=.58`）を当てる。i=0 で成り立つことを確かめる。

修正の方向性
- 対照は、判定する範囲と同じ 9〜10px の、出典で確かめた丸から取る。defense の資料も含める。
- 対照は、字形の違いで数える（同じ字形と大きさのものは 1 件とする）。
- 決定の根拠を 450 DPI だと明記する。そのうえで、450 DPI の成分が連結していないこと（近傍に別の成分がないこと）も条件にする。
- 四区画の分け方は、奇数の辺で中央の行と列を除くか、両側に等しく入れて偏りをなくす。

### [Major] v80 の陰性対照は新しい受け入れ経路を通らず、背景の正体を確かめる条件もない

対象
- `v80-textured-point-source-pilot/run.py` 43–53行目（v19 の白背景の条件を置き換えた部分）、117行目
- `protocol.md` の陰性対照の記述
- `v78-point-drawing-diagnosis/result.json`

根拠
- **陰性対照:** v78 の記録では、pack-171 と pack-269 はどちらも `polarity: "dark"` です。暗い点は、52行目の `delta > 30`（文字があると明るくなる）を原理的に満たせません。

  - pack-269 の理由は「点の外側でも文字描画が変わる」です。protocol が想定した「別の図形」かどうかを判定した結果ではありません。
  - 2 件とも、新しい明るい点の経路、ToUnicode と CID の照合、`APPROVED` の検査のどこにも到達していません。陽性は pack-364 の 1 件だけです。

  - 外周 1px が変わらないこと
  - 変わった画素の 65% 以上が 30 以上明るいこと
  - 一つのオブジェクトで固定画素を再現できること

問題
次の反例が通ります。暗い円のパスの中央に、白い「・」の文字を重ねた記号です（◉ のように見えます）。
- 外周 1px は暗い円のままなので、変わりません。
- 白い文字なので、明るさの検査を通ります。
- 文字オブジェクトは一つです。

検証方法
1. `v78-point-drawing-diagnosis/result.json` で、pack-171 と pack-269 の `polarity` が `dark` であることを確かめる。
2. v80 の 52行目が、暗い点では必ず失敗することを確かめる。
3. v80 には、背景のオブジェクトを確かめる処理がないことをコードで確かめる。

修正の方向性
- 陰性対照に、明るい点の候補を入れる。少なくとも、文字でない明るい点と、図形に重なる白い文字の 2 種類にする。
- 文字を消した後の領域について、背景のオブジェクトの外接範囲が点よりも十分に大きいことを条件にする。帯や地紋のように点の何倍もの範囲に広がっていれば通し、円や記号の大きさなら保留にする。
- 背景の種類と範囲を `evidence` に記録する。

### [Minor] v80 の CID は描かれた符号を読んだ値ではなく、ToUnicode を逆に引いた値である

対象

pack-364 の CID 638 と U+30FB は、Adobe-Japan1 として整合しています。

修正の方向性
- コンテンツストリームから、その文字の位置の文字コードを直接読み、逆引きの値と照合する。
- Adobe-Japan1 では、許す CID の集合（30FB → 638 とその異体）に入っていることを求める。
- ROS を `evidence` に記録する。
