### [Major] 属性固定 SVG は複数の要素を同時に変えており、Pele SVG との約 30 MiB の差の原因を切り分けられない

対象
`docs/agent-runs/2026-11-20-pele-png-performance/prepare.cjs` 19行、30〜33行、39〜41行

根拠
- 19行の23プロパティと `font-family` を、すべての要素に計算値のまま書いています。継承される値や、要素に関係しない値も含みます。たとえば `<path>` に `font-size`、`text-anchor`、`stop-color` が付いています（`fixture/light/0-normalized.svg`）。
- 39〜41行で、Pele にはない背景の `<rect>` を先頭に足しています。
- ファイルサイズ（明暗100枚の合計）

  | 方式 | 合計 |
  |---|---|
  | pele | 226,460 B |
  | normalized | 1,017,160 B（約4.5倍） |
  | png1x | 331,384 B |
  | png2x | 702,724 B |

  属性固定 SVG は PNG 2倍よりも大きくなっています。
- WebKit の先頭画像の画面キャプチャ（`paint/*.png`）を画素ごとに比べると、pele と normalized は明暗とも差が0画素でした。描画結果は同じです。
- それでもピーク増分は大きく違います。

  | 方式 | ピーク増分（2回の中央値） |
  |---|---|
  | pele | 0.35 MiB（各回 0.39 / 0.32） |
  | normalized | 29.61 MiB（各回 29.82 / 29.41） |
  | png1x | 34.95 MiB |
  | png2x | 98.24 MiB |

  pele の2回目は最後に走ったケースで、横ばいが再現しました。
- 全方式で `round-1-light-decoded` の時点では WebKitWebProcess の増加は約 +3 MiB 以下です。増加が出るのは、最初に暗色へ差し替えた後の `round-1-displayed` からです（png2x は 207.3 → 303.4 MiB）。
  - したがって増分は「50枚を表示した状態」ではなく、「明暗の両方を一度ずつ表示した後」の量です。

問題
- 描画結果が同じ2つの SVG の間で、約 30 MiB の差があります。
- 違いは、属性の重複（約4.5倍のバイト数）、背景の rect、`style` と CSS 変数の除去の3つが同時に入っています。
- このままでは「属性を固定すると約 30 MiB と4.5倍のサイズがかかる」とは結論できません。数値は、このスクリプト固有の書き出し方の結果です。

検証方法
1. `fixture/light/0-pele.svg` と `0-normalized.svg` の属性数とバイト数を比べる。
2. `memory/*-case.json` の checkpoint `empty` と `round-1-displayed` で、WebKitWebProcess の `private_bytes` を方式ごとに比べる。
3. `paint/pele-1-light.png` と `normalized-1-light.png` を画素ごとに比べる。

修正の方向性
- 対照の試料を足して、どの要素が効いているかを分ける。
  - 「Pele SVG に背景 rect だけを足したもの」
  - 「親と異なる計算値だけを書いた、最小限の属性固定 SVG」
- それができない場合は、報告で normalized を「全プロパティを全要素に書いた、この書き出し方の SVG」と明記する。属性固定という方式一般の評価として扱わない。
- 増分は「明暗を一度ずつ表示した後」の量だと定義に書く。
