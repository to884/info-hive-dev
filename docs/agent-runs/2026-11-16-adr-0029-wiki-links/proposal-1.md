**致命的な欠陥は確認できなかった。重大な契約欠落が1件残る。加えて、実装次第で重大になる未決の契約が1件ある。** 作者の決定1〜8を変更せずに修正できる。

### 1. 重大：読めない source ページの `raw:` が、書く段の原本保護からも落ちる

第10版は、リンクの記事を読まないことと、ADR-0023 の raw 保護を維持することを決めている。しかし、**リンクで拒んだページの原本依存を、書く段がどう扱うか**を決めていない。

反例となる配置は次のとおり。

```text
W = C:/data/wiki

W/sources/s.md
    外部ファイルとのハードリンク
    frontmatter:
      type: source
      raw: concepts/original.md

W/concepts/original.md
    通常ファイル、リンク数1、書き込み可能
    s.md が参照する原本

W/.wiki-cache/apply/raw-roots.json
    この依存を補える記録はない
```

これは、書く段の設計が扱っている「wiki の中に置いた原本」に当たる。`raw: original.md` のような配置も、同設計は明示的に想定している。[書く段の設計：673〜683、700行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/plans/wiki-apply-2026-11-14.md:673)

手順は次のようになる。

1. 新しい走査が `sources/s.md` をハードリンクとして拒む。
2. 走査結果には `concepts/original.md` が残り、`s.md` の本文は読まれない。
3. 書く段が、その可読ページ集合から `raw:` を集めると、`concepts/original.md` を保護対象として認識できない。
4. `concepts/original.md` への `edit` を用意する。行き先自体は通常ファイルなので、下層のリンク検査では拒めない。
5. 上層の `raw_in_wiki` 検査にも、このパスが入らず、原本の置き換えを許す実装になり得る。

根拠は三つある。

- ADR はハードリンクの記事を拒み、`Walk.links` にはパスと種類を返す。直接読む場合も同じ拒否を適用する。[ADR：161〜169行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/adr/0029-wiki-and-raw-hold-no-links.md:161)
- 指定版の `walk_pages()` は走査結果からページ集合を作る。`wiki_search.collect_pages()` も、列挙されたページだけを読み、そこからメタデータを得る。[wiki_pages.py：301〜327行](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_pages.py:301)、[wiki_search.py：264〜324行](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_search.py:264)
- 書く段は全ページの `raw:` から保護集合を作り、その集合で wiki 内の原本への書き込みを拒む。ADR-0029 は、この上層の契約を維持する。[書く段の設計：673〜681行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/plans/wiki-apply-2026-11-14.md:673)、[ADR：195〜197行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/adr/0029-wiki-and-raw-hold-no-links.md:195)

`link_warnings` を返すだけでは、原本保護用の情報が欠けたことを、書き込み拒否へ結び付けられない。検索結果から消すことと、保護すべき依存が存在しないことが混同されている。

**確定しているのは契約の欠落である。実際の原本置換は、未実装の `Writer` が可読ページ集合をそのまま使った場合の静的反例であり、実行結果は推測となる。** ただし、規則違反の配置での書き込みを扱うという本節の目的から、この条件を実装者任せにはできない。

過去のレビューには、この「走査の拒否による raw 保護情報の消失」という指摘はない。

### 2. 重大候補・推測：相対 `raw:` の参照先が一意に決まらない

これは、過去レビューの「raw の根を推し量る問題」と異なる。**根を渡しても、相対参照の基準位置が複数ある**という問題である。

例えば、次の履歴と配置を考える。

```text

過去の R   = C:/data/archive/raw
現在の R   = C:/data/raw

source の raw:
    archive/raw/session.md

実際に保存した raw:
    C:/data/archive/raw/session.md       ハードリンク

同名の別ファイル:
    C:/data/wiki/archive/raw/session.md  通常ファイル
```

セッションの `raw_ref_of()` は wiki の親を基準にするので、この `raw:` を実際に生成する。[wiki_session.py：1250〜1256行](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_session.py:1250)

一方、現行の `missing_raw()` は、次の三つの候補の**どれかが存在すればよい**という存在検査である。

```text
W / raw
W.parent / raw
source_page.parent / raw
```

解決した参照先を返す関数ではない。[wiki_lint.py：213〜241行](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_lint.py:213)

この存在検査を、新しいリンク検査の参照先選定へ流用すると、最初に存在した通常ファイルだけを調べ、実際の raw のハードリンクを見逃し得る。全部を調べる場合も、「どれが原本で、どれが同名の無関係なファイルか」は決まらない。

ADR は過去の raw も検査すると定めるが、この曖昧さをどう返すかは定めていない。[ADR：62〜64、140行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/adr/0029-wiki-and-raw-hold-no-links.md:62)

**新しいリンク検査は未実装なので、見逃す実装になるとは断定できない。重大候補とした理由は、原本の同定に使えない存在検査が、参照先の契約として残っているためである。**

## 修正案

### 1への修正：可読ページ集合と、保護情報の完全性を分ける

採る案は、走査と参照収集の結果に、少なくとも次を区別させることである。

```text
読めた記事
リンクで拒んだ項目
調べられなかった項目
原本保護用の依存を完全に収集できたか
```

そして、ADR に次の不変条件を加える。

> 記事を読まなかったことを、その記事からの原本参照が存在しない根拠にしてはならない。原本保護に必要な依存を完全に収集できなければ、書く段は書き込まない。

これなら、検索や閲覧はリンクを飛ばして続けられる。書く段だけが、既存の原本保護を証明できない理由で停止する。作者が退けた「全コマンドで事前検査し、リンクがあれば一律停止」へ戻す必要はない。

長期案として、raw の参照を独立した台帳に残す方法もある。ただし、既存ページ、手編集、台帳更新前の中断まで含めて完全性を保証する仕組みが増える。**まずは依存収集の不完全を明示して停止する案を採る。** 台帳による継続は、必要性が実測されてから検討できる。

試験では、リンクのページが検索から消えることに加え、**そのページを拒んだあとも、参照先原本への書き込みが許可されないこと**を確かめる。

### 2への修正：存在検査から、共通の raw 参照解決へ移す

参照の解決を、lint、問い合わせ、書く段で共用する。結果は単なるパスや真偽値にせず、次を区別する。

- 一意に決まった参照
- 存在しない参照
- 複数候補がある参照
- 調べられない参照

既存の形式について、生成元の仕様から基準を確定できるものは、その基準で解く。例えばセッションの `raw_ref` は wiki の親基準である。確定できない既存参照は、候補と理由を返し、勝手に一つを選ばない。

lint は曖昧さを未確定として通知する。書く段は、原本保護に必要な曖昧さが残れば停止する。新規保存では基準が一意になる形式を使い、既存参照の互換処理を増やさない。

新規保存をすべて絶対パスにする案もあるが、既存参照の曖昧さは残り、保存形式の変更も広い。**共通の解決契約と、曖昧さを明示する案を先に採る。**

## 全体の見立て

5回の却下は、リンク禁止という核の決定が毎回崩れた結果ではない。レビュー記録と改訂履歴からは、**対象集合、検査の起点、操作の許可、結果の通知を、別々の箇所で定義していたこと**が原因と読める。

- 第1回は、書き手の列挙と一時ファイルの変更だけでは、途中のリンクを扱えなかった。
- 第2・3回は、`Writer` を流用・分割すると、領域や根の意味が変わった。
- 第4回は、走査だけを変更しても、直接読む経路と記事の分類がそろわなかった。
- 第5回は、拒否条件と通知を足しても、行き先のハードリンクや別のツールまで契約が届かなかった。

そのたびに局所的な説明、例外、試験を追記したため、決定の根拠と実装仕様の両方が ADR に蓄積した。[改訂履歴](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/adr/0029-wiki-and-raw-hold-no-links.md:8)

今回の原本保護の欠落も同じ構造である。走査で返すページを減らした変更が、その集合を使う原本保護に及ぶことを、別の契約が捉えていない。

また、「変えたあとの走査が返すページ」を記事の定義にすると、拒否した項目と、その下の読めない記事の位置付けが曖昧になる。[ADR：57〜59行](C:/Works/info-hive-dev/.claude/worktrees/adr-wiki-links-4ebc39/docs/adr/0029-wiki-and-raw-hold-no-links.md:57) **対象になる名前の規則と、実際に読むことを許した集合を分ける必要がある。** 実装上の判定を一か所に置く方針は、そのまま維持できる。

## ADR を小さく閉じる案

ADR には、作者の決定を整理した次の不変条件と、適用境界を残す。

1. 対象はページ、索引、`log.md`、`SCHEMA.md`、対象となる `raw:` と、その途中の道である。記事以外はリンク禁止の対象にしない。
2. 対象のリンクは読まず、たどらず、置き換えず、利用者へ理由を通知する。
3. 外部ソースの取り込みは、先の中身を新しい通常ファイルとして保存する。管理対象内の違反リンクは修復しない。
4. 対象の判定、直接読み取り、走査、保存は、共通の入出力境界を使う。拒否や未確認を、通常の不在や空集合に変換しない。
5. 原本保護など、完全な依存情報を必要とする操作は、その情報を収集できなければ書き込まない。
6. 外部 PDF、根と祖先、mount、一時ハードリンクの例外、および既存 ADR との関係を明示する。作者が決めた書き込み側の厳しい検査も維持する。

共通部品は、概念上、次の操作を受け持つ一つの境界にする。

```text
記事を列挙する
記事を指定して読む
内容を保存する
```

各操作は、内容や成功結果とともに、拒否理由と必要な完全性の状態を返す。内部で走査、リンク分類、書き込み処理に分けてもよい。呼び出す側が、根の除外、リンク判定、警告の組み立てを再実装しない構造にする。`Writer` は、その境界の上で取引と raw 保護を担う。

線引きは次のようにする。

| ADR に残す | 実装設計書と試験へ移す |
| --- | --- |
| 対象、拒否時の振る舞い、例外、完全性の条件 | 関数名、引数、JSON の欄、例外型 |
| 共通部品を通す責任 | 各書き手・読み手の移行一覧 |
| `Writer` と共通部品の責任分担 | a〜e の配置、起点の渡し方、初期化順序 |
| 外部 PDF と既存 ADR の扱い | CLI・MCP・browse への警告の配送方法 |
| 保証の範囲と制約 | OS 別判定、属性、復旧手順、試験行列 |

現在の「影響」「今ある wiki と raw の直し方」、OS の観察結果、詳細な試験一覧は、実装設計書・運用文書・調査記録へ移せる。レビューの全文と版ごとの経緯も、既存のレビュー記録を参照すればよい。

ADR の承認までに必要なのは、上の不変条件が互いに矛盾しないことと、既存の原本保護との接続を決めることである。個々の API や OS 別手順の成立は、実装設計と試験で確かめる。
