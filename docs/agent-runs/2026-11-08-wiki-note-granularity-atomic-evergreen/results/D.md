実在ソースを使う試案では、オントロジー連載は既存の用語ページを更新し、SemaSynth の 2 本から知見 4 ページと案内用の 1 ページを作る構成に絞りました。併せて、索引の「シンセシス」欄に `type: source` のページが 16 本混在していることを確認したため、移行では記事の分割より先に索引の分類を整える案にします。
## 結論

- **Atomic Notes と Evergreen Notes を、LLM による保守向けに変更して採用する。推奨は候補③の併用案である。**
- 用語・エンティティのページを残し、独立して再利用・更新できる知見だけを「条件付きの主張」単位でページ化する。
- `/wiki:ingest` に「主張の抽出 → 既存ページとの照合 → 配置判定 → 判定結果の保存」を追加する。題名だけで単位を決めない。
- `type` は増やさず、Markdown を正本とする。グラフの `claim` ノードは必要な場合だけ使う。
- 既存 56 ページは段階的に扱う。指定重みでは併用案が首位だが、コスト重視では候補④が上回るため、採用範囲は PoC で確かめる。

## 根拠

**1. 原典から採る原則と、変更する原則**

Atomic Notes は、文を短く切る技法ではなく、関連する内容をまとめながら、異なる論点を分離する考え方として読むべきである。Matuschak 自身も、細かすぎるノートはリンクのつながりを断片化し、唯一の判定テストはないと述べている。[Evergreen notes should be atomic](https://notes.andymatuschak.org/Evergreen_notes_should_be_atomic)

| 原則 | 確認した内容・出典 | LLM が保守する wiki での判定 |
|---|---|---|
| 1 ノート 1 アイデア | Christian Tietze の原子性の説明は、まとまりを保ちつつ関心事を分離するもの。論証と結論を一緒に置く例がある。[原子性の説明](https://zettelkasten.de/posts/create-zettel-from-reading-notes/) | **変えれば保てる**。「1 文」「1 トリプル」ではなく、独立した問いに答える知見を単位にする |
| Luhmann の固定識別子・相互参照 | 固定番号、分岐、相互参照、キーワード索引、書誌情報との接続を確認した。[Communicating with Slip Boxes, §II](https://luhmann.surge.sh/communicating-with-slip-boxes) | **保てる**。スラッグを安定させ、題名の推敲による改名を避ける |
| Ahrens の literature note と permanent note | 著者の公開試読版は確認できたが、分類と「1 ノート 1 アイデア」の該当本文までは確認できなかった。[著者公開の試読版](https://www.soenkeahrens.de/s/2022-HTTSN-Preview.pdf) | **原典の該当箇所は未確認**。下記の対応表では役割上の区別として用いる |
| concept-oriented | 著者・本・プロジェクトごとに閉じず、複数の文脈から同じ考えへ知識を集める。[原文](https://notes.andymatuschak.org/Evergreen_notes_should_be_concept-oriented) | **保てる**。source から concept への配置判断を必須にする |
| densely linked | 関係を考えてリンクを作り、既存ノートを読み直す。[原文](https://notes.andymatuschak.org/Evergreen_notes_should_be_densely_linked) | **変えれば保てる**。リンク数の達成ではなく、関係の説明を求める |
| 題名で主張を明確にする | 完結した句を推奨するが、問い、用語の定義、アウトラインは例外として認めている。[題名の原則](https://notes.andymatuschak.org/zLhoRUyjKU665EY16u4XXJy) | **変えれば保てる**。知見ページは主張文、用語ページは名詞、synthesis は質問・話題を許す |
| 時間をかけて育つ | プロジェクトをまたいで発展し、貢献し、蓄積する。[Evergreen notes](https://notes.andymatuschak.org/Evergreen_notes) | **変えれば保てる**。新しい出典・反例・利用結果を更新契機にする。新情報なしの書き直しは成長と数えない |
| 自分のために書く | 公開原稿としての完成度を初回から求めない。[原文](https://notes.andymatuschak.org/Write_notes_for_yourself_by_default,_disregarding_audience) | **変えれば保てる**。「作者の将来の判断と、次のモデルが使うため」と読み替える。適用条件は省略しない |
| 執筆による理解・内面化 | 人が書いて考える実践としての側面 | **そのままでは保てない**。LLM が生成したことは、作者が理解したことの証拠にならない |

「Atomic Notes は Luhmann が定式化した名称」「Luhmann の原則は厳密に 1 主張 1 枚だった」とは断定しない。今回確認した本人の文章では、その明示的な規則を確認できなかった。

また、**literature note と permanent note は、必ずしも排他的な保存分類ではない**。本稿では便宜上、前者を「出典が何を述べたかを保持する記録」、後者を「出典を越えて再利用する主たる知識ノート」として区別する。Ahrens の分類の厳密な再現を、info-hive の仕様にする意図はない。

**2. 現状の確認結果**

提示されたページ数は、ファイルの配置と `type` を読み取って再確認できた。

- `source` 37、`entity` 1、`concept` 17、`synthesis` 1、合計 56 ページ。
- SemaSynth の source は 28 本。source 全体の `28 ÷ 37 ≈ 75.7%`。
- 全ページに占める source は `37 ÷ 56 ≈ 66.1%`。
- `indexes/` 内の Markdown はなく、単一の `index.md` を使っている。

ただし、判断に関係する補足がある。

| 確認事項 | 判断への影響 |
|---|---|
| 作者の `SCHEMA.md` は、ソフト上限 **4,000 文字または 400 行**、ハード上限 **8,000 文字または 800 行** | プラグイン既定の 10,000／25,000 文字を作者の wiki に適用してはならない |
| `index.md` の「シンセシス」欄に、実際には `type: source` のページが **16 本**ある | 索引の見出しから種類を推定すると、配置判断を誤る。先に索引の分類を整える |
| `concepts/オントロジー.md` は複数ソースを統合している | 現行の concept が育っていないわけではない。用語ページを全面廃止する根拠はない |
| `concepts/編集要求の復元世代を最終適用まで保持する.md` は、理由・三つの境界・適用範囲を持つ | 主張を題名にしたページは既存設計の中で成立している |
| SemaSynth の raw には、独立した期待値、環境別の一致条件、CSV の情報欠落などが明示されている | source 偏重は、知見の材料不足だけでは説明できない |

根拠は作者 wiki の `SCHEMA.md`「ページの大きさ」、`index.md`「シンセシス」、後掲の W1〜W4・R1〜R3。ここでの比率は偏りの記述であり、望ましい source 比率の目標値ではない。

**3. 既存の種類との対応**

| 既存の種類・配置 | ノート手法との対応 | 採用後の扱い |
|---|---|---|
| raw | 原資料。literature note そのものではない | 不変の根拠として維持 |
| `source` | literature/reference note に近い | 出典単位の要約、出典固有の主張、知見の配置記録を保持 |
| `entity` | 対象を識別する reference note。必要に応じて案内も担う | 人・製品等の同一性を中心に保つ。主張文の題名を強制しない |
| 用語を説明する `concept` | 定義ノート＋structure note／MOC の一部 | 定義と論点への案内を担う。知見の本文を重複して抱えない |
| 主張を説明する `concept` | permanent／evergreen note に近い | 一つの条件付き主張を、根拠・適用範囲・反例とともに育てる |
| `concept`＋`kind: experience-pattern` | 経験から得た permanent note | 観測と原因仮説を分け、既存の `status` を維持 |
| `synthesis` | 問いへの統合的回答、論証、比較 | 複数の主張をまとめてよい。一主張制約をかけない |
| `index.md`、`indexes/` | 目録・入口 | 一ページ一行を維持。論点の関係を説明する MOC とは区別 |

**欠けているのは新しいディレクトリではなく、役割の明示と昇格手順である。**

具体的には、用語ノートと知見ノートの区別、source から取り出した知見の配置先、保留理由が不足している。`permanent/`、`evergreen/`、`claims/` を一度に追加する必要はない。

**4. 推奨するページ単位**

知見ページの定義を、次のようにする。

> 一つの適用範囲について、一つの再利用可能な問いに答える主張と、その主張を理解・検証するための根拠、理由、例外を扱う。

「結論」「理由」「反例」「適用範囲」は通常、別ページにしない。一方、理由の一つが別の問いへの答えとして独立して使われ、別々に更新されるなら切り出す。

用語ページは「その用語は何か」、エンティティページは「その対象は何か」、synthesis は「この問いへの回答は何か」を単位にする。全種類に同じ原子性を要求しない。

**5. `/wiki:ingest` に追加する判定手順**

以下は提案する運用規則であり、原典に存在するアルゴリズムではない。

| 順序 | モデルが確かめること | 処理 |
|---|---|---|
| 0 | どの `SCHEMA.md`、原本の版、既存 wiki の状態を入力にするか | 規約と入力を固定する |
| 1 | 原本は何を主張・観測・提案しているか | 主な知見を候補として抽出。条件、結論、根拠位置、観測／提案の区別を記す |
| 2 | 同じ対象・関係・結論・適用範囲を扱うページや節があるか | 索引と検索で候補を絞り、本文を読む。題名の一致だけで判断しない |
| 3 | 既存の主張と同じか、補足か、異なる条件か、矛盾か | 同じ主張なら既存ページを更新。異なる条件を矛盾と扱わない |
| 4 | 単なる定義、属性、例、作業の進捗か | 用語・entity の節、または source に置く |
| 5 | 原資料から独立して説明でき、根拠と適用範囲を示せるか | できなければ source に留め、不足を記録 |
| 6 | 下記の昇格条件を満たすか | 満たせば知見ページ。満たさなければ既存ページ内の節、または source に保留 |
| 7 | 一緒に置いた主張は別々に否定・更新できるか | 独立した問いに答えるものだけ分ける。根拠・例外を機械的に分けない |
| 8 | 配置先、出典、被リンク、索引、サイズは整合するか | 局所更新し、判定結果を source に残す |

**知見ページへの昇格条件**

次の三条件をすべて満たす。

1. **根拠がある**：原本の位置を示せる。モデルの推論を含む場合、その部分を区別する。
2. **独立した答えになる**：主張、適用条件、根拠または理由を書ける。元資料の名前だけを知っていないと理解できない形ではない。
3. **独立して使う理由がある**：次のいずれかが成立する。
   - 複数のソースから同じ判断・問題に関する知見が集まっている。
   - 既存の別ページから、定義の参照を越えて、その主張を参照する必要がある。
   - 一つのソースでも、条件と判断規則、または再現した失敗と対処案が明示されている。

「今後役立ちそう」だけでは昇格させない。ただし、二ソース必須にすると SemaSynth のような一回の重要な障害が埋もれるため、単独ソースからの昇格は認める。その場合は証拠の範囲を狭く書く。

**配置判断を残す**

`source` 本文に、例えば次の表を置く。長い引用や知見本文の複製は避ける。

| ID | 知見 | 原本の位置 | 配置 | 対象 | 理由 |
|---|---|---|---|---|---|
| `c01` | 同一環境と異環境では再生成の一致条件を分ける | raw 第 7 行 | `create` | 対応する知見ページ | 判断規則が明示され、レビュー記録にも現れる |
| `c02` | 実行環境に Git 情報がなければ推定しない | raw 第 5 行 | `source_only` | 当該 source | 現時点では manifest 記録方式の詳細として保持 |
| `c03` | CSV の NULL と空文字の区別には外部情報が必要 | raw 第 13 行 | `create` | 対応する知見ページ | 別の復元判断で独立して使う。別ソースにも関連記述あり |

`ID` は当該 source 内で不変にする。ページの同一性は配置先のスラッグで保持する。同じ原本を再処理するときは、既存の対応を出発点にし、変更には理由を必要とする。

保存するのは配置の結論と短い理由であり、モデルの内部思考過程ではない。

**6. 境界事例と裁定**

| 境界事例 | 裁定 |
|---|---|
| 「OWL は記録のない事実を不明と扱う」を新規の主張ページにするか | 現在の `オープンワールド仮定.md` がその問いに答えているため、**既存ページを更新**する。主張文への言い換えだけで重複を作らない |
| 「同一環境ではバイト一致」「異環境では値・型一致」を二ページにするか | 「実行環境に応じて再現性を何で判定するか」という一つの判断規則なので、**一ページ**に置く |
| 会計期間の誤りと部門名交換の誤りを別ページにするか | 両方とも「検証対象同士の整合だけでは独立した正しさを確認できない」という知見の**反例として同居**させる |
| 原因、対処、失敗例で見出しが五つになったら分割するか | **見出し数だけでは分割しない**。同じ主張を支える役割なら維持する |
| 「当日のテストが 386 件通った」を永久的知見にするか | **source に保持**する。そこから根拠なしに一般的な設計原則を作らない |
| 後続作業で「未実装」が「実装済み」になった | 同じ対象の時点更新。通常は **`contradicts` にしない**。過去時点の状態を保ち、現在の状態への参照を足す |
| 仮説の適用範囲が一実装から一般的な並行処理へ広がる | 自動的に題名を一般化しない。範囲拡張の証拠を確認し、必要なら別の仮説として扱う |

これらの例は `page-conventions.md` に固定例として置く。モデルごとの自由な解釈を減らすには、抽象的な「アトミック」の説明より、判断の分かれる例の共有が効くという推論である。

**7. 日本語の題名とスラッグ**

- 知見の題名は「対象＋条件＋結論」を基本にする。「〜について」「〜の考察」だけでは終えない。
- 原本の確実性を強めない。観測、設計上の提案、著者の主張を本文冒頭で区別する。
- 用語・entity の題名は名詞を許す。否定命題が必要な知見を、肯定形にするために歪めない。
- 表示用 `title` とスラッグは分ける。表示用の空白や英大文字を、ファイル名にそのまま持ち込まない。
- スラッグは既存の NFC、英小文字、空白禁止、記号禁止、全 wiki 内一意の規則を維持する。
- 新規スラッグは **60 コードポイント以内を目安**とし、超過は警告にする。これは提案値であり、Windows の完全パス長を保証する値ではない。
- 題名を改善してもスラッグを毎回変えない。改名が必要なら被リンクと索引をまとめて更新する。`aliases` だけで旧 wikilink が必ず解決するとはみなさない。

実在の資料から作った例は次のとおり。すべて新規作成するという意味ではない。

| 題名 | スラッグ例 | 根拠・配置 |
|---|---|---|
| オントロジー | `オントロジー` | R1 第 23〜41 行。既存の用語ページを維持 |
| オープンワールド仮定 | `オープンワールド仮定` | R1 第 57〜65 行。既存ページを維持 |
| 再生成の一致条件は実行環境に応じて分ける | `再生成の一致条件は実行環境に応じて分ける` | R2 第 7 行、R3 第 19 行。新しい知見候補 |
| 会計データの検証には生成結果と独立した期待値を使う | `会計データの検証には独立した期待値を使う` | R3 第 15〜17 行。観測と対処案を分ける |
| 基準 manifest のハッシュ照合は基準自体の信頼を前提とする | `基準manifestのハッシュ照合は基準の信頼を前提とする` | R3 第 22 行。保証範囲の知見 |
| CSV の NULL と空文字の復元には列の規則か期待値が必要である | `csvのnullと空文字の復元には外部情報が必要である` | R2 第 13 行、R3 第 30 行。対象の CSV 方式を本文で限定 |
| 編集要求の復元世代を最終適用まで保持する | 既存スラッグを維持 | W4。既に成立している知見ページ |

長い主張を文中へ何度も埋め込む必要はない。例えば、

```markdown
再現性の判定には、[[再生成の一致条件は実行環境に応じて分ける|環境別の一致条件]]を使う。
```

とする。表示名を短くしても、条件や否定を逆転させない。主張全体を読ませたい箇所では、一覧の一項目として完全な題名を表示する。

**8. frontmatter の変更案**

`type` は現行の四種類を維持する。`concept` の役割を表すため、`kind` に次を追加する。

| `type` | `kind` | 意味 |
|---|---|---|
| `concept` | `topic` | 用語の定義と、その用語に関する知見への案内 |
| `concept` | `claim` | 条件付き主張を一つ扱う知見ページ |
| `concept` | `experience-pattern` | 既存どおり、経験から得たパターン |

既存の `kind` 未指定ページは有効なままにする。`entity` の `kind` は変更しない。

新規知見ページの例は次のとおり。

```yaml
---
type: "concept"
kind: "claim"
title: "再生成の一致条件は実行環境に応じて分ける"
claim: "同一環境ではバイト一致を、異なる環境では値と型の一致を判定する"
scope: "SemaSynth の SQLite データと CSV の再生成に関する設計"
sources: ["semasynth再現性の検証-2026-11-06", "semasynth-mvp設計の敵対的レビュー-2026-11-06"]
tags: ["手法"]
created: 2026-11-08
updated: 2026-11-08
---
```

`claim` と `scope` は追加提案である。本文には説明・根拠・反例を書く。`claim` が一フィールドであることは、意味として一主張である保証にはならない。

`experience-pattern` の `status: hypothesis|supported|superseded` は維持する。「失敗を再現した」と「提案した対処の有効性を検証した」を区別し、前者だけで対処を `supported` にしない。一般の `claim` に、この status を無条件に流用しない。

source には任意の `note_policy: "atomic-evergreen-v1"` と、配置判定時の入力ハッシュを記録する案が考えられる。ただしハッシュは、元 HTML とモデルが読んだ raw 本文のどちらを指すかを明記する。同一 HTML のハッシュだけでは、訳文を含む入力の同一性を保証できない。

方針 B に合わせ、書き出すキー・値は英語とし、新しいキーと `kind` の日本語別名を `wiki_text.py` とスキーマの対応表に加える。

| 対象 | 改訂の要点 |
|---|---|
| `ingest-workflow.md` | 手順 2 の後に知見候補の抽出、手順 4 に意味と適用範囲の照合、手順 5 に配置記録、手順 7 に昇格条件を追加 |
| `page-conventions.md` | 種類別の単位、`topic`／`claim`、境界事例、題名とスラッグの分離を追加。「五つの小見出し」は分割命令ではなく見直しの手掛かりとする |
| `SKILL.md`、`architecture.md` | 「すべて一コンセプト」の説明を種類別の単位へ合わせる |
| `SCHEMA.md.template`、`page.md.template` | 用語・知見の役割と本文構成を追加。既存の英語の検出用見出しは維持 |
| `commands/ingest.md` | 抽出と配置判定を省略しないことを明記。詳細は reference に集約 |
| `query-workflow.md` | 問いが用語定義なら `topic`、判断・原因なら `claim` を優先候補とする。どちらも必ず本文を確認 |
| `commands/learn.md`、`evolution-workflow.md` | 同じ粒度基準を使うが、経験の証拠・状態管理を維持。ingest の一般主張と混同しない |
| 索引 | 一ページ一行を維持。主張ページも索引から省かない。分割は実際の 150 ページ／300 行等の閾値で行う |
| 検索 | セクション単位の検索を維持。見出し内の主張でも検索できるため、検索可能性だけを理由にページ化しない |
| `str_replace` | 照合したページと節に限定して更新。主張・適用範囲・出典の対応を壊さない |
| `lint-workflow.md`、`commands/lint.md` | 構造検査と意味検査を区別し、原子性を「機械検査済み」と誤報しない |

現行の raw 再確認、局所更新、矛盾を黙って上書きしない規約は、そのまま利用できる。`ingest-workflow.md` 手順 6 と「避けるべきパターン」が根拠である。

**グラフでは追加の注意が必要である。**

- 現行の `ontology.yaml.template` では、`contradicts` と `supersedes` の対象型に通常の `concept` が含まれていない。`kind: claim` を付けるだけで、そのエッジを書けるようにはならない。
- `wiki_graph_extract.py::derive_node_type` は明示的な `graph.node_type` を優先する。そのため、型付き関係を必要とする知見ページだけを `graph.node_type: "claim"` とする余地はある。
- 文書の「`claim` はページを持たない」という説明と、明示的なノード型を受け付ける実装は整理が必要である。
- 全知見ページに `graph:` を付けると、型付きエッジのないページが `orphan_typed_nodes` に挙がる。無条件には付けない。
- `mentions`、`sourced_from` を使うだけでも併用案は成立する。グラフを有効にしない wiki でも同じ手順で運用できる。

同じ主張の表現改善・根拠追加は同じページを更新する。両立しない主張は双方を保持する。旧主張が明示的に置き換えられた場合にだけ `supersedes` を使う。取り込み日時の新しさを、主張の優劣や置換の根拠にしない。

また、二つの原本を比較してモデルが矛盾と判断しただけでは、関係自体を明示的な引用が裏づけるとは限らない。現行の証拠契約に収まらなければ、まず本文の「矛盾」に記録し、型付きエッジを無理に作らない。これは ADR-0009 の「グラフは任意の索引」という位置付けとも整合する。

**10. lint で検査できるもの**

現行 `wiki_lint.py` は、サイズ、リンク、frontmatter、重複スラッグ等を検査する。**見出し数による原子性判定や、意味上の主張数の判定は実装されていない。** 根拠は `lint()` の検出項目とサイズ検査、P4。

| 指標 | 機械検査の扱い |
|---|---|
| `kind: claim` に `claim`、`scope`、非空の `sources` がある | 必須項目として検査可能 |
| `claim` が一つのスカラーである | 検査可能。ただし意味上の主張数とは別 |
| 配置表の候補すべてに配置・対象・理由がある | 形式を固定すれば検査可能 |
| 配置先ページや指定した節が存在する | 検査可能。節の検査は追加実装が必要 |
| source と知見ページの出典・本文リンクが対応する | 検査可能 |
| 本文からの被リンクが少なくとも一つある | 現行検査を利用。source からのリンクも認める |
| 索引の分類とページの `type` が一致する | 追加すると今回の 16 件を検出できる |
| スラッグ、NFC、禁止文字、長さ | 形式検査。長さは警告 |
| `SCHEMA.md` に従った文字数・行数 | 現行検査を利用。引数の既定値を盲目的に使わない |
| 説明用の節を除いた知見見出し数 | 分割候補の警告。自動分割はしない |
| 題名が名詞句、接続詞や述語を複数含む | 参考警告にとどめる。日本語の文末判定を必須条件にしない |
| 同義の重複、根拠からの飛躍、適用範囲の脱落 | 意味検査が必要。語彙・埋め込みは候補抽出に使う |

引用の文字列一致も、主張が引用から導けることの証明ではない。構造 lint の合格と、知識の妥当性を分けて報告する。

**12. 再現性を確かめる PoC**

「同じソースをもう一度取り込む」には、二つの異なる試験が必要である。

1. **反復処理の安定性**：一度配置した wiki に同じ入力を再処理し、重複ページや不必要な改名が生じないか。
2. **独立判断の一致**：同じ初期 wiki、同じ原本、同じ規約を別モデル・別実行に渡し、同じ配置に到達するか。

保存済みの配置表を再利用して一回目の試験に合格しても、二回目に合格したことにはならない。

PoC は次のように行う。

- 作者 wiki の固定スナップショットと R1〜R3 の原本を使う。実際の wiki への書き込みは許可しない。
- 現行案、推奨併用案、ページ内主張案を比較する。
- 各案について二モデル×三回×三ソースを実行し、配置計画を出す。計 **54 件**。
- モデル、規約、原本、検索索引、提示順を記録する。ほかの実行結果は渡さない。
- 原本上の候補知見を人が対応付け、表現違いと意味違いを区別する。
- 同じ処理の再実行と、R2→R3／R3→R2 の順序差も別に確かめる。
- 最後に「異なる SQLite 版で何を一致させるか」「年度外データが検証を通った理由は何か」など、事前に固定した質問で再利用性を比べる。

| 指標 | 計算・意味 |
|---|---|
| 知見抽出の precision／recall | 正解候補との一致から計算。空の配置案で一致率を稼ぐのを防ぐ |
| 配置先一致率 | 同じ知見が同じ既存ページ・同じ新設単位・同じ保留区分に入った割合 |
| 同居判定の F1 | 候補知見の対について「同じページに置く」を比較。ページ名の表現差を除ける |
| 題名・スラッグ一致率 | 意味の一致と、文字列の一致を別々に報告 |
| 重複率 | 意味が同じなのに複数ページになった件数÷作成ページ数 |
| 反復処理での増分 | 同じ入力の二回目に増えたページ・ID・不要な改名の件数 |
| 根拠・条件の保持率 | 各主張に必要な原本位置と適用条件が残っている割合 |
| 検索・回答の成績 | 必要な知見を取得できた割合、誤った一般化、読んだページ数 |
| コスト | 入出力トークン、読取・更新ページ数、処理時間、追加ページ数 |

同居判定では、全候補が単独ページになると比較対象の正例がなくなるため、それだけで合格にしない。配置先一致率、抽出 recall、ページ数を併記する。

暫定の合格目安は、知見 recall 90%以上、配置先一致率85%以上、同居判定 F1 0.90以上、同じ入力の再処理による重複ゼロとする。**これらは提案する評価目標であり、実測値でも達成保証でもない。** 主張の裏づけと条件保持は別の必須条件にする。

**13. 移行**

一括分割は行わない。

1. **索引の整合を先に直す。** 「シンセシス」欄の source 16 本を、ファイルの `type` に合わせて分類する。
2. **現行 56 ページを有効なまま残す。** `kind` 未指定をエラーにせず、raw と既存スラッグを維持する。
3. **上記三ソースで試す。** 配置表と五つの新規候補を評価する。
4. **SemaSynth の残りを、利用した順に見直す。** クエリで使った source、繰り返し現れる障害・判断を優先する。
5. **用語ページは必要になったところだけ分離する。** 独立して更新する知見を切り出し、元ページには短い説明とリンクを残す。
6. **規約の適用範囲を広げる。** 効果を確認してからテンプレート・コマンド・lint に反映し、ユーザーに見える変更として版と CHANGELOG を更新する。

既存ページの空白入りスラッグ等は、今回の主張単位の導入とは別の移行事項にする。一括改名を抱き合わせない。

## 検討した代替案

**採点**

点数は設計上の見積もりであり、ベンチマーク結果ではない。1 は大きな問題が残る、5 は対策を必要とする、10 は当該条件を強く満たす、という尺度を使った。

候補③は「すべての主張を子ページにする案」ではなく、前述の昇格条件を付けた併用案である。候補④は、最も軽い Markdown の見出し・ブロック方式を代表として採点した。グラフだけに主張を置く方式は、候補④より実装負担が大きい。

| 候補 | 再利用・成長 25 | 再現性 20 | 規模・コスト 20 | 既存整合 20 | 移行・実装 15 | 合計 |
|---|---:|---:|---:|---:|---:|---:|
| **③ 用語・entity と、選択的な知見ページの併用** | 9 | 7 | 7 | 9 | 8 | **8.05** |
| **④ 主張をページ内の単位にする** | 8 | 8 | 9 | 7 | 6 | **7.70** |
| ① 現行の単位とサイズ上限を維持 | 4 | 4 | 9 | 10 | 10 | **7.10** |
| ② 全面的な一主張一ページ | 9 | 5 | 3 | 6 | 4 | **5.65** |

計算式は `Σ(点数 × 重み) ÷ 100`。

候補③は、

`(9×25 + 7×20 + 7×20 + 9×20 + 8×15) ÷ 100 = 8.05`

である。

| 候補 | 点数の根拠 |
|---|---|
| ① | 変更不要で整合性・軽さは高い。ただし現行の「主要なトピック」「今後掘り下げそう」という判断を残し、source から知見を抽出する欠落を解決しない |
| ② | 知見への直接参照は容易。反面、言い換えごとの重複、タイトルの揺れ、定義・理由・例外の過分割を招く。索引と更新対象が増え、既存用語ページの再編も必要 |
| ③ | 既存の構造を利用し、独立した知見に参照先を与えられる。ただし昇格境界の意味判断は残り、再現性を10とは評価できない |
| ④ | ファイル数を抑え、セクション検索を活用できる。強い候補だが、主張の安定 ID、節への参照、部分ごとの根拠・状態を正式に管理すると追加実装が要る。ページ単位の現行グラフとも粒度が異なる |

候補③と④の差は `8.05 − 7.70 = 0.35`、首位の約4.3%である。大差ではない。

**重みを二通り変えた結果**

| 条件 | 再利用 | 再現性 | 規模 | 整合 | 軽さ | 順位 |
|---|---:|---:|---:|---:|---:|---|
| 指定値 | 25 | 20 | 20 | 20 | 15 | ③ 8.05 ＞ ④ 7.70 ＞ ① 7.10 ＞ ② 5.65 |
| 再利用重視 | 40 | 20 | 10 | 20 | 10 | ③ 8.30 ＞ ④ 7.70 ＞ ② 6.50 ＞ ① 6.30 |
| 規模・再現性重視 | 15 | 25 | 35 | 15 | 10 | **④ 8.00 ＞ ③ 7.70** ＞ ① 7.25 ＞ ② 4.95 |

首位は入れ替わる。指定値でも、候補③の再現性を7→6、コストを7→6と見積もり直すと、`8.05 − 0.20 − 0.20 = 7.65` となり④を下回る。

したがって推奨は、「③が普遍的に最善」ではなく、**現状の不足に最小限の変更で手を入れられる③から試し、昇格しない主張は④の形で保持する**という判断である。

**ページ数とコストの見通し**

仮に現在の37 source から各五主張をすべて新規ページ化すれば、重複排除前では、

`56 + 37×5 = 241 ページ`

となり、索引分割の150ページ目安を越える。これは予測ではなく、一主張一ページの増加圧力を示す仮定計算である。

併用案でも無料にはならない。独立した知見の照合には検索と本文確認が必要である。一方、現行検索はセクション単位なので、細かくしたファイル数と埋め込み数が常に比例するわけでもない。PoC ではファイル数だけでなく、検索セクション数、読取量、更新対象数を測る必要がある。

**採らない方式**

- **全ページの主張文への改名**：Matuschak 自身の例外にも合わず、用語の入口を失う。
- **一トリプル一記事**：事実表現の単位と、説明・再利用の単位を混同する。
- **グラフの `claim` を正本にする**：任意の派生索引という ADR-0009 の位置付けと合わない。
- **「毎 source 三ページ以上」などの割当て**：知見がない資料からもページを作らせ、source 偏重を数だけで解消する。
- **見出し数による自動分割**：理由・根拠・反例が整った良い一主張ページほど、見出しが増える場合がある。

## 前提と不確実性

1. **分割判断の完全一致は保証できない。** 原典にも決定的な分割法はない。ここで提案した規則、固定例、配置記録は揺れを減らすものであり、モデル変更を越えた完全再現を証明するものではない。

2. **Ahrens の該当原文は未確認である。** 著者公開の試読版と公式ページは確認したが、literature/permanent の分類と「一アイデア」の該当節を一次資料で照合できていない。Luhmann に厳密な一主張一枚を帰属させる根拠も確認できなかった。

3. **採点と PoC の目標値は仮説である。** 今回は読取・比較・計算だけを行い、取り込み、検索性能測定、ビルド、ファイル変更は行っていない。

4. **同一連載・同一プロジェクトの複数 source は、独立した裏づけとは限らない。** 複数ページに書かれていることを、複数の独立した検証と数えない。source 数は配置判断の材料であり、真実性の点数ではない。

5. **作者の既存の用語ページを「薄い」とは評価しない。** 実際に複数出典を統合し、留保を記録している。問題は、作業記録から同じ処理が十分に起きていない点である。

6. **サイズの数え方を混同しない。** 本稿のページ数・`type` は直接確認した。補助的に文字数を数えた際はファイル全体を対象にしており、コードフェンス等を除く `wiki_lint.py` の測定値とは区別した。提示された「1,600〜4,300文字」がどの計数法によるものかは未確認である。

7. **評価基準には重なりがある。** 「既存設計との整合」と「移行・実装の軽さ」は現行案を二重に有利にしやすい。また、「判定の再現性」に形式 lint と意味判断が混在している。PoC では別々に測るべきである。

8. **出典への忠実さは、重み付き得点で相殺させない。** 根拠のない一般化、条件の脱落、source の主張を確定事実へ変える編集は、総合点が高くても不合格とする。

作者が最終的に選ぶ必要があるのは、独立ページの直接参照をどこまで重視するかである。現状には併用案が適していると判断するが、PoC で読取・更新コストが大きければ、知見の抽出規則を保ったままページ内管理の比率を上げられる。
