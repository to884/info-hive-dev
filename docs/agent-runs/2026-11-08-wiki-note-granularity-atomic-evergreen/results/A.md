## 結論

**Atomic Notes と Evergreen Notes は、変えて採る。全面的には採らない。** 推す単位は「主張の節を既定にし、数えられる条件を満たした主張だけをページに昇格させる」段階昇格の案（以下「案 5」）である。理由を 5 行にまとめる。

1. Evergreen の中心は「題名を主張の文にし、ソースではなく概念ごとに分けて、複数のソースから育てる」ことである。作者の wiki の偏りにはこれが直接効く。SemaSynth の source 28 本は `concepts:` が 0 件で、リンク先も source だけだった。
2. 一方で「1 主張 1 ページ」を全面的に採ると、ページ数、題名の揺れ、言い換えの違う重複が LLM の取り込みのたびに増える。判定の再現性と規模の両方で最下位になった（採点は後述）。
3. 検索はすでに見出し単位で切っている（`wiki_index.py:796` の `wiki-section-v1`、`wiki_search.py:75` の `HEADING_RE` は `#`〜`######` のどれでも区切る）。主張を `###` の節にするだけで、主張 1 件が検索の 1 単位になる。ページを増やす必要はない。
4. ページに昇格させる条件は 5 つ（P1〜P5）。どれも、ソースの数、ハブの数、型付きエッジの有無という数えられる事実か、固有名を取り除く言い換えの検査で判定する。ページにするかどうかを「目安」で決める今のやり方より、判定が揃いやすい。
5. 昇格したページは `type: "concept"`, `kind: "claim"` で書く。オントロジーの `claim` に `maps_from: {type: concept, kind: claim}` を足すだけで、抽出スクリプトは変えずに `contradicts` と `supersedes` を主張のページに使える（`wiki_graph_extract.py:238-258` は `(type, kind)` を先に照合する）。

## 根拠

### 1. 定義と出典、LLM が保守する wiki で保てるか

| 原則 | 出典 | 保てるか | 判定の理由 |
| --- | --- | --- | --- |
| 1 ノート 1 アイデア（atomic） | Matuschak「Evergreen notes should be atomic」。Luhmann と Ahrens の原文で "one idea per note" という文言は**未確認**（検索した二次資料にもその句はなかった） | 変えれば保てる | 「1 アイデア」の粒度はモデルごとに揺れる。粒度は節で持ち、ページにするかは数えられる条件で決める |
| 概念ごとに分ける（concept-oriented。著者、本、出来事、プロジェクトごとに分けない） | Matuschak「Evergreen notes should be concept-oriented」 | 保てる | 今の concept ページはこの形である。SemaSynth の記録はプロジェクトの順に並んでいて、この原則に反している |
| 密にリンクする（densely linked） | Matuschak「Evergreen notes should be densely linked」。本人も、どこまでリンクするかには明確な判定基準がないと書いている | 保てる | 被リンクの必須と `mentions` のエッジがすでにある |
| 題名を主張の文にする（題名は API のように働く） | Matuschak のノート「Evergreen note titles are like APIs」。**ページの本文は今回読んでおらず未確認**（二次資料と記憶による） | 変えれば保てる | 日本語の文の題名は長くなり、スラッグの規則（空白の禁止、`?` の禁止）とぶつかる。長さと形を規則にする |
| 時間をかけて育つ（evergreen） | Matuschak のノート群（二次資料の要約による） | 変えれば保てる | LLM が書く wiki では「育つ」とは、別のソースが同じ主張に出典を足し、`status` が変わることである。今の「`str_replace` で 1 文足す」手順にそのまま乗る |
| 自分のために書く | Matuschak「Write notes for yourself by default」。**未確認**（記憶による） | 保てない（置き換える） | `page-conventions.md:179-181` は LLM の中立的な語り口を定めている。代わりに「作者の将来の問い（作業のなかで引くこと）のために書く」とし、P4 の判定に使う |
| fleeting、literature、permanent の区別 | Ahrens『How to Take Smart Notes』（2017）の 3 種類（Lesswrong と zettelkasten.de の要約による）。Ahrens が literature note と permanent note を混用しているという指摘もある（Zettelkasten Forum） | 変えれば保てる | fleeting にあたるのは raw である。literature は source ページ、permanent は主張の節と主張のページに対応させる |
| 構造ノート、索引（Strukturzettel、MOC） | Luhmann の構造ノートと MOC の呼び名の出典は**未確認** | 保てる | concept と entity のページを、主張を束ねるハブとして使う |

### 2. 既存の種類との対応

| info-hive の種類 | 対応する Zettelkasten / Evergreen の種類 | 隔たり |
| --- | --- | --- |
| raw（`W1_Raw/`） | 文献そのもの、fleeting の素材 | なし |
| `source` | literature note | 本文が「主な主張、方法論、結論、未解決の問い」という散文で、主張を 1 件ずつ取り出す形がない（`page-conventions.md:110`、`ingest-workflow.md:169`）。SemaSynth の 28 本は見出しが 0〜1 個の散文の塊である |
| `concept`（用語） | 構造ノート ＋ 用語の permanent note | 主張がページの中に混ざり、どれが主張でどのソースのものかの単位がない |
| `concept` のうち題名が主張の形のもの（作者の wiki に 3 ページ） | permanent / evergreen note | 種類として区別されず、`status` もない |
| `entity` | 構造ノート（人や製品ごと） | なし |
| `synthesis` | 構造ノートか、問いに答える permanent note | なし |
| `concept` の `kind: experience-pattern` | **evergreen にいちばん近い**。題名は「再利用できるパターンを 1 つ書く」、`status: hypothesis|supported|superseded` を持ち、根拠、適用範囲と反例の節がある（`assets/pattern.md.template`） | エージェント自身の作業の経験に限られる |

**欠けている種類は 2 つある。**

- ソースから得た主張を 1 件ずつ持つ permanent note（`kind: "claim"`）。
- source の中で主張を列挙する形式（literature note の「抜き書き」）。

`claim` のノード型はオントロジーにあるが、`explicit_only` でページを持てない（`graph-workflow.md:59`）。そのため `contradicts`（主語と目的語は `claim`、`source`、`synthesis`）は、今は concept のページに付けられない。

### 3. 作者の wiki で確かめたこと（読んだだけで、書き換えていない）

- **source に溜まる偏り。** `sources/semasynth*.md` の 28 本はすべて `concepts:` がなく、リンク先は source だけで、見出しは 0〜3 個だった。28 本すべてが `tags: ["知識表現"]` で、SCHEMA.md のこのタグの説明（オントロジー、ナレッジグラフ）と合わない。取り込みのときの分類が揺れていることを示している。
- **一般化できる知見が埋もれている。** 例として、`semasynth汎用コア分離g2-2026-11-07.md` の「PYTEST_ADDOPTS で失敗テストを除外して合格にできる反例」「ImportError を捕捉すると違反が隠れる」、`semasynth-mvp設計の敵対的レビュー-2026-11-06.md` の「保存済みデータ同士の照合は、指定年度や所属の正しさを独立には確認しない」がある。「独立」は source 16 本、「manifest」は 14 本、「レビュー」は 13 本に出てくるのに、ハブのページがない。
- **主張の題名とスラッグの規則がぶつかっている。** `BM25 の IDF の式の違い.md`、`Windows での Tantivy の commit の失敗.md`、`Claude Code の stdio の MCP サーバーとジョブオブジェクト.md` はスラッグに空白を含み、`page-conventions.md:91`（空白は使わない）に反している。`wiki_lint.py` の指摘の種類（`orphans`、`oversized_*`、`duplicate_slugs` など 18 種類）にはスラッグの空白の検査がないので、見逃されている。日本語と英語が混ざる主張を題名にすると、空白はほぼ必ず入る。
- **インデックスの揺れ。** `index.md` の「## シンセシス」の見出しの下に、SemaSynth の source が 15 本並んでいる。モデルが手で保守する一覧が揺れている例である。
- **大きさの上限。** 作者の SCHEMA.md は、ソフト上限 4,000 文字または 400 行、ハード上限 8,000 文字または 800 行で、テンプレートの値（10,000 文字・100 行と 25,000 文字・200 行）と違う。concept は 1,639〜4,263 バイトなので、主張の節を足してもしばらくは収まる。
- **ページの数。** source 37、concept 17、entity 1、synthesis 1 の計 56 ページ。`index.md` は 103 行である。

### 4. 単位の候補の比較

候補は次の 6 つである。

1. 現行のまま
2. 1 主張 1 ページ
3. 併用（ハブの下にすべての主張をページとして置く）
4. 主張をページ内の単位として持つ
   - 4a: 主張を `###` の節にする
   - 4b: 主張を frontmatter かグラフの `claim` ノードにする
5. 段階昇格（4a を既定にし、条件を満たした主張だけを 3 の形のページに昇格させる）

採点は判断値で、実装も測定もしていない。

| 候補 | 再利用と成長 (25) | 再現性 (20) | 規模 (20) | 整合 (20) | 軽さ (15) | 合計 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 現行 | 3 | 4 | 8 | 10 | 10 | **6.65** |
| 2 全面 evergreen | 6 | 2 | 2 | 4 | 2 | **3.40** |
| 3 併用（全主張をページに） | 8 | 4 | 4 | 6 | 5 | **5.55** |
| 4a 主張を節に | 6 | 6 | 9 | 9 | 8 | **7.50** |
| 4b frontmatter・グラフ | 4 | 5 | 8 | 5 | 5 | **5.35** |
| 5 段階昇格（推す案） | 8 | 7 | 8 | 9 | 7 | **7.85** |

計算は「各点数 × 重み の和 ÷ 100」である。例として案 5 は (8×25 + 7×20 + 8×20 + 9×20 + 7×15) ÷ 100 = (200 + 140 + 160 + 180 + 105) ÷ 100 = 7.85。

**点数の根拠**

- **1 現行**
  - 再利用 3: SemaSynth の 28 本が 0 concept で、偏りの実例がある。
  - 再現性 4: ページにするかが「目安」で決まる（`ingest-workflow.md:194`）。
  - 整合と軽さは変更なしなので満点。
- **2 全面 evergreen**
  - 規模 2: source 37 本 × 主張 3 件でも 111 ページ増えて 167 ページになり、すぐに閾値 150 を超える（`scaling-playbook.md:18`）。主張 8 件なら 296 ページ増える。
  - 再現性 2: 1 アイデアの粒度と題名の言い回しが二重に揺れる。
  - 整合 4: 題名の長さ、空白、Windows のパス長、`?` の禁止とぶつかる。
  - 軽さ 2: 56 ページすべてを割り直す。
- **3 併用**
  - 再利用 8: 主張に直接リンクでき、育つ場所がある。
  - 規模 4: 2 とほぼ同じ数のページになる。
  - 再現性 4: ページにする閾値がない。
- **4a 主張を節に**
  - 規模 9、整合 9: 節は検索の単位になり、ページ数は増えない。
  - 再利用 6: ハブのない SemaSynth の知見は source に残りやすい。節は `contradicts` の主語にも目的語にもなれず、2 つのハブで重複する。
- **4b frontmatter・グラフ**
  - 再利用 4: frontmatter は本文の節として検索に入らない（推測）。
  - 整合 5: Markdown の本文と構造化した値が二重になり、`evidence` が必須で書く量が多い。
  - 軽さ 5: 新しいキーを読むスクリプトの変更が要る。
- **5 段階昇格**
  - 再利用 8: 4a に、複数のハブとソースにまたがる主張の置き場を足した。
  - 再現性 7: 昇格の条件 P1〜P3 は数えられる。P4 だけが判断である。
  - 規模 8: 推計で 25〜30 ページの増加にとどまり、80〜85 ページで 150 の手前に収まる（6 節）。
  - 軽さ 7: オントロジーの 1 項目、references 2 本、lint に数項目を足す。

**重みを変えたとき**

| 重みの組 | 順位 |

| A（課題の重み 25/20/20/20/15） | 5 (7.85) ＞ 4a (7.50) ＞ 1 (6.65) ＞ 3 (5.55) ＞ 4b (5.35) ＞ 2 (3.40) |

### 5. 推す案の詳細

#### 5-1. 3 層の単位

| 層 | 置き場所 | 中身 | 対応する種類 |
| --- | --- | --- | --- |
| 抜き書き | `sources/<slug>.md` の `## 主張` | 番号付きリスト。1 項目 1 文の言い換えで、末尾に振り分け先を書く（`→ [[ハブ]]`、`→ [[主張ページ]]`、`（ソース内）`） | literature note |
| 主張の節 | ハブ（concept、entity）の `## 主張` の下の `### <主張の文>` | 1〜3 段落と出典のリンク | permanent note（軽量版） |
| 主張のページ | `concepts/<slug>.md`、`kind: "claim"` | 題名は主張の文。根拠、適用範囲と反例、矛盾の節を持つ | evergreen note |

ハブ（concept と entity）は、今の用語ページをそのまま使い、構造ノートを兼ねる。

#### 5-2. 取り込みでの判定の手順

手順 4 と 5 の間に「手順 4b: 主張の列挙と振り分け」を置く。モデルは、ソースの主張ごとに次の質問を順に問う。

0. **列挙。** ソースの主張を 1 文ずつ書き出す。主張とは、ソースが観測した事実、測定、決定、推奨、定義のことである。経過の報告（「G2 が完了」「364 テストが合格」）は主張ではなく、source の本文に残す。目安は本文 1 万字あたり 5〜12 件で、外れたら列挙を見直す。
1. **定義か。** 用語の定義なら、そのハブ（concept）のリード文に回す。ハブがなければ、H1 か H2 を満たすときだけハブを作る。
   - H1: ソースが用語を定義しているか、節の見出しにしている。
   - H2: 用語が wiki の 2 本以上のソースに出る（`wiki_lint.py --suggest-pages --suggest-min 2` で確かめる）。
   - どちらも満たさなければ、source の中の用語として残す。
2. **既存の主張と同じか。** `index.md` の「主張」の行、主張のページの `aliases`、ハブの `###` 見出しを検索する。主語、述語、肯定か否定かが一致すれば同じ主張とみなす。同じなら、出典を足し（`str_replace`）、必要なら `status` を上げる。新しいページは作らない。
3. **既存の主張と矛盾するか。** 矛盾するなら `## 矛盾` に両方を書き、P3 として昇格の候補にする。
4. **昇格の条件のどれかを満たすか。** 満たせば主張のページを作るか更新する。
   - P1: 2 本以上のソースがその主張を支持するか反論する（手順 2 で一致したもの）。
   - P2: 2 つ以上のハブがその主張を必要とする（同じ見出しを 2 つのハブに書きたくなったとき）。
   - P3: `contradicts` か `supersedes` の主語か目的語になる。
   - P4: プロジェクトの作業記録から得た主張で、固有名（プロジェクト名、段階名、コミット）を取り除いた文でも真偽が判断でき、別のプロジェクトで同じ状況が起こりうる。
   - P5: ユーザーが明示的に求めた。
5. **ハブがあるか。** あれば、その `## 主張` の下に `### <主張の文>` の節を足す。
6. **どれにも当たらなければ**、source の `## 主張` に `（ソース内）` と書いて残す。

**同じ判定にならない境界の例と裁き方**

| 例 | 揺れ方 | 裁き方 |
| --- | --- | --- |
| part-1「OWL はオープンワールド仮定を採る」 | 定義か主張か | 質問 1 で定義として扱う。ハブ [[オープンワールド仮定]] のリード文に回し、主張のページは作らない |
| g2「ImportError の捕捉で違反が隠れる」「収集 0 件でも合格になる」「ガードを外した複製で検出力を確かめた」 | 1 ページか 3 ページか | 同じ対策で直り、常に一緒に引かれるなら 1 つにまとめる。題名は対策の側（「否定テストはガードを外した複製で検出力を確かめる」）にし、2 つの失敗の形は根拠の節に書く。後のソースが 1 つだけを引いたときに分割する |
| mvp レビュー「集計の一致は期間と所属の誤りを見逃す」と、会計データの再検証「独立した期待値と照合する」 | 言い換えか、別の主張か | 主語と述語が違う（前者は検出の限界、後者は対策）ので別の主張とする。後者のページの根拠から前者へリンクする |
| `BM25 の IDF の式の違い` の実測値（0.461 と 0.306） | 主張か根拠か | 測定値は根拠の節に置く。題名は一般化した因果（「BM25 の IDF の式の違いで日本語の語彙検索の再現率が変わる」）にする |
| g2「改名後は元の業務名を残さない」 | P4 に当たるか | 固有名を除くと「合成データの改名で元の名前を残さない」という設計判断で、プロジェクトの外では真偽を判断できない。ソース内に残す |

#### 5-3. 題名とスラッグの規則

- **題名**
  - 1 文の平叙文にする。主語（または条件）と述語を持たせる。
  - 空白を除いて 40 字以内にし、文末の「。」は付けない。
  - 疑問形にしない（`?` は禁止文字である）。
  - 条件は「〜では」「〜すると」で前に置く。規範の主張（「〜する」）も認める。
  - ハブは名詞句にする（例: `オントロジー`）。
- **スラッグ**
  - 既存の規則（`page-conventions.md:88-94`）に従う。題名を NFKC にし、空白を削り、英字を小文字にし、禁止文字を削る。
  - 本文のリンクは `[[スラッグ|自然な文]]` と書く。
  - Windows のパス長は、`<wiki のルート>\concepts\` に 40 字を足して 260 字の上限に十分な余裕がある（推測）。

| 出典（作者の wiki の実在のソース） | 題名 | スラッグ |
| --- | --- | --- |
| `semasynth-mvp設計の敵対的レビュー-2026-11-06` | 集計の一致だけでは会計期間と所属の誤りを検出できない | `集計の一致だけでは会計期間と所属の誤りを検出できない` |

### 7. 移行

1. **段階 0（すぐ）**: 既存のページはそのまま残す。空白を含むスラッグ 3 件の扱い（改名するか、規則を緩めるか）を決める。index の「シンセシス」の下にある source 15 行を正す。
2. **段階 1（4a）**: references と SCHEMA を改訂し、新しい取り込みから `## 主張` と主張の節を使う。lint の `unrouted_sources` と `slug_whitespace` を足す。
3. **段階 2（昇格）**: オントロジーに `claim` の `maps_from` を足す。題名が主張の形の concept 3 件に `kind: "claim"` と `status` を付ける。`編集要求の復元世代を最終適用まで保持する` はそのまま、残りの 2 件は題名を主張の文に直して `aliases` に旧名を残す。
4. **段階 3（溜まった source の掘り起こし）**: SemaSynth の 28 本に `--suggest-pages --suggest-min 2` をかけ、ハブの候補を出す。古い順に 5 本ずつ `## 主張` を足し、昇格させる。一括ではなく、PoC で振り分けの一致を確かめてから進める。ontology 連載の 5 本は、ハブの `## 主張` を整えるだけでよい。

## 検討した代替案

- **2 全面 evergreen（3.40）**: どの重みでも最下位だった。最低の見積もり（1 本 3 主張）でも 167 ページになり、閾値 150 を超える。題名の文と粒度の二重の揺れで、同じソースから同じページ割りになる見込みがいちばん低い。「自分のために書く」は中立の語り口の規約と合わない。
- **3 併用で全主張をページにする（5.55）**: 主張にリンクを張れる利点は大きいが、ページにする閾値がないので規模は 2 に近い。案 5 は、この利点を P1〜P5 を満たす主張に限って取り込んでいる。
- **4b frontmatter・グラフの claim（5.35）**: 正本の Markdown の本文と、構造化した値の二重管理になる。frontmatter は検索の節に入らない（推測）。`evidence` が必須で、取り込みの手間が重い。主張の索引としてではなく、`contradicts` を張るときの補助としてだけ使う。
- **4a 単独（7.50）**: 規模と軽さは最良だが、ハブのない SemaSynth の知見が source に残りやすい。同じ主張を 2 つのハブに書く重複を防げない。案 5 の第 1 段階として採る。
- **1 現行（6.65）**: 偏りを解かない。「小見出しが 5 つで分割」は lint で検査されていない（`wiki_lint.py` の指摘の種類に該当がない）。
- **新しい `type: "claim"` を足す案**: ディレクトリ、インデックス、別名、`upgrade` の改修が要る。`kind` で足りるので採らない。

## 前提と不確実性

- **定義の確認の範囲**: Matuschak の 3 原則（atomic、concept-oriented、densely linked）は本人のノートの題名で確かめた。題名を API のように扱う原則と「自分のために書く」は本文を読んでいない。Luhmann と Ahrens の "one idea per note" という文言、構造ノートと MOC の出典、Luhmann のカードの枚数は確かめていない。Ahrens の literature note の意味は、二次資料の間でも解釈が分かれている。
- **点数と推計**: 採点も、ページ数の推計（80〜85 ページ）も判断値である。案 5 は私が設計した案なので、自分の案を高く採点した偏りがありうる。PoC の振り分けの一致率で検証すること。
- **未確認の実装**: frontmatter の値が検索の節に入らないことは確かめていない。`claim` の `maps_from` の変更後に `wiki_graph_lint.py` の述語の検査が通るかは、実際に走らせていない。
- **作者の判断が要ること**
  - SemaSynth の記録の一部（段階の完了、テストの件数）は、wiki ではなく `log` プラグインの対象かもしれない（ADR-0006）。記事の単位の手法だけで偏りが解けるとは限らない。どこまでを wiki に残すかは、作者が決めることである。
  - 主張のスラッグで英字を小文字にするか。空白を含む既存の 3 件をどう扱うか。
  - `status` に `contested` を足すか。今は `## 矛盾` とグラフで表す前提にした。
- **基準への異議**
  - 「判定の再現性」は実測しない限り採点の差がつきにくい。PoC の一致率で置き換えるのがよい。
  - 「規模とコスト」と「移行と実装の軽さ」は、どちらもページ数で同じ向きに動き、二重に数えている面がある。
  - 「再利用と成長」は、偏り（source に溜まる）の解消を別の基準として分けると、候補 1 と 4a の差がもっとはっきりする。
