# wiki の記事の単位（Atomic Notes と Evergreen Notes）の総括

## 推奨

Atomic Notes と Evergreen Notes は、変えて採る。「1 主張 1 ページ」の全面採用は採らず、用語とエンティティのページを残し、条件と根拠を保った知見だけを `type: "concept"`、`kind: "claim"` のページに選別して独立させる併用の方向を、`SCHEMA.md` のオプトインとして始め、PoC で振り分けの一致を測ってから既定にするかを決める。4 体のどの判定規則も「モデルが変わっても同じページ割りになる」ことを示せていないので、採るのは方向であって、提示された規則そのものではない。

## 批評で動いたこと

- **エージェント A** は、再現性の 7 点を 6 点に下げた（合計 7.65）。昇格条件 P1 と `supported` の定義が、同じプロジェクトの記録を数え上げれば満たせることを認め、「別のプロジェクトか別の著者、または再現の記録」に狭めると改めた。H2 の根拠（「独立」が 16 本に出る）が一般語の出現数にすぎないことも認めた。
- **エージェント B** は、文字数がバイトだったこと（`コンテキストグラフ` は 2,891 ではなく 1,217 文字）を認め、案④への「用語ページがすぐ満ちる」という攻撃を撤回した。入れ子の `evidence` を lint が読めないことを認め、軽さを 7 から 6 に下げ、既定の重みで現行と同点（7.30）になった。それでもオプトインからの段階案という結論は維持した。
- **エージェント C** は、③の再現性 8 点とコスト 7 点に実測がないことを認め、数値上の首位を採用理由にすることを撤回した。`graph.node_type` だけを付けた最小例が `orphan_typed_nodes` に挙がることも認めた。
- **エージェント D** は、初回のページ境界が意味判断であること、グラフのノード ID の移行が欠けていることを認め、結論を「再現性のある完成手法」から「未検証の候補」に限定した。
- **最も鋭い反論**は 3 つで、いずれも議論ではなく測定で示された。
  1. 「主語、述語、肯定か否定か」だけの同一性判定は適用条件を落とす（C と D が A と B に）。実在の raw（再現性の検証、7 行目）が同一環境と異環境で一致条件を分けているので、この規則はその入力で誤統合し、誤統合が P1 の「2 本以上」を満たして昇格につながる。D は A の PoC の照合（bigram の Jaccard 0.5）で、条件だけが違う 2 文が 0.72 で一致と数えられることまで示した。
  2. B の「滞留」lint（本文 1,500 文字以上）は、対象にしたい SemaSynth の 28 本のうち 26 本を除外する（D と C が実測）。
  3. A の H2 は指定した `--suggest-pages` で検査できない（候補の正規表現は漢字 3 文字以上、カタカナ 3 文字以上、大文字始まりの英語で、「独立」も `manifest` も対象外）。試案のハブ `合成データの検証` という文字列は source に 0 回しか出ない（B、C、D が独立に確認）。数える前にモデルが概念名を発明している。
- これらは A と B の提示した規則に対しては決定的だった。併用という方向に対しては決定的ではない。4 体とも、攻撃後も用語ページを残して知見を選別する方向は崩せなかったと書いている。

## 推奨案が残る理由

- **全面 evergreen は 4 体すべてが最下位**にし、ページ数の計算（37 本 × 3 主張で 111 ページ増、167 ページで閾値 150 を超える）は誰も反証していない。原典の読みでも、Matuschak 自身が細分化しすぎるとリンク網が断片化すると書き、題名の主張化にも例外を認めている（C と D が本文を取得して確認。ただし「問い」が例外に含まれるという両者の記述は B の取得で否定された）。
- **単位の定義**は C の「条件、根拠、留保を含み、独立して更新できる 1 つの判断」が残った。「1 文」を単位にする A と B の定義は、題名の 40 字制限のために条件を削る規則（B）や条件を見ない同一性判定と結びついて、知識の意味を変える反例を出した。
- **既定の入れ物は見出しの節**にする。`split_sections` は ATX 見出しで切るので `###` の主張は検索の 1 単位になるが、`## 主張` の下の箇条書きは何行あっても 1 セクションにしかならない（C と D が実装に入力して確認）。B の反論どおり、節は `index.md` に載らないので query は検索経由でしか届かない。昇格したページだけがインデックスの 1 行を得る、という二層になる。
- **区別は `kind: "claim"`** で表す。`derive_node_type` は `(type, kind)` を `type` だけより先に照合する（4 体が確認）ので、オントロジーに `maps_from: {type: concept, kind: claim}` を 1 項目足せばスクリプトを変えずに `claim` ノードができる。C の `note_role` はどのスクリプトも読まず、ページごとに `graph.node_type` を書くしかなく、型付きエッジのないページが `orphan_typed_nodes` に挙がる。`maps_from` だけで `claim` にしたページはこの検査の対象外である（A が 287〜292 行で確認）。
- **frontmatter は平坦なキーだけ**にする。`wiki_text.py` のパーサーは入れ子を読まず空の配列にする（B、C、D が同じ入力で確認。B の `evidence[].quote` は消える）。
- **同じプロジェクトの複数ソースは独立した裏づけではない**（D の指摘。A と B が自分の規則に当たると認めた）。B の WinError の例は、G0（C ドライブの一時領域）と G1（リポジトリ内）という条件の違う 2 件を 1 文にまとめて 2 ソースの裏づけと数えていた。
- **移行は索引の分類から**始める。「シンセシス」の見出しの下に `type: source` のページが 16 本並んでいる（4 体が確認。A の 15 本は誤り）。今の lint はこれを見つけられない（B が作者の上限で lint を走らせて 0 件を確認）。
- **PoC の設計**は D の分け方が残った。同じ入力を再処理したときの冪等性と、別モデルが同じ初期状態から同じ配置に至る独立一致は別の試験であり、C の「保存した判定表を読む」は前者にしか効かない。出典への忠実さと条件の保持は加重点で相殺させず、別の必須条件にする（C と D）。現行手順でも同じ回数を取って対照にする（A と B）。
- **採点の差は判断の誤差の内側**にある。推す案と次点の差は 4 体で 0.15〜0.35 で、どの体も重みや素点を少し動かせば首位が入れ替わることを自分で示した。A の「軽さの重みが 35 を超えたときだけ逆転する」は、C と D が別の重みで反例を出した。首位を決めるのは採点ではなく PoC の一致率である。

## エージェントごとの要約

**エージェント A** は、主張を用語ページの `###` の節に置くことを既定とし、数えられる条件 P1〜P5 を満たした主張だけを `kind: "claim"` のページに昇格させる段階案を推した（7.85）。節が検索の単位になること、`maps_from` の 1 項目でスクリプトを変えずに済むこと、`orphan_typed_nodes` に当たらないことはレビューで裏づけられた。当たった指摘は、同一性判定が適用条件を落とすこと、H2 が指定ツールで検査できず試案のハブ名が規則から導けないこと、ハブのない SemaSynth の主張は source 内に残るので P1 に到達できず昇格経路が意味判断の P4 だけになること、`superseded` の検査が置換の向きを取り違えていること、題名の「ひらがなで終わる」判定が `BM25 の IDF の式の違い` を主張形と誤判定すること、感度分析の結論が反例で崩れること、「シンセシス」下の 15 本は 16 本であること。

**エージェント B** は、主張文を単位にし、入れ物（用語ページの箇条書きか独立ページか）を用語の所属数、ソース数、ページの大きさで決める案 E を推し、安定性重視では現行が首位になることを隠さず、オプトインからの段階案にした。`kind: "claim"` と `maps_from`、新しい `type` を作らない判断、首位の入れ替わりの明示は残った。当たった指摘は、作例の `evidence.quote` が raw にも source にもなく wiki の言い換えだけに出ること、入れ子の `evidence` をパーサーが読めないこと、箇条書きは検索の 1 単位にならないこと、40 字のために条件を削る規則、滞留 lint が 28 本中 26 本を除外すること、e5 と ruri の例で入れ物が二択のまま確定していないこと、WinError の例が条件の違う 2 件を統合していること、`proposed` の主語は `person` であること、Yuan An 系は 9 本ではなく 5 本であること、文字数がバイトだったこと。

**エージェント C** は、「条件、根拠、留保を含む独立して更新できる判断」を単位とし、`note_role: "claim"` で選別した知見を独立させる併用案③を推した（8.25）が、相互レビュー後に数値上の優位を撤回した。単位の定義、条件と極性と断定の強さを含む同一性判定、原典が全面分割を要求していないという読み、忠実さを必須条件にする異議、平坦なキーにする実装上の理由は残った。当たった指摘は、再現性 8 点の根拠が判定表の記憶（冪等性）であって独立一致ではないこと、`note_role` はスクリプトが読まず `graph.node_type` の明示が要り費用が高いこと、CSV の題名が原文の「列の Policy または別の期待値」を「列情報が要る」に狭めたこと、既存の `オープンワールド仮定` の節を更新するか切り出すかが規則で決まらないこと、PoC の採用条件を全件 `source_only` でも満たせること、lint 案（raw の行照合、表のパーサー）が軽さ 8 点と釣り合わないこと、`index.md` は 103 行であること。

**エージェント D** は、条件付きの主張を選別して独立させる併用案③を推し（8.05）、`kind: topic | claim`、source に残す配置表、冪等性と独立一致を分けた PoC、索引の分類を先に直す移行を提案した。PoC の設計と移行の順序は 4 体の中で最も残った。当たった指摘は、試案で取り込みから `experience-pattern` を作っており `/wiki:learn` の来歴の契約を壊していること（A と B）、配置例 c02 が自分の昇格条件 3 を満たすのに `source_only` にされ、その追加判定が未定義であること（C）、候補④を「最も軽い方式」と宣言しながら追加実装を要求する前提で減点し、その不一致だけで首位が入れ替わること（C）、`kind: topic` は既存ページに付かず区別の情報にならないこと、配置表の鮮度を保つ手順と lint がないこと、Matuschak の例外に「問い」はないこと。D 自身が示した、`kind` を変えるとノード ID が `concept:x` から `claim:x` に変わり既存の明示エッジの目的語が切れる問題と、`depends_on` が `claim` を受け付けない問題は、`maps_from` を使う A と B の案にも当たる。

## 残るリスクと未確定事項

- **再現性の中心が意味判断のまま。** A の P4、B の Q2、C の手順 4〜5、D の昇格条件 3 は、すべて「ソース固有か、再利用できるか」の判断で、機械化できていない。SemaSynth の偏りを解く経路はこの判断 1 つにかかる。PoC で測るまで、どの案も再現性に 7〜8 点を付ける根拠はない。
- **オプトインか既定か。** オプトインで始めれば既存の利用者に影響がなく PoC の結果を待てるが、作者自身の wiki では `SCHEMA.md` を書き換える手間が要る。既定にすればマイナー版で全利用者に届くが、未検証の規則を配ることになる。
- **主張ページの `status`。** A は `experience-pattern` と同じ 3 値、B は `disputed` を足した 4 値、D は一般の `claim` に `status` を流用しないという立場。流用しないと、グラフを有効にしない wiki で古い主張を query から除く手段がなくなる。
- **根拠の持ち方。** 入れ子の `evidence` は使えない。平坦なキー（C の `claim`、`scope`）か本文の節（`## 根拠`）かを決める。raw の行番号を根拠位置にする案（C、D）は、rag 連携の PDF では `raw:` が絶対パスで行が定義できない（A の指摘）。B の作例が示したとおり、根拠を wiki の言い換えから取る誤りを lint で止めるには、照合先を source の本文に限るのが現行の契約と合う。
- **グラフの移行。** `maps_from` を足すと既存の `concept:x` が `claim:x` になり、他ページの明示エッジの目的語は自動では直らない。`depends_on` は `claim` を受け付けない。既存の型付きエッジがある wiki では ID とエッジの移行手順が要る。作者の wiki で実際に該当があるかは未確認。
- **wiki の対象範囲。** SemaSynth の記録のうち段階の完了やテスト件数は、記事の単位では解けず、`log` プラグインの対象（ADR-0006）かもしれない。ソフトウェア検証の一般則、製品固有の判断、業務上の判断のどこまでを wiki で育てるかは `SCHEMA.md` に書く必要がある（C、D）。
- **スラッグ。** 空白を含む既存 3 件（B の 4 件は誤り）を改名するか規則を緩めるか。英字を小文字にすると `PYTEST_ADDOPTS` のような識別子の読みやすさが落ちる（A）。主張の単位の導入と抱き合わせない（D）。
- **PoC の規模。** B は 4 回、C は 18 回、D は 54 回と人手の対応づけを提案した。小さい試験では 1 件のずれで 0.90 を割る（B の指摘）。合格の目安（振り分けの一致 0.8〜0.9、重複 0、条件の脱落 0）はすべて提案値で、達成の見込みは不明。偏りを解かない出力（全件 `source_only`）が合格しないよう、SemaSynth から出た concept の本数を対照と比べる項目が要る（B と C）。
- **基準への異議。** 「既存設計との整合」と「移行の軽さ」で 35 の重みがあり現行が構造的に有利になる（B、D）。「規模」と「軽さ」はページ数で同じ向きに動く（A）。「出典への忠実さ」と「条件の保持」は加重点ではなく必須条件にすべき（C、D）。「判定の再現性」は採点ではなく PoC の振り分けの一致率で置き換えるべき（A、B）。
