## 結論

**作者の wiki は、今は「活用する側の機能」より「活用の材料」が不足している。** 読んだ事実は次のとおり（`~/info-hive/W0_Wiki/graph/edges.jsonl` を集計）。

| 項目 | 値 |
| --- | --- |
| ページ数 | 22（source 7、entity 1、concept 15、synthesis 0） |
| `mentions` エッジ | 128 |
| `sourced_from` / `summarizes_raw` | 26 / 7 |
| 型付きエッジ | 5。すべて `authored`、主語は `person:yuan-an` のみ |
| `synthesis/` | 0 件 |
| SCHEMA.md の「ワークフローのカスタマイズ」「ユーザーの好み」 | どちらも空 |
| 経験ページ（`kind: experience-pattern`） | 0 件 |

したがって、グラフ推論や鮮度の検証のような「活用の機能」を先に作っても、今の wiki では動かす対象がない。**スコープ B の運用（型付きエッジ、synthesis、learn を日々の切れ目で残す）が、スコープ A の機能の前提となる材料を作る**。これが本検討のいちばん重要な結論である。

### スコープ A（info-hive に次に足す機能）の上位

基準の重みでの順位。詳細は「根拠」の収束 A。

1. **案 39 + 40: 取り込み手順に「型付きエッジを 1 本以上検討する」段を足し、候補の文をスクリプトで提示する**（8.15。40 単体は 6.85）。型付きエッジ 5 本という最大の制約を解く。手順の追記と lint の注意だけで始められる。
2. **案 2: `/wiki:context <焦点>`。焦点ノードから k ホップ（2〜3）の部分グラフを、構造・意味・時間の重みと行数の予算で切り出す**（8.00。価値・波及重視の重みでは 1 位）。今の `neighbors` は 1 ホップで予算がない。`mentions` 128 本があるので 22 ページの今も動く。
3. **案 7: 回答に出典チェーン（主張 → concept → source → raw）を自動で添える**（7.65）。要件定義書 §7 の追跡経路を機械で組み立てる。`sourced_from` と `summarizes_raw` は生成済み。
4. **案 8: 鮮度 lint（`valid_to` 超過の current エッジ、`superseded` を指す参照、source より古い派生ページ）**（7.50）。今の lint は `updated` が 90 日前の `stale_pages` しか見ない。
5. **案 27: wiki の MCP サーバー化**（7.50。価値・波及重視では 2 位、軽さ重視では 33 位）。CLI 検索 1 回 3.1 秒が数十 ms になり、Codex や rag から使える。実装が重いので ADR の確定が先。

### スコープ B（今の wiki を日々どう使うか）の上位

1. **案 39: 取り込みごとに型付きエッジの候補を 1 本以上検討し、`evidence` を原文のまま写して書く**（8.85）。`depends_on`、`cites`、`contradicts`、`supersedes` が対象。
2. **案 12: 取り込み時に、新ソースが触れる既存ページの raw を読み直し、差分を「更新・矛盾・補強」に分類して報告する**（8.55）。「矛盾あり」「未解決」のタグをここで付ける。
3. **案 21: 作業の終了時に、検証済みの結果だけを `/wiki:learn` で記録する**（8.35）。経験ページ 0 件を解消する。
4. **案 16: 設計の前に `/wiki:query` で ADR の骨子（背景・選択肢・理由）を作り、`synthesis/` に `question` 付きで保存する**（7.90）。
5. **案 3 と案 5: 実装前に `--type synthesis` で過去の決定を引く。CLAUDE.md の定型文を「設計前・不具合・終了時」の場面別に拡張する**（7.85 同点）。

## 根拠

### 前提として確かめた事実

- **検索の絞り込み**: `wiki_search.py` の引数は `--type`、`--tag`、`--since`、`--backlinks`、`--top-linked`、`--granularity`、`--decide` など。`kind` の絞り込みはない（`info-hive-wiki/skills/info-hive/scripts/wiki_search.py:1123-1143`）。経験パターンは `--tag agent-experience` で代用する。
- **グラフの問い合わせ**: `neighbors` は 1 ホップの入出辺、`path` は出辺だけをたどる BFS で、`status` や `valid_to` を見ない（`wiki_graph_query.py:102-173`）。`extract` は `valid_from`、`valid_to`、`raw_ref`、`contradicts`、`supersedes` を `metadata_json` に保存しているので（`wiki_graph_extract.py:343`）、鮮度の判定に使える材料は索引にある。
- **lint の検出項目**: 孤立、リンク切れ、大きさ、frontmatter、重複スラッグ、`stale_pages`（被リンク 3 以上かつ `updated` が 90 日超）、日本語の書き損じ、`suggested_pages`（`wiki_lint.py:201-187` の `findings`）。内容の矛盾は LLM の手順（`lint-workflow.md` 手順 3）か、判定モデルの D3（`wiki_decide.py contradictions`）。判定モデルは既定で無効、質問文は英語で、日本語での評価は未実施（`references/decision-models.md`）。
- **性能**: `uv run --script wiki_search.py` は 1 回約 3.1 秒。常駐プロセスのウォーム検索は数十 ms（`docs/research/embedding-backend-unification-2026-11-05/README.md` 「段階 2 と M5 で分かったこと」）。
- **MCP 化の案**: ツールは query、get_page、list_index、lint、stats、graph、ingest_source、index_chunks。モデルと索引の持ち主は wiki のサーバー 1 つで、rag はそこに頼む（同レポート HTML §13、§15 の ADR 案 B）。ADR は未確定。
- **決定**: グラフは wiki の任意の索引で横断基盤にしない。見直す条件は「log、rag、複数の wiki から関係の問い合わせやオントロジーの管理を直接使う要件」など（`docs/adr/0009-graph-layer-stays-in-wiki.md` 「見直す条件」）。日付ノートは `notes/` に書き出してから人が ingest を決める（ADR-0006）。rag の回答は Claude Code が作る（ADR-0007）。
- **要件**: 利用場面は「技術資料を読む、実装前に調べる、不具合を直す、作業を終える、知識を見直す」（要件定義書 §2.2）。出典の追跡経路は「主張 → source の slug → 原資料の保存版 → 該当箇所」（§7）。検証状態 `unverified / machine-checked / human-reviewed` と再確認のきっかけ（§8 Q-01〜Q-08）。Project から Global への一般化（§5.3 F-E04）。横断検索は未決（§13 O-03）。
- **作者の wiki の素材**: コンテキストグラフは「焦点から k ホップ（2〜3）、構造・意味・時間の重み、予算で退去、結果は出所と時刻を付けて書き戻す」（`W0_Wiki/concepts/コンテキストグラフ.md` 「構築」）。グラウンディングは「取得・推論・検証」の往復で、行動の前に ASK で前提を確かめる（`concepts/グラウンディング.md` 「検査の例」）。

## 前提と不確実性

**依存している仮定**
