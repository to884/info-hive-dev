## 結論

**スコープ A は「蓄積した知識を、必要な範囲で取り出し、再利用前に確かめ直せる機能」を優先する。スコープ B は「設計前に使い、作業後に経験を戻す運用」を始める。** グラフやオントロジーの高度化そのものを目的にはしない。

スコープ A の上位 5 案は次のとおりである。点数は、指定された重みによる加重平均で、10 点満点。

| 順位 | 案 | 点数 | 追加する価値 |
| --- | --- | ---: | --- |
| 1 | **#5 出典変更による synthesis の再確認候補検出** | 9.00 | 保存した回答を、古い根拠のまま再利用することを減らす |
| 2 | **#3 主張・根拠の照合表** | 8.85 | 回答の重要な主張から、source、raw の該当箇所まで確認できる |
| 3 | **#1 目的と予算を指定するコンテキストの切り出し** | 8.80 | セッション開始や設計時に、必要な知識だけを理由付きで渡す |
| 4 | **#20 適用条件付きの経験検索** | 8.60 | 成功例だけでなく、適用範囲、反例、失敗例を作業前に取得する |
| 5 | **#23 ローカルの読み取り用 MCP** | 8.35 | Codex などからも、同じ取得方法で wiki を利用できるようにする |

スコープ B の上位 5 案は次のとおりである。

| 順位 | 案 | 点数 | 既存機能で行うこと |
| --- | --- | ---: | --- |
| 1 | **#19 作業終了時に、検証済みの経験を learn に残す** | 9.80 | 操作、結果、適用条件、未確認事項を記録する |
| 2 | **#6 再利用したい比較・判断を synthesis に保存する** | 9.55 | 質問への回答を、次回の調査の出発点にする |
| 3 | **#4 設計前に、根拠と反例を添えた ADR 下書きを作る** | 9.30 | query で既存知識を設計判断に変換する |
| 4 | **#18 不具合調査で、原因仮説と反証手順を作る** | 9.10 | 過去の経験を仮説生成に使い、今回の検証結果と区別する |
| 5 | **#32 知識を再利用した結果を記録する** | 9.05 | 「役立ったか」「条件が違ったか」を learn に戻す |

A は順位どおりに独立した機能を 5 本作るという意味ではない。**#3 の根拠の参照方法を整え、#5 で再確認に使い、#1 と #20 で取得を改善し、#23 から公開する**構成が候補になる。

現在の wiki は synthesis が 0 件である。したがって、最初に B を短期間試して再利用例を作り、その結果を A の PoC に使うのがよい。これは「synthesis がないから保存機能が足りない」という判断ではない。保存機能は既にある。[R2][R3]

## 根拠

### 判断の土台

以下は、確認した実装・規約と、そこからの判断である。

| 確認した事実 | 判断への影響 |
| --- | --- |
| query は既に比較、知識の不足の洗い出し、時系列の整理、synthesis 保存を扱う | これらを新コマンドにするだけでは、A の追加価値は小さい。[R3] |
| グラフはページを見つけるための索引であり、重要な主張はページと raw で確認する | 経路の発見と、主張の正しさの検証を分ける。[R4] |
| 現行の `neighbors` は 1 ホップ、`path` は有向 BFS。問い合わせの SQL に `status` や有効期間による絞り込みはない | 目的別・期間別・予算付きの取得には実装差分がある。[R5] |
| `ontology.yaml` はノード型、述語、主語・目的語の型、根拠必須条件を宣言する | 現状を OWL 推論器や行動認可エンジンとして扱わない。[R6] |
| `learn` は経験の記録、`evolve` は評価を伴うスキル改善として既にある | 日々の経験記録を始めるために、自動改善の実装は要らない。[R7] |
| `.evolution/` は保持する実験証拠であり、通常の検索・lint・統計・グラフ抽出の対象外 | 日常の取得には、通常の source、pattern、synthesis に置いた要約を使う。[R2] |
| ADR-0009 はグラフを wiki 内の任意の索引と位置付ける | MCP 化と、wiki・rag・log の関係を共通グラフにすることは別に判断する。[R8] |
| 要件定義は、設計前、障害調査、作業終了、知識の見直しを利用場面に挙げる | 回答生成以外に、判断の準備、検証、経験の再利用を含める。[R9] |

作者の wiki の `index.md` と `SCHEMA.md` も確認した。`indexes/` は存在せず、インデックスは未分割だった。4 種類のディレクトリの直下にある Markdown を数えると、source 7、entity 1、concept 15、synthesis 0、**合計 23 件**だった。依頼文の「22 ページ」と内訳の合計には 1 件の差があるが、本検討の順位を変える規模差ではない。[R2]

### 収束 A：次に足す機能

指定された基準を、以下の順で採点した。

- **価**：利用者が得る価値。重み 25。
- **整**：既存設計との整合。重み 20。
- **規**：規模への耐性。重み 20。
- **軽**：実装と検証の軽さ。重み 20。
- **波**：他プラグインへの波及。重み 15。

1〜3 点は弱い、4〜6 点は条件付き、7〜9 点は強い、10 点は当該基準で特に明確な利点があるものとした。**点数は実測値ではなく、確認した実装と要件に基づく判断値**である。

\[
A=(25価+20整+20規+20軽+15波)/100
\]

たとえば #5 は、`(25×9 + 20×10 + 20×9 + 20×8 + 15×9)/100 = 9.00`。

### 次のステップ：B の手順と SCHEMA.md 追記案

まず、次の三つを基本の流れにする。

1. **設計前**：query で根拠・反例・未確認事項を取り出す。
2. **質問後**：再利用価値のある比較・判断だけ synthesis に保存する。
3. **作業終了時**：実際の検証結果を learn に渡す。

既存コマンドへの依頼例は次のとおり。

```text
/wiki:query 今回の設計について、wiki にある選択肢、採用条件、
反例、未確認事項を整理してください。
今回の制約は……です。
事実、資料の主張、今回の推測を分け、ADR の下書きにしてください。
```

```text
/wiki:query この比較を、3か月後にも再利用できる synthesis として
保存する案を作ってください。
適用条件、反例、未確認事項と、参照した source を残してください。
```

```text
/wiki:learn 今回の作業の成果物と検証記録は……です。
使った wiki のページは……です。
観測した結果、原因についての仮説、適用条件、反例を分けてください。
既存の経験パターンがあれば統合してください。
```

不具合時は #18 を差し込む。

```text
/wiki:query 症状は……、環境は……、確認済みの事実は……です。
関連する過去の経験から原因仮説を挙げ、
各仮説を支持する観測と反証する確認手順を示してください。
過去の事例と、今回確認できた原因は分けてください。
```

現時点の知識を使う具体例としては、次の問いが適している。

> info-hive でコンテキストグラフを試すなら、現行の neighbors/path と query の組合せで何ができ、何が追加実装になるか。ADR-0009 を保つ案と、その見直しが必要な案を比較してほしい。

これなら、現在多く蓄積されているオントロジー・コンテキストグラフの概念を、実際の開発判断に利用できる。ただし、概念を説明する資料があることと、実装効果が検証されたことは区別する。

`SCHEMA.md` の「ワークフローのカスタマイズ」への追記候補は次のとおり。**今回の調査では追記していない。**

```markdown
- 設計・不具合調査の query では、事実、資料の主張、今回の推測、
  適用条件、反例、未確認事項を分ける。
- 重要な判断に使う主張は source を示し、必要な箇所だけ raw に戻って確認する。
- 新しい比較・判断を synthesis に保存するかは、
  「3か月後に再利用したいか」で決める。
- synthesis には必須の frontmatter と sources を付ける。
  question と sources_consulted は補助情報として記録する。
- 作業終了時、再利用価値のある経験を /wiki:learn に渡す。
  過去の wiki を使った場合は、ページ名と今回の結果も記録する。
- 検索や経路が見つからないことだけで、事実が存在しないとは判断しない。
```

「ユーザーの好み」には、次の一項目で始めればよい。

```markdown
- 判断を支援する回答は、結論、適用条件、根拠、反例、
  未確認事項の順で示す。比較には表を使う。
```

synthesis 保存のワークフロー例にある `question`、`asked`、`sources_consulted` だけでは、SCHEMA の必須項目を満たさない。保存時は `type`、`title`、`tags`、`created`、`updated` と、source 以外に必要な `sources` を合わせて記録する。[R2][R3]

週次には既存の `/wiki:lint` を使い、重要な矛盾候補と、実際に再利用したページを少数選んで確認する。作者の SCHEMA の文字数・行数上限は汎用テンプレートと異なるため、lint の実行時も作者の規約に合わせる。[R2]

試用後はページ数だけでなく、次を確認する。これは自動計測の実装を要件にせず、作業終了時の記録から判断できる。

- 保存した synthesis を、後の作業で使ったか。
- 経験パターンによって、調査や設計の出発点が変わったか。
- 過去の条件との違いを見つけられたか。
- 原文に戻った結果、判断を修正した例があったか。
- 記録と確認の手間を続けられたか。

## 前提と不確実性

- **採点は一人の判断である。** 他のエージェントの成果は読まず、独立に評価した。点数差 0.05〜0.2 を、実測された優劣とは扱えない。
- **現在の利用頻度は不明である。** 設計判断、不具合調査、PDF の詳細確認、他エージェントからの利用の頻度次第で、#20・#23・#25 の優先順位は変わる。
- **現在の型付きエッジの密度と、有効期間の記入率は数えていない。** #1 は本文検索と wikilink でも動く設計を条件にした。型付きエッジが豊富であるとは仮定していない。
- **実装・性能検証は行っていない。** ビルド、索引生成、コマンドによる wiki の更新、PoC は実行していない。ファイルも変更していない。
- **23 件という数は、対象 4 ディレクトリ直下の `.md` の集計である。** 依頼文の 22 件との相違は確認したが、過去の集計時点は特定していない。
- **`.evolution/` の位置付けは依頼文を補正した。** 依頼文では派生データに含まれていたが、実際の SCHEMA と参照文書は、消してよいキャッシュではなく、保持する実験証拠とする。[R2][R7]
- **現在の `ontology.yaml` は、記事で論じられるオントロジーの全能力を実装していない。** SPARQL ASK、OWL の公理推論、現実の資源状態の検査を既存機能とはみなしていない。
- **「ローカル完結」は、確認した規約では検索・埋め込みの処理に関する条件である。** Claude Code や Codex の推論実行先まで、ローカルモデルに限定されたとは解釈していない。#23 は外部への公開サーバーを意味しない。
- **外部製品の最新仕様は調べていない。** Foam・Obsidian・MCP 連携の評価は、リポジトリ内の設計と、Markdown を利用する範囲に基づく。特定クライアントの接続互換性は未検証である。

基準への異議は二点ある。
