# タスク：LLM Wiki で蓄積した情報の活用方法を、発散と収束で考える

## 作者の指示

> LLM Wiki で蓄積した情報の活用方法。
> LLM Wiki は Web や文章などから情報を取り込み、その上で概念を整理した記事を作成したり、概念同士の関連付けをおこなったり（グラフ）、定義を作ったり（オントロジー）をしている。
> これらの情報をどのように活用するか？について考察し、効果的な活用方法を考えてほしい

作者はこの検討の結果を、次の 2 つを決めるために使う（2026年11月6日に確認）。

- **スコープ A**: info-hive に次に足す機能（プラグインのロードマップへの入力）
- **スコープ B**: 今の wiki を日々どう使うか（新しい実装を前提にしない運用の手順）

発散は 2 つのスコープに共通で行い、収束は A と B に分けて行う。手法は brainstorm-diverge-converge（発散 → クラスタ → 収束）である。

## 現状として分かっていること

### wiki プラグイン（`info-hive-wiki`、プラグイン名 `wiki`、導入名 `wiki@info-hive`）

コマンドは `/wiki:<名前>` で呼ぶ。

| コマンド | 入力 → 出力 |
| --- | --- |
| init | セットアップの質問に答えると、wiki の骨組み（SCHEMA.md、index.md、log.md、graph/ontology.yaml）と実行環境を作る |
| ingest | ソース（論文、記事、文字起こし、PDF、メモ、URL）を受け取り、原本を raw に置き、`sources/<slug>.md` の要約と entity / concept ページの新規作成または部分更新、`index.md` と `log.md` の追記を行う。オントロジーがあれば根拠付きの型付きエッジを足し、graph の lint と extract も行う。PDF は rag の `register_pdf` に登録する |
| query | 質問を受け取り、`index.md` → 候補ページ →（見つからなければ `wiki_search.py` のハイブリッド検索、関係を問う質問なら `wiki_graph_query.py`）の順に調べ、`[[wikilink]]` を出典に付けた回答を返す。回答を `synthesis/` に保存することを提案する |
| graph | `extract` / `lint` / `neighbors` / `edges` / `path` / `facts` を受け取る。extract は `graph/` に nodes.jsonl、edges.jsonl、graph.sqlite、graph.graphml を作る |
| learn | タスクの成果物や経験を受け取り、変更不可の raw JSON（`raw/experiences/`）を作り、source として取り込み、concept（`kind: experience-pattern`、`status: hypothesis|supported|superseded`）のパターンページにまとめる |
| evolve | 対象スキルと改善の目的を受け取り、`.evolution/` に実験記録を残して改善案を作り、学習・検証・最終テストで評価し、承認があれば apply、依頼があれば rollback する |
| lint | 孤立ページ、リンク切れ、大きすぎるページ、frontmatter の誤り、古い日付、graph の矛盾、内容の矛盾と不足を修正案として返す |
| stats | ページ数、種類別の数、リンク密度、スケーリングの閾値（150、300、500 ページ）の判定を返す |
| upgrade | 実行環境とベクトルを作り直し、SCHEMA.md に欠けている節を追記する |

### wiki が蓄積するデータ

- ページの `type` は `source`（`sources/`）、`entity`（`entities/`）、`concept`（`concepts/`）、`synthesis`（`synthesis/`）の 4 つ。entity の `kind` は person、company、product、paper、place、organization。
- frontmatter の必須項目は `type`、`title`、`tags`、`created`、`updated`。source には `raw`、`ingested`、`authors`、`url`。source 以外には `sources`。任意で `aliases`、`question`、`sources_consulted`。
- 本文の `[[wikilink]]` から `mentions` のエッジが自動で作られる。`sources:` から `sourced_from`、`raw:` から `summarizes_raw` も自動で作られる。
- 型付きの述語（`graph/ontology.yaml` で宣言、根拠必須）: founded、owns、contains_product、works_on、chose、proposed、competes_with、depends_on、authored、cites、contradicts、supersedes。ノード型 decision、claim、raw は `explicit_only`（明示したときだけ使う）。
- 型付きエッジの必須項目: `predicate`、`object`、`source`（ソースページのスラッグ）、`evidence`（原文の引用）、`confidence`（high / medium / low）、`status`（current / historical / proposed / disputed / superseded）。任意で `valid_from`、`valid_to`、`raw_ref`、`contradicts`、`supersedes`。
- 検索はセクション単位のハイブリッド検索（語彙 + 埋め込み。現行は `intfloat/multilingual-e5-small` と sqlite-vec。統一レポートは Ruri v3 130m + usearch + Tantivy に変える案）。`--type`、`--tag`、`--since` で絞れる。
- 派生データ（`.wiki-cache/`、`graph/` の生成物、`.evolution/`）は作り直せる。正本は Markdown である。

### 作者の wiki の現在の規模と中身

- 22 ページ（source 7、entity 1、concept 15、synthesis 0）。`graph/` は生成済み。タグの体系は「並行処理」「知識表現」「AIエージェント」「情報検索」。
- 中身の多くは Yuan An の連載「Ontology and Knowledge Graphs and AI Agents」の第 1〜4 回を取り込んだ concept ページで、この検討の素材にもなる。要点は次のとおり（作者の wiki はこのリポジトリの外にあるので、ここに書き写す）。
  - **コンテキストグラフ**: 全体のナレッジグラフから、1 つのエージェント・1 つの目標・1 つの時点のために、焦点の実体から k ホップ（2〜3）で切り出した部分グラフ。エージェントの動的な作業記憶にあたる。関連度は構造（距離）・意味（型が目標に合うか）・時間（新しさ）の重み付き和で採点し、予算を超えた分は退去させ、行動の結果は確認後に出所と時刻を付けて全体のグラフへ書き戻す。
  - **グラウンディング**: 推論を取得した事実（グラフ）と規則（オントロジー）に結びつける。行動の前に SPARQL の ASK で前提条件を確かめ、偽なら行動を拒否して再問い合わせする。「取得・推論・検証」の往復。
  - **コンテキストエンジニアリング**: 有限のウィンドウに何をどの形で入れ、いつ入れ替えるかを設計する。制約はトークンの予算、遅延、注意の劣化（context rot）。答えは「もっと多く」ではなく、鮮度のある正しい事実を使える形で入れること。
  - **名前付きグラフ**: トリプルにグラフ名を足し、フィードごとの出所と時点、PROV-O による系譜を持つ。
  - **オントロジー抽出パイプライン**: 資料からオントロジーを 7 段階で作る。再現率優先、来歴、根拠づけで LLM を囲い、上位オントロジーに anchor してから coin する。T-Box（スキーマ）と A-Box（個体）を分ける。

- Markdown が正本で、索引やグラフは使い捨ての派生データである（SCHEMA.md）。

- 要件定義書 §2.2 の利用場面: 技術資料を読む、実装前に調べる、不具合を直す、作業を終える、知識を見直す。§4.2 と O-03: 複数の wiki をまたぐ横断検索は未決。§5.3: Project Wiki の知見を Global Wiki に一般化する案。

### 収束 A：次に足す機能

指定された基準を、以下の順で採点した。

- **価**：利用者が得る価値。重み 25。
- **整**：既存設計との整合。重み 20。
- **規**：規模への耐性。重み 20。
- **軽**：実装と検証の軽さ。重み 20。
- **波**：他プラグインへの波及。重み 15。

1〜3 点は弱い、4〜6 点は条件付き、7〜9 点は強い、10 点は当該基準で特に明確な利点があるものとした。**点数は実測値ではなく、確認した実装と要件に基づく判断値**である。

\]

### 次のステップ：B の手順と SCHEMA.md 追記案

まず、次の三つを基本の流れにする。

1. **設計前**：query で根拠・反例・未確認事項を取り出す。
2. **質問後**：再利用価値のある比較・判断だけ synthesis に保存する。
3. **作業終了時**：実際の検証結果を learn に渡す。

既存コマンドへの依頼例は次のとおり。

```text
/wiki:query 今回の設計について、wiki にある選択肢、採用条件、
反例、未確認事項を整理してください。
今回の制約は……です。
事実、資料の主張、今回の推測を分け、ADR の下書きにしてください。
```

```text
/wiki:query この比較を、3か月後にも再利用できる synthesis として
保存する案を作ってください。
適用条件、反例、未確認事項と、参照した source を残してください。
```

```text
/wiki:learn 今回の作業の成果物と検証記録は……です。
使った wiki のページは……です。
観測した結果、原因についての仮説、適用条件、反例を分けてください。
既存の経験パターンがあれば統合してください。
```

不具合時は #18 を差し込む。

```text
/wiki:query 症状は……、環境は……、確認済みの事実は……です。
関連する過去の経験から原因仮説を挙げ、
各仮説を支持する観測と反証する確認手順を示してください。
過去の事例と、今回確認できた原因は分けてください。
```

現時点の知識を使う具体例としては、次の問いが適している。

> info-hive でコンテキストグラフを試すなら、現行の neighbors/path と query の組合せで何ができ、何が追加実装になるか。ADR-0009 を保つ案と、その見直しが必要な案を比較してほしい。

これなら、現在多く蓄積されているオントロジー・コンテキストグラフの概念を、実際の開発判断に利用できる。ただし、概念を説明する資料があることと、実装効果が検証されたことは区別する。

`SCHEMA.md` の「ワークフローのカスタマイズ」への追記候補は次のとおり。**今回の調査では追記していない。**

```markdown
- 設計・不具合調査の query では、事実、資料の主張、今回の推測、
  適用条件、反例、未確認事項を分ける。
- 重要な判断に使う主張は source を示し、必要な箇所だけ raw に戻って確認する。
- 新しい比較・判断を synthesis に保存するかは、
  「3か月後に再利用したいか」で決める。
- synthesis には必須の frontmatter と sources を付ける。
  question と sources_consulted は補助情報として記録する。
- 作業終了時、再利用価値のある経験を /wiki:learn に渡す。
  過去の wiki を使った場合は、ページ名と今回の結果も記録する。
- 検索や経路が見つからないことだけで、事実が存在しないとは判断しない。
```

「ユーザーの好み」には、次の一項目で始めればよい。

```markdown
- 判断を支援する回答は、結論、適用条件、根拠、反例、
  未確認事項の順で示す。比較には表を使う。
```

synthesis 保存のワークフロー例にある `question`、`asked`、`sources_consulted` だけでは、SCHEMA の必須項目を満たさない。保存時は `type`、`title`、`tags`、`created`、`updated` と、source 以外に必要な `sources` を合わせて記録する。[R2][R3]

週次には既存の `/wiki:lint` を使い、重要な矛盾候補と、実際に再利用したページを少数選んで確認する。作者の SCHEMA の文字数・行数上限は汎用テンプレートと異なるため、lint の実行時も作者の規約に合わせる。[R2]

試用後はページ数だけでなく、次を確認する。これは自動計測の実装を要件にせず、作業終了時の記録から判断できる。

- 保存した synthesis を、後の作業で使ったか。
- 経験パターンによって、調査や設計の出発点が変わったか。
- 過去の条件との違いを見つけられたか。
- 原文に戻った結果、判断を修正した例があったか。
- 記録と確認の手間を続けられたか。

## 前提と不確実性

- **採点は一人の判断である。** 他のエージェントの成果は読まず、独立に評価した。点数差 0.05〜0.2 を、実測された優劣とは扱えない。
- **現在の利用頻度は不明である。** 設計判断、不具合調査、PDF の詳細確認、他エージェントからの利用の頻度次第で、#20・#23・#25 の優先順位は変わる。
- **現在の型付きエッジの密度と、有効期間の記入率は数えていない。** #1 は本文検索と wikilink でも動く設計を条件にした。型付きエッジが豊富であるとは仮定していない。
- **実装・性能検証は行っていない。** ビルド、索引生成、コマンドによる wiki の更新、PoC は実行していない。ファイルも変更していない。
- **23 件という数は、対象 4 ディレクトリ直下の `.md` の集計である。** 依頼文の 22 件との相違は確認したが、過去の集計時点は特定していない。
- **`.evolution/` の位置付けは依頼文を補正した。** 依頼文では派生データに含まれていたが、実際の SCHEMA と参照文書は、消してよいキャッシュではなく、保持する実験証拠とする。[R2][R7]
- **現在の `ontology.yaml` は、記事で論じられるオントロジーの全能力を実装していない。** SPARQL ASK、OWL の公理推論、現実の資源状態の検査を既存機能とはみなしていない。
- **「ローカル完結」は、確認した規約では検索・埋め込みの処理に関する条件である。** Claude Code や Codex の推論実行先まで、ローカルモデルに限定されたとは解釈していない。#23 は外部への公開サーバーを意味しない。
- **外部製品の最新仕様は調べていない。** Foam・Obsidian・MCP 連携の評価は、リポジトリ内の設計と、Markdown を利用する範囲に基づく。特定クライアントの接続互換性は未検証である。
- 指定された保存禁止領域 `docs/agent-runs/2026-11-06-wiki-knowledge-utilization/` は読んでいない。

基準への異議は二点ある。

第一に、A の「利用者価値」は追加差分を評価する一方、「実装の軽さ」は既存機能を高く評価する。このため、軽さを重くすると実装済みの案が上がる。全案比較には有用だが、開発対象を確定するときは、**既存機能で解決できない事例があるか**を併記したい。

第二に、A の「他プラグインへの波及」と「規模への耐性」は、現在の小規模 wiki に対して将来投資を促す。作者が当面一つの wiki を Claude Code で使うなら、API 化より B の定着を先にする判断も妥当である。逆に Codex・rag から繰り返し利用するなら #23 の順位が上がる。

作者に残る主な判断は、**「今もっと困っているのは、知識を使う習慣がないことか、取得・検証・外部利用の機能不足か」**である。今回は質問できない条件のため、B の試用でその違いを観察する進め方を採った。

## 根拠

### 1. 判断の土台

| 確認した事実 | 判断への意味 |
|---|---|
| 要件定義書 §2 は、過去の調査・設計判断・根拠を新しいセッションや別のプロジェクトで再利用することを製品の中心に置く。 | ページ数やリンク数より、作業で使われた回数と判断の質を評価する。 |
| `query-workflow.md` 手順5・6には出典付き回答と synthesis 保存が既にある。 | 「回答を保存する」だけでは新機能にならない。保存条件の運用はB、変更検出などの機械処理はAとして分ける。 |
| `commands/learn.md` は、実際の操作と成果物を確認し、適用範囲・環境・反例を記録する。 | 経験を次の作業に戻す仕組みは既にある。まず日常運用で使う。 |
| `wiki_graph_query.py` の `cmd_path` は出方向のエッジを幅優先探索する。状態・有効期間を選ぶ CLI 引数は確認できない。 | 経路が存在することと、現在も成立する意味的な関係があることは区別する。 |
| ADR-0009 は、グラフを wiki 内の任意の索引に位置付ける。 | グラフがない wiki でも主要な利用方法を成立させる。共通グラフ基盤は別判断にする。 |
| SCHEMA の `Skill evolution` は `.evolution/` を「キャッシュではない」と明記する。 | 実験履歴を検索索引と同様に廃棄しない。検索用の要約は通常のページに置く。 |
| 埋め込み統一 HTML レポート §13・§15は MCP 化を提案し、ADR の確定は別作業としている。 | MCP は有力な実装候補だが、採用済み機能として評価しない。 |

出典の詳細は末尾の「参照」に示す。

ここから導く設計上の推論は次のとおりである。

- **本文**は意味・条件・説明を持つ。
- **wikilink**は関連資料を発見する経路になる。
- **型付きエッジ**は、明示された関係とその根拠を確認する材料になる。
- **`ontology.yaml`**は、関係をどう記述してよいかの契約になる。
- **synthesis**は、複数資料をその時の問いに合わせて組み立てた判断を持つ。
- **raw**は、要約や統合の誤りを確かめるための戻り先になる。
- **経験と `.evolution/`**は、知識を実際に使った結果と改善の証拠になる。

したがって、グラフの密度を上げること自体を目的にせず、これらを作業の各段階で組み合わせる。

### 7. 次のステップ

**A：小さな PoC と ADR**

1. **根拠の束の出力契約を決める。**

**B：SCHEMA.md への追記案**

以下は提案文であり、この作業ではファイルに追記していない。

「ワークフローのカスタマイズ」への案：

```markdown
- 設計、実装、不具合調査を始めるときは、今回の目的と制約を明示して
  wiki に問い合わせる。適用できる知識、過去の反例、未確認事項を分ける。
- 取り込み後の報告では、新しく追加した知識、既存の理解を変更した点、
  対立する根拠、未確認事項を示す。
- 再利用する価値のある判断は synthesis に残す。問題と制約、選択肢、
  判断と根拠、適用条件、見直す条件を書く。既存ページとの重複を確認する。
- 作業終了時には、再利用できる経験がある場合に /wiki:learn を使う。
  成果物、観測結果、適用条件、反例を添え、原因仮説と確認済みの事実を分ける。
- 重要な判断に使う主張は、source から raw の該当箇所まで確認する。
  確認できなかった部分は未確認として残す。
```

「ユーザーの好み」への案：

```markdown
- 作業前の回答は、適用できる知識、注意する反例、未確認事項の順にする。
- 関係の経路だけを根拠に因果関係を断定しない。
- synthesis には、今の結論を見直す条件を含める。
- 同じ原資料を使う複数ページを、独立した複数の証拠として数えない。
```

使用例：

```text
/wiki:query 今回は〇〇を設計する。制約は△△。
適用できる過去の判断、反例、未確認事項を、出典付きでまとめて。

/wiki:query この設計をレビューする観点を、過去の経験から作って。
各項目に、今回適用できる条件と確認方法を付けて。

/wiki:query 今回の採用案と不採用案を比較し、
根拠、適用条件、見直す条件を synthesis として保存して。

/wiki:learn この成果物と検証記録から、観測事実、原因仮説、
適用条件、反例を分けて、再利用できる経験を記録して。
```

最初の2週間は案1・2・8を中心に試す。週末に `/wiki:lint` と `/wiki:stats` を使い、「ページが増えたか」ではなく、**以前の判断を再利用できたか、誤りを回避できたか、保存作業が負担になったか**を短く記録する。2週間は試行期間の提案であり、効果が確認済みという意味ではない。

## 前提と不確実性

1. **規模の数値に不一致がある。**  
   提示された内訳は `source 7 + entity 1 + concept 15 + synthesis 0 = 23` で、総数22と一致しない。本評価では「約22ページの小規模 wiki」と扱った。統計スクリプトは実行していないため、正確な総数は確定していない。

2. **`.evolution/` の扱いは現行ファイルを優先した。**  
   タスクの現状説明では派生データに含まれるが、作者の実 wiki の `SCHEMA.md` 196行とテンプレート193行は「キャッシュではない」とする。実験の原記録を再生成可能と仮定しない。

3. **README の節指定は実ファイルと異なる。**  
   指定された README に §13・§15はなく、同ファイル3行目が参照する HTML レポートに存在する。MCP 化はそちらの記述を根拠にした。

4. **グラフの有用性は未測定である。**  
   型付きエッジ数、根拠の充足率、有効期間の記入率、反証資料の割合は調べていない。Yuan An の連載を中心とする現状では、概念ページ数が多くても独立した証拠が多いとは限らない。案17は本文取得だけでも価値が出ることを条件にした。

5. **「ローカル完結」の範囲は確認が必要である。**  
   検索・埋め込みをローカルで行うことと、取得結果を受け取った Claude Code や Codex のモデル処理までローカルで行うことは別である。本案では検索・索引・MCP サーバーから外部サービスへ転送しないことを前提にした。全推論の端末内完結まで要求するなら、利用するエージェントとランナーの条件を追加する必要がある。

6. **evolve の実行可能性は確認していない。**  
   `evolution-workflow.md` 117行には、価格表の期限切れ後はレビューまで実行を拒否する記述がある。これが全ランナーに適用されるとは断定しないが、既存コマンドがあることだけで今日の評価実行を保証できない。

7. **採点は分析者の推定である。**  
   各機能の実装時間、精度、時間短縮は測定していない。小数点以下は加重計算の結果であり、0.05点差まで実用上有意という意味ではない。

8. **共通基準には二つの偏りがある。**  
   Aでは実装済みの運用案が「整合」「軽さ」で高得点になるため、新規実装価値が低くても上位に近づく。Bでは追加実装なしの案に限定するため「今日からできる」が10点に集中する。比較可能性のため指定基準は維持したが、最終判断では既存機能との差分と実際の使用頻度を併せて見る必要がある。

9. **書き込みと実行は行っていない。**  
   リポジトリと wiki を変更せず、ビルド、索引生成、評価実験も行っていない。指定された `docs/agent-runs/2026-11-06-wiki-knowledge-utilization` 配下と他エージェントの成果は読んでいない。長期保存すべき知見の wiki への反映も、今回の読み取り限定の範囲では行っていない。

一方、[commands/learn.md](C:/Works/info-hive-dev/info-hive-wiki/commands/learn.md) は、**観測した事実と原因についての仮説を分けて書く**よう求める。[要件定義書 §5.3](C:/Works/info-hive-dev/llm-wiki-product-concept-and-requirements-ja.md:218) の F-E03 も、「推定だけの原因を**検証済みとして**保存しない」という規則であり、仮説そのものの記録禁止ではない。

反例：

> タイムアウトを観測した。接続プールの枯渇を疑ったが、計測前に作業を終了した。

Bの規約に従うと原因仮説が消え、次回は同じ仮説の立案からやり直す。既存 learn が残せる「観測事実・未検証の仮説・未実施の確認」の区別を失う。**未検証を検証済みと偽ることの禁止を、未検証情報の保存禁止に変えている。**

**B-4［重大］出典チェーンのPoCが、参照フィールドをグラフの段として扱っている。**

案7のPoCは `sourced_from → summarizes_raw → raw_ref` をたどるとする。しかし `raw_ref` は、[SCHEMA.md.template](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/assets/SCHEMA.md.template:113) では**型付き関係の任意フィールド**であり、raw ノードから出る次のエッジではない。

反例は、concept に `sources` があり、source に `raw` があるが、型付き関係が一つもないページである。前二段は生成されるが、最後の `raw_ref` は存在しない。さらに、ある型付きエッジに `raw_ref` があっても、それが回答中の別の主張を裏付けるとは限らない。

Bは末尾で「raw パスまでで止まる」と認めている。それは限界の開示ではあるが、**上位案として掲げた主張から原文の該当箇所までの自動チェーンを、提案した探索だけでは実現できない**ことも意味する。

**B-5［重大］「基準の重みでの上位」という結論が採点表の順位と一致しない。**

結論の上位は39＋40、2、7、8、27。一方、表の基準点では以下が上位になる。

|---|---:|
| 39 | 8.15 |
| 2 | 8.00 |
| 21 | 7.80 |

案8・27は7.50点であり、上位5案とはいえない。手順案を開発候補から外したと解釈すると、手順案39だけが残る理由を説明できない。

**採点表とは異なる選別を行いながら、その結果を基準順位と呼んでいる。**

### 崩れる前提

- **エッジ0本の source は、取り込みの検討不足を表す。**  
  成立しない。A・B自身の集計では `authored` の主語はpersonである。関係を正しく別の主体ページに記録した場合でも、source自身の型付き出辺は0本になり得る。source単位の本数は、その資料から抽出された関係の総量ではない。
- **現在の `status` と有効期間だけで、過去時点の知識状態まで分かる。**  
  過去に何を知っていたかと、その関係がいつ有効だったかは別である。後日訂正された関係について、現在のデータだけから当時の認識を復元できるとは限らない。
- **経験がない状態でも「過去の経験を引く」運用が今日から十分な価値を持つ。**  
  コマンドは実行できるが、該当資料がなければ成果は空になる。B自身が経験0件を前提にしており、開始可能性と利用可能性を分離できていない。
- **MCP 化で3.1秒が数十msになる。**  
  A-3と同じ測定範囲の問題がある。

## エージェント C への攻撃

### 判定

**条件付きで採用可。確信度：中。**

今回確認できた範囲では、A・Bに相当する**致命的な既存機能の誤認や、規約の逆転は崩せなかった**。ただし、機能候補として成立することと、提示された開発順位が現在のwikiに適することは別である。

### 致命的・重大な欠陥

**C-1［重大］「現在も効果が出る」という採点条件を、将来の蓄積後の効果で置き換えている。**

Cは、synthesis が0件であることを確認しながら、synthesis 再確認機能を9.00点で首位に置き、規模耐性を9点としている。経験検索にも規模耐性9点を与えるが、現在の経験蓄積量は確認していない。

指定された規模耐性は、単に150ページ以上に対応できることではなく、**今の小規模wikiでも効果が出ることとの両立**である。

反例は、作者が当面、concept の参照と資料取り込みだけを行い、synthesisを作らない状態である。この場合、再確認機能は正しく動作しても毎回対象0件を返す。経験検索も経験がなければ同様である。

Cは「先にBを試す」と依存を開示しているため、実装不可能とまではいえない。しかし、**その試用によってデータが生まれることを前提にした順位を、現在のデータに対する順位として数値化している**。これは機能の否定ではなく、首位・上位という優先順位の根拠の欠陥である。

なお、これ以外に、今回の照合で重大と断定できる欠陥は見つからなかった。設計の詳細が未確定というだけで、追加の欠陥として数えない。

### 崩れる前提

- **source の変更が、再確認負担に見合う警告を生む。**  
  誤字修正や参考リンク追加が多く、同じsourceを多くのsynthesisが参照する場合、候補が大量に出る。Cは誤警告の問題を認識しているが、現在のwikiで許容できるという証拠はない。優先順位が下がる可能性は**推測**である。
- **内容ハッシュがあれば、既存 synthesis の根拠の変化を判定できる。**  
  保存時に参照した版のハッシュがなければ、導入前に起きた変更は現在のハッシュだけでは分からない。CはPoCとして提案しているため実装済みの誤認ではないが、既存保存物への効果には未確定の範囲がある。
- **適用条件付き経験検索が、通常の query より良い結果を返す。**  
  自由文の適用条件に例外や環境差が多い場合、単純な条件抽出・照合は誤適用を生む。CはPoCで確認するとしており、現時点で追加効果が実証されたわけではない。
- **local 完結は検索・埋め込みに限る。**  
  Cはこの解釈を明記しているが、課題文の「wiki やクエリの文字列をマシンの外に出さない」が推論先まで含むなら、ホスト型エージェントへの取得結果の受け渡しは条件に反する。実際の推論先は確認していないため、違反したとは断定しない。

## 規則

- 票数ではなく根拠の質で優劣を付ける。複数が同じ結論でも、同じ資料を写しただけなら独立に同じ結論へ至ったとは言えない。
- 根拠があり反証されていない攻撃を、成果の主張より優先する。「崩せなかった点」は独立した検証として扱う。推測と明記された攻撃で優劣を付けない。
- 正面から割れた論点は根拠で決める。決められないなら、決めるために何が要るかを書く。
- 作者の判断が要ることは、選択肢とそれぞれの帰結を並べる。
- 日本語で書き、結論を先に書く。
