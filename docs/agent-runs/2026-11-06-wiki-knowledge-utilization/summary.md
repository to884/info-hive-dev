# LLM Wiki で蓄積した情報の活用方法 の総括

## 推奨

スコープ B を先に始める。「設計前に `/wiki:query` で引いて再利用する判断を `synthesis/` に残す」「取り込み後に既存の主張との差分を報告する」「作業の終わりに観測事実と原因仮説を分けて `/wiki:learn` で残す」の 3 つを SCHEMA.md に書き、2〜4 週間回す。スコープ A は 4 体の順位表をどれもそのまま採用せず、採点の外にある 2 つの具体的な一手（`query-workflow.md` の synthesis の frontmatter の例の修正、MCP サーバー化の範囲を ADR で決める）と、着手条件つきのコード機能 3 候補（コンテキストの切り出し、出典チェーン、鮮度 lint）をロードマップの入力にする。

## 批評で動いたこと

- **4 体すべてが自己見直しで上位の結論を変えた。** A は 1 位の rag 併用を条件付きに下げ、synthesis の保存基準に frontmatter の条件を足した。B は 1 位の「型付きエッジの検討規約」を B 専用に移し、A のコード機能の順を context → 出典チェーン → 鮮度 lint → MCP に改めた。C は 1 位の synthesis 再確認の首位を撤回した。D は 3 位の synthesis 再点検を撤回し、コンテキスト切り出しの点数を仮説値と認めた。
- **決定的だった反論は 2 つ。** 1 つ目は C と D が見つけた「ingest の手順 7 と ingest-workflow の 8b に型付きエッジの段が既にある」で、私も原文で確認した。B の A 1 位の根拠「取り込みの手順に段がない」はこれで崩れた。2 つ目は A と B が C・D に向けた「synthesis も経験も `valid_*` も 0 件なのに規模 9 を付けた」で、C と D の A 上位はこれで順位の根拠を失った。A 自身の鮮度 lint も同じ理由で上位の根拠が弱い。
- **A の 1 位を崩したのは B の実測。** B が `W1_Raw/` に PDF が 0 件であることを確かめ、さらに統一レポートの ADR 案 B が rag から索引を外す向きであることを示した。rag 併用の query は今は何も返さず、計画とも逆向きになる。
- **最も実用的な発見は C の frontmatter の指摘。** `query-workflow.md` の synthesis の保存例には `title`、`created`、`updated`、`sources` がなく、そのまま保存すると `wiki_lint.py` が必須項目の欠落を報告する。A と B が原文で一致を確認した。4 体すべての B スコープの上位案がこの例を踏むので、採用条件として必須になる。
- **B の「推定の原因は記録しない」は採らない。** C と D が `commands/learn.md` と要件 F-E03 を根拠に、既存仕様は観測事実と原因仮説を分けて残すものであり、仮説の記録禁止ではないことを示した。反論は成立している。
- **「数十 ms」は MCP 全体の性能ではない。** C と D が統一レポートの測定条件を確かめ、常駐プロセス内のウォーム検索の値で通信を含まないことを示した。A と B の MCP の価値の数字はこの範囲を越えて使われていた。
- **決着しなかった点**: B が「`evolution-workflow.md` 117 行の価格表の期限切れは確認できず」としたが、私が原文を読むと「レビュー済みの価格表は 2026-10-13 に期限が切れ、レビューし直すまでは実行を拒否する」とあり、A が正しい。API のランナーで `/wiki:evolve` を今評価するには価格表の再レビューが先に要る。

## 推奨案が残る理由

- **B スコープの 3 習慣は 4 体が独立に上位に置き、どのレビューも運用そのものは崩せなかった。** 崩れたのは「保存基準が存在しない」(A の説明)、「`/wiki:query` に `--type synthesis` を渡す」(B の手順)、「仮説を記録しない」(B の文案) という付随の説明であり、本体ではない。既存の query-workflow に保存基準（3 か月後に見つけたいか）は既にあるので、差分は「毎回判断し、保存しない理由も書く」運用だけである。
- **A スコープの順位表が使えない理由は 4 体で共通。** 対象データが 0 件の機能に「今も効く」点を付けた（A、C、D）。実装不要の運用案が整合と軽さで機能案を押し上げた（A、B）。素点を束ねて再計算できない（A の 43 案中 20 案）。組合せに単体の点を付けた（B の 39+40）。5 つ目の採点表を作っても同じ偏りを持つので、推奨は順位ではなく着手条件の形にした。
- **frontmatter の例の修正は、採点に関係なく実在する不備である。** プラグインの変更として最も小さく、B スコープの全案の前提になる。パッチ版の対象になる。
- **MCP は点数で決められない。** 軽さの素点が 4 体で 3〜6 とばらつき、重みに最も敏感だった。範囲の選択で波及も ADR-0009 との関係も変わるので、ADR で決める案件である。
- **コード機能 3 候補は差分が明確で、レビューでも「候補として」は全員が残した。** `neighbors` は 1 ホップで予算がなく、`path` は出辺だけの BFS で `status` を見ない。出典の経路は `sourced_from` と `summarizes_raw` までしか自動生成されず、`raw_ref` は 0 本。lint の古さの判定は 90 日と被リンク 3 だけである。
- **横断グラフ基盤の保留は 4 体が一致し、根拠も同じ ADR-0009 の見直し条件である。** これは票数ではなく、決定文書そのものが根拠なので高い確信で採れる。

## エージェントごとの要約

**エージェント A** は作者の wiki を実測し、型付きエッジが `authored` 5 本のみで synthesis も経験も 0 件という事実を最初に示した。A スコープは rag 併用の query と MCP を同率 1 位、B スコープは取り込み報告の差分表を 1 位にした。当たっていた指摘は、rag 併用が PDF 0 件で今は効かず ADR 案 B と逆向きであること（B）、43 案中 20 案が束ね採点で再計算できないこと（B、C、D）、`contradicts` の片側だけを不整合とする lint が正常データを誤検出すること（C）、平均次数から 2 ホップの被覆を推測できないこと（C、D）、synthesis の保存基準は既存手順にあり新設ではないこと（C、D）、`status` の明記を B の 2 位に置いたが適用対象のエッジがないこと（B）。本文を読まずに「中身が薄い」と断定した点も D の指摘どおり過大である。

**エージェント B** は A と同じ実測に加え、発散を手順版とスクリプト版に分けて全案を個別に採点し、重みを 3 通りで示した。「材料が不足しており B の運用が A の前提を作る」という診断は 4 体の中で最も明快だった。しかし A 1 位の「型付きエッジの検討規約」は、既存の ingest 手順 7 を見落として「段がない」と書いた点（C、D）、スクリプト 40 を含めながら 39 単体の点を付けた点（A、C、D）、述語の型制約で concept 間はほぼ `depends_on` に限られる点（A）で崩れた。「推定の原因は記録しない」の文案は learn の仕様に反する（C、D）。CLAUDE.md に `--type synthesis` を書く手順は query の引数と合わない（A、C）。ページ数 22 も実際は 23 である。

**エージェント C** は 32 案を個別に採点し、「既存機能で解決できない事例があるか」を機能追加の判断に添えるべきだという基準への異議を最も明確に書いた。synthesis の保存例の frontmatter の不備、`.evolution/` がキャッシュではないこと、MCP の `query` 案が回答生成ではないことを C だけが、または最初に見つけた。当たっていた指摘は、synthesis 再確認（#5）と経験検索（#20）に対象データがないのに規模 9 を付けたこと（A、B、D）、型付きエッジの密度を数えずに時点指定（#11）を採点したこと（A、B）、読み取り専用 MCP に波及 10 を付けたが索引の持ち主にはならないこと（A）、learn の「知識の質 10」が基準の文言と合わないこと（B）。C は自己見直しで #5 の首位を撤回した。

**エージェント D** は C とほぼ同じ構成で、32 案を個別に採点し重みを 3 通り示した。「経路の存在と意味的関係の成立は別」「MCP にすることと横断基盤にすることは別の決定」という線引きはレビューでも崩れなかった。当たっていた指摘は、根拠の束（#18）が `raw_ref` 0 本で延長元を持たないこと（B）、synthesis 再点検（#19）と時点フィルター（#22）に対象データがないこと（A、B）、作業開始時に `/wiki:evolve history` と `show` を読む案（#14）が SCHEMA の「実験の履歴をタスクの実行に混ぜない」規約と衝突すること（C）、案 17〜32 を番号帯で B から外したが #25 と #32 は既存機能で回ること（C）。C と D の上位案の素点の組が一致している点は B が推測として挙げた。原因は断定しないが、この 2 体の一致を独立した 2 票とは数えていない。

## 残るリスクと未確定事項

- **今いちばん困っているのは「使う習慣がないこと」か「取得・検証の機能不足」か。** C が立てた問いで、これが MCP とコード機能の優先度を決める。作者しか答えられない。習慣なら B スコープだけで 1 か月回してから A を見直す。機能不足なら、どの質問で既存の query が失敗したかの実例を 3 件ほど残してから PoC に入る。
- **MCP サーバー化の範囲。** 選択肢は 3 段階ある。(a) 読み取りのみ（query、get_page、list_index）: 軽いが wiki が索引の唯一の持ち主にはならず、rag のモデル二重読み込みは解消しない。(b) 統一レポートの案 B（`index_chunks` を含む）: モデルと索引の共有という目的を満たすが、ADR-0001 の 3 条件と usearch の Windows のロックが前提になる。(c) rag に `graph` ツールを開く: ADR-0009 の「見直す条件」の 1 つ目に当たる。どれを選んでも「数十 ms」を製品の問い合わせ性能として書かない。
- **`decision` と `claim` のページ型を足すか。** ADR の置き換えを `supersedes` で残すには目的語が要るが、これらは `explicit_only` でページがなく、lint がリンク切れを出す。足すなら frontmatter の互換性（O-04）の論点を伴う。足さないなら当面は source どうしの `supersedes` に限る。
- **ADR を Global wiki に必ず取り込むか。** ユーザーの CLAUDE.md は「プロジェクト全体を自動で取り込まない」としている。Project wiki に入れる、Global には一般化した知見だけ入れる、という分け方が要件 §5.3 と整合する。
- **型付きエッジ不足が「最大の制約」かは未立証。** B は主張し、C と D は本文利用が成立すると反論した。解けなかった質問の実例が提示されていないので決められない。取り込み時の検討は既存手順 7 の上に「見送りも log に記録する」を足す補助規約にとどめ、首位には置かない。
- **コンテキスト切り出しの今の効果は未測定。** 23 ノードで 2 ホップがどこまで届くかは平均次数からは言えない。PoC の最初の作業は実 wiki での被覆率の実測にする。
- **`/wiki:evolve` は API のランナーで今は動かない。** 価格表が 2026-10-13 に期限切れで、再レビューまで実行を拒否する。日本語の評価スイートも未確認。B スコープで evolve を当面外すのは妥当である。
- **「ローカル完結」が推論先まで含むか。** C と D は検索と埋め込みに限る解釈を採った。Codex などホスト型エージェントに取得結果を渡す構成を採るなら、この解釈を ADR に明記する。
- **課題文の訂正。** ページ数は 22 ではなく 23。統一レポートの §13 と §15 は README.md ではなく `embedding-backend-unification-2026-11-05.html` にある。`.evolution/` は派生データではなく保持する実験証拠である。
- **採点の限界。** 4 体とも実装も測定もしておらず、点数は判断値である。本総括も点数の小数差では順位を決めていない。
