## 致命的・重大な欠陥

### 1. 重大：C1と`/wiki:init`を通しても、S1にも初回取得の完了にも到達しません

**反例となる手順：**

1. RuriモデルのないS0から、C1どおりプラグインを導入し、`/wiki:help`を実行する。
2. W1の`/wiki:init`を実行し、`"status": "ready"`を得る。
3. 計画243行の指定どおり、ここで時間とキャッシュ容量を記録する。

この経路では、MCP用のRuriモデルを取得しません。MCPサーバーは起動時にモデルを取得せず、検索要求で`State.embedder()`が呼ばれたときに取得を始めます。一方、`/wiki:init`の`ready`は、別系統のFastEmbed／E5モデルと索引の準備を示します。

したがって、次の食い違いが生じます。

- C1完了後に待っていても、「MCPサーバーの依存とモデル取得が終わったS1」にはなりません。
- `init`の`ready`で測定を終えると、計画が約530 MBとするRuriの取得時間と容量が範囲から外れます。
- W1の質問は索引からページを選んで回答できるため、出典付き回答が得られても、この不足を検出できません。

S1を作るために別途検索してモデルを取得すれば、未記載の準備操作が加わります。通常のwiki検索には初期化済みのwikiも必要なので、その準備で先に`init`すると、FastEmbedも取得済みになり、W1の初回条件が変わります。

**根拠：**

- [計画:197](C:/Works/info-hive-dev/.claude/worktrees/usage-docs-plan/docs/plans/usage-docs-2026-11-15.md:197)：C1の範囲は導入とhelp。
- 同238・243行：S1の定義と測定の終点。
- [setup_wiki.py:27](C:/Works/info-hive-dev/.claude/worktrees/usage-docs-plan/info-hive-wiki/skills/info-hive/scripts/setup_wiki.py:27)：`ready`を返す準備処理。
- [wiki_mcp_server.py:205](C:/Works/info-hive-dev/.claude/worktrees/usage-docs-plan/info-hive-wiki/skills/info-hive/scripts/wiki_mcp_server.py:205)：未取得モデルの取得開始。255行以降は、取得中に語彙検索で返す経路。
- 同501行以降：起動処理にはモデル取得がありません。

判定は**食い違い**です。実機の通信量は未計測ですが、この実行経路はコードで確認できます。

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
| --- | --- |
| MCPサーバーを起動すれば、そのモデルも取得される | 起動とhelpだけを行い、MCPの検索を呼ばない |
| `init`の`ready`を、両方の検索環境の準備完了に使える | E5の準備が済み、Ruriは未取得である |
| S1の準備を足しても、W1の初回条件は変わらない | 別のwikiを初期化してモデル取得を進め、共有キャッシュが温まる |
| スクリプトに0件の値があれば、読者にも0件と表示される | lintがCLI経路を使い、0件の項目を省略する |
