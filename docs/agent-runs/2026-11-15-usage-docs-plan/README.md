## 指摘の原因

重大の 1〜3 は、同じ前提から来ていた。成功の目印を、エージェントが判断して作るもの（ページの数、ページどうしのリンク、返答の本文）の上に置いていたことである。取り込みの手順は、主張をソースの要約に残すこと（`source_only`）を認め、`/wiki:init` の定義は JSON の転載を命じていない。目印を 1 つずつ差し替えるのではなく、目印に使ってよいものを、スクリプトかコマンドの定義が決めるものと、定義が出力をそのまま示すよう命じているものに限る規則を、計画の 2-5 に書いた。

重大の 4 と 5 は、どちらも「確かめたつもりで、別のものを確かめる」経路だった。4 は試行の初めの状態が決まっていなかったこと、5 は試験が試験のファイルの置き場所から対象を決めることである。初めの状態（S0、S1）と、試験を走らせる作業ツリーを、計画に書いた。

## 指摘への対応

| 指摘 | 対応 |
| --- | --- |
| 1. 取り込みで `index.md` が 1 行だけ増えるとは限らない | 2-5 の規則を立て、目印を、raw のファイル名から決まる `wiki/sources/味噌.md` と、`log.md` の決まった書式の行に替えた。`index.md` は「`[[味噌]]` の行が増える」とし、数は書かない |
| 2. W2 の共通のリンクと「2 本の出典」は、目印にならない | 目印から外した。つながりは、読者が話し合いの手順で頼む形にし、目印ではなく「こうなるはずです」という案内にとどめる。ならなかったときの対処も書く。質問の出典は「1 つ以上」とした |
| 3. `/wiki:init` の JSON が、返答の本文に出る保証がない | 目印を、会話の中のツールの呼び出しの欄の出力にした。デスクトップアプリでその欄を読めるかは、未確認に足し、段階 2 で確かめる |
| 4. 3 回の試行と大きさの計測に、初めの状態がない | VM のスナップショットで S0 と S1 を決め、各試行を S1 から始める。計測の範囲を「プラグインを入れる直前」から「`"status": "ready"`」までにし、3 つのキャッシュの大きさを前と後で記録する |
| 5. 「最新の main で試験を通す」では、変更したプラグインを試験しない | 変更したサブモジュールを checkout した同じ作業ツリーで試験を走らせ、`git -C info-hive-wiki rev-parse HEAD` を確かめると書いた。「手元にこのファイルがない」の誤りも直した |
| 6. 公開とリンクの版の対応を確かめずに終われる | 段階 3 で公開先を決めるときの 3 つの問い（版の対応、`wiki_help.py` の書き換えの規則と試験、公開の手順）を書いた。段階 4 の終わりの条件に、公開した URL の確認を足した。ADR-0022 の「版がそろう」を、リポジトリの中に限る書き方に改めた |
| 軽微: 大きさの合計と引用の根拠が合わない | 表の値は目安で、足すと約 1.8 GB、1.5 GB はコメントで計測ではない、と書いた |
| 軽微: 認証の確認と git の確認の順序 | 段階 2 の確かめる順を、git の有無 → 認証の順にした |
| 軽微: 残す文書にも消すファイルへのリンクがある | 張り替えの対象に残す文書を足し、`search.md:7` を例に挙げた。リンクの確かめ方にアンカーを足した |
| 軽微: `commands.md` だけでは `/wiki:help` がです・ます体にならない | `commands/*.md` の frontmatter も書き直すと、計画と ADR-0022 に書いた |

## 2 回目のレビュー（2 版）

重大の 1 件は、1 回目の 4 の対応が、まだ原因に届いていなかったものである。2 版は、S1 を「C1 を終え、MCP サーバーの依存とモデルの取得も終えた状態」とし、計測の終わりを `/wiki:init` の `"status": "ready"` にしていた。ところが、モデルを取ってくるきっかけは 3 つに分かれている。MCP サーバーの依存は最初に接続したとき、e5 は `/wiki:init` のとき、ruri は MCP サーバーの最初の検索のときに取る（`wiki_mcp_server.py:205`。起動のときには取らない）。2 版は「導入すれば全部そろう」と考えていたので、S1 を作れず、ruri を計測の範囲から落としていた。

計画の 2-3 を、きっかけごとの表に書き直した。S1 は「依存だけを取り、e5 と ruri は取っていない状態」とし、S1 を作るために `/wiki:init` や検索をしてはならないと書いた。計測は、きっかけごとに別々に、始まりと終わりを決めた。

| 指摘 | 対応 |
| --- | --- |
| 1. C1 と `/wiki:init` を通しても、S1 にも初回の取得の終わりにも届かない | 上のとおり。W1 の各回は S1 のスナップショットに戻して始める（新しいフォルダーだけでは、PC で共有するモデルのキャッシュが残る）。ruri を取っているあいだも語彙の検索で答えが返るので、W1 には取り終えたことの目印を置かず、案内だけを書く |
| 軽微: lint の「0 件」は、どの経路でも出る表示ではない | lint の目印を、ツールの呼び出しの欄の結果にした。MCP なら 2 つの一覧が空、CLI なら「問題は見つからなかった。」と、経路ごとに書いた |
| 軽微: 消すファイルを参照するものの列挙に `CHANGELOG.md` が抜けている | 参照するものを並べるのをやめ、消す・移すファイルの名前で `info-hive-wiki` の全体を Grep する手順にした |
| 軽微: P0 の扱いと分類の合格の条件が矛盾する | P0 を、`diataxis` の classify の対象から外すと書いた |

## 3 回目のレビュー（3 版）

重大の 1 件は、2 回目の重大と同じ原因の残りである。3 版は、ruri を取るきっかけを「W1 の最初の質問」と書いていた。実際に ruri を取り始めるのは MCP のツール `query` だけで（`stats` は取らない。`wiki_mcp_server.py:397`）、`/wiki:query` は索引から候補が見つかれば検索をしない（`commands/query.md:15`）。そのため、W1 の質問で ruri を取るとは限らず、計測の終わり（`verified.json`）に届かない正しい経路があった。

原因は、プラグインの中で起きる出来事（モデルの取得、MCP の接続）を、読者の手順に結びつけて書いていたことである。2 回目の対応は、きっかけを 3 つに分けたが、3 つ目を手順に結びつけたままにしていた。4 版では、きっかけの表を「プラグインの中の出来事」として書き直し、手順には結びつけない。計測は、チュートリアルの手順に頼らず、きっかけそのものを起こす操作（`--ensure`、`/wiki:init`、MCP のツール `query` をはっきり頼む）で行う。文書では、手順で起きる 2 つだけをその手順に書き、3 つ目は解説とトラブルシューティングに書く。

| 指摘 | 対応 |
| --- | --- |
| 1. ruri の取得を W1 の最初の質問に結びつけたので、計測の終わりに届かない正しい経路がある | 上のとおり。ruri の計測は、W1 の試行とは別の回に、MCP のツール `query` をはっきり頼み、ツールの呼び出しの欄で呼ばれたことを確かめてから計る |
| 軽微: lint の目印は、検査できなかった状態も成功として受け入れる | 目印に、読めなかったページ（`read_errors`）の項目がないことを足した |
| 軽微: `--ensure` の終了コード 0 は「MCP サーバーがつながった」ことを示さない | 依存の計測の終わりを「`--ensure` が終了コード 0 で終わった」（依存がそろい、サーバーが動いている）と書き直した。Claude Code の側がつながったことは、段階 2 の 7 で、読者が見られる場所を探して別に確かめる。`/wiki:help` が MCP を使わないことも書いた |

## 4 回目のレビュー（4 版）

3 回目の重大（ruri の計測）は、解消したと確かめられた。新しい重大の 2 件は、原因が別である。

1 件目は、`UV_SYSTEM_CERTS` の設定を、uv の版を確かめずに一律に入れさせていたことである。古い uv はこの名前を黙って無視し、しかもプラグインの起動処理は、この名前が設定されていると「利用者が決めた」とみなして、OS の証明書ストアでのやり直しをしない（`wiki_mcp_common.py` 452〜465 行）。そのため、古い uv では、設定しないときより悪くなる。2 件目は、リンク先が決まることと、リンクの書き方が決まることを取り違えていたことである。

| 指摘 | 対応 |
| --- | --- |
| 1. `UV_SYSTEM_CERTS=true` の一律の設定は、古い uv では自動のやり直しを止める | C2 の手順を、`uv sync --help` で uv が読む名前を確かめ、なければ uv を新しくしてから設定する順にした。新しくできないときだけ `UV_NATIVE_TLS` を使う。設定された名前をこの uv が読まないときにやり直さない作りは、プラグインの側の問題として、直すかを作者に諮ると書いた |
| 2. 索引の目印 `[[味噌]]` は、定義が決める文字列ではない（別名付きのリンクも認められている） | 目印を「`[[味噌` で始まるリンクの行が増える」にした。決まるのはリンク先だけで、書き方は決まらないと書いた |
| 軽微: W2 を待つ決定に、S1 の版を合わせる条件がない | S1 をプラグインの版に結びつけ、スナップショットの名前に版を書く。文書の版が変わったら、S0 から新しい S1 を作り、W1 から通すと書いた |
| 軽微: `read_errors` を足しても、一覧を取れなかったディレクトリのページは検査されずに「問題なし」になる | lint の目印に、検査したことを示す値（調べたページの数、`total_pages`）が 2 以上であることを足した |
