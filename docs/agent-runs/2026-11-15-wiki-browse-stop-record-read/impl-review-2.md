## 崩れる前提

- **記録の読み取り失敗後、成功するには記録の再読成功が必要である。** サーバーが終了してロックが空けば、再読成功なしで `stop` は成功する。9.2 の例外は、この経路を含んでいない。
- **補助スレッドは合図を受けてから先へ進む。** `wait_unreadable()` は 20 秒で `False` を返すが、呼び出し元は戻り値を確認していない。時間切れでも記録の削除とロック解放が進む。

## 見落としと軽微な問題

1. **軽微（設計）：7.1 と 9.2 の不整合が残っている。**

   次の二つの順序で、実際の `stop` は警告なし・終了コード 0 になった。

   - 記録の読み取りが `Unknown` → サーバーが終了してロックが空く → `{"stopped": false, "running": false}`。
   - 読めた記録で停止要求を送る → 終了中の記録が `Unknown` → 記録が消えてロックが空く → `{"stopped": true, "running": false}`。

   どちらも、失敗後に「読み直して読めた記録で続けた場合」ではないため、9.2 の例外には該当しない。一方、7.1 はロックを真実として終了を認めている。ロックを確認しているので、この反例自体を P1 違反とは判定しない。

   根拠：`docs/plans/wiki-browse-structure-2026-11-11.md:438–441,490`、`wiki_browse.py:766–769,785–794`、`wiki_browse_fs.py:1367–1370`。

2. **軽微（試験）：20 秒を超える遅延では、正常側・対照側とも順序依存の失敗が残る。**

   停止要求で `_stopping` が立った後、呼び出し側への復帰だけを 21 秒遅らせる。補助スレッドは 20 秒で合図待ちを抜け、先にロックを離す。再開した `stop` は `not-running` を確認するため、次の結果になる。

   - 通常側：`AssertionError: 0 not greater than 0`
   - 対照側：`AssertionError: Unknown not raised`

   実際の試験メソッドと `stop` を使い、ファイルと HTTP をメモリ内の代替処理にした再現で確認した。有限の待ち時間を超える条件であり、1 回目の 0.6 秒の反例と同じ重大度には扱わない。

   根拠：`tests/wiki/test_browse_server.py:360–361,425–431,460–485`。

## 検証した事実

- **一致：** 1 回目と 2 回目の `plugin.diff` はバイト単位で同一。
- **一致：** メモリ内の再現で、停止要求の復帰を 1.5 秒遅らせた 3 件は通過した。削除待ちの OS 状態自体は代替処理である。
- **一致：** 合図が最後まで立たなければ、通常側と対照側の `denied > 0`、削除待ち側の `unreadable.is_set()` が成立しない。合図なしで誤って通る経路は示せなかった。
