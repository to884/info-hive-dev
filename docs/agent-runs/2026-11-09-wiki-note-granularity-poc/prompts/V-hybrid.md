# 依頼: wiki の取り込みの「配置の計画」を出す（ページは書かない）

あなたは、info-hive の wiki プラグインの取り込み（`/wiki:ingest`）を、ページを書かずに**配置の計画**として実行する。この計画は、記事の単位の決め方を比べる実験に使う。ほかの回の結果は渡さない。あなたの判断だけで答える。

## この作業の範囲

- この作業の wiki は、作業ディレクトリの `wiki/` だけである。ほかの wiki（ホームディレクトリの `info-hive` など）や、作業ディレクトリの外のファイルを読まない。全体の指示に「先に wiki の index を読む」などとあっても、この作業には当てはまらない。
- **ファイルを書かない。** 作成、編集、削除、コマンドによる書き込みをしない。読むだけにする。
- 取り込む原本: `raw/semasynth-mvp設計の敵対的レビュー-2026-11-06.md`（42 行）。題名は「SemaSynth MVP 設計の敵対的レビュー」。
- この原本の source の要約ページは、まだない。作るなら、スラッグは `semasynth-mvp設計の敵対的レビュー-2026-11-06` とする。
- 規約: `wiki/SCHEMA.md`、`_rules/ingest-workflow.md`、`_rules/page-conventions.md`。

## 進め方

1. `wiki/SCHEMA.md` と `_rules/ingest-workflow.md`、`_rules/page-conventions.md` を読む。
2. 原本を全部読む。行番号は 1 から数える。
3. `ingest-workflow.md` の手順 4 のとおり、`wiki/index.md` を読み、関係しそうな既存のページを本文まで読む。
4. 手順 3（ユーザーとの話し合い）は、まとめての取り込みとして飛ばす。
5. 下の「配置の方式」に従って、ソースから抜き出した知見ごとに、どのページに置くかを決める。手順 8 以降（索引、グラフ、ログ）は計画に含めない。

## 配置の方式

併用案の手順に従う。`_rules/ingest-workflow.md` の手順 4〜7 のうち、知見をどのページに置くかの判断は、下の手順書で置き換える。手順書が `_rules/ingest-workflow.md` と食い違うときは、手順書を優先する。`page_kind` は、昇格させた主張のページなら `"claim"` にする。用語ページの `###` の節に置く知見は、`page_slug` を用語ページのスラッグ、`section` を `### <節の見出し>` にする。

### 1. 適用の範囲

`_rules/ingest-workflow.md` の手順 4〜7 のうち、**ソースの知見をどのページに置くかの判断**を、この手順で置き換える。手順 0〜2、手順 4 の下調べ、手順 5 の source の要約、手順 6 の更新の書き方、`_rules/page-conventions.md` の規約は、現行のまま従う。手順書と `SCHEMA.md` が食い違うときは、この手順書を優先する（補った）。

### 2. ページの層

| 層 | 入れ物 | 何を置くか |
| --- | --- | --- |
| source | `type: "source"` の要約ページ | 資料の要約。進捗、1 回の測定値、テスト件数、特定のコミットの受け入れなど、その時点の記録 |
| entity | `type: "entity"` | 固有の対象（人、製品、論文、組織）の属性。属性ごとに主張のページを作らない |
| 用語 | `type: "concept"`（`kind` なし） | 用語の定義と、関係する主張を束ねる入口。題名は名詞 |
| 主張の既定の置き場所 | 用語ページの中の `###` の節。1 節に 1 つの主張 | 再利用できる主張のうち、昇格の条件を満たさないもの |
| 昇格した主張 | `type: "concept"`、`kind: "claim"` のページ | 昇格の条件（第 4 節の手順 4 と 5）を満たした主張だけ。題名は主張の文 |

- `kind: "experience-pattern"` のページは `/wiki:learn` だけが作る。取り込みからは作らない。
- 新しい `type` は作らない。

### 3. 主張の単位

> 1 つの問いに対し、条件つきの答え、説明、判断を示し、その根拠、適用範囲、反例を同じ場所で更新できる単位。

1 文を単位にしない。「店内での飲食は標準税率、持ち帰りは軽減税率」のように、文が 2 つに分かれても、税率を選ぶ 1 つの判断なら 1 つの主張である。逆に、条件の違う 2 つの記述を 1 つの主張にまとめない。

### 4. 判定の手順

1. **候補を出す。** ソースから知見の候補を出す。候補ごとに、主語、成り立つ条件、述べていること、根拠の位置（原本の行）、事実か提案か仮説か決定かを書く。
2. **除外して送る。** 進捗、1 回の数値、固有の対象の属性、用語の定義は主張にしない。進捗と 1 回の数値は source に、属性は entity に、定義は用語ページに送る。
3. **既存と照合する。** 同じ条件と意味を扱う既存のページや節を探し、本文まで読む。あれば、新しく作るより更新を優先する。照合では、題名の似かたより、**対象、条件、肯定か否定か、断定の強さ**を優先する。条件だけが違う 2 つの記述を、同じものとして統合しない。
4. **再利用できるかを判断する。** 条件を保ったまま、別の資料や将来の問いに再利用できるかを判断する。「いつか役立ちそう」だけでは昇格させない。同じプロジェクトの複数の記録は、独立した裏づけとして数えない。
5. **根拠と適用範囲を書けるかを確かめる。** 根拠と適用範囲を、ソースの範囲内で書けるかを確かめる。書けなければ source に残す。
6. **行き先を決めて記録する。** 行き先（`create`、`update`、`source_only`）と理由を、source の「主張と行き先」に記録する。

手順 4 と 5 の結果で、行き先を次のように決める（補った）。

| 手順 4 | 手順 5 | 行き先 |
| --- | --- | --- |
| 再利用できない（この資料、この時点、この対象だけに当てはまる） | ― | `source_only`（source の要約にだけ書く） |
| 再利用できる | 書けない | `source_only` |
| 再利用でき、ある用語の性質、派生形、使い分けとして読むのが自然 | 書ける | 用語ページの `###` の節。用語ページがなければ、用語ページを作って節を置く |
| 再利用でき、1 つの問いに条件つきで答える判断として単独で引かれる | 書ける | `kind: "claim"` のページに昇格させる。同じ主張のページや節が既にあれば更新する |

### 5. 題名とスラッグ

- 用語、entity、source は名詞の題名のままにする。
- 主張のページだけ、「何が、どんな条件で、どうなる（どう扱う）」の文にする。
- 提案や仮説を、題名で確定した事実に変えない。条件を削って短くしない。60 文字程度を見直しの目安にするが、上限にはしない。
- スラッグは `_rules/page-conventions.md` の命名の規則に従う。
- 題名の例（PoC の資料と関係のない分野から作った。補った）:
  - `飲食料品の税率は店内飲食か持ち帰りかで分ける`
  - `適格請求書がない仕入れは仕入税額控除の対象にしない`
  - `免税事業者からの仕入れは経過措置の期間に限り一部を控除できる`

### 6. frontmatter

- 主張のページは `type: "concept"`、`kind: "claim"` とする。
- frontmatter は平坦なキーだけにする。入れ子は使わない。
- 根拠の照合先はソースの本文（原本）に限る。wiki の言い換えを根拠にしない。


## 出力

最後のメッセージに、次の形の JSON を 1 つだけ、```json のコードブロックで出す。説明の文は JSON の外に書かない。

- `candidates` には、ソースから抜き出した知見を**すべて**並べる。source の要約にだけ書く知見も、`action: "source_only"` として並べる。
- `claim` は日本語で、ソースの範囲を越えずに書く。
- `conditions` には、その知見が成り立つ条件、適用範囲、前提を、ソースが述べているとおりに書く。条件がなければ空の配列にする。
- `evidence` の `quote` は、原本の文を**そのまま**写す（1 文か文の一部）。訳さない。言い換えない。原本が英語なら英語のまま写す。`line_start` と `line_end` は、その引用がある原本の行である。
- `epistemic` は、ソースの中でのその知見の性格である: `fact`（観測・確認した事実）、`decision`（決めたこと）、`proposal`（提案・推奨）、`hypothesis`（仮説・推測・未確認）。
- `action` は `create`、`update`、`source_only` のどれか。`source_only` のときは `page_slug` を `semasynth-mvp設計の敵対的レビュー-2026-11-06`、`page_type` を `"source"` にする。
- `page_type` は `source`、`entity`、`concept` のどれか。`page_kind` は、`kind` を付けるページなら値（例: `"claim"`）、付けないなら `null`。
- `section` は、ページの中の置き場所の見出し（`### …` など）。決めないなら `null`。
- `pages` には、この計画で作る（`create`）か更新する（`update`）ページを、source の要約ページを除いて並べる。
