実際の `extract_pages()` にこの状態を渡すと、描画変更後も本文が `OLD OCR`、`ocr_source` が `adopted` となり、OCR の呼び出しは 0 回でした。一方、旧指紋の候補生成では、モデルだけが異なる設定を拾い、dpi・OCR 方針・分割設定の異なる候補を除外することを確認できました。
## 判定

**条件付きで採用可。確信度：高。** 単一の移行元に対する前回の反例は塞がれたが、旧保存先が複数あると、中断と描画変更の組み合わせで旧 OCR を再利用する経路が残る。

## 致命的・重大な欠陥

### 【重大】未記録の別の移行元から、描画変更後に同じページの旧 OCR が復活する

**再現手順**

1. 同じ PDF の次の両方に、1 ページ目の旧 OCR（本文 `OLD OCR`）を置く。
   - `always-150-e57f7c6bd9cf-extract-v1/page-000001.json`
   - `auto-150-e57f7c6bd9cf-extract-v1/page-000001.json`
2. `adopt_legacy()` を実行する。名前順で先に処理される `always` のコピーと `done` の保存まで完了させる。
3. 次の `auto` の `copying` を印へ保存する直前に停止する。
4. pypdfium2 の版を変え、同じ PDF を再処理する。

`always` は印によって除外される。しかし `auto` は未記録なので、**変更後の描画の識別で移行を開始する**。新しい OCR 保存先へ旧本文がコピーされ、`load()` が受け入れる。

ファイル操作をメモリ上に、PDF の解析をスタブに置き換え、実際の `adopt_legacy()`、`load()`、`extract_pages()` を実行した結果：

```text
停止時の印: always のみ、state=done
描画変更後の本文: OLD OCR
ocr_source: adopted
OCR の呼び出し: 0 回
```

「同じ元から二度は移さない」という元単位の条件は守っている。しかし、**すでに移したページの旧 OCR を、描画変更後も使える結果として再導入できる**。ADR の「描画変更後は移した結果も使わず、OCR をやり直す」という契約は満たさない。

**根拠**

- `info-hive-rag/scripts/rag_pdf.py:118–130`：移行元を順番に処理し、記録のない元には現在の描画の識別を割り当てる。
- 同 `:135–143`：存在確認は現在の OCR 保存先に限られ、移行完了も元ごとに記録する。
- 同 `:89–91`、`:196–204`：付け直された `adopted_render` が一致すると受け入れ、OCR を省略する。
- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:231–235`：描画変更後は旧結果を使わず OCR をやり直す契約。
- `tests/contract/test_rag_contract.py:174–204`：追加された中断試験の移行元は一つだけで、この組み合わせを通さない。

## 崩れる前提

- **移行元ごとの印で、描画変更後の旧 OCR の再導入を防げる。** 同じページを持つ `always` と `auto` の間で停止すると崩れる。一方の印は、もう一方からの再導入を制限しない。
- **中断試験で単一の移行元を使えば、移行全体の再開を検証できる。** 元の内部での中断は検証できるが、元と元の境界での中断は検証できない。
