移行の印を保存する直前に停止させる再現で、描画の識別を変えた後も同じ旧 OCR が再移行され、読み込まれることを確認しました。また、0.4.0 の実際のコードで計算した保存先を後始末の候補が拾えないことと、設定変更後の `retry_job` が旧 OCR 設定を保持することも確認できました。通常の OCR 中断からの再開と、22,000 ページ相当の一覧のページングは、メモリ上の検証では崩れませんでした。
## 判定

**条件付きで採用可。確信度：高。** 移行中断後に描画の識別が変わると、同じ旧 OCR を再移行して使う経路がある。また、OCR 設定が原因の失敗について、wiki の手順どおりに再試行しても復旧できない。

## 致命的・重大な欠陥

### 1. 【重大】移行の印の保存前に停止すると、描画変更後も旧 OCR を再移行する

**再現手順**

1. `auto-150-e57f7c6bd9cf-extract-v1/page-000002.json` に旧 OCR を置く。
2. `OcrStore.adopt_legacy()` が新しい OCR 保存先へページを書いた後、`adopted.json` を書く直前に停止する。
3. pypdfium2 の版、すなわち描画の識別を変えて再開する。

移行先のページは残るが、その元を移行済みとする印はない。描画変更で新しい `ocr_key` の保存先になるため、同じ元から再びコピーされる。その際、`adopted_render` が**変更後の描画の識別**になるので、`OcrStore.load()` は旧 OCR を受け入れる。

対象関数を実行し、次の結果を確認した。ファイル操作はメモリ上に置き換えた。

```text
停止直後: saved=True, marker=False
描画変更後: copied_again=1
load(2): 旧本文を返し、adopted_render は変更後の識別
```

「同じ元からもう一度は移さない」「移した後に描画が変われば使わない」の両方に反する。

**根拠**

- `info-hive-rag/scripts/rag_pdf.py:117`：印にある元だけを除外する。
- 同 `:125–135`：ページを書いた後、元全体の処理が終わってから印を書く。
- 同 `:89–91`：再移行で付け直された `adopted_render` が一致すれば受け入れる。
- `tests/contract/test_rag_contract.py:157–172`：検証するのは移行が完了した場合であり、この停止位置を通さない。

### 2. 【重大】wiki の再試行手順が、OCR 設定による失敗から復旧できない

**再現手順**

1. `ocr_mode="off"` で、OCR が必要なページを含む PDF を登録する。
2. ジョブが失敗した後、設定を `auto` に変える。
3. `ingest-workflow.md:28` の案内に従って `retry_job` を呼ぶ。

再試行するジョブの設定は `off` のままで、同じページで再び失敗する。メモリ上の SQLite と実際の `Jobs.retry()` で、現在の設定が `auto` でも、再試行後の保存設定が `off` のままであることを確認した。

これは `retry_job` 自体の不具合ではなく、**登録時の設定を保持する仕様と、wiki の復旧手順との食い違い**である。ADR は設定変更後の新規登録を明記しているが、今回の手順には反映されていない。

**根拠**

- `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:28`：失敗理由を直した後は `retry_job` と案内する。
- `info-hive-rag/scripts/rag_jobs.py:210–215`：再試行は状態を戻すだけで、`config` を更新しない。
- `info-hive-rag/scripts/rag_worker.py` の `get_engine()`：ジョブに保存された設定で実行する。
- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:141–142`：再試行も旧設定のまま、新設定では新規登録すると明記している。

## 崩れる前提

- **旧 OCR のコピーと移行済みの印が一体として残る。** ページ保存後、印の保存前の停止で崩れる。文書のロックは同時実行を防ぐが、この保存順序の穴は塞がない。
- **現在の設定から旧版の `generation` を再現できる。** `extract-v2` を含む現在の指紋では、0.4.0 の実際の指紋を再現できない。
- **設定を直した後の再試行は、新設定で動く。** ジョブの設定が登録時のスナップショットなので成立しない。
- **抽出の識別が同じなら、判定が `text` の最終本文は wiki と一致する。** `ocr_mode="always"` では、そのページも OCR の本文に置き換わる。

## 見落としと軽微な問題

### 【軽微】実際の 0.4.0 の残存キャッシュを後始末できない

`_legacy_generations()` は旧方針と照合する場合も、現在の `Config.fingerprint` を計算する。このため、実際の 0.4.0 の保存先を候補に含められない。

v0.4.0 タグの `rag_config.py` をそのまま実行して照合した結果、旧 `generation` は候補に含まれなかった。置換後の `_remove_legacy_extraction()` でもそのディレクトリは残る。

残存する後始末試験の `legacy_layout()` は、**現在の指紋**で旧配置を作るため、この食い違いを検出しない。

根拠：`info-hive-rag/scripts/rag_index.py:312–333`、`tests/rag/test_extraction.py:254–261`、同 `:389–396`。

### 【軽微】wiki の本文一致の説明が `always` を除外していない

`ingest-workflow.md:246` は、同じ抽出の識別なら、判定が `text` の本文は `wiki_pdf.py` と同じだとしている。しかし `always` では OCR の本文になる。例えば OCR が空文字を返せば、文字の層に本文があっても rag の本文は空になる。

根拠：`info-hive-rag/scripts/rag_pdf.py:176–194`。抽出の識別には、この最終本文の違いを区別する `ocr_mode` は含まれない。

### 【軽微】保存したページ自体には抽出の識別がない

ADR `:210` は、抽出の識別を保存したページにも入れるとしているが、`judge-*.json` と `page-*.json` にその識別はない。読み込み時もページの識別を検査せず、ディレクトリの鍵を信用する。

通常の生成経路ではディレクトリの鍵が分離するため、これ単独による誤再利用は再現していない。確認できたのは契約との食い違いである。

根拠：`info-hive-rag/scripts/rag_pdf.py:158–163`、同 `:177–180`、同 `:198–202`。

## 検証した事実

- **一致**：rag の `rag_pdf_layer.py` と wiki の `wiki_pdf_layer.py` は、実際のバイト列が同一だった。
- **一致**：既定設定の指紋は、試験の固定値 `48605951088f2fc5c45ad3b14dc2a4ebd35142874e58106adfeca22215e48f94` と一致した。
- **一致**：`auto` から `always` への変更で、抽出の鍵と指紋は変わり、OCR の鍵は変わらなかった。
- **一致**：22,000 ページ相当の保存記録を使い、交互に並ぶ `text` の11,000範囲をページングして、全番号を取得できた。この入力の保存レポートは374,712バイト、先頭応答は4,064バイトだった。
- **食い違い**：実際の v0.4.0 の設定コードで計算した `generation` は、現在の後始末候補に入らなかった。
- **一致**：依存の固定は MCP サーバーと CI に記載されている。
- **確かめられず**：依頼元が報告した依存付き試験群の成功。既存の Python 3.12 仮想環境を起動できず、再実行していない。上記の再現は標準ライブラリ、メモリ上のファイル操作・SQLite、および対象関数そのものを使った。リポジトリのファイルは変更していない。

## 崩せなかった点

- 通常の OCR 中断では、判定済み2ページ・本文確定1ページ・`pending=2` が残り、再開後は3ページすべてが確定した。
- **移行の印まで保存済みの場合**は、描画の識別を変えると再移行せず、変更前の OCR を読み込まなかった。
- `Engine.ingest_pdf()` からの抽出、移行、レポート生成は文書の抽出ロック内にある。今回追加された経路に、ロック外で共有キャッシュを書き換える箇所は見つからなかった。
- 失敗したジョブの `result` が `page_report` だけでも、対象の wiki 手順は成功時の `raw` や `extracted_markdown` を読まないため、その形式だけによる破綻は見つからなかった。
