# オントロジー機能の提供方法と利用体験の比較

2026-11-19。主担当による総括。multi-agent-dispatch の analysis モードで 4 モデルを実行した。
相互レビューと追加モデルによる総括は実行していない。以下の採否は主担当が資料を確認して判断したもので、モデル間の合意やレビュー承認ではない。
元の依頼は task.md、各回答は results/A.md〜D.md、モデル・状態・使用量は run.json にある。

## 推奨

wiki プラグイン内に専用の ontology 操作を加える案を維持する。
一方、引数なしの入口は提案の即時開始から「LLM を使わない利用状況の診断と状態の表示」へ変える。
明示した propose は問い・実例・試行・差分をまとめ、確認した案だけを apply する。
自然言語で提案を求められた場合は、同じ流れで診断から提案まで進める。
定義と関係の記録を区別し、初期版は既存の型・IDを変えず、少数の事例を選んで使える状態まで通す。

## 4 回答の比較

| 記号・モデル | 推奨する入口 | 特徴・重視する点 | 主担当の判断 |
| --- | --- | --- | --- |
| A: Opus 5.5 | ontology check / propose / apply | 決定的な診断を先に提供。ID変更の影響を数え、共通の書き手に適用を任せる | 診断と影響検査は採用。共通の書き手が実装済みであるとは扱わない |
| B: Fable 5.2 | 引数なし ontology で診断、propose / apply | stats・lint からの案内。述語を先に増やし、影響を示せれば既存ページの再分類も許す | 入口と案内を採用。再分類は初期版で見送る。種類より述語を必ず優先する方針にはしない |
| C: GPT-6.2 Sol | graph propose / apply | 既存の操作を増やさず、問いと実ページから差分を作る。適用後も同じ問いで確認 | 利用の流れを採用。入口は対案として残す。C は補助エージェントの検討を含む |
| D: GPT-6.2 Astra | graph suggest --user など | 既存語彙の再利用を先に確認。語彙不足と、関係が未記録であることを切り分ける | 提案の判定の中心に採用。graph への統合は対案として残す |

別プラグインを作らず wiki 内に置く点、1 回に 1 wiki を扱う点、目的の問いと実例を示す点は各回答で一致した。
既存の語彙で足りる、根拠不足で保留する、という結果も必要である。

## 最初の提供案から変えること

1. **まず利用状況を見せる。** 現在の種類・述語の使用状況、記録済みの関係、保留中の提案を表示する。数値は判断材料であり、未使用の種類や低い比率だけで不適合と判定しない。
2. **語彙不足と記録不足を分ける。** 問いが既存の語彙で表せるなら、新しい定義を増やさず、根拠付きの関係の記録を提案する。
3. **機能を作る順と、提供完了を分ける。** 診断、提案・試行、適用の順で作る。診断・提案だけを先に公開しても、「提案から適用まで」の機能が完成したとはしない。
4. **適用は共通の書く段と整合させる。** ADR-0023 を利用・拡張する方針を優先し、ontology だけに別の書き手を作らない。必要な書き手と ontology の扱いを設計・実装してから apply を提供する。

専用 ontology を推す理由は、利用者が編集・試行・採用を扱う入口と、既存 graph の検査・生成・照会の入口を分けて案内しやすいためである。
graph に拡張する案も技術的に成立し得る。こちらは操作名を増やさず、既存利用者が発見しやすい利点がある。
どちらが使いやすいかは利用者での比較は未実施で、根拠のある設計上の推奨にとどめる。

## 指摘と主張の検証

| 主張・提案 | 反証の検討と確認 | 判断 |
| --- | --- | --- |
| 別プラグインにしない | ADR-0009 はグラフとオントロジーを wiki 内に残す決定。専用 ontology と graph の拡張のどちらかまでは決めていない | wiki 内への配置は採用。入口名はこの ADR だけから確定しない |
| 共通の wiki_apply.py に乗せれば apply を実現できる | ADR-0023 はページ・索引・ログを共通の書き手に移す承認済み設計。ただし現行の scripts に wiki_apply.py はなく、ontology.yaml も決定の対象に明記されていない | 設計との整合は採用。既存の実装として使えるとの読み方は棄却。ontology の扱いを拡張し、共通の書く段とともに実装することが前提 |
| 型付きエッジが少なく、標準語彙なので内容に合っていない | 記録不足でも同じ集計になり得る。語彙を変えても記事に関係を書かなければエッジは増えない。各回答の集計は作業ツリーと公開コミットで時点も異なる | 数値だけによる不適合判定は棄却。診断の材料として採用し、問い・実例で語彙不足を確認する |
| 新しい種類には maps_from が必要である | derive_node_type は graph.node_type の明示指定を先に返す。新しい種類を新規の対象ページで使う場合、自動対応付けは必須ではない | 一般化を棄却。述語だけを常に先にする理由にはしない |
| 既存ページの再分類を許すべき | 影響検査は有用だが、wiki 外に保存された ID や参照は完全に把握できない。新規の対象ページを作る案なら、既存 source を release と誤分類せずに済む | 影響の表示を採用。初期版の再分類禁止は維持し、明示した移行機能として後続へ送る |
| stats・lint から案内する | 現行の診断は用途に適する語彙を評価する実装ではない。案内を追加するなら新しい動作として実装する必要がある | 将来の案内に採用。低い使用率だけの警告や、記事を取り込むたびの通知は行わない |
| ひな形と同じなので過去に一度も編集されていない | 同一の現在内容から編集履歴までは分からない | 履歴についての推断は採用しない |

確認した箇所は `docs/adr/0009-graph-layer-stays-in-wiki.md`、`docs/adr/0023-wiki-apply-uses-journal-and-per-wiki-lock.md`、`info-hive-wiki/skills/info-hive/scripts/wiki_graph_extract.py` の derive_node_type/page_node_id、wiki_codex.py の workflow、wiki_help.py の PREFERRED_ORDER である。
新しい操作を Codex に届けるには、正本の commands/ontology.md を作るだけでなく、操作の許可一覧と help にも加える必要がある。

## 利用者の流れ

「この wiki のつなぎ方を見て」
→ 対象 wiki と利用状況を確認
→ 「何をたどりたいか」を選ぶ・伝える
→ 既存語彙の再利用か、追加が必要かを見る
→ 出典付きの少数事例と変更範囲を試す
→ 選んだ差分を適用
→ 同じ問いを出典までたどって確認する。

プロジェクトとユーザーは別々に行い、定義・提案・確認済みの対象を混ぜない。
グラフ層の導入を伴う場合は、その後の運用変更も含めて選んでもらう。
適用後の通常の ingest は、採用済み語彙を使う。毎回の自動追加は行わない。

## 比較の条件と限界

- 外側の dispatch は A/B/C/D の 4 実行すべて成功した。各回答は全員終了後に results に保存された。
- A/B は作業ツリーと既存の主担当の提供案を読んだ。C/D はローカルの読み取りプロセスの制約により GitHub の公開資料を読んだと報告しており、全員が同一スナップショットを使った比較ではない。
- C は、自身の制約下で Sol/Astra の補助エージェントにも依頼し、その検討を含めたと報告した。したがって、4 件を厳密に独立した 4 票として多数決に使わない。A/B/D は外側の依頼を担当する一体として検討したと明示した。
- 相互レビューは行っていないので、「他案を読んでモデルが判断を変えた」とは説明しない。本書の変更は主担当の判断である。
- ユーザー wiki の実データを根拠とする評価、利用者による操作比較、実装・本番適用は未実施。
- 内側の補助エージェントの使用量を独立に網羅した会計はない。run.json に外側の CLI が報告した値を残す。

## 次に具体化する事項

診断で出す事実と、その説明を最初に定める。
続けて、提案の固定・少数事例の試行・共通の書く段との接続を、実装前の契約として設計する。
既存の種類・IDを変える移行、適用記録の保持とキャッシュ掃除の関係、途中失敗からの復旧、提案の有用性の評価を詰める。
