# 古い uv の UV_SYSTEM_CERTS の扱いの直し（wiki 0.19.4）の敵対的レビュー

利用者向け文書の計画（[docs/plans/usage-docs-2026-11-15.md](../../plans/usage-docs-2026-11-15.md) の 2-1）で見つけたプラグインの不具合を、作者の決定で直した。古い uv は `UV_SYSTEM_CERTS` を黙って無視するのに、MCP サーバーの入口と中継は、これが設定されているだけで「利用者が決めた」とみなし、OS の証明書ストアを使ったやり直しをしなかった。

レビューは GPT-6.1 Sol（effort high）に 2 回頼んだ。

## 1 回目（プラグインの 2ce076d）

判定は条件付きで採用可で、重大は 1 件だった。`uv sync --help` が失敗すると、uv の版の判定が「`UV_SYSTEM_CERTS` を読む」を返すので、古い uv で `UV_SYSTEM_CERTS=true` を決定と取り違え、直すはずの起動の失敗が残る。

原因は、uv の版の判定が「読む」と「確かめられない」を同じ値で返していたことである。判定を 3 つの状態（読む、読まない、分からない）にし、分からないときは両方の名前を真にしてやり直すようにした（b9d9625）。

| 指摘 | 対応 |
| --- | --- |
| 重大: `uv sync --help` の失敗を、`UV_SYSTEM_CERTS` を読む uv とみなす | 上のとおり。利用者の設定がないときも同じにした |
| 両方の変数があるときの優先順位の前提が、uv と合わない | 両方あれば、どの uv でも決定なので、版を確かめずに止まり、案内に両方を書く |
| 真偽の値の前後の空白を除いていたが、uv は除かない | 除かずに読む |
| 試験に `uv sync --help` の失敗がない | 終了コード、`OSError`、待ちきれないときの試験を足した |

## 2 回目（プラグインの b9d9625）

判定は採用可だった。軽微な指摘 2 件を直した（b4599b1）。

| 指摘 | 対応 |
| --- | --- |
| uv 0.11 と 0.12 は両方の変数を見るので、「新しい uv は `UV_SYSTEM_CERTS` を使う」は一部の版で誤る | 優先する変数を断定せず、版による違いを書く |
| `uv sync --help` がどちらの名前も挙げないときも、「動かなかった」と案内する | 「動かなかったか、どちらの名前も挙げなかった」とした。この場合の試験も足した |

実際の uv での結合試験（自己署名の証明書の索引で、入口が止まること）は、手元で流して通った。古い uv で `UV_SYSTEM_CERTS=true` を設定した結合試験はしていない。
