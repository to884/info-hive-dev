2 回目の指摘への対応:
- 重大（1 行で完結した配列が、後ろのコメントの行を取り込む。`sources: [it's]` のあとに `# don't ]`）: `]` で終わる行は、0.9.5 までと同じに、常に 1 行の配列として読み、後ろの行を見ない（1 回目の重大 2 への対応を取り消した）。行末の `]` が、空白のないコメント（`[a,# メモ ]`）、引用符、入れ子の括弧の中にある複数行の配列は、YAML と違う値になる。これは「YAML の値と違ってよい箇所」として、設計 2.1 の表と CHANGELOG に書いた。0.9.5 が読めていた値を変えないこと（決まりの 3）を、この限られた書き方での YAML との一致（決まりの 1）より優先した。
- 同じ指摘の原因（括弧が閉じているかを、YAML と違う引用符の読み方で見ていた）: `]` で終わらない 1 行目から始まる複数行の `[...]` では、括弧が閉じているかを YAML と同じに見る（`_fm_flow_line()`。引用符は値の先頭でだけ始まり、引用符のない値の途中の `'` と `"` は文字）。要素に分けるのは、今までどおり `_fm_split_items()` である。
- 軽微（試験の `as_parser()` が、同じキーを 2 度書いたときに後の値を上書きする）: 後のノードで見分けるようにし、その試験を足した。
- 軽微（ID をそのまま書く条件）: 「XML に書ける文字だけで、U+FFFD を含まない ID」と、CHANGELOG、設計 2.11、docstring に書いた。

確かめたこと（設計 4）: `k: [` と `]` の間に引用符、`'`、括弧、コメントの形、エスケープなどの断片を並べ、そのあとにコメントの行と字下げした行を続けた入力 300,000 件で、0.9.5 が 1 行の配列として読んだ値が変わったのは 10 件（どれも、二重引用符の要素の中の YAML のエスケープ）で、後ろの行を取り込んだ入力は 0 件だった。
