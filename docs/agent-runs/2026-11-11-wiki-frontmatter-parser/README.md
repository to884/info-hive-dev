# wiki 0.9.6（frontmatter のパーサーが読む YAML の書き方）の敵対的レビュー

2026-11-11、`info-hive-wiki` の frontmatter のパーサー（`wiki_text.parse_frontmatter_text`）が読む YAML の書き方を広げる変更を、設計と実装のそれぞれで GPT-6.1 Sol（effort high、`ask-codex` の `review`）に敵対的レビューしてもらった。設計は `docs/plans/wiki-frontmatter-parser-2026-11-11.md` にある。

## コミットの対応

info-hive-wiki に push したのは、228c3a6（最初の実装）と afc3404（実装のレビューへの対応）の 2 つである。レビューの依頼の文面が指しているコミットは、レビューのたびに作った手元のもので、push した履歴にはない。

| レビューが見たコミット | 中身 | push した履歴 |
| --- | --- | --- |
| 26d8c8e（実装の 1 回目） | 最初の実装。親は 0.9.5 のブランチの 426d6bf | 228c3a6（同じ内容。0.9.5 がマージされた main の a896b6a に載せ替えた） |
| a27d311（2 回目） | 26d8c8e に、1 回目の指摘への対応を足したもの | afc3404 にまとめた |
| 4be1577（3 回目） | 載せ替えたあとの 228c3a6 に、1 回目と 2 回目の指摘への対応を足したもの | afc3404 にまとめた |

3 回目のレビューのあとに afc3404 で変えたのは、`wiki_text.py` のコメント 2 行と CHANGELOG の 1 文だけである（Unicode の空白のあとの `#` の説明）。スクリプトの動きは、3 回目のレビューが見た 4be1577 と同じである。

## 設計

- `design-review-task.md`: 依頼の文面。設計書と、設計を確かめるための試作（`wiki_text.py`）を対象にした。
- `design-review-1.md`: 判定は「却下」（確信度：高）。

| 指摘 | 対応 |
| --- | --- |
| 致命 1: `]` を書き忘れた配列（`tags: [a,` のあとに `type: source`、`title: X]`）が、後ろの欄を取り込み、0.9.5 が読んでいた `type` と `title` を失う | 閉じる前に、字下げのないキーの行が来たら、`]` を書き忘れたものとして、今までどおり読む。「0.9.5 がキーの行として読んでいた行は、今も同じキーの行として読む」を決まりにした（設計 2.1、2.3） |
| 致命 1 の後半: YAML にないエスケープと YAML のエスケープが混ざる値（`"\d+\n"`）で、`\n` だけが改行に変わる | 値の中に戻せないエスケープが 1 つでもあれば、値の全体を 0.9.5 までと同じに読む（設計 2.5） |
| 重大 2: 複数行の `[...]` で、`,` や `[` の直後の空白のないコメント（`[a,# コメント`）が値に混ざる。数が合うので `unread_field` も出ない | YAML と同じく、`,`・`[`・`]`・`{`・`}` と閉じた引用符の直後の `#` もコメントにした（設計 2.3）。`unread_field` が値の中身を比べないことは、設計 2.8 に書き、範囲外に残した |
| 重大 3: エスケープで NUL などの制御文字が値に入り、GraphML が、書き出しは成功するのに読めない XML になる | GraphML に書く文字列で、XML に書けない文字を U+FFFD に置き換える（設計 2.11）。ファイルに直接書いた制御文字でも、0.9.5 から同じことが起きていた |
| 重大 4: 値の前後の Unicode の空白（U+00A0）を除くことと、U+0085 を行の区切りにしないことが、`BaseLoader` と違うのに、設計に書いていない | どちらも 0.9.5 までの読み方で、変えない。「YAML の値と違ってよい箇所」の表に足し、試験で値を固定した（設計 2.1） |
| 軽微: 閉じない `[` を並べると、行の数の 2 乗の時間がかかる | キーの行で止めるので、行の数に比例する。試験を足した |
| 軽微: サロゲートの対の説明より、実装の対象が狭い（`\U0000D83D\U0000DE00` はまとめない） | 設計 2.5 に、まとめるのは `\u` を 2 つ続けた形だけと書いた |
| 軽微: 索引のハッシュが frontmatter の値を含まないという説明が、事実と違う（題名を含む） | 設計 2.9 を書き直した。題名が変われば、その項目だけが入れ替わる |
| 軽微: ブロックのスカラーで書いた `type` は、末尾の改行のために `source` に当たらない | 設計 2.6 に、欄ごとの使われ方を書いた。`type`・`kind` の前後の空白を除いて比べることは、範囲外に残した |
| 軽微: 版の根拠が、別のブランチの予定になっている | 設計 2.10 を、この変更の中身で書き直した |

Sol が確かめられなかった「Tantivy と MCP の索引の更新」は、こちらで確かめた。エスケープの NUL、BEL、タブ、改行を含む題名と、ブロックのスカラーの題名のページを、MCP の索引（`WikiIndex.refresh()`、`search()`、`get_page()`）、CLI の検索、lint、統計、グラフの抽出とグラフの lint に通し、どれも止まらず、GraphML を XML として読めた。

## レビューの前後に測ったこと

- 手元の frontmatter（このリポジトリの `wiki/` 6 件、作者のユーザースコープの wiki 48 件、`info-hive-wiki` の 76 件）で、0.9.5（426d6bf）のパーサーと比べた。差は `skills/info-hive/SKILL.md` の `description: |` の 1 件だけで、wiki のページには差がなかった。

- でたらめな行を並べた入力（30,000 件）で、0.9.5 が読んだキーを失う入力は 0 件だった。

数字は設計 4 にある。
