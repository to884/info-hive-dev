## 判定

**却下。確信度：高。** 正しい複数行配列で、値の途中の Unicode 空白をコメントの区切りと誤認し、値の一部または配列全体を失う。設計2.1の決まり1に反し、明記された例外にも当たらない。

## 致命的・重大な欠陥

### 【重大】U+00A0・全角空白の直後の `#` を、誤ってコメントとして捨てる

再現入力を、空白の種類が分かる Python 表記で示す：

```python
fm = "tags: [a,\n b\u00A0#c\n]"
```

これは正しい YAML である。実行結果：

```python
# BaseLoader
{'tags': ['a', 'b\xa0#c']}

# 4be1577
{'tags': ['a', 'b']}
```

U+00A0 は、この位置では YAML のコメントを開始する区切りではない。`#c` までが値の一部だが、実装は捨ててしまう。

全角空白 U+3000、U+2003 でも再現する。閉じ括弧を同じ行に置くと、配列全体を読めなくなる：

```python
fm = "tags: [a,\n b\u00A0#c]"

# BaseLoader
{'tags': ['a', 'b\xa0#c']}

# 4be1577
{'tags': '[a,'}
```

誤ってコメントにした範囲に `]` が含まれるため、閉じない配列として扱われる。

今回対象の「字下げ4つの配列」でも、同じ原因で値が欠ける：

```python
fm = "tags:\n    - b\u00A0#c"

# BaseLoader
{'tags': ['b\xa0#c']}

# 4be1577
{'tags': ['b']}
```

原因は、コメントの区切りに Python の `.isspace()` を使うこと。複数行配列では `_fm_flow_line()`、ブロック配列では `_fm_strip_comment()` が該当する。

設計2.1の例外は「**値の前後**の Unicode 空白を除く」ことである。この反例の空白は `b` と `#c` の間にあり、値の途中なので、その例外では説明できない。引用符、入れ子、アンカー、継続行などの除外構文も使っていない。

検索への影響も確認した。同じ `tag=['b\u00A0#c']` で `passes_filters()` を呼ぶと、`BaseLoader` の辞書では一致し、実装の辞書では一致しなかった。

根拠：[複数行配列の空白判定](C:/Works/info-hive-dev/.claude/worktrees/frontmatter-parser/info-hive-wiki/skills/info-hive/scripts/wiki_text.py:370)、[既存のコメント判定](C:/Works/info-hive-dev/.claude/worktrees/frontmatter-parser/info-hive-wiki/skills/info-hive/scripts/wiki_text.py:312)、[設計の例外表](C:/Works/info-hive-dev/.claude/worktrees/frontmatter-parser/docs/plans/wiki-frontmatter-parser-2026-11-11.md:43)。

## 崩れる前提

- **Python の `.isspace()` で YAML のコメント区切りを判定できる。** U+00A0、U+3000、U+2003 の直後に `#` があると崩れる。
- **Unicode 空白による食い違いは、前後の空白除去という例外で覆える。** 値の途中の空白がコメント判定へ影響する場合は覆えない。
- **配列として読めたことと要素数の一致で、読み取り失敗を補足できる。** 別行に `]` を置いた反例では要素数が一致し、`sources` に置き換えても `unread_field` は出なかった。値の比較をしないという設計上の限界に当たる。

## 見落としと軽微な問題

独立した軽微な欠陥は見つからなかった。

試験の見落としとして、Unicode 空白の固定ケースは前後の除去を確認しているが、値の途中の空白と `#` の組み合わせを確認していない。無作為試験も、この空白の組み合わせを生成しないため、上記の欠陥を通過する。[該当する固定ケース](C:/Works/info-hive-dev/.claude/worktrees/frontmatter-parser/tests/wiki/test_frontmatter_parser.py:168)。

CHANGELOG の「Unicode の空白も除く」という説明も前後に限定されており、値の途中から `#` 以降を失う挙動の記載はない。

## 検証した事実

Python 3.14.6、PyYAML 6.0.3 を使用した。対象スクリプトに `4be1577` からの作業ツリー差分がないことを確認した。ファイルは変更していない。

| 確認項目 | 結果 |
|---|---|
| `[it's]` が後続コメントを取り込む反例 | 再現しない。旧版・`BaseLoader` と一致 |
| `[a"b]` の同種の反例 | 再現しない |
| 閉じない配列が後続 `type`・`title` を失う反例 | 再現しない |
| `"\d+\n"` の部分デコード | 再現しない |
| コメント中の `]` で終わる一行目 | YAML との差は残るが、今回の設計に明記された |
| `source-url:` を挟む配列の終了 | 挙動は設計3と CHANGELOG に記載された |
| 重複キーを含む `as_parser()` | 前回の反例では実装と一致 |

GraphML は `io.BytesIO` で実際の書き出し関数を実行した。ファイル書込を伴う試験群全体は実行していない。
