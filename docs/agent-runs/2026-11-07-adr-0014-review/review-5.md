埋め込まれた差分・ADR・試験だけを使い、移行と後始末の境界条件を確認します。シェルでのファイル読み取りや書き換えは行いません。
抽出版と generation の連動は、提示された差分では整合しています。一方、取り込み待ちの一覧について、再度の設定変更で未処理の場所が隠れる経路と、一時的に読めないパスを一覧から永続的に落とす経路が見えます。後始末と要再確認の情報への影響を確認しています。
## 判定

**却下。確信度：中。** 抽出版と generation に関する既指摘は、提示された差分では崩せませんでした。ただし、一時的に利用できない PDF の再取り込み情報を永続的に削除する経路が残っています。

## 致命的・重大な欠陥

### 重大：一時的なパスの不通で、再取り込み待ちの情報を失う

`os.path.exists(place) == False` を「その場所はもうない」と扱い、その結果を `_prune_previous()` が保存します。一時的な不通と恒久的な削除を区別していません。

反例：

1. ネットワークドライブ上の PDF A と、ローカルの PDF B を登録する。
2. モデルを変更して B を取り込み直す。索引が空になり、A の場所と `source_pages` が `previous-index.json` に残る。
3. ネットワークドライブが一時的に切断され、A に対する `os.path.exists()` が `False` になる。
4. 別のローカル PDF C を取り込む。
5. `_reingest()` が A を除外し、`_prune_previous()` が A の再取り込み情報を削除する。ほかに利用者がなければ、抽出結果も削除対象になる。
6. 接続が戻っても、A は再取り込み待ち一覧に復帰しない。空にする前の `source_pages` も失われている。

少なくとも、再取り込み一覧と出典の復元情報の喪失は提示コードから確認できます。要再確認の印が最終的にどう欠落するかは、印を更新する処理の本文がないため未検証です。

根拠：`scripts/rag_index.py` の `_reingest()` に追加された `os.path.exists(place)`、および `_prune_previous()` の一覧の書き直しと抽出結果の削除。ADR-0014 の「もうない場所」という判定には、存在確認の失敗が一時的ではないという前提が必要です。

## 崩れる前提

- **存在確認が失敗した場所は、今後も不要である。** ネットワーク切断やアクセス権の一時的な問題で崩れます。確認時点の状態が、復元情報の恒久的な削除に直結します。
- **前の一覧と現在の台帳に、同じ `doc_id` が同時に現れない。** 同じ内容を複数の場所に登録し、一部だけ取り込み直すと崩れます。下記の一覧欠落が発生します。
- **0.4.0 の結果を削除できる範囲が、抽出版の変更後も同じである。** ADR は指紋を再現できる方針だけを対象にする制約を明記しています。「旧結果を常にすべて消す」という保証にはなっていません。

## 見落としと軽微な問題

### 軽微：再度の設定変更で、未処理の場所が `status` から隠れる

反例：

1. 同じ内容 D を場所 A・B で登録する。
2. モデルを変更し、A だけ取り込み直す。
3. 前の一覧には `D: paths=[B]`、現在の台帳には `D: paths=[A]` がある。
4. さらにモデルを変更し、取り込む前に `status` を呼ぶ。

方針が古い場合の `_reingest()` は `pending.update(current)` を実行するため、D の項目全体が現在の台帳で上書きされ、返される場所は A だけになります。B が一覧から隠れます。

根拠：`scripts/rag_index.py`、`_reingest()` の `if self._stale_policy(folder)` 分岐。ADR-0014 の「方針が変わった索引では台帳の文書と一覧の文書」を返す記述と食い違います。永続的に B が失われるかは、未提示の索引初期化処理に依存するため断定しません。

埋め込まれた `test_two_changes_in_a_row_keep_every_source_page` は `source_pages` を確認していますが、この段階の `paths` の和は確認していません。

## 検証した事実

すべて提示本文の静的確認です。ファイルの読み取り、書き換え、試験の実行は行っていません。

- **0.4.0 との指紋互換：一致。** `extract-v1` では追加処理が実行されず、提示された旧 policy 配列と同じになります。試験に書かれたハッシュ値そのものは未計算です。
- **抽出版変更と generation：一致。** 抽出版変更が指紋に入り、`generation()` に伝わります。
- **0.4.0 の抽出結果の誤採用防止：一致。** 抽出版変更後は、移動処理に入る前に戻ります。
- **同じ内容の複数場所：通常の取り込み直しでは一致。** 方針が現在と一致する分岐は、未登録の場所を残します。再度の設定変更時には上記の食い違いがあります。
- **`configure(ocr_dpi=0)`：握り潰しは解消。** `0` が `Config(values)` に渡ります。`Config` の検証処理は未提示なので、拒否する実装自体は確認できません。
- **旧 generation の後始末：提示範囲では一致。** 現在の式の値と、台帳に記録された値の両方を jobs の削除対象にしています。
- **`_extraction_in_use()` と要再確認の印：全体は確認できず。** 本文がなく、依存先の変更から分かる影響までの判断です。

## 崩せなかった点

- 抽出版を上げたときに、0.4.0 の抽出結果を新しい版として移す経路。
- 抽出版を上げたときに、前の版と同じ generation で埋め込みの途中経過を使う経路。
- `extract-v1` のままで、今回の追加処理が既存の指紋を変える経路。
- 既存文書の処理で、台帳に記録された generation を無視する経路。
- モデルだけを変更した反例で、空にしたあとに置き換えた文書の legacy 結果が、今回追加された削除処理から漏れる経路。
