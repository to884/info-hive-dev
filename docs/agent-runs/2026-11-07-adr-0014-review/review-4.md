埋め込まれた差分と試験本文だけで、強制終了時の状態遷移、共有キャッシュの削除条件、既存索引との整合性を確認します。シェルでの読み取りやファイルの変更は行いません。
抽出の版を上げた場合の索引更新と、索引を空にした後の複数パスの復元に、整合性が崩れる反例があります。試験は前者を `unchanged` として受け入れており、後者は複数の場所に登録した同一 PDF を対象にしていません。
## 判定

**却下。確信度：高。** 抽出の版を上げても検索索引が更新されず、古い抽出結果を新版のキャッシュへ移す経路もあります。また、索引の再構築で同じ PDF の登録済みパスが失われます。判断は提示された差分と試験本文の静的確認に基づき、試験は実行していません。

## 致命的・重大な欠陥

### 1. 【重大】抽出版の更新が索引に反映されず、旧版の結果を新版として再利用する

**反例 A：0.5.0 の索引が既にある場合**

1. `extract-v1` で、文字化けした本文を抽出・索引化する。
2. ページ判定や文字の取り出し方を修正し、`EXTRACT_REVISION` を `extract-v2` に上げる。
3. 同じ PDF を再投入する。

`extraction_key` は変わりますが、`fingerprint` は変わりません。`ingest_pdf()` は `existing` 分岐に入り、新しい本文の Markdown だけを作り、埋め込みと索引を更新せず `unchanged` を返します。したがって、返された Markdown は修正後、検索対象は修正前の本文になります。再投入しても修正後の語句を検索できません。

**反例 B：0.4.0 の抽出結果が残っている場合**

同じ版更新を行ってから取り込むと、`_legacy_generations()` は抽出版を含まない指紋から旧 generation を選びます。`_adopt_legacy_extraction()` が旧ページ JSON を `extract-v2` のディレクトリへ移すため、`extract_pages()` は旧結果を読み、修正後の抽出そのものが行われません。

**根拠：**

- `scripts/rag_config.py`：`Config.fingerprint`、`Config.extraction_key`
- `scripts/rag_index.py`：`_legacy_generations()`、`_adopt_legacy_extraction()`、`ingest_pdf()` の `existing` 分岐
- `tests/rag/test_extraction.py`：`test_raising_the_extraction_revision_returns_an_existing_markdown()` は `unchanged` を期待し、Markdown の存在と抽出回数だけを確認しています。検索本文の更新は確認していません。

### 2. 【重大】再構築すると、同一 PDF に登録した複数のパスが失われる

**再現手順：**

1. 同じ内容の PDF を、独立したファイル `A.pdf` と `B.pdf` に置く。
2. 両方を同じ wiki に登録する。旧台帳の同一 `doc_id` に、場所 A・B が記録される。
3. 埋め込みモデルを変更する。
4. A だけを取り込み直す。

`_reset_index()` は A・B を `previous-index.json` に保存してから、`locations` を全削除します。その後、保存一覧から復元されるのは `source_pages` であり、登録済みパスではありません。

さらに `_reingest()` は、その `doc_id` が現在の索引にあるだけで旧項目を対象外にします。`_prune_previous()` によって A・B を保持していた項目が消え、B は台帳にも取り込み直し一覧にも残りません。

この後 A を削除しても、存在する B を登録済みの代替場所として扱えません。**同じ内容を一度取り込み直しただけで、以前の場所の情報が失われます。**

**根拠：**

- `scripts/rag_index.py`：`_reset_index()` の `DELETE FROM locations`
- 同：`ingest_pdf()` の `restored["source_pages"]` 復元処理。旧 `paths` の復元処理は追加されていません。
- 同：`_reingest()` の `doc_id not in current` 条件、`_prune_previous()`
- 提示試験には、同一 wiki・同一 SHA-256・複数パスを登録してから再構築する試験がありません。

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
|---|---|
| 指紋が同じなら、既存の索引本文を使い続けてよい | `EXTRACT_REVISION` の更新で抽出本文が変わる。 |
| 旧 generation の指紋から、現在と抽出方法が同じだと証明できる | 指紋に抽出版が含まれていない。 |
| 同じ SHA-256 を一度取り込み直せば、旧登録情報を捨ててよい | 同じ内容が複数のパスで登録されている。 |
| 旧モデルと revision を再現すれば、再利用できる旧 generation を列挙できる | 旧索引と現在の分割設定が異なる。 |

## 見落としと軽微な問題

- **【軽微】分割設定変更時に、0.4.0 の抽出結果を再利用できません。**  
  `_legacy_generations()` は現在の設定に旧モデルと旧 revision だけを上書きして指紋を再計算します。例えば旧 `chunk_chars=500`、現在 `chunk_chars=1000` では旧指紋を再現できず、OCR 設定が同じでも旧キャッシュを見つけられません。根拠は `scripts/rag_index.py::_legacy_generations()` です。

- **【軽微】削除ロックの競合を後で回収する経路がありません。**  
  `_remove_extraction()` は `Timeout` なら処理を終了します。別 wiki の取り込みが抽出ロックを保持中に旧版を置換し、その別取り込みも公開前に失敗すると、どの wiki も使わないキャッシュが残り得ます。提示差分には削除の再試行を記録する処理がありません。

- **強制終了・キャンセル・Windows の削除挙動は、提示試験では検証されていません。**  
  移動中断試験は、1 ページだけ移した状態を手動で作っています。`_reset_index()` の各永続化境界での強制終了、実際のキャンセル要求、Windows で開いているファイルの削除失敗は扱っていません。これらを通過したという根拠にはなりません。

## 検証した事実

- **一致：** 抽出キーは埋め込みモデル・分割設定を含まず、同じ `data_dir` の wiki 間で共有されます。
- **一致：** 最初の埋め込み呼び出しが例外を出す場合、`_reset_index()` には到達せず、旧索引の削除は始まりません。
- **一致：** リセット前に旧文書一覧を書き、その後に SQLite の削除をコミットしています。
- **一致：** `_extraction_in_use()` 自身が開く SQLite 接続は、`closing()` で閉じられます。
- **食い違い：** 抽出版の更新は抽出キーには反映されますが、索引更新と旧結果の移行判定には反映されません。
- **確かめられず：** `_catalog()` 全体の接続寿命、キャンセルの受理境界、ワーカー再開との整合性。該当する既存実装本文は提示されていません。

## 崩せなかった点

- 抽出設定を変えず、モデルだけを変更する通常経路では、共有キャッシュを再利用する条件は成立しています。
- 移行元と移行先が同じ抽出方法の結果である限り、ページ単位の移動途中で停止しても、次回は未移動ファイルを移す構造です。
- `_remove_extraction()` は、対象の抽出ロックを取得できない場合には削除しません。
