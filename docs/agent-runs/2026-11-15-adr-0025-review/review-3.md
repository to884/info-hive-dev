もう一つ、版がずれた組み合わせに問題が残っています。新しい wiki の手順は `page_report` を必須にしますが、併用を許している旧 rag にはその返却値がありません。OCR 移行の一度限りの例外については、描画版が不明な結果を使うこと自体は明示された割り切りなので、欠陥と混同せず、試験で例外の寿命を確認できるかを整理しています。
## 判定

**条件付きで採用可。確信度：高。** 前回の指摘への対応は、仕様の追加として書かれている。ただし、200 件を超えるページ情報の欠落と、新しい wiki・旧 rag の組み合わせで通知経路が成立しない問題が残る。

## 致命的・重大な欠陥

### 1. 【重大】`page_report` の打ち切りで、確認すべきページを特定できなくなる

**主張：** 省略の印は情報の欠落を知らせるだけで、残りのページ番号を取得する手段にはならない。

**反例：**

1. 1,000 ページの PDF を取り込む。全ページの判定は `text`。
2. 1〜200 ページと 901 ページが、画像面積によって確認対象になる。
3. `page_report` は「201 ページ、番号は 1〜200、省略あり」を返す。
4. 最後の確認対象が 901 ページでも 902 ページでも、この報告は同じになる。本文だけから画像面積の違いは分からない。
5. エージェントは、残りのページ番号を通知できず、指定された画像確認も実行できない。

印の割合は 20.1% なので、3 割以下という基準でも防げない。これはレビュー 2 の指摘 1 が、件数の多い場合に残ったものになる。

また、OCR 済み・OCR 結果が空の一覧には、正確な件数を返す指定もない。これらが 200 件を超える場合は、「番号と数を伝える」という要求を満たせない。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:103`：番号と数を通知する要求。
- 同 `:108`、`:131`：rag の情報源と、各一覧の 200 件制限。
- 同 `:95`：wiki には詳細範囲を指定する `--pages` があるが、rag 側には対応する取得契約がない。
- `info-hive-rag/scripts/rag_server.py:138`：現行 `job_status` の引数にも範囲指定はない。

### 2. 【重大】許容する版の組み合わせで、新しい通知契約を実行できない

**主張：** 本文一致の保証を同じ抽出識別に限定するだけでは、新しい手順が要求する API の欠落を解消できない。

**反例・再現手順：**

1. wiki だけを ADR の仕様に更新し、rag は現行の 0.5.3 のまま使う。
2. `synth-scan-header.pdf` を取り込む。
3. rag は利用可能なので rag 経路を選ぶ。判定は `text`、`auto` では OCR されず、本文はヘッダーだけになる。
4. 旧 rag の `job_status` には `page_report` がなく、`status` にも OCR 設定がない。
5. 新しい手順が必須とする確認情報を取得できず、画像確認の対象を知れない。

ADR は版を合わせることを強制せず、古い版との併用を明示的に想定している。しかし、必要な返却値がない場合の扱いは定義していない。レビュー 1 の指摘 5 は、本文一致の説明については訂正されたが、今回追加した API 契約について再び成立していない。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:108`、`:114`、`:157`、`:203`。
- `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:15`：rag ツールが使える場合に選ぶ経路。
- `info-hive-rag/scripts/rag_jobs.py:82`：保存した結果を返す処理。
- `info-hive-rag/scripts/rag_index.py:660`：現行の完了結果には `page_report` がない。
- `info-hive-rag/scripts/rag_server.py:181`：現行 `status` に OCR 設定はない。

現行 `Jobs.status()` を SQLite のメモリ上の台帳で実行し、保存済み結果にない `page_report` が補われないことも確認した。

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
| --- | --- |
| 件数と先頭 200 件、省略の印があれば、対象ページを確認できる | 201 件目以降の番号が必要になる |
| 本文一致の保証範囲を限定すれば、版のずれを許容できる | 新しい手順が、旧 rag にない返却値を必須とする |
| wiki の JSON とページ番号を比較すれば、`page_report` 全体を検証できる | wiki に存在しない OCR 済み・OCR 空結果の情報が誤っている |
| 描画変更と旧形式移行を別々に試せば、一度限りの例外を確認できる | 旧形式から移した結果を、再取り込みや描画変更後にも使う |

## 見落としと軽微な問題

- **【軽微】移行例外の寿命を契約試験で確かめられない。** ADR `:130` は「移す 1 回だけ」とする。一方、`:149`〜`:151` の試験には、旧形式を移した後の再取り込み、さらに描画版を変更した場合の期待動作が明記されていない。通常の新形式キャッシュの描画変更試験と、旧形式の初回移行試験だけを通しても、この例外が繰り返し適用される実装を排除できない。

- **【軽微】OCR が全ページで空になった失敗ジョブの報告契約がない。** 現行コードでは、全ページの OCR 結果が空ならチャンクが作られず、`rag_index.py:528` で失敗する。`rag_worker.py:162` は例外文字列だけを保存する。ADR `:131` は `page_report` を返すとするが、失敗時にも保存・返却する範囲を定めていない。`:152` の wiki との比較でも、OCR 空結果の一覧は検証できない。

- **【軽微】30〜70 分という見込みは、決めた呼び出し方の実測ではない。** ADR `:65` はページごとの `extract_text` 呼び出しを決めるが、根拠の `scripts/try_pdfminer_vertical.py:23` は文書全体を一度に抽出する。承認条件 `:170` はこの差を測る内容になっているものの、影響欄 `:217` の見込みはまだ裏付けられていない。

## 検証した事実

- **一致：** 保存済み出力と `pages.json` から新条件を再計算すると、確認対象は **33 ページ中 8 ページ**。BERT は 4・6 ページ、白書概要は 1・9 ページ、官報は 4 試料だった。
- **一致：** 3 組すべての `aggregate.check()` を書き込みなしで実行し、判定ダイジェスト、対応表、判定用の写し、抽出出力の整合性を確認した。
- **一致：** 保存された pdfminer 縦書き検出ありの 7 出力に U+FFFE はなかった。任意の PDF で出ないという一般保証までは確認していない。
- **一致：** 本文一致と最終本文の区別、誤判定の影響、`off`、登録時設定による再試行は、初回レビュー後の説明で訂正されている。
- **一致：** `page_report` と `status` の設定追加は、今回は新しく実装する変更として明記されている。現行 API に存在しないこと自体を、新版同士の設計欠陥とは扱っていない。
- **一致：** OCR 設定変更による索引指紋の変化と、取り込み時の索引初期化は、現行コードおよび ADR-0014 と整合する。
- **確かめられず：** 新しい抽出処理、OCR 保存・移行、`page_report`、長い PDF の性能は未実装・未実測。実際の OCR は今回実行していない。
- リポジトリのファイルは変更していない。

## 崩せなかった点

- OCR 保存を文字層抽出から分離する方針は、初回レビューの保存構造との矛盾に対応している。
- 通常の OCR キャッシュ鍵に描画版と dpi を含める仕様は、レビュー 2 の指摘 3 に対応している。
- 旧 OCR の描画版が不明であることは隠されておらず、初回再利用は明示された割り切りである。その割り切り自体を未認識の欠陥とは判定しない。
- BERT の既知の `(cid:80)` を新しい確認条件が拾う点は崩せなかった。
