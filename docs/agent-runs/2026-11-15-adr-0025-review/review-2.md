## 判定

**条件付きで採用可。確信度：高。** 初回の本文一致・誤判定・再試行についての説明は訂正されている。ただし、確認対象ページを利用者へ届ける経路と、OCR キャッシュの互換性に欠落があり、現在の承認条件を満たしても残る。

## 致命的・重大な欠陥

### 1. 【重大】rag 経由では「確かめるべきページ」と `ocr_empty` を知る経路が定義されていない

**主張：** 印を計算することと、取り込みを担当するエージェントに通知することがつながっていない。初回指摘2・4は、この経路について未解決である。

**反例・再現手順：**

1. rag が有効な状態で `synth-scan-header.pdf` を取り込む。
2. 判定は `text`、`image_coverage=1.0` なので、確認対象になる。
3. `auto` では OCR されず、本文はヘッダーだけになる。
4. 現行手順が読むのは `result.extracted_markdown`。ここには確認対象の印も画像面積もない。

改訂 ADR が明示する rag の返却値追加は「抽出の識別」だけである。wiki 用の `wiki_pdf.py --json` を rag 経路でも呼ぶ指定もない。したがって、ADR の「ページの番号と数をユーザーに伝える」「Read で見る」を実行するための情報がない。

同じ問題は `ocr_empty` にもある。本文のあるページと OCR 結果が空のページを混在させると、後者は `document.md` で見出しだけになる。ジョブ全体は完了しうるが、エージェントには空になった理由が渡らない。なお、既存の `result.review_pages` は旧版の資料を参照する**wiki 記事**の一覧であり、この PDF ページの確認対象一覧ではない。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:95`、`:103`〜`:108`、`:124`
- `info-hive-rag/scripts/rag_pdf.py:104`〜`:110`
- `info-hive-rag/scripts/rag_index.py:299`〜`:303`、`:660`〜`:664`
- `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:15`〜`:30`
- `info-hive-wiki/commands/ingest.md:48`〜`:51`

現行 `_write_markdown()` をメモリ上で実行し、確認対象のヘッダーページと `ocr_empty` ページから、本文と見出しだけが出ることを確認した。

### 2. 【重大】`status` で現在の `ocr_mode` を確認する手順は実行できない

**主張：** ADR が既存機能として頼っている返却項目が存在しない。

**反例・再現手順：**

1. 利用者の設定が `ocr_mode=off` である。
2. `scan` ページを見つけ、ADR の指示どおり `status(wiki_root)` を呼ぶ。
3. 応答に `ocr_mode` がないため、指定された方法では `off` を確認できない。
4. 登録すれば、OCR が必要なページでジョブが失敗する。

`status` は索引の状態とジョブ一覧を返す。ジョブ一覧でも `Jobs.status()` が保存済み `config` を取り除くため、そこから設定を取得できない。ADR の変更対象にも、`status` へ設定を追加する指定はない。

これは、訂正済みの「設定変更後は新規登録する」という説明とは独立した欠落である。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:107`、`:191`〜`:196`
- `info-hive-rag/scripts/rag_server.py:180`〜`:190`
- `info-hive-rag/scripts/rag_jobs.py:82`〜`:96`
- `info-hive-rag/scripts/rag_pdf.py:104`〜`:107`

現行 `rag_server.status()` を、索引とジョブを模したメモリ上の依存先で実行し、`ocr_mode` が返らないことを確認した。

### 3. 【重大】独立した OCR キャッシュの鍵が、描画元の版を区別しない

**主張：** 新しい鍵は PDF・ページ・dpi・NDLOCR-Lite・モデルの版を区別するが、OCR の入力画像を生成する pypdfium2／PDFium の版を区別しない。文字層抽出だけの変更と、描画の変更が同じ再利用条件になっている。

**崩れる条件・手順：**

1. 旧 pypdfium2 で OCR したページを保存している。
2. 新版で pypdfium2 の固定値を変更する。NDLOCR-Lite、モデル、dpi は変えない。
3. 同じ PDF を取り込み直す。
4. 文字層の抽出識別は変わるが、OCR の鍵と旧結果の移行条件は一致するため、旧 OCR 本文を再利用できる。

旧新版で描画が異なるページでは、新しく描画した画像を OCR した本文と、再利用する本文が異なりうる。現行の旧保存形式には描画元の版がなく、ディレクトリ名にも含まれないため、移行時にその同等性を確認できない。

**確認できたのは鍵の衝突と記録の欠落である。具体的な PDF と旧新版の組で OCR 本文が変わることは未検証であり、その発生は推測。** ただし、ADR の再利用条件が描画変更を区別できないこと自体は確定している。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:120`〜`:123`
- `info-hive-rag/scripts/rag_pdf.py:65`〜`:67`：画像は `page.render()` から生成
- `info-hive-rag/scripts/rag_pdf.py:109`〜`:111`：保存ページに描画元の版がない
- `info-hive-rag/scripts/rag_config.py:147`〜`:157`：旧保存先にも描画元の版がない
- `info-hive-rag/scripts/rag_server.py:4`：現行依存は `pypdfium2>=5,<6`

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
| --- | --- |
| 確認対象の印を計算すれば、取り込み担当にも分かる | rag 経路では本文だけを読み、印・判定・`ocr_empty` が返却されない |
| `status` から OCR 設定を確認できる | 現行応答には設定がなく、ジョブの設定も除去される |
| 同じ PDF・dpi・OCR 版なら、同じ画像を認識した結果として扱える | 描画エンジンの版によって画像が変わる |
| `always` に変更して対象 PDF を新規登録すれば、影響はその取り込みで説明できる | OCR 設定は索引指紋にも入り、既存の別 PDF の検索にも影響する |
| 承認条件3つと契約試験で、新しく決めた動作を確かめられる | OCR 保存・旧結果移行・通知経路が試験対象に含まれていない |

## 見落としと軽微な問題

- **【軽微】`always` の説明に、既存索引への影響がない。**  
  PDF A・B を同じ wiki に取り込み済みの状態で `always` に変更すると、検索は方針不一致で停止する。A を取り込み直すと、その wiki の索引全体が作り直され、B は再登録するまで検索対象から外れる。ADR の説明は PC 設定・所要時間・ジョブの設定保持までで、この影響を含まない。根拠：ADR `:110`〜`:114`、`rag_config.py:137`〜`:144`、`rag_index.py:199`〜`:203`、`:225`〜`:242`。ADR-0014 の方針変更規則とも一致する。

- **【軽微】新しい印の負担は、既存資料だけでもかなり増える。**  
  保存済み pdfminer 出力に新条件を適用すると、公開33ページ中 **16ページ**が確認対象になる。白書の概要は12ページ中10ページで、そのうち8ページは画像面積が0.5未満でも私用領域の文字によって追加される。例として概要2ページ目の5文字は、文頭の U+F06C である。承認条件の「多すぎない」には合否の境界がなく、この結果を採用・不採用のどちらとも判断できる。根拠：ADR `:73`〜`:78`、`:157`、検証ディレクトリの `pages.json` と `outputs/*__pdfminer-vertical.txt`。

- **【軽微】承認条件と契約試験に、OCR 分離・移行の検証がない。**  
  OCR を毎回実行してしまう実装でも、記載された文字層比較・wiki 出力・性能・ページ対応・印の検出は合格できる。今回新しく決めた「旧 OCR を条件付きで移す」「抽出方式だけ変えても OCR を再利用する」は、その試験では確かめられない。根拠：ADR `:121`〜`:122`、`:130`〜`:138`、`:153`〜`:157`。

- **【軽微】検証報告の状態説明が一部古い。**  
  冒頭は ADR-0024 を「提案」と記載している。また制約には「Sol の判定は10ページ、1回だけで、点のぶれは測っていない」とあるが、同じ文書の後半では3組の結果と判定間の変動を扱っている。根拠：`docs/research/adr-0024-verification-2026-11-15.md:3`、`:122`、`:154`、`:175`。

## 検証した事実

- **一致：** 初回指摘1の「最終本文の一致」と「誤判定は本文に影響しない」という混同は、改訂 ADR の表と反例で訂正されている。
- **一致：** 初回指摘2の BERT 6ページ目は、新しい印の条件で拾える。保存済み出力には `(cid:80)` が1個ある。ただし、rag から通知する経路は欠陥1のとおり未定義。
- **一致：** 初回指摘3の「抽出版を変えても現行保存形式のまま OCR を再利用できる」という説明は撤回され、保存を分ける変更として書かれた。
- **一致：** 旧保存先から PDF の SHA-256、dpi、`OCR_REVISION` の接頭辞は取得できる。旧ページ JSON 自体にそれらがないことだけを理由に、移行不可能とは判断できない。
- **一致：** `retry_job` は登録時の設定を書き換えない。設定変更後の新規登録は、新しい指紋で受け付けられる。
- **一致：** 初回指摘5に対し、一致の保証範囲は試験した版に限定され、配布後の版ずれを許容すると明記された。
- **一致：** 3組すべての `aggregate.check()` を書き込みなしで実行し、判定ダイジェスト・対応表・判定用の写し・元出力の整合を確認した。主要な平均値も ADR と一致した。
- **確かめられず：** 新しい OCR 保存・移行、製品版の `wiki_pdf.py`、500ページ以上での性能、特殊なページ構造での対応は、今回実動作を確認していない。実際の OCR も実行していない。
- リポジトリのファイルは変更していない。

## 崩せなかった点

- 文字層の一致と最終本文の不一致を区別する、改訂後の説明。
- `auto`・`always`・`off` の基本的な OCR 分岐。
- `EXTRACT_REVISION` を索引指紋へ反映し、旧本文と新索引の混在を防ぐ方針。
- OCR 結果を文字層抽出から独立させること自体。ADR-0014 の保存方式を変更する設計としては成立する。
- メモリの合否基準、Poppler の除外理由、比較表の試作の意味は、初回指摘に対応している。
