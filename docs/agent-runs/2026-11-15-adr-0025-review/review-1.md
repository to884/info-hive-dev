## 判定

**条件付きで採用可。確信度：高。** 本文の一致、誤判定への耐性、OCR 結果の再利用に、仕様内の矛盾と現行コードとの食い違いがある。現在の承認条件 2 つを満たしても、以下の欠陥は残る。

## 致命的・重大な欠陥

### 1. 【重大】「同じ本文になる」「判定を誤っても本文の質は下がらない」は、決定した出力と両立しない

**主張：** ADR の理由は最終本文の一致を述べているが、一致する可能性があるのは、同じ版・設定で取り出した文字層の中間結果に限られる。

**反例・再現手順：**

- 官報の 2 ページ目は `vertical`。wiki は pdfminer の本文に警告を付け、rag の `auto` は OCR 本文を採用する。
- 通常の `text` ページでも、rag の設定が `always` なら OCR 本文になる。
- `garbled`・`scan` では、wiki の警告文と rag の OCR 本文が異なる。
- 回転した横書き表を `vertical` と誤判定した場合、rag は pdfminer 本文を採用せず OCR に置き換える。ADR の例示と逆である。
- `garbled` と誤判定した場合、wiki は pdfminer の本文を捨てる。本文と判定を分離したことでは、この影響を避けられない。

現行の `extract_pages()` を、PDF と OCR と保存先を模したメモリ上のスタブで実行した。`text + always` と `vertical + auto` の双方で、本文が OCR の戻り値に置き換わった。

契約試験で共通の抽出関数だけを比較すれば、この食い違いを残したまま合格できる。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:60`、`:74`〜`:78`、`:91`、`:102`、`:125`〜`:126`
- `info-hive-rag/scripts/rag_pdf.py:104`〜`:110`
- `info-hive-rag/scripts/rag_index.py:299`〜`:302`
- `docs/research/adr-0024-verification-2026-11-15/pages.json` の官報各ページ

旧レビュー `review-1.md` の指摘1で扱われた、文字層と最終本文の混同が再発している。

### 2. 【重大】PDFium の判定は、新しく採用する pdfminer 本文の破損を検査していない

**主張：** 本文の生成元を変える一方、確認対象を決める数値は別エンジンの出力から計算する。既存の検証結果にも、この組み合わせでは通知されない破損がある。

**具体例：** BERT の 6 ページ目。

1. PDFium の判定は `text`、`bad_ratio=0`、`image_coverage=0`、`review=false`。
2. 採用候補の pdfminer 本文には、総和記号が `(cid:80)` として式から離れて出ている。
3. Sol の 3 回目の判定も、確率式の分数構造と総和記号の分離を致命的な誤りとして記録している。
4. 新 ADR の wiki は本文をそのまま出し、rag の `auto` も OCR しない。確認対象の通知にも入らない。

数式を含むページ全体が読めない、と主張しているのではない。**本文の意味に関わる既知の破損が、採用する判定経路では無通知になる**という反例である。

ところが承認条件は、速度とページ対応だけである。この出力のままでも両条件を満たせる。`garbled` の説明にある「同じ文字の対応表を使うので pdfminer でも化ける」という断定についても、エンジン間の復号結果の一致を検証した資料は示されていない。逆方向まで含む正常性の対応関係は確かめられない。

**根拠：**

- `docs/research/adr-0024-verification-2026-11-15/pages.json:84`〜`:91`
- `docs/research/adr-0024-verification-2026-11-15/judge3/bert-p6/D.txt:155`
- 同 `judge3/mapping.json` の `bert-p6`：`D=pdfminer-vertical`
- 同 `judge3/sol-result.md:52`
- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:56`、`:76`、`:82`、`:118`〜`:119`
- `info-hive-rag/scripts/rag_pdf.py:18`〜`:54`

### 3. 【重大】抽出識別の更新と「OCR 結果は使い回す」が矛盾している

**主張：** ADR-0014 は、今回の変更で OCR を再利用できる根拠になっていない。

**再現手順：**

1. `extract-v1` で OCR 済みの PDF を持つ。
2. ADR に従って `extract-v2` に上げる。
3. 同じ PDF を取り込み直す。

現行コードでは `extraction_key` が変わり、別の抽出ディレクトリを使う。旧 `page-*.json` は参照されず、OCR 対象ページでは OCR が再実行される。ADR 自身も、識別の異なる結果と識別のない旧結果を使い回さない、と決めている。

OCR 結果は本文と同じ `page-*.json` に入り、OCR 専用の独立した保存・移行経路はない。したがって、影響欄の「OCR の結果は、ADR-0014 のとおり使い回す」は成立しない。記載の 30〜70 分も pdfminer だけの時間であり、移行時にはそこへ OCR 再実行が加わる。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:92`〜`:93`、`:158`
- `docs/adr/0014-rag-keeps-extraction-independent-of-embedding.md:29`：抽出版変更で抽出と埋め込みをやり直す
- 同 `:46`：再利用できるのは抽出設定が同じ場合
- `info-hive-rag/scripts/rag_config.py:147`〜`:162`
- `info-hive-rag/scripts/rag_pdf.py:96`〜`:110`

### 4. 【重大】確認対象を rag に渡す経路に、欠落を解消しない状態と、旧設定で再試行する状態が残る

**具体例：** 既存試料の `synth-scan-header.pdf` は、全面のスキャン画像と33文字のヘッダーを持ち、判定は `text`、確認対象は真である。

ADR の選択肢から rag を選び、既定の `auto` で登録しても OCR は実行されず、ヘッダーだけが本文になる。アウトライン文字の `blank` ページも、`auto` では OCR されない。

さらに OCR を強制しようとすると、現行 API と既存手順には次の状態がある。

- `register_pdf` にページ指定・OCR 強制の引数はない。
- `always` への変更は PC 設定の変更であり、未完了ジョブがあれば拒否される。
- `auto` で登録して失敗したジョブを、設定変更後に `retry_job` しても、登録時に保存した `auto` で再実行される。
- 利用者の既存設定が `off` なら、`garbled`・`scan`・`vertical` は OCR されずエラーになる。

新 ADR は「既定の設定で OCR される」とは書いているが、実際の設定・保存済みジョブ・再試行を扱う手順を定めていない。通常の取り込み手順に従うだけでは、確認対象の欠落が解消されない。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:83`
- `info-hive-rag/scripts/rag_pdf.py:104`〜`:108`
- `info-hive-rag/scripts/rag_server.py:81`〜`:89`、`:125`
- `info-hive-rag/scripts/rag_jobs.py:79`、`:206`〜`:211`
- `info-hive-rag/scripts/rag_worker.py:129`〜`:135`、`:155`
- `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:28`
- `info-hive-wiki/commands/ingest.md:52`

旧レビュー `review-2.md` の指摘1と `review-3.md` の指摘1に対する扱いが引き継がれていない。

### 5. 【重大】開発時の契約試験では、独立して導入・更新されるプラグインの一致を保証できない

**崩れる手順：**

1. 開発側で新 wiki と新 rag を組み合わせ、契約試験を通す。
2. 利用者は片方だけを更新する。
3. 旧 wiki と新 rag、または新 wiki と旧 rag を併用する。

旧 wiki の通常手順は `pdf-reading`・pdftotext・pdfminer の任意選択であり、新 rag の固定した抽出と一致する保証がない。rag の依存宣言は `wiki@info-hive` だけで、対応する wiki の版や抽出識別を照合する仕様は ADR にない。

また、両方の `EXTRACT_REVISION` を同じ値に上げる運用規則は、利用者環境で両方が更新されたことを保証しない。契約試験が確かめられるのは、試験した組み合わせと試料についての一致である。

**根拠：**

- `docs/adr/0025-pdf-text-layer-with-pdfminer-vertical.md:96`〜`:106`、`:126`
- `info-hive-rag/.claude-plugin/plugin.json:5`〜`:6`
- `info-hive-wiki/skills/info-hive/references/ingest-workflow.md:200`
- `docs/agent-runs/2026-11-15-adr-0024-review/review-1.md:72`

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
| --- | --- |
| 抽出関数が一致すれば最終本文も一致する | rag が OCR する、wiki が警告を付ける・本文を抑止する |
| 判定と本文を分離すれば、誤判定は本文に影響しない | 判定によって OCR への置換や本文の抑止が起きる |
| PDFium の数値で pdfminer 本文の正常性を判断できる | pdfminer 側で `(cid:…)` や配置の破損が生じる |
| 抽出版を変えても既存 OCR を再利用できる | OCR 本文を含む保存ページ全体が、異なる抽出識別として拒否される |
| 現在の OCR 設定で再試行される | ジョブが登録時の設定を保持している |
| 同時変更と契約試験で、配布後も一致する | 利用者が異なる世代のプラグインを組み合わせる |
| 速度とページ対応の合格で採用する動作を確かめられる | 本文破損・抑止・OCR 分岐が合否の対象外になる |

## 見落としと軽微な問題

- **【軽微】比較表の「PDFium の文字の層」は、生の文字層を評価した結果ではない。** 実際は `vertical` などの本文を捨てる ADR-0024 の試作である。官報2ページ目の網羅1・総合1には、この抑止が含まれる。この平均を、生の PDFium 文字層や OCR を含む rag の現行品質と同一視できない。根拠：検証報告 `:39`、`scripts/extract.py:56`〜`:64`、`summary2.md:14`。

- **【軽微】Poppler を比較から外した理由が数値と食い違う。** 検証報告 `:103` は「1回目で Xpdf を上回る点がなかった」とする。しかし `summary.md:6` の BERT 6ページ目では読み順4対3・表4対3、`:14` の官報2ページ目では読み順2対1で上回っている。依存導入の負担とは別に、この除外理由は誤りである。

- **【軽微】調査報告の状態が後続の実測と同期していない。** `pdf-extraction-tools-survey-2026-11-15.md:21`〜`:22`、`:69` は pdf_oxide・pdfplumber を未計測としているが、検証報告には3回目の実測がある。また `:72` の「pdfminer の読み順を保ったまま」は、今回の左右段混在という実測と両立しない。pdfplumber は文字の位置などから独自に語・行を組み立てる。[公式の抽出仕様](https://github.com/jsvine/pdfplumber#extracting-text)

- **【軽微】メモリの承認基準がない。** ADR `:118` はメモリを測るとするが、合否は時間だけである。メモリ不足を起こす測定結果でも、時間条件だけなら判断が定まらない。`extract_text` を文書全体に一度呼ぶ測定と、製品のページ単位・再開処理を含む測定の区別もない。

- **【軽微】分割出力の同一性には未定義の境界がある。** ADR `:84` はページ内位置を指定できるが、`vertical` の警告とページ見出しを継続出力時にどう扱うか、`--json` の詳細範囲の既定値、再実行間に原本が変わった場合の扱いは定まっていない。現在は実装がなく、欠落や重複が起きるかは確かめられない。

## 検証した事実

- **一致：** 3組すべてで既存の `aggregate.check()` を書き込みなしで実行し、判定ダイジェスト、対応表、判定用の写し、元の抽出出力の一致を確認した。
- **一致：** ADR に掲載された方式別平均は `summary*.md` と一致する。pdfminer の縦書き検出ありは2回目と3回目だけに含まれる。
- **一致：** 保存された pdfminer 縦書き検出ありの7試料には U+FFFE がなかった。一方、BERT に3個、官報各試料にも `(cid:…)` が残っている。
- **一致：** `auto`・`always`・`off` の分岐を現行 `extract_pages()` とメモリ上のスタブで確認した。実際の OCR は実行していない。
- **食い違い：** OCR 再利用の説明は ADR-0014 と現行の保存構造に反する。
- **確かめられず：** `wiki_pdf.py`、新しい抽出識別の保存・移行、分割 CLI、500ページ以上での性能、特殊なページ構造での対応は未実装・未検証である。
- リポジトリのファイルは変更していない。

## 崩せなかった点

- 抽出識別をキャッシュキー・保存ページ・索引指紋に入れ、識別不明の旧結果も拒否する仕様は、旧レビューの「新本文と旧索引の混在」に対応している。
- `EXTRACT_REVISION` の変更で索引が取り込み直し対象になる説明は、現行コードと一致する。
- LF に正規化した文字列を比較し、ファイルのバイト一致とは区別する仕様は `_write_markdown()` と矛盾しない。
- 本文の写しを作らないことと、通常取り込みで PDF 原本を raw に置くことは矛盾しない。
- 依存方向を保って wiki に独立した抽出処理を置くこと自体は、現行の取り込み規則に反しない。
