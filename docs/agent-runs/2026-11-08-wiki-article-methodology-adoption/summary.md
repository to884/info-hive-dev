# wiki の記事作成の方法論の提案を info-hive に導入すべきかの総括

## 推奨
提案は一括では導入せず、まず lint に索引の分類検査、出典参照の検査、正式タグの検査を足し（マイナー 0.7.0）、次に source ページの「主張と行き先」の記録を取り込みの規約に足す。`kind: "claim"` と `claim` 限定の 3 値 `status` は、直前の検討の PoC に合格したときだけ入れる。`id`、`scope`、入れ子の `relations`、`type: journal`・`graph`、全ページの `status`、出典なしの `draft`、`/wiki:decide`、status を上げる意味の `/wiki:promote` は導入しない。承認済みの ADR は変えない。

## 批評で動いたこと
- エージェント A は、自分の実測の誤りを認めた。正式タグ以外のタグは 0 件ではなく、`Windows`、`Claude Code`、`MCP` が実在する（エージェント D も独立に確認）。また「行き先どおりに更新する」規定を段階 2 に組み込んでいた点を、エージェント C の立場に寄せて「記録は段階 2、行き先に従う規定は PoC のあと」に改めた。`kind: "claim"` と `maps_from` を同時に入れる計画も、別々に進める形に改めた。
- エージェント B は、`status` の 4 値を 3 値（`hypothesis`・`supported`・`superseded`）にそろえる案に改め、「`supported` なら `sources` 2 本以上」の検査の価値を下げ、`questions.md` の軽さの点数を下げ、「手順と概念を混ぜない」を絶対規則ではなく長い手順に限る文言に改めた。
- エージェント C は、PoC の件数が片側 18 件で、現行との対照を含めると 36 件になることを認めた。段階 A と B の SemVer の境目があいまいだったことも認めた。
- エージェント D は、レビューの入力に自分の初回成果が含まれていなかったため、自分を他案より上位とは判定しなかった。D の自己評価は総括では使っていない。
- 最も鋭く決定的だった反論は、B の段階 2 の合図「PoC が合格したら、または `source_only` 以外の行き先が 10 件以上たまったら」に対する C と D の致命判定である。件数は LLM 自身の未検証の判定を数えているだけで、PoC を迂回できる。B はこれに反論しておらず、総括では件数を合図に入れない。
- 決定的ではなかった反論は、推測と明記されたものである。A が挙げた「主張の表で source が 4,000 文字の上限を超える見込み」、B が挙げた「`--fix` の採点が契約変更を反映していない」は、未確定事項に回した。

## 推奨案が残る理由
- **索引の分類誤り 16 件は 4 体が独立に実測した。** A は別名表との照合で 16 件、B と C は `index.md` の 74〜104 行の偶数行で、D は「シンセシス」欄 18 項目中 16 本で、それぞれ確かめた。現行の `wiki_lint.py` が `index.md` を走査から外すことも 4 体が確認した。この検査を最初に入れる根拠がもっとも固い。
- **出典参照の検査は、規約と実装の差として 4 体が確認した。** 既定の必須キーに `sources` がなく、`sources:` と `raw:` の解決を lint が見ていない。作者の wiki では現在 0 件であり、価値は予防にとどまる。B の指摘どおり、0 件の検査を 2 位に置く根拠は点数にはない。総括では、実装が軽く同じリリースに入るので同時に入れる、という扱いにする。
- **正式タグの検査は、A の訂正と D の実測で 2 ページ以上に当たることが確かめられた。** 実装はタグの一覧を `--allowed-tags` で渡す形で済む。
- **「主張と行き先」の記録は 4 体が独立に到達した唯一の改善策だが、効果は未測定である。** C と D が自己申告し、A も見直しで認めたとおり、「source の偏りを解く」という価値の点数は実測ではない。そのため、記録としては入れるが、記録に従って更新を強制する規定は PoC のあとにする。
- **不採用の群は、どの攻撃も崩せなかった。** `id` はスラッグと常に同値、`scope` は ADR-0008 の保存先の境界を満たさない（D が B の「タグで見分ける」代案を反証）、入れ子の `relations` は `wiki_text.py` のパーサーが読まない、`journal` は ADR-0006 に反する、`graph` は層でありページ型ではない。4 体が独立にコードと ADR を引いて同じ結論に至り、相互レビューでも 4 体とも「崩せなかった点」に挙げた。
- **ADR を変えないという結論も 4 体が一致し、崩れなかった。** 唯一の例外候補は ADR-0008 と作者の wiki の実態の食い違いだが、これは提案との衝突ではなく作者の 2 つの決定の間の問題である（後述）。

### 割れた論点の決着
- **`kind: "claim"` のページに `status` を持たせるか。** C と D は「編集状態、確からしさ、失効を一列に混ぜない」として持たせない。A と B は `experience-pattern` の 3 値を流用する。B の攻撃「持たせないと古い主張を機械的に見つける手段がない」は、直前の検討の総括にも残っていた論点であり、C も D も反論を示していない。根拠が決める向きは「持たせる」である。ただし 3 値で、`claim` 限定、オプトイン、PoC 合格後とする。B が 4 値目としていた `disputed` は B 自身が 3 値への縮小を提案しており、矛盾は本文の `## 矛盾` の見出しで表す。
- **「主張と行き先」をいつ手順に組み込むか。** A・B・D は段階 2 で入れ、C は PoC 後とした。A が見直しで「記録と規定を分ける」形に寄せたので、記録は段階 2、更新の強制は PoC 後で決着する。
- **グラフの移行。** `kind` の付与と `claim` の `maps_from` 追加は別段階にする（C・D）。C が実関数で再現した反例を完了条件に足す。`maps_from` を足すと `concept:a --depends_on--> concept:b` の主語が `claim:a` になり、`depends_on.subject_types` に `claim` がないため型不一致になる。ID の参照切れだけを見ても移行は完了しない。A と B にはこの条件が欠けていた。
- **A のログ書式の検査は採らない。** C は `wiki_evolve_loop.py` の正規出力 `- YYYY-MM-DD: ...` が反例になることを、D は `log.md` の前文 9 行が引っかかることを示した。
- **`## 主な主張` のない 32 本を「主張が欠けた 32 本」とは数えない。** D の指摘どおり、`page-conventions.md` は固定テンプレートを求めていない。必須の節の検査は SCHEMA で選んだときだけ有効にする。
- **`broader` を証拠なしの型付きエッジにする A の案は保留のまま費用を見直す。** `requires_evidence: false` をコードが受け入れることは B・C・D が確認したが、C と D は実関数で、`source`・`evidence`・`confidence`・`status` をすべて省いた循環エッジが検出 0 件で通ることを再現した。`graph-workflow.md` の全フィールド必須の契約との食い違いと、循環検査の不在を、導入前に解く必要がある。
- **`questions.md` の置き場所は 3 案とも欠陥があった。** A の `log.md` に `gap` の行を残す案は、追記専用のため回答済みの状態を表せない（B）。D の `indexes/questions.md` は、`wiki_stats.py` が `indexes/` の存在で分割済みと判定するため分割の助言が消え、MCP の `list_index` が台帳を索引として返す（A・B・C が独立に再現）。B のルート直下は `wiki_lint.py`、`wiki_graph_extract.py`、`wiki_search.py`、MCP サーバーの skip 一覧を直す必要がある。副作用が最も小さいのはルート直下だが、導入は「答えられなかった問いが実際に繰り返されたら」まで保留する。

### 導入の順序
| 段階 | 入れるもの | 合図 | SemVer |
| --- | --- | --- | --- |
| 0 | 作者の wiki の手直し。index の 16 本を「ソース」へ移す。log 140 行目を直す | 今 | なし |
| 1 | lint に `index_type_mismatch`（見出し直下の wikilink だけを読み、冒頭の `[[消費税]]` の例示を除外）、`unresolved_sources`、`missing_raw`、`unknown_tags`。方法論の整理と「問題が起きたら入れる」原則を、新しい ADR（記事の作成と保守の方法論）に書く。既存の ADR は改訂しない | 今 | マイナー 0.7.0 |

メジャーが要る要素はない。

## エージェントごとの要約
**エージェント A** は、提案の骨格は現行に既にあると見て、lint の 7〜9 項目と source の「主な主張」と行き先を中心に採り、frontmatter の拡張と新コマンドを退けた。実測が最も多く、index・`sources`・`raw`・節・タグ・log の件数を数えた。当たっていた指摘は、タグ 0 件が source だけの集計だったこと（C・D）、ログ書式検査が評価ループの正規出力と前文を誤検出すること（C・D）、`broader` の「1 項目足すだけ」が契約と循環検査を落としていること（C・D）、`gap` 行が回答済みの状態を持てないこと（B）、空白を含むファイル名が 3 本ではなく 4 本であること（B）である。見直しで自分の誤りを明示し、結論を C に寄せた。

**エージェント B** は、`/wiki:promote` を source から `claim` への昇格に読み替え、`status` を `claim` 限定にし、`questions.md` を自動追記の台帳に変える案を出した。索引検査と主張の一覧を最初に置く結論は 4 体と一致する。当たっていた指摘は、段階 2 の合図が件数で PoC を迂回できること（C・D が致命と判定）、`experience-pattern` に新しい検査をかけて既存契約を変えていること（A・D）、作例で raw 5 行目の Git 情報の規則を 7 行目の再現性判定の条件に誤結合したこと（C・D）、「暗黙エッジは `sources:` と `raw:` だけ」が `mentions` を落としていること（D）、「手順主体のページはない」に `オントロジー抽出パイプライン` の反例があること（D）、名詞句の題名のページを主張形としたこと（A・C）である。段階 1 は残り、段階 2 の計画はそのままでは残らない。

**エージェント C** は、提案を置き換え設計ではなく手法の選択として扱い、索引検査、出典検査、配置の小規模 PoC を最初に置いた。形式検査と内容レビューの分離、`kind` 付与とグラフ型移行の分離、提案自体の誤りの網羅的な一覧が強みで、A と D の両方が「最も崩れにくかった」と判定した。当たっていた指摘は、`claim` ページの失効を表す手段がないこと（B）、採点表の上位が「維持する既存機能」で埋まり新規投資の順位として読めないこと（B）、0 件の出典検査を 2 位に置く根拠が点数にないこと（B）、段階 A と B の SemVer が揺れること（B・自認）、PoC 件数が片側だけだったこと（D・自認）である。

**エージェント D** は、C とほぼ同じ骨格で、CQ の台帳、レビュー状態の設計条件、PoC の必須条件（捏造・条件の脱落 0 件）を最も具体的に書いた。グラフ移行を分ける判断と、Diátaxis を絶対規則にしない反例（`編集要求の復元世代…` の番号付きの境界は手順ではない）は 3 体が崩せなかった。当たっていた指摘は、`indexes/questions.md` が `wiki_stats.py` の分割判定と MCP の `list_index` を誤動作させること（A・B・C）、`claim` ページの失効手段がないこと（B）、最初の 3 つの 3 番目「型別の出典検査」が採点表に独立の行を持たないこと（A・B）、ADR-0008 と作者の全体指示の食い違いを挙げていないこと（B）である。

4 体とも、採点は採否の決め手になっていない。変えて導入する要素は変更後の案で、導入しない要素は原案で採点しているため、採る側が高く出ることは最初から決まっていた。

## 残るリスクと未確定事項
- **SemaSynth の記録 28 本の置き場所。** ADR-0008 は「ユーザースコープにプロジェクト固有の情報を置かない」と決め、作者の全体指示は「どのプロジェクトの作業でも `~/info-hive/W0_Wiki/` に残す」と求めている。衝突は提案とではなく、作者の 2 つの決定の間にある。選択肢は、(a) プロジェクトの wiki か `50_Notes` に移す（ADR は変えず、ユーザースコープの source は 9 本に減る）、(b) 残して ADR-0008 か全体指示を改める（主張の昇格で再利用できる知見だけを `concept` に出す運用が前提）、(c) タグで区別する（D が ADR-0008 の境界を満たさないと反証したので勧めない）。
- **空白を含むファイル名 4 本の改名。** `concepts/` に 3 本、`synthesis/` に 1 本。改名するなら被リンクの移し替えと同時に行う。
- **必須の節を有効にするか。** 有効にすると `## 主な主張` のない 32 本に LLM が raw から書き足す作業が要る。無効のままでも段階 1 と 2 は動く。
- **PoC の規模と合格値。** 固定 3 資料、2 モデル、3 回、現行と変更案の 2 方式で 36 件を起点にする。一致率 85% などの値は直前の検討の暫定値で、達成の見込みは分からない。捏造と条件の脱落は 0 件を必須条件にする。
- **`--fix` の契約変更。** 現行は「検出するが修正しない」が契約である。限定した機械的修正だけを差分の承認つきで許すかは作者の判断で、1 回の lint で機械的な指摘が 20 件を超えたときに再検討する。
- **確かめられなかったこと。** 主張の表で source が 4,000 文字のソフト上限を超えるか（A の推測）。Foam が日本語ファイル名の `[[slug]]` を解決するか。SKOS・Diátaxis・KCS の外部文書は C と D だけが参照し、A・B は確かめていない。lint を作者の wiki で実行した体はおらず、件数はすべて読み取りと集計による。
