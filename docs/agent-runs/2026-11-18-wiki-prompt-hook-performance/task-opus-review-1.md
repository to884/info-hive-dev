# 性能修正の敵対的レビュー

利用者の依頼は「並列作業中の性能課題を解消して、Opusのレビューまで進めて」。Claudeのworktree `prompt-context-hook` をCodexで引き継いでいる。レビューは読み取り専用で行い、製品や測定結果を書き換えない。日本語で返す。

このworktreeには前の段階の多くの未コミット変更がある。モデル再測定・採点・表の確定は既に別のOpusレビューを完了しており、今回の主対象にはしない。レビュー対象は今回の性能修正である。

## 目的と今回の差分

- UserPromptSubmitのフックは、候補の語彙の選別を期限付きの子で行い、親が候補JSONをflushしてから既出状態を保存する。内部2.5秒・外側timeout 5秒。ゲート、候補の2,000文字上限、状態の保存順、モデル表は今回変えない。
- 旧 `uv run --script` は依存が空でもuvの仮想環境を通っていた。登録行を `uv run --no-project --no-config -qq --offline --no-python-downloads --python ">=3.12,<3.15" python -I -S <hook>; exit 0` に変更した。子もCPythonの `_base_executable` を `-I -S` で使う。
- `wiki_pages` は、ファイルを走査するだけでも同梱Markdownパーサーのハッシュ計算・import・初期化をしていた。パーサーとPARSER_IDを参照時まで遅らせた。共有の初期化をRLockで保護し、公開属性を `__getattr__` で保つ。Markdown設定とハッシュの内容は同じ。閲覧のToken型取得も、同梱版を明示的に参照するよう修正した。
- この2つだけでは、CPU飽和時に候補欠落が残った。Windowsの実行入口だけをAboveNormalにし、解析の子にも明示する。importするホストの優先度や他プロセスは変えず、変更不能なら通常で動かす。High/Realtimeは使わない。特にこの対応の副作用と失敗経路を厳しく見ること。

## 根拠と評価の範囲

`docs/research/wiki-prompt-hook-performance-2026-11-18.md` が今回の記録。150ページの合成wiki、同じ2ページの明示参照、異なるsession_id、フック4本同時、20回。APIを呼ばずPythonの繰り返し起動と全wikiファイルの読み込みで負荷を作る。他の作業を止めていないため、負荷本数が同じでもPCの全負荷を完全には揃えられていない。

- 起動と遅延解析器だけの版・16負荷、実際の入口: p95 4,252.9ms、最大4,601.4ms、候補14/20 (`actual-parallel-16.json`)。
- 最終版8負荷、実際の入口: p95 2,048.0ms、最大2,396.2ms、候補20/20 (`foreground-parallel-8.json`)。
- 最終版16負荷、実際の入口: p95 2,661.0ms、最大2,777.5ms、候補20/20 (`foreground-parallel-16.json`)。
- 追加負荷なし、他作業は継続: 検索p95 1,167.9ms、候補10/10。短文p95 747.2ms (`foreground-serial.json`)。1秒の目安を満たしたとは主張しない。
- 初期の実作業中の5.3秒・3/10には当時の連続資源計測がなく、その全原因や任意の負荷を解決したとは主張しない。途中の候補欠落や計測器の誤りの記録も残し、最終版に混ぜない。詳細は報告書の区別を確認する。

最終版データは登録済みコマンドと実際の入口を使い、計測コードを挿入しない。候補到達はJSONのevent/候補2件のidentity/2,000文字以内/終了コード0/標準エラーなしで数える。各データにコードのhashと負荷の反復数を残している。

これまでの試験: 走査・lint・ページ集合・フック・測定の155件が成功（3 skip）。その後の優先度の実装もフック・実起動・測定の96件が全成功。優先度の試験は、importする側が不変で、実際の入口と子だけがAboveNormalになることを確認する。browseとページ集合をPyYAML付きPython 3.12で追加検証している。

## 特に壊してほしい箇所

- lazy初期化により、検索キャッシュのPARSER_IDやMarkdownの解析規則、同梱版の検証、閲覧の初期化、並列の初回呼び出しが崩れないか。
- `-I -S` と基底Pythonで、3.12〜3.14のCPython/venv/Windows以外でも標準ライブラリと同梱モジュールを読めるか。利用者のプロジェクトやuv設定の同期が戻らないか。
- 優先度変更の適用範囲、ABI、失敗時の動作、他の処理への影響。ハードな期限、失敗時の0、出力前後の状態保存の順序を損なっていないか。
- 性能測定の成功判定が空出力・壊れた出力・実行されない負荷を成功に数えていないか。最終の性能の説明が根拠を超えていないか。

必要なファイルを自分で読む。リポジトリ全体や158回のモデル測定を再実行しない。Claude/CodexのCLIや他の有料モデルを追加で呼ばない。他セッションのプロセスを終了・操作しない。負荷ベンチマークは既に生データがあるので、不足がある場合だけ狭く検証する。

採用可・条件付き・却下を、重大度と具体的なファイル/行/反例で返す。既知の測定範囲の限界と、今回の実装の欠陥を区別する。推測は推測と明記する。
