## 致命的・重大な欠陥

1. **【重大】`Path.resolve()` が実在パスの大文字小文字をそろえるという前提は、Linux では成立しない。項目上限も誤集計を防がない。**

   Linux で、大文字小文字を区別しない VFAT 上に `/mnt/fat/Wiki/` を置き、wiki 引数にはその表記、Raw 引数には `/mnt/fat/wiki/` を渡す反例です。両方が同じディレクトリを指しますが、POSIX の `realpath()` は通常のパス要素の表記を入力のまま残します。文字列比較では一致せず、wiki 自身を Raw として測れます。

   計画85行は、この検査漏れを項目上限で止めるとしています。しかし、中身が上限未満なら走査は完了し、wiki のページや生成物を Raw の容量として報告します。上限はルートの正しさを検証しません。

   根拠：[計画:82](C:/Works/info-hive-dev/docs/plans/wiki-raw-size-in-stats-2026-11-11.md:82)、同84–85行。[CPython 3.10 の POSIX 実装](https://github.com/python/cpython/blob/v3.10.0/Lib/posixpath.py#L355)には通常の要素をディスク上の表記へ置き換える処理がありません。VFAT の大文字小文字を区別しない動作は、[Linux カーネル文書](https://docs.kernel.org/filesystems/vfat.html)でも確認できます。

   今回は実マウントでの再現はしていません。`lstat()` を差し替え、両表記が存在する通常ディレクトリという条件では、POSIX の解決結果に入力の大小文字が残ることを実行確認しました。計画283–284行の試験は「区別する Linux」「区別しない Windows」なので、この組み合わせを検証しません。

2. **【重大】MCP では、自動ルートをリンクとして拒否する前に、そのリンク先を走査できる。**

   Windows・Python 3.10 で、`wiki/raw/` を大きな外部書庫へのジャンクションにし、隣の `raw/` と作業領域設定を置かない反例です。

   計画38・108行は上限なし列挙を残すことを明記していますが、その残存経路が新しい「自動リンクは測らない」という防御を先回りする点までは扱っていません。これは、目的26行の「意図しない場所・リンクの先を読まない」を満たしません。

   根拠：[wiki_mcp_server.py:395](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_mcp_server.py:395)、[wiki_index.py:814](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_index.py:814)、同849行、[計画:78](C:/Works/info-hive-dev/docs/plans/wiki-raw-size-in-stats-2026-11-11.md:78)。Python 側は [3.10 の再帰処理](https://github.com/python/cpython/blob/v3.10.0/Lib/pathlib.py#L435)と、[シンボリックリンク判定](https://github.com/python/cpython/blob/v3.10.0/Modules/posixmodule.c#L12520)を照合しました。実機再現は未実施です。

   計画304行の試験は名前の列挙と `stat()` を許すので、本文を読まなくても起きるこの違反を検出しません。

3. **【重大・決め残し】Raw の探索に使う wiki の表記が CLI と MCP でそろっていない。**

   現在の CLI の wiki 引数の扱いを維持する前提で、次の配置が反例です。

## 崩れる前提

- **「実在するパスなら `resolve()` 後の文字列で同一性を判断できる」**

  `most_linked` の同点処理は列挙順に依存します。集合と件数が同じでも、上位10件の構成が変わります。

前回の「設定と旧 Raw を合算する」「参照先を案内するだけで存在確認する」という前提は、本文では解消しています。別名の内部 Raw がページになる制約は、解消せず対象外と明記されています。
