# Claude Code のセッションを wiki に取り込む機能の再設計 の総括

## 推奨

エージェント A の抽出と返答の宛先の規則（`uuid` のある記録だけを会話のつながりとし、`queued_command` と `isMeta` を境界にし、`parentUuid` で宛先を決める）を土台にし、A の「位置だけを持つ決定から raw を 1 回で生成し、raw 全体のハッシュで書く内容を縛り、排他作成で公開する」構造を採る。これに、C と D が示し A と B も必要と認めた「wiki の変更も人が確認してから書く門」を足す。C と D の「未知の版と種類で入力全体を拒む」規則と「確認待ちの間も wiki を占有する所有権」は、初版では採らない。

## 批評で動いたこと

- **A は自分の結論を改めた。** raw だけを確認の門にしていたため、伏せる前の本文を知るモデルが記事と関連ページに顧客名を書き戻せる経路（C と D が独立に指摘、B も自分の案に当たると認めた）を認め、wiki の変更にも確認の門が要ると結論を変えた。形式の意味だけが変わる場合を「保証しないこと」に足した。
- **B は自分の境界の規則を実測で否定し、採用の条件を A の規則への置き換えにした。** `attachment` と `isMeta` を丸ごと透過にする規則で、アシスタントの本文 3,487 件のうち 980 件（28%）の宛先がずれ、キューに入った人の発言 11 件が黙って消えることを B 自身が集計した。
- **C は自分の案を却下に改めた。** wiki 内のパスが Windows のジャンクション経由で公開済みの raw を指すとき、承認ダイジェスト、変更前ハッシュ、所有権のすべてを通ったまま raw が書き換わることを、実際のファイル操作で再現した。D への攻撃として見つけ、自分の案にも当たると認めた。
- **D は条件付き採用可を維持した**が、承認が人のものである証明、参加しない書き手、意味だけの形式変更を限界として認めた。
- **最も鋭い反論**は、A が出し B が独立に再現した「透過の規則が実物で約 2〜3 割の宛先を誤る」という集計である。A と B の数値はファイルの伸びの分だけ違って一致しており（人の発言 632 対 634、`queued_command` 239、`peer` の `isMeta` 110）、同じ資料を写したのではなく独立に測ったことを示す。この反論は B の判定を数値で変えたので決定的だった。C のジャンクションの反例は 2 番目に強い。C の判定を変えたが、未実装の設計に対する素のファイル操作による再現である。
- **D が C に与えた「条件付き採用可」は、重みを置かない。** D の攻撃は書き込み先の実体の別名を試しておらず、C はその後に自分で反例を見つけて却下に改めた。C の自己却下が D の判定を上書きする。

## 推奨案が残る理由

- **境界の規則は 2 体の独立した集計で裏づけられた。** A の規則で `parentUuid` をたどると解決できない記録は 0 件で、B が同じ規則で再計算した宛先の内訳（人 1,486、通知 673、キュー 545、`isMeta` 334 など）は A の数と一致した。3 版目と B の規則は、この集計で実際に失う側に倒れる。
- **位置だけを持つ決定ファイルは、ディスクに秘密を残さない。** B の指示ファイルは伏せる文字列そのものを含み、一時ディレクトリが Git の作業ツリーの中にある配置で目的に反する（C と D が独立に指摘）。A の決定ファイルは位置だけで、この攻撃を受けない。
- **raw 全体のハッシュで縛る。** B の `render_sha256` は本文だけで、題名とスラッグの差し替え、`sessionId` の差し替え、ゼロ幅の正規表現による書き足しの 3 通りで破られた（A、C、D がそれぞれ示し、D はメモリ上で確認した）。A の `render_sha256` は frontmatter を含む raw 全体で、題名に伏せた文字列が入れば拒む。この点は攻撃に耐えた。
- **排他作成と `--force` なしは 4 体とも崩せなかった。** ただし `os.link` が使えないときに `open(raw, "xb")` で書く B の代替は、C と D の両方が「frontmatter とターン数が一致する不完全な raw を正式名で残し、再開で原本として読まれる」ことを示した。生き残る選択は「`os.link` が使えなければ止める」である。
- **完了を判定しない A の方針は耐え、既存 lint に任せる B の方針は崩れた。** C が指定版の `lint()` を実行し、相互リンク済みで索引項目のない 2 ページに指摘が出ないこと、`log.md` が走査対象外であることを確かめた。A は W2 と同じく人に聞くので、この試験に影響されない。
- **未知の形式を全体で拒む規則は使えない。** A と B が独立に、12 日間で 5 つの版が現れ、最初の版のプロファイルでは 63 ファイル中 57 を拒むことを測った。版をまたぐセッションは全部の版に対応するまで取り込めない。閉じる側には倒れるが、「1 回の依頼で取り込む」目的を日常的に満たせない。

## エージェントごとの要約

**エージェント A** は、3 回の却下の原因を「安全に関わる事実を、書き手の結果として持たず、推して得ていた」と見立て、α 編集の事後判定、β 状態と同一性の間接推定、γ 位置と形からの推測、δ 既定で通す、の 4 類に分けた。実物の集計で、3 版目の規則がキューに入った入力への返答 545 件を前のターンに混ぜることを示した。提案は、位置だけの決定、標準出力だけの確認、raw 全体のハッシュ、排他作成である。当たっていた指摘は、wiki への書き戻しの経路がないこと（A 自身が認めた）、`uuid` のない未知の記録を黙って読み飛ばして境界を失うこと（C と D が合成例で示し、A の対照表の「生じない」と自己攻撃が食い違う）、「T だけを通って親をたどる」規則が親がアシスタントである 2,189 件の通常の連鎖を処理できず、調査用の分類と仕様が一致しないこと（C と D が独立に指摘。考えは正しいが文面のままでは実装できない）、3 版目の本文の形で意味を決める規則を 4 つ引き継いでいること（B）、索引とログの共有による競合を解決していないこと（C と D）である。

**エージェント B** は、原因を「スクリプトが観測できない領域への全称の保証」とし、X 編集の意図、Y 工程の状態、Z 形式の意味、W 同一性の 4 族に分けた。提案は、指示 JSON の適用、ディスクに置かない `preview`、排他作成、`render_sha256` の一致である。純粋な関数 `render()` と「確認した本文と書く本文を一致で結ぶ」考えは耐えた。当たっていた指摘は、透過の規則が実物で 980 件の宛先を誤り 11 件の人の発言を捨てること（A が指摘、B 自身が再現）、指示ファイルが秘密を含み Git 外を保証しないこと（C、D）、ハッシュが本文だけで題名と出所を縛らないこと（A、C、D）、`with` とゼロ幅一致で言い換えと書き足しができること（A、D）、`xb` 代替が不完全な raw を残すこと（C、D）、既存 lint に完了を任せる根拠がないこと（C が実行で確認、D も指摘）である。

**エージェント C** は、原因を「保証したい事実の代わりに、似た観測結果を証拠として使った」とし、意味の推定、表現を戻す設計、同一性の範囲不足、公開プロトコルの不足の 4 つに分けた。提案は、操作から raw を生成し、Git 外の作業領域を `.git` の祖先で検査し、raw と wiki の変更をまとめて承認し、SQLite の台帳と wiki 単位の所有権で公開する構造である。2 段の確認、変更前と変更後のハッシュによる 3 通りの再開、記事の存在で完了を判定しない規則は耐えた。当たっていた指摘は、版と種類のプロファイルで 57/63 を拒むこと（A、B）、確認待ちの間も wiki を占有し、既存手順 6 の `str_replace` を所有権に参加させる手段がないこと（A、B）、`attachment` の 36 種類の下位の扱いが未決なこと（A）、伏せる位置をモデルがコードポイントで指定する変換手段がないこと（B）、既存手順 3〜8 を計画の生成に変える手段を示していないこと（B）、ジャンクション経由で raw が変更されること（C 自身）である。

**エージェント D** は、原因を 5 類（内容と制御構造の混在、意味の推測、出所と成果物の同一視、確認・保存・完了の同一視、局所の検査を全体の保証にする）に分けた。提案は C に近く、メモリだけに候補を置く `serve`、ローカル HTTP の確認画面、2 段の確認、`os.link` の公開、OS ロックである。4 つの識別子を分ける整理と、承認をダイジェストで縛る規則は耐えた。当たっていた指摘は、同じプロファイルの拒否（A、B）、長い確認の間プロセスのメモリに頼ると打ち切りや休止で作業が消えること（A）、既存の lint とグラフをメモリ上の案に向けるアダプターの改修量が見積もりに入っていないこと（A、B）、HTTP の確認画面が人の承認を証明せず仕組みだけ増やすこと（B、D 自身も認めた）、ジャンクション経由の raw 変更（C）、同じ `ingest_id` に複数の確認計画が同居し台帳が巻き戻る規則の決め残し（C）である。

## 残るリスクと未確定事項

- **全案に共通する限界。** (1) いま動いているセッションの記録や、ツールの出力の退避先が Git の作業ツリーの中にある配置では、確認前の本文や `mark --text` の文字列がそこに残る（C の指摘。C 自身の案にも当たる）。(2) wiki 内の書き込み先がリンクやジャンクションで raw に解決する配置。既存の手順 3〜8 を動かすどの案にも当たり、既存のふつうの取り込みにもある穴である。書き込み先の実体が raw と重ならない検査を足す必要がある。(3) スラッグが違っても索引、ログ、関連ページは共有される。A と B は解決せず、C と D の所有権も既存手順 6 のモデルの編集を縛れない。これも既存の取り込みにある穴である。
- **未知の形式の扱い（作者が決める）。** 選択肢は 3 つある。全体を拒む（C、D。漏れないが 57/63 を拒み、日常的に使えない）。`uuid` のある未知は境界にし、`uuid` のない未知は読み飛ばす（A。実物では入力を運ぶ記録はすべて `uuid` を持つが、持たない形で届けば境界と印なしに前のターンへつながる）。`uuid` のない未知の最上位の種類が現れたら警告するか止める（折衷。`custom-title` のようなメタデータは既知として並べる必要がある）。決めるには、入力を運ぶ記録が `uuid` を欠くことが実際にあるかを、版の更新をまたいで観測する必要がある。
- **wiki の変更の確認の門の形（作者が決める）。** C と D の「全変更を計画にして承認後に適用する」形は、B が指定版の `ingest.md` で確かめたとおり、`str_replace` と `wiki_graph_extract.py` が wiki に直接書く既存手順 3〜8 の書き換えを要し、改修量が大きい。軽い形は、要約ページと関連ページの差分をユーザーに示してから書く手順を既存手順 4〜6 に足すことで、人の確認には頼るが既存の道具を変えない。
- **並行実行の範囲（作者が決める）。** raw の排他作成だけ（A、B。索引とログの競合は既存どおり防がない）か、wiki 単位の所有権（C、D。長い確認の間、同じ wiki への Web と PDF の取り込みが止まり、既存の編集は縛れない）か。
- **先頭の `<system-reminder>` の既定（作者が決める）。** A は既定で除いて警告し、B、C、D は除かず人が決める。どちらでも N（人が書いた同じ要素との区別）は限界として残る。既定で除く側は、中身にメールアドレスが入りうる点で漏れにくい。
- **raw に逐語の会話を置くか、記事だけを置くか。** 4 体とも逐語を推奨し、理由は根拠を会話にたどれることである。確認の量は最大例で約 16 万文字、16 区画で、これを受け入れられないなら記事だけの別モードを先に決める必要がある（D）。
- **ツールの要約を残すか。** A と B は既定で残す。C と D は初版では入れない（秘密の経路と確認量を減らす）。
- **実装前に試すこと。** `${CLAUDE_SESSION_ID}` がプラグインのコマンド本文で置き換わるか、取り込みの依頼の記録がコマンドの本文が動く前に書かれているかは、4 体とも確かめていない。D はリリース条件にし、A と B は人が切る位置を決める代替を残す。NTFS での `os.link` の排他、macOS と Linux のファイルシステムも未確認である。
- **A の仕様の直し。** 親をたどる規則に「`assistant` を透過として通る」を明記し、調査用の分類と一致させること。これは採用の条件である。
