# タスク: Claude Code のセッションを wiki に取り込む機能の再設計

## 作者の指示

「再設計する」。進め方は、作者が「4 体に独立に再設計させる」を選んだ。渡すのは、これまでのレビューで崩れた前提と、制約だけである。前の設計者の解決案は渡さない。

## 何を作るか

`info-hive-wiki`（Claude Code プラグイン `wiki`）に、Claude Code のセッションの記録（JSONL）から、会話の内容を wiki に取り込む機能を足したい。利用者は `/wiki:ingest session` のように頼み、セッションの会話が、raw の原本と、記事の形のソースの要約ページ（`wiki/sources/<スラッグ>.md`）として wiki に入る。

これまでの設計（`docs/plans/wiki-session-ingest-2026-11-14.md`、3 版目）は、GPT-6.1 Sol の敵対的レビューで 3 回続けて却下された。指摘は回ごとに、その回に新しく足した仕組みに出た。作者は、指摘を 1 つずつ塞ぐ直し方を禁じている（`AGENTS.md` の「設計と実装のレビューについて」）。

あなたの仕事は、**この機能を設計し直すこと**である。実装はしない。リポジトリのファイルは変えない。3 版目を直すのではなく、3 回の却下に共通する原因を自分で見立て、その原因がそもそも生じない構造を提案してほしい。仕組みを減らしてよい。3 版目の「作者が決めること」の 1〜7（raw に逐語の会話を置くか記事だけを置くか、伏せ字の確認を機械の検査にするか人の確認だけにするか、を含む）も、設計し直してよい。

## 果たすべきこと（変えない目的）

- 1 回の依頼で、セッションの会話を、raw の原本と、記事の形のソースの要約ページとして wiki に入れる。
- モデルの思考（`thinking`）を、raw にも wiki にも入れない。
- 秘密の情報と個人の情報（トークン、メールアドレス、顧客の名前など）が、人の確認を経ずに、Git で管理される場所（raw のルート、wiki）に入らない。
- info-hive はプラグインである。開発用の PC に固有の置き場所や値を仕様にしない。Claude Code の記録の形式は公開された仕様ではない。形式が変わったときに、漏れる側に倒れない。
- 取り込んだあとの raw は変えない（ADR-0004、`SKILL.md`）。
- 既存の取り込み（`commands/ingest.md` の手順 1〜8 と W1〜W9）と、承認済みの ADR に食い違わない。新しいコマンドは「既存のコマンドで表せない手順が出てから足す」（ADR-0015）。
- スクリプトは Python 3.12 以上、標準ライブラリと同梱の markdown-it-py だけで書く（ADR-0018）。Windows、macOS、Linux で動く。
- 人とエージェントが読む文章は日本語、機械が読むキーと識別子は英語にする。

## これまでのレビューで崩せなかった点（使ってよいが、使わなくてもよい）

- `.jsonl` は `inspect` にかけ、セッションの記録と認めなければ止まる（明示の依頼なしに、ふつうの取り込みへ回さない）。
- ターンの本文を、本文の中の最長のバッククォートの並びより長いフェンスで囲む（本文が構造を壊さない）。
- 話者を、記録ごとの属性（`origin.kind` など）だけで決め、本文の形から推さない。
- 取り込む範囲を、記録の `uuid`（`--before <uuid>`）で決める。
- ソースの要約ページの `raw` の値を、`wiki_lint.missing_raw()` が見つける形で計算する。

## 成果に含めるもの

1. **原因の見立て。** 3 回の却下（1 回目の A〜H、2 回目の I〜P、3 回目の重大 5 件と軽微 3 件）に共通する原因は何か。指摘を、原因の構造で分類する。前の設計者は「人が編集した写しを元と照らして検査する構造」と「複数のファイルの有無から状態を推す構造」の 2 つと見立てたが、これは仮説であり、自分で確かめること。
2. **提案する構造。** 次を、実装できる細かさで決める。
   - 入口（引数と、記録の認識）
   - raw に何を、どの形で置くか
   - 秘密の情報と個人の情報を、誰が、いつ、どの手段で除くか。人の確認の前の文を、どこに置くか（または置かないか）
   - 途中で止まったとき、取り込み直すとき、同じ wiki を 2 つのセッションが同時に扱うときの振る舞い
   - 何をもって「同じ取り込み」とするか
   - スクリプトのコマンドと引数、終了コード、出力のキー
   - `commands/ingest.md` に足す手順
3. **指摘との対照。** A〜P と、3 回目の重大 1〜5、軽微 1〜3 のそれぞれが、提案する構造では「生じない」「生じるが、こう扱う」「限界として認める」のどれかを、理由つきで書く。
4. **保証しないこと。** 機械では保証できず、人の確認や運用に頼る点を、隠さずに並べる。
5. **試験の方針。** 構造の全体を確かめる試験（失敗の注入、対照つき）の概要。
6. **作者が決めること。** 推奨と、ほかの選択肢。
7. **自分の案への攻撃。** 自分の提案を崩す、いちばん強い反例を 3 つ以上挙げ、成り立つかどうかを書く。確かめたことと推測を分ける。
