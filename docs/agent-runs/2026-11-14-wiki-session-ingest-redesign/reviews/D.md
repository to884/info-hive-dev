| 所有権・世代検査と実際の書き込みが同じ排他区間にある | 検査後にトランザクションを閉じ、後からファイルやグラフを書く | その実装なら破れる。ただし、Cはそう実装するとは書いていない |
| 完成したrawディレクトリは非空のままである | 外部処理が中身を消して空にする | Cが除外した外部書き手の問題 |
| 承認ダイジェストが人の承認を表す | エージェントが人に見せずに `apply --approved` を呼ぶ | Cも認める限界。ダイジェストは人間本人の認証ではない |
| 対応済みの版・構造なら本文の意味も既知である | 同じ版・同じ `text` の形で、意味だけが変更される | Cも認める限界。機械だけでは識別できない |

所有権の世代を、呼び出し側がどこに保持し、どの値と照合するかは十分具体化されていない。したがって、古い実行主体を実装で排除できることまでは確認できない。ただし、「検査しない実装」を仮定してCを却下することもしない。

### 検証した事実

- **一致：** Unixでは、`os.rename()` の宛先が非空ディレクトリなら失敗する。Windowsでは宛先が存在すれば失敗する。完成した非空ディレクトリを公開するCの説明は、Pythonの仕様と一致する。[Python 3.12 `os.rename`](https://docs.python.org/3.12/library/os.html#os.rename)
- **一致：** `missing_raw()` はファイルだけでなくディレクトリも許し、相対パスを複数の基準で探索する。Cの入れ子のraw配置自体は、この検査と矛盾しない。`wiki_lint.py@7495ca5:213–241`。
- **一致：** 初期化の共通判定は `.gitignore` を検査しない。Cはそれを機密保護の根拠にしていない。`wiki_initialized.py@7495ca5:67–91`。
- **一致：** 取り込みは記事作成だけでは完了しない。Cの `graph_pending` と `complete` の区別は、この既存契約と一致する。
- **字面上の食い違い：** 台帳の初回書き込みは、要点の話し合いより前にある。
- **確かめられず：** SQLiteの所有権検査とファイル変更をまたぐ実装、各OSでの障害回復、グラフ処理を含む世代検査。Cも実機検証済みとは主張していない。

### 崩せなかった点

- 未知形式を部分採用せず、全体停止する入口。
- 記録を応答ターンへ統合せず、本文と入力上の位置の対応を保つ方式。
- raw・題名・ファイル名・wikiへの追加内容をまとめて確認する範囲。
- 承認した計画を永続化してから適用し、変更前・変更後・競合を区別する再開方式。
- 記事やrawの存在だけで完了と判定しない規則。
- 完成したrawディレクトリを新規公開し、その後は上書きしない規則。
