# ADR-0029 段階3の MCP 起動ファイルのレビュー

2026-11-19。GPT-6.2 Astra（medium）で [設計](../../plans/adr-0029-stage3-mcp-startup.md) と実装をレビューした。レビュー先のローカル読み取りが起動しなかったため、設計、ADR の不変条件、関連コードと回帰試験を依頼文に含めて再実行した。実行試験は指定の worktree で行った。

## 指摘と対応

| 指摘 | 確認と対応 |
| --- | --- |
| 旧サーバーの停止に失敗しても記録が消える | アクセス拒否と終了待ちの時間切れで旧記録を残し、後続を起動しない試験を追加した。生存する PID の旧記録で起動時刻を確認できない場合も同じ扱いにした。 |
| 起動が時間切れになった子が後から新しい記録を置き換える | タイムアウト時に起動試行の許可を取り消す。子は記録用のロックの中で許可を照合する。起動を待つ中継も公開された識別子を照合する。 |
| 旧版と新版で同じ起動ロックが働く保証がない | 旧版の filelock 4.2.9 と、新版の先頭 1 バイトのロック（Windows）または `flock`（Linux）を実プロセスで競合させた。Windows では新版がハンドルを開いている間の削除を拒む。 |
| 起動ログの追記がリンク先を変え、診断も失われる | `logs/`、`server.log` と `launch.log` を経路検査に通した。ログの拒否はパスと理由を返し、`launch.log` に書けなければ標準エラーに理由を出す。子の異常終了と時間切れの両方で `server.log` の場所を案内する。 |
| `server.json` の事前検査と、実際に読むファイルの実体が結び付いていない | 末端のリンクを追わずに開き、本文を読む前にハンドルの属性と検査済みの実体を照合する。通常ファイルへの差し替えも回帰試験で拒む。 |
| コピーされた記録を使うと、別のデータの根のサーバーを再利用・停止できる | 実プロセスの環境からデータの根を求め、現在の根と実体を照合する。旧版の既定の根も子の `HOME` または `USERPROFILE` などから復元し、復元できなければ記録を残す。 |
| 時計の逆転を PID の再利用と誤認する | 新版は記録の起動識別子とプロセスの環境を照合する。公開時刻しか持たない旧記録の時刻が逆転している場合は、記録を残して理由を返す。 |
| 旧版の中継が時間切れになったあと、起動待ちだった旧版の子が記録を公開できる | 旧版の子は新しい公開許可を確認しない。同じデータの根で切り替えるときは、旧版の中継と未公開の子が終了していることを設計に明記した。公開済みの旧サーバーは新版が帰属と停止を確認して切り替える。 |
| 起動識別子が食い違うと、稼働中の記録まで消える | プロセスが存在しない場合と、存在して識別子が違う場合を分けた。後者は記録を残して理由を返す。 |
| スクリプト名を引数に取る別のプログラムを停止できる | Python の実行ファイルと、実際に実行対象になるスクリプト引数の位置と配布パスを確認する。エディターを指す記録は保持し、そのプロセスへの停止要求は送らない。 |
| 直接起動で、稼働中の記録を上書きできる | 直接起動は、記録用のロックの下で、予約と記録の両方がない場合にだけ公開する。稼働中の記録に対して拒否する試験を追加した。 |
| 記録から識別子だけが消えると、新版の子を旧版として扱う | 識別子が片側だけにある場合は拒否し、両側にない場合にだけ旧版または直接起動の時刻照合を使う。両方向の欠落を試験した。 |
| 相対名や `-u` 付きで直接起動したサーバーを再利用できない | Python の実行対象を特定して、相対名を子プロセスの作業ディレクトリから解決する。実際に `python -u wiki_mcp_server.py` で直接起動して再利用を確かめた。起動後に作業ディレクトリが変わる仮定については、現行の MCP 起動・索引コードにその変更を行う経路がないことを確認した。 |
| 別の場所にある同名の Python スクリプトを旧版と誤認する | 別のインストール先で起動識別子を持たないプロセスは、記録のループバックアドレスとポートを自分の待ち受けソケットとして所有することも確認する。同じ末尾のスクリプトを引数に持つだけのプロセスを停止しない試験を追加した。 |

最後に異なるインストール先の照合と相対パスの支援範囲を再レビューし、Astra の判定は承認だった。再レビューはコードと試験の記述を照合し、実プロセスの試験は下記のとおり担当側で実行した。

## Claude Opus 5.5 による再レビュー

2026-11-19。Claude Opus 5.5（high）で設計と実装を独立にレビューした。初回判定は差し戻しで、重大1件と軽微2件があった。

| 指摘 | 確認と対応 |
| --- | --- |
| 強制終了後に PID が別プロセスに再利用されると、古い記録が残って次の起動を拒み続ける | 記録の PID が別の実行内容を指し、そのポートが明示的に接続を拒む場合は、通常の起動経路で古い記録だけを片付ける。別プロセスへの停止要求は送らない。タイムアウト、候補の識別子の不一致、実行内容を確認できない権限エラーでは記録を保持する。理由と記録の場所を示し、停止を確認できた場合の退避手順を案内する。 |
| ロックを明示的に解除していない | 取得後の処理が失敗した場合も、明示的に解除してからハンドルを閉じる。Windows のロックはハンドルを閉じた後の解除に時間がかかる場合がある。 [Microsoft Learn の LockFileEx リファレンス](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex#remarks) |
| Windows で旧版によるロック名の削除と新版のオープンが重なった場合の扱いが曖昧 | 旧版の中継が終了しているという切り替え条件を維持した。条件外で共有違反が起きた場合は利用者に知らせることを設計に明記し、ロックのコメントもファイル名を安定させる目的に合わせた。 |

修正確認では軽微2件が解消し、Windows の接続拒否を0.5秒で待ち切れないことが追加で分かった。同じ閉じたループバックのポートを実測すると、0.5秒の制限では `TimeoutError`（0.517秒）、3秒の制限では `ConnectionRefusedError`（2.031秒）だった。古い記録を片付ける判断に使う時間制限を3秒にし、通常の接続確認は0.5秒のままにした。

最終の修正確認は承認だった。Windows で実ソケットを使い、記録に入っていた別プロセスが終了せず、新しいサーバーが起動したことを確認した。WSL でも閉じた実ポートが接続拒否と判定された。環境によって拒否の応答に3秒を超える場合は、記録を保持して案内を返す。

- Windows、Python 3.12 で起動・再利用・終了、リンクによる拒否、所有者の照合を含む45件を実行し、44件成功、POSIX 専用1件をスキップした。共通ロックを使う MCP 索引と raw 保存の追加回帰4件はすべて成功した。
- WSL（Ubuntu 24.04）、Python 3.12 で `umask 000` のまま19件を実行し、16件成功、Windows 専用3件をスキップした。
