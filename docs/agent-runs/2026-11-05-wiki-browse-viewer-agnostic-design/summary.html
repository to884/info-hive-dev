info-hive-wiki · ADR-0010 草案

/wiki:browse は、Wiki を解釈する中核と表示の方式を分ける

状態 提案 決定日 未定 補う ADR 0002 関連 0001・0005・0007・0008・0009

閲覧の手段は、ローカル HTTP サーバー、デスクトップアプリ、静的 HTML のどれかにする。どれを採っても作り直しにならないよう、4 体のエージェントが独立に設計し、互いに敵対的にレビューした。その総括をもとにした案である。

結論

  • Wiki の解釈は Python の 1 か所に置く。走査、frontmatter の正規化、リンクの解決、見出し ID、被リンク、型付きの関係、Markdown の変換、診断を担う。表示の側は Markdown を解釈しない。
  • 3 つの方式は、中核の出力を届けるだけの薄いアダプタにする。どの方式も中核の規則を書き直さない。
  • 契約は、いちばん厳しい file:// に合わせる。file:// で動く HTML なら、サーバーでもアプリでもそのまま動く。

契約

3 つの方式が共通に守る規則である。表を切り替えて読む。

リンクページ間のリンクは相対の href だけで書く。同じ HTML を、file://、http://127.0.0.1:<port>/<token>/…、アプリの独自スキームのどれで開いても動かす。
スクリプトclassic な <script src> だけを使う。ES モジュール、fetch、Web Worker を前提にしない。検索の索引などは data/*.js として書き出す。
ナビゲーション各ページに埋め込まず、共有の nav.js を読み込む。<noscript> で index.html へのリンクを残す。
事前に描く範囲本文、メタ欄、被リンク、ページごとの関係表、未解決リンクは、中核が描いた HTML に含める。JavaScript を切っても読める。
外部への通信しない。CDN を使わず、CSP で外部からの読み込みを禁じる。
トークンサーバーのトークンは URL のパスの先頭に置く。相対リンクが自然に引き継ぐので、HTML を方式ごとに変えずに済む。
複数 WikiWiki の識別子を URL のパス（/w/<wiki-id>/…）に含めて切り替える。ADR-0002 では拡張の方向の 1 つで、決定の行はなかった。
ページの識別子NFC にそろえた POSIX の相対パスから .md を除いたもの。出力のファイル名と URL の名前は export_name() だけで決める。
リンクの状態解決済み、未解決、ambiguous を区別する。重複したスラッグへのパスのないリンクでは、どちらかへ勝手に移動しない。判定は lint の duplicate_slugs と同じ。
見出し見出しの存在の確認を、ページの解決と別の規則にする。ID の生成（NFC、重複時の連番）も中核で決める。
契約の版出力に契約の版（仮称 protocol_version）を持たせる。未対応の版を受け取ったアダプタは表示せずに止まる。
世代世代の識別子と生成日時を持たせ、新しい世代を作り終えてから切り替える。途中の生成物を見せない。
能力の宣言検索（live・embedded・none）、RAG、複数 Wiki、変更の反映を capabilities で宣言する。生成物の情報とホストの能力を分け、持ち運べる生成物に絶対パスを入れない。
状態の区別「使えない」「古い」「0 件」を区別して返し、画面でも区別して示す。
検索の結果方式によらず、wiki_search.py --json の形にそろえる。
Wiki のルートスキルと同じ順で解決する（指定したパス、プロジェクトの指示、グローバルの指示、現在のプロジェクトの wiki/）。場所を決め打ちしない。
埋め込むデータ</script>、U+2028、U+2029 などをエスケープする。
共通ADR-0001 の 3 条件と AC-D02 を 3 方式に共通の条件にする。書き込みの API を持たず、未解決リンクをクリックしてもファイルを作らない。
サーバー127.0.0.1 への固定、起動ごとのトークン、Host ヘッダーの確認（ADR-0002 のまま）。
アプリポートを開かない stdio の IPC を既定にする。外部の URL はアプリの中で開かず、確かめてから OS のブラウザに渡す（S-07）。
静的 HTML<meta> の CSP を付ける。書き出し先は未決。
交換できること試験用の Wiki で、3 方式のリンクの移動、被リンク、診断の結果が一致することを、実際に動かして確かめる。
閲覧専用操作の前後で Wiki のファイルのハッシュが変わらないこと、外部への通信が 0 件であること（サーバーでは 127.0.0.1 以外が 0 件）を確かめる。
バイト一致生成器の回帰検査にだけ使う。同じ HTML でも、基準の URL、CSP、WebView の権限で動作は変わるので、交換できることの証明には使わない。

作る順序

1〜3 は、どの方式に決まっても無駄にならない。

  1. resolve_link() と clean_link_target() を共通モジュールに切り出す。今は lint と search に 1 つずつあり、NFC にそろえる順が違う。
  2. 中核、ページの HTML のテンプレート、日本語の CSS を作る。
  3. 第 1 段階（ページ、ナビゲーション、メタ欄、被リンク、関係表、未解決リンク）を、静的に描ける形で完成させる。mermaid と svg の表示は ADR-0005 のとおり含めない。
  4. 選んだ方式のアダプタを作る。最初は構成 B のサーバーとする。
  5. 検索、全体のグラフ、RAG のデータ源を足す。

ADR-0002 との関係

置き換える 2 行

  • 作る順序：共通モジュールと、静的に描ける第 1 段階を先に作る。
  • 書き出し：静的 HTML を副機能から、サーバー、アプリと並ぶ 1 つの方式にする。サーバーで開いたときに変換する既定の動作は変えない。

保つ行

  • markdown-it-py による変換と、生の HTML を出さない設定
  • 閲覧専用、ADR-0001 の対策、対応 OS

網掛けの選択肢は総括が推した案である。1 を決めないと中核を書けない。

1 閲覧の「ページ」の集合 最初に決める

lint と search で、ページとして扱う集合が違う。wiki_lint.py は最上位の README.md と .evolution を除外する（L110〜111）。wiki_search.py は README.md を除外せず、.wiki-cache とドットで始まる名前を除外する（L286〜289）。

lint の集合を正とする 推し

F-G06 が lint との一致を求めている。wiki_search.py の側をそろえる。

search の集合を正とする

lint の結果と画面の未解決リンクが食い違う。

あわせて、index.md と indexes/ をナビゲーションの入力としてどう扱うかを決める。

2 書き出し先

<WIKI_ROOT>/.wiki-cache/browse/

1 か所で管理できる。「Wiki を変更しない」の範囲を、派生データを除くと明文化する必要がある。Wiki を OneDrive などで同期していると、生成物も同期される。

OS のユーザーキャッシュ

選択肢レポートの No.81 と整合し、Wiki の中に何も足さない。場所の解決と掃除の規則が要る。
3 静的出力のファイル名

大文字小文字だけが違うページは、NTFS と APFS で同じファイルになる。どちらの案でも export_name() で対処する。lint にこの検査を足すかも決める。

読める名前＋衝突時だけ接尾辞

受け渡しに向く。切り詰めの規則と、ページを足しても既存の URL が変わらない規則が要る。

すべて ASCII の ID

OS の間の衝突を避けやすいが、URL とファイル名が読めなくなる。
4 RAG への経路

rag の検索の入口は MCP だけである。ワーカーは MCP の接続中だけ動き（rag_worker.py:1）、rag_index.py の Engine.search（L302）には argparse も __main__ もない。どの案も rag の設計の変更で、ADR-0007 の見直しになる。

rag に検索の CLI を足す

呼ぶたびに torch とモデルを読み込む。ワーカーとの索引の排他も要る。

browse を MCP のクライアントにする

起動の費用は避けられるが、rag の MCP サーバーの寿命に縛られる。

常駐の検索サービス

ADR-0007 の「接続中だけ動く」構成を改めることになる。
5 静的版の検索の範囲

題名・要約・タグだけ

tokenize() の規則を JavaScript に二重に持たずに済む。

本文も bigram で検索

Python と同じ試験データで、一致を確かめ続ける費用が残る。
6 アプリの技術

アプリを採るときに決める。条件は、埋め込みの Web エンジンを持ち、Windows・macOS・Linux で動き、中核を子プロセスとして起動できること。

Tauri 2（Rust）

配布物が小さい。OS ごとに WebView が違い（WebView2、WKWebView、WebKitGTK）、描画がそろわない。

Electron（TypeScript）

Chromium で描画がそろうが、配布物が大きい。

日本語の表示を重く見るので、Linux の WebKitGTK での描画が分かれ目になる。アプリはプラグインではないので、別のリポジトリ（仮称 to884/info-hive-viewer）に置く形を想定する。sidecar は OS と CPU ごとに要り、「移植性」はソースの移植性にとどまる。

実装の前に PoC で確かめること

どれもまだ誰も確かめていない。前提と違えば、この案を見直す。

  • 未確認file:// で開いたページで、<script src> による別ファイルの読み込みが主要なブラウザで動く。fetch は移植性のある前提にできない。
  • 未確認Linux の WebKitGTK で、日本語の CSS（line-break: strict など）が崩れずに描ける。
  • 未確認Tauri の独自スキームの URL の形が OS で違っても、相対リンクだけで閉じた HTML がそのまま動く。
  • 未確認ナビゲーションの 1 項目が約 100 バイトに収まる。埋め込めば 1,000 ページで約 100 MB になる、という見積もりの前提である。
  • 未確認3 方式で、合格の条件の試験が通る。

批評で動いた点

A の論証を 1 つ削った 撤回

wiki と rag は Python の版が違うので、同じプロセスに載らない。

wiki の >=3.10 と rag の >=3.12,<3.13 は 3.12 で重なる。プロセスを分ける結論は「Python 以外のアプリからは import できない」という理由で残る。

B の受け入れ条件を格下げした 格下げ

HTML がバイト単位で同じなら、3 方式を入れ替えられる。

基準の URL、CSP、IPC で動作は変わる。バイト一致は回帰検査に回し、合格の条件は実際の動作で測る。

契約に足した規則 追加

  • 共有の nav.js（B）
  • データの世代（C、D）
  • ambiguous なリンク（D）
  • 見出しの確認を分ける（C）
  • ルートを設定から解決（C、D）
  • 埋め込みデータのエスケープ（C）
  • 出力のファイル名の衝突（A）

採らなかった選択肢

選択肢採らなかった理由
サーバーを先に作り、ほかは後で考えるサーバーを前提にした画面は、静的版とアプリに移すときに作り直しになる。
SPA にし、データを JSON で取得するfile:// では JSON を取得できず、静的版だけ別の作りになる。JavaScript を切ると読めない。
アプリの言語で規則を書き直す規則を 2 つの言語で保守することになる。アプリが Python を起動できない場合の最後の手段として残す。
ネイティブ描画の GUI（Qt など）本文は HTML なので結局 Web エンジンが要る。日本語の CSS とナビゲーションが二重になる。
pywebview（Python）中核と同じ言語である利点はあるが、OS ごとの依存が要る。試作の候補として残す。
HTTP サーバーを窓で開くだけの殻ポートを開くので ADR-0001 の対策がアプリにも要る。stdio の IPC を既定にし、HTTP は予備にする。

決定行列の点と順位は既製の構成を比べたもので、自作のアプリは採点の対象に入っていない。
