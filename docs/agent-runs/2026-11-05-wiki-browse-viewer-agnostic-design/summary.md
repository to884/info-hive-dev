# ブラウズの手段を三案のどれでも採れる設計 の総括

## 推奨

4 体が独立に同じ骨格に達した。「Wiki の解釈（走査、frontmatter の正規化、リンク解決、見出し、被リンク、型付き関係）を Python の 1 か所に置き、ローカル HTTP サーバー、デスクトップアプリ、静的 HTML は、その出力を表示する薄いアダプタにする。契約は三案でいちばん厳しい `file://` に合わせる」を採用し、各エージェントが見つけた追加の規則（後述）を契約に足して、ADR-0002 を補う新しい ADR として記録することを推奨する。

## 批評で動いたこと

- **エージェント A** は、他の 3 案を読んで 8 点を改めた。ナビゲーションを各ページに埋めず共有スクリプトにする（B の約 100 MB の試算を受けて）、データの世代と `ambiguous` なリンクの状態を契約に入れる（C、D）、見出しの存在確認をページの解決と分ける（C）、Wiki のルートを設定から解決する（C、D）、埋め込みデータのエスケープ（C）など。骨格は変えていない。
- **エージェント B** は 5 点を改めた。静的出力のファイル名の衝突（A）、RAG が browse から呼べない事実（A）、見出しの規則（C）、世代と状態（C、D）を取り込み、さらにレビュー中に **lint と search でページ集合が違う**という新事実を見つけた。
- **エージェント C と D** は、レビュー時に自分の初回成果を参照できず、自己修正を記録していない。両者とも結論の順位で C の案（D は C を、C は D を）を推した。
- **最も鋭い反論は 2 つ。** (1) C と D による「wiki と rag は Python の版が違うので同じプロセスに載らない、という A の根拠は誤り」。`>=3.10` と `>=3.12,<3.13` は 3.12 で重なることを私も確かめた。A の結論（プロセス境界）は「Python 以外のアプリから import できない」という別の理由で残るので、決定的ではないが A の論証を 1 つ削った。(2) C と D による「HTML のバイト一致は交換可能性の証明にならない」。基準 URL、CSP、IPC で動作は変わる。これは B の受け入れ条件の格下げを要する指摘で、当たっている。

## 推奨案が残る理由

- **骨格は 4 体が独立に導いた。** A と B はサブモジュールのコードを読み、C は ADR と一次資料から、D は文書だけから、同じ「意味の共通化とアダプタ分離」に達した。同じ資料の写しではない。
- **`clean_link_target()` の二重実装**（lint は分割前、search は分割後に NFC）は B と C が確かめ、一致した。規則を 1 か所に置く理由がコードで裏付けられている。
- **RAG に MCP 以外の入口がない**ことは、B、C、D のレビューで一致した。私も `rag_index.py` に `argparse` と `__main__` がなく、`commands/search.md` が MCP の `search` を呼ぶことを確かめた。三案のどれを選んでも rag 側の変更が要る、という A の指摘は残る。ただし「CLI が唯一の解決」ではない（後述）。
- **lint と search のページ集合の食い違い**を私も確かめた。`wiki_lint.py:110` は `README.md` を除外し、`wiki_search.py:286` は除外しない。`.wiki-cache` の扱いも逆。F-G06 が lint との一致を求めるので、lint の集合を正とするのが筋である。
- **ADR-0002 に「複数 Wiki は URL に識別子を含める」という決定行はない**ことを確かめた。B がその改訂を求めた根拠は選択肢レポートの記述であり、A と C の「相対リンクなら `file://` でも複数 Wiki を扱える」が正しい。
- **割れた論点の決め方。** A と B の「同じ HTML を相対リンクだけで閉じ、`<script src>` だけを使い、トークンはパスの先頭」は、アダプタの食い違いを仕組みで防ぐ唯一の具体策なので採る。一方、合格条件は C と D のとおり動作で測る（試験用 Wiki で、三方式のリンク遷移、被リンク、診断が一致する）。バイト一致は生成器の回帰検査として残し、証明には使わない。

## エージェントごとの要約

**エージェント A** は 7 つの不変条件を立て、中核を Python に置いてプロセス越しに呼ぶ、相対リンクで閉じる、`file://` を最低条件にする、RAG は任意、という最も具体的な設計を出した。コードを読んで、静的出力のファイル名衝突（大小文字、NTFS）、RAG の入口の不在、NFC の順序の差を掘り当てた点は他にない。当たっていた指摘は、Python の版を理由にした同一プロセス不可の論証が誤り（C、D）、ナビゲーションの埋め込みで約 100 MB になる（B）、Qt を「画面が二重になる」として除外したのは QtWebEngine を見落としている（C）、`export_name()` が切り詰めや既存 URL の安定性まで決めていない（D）、RAG の CLI 追加はワーカーとの索引競合とモデル再読み込みの費用を見ていない（B、C、D）。

**エージェント B** は「コンパイラ 1 つ＋版付きバンドル」の形で、既存関数の再利用表、ナビゲーションの容量試算、検索の段階宣言（`live`、`embedded`、`none`）、受け入れ試験を示した。当たっていた指摘は、書き出し先 `<WIKI_ROOT>/.wiki-cache/browse/` が「Wiki を書き換えない」契約と矛盾しうる（A、C、D）、`resolve_link()` は見出しを捨てるので「既存関数で足りる」は過大（C）、SHA-256 の解析キャッシュだけでは被リンクの差分更新は成立しない（C、D）、バイト一致は証明にならない（C、D）、複数 Wiki と相対リンクを不要に対立させた（A、C）。

**エージェント C** は共通契約を `PageRef`、`PageView`、`Capabilities`、`SnapshotInfo` などの項目で定義し、リンクの意味と URL の分離、見出し解決の別契約、ルートの決め打ち回避（実際の Wiki が `W0_Wiki/` にある）、「利用不可」「障害」「0 件」の区別、自作アプリが決定行列の採点対象外であることを指摘した。当たっていた指摘は、形式の逸脱（A、B）、出力ファイル名の衝突規則がない（A、D）、スナップショット ID だけでは走査中の変更に対する整合性を保証しない（D）、JSON/stdio の契約が実装粒度に達していない（D）、RAG の入口の不在を特定していない（A、B）。

**エージェント D** は層ごとの責務と「依存させないもの」の表、`{wiki_id, page_id, anchor_id}` の参照モデル、`ambiguous` を含むリンク状態、`stale` などの誤り状態、ADR-0009 のグラフ先行削除への対処を示した。重複スラッグで `resolve_link()` が一意に決まらない穴を指摘したのは D だけである。当たっていた指摘は、サブモジュールを読んでおらず実装の裏付けが弱い（A、B）、ASCII の出力 ID は URL が読めなくなる費用を比較していない（A、B）、RAG の到達性を扱っていない（A、B）、数値がない（B）。

## 残るリスクと未確定事項

- **先に決めること。** 閲覧の「ページ」の集合を lint の集合にそろえる（`wiki_search.py` 側を直す）。これを決めずにコンパイラは書けない。
- **書き出し先。** `.wiki-cache` の中なら 1 か所で管理できるが、F-G06 と AC-D02 の「変更しない」の範囲を明文化し、OneDrive などの同期に生成物が混ざる。OS のユーザーキャッシュなら選択肢レポート No.81 と整合するが、場所の解決と掃除の規則が要る。
- **静的出力のファイル名。** 読める名前＋衝突時だけ決定的な接尾辞なら受け渡しに向くが、切り詰めと既存 URL の安定性の規則が要る。すべて ASCII の ID なら OS 間の衝突を避けやすいが、URL とファイル名が読めなくなる。
- **RAG の入口。** rag に検索 CLI を足すと呼ぶたびに torch とモデルを読み込み、ワーカーと索引の排他が要る。browse が MCP クライアントになると起動費用は避けられるが、rag の MCP サーバーの寿命に縛られる。常駐の検索サービスは第三案だが ADR-0007 の見直しになる。どれも rag 側の設計変更である。
- **静的版の検索の範囲。** 題名・要約・タグだけなら `tokenize()` の二重化を避けられる。本文の bigram 検索を JavaScript に移すなら、Python と同じ試験データで一致を確かめ続ける費用が残る。
- **アプリの言語。** Tauri 2 は配布物が小さいが OS ごとに WebView が違い、Linux の WebKitGTK での日本語の描画が未確認。Electron は描画がそろうが配布物が大きい。いずれも sidecar は OS と CPU ごとに用意する必要があり、「移植性」はソースの移植性にとどまる。
- **ADR-0002 の改訂範囲。** 変わるのは「作る順序」（共通モジュールと静的に描ける第 1 段階を先に）と「書き出し」（副機能から並列の方式へ）の 2 行だけで、複数 Wiki の行は変える必要がない。
- **誰も確かめていないこと。** `file://` での `<script src>` と `fetch` の挙動、WebKitGTK での日本語 CSS、Tauri の独自スキームの URL、ナビゲーション 1 項目 100 バイトという前提、三方式での実機の適合試験。実装の前に PoC で確かめる必要がある。
