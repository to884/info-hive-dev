## 判定

**却下。確信度：高。** NFC/NFD だけが違う別ファイルでは、ページを区別する情報がエッジに渡らず、同じ関係が再び消える。契約 2 と「どのページの関係も残る」という説明を満たさない。

## 致命的・重大な欠陥

1. **重大：正規化で同じパスになる別ページの関係が、再び 1 本にまとまる。**

   反例は、NFC/NFD のファイル名を区別できるファイルシステム上の次の 2 ファイルである。

   - `concepts/\u30ac.md`（NFC の「ガ」）
   - `concepts/\u30ab\u3099.md`（NFD の「カ＋結合濁点」）

   両方を `type: concept` とし、同じ `depends_on → concept:y`、`source`、`evidence` を書く。既定のノード ID は両方とも `concept:ガ` になる。

   実装では `page_key()` がディスク上の名前を使うため、主語の対応には 2 ページとも残る。しかし、`make_edge()` に渡す `page` は NFC 済みの `rel_path` であり、両方とも `concepts/ガ.md` になる。結果としてエッジ ID が一致し、`push()` が後の関係を捨てる。

   実際の `collect_pages()` を、ファイル列挙と読み込みだけメモリ上の入力に置き換えて実行したところ、型付きエッジは **2 本ではなく 1 本**だった。`duplicate_node_id` の診断も、異なるディスク上の名前を失い、`pages` に同じ `concepts/ガ.md` を 2 回入れていた。

   根拠：`skills/info-hive/scripts/wiki_graph_extract.py` の 174–177 行（パスの正規化）、253–259 行（ページキー）、295 行（診断用パス）、399–403 行（重複除去）、440 行（エッジの `page`）。同じ問題は 463、488、504 行の暗黙のエッジにもある。

   `CHANGELOG.md:20–21` と `references/graph-workflow.md:27–31` の、別ページの関係を残すという記述とも食い違う。

## 崩れる前提

- **「`page` が違えば別ページを区別できる」**  
  `page` に使う `rel_path` は正規化済みである。NFC/NFD の違いだけで共存する別ファイルでは成立しない。内部キーをディスク上のパスに替えても、出力時にその区別を失っている。

- **「契約 6 の source ページの除外は、診断の除外も含む」**  
  依頼文で明示された例外は、`sourced_from` の生成義務についてだけである。現実装は、候補の解決と診断もまとめて省いている。

- **「重複がない wiki なら、ID 以外のエッジは変わらない」**  
  無条件には成立しない。重複がなくても `sources: [" src "]` は、旧実装ではエッジなし、新実装では `source:src` へのエッジになる。パス、wikilink、単一文字列の修正でもエッジは増える。通常のスラッグのリストに範囲を限れば、比較した入力では一致した。

## 見落としと軽微な問題

- **軽微：source ページの未解決・曖昧な `sources:` が診断されない。**  
  `type: source`、`sources: [missing]` のページを与えると、`build_edges(..., diagnostics)` は診断を追加せず、グラフ lint の `unresolved_sources` も件数 0 になる。原因は `wiki_graph_extract.py:468` が、診断を含む処理全体を囲んでいること。契約 6 の生成除外は受け入れても、契約 4 の診断とは食い違う。`graph-workflow.md:29` と `CHANGELOG.md:27` にも、この診断除外は書かれていない。

- **軽微：数値の目的語について、extract と lint の照合が一致しない。**  
  一方のページを `graph.node_id: 1`、別ページの関係を `object: 1` にすると、extract はノード ID と目的語をともに `"1"` として接続する。一方、lint は整数 `1` のまま辞書を引くため、`broken_object_refs` を報告する。根拠は `wiki_graph_extract.py:434` と `wiki_graph_lint.py:223–236`。目的語側の不一致は既存だが、今回のノード ID の文字列化でも残っている。

- **軽微：GraphML では、残した平行エッジの宣言元ページが分からない。**  
  2 本のエッジと異なる ID は出力されるが、エッジの `page` 属性は出力されない。これは既存の制約である。根拠：`wiki_graph_extract.py:685–694`。試験の `test_graph_duplicate_slugs.py:335–336` は述語の出現数だけを数えており、ページ情報の保持は検証していない。

- **軽微：手順書のパスの例が一致しない。**  
  `graph-workflow.md:29` は、`a/Foo.md` を指す例として `sources/a/Foo` を挙げている。しかし、この参照が探すのは `sources/a/Foo.md` である。

- **軽微：16 件の試験には、上の正規化衝突と source ページの診断除外がない。**  
  `neighbors` と `path` の検証もない。また、確認した親リポジトリとプラグインの CI には、`test_graph_duplicate_slugs.py` の実行指定がなかった。

## 検証した事実

| 対象 | 結果 |
|---|---|
| 契約 1：主語を宣言元ページから引く | 一致。スラッグから引き直していない |
| 契約 2：別ページの同じ関係を残す | 不一致。上記 NFC/NFD の反例で 1 本に減る |
| 契約 3：目的語をノード ID として扱う | 抽出処理は一致。ページ参照として解いていない |
| 契約 4：出典候補の一意性と診断 | 非 source ページでは一致。source ページは診断も省く |
| 契約 5：共有 ID と曖昧な目的語を診断 | 通常の異なるパスでは一致。正規化衝突時は抽出診断のパスを取り違える |
| 契約 6：一意に解決する出典から生成 | 依頼文の source ページ除外を適用すれば、確認した入力では一致 |

追加で次を確認した。

- `64acc43` と現実装を読み込み、既存の `eval/decisions/fixtures/graph_wiki` を比較した。4 ページ、5 エッジで、ノードと ID 以外のエッジ内容は一致した。
- `wiki_lint` 全体を 9 種類の `sources:` 入力で比較し、結果は一致した。`missing_raw()` も、URL、絶対パス、相対パス等を含む 6 種類で一致した。
- 実際の SQLite 作成処理をメモリ DB に対して実行した。通常の異なるパスの平行エッジは 2 本とも保存され、`edges`、`neighbors`、`facts` に残った。`path` は最短経路の 1 本を返した。
- 試験は実際に 16 件ある。ただし、一時ファイルを書き込むため、読み取り専用の今回の環境では試験一式を実行していない。CLI のファイル公開処理と MCP 経由の実行は未検証である。

## 崩せなかった点

- 通常の `a/Foo.md` と `b/Foo.md` に異なるノード ID を付けた場合の主語と、パス付き wikilink の解決。
- 通常の異なるパスで同じノード ID を共有した場合の、両ページの関係の保持。
- 共有ノード ID を目的語にした型付き関係の除外と診断。
- 一意のページを指すパス付き `sources:` が、共有ノードへの `sourced_from` になるという実装判断。
- `nodes.slug` の UNIQUE 除去による、ID を使う問い合わせ処理への破綻。
