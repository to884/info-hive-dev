## 判定

**条件付きで採用可。確信度：中。** 前回の重大な反例は解消し、受け入れ済みの順序依存を超える重大な破綻は崩せなかった。ただし、辞書キーの文字列化には値の消失と既存出力の変化があり、「出力は変わらない」という説明は成立しない。

## 致命的・重大な欠陥

なし。

## 崩れる前提

- **文字列化した辞書キーが一意になるとは限らない。** 数値の `2` と文字列の `"2"` が共存すると衝突する。
- **Python の `str(key)` と JSON のキー変換は一致しない。** 真偽値や null のキーで異なる。
- **診断が出ても、既存のエッジ参照は自動修正されない。** 受け入れ済みのケースでは、並べ替え後も ID が別項目へ移る。今回確認した範囲では診断されており、この既知の制約を再び重大欠陥には数えない。

## 見落としと軽微な問題

1. **軽微：キーの文字列化で、辞書の値が黙って消える。**

   次は YAML として異なる 2 キーを持つ。

   ```yaml
   notes:
     2: numeric
     "2": textual
   ```

   `_normalize_for_json()` の結果は次になる。

   ```json
   {"notes": {"2": "textual"}}
   ```

   `numeric` が失われる。元の辞書のキー順を逆にすると、今度は `textual` が失われることも確認した。

   根拠：`skills/info-hive/scripts/wiki_graph_extract.py:577` の辞書内包表記。同じ変換を ID 計算にも使うため、このケースではキー順だけで出力値と ID が変わりうる。追加試験の `test_graph_duplicate_slugs.py:456–466` は、文字列化後も異なる `2` と `label` だけを確認している。

2. **軽微：以前書き出せた真偽値・null のキーも、別の名前になる。**

   `64acc43` と現実装で直列化結果を比較した。

   | 元のキー | 旧出力のキー | 新出力のキー |
   |---|---|---|
   | `True` | `"true"` | `"True"` |
   | `False` | `"false"` | `"False"` |
   | `None` | `"null"` | `"None"` |

   根拠は同じ `_normalize_for_json()`。`CHANGELOG.md:32` の「JSON はどのみちキーを文字列にするので、出力は変わらない」は、この入力では食い違う。

## 崩せなかった点

- 番号付けと ID 計算の空値の扱いの不一致。
