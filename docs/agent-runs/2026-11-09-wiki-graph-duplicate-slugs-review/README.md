# wiki 0.9.2（グラフの同じスラッグのページ）の敵対的レビュー

2026-11-09、`info-hive-wiki` の `wiki_graph_extract.py` で、別のディレクトリに同じスラッグのページがあるとエッジが別のページのノードに付く不具合の修正を、GPT-6.1 Sol（effort high、`ask-codex` の `review`）に敵対的レビューしてもらった。

- `review-task.md`: 依頼の文面
- `review-1.md`: Sol の結果。判定は「採用可」（確信度：中）。致命的・重大な欠陥はなし。

軽微な指摘への対応:

1. パスのないリンクの試験が独立していない → `test_bare_link_alone_points_to_neither` を足した。
2. ノードにならなかったページへのリンクの説明が抜けている → CHANGELOG と `references/graph-workflow.md` に書き、`test_link_to_page_without_its_own_node_makes_no_edge` を足した。
3. 文字列でない node_id で lint と extract が食い違う → 修正前からある。コメントを正確にし、範囲外として PR に書いた。
4. NFC と NFD の名前の違いだけのファイルの出力のパスが重なる → 修正前からある仕様の制約。範囲外として PR に書いた。

## 2 回目と 3 回目（閲覧の関係表の契約に合わせたあと）

1 回目のあと、閲覧（browse）の関係表がグラフの抽出に求める契約（`feature/wiki-browse-stage1` の `docs/plans/wiki-browse-stage1-2026-11-09.md` の 3、コミット d4391da）が決まり、それに合わせて直した。エッジの ID にページを入れる、同じ `graph.node_id` のページの関係を捨てずに診断する、`sources:` をページに解決する、の 3 つである。

- `review-task-2.md`、`review-2.md`: 判定は「却下」（確信度：高）。重大 1 件は、NFC と NFD の名前の違いだけの 2 つのファイルで、エッジの `page` が同じ NFC のパスになり、同じ関係が 1 本にまとまること。軽微は、ソースのページの `sources:` を診断しない、lint が数値の目的語を照合しない、GraphML にエッジの `page` がない、手順書の例の誤り、試験と CI の不足。
  - 対応: エッジの ID にはディスク上のパスを入れる（出力の `page` は NFC のまま）。候補のページの一覧はディスク上のパスにした。ソースのページでも診断を挙げる。lint の目的語を文字列にして照合する。GraphML に `d_page` を足した。手順書を直した。試験を 19 件にし、CI に足した。
- `review-task-3.md`、`review-3.md`（2 回目のセッションの続き）: 判定は「採用可」（確信度：中）。致命的・重大な欠陥はなし。
  - 軽微 1（Linux でファイル名に `\` を含むと、ページのキーが別のページと重なる）: `disk_rel_path` を `as_posix()` で作るようにした。`\` はページの規約で禁じているが、キーが重ならないほうがよい。
  - 軽微 2（ソースのページの試験が未解決だけを見ている）: 曖昧なケースも足した。

## 4 回目から 6 回目（関係の項目ごとのエッジと、sources: の分け方の共有）

3 回目のあと、browse が頼る性質が 2 つ加わった（`feature/wiki-browse-stage1` の計画の 3、コミット cb30278）。(a) `graph.relationships` の項目 1 つから必ず 1 本のエッジができ、`status` などだけが違う 2 件もまとめない。(b) `sources:` の値を lint の `unresolved_sources` と同じ `wiki_pages` の関数で分ける。

- `review-4.md`: 「却下」（確信度：高）。重大は、項目の中身全体を ID に入れたので、`contradicts` で互いのエッジの ID を書くと ID が変わり続けること。
  - 対応: ID に入れる欄を決めた（`VARIANT_FIELDS` と、エッジの ID の形でない参照の値）。入れ子の拡張の欄で止まらないようにした。文書の「必ず 1 本」に、エッジにする項目に限ることを書いた。
- `review-5.md`: 「却下」（確信度：高）。重大は 2 つ。省いた欄と空文字の扱いが番号の数え方と ID で食い違い、2 件が 1 本になること。`contradicts` だけが違う項目を並べ替えると、ID が別の項目に移ること。
  - 対応: 番号は、番号を入れる前の ID で数える。ノード ID などの参照の値は ID に入れ、エッジの ID の形の値だけを外す。それだけが違う項目は、並べ替えで ID が移りうるので `order_dependent_edge_ids` の診断に挙げる。出力の JSON のキーを文字列にそろえた。
- `review-6.md`: 「条件付きで採用可」（確信度：中）。致命的・重大な欠陥はなし。軽微は、キーをそろえるときに `2` と `"2"` がぶつかって値が消えること、`True` と `None` のキーが JSON と違う名前になること。
  - 対応: キーを json.dumps と同じ規則で変換し、文字列のキーとぶつかる数値などのキーには `#int` のように型の名前を付けた。試験を足した。
