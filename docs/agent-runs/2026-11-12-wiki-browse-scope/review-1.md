## 判定

**却下。確信度：高。** スコープ判定に使った外部設定を、その後の閲覧処理が削除・置換できる経路があります。また、明示された設定を見失う誤判定と、旧版サーバー再利用時の画面・起動出力の食い違いを確認しました。

以下の行番号は現行ソース基準です。破壊操作は実行せず、ファイル操作をモックした検証とコードの照合で確認しました。

## 致命的・重大な欠陥

1. **【致命】新しく読む作業領域設定が、書き込みから保護されていない。**

   次の配置で成立します。

   - wiki は `D:/team/wiki`。
   - 閲覧の状態ディレクトリを `S = <data_dir>/browse/<wiki_key>.server` とする。
   - `S` は `.browse-server` を持つ既存ディレクトリで、稼働中のサーバーはない。
   - `S/server.json` に `{"kind":"user","dirs":{"wiki":"wiki"}}` を置く。
   - `D:/team/.info-hive/workspace.json` を、`S/server.json` へのシンボリックリンクにする。

   `serve` はこの設定を読み、`user` と判定します。しかし、保護対象は wiki とページ等の外部入力だけなので、その直後に設定の実体である `S/server.json` を削除し、サーバー記録に置き換えます。設定は `kind` を失い、終了時には実体ごと消され得ます。

   メモリ上の検証で、次の順序を確認しました。

   ```text
   設定の実体 server.json を読む
   protected を [wiki root] に設定する
   同じ server.json を unlink する
   同じ server.json にサーバー記録を書く
   ```

   `Guard.unlink()` 本体も、wiki だけを保護した状態では、この別ドライブ上の削除を許可しました。実ディスク上でのリンク作成・削除は未実施です。

   **根拠：** `wiki_browse.py:105`、`:749`、`:802`、`:812`、`:833`、`:839`。`wiki_browse_core.py:183` の `external_inputs()` は作業領域設定・案内ファイルを収集しません。第1段階設計の `:42`、`:223` にある「読んだ入力の実体を変更しない」と食い違います。

2. **【重大】ジャンクションで wiki 全体を別の場所に置くと、明示的な `kind` が失われる。**

   再現配置：

   ```text
   C:/personal/.info-hive/workspace.json
     {"kind":"user","dirs":{"wiki":"wiki"}}

   C:/personal/wiki  →  D:/team/wiki へのジャンクション
   D:/team/.git/
   ```

   `C:/personal/wiki` を指定して開いても、`wiki_root()` が先に `D:/team/wiki` に解決します。設定探索はそこから始まるため、`C:/personal` の設定には到達しません。結果は次になります。

   ```json
   {"kind":"project","name":"team","basis":"git"}
   ```

   これは「設定の `kind` が最も強い」「設定を書いた配置では正しく出す」という保証の反例です。設定の `dirs.wiki` は実体として対象 wiki を指しています。

   **根拠：** `wiki_browse.py:70` の先行する `resolve()`、`:105` の探索開始点、`wiki_workspace.py:179` の実体からの祖先探索。リンクの対応を模擬した検証で上記結果を確認しました。

3. **【重大】対象外の近い設定が、対象 wiki を明示した上位設定を隠す。**

   次の配置では、上位の有効な `kind:user` が使われません。

   ```text
   D:/team/.git/
   D:/team/.info-hive/workspace.json
     {"kind":"user","dirs":{"wiki":"wiki"}}

   D:/team/wiki/.info-hive/workspace.json
     {"kind":"project","id":"inner","dirs":{"wiki":"another"}}
   ```

   `D:/team/wiki` を開くと、内側の設定が最初に見つかります。その `dirs.wiki` は別の場所なので棄却されますが、上位設定の探索は再開されません。そのまま Git 判定へ進み、`project / team` と断定します。

   メモリ上の検証結果も `{"kind":"project","name":"team","basis":"git"}` でした。「別の場所を指す設定は使わない」は、実装上、その設定が上位の有効な設定まで遮る動作になっています。

   **根拠：** `wiki_workspace.py:180`〜`:194` は最初の設定で戻り、`wiki_browse.py:105`〜`:124` は不一致後に探索を続けません。設計 `docs/plans/wiki-browse-scope-2026-11-12.md:43` の設定付き配置への保証と食い違います。

4. **【重大・設計欠陥】ユーザー作業領域の子孫をすべて `user` とするため、プロジェクトを誤表示する。**

   例えば `~/info-hive/project-A` を Git リポジトリにし、そこで通常の `/wiki:init` により `wiki/` を作ると、作業領域設定がない場合は次になります。

   ```json
   {"kind":"user","name":null,"basis":"user_home"}
   ```

   `project-A/.git` が存在しても確認されません。旧配置の `~/wiki/project-A/wiki` でも同じです。独立したプロジェクトの既定配置なのに、画面と起動出力の両方がユーザースコープと断定します。

   ADR-0008 の「ユーザー作業領域にはプロジェクト固有情報を置かない」という運用前提はありますが、`/wiki:init` はこの配置を拒否しません。

   **根拠：** `wiki_browse.py:117`〜`:127` の包含判定と優先順位、`init_wiki.py:180`〜`:194`、`commands/init.md` のプロジェクト初期化手順。Windows パスを使ったメモリ上の検証で確認しました。

5. **【重大】旧版サーバーの再利用では、起動出力が画面にないスコープを報告する。**

   再現手順：

   1. 0.11.2 の閲覧サーバーを起動したままにする。
   2. 新版へ更新する。
   3. 同じ wiki に新版の `serve` を実行する。

   旧版の `server.json` には `scope` がありません。新版は再利用に成功し、呼び出した側の判定を `scope` として出力します。しかし、応答を描くのは旧版サーバーなので、サイドバーにもタブにもスコープはありません。再実行を繰り返しても旧版を再利用します。

   互換記録を使った検証では、出力が `reused:true, scope:"project", scope_name:"team"` になる一方、旧版相当の `Core(scope=None)` の HTML に `_scope` がないことを確認しました。

   **根拠：** `wiki_browse.py:762`〜`:768`、`:824` のフォールバック。設計 `:36` はこの動作を明記していますが、`commands/browse.md:14` の「画面にも同じスコープ」と食い違います。追加されたサーバー試験は、新版同士の再利用だけを扱っています。

## 崩れる前提

- **「設定を書けば推測を訂正できる」**  
  wiki 全体がジャンクションの場合や、対象外の近い設定がある場合は、対象を指す設定まで到達しません。

- **「ユーザー作業領域の配下には、独立したプロジェクトの wiki がない」**  
  リポジトリをその配下に置くだけで崩れます。実装はこの運用規則を検査していません。

- **「スコープ判定は読むだけなので、閲覧専用の守りに影響しない」**  
  新しく読んだ設定の実体が、閲覧の状態・出力ファイルと重なる場合に崩れます。

- **「再利用したサーバーが、起動出力と同じ表示能力を持つ」**  
  `scope` 導入前のサーバーが稼働している場合に崩れます。

- **「Git 配下であることが、プロジェクトスコープの証拠になる」**  
  設定なしの個人用 wiki を独立した Git リポジトリ配下に置けば崩れます。これは設計 `:44` に既知の制限として書かれていますが、目的1への例外であることは変わりません。

## 見落としと軽微な問題

- **【軽微】保存された差分と現行ソースが一致していません。**  
  `info-hive-wiki.diff` では `wiki_dir.resolve()` が例外捕捉の外にあります。現行の `wiki_browse.py:104`〜`:110` では捕捉内に移り、`RuntimeError` も追加されています。差分側の例外漏れを、現行ソースの未修正欠陥としては数えていません。

- **【軽微】壊れた表示名で、閲覧全体が停止します。**  
  設定の `id` を JSON の `"\ud800"` とすると、`check_config()` は受理しますが、サーバー記録の UTF-8 化が `UnicodeEncodeError` になります。検査の受理と例外発生を実行確認しました。`wiki_browse.py:839`、`wiki_browse_fs.py:168` が経路です。異常な設定に限るものの、「設定が壊れていても閲覧を止めない」の例外です。

- **【軽微】スコープの違いが世代に入りません。**  
  同じ `Snapshot` に異なるスコープを渡すと、HTML と manifest は変わりますが `generation` は同じです。実行確認しました。世代だけを比較する既存の検査では、この混在を識別できません。根拠は `wiki_browse_core.py:536`、`:1084`、`:1177` と `browse_assets/app.js:34` です。

- **追加試験は主要な反例を扱っていません。**  
  `ScopeTest` に、wiki 全体のジャンクション、対象外の近い設定と有効な上位設定の併存、設定入力と書き込み先の重複がありません。`test_serve_reports_the_scope_shown_on_screen` も旧版記録を扱いません。既存試験の通過では、上記欠陥は否定できません。
