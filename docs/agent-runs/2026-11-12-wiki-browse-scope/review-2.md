## 判定

**却下。確信度：高。** コマンド側が読んだ設定の実体を削除・置換できる経路が残っています。また、指示の置き場所による誤分類と、記録破損時の画面・起動出力の不一致が成立します。

実行検証は Windows の Python 3.14.6 で、メモリ上の写しとモックを使いました。ファイルの変更、リンクの作成、実ファイルの削除は行っていません。

## 致命的・重大な欠陥

1. **【致命】設定の読み取りをコマンド側へ移しても、読んだ入力の保護漏れは残る。**

   次の配置で成立します。

   - 作業ディレクトリは `D:/team`、wiki は `D:/team/wiki`。
   - wiki を指定するプロジェクト・グローバルの指示はない。
   - `S = <data_dir>/browse/<wiki_key>.server` は `.browse-server` を持つ既存ディレクトリで、サーバーは停止中。
   - `S/server.json` に `{"version":1,"kind":"user","dirs":{"wiki":"wiki"}}` を置く。
   - `D:/team/.info-hive/workspace.json` は `S/server.json` へのシンボリックリンク。

   `/wiki:browse` の手順 0 は設定を読み、`D:/team/wiki` と `user` を選びます。しかし、子プロセスに渡すのは wiki とスコープだけです。設定の実体は保護対象に入らず、`serve` が同じ `S/server.json` を削除し、サーバー記録で置き換えます。設定は `kind` と `dirs` を失います。

   設定 JSON が `wiki_workspace.check_config()` を通ること、実体の識別と削除だけをモックした実際の `Guard` が削除を許すことを確認しました。実ディスクでの破壊は未実施です。

   **根拠：** `info-hive-wiki/commands/browse.md:12`、`wiki_browse.py:730`・`:786`・`:817`・`:823`、`wiki_browse_core.py:179`。スクリプト名はいずれも `info-hive-wiki/skills/info-hive/scripts/` 配下です。設計 `docs/plans/wiki-browse-scope-2026-11-12.md:45` の「原因 A の指摘 1〜4 は起きない」は、コマンドを含む閲覧全体では成立しません。

2. **【重大】「プロジェクトの指示にある」だけで、そのプロジェクトの wiki と断定する。**

   反例は次の指示です。

   ```text
   グローバルの指示:
     ユーザースコープの wiki は U。全プロジェクトで共有する。

   プロジェクト P の指示:
     このプロジェクトでも、共有のユーザースコープの wiki U を使う。
   ```

   手順 0 を忠実に適用すると、近いプロジェクトの指示で `U` を発見したため、`--scope project --scope-name P` になります。指示本文が明示しているユーザースコープを、指示ファイルの置き場所によって反転させています。

   同じ `U` を指す作業領域設定が `kind:user` でも、その設定は後順位なので訂正されません。ユーザーが `U` を明示した場合も、グローバル・プロジェクトの両方に一致したときの分類規則がありません。

   これはエージェントが表を誤適用した場合ではなく、表自体の反例です。実際のエージェントによるコマンド実行は未測定で、文書規則の適用結果として確認しました。

   **根拠：** `info-hive-wiki/commands/browse.md:12`、設計 `docs/plans/wiki-browse-scope-2026-11-12.md:33`〜`:40`。前提の `info-hive-wiki/skills/info-hive/SKILL.md:71` は、ユーザー wiki をプロジェクト横断の知識基盤として説明しています。

3. **【重大】記録のスコープが破損すると、画面とは違うスコープを成功として報告する。**

   再現手順：

   1. `--scope project --scope-name proj` でサーバーを起動する。
   2. `server.json` のポート・トークン・インスタンスを保ち、`scope` だけを削除するか、`null` または `{"kind":"user","name":null}` に変える。
   3. 同じ wiki の `serve` を再実行する。

   サーバーのメモリ上のスコープは変わらないため、画面は「プロジェクトの wiki / proj」のままです。一方、再利用側は記録に従い、`scope:null` または `scope:"user"` を出力します。`status` が確認するのはインスタンスであり、画面のスコープではありません。

   `serve` の再利用分岐と実際の `Core` 描画を使ったモック検証で、両方の不一致を確認しました。また、記録の名前を `"a\ud800b"` にすると、`_recorded_scope()` を通過し、UTF-8 の起動出力で `UnicodeEncodeError` になります。

   **根拠：** `wiki_browse.py:603`、`:703`、`:743`〜`:750`、`:765`、`:800`〜`:808`。設計 `docs/plans/wiki-browse-scope-2026-11-12.md:51` の「記録が読めないなら画面にも出ていない」という推論は成立しません。

## 崩れる前提

- **呼び出し元へ読み取りを移せば、入力保護の問題がなくなる。**  
  呼び出し元が読んだ実体と、子プロセスの状態ファイルが重なると崩れます。

- **指示ファイルの適用範囲と、参照先 wiki の保存範囲は同じである。**  
  プロジェクトの指示が共有ユーザー wiki を参照すると崩れます。

- **同じ wiki を指す情報源の間で、スコープが矛盾しない。**  
  グローバル・プロジェクト双方の登録や、指示と設定の併存で崩れます。

- **正しいインスタンスに接続できれば、ディスクのスコープも正しい。**  
  認証情報を保ったまま `scope` だけが破損すると崩れます。

## 見落としと軽微な問題

- **【軽微】スコープ名による絶対パス検査の除外が、表示しないファイルにまで及ぶ。**  
  `wiki_browse_core.py:545`〜`:547` は名前を `recorder.common` に加えます。`--scope-name C:/Private/ReviewHome` に相当する設定で、生成器由来の同じパスを `nav.js` に注入すると、スコープなしでは `leaks`、ありでは `warnings` になりました。スコープ名をデータファイルに出さない設計とは整合しません。これは別途混入がある場合の検査漏れであり、通常生成での漏出は確認していません。

- **追加試験は、主張の一部しか検証していません。**  
  `tests/wiki/test_browse.py:955` は表示がないことだけを確認し、外部ファイルへの読み取りを禁止していません。`:963` の壊れた記録の試験は、稼働サーバーの画面との一致を確認していません。`tests/wiki/test_browse_server.py:604` 以降は正常な新版サーバー同士で、指示の競合、入力実体の重複、記録破損を扱っていません。
