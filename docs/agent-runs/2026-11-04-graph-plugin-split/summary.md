# グラフ・オントロジー機能のプラグイン分割の総括

## 推奨

**現時点では別プラグインに分けず、wiki 内で任意機能としての有効化・依存準備・索引更新の境界を整理することを推奨します。** wiki 外からの具体的な利用、重い専用依存、独立リリースの必要性が生じた時点で、分割を再検討してください。

## 批評で動いたこと

- **エージェント C は、公開 CLI/API を先に選ぶ姿勢を修正しました。** D の成果とレビューから、再生成の中断・同時実行、skills.sh と他ランタイムの既存利用者を検討に追加しました。共有処理は、公開インターフェースと単一の保守元からの配布時同梱を比較する立場へ変わっています。
- **エージェント D は、MCP と共有コードの同梱を既定案にする姿勢を修正しました。** C の指摘を受け、MCP の接続管理と、同梱したコードの版のずれを追加費用として認めました。まず CLI で必要な入口を満たせるか確認する順序へ改めています。
- **最も鋭い反論は、両案とも「分割後に共有処理をどう確実に呼ぶか」が未完成だったことです。** C の絶対パス受け渡し案は `/graph:lint` の直接起動などを説明し切れず、D の同梱案は日本語対応表や D2 の質問定義・閾値の所有と版管理が不足していました。これは両分割案をそのまま採用しない決定的な理由ですが、将来の分割が不可能という証拠ではありません。
- 当面の結論は変わっていません。相互レビューの順位は逆ですが、差は未実証の将来案への評価です。**現状把握の広さでは D、共有処理の保守元を集約する着眼では C に強みがあり、一方を全面採用する根拠はありません。**

## 推奨案が残る理由

- **配布を分けても、wiki の手順との結び付きは残ります。** グラフはページ形式、wikilink、出典を入力とし、取り込み・問い合わせ・lint・upgrade に組み込まれています。分割後も呼び出す時点、鮮度、失敗時の扱いを調整する必要があります。
- **「任意の層」という説明と実装の差が、レビューで確認されています。** init と upgrade はグラフ用ファイルを配置し、通常セットアップにも PyYAML が含まれます。オントロジー欠落時は extract が続行、lint がエラー、query が DB を確認するという違いがあります。まずこの契約を揃えるべきです。
- **索引更新の条件にも修正余地があります。** extract は `graph:` 以外に wikilink、`sources`、`raw` も使うため、型付き関係の追加だけを再生成の条件にできません。また、既存 DB を削除してから再生成する実装は確認されましたが、中断・競合による障害は再現されていません。
- **軽量化の利益は未測定です。** グラフ専用の常駐処理はなく、分割しても検索側のモデル導入は残ります。PyYAML の明示的な要求を分けることはできますが、推移的依存まで消えるかは未確認です。有効化と準備処理の内部整理でも、改善の一部は得られます。
- **独立配布を支える試験が不足しています。** 既存の graph lint・D2 関連試験はありますが、extract から四つの問い合わせまでを通す専用回帰試験は確認されていません。PyYAML 不在で一部試験はスキップされますが、CI は明示導入しているため、通常の CI が検査を省いているという意味ではありません。
- **log・rag の分割理由は、そのまま当てはまりません。** log には wiki と異なる記録の性質、rag には永続ジョブなどの独立した実行責務があります。現行グラフは wiki の既存データを調べる索引です。移植元と配置を揃えることだけを理由に同梱する必要はありませんが、今分割すれば修正の振り分け先と互換性確認は増えます。

直近は、グラフの状態と各入口の動作を定義し、準備完了の契約、更新条件、手順の正本を揃えるのが妥当です。そのうえで親リポジトリの `tests/graph/` に、日本語・正規化・独自オントロジー・暗黙のエッジ・問い合わせ・無効状態・再生成中断の回帰試験を整える案を採ります。`graph/` の通常ページ走査からの除外は維持します。

## エージェントごとの要約

**エージェント C** は、wiki 内で境界を整理し、実需要が生じてから分割する結論です。共有する日本語処理と判定処理を wiki に集約する方向には、修正箇所を一つに保つ利点があります。一方、公開 CLI の発見・直接起動・更新後の再解決、バッチ処理の契約が不足していたという D の指摘は妥当です。skills.sh などの移行対象と、PyYAML を外す際の準備完了条件・既存テストへの影響も補う必要がありました。

**エージェント D** も、同じ当面の結論です。CLI 間の挙動差、既存の導入経路、DB 再生成中断まで扱い、運用上の判断材料を広く示しました。一方、MCP を追加する費用と、共有コードを複数配布した際の版のずれを過小に扱っていたという C の指摘は妥当です。一致試験だけでは独立更新後の整合を保証できず、保守元・配布版・対応する組み合わせまで定める必要があります。

## 残るリスクと未確定事項

- **提供範囲をどうするか。** wiki の任意索引に限定するなら同梱が自然です。log・rag・複数 wiki を横断する基盤を近い将来の中核にするなら、分割の優先度は上がります。ただし、名前空間、出典位置、更新・削除通知の設計が先に必要です。
- **「使わない」をどう定義するか。** 新規 wiki でオントロジー配置と依存準備を選択式にすれば任意性は明確になりますが、現在の既定動作が変わります。既存オントロジーは保全し、upgrade が有効状態を勝手に変えない方針を決める必要があります。
- **分割時の接続方式。** 公開 CLI は実装を集約できますが、全入口での発見・互換性契約が必要です。配布時同梱は実行時の場所解決を減らせますが、単一保守元と版管理が必要です。MCP は発見しやすい窓口になりますが、接続障害や同時実行への責任が増えます。対象環境での試作結果なしに優劣は確定できません。
- **分割する場合の構成と移行。** `graph@info-hive`、リポジトリ `to884/info-hive-graph`、依存方向 `graph → wiki` が両案の共通案です。グラフ固有のコード・テンプレート・手順を移し、wiki は全体の進行と任意連携を持ちます。コマンドは `/graph:*` とし、汎用フックによる完了推測より明示的な呼び出しを優先します。利用者のページと `<WIKI_ROOT>/graph/ontology.yaml` は保持し、生成物を再作成します。
- **互換性とリリース。** `/wiki:graph`・旧パスの互換期間、skills.sh・他ランタイムの継続方法を決める必要があります。graph を先に提供し、wiki の撤去を後にします。SemVer、`plugin.json`、CHANGELOG、タグ、GitHub リリース、マーケットプレイス導入確認を揃え、マーケットプレイス項目には `version` を書きません。依存の版制約を使う場合は、公式文書で示されたタグ方式と現行運用の整合確認が必要です。
- **見直しの基準。** wiki 外の実利用、重い専用依存、独立更新の支障、測定された非利用者負担が分割の契機です。分割後も同時更新と連携障害が続き、独立利用が増えなければ再統合を検討します。

両成果とレビューは静的な読解が中心です。この総括では、提示された成果・レビューを判断材料とし、コードや公式仕様の再確認、接続案の実動作検証は行っていません。
