# 実体を単位にする要件のレビューへの応答

2026-11-19。Opus 5.5 / high。原文は [opus-review.md](opus-review.md)。
判定は REJECTED（Major 2件、Minor 2件）。以下は修正前に既存の手順と照合した判断である。

## 1. 既存の ingest と対象記録の一意性

`ingest-workflow.md` の手順4は名前だけでなく候補ページの本文を読んで既存との関係を判断する。手順7も全対象を無条件にページ化せず、独立したページにする価値を判断する。
したがって「現行が同名だけで自動統合する」「1記事に出たすべての実体をページ化する」と断定する読みは棄却する。
一方、`entities:`・`sources:` と実体ページの作成・更新、`graph-workflow.md` の実体間の出典付き関係が既存の手順にあることを確認した。
extractの制限をプラグイン全体の未対応と読ませる表現、別保存方式で既存entityページを識別の対象に含める要件の欠落は実際の不足である。
現行能力を分けて記述し、既存entityページのIDを再利用するか明示的に対応付ける要件、通常ingestと同一性の規則を共用する要件を追加する。

## 2. 採用後の ingest の扱い

「現行ingestが必ずsourceページに実体間の関係を書く」という断定は棄却する。手順8bはページの更新後に関係を追加し、参照先のgraph-workflowには実体ページに関係を書く例がある。
ただし、将来別の正本を選ぶ場合を含め、提案・適用と通常ingestの共通の対象識別・保留・根拠の記録を提供範囲に明記していない点は不足である。
初期版でingestも共通規則へ接続する案を採る。提案だけで閉じず、採用後の取り込みでも実体を主語にする。語彙の自動拡張とは区別し、同一性が未確定なら確定した対象への帰属を保留する。
共通規則と保存方式への接続が完成するまでは、採用後の取り込みまで提供済みとは報告しない。

## 3. 会話・報告の例

会話の「記事のつなぎ方」「記事の変更」などは、今回の主役を伝える例として不適切なまま残っている。対象・関係・根拠の記録を主語とする例へ変更する。
1事例でも複数記事と複数実体は含み得るため、1事例であること自体は欠陥とはしない。しかし例はその条件を示していないので、架空の顧客と製品、複数の出典、同一性を確認する候補を具体的に示す。

## 4. 診断の指標

非LLMの診断でも、保存済みの同一性の保留や既存ID重複は示せるので、「字面の一致しか示せない」という一般化は棄却する。
一方、手順0の指標が語彙の使用率に偏り、何を重複と呼ぶかが曖昧なのは不足である。対象・関係・根拠・保存済み保留の件数を中心にし、字面の一致は同一性の確認候補と明記する。

会話例は1記事に複数実体・複数記事に同一実体を含め、顧客番号・製品番号による対応の根拠を示した。言及しかない製品から利用関係を推測しない例にした。
