## 判定

**条件付きで採用可。確信度：高。** 保存された試料についての観測記録としては使えるが、比較対象の誤認、指標の偽陽性、位置の誤採点がある。このまま形式全般の採用方針を決める根拠にはできない。

以下、`B/` は `docs/research/markitdown-benchmark-2026-11-15/` を指す。

## 致命的・重大な欠陥

1. **【重大】「Poppler 4.00」を比較したことになっているが、実際は Xpdf tools 4.00 である。**

   `Get-Command pdftotext` が返した実行ファイルは `C:\Program Files\Git\mingw64\bin\pdftotext.exe`。`pdftotext -v` は `4.00`、著作権表示は `Glyph & Cog`、同じインストールの `etc/package-versions.txt` には `mingw-w64-x86_64-xpdf-tools 4.00-1` とある。この実行ファイルで4件のPDFを再抽出すると、保存済みの pdftotext 出力とすべて完全一致した。

   したがって、測ったのは Xpdf の結果であり、Poppler に対する速度・読み順・表の優劣は確かめられていない。ただし、wiki の手順自体は `pdftotext` としか指定していないため、「手元の pdftotext を実行した」という再現性まで否定するものではない。

   根拠：レポート26行、`B/scripts/run_bench.py:100–102,240–241`、`B/results.json:13`。

2. **【重大】「読み順1.0なら原本と同じ順に読める」は、実際の出力で反証される。**

   `slides.pdf` の MarkItDown 出力は、始業と終業の文を語の途中で交互につないでいる。それでも読み順は **1.0**。壊れた2文と年度の文字列が `missing` に入り、読み順の分母から除外されるからである。混線によって照合不能になった部分ほど、読み順の評価から消える。

   表も同様で、`expenses.pdf` の MarkItDown 出力は列対応を壊しているのに、PDFium と同じ **読み順1.0、表の行6/9** になる。空白と `|` を消してから文字列を探すため、セルの境界の破壊を検出できない。

   さらに、試料のCSV全行を空白でつないだ**1行の文字列**を `metrics()` に渡すと、網羅率1.0、読み順1.0、表の行5/5となった。「表の行」は、行の分離やMarkdownの表であることすら保証しない。Sol は今回これらの混線を指摘しているが、機械指標による裏付けとは扱えない。

   根拠：レポート62–63行、`B/scripts/run_bench.py:167–199`、`B/outputs/slides.pdf__markitdown.md:20–22`、`B/outputs/expenses.pdf__markitdown.md:1–6`、`B/summary.md` の該当行。

3. **【重大】Sol の位置の採点に、保存データと矛盾する判断がある。**

   Sol は、スライドPDFの pdftotext 出力について「明示的なページ境界はない」と記述し、pdfminer とともに位置を2点にしている。しかし、判定用ファイルにも両方式とも **5個の `\f` が残っており、分割すると5ページを復元できる**。表計算PDFにも両方式とも2個ある。単なる推測ではなく、判定用ファイルのバイト列で確認した食い違いである。

   また、レポートの「MarkItDown はページ番号を返せない」も断定過剰である。`handbook.pdf` の出力には「ページ1・2・3」が残り、Sol も位置を4点としている。機械指標が数える形式の目印がないことと、ページを特定できないことは一致しない。

   この採点から、PDFium の位置情報が他方式より優れる程度をそのまま判断することはできない。

   根拠：`B/judge/sol-result.md:117–146,185–226`、`B/judge/slides_pdf/A.md,B.md`、`B/judge/expenses_pdf/A.md,D.md`、`B/scripts/run_bench.py:191–193`、レポート94行、`B/outputs/handbook.pdf__markitdown.md:26,35,52`。

4. **【重大】「import に約3.5秒」という原因の特定は、計測していない。**

   `_cold()` が測るのは、Python のプロセス起動、ベンチマーク自身の読み込み、依存の読み込み、`MarkItDown` の構築、初回変換、終了までの全体である。`_warm()` は最初の呼び出し全体を捨てる。import だけ、インスタンス構築だけ、初回変換だけの時間は記録されていない。

   したがって「この環境で1回実行すると約3.7〜4.5秒」は支持されるが、「そのうち約3.5秒がimport」とは分離できない。異なる初期化方法や組み込み先に、この数値をそのまま適用する前提も成立していない。

   根拠：レポート11、137、163行、`B/scripts/run_bench.py:154–159,211–228`。

5. **【重大】掲載された再現手順は、変更後の出力と古いSol判定を混ぜた結果を生成できる。**

   `run_bench.py` の依存には MarkItDown の版固定がない。一方、`prepare_judge.py` は判定用のサブディレクトリを作り直すだけで、既存の `sol-result.md` を残す。最後の `aggregate.py` は、その残った判定を無条件に読み込む。掲載手順には、新しい出力をSolに判定させる工程がない。

   反例は、依存更新で `expenses.pdf` の列ずれが解消された状態で掲載手順を実行する場合である。新しい機械指標と出力に、旧出力への「致命的1件・総合1」という判定を結合できてしまう。判定と出力の内容を結び付ける検証もない。

   根拠：レポート170–176行、`B/scripts/run_bench.py:3`、`B/scripts/prepare_judge.py:19–40`、`B/scripts/aggregate.py:19–29`。

## 崩れる前提

- **Office が生成したPDFの読み順が、採用対象のPDFを代表する。** 別の生成ソフトや文字の格納順が異なるPDFでは崩れる。レポート自身も154行で認めており、冒頭の形式別方針にはこの限定が反映されていない。
- **文字列が存在すれば、正しい項目の値として残っている。** 表の列ずれ、別項目への移動、重複する数値で崩れる。今回の表計算PDFが実例である。
- **判定者が改ページなどの制御文字を認識する。** 今回すでに崩れている。方式名の匿名化だけでは、この表示上の差による採点偏りは消えない。
- **ZIPという形式単位で採用を判断できる。** 試料はDOCX・CSV・JSONだけである。PDFや未評価の形式を含むZIPにも同じ結論が及ぶという根拠はない。これは未検証であり、失敗すると断定したものではない。
- **総合5ならragへの適合性も示せる。** 判定依頼の用途は「LLMが要約ページを書くこと」である。検索、チャンク分割、出典位置の返却は評価対象に入っていない。

## 見落としと軽微な問題

- **【軽微】日付を正解から外したという説明は実装と食い違う。** レポート56行は除外したとするが、`expenses.pdf` の正解42項目には日付3件が残る。0.929は39/42であり、除外した値ではない。4方式に同じ影響なので、今回の相対順位は変わらない。根拠：`B/scripts/run_bench.py:85`、`B/scripts/content.py:177–186`、`B/results.json:388–477`。
