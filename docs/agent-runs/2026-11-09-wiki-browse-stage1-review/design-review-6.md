## 判定

**却下。確信度：中。** 書き込み直前の検査を記載どおりに適用すると、Wiki 外の通常の出力先を作れない。また、新規出力を同時に作る場合、入れ子禁止の検査とロック保持の間に競合が残る。

## 致命的・重大な欠陥

**1.【重大】親ディレクトリの包含検査が、Wiki 外への正常な書き出しを拒否する。**

次の配置を仮定する。シンボリックリンクやジャンクションはない。

```text
Wiki:       C:/work/wiki
出力先:     C:/work/view
作業場所:   C:/work/view.browse-work
```

`build C:/work/wiki --out C:/work/view` を実行する。

出力先と作業場所は Wiki と重ならず、§7 冒頭の検査を通る。しかし、作業場所を作る直前の検査では、親の `C:/work` が Wiki を**含む**ため拒否される。「対象と親」の両方に、包含関係を双方向で拒否する規則を適用した結果である。

`PureWindowsPath` によるメモリ上の確認でも、出力先・作業場所との重複は偽、親との重複は真になった。Wiki と生成物を共通の作業フォルダーに置く通常の配置で、新規書き出しが成立しない。

根拠：[出力先の許可条件・L105](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:105)、[書き込み直前の検査・L121](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:121)。

**2.【重大・推測】新規出力の同時起動では、目印による入れ子検査を両方が通過できる。**

**仮定：** 入れ子検査を事前に行い、公開直前には、明記された Wiki 保護の検査だけを行う実装とする。製品実装は未存在なので、実プロセスでの再現ではない。

Wiki と無関係な `/exports/` の下で、最初は存在しない次の出力先を選ぶ。

```text
A の出力先: /exports/site
B の出力先: /exports/site/nested
```

成立する順序は次のとおりである。

1. A が出力先・入れ子の検査を通り、`site.browse-work/build.lock` を取得する。
2. B も検査する。この時点で `site` はまだ存在せず、祖先に目印がない。
3. B が `site/nested.browse-work/` を作り、ロックを取得する。その過程で `site/` もできる。
4. A が入れ替え手順3に進む。今は `site/` があるため、B の作業場所と保持中のロックごと `old-*` に移せる。
5. A の旧世代削除が、実行中の B の作業場所まで削除しうる。

出力先ごとのロックは別なので、この順序を排除しない。書き込み直前の共通検査にも、別の browse の目印を再確認する規定はない。過去レビュー5の対策は、**既に目印が存在する入れ子**を拒否するが、検査後に成立する入れ子を閉じていない。

根拠：[入れ子検査・L106](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:106)、[出力先ごとの排他・L111](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:111)、[入れ替え・L117](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:117)。[試験・L170](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:170)にも、この新規出力同士の同時起動は明記されていない。

## 崩れる前提

- **「書き込み先の親が Wiki を含むなら、その書き込みは Wiki を変更する」**  
  兄弟ディレクトリへの `mkdir` でも成立する包含関係であり、欠陥1の誤拒否になる。

- **「検査時に別の browse の目印がなければ、入れ替え時にも存在しない」**  
  別の新規 build が検査後に作業場所を作ると崩れる。出力先ごとのロックでは共有の祖先を保護できない。

- **「見出し同士の ID が重ならなければ、アンカーは一意になる」**  
  テンプレート自身の ID と重なる場合を含んでいない。下記の PoC で再現した。

## 見落としと軽微な問題

**【軽微】移植元の PoC に、見出しの移動を誤る反例が残っている。**

メモリ上のページに次を与え、PoC の `Core`、`resolve()`、描画関数を実行した。

```markdown
# nav

## **Definition**
```

結果は次のとおりだった。

- `[[a#nav]]` は解決済みになるが、生成 HTML に `<nav id="nav">` と `<h1 id="nav">` が共存する。見出しより先にナビゲーションが同じ ID を持つ。
- `[[a#Definition]]` は `missing_heading` になる。見出しの照合対象が表示文字ではなく、`**Definition**` という Markdown 原文だからである。

根拠：[見出し文字列の取得](C:/Works/info-hive-dev/poc/browse/gen.py:205)、[アンカーの照合](C:/Works/info-hive-dev/poc/browse/gen.py:225)、[テンプレートの `nav` ID](C:/Works/info-hive-dev/poc/browse/gen.py:409)。

設計の見出し規則と試験には、この2件への扱いがない。PoC の試験も、[同じ ID の要素があるかだけを見る](C:/Works/info-hive-dev/poc/browse/static-test/probe.js:25)ため、前者を成功と判定できる。**PoC の欠陥は再現済み。新実装への残存は未確認。**

**【軽微】再構築失敗時の「古い」の画面表示が定まっていない。**

[設計 L133](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:133)は、旧中核を使い続け、失敗を `data/diagnostics.js` に載せるとする。しかし、旧 HTML と旧 `nav.js` の世代は一致するため、L98 の世代不一致表示は発火しない。失敗を各ページにどう提示するか、失敗後の閲覧で古さを確認する試験も明記されていない。

これは、[ADR-0010 L63](C:/Works/info-hive-dev/docs/adr/0010-wiki-browse-separates-core-from-delivery.md:63)の「古い」を画面でも区別する契約についての欠落である。

## 崩せなかった点

- ADR-0016 による2方式の合格条件自体は、今回の対象では崩せなかった。
- 127.0.0.1 固定、厳密な Host 照合、トークンという契約から、DNS rebinding の突破手順は示せなかった。
- デコード後の禁止要素検査と既知の出力名への限定から、任意ファイル取得の経路は示せなかった。
- 読み取り前の変更印、再構築の直列化、要求ごとのスナップショット固定について、以前の世代逆転の反例は適用できなかった。
- グラフ抽出の契約を満たす入力を前提にすると、今回確認した範囲では、関係表の振り分けを崩せなかった。
- 生成記録の出力外への配置、公開前の漏れ検査、`published_seq` による旧世代の選択は、設計に明記されている。
