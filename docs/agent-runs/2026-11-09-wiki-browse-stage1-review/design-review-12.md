## 判定

**却下。確信度：高。** 復旧を妨げる目印検査の矛盾と、lint と異なるリンク判定になる入力を確認した。また、最初の書き込みより前に保護範囲を決める保証が、Python の import による書き込みを扱っていない。

## 致命的・重大な欠陥

### 1. 【重大】正規の退避世代・作りかけ世代を、入れ子検査が拒否する

**主張：** §6.4 を記載どおりに適用すると、§7 の復旧処理に到達できない。

**再現手順：**

1. 公開済みの世代 G1 がある。
2. 次の build が `tmp-2/.browse-generation` を作る。
3. 書き出し先を `old-2` に移した直後、次の名前変更より前に停止する。
4. 再度 build する。

この時点の配置は次のようになる。

```text
site/                         存在しない
site.browse-work/
  .browse-work
  tmp-2/.browse-generation
  old-2/.browse-generation     G1
```

§7 は、作業用ディレクトリについて §6.4 を確かめてから片付け・復元へ進む。しかし §6.4 は「最上位のもの以外の browse の目印があれば止まる」とするため、正規の二つの `.browse-generation` で停止する。G1 は残っていても、書き出し先へ復元されない。

途中停止以外にも、旧世代の削除に失敗して `old-*` が残るだけで、次回の片付け前に拒否される。自分の作業用ディレクトリ内の世代を例外にする規則はない。

**根拠：** [計画 §6.4・目印の配置と入れ子禁止](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:241)、[§7・復旧前の検査](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:260)、同 L262、L264、L268、L270。

**検証結果：設計の内部矛盾。** 製品実装での再現ではない。§11 L417 の復旧試験は、この機構のままでは通らない。試験の欠落ではなく、機構と試験の衝突である。

### 2. 【重大】CR 改行の frontmatter が、browse だけ本文になり、`broken_links` と一致しない

**主張：** バイト列を `utf-8-sig` でデコードするだけでは、lint の `read_text(encoding="utf-8-sig")` と同じ文字列にならない。

**反例：** 次のファイルを、改行がすべて CR（`\r`）の UTF-8 とする。`existing.md` は存在し、`missing.md` は存在しない。

```markdown
---
type: "concept"
sources: ["[[missing]]"]
---
body [[existing]]
```

0.9.2 の実関数で、二つの読み方を比較した結果は次のとおりだった。

| 読み方 | frontmatter | 本文から抽出されるリンク |
| --- | --- | --- |
| lint の `read_text()` 相当 | 正常に認識 | `existing` |
| 設計のバイト列→`decode()` | 認識せず、`malformed=True` | `missing`, `existing` |

`read_text()` は改行を LF にそろえる。一方、設計のデコードでは CR が残り、`\n` を要求する `FRONTMATTER_RE` に一致しない。Markdown パーサーは残された frontmatter も本文として解析するため、`sources:` 内の wikilink が本文のリンクになる。

結果として、lint の `broken_links` は空、browse の `unresolved` は `missing` を含む。メタ欄の `type` と `sources` も失われる。パーサーと正規表現を共有しても、その前段で本文が異なる。

**根拠：** [計画 §2・デコードとページ辞書](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:79)、[§3.3・一致の主張](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:110)。`599611e:skills/info-hive/scripts/wiki_lint.py` の `FRONTMATTER_RE`（L110）、`parse_frontmatter_raw()`（L300–313）、`collect_pages()` の `read_text()`（L327）。

**検証結果：実関数で食い違いを再現。** ファイルは作らず、同じバイト列に対する読み取りをメモリ上で比較した。

### 3. 【重大】import によるバイトコード書き込みが、最初の保護判定を先行できる

**条件：** Python の既定どおりバイトコード書き込みが有効で、プラグインを含むディレクトリを Wiki ルートに指定する。import 先は書き込み可能で、キャッシュは未作成または更新が必要な状態とする。この配置を禁止する規則はない。

**再現手順：**

1. Wiki ルートの配下に `info-hive-wiki/` がある状態で、設計の起動コマンドを実行する。
2. browse が `wiki_pages` などの共通モジュールを import する。
3. Python が、スクリプトや同梱パーサーの配下に `__pycache__/*.pyc` を作る、または更新する。

これらは `wiki_browse_fs.py` を通らず、CLI が Wiki を特定して §6.1 を実行するより前に発生しうる。後から保護判定で停止しても、既に Wiki 内のファイル一覧が変わっている。

**根拠：** [計画 §6・すべての書き込みを保護関数に通す保証](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:211)、同 L218、[§9・起動コマンド](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:340)。`wiki_pages.py` の共通モジュールと同梱パーサーの import。起動手順にはバイトコード書き込みを止める指定がない。

**検証結果：書き込み要求を確認。** ローカルの `wiki_pages` の import で、キャッシュ未存在相当の条件を与え、書き込み関数をメモリ上で横取りしたところ、プラグイン配下へのキャッシュ書き込み要求が71件あった。実際の書き込みは行っていない。ローカルは0.9.0であり、0.9.2については同じ import 経路が残っていることをコードで確認した。

## 見落としと軽微な問題

- **【軽微・推測】初回の同時 `serve` が、使い回しに到達しない初期化競合がある。**
