## 判定

**却下。確信度：高。** 関係の誤帰属、変更の見逃し、Windows で使えない出力名を確認した。また、閲覧専用・絶対パスの非公開・世代の切り替えについて、設計と試験だけでは必須条件を保証できない。

以下では、設計上の欠落と、現行コード・PoC で確認できた欠陥を区別する。ファイルは変更していない。

## 致命的・重大な欠陥

1. **重大：採用予定の関係表生成は、別ページの関係を誤帰属させる。〔再現済み〕**

   `a/Foo.md` と `b/Foo.md` に、それぞれ異なる `graph.node_id`、`concept:first` と `concept:second` を付ける。前者だけに型付きの関係を書く。

   現行の `build_nodes()` と `build_edges()` を実行すると、前者に書いた関係が次の形になる。

   ```json
   {
     "subject": "concept:second",
     "page": "a/Foo.md"
   }
   ```

   `slug_to_id["Foo"]` が後者で上書きされ、エッジの主語もスラッグから引かれるためである。異なる `node_id` を付けても防げない。関係表を主語で振り分ければ、別ページに関係が表示される。

   根拠：設計 L39、`info-hive-wiki/skills/info-hive/scripts/wiki_graph_extract.py:241`（`build_nodes`、特に L275）、同 L308（`build_edges`、特に L330）。設計が通常リンクについて要求する `ambiguous` の扱いとも整合しない。

2. **重大：`ontology.yaml` の変更を検出できず、関係表と能力の宣言が古いままになる。〔確認済み〕**

   サーバー起動後、Markdown を変更せずに `graph/ontology.yaml` を追加・削除・変更する。設計の変更検出は `.md` しか見ないので、中核は作り直されない。

   例えば、起動時にオントロジーがなければ、追加しても `relations: false` のままになる。削除しても、以前の関係表が残る。`node_types` の対応を変えた場合も古いノード型が使われる。

   現行 `stat_signature()` に対し、Markdown の属性を固定してオントロジーのサイズ・時刻だけを変更した入力では、署名が同じになった。

   根拠：設計 L39・L72、`info-hive-wiki/skills/info-hive/scripts/wiki_index.py:814`。関係表が依存する入力と、再生成を判定する入力が一致していない。

3. **重大：`--out` の条件では、Wiki に生成物を書かないことを保証できない。〔設計上の欠落〕**

   Wiki 内に空の `preview/` を用意し、`build <WIKI_ROOT> --out <WIKI_ROOT>/preview` を実行する。設計 L63 の条件では許可され、Wiki 内に HTML、JavaScript、目印などが作られる。隣に置く生成記録も Wiki 内になる。

   また、出力先と Wiki の包含関係を検査する規則がなく、シンボリックリンクや Windows のジャンクションを解決した後の検査もない。「空か、目印がある」は出力ディレクトリの所有判定であり、Wiki の保護にはならない。

   根拠：設計 L49・L62〜64。ADR-0010 L164〜165 は既定先を Wiki 外にする理由を「Wiki に何も足さない」としている。L103 のハッシュ試験も、既存ファイルだけを比べれば新規生成を見逃す。

4. **重大：絶対パス検査は、PoC の方式では Windows の診断を検出できない。公開後の失敗処理も未定義。〔PoC で再現済み〕**

   `wiki_lint.collect_pages()` の `read_error` には `str(OSError)` が入る。Windows のファイル名は例外文字列内でバックスラッシュがエスケープされ、さらに JSON 化すると追加でエスケープされる。

   `C:\Users\Alice\Wiki\concepts\secret.md` を含む `FileNotFoundError` を診断 JSON に入れ、PoC の `scan_leaks()` に渡した結果は次のとおりだった。

   ```text
   絶対ファイル名を復元できる: true
   検出結果: []
   ```

   設計は診断への `read_error` の掲載と、書き出した後の検査を定めるが、例外・JSON・HTML・URL の表現をどう検査するかは定めていない。また、検出時に公開済みの出力を撤回する規則もない。PoC は世代を入れ替えた後に検査している。

   根拠：設計 L29・L42・L49、`wiki_lint.py:331`〜337、`poc/browse/gen.py:354`〜381・L385〜395。PoC は検出結果を記録するだけで、`main()` は L479 で成功を返す。設計の「失敗にする」だけでは、安全な出力だけが残る保証にならない。

5. **重大：そのまま移す出力名の規則に、Windows の予約名の取りこぼしがある。〔再現済み〕**

   PoC の `export_name()` に次を渡す。

   ```text
   concepts/COM¹ → concepts/COM¹.html
   concepts/LPT² → concepts/LPT².html
   ```

   Windows Python 3.14.6 の `ntpath.isreserved()` は、両方の出力ファイル名を予約名と判定した。PoC の予約名集合は ASCII の `COM1`〜`COM9`、`LPT1`〜`LPT9` だけである。

   Linux などで作成したこれらのページを Windows に持ち運べる静的版にする、という前提が崩れる。

   根拠：設計 L31 の「規則をそのまま移す」、`poc/browse/gen.py:39`・L81〜84。`names_check.py:43` の予約名試験にも、この入力はない。

6. **重大：世代の入れ替えと要求間の整合性は、保証を記述しただけで手順がない。〔設計上の欠落〕**

   PoC の切り替えは次の順である。

   ```text
   final → old
   temporary → final
   old を削除
   ```

   最初の rename 後に停止すれば、正式な出力先が消える。Windows で二つ目の rename が失敗した場合も、復元処理がない。並行する `build` を排他する処理もない。

   サーバー側も、再構築中の要求、構築失敗、読み取り途中の編集をどう扱うかが未定義である。HTML の取得後、`nav.js` の取得前に更新が起きる場合の世代固定もない。さらに世代ハッシュは識別子と本文だけなので、メタ欄・索引・オントロジーを変更しても世代が変わらない。

   根拠：設計 L58・L64・L71〜72、`poc/browse/gen.py:276`〜277・L354〜361。ADR-0010 L61 の「新しい世代を作り終えてから切り替え、途中の生成物を見せない」を満たす手順としては未完成。将来の実装が必ず PoC の方式になるとは断定しないが、計画段階で未決のままである。

7. **重大：合格条件に必要な試験が欠け、移植予定のブラウザ試験も安全性を合否にしていない。〔確認済み〕**

   設計 L106 が指定する比較は `file://` とサーバーだけで、ADR-0010 L81 の **3 方式**の確認を満たさない。アプリを製品として作らないことと、試験用アダプタによる契約の確認を省くことは別である。

   また、`test.mjs` は外部要求と CSP 違反を記録するが、それを失敗条件にしていない。`allEqual` の比較対象にも含めず、最後に明示的な失敗終了をしない。外部要求が発生していても、比較した画面結果が同じなら `allEqual: true` になり得る。

   起動性能も、要求された「コマンド実行から最初の表示まで」を「`serve` 起動から最初の応答まで」に縮めている。`uv` の準備、ブラウザ起動、スクリプト読み込み・描画を除外できてしまう。

   根拠：設計 L103〜107、ADR-0010 L81〜83、選択肢レポート L559〜563、`poc/browse/test.mjs:109`〜126・L165〜172。

## 崩れる前提

- **「スラッグからグラフノードを一意に引ける」**  
  別ディレクトリに同名ページがあれば崩れる。通常のリンクでは曖昧として扱う入力を、関係表では一方に寄せてしまう。

- **「Markdown の属性が同じなら、表示の入力も同じ」**  
  オントロジーだけの変更で崩れる。同じサイズ・更新時刻を維持した本文変更も検出できない。

- **「生成器の目印があれば、その場所を置き換えてよい」**  
  Wiki 内の出力先、リンク経由の出力先、出力先に後から保存された資料で崩れる。包含関係と所有範囲が未定義である。

- **「全ページを二度読んでも同じ内容になる」**  
  lint 用の収集とグラフ用の収集の間で編集されると崩れる。本文と関係表が別の時点の内容になる。

- **「同じ描画関数なら同じ HTML になる」**  
  サーバーは `raw` を文字列、既定の静的版はリンクとして出すため、同じページでも既定値では一致しない。試験で一致を要求する設定範囲が定まっていない。

- **「ページ一覧への限定だけで、入力ファイルも Wiki 内に閉じる」**  
  `wiki_pages.iter_page_files()` はファイルのシンボリックリンクを排除せず、収集側はその内容を読む。Wiki 外を指す `.md` の扱いは未決定。これだけで認証突破が起きるとは確認していない。

## 見落としと軽微な問題

- **軽微：ナビゲーションの説明と採用関数が一致しない。**  
  `collect_index_entries()` は任意の見出しを読まず、種類として認識した見出しだけを読む。`## 概覧` の下に `- [[concepts/Foo]]` を置くと、実行結果は空だった。ページは「そのほか」に落ち、元のグループが失われる。分割索引でも、ファイル名や見出しが種類を表さなければ落ちる。根拠：設計 L40、`wiki_lint.py:135`〜183。

- **軽微：「使えない」「古い」「0 件」の区別がない。**  
  オントロジーがない場合と読めない場合を、どちらも `relations: false` にする。ADR-0010 L63 の状態区別を満たさない。根拠：設計 L39。

- **軽微：明示的な停止手段が落ちている。**  
  選択肢レポート第6.8節 L517 の `/wiki:browse --stop` が設計にない。複数回起動した場合の識別・再利用・停止対象も未定義である。

- **軽微：暗黙の関係が被リンクと重なるという説明は成立しない。**  
  本文にリンクがなく、`sources:` にだけ参照がある場合、`sourced_from` は本文の被リンクに現れない。`summarizes_raw` も通常のページ間リンクとは異なる。根拠：設計 L38〜39、`wiki_graph_extract.py:384`〜415。

- **軽微：コマンド本数が既に古い。**  
  現行 `commands/` は 10 本で、マーケットプレイスも「10 本」と記載済み。browse 追加後は 11 本になる。設計 L80 の「9 本から10 本」は誤り。
