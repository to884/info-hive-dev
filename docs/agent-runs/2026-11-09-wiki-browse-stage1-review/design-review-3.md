**却下。確信度：高。** ADR の合格条件を満たしておらず、現行のグラフ関数を使った反例でも、関係の欠落と誤った主語を確認した。停止処理と復旧処理にも、安全性を保証できない競合や未定義の状態が残る。

## 致命的・重大な欠陥

### 1. 【重大】ADR-0010 の合格条件を、未承認の解釈で縮めている

**主張：** 2 方式の動作確認では、依頼された「ADR-0010 の合格条件を満たす」という目的に到達しない。

**反例：** サーバーと静的 HTML の全試験が成功しても、子プロセス経由の実装をアプリの独自スキームで開いた場合の、リンク、CSP、被リンク、診断は未検証のままである。「アプリの技術は今は決めない」は、3 方式の受け入れ試験を免除する決定ではない。

**根拠：** 計画 L138 は、3 方式の確認を 2 方式に縮め、作者への確認を PR に先送りしている。`docs/adr/0010-wiki-browse-separates-core-from-delivery.md` L79–83 は、3 方式を実際に動かす確認を要求している。同 ADR L192 の技術選定の保留とは別の条件である。**結果：食い違い。**

### 2. 【重大】重複スラッグのページを非表示にしても、通常ページの関係表に汚染が残る

**主張：** 重複ページ自身の関係表を隠す規則では、別ページの「入ってくる関係」を保護できない。

**反例：** 次の 3 ページを、現行の `build_nodes()` と `build_edges()` に渡した。

- `concepts/x.md`：`node_id: concept:x`、関係 `uses → concept:y`
- `entities/x.md`：`node_id: person:x`
- `concepts/y.md`：`node_id: concept:y`

実際のエッジは、`subject: person:x`、`object: concept:y`、`page: concepts/x.md` になった。関係を書いていない人物が主語になる。目的語 `concept:y` は一意なので、計画の入ってくる関係の条件を通る。

また、両方の `x.md` に同一の関係を書く反例では、エッジが 1 本に潰れ、片方の `page` が失われた。

**根拠：** 計画 L48–51。`info-hive-wiki/skills/info-hive/scripts/wiki_graph_extract.py` L241–279 のスラッグ索引、L282–288 のページを含まないエッジ ID、L322–330 の重複排除と主語決定。**結果：現行関数で再現。** 入ってくる関係について、曖昧な起点を除外する規則は計画にない。

### 3. 【重大】lint が解決できる `sources:` から、関係が作られない

**主張：** 「`sources:` の関係を表に出す」という仕様を、採用予定の関数では満たせない入力がある。

**反例：**

```yaml
# concepts/a.md
type: "concept"
sources: ["sources/paper"]
```

`type: "source"` の `sources/paper.md` を用意したページデータで確認したところ、lint の `unresolved_sources` は `[]`、グラフのエッジも `[]` だった。参照が正常でも `sourced_from` が消える。

**根拠：** 計画 L48、L52、L60。`wiki_lint.py` L547–557 は `resolve_link()` でパス付き参照を解決する。一方、`wiki_graph_extract.py` L384–399 は `slug_to_id.get(str(src_slug))` で直接引くため、`sources/paper` とスラッグ `paper` が一致しない。**結果：現行関数で再現。**

### 4. 【重大】Wiki 外のページを browse だけで除外すると、lint とリンク判定が一致しない

**主張：** 安全のための除外規則と、現行 lint との一致条件が両立していない。

**反例：** `concepts/external.md` を、Wiki 外の読める Markdown ファイルへのシンボリックリンクにし、通常ページに `[[external]]` を書く。

現行の `iter_page_files()` はリンク先がファイルなら収集し、lint はその内容を読むため、リンクを解決する。計画の browse は `outside_wiki` としてページを除外する。browse が未解決にすれば lint と不一致になり、解決済みにすれば開ける出力ページがない。

**根拠：** 計画 L34、L130、L134。`wiki_pages.py` L49–58、`wiki_lint.py` L319–346、L428、L449–464。**結果：コード上の食い違いを確認。実ファイルによる再現は未実施。**

### 5. 【重大】`stop` のロック確認は、PID の再利用による誤終了を防がない

**主張：** ロック取得失敗と `os.kill()` は一体の操作ではなく、その間に対象プロセスが変わりうる。

**再現手順：**

1. `stop` が、サーバー A のロックを取得できず、記録の PID を読む。
2. A が終了し、OS がロックを解放する。
3. 同じ PID が別プロセスに再利用される。
4. `stop` が、保存していた PID に `os.kill()` を実行する。

ロック確認時には A が存在していても、終了要求時の PID が A を指す保証はない。2 つの `stop` の並行実行でも、この窓は生じる。

**根拠：** 計画 L111 は、この手順で PID 再利用を防げると説明している。ところが、ロックの保持者と記録の PID を結び付ける操作は定義されていない。**結果：設計上の競合。実プロセスの誤終了試験は未実施。**

### 6. 【重大】サーバー状態の実体が Wiki 内にある場合を、明記された検査では排除できない

**主張：** `data_dir` が Wiki 外でも、その下の状態ディレクトリが Wiki 外とは限らない。

**反例：** `INFO_HIVE_DATA_DIR=C:/Cache/info-hive` とし、`C:/Cache/info-hive/browse/<wiki_key>.server/` を Wiki へのジャンクションにする。

`data_dir` 自体の比較は通るが、`server.lock` と `server.json` の作成先は Wiki 内になる。閲覧操作が正本にファイルを追加する。

**根拠：** 計画 L108–110。第 8 節の具体的な検査対象は `data_dir` であり、第 7 節 L90 のような、実際の書き込み先を `Path.resolve()` して検査する規定がない。L136 のサーバー試験にも、この状態パスの反例は挙がっていない。**結果：設計の検査対象に穴。ジャンクションによる実行再現は未実施。**

### 7. 【重大】複数の `old-*` が残った場合、戻す世代が決まらない

**主張：** Windows で削除に失敗した退避世代が蓄積すると、停止後の復旧先を一意に決められない。

**再現手順：**

1. 書き出しは成功するが、旧世代の削除に失敗し、`old-100` が残る。
2. 次の書き出しでも削除に失敗し、`old-200` が残る。
3. さらに次の入れ替えで、出力先を `old-300` に移した直後に停止する。
4. 次回起動すると、出力先がなく、`old-*` が 3 個ある。

手順 1 は「その `old-*` を戻す」としか定めていない。最新の成功世代を選ぶ根拠がない。また、手順 5 は「次の 1 で消す」とするが、手順 1 に既存の `old-*` を消す処理は書かれていない。

**根拠：** 計画 L93–98 の入れ替え手順。**結果：復旧手順が未定義。** この状態から後続の生成も失敗した場合、保持される「前の世代」が、直前の成功世代である保証がない。

## 崩れる前提

- **「スラッグが一意なら、ノードとページの対応も一意」**  
  異なるスラッグに同じ `graph.node_id` を指定すると崩れる。現行 `build_nodes()` は後のノードを捨て、そのページの関係も消える。重複スラッグだけの検査では捕捉できない。

- **「親ディレクトリが Wiki 外なら、その下への書き込みも Wiki 外」**  
  子ディレクトリのジャンクションやシンボリックリンクで崩れる。

- **「ロックが取れなかったので、記録の PID は今もサーバーである」**  
  ロック確認後の終了、再起動、PID 再利用で崩れる。

- **「混ざったスナップショットは次の要求で直る」**  
  **推測：** 再構築前後のどの時点の変更印を保存するかが未定義である。読み取り後に編集されたファイルの新しい stat 値を保存すると、古い内容に新しい印を対応付け、次回の再構築を省略しうる。再構築を複数起動できる実装なら、古い処理が最後に完了して新しい世代を戻す競合も残る。

## 見落としと軽微な問題

- **【軽微】ナビゲーションの先頭項目の所属が未定義。**  
  計画 L55 の「直前の見出し」は、`index.md` が `- [[a]]` から始まる場合には存在しない。また、「最初の wikilink（解決したもの）」が、最初のリンクの解決成功を要求するのか、最初に解決できるリンクを探すのか不明。`- [[missing]] — 関連：[[a]]` で結果が変わる。

- **【軽微】入力の境界規則がページに限定されている。**  
  L34 は「ページ」を Wiki 外から読まないとするが、L54 では索引をページとして扱わない。外部 Markdown を指す `index.md` や、外部 YAML を指す `graph/ontology.yaml` に同じ検査を適用するか不明である。索引の見出しはナビゲーションに出るため、外部ファイルの内容が生成物に混入しうる。

- **【軽微】生成記録の置き場所が矛盾している。**  
  L74 は `<出力先>.build-report.json`、L89 は生成記録もすべて `<出力先>.browse-work/` 内とする。加えて L162 は、修正後の L138 と異なり、子プロセスを含む「3 方式の一致」を対処として掲げたままである。

- **【軽微】通常の Markdown 外部リンクの扱いがない。**  
  同梱 parser は `[outside](https://example.invalid/?q=wiki-content)` を外部の `<a href>` に変換することを確認した。`raw: url` を文字にする規則だけでは本文の外部リンクを扱えない。CSP によるリソース取得制限と、リンククリック時の外部遷移は別である。ブラウザでの遷移試験は未実施。

- **【軽微】試験の列挙から抜けている条件がある。**  
  JavaScript 無効時の閲覧、上記の停止競合、複数退避世代からの復旧、外部リンクをクリックする操作がない。日本語 CSS についても、選択肢レポート L556–558 の全コーパス表示と禁則・はみ出しの合格条件が、計画の試験に明記されていない。
