## 判定

**却下。確信度：中。** 入れ替え直前の再検査を追加しても、稼働中のロックが移動し、別の build の一時ファイルを削除する競合が残る。以下は設計上の反例であり、完成実装での再現ではない。

## 致命的・重大な欠陥

### 1. 【重大】移動されたロックの元の場所を再利用でき、別の build の生成物を掃除できる

**主張：** §7 の「残る競合でも、ほかの書き出しのファイルは消さない」という保証は成立しない。削除前の目印検査は、移動されたロックと、現在そのパスにある作業場所の同一性を確認しない。

**反例：** Linux で、Wiki と無関係な空ディレクトリ `/exports/site/` を用意する。同じ Wiki を読む三つの build を、次の順序で進める。

1. A は `/exports/site` を出力先にし、入れ替え直前の検査を通る。この時点では空なので許可される。
2. A の検査直後に、B が `/exports/site/nested` への build を開始する。祖先に目印はなく、B は `nested.browse-work/build.lock` を取得する。掃除の手順に入る前で待機する。
3. A が `site` を自身の `old-*` に移す。B の作業場所と、保持中のロックも一緒に移る。
4. A が新世代を `site` に置く前に、C が B と同じ出力先への build を開始する。元の `site` は存在しないため、C は作業場所を新設し、**別のロックファイル**を取得できる。
5. C が、目印 `.browse-generation` のある `tmp-1` を作る。
6. B が再開し、§123 のとおり元のパスを解き直して掃除する。そのパスは今や C の作業場所である。C の `tmp-1` は §116 の削除条件を満たすため、B が削除できる。

同じ Wiki の新規作業場所なら、世代ハッシュと `published_seq` も同じ値になり得る。目印の内容からも B と C を区別できない。C の一時ディレクトリ内に別の作業場所の目印がなければ、§121 の追加検査も通る。

**検証範囲：** パスの移動とロックの所有者を表すメモリ上のモデルで、B が保持するロックと元のパスの現在のロックが異なり、B の掃除候補が C 所有になることを確認した。実プロセスでの競合・削除は未実施。

**根拠：**

- [設計 §7・排他と掃除](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:112)：出力先ごとのロックと、残った `tmp-*` の削除。
- [設計 §7・再検査](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:121)：検査後の競合を認めながら、他の build のファイルは消さないとする。
- [設計 §7・書き込み直前の検査](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:123)：現在のパスを解き直すが、保持するロックとの同一性は確認しない。
- [現行 `extract_lock` の注意書き](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_graph_common.py:165)：ロックファイルの削除・再作成によって二重取得が成立することを明記している。
- [設計の同時実行試験](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:174)：子の作業場所を作ってから親が検査する順序だけで、上記の順序を含まない。

## 崩れる前提

- **「自分の作業場所のパスは、保持中のロックが保護する場所であり続ける」**  
  祖先の入れ替え後、別の build が元のパスを再作成すると崩れる。

- **「目印のある残存 `tmp-*` は、停止した実行の生成物である」**  
  ロックが移動すると、同じパスに別の実行が作った、稼働中の `tmp-*` が現れる。

- **「markdown-it の `text` と `code_inline` を連結すれば、見出しの表示文字になる」**  
  wikilink の別名や、代替テキストだけに変換する画像を見出しに含めると崩れる。

## 見落としと軽微な問題

### 【軽微】別名付き wikilink を含む見出しでは、表示文字によるアンカー照合が失敗する

`a.md` に次を書く。`other.md` は存在するものとする。

```markdown
## [[other|Definition]]
```

画面の見出しは `Definition` になる。一方、設計 §3 の指定どおり `inline` の子の `text` を連結すると、入力は `[[other|Definition]]` のままであり、見出し ID は `otherdefinition` になる。`[[a#Definition]]` 側の ID は `definition` なので一致しない。

同梱 markdown-it-py 3.0.0 のトークンと、PoC から抽出した描画関数をメモリ上で実行し、次の HTML を確認した。

```html
<h2 id="otherdefinition"><a href="other.html">Definition</a></h2>
```

`## ![Definition](diagram.png)` でも、指定された子トークンの連結結果は空になる。画像を代替テキストにする表示規則とは一致しない。

根拠：[設計の見出し規則](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:46)、[画像の表示規則](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:98)、[PoC の wikilink 置換](C:/Works/info-hive-dev/poc/browse/gen.py:243)。§11 の `**Definition**` の試験では、この反例を検出しない。

## 崩せなかった点

- ADR-0016 による2方式の合格条件自体は、今回の否定理由にしていない。
- 127.0.0.1 固定、厳密な Host 照合、起動ごとのトークンを破る DNS rebinding の反例は示せなかった。
- デコード後の禁止要素検査と、既知の出力名だけを返す規則から、任意ファイル取得の経路は示せなかった。
- 読み取り前の変更印、組み立ての直列化、要求ごとの写しの固定について、以前の世代逆転の反例は適用できなかった。
- 指定された抽出契約を満たす前提では、関係表の振り分けを崩せなかった。
- PID による誤終了、識別子衝突の黙った上書き、外部入力の実体を保護しない削除については、過去の反例を適用できなかった。
