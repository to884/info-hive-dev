前回指摘の H→G→H と失敗ジョブによる設定変更の行き止まりは、メモリ上の検証では再現しませんでした。登録時と異なる識別子のファイルは、本文を読む前に拒否されることも確認できています。残った欠陥と試験で未確認の範囲を整理します。
## 判定

**却下。確信度：高。** 残っている旧版の索引を誤って削除する反例と、受理したネットワークドライブの登録がワーカーで必ず拒まれる経路がある。UNC の解決前拒否にも入力表記による抜け道が残る。

## 致命的・重大な欠陥

1. **重大：過去にハードリンクだった場所を無条件で移し、実在する旧版の索引を削除する。**

   再現手順：

   1. A と B を同じファイルのハードリンクとし、内容 H で両方を取り込む。
   2. A を、H を保持する独立したファイルで置き換える。コピーして `os.replace()` する操作で成立する。
   3. B を内容 G に書き換え、B を取り込む。

   台帳の A には、置き換え前の識別子が残る。実装はその記録だけで A を B の別名に含め、**現在の A の識別子を確認せず、A→G に更新する**。H の場所の行がなくなるため、H の文書、チェックポイント、索引行も削除する。実際の A には H が残っている。

   実際の `Engine.ingest_pdf()`、メモリ上の SQLite、代替したファイル情報・索引で、A/B がともに G に更新され、H の文書と索引行が消えることを再現した。実ファイルを使った再現は未実施。

   根拠：[別名を選ぶ SQL](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_index.py:263)、[別名を無条件で更新](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_index.py:325)、[旧版の削除](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_index.py:336)。ADR の「ほかの場所に古い版が残っていれば、古い版の文書は残す」と食い違う。

2. **重大：ネットワークドライブが UNC に解決されると、受付後のワーカーで拒否される。**

   再現条件は、`Z:/book.pdf` が `\\server\share\book.pdf` に解決されること。

   - `Config.pdf_path()` は、元の Z: がネットワークドライブなら、この解決結果を受理する。
   - `Jobs.register()` は、その **UNC の解決結果**を `source` に保存する。
   - ワーカーは保存した `source` を `Engine.ingest_pdf()` に渡す。
   - `ingest_pdf()` は再び `Config.pdf_path()` を呼ぶため、今度は先頭の UNC 拒否に入り、失敗する。

   実際の `Config.pdf_path()` に解決結果とドライブ判定を代替して、Z: の入力は受理され、その返り値の再入力は拒否されることを確認した。実ネットワークドライブへの接続は未実施。

   根拠：[解決結果を受理・返却](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_config.py:156)、[解決後のパスを保存](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_jobs.py:82)、[ワーカーから再投入](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_worker.py:155)、[再度のパス検証](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_index.py:243)。ADR の「ドライブ文字を割り当てたネットワークドライブは受け付ける」と食い違う。

3. **重大：区切り文字を混在させた UNC 入力は、解決前の拒否をすり抜ける。**

   Windows で次の文字列を渡す。

   ```text
   /\unknown-server/share/book.pdf
   \/unknown-server/share/book.pdf
   ```

   どちらも現在の `startswith("\\\\")` と `startswith("//")` に一致しない。しかし Windows の `Path` は、どちらも `\\unknown-server\share\book.pdf` という絶対 UNC パスとして扱う。そのため `resolve(strict=True)` が実行される。

   実際の `Config.pdf_path()` で、両入力とも解決処理まで到達し、その時点のパスが UNC になっていることを確認した。**最終的に拒否されても、解決前に外部接続を防ぐという保証は成立しない。** ローカルにリンクを設置する権限も不要である。実サーバーへの接続と認証情報の送信は検証していない。

   根拠：[文字列による拒否と、その後の解決](C:/Works/info-hive-dev/info-hive-rag/scripts/rag_config.py:144)、[ADR の解決前拒否](C:/Works/info-hive-dev/docs/adr/0013-rag-records-pdfs-by-absolute-path-and-hash.md:35)。

| 暗黙の前提 | 崩れる条件と結果 |
| --- | --- |

## 見落としと軽微な問題

- **軽微：試験は、ネットワークドライブの受付からワーカー実行までを通していない。**

- **軽微：「差し替えたファイルを読まない」という試験は、読まなかったことを検査していない。**  
  [test_jobs.py:339](C:/Works/info-hive-dev/tests/rag/test_jobs.py:339) が確認するのは例外だけである。本文を読んだ後に同じ例外を投げる誤実装でも通る。また、親フォルダーの差し替えと実ワーカーの経路は通していない。現在の実装については、別途ハンドルを代替し、識別子不一致時の `read()` が0回であることを確認した。

- **軽微：同一サイズ・更新時刻での内容変更という説明に対し、試験は内容を変更していない。**  
  [test_jobs.py:240](C:/Works/info-hive-dev/tests/rag/test_jobs.py:240) は新しいジョブ ID の生成を検査するが、PDF の差し替え、新しい SHA-256、索引の更新までは検査しない。

- **軽微：環境依存の重要試験は、未実行でも成功終了できる。**  
  NFC/NFD、ハードリンク、識別子による差し替え検出には `skipTest()` がある。ハードリンク試験はあらゆる `OSError` をスキップにする。Windows のリンク試験は他 OS では実行されない。スキップは unittest の出力には現れるが、「失敗なし」という要約だけでは実行済みと判断できない。今回報告された28件にスキップが含まれていたかは、確かめられず。

## 検証した事実

| 前回指摘 | 結果 |
