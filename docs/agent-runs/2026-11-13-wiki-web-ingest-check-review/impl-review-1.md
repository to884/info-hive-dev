## 判定

**却下。確信度：高。** コードやリンク先を変更した raw が検査を通る一方、取得器が実際に出す Markdown に正しく補足した raw が拒否される。設計２版が保証するとした条件に、複数の食い違いがある。

## 致命的・重大な欠陥

以下の反例は、ファイル入出力だけをメモリに置き換え、実装の `freeze`・`check` を実行して確認した。共通の題名と frontmatter は一部省略している。訳の検査では `needs_translation: true` とし、`translated_by` を設定した。

### 1. 【重大】リスト内のコードブロックを認識せず、コード変更が両段階を通る

取得器は `<ul><li>item<pre>SELECT 1; -- rationale</pre></li></ul>` から次を出す。

````markdown
- item
  ```
  SELECT 1; -- rationale
  ```
````

コメントを削って `SELECT 1;` にしても、**`freeze` は終了コード０**。変更前を `cleaned.md` にした `check` も、**終了コード０・警告なし**だった。

`CONTAINER_RE` は、リスト記号や引用記号を伴わない字下げを取り込まない。そのため `  ``` ` をフェンスと認識せず、コード全体を通常の文章として扱う。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の48行、186〜207行。取得側は `wiki_fetch.py` の856〜877行。

### 2. 【重大】認識できたコードでも、コード自身の文字を接頭辞として捨てて比較する

次のコードの `- 1` を `1` に変更しても、**`check` は終了コード０・警告なし**だった。

````markdown
```
- 1
```
````

`block_code()` はコードの各行にも `container_prefix()` を適用する。コード本文の `- ` がリスト記号として除去され、変更前後が同じ文字列になる。引用内のコードでも、`> - dangerous` → `> dangerous` が通った。

これはコードの意味が変わる変更であり、設計の「コードブロックの中身を変えない」と食い違う。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の408〜414行、556〜557行。

### 3. 【重大】エスケープされた `]` を含むリンクは、URL の部分削除が `freeze` を通る

取得器は `<a href="safe">a]b</a>` を、正しく次のように出す。

```markdown
Read [a\]b](https://x.example/safe).
```

これを次に変更しても、**`freeze` は終了コード０・警告なし**だった。

```markdown
Read [a\]b](https://x.example/).
```

`ATOM_RE` はエスケープされた閉じ括弧を扱えず、このリンクを保護対象のかたまりとして認識しない。その結果、リンク先の変更を単なる文字削除として許し、変更済みの URL が `cleaned.md` に固定される。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の131〜165行、213〜222行。取得側は `wiki_fetch.py` の758行。

### 4. 【重大】`difflib` の固定した対応づけが、正当な削除を並べ替えと誤判定する

取得時：

```markdown
# A

a

b

Share a
```

削除後：

```markdown
# A

b

a
```

操作は、最初の段落 `a` の削除と、最後の段落の `Share ` の削除だけである。残る段落の順序は変えていない。しかし **`freeze` は終了コード１**となり、残した `b` を「取得した内容にない行か、並びの変わった行」とした。

`SequenceMatcher` が出力末尾の `a` を入力先頭の `a` に対応づけ、その外側では対応を探さない。設計の許す行対応が存在しても拒否する。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の245〜269行。

### 5. 【重大】リストの継続行にある画像へ、正しい字下げで補足すると拒否する

取得器は `<ul><li>item<img src="i.png"></li></ul>` から次の形を出す。

```markdown
- item
  ![x](assets/a/1.png)
```

画像ファイルを置き、指示どおり同じリスト項目内に補足した。

```markdown
- item
  ![x](assets/a/1.png)

  > Model 補足: 図の説明。
```

結果は **`check` の終了コード１**。「画像の補足がない」と「ブロックの数が違う」が出る。

画像行の字下げが `container_prefix()` で失われ、補足に字下げのない `> ` を要求する。試験の成功例は画像が `- item two ![...]` と同じ行にあり、この形を確かめていない。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の48行、118〜121行、337〜342行。取得側は `wiki_fetch.py` の856〜877行。

### 6. 【重大】alt にエスケープされた `]` があると、無編集の raw が `freeze` を通らない

HTML の `alt="a]b"` は、取得器で次になる。

```markdown
![a\]b](assets/a/1.png)
```

画像ファイルも `fetch.json` の対応項目もある状態で、**一文字も編集せずに `freeze` すると終了コード１**。「画像の行を消したのに、ファイルが残っている」となる。

`IMAGE_RE` がこの画像を認識せず、参照数を０と判定する。正しい補足を付けた `check` でも補足が取り除かれず、ブロック数の不一致になる。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の128〜138行、294〜307行。取得側は `wiki_fetch.py` の1102〜1103行。

### 7. 【重大】ブロック先頭の種類と項目数だけでは、内部の構造変更を止められない

次はいずれも **`check` の終了コード０・警告なし**だった。

- `- Parent\n  - Child` → `- Parent\n- Child`：子項目を親と同じ階層に移動。
- `> First\n> Second` → `> First\nSecond`：２行目の引用記号を削除。
- 表の区切り行 `|---|---|` → `| あ | い |`：表を成立させる区切り行を消失させる。

`block_kind()` が見るのは先頭行だけで、リストは項目の総数、表はパイプの数を比較する。設計が検査対象とした字下げ・引用の深さ・表の形を、内部の各行では保証していない。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の390〜405行、426〜438行、553〜567行。

### 8. 【重大】補足の取り除き方が、複数の補足とコード内の画像記法を誤認する

二つの反例を確認した。

**複数の補足のすり抜け：**

```markdown
![x](assets/a/1.png)

> Model 補足: 説明１。
> Other 補足: 説明２。
```

**終了コード０・警告なし**。２行目の補足開始を最初の補足の本文に吸収し、補足数を１、表示名を `Model` だけと判定する。「補足が２つ以上」「表示名が不一致」の両方を見逃す。

**正しいコードの誤拒否：**

フェンス内に `![x](assets/a/1.png)` というコード例があり、フェンス外に同じパスの実画像があるページで、実画像だけに正しい補足を書くと、コード例にも補足を要求して終了コード１になる。

`strip_captions()` はコード内かどうかを判定していない。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の325〜354行、517〜535行。

### 9. 【重大】取得済み画像を翻訳段階で削除すると、補足なしでも通る

次の手順を確認した。

1. 画像ファイルと `fetch.json` の `images[].path` がある状態で `freeze` を成功させる。
2. 画像ファイルだけを削除する。
3. 画像記法は残し、補足を書かずに `check` する。

結果は **終了コード０・警告なし**だった。

`check` はファイルがないことを「取得できなかった画像」と扱う。取得時には保存できていたという `fetch.json` の情報を使わず、ファイル欠落と補足欠落を同時に見逃す。

根拠：`info-hive-wiki/skills/info-hive/scripts/wiki_rawcheck.py` の514〜526行。`images` の辞書は作られるが、この判定に使われていない。

## 崩れる前提

- **入れ物の接頭辞は各行から独立して判定できる。** リスト継続行の空白だけの字下げと、コード本文に含まれる `- `・`> ` で崩れる。
- **完全一致した行を先に固定しても、正当な削除の対応は残る。** 同じ短い文字列が別の段落や削除後の行に現れると崩れる。
- **正規表現が取得器の出すリンク・画像をすべて認識する。** ラベルや alt にエスケープされた `]` があると崩れる。
- **先頭行の種類と総数が一致すれば、ブロック内部の構造も保たれる。** 入れ子の平坦化、途中行の引用解除、表の区切り行の変更で崩れる。
- **今ファイルがない画像は、取得時にも取得できなかった画像である。** `freeze` 後の削除・欠落で崩れる。
- **作業フォルダーが存在すれば、再開に必要な写しもそろっている。** `fetch.json` の書き込み失敗で崩れる。

## 見落としと軽微な問題

- **【軽微】不完全な作業フォルダーを再開可能と報告する。** 既存 raw がある状態で `--force` を実行し、`fetched.md` 成功後の `fetch.json` 書き込みを失敗させた。raw は書かれないが、再取得は `unchanged: true, work_dir: true` を返す。コマンドはこの状態を手順４から再開させるが、`freeze` に必要なファイルがない。根拠：`wiki_fetch.py` の1207〜1213行、1362〜1367行、`commands/ingest.md` の31行。

- **【軽微】雑音規則は、短い本文中の参考リンクも消す。** `<p>Short introduction.</p><p><a href="/tag/spec">Tag specification</a></p><p>Top highlight</p>` は最初の段落だけになる。80文字以上の段落がなければ、本文全体を「本文の前」と扱うためである。これは**設計に明記された限界と一致**するが、試験は長い先頭段落を置いた対照しか確かめていない。根拠：`wiki_fetch.py` の378〜400行、`tests/wiki/test_wiki_web_check.py` の102〜109行。

- **【軽微】削除した元文字列の記録が300文字で切れる。** 長いラベルのタグリンクを削除すると、`removed_by_rule.text` には先頭300文字しか残らない。MediaWiki の削除記録も同様である。根拠：`wiki_fetch.py` の348行、402行。

- **【軽微】固有名詞の警告に、設計より広い除外がある。** `## City of Greenwich` → `## グリニッジの町` は警告なし。見出し・表では通常の大文字始まりの語を一律に除外するためである。根拠：`wiki_rawcheck.py` の469行、581〜585行。

- **【軽微】試験の名前やケース名だけでは、保証した機能を確認できない。** `test_raw_is_not_written_when_snapshot_fails` はパスを返す `work_dir()` 自体を失敗させており、写しの途中書き込み失敗を試していない。`test_snapshot_matches_raw_and_records_language` は最終内容の一致を確認するが、書き込み順序は確認しない。`test_errors` はエラー種別を照合せず、いずれかの理由で失敗すれば通る。入れ子コード、画像の継続行、エスケープされた括弧、連続する補足開始行の対照もない。根拠：`tests/wiki/test_wiki_web_check.py` の167〜192行、392〜415行。

## 検証した事実

- 指定された実装、差分、試験、設計２版、設計レビュー、取り込みコマンドとワークフローを読んだ。
- **食い違い：** 上記のコード・リンク保護、入れ物の形、画像・補足の判定は、設計の停止条件を満たさない。
- **一致：** 写しの書き込みが失敗した場合、raw の書き込み処理には到達しない。`fetch.json` の書き込み失敗を注入して確認した。
- **一致：** リスト継続行の画像・コード、エスケープされたリンクラベルと alt は、取得器自身が生成する形である。
- **確かめられず：** 既存試験全体の成功。`python -B -X utf8 -m unittest tests/wiki/test_wiki_web_check.py tests/wiki/test_wiki_fetch.py` は44試験中37試験が、読み取り専用環境で一時ディレクトリを作れずエラーになった。これは実装の試験失敗とは数えていない。
- リポジトリのファイルは変更していない。追加の反例はメモリ上で実行し、実際の再帰削除は行っていない。

## 崩せなかった点

- 通常のリンクの URL 部分削除は `freeze` が拒否し、翻訳段階での通常のリンク欠落も `check` が拒否した。
- 通常のインラインコード変更は `check` が拒否した。
- ４文字のフェンス内に３文字のバッククォートがあるコードは、無変更なら通り、本文を変更すると拒否された。
- `\|` を含む表で、エスケープを保ったセルの訳は通った。
- １行の離れた２か所の雑音削除は `freeze` を通った。
- UTF-8 の復号は、残存する `windows-1252` の meta 指定より優先された。
- 末尾ピリオド、`CON`、`COM1.txt`、`LPT¹` は取得器のスラッグ検査で拒否された。
- 有効なスラッグで作業パスの各段がリンクと判定された場合、再帰削除には進まなかった。ただし実ジャンクションを作る試験は実行できていない。
