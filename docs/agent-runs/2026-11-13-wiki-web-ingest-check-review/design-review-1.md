## 致命的・重大な欠陥

### 1. 【重大】`freeze` は本文・コード・リンクの削除を正当化してしまう

**反例：** 取得したコードが次の場合、コメント部分の削除は「1 行の中の 1 か所の続いた文字列の削除」なので許される。

```sql
SELECT 1; -- rationale
```

これを `SELECT 1;` にして `freeze` すると、変更済みのコードが `cleaned.md` の基準になる。その後の `check` はコメントが消えたコードとの一致を調べるため、原本の変更を検出しない。本文リンクだけの行や図の説明文の段落を丸ごと削った場合も同じである。

削除対象が雑音であることを確かめる条件はなく、削除内容の出力・記録も合否条件ではない。「削除と訳を分ければ、どちらも厳密に検査できる」という主張とは食い違う。

**根拠：** 計画15〜18、49〜54、68〜70行。現行の [ingest.md](C:/Works/info-hive-dev/.claude/worktrees/web-ingest-check/info-hive-wiki/commands/ingest.md:35) は本文の削除を禁止している。比較で起きた説明文やリンクの欠落も、削除段階で起きれば基準に取り込まれる。

### 2. 【重大】インラインコードと識別子の変更を止める条件がない

**反例：**

```markdown
Call `safe_mode(false)` only for tests.
```

取得器はこの形を実際に出力する。訳文を次にしても、段落数・種類・URL・画像・表・リストの条件はすべて一致する。

```markdown
試験時だけ `safe_mode(true)` を呼ぶ。
```

コード**ブロック**は存在しない。`true` の追加が英字の警告になる可能性はあるが、警告では停止しない。識別子保存という現行規則を機械的に保証する検査にはなっていない。

**根拠：** 取得器538〜543、638〜640行。計画68、79行。[ingest-workflow.md](C:/Works/info-hive-dev/.claude/worktrees/web-ingest-check/info-hive-wiki/skills/info-hive/references/ingest-workflow.md:95) は識別子の変更を明示的に禁止している。

### 3. 【重大】正しい雑音の削除でも、許された編集だけでは到達できない

二つの独立した反例がある。

- `<p>Alpha <span>Share</span> beta <span>Tweet</span> gamma</p>` は、取得器で **`Alpha Share beta Tweet gamma` という1行**になる。本文を保って `Alpha beta gamma` にするには、離れた2か所の削除が必要である。1か所の連続削除では不可能で、行全体の削除は本文まで失う。
- 著者紹介欄が `<h2>About the author</h2><p>Writer bio</p>` なら、雑音を正しく取り除くには見出しも消す必要がある。しかし `freeze` は見出しの削除を一律に禁止する。紹介文だけ消すと、雑音の見出しが残る。

どちらも現行取得器の出力で再現した。翻訳前の日本語ページでも発生する。

**根拠：** 計画50、52、95行。取得器630〜674、709〜724行。現行 `commands/ingest.md` 35行は著者紹介欄などの削除を要求する。

### 4. 【重大】画像ファイルの検査条件が、現行取得器の出力と両立しない

**反例A：未取得画像。** `--no-images`、取得失敗、上限超過では、画像行を残し、対応ファイルを作らない。計画の「残した画像の行の画像のファイルは、あること」をそのまま適用すると、正常な出力が `freeze` を通らない。`check` には未取得画像の扱いがあるが、先行する `freeze` に例外がない。

**反例B：共有ファイル。** 同じ画像 URL を2回使う HTML では、取得器は1ファイルを共有する。片方を飾りとして削除し、もう片方を本文として残すと、そのファイルについて「消してあること」と「あること」を同時に要求される。異なる alt を付けた2画像でも再現した。

**根拠：** 計画51、74行。取得器1133〜1149行。両方とも取得器をメモリ内で実行して確認した。

### 5. 【重大】ブロックの定義に、現行出力の入れ子を扱う契約がない

取得器は、次のような画像を実際に出力する。

```markdown
- ![x](assets/example/example-01.png "https://example.org/img.png")
- Second item
```

```markdown
> Before
>
> ![x](assets/example/example-01.png "https://example.org/img.png")
>
> After
```

前者に指示どおり独立した補足引用を挿入すると、元の1リストが分断される。後者では画像と補足が同じ引用の内部に入り、引用ブロック全体を補足として除外すれば原文まで除外することになる。

計画は「画像の行」「リスト」「引用」を並列のブロックとして列挙しているが、入れ子の画像の識別、補足の所属、除外後の再構成を定義していない。この定義次第で、正しい補足を拒むか、本文を照合対象から落とすかが変わる。空行を含むリスト内コードも現行出力に存在する。

**根拠：** 計画60、66〜74行。取得器731〜745、753〜774行。上記の出力とリスト内コードは実行で確認した。特定のパーサー実装の欠陥を断定しているのではなく、合否を決める仕様が未確定である。

### 6. 【重大】新しい雑音規則には、本文を確実に消す入力がある

**反例：**

```html
<table>
  <tr><th>field</th><th>value</th></tr>
  <tr><td class="metadata">checksum</td><td>abcd</td></tr>
</table>
```

これは本文のデータ表であり得るが、計画では1セルの `metadata` を理由に表全体が消える。MediaWiki のホストや特定の告知構造に限定する条件はない。

また、本文中の参考リンクが次の1段落なら、パスの条件だけで削除対象になる。

```markdown
[Tag specification](https://docs.example/tag/release-1)
```

UI の文言を論じる記事に独立した段落として出る `Top highlight` も同様である。

`removed_by_rule` の確認と `--keep-noise --force` で復旧する道はある。しかし、モデルが誤削除に気づかなければ、`fetched.md` 自体に本文がなく、その後の検査はすべて通る。既存の `NOISE_WORDS` の不具合とは別の、新規規則による欠落である。

**根拠：** 計画24、28〜35、94行。表とリンクが現行取得器では本文として残ることを確認した。

### 7. 【重大】`--html-file` は、保存元 URL と文字コードの前提が不足している

**URL の反例：** ユーザーの URL が `https://example.org/request/start`、ブラウザで転送された先が `https://example.org/actual/article/`、保存した HTML が `<img src="img.png">` を含み、`<base>` がない場合である。

計画の `final_url = 渡したURL` では `/request/img.png` を取得するが、表示されたページの画像は `/actual/article/img.png` である。本文の相対リンクも同じように壊れる。ブラウザの実際の URL を渡すという条件は書かれていない。

**文字コードの反例：** DOM を UTF-8 で保存し、元ページ由来の `<meta charset="windows-1252">` が残った場合、現行の `decode_html` にヘッダー指定なしで渡すと、`café` が `cafÃ©` になることを確認した。計画は HTML ファイルの文字コードと復号方法を定義していない。

どちらも、壊れた変換結果が照合基準になるため、後段の検査では検出できない。文字コードの指摘は、既存の復号処理をそのまま使う実装を仮定したもの。

**根拠：** 計画37行。取得器179〜197、588〜589、1092〜1094行。通常の HTTP 取得は159行で転送後の URL を返す。

### 8. 【重大】作業用の写しの欠落・消去からの回復状態が定義されていない

**反例：** raw の保存に成功した直後、`fetched.md` または `fetch.json` の書き込みに失敗する。その後、同じ URL・スラッグで再実行すると、既存 raw の `source_sha256` が一致するため `unchanged` になり、計画では作業用の写しを作らない。取得し直しても検査の基準が復元されない。

現行コマンドは `unchanged` を「同じ内容をすでに取り込んでいる」と説明するが、この状態の raw は翻訳・検査前でもある。原文ハッシュだけでは完了を判定できない。これは単一実行の途中失敗であり、対象外とされた同時取り込みの排他とは無関係である。

さらに、古い作業フォルダーと `--finish` の再帰削除について、親ディレクトリのシンボリックリンク／ジャンクションを含む削除範囲の制約がない。`.wiki-cache/ingest` が外部を指す状態で、組み立てたパスをそのまま削除する実装なら外部の同名フォルダーを消す。**こちらは未規定事項からの推測であり、削除の実行や実装上の欠陥の確認はしていない。**

**根拠：** 計画24、58、84、99行。取得器1074〜1082、1191行。現行 `commands/ingest.md` 31行。取得器には既存の raw 保存について範囲検査があるが、新しいキャッシュ削除の仕様には対応する条件がない。

## 崩れる前提

- **削除だけなら原本を傷つけない。** 本文、SQL コメント、リンク、図の説明文も削除だけで失える。
- **雑音は行単位か、各行1か所にまとまる。** HTML のインライン要素が1行に結合されると崩れる。雑音にも見出しがある。
- **画像の出現と保存ファイルが1対1である。** URL の重複による共有と、未取得画像で崩れる。
- **画像は独立した最上位ブロックにある。** リスト・引用の内部に画像を持つ現行出力で崩れる。
- **ブロックの種類列が同じなら順序を保ったと言える。** URL などを含まない同種の段落を交換しても、列挙された検査条件は一致する。種類の順序と内容の順序は別である。
- **HTML ファイルだけで表示時の文脈を復元できる。** 転送後の URL と保存時の文字コードが失われると崩れる。
- **同じ原文ハッシュなら取り込み済みである。** 保存後、翻訳・検査前に中断した場合に崩れる。

## 見落としと軽微な問題

- **【軽微】言語判定の「今の手順と同じ」は食い違う。** 計画26行は `source_lang` が空の場合だけ `ja_ratio` を使う。一方、`commands/ingest.md` 36行は、本文と食い違う場合も割合を見る。誤った `lang="ja"` の英語本文では、計画の検査が正しい翻訳と `translated_by` を拒む。この食い違いは実装前に確定できる事項である。
- **【軽微】Windows の予約名の列挙が不足する。** `COM¹`、`COM²`、`LPT³` は現行 `check_slug` を通り、Windows 上の `os.path.isreserved` は予約名と判定した。計画39行の ASCII 数字だけの列挙では含まれない。
- **【軽微】フェンス・表・入れ子コードの構文試験が不足する。** 取得器は長さ可変のコードフェンス、エスケープされた `\|`、リスト内コードを出す。これらの単なるパーサー実装ミスは実装試験で発見すれば足りる。ただし、画像補足の所属については前述の設計問題である。
- **【軽微】警告の記録先が曖昧である。** 計画84行の「要約ページの `log.md` の行」は、要約ページと wiki のログファイルを混同している。現行ワークフローは `wiki/log.md` に記録する。

## 検証した事実

- 指定された計画、比較レポート、取得器、コマンド、取り込みワークフローを読んだ。
- **一致：** 取得器は通常の段落内画像を独立ブロックにする。一方、リスト・引用の内側の画像には、その構造を示す接頭辞が残る。
- **一致：** 同じ画像 URL の複数出現は同じ保存ファイルを参照する。未取得画像には保存ファイルがない。
- **一致：** 2か所のインライン雑音が1行になる。提示した正しい削除結果が1か所の連続削除では得られないことも確認した。
- **食い違い：** 「言語判定は今の手順と同じ」は、コマンド側の本文との不一致を扱う規則と一致しない。
- **確かめられず：** 新しい `freeze`・`check` の実際の合否。`wiki_rawcheck.py` は未実装である。比較の12実行の raw を使った再検証も行っていない。

## 崩せなかった点

- 正しい `cleaned.md` を基準にした**翻訳段階**のフェンス内コメントの変更は、計画どおり比較すれば停止する。
- 翻訳段階で本文リンクの URL やその出現数が減る変更は、ブロックごとの URL 多重集合の比較で停止する。
- 図の説明文を alt に移す比較時の失敗は、翻訳段階で起きれば画像行の完全一致に反する。
- 原文にない `<>` の追加と図の数値の読み違いを停止できないことは、計画が認めた限界である。その限界自体を新しい欠陥としては数えていない。
- 通常の `../`、パス区切り、ドライブ指定によるスラッグ経由の脱出は、現行の文字検査と範囲検査を崩せなかった。
