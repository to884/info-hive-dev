# 実装の 9 回目のレビューの指摘の、原因の構造による分類

対象: `wiki_rawcheck.py` と `wiki_fetch.py` の 9 回目の実装（8 回目の指摘の直しと、Sonnet 5.5 での 2 回目の試行の改善を含む）。レビュー: [impl-review-9.md](impl-review-9.md)（GPT-6.1 Sol、effort high、**条件付きで採用可**、確信度 高）。前の分類は [impl-root-causes-1.md](impl-root-causes-1.md)〜[impl-root-causes-8.md](impl-root-causes-8.md)。

致命的・重大な欠陥はなかった。8 回目の反例（エスケープの削除、行頭の `|` を省いた余剰のセル、別の列数の表との取り違え、リストの間の雑音の削除）は、どれも再発しなかった。表の行のセルの数を木の対応の中で守る処理、表の規則の差し替え、リストを項目に開く対応は崩せなかった、とされた。

軽微な指摘 3 件と、記録の食い違い 1 件を直した。

| 原因の構造 | 崩れた前提 | 指摘 | 直し方 |
| --- | --- | --- | --- |
| 出現ごとの記録を、保存先のパスで引いていた | 同じパスの画像なら、取得の記録のどの出現を使ってもよい | 軽微 1（同じ画像を alt を変えて 2 か所で使うと、`freeze` の `images` が後ろの出現の alt を返す。後ろを消しても、残った前の画像に消した出現の alt が付く） | 残った画像の alt と元の URL は、本文に残った画像の記法そのもの（取得器は元の URL を title に書く）から取る。取得の記録からは保存先のパスだけを使う |
| 取得の同一性を、frontmatter という代わりの量で判定していた | 取得の日時と原文のハッシュを含む frontmatter が同じなら、同じ取得である | 軽微 2（同じ秒に、画像を取らずに `--force` で取り直し、raw を書けずに止まると、frontmatter が同じなので、本文の違う写しで再開できた） | 同一性を量で推し量るのをやめ、書き込みの順で保証する。`wiki_fetch.py` は、写しがそろった印（`fetch.json`）を、raw を書き終えてから置く。raw を書けずに止まれば、写しはそろわない。frontmatter の比較は、写しをそろえたあとで raw の frontmatter を書き換えたか、別の版に戻したものを見分けるためだけに残した |
| 節点の行番号を、開始トークンからだけ取っていた | どの節点も、開始トークンが行の位置を持つ | 軽微 3（表のセルの開始トークンは位置を持たず、セルの中の誤りの行番号が空になる。添える文もインラインのコードを除いていて、変えたコードが出力に出ない） | 開始トークンに位置がなければ、中の inline の位置を節点の位置にする。誤りに添える文は、インラインのコードも含める |
| 記録の主張と、`check` の照らす範囲が食い違っていた | 番号つきのリストの項目の番号は、どちらの段でも照らしている | 検証した事実の食い違い（`freeze` の `derivable` は `info` を比べるが、`check` の `compare` は比べず、`2.` を `999.` にしても通った） | `compare` も、コードブロックのほかの節点で `info`（項目の番号）を比べる |

`impl-root-causes-8.md` の「写しの完成を、ファイルの有無だけで判定していた」への直し（frontmatter の比較）は、この回で、書き込みの順による保証に置き換えた。8 回目の試験 `test_work_dir_of_another_fetch_is_not_resumed` は、取り直しが失敗したあと写しが「そろっている」ことを前提にしていたので、「そろっていない」に改めた。

## レビューの外で見つけたもの

8 回目に足した総当たりの試験（`test_single_character_edits_never_hide_content`）が、全体を流すとまれに（10 回に 1 回ほど）エラーになった。`wiki_fetch.py` の `write_outputs` の `os.replace`（raw の一時のファイルから正式な名前へ）が、`PermissionError: [WinError 5]` で失敗していた。試験はループの中で毎回 `--force` で取り直し、同じ raw を約 300 回置き換えていた。Windows では、ほかのプロセス（ウイルス対策の検査などと思われる）が置き換え先を開いていると、名前の変更が拒まれる。

- 試験は、ループの中で取り直さず、raw だけを書き換える形に改めた（`freeze` はいつも取得の写しと照らすので、取り直しは要らなかった）。直したあと、関連する試験の全体を 8 回続けて流し、すべて通った。
- あわせて、試験の誤りを 1 つ直した。訳の段に移るとき、前の段で通った削除の内容が `cleaned.md` に固定されたままで、訳の段の基準が、手を入れていない取得の内容と違うことがありえた。訳の段に移るときに、手を入れていない内容で固定し直す。
- `write_outputs` の名前の変更が、Windows でほかのプロセスに拒まれうることは、この変更の前からある。利用者が取り込みでこれに当たると、`wiki_fetch.py` は `PermissionError` で止まり、raw は前のまま残る（写しはそろわない）。取り直せば済むが、名前の変更をくり返し試す直しは、この変更では扱わない。

足した試験は `ReviewCounterexample9Test` と `FetchCounterexample9Test` の 5 件である。frontmatter の比較の試験を除く 4 件は、直す前の版（6fea489）ではすべて落ちることを確かめた。
