# 実装の 1 回目のレビューの指摘の、原因の構造による分類

対象: `wiki_rawcheck.py` の最初の実装。レビュー: [impl-review-1.md](impl-review-1.md)（GPT-6.1 Sol、effort high、却下）。

| 原因の構造 | 崩れた前提 | 指摘 | 直し方 |
| --- | --- | --- | --- |
| Markdown の構造を、行ごとの正規表現で推し量っていた | 行の先頭の接頭辞から入れ物が分かる。正規表現で、取得器の出すリンク、画像、コードをすべて見分けられる。ブロックは先頭の行で種類が決まる | 重大 1（リストの中の字下げしたコード）、重大 2（コードの本文の `- ` を接頭辞として捨てる）、重大 3・6（エスケープした `]` を含むリンクと画像）、重大 5（リストの続きの行の画像の補足）、重大 7（入れ子の平たん化、表の区切り行）、重大 8 の後半（コードの中の画像の記法） | 同梱の markdown-it-py（`wiki_pages.new_parser()`。lint と閲覧と同じ設定）で読み、トークンで照らす。行の接頭辞や正規表現で構造を推し量らない |
| 削除の段の照らし合わせを、行の一致の固定と、その外の探索の 2 段にしていた | 一致した行を先に固定しても、正しい削除の対応は残る | 重大 4（同じ短い行が別の場所にあると、正しい削除を並べ替えと判定する） | 取得した内容を単位の並びにし、raw の並びが部分列であるかを、先頭から貪欲に照らす（部分列であるかの判定は、貪欲で正しい）。行の対応は持たない |
| 画像を取得したかを、今ファイルがあるかで推し量っていた。補足を行ごとに読んでいた | ファイルがない画像は、取得できなかった画像である。補足の始まりは、引用の最初の行だけである | 重大 9（freeze のあとに消したファイル）、重大 8 の前半（1 つの引用の中の 2 つ目の補足） | 取得したかは `fetch.json` の `images[].path` で決め、取得した画像のファイルがなければ誤りにする。補足は引用のトークンで読み、本文の中に 2 つ目の補足の始まりがあれば誤りにする |
| 作業用の写しのそろい方を、フォルダーの有無で見ていた | フォルダーがあれば、再開に要る写しもそろっている | 軽微（`fetch.json` を書けなかった写し） | `fetch.json` を最後に書き、写しがそろったかは `fetched.md` と `fetch.json` の両方で判定する |
| 記録の切り詰め、試験の確かめ方 | — | 軽微（消した文字列を 300 文字で切る、試験が誤りの種類を照らさない、反例の形の試験がない） | 記録は切らない。試験は誤りの種類を照らし、レビューの反例をすべて試験にする |

設計に明記した限界（本文の前の部分の判定、見出しと表では CamelCase とすべて大文字の語だけを名前の照合の対象にすること）は変えない。見出しと表の扱いは、設計案に書き足す。
