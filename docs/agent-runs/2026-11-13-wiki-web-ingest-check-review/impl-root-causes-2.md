# 実装の 2 回目のレビューの指摘の、原因の構造による分類

対象: トークンの木で照らすように作り直した `wiki_rawcheck.py`。レビュー: [impl-review-2.md](impl-review-2.md)（GPT-6.1 Sol、effort high、却下）。前の分類は [impl-root-causes-1.md](impl-root-causes-1.md)。

1 回目の指摘（リストの中のコード、コードの本文の接頭辞、エスケープした `]`、並べ替えの誤判定、項目の末尾の画像の補足、入れ子と表の変更、コードの中の画像の記法、freeze のあとに消した ASCII のパスの画像）は崩せなかった。

| 原因の構造 | 崩れた前提 | 指摘 | 直し方 |
| --- | --- | --- | --- |
| 同じものを、別の表現のまま比べていた | パーサーの画像のパスと、`fetch.json` のパスは同じ文字列になる | 重大 1（日本語のパスが `%E6…` になり、正しい raw を拒み、ファイルの欠落を見逃す） | パーサーの画像のパスを、比べる前に `unquote` で戻す |
| 補足を、形だけで見分けていた | 補足の形の引用は、モデルが足したものだけである。2 つ目の補足は、引用の直下の段落にしか現れない | 重大 3（入れ子の引用やリストの中の 2 つ目の補足）、重大 4（原文の「Alice 補足:」を補足として取り除く） | 取り除く補足は、画像を含むブロックのすぐあとの、取得した画像の数までに限る。それより後ろは原文として照らす。補足の中は段落だけとし、入れ子の中まで 2 つ目の補足を探す |
| 補足の位置を「画像の行の次」と決めていた | 画像の行の終わりは、段落の終わりと同じである | 重大 2（リストの項目で画像のあとに文が続くと、補足で段落が割れる） | 補足の位置を「画像を含むブロック（段落）のすぐあと」に改め、手順を直す |
| 削除の単位が粗すぎた | 強調を丸ごと 1 つの単位にしても、雑音だけを消せる | 重大 5（強調の中の共有リンクを消せない） | 強調は、中の単位の並びを持つ単位にし、中を再帰的に照らす。リンクは丸ごと 1 つの単位のまま |
| 消す先を、入口で検査していなかった | `--slug` は wiki_fetch.py が検査したものしか来ない | 重大 6（`--slug ../..` で wiki のルートを消す先にできる） | `wiki_rawcheck.py` もスラッグを検査する。消す先は、作業用のフォルダーの置き場の直下に解決されるものに限る |
| トークンの木が、記法と参照の定義を持たない | トークンが同じなら、本文は文字どおり同じである | 軽微（訳さないページの `**` → `__`、参照の定義の書き足し） | 訳さないページは、補足の行を除いた本文を文字どおり比べる。参照の定義は、削除の段では消すことだけ、訳と補足の段では変えないことを、別に比べる |
| 写しの完成を、ファイルの有無で見ていた | ファイルがあれば読める | 軽微（書きかけの `fetch.json`） | `fetch.json` を一時の名前で書き終えてから名前を変える。そろったかは、JSON として読めるかで判定する |
| 雑音の規則の文字数に記号を数えていた | Markdown の文字数は本文の文字数である | 軽微（強調の `**` で 80 文字の判定が変わる） | 強調とコードの記号を除いて数える |
| 試験の穴 | — | 軽微（書き込みの途中の失敗、ASCII だけのパス、壊れた JSON） | 書き込みの途中で失敗させる試験、日本語のスラッグを取得から検査まで通す試験、壊れた JSON の試験を足した |

`> First\nSecond` は、CommonMark の続きの行で同じ引用になるので、構造の変更とはみなさない（レビューも同じ判断）。
