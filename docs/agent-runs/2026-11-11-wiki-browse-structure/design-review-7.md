## 判定

**却下。A に当たる指摘は1件。確信度：高。** `<data_dir>/browse` 自体がジャンクションの場合、失敗も競合もない実行で、その先の利用者ファイルを削除できる。加えて、探索には確定後の非ゼロ終了を合格にする穴が残る。

新実装は未実装である。以下では、設計から導いた反例、試作の仮想入出力での再現、実 OS での読み取り確認を区別する。ファイルは変更していない。

## 致命的・重大な欠陥

### 1. 【重大・A】共通の領分の入口がジャンクションだと、その先を領分として削除する

次の配置を使う。`KEY` は対象 Wiki の `wiki_key` である。

```text
C:\box\wiki\a.md

C:\box\data\browse → C:\box\user\      ジャンクション

C:\box\user\KEY\
  private.txt                         利用者のファイル。一覧はない
```

`INFO_HIVE_DATA_DIR=C:\box\data` とし、`--out` を付けずに書き出す。

1. 6.4 の初期化は、既存の `browse` を作り直さない。試作の `ensure_dirs()` も、種類が `link` なら探索を終える。
2. 6.1 は親を解いて識別子を照らすが、調べるのは Wiki のルートとの重なりである。`C:\box\user` は Wiki の外なので通る。
3. 作業用の `KEY.browse-work` は通常のディレクトリとして作れる。
4. 既定出力なので、`user\KEY` に一覧がなくても門を通さない。
5. `user\KEY` を退避し、新世代を公開し、退避した `private.txt` を削除する。

試作の実関数を、ジャンクションの解決を行う仮想 OS で実行した結果は次だった。

```text
rc = 0
private.txt は残らない
private.txt は KEY.browse-work\del-1 内で削除される
警告 = []
```

**崩れる前提は、「パスの綴りが領分の下なら、そこで扱う実体も領分である」である。** 最後の名前をたどらない口でも、途中のジャンクションを通った親は外部にある。識別子が一致することは、その親を browse が所有することの証明にはならない。

これは、2.3 の「リンクやジャンクションの先は、領分の外」と、2.1 の領分外の名前・中身の保護に反する。手置きしたジャンクション自体を守らないという作者の決定では、その先のファイルの削除は許されない。

根拠：

- [設計2.3：リンクの先は領分外](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:144)
- [設計6.1：確認するのは Wiki との重なり](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:301)
- [設計6.3：既定出力は門を通さない](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:360)
- [試作の初期化](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_model.py:656)、[既定出力の判定](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_model.py:613)

Windows／Python 3.14.6 の実 OS でも、既存の `C:\Documents and Settings → D:\Users` に対する試作の `Guard.place()` が通ることを、読み取りだけで確認した。反例の一連の削除は仮想 OS 上での確認であり、実ディスクでは実施していない。ジャンクションが別ディレクトリを参照することは、[Microsoft の仕様](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)とも一致する。

### 2. 【重大・C】確定後に非ゼロで終わっても、旧世代が残っていれば探索を通る

反例となる実行は次である。

1. 前の世代 G を `old-N` に退避する。
2. 新世代 N を書き出し先に公開する。
3. 確定後の作業用ディレクトリの列挙が失敗する。
4. 失敗を単位の失敗として伝播し、非ゼロで終わる。G は `old-N` に残る。
5. 次の実行は成功する。

9.2 は、この場合に**終了コード0と新世代**を要求する。しかし `check_build()` は、非ゼロ終了では確定前後を分けず、`G in olds` が真なら合格にする。

この状態をメモリ上で判定器へ渡した結果は、**指摘 `[]`** だった。確定位置は試験側から渡しており、試作の `STATE["committed"]` には依存していない。

例えば、確定後の `x_or_empty(work)` を、失敗を送出する `listdir(work)` に戻す種類の欠陥が、この経路を作る。既存の `commit_then_fail` が別の位置で検出されることは、この取りこぼしを否定しない。

**崩れる前提は、「最後の公開世代が残る」という確定前の条件で、確定後の終了状態も検証できることである。**

根拠：

- [設計9.2：確定後は0](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:455)
- [探索：役割の判定は `rc == 0` の側だけ](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_sweep.py:492)
- [探索：非ゼロなら `G in olds` を許す](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_sweep.py:514)

これは設計の確定後の規則を崩した指摘ではなく、**その規則を探索が確かめていない**という指摘である。

## 崩れる前提

| 分類 | 前提 | 崩れる条件 |
|---|---|---|
| A | 最後の名前をたどらなければ、領分外には触れない | 共通の領分の入口 `browse` 自体が外部へのジャンクション |
| A | 親の識別子を確認すれば、そこで既定出力を扱ってよい | 親が正しく識別できる外部ディレクトリで、所有確認を門ごと省略する |
| C | 非ゼロでも旧世代が残れば、終了状態は正しい | 新世代の公開後に非ゼロ終了し、旧世代も残る |
| C | 目印がリンクである状態を足せば、その読み取り規則も検証できる | リンク先に正しい所有者があり、同じ Wiki のロックが保持されている |
| C | 世界の差分は、全ファイルの通常の中身を比較する | 保護対象のファイル名が `.lock` で終わる |

## 見落としと軽微な問題

- **【軽微・C】目印のリンクを、試作は読まない。**  
  設計6.2 は目印のリンク先を読むとするが、`read_text()` は `kind != "file"` なら `None` を返す。正しい所有者 A を持つリンクと、同じ Wiki の保持中ロックを与えると、本文を一度も読まず、`Stop: 別の Wiki が、同じ場所を使っている` になった。探索のリンク先は通常のページ本文なので、「所有者が本当に一致するリンク」の経路を確かめていない。[設計](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:347)、[試作](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_model.py:451)、[探索の配置](C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-browse-structure/write_sweep.py:202)。

- **【軽微・C】世界の差分は、任意の `.lock` ファイルの中身を量らない。**

- **【軽微・C】10には、読めない索引について追加するナビゲーションの「不完全」表示がない。**  
  4.1 には明記されているが、変更表の読めない入力の行はページだけである。[4.1](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:245)、[変更表](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:580)。
