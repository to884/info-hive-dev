書く側には、固定名の `server.json` を作成者や中身に関係なく browse のものとする経路が残っています。また、NTFS の代替データストリームは、ファイル名と通常の内容のハッシュでは照合されません。過去17件の対応表と、こうした新しい欠陥を試験が見逃す条件を分けて整理します。
## 判定

**却下。確信度：高。** 制御用ファイルの所有判定が「自分が作ったものだけを変える」を満たさず、状態ファイルの置換途中の中断にも復旧の穴がある。R1〜R4を満たしても残る入力欠落と、正しい部分劣化を不合格にする試験基準も確認した。

作者の5つの決定は、いずれも反証の対象としていない。新設計は未実装なので、以下では仕様から導いた反例と、現行関数・試作をメモリ上で実行して確認した結果を区別する。

## 致命的・重大な欠陥

### 1. 【致命】制御用ファイルは、中身が違っても名前だけで所有を認定する

世代には名前・種類・ハッシュの照合を要求する一方、制御用ファイルは「目印のあるディレクトリの、決まった名前」で browse のものになる。

反例：

1. 一度サーバーを起動して終了し、状態ディレクトリと目印を残す。
2. 利用者が、新しい別ファイルを `server.json` という名前で置く。内容は私的なメモなど、browse の記録とは異なるものにする。
3. `serve` を実行する。
4. 許された名前しか存在しないので状態ディレクトリは検査を通り、新しいサーバー記録による置換で、そのメモが失われる。

Wiki の外であり、新しい一時ファイルも排他作成できる。世代の一覧照合にも違反しない。競合、一覧の改変、同じ中身のファイルへの交換は必要ない。

**崩れる前提は「制御用の予約名なら、現在そこにあるものも browse が作った」である。** 作者が変更した所有原則を、制御用ファイルだけが満たしていない。

根拠：[構造設計§5.2〜5.3](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:134)、特に[制御用ファイルの所有判定](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:152)と[次の `serve` による置換](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:174)。仕様からの反例であり、実ファイルの削除は実施していない。

### 2. 【重大】通常の内容のハッシュと列挙では、NTFS の別ストリームにある利用者データを守れない

Windows／NTFS では、ファイルにもディレクトリにも代替データストリームを付けられる。通常の内容、大きさ、ディレクトリの項目一覧とは別にデータが存在する。[Microsoft の説明](https://learn.microsoft.com/en-us/sysinternals/downloads/streams)

反例は2通りある。

- 正常な世代の `a.html` に、利用者が `a.html:notes` を追加する。通常の内容の SHA-256 は変わらず、一覧にも項目は増えない。世代は照合を通り、退避後の削除で `notes` も失われる。
- 利用者が作った書き出し先ディレクトリに、子項目を作らず、ディレクトリ自身の `:notes` にデータを置く。項目の列挙では空なので、§5.3の例外による `rmdir` の対象になる。

後者は、**「空のディレクトリを取り除いても、内容は失われない」**という例外の根拠を崩す。前者も、「同じ中身のファイルを利用者が置いた」という限界とは異なり、生成ファイルに別のデータを追加した場合である。

一覧の改変、マウント、検査後の競合は必要ない。§8.1の世界の差分も、通常の内容のハッシュと属性だけなら、ストリーム内のデータ消失を捉えられない。

根拠：[一覧に記録する内容と照合条件](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:142)、[空のディレクトリの扱い](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:149)、[ADRの例外の理由](/C:/Works/info-hive-dev/docs/adr/0017-wiki-browse-changes-only-what-it-created.md:34)。OS仕様と削除手順から導いた反例であり、実NTFS上の破壊試験は実施していない。

### 3. 【重大】`server.json` の置換途中の中断は、次の起動・停止を拒み続ける状態を作る

§5.2は、同じディレクトリに新しいファイルを排他作成してから置換すると定める。一方、§5.3は、制御用の決まった名前以外の項目があれば、そのディレクトリを使わない。

現行の置換方法をこの規則に組み合わせると、次が起きる。

1. サーバーのロックを取る。
2. 状態ディレクトリに `.server.json.<PID>.<乱数>.tmp` を排他作成する。
3. `os.replace` より前にプロセスが止まる。
4. OSはロックを解放するが、一時ファイルは残る。
5. 次の `serve`／`stop` は、許されていない項目があるとして状態ディレクトリを拒む。

一時名を固定した場合も、残ったファイルの所有判定と、次の排他作成までの処理が未規定である。**「途中で止まった世代を残す」規則は、制御用ファイルの一時物には適用されない。**

これは単一の中断で成立する。§11にある世代の残骸や、二重の障害ではない。§6と§8.2が要求する「次の `serve` は成功する」も保証できない。

根拠：[置換方法と制御用ディレクトリの規則](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:134)、[起動・終了の状態](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:173)、[次の起動の試験条件](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:215)、[現行の一時名](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_fs.py:152)。

### 4. 【重大】R1〜R4では、循環判定の失敗による無通知の入力欠落を閉じられない

走査計画は、循環判定の `stat` が失敗すると、`realpath` と `normcase` による文字列比較へ切り替える。この失敗は、R2の列挙失敗でも、R3の `.md` の種類判定失敗でもない。

反例：

```text
大小文字を区別する C:/w/
  B/x.md
  b/j/ → C:/w/B/    # 循環していないジャンクション
```

`j` の循環判定で、`os.stat(C:/w/B)` だけが一度 `PermissionError` になると、次が起きる。

1. 識別子での比較を放棄する。
2. `normcase("C:/w/B") == normcase("C:/w/b")` が真になる。
3. 循環と誤判定して `j` を飛ばす。
4. 列挙失敗でもファイル判定失敗でもないので、要求された通知が出ない。
5. browse は、入力の欠けた新しい中核を正常として採用できる。

試作の実際の `same_or_ancestor()` に仮想属性を与え、次を確認した。

```text
正常時:                       False
stat の1回だけ PermissionError: True
```

Windows がディレクトリ単位の大小文字区別を扱えることも、[Microsoft の仕様](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)と一致する。

**崩れる前提は「識別に失敗しても、文字列比較なら既知の結果へ戻せる」である。** lintも同じ走査関数を使えば、両者が同じ欠落を共有するため、lintとの一致では検出できない。P1・P2と守ること9の問題である。

根拠：[走査計画の識別失敗時の規則](/C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:96)、[試作の握りつぶしと文字列比較](/C:/Works/info-hive-dev/docs/agent-runs/2026-11-11-wiki-walk-excluded-dirs/walk_probe.py:65)、[R1〜R4](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:82)。

### 5. 【重大】§8.2は、§3が要求する正しい部分劣化を不合格にする

入力の中身を読めない場合、§8.2が認める差は「そのページの表示、診断、不完全の表示だけ」である。しかし、読めない本文からはリンクを集計できない。

反例：

```text
a.md: [[b]] [[missing]]
b.md: # B
```

`a.md` の読み取りだけが失敗した場合、少なくとも次が変わる。

- 未解決リンク一覧から、`a.md → missing` が消える。
- `b` の被リンクから `a` が消える。
- 関係の入力に使っていれば、他ページの関係表も変わる。

現行の実際の `Core` に、正常な写しと読み取り失敗の写しを与え、次を確認した。

```text
未解決リンク: [("a.md", "missing")] → []
b の被リンク: ["a"]                → []
```

§3は、このような一覧を「不完全」として続けると定めている。その正しい実装が、§8.2の限定に違反する。

索引本文を読めない場合のナビゲーション、オントロジーを読めない場合の関係表にも、同じ食い違いがある。**崩れる前提は「1入力の中身の欠落は、その入力の表示にしか影響しない」である。**

根拠：[部分劣化の仕様](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:100)、[劣化の試験基準](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:212)、[現行の読めないページの除外](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_core.py:548)。

## 崩れる前提

| 前提 | 崩れる条件 |
|---|---|
| 制御用の固定名は、現在のファイルの作成者も証明する | 利用者が同名・別内容のファイルを新しく置く |
| 項目一覧と通常の内容のSHA-256で、消えるデータを列挙できる | NTFSの名前付きストリームがある |
| OSがロックを解放すれば、次の起動も可能になる | 記録の置換用一時ファイルが残り、ディレクトリの検査に拒まれる |
| `stat` 失敗後の文字列比較は、実体比較の代わりになる | 大小文字を区別する場所、別名、解決し切れなかったパス |
| 同じ走査関数なら、不完全な入力も検出できる | lintとbrowseが同じ無通知の欠落を共有する |
| 読めないページの影響は、そのページだけに閉じる | 被リンク、未解決リンク、参照先の解決、関係表へ依存がある |
| OSの口への例外注入で、I/Oの失敗形態を覆える | 短い読み書き、正常値に変換された失敗、異常時だけ通る経路 |

## 見落としと軽微な問題

- **【軽微・P2の範囲】3モジュールの構文木検査は、依存先の握りつぶしを検査しない。**  
  現行の `wiki_graph_common._try_lock()` は全 `OSError` を偽にし、`_unlock()` は黙殺する。内部のロック操作に `EIO` を注入し、実関数がそれぞれ `False`／通常復帰になることを確認した。「競合で取得できない」と「ロック操作自体が壊れた」は別である。[該当関数](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_graph_common.py:138)。新設計の「ロックの取得と解放」がどの深さの口を指すかは未規定で、これらをそのまま口にすると、前版と同じ注入の迂回が残る。

- **【軽微・口の一覧外】明示的な依存先I/Oと標準入出力が残る。**  
  `wiki_pages` はインポート時に `_vendor_digest()` で `rglob()` と `read_bytes()` を実行する。読み取りを拒否すると、コマンドの例外境界へ入る前に `PermissionError` になった。`core` の標準入力読み取り、応答の `write`／`flush`、公開後の標準出力も、ファイルI/Oと通信I/Oのどちらの一覧に入るか決まっていない。[依存先の読み取り](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_pages.py:78)、[標準出力](/C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse.py:321)。

- **【軽微】`del-N` の「次回、続きを消す」と完全照合の関係が未規定である。**  
  削除済みの項目が一覧から欠けた `del-N` は、完全一致では通らない。残存項目だけの照合を認める別規則は書かれていない。§11の残骸として残すことはできても、§5.3と攻撃表の「続きを消す」は保証されない。[削除と再開の規則](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:144)。

- **【軽微・読む側の結果】警告するトークンの範囲が、読める記録の範囲より狭い。**  
  別Wikiの稼働中の `server.json` を指すページや、記録をコピーしたページも読む。一方、検査は「そのWikiのサーバーの記録」のトークンだけを探す。別Wikiの操作トークンは、現在のWikiのサーバーを止めても無効にならず、警告も保証されない。§9の「`server.json` を指すページには検査が警告する」という記述は、そのままでは広すぎる。[検査の範囲](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:113)。

- **【軽微・P8】例外だけを注入する探索には、正常復帰の異常が入らない。**  
  例として `os.write()` は実際に書いたバイト数を返す。[Pythonの仕様](https://docs.python.org/3.12/library/os.html#os.write)。短い書き込みを成功と誤認する実装は、`PermissionError`／`EIO` の探索と、列挙された対照だけでは検出できない。また、正常実行の呼び出し数だけを使う探索は、障害後にだけ現れる経路を網羅しない。2障害同時という既知の限界とは別である。

- **【軽微・依存と順序】R1〜R4が入らなかった経路では、P3は構造上の保証ではなくなる。**  
  これは設計自身が認めている。依存先は現時点でも `index_files()` を変更対象外としており、索引の列挙失敗を検出できなくなると明記する。したがって「走査計画がmainに入った」は、R1〜R4やP3成立の確認にはならない。[代替経路](/C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:89)、[依存先に残る退行](/C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:139)。

- 読む側から置き場所による拒否を取り除けば、前版の「ハードリンクを所属判定できない」「読まないページの未解決リンクが消える」という前提は不要になる。
- R1どおり起点ごとに走査し、循環しない別名を残すなら、前版の訪問済み実体の共有による欠落は起きない。
- 画面部品を起動時に読み終えるなら、要求中の部品読み取り失敗の経路は閉じる。
