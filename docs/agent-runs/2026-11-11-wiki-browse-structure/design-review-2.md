## 判定

**却下。確信度：高。** P4 の判定は、ハードリンク経由の状態ファイルの読み取りを防げず、逆に読み取りを拒んだページでは「lint と同じ判定」を維持できない。P3 の走査規則、P6 の終了処理、P8 の試験にも、記述どおりでは両立しない条件が残る。

## 致命的・重大な欠陥

### 1. 【致命】P4 の祖先判定では、状態ファイルのハードリンクを読んでしまう

**崩れる前提：ファイルの実体には、祖先をたどれば判定できる一意の置き場所がある。**

反例は、同じファイルシステム上で次の手順を踏むと成立する。

1. サーバーを起動する。
2. 稼働中の `server.json` のハードリンクを、Wiki の `concepts/record.md` として作る。
3. 閲覧口から `concepts/record.html` を要求する。

ハードリンクはシンボリックリンクではない。`realpath(concepts/record.md)` は Wiki 内の名前のままで、その祖先に状態ディレクトリも `<data_dir>/browse/` も現れない。したがって、§4 の判定手順では読み取りを許してしまう。

同じ実体には、稼働中の `control_token` が入っている。P7 で `Path` を取り除いても、トークンは読み取った本文として描かれる。`build-report.json` のハードリンクなら、同じ経路で生成器が書いた Wiki の絶対パスが入る。

現行の `Core` に相対パスと記録の本文を渡したメモリ上の検証では、HTML にトークンとルートの目印が出ることを確認した。実際のハードリンクの作成は行っていない。

これは、**P4 の具体的な判定手順が、原則P4を実現していない**反例である。P7 の「絶対パスが入るのは利用者が入力に書いたときだけ」という主張も崩れる。

根拠：[構造設計§4](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:64)、[同§7](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:107)、[現行の実体解決](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_core.py:174)、[記録の内容](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse.py:634)。

### 2. 【重大】P4 を厳密に守ると、守ること2の未解決リンク一致を満たせない

**崩れる前提：意図的に読まないページを増やしても、lint との判定は変わらない。**

次の配置を考える。

```text
wiki/concepts/user.md → exports/site/user.md

exports/site/
  .browse-generation
  user.md                 本文: [[missing]]
```

書き出し先に利用者のファイルがある配置は、§4自身が想定している。

lint は `concepts/user.md` を読めるページとして扱い、`missing` を `broken_links` に入れる。一方、P4 は持ち場にある実体を読まず、`browse_area` として描画から除く。本文を読まない以上、そこにある `missing` を列挙できない。

現行の lint と、「P4に従い本文を渡さない写し」を使った検証結果は次のとおりだった。

```text
lint.broken_links:  [("concepts/user.md", "missing")]
browse.unresolved: []
```

これは過去1-3の「表示対象から外れたページの未解決リンクが消える」と同じ構造である。衝突ページから持ち場のページへ、除外理由が変わっただけである。

根拠：[構造設計の維持する契約](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:9)、[P4の読み取り禁止](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:66)、[元の守ること2](C:/Works/info-hive-dev/docs/plans/wiki-browse-stage1-2026-11-09.md:43)、[現行の読めないページの除外](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_core.py:548)。

### 3. 【重大】P3 の「同じディレクトリには2度降りない」は、循環のない配置でも lint と違う集合を作る

**崩れる前提：ディレクトリの実体の重複は、循環または不要な重複である。**

Windowsで次を置く。

```text
wiki/
  a/x.md
  alias/ → a/       ジャンクション
```

lint の `rglob` は `a/x.md` と `alias/x.md` を別のページとして返す。P3 が実体ごとに1回だけ降りるなら、片方を落とす。`[[x]]` も、lint では複数候補なのに browse では1候補になり得る。

仮想ディレクトリを与え、現行の `rglob` と `iter_page_files()` を通した結果：

```text
lint:                 ["a/x.md", "alias/x.md"]
実体ごとに1回の走査: ["a/x.md"]
```

さらに、`indexes` を `concepts` へのリンクにすると、同じ実体が「ページの置き場所」と「索引の置き場所」になる。全体で訪問済みを共有すると、走査順によってページか索引のどちらかが欠ける。

依存先の走査計画は、循環しない別名経路を残すと明記している。したがって「将来 `walk_markdown()` に乗り換えれば作りで一致する」という説明にも、現時点で食い違いがある。

根拠：[構造設計§3](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:56)、[現行のページ列挙](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_pages.py:52)、[別計画の別名経路の扱い](C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:102)。

### 4. 【重大】P2 の完全な属性取得は、入力でない場所の障害を閲覧の障害に戻してしまう

**崩れる前提：除外ディレクトリへ降りなければ、その場所に依存しなくなる。**

§2は、一覧の各項目について種類と属性を取得し、一つでも分からなければ一覧全体を失敗させる。一方、§3が禁止しているのは、除外ディレクトリへ「降りる」ことである。

次の単一障害が反例になる。

```text
wiki/
  concepts/a.md
  raw/
```

Wikiルートの一覧は取得できるが、一覧項目 `raw` の属性取得だけが `Unknown` になる。P2どおりならルートの一覧全体が失敗し、閲覧は古い状態か503になる。

しかし§8.1は、入力でない `raw/` への呼び出しの失敗では、古い表示も503も許さず、結果をNと同じにすると要求する。**P1・P2を守った結果が、P8の要求に違反する。**

別計画には「除外名の項目は種類を調べる前に飛ばす」という明示があるが、こちらの一覧の契約にはない。過去7-1の不要な依存を、ディレクトリ列挙から属性取得へ移す余地が残る。

根拠：[一覧の契約](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:46)、[除外の規則](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:56)、[非入力障害の判定](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:126)、[別計画の判定順](C:/Works/info-hive-dev/docs/plans/wiki-walk-excluded-dirs-2026-11-11.md:78)。

### 5. 【重大】サーバー終了は、記録の削除を確定点にしても「すべて済むか、前のまま」にならない

**崩れる前提：記録の変更が、サーバーの生死とロックを含む状態の確定点になる。**

現行の順序を保つと、次の1回の失敗で崩れる。

1. 稼働中サーバーに `control/stop` を送る。
2. サーバーが待ち受けを終了し、ソケットを閉じる。
3. `_finish()` で記録を消そうとする。
4. Guardの走査か記録の削除が `Unknown` になる。
5. 記録を残し、ロックを解放して終了する。

結果は次になる。

| 状態 | サーバー | 記録 | ロック |
|---|---|---|---|
| 停止前 | 稼働 | あり | 保持 |
| 停止完了 | 停止 | なし | 解放 |
| 上記の失敗後 | 停止 | あり | 解放 |

失敗後は、前の状態でも完了状態でもない。サーバーを既に止めた事実は、記録を残しても戻らない。

§6の表はこの残存記録を認める一方、その直前の文章と§8.1は、仕事全体・記録・ロックが確定前後のどちらかになると要求する。両方を文字どおり満たせない。

根拠：[P6の全体契約と表](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:82)、[試験の許す状態](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:123)、[停止要求](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse.py:568)、[ソケットを閉じてからの終了処理](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse.py:774)。

### 6. 【重大】層の入口への例外注入では、層の内部の失敗の握りつぶしを検出できない

**崩れる前提：すべてのI/Oが層を通れば、層の呼び出しへの注入で、実際のI/O障害も検査できる。**

例えば、層に次の欠陥が残っている場合である。

```python
def list_entries(path):
    try:
        return read_os_entries(path)
    except OSError:
        return []
```

`list_entries()` の入口を `Unknown` に差し替える試験では、この `except` を通らない。呼ぶ側がPへ戻れば合格する。

実際の `read_os_entries()` が `PermissionError` になったときだけ、空の新しい結果を採用する。メモリ上の小さなモデルで、次を確認した。

```text
層の入口への注入: 合格
内部の実I/O相当の失敗: 新しい空集合になり、不合格
```

現行の `wiki_browse_fs.py` に既にある `_is_link()` も、内部の `os.lstat()` の `PermissionError` を偽に変換する。実関数への注入で `False` を確認した。これを層に置くこと自体では、P1違反は検証されない。

§8.4の対照が「呼ぶ側でUnknownを空に変換する欠陥」だけを再現すれば、その対照は落ちても、上の内部欠陥は残る。過去5-1・6-1と同じ種類である。

根拠：[層による注入漏れ防止の主張](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:48)、[探索の注入点](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:134)、[対照](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:158)、[現行の握りつぶし](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_fs.py:81)。

## 崩れる前提

| 原則 | 残っている前提と崩れる条件 |
|---|---|
| P1 | `Unknown` が正しく作られること。OSの失敗が層の内部で空・偽へ変換されると、P8の入口注入からは見えない。**Unknownを最後まで保持する契約そのものは崩せなかった。** |
| P2 | 層を通ることと、不要な場所へ触れないことは別である。非入力項目の属性取得でも一覧全体を失敗させられる。 |
| P3 | 実体の重複と論理的な入力名の重複を同一視している。循環のないジャンクションや、ページと索引の共有先で崩れる。 |
| P4 | 実体の所属を祖先で完全に判定できること。また、読まないページを増やしてもlintとの一致が保てること。どちらも崩れる。 |
| P5 | 「仕事ごとに1走査」と「破壊操作ごとに再走査」が両立すること。静的書き出しには複数の破壊操作があるため、§3と§5は文字どおりには両立しない。 |
| P6 | 記録の確定が、サーバーの停止などの不可逆な副作用も代表すること。停止後の記録削除失敗で崩れる。 |
| P7 | 機械情報を含む本文は利用者が書いたものだという前提。生成器の記録へのハードリンクで崩れる。 |
| P8 | 無障害の同じ実装から得たNが、正しい結果であること。正常経路にもある誤りは、Nとの比較で共通化される。 |

P5の「持ち場D」も未確定である。`<data_dir>/browse/` と、その下の世代・状態ディレクトリは重なる。祖先の持ち場すべてへ規則を適用すると、ある既定の書き出し内の入力を守るために、別の状態ディレクトリの更新まで拒む。どのDを単位にするかで、許可結果が変わる。

## 見落としと軽微な問題

**【軽微・試験設計】§8.5の17件は、次のように照合できる。** 「検出可」は、記述された入力・経路を実際に実行する場合であり、試験の実装済み・成功を意味しない。

| 指摘 | 挙げられた道具での検出 |
|---|---|
| 1-1 絶対出力名で別出力を上書き | **範囲チェックだけでは不可。** 上書き先も目印付きのbrowseの持ち場なら通る。Nも同じ誤実装から作ると一致する。現行の個別試験は、別出力の保全を直接確認している。 |
| 1-2 削除時の属性変更 | **検出可。** 読み取り専用ハードリンクの配置と、実際に変更される属性の比較が条件。 |
| 1-3 非表示ページの未解決リンク消失 | **lintの `broken_links` との比較なら検出可。** 入力ファイル集合の一致だけでは不可。今回のP4による除外も同種である。 |
| 1-4 絶対パス検査の誤り | 分類は廃止されるため、旧分類の期待は適用できない。生成器による混入は、入力に目印がない条件の検査で検出可。 |
| 1-5 オントロジーの内部構造異常 | **条件付き。** `node_types: []` をオントロジーに置く必要がある。ページのfrontmatterに置くだけでは元の反例を通らない。 |
| 1-6 空出力先で旧世代消失 | **検出可。** 空出力先と退避世代を用意し、復旧後の生成も失敗させる組み合わせが条件。 |
| 2-1 `~` のrawで生成失敗 | 有効な入力の無障害実行が成功する、という判定があれば検出可。敵対的入力の用意だけでは成功を検査したことにならない。 |
| 2-2 不正URLで応答なし | **検出可。** URLを含むページの実際の要求・描画を行うことが条件。 |
| 2-3 重なりを検出しても終了しない | **元の終了条件は新仕様では検査対象外。** トークン検査だけでは、目印を参照した場合の別ファイルの削除禁止を検証できない。 |
| 3-1 再構築と終了の競合 | **条件付き。** Wikiの変更だけでなく、再構築途中に終了処理を挟む実行順序が必要。単一スレッドでファイルを変えるだけでは、その順序にならない。 |
| 3-2 YAMLの日付異常 | **検出可。** オントロジーとページの両方の位置を通すことが条件。 |
| 4-1 ロック待機中の入力追加 | **検出可。** 保護対象決定後に変更し、取得後の記録操作まで実行することが条件。 |
| 4-2 入力の印の失敗が500 | **検出可。** 印の取得を含む要求全体への判定がある。 |
| 5-1 列挙障害が正常な空集合になる | **層内部への障害注入がなければ不可。** 欠陥6のとおり、入口のUnknown注入は握りつぶしを迂回する。 |
| 6-1 属性障害で保護対象が外れる | **同じ注入点の穴がある。** `identity()` 自体をUnknownにすることと、内部の `stat()` を失敗させることは別である。 |
| 6-2 リンク先索引の変更見落とし | **検出可。** 非空のナビゲーションを変更し、旧応答を古い表示なしで返す元の誤りはN/P比較で落ちる。 |
| 7-1 非入力ディレクトリ障害で停止 | 対象パスへの障害を実際に起こせれば検出可。ただし、今回の属性取得による依存は、一覧の層の入口だけでは再現されない。 |

根拠：[対応表](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:168)、[別出力を直接保全確認する現行試験](C:/Works/info-hive-dev/tests/wiki/test_browse.py:175)、[lintとの比較](C:/Works/info-hive-dev/tests/wiki/test_browse.py:154)。

ほかに、次の問題がある。

- **【軽微】P3とP5の走査回数の矛盾。** 「仕事ごとに1度だけ」と、既存世代の移動・公開・削除それぞれの再走査は別の実装になる。原因分析の「1,000ファイルで1,000回調べない」という説明も、一時ファイルの名前変更を破壊操作に含めるかで変わる。性能の成立は確かめられていない。[構造設計§3](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:54)、[§5](C:/Works/info-hive-dev/docs/plans/wiki-browse-structure-2026-11-11.md:74)、[原因分析A](C:/Works/info-hive-dev/docs/agent-runs/2026-11-09-wiki-browse-stage1-review/impl-root-causes.md:41)。

- **【軽微】持ち場の定義と作成途中の試験が合わない。** カスタム出力用の作業ディレクトリは、目印のない一時ディレクトリを作ってから目印を置く。この最初の作成先は、§4の既存目印による持ち場判定では持ち場に入らない。「すべての書き込み先が持ち場内」という判定には、作成途中の扱いがない。[現行の作成順](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_fs.py:209)。
- **【軽微】目印を最後に消しても、再発見できるとは限らない。** 目印の削除後、最後の `rmdir()` だけが失敗すると、目印のない残骸になる。現行の世代列挙はこれを拾わない。「次の書き出しで消す」という説明は、この単一障害を含んでいない。[削除順](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse_fs.py:251)、[世代列挙](C:/Works/info-hive-dev/info-hive-wiki/skills/info-hive/scripts/wiki_browse.py:111)。
- **【軽微】振る舞い変更の表が契約変更を網羅していない。** P4による未解決リンク集合の変化がない。また、本文の読み取り失敗をページ単位で残す現行動作と、N/Pだけを許す§8.1の関係が決まっていない。現行試験は、読めないページだけ404となり、その後復帰することを要求している。[該当試験](C:/Works/info-hive-dev/tests/wiki/test_browse_server.py:478)。
- **【軽微】2計画の引き継ぎが未確定。** 原因分析はBを後回しにするが、この版はbrowse内に走査を作る。依存先は索引の別列挙を残す。両計画とも0.10.1を指定し、同じ走査関連コードを対象にするため、§10だけでは最終的な規則と適用順が決まらない。
