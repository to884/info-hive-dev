## 判定

**却下。確信度：高。** `apply` 同士に限定しても、未適用の変更を「済み」と判定する反例と、同じファイルへの変更を失う適用手順が残る。秘密検査とパス検査にも、承認前の保存を防げない経路がある。

## 致命的・重大な欠陥

**1.【重大】別の場所にある同じ文章を、対象の変更が「当て済み」である証拠にしてしまう。**

次のファイルを考える。`L` と `R` は、それぞれ前後3行の文脈である。

```python

R = "q1\nq2\nq3\n"
before = "# A\n" + L + "old\n" + R + "# B\n" + L + "new\n" + R
after = before.replace("old\n", "new\n", 1)
current = before.replace("old\n", "other\n", 1)
```

取り込みAが承認された変更は、節Aの `old` → `new` である。その適用前に、別の取り込みBが同じ箇所を `other` に変えた。

この `current` では、差分の塊の「当てる前」は0か所、「当てたあと」は節Bの1か所だけに一致する。10節の表に従うと **「当て済み」になるが、節Aは `other` のまま**である。合成データで、この一致数を確認した。

236行の「ほかの場所にたまたま一致すれば競合になる」は成立しない。まさにその一致を「済み」にする分岐が225行にある。ロックに参加する取り込みが順番に実行されても起きる。

根拠：[設計書:225](/C:/Works/info-hive-dev/docs/plans/wiki-session-ingest-2026-11-14.md:225)、[再開の説明:236](/C:/Works/info-hive-dev/docs/plans/wiki-session-ingest-2026-11-14.md:236)。

**2.【重大】`append` の重複判定が追記先の節に結び付いておらず、S10のログが欠落する。**

次のログがあるとする。

```markdown

## [2026-11-14] ingest | 今回の資料
```

S10で今回の項目に足すブロックが、次の1行だった場合である。


**3.【重大・仕様の欠落】同じパスへの複数変更を合成する規則がなく、単一の `apply` 内で更新を失う。**

新しいソースページとコンセプトページを作る取り込みで、同じ `index.md` に次の2操作を登録する。

- 「ソース」の節へソースページの項目を追加する。
- 「コンセプト」の節へコンセプトページの項目を追加する。

213行は、変更ごとに現在の行き先から新しい内容を作り、すべてをメモリに用意する。230行は、それを順番に置き換える。この記述どおりなら、元の索引を `I0` として、それぞれ `I0＋ソース項目` と `I0＋コンセプト項目` が作られ、後者の置換が前者を消す。

同一パスの操作を一つに集約する規則、先の変更結果を次の入力にする規則、重複登録を拒む規則のいずれもない。読み直しを最後の内容と比較すれば欠落を見逃し、各変更の内容と比較すれば、すでに書いた後で不一致になる。

**外部の書き手も並行プロセスも不要**であり、wiki単位のロックでは防げない。未実装なので実際の実装が必ずこの方式になるとは断定しないが、中心となる適用規則がこの反例を排除していない。

**4.【重大・仕様の欠落】`append` の対象見出しが、`plan_sha256` の算出項目にない。**

201行が列挙する算出項目には、種類、パス、前後のハッシュ、追加ブロックなどがあるが、`append` の `--section` がない。`append` には変更前後のファイルのハッシュも定義されていない。

次の配置を考える。

**7.【重大】適用先からロックファイルを除外しておらず、POSIXでは自分の排他を壊せる。**

`track --path .wiki-cache/apply.lock` を拒む規則がない。過去の適用で残ったロックファイルを追跡し、`after` の内容を変更した計画を考える。

POSIXでは、次の順序になる。

1. Aが既存の `apply.lock` を開いてロックする。
2. A自身の `patch` が、そのパスを `os.replace` で置き換える。
3. Aのロックは、置換前のファイルを指したままである。
4. Bが新しい `apply.lock` を開き、ロックを取得する。
5. AとBが同じwikiへの書き込み区間に同時に入る。

指定版の `wiki_graph_common.py:168` は、まさにこの理由でロックファイルを消さずに残すと説明している。新しい道具の対象パス検査には、自分のロックファイルや管理領域を保護する規則がない。

この反例はPOSIX側についての設計上の指摘であり、今回Windowsで置換を再現したものではない。

根拠：[任意の相対パスを受ける登録:189](/C:/Works/info-hive-dev/docs/plans/wiki-session-ingest-2026-11-14.md:189)、[ロック:211](/C:/Works/info-hive-dev/docs/plans/wiki-session-ingest-2026-11-14.md:211)、[置換:230](/C:/Works/info-hive-dev/docs/plans/wiki-session-ingest-2026-11-14.md:230)、`wiki_graph_common.py@83dbb30:165–169`。

## 崩れる前提

| 暗黙の前提 | 崩れる条件 |
