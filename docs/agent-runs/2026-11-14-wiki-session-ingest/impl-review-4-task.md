# 依頼: セッションの取り込みの実装の敵対的レビュー（4 回目）

3 回目のレビュー（`impl-review-3.md`、却下）の指摘を直した版である。目的、対象、範囲の外は 1 回目の依頼（`impl-review-1-task.md`）と同じ。崩れた前提と原因の構造は `impl-root-causes.md` の「3 回目のレビューのあと」にある。

## 直し方

原則を「形を変える前の元の文の全体で見つけ、見つけた結果から、出力の文と探す文字列の両方を作る」に直した。

- `find_secrets()` が元の文の上で規則の範囲を見つけ、`redact_parts()` が、部品（ブロック、ツールの名前と値）をつないだ全体で見つけた範囲を、部品ごとに切り分けて伏せる。部品の境目をまたぐ秘密は、またいだ両方の部品で伏せる。
- アシスタントのターンは、まとめた記録の `text` と、改行を残したツールの名前と値（`--tools none` で出力しない値も、見つける文には入れる）をつないだ全体で当て、そのあとでツールの要約を 1 行にして切る。形を変えたあとにも、もう一度当てる。
- 人の発言は、加工（差し込みを除く、コマンドの要素を 1 行にする）の前に当てる。`cwd` と `git_branch` も、改行を空白にする前に当てる。
- 秘密の鍵の塊の本体の行は、元の改行で分けて探す文字列にする。
- 書いたあとの `scan --path` は、wiki への書き込みをすべて終えたあと（S10。グラフのエッジとログのサブ行のあと、`verify` の前）に移した。
- 結合文字の列は、正規化で切れない塊の先頭を返すことを説明に書いた（行は正しい）。

直す前の実装で、足した試験が 5 件とも落ちることを確かめた。手元の実物の記録 982 ファイルで、`reply_unresolved` は 0 件、自己検査の失敗も 0 件のままだった。

## 特に見てほしいこと

- 元の文で見つけてから形を変える、という順になっていない経路が、まだ残っていないか。
- `redact_parts()` の切り分けで、伏せ残しや、伏せた文字列の欠けが起きる入力がないか。
- 1〜3 回目に崩せなかった点が、直しで崩れていないか。
