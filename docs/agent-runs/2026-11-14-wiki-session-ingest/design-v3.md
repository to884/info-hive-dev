# Claude Code のセッションを wiki に取り込む（2026年11月14日）

## 背景

今のプラグインには、セッションの会話を取り込む手段がない。`/wiki:ingest` は文字起こしを `.md` か `.txt` のソースとして受け付ける（`references/ingest-workflow.md` の「ファイルの置き方」）。しかし、Claude Code が残すセッションの記録は JSONL で、会話のほかに大量の記録を含む。そのまま渡すと、取り込みのコンテキストの大半を雑音が占める。

2026年11月14日に、検証環境の PC にある 1 つのプロジェクトの記録（61 ファイル）を調べた。分かったことは次のとおりである。値は「検証環境の値」の節にまとめた。

- 記録の種類は 20 ある。会話を表すのは `user` と `assistant` だけで、ほかは `api-request`、`attachment`、`file-history-snapshot`、`queue-operation` などの記録である。
- `user` の記録の大半は会話ではない。最も多いのはツールの結果（12,759 件）である。ほかに、バックグラウンドの作業の通知（`origin.kind` が `task-notification`、322 件）、ほかのセッションからの伝言（`peer`、107 件）、CI の監視の通知、スキルの本文の読み込み（`isMeta`）、圧縮の要約（`isCompactSummary`）がある。人の発言は `origin.kind` が `human` の記録（626 件）にある。
- `origin.kind` が `human` の記録も、すべてが人の打った文ではない。626 件のうち 91 件は、本文がタグで始まっていた。ハーネスが差し込んだ `<system-reminder>`（52 件）、スラッシュコマンドの呼び出し（`<command-message>`、25 件）、デスクトップアプリのボタンが作った依頼（`<create-pr-command>`、11 件）、貼り付けた文（`<pasted_content>`、3 件）である。`<system-reminder>` は、52 件とも本文の先頭にあった。記録には、これがハーネスの差し込みであることを示す属性がない。
- `origin` のない `user` の記録もある。中断の印（`[Request interrupted by user]`）、手元のコマンド（`/model` など）とその出力、`claude -p` で渡した依頼（`promptSource` が `sdk`）である。61 ファイルのうち 7 ファイルは `origin` を 1 つも持たず、どれも `claude -p` のセッションだった（1 回目のレビューで確かめた）。
- 1 ファイルは、ファイル名の ID と、最初の記録の `sessionId` が違い、2 つの ID の記録を含んでいた（2 回目のレビューで確かめた）。別のセッションから写した記録を含むものと見られる。
- `assistant` の記録は、内容のブロック 1 つにつき 1 件である。1 つの応答が最大で 22 件に分かれていた。思考（`thinking`）のブロックも記録に残っている。
- `parentUuid` が枝分かれする箇所は 2,743 あった。どれも、ツールの呼び出しの記録が、次のブロックとツールの結果の 2 つの子を持つものだった。巻き戻しによる枝分かれは見つからなかった。
- 会話を圧縮しても、圧縮の前の記録は消えない。圧縮の要約は、`isCompactSummary` の付いた `user` の記録として足される。コンテキストから記事を書くと圧縮の前の内容が欠けるが、記録から書けば欠けない。
- サブエージェントの記録は、本体のファイルには入っていない。`<セッション ID>/subagents/agent-*.jsonl` に別に置かれる。
- 記録には、利用者が意図せず残した情報が入る。このセッションの記録には、環境変数の一覧を出したツールの結果が入っており、メールアドレスとアカウントの UUID が含まれている。ツールの結果を除いても、アシスタントの本文がそれを引用することがある。セッションの題名やブランチの名前に、顧客の名前のような文字列が入ることもある。
- 記録の形式は公開された仕様ではない。記録ごとに `version`（2.1.309〜2.1.321）がある。
- 実行中のセッションの ID は、コマンドの本文から得られる見込みである。Claude Code 2.1.321 の本体のコードには、本文の `${CLAUDE_SESSION_ID}` をセッションの ID に置き換える箇所が 2 つある（`${CLAUDE_SKILL_DIR}`、`${CLAUDE_EFFORT}` の置き換えと並んでいる）。ただし、プラグインの `commands/*.md` がその置き換えを通ることは確かめていない。公開の文書も確かめていない。
- 記録は、いつまでも残るとは限らない。Claude Code には記録を残す日数の設定 `cleanupPeriodDays` があり、期間を過ぎた記録を消す（本体のコードで設定の名前を確かめた。既定の日数は確かめていない）。

## 目的

- 1 回の `/wiki:ingest` で、Claude Code のセッションの会話を、raw の原本と、記事の形のソースの要約ページとして wiki に入れる。
- raw は、記録から決まった手順で作る。記録の同じ範囲を、同じ版の抽出器に同じ引数で渡せば、どの PC でも同じ raw ができる。記録の SHA-256 で出所を確かめられるのは、元の記録が残っている間だけである。記録そのものは raw に写さない（Web ページの原文の HTML を残さない ADR-0004 と同じ割り切り）。記録が消えたあとは、raw が唯一の原本になる。
- モデルの思考は raw に入れない。秘密の情報と個人の情報は、機械的に伏せ、残りを人が確かめる。**raw のルートには、確認を終えたものだけを書く。** 確認の前の写しは、Git の管理から外れた作業用のフォルダーに置く。人は、本文と、会話から来た frontmatter の値のどれに残った情報も伏せられる。題名とファイル名は、書く前に人が決める。
- 開発用の PC の置き場所や記録の形に、仕様を合わせない。記録のパスを渡せば、どの環境でも動く。記録の形が変わったときも、入口で認識できなかったときも、ユーザーの明示の指示なしには何も通さない（漏れる側に倒れない）。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| サブエージェントの記録 | 本体と別のファイルで、量が多い。既定でも引数でも読まない。見つけたファイルの数だけを報告する。需要が出たら足す |
| デスクトップアプリの Export の zip | 中の構成を確かめていない。zip を展開して JSONL のパスを `session:<パス>` で渡せば使える |
| Claude Code 以外のエージェント（Codex など）の記録 | 形式が違う。`.jsonl` で渡されたら、入口で止まるか、ユーザーに確かめる（「1. 入口」） |
| `claude -p` のセッション | 人の発言が記録されない（「作者が決めること」の 6） |
| ツールの結果の中身 | 雑音と秘密の情報の大半がここにある。ツールの呼び出しは 1 行の要約だけを残す |
| 日本語でないセッションの翻訳 | ADR-0004 が Web ページを訳すのは、英語の根拠と日本語の要約の照合を通すためである。セッションは作者自身の会話で、ほとんどが日本語である。需要が出たら決める |
| セッションの終わりにフックで自動で取り込むこと | 取り込みは、依頼されたソースだけを明示して行う |
| 取り込んだセッションの続きを、差分として足すこと | 1 回の取り込みは、記録の 1 つの範囲の写しとして扱う（「9. 取り込み直し」） |
| Web ページの取り込みの `raw` の値の直し | W9 は `raw` に `"raw/<スラッグ>.md"` と書くので、raw のルートを変えた wiki では lint が原本を見つけられない（1 回目のレビューの重大 6）。この設計のセッションの取り込みでは直す（「8. 取り込み」）。Web ページの側は、別の変更として直す |

## 決めること

### 1. 入口

ADR-0015 は、新しいコマンドを「既存のコマンドで表せない手順が出てから足す」と決めている。セッションの取り込みは、Web ページの取り込み（W1〜W9）と同じく、`/wiki:ingest` のソースの種類の 1 つとして表せる。そこで、新しいコマンドは足さず、`/wiki:ingest` の引数で受け付ける。

| 引数 | 対象 |
| --- | --- |
| `session` | 実行中のセッション |
| `session:<セッション ID>` | 同じ Claude Code の設定のディレクトリにある、ほかのセッション |
| `session:<パス>` | 記録のファイル |
| `<パス>.jsonl` | `inspect` の判定による（下の表） |

**入口は、閉じる側に倒す。** セッションの手順は思考を除き、伏せ字をかけ、人の確認を通すが、ふつうの取り込みはソースをそのまま raw に置く。記録をふつうの取り込みに回すと、そのすべてを迂回する。そこで、`.jsonl` は、キーワードの有無によらず、まず `wiki_session.py inspect` にかける。

- 判定が `session`（セッションの記録として読め、「4. 残すものと除くもの」の規則で人の発言が 1 件以上ある）なら、セッションの手順に進む。
- そうでなければ（判定が `not_session`）、止まる。何も書かない。記録の形が変わったか、別のエージェントの記録か、会話の記録でない JSONL であることを、ユーザーに伝える。会話の記録らしい形かどうかを見分けて、ふつうの取り込みに回す分かれ道は作らない。形で見分ける規則は、形を少し変えた記録に必ず破られるからである。
- 会話の記録でない JSONL を、ふつうのソースとして取り込みたいときは、ユーザーがそう明示して頼む。そのときだけ、ふつうの取り込みに進む。思考を含む記録がそのまま raw に入るおそれを、そのときに伝える。
- 引数が既存のファイルのパスなら、キーワードより先にファイルとして扱う。`session` という名前のファイルを取り込めなくならないようにするためである。そのファイルが `.jsonl` なら、上に従う。
- 実行中のセッションの ID は、`commands/ingest.md` の本文に `${CLAUDE_SESSION_ID}` と書いて得る。置き換えが起きなかったとき（文字列が `${` で始まる、または空）は、推測せずに、記録のパスか ID をユーザーに聞く。

専用のコマンド（`/wiki:session`）にする案もある。コマンドの一覧に名前が出て見つけやすいが、手順は `/wiki:ingest` と同じものを呼ぶだけになる。ADR-0015 の条件に当たるかは「作者が決めること」の 1 である。どちらを選んでも、キーワードのない `.jsonl` が `/wiki:ingest` に来る経路は残るので、上の判定は要る。

### 2. 記録の場所

- パスを渡されたら、そのファイルだけを読む。ファイルは書き換えない。
- ID を渡されたら、まず形を確かめる。小文字の 16 進数の UUID（`8-4-4-4-12`）でなければ、エラーにする。パスの区切りや `..` を含む値で、別の場所を読まないためである。
- ID のファイルは、`<設定のディレクトリ>/projects/*/<ID>.jsonl` を 1 階層だけ探す。設定のディレクトリは、環境変数 `CLAUDE_CONFIG_DIR` があればそれ、なければ `~/.claude` である。設定のディレクトリそのものは、利用者が決めた場所なので、リンクでもよい。
- 探すときは、設定のディレクトリより下のリンクをたどらない。`projects`、その下のディレクトリ、見つけたファイルのどれかが、シンボリックリンクか、Windows のジャンクションかシンボリックリンクの再解析ポイントなら、候補にしない。ID の字面が正しくても、リンクの先の別の場所を読まないためである。
- 見つけたファイルの記録のどこかに、`sessionId` が渡された ID と一致するものがなければ、エラーにする。最初の記録の値とは比べない。別のセッションから写した記録を含むファイルがあるからである。
- 0 件ならエラーにし、パスで渡すように書く。2 件以上なら、見つけたパスを並べてエラーにする。
- プロジェクトのディレクトリの名前（`C--Works-info-hive-dev` のように、作業ディレクトリを変換した名前）は組み立てない。変換の規則も公開されていないからである。
- この探し方は、公開されていない置き場所に頼っている。動かなくなったときは、パスを渡す方法が残る。

**セッションの ID は、次の順に決める。**

1. ID で探したときは、その ID（ファイル名と同じ）。
2. パスで渡したとき、ファイル名（拡張子を除く）が UUID なら、それ。
3. そうでなく、範囲の中の記録の `sessionId` の値が 1 種類だけで、UUID の形なら、それ。Export の zip を展開して名前を変えたファイルなどで使う。
4. どれでもなければ、`--session-id` で明示するよう求めて止まる（`inspect` は `not_session` を返し、理由を出す）。`--transcript` と `--session-id` を一緒に渡したときは、その ID が記録のどこかの `sessionId` にあることを確かめる。

記録の中に、決めた ID と違う `sessionId` の記録があれば、`warnings` に `mixed_session_ids`（ID ごとの記録の数）を入れる。それらの記録も、ファイルの順に残す。別のセッションから写した部分なら、人が確認でターンを消す。

### 3. 読み方と範囲

- 1 行ずつ読み、行ごとに JSON として解釈する。ファイルの全体をメモリに読まない（検証環境の最大は 51.9 MB だった）。
- **範囲は、ファイルの先頭から、終わりの位置までである。** 終わりの位置は次のどちらかである。
  - `--before <uuid>` を渡したら、記録そのものの `uuid` キー（`parentUuid` や `leafUuid` ではない）がその値である最初の記録の、行の先頭。その記録とそのあとは読まない。見つからなければエラーにする。実行中のセッションでは、取り込みの依頼の記録の `uuid` を渡す（S1 で `inspect` が出す）。この範囲で取り込み直しの同一性（「9. 取り込み直し」）が成り立つのは、記録のファイルが追記だけで書かれ、前の行が書き換わらないときである（「まだ確かめていないこと」）。
  - 渡さなければ、最後の改行のあと。改行で終わらない最後の行は、書きかけとみなして読まない。
- `source_sha256` は、範囲のバイト列に対して取り、その長さを `source_bytes` に書く。`--before` で範囲を決めれば、記録がそのあとに伸びても、同じ範囲から同じ値が出る。
- UTF-8 として読めない行と、JSON として読めない行は、飛ばす。飛ばした位置はターンの境界として扱い、印を置く（「4. 残すものと除くもの」の「ターンの境界」）。数を `broken_lines` に入れ、`warnings` に `broken_lines` を入れる。
- 記録は、ファイルの順に並べる。`parentUuid` の木はたどらない。並列のツールの呼び出しでできる枝分かれは、ファイルの順に並べれば正しく並ぶ。同じ親を持つ人の発言が 2 つ以上あるとき（巻き戻しの疑い）は、両方を残し、`warnings` に `possible_rewind` を入れる。人が読み直して、要らない側のターンを消す（「7. 伏せ字の確認」）。
- ファイルの大きさの上限は、既定で 256 MiB とし、`--max-bytes` で変えられる。超えたら読まずにエラーにする。

### 4. 残すものと除くもの

**許可リストにする。** 下の規則で残すと決めた記録とブロックだけを raw に入れ、ほかはすべて除く。知らない種類の記録とブロックはエラーにせず、除いた数を種類ごとに `excluded` に入れる。除くものを並べる方式（拒否リスト）にすると、Claude Code が新しい種類の記録を足したときに、それが raw に入ってしまう。

**話者は、記録ごとの属性だけで決める。** 本文の形（タグで始まるか、など）からは決めない。ファイル全体の形式からも決めない。

| 記録 | 条件 | 扱い |
| --- | --- | --- |
| `user` | `origin.kind` が `human`。`isMeta`、`isCompactSummary`、`isSidechain` のどれも真でない。ツールの結果でない | 人の発言。本文は下の「人の発言の本文」で加工する。加工で空になっても、ターンの境界にする |
| `user` | `origin` がなく、本文が `[Request interrupted by user]` か `[Request interrupted by user for tool use]` と完全に一致する | 中断の印（「（ユーザーが中断した）」）。ほかの文字列は、似ていても印にしない |
| `user` | `origin.kind` が `task-notification` か `peer` | 除く。ターンの境界にする |
| `user` | そのほか（`origin` がなく中断の印でもない、`origin.kind` が上にない値、`isMeta`、`isCompactSummary`、`isSidechain`） | 除く。`user:unattributed` などの種類で数える。ターンの境界にする |
| `user` | ツールの結果 | 除く。ターンの境界にしない |
| `assistant` | `isSidechain` と `isApiErrorMessage` が真でない | ブロックごとに次の 3 行で扱う |
| `assistant` のブロック | `text` | 残す |
| 同上 | `tool_use`、`server_tool_use` | 1 行の要約にする（下の表） |
| 同上 | そのほか（`thinking`、`redacted_thinking`、知らない種類） | 除く。思考は `commands/learn.md` の「モデルの非公開の推論を収集しない」と同じ理由で除く |
| そのほか | `system`、`attachment`、`api-request*`、`file-history-*`、知らない種類 | 除く。ターンの境界にしない |

**人の発言の本文。** 属性が人と示す記録にも、ハーネスとアプリの文が入る（「背景」）。加工は、観測した既知の形を、観測した位置に限って行う。

1. 本文の先頭に続く `<system-reminder>`〜`</system-reminder>` の塊を、除く。先頭にないものは除かない。除いたターンの番号と塊の数を、`warnings` の `stripped_reminder` に入れる。`--keep-reminders` を付けると除かない。人が本文の先頭に同じ要素を書いたときと、ハーネスが差し込んだときは、記録の属性では見分けられない。既定で除くのは、検証環境の 52 件がどれも差し込みの形だったからである。人の文を除いてしまったと確認で気づいたら、`--keep-reminders` で抜き出し直す。
2. 1 のあとの本文が、`<command-name>`、`<command-message>`、`<command-args>` の要素と空白だけでできていれば、「コマンド: `/<名前> <引数>`」の 1 行にする。
3. 1 のあとの本文の全体が、既知のアプリの要素 1 つ（今は `<create-pr-command>` だけ）なら、中身を除き、「（アプリの操作: create-pr-command。内容は除いた）」の 1 行にする。除いた数は `user:app:<名前>` で数える。既知の要素の一覧は、スクリプトの中の定数にする。
4. そのほかの本文は、そのまま残す。タグを含んでいても、知らない名前のタグで始まっていても残す（人が書いた HTML を捨てないため）。ただし、本文が `<` で始まる発言には、`warnings` に `leading_tag`（タグの名前とターンの番号）を入れる。ハーネスが知らない形で文を差し込んだのかもしれないので、人の確認で見る。
5. 内容のブロックの画像は「［画像］」の 1 行にする。画像は保存しない。`text` と `image` のほかのブロック（`document` など、知らない種類を含む）は除き、`user:block:<種類>` で数える。
6. 1〜5 のあとで空になった発言は、「（人の発言。内容は除いた）」の印のターンにする。境界を消さないためである。

**ツールの呼び出しの要約。** ツールごとに決めた入力の項目を 1 つだけ使う。コマンドの文字列は使わない。秘密の情報を含みやすいからである。

| ツール | 使う項目 |
| --- | --- |
| `Read`、`Edit`、`Write`、`NotebookEdit` | `file_path` |
| `Grep`、`Glob` | `pattern` |
| `Bash`、`PowerShell` | `description`（`command` は使わない） |
| `WebFetch` | `url` |
| `WebSearch` | `query` |
| `Agent` | `description` |
| `Skill` | `skill` |
| そのほか（MCP のツールなど） | ツールの名前だけ |

値は改行を空白に変え、120 文字で切る。要約の行は `[ツール] <名前> <値>` の形で、アシスタントのターンの本文の、それが現れた位置に置く。`--tools none` を付けると、要約を残さない。

**ターンの境界。** ターンは、人の発言 1 つ、または境界から次の境界までのアシスタントの出力の全体である。境界は次の位置にある。

- 人の発言の記録（加工で空になったものも含む）と、中断の印。
- 除いた記録のうち、上の表で「ターンの境界にする」としたもの。
- 読めない行。

境界のうち、記録を除いた位置と読めない行の位置のあとにアシスタントの本文が続くなら、印のターンを 1 つ置く。印がないと、通知への返事が前の人の発言への返事のように読め、読めない行の前後の応答が 1 つにつながるからである。続けて同じ種類の境界があれば、印は 1 つにまとめる。

| 境界 | 印のターンの本文 |
| --- | --- |
| `task-notification` | （バックグラウンドの作業の通知。内容は除いた） |
| `peer` | （ほかのセッションからの伝言。内容は除いた） |
| そのほかの除いた記録 | （人の発言でない記録。内容は除いた） |
| 読めない行 | （読めない行が <数> 行あった。前後のつながりは確かめていない） |
| 加工で空になった人の発言 | （人の発言。内容は除いた） |

**人の発言がないとき。** 人の発言が 1 件もなければ、何も書かずに終了コード 2 で止まる。記録の属性の値が変わって何も人と認められなくなったときも、ここで止まる。

### 5. 伏せ字

残す本文、ツールの要約、会話から来た frontmatter の値（`cwd`、`git_branch`）に、次の規則で伏せ字をかける。**規則は、記録と引数だけで決まる。実行する PC の値（ホームのディレクトリ、ユーザー名、環境変数）は使わない。** 同じ記録から、どの PC でも同じ raw を作るためである。規則は機械的なので、漏れがあることを前提にする。漏れは人の確認でふさぐ（「7. 伏せ字の確認」）。

| 種類 | 規則 | 置き換え |
| --- | --- | --- |
| メールアドレス | `ローカル部@ドメイン` の形 | `［メール］` |
| ホームのディレクトリ | `C:\Users\<名前>`、`C:/Users/<名前>`、JSON の文字列のように `\` を重ねた `C:\\Users\\<名前>`（ドライブの文字は問わない。大文字と小文字を区別しない。区切りは 1 つ以上の `\` か `/`）、`/Users/<名前>`、`/home/<名前>` | `~` |
| 秘密の値 | 既知の接頭辞の値（`sk-`、`ghp_`、`gho_`、`github_pat_`、`xoxb-` など、`AKIA` で始まる 20 文字、`eyJ` で始まる 3 つに分かれた JWT）、`-----BEGIN … PRIVATE KEY-----` の塊、`token`、`secret`、`password`、`api_key` などの名前に続く `=` や `:` の値 | `［伏せ字］` |

- 規則に当たらない場所のホームのディレクトリ（`/srv/profiles/<名前>` など）は、残る。人の確認で伏せる。
- UUID は伏せない。セッションの ID は出所として必要で、アカウントの UUID が出るのは主にツールの結果だからである。
- 種類ごとの件数を `redactions` に入れる。

### 6. raw の形

raw は `<RAW_ROOT>/<スラッグ>.md` に置く。Web ページと同じく、raw のルートの直下である。raw を書くのは、確認を終えたときの `check --finish` だけである（「7. 伏せ字の確認」）。確認の前の写しは、作業用のフォルダーに同じ文法で書く。

**題名とスラッグは、書く前に人が決める。** `wiki_session.py inspect` が、記録の最後の `custom-title`（なければ最初の人の発言の先頭 40 文字）から題名とスラッグの案を出す（伏せ字の規則をかけ、改行を空白に変えたもの）。モデルはその案をユーザーに示し、題名とファイル名に残してよいかを確かめてから、`extract` の `--title` と `--slug` に渡す。題名は 1 行で、制御文字と書式の文字（Unicode の `Cc`、`Cf`）を含まず、前後に空白がなく、120 文字以内でなければならない。満たさなければ `extract` はエラーにする。スラッグは `<開始日>-<題名>` の形を目安にし、命名は `references/page-conventions.md` の規則に従う。スラッグは `wiki_fetch.check_slug()` で検査する（`/`、`\`、`..`、ファイル名と wikilink に使えない記号、Windows の予約された名前を拒む）。スラッグは作業用のフォルダーの名前にもなり、`check --finish` はそのフォルダーを消すので、検査を通らないスラッグでは何もしない。ファイル名と題名は、raw を書いたあとに変えられないので、ここで決める。

**raw は、決まった文法で書く。** スクリプトの書き手が書き、確認の検査ではスクリプトの読み手が読む。文法から外れたファイルは、読み手が拒む。

````text
---
<キー>: <値>            ← 下の表のキーを、表の順にすべて書く。値は wiki_text.format_fm_value() で書く
---
                        ← 空の行
## T<番号> <話者>（<時刻>）
                        ← 空の行
<フェンス>text
<本文の行>              ← 0 行以上。各行は LF で終わる
<フェンス>
                        ← 空の行。ここから次のターン
## T<番号> 通知（<時刻>）
                        ← 空の行
（<印の文>）
                        ← 空の行
````

- ファイルは LF だけで改行し、CR を含まない。最後は 1 つの LF で終わる。UTF-8 で書く（`wiki_fetch.py` と同じく、バイト列で書く）。
- 題名の見出し（`#`）は本文に置かない。題名は frontmatter の `title` にだけある。
- **フェンスの外に置くのは、スクリプトが決めた語、整形した時刻、形を検査した識別子だけである。** 話者は `ユーザー`、`Claude（<モデル>、…）`、`通知` のどれかである。モデルの名前は記録の `message.model` から取り、英数字と `._:-[]` だけの 64 文字以内でなければ `不明` と書く。印の文は、表に決めたものだけである。会話から来た文字列は、frontmatter の値（`format_fm_value()` で引用する）とフェンスの中にだけ置く。
- フェンスは、バッククォートを並べたもので、本文の中の最も長いバッククォートの並びより 1 つ長くし、3 より短くしない。情報の文字列は `text` である。本文は記録の文字列のままで、改行は LF にそろえる（CR LF と CR を LF にする）。CommonMark では、このフェンスを閉じられるのは同じ長さ以上のバッククォートの行だけなので、本文の中の閉じていないフェンス、見出し、HTML、字下げは、フェンスの外に出ない。同梱のパーサー（`wiki_pages.new_parser()`）で、閉じていないフェンス、本文の見出し、4 つのバッククォートのフェンス、チルダのフェンス、字下げした区切り、閉じていない HTML のブロック、改行で終わらない本文の 7 つが、それぞれ 1 つのフェンスに収まることを確かめた（2026年11月14日）。2 回目のレビューでも、空の本文、CR だけの改行、U+2028 などを含む 12 の例で、外に出ないことが確かめられた。
- 本文の Markdown は、raw では描画されず、文字のまま読まれる。raw は記事ではなく原本なので、これでよい。記事はソースの要約ページで書く。
- 時刻は、`--utc-offset`（既定は `+00:00`）で直した時刻で、渡した値を frontmatter の `utc_offset` に残す。`/wiki:ingest` は、実行する PC の時差を渡す。
- ターンの番号（`T12`）は、原本を開いて探せる文字列であり、URL のアンカーではない。`page-conventions.md` は、根拠の位置を「節の見出し、PDF のページ番号、行の範囲のように、原本を開いて探せる形」で書くとしており、ターンの見出しはその「節の見出し」に当たる。

**frontmatter のキー**は次のとおりで、この順に書く。平らなキーだけである（`wiki_text.py` は入れ子を読まない）。

| キー | 中身 | 確認で変えてよいか | 同一性に入るか |
| --- | --- | --- | --- |
| `title` | 人が決めた題名 | 変えない | 入る |
| `source_kind` | `"claude-code-session"` | 変えない | ― |
| `session_id` | 記録のファイル名の ID | 変えない | ― |
| `cwd`、`git_branch` | 範囲の中の最初の人の発言の記録の値。伏せ字の規則をかける | ひと続きの文字の並びを `［伏せ字］` に置き換えることだけ | ― |
| `started_at`、`ended_at` | 範囲の中の最初と最後の記録の時刻（UTC） | 変えない | ― |
| `claude_code_versions` | 範囲の中の版を小さい順に `, ` でつないだもの | 変えない | ― |
| `source_sha256`、`source_sha256_of`、`source_bytes` | 範囲のバイト列の SHA-256、`"jsonl"`、長さ | 変えない | 入る（`source_sha256`、`source_bytes`） |
| `extracted_by` | `"wiki_session.py <版>"` | 変えない | 入る |
| `cut_before` | `--before` の値。渡さなければ `""` | 変えない | 入る |
| `tools`、`keep_reminders`、`utc_offset` | 引数の値 | 変えない | 入る |
| `turns`、`excluded_records`、`redactions` | 抜き出したときの数 | 変えない | ― |
| `reviewed_at`、`manual_markers`、`deleted_turns` | 確認の記録。作業用のフォルダーの写しでは `""` と `0` | `check --finish` だけが書く | ― |

- 記録のファイルの場所は書かない。場所は raw の同一性に関係がなく、場所の名前（プロジェクトのディレクトリの名前）に会話から来た文字列が入るからである。記録は `session_id` で探せる。

### 7. 伏せ字の確認

Web ページの W2〜W8 と同じく、作業用の写しを残し、人の確認のあとで raw を固定する。Web ページと違い、**確認の前の写しは raw のルートに書かない。** raw のルートは Git で管理されていることが多く、ほかのセッションが同じ作業ツリーで動いていることもある。伏せる前の文が、コミットや同期でほかへ出ないようにするためである。

1. `wiki_session.py extract` が、作業用のフォルダー `<WIKI_ROOT>/.wiki-cache/ingest/<スラッグ>/`（`wiki_rawcheck.work_dir()` と同じ場所）に、`extracted.md`（照らす元）と `review.md`（人が手を入れる写し。中身は `extracted.md` と同じ）を書く。最後に、写しがそろった印として `session.json`（同一性のキーの値を入れる）を置く。どのファイルも、一時ファイルに書いてから名前を変える。名前の変更の試し直しは、`wiki_fetch.py` の `replace_with_retry()` を使う。印が置けなければ、写しは未完成として扱う（`wiki_fetch.py` の `fetch.json` と同じ）。書いたあとで、`extract` は自分の読み手で `review.md` を読み直し、下の検査の字面と構造の検査と、同梱のパーサーでの検査を自分の出力にかける。通らなければ、抽出器の誤りとしてエラーにする。`.wiki-cache/` は、`init_wiki.py` が置く `.wiki-cache/.gitignore`（中身は `*`）で Git から外れる。この `.gitignore` がなければ、`warnings` に `work_dir_not_ignored` を入れる。
2. モデルは、出力の `redactions`、`excluded`、`warnings`（`stripped_reminder`、`leading_tag`、`broken_lines`、`possible_rewind`、`mixed_session_ids`、`work_dir_not_ignored` を含む）をユーザーに示す。
3. モデルが `review.md` を読み、規則で伏せられなかった秘密の情報と個人の情報（第三者の名前、非公開のリポジトリの内容、顧客の情報、規則に当たらない場所のホームのディレクトリなど）を探して、候補をユーザーに示す。`cwd` と `git_branch` の値も見る。何を伏せるかはユーザーが決める。
4. `review.md` に手を入れてよいのは、次の 2 つだけである。
   - フェンスの中の、ひと続きの文字の並びを、`［伏せ字］` 1 つに置き換える。何行にわたってもよい。`cwd` と `git_branch` の値の中の並びも、同じように置き換えてよい。
   - ターンを丸ごと消す。見出しの行、その下の空の行、フェンスの全体（印のターンなら印の文）、そのあとの空の行をまとめて消す。番号は振り直さない。
   印を残さずに文字を消すことはしない。「通らなかった」から「らなか」を消すと「通った」になるように、印のない削除は意味を裏返せるからである。置き換えなら、読む人にも検査にも、そこで何かを伏せたことが見える。見出しの行、フェンスの区切りの行、印のターンの文、frontmatter のキーとほかの値は変えない。書き足しと言い換えはしない。
5. `wiki_session.py check --wiki <WIKI_ROOT> --raw-root <RAW_ROOT> --slug <スラッグ> --finish` で、`review.md` を `extracted.md` と照らし、通れば raw を書く。

**`check` は、字面と構造と中身の 3 つを照らす。**

- 字面: スクリプトの読み手で `review.md` を読む。読み手は「6. raw の形」の文法だけを受け付け、文法から外れた行（参照の定義、コメント、余分な段落や空の行、CR、文法にない frontmatter の行など）があれば誤りにする。読んだ結果（frontmatter の値と、ターンの見出し、フェンス、本文の行の並び）を同じ書き手で書き直し、そのバイト列が `review.md` のバイト列と 1 バイトも違わないことを確かめる。パーサーが捨てる文字列や書き換える文字を書き足しても、書き直しで一致しなくなる。本文の行には、そのターンのフェンスを閉じうる行（3 つ以下の空白のあとに、フェンスの長さ以上のバッククォートだけが続く行）があってはならない。置き換えた結果そういう行ができたら、置き換える範囲を変える。
- 構造: 読み手が取り出したターンの並び（見出しの行、フェンスの区切りの行、印の文）が、写しのターンの並びから、いくつかのターンを丸ごと除いたものでなければならない。見出しの行は 1 文字も違ってはならない。ターンの番号は写しの中で重ならないので、`review.md` の各ターンは、見出しの行で写しのただ 1 つのターンに対応づく。補助の検査として、同梱のパーサーで `review.md` を読み、2 段目の見出しとフェンスが、読み手の取り出したターンと 1 対 1 に対応することも確かめる。
- 中身: 対応づいたターンごとに、読み手が取り出した本文の文字列 R を、写しの同じターンの本文 B と照らす。R を `［伏せ字］` で区切った断片を p0、p1、…、pn とする。B が、p0、s1、p1、s2、…、sn、pn をこの順に並べたものに等しく、どの si も 1 文字以上であれば通る。つまり、B のひと続きの並び si を、それぞれ `［伏せ字］` 1 つに置き換えたものが R である。照らし方は、p0 が B の先頭に、pn が B の末尾に一致し、間の断片を左から順に、前の位置から 1 文字以上あとの最も早い位置で探す（この探し方で見つからなければ、ほかの並べ方でも見つからない）。si が `［伏せ字］` そのものなら、写しにもともとあった印（自動の伏せ字を含む）をそのまま残したものとみなす。`cwd` と `git_branch` の値も、値ごとに同じ規則で照らす。そのほかの frontmatter の値は、写しと同じでなければならない。比べるのは読み手が取り出した文字列で、パーサーのトークンではない（パーサーは NUL を U+FFFD に変える）。

本文をターンの外へ移す編集（1 回目のレビューの重大 5 の反例）は、構造か中身のどちらかで誤りになる。見出しの行は構造の側で固定され、中身はターンの中でしか照らされないからである。

**通ったら、raw を書く。** `check --finish` は、次の順に進む。

1. `<WIKI_ROOT>/sources/<スラッグ>.md` があれば、止まる（終了コード 1）。取り込んだあとの raw は変えない（「9. 取り込み直し」）。
2. `review.md` の frontmatter に、`reviewed_at`（UTC の時刻）、`manual_markers`（`［伏せ字］` そのものでない si の数。人が足した印の数）、`deleted_turns`（消したターンの数）を入れたものを、raw として、一時ファイルに書いてから名前を変えて置く。
3. 作業用のフォルダーを、`wiki_rawcheck.remove_work_dir()` で消す。

2 の前に止まれば、raw はなく写しが残るので、`check` からやり直せる。2 のあと 3 の前に止まれば、raw があるので確認済みとして扱う（「9. 取り込み直し」）。残った写しは、次の `extract` が、raw と同一性のキーが同じことを確かめてから消す。

この検査は、書き足し、言い換え、印のない削除、構造の変更がないことを保証する。`［伏せ字］` で隠したことで文の意味が変わらないことは保証しない。それは人が確かめる。

`wiki_rawcheck.py freeze` を使わない理由は 2 つある。コードブロックを丸ごと残すか丸ごと消すかしか許さないが、ここでは本文の全体がフェンスの中にある。また、置き換えを許さない。

### 8. 取り込み（記事の形）

`check` を通ったら、`/wiki:ingest` の手順 3〜8 に進む。セッションのソースに固有の決まりは次のとおりである。

- ソースの要約ページ `sources/<スラッグ>.md` を、記事の形で書く。`session_id` にはセッションの ID を書く。本文の構成は「概要、背景、経緯、決めたことと理由、採らなかった案と理由、残った課題、主張と行き先、関係するページ」とする。`page-conventions.md` は本文に固定のテンプレートを求めていないので（ADR-0015）、これはセッションのソースだけの型である。
- `raw` には、`extract` と `check` の出力の `raw_ref` を書く。`raw_ref` は、raw のファイルの、wiki の親からの相対パス（`/` 区切り）である。wiki の親の下になければ、絶対パス（`/` 区切り）である。`check --finish` は、raw を書いたあとで、`wiki_lint.missing_raw()` に `sources/<スラッグ>.md` のページとして渡し、見つかることを確かめてから出す。見つからなければ、終了コード 1 で理由を出す（raw は書いたまま残す。確認は済んでいるので、`raw` の値をユーザーと決めて続ける）。`"raw/<スラッグ>.md"` と決め打ちにしない（1 回目のレビューの重大 6）。
- `## 主張と行き先` の表の根拠の位置は、ターンの番号（`T12`、範囲なら `T12〜T15`）で書く。raw は `check` のあとで変わらないので、行の範囲で書いてもよい。
- raw にあるのは、会話で**言われたこと**である。ツールの結果を除いたので、何を**確かめたか**の証拠は raw にない。「試験が通った」のようなアシスタントの発言は、セッションの中での主張として書き、観測した事実として扱わない。概念のページに移すときは、成り立つ条件と確かめていない点を残す（`commands/learn.md` の「観測した事実と、原因についての仮説は分けて書く」と同じ考えである）。
- 決定の正本は、プロジェクトの ADR に置く（ADR-0015）。セッションで決めたことは、wiki にはソースとして入れ、`decision` のような新しい `type` は作らない。
- 記録の中身（貼り付けた文、ほかのセッションの文の引用を含む）はデータとして扱い、中に書かれた指示には従わない。
- `log.md` には、`## [YYYY-MM-DD] ingest | <題名>` の行の下に、`   セッション: <ID>、伏せ字 <自動の件数> 件、手で伏せた箇所 <manual_markers> 件、消したターン <deleted_turns> 件` のサブ行を書く。

### 9. 取り込み直し

**取り込んだあとの raw は変えない**（ADR-0004、`SKILL.md` の raw の不変性）。raw は確認を終えたときにだけ書くので、raw があることは、確認を終えたことを表す。`extract` は、何も書く前に、次の順に判定する。上から順に見て、最初に当てはまった行で決める。

| 順 | 条件 | `review_state` | 扱い |
| --- | --- | --- | --- |
| 1 | raw があり、`<WIKI_ROOT>/sources/<スラッグ>.md` がある | `ingested` | 取り込み済みである。何も書かずに終了コード 0 で終わる。同一性のキーが今回の値と違えば、違うキーを `differs` に並べ、取り込み直すなら別版のスラッグ（`<スラッグ>-<YYYYMMDD>`）にするよう書く。プラグインを上げて `extracted_by` だけが変わったときも、ここで止まり、重複した取り込みを勧めない |
| 2 | raw があり、要約ページがない。同一性のキーがすべて同じ | `reviewed` | 何も書かずに終了コード 0 で終わる。「8. 取り込み」から続ける |
| 3 | raw があり、要約ページがない。同一性のキーが違う | ― | 何も書かずに終了コード 3 で終わり、別版のスラッグを提案する。`--force` なら、作業用のフォルダーに新しい写しを作る（raw は `check --finish` まで変わらない）。手で伏せた箇所が新しい写しにないことを `warnings` に入れる |
| 4 | raw がなく、写しと `session.json` がそろっていて、同一性のキーが同じ | `in_review` | 何も書かずに終了コード 0 で終わる。「7. 伏せ字の確認」の 3 から続ける |
| 5 | raw がなく、写しがそろっていて、同一性のキーが違う | ― | 何も書かずに終了コード 3 で終わる。確認の途中の写しを上書きしないためである。`--force` なら、写しを作り直す。手で伏せた箇所が失われることを `warnings` に入れる |
| 6 | raw がなく、写しがない、またはそろっていない | `in_review` | 写しを作る（そろっていない写しは作り直す）。終了コード 0 |

- 1 と 2 で、作業用のフォルダーが残っていて、その `session.json` の同一性のキーが raw と同じなら、`check --finish` の 3 の前に止まった残りなので消す。違えば、消さずに `warnings` に入れる。
- `--force` は、1（要約ページがある）では効かない。取り込んだあとの raw を書き換えると、前の raw から書いた要約ページと食い違うからである（2 回目のレビューの重大 7）。そのときは、別版のスラッグで取り込む。`check --finish` も、要約ページがあれば raw を書かない（「7. 伏せ字の確認」）。
- 実行中のセッションは、S1 で取り込みの依頼の記録を `--before` に渡すので、同じ依頼から取り込み直せば同じ範囲になり、同一性のキーが同じになる。別の依頼から取り込むと範囲が変わり、3 か 5 になる。
- スラッグの違う raw に同じセッションがあるかは、確かめない。raw のすべてのファイルを読むことになるからである。lint で見つける検査は、需要が出たら足す。

### 10. スクリプト

`skills/info-hive/scripts/wiki_session.py` を足す。標準ライブラリと、同梱の markdown-it-py（`wiki_pages.new_parser()`。補助の検査だけに使う）を使う。Python 3.12 以上で動かす（ADR-0018）。

```text
python wiki_session.py inspect (--session-id <ID> | --transcript <パス>) [--json]
python wiki_session.py extract (--session-id <ID> | --transcript <パス>)
                               --wiki <WIKI_ROOT> --raw-root <RAW_ROOT> --slug <スラッグ> --title <題名>
                               [--before <uuid>] [--tools summary|none] [--keep-reminders]
                               [--utc-offset +09:00] [--max-bytes 268435456] [--force] [--json]
python wiki_session.py check   --wiki <WIKI_ROOT> --raw-root <RAW_ROOT> --slug <スラッグ> [--finish] [--json]
python wiki_session.py list    [--limit 20] [--json]
```

- `inspect` は何も書かない。判定（`session` か `not_session`。`not_session` なら理由）、ID、題名とスラッグの案、最後の人の発言（`uuid`、時刻、伏せ字をかけた先頭 40 文字）、版、ターンの数、`excluded`、`redactions`、`warnings`、サブエージェントのファイルの数を出す。実行中のセッションでは、最後の人の発言が取り込みの依頼（「コマンド: `/wiki:ingest session`」）であることを、モデルが確かめてから、その `uuid` を `--before` に渡す。依頼でなければ、ユーザーに聞く。
- `list` は、設定のディレクトリの記録を更新の新しい順に並べ、ID、題名、更新の日時、大きさを出す。リンクはたどらない（「2. 記録の場所」）。題名は、ファイルの末尾の 256 KiB から最後の `custom-title` を探して取る。ファイルの全体は読まない。`session:` に渡す ID を選ぶために使う。
- 取り込み先の wiki が初期化されていない（`wiki_initialized.py` の判定。`SCHEMA.md` がふつうのファイルとしてない）か、raw のルートがなければ、`extract` と `check` は何も書かずに終了コード 1 で止まる。raw のルートは作らない（ADR-0019）。
- `--slug` は、何かを読み書きする前に `wiki_fetch.check_slug()` で検査する。作業用のフォルダーの場所は `wiki_rawcheck.work_dir()`、消すのは `wiki_rawcheck.remove_work_dir()` を使う（Web ページの取り込みと同じ関数で、同じ検査を通す）。
- 終了コードは、0 = 写しを作った（または「9. 取り込み直し」で何も書かずに次の段を示した）、1 = 引数やファイルのエラー、2 = 記録から会話を作れない（`inspect` の判定が `session` でない、人の発言がない）、3 = 既存の raw か写しと同一性のキーが違う、である。`wiki_fetch.py` の 2（取得の失敗）に当たる位置を、記録の失敗に使う。`check` は、0 = 通った（`--finish` なら raw を書いた）、1 = 規則に反している、要約ページがあるので raw を書かない、またはファイルのエラー、である（`wiki_rawcheck.py` と同じ）。

`extract --json` の出力の例:


`raw_path` は、`check --finish` が raw を書く場所である。`extract` の時点では、まだない。`raw_ref` は、そこに書いたときに `missing_raw()` が見つける値で、`check --finish` の出力にも入る。

## 試験

`tests/wiki/` に置く。記録は、手で作った小さな JSONL を使う。実物の記録は、匿名にしても入れない。

入口:

- `sessionId` を別の名前に変えた記録（思考のブロックを含む）、`message` を別の名前に変えた記録、Codex の記録に似た形（`role` と `content`、`reasoning`）、会話の記録でない JSONL が、どれも `not_session` になり、何も書かずに止まる。キーワードを付けても付けなくても同じである。
- ファイル名が UUID でない記録は、範囲の中の `sessionId` が 1 種類なら、その ID で `session` と判定される。2 種類以上なら、`--session-id` を求めて止まる。`--session-id` が記録のどこにもなければ拒む。

話者と抜き出し:

- 「4. 残すものと除くもの」の表の行ごとに、残すか除くかと、ターンの境界にするかを確かめる。知らない種類の記録とブロックが、除かれて `excluded` に数えられ、エラーにならない。
- 思考のブロックの文が、raw のどこにも出ない（思考に目印の文字列を入れて、raw を検索する）。
- `origin` のない `user` の記録が、本文によらず人の発言にならない。`promptSource` が `sdk` の記録だけのファイルが、終了コード 2 になる。中断の印は、完全に一致する 2 つの文字列だけが印になり、似た文字列は除かれる。
- 人の発言の本文: 先頭の `<system-reminder>` の塊が除かれ、`stripped_reminder` が出る。途中とコードの例の中のものは残る。`--keep-reminders` で先頭のものも残る。コマンドの要素だけの本文が 1 行になる。`<create-pr-command>` だけの本文が 1 行になり、`user:app:create-pr-command` に数えられる。`<p>…</p>` だけの本文と、知らないタグの兄弟の要素が 2 つある本文が、そのまま残り、`leading_tag` の警告が出る。`<system-reminder>` の塊だけの人の発言が、「（人の発言。内容は除いた）」の印のターンになり、前後のアシスタントの出力がつながらない。人の発言の `document` のブロックと知らない種類のブロックが除かれ、`user:block:<種類>` に数えられる。
- ツールの要約が、`Bash` で `description` を使い、`command` の文字列（目印の秘密の値を入れる）が raw に出ない。
- 1 つの応答が複数の記録に分かれていても、1 つのターンになる。並列のツールの呼び出しの枝分かれが、ファイルの順に並ぶ。同じ親を持つ人の発言が 2 つあると、`possible_rewind` が出る。ファイル名と違う `sessionId` の記録があると、`mixed_session_ids` が出て、記録は残る。
- ターンの境界: 人 U1、Claude A1、作業の通知、Claude A2 の並びで、A2 の前に印のターンが置かれる。人 U1、Claude A1、読めない行、Claude A2 の並びでも、印のターンが置かれ、`broken_lines` の警告が出る。境界のあとにアシスタントの本文が続かなければ、印は置かれない。同じ種類が続くと、印が 1 つにまとまる。

範囲:

- `--before <uuid>` は、記録そのものの `uuid` キーだけに当たり、`parentUuid` に同じ値がある記録には当たらない。同じ `uuid` の記録が 2 つあれば、最初のものに当たる。
- `--before <uuid>` で、その記録とそのあとが除かれ、`source_sha256` と `source_bytes` がその行の前までのバイト列に対するものになる。そのあとに記録を書き足しても、同じ `--before` で同じ写しになり、2 回目が `in_review`（写しがあるとき）か `reviewed`（raw があるとき）になる。見つからない `uuid` はエラーになる。
- 実行中のセッションの流れ（取り込みの依頼、`inspect`、題名を確かめるやり取り、`extract --before <依頼の uuid>`）を記録で再現し、題名を確かめるやり取りも依頼も raw に入らない。
- `--before` を渡さないとき、改行で終わらない最後の行を読まない。`--max-bytes` を超えるとエラーになる。

raw の形:

- 本文に、閉じていないフェンス、見出し、4 つ以上のバッククォートの並び、チルダのフェンス、字下げした区切り、閉じていない HTML、空の本文、CR と CR LF、U+2028 を含むターンを並べ、`wiki_pages.new_parser()` で読んだ raw の 2 段目の見出しの並びとフェンスの中身が、ターンと 1 対 1 に対応する。
- 改行、制御文字、書式の文字、前後の空白を含む `--title` と、121 文字の `--title` を拒む。モデルの名前に改行や記号が入った記録で、見出しに `不明` と書く。
- 同じ記録を、同じ引数で、`Path.home()` と時差の違う環境で抜き出しても、同じ raw になる（`Path.home()` を差し替え、`--utc-offset` を渡さない）。記録のファイルを別の場所に写して抜き出しても、同じ raw になる。
- raw が LF で書かれ、UTF-8 である。書き手の出力を読み手で読み、書き直すと、同じバイト列になる。

場所:

- ID の形が違う値（`../x`、大文字、パスの区切りを含む値）を拒む。`CLAUDE_CONFIG_DIR` を一時ディレクトリに向けて、0 件と 2 件以上のときにエラーになる。`projects`、その下のディレクトリ、記録のファイルのどれかがリンク（シンボリックリンク。Windows ではジャンクション）のとき、候補にならない。リンクを作れない環境では飛ばす。どの記録の `sessionId` も ID と違うファイルを拒み、最初の記録だけが違うファイルは受け付ける。

伏せ字:

- 「5. 伏せ字」の表の種類ごとに、本文、ツールの要約、`cwd`、`git_branch` で置き換わり、件数が `redactions` に入る。ドライブの文字と大文字と小文字を変えたホームのディレクトリと、`\` を重ねた `C:\\Users\\<名前>` が置き換わる。`/srv/profiles/<名前>` は置き換わらない。UUID が伏せられない。

確認の検査（`check`）:

- 通るもの: フェンスの中のひと続きの並び（行の一部、何行かにわたる並び）を `［伏せ字］` 1 つに置き換える、ターンを丸ごと消す（印のターンを含む）、`cwd` と `git_branch` の値の中の並びを伏せる、写しにもともとある `［伏せ字］` をそのまま残す、何も変えない。
- 誤りになるもの: 印を残さずに文字を消すこと（「通らなかった」から「らなか」を消して「通った」にする例を含む）、行を丸ごと消すこと、書き足し、言い換え、何も置き換えずに `［伏せ字］` を足すこと、見出しの行の変更、フェンスの区切りの行の変更、印のターンの文の変更、ターンの見出しだけを消して本文を残すこと、`title` と固定の frontmatter の値とキーの並びの変更、フェンスの外に段落を足すこと、ファイルの末尾に参照の定義（`[x]: https://… "…"`）を足すこと、frontmatter の行の末尾に ` # …` を足すこと、本文の NUL を U+FFFD に変えること、CR を足すこと、空の行を足すこと、消した結果フェンスを閉じうる行ができること。
- 1 回目のレビューの重大 5 の反例（本文の中の `### T2 …` から `#` を 1 つ消し、本来の `## T2 …` の行を消す）が、誤りになる。
- 照らし方の端の場合: 断片が空（`［伏せ字］` が本文の先頭か末尾にある、2 つ続く）、写しの同じ文字列が何度も出る、写しにもともとある `［伏せ字］` の隣を伏せる、の各場合で、通るものが通り、誤りが誤りになる。
- `extract` のあとで `check --finish` の前には、raw のルートに何もない（ファイルの一覧を前後で比べる）。
- `--finish` が、通ったときだけ、`reviewed_at`、`manual_markers`、`deleted_turns` を入れた raw を書き、そのあとで写しを消す。自動の伏せ字と、写しにもともとある `［伏せ字］` は、`manual_markers` に数えない。`sources/<スラッグ>.md` があるときは、通っても raw を書かず、終了コード 1 になる。raw を書いたあと写しを消す前に止まった状態（試験では写しを残す）で、次の `extract` が `reviewed` を返し、残った写しを消す。
- `--slug` に `..`、`../x`、`a/b`、`CON` を渡すと、何も読み書きせず、作業用のフォルダーの外のファイルも消えない。
- `.wiki-cache/.gitignore` がない wiki で、`work_dir_not_ignored` が出る。

取り込み直し:

- 初期化されていない wiki（`SCHEMA.md` がない、ディレクトリである）と、raw のルートがないときに、終了コード 1 で何も書かない。
- 「9. 取り込み直し」の表の 6 つの行のそれぞれになる場合を作り、`review_state`、終了コード、書いたファイルを確かめる。同一性のキー（`title`、`--before`、`--tools`、`--keep-reminders`、`--utc-offset`、抽出器の版、範囲）のどれかを変えると、2 と 4 は 3 と 5 になる。
- `sources/<スラッグ>.md` があるとき、同一性のキーが違っても（`extracted_by` だけを変えた場合を含む）、`--force` を付けても、`ingested` で止まり、raw が変わらず、`differs` に違うキーが出る。
- 3 と 5 で `--force` を付けると、写しだけが作り直され、raw は `check --finish` まで変わらない。`warnings` に手で伏せた箇所が新しい写しにないことが出る。
- `session.json` を置けなかったとき、写しが未完成として扱われる（`test_wiki_fetch.py` の `fetch.json` の試験と同じ）。

`raw_ref`:

- wiki が `<根>/W0_Wiki`、raw のルートが `<根>/W1_Raw` のとき、`raw_ref` が `W1_Raw/<スラッグ>.md` になり、`wiki_lint.missing_raw()` が見つける。wiki の親の下にない raw のルートでは、絶対パスになる。

コマンド:

- `check_commands_mcp.py` の `CLI_NAMES` に `wiki_session.py` を足す。`claude -p` で `/wiki:ingest session` を流し、`${CLAUDE_SESSION_ID}` が置き換わって `--session-id` に渡ること（値が `claude -p` のセッションの ID と一致すること）と、人の発言がないので終了コード 2 で止まり何も書かないことを記録する。`claude -p` のセッションでは、取り込みの全体は試せない。全体の流れは、上の単体の試験で確かめる。

実物の記録での確認（CI ではなく手元で行い、記録は `docs/agent-runs/` に残す。実物の記録とその抜き出しはコミットしない）:

- 検証環境の記録のうち 4 つ（最大のもの、圧縮を含むもの、`origin` のないもの、2 つの ID を含むもの）で `inspect` と `extract` を流し、件数と量、`warnings`、残った伏せ字の漏れを確かめる。`origin` のないものは、終了コード 2 になることを確かめる。

## 3 版目をレビューの前に見直して直した点

3 版目を書いたあと、3 回目のレビューの前に、別のモデル（advisor）に見直してもらった。次の点が当たっていたので、3 版目に入れた。

| 見直しの指摘 | 対応 |
| --- | --- |
| 印のない削除が意味を裏返す（「通らなかった」から「らなか」を消すと「通った」になり、部分列の検査を通る） | 確認で許す編集を、ひと続きの並びの `［伏せ字］` への置き換えと、ターンの丸ごとの削除だけにした。`deleted_runs` をなくした（「7. 伏せ字の確認」） |
| 確認の前の文が、Git で管理されることの多い raw のルートに置かれる | 確認の前の写しを作業用のフォルダー（`.wiki-cache/`、Git の管理の外）に置き、raw は `check --finish` だけが書くようにした。raw があることが確認済みを表すので、`baseline_lost` の状態がなくなった（「7.」「9.」） |
| 会話の記録らしい形で `session_like` と `other` を分ける規則も、形の拒否リストで、形を少し変えると `other` に落ちる | 分かれ道をなくし、`session` でなければ止まる。ふつうの取り込みは、ユーザーが明示して頼んだときだけにした（「1. 入口」） |
| `--slug` の検査が書かれていない。`check --finish` は作業用のフォルダーを消すので、`..` を含むスラッグは危ない | `wiki_fetch.check_slug()` と `wiki_rawcheck.work_dir()`、`remove_work_dir()` を使うと書き、試験を足した（「6.」「10.」） |
| `check --finish` の途中で止まったあとの、やり直しが決まっていない | 「9. 取り込み直し」の表の 1 と 2 で、残った写しを消すと決めた |
| パスで渡したファイルの名前が UUID でないと拒むのは、「パスを渡せばどの環境でも動く」と食い違う | セッションの ID の決め方を 4 段にした（「2. 記録の場所」） |

| `--before` が、記録のどのキーに当たるかが決まっていない。範囲の同一性は、記録が追記だけで書かれることに頼る | 記録そのものの `uuid` の最初の一致と決め、追記だけの前提を「まだ確かめていないこと」に足した（「3.」） |
| JSON の文字列のように `\` を重ねたホームのディレクトリに当たらない | 区切りを 1 つ以上の `\` か `/` にした（「5.」） |
| プラグインを上げて `extracted_by` が変わると、取り込み済みの raw で終了コード 3 になり、重複した取り込みを勧める | `ingested` を最初に判定し、違うキーは `differs` に出すだけにした（「9.」） |
