# 依頼: セッションの取り込みの実装の敵対的レビュー（5 回目）

4 回目のレビュー（`impl-review-4.md`、却下）の指摘を直した版である。目的、対象、範囲の外は 1 回目の依頼（`impl-review-1-task.md`）と同じ。崩れた前提と原因の構造は `impl-root-causes.md` の「4 回目のレビューのあと」にある。

## 直し方

原則は「見つける、決める、変えるを分ける」である。

- `find_secrets()` は、元の文で、すべての規則の範囲を捨てずに見つけ、重なる範囲を和集合にまとめる（置き換えは、まとめた中でいちばん強いもの）。探す文字列は、すべての規則のものを残す。計算は件数の対数倍。
- 人の発言は、元の文で差し込み（先頭の `<system-reminder>`）とコマンドの要素を判定して残す範囲を決め、その範囲に、元の文で見つけた伏せ字の範囲を当てる（`apply_ranges()`）。コマンドの引数は、伏せたあとで 1 行にする。
- 終わりの行のない秘密の鍵の塊は、鍵の本体の形の行（16 文字以上の Base64 の文字だけ。間の空の行は飛ばす）が続くところまでにした。文の最後までにすると、続く人の発言や終了タグを巻き込んでいた。
- 決定のファイルの名前を `<16 進 16 桁>.json` にし、スラッグを入れない（設計の 8 節の変更。作者が承認した）。どの取り込みのものかは中身で見分け、`decide list` が `session_id`、`source_sha256`、`cut_before` を出す。`decide init` も、書く前にスラッグを自動の伏せ字の規則で確かめる。
- ディスクの走査の試験は、ファイルの中身に加えてパスも調べる。

直す前の実装で、足した試験（和集合、構造の判定、件数の多い入力、スラッグ）が落ちることを確かめた。手元の実物の記録 982 ファイルで、`reply_unresolved` は 0 件、自己検査の失敗も 0 件のままだった。

## 特に見てほしいこと

- 見つける、決める、変えるの順になっていない経路が、まだ残っていないか（アシスタントのターン、ツールの要約、`cwd`、`git_branch`、題名、`human_tail`）。
- 和集合にしたことで、伏せ残しや、構造の判定の誤りが新しく起きる入力がないか。
- 決定のファイルの名前を変えたことで、続きから使う手順（S2、11 節）に穴ができていないか。
- 1〜4 回目に崩せなかった点が、直しで崩れていないか。
