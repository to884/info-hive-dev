# 依頼: セッションの取り込みの実装の敵対的レビュー（3 回目）

2 回目のレビュー（`impl-review-2.md`、却下）の指摘を直した版である。目的、対象、範囲の外は 1 回目の依頼（`impl-review-1-task.md`）と同じ。2 回続けて却下されたので、崩れた前提と原因の構造を `impl-root-causes.md` に書いてから直した。

## 直し方（原因の構造で分けたもの）

共通の原因は「検査や変換を、利用者が最後に見る単位より小さい単位にかけ、結果を組み合わせれば全体と同じになる」という仮定だった。直しは、検査と変換を最後に見る単位の全体にかけることである。

- 伏せ字は、アシスタントのブロックごとではなく、つないだターンの本文の全体にかける（ツールの要約は、切る前にもかける）。秘密の鍵の塊は、塊の全体に加えて、本体の各行も `scan` で探す。
- `scan` は、S8 で直したあとのページの全文を受け取り、S9 で書いたあとのファイルの全体を `--path` で照らす。設計の 10 節と S8、S9 の変更で、作者が承認した（設計書に反映し、書いたあとの照合なので見つかったときは作業ツリーに入っていることを「保証しないこと」の 7 に書いた）。
- 列の位置は、正規化で切れない塊ごとの対応から求める（塊ごとの正規化をつないだものが全体と違う行は、列を行の先頭にする）。計算は行の長さに比例する。
- `mark` は重なる一致も数える。
- `check_session_readonly.py` は、2 つの経路の Read が成功し、4 つの Write と Edit がすべて `EPERM` で失敗したときだけ合格にする。
- 試験を繰り返して見つけた前提（Windows の `os.rename` は、同時の名前の変更でアクセスの拒否を返すことがある）も直した。`write` は、例外の種類ではなく、ディスクの行き先を確かめ直して `conflict` か `identical` にする。

## 特に見てほしいこと

- 「最後に見る単位の全体」にかけていない検査や変換が、まだ残っていないか（`cwd`、`git_branch`、ツールの要約、題名、`human_tail`、`title_candidate`、frontmatter の値）。
- `scan --path` と S8、S9 の手順に、書いたものを照らさずに済む経路が残っていないか。
- 1 回目と 2 回目に崩せなかった点が、直しで崩れていないか。
