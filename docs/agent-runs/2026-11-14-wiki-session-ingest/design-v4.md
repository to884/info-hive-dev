## 背景

今のプラグインには、セッションの会話を取り込む手段がない。`/wiki:ingest` は文字起こしを `.md` か `.txt` のソースとして受け付けるが、Claude Code が残すセッションの記録は JSONL で、会話のほかに大量の記録を含む。

2026年11月14日に、検証環境の PC にある 1 つのプロジェクトの記録（61〜63 ファイル）の構造を調べた。会話の文は読み出していない。値は「検証環境の値」の節にまとめた。

- 記録の種類は 21 ある。`uuid` を持つのは `user`、`assistant`、`attachment`、`system` の 4 種類だけで、ほかの 17 種類（`custom-title`、`last-prompt`、`queue-operation` など）は持たない。会話のつながり（`parentUuid`）に入るのは、`uuid` を持つ記録だけである。
- 人の発言は、`origin.kind` が `human` の `user` の記録にある。ただし、Claude が作業している間に人が打った発言は、`attachment` の `queued_command` として届き、あとに `user` の記録として現れない（11 件を確かめた）。`queued_command` は 239 件あり、`origin.kind` は作業の通知 129、なし 73、ほかのセッションからの伝言 26、人 11 だった。
- `promptSource` は話者の判定に使えない。人の発言 632 件のうち 607 件が `sdk` だった（3 版目は、`sdk` を `claude -p` の印とみなしていたが、誤りだった）。
- `origin` のないファイル 7 件は、どれも `claude -p` のセッションだった。1 ファイルは、ファイル名の ID と最初の記録の `sessionId` が違い、2 つの ID の記録を含んでいた。
- `isMeta` の記録の `origin` は、なし 145、伝言 110、作業の通知 1 だった。スキルの本文の読み込みと、ほかのセッションからの伝言が、同じ `isMeta` で届く。
- アシスタントの記録は、内容のブロック 1 つにつき 1 件である。ブロックの種類は `tool_use` 13,602、`thinking` 7,900、`text` 3,486、`server_tool_use` 97、`advisor_tool_result` 84 だった。
- アシスタントの本文（`text`）の記録 3,491 件について、`parentUuid` をたどると、返答の宛先は、人 1,481、作業の通知 674、キューに入った入力 545、`isMeta` 334、`origin` のない記録 259、伝言 113、圧縮の要約 85 だった。たどれないものは 0 件だった。3 版目の規則（`attachment` を境界にしない）では、キューに入った入力への返答 545 件が、前のターンの返答に混ざる。
- `parentUuid` の枝分かれ 2,743 か所は、どれも並列のツールの呼び出しによるもので、巻き戻しは見つからなかった。
- 会話を圧縮しても、圧縮の前の記録は消えない。
- 記録には、利用者が意図せず残した情報（環境変数の一覧の出力に含まれたメールアドレスなど）が入る。セッションの題名やブランチの名前に、顧客の名前が入ることもある。
- 記録の形式は公開された仕様ではない。12 日間で 5 つの版（2.1.309〜2.1.321）が現れた。
- Claude Code 2.1.321 の本体のコードには、本文の `${CLAUDE_SESSION_ID}` をセッションの ID に置き換える箇所がある。プラグインのコマンドの本文がそこを通るかは、確かめていない。記録を残す日数の設定 `cleanupPeriodDays` があり、期間を過ぎた記録は消える。

wiki の書き込みについても調べた（[concurrency-check.md](../agent-runs/2026-11-14-wiki-session-ingest/concurrency-check.md)）。

- 取り込みの手順 5〜8 で、要約ページ、関連ページ、`index.md`、`log.md` を書くのはモデルで、Claude Code の Write と Edit のツールを使う。排他はない。ロックを持つのは、グラフの抽出（`.extract.lock`）と閲覧だけである。
- Claude Code の Write は、読んだあとに変わったファイルを書き直すのを拒む。Edit はディスクの今の内容に当たるので、先に足されたほかの行を消さない。しかし、Edit も中では「読む、直す、書く」で原子的ではない。10 ミリ秒ごとに書き換えるプロセスと並べると、Edit が成功と報告した行が消え、相手の 1,500 行のうち 7 行も消えた。どちらにも誤りは出なかった。
- lint は、索引に足りない項目と、ログの抜けを見つけない。

## 目的

- 1 回の `/wiki:ingest` で、Claude Code のセッションの会話を、raw の原本と、記事の形のソースの要約ページとして wiki に入れる。
- モデルの思考は、raw にも wiki にも入れない。
- 秘密の情報と個人の情報は、人の確認を経ずに、Git で管理される場所（raw のルート、wiki）に入らない。確認の前の文は、ディスクに置かない。
- raw は、記録の範囲、引数、抽出器の版、人の決定から、スクリプトが決まった手順で作る。同じ入力からは、どの PC でも同じバイト列ができる（時差は引数として入力に含む）。記録の SHA-256 で出所を確かめられるのは、元の記録が残っている間だけで、記録が消えたあとは raw が唯一の原本になる（ADR-0004 と同じ割り切り）。
- 取り込んだあとの raw は変えない。
- 決まった処理（抜き出し、伏せ字、raw の生成、ハッシュ、差分の計算、秘密の検査、索引とログへの追記、書き込み）は、モデルを使わず Python で行う。モデルが行うのは、判断の要る処理（伏せる候補を探す、記事と関連ページの文を書く、パッチの競合を直す）だけである。
- wiki に書く段は、wiki 単位のロックを持つ 1 つのプロセスで、短い時間で終える。確認と記事を書く間は、ロックを持たない。
- 開発用の PC の置き場所や記録の形に、仕様を合わせない。記録の形が変わっても、漏れる側に倒れない。

## 前提にすること

- **Claude Code のツールを通らない書き手は考えない**（作者の判断の 6）。エディター、Codex、そのほかのスクリプトが wiki を同時に書き換えることは、起きないものとする。
- ロックは、書く段のプロセス（`wiki_apply.py apply`）どうしの排他である。モデルが Claude Code の Edit で wiki を直接書き換える手順（今の Web ページと PDF の取り込みの手順 6、`/wiki:query` と `/wiki:learn` の保存）は、ロックに参加しない。それらと並べたときの扱いは、「作者が決めること」の 1 にある。

## 範囲に入れないこと

| 入れないこと | 理由 |
| --- | --- |
| サブエージェントの記録 | 本体と別のファイルで、量が多い。見つけたファイルの数だけを報告する |
| デスクトップアプリの Export の zip | 中の構成を確かめていない。展開した JSONL のパスを渡せば使える |
| Claude Code 以外のエージェントの記録 | 形式が違う。`inspect` が認めずに止まる |
| `claude -p` のセッション | 人の発言が記録されない。終了コード 2 で止まる |
| ツールの結果の中身 | 雑音と秘密の情報の大半がここにある。ツールの呼び出しは 1 行の要約だけを残す |
| 日本語でないセッションの翻訳 | 需要が出たら決める |
| セッションの終わりにフックで自動で取り込むこと | 取り込みは、依頼されたソースだけを明示して行う |
| 取り込んだあとの raw の書き直し（`--force`） | ADR-0004 の不変性と食い違う。範囲や決定を変えたら、別版のスラッグにする |
| 意味の重複の検出 | 同じ概念を別のスラッグで作ること、同じセッションを別のスラッグで 2 回取り込むことは防がない |

## 決めること

### 1. 入口

- 引数は `session`（実行中のセッション）、`session:<ID>`、`session:<パス>`、`<パス>.jsonl` である。引数が既存のファイルのパスなら、キーワードより先にファイルとして扱う。
- 新しいコマンドは足さず、`/wiki:ingest` の引数で受け付ける（ADR-0015）。
- `.jsonl` は、キーワードの有無によらず `inspect` にかける。`verdict` が `session` でなければ止まる。ふつうの取り込みに進むのは、ユーザーが明示して頼んだときだけである。
- `verdict` が `session` になる条件は、範囲の中に「人の発言」（4 節の区分 H）が 1 件以上あり、どの行も JSON のオブジェクトで、`uuid` のある記録が `type` を持つことである。`promptSource` は見ない。
- 実行中のセッションの ID は、`commands/ingest.md` の本文に `${CLAUDE_SESSION_ID}` と書いて得る。置き換わらなければ、ユーザーに ID かパスを聞く。

### 2. 記録の場所と ID

- ID からパスへの変換は `locate` だけが行う。ほかのコマンドは、すべて `--transcript <パス>` を取り、`--session-id` は任意である（3 回目の軽微 2）。
- `locate` は、`<設定のディレクトリ>/projects/*/<ID>.jsonl` を 1 階層だけ探す。設定のディレクトリは `CLAUDE_CONFIG_DIR`、なければ `~/.claude` である。ID は小文字の UUID でなければ拒む。設定のディレクトリより下のシンボリックリンクとジャンクション（`projects`、その下のディレクトリ、ファイル）はたどらない。0 件か 2 件以上ならエラーにする。プロジェクトのディレクトリの名前は組み立てない。
- `session_id` は、ファイル名（拡張子を除く）が UUID ならそれ、範囲の中の `sessionId` が 1 種類ならそれ、どちらでもなければ `--session-id` を求めて止まる。`--session-id` を渡したら、記録のどこかの `sessionId` にあることを確かめる。決めた ID と違う `sessionId` の記録があれば、`mixed_session_ids` の警告を出す（記録は残す）。

### 3. 範囲

- 範囲は、ファイルの先頭から、`--before <uuid>`（記録そのものの `uuid` キーが最初に一致した記録の、行の先頭）まで、または最後の改行までである。改行で終わらない最後の行は読まない。
- `source_sha256` と `source_bytes` は、範囲のバイト列から取る。ファイルの大きさの上限は既定で 256 MiB とする。
- UTF-8 か JSON として読めない行は飛ばし、`broken_lines` に数えて警告する。読めない行が、返答の宛先をたどる途中にあれば、宛先は「不明」になる（4 節）。

### 4. 分類と返答の宛先

**`uuid` のない記録は、読み飛ばす**（作者の判断の 1）。種類ごとに `ignored` に数える。観測した 17 種類（`custom-title`、`last-prompt`、`queue-operation`、`file-history-snapshot`、`api-request` など。スクリプトの定数にする）にない種類が `uuid` なしで現れたら、読み飛ばしたうえで `unknown_uuidless_type` の警告を出す。会話の入力が `uuid` のない新しい形で届くと、境界と印が失われる。これは限界として認める（「保証しないこと」の 3）。

`uuid` のある記録は、次の表で分ける。表にないものは、すべて境界 X である。

| 区分 | 条件 |
| --- | --- |
| 人の発言 H | `user` で、`origin.kind` が `human`、かつ `isMeta`、`isCompactSummary`、`isSidechain` のどれも真でない。または、`attachment.type` が `queued_command` で、`attachment.origin.kind` が `human`、かつ `prompt` が文字列 |
| 中断 I | `user` で `origin` がなく、本文が `[Request interrupted by user]` か `[Request interrupted by user for tool use]` と完全に一致する |
| アシスタント A | `assistant` で、`isSidechain` と `isApiErrorMessage` が真でない |
| 透過 T | 本文が `tool_result` のブロックだけの `user`。`attachment` のうち、観測した文脈の差し込みの種類の一覧（スクリプトの定数）にあり、`queued_command` でなく、`origin` を持たないもの。`system` のうち、`subtype` が `stop_hook_summary`、`informational`、`api_error` のもの |
| 境界 X | それ以外のすべて。`origin.kind` が `human` でない `user`、`isMeta`、`isCompactSummary`、知らない `type`、一覧にない `attachment`、`human` でない `queued_command`、`prompt` が文字列でない `queued_command`、`system` の `compact_boundary` と `local_command` と知らない `subtype` を含む |

- **アシスタントのブロック。** `text` は残す。`tool_use` と `server_tool_use` は 1 行の要約にする（5 節）。ほかのブロック（`thinking`、`redacted_thinking`、`advisor_tool_result`、知らない種類）は除く。
- **返答の宛先。** 本文を持つ A の記録ごとに、`parentUuid` をたどる。たどる途中で通ってよいのは、A と T の記録である。H、I、X のどれかに着いたら、それが宛先である。親が範囲にないか、範囲の中の読めない行に当たったら、宛先は「不明」である。たどった回数が範囲の記録の数を超えたら、循環とみなして「不明」にし、`reply_unresolved` の警告を出す（4 体のレビューで D と C が指摘した、A の区分を通れない規則の欠落を直した）。
- **ターン。** H と I は、つねにターンになる。宛先が X か「不明」の A があれば、その宛先の位置に印のターンを 1 つ置く（宛先として参照されない X には印を置かない）。続く A の本文は、宛先が同じ間だけ 1 つのターンにまとめる。
- **印の文。** 宛先の区分ごとに、スクリプトが決めた文だけを使う。例は「（バックグラウンドの作業の通知。内容は除いた）」「（ほかのセッションからの伝言。内容は除いた）」「（スキルの本文などの差し込み。内容は除いた）」「（人の発言でない記録。内容は除いた）」「（返答の対象の記録が範囲にないか、読めない）」。

### 5. 本文の加工と、ツールの要約

人の発言の本文は、次の順に加工する。

1. 本文の先頭に続く `<system-reminder>`〜`</system-reminder>` の塊を除き、`stripped_reminder` の警告を出す。`--keep-reminders` で除かない。
2. 本文が `<command-name>`、`<command-message>`、`<command-args>` の要素と空白だけなら、「コマンド: `/<名前> <引数>`」の 1 行にする。
3. 本文の全体が既知のアプリの要素 1 つ（今は `<create-pr-command>` だけ）なら、中身を除いた 1 行にする。
4. ほかはそのまま残す。本文が `<` で始まれば、`leading_tag` の警告を出す。
5. 画像のブロックは「［画像］」の 1 行にする。`text` と `image` のほかのブロックは除き、`user:block:<種類>` に数える。
6. 空になった発言は、「（人の発言。内容は除いた）」の印のターンにする。

1〜3 は本文の形で意味を決める規則で、人が同じ形の文を資料として書いたときと見分けられない。限界として認める（「保証しないこと」の 4）。

ツールの呼び出しは、ツールごとに決めた入力の項目を 1 つだけ使い、`[ツール] <名前> <値>` の 1 行にする（`Read`、`Edit`、`Write`、`NotebookEdit` は `file_path`、`Grep` と `Glob` は `pattern`、`Bash` と `PowerShell` は `description`、`WebFetch` は `url`、`WebSearch` は `query`、`Agent` は `description`、`Skill` は `skill`、ほかは名前だけ）。値は改行を空白に変え、120 文字で切る。`--tools none` で残さない。

### 6. 自動の伏せ字

残す本文、ツールの要約、`cwd`、`git_branch` に、次の規則で伏せ字をかける。規則は記録と引数だけで決まり、実行する PC の値は使わない。

| 種類 | 規則 | 置き換え |
| --- | --- | --- |
| メールアドレス | `ローカル部@ドメイン` の形 | `［メール］` |
| ホームのディレクトリ | `<ドライブ>:` のあとに 1 つ以上の `\` か `/`、`Users`、区切り、名前（大文字と小文字を区別しない）。`/Users/<名前>`、`/home/<名前>` | `~` |
| 秘密の値 | 既知の接頭辞の値（`sk-`、`ghp_`、`gho_`、`github_pat_`、`xoxb-` など、`AKIA` で始まる 20 文字、`eyJ` で始まる 3 つに分かれた JWT）、`-----BEGIN … PRIVATE KEY-----` の塊、`token`、`secret`、`password`、`api_key` などの名前に続く `=` や `:` の値 | `［伏せ字］` |

これを当てた結果を「土台」と呼び、その SHA-256 を `base_sha256` とする。

### 7. raw の形

- 文法は 3 版目と同じである。frontmatter、空の行、ターンの並び。各ターンは、見出しの行、空の行、本文（フェンスか印の文）、空の行である。LF だけで改行し、最後は 1 つの LF で終わる。UTF-8 で書く。
- 見出しは `## T<n> ユーザー（<時刻>）`、`## T<n> Claude（<モデル>、<時刻>、T<m> への返答）`、`## T<n> 印（<時刻>）` のどれかである。宛先が「不明」なら `不明への返答` と書く。
- フェンスは、本文の中の最も長いバッククォートの並びより 1 つ長くし、3 以上にする。情報の文字列は `text` である。
- フェンスの外に置くのは、スクリプトが決めた語、整形した時刻、ターンの番号、形を検査したモデルの名前（英数字と `._:-[]` だけの 64 文字以内。外れたら `不明`）だけである。題名の見出しは置かない。
- 確認で消したターンは、見出しを残し、本文を「（確認で消した）」の印の文にする。番号と「T<m> への返答」を保つためである。
- frontmatter は平らなキーで、値は文字列か数である。`title`、`source_kind`（`"claude-code-session"`）、`session_id`、`cwd`、`git_branch`、`started_at`、`ended_at`、`claude_code_versions`、`source_sha256`、`source_sha256_of`（`"jsonl-range"`）、`source_bytes`、`cut_before`、`extracted_by`、`tools`、`keep_reminders`、`utc_offset`、`turns`、`excluded_records`（`"種類=数, …"`）、`auto_redactions`、`manual_redactions`、`dropped_turns` をこの順に書く。**実行の時刻は書かない**（3 回目の軽微 3）。
- 時刻は `--utc-offset`（既定は `+00:00`）で直す。`/wiki:ingest` は、ユーザーの時差を渡す。時差を変えると別のバイト列になり、別の取り込みになる。
- 書いたあとで、スクリプトは自分の出力を同梱のパーサー（`wiki_pages.new_parser()`）で読み、2 段目の見出しとフェンスがターンと 1 対 1 に対応することを確かめる。通らなければ書かない。

### 8. 確認と決定

- **`show`** は、土台に決定を当てた、raw と同じバイト列を、ターンの範囲（`--turns T1-T20`）を指定して標準出力に出す。ファイルは書かない。モデルは全体を分けて読み、伏せる候補をユーザーに示す。何を伏せるかはユーザーが決める。
- **決定のファイル**は `<WIKI_ROOT>/.wiki-cache/session/<スラッグ>-<乱数>.json` で、`decide init` が作る。中身は `format`、`extracted_by`、`session_id`、`source_sha256`、`source_bytes`、`cut_before`、`options`、`base_sha256`、`spans`（ターンの番号か `cwd` か `git_branch` と、その中の開始と終わりの位置）、`drop`（消すターンの番号）である。**伏せる文字列そのものは書かない。** 位置だけなので、このファイルがコミットされても秘密は漏れない。
- **`decide mark --target <T5|cwd|git_branch> --text <文字列> (--nth <k> | --all) [--all-turns]`** は、土台の中の完全一致を探して位置に変え、`spans` に足す。一致がなければ拒む。`--nth` も `--all` もなく 2 か所以上に一致すれば、曖昧なので拒む。
- **`decide drop --turn <T9>`** は、消すターンを足す。
- **`show --meta`** は、`base_sha256`、`render_sha256`（raw の全体のバイト列の SHA-256）、文字数、ターン数、`manual_redactions`（重なりをまとめた区間の数）、`dropped_turns`、残った警告を出す。モデルはこれを示し、ユーザーの承認を得る（S5）。
- 題名とスラッグに、伏せた区間の文字列か、自動の伏せ字の規則に当たる文字列が入っていれば、`show --meta` と書く段のどちらも拒む。題名は 1 行で、制御文字と書式の文字を含まず、前後に空白がなく、120 文字以内でなければならない。スラッグは `wiki_fetch.check_slug()` で検査する。
- 確認の前の文は、標準出力と、いま動いているセッションの記録（`~/.claude` の下）にしか現れない。`decide mark --text` に渡した文字列も、いま動いているセッションの記録に残る（「保証しないこと」の 5）。

### 9. wiki の変更を用意する（`wiki_apply.py`）

wiki に書く変更は、モデルが作業用のフォルダーに用意し、スクリプトが差分にして人に見せる。書くのは S8 の `apply` だけである。`wiki_apply.py` は、セッションの取り込みに限らない、wiki に書く段の共通の道具である。

**作業用のフォルダー。** `wiki_apply.py begin --wiki <WIKI_ROOT> --name <スラッグ>` が、`<WIKI_ROOT>/.wiki-cache/apply/<スラッグ>-<乱数>/` を作り、そのパスを出す。

- wiki のディレクトリか、その祖先に `.git`（ディレクトリかファイル）があれば、Git の作業ツリーの中とみなす。そのときは `git check-ignore -q` でこのフォルダーが無視されることを、`git ls-files` で追跡されているファイルがないことを確かめる。無視されない、追跡されている、または `git` を実行できずに確かめられないときは、作らずに止まる（終了コード 1）。警告だけにはしない（3 回目の重大 1）。`.git` がどの祖先にもなければ、確かめずに作る。
- このフォルダーに置くのは、確認を終えた raw から書いた記事の文と、関連ページの直しである。確認の前の会話の文は置かない。

**変更の種類。** 4 つある。どれも wiki のルートからの相対パスで指す。

| 種類 | 登録のしかた | 中身 | 書く段での当て方 |
| --- | --- | --- | --- |
| `raw` | `wiki_session.py stage-raw --apply-dir <D> --transcript <P> --decisions <F> --slug <S> --raw-root <R> --expect-sha256 <H> …` | raw の中身は置かない。生成に要る引数と `render_sha256` だけを `plan.json` に書く | 記録と決定から作り直し、ハッシュが一致したら、重ねて書かない形で置く |
| `create` | `wiki_apply.py create --apply-dir <D> --path sources/<S>.md` | モデルが `<D>/after/<パス>` に新しいファイルを書く | 行き先がなければ、重ねて書かない形で置く |
| `patch` | `wiki_apply.py track --apply-dir <D> --path concepts/<x>.md` | スクリプトが今の中身を `<D>/before/<パス>` と `<D>/after/<パス>` に写す。モデルは `after` の側を Edit で直す | 3 方向で当てる（下） |
| `append` | `wiki_apply.py add-block --apply-dir <D> --path index.md --section "<見出しの行>" --line "<行>" [--line "<行>" …]`、`--path log.md --line "<見出しの行>" --line "<サブ行>"`（`--section` なしはファイルの末尾） | 1 行以上のまとまり（ブロック）と見出しを `plan.json` に書く | 見出しの節の末尾（次の同じか上の段の見出しの前）か、ファイルの末尾に、ブロックをまとめて足す |

- 索引とログは、2 つの取り込みがほぼ同じ場所に行を足すので、パッチにすると競合しやすい。そこで、足すだけの `append` にする。足すのは行ではなくブロックで、ログの見出しの行とサブ行は 1 つのブロックにする。ブロックの全体が、同じ並びで続けて、行き先にすでにあれば「済み」とみなす。1 行だけが一致しても「済み」にしない（ほかの取り込みのサブ行と同じ文の行が、たまたまあることがあるため）。
- 関連ページの直しは、場所も中身も決まっていないので、パッチにする。
- 要約ページと新しいページは、`create` にする。

**`diff`。** `wiki_apply.py diff --apply-dir <D>` は、次を行う。

1. 登録された変更の全体から、統一差分（`patch` は `before` と `after`、`create` は空からの差分、`append` は足す行）を作り、標準出力に出す。
2. パスを検査する。どのパスも wiki のルートの中にあり、途中の階層と行き先が、シンボリックリンクでもジャンクションでもない。行き先の実体が raw のルートの中にない（4 体のレビューで C が示した、ジャンクションを経由して raw を書き換える反例を防ぐ）。`raw` の行き先は、raw のルートの直下である。
3. 秘密を検査する。検査する文は、足す文（`create` の全体、`patch` で足す行、`append` のブロック）と、すべての変更のパス（ファイル名を含む）と、`append` の見出しである。そこに、自動の伏せ字の規則に当たる文字列がないことを確かめる。さらに、計画に `raw` の変更があれば、**かならず**、禁じる文字列の集まりに当たる文字列がないことを確かめる。禁じる文字列は、`stage-raw` が `plan.json` に書いた記録のパスと決定のファイルから、メモリの中で作る。中身は、決定で伏せた区間の元の文字列と、自動の伏せ字が置き換えた元の文字列（メールアドレスの全体とローカル部、ホームのディレクトリの名前の部分、秘密の値）である。ディスクにもコマンドの引数にも出さない。比べるときは、両方を NFKC で正規化し、大文字と小文字をそろえる。見つかったら、場所（パスと行）と規則の名前だけを出し、文字列は出さない。終了コード 1 にする。
4. 変更の全体（種類、パス、`before` と `after` のハッシュ、足すブロック、`raw` の `render_sha256`、記録の `source_sha256` と決定のファイルの SHA-256）から `plan_sha256` を作って出す。秘密の検査の入力も `plan_sha256` に縛られるので、検査を飛ばした計画や、別の決定で検査した計画は、`apply` で一致しない。

モデルは、差分と `plan_sha256` をユーザーに示し、承認を得る（S7。作者の判断の 2 の軽い形）。

### 10. 書く段（`wiki_apply.py apply`）

`wiki_apply.py apply --apply-dir <D> --expect-sha256 <plan_sha256> [--json]` は、1 つのプロセスで次を行う。

0. **ロックの前に、wiki に関わらない準備をする。** `raw` の変更があれば、記録を読み直し、決定を当てて raw のバイト列を作り、`render_sha256` が一致することを確かめる。一致しなければ、何も書かずにエラーにする（記録か決定が変わった）。記録を読むのは時間がかかる（検証環境の最大は 51.9 MB）が、wiki の状態によらないので、ロックの外で行う。9 節の秘密の検査も、ここで行う。

1. **ロックを取る。** `<WIKI_ROOT>/.wiki-cache/apply.lock` を開き、OS のファイルのロック（`wiki_graph_common._try_lock()`。Windows は `msvcrt.locking`、POSIX は `fcntl.flock`）を取る。取れなければ、0.2 秒ごとに試し、既定で 60 秒待つ（`--wait`）。取れなければ、何も書かずに終了コード 4 で終わる。プロセスが落ちれば、OS がロックを外すので、残ったロックを消す手順は要らない。
2. **検査する。** wiki が初期化されていることを `wiki_initialized` で、`plan_sha256` が今の作業用のフォルダーの中身から作った値と一致することを確かめる。9 節のパスの検査をやり直す（行き先の状態は、ロックを取ってから見る）。
3. **新しい中身を、すべてメモリの中で作る。** 変更ごとに、次の表で決める。1 つでも「競合」があれば、何も書かずに 6 へ進む。

| 種類 | 今の行き先 | 結果 |
| --- | --- | --- |
| `raw` | ない | 0 で作ったバイト列を「書く」 |
| 同上 | ある。0 で作ったバイト列と同じ | 「済み」 |
| 同上 | ある。違う | 「競合」（`slug_taken`） |
| `create` | ない | 「書く」 |
| 同上 | ある。`after` と同じ | 「済み」 |
| 同上 | ある。違う | 「競合」 |
| `patch` | `before` と同じ | `after` を「書く」 |
| 同上 | `after` と同じ | 「済み」 |
| 同上 | どちらとも違う | `before` から `after` への差分の塊（前後 3 行の文脈つき）ごとに、今の中身と照らす。塊の「当てる前」（文脈と消す行）がただ 1 か所に完全に一致し、「当てたあと」（文脈と足す行）が一致しなければ、その塊を当てる。「当てたあと」がただ 1 か所に一致し、「当てる前」が一致しなければ、その塊は当て済みとみなす。どちらでもなければ「競合」。当てる塊があれば「書く」、全部が当て済みなら「済み」 |
| `append` | ブロックの全体が、同じ並びで続けて、すでにある | 「済み」 |
| 同上 | ない。`--section` の見出しがただ 1 つある、または `--section` がない | 「書く」 |
| 同上 | ない。見出しがないか 2 つ以上ある | 「競合」 |

4. **書く。** 順に、`raw`、`create`、`patch`、`append`（索引）、`append`（ログ）を書く。`raw` と `create` は、一時ファイルに書いて fsync し、重ねて書かない形で置く（POSIX は `os.link` のあとに一時ファイルを消す。Windows は `os.rename` で、行き先があれば `FileExistsError` になる）。リンクを作れないファイルシステムでは、書かずに終了コード 1 にする。`patch` と `append` は、一時ファイルに書いてから `os.replace` で置き換える（名前の変更の試し直しは `wiki_fetch.replace_with_retry()` を使う）。改行と文字コードは、行き先のファイルの今のもの（LF か CRLF、UTF-8 の BOM の有無）を保つ。
5. **読み直す。** 書いたファイルを読み、作った中身と一致することを確かめる。`raw` は、`raw_ref`（wiki の親からの相対パス。親の下になければ絶対パス）を作り、`missing_raw()` で見つかることを確かめる。
6. **ロックを外す。** 「競合」があれば、終了コード 3 で、競合した変更のパスと理由を出す。なければ終了コード 0 で、変更ごとの結果（`written`、`already`）と `raw_ref` を出し、作業用のフォルダーを消す（`--keep` で残す）。

**ロックを持つ時間。** 1〜6 は、モデルを呼ばず、記録も読まない 1 つのプロセスの区間なので、書くファイルの数と大きさの分だけで終わる（ふつうは 1 秒より短い見込み。実装で測る）。記録を読む 0 と、確認と記事を書く S1〜S7 の間は、ロックを持たない。そのため、ほかの取り込みが長く止まることはない。

**途中で止まったとき。** 4 の途中でプロセスが落ちると、書いた変更と書いていない変更が混ざる。同じ `apply` をもう一度実行すると、書いた変更は 3 の表で「済み」になり、残りだけを書く。3 方向で当てた `patch` も、塊ごとの「当て済み」の判定で「済み」になる。どの変更も、今の中身を見て「済み」と判定できるので、書いたかどうかの記録（日誌）は要らない。ただし、当て済みの判定は、塊の「当てたあと」が今の中身のほかの場所にたまたま一致しないことに頼る。一致すれば「競合」になり、モデルが直す（漏れる側にも、二重に当てる側にも倒れない）。

**競合したとき（S9）。** 競合は、ほかの取り込みが、用意したあとに同じファイルを書き換えたときに起きる。モデルは、競合したファイルを今の中身から用意し直す（`patch` なら `track` をやり直して `after` を直す。`create` と `raw` の競合は、スラッグを変えるか、取り込みをやめるかをユーザーに聞く）。用意し直したら、`diff` をやり直して差分を示し、承認を得てから、`apply` をやり直す。承認をやり直すのは、競合の直しで中身が変わるからである。

### 11. 同じ取り込みと取り込み直し

- **同じ取り込み**とは、作った raw のバイト列が、`<RAW_ROOT>/<スラッグ>.md` のバイト列と一致することである。出力を変える入力（範囲、ID、引数、抽出器の版、決定、題名、時差）は、自動的に同一性に含まれる（3 回目の重大 2）。
- raw は上書きしない。`--force` はない。範囲や決定を変えたら、別版のスラッグ（`<スラッグ>-<YYYYMMDD>`）にする。
- **取り込みが済んだかは、スクリプトは判定しない**（3 回目の重大 4）。`inspect --wiki <W> --raw-root <R> --slug <S>` は、raw の有無と、raw の frontmatter の `session_id`、`source_sha256`、`cut_before`、要約ページの有無、残っている作業用のフォルダーを、情報として出す。そこから先は、Web ページの W2 と同じく、モデルが wiki を見てユーザーに聞く。
- 決定のファイルは、`write` に当たる `apply` が成功したら消す。止まったときは残り、`base_sha256` が今の土台と一致する限り、続きから使える。一致しなければ拒む。

### 12. スクリプト

`skills/info-hive/scripts/wiki_session.py` と `wiki_apply.py` を足す。Python 3.12 以上で、標準ライブラリと、同梱の markdown-it-py（自己検査だけ）を使う。

```text
python wiki_session.py locate    --session-id <ID> [--json]
python wiki_session.py list      [--limit 20] [--json]
python wiki_session.py inspect   --transcript <P> [--session-id <ID>] [--before <uuid>] [--wiki W --raw-root R --slug S] [--json]
python wiki_session.py show      --transcript <P> [共通の引数] --title <T> [--decisions <F>] [--turns T1-T20] [--meta] [--json]
python wiki_session.py decide    init|mark|drop|list --decisions <F> ...
python wiki_session.py stage-raw --apply-dir <D> --transcript <P> [共通の引数] --title <T> --decisions <F>
                                 --raw-root <R> --slug <S> --expect-sha256 <render_sha256>

python wiki_apply.py begin    --wiki <W> --name <S>
python wiki_apply.py create   --apply-dir <D> --path <相対パス>
python wiki_apply.py track    --apply-dir <D> --path <相対パス>
python wiki_apply.py add-block --apply-dir <D> --path <相対パス> [--section <見出しの行>] --line <行> [--line <行> …]
python wiki_apply.py diff     --apply-dir <D> [--json]
python wiki_apply.py apply    --apply-dir <D> --expect-sha256 <plan_sha256> [--wait 60] [--keep] [--json]
python wiki_apply.py abort    --apply-dir <D>
```

共通の引数は `[--session-id <ID>] [--before <uuid>] [--tools summary|none] [--keep-reminders] [--utc-offset +09:00]` である。

| 終了コード | 意味 |
| --- | --- |

### 13. `commands/ingest.md` に足す手順

手順 2 に、ソースが `session`、`session:…`、`.jsonl` なら S1〜S10 に進む、と足す。手順 4〜8 は、セッションの取り込みでは S6〜S10 に置き換わる。

- **S1.** 記録のパスを決める。実行中のセッションなら、`${CLAUDE_SESSION_ID}` を `locate` に渡す。置き換わらなければ、ユーザーに聞く。`inspect` を実行し、`verdict` が `session` でなければ止まる。実行中のセッションなら、`human_tail` から取り込みの依頼の `uuid` を確かめて `--before` にする。
- **S2.** 題名とスラッグをユーザーと決める。`inspect --wiki --raw-root --slug` で、raw と要約ページと作業用のフォルダーの有無を見る。あれば、11 節に従ってユーザーに聞く。
- **S3.** `decide init` を実行し、`show --turns` で全体を分けて読む。
- **S4.** 伏せる候補とターンを示し、ユーザーが決めたものを `decide mark` と `decide drop` に入れる。
- **S5.** `show --meta` の件数、警告、`render_sha256` を示し、承認を得る。
- **S6.** `wiki_apply.py begin` を実行し、`stage-raw` で raw を登録する。手順 4（要点の話し合い）と手順 5（関係するページを洗い出す）を行う。要約ページを `create` で、関連ページの直しを `track` と `after` の Edit で、索引の行とログの見出しの行とサブ行を `add-block` で用意する。手順 7 の型付きのエッジ（ページの frontmatter の `graph.relationships[]`）を足すなら、ここで、同じ `create` と `patch` の中に入れる。要約ページの `raw` には、`stage-raw` が出す `raw_ref` を書く（`apply` が書いたあとに `missing_raw()` で確かめる）。根拠の位置はターンの番号で書く。ログのサブ行には `manual_redactions` と `dropped_turns` を書く。伏せると決めた文字列を、要約ページと関連ページに書かない。
- **S7.** `wiki_apply.py diff` を実行する。秘密の検査で見つかったら、その場所を直して `diff` をやり直す。差分と `plan_sha256` を示し、承認を得る。
- **S8.** `wiki_apply.py apply --expect-sha256` を実行する。
- **S9.** 終了コード 3 なら、10 節の「競合したとき」に従う。終了コード 4 なら、ほかの取り込みが書いているので、少し待ってやり直すかをユーザーに聞く。
- **S10.** 手順 7 のグラフの lint と抽出を行う（`wiki_graph_lint.py` は読むだけ、`wiki_graph_extract.py` はグラフの DB を既存のロックで書く）。ログのグラフのサブ行（`   グラフ: ノード +N、型付きエッジ +M`）は、Edit で書かず、もう 1 回 `begin`、`add-block`、`diff`、承認、`apply` で書く。手順 8（報告）を行い、決定のファイルを消す。S1〜S10 の間に、モデルが Edit と Write で wiki と raw のルートを直接書くことはない。

## 保証しないこと

1. **人が実際に読んで決めたこと。** モデルが `show` と `diff` をユーザーに示さずに進めることは、機械では止められない。手順の遵守に頼る。
2. **規則と人の両方が見落とした個人の情報。** `mark` は完全一致で探す。`diff` の秘密の検査は、NFKC と大文字と小文字をそろえた一致で、伏せた文字列そのものだけを探す。言い換え、ローマ字、略称は見つけない。
3. **`uuid` のない新しい形で届く入力。** 読み飛ばすので、内容は漏れないが、境界と印が失われ、前後の返答が 1 つのターンにつながる。知らない種類なら `unknown_uuidless_type` の警告で気づける（作者の判断の 1）。
4. **本文の形で決める規則。** 先頭の `<system-reminder>`、コマンドの要素、`<create-pr-command>` を、人が同じ形で書いたときと見分けられない。警告と引数で戻せるのは `<system-reminder>` だけである。
5. **いま動いているセッションの記録。** `show` の出力、`decide mark --text` の文字列、伏せる候補の相談は、いま動いているセッションの記録（`~/.claude` の下）に残る。設定のディレクトリが Git の作業ツリーの中にある配置では、そこから漏れうる。あとでその範囲を取り込むときは、もう一度、伏せ字と確認を通る。
6. **ロックに参加しない書き手との競合。** 今の Web ページと PDF の取り込みの手順 6、`/wiki:query` と `/wiki:learn` の保存は、モデルが Edit で直接書くので、ロックを取らない。それらと `apply` が数ミリ秒の中で同じファイルを書くと、どちらかの変更が消えうる（「作者が決めること」の 1）。Claude Code のツールを通らない書き手は、考えない（前提）。
7. **取り込みの手順の完了。** 手順 7（グラフ）と手順 8（報告）が済んだかは、人の判断に頼る。
8. **意味の重複。** 同じ概念を別のスラッグで作ることと、同じセッションを別のスラッグで 2 回取り込むことは防がない。
9. **書いたあとに見つかった秘密。** 人が raw と要約ページを消し、Git の履歴も直す。プラグインは自動では直さない。
10. **一時ファイルの残り。** 電源が切れたときなど、確認済みの文の一時ファイルが raw のルートと wiki に残りうる。名前は `.wiki-apply-*.tmp` で、`inspect` が見つけて報告する。

## 試験

`tests/wiki/` に置く。記録は、手で作った JSONL と、合成の記録を作る生成器を使う。実物の記録は入れない。

- **抜き出しの性質。** 生成器で、知らない `type`、`uuid` のない知らない種類、一覧にない `attachment`、`queued_command`（人、通知、`prompt` が文字列でないもの）、`isMeta` の伝言、壊れた行、親がアシスタントの連鎖、循環する `parentUuid`、思考に入れた目印、秘密の目印を混ぜる。確かめるのは、(1) 思考の目印がどこにも出ない、(2) 各ターンの「T<m> への返答」が、素朴に書いた参照の実装で求めた宛先と一致する、(3) 見出しとフェンスが 1 対 1 になる、(4) `HOME`、`TZ`、記録の置き場所を変えても同じバイト列になる、の 4 つである。**対照**として、3 版目の規則（`attachment` を境界にしない）と、除くものを並べる方式に差し替えると、(2) と (1) が落ちることを確かめる。
- **ディスクの走査。** `inspect`、`show`、`decide` の前後で、wiki、raw のルート、作業ツリーの全部のファイルを走査し、本文の目印がどこにもないこと、決定のファイルに `mark` に渡した文字列がないことを確かめる。対照として、写しを書く実装に差し替えると落ちることを確かめる。
- **縛り。** `show --meta` のあとに範囲の行を書き換えると、`apply` が拒む。決定のファイルを書き換えると拒む。作業用のフォルダーの `after` を `diff` のあとに書き換えると、`plan_sha256` が一致せず拒む。曖昧な `mark` と一致のない `mark` を拒む。題名に伏せた文字列が入っていれば拒む。
- **秘密の検査。** 要約ページ、関連ページの直し、索引のブロック、`create` のファイル名、`append` の見出しに、決定で伏せた文字列そのもの、全角にしたもの、大文字にしたものを入れると、`diff` と `apply` が場所だけを出して拒み、標準出力にも引数にも文字列が出ない。自動の伏せ字が置き換えた元の文字列（メールアドレスのローカル部だけ、ホームのディレクトリの名前だけ）と、自動の伏せ字の規則に当たる文字列も拒む。`plan.json` から記録と決定のパスを消した計画、別の決定のファイルに差し替えた計画は、`plan_sha256` が一致せず拒む。
- **パスの検査。** wiki の中のパスの途中の階層か行き先を、raw のルートへのシンボリックリンクかジャンクションにすると、`diff` と `apply` が拒み、raw が変わらない。wiki の外を指す `..` のパスを拒む。リンクを作れない環境では飛ばす。
- **Git の検査。** `.wiki-cache/.gitignore` がない作業ツリーと、作業用のフォルダーのファイルがすでに追跡されている作業ツリーで、`begin` が止まる。祖先に `.git` があり `git` を実行できない環境でも止まる。どの祖先にも `.git` がなければ作る。
- **競合と並行。** 2 つのプロセスで、別のスラッグの取り込みを同時に `apply` することを 200 回繰り返し、索引とログに両方の行が残り、関連ページの別々の直しが両方当たることを確かめる。同じ行の直しが重なると、後の側が「競合」になり、何も書かないことを確かめる。同じスラッグの raw を 2 つのプロセスが同時に書くと、1 つだけが `written` になる。対照として、ロックを外した実装と、`os.replace` で raw を置く実装に差し替えると、行の消失と上書きが起きることを確かめる。ロックを持ったまま止めたプロセスがあると、ほかの `apply` が `--wait` のあとに終了コード 4 になる。プロセスを落とすと、ロックが外れる。
- **失敗の注入。** `apply` の 4 の各書き込みの前と後で例外を起こし、もう一度 `apply` すると、書いた変更が「済み」、残りが `written` になり、最後の状態が、止めずに書いたときと同じになる。ほかの取り込みが先に書き換えたファイルに 3 方向で当てた直後に落とした場合も、2 回目で「済み」になり、二重に当たらない。
- **3 方向の当て方。** 文脈が 1 か所だけ一致する、2 か所に一致する（競合）、消す行がほかから変えられた（競合）、ファイルの末尾に行が足された（当たる）、一部の塊だけが当て済み（残りを当てる）、CRLF と BOM のファイル（改行と BOM が保たれる）を確かめる。
- **ブロックの追記。** ログの見出しの行とサブ行が、ほかの取り込みの行に割り込まれずに続けて足される。サブ行と同じ文の行が別の場所にあっても、「済み」にならない。
- **ロックの区間。** `apply` の 0 で記録を読む間に、ほかの `apply` がロックを取って書けることを確かめる（記録の読み出しを遅らせる差し替えで）。
- **実物での確認**（手元で行い、コミットしない）。検証環境の記録で `inspect` と `show --meta` を流し、印の数、`reply_unresolved`、`unknown_uuidless_type`、`raw` の作り直しの時間を記録する。
- `check_commands_mcp.py` の `CLI_NAMES` に `wiki_session.py` と `wiki_apply.py` を足す。`claude -p` で `/wiki:ingest session` を流し、`${CLAUDE_SESSION_ID}` が置き換わって `locate` に渡り、人の発言がないので終了コード 2 で止まることを記録する。
