# /wiki:help の個別のヘルプと、wiki 0.14.0 のリリースの記録

2026-11-14 の、`/wiki:help <コマンド名>` で 1 つのコマンドの詳しいヘルプを出せるようにした変更と、それを含めた wiki 0.14.0 のリリースの記録である。原本は、GPT-6.1 Sol の敵対的レビューの依頼と結果を残した `docs/agent-runs/2026-11-14-wiki-help-command/` である。設計は `docs/plans/wiki-help-command-2026-11-14.md`（3 版目）にある。マージとリリースの経過は、作業の記録から書いた。

## 経緯

1. 作者が「`/wiki:help [command]` で個別のコマンドのヘルプを出したい」と頼んだ。今の `/wiki:help` は `commands/*.md` の frontmatter から全コマンドの 3 行の一覧を出すだけで、引数を受け取らなかった。
2. 表示の中身を作者に聞くと、「frontmatter と `docs/commands.md` の節」だった。使用例と詳しい説明はすでに `docs/commands.md` にあり、ヘルプ専用の文章は書かない。`docs/` は導入したプラグインにも入っている。
3. 進める範囲を聞くと、はじめは「PR の作成まで」で、計画の承認の場面で「0.14.0 としてリリースする」に変わった。0.14.0 は、PR #53 で main の `plugin.json` に入っていたが、タグとリリースはまだなかった。
4. 1 版目の設計のレビューは却下だった。利用者の引数を引用符で囲んでシェルに渡すと注入できること（致命）と、対話のセッションで `/wiki:help /wiki:query` が 2 つのコマンドとして展開されること（重大、推測）である。シェルには英数字と `-` だけを渡し、`/wiki:` を付けない名前を案内することにした（[[コマンドの引数の渡し方]]）。
5. 節の相対リンクは、はじめ導入先のファイルを指す `file:///` にした。作者がデスクトップアプリで確かめると、左クリックでは開けず、右クリックから VS Code なら開けた。作者の選択で、GitHub の導入した版のタグへの URL にした（[[コマンドの出力のリンク]]）。
6. 2 版目と 3 版目の実装のレビューは、どちらも条件付きで採用可だった。範囲の外の書き方を書き換えと同じ正規表現で探していたこと、宛先を復号して比べていたことが崩れた前提だった。書き換えの結果を、同梱の markdown-it で独立に照らし合わせる作りにした。その直しを同じセッションの続きで確かめてもらい、採用可になった。軽微な 2 件も直した。
7. 作業の途中で、子の main に PR #54（fetch の `PermissionError` の修正）が入った。その修正は CHANGELOG の `[Unreleased]` にあった。`v0.14.0` のタグには #54 のコードも入るので、作者に確かめ、0.14.0 の Fixed に移した。オープンの PR #55 は待たず、含めなかった。
8. Sol の 3 回目のレビューを待つ間に、PC がハングアップして再起動した。切り離して起動したレビューは、起動の 1 行だけをログに残して止まっており、状態のファイルは `running` のままだった。結果がないので、同じセッションの続き（`--resume`）でやり直した。その間に親の main に PR #96 が入っていたので、まだ push していなかった親のブランチを `origin/main` の上に載せ直した。
9. 子の to884/info-hive-wiki#56 と親の to884/info-hive-dev#98 を作った。GitHub の Codex の自動レビューは、どちらも指摘なしだった。作者の「CI 後に進めて」を受けて、子の CI の 4 つと、子の PR の先頭を指す親の CI の 9 つの終わりを 1 回だけ待ち、通ってから子をマージした（`bef68e9`、木の差はない）。
10. 注釈付きのタグ `v0.14.0`（`bef68e9`）と GitHub リリースを作った。使い捨ての設定でマーケットプレイスから入れると 0.14.0 になり、0.13.0 から変わった 12 のファイルの SHA-256 がタグの中身と一致した。入った `wiki_help.py` は詳細のリンクを `https://github.com/to884/info-hive-wiki/blob/v0.14.0/...` で出し、そのページは 200 で開いた。
11. 親の参照を子の main のマージのコミットに付け替え、その CI の 9 つが通り、参照先が子の main の先頭と同じことを確かめてから、親をマージした（`192715a`）。2 つの PR のリモートブランチを消した。

## 決めたこと

- 版は 0.14.0 のまま変えなかった（作者の決定）。版の番号が変わらないので、PR #53 のマージ（2026-11-13 23:33Z）以降に main から 0.14.0 を入れた利用者には、この変更は次に版を上げるまで届かない。
- 詳細は `docs/commands.md` の節から作る。コマンドを足したら、その節を書く。すべてのコマンドに節があり、警告なしに出ることを試験で確かめる。
- 名前が見つからなければ、`difflib` の近い名前と使えるコマンドの一覧を示して、終了コード 1 で止まる。名前は `commands/` から集めた一覧の中だけで照らし、名前からパスを作らない。
- 試験は、AGENTS.md に従って親の `tests/wiki/test_help_command.py`（38 件）に置き、親の CI（`wiki-mcp.yml`）で動かす。プラグインの `eval/scripts/test_help.py`（移植元から引き継いだ一覧の試験）は変えなかった。

## レビューの指摘と直し方

| 回 | 判定 | 崩れた前提 | 直し方 |
| --- | --- | --- | --- |
| 設計の 1 回目 | 却下 | 引用符で囲めば、シェルにとって 1 つの値になる | シェルに届く文字を英数字と `-` に限る |
| 設計の 1 回目 | 却下 | `$ARGUMENTS` に、利用者が書いた後ろの文字列が届く | `/wiki:` を付けない名前を案内する |
| 実装の 1 回目 | 条件付きで採用可 | 範囲の外の書き方を、書き換えと同じ読み方で探せば見つかる | 書き換えの結果をパーサーで照らし合わせる。節の見出しと範囲もパーサーで読む |
| 実装の 2 回目 | 条件付きで採用可 | URL の全体を復号して同じなら、宛先も同じ | 復号せずに、`normalizeLink()` で正規化して比べる。`urlsplit` で部分に分ける |
| 実装の 3 回目 | 採用可 | 画像の `content` が同じなら、描く代替テキストも同じ | `renderInlineAsText()` で描く文字にして比べる |

## 途中で起きたこと

- `Write` で試験のファイルに書いた `"\u3000query\u3000"` が、見えない全角の空白そのものに変わった。書いたあとの走査で見つけ、`"\N{IDEOGRAPHIC SPACE}..."` に直した。
- `claude -p --plugin-dir` で 6 通りの呼び出しを確かめた。`/wiki:help query'; echo HELP_ARG_EXECUTED; #` では、エージェントがスクリプトに引数を渡さず、一覧だけを出した。`claude -p` では `/wiki:help /wiki:query` も `query` のヘルプを出した（対話のセッションとの違いは [[コマンドの引数の渡し方]]）。
- 切り離したレビューの結果は、PC の再起動で失われる。状態のファイルが `running` のままでも、ログに結果がなければ、やり直す。
