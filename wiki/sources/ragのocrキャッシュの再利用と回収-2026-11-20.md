# RAG の OCR 結果の再利用と不要キャッシュの回収

[[rag全量ocr後のann保守と中断再開-2026-11-19]] で残ったキャッシュ管理の 2 件を修正した。
[[info-hive-rag]] の再登録で保存済み OCR を保持し、索引リセット後に不要な抽出結果を回収する。
詳細と証跡は `docs/research/rag-cache-retirement-2026-11-20.md` にある。

## 保持と回収の順序

退役台帳の `rows_pending` で、索引行の削除待ちとキャッシュだけの回収待ちを分ける。
旧 2 列の台帳は行の削除待ちとして移行する。
行の削除前に再開位置を無効にし、行と索引の保守後にキャッシュだけの回収待ちへ移す。
この段階では、新しい行や再開位置を変更しない。

再登録する文書は抽出ロックを先に取り、索引行だけを後始末して抽出結果を残す。
索引リセットでも現在の取り込みの抽出結果は保持する。
ほかの wiki が参照中か、抽出ロックがあるときは、回収の記録を残して後で再試行する。

## 実行結果

修正前は OCR の再実行と不要キャッシュの残留を 2 件の試験で再現した。
修正後は Windows 回帰 84 件成功、Linux 回帰 82 件成功・Windows 専用 2 件スキップだった。
旧台帳の並行移行、共有参照、ロック解除後の回収、新しい行・再開位置の保持、設定変更後の途中再開も確認した。

Windows の実 OCR・実モデルの MCP 21 項目も成功した。
13 ジョブ中、OCR の呼び出しは新規スキャン 2 件への 2 回だけで、再利用を期待する経路では 0 回だった。
保存済みページと document.md のハッシュ・更新日時が再登録で一致した。
旧形式と別の抽出キーの検証用キャッシュも回収し、共有先の最後の参照がなくなると共有キャッシュを回収した。
両 wiki の公開台帳と行数が一致し、最後の回収待ちは 0 だった。

分割サイズを変えて索引リセットを起動し、OCR の方針・解像度・抽出の版は変えていない。
OCR 条件が違う古い結果を使う変更ではない。
全量の ANN 試験は再実行しておらず、以前の全量 OCR と ANN の証跡はそのまま残した。
OS の電源断・再起動、WSL 停止は行っていない。

検証した rag_index.py は `021ea0774ec104f2b1b827498a6192bf64a68fc2d3dcb0d8d1d2373240aa7ab6` で、検証時点では変更は未コミットだった。

## 追加の反例と検証範囲

初回の回帰 81 件・MCP 17 項目の後、一覧から外した回収対象の消失、別 wiki の中断中ジョブ、共有違反の 3 反例を再現して修正した。
回収の意図を台帳に集約し、相手の wiki の方針で未完了ジョブの世代を調べ、削除失敗を再試行する。
追加修正後も Opus の再レビューは Critical・Major なしの承認となった。

実 MCP の中断は全 1 チャンクの保存後・公開前にテスト例外を起こしたもので、retry_job で同じ ID の 2 回目が完了した。
複数バッチの途中からの再開は回帰試験で確認した。
未完了の内部ジョブは、失敗・キャンセル後も明示的な再試行のために OCR を保持する。放棄を推測して削除する機能は含めない。
