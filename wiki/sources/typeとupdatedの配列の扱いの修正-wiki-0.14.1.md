# type と updated を配列や値なしで書いたページの扱いの修正と、wiki 0.14.1 のリリースの記録

2026-11-14 の、frontmatter の `type`、`kind`、`updated`、`created` を配列や値なしで書いたページの取り違えの修正と、そのリリースの記録である。原本は、Sol の敵対的レビューと対応を残した `docs/agent-runs/2026-11-14-wiki-scalar-list-values/` である。作りかけの差分を見つけた経緯、競合の解き方、リリースと導入の確かめは、作業の記録から書いた。

## 経緯

1. 不要なブランチと worktree を片付けているとき、worktree `full-ocr-continue-94ee76` の `info-hive-wiki` に、コミットされていない差分（12 ファイル、+102/−35）が残っているのを見つけた。2026-11-13 に 0.13.1 として作りかけた、この修正だった。どのセッションの作業かは、セッションの記録から分からなかった。作者の依頼で、いまの main に載せ直して仕上げた。
2. 差分を退避してから、wiki の新しい worktree を `origin/main` から作り、`git apply --3way` で当てた。コードと文書の 10 ファイルはそのまま当たり、`plugin.json` と `CHANGELOG.md` だけが競合した。2 つは main の内容に戻し、記載を `[Unreleased]` に書き直した。
3. 0.12.2 で `title` を直したとき、`type` と `updated` は「配列で書かれたときにどの値を使うかを決めないと直せない」として残していた（[[frontmatterのリストの値]]）。この修正は `title` と同じく要素をつなぐ規則を選んだ。`wiki_pages.scalar_value()`、`type_value()`、`kind_value()` を足し、`type`、`kind`、`updated`、`created` を読む箇所をそろえた。
4. 試験は、プラグインの `eval/scripts/test_scalar_values.py`（10 件）と、MCP の `query` の経路を見る親の `tests/wiki/test_wiki_index.py`（1 件）に置いた。親の試験は、修正前の wiki で `(['concept'], ['2026-03-01'])` を返して失敗した。
5. GPT-6.1 Sol の敵対的レビューは、条件付きで採用可（確信度 中）だった。軽微な指摘 4 件に対応した（下の「途中で起きたこと」）。直しはレビューにかけ直していない。
6. 評価ゲートの出力は、修正の前後でバイト単位で同じだった。文字で書いたページの結果は変わらない。
7. 子の PR（to884/info-hive-wiki#55）と親の PR（to884/info-hive-dev#97）を出した。版は、はじめ上げなかった（下の「決めたこと」）。
8. 親の PR に、Codex の自動レビューが「マージ前に `plugin.json` と CHANGELOG の版を上げる」と指摘した（AGENTS.md の規則）。番号が決まるまで直さないと返信し、スレッドは解決しなかった。
9. 別のセッションが `/wiki:help` の個別のヘルプ（#56）を main に入れ、v0.14.0 をリリースした。親の PR がサブモジュールの参照で競合した。子のブランチに wiki の main を取り込み（`193e5d1`）、親はそのマージコミットを指すようにした。
10. v0.14.0 のタグが付き、`[Unreleased]` にこの修正だけが残ったので、作者が 0.14.1 に決めた。子の PR で版を上げ（`5ac841b`）、親の参照もそこに進めた。版の指摘のスレッドに返信して解決した。
11. 子の CI の 4 つと、子の PR の先頭を指す親の CI の 9 つの終わりを 1 回だけ待ち、通ったのを確かめてから子をマージした（`7495ca5`）。親の参照をそのマージコミットに付け替えた（`2085168`、木の差はない）。付け替えたあとの親の CI の 9 つの終わりも 1 回だけ待ち、参照先が子の main の先頭と同じことを確かめてから、親をマージした（`ca7b09a`）。
12. 作る直前に `git ls-remote --tags` と `gh release list` を取り直し、注釈付きのタグ `v0.14.1`（`7495ca5`）と GitHub リリースを作った。リリースの本文は CHANGELOG の 0.14.1 の節と同じだった。
13. 使い捨ての設定でマーケットプレイスから入れ、0.14.1 が入ることを確かめた（[[リリースの確かめ方]]）。v0.14.0 から変わった 13 のファイルの SHA-256 がタグの中身と一致した。入った `wiki_search.py` で `type: [概念]`、`updated: [2026-03-01]` のページを検索すると、`concept`、`2026-03-01` が返った。

## 決めたこと

- 値をそろえる規則: 文字と `None` はそのまま返す（`""` も変えない）。配列は空でない要素を「, 」でつなぐ。`type` と `kind` の要素は日本語の別名を英語に直す。空なら `None` にする。グラフのノードでは、今までどおり `""` にする。
- 要素が 2 つ以上ある `type: [concept, entity]` は「concept, entity」になる。`--type concept` にも `--type entity` にも当たらず、`--type "concept, entity"` にだけ当たる。
- lint の指摘の値の規則を 1 つにした。書き方を指摘するもの（`non_iso_dates` の `value`）だけを書かれた形のまま出す。判定に使った値を示す欄（`index_type_mismatch` と `unresolved_sources` の `type`、`stale_pages` の `updated`）は、比べた値と同じくそろえた値を出す。Sol が `type` の欄を指摘したとき、欄ごとに塞がず、この規則を決めて `stale_pages` も合わせた。
- 閲覧（browse）は直さなかった。browse の構造を直す設計が別に進んでいる。索引にないページを種類で分ける欄に、配列の `type` が `['concept']` と出る。
- 版を決めるのを、v0.14.0 にタグが付くまで待った。main の `plugin.json` は 0.14.0 だったがタグがなく、`[Unreleased]` には別のセッションの修正（#54）も入っていた。この PR で番号を決めて上げると、#54 も一緒に出荷することになった。
- 版はパッチ（0.14.1）にした。取り違えと止まるのを直す修正で、新しい機能はない。

## 途中で起きたこと

- 最初に、作りかけの差分がいまの main に「4 ファイルで競合する」と報告した。古いコミットのままのサブモジュールの作業ツリーで `git apply --check --3way` を試したためで、誤りだった。いまの main の worktree で当てると、競合は `plugin.json` と `CHANGELOG.md` だけだった。差分の当たり方は、当てる先の木で確かめる。
- Sol の指摘 4 件。
  - lint の `type` の欄がそろえた値になり、CHANGELOG の「書かれた形のまま出す」に反する。上の lint の規則を決め、CHANGELOG に書いた。
  - グラフのノードの値なしは `null` でなく `""` になる。振る舞いは前からなので変えず、CHANGELOG を直した。
  - 「どの `--type` にも当たらない」は誤りだった。CHANGELOG を直した。
  - `--decide` の試験で、証拠がソースの本文にあるので判定の候補が 0 件になり、`decide_evidence()` の source の判定を戻しても気づかない。証拠が本文にない関係を足し、`evidence_check.candidates` が 1 になることを確かめた。
- 足した試験は、該当する実装を元に戻して失敗することを確かめた（親の索引の試験、`decide_evidence()`、`stale_pages`）。
- `eval/retrieval/test_setup.py` は、埋め込みの依存（`fastembed`、`sqlite-vec`）がない環境では失敗する。修正前の main でも同じだった。
- v0.14.0 を出したセッションからの連絡で、0.14.0 が使用済みになったと知った。v0.14.1 を出したことを伝えようとしたが、そのセッションはアーカイブされていて届かなかった。
