# Box Drive 2 台での記事削除と編集の競合・復旧

Windows 11 ホストと Hyper-V の Windows 11 VM で、同じ Box アカウントと Box Drive 2.56.271.0 の Cloud Files 方式を使った。検証用 wiki は info-hive v0.39.0 で初期化した。記事・`index.md`・`log.md` の共通初版を Box と両端末で照合し、両端末で固定した。

## オフライン削除と編集

ホストでは Box への通信をプロキシで拒否し、VM では仮想 NIC を切断した。ホストでは記事を削除し、索引から項目を外してログに削除を記録した。VM では同じ記事を編集し、索引の要約を更新してログに編集を記録した。再接続前に、VM が実際に保存した記事を Box の外へコピーした。回収したコピーを VM 版の SHA-1 と SHA-256 で照合した。

ホストのプロキシ解除と VM の NIC 接続の開始差は約 2.7 ミリ秒だった。先行試行では時刻を受け渡すファイルがロックされ、約 4.7 秒の開始差が出たため集計から外した。以下は新しい検証フォルダーでやり直した 1 回の観測結果である。

| ファイル | 再接続後の結果 |
| --- | --- |
| `concepts/guide.md` | VM 版を Box が受け取った後、同じファイル ID の VM 版がごみ箱に入った。両端末で正規名が見えなくなり、記事の別名コピーは観測されなかった。 |
| `index.md` | 正規名に VM の更新済み要約が残った。記事への項目を外したホスト版は別名コピーになった。正規名の索引には、存在しない記事へのリンクが残った。 |
| `log.md` | 正規名には VM の編集記録、別名コピーにはホストの削除記録が残った。 |

再接続の基準時刻から約 1.4 秒後の Box API 応答で、元の記事と同じファイル ID に VM 版の SHA-1 を確認した。約 13 秒後の観測では記事は両端末で見えず、約 14.5 秒後の Box API 応答で同じ ID と SHA-1 の記事がごみ箱に入っていることを確認した。約 34 秒後の観測で、記事の不在と索引・ログの両版が両端末で一致した。

## 編集内容の回収と再同期

1. Box Web を操作できなかったため、再接続前に VM で保全した編集済み記事を使った。保全コピーはごみ箱内の版と SHA-1 が一致した。ホストから元の wiki パスに新規ファイルとして戻し、新しい Box ファイル ID が付いたことを確認した。Box が提供するごみ箱からの復元手順は公式資料を参照する。 [Box のごみ箱の管理](https://support.box.com/hc/en-us/articles/360044196093-Managing-Trash)
2. 復旧した記事を参照する索引の項目を 1 件載せ、ログに元の削除、編集、復旧をそれぞれ 1 件残した。ホストからの書き戻し開始から約 26 秒後の観測で、記事・索引・ログの SHA-1 がホスト・VM・Box API で一致した。両端末の SHA-256 も復旧版と一致した。
3. 索引とログの競合コピー 2 本を `wiki/` と同じ階層の `recovery-archive/` に移した。退避開始から約 26 秒後の観測で、退避先の SHA-1 が両端末と Box API で一致し、両端末の wiki 内の競合コピーは 0 本になった。

書き戻し前と退避後のホストで BM25 検索を行い、VM が編集した文の「赤い目印」で記事を見つけられた。lint のリンク切れと重複スラッグは 0 件だった。
