# 初期化していないディレクトリを wiki として扱わない修正と、wiki 0.13.0 のリリースの記録

2026-11-13 の、`/wiki:init` をしていないディレクトリを wiki として扱っていた穴の修正と、そのリリースの記録である。原本は、GPT-6.1 Sol の敵対的レビューの依頼と結果を残した `docs/agent-runs/2026-11-13-wiki-uninitialized-root/` である。設計は `docs/plans/wiki-uninitialized-root-2026-11-13.md`（4 版目）、決定は ADR-0019（状態は提案）にある。マージとリリースの経過は、作業の記録から書いた。

## 経緯

1. 作者が「`/wiki:init` をしていないときに、ほかのコマンドを実行するとどうなるか」を尋ねた。調べると、何もない場所では止まるが、`SCHEMA.md` のない `wiki/`（GitHub の wiki の写しなど）があると、それを wiki として扱っていた。lint と統計は普通に報告し、検索の `--cache` はその中に `.wiki-cache/` を書いた。`init_wiki.py --upgrade` は実質の初期化になり、`wiki_fetch.py` は raw のルートを作った。
2. 初期化された wiki の判定を、ルートの `SCHEMA.md` の有無に決め、`wiki_initialized.py` の 1 か所に置いた（[[初期化されたwikiの判定]]）。`init_wiki.py` が必ず作って上書きしないファイルで、`wiki_evolve.py` と rag の `rag_config.py` がすでに同じ規則を使っていた。ADR の番号は、0017 を Raw の大きさの設計が予約していたので 0019 にした。
3. 試験を先に書き、古い実装で落ちることを確かめた。MCP の `query` と `stats` が、`SCHEMA.md` のないディレクトリの索引をデータの場所に作ることも、この試験で初めて確かめた。
4. Sol の敵対的レビューを 4 回頼んだ。設計の 1 回目、実装の 1 回目、2 回目は却下で、指摘を 1 つずつ塞がず、崩れた前提ごとに直した（下の表）。2 回目の重大の直しを、同じセッションの続きで確かめてもらい、採用可（確信度：高）になった。
5. 作業の途中で、別のセッションが子の main に 0.12.2 を入れた（タグはまだだった）。子のブランチに `origin/main` をマージし（force push はしない）、版は 0.13.0 のままにして、CHANGELOG の 0.13.0 の節を 0.12.2 の上に置いた。0.12.2 で足された試験の素材にも `SCHEMA.md` を足した。
6. どちらを先に出すかを作者に聞くと、「0.12.2 を先に出す」だった。このセッションで、注釈付きのタグ `v0.12.2`（`6db310e`）と GitHub リリースを作り、マーケットプレイスから 0.12.2 が入ることを確かめた（[[titleが値なしや配列のときの修正-wiki-0.12.2]]）。
7. マージとリリースの承認は、はじめ別のセッションの伝言で届いた。`gh pr merge` を、auto mode の判定が「レビューなしのマージ」として止めた。作者がこのセッションで許可してから進めた（[[リリースの確かめ方]]）。
8. 子の CI の 4 つ（`0a7b681`）と、それを指す親の CI の 9 つ（`d0e4571`）が通ったのを確かめて、子の to884/info-hive-wiki#52 をマージした（`8cb49d6`、木の差はない）。親の参照を付け替え（`731f714`）、その CI の 9 つが通ってから、親の to884/info-hive-dev#90 をマージした（`1dce1ba`）。
9. 注釈付きのタグ `v0.13.0`（`8cb49d6`）と GitHub リリースを作った。使い捨ての設定でマーケットプレイスから入れると 0.13.0 になった。0.12.2 から変わった 45 のファイルの SHA-256 がタグの中身と一致した。入った `wiki_lint.py` と `wiki_search.py --cache` は、`SCHEMA.md` のないディレクトリを何も書かずに断り、置くと答えた。2 つの PR のリモートブランチを消した。

## 決めたこと

- 版はマイナー（0.13.0）にした。今まで答えていたディレクトリを断り、`wiki_fetch.py` の `--wiki` が必須になるので、0.x の互換でない変更である。
- 初期化（`init_wiki.py` を `--upgrade` なしで）は止めない。中身のある、`SCHEMA.md` のない `wiki/` があるときに、そこを使うかは `/wiki:init` の文章でユーザーに聞く。
- 評価のランナーが受け取るコーパスの写しと、Python のバイトコードのキャッシュは、判定の対象の外にした。理由は [[初期化されたwikiの判定]] にある。
- コマンド 9 つとスキルの指示に、同じ文で「`SCHEMA.md` がなければ何もせず `/wiki:init` を提案する」を入れた。スキルの「下の初期化の手順を実行する」は、提案してからにした。

## レビューの指摘と直し方

| 回 | 崩れた前提 | 直し方 |
| --- | --- | --- |
| 設計の 1 回目 | 入口で 1 回確かめれば足りる。入口は手で表にできる | 長く動くサーバーは要求ごとに判定する。入口を試験で数える。`--stop` も判定する |
| 実装の 1 回目 | 判定の前に解決しないのは MCP と閲覧だけでよい | 判定と解決を一度に行う `resolve()` を足した。POSIX では `kb/ない/..` が解決で `kb` に縮み、別の wiki に `.evolution/` を作りえた |
| 実装の 1 回目 | 入口は正規表現で数えれば漏れない | `__main__` を持つスクリプトを構文木で見つけ、閉じた一覧に分類させた。サブコマンドは振り分けの前で判定する |
| 実装の 2 回目 | 調べられないなら本文も読めない | `SCHEMA.md` だけが循環するリンクだと本文は読める。閲覧のサーバーは「調べられない」ときに新しい内容を組み立てない |

## 途中で起きたこと

- 試験の基準を取るための一括の実行の途中で、ファイルを書き換え始めたので、後半の結果が変更の入ったものになった。一括の実行中は書き換えない。
- 手元の親の `main` は古く（to884/info-hive-dev#60 のマージ）、1 回目の実装のレビューの依頼の `git diff main..HEAD` に関係のない変更が混ざった。2 回目からは分岐点（`d100dfd`）と比べた。
- `Edit` で、`old_string` と `new_string` を空白で終わらせると、その空白が落ちた（`action = "..."` が `action ="..."` になった）。行の中の空白だけが変わった行を差分から探して見つけた。
- `<wiki>/ない/..` の試験は、Windows ではファイルシステムを呼ぶ前に `..` が縮むので当てはまらない。WSL の Ubuntu で動かして確かめた。
- Auto-fix のある PR で、親の CI を待ってからマージするときは、作者の「CI のあとで続けて」を受けて、実行の終わりを 1 回だけ待った（`gh run watch` を裏で）。
