# Box Drive 2 台で同じ記事の別々の節を編集したときの競合と復旧

Windows 11 ホストと Hyper-V の Windows 11 VM で、同じ Box アカウントと Box Drive 2.56.271.0 の Cloud Files 方式を使った。検証用 wiki は info-hive v0.39.0 で初期化した。3 ファイルの共通初版が両端末と Box で一致することを確認し、両端末でファイルを固定した。

## オフライン編集と再接続

ホストは Box への通信をプロキシで拒否し、VM は仮想 NIC を切断した。ホストと VM は同じ記事の離れた 2 つの節を別々に編集した。両方が `index.md` の同じ要約行を書き換え、`log.md` に自分の操作を 1 件ずつ追記した。既存の Markdown を直接上書きし、保存した内容を切断中に照合した。

再接続操作を同じ時刻に予定し、ホストのプロキシ解除と VM の NIC 接続の開始差は約 3.8 ミリ秒だった。

| ファイル | 正規名に残った VM 版 | 別名の競合コピーに残ったホスト版 |
| --- | --- | --- |
| `concepts/guide.md` | 南の節のみ変更 | 北の節のみ変更 |
| `index.md` | 南の変更を記載した要約 | 北の変更を記載した要約 |
| `log.md` | VM の操作のみ追記 | ホストの操作のみ追記 |

基準時刻から約 1.9～2.0 秒後の Box API 応答で正規名の 3 ファイル、約 10.6～11.7 秒後の応答で別名コピー 3 本を、想定した SHA-1 と照合した。約 18 秒後の観測で、計 6 ファイルが両端末にそろった。別々の節への変更を含む記事もファイル単位で分かれた。

## 復旧と同期

1. 共通版と、実際に同期された正規版および競合コピーを Box の外に保全した。`git merge-file` の三方向マージは記事の北と南の変更を統合した。記事をもとに `index.md` の要約 1 行を作り直し、`log.md` に両操作を 1 件ずつ反映した。
2. ホストから統合した 3 ファイルを正規名に書き戻した。保存開始から約 22 秒後の観測で、両端末と Box API の SHA-1 が一致し、両端末の SHA-256 は書き戻し前の統合版と一致した。
3. 競合コピー 3 本を `wiki/` と同じ階層の `recovery-archive/` に移した。退避開始から約 27 秒後の観測で、退避先の SHA-1 が両端末と Box API で一致し、両端末の wiki 内の競合コピーは 0 本になった。

書き戻し前と退避後にホストの BM25 検索で、両方の節の変更から同じ記事を見つけた。lint のリンク切れと重複スラッグは 0 件だった。時刻はいずれも同じアカウントで行った 1 回の試験の観測値である。
