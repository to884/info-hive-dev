# Building an Ontology Agent: Which Parts Actually Need an LLM?

Srikrishnan Shankar が 2026-08-20 に公開した、企業のデータから業務の概念を発見する実験の記事である。1,000 件を超えるソースファイルと、Word・Excel を中心とする約 100 件以上の製品文書を扱った。LLM を意味の推論に絞り、証拠の抽出、整理、既存概念との照合、検証を周囲の処理に分担させる。

原本は `raw/building-an-ontology-agent.md`（GPT-6 の訳と図の補足）である。通常の取得は HTTP 403 になったため、ユーザーがブラウザから保存した全文の HTML を使った。

## 処理の分担

| 段階 | 方法と役割 |
| --- | --- |
| 証拠を作る | コードのクラス名・依存関係・コメント、文書の用語・エンティティ・名詞句・関係を、共通の Evidence Record にする。CamelCase の分割、TF-IDF、固有表現認識、Hearst patterns、依存構造解析を使う |
| 証拠をまとめる | 密な埋め込みと HDBSCAN で意味の近い証拠をまとめ、代表的な情報を小さな Evidence Packet にする。グループ数を先に決めず、外れ値を残せる |
| 概念を提案する | LLM がパケットから、業務上の概念のラベル、種類、定義、証拠への参照を提案する。オントロジーには直接書かせない |
| 既存概念と照合する | ラベルの完全一致、BM25、埋め込みの類似度で、同値、別名、狭義、広義、関連、新規、証拠不足などに分類する |
| 採用を検証する | 証拠の有無、ラベルと定義、許可された種類、データのフィールドや UI の用語らしさを、決定的な規則で検査する |

> 処理の分担 補足: LLM が受け取るのは、関係する証拠をまとめたパケットである。大量の生データからグループを発見する仕事と、提案を正式な知識として採用する仕事を分けている（[[オントロジー候補の生成と採用の分離]]）。

## 生成より選択が難しかった

文書からは数千件の証拠と千件を超えるパケットができた。著者が使った小さなローカルモデルは、証拠が足りなければ見送ってよいと明示されても、ほとんど見送らず、もっともらしい概念名と定義を生成した。

著者は、課題を「生成できるか」から「知識として加えるべきか」へ捉え直した。重複検出、ラベルのフィルター、検証、照合でオントロジーは整理されたと述べるが、見送りの能力はなお重要な課題としている。指示と採用判定の分担については [[エージェントに守らせる決まりの書き方]] も参照。

## 出所と限界

概念から、提案、証拠パケット、証拠レコード、元のソースへ逆にたどれるようにする。採用した理由だけでなく、証拠不足や既存概念との一致で退けた理由も明示できる。

この記事は設計と実験の報告であり、モデル名、プロンプト全文、抽出やクラスタリングの設定、精度・見送り率・費用の比較測定は示していない。費用が下がる可能性には触れるが、効果は規模とモデルに依存すると留保している。MinHash は有用な手法の一覧にあるものの、具体的にどの段階で使ったかは説明されていない。
