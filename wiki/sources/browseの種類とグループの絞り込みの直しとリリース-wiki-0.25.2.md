# browse の種類とグループの絞り込みの直しと wiki 0.25.2 のリリース

`/wiki:browse` の Index のページで、左の木で選んだグループと右の種類のボタンが重なって一覧が 0 件になる不具合を直し、wiki 0.25.2 として出した記録である。原本は `docs/agent-runs/2026-11-17-wiki-browse-filter-type-group/`、設計は `docs/plans/wiki-browse-filter-type-group-2026-11-17.md` にある。

## 経緯

1. 作者の報告: 左の木で「ソース」のグループを選んだまま、右の「コンセプト」のボタンを押すと、一覧が 0 件になる。絞り込みは、検索語、種類、タグ、グループのすべてを満たす行だけを残していた（探しやすさの設計の 4.3）。索引の見出しのグループは、たいていページの種類と重なるので、別の種類を選ぶと満たす行がなくなる。
2. 直し方として、0 件になるボタンを押せなくする案と、種類を押すとグループを外す案を示し、作者は後者を選んだ。逆の順（種類を選んでから左の木でグループを選ぶ）も同じく 0 件になるので、同じ規則で直した。種類とグループは、あとから選んだほうだけを効かせる。「すべて」でない種類を押すとグループを外し（断片は `replaceState` で消す）、別のグループを選ぶと種類を「すべて」に戻す。タグと検索語は重ねたままにした。
3. Sol の敵対的レビューを、設計と実装に 1 回ずつ受けた。どちらも「採用可」で分類 A は 0 件だった。設計のレビューは、履歴を戻ると選んだ種類が戻らないこと（種類は URL に入らない）を指摘し、限界に書いた。実装のレビューは、検索語とタグの保持の試験が欄の値だけを見て、絞り込みに効いているかを確かめていないことを指摘した。「エンティティ」だけなら 1 件のところ、検索語かタグが効いて 0 件になることを確かめる形に直した。
4. 試験は、Chromium と WebKit で失敗 0 件、Firefox はサーバーの方式で失敗 0 件だった（静的の方式の 3 件は、前から記録されている試験の道具の制約。[[browseの画面の確かめ方]]）。
5. 子の PR（to884/info-hive-wiki#80）の CI 4 つと、親の PR（to884/info-hive-dev#161）の CI 17 が通ってから、子をマージした（`e8886d6`）。注釈付きのタグ `v0.25.2` と GitHub リリースを作った。
6. 使い捨ての設定でマーケットプレイスから入れ、0.25.2 が入ることを確かめた。v0.25.1 から v0.25.2 までに変わった 3 つのファイルの SHA-256 が、すべてタグの中身と一致した。

## 分かったこと

- **分類で選ぶ 2 つの絞り込みは、重ねると 0 件になりやすい。** 索引の見出しのグループと、ページの種類は、同じ分類を別の名前で表していることが多い。重ねて絞る条件は、互いに独立した軸（タグ、検索語）に限る。
- **「欄に残っている」と「絞り込みに効いている」は別に確かめる。** 欄と内部の条件は別に持つので、条件だけが消える誤りは、欄の値を見る試験では見つからない。件数が変わる材料で確かめる。
