# browse の stop が Windows でときどき止まる件の直し（wiki 0.19.1）の記録

2026-11-15 の、`/wiki:browse --stop` が Windows で「確かめられないので、何も変えずに止める: open_read: PermissionError」でときどき止まる件の直しの記録である。原本は、実測、Sol の敵対的レビュー、対応を残した `docs/agent-runs/2026-11-15-wiki-browse-stop-record-read/` である。

## 経緯

1. 別のセッションの PR（to884/info-hive-dev#115）の CI で、`browse (windows-latest, 3.12)` の `ProcessTest.test_stop_while_starting_waits_for_record` が落ちた。#115 は browse のコードに触れておらず、同じコードで通る回もあった。別の作業として直した。
2. 読む口 `open_read` は `os.open` だった。サーバーの記録の書き方（`server.json.new` を作って `os.replace`、終わるときに `os.unlink`）と 2 つのプロセスで同時に回して数え、原因を 3 つに分けた（[[windowsのファイルの共有と削除待ち]]）。共有の指定を直すだけでは、削除待ちの失敗が残る。
3. 設計の 7.1 は、ロックがあって記録を読めなければ「動いているが、届かない」として待つと決めていた。`serve_start` は従っていたが、`stop` が使う `probe_server` は従っていなかった。
4. 直しは 2 つにした。読む口を、ファイルを作る口と同じ共有（`FILE_SHARE_DELETE` を含む）の `CreateFileW` で開く。`probe_server` と `serve_start` は、記録を読めなければ `('unreadable', Unknown)` を返し、`stop` と `serve` は待って、読めた記録だけで続ける。時間が切れたら、読めなかった理由を知らせる。
5. 試験は、親の `tests/wiki/test_browse_server.py` の `UnreadableRecordTest`（10 件）に置いた。途中の状態を決まった順に作る。DELETE の権利のハンドルを持ったまま読む、`SetFileInformationByHandle(FileDispositionInfo)` で記録を削除待ちにしたまま `stop` を動かす、記録を開く口だけに `PermissionError` を入れる、の 3 つの形である。直す前のコードでは、対照でない 7 件がすべて落ちた。対照 `read_without_share_delete` と `unreadable_record_fails` を足した。
6. GPT-6.1 Sol の敵対的レビューは 2 回で、どちらも条件付きで採用可だった。1 回目の重大は試験で、補助のスレッドが 0.6 秒の待ちで順を作っていたため、正常な停止でも落ちる順があった。2 回目は、それを 20 秒に延ばしただけだと指摘された（軽微）。どちらも、順を時間で作っていたことが原因である。補助のスレッドは「合図が立つか、`stop` が戻るか」まで待つ形にした。
7. 設計の 9.2 の「どの場所でも」の行（「分からない」を入れて 0 で終われば新しい警告が要る）と 7.1 が食い違っていた。1 回目の直しは例外を場面で書き、2 回目に覆わない経路を指摘された。例外を原理で書き直した。読めなかった答えを使わず、あとで分かったこと（読めた記録か、ロックが空いたこと）だけで決めた場合で、記録の読み取りにだけ当てる。
8. 作業のあいだに、info-hive-wiki の main は 0.18.1（#61）と 0.19.0（#63）まで進んだ。はじめ 0.18.2 にしていた版を 0.19.1 にし、直しのコミットを 0.19.0 の main に載せ直した。0.19.0 の上では、親の読む側の探索（`browse_read_sweep.py`）が古い見出しのマークアップを照らして落ちたので、to884/info-hive-dev#118 と同じ 1 行の直しを入れた。
9. プラグインの PR（to884/info-hive-wiki#64）と、サブモジュールの参照を合わせる親の PR を出した。マージ、タグ、リリースは、この記録の時点ではしていない。
10. #64 は `6d712a8` でマージされた。タグとリリースは、0.19.2 のセッションが、0.19.2 をマージする前に作った（注釈付きのタグ `v0.19.1` を `6d712a8` に付けた）。マーケットプレイスから入れられるのは 0.19.2 だが、0.19.1 で変わったファイルは 0.19.2 で変わっておらず、入ったものとタグの中身が一致した（[[captureの記録の改行の直しとリリース-wiki-0.19.2]]）。

## 決めたこと

- 置き換える先が開かれていると `os.replace` が失敗する件（起動が、ほかの browse が読んでいる古い記録を置き換えられない）は、この直しに含めず、設計の 11 に限界として書いた。直すには、POSIX の名前の付け替えか、置き換えの試し直しが要り、口と探索の決まりを変える。CI の経路では起きない。
- 読む口を変えても、入力の読み取りは遅くならなかった（1,000 ファイルで 385 ms。`os.open` の形は 457 ms）。
