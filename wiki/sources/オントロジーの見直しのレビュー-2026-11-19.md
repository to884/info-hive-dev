# オントロジーの見直しと移行の4モデルレビュー

2026-11-19にOpus 5.5、Fable 5.2、GPT-6.2 Sol、GPT-6.2 Astraが設計書3本をレビューした。原文は `docs/agent-runs/2026-11-19-wiki-ontology-maintenance-multi/review-verification.md`。rawは主担当の検証記録の写しであり、会話全文ではない。

## 結論と確認の範囲

4モデルとも要修正と判定した。実体の粒度と、利用者の指示で定義・記録を見直す方針は維持する。指摘の件数はモデル別の分類であり、独立した欠陥の総数ではない。
相互レビューは未実施。A/Bは過去レビューも参照し、C/Dはローカルの読み取り環境を起動できず、添付された設計書を利用した。Cは公開GitHubの実装とADRも参照した。
Fableによる総括は利用上限で失敗し、原文の採否は主担当がローカルコード・ADRと照合した判断である。反例は机上検証で、実装試験や発生頻度の測定はしていない。

## 修正対象として確認した重要課題

| 項目 | 必要な条件 |
| --- | --- |
| V1 役割の意味 | A社が製品Aの顧客、製品Bの代理店なら、製品Bの顧客には自動で含めない。相手・対象・期間を扱う |
| V2 分割後の参照 | 「利用する」を試用と契約へ分割したとき、「未契約」が否定する主張を根拠から選ぶ |
| V3 網羅性と集計 | 未抽出・同一性の保留・移行残件を区別する。出典2件を顧客2社として数えない |
| V4 連続する移行 | v1の保留をv3の確定記録1件へ移し、旧残件0件と判断履歴を両立する |
| V5 公開版 | 問い合わせが旧グラフと新しい記事を混ぜない。書かない依存先の変化も検査する |
| V6 並行取り込み | 同じメーカー・品番を同時に取り込んでも実体1件・出典2件にする |

V7では定義文・適用条件・該当例と非該当例・用途・採用理由を正本に残すこと、V8では記事と原本の確認範囲を分けることを求めた。
V9では型や版が未確定の状態を黙って現行のconceptへ落とさず、旧配置のwikiへの適用条件も検査する必要がある。V10では、表示・採用済みの同じ案に再承認を求めないよう条件を統一する。

## 採用しなかった断定

- 固定IDへの変更が唯一の解決という断定は棄却した。旧IDとの対応を保持する方式も評価できる。
- 顧客を役割として表すとユーザー要件に違反するという断定は採用しない。要求は粒度であり、形式的なクラスの固定ではない。
- ページ削除・改名と、正本の単一ファイル化がすべての方式で必須という断定は棄却した。
- 部分移行の除外や、ingest時の乖離の印の自動収集は選択肢であり、必須とはしない。
