# browse の静的描画の隔離とメモリ調査（2026-11-17〜19）

Claude Code の `static-mermaid` worktree を Codex で引き継ぎ、`file://` で開く browse の図をどう描くかを検証した記録。raw には実験条件、測定値、反復ごとの結果、調査報告と原標本の SHA-256 を保存した。製品の経緯は [[browseの図の描画とリリース-wiki-0.26.0-0.27.0]] にある。 [検証済み経験の原記録](../../raw/experiences/browse-static-figures-2026-11-19.json)

## 11 月 17 日　図ごとの隔離

GPT-6.2 Sol と Astra で候補を比較した。`relay-srcdoc` は図ごとに使い捨ての中継と描画用の iframe を作る。親から描画側へ渡すのは、その図のソースと許可した配色・書体の設定だけに絞った。`pageDir`、ページ名、図の識別子、検索データは渡さない。Astra の敵対的レビューで、同時に存在する描画枠が別の図の内容を渡し合えることが分かった。枠を逐次実行にして破棄と再描画の試験を追加し、Chromium Headless Shell、Firefox、WebKit、Chrome、Edge で計 60 項目が通った。

その後、埋め込みや `opener` で結ばれた別ページの間では、各ページ内で逐次化しても通信できる反例が見つかった。最終 60 項目は、単独の最上位ページで試した結果である。サーバー版の入口の制限は、静的版の試作と切り分けて検証した。

## 11 月 18 日　Blob の作成元とブラウザの保持メモリ

50 図を明暗で描いた当初の Blob 版では、画像解放・GC 要求後の私有コミットが `srcdoc` 版より Chrome で約 79 MiB、Edge で約 70 MiB 多く、Chromium Headless Shell では約 188 MiB 少なかった。Chrome、Edge、Chromium 通常版では作成元 iframe のレンダラが別 PID で残った。作成元を外すとその PID が消えた。Headless Shell では `srcdoc` の描画枠が親の PID を共有し、タブを開いている間そのプロセスにコミットが残った。同じ Chromium 141 の通常バイナリでは差の向きが反転した。

Blob の作成元を配色ごとの描画終了時に破棄するよう修正し、5 ブラウザで明→暗→明の再描画も確認した。同じ 50 図・2 配色を各方式 2 回ずつ測り、画像解放・GC 要求後の Blob − `srcdoc` の私有コミット差は Chrome +12.6、Edge +1.0、Firefox +74.4、Chromium Headless Shell −171.4、WebKit −683.3 MiB だった。WebKit の Blob 版は `about:blank` で 10 秒待った後もブラウザ全体で約 2.91 GiB、そのうち Web プロセスで約 2.33 GiB を保持した。タブを閉じると Web プロセスが終了した。

## 11 月 18 日　WebKit の私有コミットを分類

- 空白ページで追加 GC を行った後の Web プロセスでは、描画前からの増分が 925〜946 MiB 残った。そのうち 752〜768 MiB（約 81%）は libpas の small/medium bootstrap heap の空きだった。
- 初回に残った 173〜178 MiB を再測定すると、その試行の残差は 125.5 MiB と 148.2 MiB だった。約 114 MiB は segregated ヒープの空き、メタデータ用領域の未使用部分、JIT プールの未割り当て部分で説明できた。bitfit では 3.28〜7.89 MiB の使用中割り当ても確認した。
- 用途が残った 9.4〜15.6 MiB のうち、7.7〜8.7 MiB は `PrivateUsage` と `VirtualQueryEx` の計上差だった。列挙できた増分は libpas の large ヒープの使用中割り当てやスレッドローカルキャッシュの確保領域に照合した。計上差を再測定し、マッピングにひもづく分を引くと 7.34〜8.20 MiB が残った。ページテーブルに対するコミット課金と整合するが、カーネルのカウンターの直接読み取りは実行環境の制約で未完了。

## 11 月 18 日　同じタブでの再描画

50 図と明暗 2 配色を繰り返すと、同じ文書で配色を切り替えたときの待機後の保持量は `srcdoc` で 4.23 から 22.54 GiB（9 周完了）、Blob で 3.60 から 16.81 GiB（10 周完了）に増えた。記事を離れて同じタブで戻る条件は 10 周完了し、`srcdoc` は 2.39 から 6.35 GiB、Blob は 3.46 から 3.59 GiB だった。最初に可視の 4 図だけを描く方法と、同一文書で配色別の画像を再利用する方法も検証した。閲覧時の反復描画が負荷を作り、WebKit の割り当て器の挙動が保持量に影響した。ブラウザの欠陥かどうかは未確定。

同じ文書の確認、表示枚数をそろえた比較、コミット余力が少ない場合の停止手順は [11 月 18 日の測定レビュー](../../docs/agent-runs/2026-11-19-wiki-static-svg-vs-png/2026-11-18-repeat-tab-review.md) に記録した。原記録のパスは測定当時のもので、SVG／PNG 比較の原標本と再測定手順の保存先は次の節にある。

## 11 月 19 日　SVG と resvg で事前生成した PNG

同じ 50 図の明暗 SVG から、resvg 0.50.0 と `YuGothR.ttc` で同じ寸法の PNG を生成した。Windows 版 Playwright WebKit 26.0 で、同一文書・同一タブを維持して各方式を 10 周、順序を反転して 2 回ずつ測った。各周で全画像をデコードし、暗色を表示したまま 5 秒待機した。手動 GC は使っていない。 [報告書](../../docs/research/wiki-browse-static-svg-vs-png-2026-11-19.md) · [10 周の原標本](../../docs/agent-runs/2026-11-19-wiki-static-svg-vs-png/ten-rounds/results.json)

| 指標 | SVG | PNG |
| --- | ---: | ---: |
| 観測したピーク私有コミットの中央値 | 844.53 MiB | 830.75 MiB |
| 描画前からのピーク増分の中央値 | 63.08 MiB | 33.34 MiB |
| 10 周目の待機後の私有コミットの中央値 | 843.06 MiB | 829.40 MiB |
| 先頭図のデコード完了まで（2〜10 周目の中央値、明／暗） | 12.5／12.0 ms | 14.5／14.0 ms |
| 明暗計 100 枚のファイルサイズ | 1,282,530 B | 287,735 B |

各周の待機後の値は報告書と raw にある。全ケースの観測ピークは 862 MiB 未満で、10 周の範囲では閲覧時の Mermaid 描画で見えた GiB 単位の増加は観測されなかった。PNG のピーク増分は両反復で約 30 MiB 小さく、ファイルサイズは 77.6% 小さかった。SVG の 2 回目は開始時の GPU プロセスが約 32 MiB 小さく、絶対ピークはその回だけ SVG のほうが小さい。初回デコードはばらつきがあり、PNG の遅い 1 回（明色 4,450 ms）は残り 3 回で再現しなかった。resvg は CSS などに警告を出し、代表図の文字や縁に差があった。CairoSVG、実機 Safari、全図の画質、圧縮転送時のサイズは測定していない。 [初回の追加測定](../../docs/agent-runs/2026-11-19-wiki-static-svg-vs-png/first-round/summary.json) · [再測定用 ZIP](../../docs/agent-runs/2026-11-19-wiki-static-svg-vs-png/static-image-assets-r2-20261119.zip)

## 同じ画像を使った再測定

Windows 版 Playwright WebKit で同じ50図を明暗各10周・2反復測り直した。描画前からのピーク私有コミット増分の中央値は SVG 62.27 MiB、PNG 35.23 MiB で、PNG の増分が 27.04 MiB 小さかった。前回の中央値はそれぞれ 63.08 MiB、33.34 MiB だった。初回の明色では速い形式が反復によって入れ替わった。 [再測定の報告](../../docs/research/wiki-browse-static-svg-vs-png-remeasurement-2026-11-19.md) [今回の原標本と集計](../../docs/agent-runs/2026-11-19-wiki-static-svg-vs-png-remeasurement/)

## Pele SVG と PNG の表示比較

実際の wiki の 4 図を Pele で生成し、その SVG から resvg で明暗 1 倍・2 倍の PNG を作った。CSS 変数を含む SVG の直接変換では PNG の図形が黒くなった。変数を試験的に展開した画像は Chromium と Windows 版 WebKit で表示できたが、代表画像では文字や角丸に差が残った。画像合計は SVG 40,522 B、PNG 1 倍 202,536 B、2 倍 471,625 B。対象は 4 図で、変換器、フォントと CSS の扱いに依存する。 [比較報告と原標本](../../docs/agent-runs/2026-11-19-pele-png-comparison/report.md)

## resvg の CSS とフォント

Pele の代表 2 図について、ルートの CSS 変数の試験的な展開と、矩形の rx 属性への変換で resvg の色と角丸を確かめた。Chromium は代表ラベルに Noto Sans JP Regular を使い、前回の resvg は Yu Gothic だけを読み込んでいた。resvg も Noto Sans JP を使うと文字の見え方が近づいた。背景色は resvg のオプションで指定できた。 [調査記録と画像](../../docs/agent-runs/2026-11-19-pele-resvg-investigation/report.md)

## 図種・CSS・フォントの追加検証

実際の 4 図と追加の 8 原稿を明暗で生成し、CSS の継承・循環・百分率の対照図 3 件を加えた。フォントを固定し、ブラウザの解決済み属性を書き出すと、rx・ry の auto を属性に書いた場合に Chromium の角丸が失われた。auto の属性を省いて再比較した全 54 条件で元と変換後の SVG は同じ RGB だった。PNG は画素差が残った。ラベルの図形内への収まりと PNG の全文字は未確認。 [報告・画像・再実行手順](../../docs/agent-runs/2026-11-19-pele-png-compatibility/report.md)
