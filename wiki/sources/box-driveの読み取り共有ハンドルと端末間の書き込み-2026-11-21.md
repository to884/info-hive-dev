# Box Drive 上で読み取り共有ハンドルが書き込みを防げる範囲

前回と同じ Box Drive 上の検証用 wiki、Windows 11 ホスト、Hyper-V 上の Windows 11 VM、照合用 JSON を使った。VM で記事・`index.md`・`log.md` を `FileAccess.Read` と `FileShare.Read` で開いた。判定直前と直後の書き込み試行が終わるまで 3 本のハンドルを保持した。 [Microsoft の FileShare 仕様](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare) [[box-driveの最終照合後の変更と引き継ぎ判定-2026-11-21]]

通常の照合処理を呼ぶ計測用ラッパーで、VM の 2 回目の照合が終わって判定を返す直前と、判定直後の 2 段階を作った。各段階で VM の別プロセスが `log.md` を書き込み用に開こうとした。その後ホストで別内容の `log.md` を保存し、ホストで読み戻した SHA-256 と Box API 応答の SHA-1 をそれぞれ保存した版と照合した。

## 実測結果

| ハンドルを保持していた時点 | VM の別プロセス | ホストからの変更 | VM で読めた `log.md` |
| --- | --- | --- | --- |
| 2 回目の照合後、判定の直前 | 書き込み用オープンを拒否（Win32 エラー 32、共有違反） | 1 回目の保存に成功し、Box API 応答でも SHA-1 が一致 | 試験前の版 |
| 「引き継ぎ可」（0）の直後 | 書き込み用オープンを拒否（同じエラー 32） | 2 回目の保存に成功し、Box API 応答でも SHA-1 が一致 | 試験前の版 |

スクリプトはハンドルを保持した状態で 3 ファイルを 2 回読み、どちらも照合用 JSON と一致した。VM ではハンドルを閉じた後の約 68 秒の観測中もホストの 2 回目の変更を確認できず、最後の照合で試験前のログを読んだ。その後、ホストから元の内容を書き戻し、Box API 応答とホスト・VM の実ファイルを照合して、両端末で「引き継ぎ可」（0）を再確認した。

今回のハンドルで VM 内の別プロセスの書き込みは防げた。ハンドル保持中でも、別端末からの保存と Box への反映は進んだ。この構成で 1 回の実測である。
