# raw の段の確かめのスクリプトで、証拠を読み切ることと、レビューを打ち切った記録（2026-11-15）

URL の取り込みの分担を確かめる開発用のスクリプト（`tests/wiki/check_web_raw_agent.py`）を、wiki 0.18.1 のリリース（[[rawの段の取り直しとW8の出力のリリース-wiki-0.18.1]]）のあとも直し、15 回目の敵対的レビューで打ち切った記録である。原本は `docs/agent-runs/2026-11-14-wiki-web-raw-agent-review/` の `fix-proposal-14/`（修正案と総括）、`review-15.md`、`root-causes-15.md`、`frequency.md` にある。プラグインは変えていない。

## 経緯

1. 14 回目の指摘（JSONL を `splitlines` で分けて記録が切れる）は、先に直して 0.18.1 の親の PR（to884/info-hive-dev#115）に入れた。
2. 同じ指摘について、GPT-6.1 Sol に、直す前の版だけを渡して、独立に修正案を考えてもらった。直したあとの版と、その後の git の履歴は読まないように頼んだ。中心の直しは先の修正と一致したが、Sol の案は「読めた回に違反がないことと、要る回をすべて読めたことを分ける」に広げていた。照らすと、先の修正には、結果のない `check --finish` の呼び出し、途中で切れた check の JSON、読めないメタデータの 3 つの穴が残っていた（`fix-proposal-14/synthesis.md`）。
3. その穴を直した PR（to884/info-hive-dev#123）を出し、15 回目のレビューを受けた。却下で、重大は 2 件だった。どちらも、読めないものを数える決まりを、見つけたものにしか当てていなかった。
   - 行の頭から始まる JSON だけを候補にしていたので、前のコマンドの改行のない出力のあとに続く本物の JSON を、回にも読めない候補にも数えなかった。
   - 見つかった `agent-*.jsonl` を読めたかだけを見ていたので、起動したエージェントの記録のファイルが丸ごとなくても通した。
4. check の JSON の印（`"stage": "check"`）をどれも説明する形にし、メインの Agent の呼び出しを、結果の `toolUseResult.agentId` で `agent-<agentId>.jsonl` と結んだ（`root-causes-15.md`）。実際の記録 4 件で、agentId がファイルの名前と一致することを確かめた。結果は 22/22、22/22、20/21、22/22 だった（20/21 は、W8 を文字の出力で終えた 0.16.1 の版）。
5. 作者が、指摘の発生頻度を尋ねた。実際の記録 4 件で数えると、11〜15 回目の指摘の条件は 1 回も起きていなかった（下の表）。作者の判断で、16 回目のレビューをせずに #123 をマージした。

## レビューで崩れた前提（14 回目の総括と 15 回目）

| 回 | 崩れた前提 | 作りで決めた形 |
| --- | --- | --- |
| 14 の総括 | 読めた回に違反がなければ、違反はない | 読めない行、メタデータ、結果のない呼び出し、読めない JSON は、違反がないとは言えないとして不合格 |
| 15 | check の JSON は行の頭から始まる | 印をどれも説明する。render の値の行の中の印はページの値として数えず、それ以外の説明できない印は判定できない |
| 15 | 見つかった記録を読めれば、起動したエージェントの記録がそろっている | Agent の呼び出しを、結果の agentId で記録のファイルと結ぶ |

## 指摘の条件が実際に起きたか

実際の取り込みの記録 4 件（W8 の呼び出しは合わせて 4 回）で数えた（`frequency.md`）。

| 数えたこと | 結果 |
| --- | --- |
| W8 を、ほかのコマンドと 1 つの Bash の呼び出しにまとめた（11、12、15 の前提） | 4 回中 4 回 |
| 1 つの結果に check の出力が 2 回以上、結果が誤り（11、12） | 0 回 |
| 行の途中から始まる check の JSON（15 の 1） | 0 回 |
| 記録の中の U+2028、U+2029、U+0085（14） | 0 文字 |
| 読めない行、agentId で結べないエージェントの記録（14、15 の 2） | 0 件 |

> Claude Opus 5.5 補足: 表は、レビューで挙がった欠陥の条件が、実際の取り込みのセッションの記録で起きた回数である。前提（1 つの呼び出しにまとめること）は 4 回とも起きたが、欠陥になる細かい条件は 1 回も起きていない。4 件は少ないので、頻度の数字ではなく、起きやすさの目安として読む。

11 回目から、指摘の条件はだんだん細かくなった。レビューの質が落ちたのではなく、残る穴がまれな場面に移ったと読める。どの指摘も、起きたときの影響は確かめのスクリプトの合否の誤りで、利用者の wiki は壊れない。
