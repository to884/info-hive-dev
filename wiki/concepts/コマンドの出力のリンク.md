# コマンドの出力に載せるリンク

コマンドがチャットに出す Markdown に、プラグインの文書へのリンクを載せるときの決まりである。`/wiki:help <名前>` が `docs/commands.md` の節を出すときに決めた（[[helpの個別のヘルプとリリース-wiki-0.14.0]]）。節の相対リンク（`./workflows.md#ソースを取り込む`）は、チャットでは行き先が分からないので書き換える。

## 行き先は GitHub の導入した版のタグ

| 行き先 | デスクトップアプリの Code タブ | ほかの問題 |
| --- | --- | --- |
| `file:///C:/.../docs/workflows.md` | 左クリックでアプリの中のブラウザーが開き、「セッションの外のフォルダーにある」として開けない。右クリックの「次で開く」から VS Code なら開ける（作者が 2026-11-14 に確かめた） | 同梱の markdown-it は、既定で `file:` の宛先をリンクとして読まない（`validateLink`）。描画する側によっては生の文字列になる |
| `https://github.com/<owner>/<repo>/blob/v<version>/docs/workflows.md#...` | 左クリックでアプリの中のブラウザーが開き、見出しのアンカーにも移る | ネットが要る。タグのない開発中の版（`--plugin-dir` で試すとき）では 404 になる |
| パスを文字で見せる（`docs/workflows.md`） | どこでも崩れない | 押せない |

> 行き先の比べの表 補足: 作者の選択で GitHub の導入した版のタグにした。`plugin.json` の `repository` と `version` から作り、どちらかが使えなければ書き換えずに警告する。画像は文書のページ（`blob`）ではなく、ファイルそのもの（`https://raw.githubusercontent.com/<owner>/<repo>/v<version>/...`）を指す。

## 書き換えは、独立した読み方で確かめる

標準ライブラリとパーサーは、元の文字列の中のリンクの宛先の位置を返さない。そこで、書き換えは正規表現で文字列の上で行い、その結果を同梱の markdown-it（`wiki_pages.new_parser()`）で確かめる。

- 書き換えの前は文書の全体を読み、節の本文の行にある最上位のブロックのトークンを取る。後は書き換えた本文だけを読む（チャットに出す形）。リンクの宛先を除いた木の形と、宛先の並びを比べる。
- 宛先は復号せずに比べる。期待する宛先は、前の宛先（パーサーが正規化したもの）を書き換え、同じパーサーの `normalizeLink()` で正規化したものである。URL の全体を百分率復号して比べると、`a%23b.md` と `a#b.md` を同じとみなす（実装の 2 回目のレビューの重大な指摘）。
- 宛先は `urlsplit` で部分に分け、パスだけをファイルにする。クエリとフラグメントは書かれたまま付ける。
- 画像の子（代替テキストを読んだトークン）はたどらず、代替テキストはパーサーが描く文字（`renderInlineAsText()`）で比べる。画像の `content` は元の記法のままで、参照リンクの定義が効かなくなって描く文字が変わっても同じになる（3 回目のレビュー）。
- 食い違えば、書き換えずに節をそのまま出して警告する。コードの例を壊したものや、誤った宛先を出さない。ただし、節の外の参照リンクの定義に頼るリンクは、そのまま出しても文字になる。出荷する文書に参照リンクの定義がないことは試験で確かめる。
- 節の見出しと範囲もパーサーで読む。行の正規表現でフェンスを数えていたとき、リストの中のフェンスの閉じの行を最上位のフェンスの開きと読み、節が文書の終わりまで延びた。

2 版目は、範囲の外の書き方を、書き換えと同じ自前の正規表現で探していた。両方が見落とす書き方（引用の中の字下げしたフェンス、節の外の参照リンクの定義）では、コードの例が書き換わるかリンクが消えるのに、検査も試験も通った。試験が本体と同じ判定を使っていたので、本体の見落としを試験も見落とした。確かめる側は、書き換えと独立した読み方にする。実物の試験も、元の節の宛先から、本体の関数を使わずに出力の宛先を求めて照らす。
