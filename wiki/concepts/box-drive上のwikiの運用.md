# Box Drive 上の info-hive wiki の運用

Windows 版 Box Drive の Cloud Files 方式では、1 台の PC で info-hive wiki の基本操作が動いた。複数端末で編集すると、Box の同期はファイル単位のため、wiki 全体で同じ更新時点を保てないことがある。複数端末への共有は、書き込み元を 1 台に固定し、確定版を配布する。[[box-driveでのwiki互換性-2026-11-19]]

## できること

Windows 11、Box Drive 2.56.271.0（Cloud Files 方式）、wiki v0.38.1 で、1 台を使って次の操作を確認した。オフライン試験では、初期化と検索モデルの準備を接続中に済ませ、`wiki/` と `raw/` を「このデバイス上で常に保持」にした。Box 宛ての通信を遮断すると、オンライン専用の対照ファイルは読み込めなかった。[[box-drive-wiki-compatibility-2026-11-19]] [[box-driveのオフライン編集と再同期-2026-11-19]]

| 操作 | Box に接続中 | Box に接続できないとき |
| --- | --- | --- |
| 閲覧 | 記事と原本の閲覧、browse の静的 HTML 生成とローカル HTTP 閲覧。オンライン専用に戻した記事と原本の再取得も確認。 | ダウンロード済みの記事と原本の閲覧。browse の静的 HTML に切断中の編集を反映できた。 |
| 検索・点検 | CLI の BM25 とハイブリッド検索、MCP のハイブリッド検索とページ取得、lint。 | 準備済みの環境で CLI の BM25 とハイブリッド検索が動き、更新記事と新規記事を検索できた。オフラインでの MCP 検索は未検証。 |
| 作成・編集 | wiki の標準初期化、日本語 Markdown 原本の保存、記事とログの置き換え。 | 記事・`index.md`・`log.md` の更新、新規記事と原本の追加。 |
| グラフ | SQLite グラフの生成と整合性検査、MCP でのノード照会。 | 未検証。 |

オフライン編集後は、再接続すると変更した 5 ファイルの SHA-1 が Box API の応答と一致した。オンライン専用に戻して再取得した後も、SHA-256 は保存した内容と一致した。[[box-driveのオフライン編集と再同期-2026-11-19]]

出先で使う前に、`wiki/` と `raw/` を同じ親フォルダーに置き、親フォルダーのダウンロードが終わったことを確認する。閲覧用に確定版を配る場合は静的 HTML、原本も使う場合は必要な原本を含むアーカイブを使える。検索やグラフが必要な端末では、アーカイブをローカルに展開して索引とグラフを作り直す。[[box-driveでのwiki互換性-2026-11-19]] [Box のオフライン利用](https://support.box.com/hc/en-us/articles/360043697574-Making-Content-Available-Offline)

## 編集担当の引き継ぎと同期確認

1. **送り手が保存して編集を終える。** 記事・`index.md`・`log.md` を保存して閉じる。エクスプローラーの状態欄で対象ファイルの同期中表示が消え、問題表示がないことを確認する。送った変更の目印やファイルの SHA-256 を控える。 [Box Drive の状態アイコン](https://support.box.com/hc/en-us/articles/43854492838419-New-Box-Drive-for-Windows-Built-on-a-New-Architecture)
2. **受け手が 3 ファイルを開き直す。** 記事の変更、索引の要約、ログの最新の追記が送り手の確定版と一致することを確かめる。厳密に照合する場合は、両端末で `Get-FileHash -Algorithm SHA256` を使う。緑のチェックはダウンロード済みやオフライン保持の目印に使い、引き継ぎは受け手で新版を確認してから行う。 [Box Drive の状態アイコン](https://support.box.com/hc/en-us/articles/43854492838419-New-Box-Drive-for-Windows-Built-on-a-New-Architecture)
3. **編集担当を切り替える。** 3 ファイルがそろったら受け手だけが編集する。保存後は送り手でも 3 ファイルを見直し、両方の変更が残っていることと、新しい競合コピーがないことを確認する。そろわない間は編集を止め、別名コピーが出たら「競合時の復旧手順」に進む。

ホストから VM に引き継いだ実機試験では、3 ファイルを Box と両端末で照合できた最初の時点は、ホストの保存から約 34 秒後、VM の保存から約 25 秒後だった。ホストの保存から約 8 秒後には Box 側の SHA-1 と両端末の Windows Cloud Files の同期済み状態を確認できたが、VM の内容はまだホスト版にそろっていなかった。最終版には両方の変更が残り、両端末の競合コピーは 0 件だった。秒数はこの 1 回の観測値。[[box-driveのホストからvmへの編集引き継ぎ-2026-11-20]]

### SHA-256 で引き継ぎの可否を判定する

記事 1 本とルートの `index.md`・`log.md` を引き継ぐときは、[照合スクリプト](../../poc/box-drive-wiki-handoff/check_handoff.py) を両端末で使う。作業中にほかのファイルも変更した場合は、そのファイルも受け手で別途照合する。送り手は保存して編集を終え、今回の照合用 JSON を Box 同期フォルダーとは別の経路で受け手に渡す。

```powershell
# 送り手で、UTF-8 の照合用 JSON を新規作成
python -X utf8 -B .\check_handoff.py capture --wiki $senderWiki --article 'concepts/guide.md' --manifest $manifest
python -X utf8 -B .\check_handoff.py check --wiki $receiverWiki --manifest $manifest # 受け手で同じ JSON を指定
```

各端末で `$senderWiki` または `$receiverWiki` にその端末の wiki ルート、`$manifest` に JSON のローカルパスを指定する。記事のパスは wiki からの相対パスを `/` 区切りで指定する。`check` は終了コード 0 で「引き継ぎ可」、1 で「待機」、2 で入力エラーを返す。`--json` を付けるとファイルごとの判定を JSON で確認できる。1 回目で 3 ファイルの SHA-256 が一致し、競合コピーの候補がなければ 3 ファイルを読み直す。2 回目も同じ条件を満たすと「引き継ぎ可」と表示する。判定には最後に読み取った内容を使う。VM で 2 回目の照合後、判定前に `log.md` を変えた試験では、その実行は「引き継ぎ可」（0）、直後の再実行は「待機」（1）、元に戻した後は「引き継ぎ可」（0）だった。送り手は、受け手が編集を始めるまで編集を止めておく。[[box-driveの最終照合後の変更と引き継ぎ判定-2026-11-21]]

**検証結果。** 同じ Box Drive 上の VM で3状態を実測した。すべて旧版なら「待機」（終了コード 1）。記事だけ新版でも、索引とログが不一致のため「待機」（1）。3 ファイルがそろい、競合コピーがなければ「引き継ぎ可」（0）になり、直後の再照合でも同じだった。VM の `log.md` をサイズと更新日時が同じ別内容にした試験では、ログの SHA-256 の不一致だけで「待機」（1）になった。元の内容に戻すと両端末で「引き継ぎ可」（0）になった。VM で 1 回目の全件一致後に `log.md` を変更すると、2 回目で不一致を検出して「待機」（1）になった。元に戻して通常どおり再実行すると「引き継ぎ可」（0）になった。[[box-driveの編集引き継ぎをsha256で判定した試験-2026-11-21]] [[box-driveの同じ更新日時とサイズでの引き継ぎ待機-2026-11-21]] [[box-driveの2回目の照合による変更検出-2026-11-21]]

- **競合コピーが残る場合。** 以前 Box Drive が作った競合コピーを検証用 wiki に複製し、正規の 3 ファイルの SHA-256 が一致していても、コピーが 3 本または 1 本残るとホスト・VM ともに「待機」（1）になることを確認した。必要な変更を回収してからコピーを wiki の外へ退避し、受け手で退避が反映されたことを確認して再照合する。試験では残り 0 本で両端末が「引き継ぎ可」（0）に戻った。[[box-driveの競合コピーによる引き継ぎ待機-2026-11-21]]
- **対象ファイルが欠けるか、読めない場合。** VM の `log.md` を一時退避した試験では「欠落」、排他ロックした試験では「読み取れない」と判定された。どちらも記事と索引の SHA-256 は一致したが、VM は「待機」（1）だった。欠落を観測した時点のホストは「引き継ぎ可」だった。受け手で欠落を解消するかロックを解除してから再照合する。試験ではログの復旧・ロック解除後に 3 ファイルが一致し、「引き継ぎ可」（0）に戻った。[[box-driveのファイル欠落による引き継ぎ待機-2026-11-21]] [[box-driveの排他ロックによる引き継ぎ待機-2026-11-21]]
- **VM で読み取り共有ハンドルを保持した場合。** 判定の前後とも VM 内の別プロセスからの書き込みを拒否した。ホストの 2 回の変更は保持中も Box に届き、VM は判定時に試験前の版を読んだ。[[box-driveの読み取り共有ハンドルと端末間の書き込み-2026-11-21]]
- **Box Web のロックと同一アカウント。** ロック中もホストと VM の順次保存が Box に届いた。[[box-webのロック中のbox-drive保存と同期-2026-11-21]]
- **別アカウントでのロック試験。** VM で保存できても Box は `403 ITEM_LOCKED` を返した。手動解除後は再保存なしで、Box に約 15 秒、ホストに約 32 秒で反映を確認した。期限切れでも自動同期し、両試験とも同期版で両端末が「引き継ぎ可」。[[box-webのロック期限切れと別アカウントのbox-drive同期-2026-11-21]] [[box-webの手動ロック解除とbox-driveの自動同期-2026-11-21]]

### 受け手に旧版が残ったまま切り替えた試験

ホストが 3 ファイルを保存して編集を終え、約 8 秒後に Box 側の SHA-1 がすべてホスト版と一致した。その直後に VM で 3 ファイルを開くと、SHA-256 はいずれも編集前の共通版だった。この状態で VM から保存すると、記事・`index.md`・`log.md` の正規名にはホスト版が残り、VM 版は 3 ファイルとも別名の競合コピーになった。[[box-driveの旧版からの編集引き継ぎと復旧-2026-11-20]]

**判定方法。** 引き継ぎ前に、受け手の 3 ファイルを送り手の確定版と 1 本ずつ照合する。どれかが旧版なら、受け手での編集開始を待つ。切り替え後に変更が見つからない場合は、正規名と別名コピーの両方を調べ、保全した版とハッシュや本文を照合する。この試験では、正規名に欠けていた VM の変更を別名コピーからすべて回収できた。

共通版と両方の編集版を保全し、三方向マージで出た衝突を 3 ファイルとも手で解消した。記事の両変更を残し、要約は 1 件、ログは両操作を各 1 件にした。ホストからの書き戻し開始から約 25 秒後に Box と両端末で統合版を照合し、別名コピー 3 本の退避後に wiki 内の競合コピーが両端末で 0 件になったことを確認した。[[box-driveの旧版からの編集引き継ぎと復旧-2026-11-20]]

## 避けたほうがよい操作

- **複数端末や Box Web からの並行編集・取り込み。** 別々の記事を編集しても、共通の `index.md` と `log.md` を両方が保存すると競合する。記事・索引・ログ・原本は個別に同期するため、同期中は更新前と更新後のファイルが混在し得る。書き込み元を 1 台に固定する。[[box-driveの2クライアント同時再接続-2026-11-20]] [Box のファイル競合](https://support.box.com/hc/en-us/articles/360044193873-File-Version-Conflicts)
- **別端末で編集されている記事の削除。** 試験では VM の編集を Box が受け取った後に記事がごみ箱へ移り、本文の競合コピーは両端末に現れなかった。削除・移動を伴う作業も書き込み元を 1 台にそろえる。[[box-driveの記事削除と編集の競合と復旧-2026-11-20]]
- **正規名や lint の結果だけで復旧を判断すること。** 記事が両方残った状態でも、索引や操作ログが欠ける。欠落を再現した試験では、lint のリンク切れと孤立ページはともに 0 件だった。保全した版を使って欠落や重複を照合する。[[box-driveのwikiの競合と復旧-2026-11-19]]
- **Box の同期だけを完全なバックアップや端末間の排他に使うこと。** `wiki/.page-template.md` など先頭がドットのファイルや、一時ファイルには同期対象外のものがある。グラフ抽出の OS ロックが調整するのは同じ端末内の処理に限られる。 [Box の同期対象外ファイル](https://support.box.com/hc/en-us/articles/360044195433-File-Types-Ignored-or-Blocked-by-Box-Sync-and-Box-Drive)
- **検索 DB の共有と、読み取り接続を開いたままのグラフ再生成。** MCP の `INFO_HIVE_DATA_DIR` は既定の端末ローカル領域に置く。CLI の検索で `.wiki-cache/embeddings.sqlite` への書き込みを避けるには `--no-embed` を指定し、`--cache` を付けない。グラフ DB は、読み取り接続を閉じてから再生成する。試験では Box 配下と通常のローカルフォルダーの両方で、接続を閉じると再生成できた。[[box-driveでのwiki互換性-2026-11-19]] [[box-drive-wiki-compatibility-2026-11-19]] [[windowsのファイルの共有と削除待ち]]

## 競合時の復旧手順

1. **全端末で編集と取り込みを止める。** 開いたままの下書き、未同期のローカル版、正規名の版、別名の競合コピーを Box の外へコピーする。編集前の共通版が手元にあれば保全する。手元になければ、取得できる範囲で Box の版履歴を確認する。記事の正規名が消えていたら、下の「記事が消えた場合」に進む。 [Box の版履歴](https://support.box.com/hc/en-us/articles/360043697054-Accessing-Version-History)
2. **Box の外で記事を統合する。** 共通版と両方の編集版で三方向マージを行い、本文と frontmatter を照合する。同じ行で衝突した箇所は出典と編集意図を確認して手で解消する。別々の記事が両方残っている場合は、まず両記事の変更が反映されていることを確認する。[[box-driveの同じ記事の節編集と復旧-2026-11-20]] [[box-driveの同じ行の競合と手動復旧-2026-11-20]]
3. **確定した記事に合わせて索引とログを直す。** `index.md` の掲載項目、要約、リンク先を照合し、分割済みなら該当する `indexes/` と上位索引の件数も確認する。`log.md` には両方の操作を 1 件ずつ残し、同日・同見出しでも内容を見て区別する。検索と lint に加え、保全した版と突き合わせて、変更の取りこぼしや重複を確認する。グラフを使う場合は同期外で再抽出する。[[box-driveの2クライアント競合の復旧-2026-11-20]] [[box-driveのwikiの競合と復旧-2026-11-19]]
4. **1 台から正規名に書き戻す。** アップロード後に、記事・索引・ログの内容を Box と各端末で照合する。試験ではファイルの SHA-1 を Box API の応答と比較した。確認後に競合コピーを `wiki/` の外へ退避する。Box 内の `recovery-archive/` などに移した場合は、退避先と、wiki 内に別名コピーが残っていないことも両端末で確認してから編集を再開する。[[box-driveの2クライアント競合の復旧-2026-11-20]] [[box-driveの同じ行の競合と手動復旧-2026-11-20]]

### 記事が消えた場合

1. **ごみ箱と保全コピーを確認する。** Box Web のごみ箱で候補の元の場所、削除時刻、ファイル ID やサイズなど確認できる情報を、削除前の記録と照合する。未同期の編集版を Box の外に確保する。 [Box のごみ箱の管理](https://support.box.com/hc/en-us/articles/360044196093-Managing-Trash)
2. **元の記事を復元する。** 同名の再作成版があれば先に `wiki/` の外へ退避し、Box と両端末で元のパスが空いたことを確認する。Box Web から元の記事を復元し、ファイル ID、現行版、編集済みの本文を照合する。ごみ箱から復元できない場合は、保全コピーから記事を作り直す。試験でこの方法を使うと、新しい Box ファイル ID が付いた。[[box-webのごみ箱復元と版の確認-2026-11-20]] [[box-driveの記事削除と編集の競合と復旧-2026-11-20]]
3. **残りの編集と索引・ログを回収する。** 復元された本文と保全した編集版を比べ、足りない変更を統合する。上の手順 3 と 4 に戻り、索引とログの競合も解消して全端末で確認する。[[box-driveの記事削除と編集の競合と復旧-2026-11-20]]

Box Web の復元試験では、元のファイル ID と現行版 V2 のバージョン ID が維持された。復元確定から約 44 秒後の照合で、VM がオフライン保存した本文の SHA-1 はホスト・VM・Box API で一致し、両端末の SHA-256 も一致した。試験アカウントのプランでは Box Web の版履歴を開けなかった。**復元後の旧版 V1 の Box API 取得と、削除前の初版との照合は未検証。** [[box-webのごみ箱復元と版の確認-2026-11-20]]

## 競合と復旧の実測

| ケース | 再接続後の状態 | 復旧で確認したこと |
