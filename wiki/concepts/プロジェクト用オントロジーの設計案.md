# info-hive のプロジェクト用オントロジーの設計案

「何を作り、なぜ選び、どの版で直し、どこまで確かめたか」を追うための設計案である。
2026-11-18 の設計第 2 版をまとめたもので、**本番のオントロジーには未適用**である（[[プロジェクト用オントロジーの設計-2026-11-18]]）。
種類や述語を wiki に紹介することと、その語彙を本番で採用することは分ける。

## 対象と出典を分ける

既存の `product`、`concept`、`source`、`decision` を使い、次の 6 種類を追加する案である。
既存の定義を残した候補全体は 18 種類・26 述語になる。

| 種類 | 表す対象 |
| --- | --- |
| `component` | 製品の中で責務を持つ構成要素。Web raw の作成など |
| `release` | 自前・外部の製品の特定版。rag 0.5.1、yt-dlp 2026.8.19 など |
| `change` | コード・文書・設定・プロンプトを含む、範囲を特定した変更 |
| `issue` | 条件と期待との差を観測した問題。原因の仮説とは区別する |
| `evaluation` | 対象版・方法・結果・限界を特定した評価の実施 |
| `artifact` | リポジトリとパス・識別子・URL で区別する文書、設定、公開文面など |

> 対象の補足: リリースの報告書は `source` のまま残す。記事に登場する版・変更・問題・評価は、必要な問いに応じて別ページにする。1 ページ 1 ノードという [[グラフの抽出の契約]] を維持する。

## 追跡する関係

| 追加する述語 | 主語 → 目的語 |
| --- | --- |
| `part_of` | component/artifact → product/component |
| `release_of` | release → product |
| `delivers` | release → change |
| `changes` | change → component/artifact |
| `affects` | issue → product/component/release |
| `fixes` | change → issue |
| `implements` | change → decision |
| `motivated_by` | decision → issue/evaluation |
| `selects` | decision → product/concept/release |
| `evaluates` | evaluation → product/component/release/change/decision/artifact |
| `applies_to` | concept → product/component |

> 関係の補足: 11 述語を追加し、既存の `depends_on` の両側には component と release を加える案である。型の一致は意味の正しさを保証しない。各関係には出典・引用・確信度・状態を付け、版と条件を本文と notes に残す。

たとえば [[pdfのヘッダーの判定の修正-rag-0.5.1]] から、rag 0.5.1 が変更を出荷し、その変更が「先頭に 1 バイトの改行がある PDF 2 件の拒否」を解消した、という関係を記述する。
受け付ける前置きは 1024 バイト以下であり、任意の不正 PDF を受け付ける修正には広げない。
直接抽出の確認と MCP→索引化の未確認は、評価ページと出典の本文から別々に読む。

## 版・判断・結果の扱い

外部ツールも製品と版を分ける。
`release:wiki-0.23.0 → depends_on → release:yt-dlp-2026.8.19 → release_of → product:yt-dlp` と記録し、旧版の固定依存を現在の全版の依存と読まない。
ADR の「版を固定して yt-dlp を使う」という判断と、実装で固定した数値の版も分ける。

[[ingestに使うモデル]] に関わる判断では、11-13 の Sonnet の継続と、11-14 に記録された raw の分担を別の decision にする。
測定が raw に限られたことと、当時の運用範囲を混ぜない。
手順と条件を説明する concept は、特定時点の選択を表す decision と別の対象である。

`evaluates` は評価したことを示し、合格を意味しない。
対象が各回で変わる 17 回のレビューの集合を、最終出荷版への評価として登録しない。
`current` も「最新版」「問題が未解決」「試験に合格」を意味しない。
固定版への事実はその版について扱い、現在を問う場合は先に対象の版を特定する。

## 採用と回答の手順

候補 YAML は種類と関係の制約であり、記事から事実を自動で生成する処理ではない。
人またはホストの LLM が候補を作り、既存 ID と照合し、根拠を読んで採用してから Markdown に書く（[[オントロジー候補の生成と採用の分離]]、[[スキーマの導出と事実の抽出の分離]]）。
保存の正本は Markdown と ontology.yaml、JSONL と SQLite は再生成する索引とする。

グラフの結果だけから答えず、所有ページの frontmatter・本文、評価ページ、出典の該当箇所を開く。
現行 CLI のテキスト出力は notes を表示せず、evidence も切り詰めるためである。
型による全件一覧と判断の承認状態の機械的な検索は未実装で、インデックス・台帳・JSONL と本文による確認が必要になる。

設計時の隔離試料は対象 33・出典 7 の 40 ページ、型付き関係 38 本だった。
型・参照・引用の実在を検査した結果であり、意味や真実性を保証する結果ではない。
Opus の初回判定は条件付きで採用可で、指摘を第 2 版に反映した。修正後の独立再レビューは未実施である。
採用時は必要な事例だけから対象ページと関係を増やし、全記事を一括で構造化しない。
