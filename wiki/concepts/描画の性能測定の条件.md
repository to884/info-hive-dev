# 描画の性能測定の条件

[[browseの静的mermaidの隔離と性能の検証-2026-11-18]] の診断で使った、図ごとの枠の準備・監視・処理履歴・保持を分けて読む条件である。

## 比較の条件

時間だけの走行はメモリ監視なしで、図数ごとに新しいブラウザを使い、反復の中央値と範囲を残す。
別に監視の有無 × 前処理の有無の 2×2 を置き、比較内では接続後に双方とも 10 秒待つ。メモリの走行は描画後、待機後、GC 要求後、画像と結果の解放後、context 終了後を区別する（原本 T303、T325、T351）。

ブラウザの順だけを回すと同じエンジンの条件順が重なる穴があったため、条件順を反転し実際の記録でも照合した（原本 T366、T421）。
通常測定には比較用の 10 秒待機がない。同じ名目の「新規・監視なし」の初回でも、通常測定の中央値は因子比較の Firefox 1.54 倍、WebKit 1.91 倍だった。
待機だけの因果効果とせず、時刻や背景の負荷等の未統制の差を残す（原本 T425、T436）。

## 時間区間と保持の読み方

枠の追加から `ready` までと、入力後の結果までを分ける。非同期の後始末や GC も混ざるため、前者をコンパイルだけの費用とは呼ばない。
この試作の 50 図では、中央値になった初回走行の約 70〜86% が `ready` までの待ち時間だった（原本 T363、T414）。

弱参照の校正は、強く保持した iframe が生き、参照を解放した iframe が回収される確認に限る。外側の JavaScript の参照先が消えても、内側の実行領域や native cache の回収の証明にはしない。
WebKit の 50 図では画像解放・GC 後も約 4.1 GiB の private bytes が残り、context 終了後に約 0.38 GiB へ減った（原本 T406）。
これを図だけの物理 RAM 占有量、リークがない証明、秘匿データの物理的な消去の証明にしない。

## 対照と来歴

画像不足、監視の起動失敗、時間切れを成功にしない対照を置き、途中経過を残す（原本 T313、T342、T414）。
コードと生成物のハッシュを固定し、修正の影響する走行を採り直す。この診断は条件順の式だけの差を確認し、通常測定を保持して旧順序の因子比較を除外した（原本 T366、T421）。
[[図ごとの描画の隔離]] を維持して評価し、100 秒超が再現しなかったことだけで解決済みや製品化完了としない（原本 T440）。
