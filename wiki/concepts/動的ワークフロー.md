# 動的ワークフロー

**動的ワークフロー（Dynamic Workflow）**は、複数のエージェントへの割り当て、並列実行、結果の検証と集約を、実行できるスクリプトに置く手法である。
モデルが対象に合わせてスクリプトを生成する実装も、確認済みのスクリプトを保存して繰り返す実装もある。
[[managed-agents-cma-dreaming-with-a-dynamic-workflow]]、[[building-dynamic-workflows-a-new-agentic-system]]、[Claude Code の Dynamic Workflows](https://code.claude.com/docs/en/workflows)

## Anthropic の二つの実行環境

| 実行環境 | スクリプトと起動 | 実行結果の確認 |
| --- | --- | --- |
| Claude Code | JavaScript で `agent()`、`parallel()`、`pipeline()` を組む。モデルと出力スキーマを呼び出しごとに指定できる。保存したスクリプトはコマンド名と `args` で再実行できる。 | `/workflows` で進捗を確認する。同じセッションから再開すると、再利用できる完了結果を使う。 |
| Claude Managed Agents | セッション内のエージェントがプログラムを書き、管理ランタイム上でワークフローを開始する。Dreaming の Cookbook では、会話ごとの抽出を並列に行い、最後にメモリストアを整理する。 | セッションの `workflow_run.*` イベントで段階と終了結果を確認する。ワーカーの失敗を処理したうえで全体が完了する実行もある。 |

[Claude Code のワークフロー仕様](https://code.claude.com/docs/en/workflows)、[Managed Agents の実行イベント](https://platform.claude.com/docs/en/managed-agents/workflow-runs)、[[managed-agents-cma-dreaming-with-a-dynamic-workflow]]

Managed Agents の **Dreams** は、過去のセッションと既存のメモリストアを入力にして、新しいストアを返す機能である。
Dreaming の Cookbook は、Dynamic Workflows を使って同じストアを更新する例である。
[Managed Agents の Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)、[[managed-agents-cma-dreaming-with-a-dynamic-workflow]]

## 組み方の段

[[building-dynamic-workflows-a-new-agentic-system]] の設計では、計画が実行されるまでに次の段を踏む。リードが読むのは、通常のコードが作る約 500 トークンのファクトシート（仕事の大きさ、価格、上限、予算）だけで、1,348,181 トークンの仕事に対し、リードの 1 回の計画の呼び出しが読んだのは 1,780 トークンだった。

1. 素のコードがシートを作る（偵察）。
2. リードがシートから計画のプログラムを書く。
3. ホワイトリストと長さの上限（80 行、6,000 文字）で検査し、費用の前に拒む。理由を返し、リードに直させる。
4. 費用のかからない代役のモデルで計画を 1 回実行し、ワーカーの数と費用を見積もる（リハーサル）。
5. 自動の上限（記事では 40 クレジット以下かつ予算の 3 分の 1 以下）を超える計画は、人が決めるまで保留する。
6. 1 つの予算のもとで、バックグラウンドで実行する。

同じ記事では、台帳に回答を質問の指紋で記録して再実行に備え、メーターで上限を管理する。

## 守りの向き

記事の計画の言語の制限は、計画が自分のリードから来ることを前提にしており、著者はこれをセキュリティの境界ではないと明言している。目的は、暴走する計画と費用の見積もりちがいを実行の前に拒むことである。信頼できない入力への守りは別で、cookbook はトランスクリプトを指示ではなくデータとして扱い、道具を 5 つに絞り、ネットワークの許可リストを空にし、使うセッションには読み取り専用でマウントする。

## 測定の読み方

記事の監査（849 ファイル、72 個の埋め込みバグ）の結果である。

| 設計 | 再現率の平均 | 適合率の平均 | 費用の平均（クレジット） |
| --- | --- | --- | --- |
| エージェント 1 つだけ | 0.02 | 1.00 | 23.7 |
| 人が書いた固定計画 | 0.30 | 0.82 | 13.8 |
| 動的ワークフロー | 0.45 | 0.71 | 48.4 |

- 動的ワークフローは、固定計画より再現率が +0.06〜+0.25（95% 区間）高いが、費用は約 3.5 倍で適合率は下がる。
- 14 回スキャンさせた固定計画を著者は実行していないので、向上を「多く読んだこと」と「良く計画したこと」に分けられない。
- 各設計のランは 3 回以下、ライブラリは 1 つ、モデルは 1 系統で、記事のモデルは Qwen 系である。事前の 11 個の予測のうち成り立ったのは 3 個で、懐疑者の効果と失敗する呼び出しを実行する効果は成り立たなかった。
- リハーサルは、実際のランと同じ予算を見せないとずれる。同じ計画でも、予算 150 を見せると 23.9 クレジット、45 を見せると 8.3 クレジットになり、固定計画の見積もり 10.1 は実際の 13.8 より 27% 低かった。

## info-hive-wiki での /wiki-dream

Codex のローカル定期ジョブ「Wiki Dreaming の差分提案」は、現在、毎日正午（日本時間）に起動する設定である。2026-11-21 の登録時は毎日午前 3 時で、2026-11-22 に正午へ変更した。`--scheduled --limit 2` で [Python の起動スクリプト](../../poc/wiki-dream/run.py) を呼び、1 回につき最大 2 件の会話を対象にする。Python は実行を許可した Claude Code の保存済みワークフロー [`/wiki-dream`](../../.claude/workflows/wiki-dream.js) を名前で指定して非対話で起動する。

1. Python は取り込み済みの会話から、SQLite の台帳に処理済みとして記録されたセッション ID と原本の SHA-256 の組を除外する。原本のハッシュが変われば再び対象にする。
2. Haiku 5.5 が会話ごとに根拠を抽出する。Sonnet 5.5 が原本と既存記事を照合し、訂正や出典の追加などの修正案をまとめる。
3. Python が分割した原本の末尾の確認コード、引用箇所、記事の版、リンク先を検査し、レビュー用の差分を保存する。台帳への処理済みの記録は保存後に行う。失敗した会話は以後の回で 1 件ずつ別のワークフローで再試行する。

定期ジョブの出力は差分までとする。承認後の反映は `wiki_apply.py` を使い、承認した `plan_sha256` を指定する。Claude Code のワークフロー本体はファイルやシェルに直接アクセスできないため、入出力の準備、ハッシュ照合、台帳の更新は外側の Python が担当する。
[Claude Code の実行制約](https://code.claude.com/docs/en/workflows#behavior-and-limits)、[非対話実行の権限](https://code.claude.com/docs/en/workflows#approve-the-plan-before-it-runs)、[[wiki公開版の通常保存-2026-11-19]]

### 2026-11-21 の手動試行

Claude Code 2.1.325 で定期ジョブと同じ `--scheduled` の経路を手動で起動し、会話 2 件と関連記事 5 件を対象にした。Haiku は 2 回、Sonnet は 1 回完了し、[[図ごとの描画の隔離]] に出典を補う差分 1 件が `git apply --check` を通った。同じ会話を指定して再実行すると、2 件とも台帳で除外された。再試行と読み込み不足の検出を含む自動テスト 17 件も通った。
