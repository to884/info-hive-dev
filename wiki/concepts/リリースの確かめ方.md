# プラグインのリリースの確かめ方

`info-hive-wiki` と `info-hive-rag` のリリースを、完了したと言えるまでに確かめることの記録である。AGENTS.md の wiki の節は、リリースのコミットが main に入り、`vX.Y.Z` のタグを push し、GitHub リリースを作り、マーケットプレイスからの導入を確かめるまで、完了を報告しないと決めている。rag の節にはこの規則がないが、rag 0.5.1 でも同じ条件で確かめた。

## main に入れば届く

マーケットプレイス（`to884/info-hive-marketplace`）の項目には `version` を書かず、各プラグインの main を配る。`plugin.json` の `version` を上げたコミットが main に入った時点で、利用者に更新が届く。タグとリリースは、そのあとに作る記録である。AGENTS.md は、マージの前に版を決めると決めている。

CHANGELOG の日付の入れ方は、2 つのプラグインで違った。wiki 0.11.1 は、マージの前にその日の日付を入れた。rag 0.5.1 は、日付を「未定」としたままマージし、あとの #8 で入れた。rag 0.5.3 は、PR の中で日付を入れるコミット（76f00e6）を足してからマージした。wiki 0.12.0 は、PR を出す前に、マージする日（日本時間の 2026-11-13）に直した。GitHub の時刻は UTC なので、マージやリリースの記録の日付が 1 日前になることがある（[[browseのスコープ表示とリリース-wiki-0.12.0]]）。rag の CHANGELOG は、日付を「その版が main に入り、マーケットプレイスから配られ始めた日」と決めている。

## タグとリリースの形

| | wiki | rag |
| --- | --- | --- |
| タグ | CONTRIBUTING.md は注釈付き（`git tag -a vX.Y.Z -m "vX.Y.Z: <要約>"`）と決めている。実際は v0.1.0〜v0.5.0 が注釈付き、v0.6.0〜v0.11.0 が注釈なし、v0.11.1 から v0.16.0 までが注釈付き | 注釈なし（v0.4.0、v0.5.0〜v0.5.3） |
| リリースの題名 | `vX.Y.Z` | `vX.Y.Z` |
| リリースの本文 | CHANGELOG のその版の節 | CHANGELOG のその版の節と「更新のしかた」 |

> タグとリリースの形の表 補足: wiki の手順は `info-hive-wiki/CONTRIBUTING.md` の「リリースの手順」にある。`info-hive-rag` の Markdown には手順の文書が見当たらないので、前のリリースにそろえる。

## マーケットプレイスからの導入を確かめる

手元の導入を変えないように、使い捨ての設定フォルダーで確かめる。

```bash
export CLAUDE_CONFIG_DIR=<使い捨てのフォルダー>
claude plugin marketplace add to884/info-hive-marketplace
claude plugin install rag@info-hive      # 依存の wiki@info-hive も入る
claude plugin list                       # 版を確かめる
```

- 入ったファイルは `<フォルダー>/plugins/cache/info-hive/<プラグイン>/<版>/` にある。版だけでなく、変更した箇所がその中にあることも確かめる。
- 変更した箇所は、コードの 1 行に収まる部分の文字列で探す。rag 0.5.3 では、新しいエラーメッセージを丸ごと探して 0 件になった。f 文字列が 2 行に分かれていたためである（[[pdfのヘッダーの書き方の修正-rag-0.5.2-0.5.3]]）。0 件のときは、すぐに「入っていない」と決めず、main のコードでの書き方と見比べる。
- 文字列で探すかわりに、変更したファイルの SHA-256 を、タグの中身（`git show vX.Y.Z:<パス>`）と比べてもよい。wiki 0.12.0 では、変更した 4 つのファイルがすべて一致した。あわせて、入ったスクリプトを使い捨ての wiki で 1 回動かし、変更が働くことを確かめた（`build --scope project` の索引に表示が出た）。
- 確かめたら、使い捨てのフォルダーを消す。
- 版ごとの確かめの記録（確かめた範囲と見つけたこと）は、[[リリースごとの導入の確かめの記録]] にある。Codex は一時的な `CODEX_HOME` で公開カタログから導入し、配布先を `source: "url"` と Git の HTTPS URL で指定する（[[codexのプラグインと会話の取り込みのリリース-wiki-0.29.0]]）。
- 次の版が main に入ったあとでタグを打った版は、マーケットプレイスから入れられない。main の版が入るためである。wiki 0.15.0 は、0.16.0 が main に入ってからタグを打った。入った 0.16.0 で、v0.14.1 から v0.15.0 までに変わったファイルのうち 0.16.0 で変わっていない 4 つの SHA-256 がタグの中身と一致することを確かめ、そこまでを確かめたと報告した（[[追い越された版のリリース-wiki-0.15.0]]）。続けて出した 0.16.0 は、変わった 9 のファイルがすべてタグの中身と一致した（[[セッションの取り込みのリリース-wiki-0.16.0]]）。

## リポジトリをまたぐマージの順番

1 つの修正が rag、wiki、親リポジトリにまたがるときは、次の順にする（[[取り込み手順の追従とリリース-wiki-0.11.1]]）。

1. 振る舞いを変えるプラグイン（rag）
2. それを案内する文書のプラグイン（wiki）。先に入れると、文書が先走る
3. 親リポジトリのサブモジュールの参照。PR を作るときは子の PR の head を指し、子のマージのあとで、子の main のマージコミットに付け替えてからマージする

親の to884/info-hive-dev#84（rag 0.5.3）も、子の main のマージコミットの手前（CHANGELOG の日付を入れる前のコミット）を指したまま出されていた。親の PR をマージする前に、参照先が子の main の先頭と同じかを確かめる（`gh api repos/<親>/contents/<サブモジュール>?ref=<head>` の `sha`）。

子の main に入れた時点で利用者に届くので、子をマージする前に、親の PR の CI も通っていることを確かめる。閲覧の Linux だけの試験とブラウザの試験は、親の CI（`wiki-browse.yml`）でしか動かない。wiki 0.12.0 では、親の PR が子の PR の head を指した状態で両方の CI が通るのを待ってから子をマージし、付け替えたあとの親の CI が通ってから親をマージした（[[browseのスコープ表示とリリース-wiki-0.12.0]]）。wiki 0.18.0 では、付け替えたあとの親の CI を待たずに親をマージした。子の main に PR の head から新しいコミットがなく、参照先の中身が CI を通した head と同じ（差分が空）だったためである（[[browseの探しやすさとFluent2のリリース-wiki-0.18.0]]）。

wiki 0.12.1 では、作者の指示で、親の CI の 2 つのジョブ（mcp と browse の Windows）が走っているうちに子をマージした。親の CI はあとで通った。もし失敗していたら、子をマージした時点で届いた変更を、届いたあとで直すことになっていた。指示を受けたときは、親の CI が残っていることを伝える（[[検索の結果のtagsとsourcesの修正-wiki-0.12.1]]）。wiki 0.12.2 では、作者の「CI が通ったら子をマージして」という指示で、親の CI の 9 つと子の CI の 4 つが通ったのを確かめてから子をマージした。付け替えたあとの親の CI が通り、参照先が子の main の先頭と同じことを確かめてから、親をマージした（[[titleが値なしや配列のときの修正-wiki-0.12.2]]）。wiki 0.13.0 も同じ順にした。付け替えたあとの親の CI は、作者の「CI のあとで続けて」を受けて、実行の終わりを 1 回だけ待ってからマージした（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。wiki 0.14.0 も、作者の「CI 後に進めて」を受けて、子の CI と子の PR の先頭を指す親の CI の終わりを 1 回だけ待ってから子をマージし、付け替えたあとの親の CI も同じに待ってから親をマージした。Auto-fix は CI の失敗だけを知らせ、通ったことは知らせないので、「CI のあとで」の指示には、この 1 回の待ちで応える（[[helpの個別のヘルプとリリース-wiki-0.14.0]]）。wiki 0.14.1 も、作者の「0.14.1 で進めて」を受けて、同じ順にした。

別の PR が子の main を進め、親の main がその子のマージコミットを指すと、親の PR がサブモジュールの参照で競合する。wiki 0.14.1 では、子の PR のブランチに子の main を取り込み（force push はしない）、親の参照をそのマージコミットに変えた。どちらの変更も含むので、親の競合はそれで解ける。子の CHANGELOG も競合したので、`[Unreleased]` には自分の項目だけを残した（[[typeとupdatedの配列の扱いの修正-wiki-0.14.1]]）。

親のリポジトリ（to884/info-hive-dev）は、GitHub の自動マージを許していない（`Auto merge is not allowed for this repository`）。CI が通るのを待ってマージするときは、通ったのを確かめてから手でマージする。設定は変えていない。

子のリポジトリ（to884/info-hive-wiki）は自動マージを許すが、ブランチの保護で CI を必須にしていない。このため `gh pr merge --auto` は、CI が走っていても待たずにその場でマージする。wiki 0.19.0 では、作者の「自動マージを入れる」の指示でこれを実行し、`python-windows (3.12)` が走っているうちにマージされた（あとで通った）。CI のあとでマージする指示には、自動マージに頼らず、CI の終わりを 1 回待ってから手でマージする（[[browseの記事のページのFluent2のリリース-wiki-0.19.0]]）。

付け替えたあとの親の CI が始まらないときは、まず PR の競合を確かめる。GitHub は、base と競合している PR では `pull_request` のワークフローを走らせない。wiki 0.19.3 では、付け替えのあいだに別の PR が main に入って `wiki/log.md` が競合し、付け替えたあとの CI が 1 件も始まらなかった。main を取り込んで競合を解き、そのあとの CI を待ってからマージした（[[browseを5つのブラウザで確かめた記録とリリース-wiki-0.19.3]]）。

## マージの承認

マージを頼むのが別のセッションの伝言だと、マージするセッションの auto mode の判定が、`gh pr merge` を「レビューなしのマージ」として止めることがある。wiki 0.13.0 では、作者の承認が別のセッションを通して届き、マージが止められた。判定を回避せずに止め、作者がそのセッションで許可してから進めた（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。別のセッションにマージを任せるときは、作者がそのセッションで直接許可する必要があるかもしれないと考えておく。

## 版を決めるとき

- 版を決める前に、`origin/main` の `plugin.json` とタグを取り直す。手元のサブモジュールの参照は、親の main が指す古い版のことがある。0.11.1 では、親の main は 0.10.1 を指していたが、wiki の main はすでに 0.11.0 だった。
- 並行するセッションが同じプラグインの版を準備していることがある。気づいたら、使った版を相手に伝え、どちらを先に main に入れるかは作者に確かめる。wiki 0.13.0 の PR を出したあとで、別のセッションが 0.12.2 を main に入れた。PR のブランチに `origin/main` をマージし（force push はしない）、版は 0.13.0 のまま、CHANGELOG の 0.13.0 の節を 0.12.2 の上に置いた。出す順を作者に聞くと 0.12.2 が先で、0.13.0 のセッションが v0.12.2 のタグとリリースを作った（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。0.12.2 のセッションとは系列が違い、直接は伝えられなかったので、作ったことを作者に伝えた。
- main の `plugin.json` が上がっていてタグのない版に、あとから変更を足すことがある。wiki 0.14.0 では、作者の決定で、PR #53 が main に入れた 0.14.0 に `/wiki:help` の個別のヘルプを足した。版の番号が変わらないので、その間に main から 0.14.0 を入れた利用者には届かない。タグを打つまでに main に入ったほかの PR の `[Unreleased]` の項目（#54 の修正）は、タグにそのコードが入るので、作者に確かめてからその版の節に移した。まだオープンの PR（#55）は待たなかった（[[helpの個別のヘルプとリリース-wiki-0.14.0]]）。
- 版を上げた PR をマージしたら、タグとリリースまで続けて行う。wiki 0.15.0 は、タグもリリースもないまま次の PR（0.16.0）がマージされ、追い越された。あとから `5adb069`（0.15.0 のマージコミット）にタグを付けてリリースしたが、マーケットプレイスからの導入は確かめられなかった（[[追い越された版のリリース-wiki-0.15.0]]）。
- wiki 0.19.1 は、main に入ったまま、タグもリリースもないうちに、0.19.2 の PR のマージを頼まれた。先に 0.19.2 を入れると、0.19.1 を出すセッションが main の先頭に v0.19.1 を付けるおそれがあった。作者の決定で、0.19.2 のセッションが v0.19.1 を 0.19.1 のマージコミット（`6d712a8`）に付けてリリースしてから、0.19.2 をマージした（[[captureの記録の改行の直しとリリース-wiki-0.19.2]]）。タグを付けるときは、`main` ではなくその版のマージコミットを指定する。
- main に入った版の中身を、同じ番号のまま変えても、その版をすでに入れた利用者には更新として届かない。wiki 0.17.0 の作業で、構造の直しを 0.15.0 に含める案を、作者がこの理由で退けた（0.15.0 は main に入った時点で届いていた）。あとから入る変更は、新しい番号にする（[[browseの構造の直しとリリース-wiki-0.17.0]]）。
- 版を決められないうちは、変更を CHANGELOG の `[Unreleased]` に書き、`plugin.json` を上げずに PR を出す。wiki 0.14.1 の PR を出したとき、main の `plugin.json` は 0.14.0 でタグがなく、`[Unreleased]` に別のセッションの修正（#54）があった。この PR で番号を決めて上げると、#54 も一緒に出荷することになった。Codex の自動レビューが「マージ前に版を上げる」と指摘したが、番号が決まるまで直さないと返信して待った。v0.14.0 にタグが付き、`[Unreleased]` にこの修正だけが残ってから、作者が 0.14.1 に決めた（[[typeとupdatedの配列の扱いの修正-wiki-0.14.1]]）。
- タグとリリースを作る直前に、`git ls-remote --tags origin` と `gh release list` を取り直す。rag v0.5.3 では、2 つのセッションが同じリリースを作ろうとした。あとのセッションがこの確かめで作成済みだと気づき、リリースは 1 つで済んだ（[[pdfのヘッダーの書き方の修正-rag-0.5.2-0.5.3]]）。作ったら、関わっているセッションにすぐ伝える。wiki v0.12.2 でも、作る直前の確かめで、タグとリリースが作者のアカウントですでに作られていると分かった（0.13.0 のセッションが、作者の指示で先に作っていた）。作り直さず、タグが注釈付きで子の main のマージコミットを指すこと、リリースの本文が CHANGELOG のその版の節と同じことを確かめてから、導入の確かめに進んだ（[[titleが値なしや配列のときの修正-wiki-0.12.2]]）。

- オープンの PR が名乗っている版も、使われているとみなす。wiki 0.23.0 は、オープンの to884/info-hive-wiki#71 が 0.22.0 を名乗っていたので 0.23.0 にした（[[youtubeの字幕の取り込みの実装とリリース-wiki-0.23.0]]）。

- wiki 0.31.0 では、0.30.0 を予定した PR の作業中に、別の作業が 0.30.0 を公開した。その main を取り込み、両ホストの manifest と CHANGELOG を 0.31.0 に変更し、マージ直前にもタグと main の版を確認した（[[wikiの記事リンクの拒否とリリース-wiki-0.31.0]]）。

## 報告の前に状態を取り直す

PR のマージやリリースの状態は、ほかのセッションや作者が変える。報告に書く直前に、`gh pr view` などで取り直す。0.11.1 のときは、確かめた後にマージされた PR を「まだマージされていない」と報告した。

## CI

- `info-hive-wiki` のスクリプトを変えたら、`info-hive-wiki` 自身の CI の手順も手元で流す（[[グラフのlintの期待値]]）。
- 親の `browse (windows-latest)` は、ランナーが遅いと、静的版の試験の `file://` の `page.goto` が 30 秒でタイムアウトすることがある。再実行で通った（観測は 1 回）。変更がブラウザの試験に関わらないことを確かめてから、失敗したジョブだけを再実行する。
- wiki 0.18.1 の親の PR（to884/info-hive-dev#115。browse のコードを変えていない）では、`browse (windows-latest, 3.12)` が 2 回続けて、別の試験で落ちた。1 回目は、起動中の `stop` が `server.json` を開けない `PermissionError`（Windows の共有の違反と見られる。直しは別の作業にした）、再実行は、サーバーの版のブラウザの試験の `ERR_CONNECTION_FAILED` だった（[[rawの段の取り直しとW8の出力のリリース-wiki-0.18.1]]）。
