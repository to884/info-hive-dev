# プラグインのリリースの確かめ方

`info-hive-wiki` と `info-hive-rag` のリリースを、完了したと言えるまでに確かめることの記録である。AGENTS.md の wiki の節は、リリースのコミットが main に入り、`vX.Y.Z` のタグを push し、GitHub リリースを作り、マーケットプレイスからの導入を確かめるまで、完了を報告しないと決めている。rag の節にはこの規則がないが、rag 0.5.1 でも同じ条件で確かめた。

## main に入れば届く

マーケットプレイス（`to884/info-hive-marketplace`）の項目には `version` を書かず、各プラグインの main を配る。`plugin.json` の `version` を上げたコミットが main に入った時点で、利用者に更新が届く。タグとリリースは、そのあとに作る記録である。AGENTS.md は、マージの前に版を決めると決めている。

CHANGELOG の日付の入れ方は、2 つのプラグインで違った。wiki 0.11.1 は、マージの前にその日の日付を入れた。rag 0.5.1 は、日付を「未定」としたままマージし、あとの #8 で入れた。rag 0.5.3 は、PR の中で日付を入れるコミット（76f00e6）を足してからマージした。wiki 0.12.0 は、PR を出す前に、マージする日（日本時間の 2026-11-13）に直した。GitHub の時刻は UTC なので、マージやリリースの記録の日付が 1 日前になることがある（[[browseのスコープ表示とリリース-wiki-0.12.0]]）。rag の CHANGELOG は、日付を「その版が main に入り、マーケットプレイスから配られ始めた日」と決めている。

## タグとリリースの形

| | wiki | rag |
| --- | --- | --- |
| タグ | CONTRIBUTING.md は注釈付き（`git tag -a vX.Y.Z -m "vX.Y.Z: <要約>"`）と決めている。実際は v0.1.0〜v0.5.0 が注釈付き、v0.6.0〜v0.11.0 が注釈なし、v0.11.1 から v0.13.0 までが注釈付き | 注釈なし（v0.4.0、v0.5.0〜v0.5.3） |
| リリースの題名 | `vX.Y.Z` | `vX.Y.Z` |
| リリースの本文 | CHANGELOG のその版の節 | CHANGELOG のその版の節と「更新のしかた」 |

> タグとリリースの形の表 補足: wiki の手順は `info-hive-wiki/CONTRIBUTING.md` の「リリースの手順」にある。`info-hive-rag` の Markdown には手順の文書が見当たらないので、前のリリースにそろえる。

## マーケットプレイスからの導入を確かめる

手元の導入を変えないように、使い捨ての設定フォルダーで確かめる。

```bash
export CLAUDE_CONFIG_DIR=<使い捨てのフォルダー>
claude plugin marketplace add to884/info-hive-marketplace
claude plugin install rag@info-hive      # 依存の wiki@info-hive も入る
claude plugin list                       # 版を確かめる
```

- 入ったファイルは `<フォルダー>/plugins/cache/info-hive/<プラグイン>/<版>/` にある。版だけでなく、変更した箇所がその中にあることも確かめる。
- 変更した箇所は、コードの 1 行に収まる部分の文字列で探す。rag 0.5.3 では、新しいエラーメッセージを丸ごと探して 0 件になった。f 文字列が 2 行に分かれていたためである（[[pdfのヘッダーの書き方の修正-rag-0.5.2-0.5.3]]）。0 件のときは、すぐに「入っていない」と決めず、main のコードでの書き方と見比べる。
- 文字列で探すかわりに、変更したファイルの SHA-256 を、タグの中身（`git show vX.Y.Z:<パス>`）と比べてもよい。wiki 0.12.0 では、変更した 4 つのファイルがすべて一致した。あわせて、入ったスクリプトを使い捨ての wiki で 1 回動かし、変更が働くことを確かめた（`build --scope project` の索引に表示が出た）。
- 確かめたら、使い捨てのフォルダーを消す。
- 0.9.2 でも、空の設定ディレクトリで同じように確かめた（[[グラフの抽出の修正-0.9.2]]）。

## リポジトリをまたぐマージの順番

1 つの修正が rag、wiki、親リポジトリにまたがるときは、次の順にする（[[取り込み手順の追従とリリース-wiki-0.11.1]]）。

1. 振る舞いを変えるプラグイン（rag）
2. それを案内する文書のプラグイン（wiki）。先に入れると、文書が先走る
3. 親リポジトリのサブモジュールの参照。PR を作るときは子の PR の head を指し、子のマージのあとで、子の main のマージコミットに付け替えてからマージする

親の to884/info-hive-dev#84（rag 0.5.3）も、子の main のマージコミットの手前（CHANGELOG の日付を入れる前のコミット）を指したまま出されていた。親の PR をマージする前に、参照先が子の main の先頭と同じかを確かめる（`gh api repos/<親>/contents/<サブモジュール>?ref=<head>` の `sha`）。

子の main に入れた時点で利用者に届くので、子をマージする前に、親の PR の CI も通っていることを確かめる。閲覧の Linux だけの試験とブラウザの試験は、親の CI（`wiki-browse.yml`）でしか動かない。wiki 0.12.0 では、親の PR が子の PR の head を指した状態で両方の CI が通るのを待ってから子をマージし、付け替えたあとの親の CI が通ってから親をマージした（[[browseのスコープ表示とリリース-wiki-0.12.0]]）。

wiki 0.12.1 では、作者の指示で、親の CI の 2 つのジョブ（mcp と browse の Windows）が走っているうちに子をマージした。親の CI はあとで通った。もし失敗していたら、子をマージした時点で届いた変更を、届いたあとで直すことになっていた。指示を受けたときは、親の CI が残っていることを伝える（[[検索の結果のtagsとsourcesの修正-wiki-0.12.1]]）。wiki 0.12.2 では、作者の「CI が通ったら子をマージして」という指示で、親の CI の 9 つと子の CI の 4 つが通ったのを確かめてから子をマージした。付け替えたあとの親の CI が通り、参照先が子の main の先頭と同じことを確かめてから、親をマージした（[[titleが値なしや配列のときの修正-wiki-0.12.2]]）。wiki 0.13.0 も同じ順にした。付け替えたあとの親の CI は、作者の「CI のあとで続けて」を受けて、実行の終わりを 1 回だけ待ってからマージした（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。

親のリポジトリ（to884/info-hive-dev）は、GitHub の自動マージを許していない（`Auto merge is not allowed for this repository`）。CI が通るのを待ってマージするときは、通ったのを確かめてから手でマージする。設定は変えていない。

## マージの承認

マージを頼むのが別のセッションの伝言だと、マージするセッションの auto mode の判定が、`gh pr merge` を「レビューなしのマージ」として止めることがある。wiki 0.13.0 では、作者の承認が別のセッションを通して届き、マージが止められた。判定を回避せずに止め、作者がそのセッションで許可してから進めた（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。別のセッションにマージを任せるときは、作者がそのセッションで直接許可する必要があるかもしれないと考えておく。

## 版を決めるとき

- 版を決める前に、`origin/main` の `plugin.json` とタグを取り直す。手元のサブモジュールの参照は、親の main が指す古い版のことがある。0.11.1 では、親の main は 0.10.1 を指していたが、wiki の main はすでに 0.11.0 だった。
- 並行するセッションが同じプラグインの版を準備していることがある。気づいたら、使った版を相手に伝え、どちらを先に main に入れるかは作者に確かめる。wiki 0.13.0 の PR を出したあとで、別のセッションが 0.12.2 を main に入れた。PR のブランチに `origin/main` をマージし（force push はしない）、版は 0.13.0 のまま、CHANGELOG の 0.13.0 の節を 0.12.2 の上に置いた。出す順を作者に聞くと 0.12.2 が先で、0.13.0 のセッションが v0.12.2 のタグとリリースを作った（[[初期化していないディレクトリの扱い-wiki-0.13.0]]）。0.12.2 のセッションとは系列が違い、直接は伝えられなかったので、作ったことを作者に伝えた。
- タグとリリースを作る直前に、`git ls-remote --tags origin` と `gh release list` を取り直す。rag v0.5.3 では、2 つのセッションが同じリリースを作ろうとした。あとのセッションがこの確かめで作成済みだと気づき、リリースは 1 つで済んだ（[[pdfのヘッダーの書き方の修正-rag-0.5.2-0.5.3]]）。作ったら、関わっているセッションにすぐ伝える。wiki v0.12.2 でも、作る直前の確かめで、タグとリリースが作者のアカウントですでに作られていると分かった（0.13.0 のセッションが、作者の指示で先に作っていた）。作り直さず、タグが注釈付きで子の main のマージコミットを指すこと、リリースの本文が CHANGELOG のその版の節と同じことを確かめてから、導入の確かめに進んだ（[[titleが値なしや配列のときの修正-wiki-0.12.2]]）。

## 報告の前に状態を取り直す

PR のマージやリリースの状態は、ほかのセッションや作者が変える。報告に書く直前に、`gh pr view` などで取り直す。0.11.1 のときは、確かめた後にマージされた PR を「まだマージされていない」と報告した。

## CI

- `info-hive-wiki` のスクリプトを変えたら、`info-hive-wiki` 自身の CI の手順も手元で流す（[[グラフのlintの期待値]]）。
- 親の `browse (windows-latest)` は、ランナーが遅いと、静的版の試験の `file://` の `page.goto` が 30 秒でタイムアウトすることがある。再実行で通った（観測は 1 回）。変更がブラウザの試験に関わらないことを確かめてから、失敗したジョブだけを再実行する。
