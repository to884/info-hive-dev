# ドリーミングを info-hive-wiki に適用できるか

ドリーミング（dreaming）の記事 [[components-of-agent-memory]] と cookbook [[managed-agents-cma-dreaming-with-a-dynamic-workflow]] を、info-hive-wiki の今の仕組みと照らした、2026-11-19 のクエリの回答である。

## 結論

考え方は取り入れられるが、cookbook の作りをそのまま持ち込むのは勧めない。

- 取り入れられること: 複数の会話を、使っていない時間にまとめて見直し、wiki の直しを提案させる。重複の統合、リンクの付け替え、索引の仕上げは、書き手のいない最後の段で行う。
- 合わないこと: レビューなしで wiki をその場で書き換えること。ロックを持たずに、並行して書くこと。

## 記事の要点

- ドリーミングは、セッションの外の時間にトランスクリプトを見直してメモリを整理することである。ノートの誤りを直す、wiki を組み立てる、最上位の層を小さく保つ、セッションをまたぐパターンを見つける（[[エージェントのメモリの階層]]）。
- cookbook は 3 種のエージェントで組む。リードはワークフローを書くだけで、トランスクリプトを読まない。アナライザーはトランスクリプト 1 件に 1 体で、並行して書く。オーガナイザーは最後に 1 回だけ動き、重複を統合して `_index.md` を仕上げる。
- cookbook は、既定でレビューがなく、悪いトランスクリプトが翌朝にはエージェントに届きうると書いている。Managed Agents の Dreams は新しいストアに書き出し、cookbook は同じストアをその場で更新する。
- wiki が効くのは、検索と組み合わせて、文書をまたぐ問いに答えるときである。抽象化しないまま、元の文書の 1.77 倍に膨らんだ wiki の例もある（[[components-of-agent-memory]]）。

## 照らし合わせ

```mermaid
flowchart LR
  T["会話の raw（承認済み）"] --> A["アナライザー（会話ごと、読むだけ）"]
  A --> P["作業用のフォルダーの直しの提案"]
  P --> O["オーガナイザー（1 回だけ、統合とリンク）"]
  O --> U["ユーザーの承認"]
  U --> W["wiki_apply.py（唯一の書き手）"]
  W --> K["wiki のページ、索引、ログ"]
```

> Claude Opus 5.5 補足: 図は、上の表の見立てを 1 つの流れにした案である。どのソースにも書かれておらず、試していない。`wiki_apply.py` は実装される前である。

Managed Agents に固有の部分（メモリストアのマウント、500 ファイルの上限、マウントの `instructions` の 4,096 文字、cron で動かすこと）と費用の数値は、そのままは当てはまらない。

## wiki が扱っていないこと

- info-hive のプラグインで、会話の見直しを定期に動かす方法。
- 手元の会話で見直したときの費用。

Claude Code か Codex で cron のように定期にエージェントを動かす手順の公式の文書を取り込むと補える。

## 回答のときの確信度

2026-11-19 の判定で、回答全体は「中」だった。記事の内容は、ソースの要約ページで確かめた（高）。適用できるかの見立ては、前提にない判断を加えたものである（中）。書く段の設計と 0.29.0 のページは、索引を埋め込んでいる途中の検索で見つけた（中）。wiki が変われば判定も変わるので、後のクエリではこの値を引き継がない。

上げる方法:

- 読み戻しとロックのどちらが確かかを、同時の書き込みの試験で確かめ、`/wiki:learn` で記録する。
- 小さな会話の束で、提案だけを出すドリームを試し、その結果を記録する。
